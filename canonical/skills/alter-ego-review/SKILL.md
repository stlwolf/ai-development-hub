# alter-ego-review — owner の観点で構造から見るレビュー

## この skill が埋めるもの

人がレビューで構造の問題を見逃す原因は二つある。

一つは、前提を確かめていないことである。「単位は分かれているものだ」と思っていると、実際に分かれているかを見ない。コードのファイルは読んでいても、どう入ってどう依存しているかは目に入らない。

もう一つは、読解の深さである。その言語やフレームワークを毎回書いているわけではないと、細部（二重定義、埋め込まれた既定値、境界を跨ぐ依存）を読み切れない。一般的なコーディング原則として絶対に見るべき点であっても、読めなければ拾えない。

この skill は、この二つを agent が肩代わりする。前者には「判断を入れない構造の要約」を冒頭に置くことで、後者には差分を端から端まで読んで一般原則の違反を拾うことで応える。

同時に、owner が本当に見ているのは「原則に合っているか」ではなく「その PR の文脈で違和感があるか」である。値が埋まっていること自体は良くも悪くもない。同じ PR の文書が「別の環境は後で」「別のアカウントへ移す」と予告しているなら、その値は変わる値であり、埋めれば移すときにコードを触ることになる。違和感の根拠は PR 自身の中にあることが多い。この skill はその突き合わせを機械的に行う。

## 手順

### 1. 材料を集める

差分だけでは足りない。次を読む。

- 差分の全体（`gh pr diff` など）。大きくても分割せず全部読む。読み切ることがこの skill の存在理由である
- PR 本文と、PR に同梱された文書（kickoff、plan、decision、README の変更）
- PR 本文と文書からリンクされている issue の本文

読みながら「予告されている変更」を拾い出す。次のような記述がそれに当たる。

- 別の環境（stg の次に prd など）を後で出す
- 別のアカウント、別のリージョン、別のテナントへ移す
- 「後追い」「#N で対応」「別 issue」「TODO」「いったん」「今は」
- 「stg だから」「検証用だから」「移行期間中は」のように、条件付きで許容している記述

これが手順 4 の突き合わせ相手になる。予告が一つも無い PR は少ない。

### 2. 構造の要約を書く（判断を入れない）

差分が作る、または変える構造を、良し悪しを一切書かずに列挙する。owner はこれを読んで、自分の前提と実態のずれを自分で見つける。

- 単位の数と名前。stack、module、service、package など、その系で「まとめてデプロイされる」または「まとめて変更される」単位
- 各単位に入っている workload や責務。web、worker、cron、migration、監視、鍵、ログなど
- 変更の単位。ある部分を変えたとき、何が一緒に置き換わるか。単位の中で独立して動くものが複数あるなら、それを明記する
- 環境固有の値の所在。どの値がどこに置かれているか。引数として渡されるものと、コードの中に既定値として置かれているものを分ける
- 境界を跨ぐ依存。export と import、共有されるリソース、参照だけしている既存リソース
- 宣言の外で作られた構成要素。この変更の作業で作られたが、コードや IaC には無いもの。手で足した許可ルール、データベース側の権限付与、手で投入した値、手で push した成果物。文書や作業記録から拾う

この節は、指摘が一つも無い PR でも書く。構造が見えること自体に価値がある。

### 3. 前提と実態を突き合わせる

同梱文書や PR 本文が述べている構造（「foundation と app の 2 層に分ける」など）と、手順 2 の要約を並べる。文書の言う分け方と、実態の分け方が違えば、それが最初の質問になる。文書の分け方と実態が一致していても、その分け方が変更の単位と一致していなければ、それも質問になる（文書は 2 層と言い、実態も 2 層だが、片方の層に独立した workload が 5 つ入っている、など）。

### 4. 各判断を予告と突き合わせる

差分の中の判断を一つずつ、手順 1 で拾った予告に照らす。判断とは次のようなものである。

- 埋め込まれた値（ID、ARN、endpoint、名前、アカウント）
- 環境を固定する guard（`env !== 'stg'` で落とす、など）
- 一つの単位への同居
- 恒久的に残るタグや名前に、一時的な文脈（移行プロジェクト名など）を使っていること
- deploy や運用の手順（手打ちのコマンド、承認の省略、既定値に頼る引数）

問いは一つである。「予告された変更が起きたとき、この判断は変わるか」。

- 変わるなら違和感の候補にする。理由を「#N の変更でこの値は変わる。今ここに置くと、そのときコードを触ることになる」の形で書く
- 変わらない、一箇所でしか使わない、既存リソースの実名をそのまま参照しているだけ、なら挙げない。埋まっていること自体は問題ではない
- 「変わらない」の根拠が「そのときはこの単位ごと差し替える予定だから」であるときは、見送る前に一度問う。差し替えるコストと、今から値を注入する形にしておくコストのどちらが安いか。差し替えの予定が追跡された issue になっていないなら、その予定自体が後で変わりうる。この場合は見送りではなく質問にする
- 判断できないなら質問にする

これが、一般原則を機械的に全部挙げることと、owner の違和感との違いである。

### 5. 一般原則を全部読んで拾う

手順 4 とは別に、差分全体を一般原則で走査する。ここは agent の読解力がそのまま効く場所であり、人が読めない深さまで読む。

- 責務の分離。一つの単位に、独立して変わるものが同居していないか
- 二重定義。同じ値や同じ知識が二箇所以上にないか。片方だけ直すと壊れる形になっていないか
- 注入と埋め込み。環境で変わる値が、渡される形ではなく、コードの中の既定値になっていないか。既定値があると「渡し忘れても動く」ので、別の環境で黙って前の値が使われる
- fail-open な既定値。引数やコンテキストのキーを打ち間違えたとき、エラーになるか、既定値で通ってしまうか
- 手順の固定。deploy や移行の手順が、手で打つコマンドのままか、入口が固定されているか。実行先の確認（アカウント、環境）が手順に組み込まれているか
- 同じ PR の文書どうしの矛盾。同じ操作を別の値で書いている箇所がないか（同じ環境を別のプロファイルで出す、など）

ここまでがコードの原則である。運用者がいるシステムには、それとは別に運用の原則がある。誰かがこれを動かし続け、別の人が手順を再現し、失敗したら戻す。次を同じ深さで見る。

- 単独で出せる単位になっているか。独立して動くものを一つずつ出せるか、それとも全部まとめてしか出せないか
- 戻す経路があるか。出したものを前の状態に戻す手順が、書かれているか、試されているか
- 変更の影響範囲が変更対象に閉じているか。一箇所を直したとき、関係ないものが一緒に置き換わらないか
- 手順を別の人が再現できるか。実行した人の手元にしか無い値や判断が、手順に紛れていないか
- 記録の欠落。この変更で作られたもののうち、コードにも文書にも載っていないものがないか（手順 2 で拾った「宣言の外で作られた構成要素」が、どこかで追跡されているか）

運用の原則から出す項目は、「こういう場面で困る」というリスクの話として出さない。「この変更で作られたもののうち、ここが記録に無い」「この手順のここが再現できない」という、欠けているものの話として出す。owner は危険の見積もりには同意しないことがあるが、欠落には同意する。あわせて、それが起きる確実さを一語で添える。確実（手順どおりに進めば必ず起きる）、条件付き（何が起きたら起きるかを書く）、低頻度（起きうるが頻度は低い）。

拾ったものは「一般」ラベルを付ける。ただし出す前に手順 4 の突き合わせを通す。一般原則に反していても、その PR の文脈で変わらない値なら「見送った候補」に回す。

### 6. 書かれている理由を扱う

差分やコメントに理由が書かれている判断は多い。理由は受け取る。ただし、理由があることと、その理由がずっと成り立つことは別である。

- その理由はいつ偽になるか。手順 1 の予告の中に、偽になる時点が書かれていることが多い（「prd は #N」「移設は #M」）。書かれていれば、それを接続して示す
- 理由が安全側の形（fail-fast にした、既定の挙動を変えないようにした、念のため検査を足した）をしているときは、置き場所ではなく要否を問う。安全側の判断は反証されにくく、レビューは「どこに置くか」を問いがちで「要るのか」を問いにくい
- 偽になったとき誰が気づくかの仕組み（追跡している issue、期限、外す手順）があるかを見る。無ければ質問にする

### 7. 出力を組む

下の出力形式に従う。組むときに二つのことをする。

- 項目どうしの影響を書く。ある項目を直すと別の項目が要らなくなることがある（既定値を無くして未指定なら落ちる形にすれば、環境を固定する guard は要らない）。一つずつ別々に出すと、owner は両方に答えることになる。「A を直せば B は不要になる」と一文で繋ぐ
- 直し方として検査や guard を足す案を出すときは、予告された変更がその検査を外すことになるかを見る。移設や別環境の予告があるとき、アカウントや環境を固定する検査は、そのときに外す対象になる。そうなら、検査を足す案ではなく、手順の側で閉じる案（入口を固定する、実行前に実行先を確認する）を先に置く。どちらを選ぶかは owner の判断なので、この種の直し方は「推測」ラベルにする

## 指摘と質問の線

- 指摘（こうすべき）にするのは、予告が追跡された issue や文書として確定していて、その変更でこの判断が確実に変わる場合。一般原則の違反で、文脈上も変わる値である場合
- 質問（説明を求める）にするのは、予告が曖昧な場合、理由が書かれていて有効期限だけが問題の場合、意図かどうかで評価が変わる場合、判断できない場合
- 迷ったら質問にする。指摘が外れると使われなくなるが、質問が外れても答えれば済む

## 根拠のラベル

各項目に一つ付ける。

- 一般。一般に認められた原則から言えること。責務の分離、二重定義、注入、fail-open、手順の固定など。agent が読み切って拾う側
- 推測。owner の判断や好みを推測して言っていること。「この線で分けるべきだ」「このタグは外すべきだ」のような、原則からは一意に決まらないもの

分ける理由は、校正の対象が推測側だけだからである。一般側が外れたら適用の失敗であり、owner の観点を教える話ではない。推測側は owner がまだ言葉にしていない判断そのものなので、外れたら記録し、次の版に反映する。

## 出力形式

```markdown
## 構造の要約
（判断を入れない。単位、各単位の中身、変更の単位、環境固有値の所在、境界を跨ぐ依存）

## 前提とのずれ
（文書が述べる構造と実態の差。無ければ「無し」）

## 指摘（こうすべき）
- `file:line` — [一般|推測] 内容。予告との接続: #N の変更でこの判断は変わる。（運用の項目なら）起きる確実さ: 確実 / 条件付き（条件）/ 低頻度。（他の項目と繋がるなら）A を直せば B は不要

## 質問（説明を求める）
- `file:line` — [一般|推測] 内容。何が分かれば判断できるか。（運用の項目なら）起きる確実さ: 確実 / 条件付き（条件）/ 低頻度

## 見送った候補
- `file:line` — 一般原則では挙がるが、文脈上変わらない値なので見送り（一行）

## 書かれている理由と、その有効期限
- `file:line` — 理由の要約。偽になる時点: #N / 不明。気づく仕組み: あり / なし

## 自己申告
質問 N 件 / 指摘 N 件。推測ラベル N 件（校正の対象）。読んだ範囲: 差分全体 / 同梱文書 M 本 / 関連 issue K 本
```

自己申告の「質問と指摘の比率」は、この分身が owner の判断をどれだけ引き受けられているかの目盛りである。質問が多いうちは判断を預けられていない。回を重ねて指摘が増え、推測ラベルの外れが減るのが望ましい方向である。

## この skill がしないこと

- 一般基準（クラウド事業者の推奨、フレームワークの公式ガイド）そのものとの照合。それを担う別のレビューがあるなら、その出力を入力として受け取る。この skill は、その基準が「組織固有の判断は依頼側が持つ」として空けた場所を埋める
- 決定。どの線で分けるか、いつ移すかは owner が決める。この skill は違和感と根拠を出すところまで
- 差分の外にあるコードのリファクタ提案。構造の要約に差分外の既存構造が要るときは読むが、提案の対象は差分の中に限る
- 記憶。前回のレビューで受け入れられた逸脱を、今回省かない。同じ入力には同じ結果を返す。受け入れの記録を持つのは呼び出し側である
- 人間向けの要約。上位 N 件の抜き出しや短縮版は作らない。この出力は正本であり、別の agent や統括がそのまま読む。人が読みやすい形は、この正本から別の表示の層が作る

## 校正

推測ラベルの項目は、owner の反応（的を射ている、外れている、正しいが気にしない）を集める材料である。反応をどこに記録するかは呼び出し側が決める。この skill の本文に owner の観点を書き足すのは、反応が溜まってからにする。最初から観点を書き下ろそうとすると、内省で書いた原則は機械的になって死ぬ。過去の実物への反応から書くほうが正確である。

## 例

環境固有の値と予告の接続の例。

- 差分: `const DEFAULT_CERT_ARN = 'arn:aws:acm:...:123456789012:certificate/...'` と、それを既定値に使う `props.certArn ?? DEFAULT_CERT_ARN`
- 同梱文書: 「prd は別 issue #N で対応」「アカウント移設は #M」
- 出力: `lib/app-stack.ts:92` — [一般] 証明書 ARN がスタック内の既定値になっている。予告との接続: #N（prd）と #M（移設）でこの値は変わる。既定値があると渡し忘れても stg の証明書で synth が通る。既定値を持たず、entrypoint から必須で渡し、無ければ synth で落ちる形にする

同居の例。

- 差分: 一つの stack に cluster、ALB、web service、worker service ×4、cron の task-def、migration の task-def、ログの鍵、alarm
- 同梱文書: 「foundation と app の 2 層に分ける」
- 構造の要約: 「app stack に、独立して変わる workload が 4 種（web、worker、cron、migration）入っている。worker の command を変えると web の task-def を含む changeset が走る」
- 前提とのずれ: 「文書は 2 層と述べ、実態も 2 層。ただし app 層の内側は分かれていない。文書はその内側の分け方に触れていない」
- 質問: [推測] web、worker、cron、migration を別々にデプロイする想定があるか。あるなら、今の一つの stack はその単位になっていない

見送りと、見送らない境目の例。

- 差分: 既存 VPC の ID を定数で参照している。同梱文書に「既存 VPC は参照のみ、変更しない」
- 予告: 移設時は VPC ごと作り直す（#M）
- 見送る場合: 移設の手順が issue として追跡されていて、この定数を含む単位ごと差し替えることが決まっているなら、この定数単独では変わらない。見送った候補に一行で記録する
- 見送らない場合: 差し替えの予定が文書の一文にしか無く、追跡されていないなら、質問にする。「移設時はこの単位ごと差し替える前提と読めるが、差し替えるコストと、今から ID を注入する形にしておくコストのどちらが安いか」。差し替え前提は後で注入に変わることがあり、そのときこの定数は直す対象になる

運用の原則の出し方の例。

- 作業記録: データベースの許可ルールに手で 1 本足し、データベース側で権限付与を手で実行した。どちらもコードには無い
- 出さない形: 「task 用の許可グループを作り直すと、古いほうが参照されていて消せなくなる危険がある」
- 出す形: [一般] この変更で作られたもののうち、許可ルール 1 本と権限付与が、コードにも文書にも記録されていない。起きる確実さ: 条件付き（許可グループを置換する変更が入ったとき）。どこで追跡するかが分かれば判断できる
