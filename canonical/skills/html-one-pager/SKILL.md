# html-one-pager — 人に見せて答えてもらうページ

人に判断や確認を求めるページは、作るたびに形がばらばらだと、読む人が毎回「どこを見て、どう答えるか」を探し直すことになる。このスキルは、ページの形・部品・札の言葉・答えの返し方を1つにそろえる。ページを作る側はデータ（JSON）だけを書き、同じフォルダの `build.py` が検証してから描く。

## 前提

- Python 3.9 以上。標準ライブラリだけを使い、追加のインストールは要らない。
- tmux と git は無くても動く。tmux の中で走らせると、送り元にペインの位置が自動で入る。
- このフォルダだけで動く。`build.py` は自分の置き場所から型・CSS・JS・用語集を読み、走らせたときの作業ディレクトリに頼らない。以下のコマンドの `<このスキルのフォルダ>` は、このスキルを読み込んだときに示されるフォルダのパスに置き換える。

## いつ使うか

- 人に判断を選んでもらう・確認してもらう・回答を集めるページを作るとき。
- いくつかの作業から届いた判断待ちを、1枚にまとめて見せるとき。
- レビュー（別のモデルのセカンドオピニオンを含む）の指摘と、それぞれを採ったかを一覧にして見せるとき。
- 見取り図や説明のような読み物のページを作るとき。中身は自由に書き、ヘッダーだけをこのスキルでそろえる。
- 回収した答えで、ページを「回答済み」にして出し直すとき。

使わないのは、リポジトリに入れる文書（README など）や、ページを伴わない会話の返答である。

## 隣の指示との順序

claude.ai の artifact に公開するときは、Artifact の道具の説明と組み込みの `artifact-design` も読み込まれる。そのときの分担は次のとおりである。

- ページの形・部品・札の言葉・色と文字はこのスキルが決める。`artifact-design` が言う「すでにある設計の決まり」にあたるので、新しい見た目は作らない。
- page contract（断片で書く・`<title>` を先頭に置く・色のトークンと暗い表示・外部の読み込みは Google Fonts だけ・幅の狭い画面）は、`build.py` が出す断片がすでに満たしている。
- 公開の操作そのもの（最初の呼び出しの順・`icon`・`description`）は、Artifact の道具の説明に従う。

## 作り方の流れ

1. **種別を決める。** そのページで何をしてもらうかを先に決め、下の「種別と部品」の表から種別を1つ選んで、データの `kind` に書く。1ページに種別は1つである。2つの種別の中身があるなら、ページを分ける。ただし、一覧から選ぶ問いは、承認・束・判断ボードのページにも置ける（「一覧から選ぶ問いの行の選択」の節）。答え方の形（問いのカードか、一覧から選ぶか）ではページを分けない。**答えを待つページ（回答待ちのページと、開いた問いのある判断ボード）は、答えを集める側（ページを出して答えを回収する1つのセッション）ごとに、同時に1枚までにする。** 作業のまとまりが違う問いは、1枚の中で分け（束の group・判断ボードの節）、開いている承認のページに別の作業の問いが来たら、同じ URL のまま束に作り替える（カードの key は変えない。番号は札にそのまま書く）。別のページにしてよいのは、量が多いとき（候補が40件ある一覧など）である。
2. **部品を並べる。** 種別が要る部品・置いてよい補足・並びを決めている。中身をどこに置くか（カードの要点・カードの塊・表・本文）は「中身の置き場」の節で決める。
3. **データを書く。** 書き方は「データの書き方」の節と、選んだ種別の見本（「種別と部品」の表の右の列）にある。札と番号は「札と番号」の節、本文の中の番号と識別子は「番号と識別子の書き方」の節に従う。書き出し先は、リポジトリに入れない場所にする。何度も出し直すページ（判断ボードなど）のデータは、数日で消える一時の場所（scratchpad など）に置かない。
4. **検証する。** `check` で誤りが無くなるまで直す。`--body` で本文を差し込むページは、`check` にも同じ `--body` を付ける（付けないと、部品も本文も無いページとして E-S1 で止まる）。
5. **作る。** artifact に公開するなら断片（既定）、手元で開くなら `--standalone` で作る。版の時刻は作ったときの時刻になるので、公開の直前に作る。
6. **公開する。** artifact なら「公開と回収」の節のとおり。
7. **回収して、回答済みにする。** 答えを読み取ったら（「答えを受け取る」の節）、`status` を `answered` にし、答えを `answers` に写して1回だけ作り直し、同じ場所に公開する。判断ボードでは、回答済みにせず、答えたカードを「決まったこと」の表へ移す（「判断ボードの更新のしかた」の節）。

## 種別と部品

種別は、既存の部品（判定カード・判断待ちの束・指摘の一覧・表・本文）の組み合わせの名前である。種別ごとに、要る部品・置いてよい補足・並びが決まっていて、`check` がそれを見る。表に無い部品は置けない。

| 種別（`kind`） | してもらうこと | 要る部品と並び | 置いてよい補足 | `--body` | 答える部品 | 見本 |
|---|---|---|---|---|---|---|
| `confirm`（認識合わせ） | 中身を確かめ、「確定」か「違和感がある」かを答えてもらう | 判定カードの節（`decisions`）1つ。カードは確かめる対象ごとに1枚で、どのカードも塊（`blocks`）を持つ | なし | 置かない | 持つ | `confirm.json` |
| `approve`（承認） | 問いに1つずつ答えてもらう。最後に全体を承認してもらうこともある（plan の承認ではふつう置く） | 判定カードの節1つ以上。全体の承認のカード（札は `承認`）を置くなら、ページの最後のカードに1枚だけ | 表（判定カードの節のあと）・選ぶ表（選び方のカードの節の直後）・タブ | 置ける（カードの上に出る） | 持つ | `approve.json`・`decide.json` |
| `pick`（一覧から選ぶ） | 一覧の中から選んでもらう | 判定カードの節1つ（カード1枚・選び方）を先頭に置き、そのあとに表を1つ以上。表の少なくとも1つが番号の列（`type: no`）を持つ。選び方のカードに `select` を書くと、表の行ごとに選べる（「一覧から選ぶ問いの行の選択」の節） | なし | 置かない | 持つ | `pick.json` |
| `map`（見取り図） | 読んで把握してもらう | 表1つ以上か、`--body` の本文 | タブ | 置ける | 持たない | `grasp.json`・`table.json` |
| `bundle`（束） | いくつかの作業から届いた判断待ちに答えてもらう | 判断待ちの束の部品（`bundle`）1つ。タブで分けるときは、タブごとに1つまで | group の中の選ぶ表（group のカードのあと）・タブ | 置ける | 持つ | `bundle.json` |
| `review`（レビュー） | 指摘と、それぞれを採ったかを見てもらう | 依頼したレビューの情報（ページの `request`）と、指摘の一覧（`findings`）1つ以上を部品の先頭にまとめて置く | 表・判定カード（指摘の一覧のあと。採否を決めてほしい指摘があるとき） | 置ける | 判定カードを足したときだけ | `review.json` |
| `board`（判断ボード） | 長く更新し続けるページで、いま決めることと決まったことを1枚で見てもらう | 判定カードの節（0以上）を先に、表（0以上）をあとに置く。部品は1つ以上で、開いた問いが0枚なら番号の列の無い表だけでもよい | 選ぶ表（選び方のカードの節の直後）・タブ | 置かない | 開いたカードがあるときだけ | `board.json` |

- 要る部品と並びの決まりは、次の当てはめのずれを止めるためにある。答える部品の無い種別（`map`）に判定カードを置く。認識合わせの中身を平らな要点に流し込む（`confirm` のカードに `blocks` が無い）。一覧の番号を `#N` や裸の数字で書く（`pick` に番号の列が無い）。選び方のカードが表の下にある・指摘の一覧が先頭に無い。
- `confirm` では、平らな要点だけのカードを置けない。平らな要点で足りる確かめは、認識合わせでなく承認の問いとして書く。
- 「並び」は部品（`sections`）の順を指す。`--body` の本文は、いつも部品の上に出る。本文を置けるのは、部品の上に本文があっても読む順を壊さない種別だけである。外から来た文を本文に写さない（「書くときの注意」）ので、認識合わせには本文を置かない。判断ボードでは、本文が判断のカードの上に出て読む順が崩れるので置かない。
- タブ（ページの `tabs`）は、長いページを短くするためか中身を区分するために、部品と本文をタブに分ける補足である。書き方は「タブで分ける」の節にある。
- 置いてよい補足は、実際に要るとした使い方だけにしてある。種別に収まらない中身があるときは、無理に当てはめず、ページを分けるか、合う種別を選び直す。
- 1枚のカードに問いをいくつもまとめない。問いは1枚に1つにする（部品の形からは見分けられないので、`check` は止めない）。

### 札と番号

ページの中の項目の識別子（`Q2`・`候補4` のような、接頭辞の語のあとに数字を続けたもの）を定義できるのは、カードの札（`tag`）と、表の番号の列（`type: no`）の値の2か所だけである。要点や本文に `B2` と書いても、識別子の定義にはならない。接頭辞は書き手が決めず、種別ごとに次の表で決まっている。ただし、選び方のカードが名指した表（選ぶ表）の番号は、種別に関係なく `候補` である。語そのものは `glossary.md` の「識別子の接頭辞」の表にある。

| 種別 | 識別子を定義する場所 | 形 | 書かないとき |
|---|---|---|---|
| `approve` | 問いのカードの札と、選ぶ表の番号の列 | 札は `Q<数字>`。全体の承認のカードの札は `承認` で、番号を付けず、ページの最後のカードに1枚だけ置く。選ぶ表の番号は `候補<数字>` | 札は、問いのカードの順に Q1・Q2… を振る。選ぶ表の番号は振らない。必ず書く |
| `pick` | 表の番号の列 | `候補<数字>` | ページの中の、番号の列のある行の順に 候補1・候補2… を振る（表をまたいで続ける） |
| `map` | 表の番号の列 | `ID:<数字>` | 同じく ID:1・ID:2… を振る |
| `board` | 問いのカードの札と、表の番号の列（決まったこと・選ぶ表） | 札と決まったことの表は `Q<数字>`、選ぶ表は `候補<数字>` | 振らない。必ず書く（カードや表を移しても番号を変えないため） |
| `bundle` | group の中の選ぶ表の番号の列 | `候補<数字>` | 振らない。必ず書く |
| `confirm` | 定義しない。カードの札は、確かめる対象の issue（`#N`・`owner/repo#N`）か、書かない | — | 札を出さない |
| `bundle`・`review`・`pick` のカード | 定義しない。カードの札は自由な短い文字列で、識別子にならない | — | 札を出さない |

- 数字は1から始め、`0` で始めない（`Q0`・`Q01` は誤り）。
- 1ページの中で、書いたものと書かないものを混ぜない。混ぜると、振る番号が書いた番号と重なりうるので止まる。書くなら全部に書く。番号の列の値を書かないときは、その行のその key を省くか、空の文字列にする。
- 識別子はページの中で重ねない（カードの札と番号の列の値を合わせて見る。束の group の中の選ぶ表も含める）。
- 選ぶ表（選び方のカードが名指した表）の番号は、行の答えの保存先（`<カードの key>--<番号の数字>`）に入る。承認・束・判断ボードで必ず書かせるのは、表を足したり除いたりしても番号が変わらず、保存された答えが別の行を指さないようにするためである。
- ほかの文書の番号（plan の `DJ-4` など）をカードの札に書かない。そのカードがほかの文書の何を指すかは、カードの題か塊に書く。

どのページにも、次の部品が必ず入る。

- **ヘッダー**: タイトルの上に、左の列に項目名・右の列に値の表が、本文と同じ大きさの文字で出る。項目はリポジトリ・tmux・issue・ブランチ・版・状態の6つで、無い項目は行ごと省かれる。tmux の値は「2.2（CC:shop）」のように、ウィンドウとペインの番号と、括弧の中のウィンドウの名前で書く。版の値は `YYYY-MM-DD HH:MM JST（最終更新）` で、作ったときの時刻を JST で書いたものである。artifact のサービスの内部の版の番号は出さない。幅の広い画面では表が2列に並び、狭い画面では縦に積まれる。束の group の見出しの下にも、同じ形の表（リポジトリ・tmux・issue・ブランチ・状態）が出る。
- **目的**: `why` の1文。読む人が経緯を覚えていなくても、なぜいま読むのかが分かるように、きっかけの出来事を書く。
- **関連リンク**: `links`。issue・PR・計画の文書など、答えるときに開きたいものを並べる。長い文書（節がいくつもある文書）を指すときは、答えに要る節の見出しのアンカーまで付け、`label` に節の名前を書く（例: `13.5 一覧から選ぶ問いの直し`）。アンカーは、文書を表示している画面の見出しのリンクから写す（GitHub なら見出しの横のリンク）。見出しの文字から手で作ると、記号（`.`・`:`・括弧）の扱いで外れることがある。

## データの書き方

ページ1枚を JSON 1つで書く。知らない項目は誤りとして弾かれる（打ち間違いを黙って無視しないため）。見本は `examples/` にある。

- `examples/approve.json`: 問いのカードと全体の承認のカードを置き、本文で問いの番号を指した承認のページ（`PR #N`・`owner/repo#N` のリンクも含む）
- `examples/decide.json`: 問いのカードだけを置いた承認のページ
- `examples/bundle.json`: 別のリポジトリの2つの作業の判断待ちをまとめ、片方の group に選び方のカードと group の中の選ぶ表を置いたページ
- `examples/review.json`: 依頼したレビューの情報と、2つのモデルの指摘の一覧を置いたレビューのページ
- `examples/grasp.json` と `examples/grasp-body.html`: 読み物のページ（ヘッダーだけをそろえる）
- `examples/table.json`: 表の部品と、外部の課題管理の ID のリンクのページ
- `examples/confirm.json`: 根拠を省き、小見出し付きの塊（`blocks`）で中身を置いた認識合わせのページ
- `examples/pick.json`: 選び方のカードを先頭に置き、候補を番号の列のある表に並べた、一覧から選ぶページ
- `examples/board.json`: いま決めることを要る順の節に並べ、2つ目の節の直後に選ぶ表を置き、決まったことともらう値を表にした、判断ボードのページ
- `examples/board-tabs.json`: `board.json` を、段のある3つのタブ（いま決めること・決まったこと・もらう値）に分けた判断ボードのページ
- `examples/map-tabs.json` と `examples/map-tabs-body.html`: 段が3つ・タブが8つの見取り図。7つのタブは本文のパネルで、1つのタブはデータの表である

| 場所 | 項目 | 必須 | 決まり |
|---|---|---|---|
| ページ | `format` | 必須 | `1` |
| ページ | `title` | 必須 | ページの名前。`<title>` と見出しになる |
| ページ | `kind` | 必須 | 種別。`confirm`・`approve`・`pick`・`map`・`bundle`・`review`・`board` のどれか（「種別と部品」の表）。前の版の `purpose` は `kind` に置き換えたので、書くと誤りになる |
| ページ | `status` | 必須 | `awaiting`（回答待ち）・`answered`（回答済み）・`live`（随時更新）のどれか |
| ページ | `why` | 必須 | ページの目的の1文（「目的」の札で出る） |
| ページ | `source` | 必須 | 送り元。下の行 |
| ページ | `links` | 任意 | `{label, url}` の並び。url は `https://` か `http://` で始める |
| ページ | `sections` | 必須 | 部品の並び。`--body` を渡すときは空でもよい |
| ページ | `answers` | 任意 | 回収した答え。`status` が `answered` のときは必須 |
| ページ | `request` | レビューのページでは必須 | 依頼したレビューの情報。ほかの種別では置けない。書き方は「レビューのページの依頼の情報」の節 |
| ページ | `tabs` | 任意 | タブの並び（2つ以上）。置けるのは見取り図・判断ボード・承認・束で、書き方は「タブで分ける」の節 |
| タブ | `key`・`label` | 必須 | `key` は URL の `#` とパネルの id になる名前で、英小文字で始まり、英小文字と数字だけが続く20文字まで（`-` と `_` は使えない）。ページの中で重ねない。`label` はタブに出す名前で、書式は効かない |
| タブ | `row` | 任意 | 段の名前。書くなら全部のタブに書き、同じ段のタブは続けて並べる |
| 部品 | `tab` | `tabs` のあるページでは必須 | その部品を入れるタブの `key`。`tabs` の無いページでは書かない。束の group の表には書かない |
| source | `repo` | 必須 | リポジトリの名前 |
| source | `repo_url` | 任意 | リポジトリの URL。あれば issue・ブランチ・本文の `#N` がリンクになる |
| source | `issue` | 任意 | issue の番号（1以上の整数） |
| source | `branch` | 任意 | ブランチの名前 |
| source | `tmux` | 任意 | `{window, pane, name}`。ページの `source` で書かなければ、作ったセッションのペインから引く |
| source | `trackers` | 任意 | 外部の課題管理の `{prefix, url}` の並び。書き方は「表の部品の書き方」の節 |
| `decisions` | `title`・`cards` | 必須 | 判定カードを1枚以上 |
| `bundle` | `title`・`groups` | 必須 | 各 group は `source`・`title`・`cards`（必須）と `why`・`tables`（任意）。`tables` は group の中の選ぶ表の並びで、表の部品と同じ形で `key` を必ず書く |
| `findings` | `title`・`items` | 必須 | `lane`（任意・どのモデルの指摘か）。各 item は `text`・`severity`（`high`・`mid`・`low`）・`adopted`（`adopted`・`partial`・`rejected`）・`reason` が必須で、`evidence` は任意 |
| `table` | `title`・`columns`・`rows` | 必須 | 列を1つ以上・行を1つ以上。書き方は「表の部品の書き方」の節 |
| `table` | `key` | 任意 | 選び方の `tables` で名指すときに書く表の key。カードの key と同じ形で、ページの中の表どうし（束の group の表を含む）で重ねない |
| カード | `key` | 必須 | 英小文字で始まり、英小文字・数字・`_`・`-` が続く64文字まで。ページ全体で重ねない（保存先の文書の id になる） |
| カード | `title`・`recommend`・`options` | 必須 | `recommend` は推奨する選択肢の key。`options` は2つ以上 |
| カード | `reason` | 任意 | 推奨の根拠。省いてよい条件は下の「根拠を省いてよいカード」。書いたのに空なら E-C4 で止まる |
| カード | `tag`・`points`・`evidence` | 任意 | `tag` はカードの札。形は種別で決まる（「札と番号」の節）。`points` の各要素は文字列か `{text, evidence}` で、置けるのは全体の承認のカードと認識合わせのカードだけ（「中身の置き場」） |
| カード | `select` | 任意 | 選び方のカードに書く、表の行を選ぶ数・推奨の行・選ぶ表。一覧から選ぶページ・承認・束・判断ボードのカードに書ける。書き方は「一覧から選ぶ問いの行の選択」の節 |
| カード | `blocks` | 問いのカードと認識合わせのカードでは必須 | 小見出し付きの要点の塊の並び（1つ以上）。各塊は `title`（小見出し）と `points`（1つ以上・要素は `points` と同じ形）。`points` があれば、その後に出る。問いのカードの塊の題の並びは「問いのカードの書き方」の節 |
| 選択肢 | `key`・`label` | 必須 | `kind` は任意で、選んだときの色（`go`・`fix`・`warn`・`no`） |

- 推奨は先に出る。カードの中で、タイトルのすぐ下に推奨の選択肢と根拠（書いたとき）が出て、選択肢のボタンにも「推奨」の札が付く。
- **根拠を省いてよいカード**: 推奨に説明が要らないカードでは `reason` を書かない。たとえば「この内容で確定」と「直してほしい（補足欄に）」から選ぶ確認のカードである。このときは根拠の行が出ず、推奨の行だけが出る。推奨のほかの選択肢を選ぶ理由が実際にありうるカード（いくつかの案を比べて1つを選ぶ判断）では、なぜその案を推すかを書く。どのカードにも同じ定型文を書くくらいなら、省く。
- 確かめた度合い（`evidence`）は `verified`（確かめた）・`sourced`（出典あり・未確認）・`guess`（推測）で書く。カード・要点・指摘に付けられる。
- 札とページの固定の文は `glossary.md` の言葉で出る。データには英語の key を書く。問いのカードの塊の題も `glossary.md` の語で書く。用語は `glossary.md` の「和訳しない用語」に合わせる（ブランチを「枝」と書かない、など）。
- 本文の文字列はすべて平文として扱われ、HTML にはならない。効く書式は、`` `…` `` がコードの書式になることと、`https://…` と番号・識別子がリンクになることだけである。番号と識別子のリンク先は「番号と識別子の書き方」の節にある。ページのタイトル・選択肢のボタン・リンクの `label`・`tag`・`lane` には書式が効かず、文字のまま出る。

### 番号と識別子の書き方

本文の文字列の中の番号と識別子は、何を指すかでリンク先が決まる。

| 書き方 | 指すもの | リンク先 |
|---|---|---|
| `#N` | 近い送り元のリポジトリの issue | `<repo_url>/issues/N`（近い送り元に `repo_url` があるとき） |
| `PR #N` | 近い送り元のリポジトリの PR | `<repo_url>/pull/N`（同じく `repo_url` があるとき）。`PR #215` の全体が1つのリンクになる |
| `owner/repo#N` | 別のリポジトリの issue（PR も、GitHub が転送するのでこの形で書く） | 近い送り元の `repo_url` と同じホストの `/<owner>/<repo>/issues/N`（同じく `repo_url` があるとき） |
| `<接頭辞>-<数字>`（`OPS-41`） | 外部の課題管理の課題 | 近い送り元の `trackers` の URL（その接頭辞を登録したとき） |
| ページで定義した識別子（`Q2`・`候補4`） | そのページの中のカードや表の行 | そのカードや行（新しいタブを開かず、ページの中で移る） |
| 裸の数字・ページで定義していない識別子（ほかの文書の `DJ-4` など） | — | リンクにしない |

- **別のリポジトリの番号は、必ず `owner/repo#N` と書く。** `#N` と書くと、近い送り元のリポジトリの issue へのリンクになる。スクリプトは、`#N` が別のリポジトリの番号かを見分けられない。リポジトリの名前だけを前に付けた `repo#N` はリンクにならない。
- ページの中の識別子は、「札と番号」の節のとおり、カードの札と表の番号の列で定義したものだけである。本文に `Q2` と書けばそのカードへ、`候補4` と書けばその行へ移るリンクになる。飛んだ先のカードや行には枠の色が付く。
- 前に英数字・`_`・`.`・`/`・`#`・`-` が続くもの（`FAQ2`・`docs/Q2`）と、後ろに英数字・`_` が続くもの（`候補43` の中の `候補4`）、後ろに `.`・`/`・`-` と英数字が続くもの（`Q2.md`・`Q2-3`）は、ページの中の識別子として扱わない。コードの書式の中と URL の中も変えない。
- **番号ごとに接頭辞を書く。** `候補43・候補41・候補49` と書き、`候補43・41・49` と書かない。番号を3つ以上並べ、並んだ番号がすべてそのページで定義されていると、E-I3 で止まる。番号が2つだけの形（`候補43・41`）は、`Q2・3件` のような普通の文と見分けられないので止まらず、後ろの数字は文字のまま出る。
- 束の group の中では group の送り元を使い、group に `repo_url` や `trackers` が無ければリンクにしない（ページの送り元へは戻らない）。group の中の選ぶ表の番号（`候補4`）はページで定義した識別子なので、group の中の文からもページの文からも、その行へ飛ぶリンクになる（ページの中のリンクは送り元に頼らない）。

### 問いのカードの書き方

問いのカードは、読む人が1回読めば何を決めるかが分かるように書く。ここで**問いのカード**とは、判定カードのうち、認識合わせのカードと、承認のページの全体の承認のカード（札 `承認`）を除いたものを指す。承認と判断ボードの問い、束のカード、一覧から選ぶページの選び方のカード、レビューのページに足した判定カードがこれに当たる。

- **題は問いの形にする。** 題は「〜か」「〜？」で終わる文にする（末尾の括弧書きは除いて見る）。話題の名前（「判断のページの種別」）や、推奨を言い切った文（「通知はチャットに送る」）にしない。題だけで問いが分かるなら短くてよい。全体の承認のカードの題も問いの形にする（「この plan で実装に進むか」）。認識合わせのカードの題は、確かめる対象の名前のままでよい。
- **中身は塊に置く。** 1つ目の塊の題は「何を決めるか」で、問いの前提（なぜいま決めるか・答えが何に効くか・何から選ぶか）を書く。2つ目は「推奨の中身」で、推奨の選択肢を選んだら何がどうなるかを書く。推奨のほかの案があるなら、3つ目を「ほかの案」にして、それぞれの案の弱いところを書く。4つ目からは自由な題の塊を置ける。問いのカードには平らな要点（`points`）を置かない。塊の題の語は `glossary.md` の「問いのカードの塊の題」にある。
- **選択肢の名前は、選んだら何をするかを書く。** 推奨のボタンには「推奨」の札が付くので、推奨の語で始まる名前（「推奨の案で進める」）にしない。名前を括弧書きだけにもしない。別のカードの推奨を指す括弧書き（「答えない（Q27 で推奨の形を選ぶ）」）はよい。
- **ほかの文書の符号を、何を指すかを書かずに使わない。** 検討の文書の中の案の符号（`1A`・`4B'`）や plan の `DJ-4` を、題・選択肢の名前・塊にそのまま書かない。中身を書くか、符号を書くなら同じ文に中身を添える。カードの札にほかの文書の番号を書かない決まり（「札と番号」の節）を、カードの文の全体に広げたものである。
- 根拠（`reason`）は今までどおり任意である。カードの中の並びは、題 → 推奨の行 → 根拠 → 塊 → 選択肢 → 補足欄で、推奨は先に出る。

`build.py` は、題の形（E-Q1）・選択肢の名前（E-Q2）・塊の題の並びと `points`（E-Q3）を止める。どれも表記の決まりで、題が問いの形でも、何を決めるかが分かるとは限らない。中身が分かるかは、書く側が見本（`examples/approve.json`・`examples/decide.json` など）に合わせて確かめる。

```json
{
  "key": "notify_on_third",
  "title": "再試行の失敗を、何回目で通知するか",
  "recommend": "third",
  "reason": "1回目と2回目の失敗はよく起きるので、毎回通知すると大事な通知が埋もれるため。",
  "blocks": [
    {"title": "何を決めるか", "points": ["再試行が失敗したとき、毎回通知するか、何回目で通知するかを決める。"]},
    {"title": "推奨の中身", "points": ["1回目と2回目の失敗は警告のログに残すだけにし、3回目の失敗で通知する。"]},
    {"title": "ほかの案", "points": ["毎回通知する。1日に約40件の通知になり、大事な通知が埋もれる。"]}
  ],
  "options": [
    {"key": "third", "label": "3回目で通知する", "kind": "go"},
    {"key": "every", "label": "毎回通知する", "kind": "warn"}
  ]
}
```

### 答えたカードを畳む表示

判定カードの頭（札・題）の下に開閉の行があり、押すと、カードの中身（推奨の行・根拠・塊・選択肢・補足欄）を畳んだり開いたりできる。データに書くことは無い。問いが多いページで、答えた問いを短くし、残りの問いを目に入りやすくするためである。

- 畳んだカードには、頭と「答え: <選んだ選択肢の名前>」が出る。一覧から選ぶカードには、選んだ行も出る。答えの無いカードも手で畳め、そのときは「答え: 未回答」が出る。
- 回答待ち・随時更新のページでは、保存先の答えを最初に読み終えたときに1回だけ、答えのあるカードを畳む。読み終える前に選んだか補足を書いたカード、中の要素（補足欄・選択肢のボタン・リンク）にフォーカスがあるカード、選んだ行が選べる数を超えている選び方のカード（別の画面で選んだ行が届いたとき）は畳まない。畳んだあとに届いた行で選べる数を超えたときは、開閉の行の答えの文に外すよう知らせる文が付く。そのあとに届いた答えや、そのあとに選んだカードでは畳まない（押したときだけ畳む）。保存できない表示では、何も畳まない。
- 回答済みのページでは、`answers` に答えのあるカードを畳んで描き、未回答のカードは開いて描く。
- 判断ボードでは、答えてから、回収してカードを「決まったこと」の表へ移すまでのあいだ、答えたカードが畳まれる。
- 開閉はブラウザの開閉の要素（`details` と `summary`）が受け持つので、JS の無い表示でも、キー（Tab で移って Enter か Space）でも開け閉めできる。

### 中身の置き場

判断に要る中身は、形に合わせて次の4つに置き分ける。

- **カードの `points`**: 判断に要る点が平らな箇条書きで足りるとき。置けるのは、全体の承認のカードと認識合わせのカード（`blocks` の前に足すとき）だけである。問いのカードは `points` を持たず、中身を塊に書く（「問いのカードの書き方」）。認識合わせのカードは `points` だけでは書けず、必ず `blocks` を持つ。
- **カードの `blocks`**: 1つのカードの中身に塊が複数あるとき（問いのカードの「何を決めるか」「推奨の中身」「ほかの案」、認識合わせの「この issue でやること」「issue に書いていないが要ること」「どの観点で見たか」など）。塊ごとに小見出しが付く。見出しにしたい行を `points` に混ぜない。混ぜると、見出しと中身が1本の箇条書きに並んで区別がつかない。問いのカードと認識合わせ（`confirm`）のカードは、必ず `blocks` を持つ。
- **表の部品（`table`）**: 番号・識別子・中身・状態のように、同じ形の行が並ぶとき。一覧から選ぶ問いの候補と、判断ボードの決まったことは、番号の列を持つ表に置く。
- **`--body` の本文**: カードをまたぐ長い説明・図・自由な配置のとき。このとき、カードをまたぐ説明は本文に置き、カードには問いと選択肢と、問いのカードに要る塊（「何を決めるか」「推奨の中身」）だけを置く。本文はページを作る側が書く HTML なので、issue の本文やレビューの出力など外から来た文章は本文に写さず、上の3つ（データの文字列）に入れる（「書くときの注意」）。

```json
{
  "key": "intake_216",
  "tag": "#216",
  "title": "タイムアウトの既定値を見直す",
  "recommend": "ok",
  "blocks": [
    {"title": "この issue でやること", "points": ["設定ファイルの既定値を、先月の記録から決め直す。"]},
    {"title": "issue に書いていないが要ること", "points": [{"text": "再試行の3回が上限の時間に収まるかを確かめる。", "evidence": "guess"}]}
  ],
  "options": [
    {"key": "ok", "label": "この内容で確定", "kind": "go"},
    {"key": "fix", "label": "直してほしい（補足欄に）", "kind": "fix"}
  ]
}
```

### 表の部品の書き方

番号・識別子・中身・状態を並べる表は、`--body` に HTML で書かず、表の部品（`table`）でデータとして書く。線・エスケープ・リンク・幅の狭い画面での形（行をカードの形に積み、各欄の上に列の見出しを出す）が部品の側で決まる。

```json
{
  "type": "table",
  "title": "対応",
  "columns": [
    {"key": "no", "label": "番号", "type": "no"},
    {"key": "refs", "label": "issue / PR", "type": "ref"},
    {"key": "tracker", "label": "外部の課題", "type": "ref"},
    {"key": "what", "label": "中身"},
    {"key": "result", "label": "結果"}
  ],
  "rows": [
    {"no": "ID:1", "refs": ["#212", "PR #215"], "tracker": "OPS-41", "what": {"text": "再試行を3回までにする", "evidence": "verified"}, "result": "マージ済み"},
    {"no": "ID:2", "refs": [], "tracker": ["OPS-42", "OPS-43"], "what": "振り返りを書く", "result": ""}
  ]
}
```

- **列**（`columns`）: 各列は `key`（カードの key と同じ形・表の中で重ねない）・`label`（列の見出し）・`type`（任意）を持つ。`type` は `text`（既定）・`ref`（識別子の列）・`no`（番号の列）のどれかである。番号の列を置けるのは `pick`・`map`・`board` の表と、承認と束の選ぶ表（選び方の `tables` が名指した表）だけで、1つの表に1列までである。
- **番号の列**（`type: no`）: その表の行の番号を書く列である。行の key を省いてよい唯一の列で、値は文字列にする。
- **行**（`rows`）: 各行は、列の `key` をちょうどそろえたオブジェクトで書く。足りない key も知らない key も誤りになる（番号の列の key だけは省いてよい）。
- **`text` の欄**: 文字列か `{text, evidence}`。ほかの文字列と同じ書式（コード・URL・`#N`・外部の課題管理の ID）が効く。空の文字列は空の欄になる。
- **`ref` の欄**: 識別子1つの文字列か、識別子の配列。受け付ける形は `#N`（issue）・`PR #N`・`owner/repo#N`（別のリポジトリの issue）・外部の課題管理の ID（`<接頭辞>-<数字>`）の4つで、どれも必ずリンクになる。リンク先は「番号と識別子の書き方」の表のとおりで、表示の文字は書いたまま残る（`PR #215` は「PR #215」と出て、`<repo_url>/pull/215` へリンクする）。リンクにできないとき（形が違う・`#N` や `PR #N` や `owner/repo#N` なのに送り元に `repo_url` が無い・接頭辞が送り元の `trackers` に無い）は E-L1 で止まる。空の配列は空の欄になる。
- **番号と識別子は別の列にする。** 行の番号は番号の列（`type: no`・形は「札と番号」の節）に、issue・PR・外部の課題管理の ID は `ref` の列に書く。1つの欄に混ぜると、幅の狭い画面で2行に分かれて読みにくく、識別子がリンクにもならない。`ref` の列に番号を混ぜると E-L1 で止まる。この例は見取り図（`map`）の表なので、番号の接頭辞は `ID:` である（`ID:1` の形）。
- **外部の課題管理の ID** は、送り元（`source`）の `trackers` に接頭辞と URL の元を書いたときだけリンクになる。`url` には `{id}` をちょうど1つ書き、そこに ID の全体（`OPS-41`）が入る。接頭辞は英大文字で始まり、英大文字と数字が続く10文字までである。

```json
{
  "repo": "shop",
  "repo_url": "https://github.com/example-org/shop",
  "trackers": [{"prefix": "OPS", "url": "https://tracker.example.com/browse/{id}"}]
}
```

- **表の key**（`key`・任意）: 選び方のカードが `tables` で名指すときに書く（「一覧から選ぶ問いの行の選択」）。
- 表は答える部品ではない。表だけのページは保存のコードを持たず、`db` を付けずに公開する。

### 一覧から選ぶ問いの行の選択

選び方のカードに `select` を書くと、番号の列のある表の各行の番号の欄にチェックが付き、行ごとに選べるようになる。候補が多くても、読みながらその行で選べる。選び方のカードを置けるのは、一覧から選ぶページ（`pick`）と、承認・束・判断ボードのページである。認識合わせとレビューのカードには置けない。

```json
{
  "key": "pick_tools",
  "title": "どの候補を試すか",
  "recommend": "chosen",
  "select": {"max": 2, "recommend": ["候補2", "候補5"]},
  "blocks": [
    {"title": "何を決めるか", "points": ["下の表の候補から、2週間試す監視の道具を2つまで選ぶ。"]},
    {"title": "推奨の中身", "points": ["候補2 と 候補5 を試す。どちらも今のログの置き場をそのまま読める。"]}
  ],
  "options": [
    {"key": "chosen", "label": "選んだ候補を試す", "kind": "go"},
    {"key": "none", "label": "どれも試さない", "kind": "no"}
  ]
}
```

- `max`（必須）は選べる行の数の上限、`min`（任意）は下限で、どちらも1以上の整数である（`min` は `max` 以下）。`recommend`（任意）は推奨の行の番号の並びで、ページで定義した番号（`候補2`）を `max` 個まで書く。推奨の行には「推奨」の札が付く。「上位2つを選ぶ」は、`max: 2` と、上位2つを `recommend` に書いて表す。
- 選び方のカードには「表の行を 2 つまで選ぶ」と「選んだ行（1）: 候補5」の行が出る。上限に達すると、まだ選んでいない行のチェックは押せなくなる。選び方のカードの選択肢（「選んだ候補を試す」など）は、今までどおり選ぶ。
- 行の答えは、判定カードと同じ形（「答えの保存の形」の節）で、doc id を `<選び方のカードの key>--<番号の数字>`（`pick_tools--5`）にした文書に入る。`choice` は選んだら `pick`、外したら `null` である。行の答えの key はカードの key に `--` と数字を足したものなので、カードの key の64文字の決まりの外にある。回答待ちの件数には、行は数えない。
- ページは、保存先の答えを一度読み終えるまで、行のチェックを押せない状態にする（別の画面で選んだ行が遅れて届き、上限を超えて選べてしまうのを防ぐ）。それでも別の画面と同時に選んで上限を超えたときは、選び方のカードに「選べる数を超えています」と出る（ページは行を外さない）。回収した答えが上限を超えていたら、`answers` は E-A1 で止まるので、どの行を残すかを owner に確かめてから写す。`answers` を書かない判断ボードでは、`check --answers` で同じ確かめをする（「判断ボードの更新のしかた」）。
- 保存できない表示の返答の文には、選び方のカードの行の下に「選んだ行: 候補2、候補5」が出る。

**選ぶ表の名指し（`tables`）。** どの表の行を選ぶかは、`select` の `tables` に表の `key` を並べて名指す（例: `"tables": ["trial_shops"]`）。名指された表を、ここでは**選ぶ表**と呼ぶ。

- 一覧から選ぶページでは `tables` は任意である。書かなければ、ページの番号の列のある表をすべて選ぶ表にする（今の書き方のまま。`examples/pick.json`）。書けば、名指した表の行だけを選べる。一覧から選ぶページの選び方のカードは、今のとおり1枚である。
- 承認・束・判断ボードでは `tables` を必ず書く。1ページに、選び方のカードと選ぶ表の組をいくつ置いてもよい（`examples/board.json`・`examples/bundle.json`）。
- 1つの表を名指せるのは、1枚の選び方のカードだけである。名指す表は番号の列を持つ。
- 選ぶ表の番号は `候補<数字>` で、承認・束・判断ボードでは必ず書く（「札と番号」の節）。候補の番号は、ページの中で表をまたいで重ねない。
- **並び**: 承認と判断ボードでは、判定カードの節の直後に、その節の選び方のカードが名指した表を、節の中のカードの順・1枚のカードの中は `tables` の順で続けて置く。あいだにほかの部品を挟まない。選ぶ表でない表は、今のとおり最後の判定カードの節のあとに置く。全体の承認のカードがあるページでは、選び方のカードを別の節に置けば、選ぶ表のあとに全体の承認のカードを置ける。
- **束**: 選ぶ表は、group の `tables` に置き、group のカードのあとに出る。表の中の `#N` などは group の送り元でリンクになる。名指せるのは同じ group の選び方のカードだけで、group には選ぶ表のほかの表を置けない。
- **行の答えの key の重なり**: 行の答えの key（`<カードの key>--<番号の数字>`）を、ページのほかのカードの key と重ねない。カードの key は `-` を含めるので、選び方のカード `tools` の候補1 と、別のカード `tools--1` は同じ保存先になる。重なれば E-C1 で止まる。
- 選び方のカードも問いのカードなので、書き方は「問いのカードの書き方」の節に従う。選び方のカードを畳むと、答えの行に選んだ行も出る（「答えたカードを畳む表示」）。

### レビューのページの依頼の情報

レビューのページは、指摘を読む人が「どんなレビューを、なぜ、何を通して頼んだか」を分かるように、ページの項目 `request` に5つの情報を書く。ページでは、ヘッダー（目的・関連リンク）のあと、指摘の一覧の前に「依頼したレビュー」の表として出る。

```json
{
  "target": "PR #215 の差分（決済の再試行）",
  "type": "実装のレビュー",
  "via": "セカンドオピニオン（別の会社のモデル2つ）",
  "focus": "冪等キーの使い回し・タイムアウトの値の置き場・再試行の間隔",
  "why": "決済の会社への依頼が増えうる変更なので、マージの前に別の目で見たい。"
}
```

- `target`（対象）は何をレビューしてもらったか、`type`（種類）はどの段のレビューか（実装のレビュー・設計の確かめ・振り返りの確かめなど）、`via`（経由）はどの道具や人を通したか、`focus`（観点）は何を見てもらったか、`why`（なぜ）はなぜこのレビューを取ったかである。5つとも必須の、空でない文字列で、本文と同じ書式（`#N`・`PR #N`・URL など）が効く。
- `via` は決まった値にせず、自由な文で書く（「Copilot（PR のレビュー）」「セカンドオピニオン（別の会社のモデル2つ）」「人のレビュー」など）。どのモデルの指摘かは、指摘の一覧の `lane` に書く。
- 依頼の違う2つのレビュー（たとえばセカンドオピニオンと Copilot）は、1ページに混ぜず、ページを分ける。

### 判断ボードの更新のしかた

判断ボード（`board`）は、作ったあとも判断が足されたり決まったりして、何度も出し直すページである。読む人は上から順に読む。

- **判定カードの節は、要る順に並べ、節の題に「いつまでに・何のために」を書く。** たとえば「1. 今日決めること（切り替えの手順を書くため）」「2. 今週中に決めること（当日の段取りのため）」のようにする。項目を足す仕組みは無いので、節の題で書き分ける。
- **問いは1枚に1つにする。** 1枚のカードに問いをまとめると、1つにだけ違和感があるときに選べない。
- **決まったカードは、その番号のまま「決まったこと」の表へ移す。** 表は番号の列（`Q<数字>`）を持ち、選んだ答え・補足・いつ決まったかを行に書く。表は答える部品でないので、移したものは選べなくなる。移したあとは、その行を正とする（保存先にはカードの答えが残るが、ページはもう読まない）。ページ全体を回答済み（`answered`）にはせず、状態は `live` のままにする。
- **表から行を消すなら、消したあとの正本をページの外の記録（ページを使う側の台帳など）に置く。** 「決まったこと」の表を、直前に決まった分だけに入れ替える使い方では、消えた行の答えがページから無くなる。消えた行の答えを、保存先から読み直して正にしない。
- **番号は使い直さない。** 決まったものや消したものの番号を、別の問いに使わない。ページの中の重なりは E-I2 で止まるが、出し直しの版をまたいだ使い直しは止められない。カードの key も使い直さず、同じ key のまま問いや選択肢の意味を変えない。保存先の答えは key で残るので、使い直すと前の答えが別の問いに付く。変えるときは、古いカードを取り下げて（ページから除き、取り下げたことを表かページの外の記録に残す）、新しい key と番号で足す。
- **読む人に案内したあとに足した問いには、題の頭に「追加: 」を付ける。** 「全部推奨どおり」のような一括の答えは、印の無い問いにだけ当てる（「答えを受け取る」の節）。読む人が読み終えた版に無かった問いに、読んでいない一括の答えを当てないためである。印をいつ外すかは、ページを使う側が決める。
- **値の依頼（貼ってもらう文字列）はカードにしない。** 選択肢で表せない値のために、意味のない選択肢を作らない。値の名前・どこで読むか・状態を表の行に書き、値そのものは、その値を求めるカードの補足欄か会話で受け取る。
- **選び方のカードを表へ移すときは、そのカードが名指した選ぶ表も、同じ出し直しでページから除く。** 除いた表の行は押せなくなる。除き忘れると、名指されていない `候補` の番号の列が問いの番号の形でないので E-I1 で止まる。移した行には、選んだ行を番号と名前で書く（`候補2（駅前店）・候補3（アウトレット）で試す`）。表を除くので、番号だけでは何を選んだか分からなくなるためである。
- **選んだ行の数は、移す前に `check --answers` で確かめる。** 保存先から読んだ文書をすべて `answers` と同じ形（`{"<key>": {"choice", "note", "at"}}`）に写し、カードと選ぶ表を除く**前**のデータに当てる。ページに無い key（前に移したカードの答え）は数えるだけで止めない。上限を超えていたら、どの行を残すかを owner に確かめる。
- **候補の番号も使い直さない。** 移した行の「候補2」が、あとで足した別の選ぶ表の候補2 へのリンクにならないようにするためである。
- 判定カードをすべて表へ移したページは、答える部品の無いページとして描かれる（保存のコードを持たない）。終わった判断ボードの姿である。開いた問いが0枚のときは、番号の列の無い表（作業の表など）だけを置いてもよい。

### 判断待ちの束

- 判断待ちの束を作るときは、判断を出す側のセッションが `build.py source --git <作業しているディレクトリ>` で自分の送り元を出し、カードと一緒に束を作る側へ渡す。カードの key は、作業ごとに前置きを付けるなどして、ページ全体で重ならないようにする。
- 一覧から選ぶ問いは、選び方のカードと選ぶ表を同じ group に置く（「一覧から選ぶ問いの行の選択」）。表の key と候補の番号も、ページ全体で重ならないようにする。

### タブで分ける

1枚のページの中を、タブで分けられる。縦に長いページを短くするためにも、中身を区分するためにも使う。URL は1つのままで、選んだタブは URL の `#` に残る（`#steps` を付けて開けば、そのタブが開く）。

- **置ける種別**: 見取り図（`map`）・判断ボード（`board`）・承認（`approve`）・束（`bundle`）に置ける。認識合わせ・一覧から選ぶ・レビューのページには置けない（E-K2）。
- **定義はページの `tabs` に書く**: タブを2つ以上並べる。各タブは `key`（URL の `#` の名前・英小文字と数字だけ）・`label`（タブに出す名前）・`row`（任意・段の名前）を持つ。本文でタブを使うときも、名前と段は `tabs` に書く。

```json
{
  "tabs": [
    {"key": "now", "label": "いま決めること", "row": "判断"},
    {"key": "done", "label": "決まったこと", "row": "記録"},
    {"key": "values", "label": "もらう値", "row": "記録"}
  ]
}
```

- **データの部品をタブに入れる**: `tabs` を書いたページでは、すべての部品に `tab`（タブの `key`）を書く。同じタブの部品は続けて並べ、タブの順は `tabs` の順にする。選び方のカードと、そのカードが名指した選ぶ表は、同じタブに置く。束のページでは、束の部品をタブごとに1つまで置ける（タブの無い束のページは、今までどおり1つ）。
- **本文をタブに入れる**: 本文（`--body`）には、タブの中身（パネル）だけを書く。パネルは、`class="hp-tabpanel"` と `id="<タブの key>"` を持つ `section` か `div` で、本文の一番外に置く。タブのあるページでは、本文の一番外にはパネルと `style`・`script` だけを置く（パネルの外の中身は、どのタブを選んでも出続けるため）。1つのタブの中身は、本文のパネルかデータの部品のどちらか片方にする。本文は部品の上に出るので、`tabs` には本文のパネルのタブを先に、データの部品のタブをあとに並べる。

```html
<section class="hp-tabpanel" id="steps">
  <section>
    <h2 class="hp-sec-title hp-tab-same">当日の進み方</h2>
    <p>…</p>
  </section>
</section>
```

- **本文の id**: タブのあるページの本文では、id を `hp-` で始めない（`build.py` が描く要素の id の頭である）。タブの `key` と同じ id をパネルのほかに書かない。同じ id を2回書かない（E-N4）。`<div/>` のように空の要素でない要素を `/>` で閉じる書き方と、1つの要素に同じ属性を2回書く書き方は止まる（ブラウザと `build.py` で、パネルの内か外かの読み方がずれるため）。本文の終わりで閉じていない要素（閉じ忘れた最後のパネルや `style`）も止まる（本文のあとに描くデータの部品のパネルが、その中に入るため）。`textarea` と `title` の中は文字として、`template` の中は文書の外として読む。
- **段**: 1つの段に置けるタブは6つまでである。`row` を書かないページは全体を1つの段として数えるので、タブが7つ以上なら、`row` で段に分けるまで `check` が止まる（E-N2）。`row` は全部のタブに書くか、どれにも書かない。同じ段のタブは続けて並べる。
- **見出し**: タブの中の最初の部品の題がタブの名前と同じなら、JS が動いているあいだはその題を出さない（タブの名前が見出しの代わりになる）。本文のパネルで同じにするときは、最初の見出しを `class="hp-sec-title hp-tab-same"` にする。
- **余白**: 帯の下の線から最初の部品までは 28px、パネルの中の部品どうしは 36px になる。タブの無いページの余白は変わらない。
- **帯**: タブの帯は、上に貼り付く帯（全部推奨どおりの案内と保存の状態）と同じ箱に入る。段ごとに1行で、左に段の名前が出る。幅が足りないときは、段は1行のまま、段の中だけを横に送る。
- **隠れたタブを指すリンク**: 本文の `Q2`・`候補4` のリンクや、本文に書いた `#…` のリンクが隠れたタブの中を指していたら、押すとそのタブに切り替えてから移る。
- **未回答の件数**: 回答待ちと随時更新のページでは、判定カードのあるタブの名前の横に「回答待ち N 件」が出る（0件なら出ない）。回答済みのページには出ない。
- **キーと読み上げ**: タブは、左右の矢印キー（段をまたいで回る）・Home・End・Space で選べる。読み上げでは、段がいくつあってもタブの並びは1つで、段の名前は各タブの説明として伝わる。
- **答え**: タブを切り替えても、選んだ答えと補足は消えない。隠れたタブのカードの答えも保存され、保存できない表示の返答の文にも入る。
- **JS が動かない表示**: すべてのタブの中身が縦に並び、帯のリンクが目次になる。

## コマンド

`<このスキルのフォルダ>` と `<…>` を置き換えて打つ。どれも、誤りがあれば HTML を書かずに終了コード 1 で止まり、ファイルが読めないなど中身より前の失敗は終了コード 2 で止まる。

データを検証する（HTML は書かない）。

```bash
python3 '<このスキルのフォルダ>/build.py' check '<データの JSON>'
```

読み物の本文と一緒に検証する（本文を差し込むページは、`sections` が空でも通る）。

```bash
python3 '<このスキルのフォルダ>/build.py' check '<データの JSON>' --body '<本文の HTML の断片>'
```

`check` が見るのはデータだけである（`--body` を付ければ、本文のタブのパネルと id も見る）。完成した HTML の外部の読み込み（E-B1）は、`build` のときに見る。本文にタブのパネルを置くページは、`check` にも同じ `--body` を付ける。付けないと、本文のパネルのタブが中身の無いタブとして E-N3 で止まる。

回収した答えを、ページに当てて確かめる（判断ボードで選び方のカードを表へ移す前など）。答えの JSON は、保存先から読んだ文書をすべて `answers` と同じ形（`{"<key>": {"choice", "note", "at"}}`）に写したものである。ページにある key は `answers` の検査（E-A1・選び方のカードごとの上限）で見て、ページに無い key は数だけを出して見ない。ページの状態（回答待ち・随時更新・回答済み）には関係なく見る。

```bash
python3 '<このスキルのフォルダ>/build.py' check '<データの JSON>' --answers '<回収した答えの JSON>'
```

artifact に公開する断片を作る。

```bash
python3 '<このスキルのフォルダ>/build.py' build '<データの JSON>' -o '<書き出す HTML>'
```

手元のブラウザで開く完全な文書を作る。artifact の仕組みの無いところで使うときもこちらにする。

```bash
python3 '<このスキルのフォルダ>/build.py' build '<データの JSON>' -o '<書き出す HTML>' --standalone
```

読み物の本文（HTML の断片）を、ヘッダーの下に差し込んで作る。

```bash
python3 '<このスキルのフォルダ>/build.py' build '<データの JSON>' --body '<本文の HTML の断片>' -o '<書き出す HTML>'
```

作ったセッションの送り元（tmux の位置と、渡したディレクトリの git の repo・repo_url・ブランチ）を JSON で出す。git は作業ディレクトリでなく、渡したディレクトリから引く。

```bash
python3 '<このスキルのフォルダ>/build.py' source --git '<作業しているディレクトリ>'
```

スクリプトの検査を回す（どの作業ディレクトリからでもよい）。

```bash
python3 '<このスキルのフォルダ>/tests/test_build.py'
```

ページのコード（`page.js`）の振る舞いを確かめる検査は、`node` がある環境でだけ走る（無ければ飛ばす）。

ほかに、`build` は `--tmux off`（送り元の tmux を自動で引かない）と `--now 2026-10-19T09:05:00+00:00`（版の時刻を渡す）を受け付ける。どちらも、同じページを作り直して比べたいときに使う。

## 検証の規則

誤りは1件1行で、規則の番号・場所・理由が出る。

```text
E-C3 sections[0].cards[0].recommend: 推奨 "ok" が選択肢（go, fix）に無い
```

| 番号 | 何を弾くか |
|---|---|
| E-F1 | `format` が 1 でない（この誤りがあると、ほかは見ない） |
| E-F2 | 知らない項目がある（前の版の `purpose` は、`kind` に置き換えたことを理由に添えて止める） |
| E-F3 | 必須の項目が無いか、型が違う（型が違う項目の下は見ない） |
| E-H1 | `title`・`why`・リンクの `label`・group の `why`・`request` の項目が空 |
| E-H2 | 送り元の値（repo・issue・branch・tmux・trackers）か URL の誤り |
| E-H3 | `kind`・`status` が決まった値でない |

## 公開と回収（claude.ai の artifact）

### 公開する

- 断片（`--standalone` を付けないもの）を、Artifact の道具で公開する。答える部品（判定カード・判断待ちの束）を持つページは `capabilities: {db: {}}` を付ける。答える部品の無いページ（読み物・指摘の一覧だけのページ）には付けない。答える部品の無いページは、保存のコード（JS）も埋め込みのデータも持たないので、`capabilities` を付けずに公開しても、`db` を参照しているのに宣言していないという注意は出ない。タブのあるページはタブを切り替える JS を持つが、保存先は使わないので、答える部品が無ければ `capabilities` は付けない。
- 作り直したページは、同じファイルのパスか同じ URL へ公開する。保存された答え（`db`）は、出し直しても残る。
- 公開したら、保存先を1回読んで確かめる。Claude Code では `ArtifactData` の `list` で、collection `decisions` を読む。

### 答えの保存の形

ページは、collection `decisions` に、doc id をカードの key にした文書を書く。項目は次の4つである。

```json
{"key": "retry_policy", "choice": "go", "note": "上限は5回にしたい", "at": "2026-10-19T09:12:00.000Z"}
```

- `choice` は選んだ選択肢の key で、まだ選んでいなければ `null` になる。`note` は補足、`at` は最後に書いた時刻である。
- ページは、変えた項目（`choice` か `note`）と `at` だけを書く。その key の文書がまだ無いときだけ、4つの項目をまとめて書く。別の画面で先に選んだものを、古い状態で上書きしないためである。
- 2つの画面がほぼ同時に同じ項目を書くと、後から届いたほうが残る。まだ文書の無いカードで、2つの画面がほぼ同時に違う項目（片方が選択、片方が補足）を初めて書いた場合も、後から届いた書き込みが4つの項目をまとめて書くので、先に書いた項目が消えうる。保存先には取引も「無ければ作る」書き込みも無いので、ページでは防げない。
- 保存できない表示（artifact の外・`db` を付けずに公開したページ）では、ページが選んだ内容から返答の文を組み立て、コピーのボタンと読み取り専用の欄を出す。読む人はそれを写して会話に貼る。

### 答えを受け取る

- 答えはページで選んでもらうのを基本にし、会話の答えも受け付ける。回収するときは、会話で何と言われても（「全部推奨どおり」でも）、毎回保存先を読む。読まずに推奨で埋めると、ページで選んだ別の答えを捨てることになる。
- 会話の答えは、どのカードへのどの答えかが一通りに決まるものだけを受け付け、言葉を補足（`note`）に残す。一通りに決まらなければ、そのカードは未回答のままにし、読み取った内容を1行で返して確かめる。
- 同じカードで、ページの答えと、会話でそのカードを名指しした答え（「Q2 は別案」）が食い違ったら、会話の答えを採り、食い違ったことを1行で返す。
- 「全部推奨どおり」の一言（一括の答え）のときは、ページで選ばれていないカードには推奨の key を、ページで選ばれたカードにはページの答えを入れる。題の頭に「追加: 」のあるカード（案内したあとに足したカード）には当てない。一覧から選ぶ行は、ページで1つも選ばれていなければ `select` の `recommend` の行を選んだものとして扱い、ページで選ばれていればページの答えを採る。
- 推奨と食い違う一括の答え（推奨が分かれているのに「全部 A でいい」など）は、答えを使った外への操作の前に、1行で確かめる。音声の聞き取りで「推奨」の語が抜けることがある。
- 判断ボードでは、回収した答えは、カードを「決まったこと」の表へ移すときに表の行に書く（「判断ボードの更新のしかた」）。下の「回答済みにして出し直す」は使わない。

### 回答済みにして出し直す

1. 保存先を読み（Claude Code では `ArtifactData` の `list` で `decisions`）、文書ごとに `answers` へ写す。形は `{"<カードの key>": {"choice": …, "note": …, "at": …}}` である。一覧から選ぶ行の文書（`<カードの key>--<番号の数字>`）も同じ形で写す。
2. データの `status` を `answered` にし、`answers` を足して `build` で作り直す。
3. 同じ場所へ1回だけ公開する。回答済みのページは、選択肢と補足欄を押せない状態で、`answers` の答えだけを見せる。`answers` に無いカードには「未回答」が出る。
4. 回答済みにしたあとは保存先を読み直さない。保存先の書き込みを止める仕組みは無いので、前に開いていた画面から書かれることがありうる。食い違っても `answers` を正とする。

## 本文（`--body`）の見た目

本文の中の要素には、2通りの見た目がある。

- **class を付けない素の要素にも、最低限の見た目が付く。** 対象は `section`・`h2`・`h3`・`p`・`ul`・`ol`・`table`（中の `th`・`td`）・`pre` である。表には線と余白が付き、`h2` は部品の見出しと同じ形になり、`section` の中の要素には間隔が付く。幅の狭い画面では、素の表は表の中だけが横に送られ、ページは横に揺れない。
- **部品と同じ見た目にしたいときは、下の class を付ける。** 幅の狭い画面で表の行をカードの形に積みたいときは、`hp-table` を付け、各 `td` に `data-label` で列の名前を書く。
- class の付いた要素には、素の要素の見た目は1つも付かない。素の要素の見た目は詳細度 0 の規則なので、本文の中に書いた CSS がいつも勝つ。
- 番号・識別子・状態を並べる表は、本文に HTML で書くより、表の部品（`table`）でデータとして書くほうがよい。エスケープとリンクと幅の狭い画面での形が、部品の側で決まる。

本文で使える class は次のとおりである。この一覧に無い `hp-` で始まる class は、部品の中の作りに使うもので、名前が変わりうる。

| class | 付ける要素 | 見た目 |
|---|---|---|
| `hp-sec` | `section` | 部品の塊。中の要素のあいだに間隔を置く |
| `hp-sec-title` | `hp-sec` の中の `h2` | 部品の見出し |
| `hp-card` | `div`・`article` | 枠の付いた箱 |
| `hp-lbl` | `p`・`span` | 小さく薄い文字の項目名 |
| `hp-table-wrap` | `hp-table` を包む `div` | 幅が足りないとき、表の中だけを横に送る |
| `hp-table` | `table` | 線の付いた表。幅の狭い画面では行がカードの形に積まれる |
| `data-label` 属性 | `hp-table` の中の `td` | 幅の狭い画面で、欄の上に出る列の名前 |
| `hp-chip` | `span` | 札の形。下の色の class と一緒に付け、文字は `glossary.md` の札の言葉を使う |
| `hp-ev-verified`・`hp-ev-sourced`・`hp-ev-guess` | `hp-chip` の `span` | 確かめた度合いの札の色 |
| `hp-sev-high`・`hp-sev-mid`・`hp-sev-low` | `hp-chip` の `span` | 重さの札の色 |
| `hp-ad-adopted`・`hp-ad-partial`・`hp-ad-rejected` | `hp-chip` の `span` | 採否の札の色 |
| `hp-tabpanel` | 本文の一番外の `section`・`div`（`id` はタブの key） | タブの中身（パネル）。中の要素のあいだに 36px を置く。「タブで分ける」の節 |
| `hp-tab-same` | パネルの最初の見出し（`hp-sec-title` と一緒に付ける） | タブの名前と同じ見出し。JS が動いているあいだは隠れる |

## 書くときの注意

- `--body` の本文は、信頼したコードとして扱われる。エスケープされないので、本文の script・イベントの属性・CSS は、答えの処理やヘッダーを変えられる。本文はページを作るセッションが自分で書くものに限る。issue の本文やレビューの出力など、外から来た文章を見せるときは、`--body` に写さず、データの文字列に入れる（平文として出る）。
- `--body` の本文では、相対のパス（`/assets/chart.png`・`helper.js` など）でファイルを読み込まない。artifact に公開したページは1枚だけで、ほかのファイルを解決しない。画像は `data:` の URL か、HTML と CSS で描く。`build.py` が止めるのは Google Fonts 以外の外部の読み込み（E-B1）だけで、相対のパスは止めない。
- `--body` の本文の中では、型の色と文字のトークン（`var(--surface)`・`var(--line)`・`var(--accent)`・`var(--muted)`・`var(--font-mono)` など）を使う。そうすれば明暗の表示がそろう。本文の中の幅の狭い画面への対応は、素の表と「本文（`--body`）の見た目」の class が受け持つ範囲のほかは、本文を書く側が持つ。
- タイトルはページの名前にする。説明はタイトルに足さず、`why` に書く。

## 限界

- 入口の発火は、この description との一致に頼っている。発火を確かめたのは Claude Code だけで、ほかのツールでは名前を指して読み込ませる。
- 保存先の書き込みを止める仕組みは無い。回答済みにしたあとの書き込みは、`answers` を正とすることで扱う。
- 2つの画面がほぼ同時に同じ項目を書いたとき、またはまだ文書の無いカードの違う項目を初めて書いたときは、後から届いた書き込みが残る（「答えの保存の形」の節）。
- `--body` の本文の安全さは、外部の読み込みが無いことまでしか確かめない。
- 外部の課題管理の ID としてリンクにできるのは `<接頭辞>-<数字>` の形だけである。数字だけの ID や小文字の接頭辞の ID はリンクにならない。`--body` の本文の中の `#N`・ID・ページの中の識別子も、リンクには変えない。
- 番号を2つだけ並べた書き方（`候補43・41`）は止められない。後ろの数字は文字のまま出る。
- `PR #N` のリンク先（`/pull/N`）は GitHub の形である。GitLab などのリポジトリでは、PR のリンクが開けない。
- `owner/repo#N` のリンク先のホストは、近い送り元の `repo_url` のホストと同じになる。ほかのホストのリポジトリは指せない。
- `#N` が実在の issue か、別のリポジトリの番号を `#N` と書いていないかは、ネットワークを使わないスクリプトでは確かめられない。
- 問いのカードの書き方の検査（E-Q1〜E-Q3）は表記の決まりで、中身が分かるかは見ない。選択肢の名前の括弧書きの中は見ないので、「実施する（推奨どおり）」は止まらない。ほかの文書の符号を説明なしで使っていないか（`2FA` のような普通の語と見分けられない）と、関連リンクのアンカーが実在するか（ネットワークを使わない）も確かめない。
- 図・読み比べ・「何もしなければ受け入れ」の印付けの部品は、まだ無い。
- タブを選んだときに書き換える URL の `#` が、artifact の表示の外側の URL（共有するリンク）に届くかは、表示の側の作りによる。手元で開く完全な文書（`--standalone`）では、アドレス欄の `#` が変わる。
- 本文のタブのパネルは標準の `html.parser` で読むので、ブラウザと読み方が違う形（表の中にパネルを書くなど）は見落としうる。パネルの要素を `section` と `div` に絞り、`/>` で閉じる書き方と同じ属性の2回を止めて、ずれる形を減らしている。
- 本文の id を `hp-` で始めない決まりを検査するのは、タブのあるページだけである。タブの無いページの本文に `hp-` で始まる id を書くと、ページの JS が操作する要素と取り違えうる。
- 段の数には上限が無い。段が多いと、上に貼り付く帯が画面の多くを占める。
