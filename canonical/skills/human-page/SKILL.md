# human-page — 人に見せて答えてもらうページ

人に判断や確認を求めるページは、作るたびに形がばらばらだと、読む人が毎回「どこを見て、どう答えるか」を探し直すことになる。このスキルは、ページの形・部品・札の言葉・答えの返し方を1つにそろえる。ページを作る側はデータ（JSON）だけを書き、同じフォルダの `build.py` が検証してから描く。

## 前提

- Python 3.9 以上。標準ライブラリだけを使い、追加のインストールは要らない。
- tmux と git は無くても動く。tmux の中で走らせると、送り元にペインの位置が自動で入る。
- このフォルダだけで動く。`build.py` は自分の置き場所から型・CSS・JS・用語集を読み、走らせたときの作業ディレクトリに頼らない。以下のコマンドの `<このスキルのフォルダ>` は、このスキルを読み込んだときに示されるフォルダのパスに置き換える。

## いつ使うか

- 人に判断を選んでもらう・確認してもらう・回答を集めるページを作るとき。
- いくつかの作業から届いた判断待ちを、1枚にまとめて見せるとき。
- レビュー（別のモデルのセカンドオピニオンを含む）の指摘と、それぞれを採ったかを一覧にして見せるとき。
- 見取り図や説明のような読み物のページを作るとき。中身は自由に書き、ヘッダーだけをこのスキルでそろえる。
- 回収した答えで、ページを「回答済み」にして出し直すとき。

使わないのは、リポジトリに入れる文書（README など）や、ページを伴わない会話の返答である。

## 隣の指示との順序

claude.ai の artifact に公開するときは、Artifact の道具の説明と組み込みの `artifact-design` も読み込まれる。そのときの分担は次のとおりである。

- ページの形・部品・札の言葉・色と文字はこのスキルが決める。`artifact-design` が言う「すでにある設計の決まり」にあたるので、新しい見た目は作らない。
- page contract（断片で書く・`<title>` を先頭に置く・色のトークンと暗い表示・外部の読み込みは Google Fonts だけ・幅の狭い画面）は、`build.py` が出す断片がすでに満たしている。
- 公開の操作そのもの（最初の呼び出しの順・`icon`・`description`）は、Artifact の道具の説明に従う。

## 作り方の流れ

1. **目的を決める。** そのページで何をしてもらうかを先に決め、データの `purpose` に書く。
2. **部品を選ぶ。** 下の「目的と部品」の表から選ぶ。
3. **データを書く。** 書き方は「データの書き方」の節と `examples/` の見本にある。書き出し先は、リポジトリに入れない一時の場所にする。
4. **検証する。** `check` で誤りが無くなるまで直す。
5. **作る。** artifact に公開するなら断片（既定）、手元で開くなら `--standalone` で作る。版の時刻は作ったときの時刻になるので、公開の直前に作る。
6. **公開する。** artifact なら「公開と回収」の節のとおり。
7. **回収して、回答済みにする。** 答えを読み取ったら `status` を `answered` にし、答えを `answers` に写して1回だけ作り直し、同じ場所に公開する。

## 目的と部品

| 目的（`purpose`） | 勧める部品 | 答える部品 | 状態（`status`）の目安 |
|---|---|---|---|
| `decide`（判断してもらう） | 判定カード（`decisions`）・判断待ちの束（`bundle`） | ふつうは持つ | 答えを待つ間は `awaiting`。束のように判断が足されていくなら `live`。回収したら `answered` |
| `grasp`（把握してもらう・見取り図） | `--body` の本文 | ふつうは持たない。確かめてほしい点があれば判定カードを足してよい | `live` |
| `review`（レビューの結果を見てもらう） | 指摘の一覧（`findings`） | ふつうは持たない。採否を決めてほしい指摘があれば判定カードを足す | `live`。判定カードを足したら `awaiting` |

目的は部品の組み合わせを縛らない。答える部品の有無は、目的と別に選んでよい。

どのページにも、次の部品が必ず入る。

- **ヘッダー**: タイトルの上に小さな文字で2行が出る。1行目は送り元（リポジトリ・tmux のウィンドウとペイン・issue・ブランチ）で、無い項目は省かれる。2行目は版（`版 YYYY-MM-DD HH:MM JST（最終更新）`）と状態である。版は作ったときの時刻を JST で書いたもので、artifact のサービスの内部の版の番号は出さない。
- **なぜこのページか**: `why` の1文。読む人が経緯を覚えていなくても、なぜいま読むのかが分かるように、きっかけの出来事を書く。
- **関連リンク**: `links`。issue・PR・計画の文書など、答えるときに開きたいものを並べる。

## データの書き方

ページ1枚を JSON 1つで書く。知らない項目は誤りとして弾かれる（打ち間違いを黙って無視しないため）。見本は `examples/` にある。

- `examples/decide.json`: 判定カードのページ
- `examples/bundle.json`: 別のリポジトリの2つの作業の判断待ちをまとめたページ
- `examples/review.json`: レビューの指摘の一覧のページ
- `examples/grasp.json` と `examples/grasp-body.html`: 読み物のページ（ヘッダーだけをそろえる）

| 場所 | 項目 | 必須 | 決まり |
|---|---|---|---|
| ページ | `format` | 必須 | `1` |
| ページ | `title` | 必須 | ページの名前。`<title>` と見出しになる |
| ページ | `purpose` | 必須 | `decide`・`grasp`・`review` のどれか |
| ページ | `status` | 必須 | `awaiting`（回答待ち）・`answered`（回答済み）・`live`（随時更新）のどれか |
| ページ | `why` | 必須 | なぜこのページかの1文 |
| ページ | `source` | 必須 | 送り元。下の行 |
| ページ | `links` | 任意 | `{label, url}` の並び。url は `https://` か `http://` で始める |
| ページ | `sections` | 必須 | 部品の並び。`--body` を渡すときは空でもよい |
| ページ | `answers` | 任意 | 回収した答え。`status` が `answered` のときは必須 |
| source | `repo` | 必須 | リポジトリの名前 |
| source | `repo_url` | 任意 | リポジトリの URL。あれば issue・ブランチ・本文の `#N` がリンクになる |
| source | `issue` | 任意 | issue の番号（1以上の整数） |
| source | `branch` | 任意 | ブランチの名前 |
| source | `tmux` | 任意 | `{window, pane, name}`。ページの `source` で書かなければ、作ったセッションのペインから引く |
| `decisions` | `title`・`cards` | 必須 | 判定カードを1枚以上 |
| `bundle` | `title`・`groups` | 必須 | 各 group は `source`・`title`・`cards`（必須）と `why`（任意） |
| `findings` | `title`・`items` | 必須 | `lane`（任意・どのモデルの指摘か）。各 item は `text`・`severity`（`high`・`mid`・`low`）・`adopted`（`adopted`・`partial`・`rejected`）・`reason` が必須で、`evidence` は任意 |
| カード | `key` | 必須 | 英小文字で始まり、英小文字・数字・`_`・`-` が続く64文字まで。ページ全体で重ねない（保存先の文書の id になる） |
| カード | `title`・`recommend`・`reason`・`options` | 必須 | `recommend` は推奨する選択肢の key。`reason` は推奨の根拠。`options` は2つ以上 |
| カード | `tag`・`points`・`evidence` | 任意 | `tag` は判断の番号などの短い札。`points` の各要素は文字列か `{text, evidence}` |
| 選択肢 | `key`・`label` | 必須 | `kind` は任意で、選んだときの色（`go`・`fix`・`warn`・`no`） |

- 推奨は先に出る。カードの中で、タイトルのすぐ下に推奨の選択肢と根拠が出て、選択肢のボタンにも「推奨」の札が付く。
- 確かめた度合い（`evidence`）は `verified`（確かめた）・`sourced`（出典あり・未確認）・`guess`（推測）で書く。カード・要点・指摘に付けられる。
- 札とページの固定の文は `glossary.md` の言葉で出る。データには英語の key を書く。用語は `glossary.md` の「和訳しない用語」に合わせる（ブランチを「枝」と書かない、など）。
- 本文の文字列はすべて平文として扱われ、HTML にはならない。効く書式は3つだけで、`` `…` `` がコードの書式に、`https://…` がリンクに、`#N` が issue へのリンク（近い送り元に `repo_url` があるとき）になる。束の group の中では group の送り元を使い、group に `repo_url` が無ければリンクにしない。
- 判断待ちの束を作るときは、判断を出す側のセッションが `build.py source --git <作業しているディレクトリ>` で自分の送り元を出し、カードと一緒に束を作る側へ渡す。カードの key は、作業ごとに前置きを付けるなどして、ページ全体で重ならないようにする。

## コマンド

`<このスキルのフォルダ>` と `<…>` を置き換えて打つ。どれも、誤りがあれば HTML を書かずに終了コード 1 で止まり、ファイルが読めないなど中身より前の失敗は終了コード 2 で止まる。

データを検証する（HTML は書かない）。

```bash
python3 '<このスキルのフォルダ>/build.py' check '<データの JSON>'
```

artifact に公開する断片を作る。

```bash
python3 '<このスキルのフォルダ>/build.py' build '<データの JSON>' -o '<書き出す HTML>'
```

手元のブラウザで開く完全な文書を作る。artifact の仕組みの無いところで使うときもこちらにする。

```bash
python3 '<このスキルのフォルダ>/build.py' build '<データの JSON>' -o '<書き出す HTML>' --standalone
```

読み物の本文（HTML の断片）を、ヘッダーの下に差し込んで作る。

```bash
python3 '<このスキルのフォルダ>/build.py' build '<データの JSON>' --body '<本文の HTML の断片>' -o '<書き出す HTML>'
```

作ったセッションの送り元（tmux の位置と、渡したディレクトリの git の repo・repo_url・ブランチ）を JSON で出す。git は作業ディレクトリでなく、渡したディレクトリから引く。

```bash
python3 '<このスキルのフォルダ>/build.py' source --git '<作業しているディレクトリ>'
```

スクリプトの検査を回す（どの作業ディレクトリからでもよい）。

```bash
python3 '<このスキルのフォルダ>/tests/test_build.py'
```

ほかに、`build` は `--tmux off`（送り元の tmux を自動で引かない）と `--now 2026-10-19T09:05:00+00:00`（版の時刻を渡す）を受け付ける。どちらも、同じページを作り直して比べたいときに使う。

## 検証の規則

誤りは1件1行で、規則の番号・場所・理由が出る。

```text
E-C3 sections[0].cards[0].recommend: 推奨 "ok" が選択肢（go, fix）に無い
```

| 番号 | 何を弾くか |
|---|---|
| E-F1 | `format` が 1 でない（この誤りがあると、ほかは見ない） |
| E-F2 | 知らない項目がある |
| E-F3 | 必須の項目が無いか、型が違う（型が違う項目の下は見ない） |
| E-H1 | `title`・`why`・リンクの `label`・group の `why` が空 |
| E-H2 | 送り元の値（repo・issue・branch・tmux）か URL の誤り |
| E-H3 | `purpose`・`status` が決まった値でない |
| E-P2 | 状態と部品の組み合わせの誤り（回答待ちなのに答える部品が無い・回答済みでないのに `answers` がある・回答済みなのに `answers` が無い） |
| E-C1 | カードの key が形に合わないか、ページの中で重なる |
| E-C2 | 選択肢が2つ未満か、選択肢の key が形に合わないか重なる |
| E-C3 | 推奨が選択肢の中に無い |
| E-C4 | 推奨の根拠が空 |
| E-C5 | カードのタイトル・札・要点・選択肢の label が空 |
| E-T1 | 札の値（`evidence`・`severity`・`adopted`・`kind`）が決まった値でない |
| E-S1 | 部品の `type`・`title`・中身の誤り（知らない type・カードや item が0件・部品も本文も無い） |
| E-S2 | 指摘の本文・理由・`lane` が空 |
| E-A1 | `answers` の key がカードに無いか、`choice` がそのカードの選択肢でも `null` でもないか、`note`・`at` が文字列でない |
| E-B1 | 完成した HTML に、Google Fonts 以外の外部の読み込みがある（`--body` の本文から入ったものを含む） |

## 公開と回収（claude.ai の artifact）

### 公開する

- 断片（`--standalone` を付けないもの）を、Artifact の道具で公開する。答える部品を持つページは `capabilities: {db: {}}` を付ける。読み物や指摘の一覧だけのページには付けない。
- 作り直したページは、同じファイルのパスか同じ URL へ公開する。保存された答え（`db`）は、出し直しても残る。
- 公開したら、保存先を1回読んで確かめる。Claude Code では `ArtifactData` の `list` で、collection `decisions` を読む。

### 答えの保存の形

ページは、collection `decisions` に、doc id をカードの key にした文書を書く。項目は次の4つである。

```json
{"key": "retry_policy", "choice": "go", "note": "上限は5回にしたい", "at": "2026-10-19T09:12:00.000Z"}
```

- `choice` は選んだ選択肢の key で、まだ選んでいなければ `null` になる。`note` は補足、`at` は最後に書いた時刻である。
- ページは、変えた項目（`choice` か `note`）と `at` だけを書く。その key の文書がまだ無いときだけ、4つの項目をまとめて書く。別の画面で先に選んだものを、古い状態で上書きしないためである。
- 2つの画面がほぼ同時に同じ項目を書くと、後から届いたほうが残る。
- 保存できない表示（artifact の外・`db` を付けずに公開したページ）では、ページが選んだ内容から返答の文を組み立て、コピーのボタンと読み取り専用の欄を出す。読む人はそれを写して会話に貼る。

### 答えを受け取る

- 答えの場所はページの1つだけである。会話で答えを1件ずつ受け取る形は使わない。
- 例外は「全部推奨どおり」の一言である。このときは、ページで選ばれていないカードには推奨の key を、ページで選ばれたカードにはページの答えを入れる。ページに保存した答えがあれば、その項目はページの答えを正とする。

### 回答済みにして出し直す

1. 保存先を読み（Claude Code では `ArtifactData` の `list` で `decisions`）、文書ごとに `answers` へ写す。形は `{"<カードの key>": {"choice": …, "note": …, "at": …}}` である。
2. データの `status` を `answered` にし、`answers` を足して `build` で作り直す。
3. 同じ場所へ1回だけ公開する。回答済みのページは、選択肢と補足欄を押せない状態で、`answers` の答えだけを見せる。`answers` に無いカードには「未回答」が出る。
4. 回答済みにしたあとは保存先を読み直さない。保存先の書き込みを止める仕組みは無いので、前に開いていた画面から書かれることがありうる。食い違っても `answers` を正とする。

## 書くときの注意

- `--body` の本文は、信頼したコードとして扱われる。エスケープされないので、本文の script・イベントの属性・CSS は、答えの処理やヘッダーを変えられる。本文はページを作るセッションが自分で書くものに限る。issue の本文やレビューの出力など、外から来た文章を見せるときは、`--body` に写さず、データの文字列に入れる（平文として出る）。
- `--body` の本文の中では、型の色と文字のトークン（`var(--surface)`・`var(--line)`・`var(--accent)`・`var(--muted)`・`var(--font-mono)` など）を使う。そうすれば明暗の表示がそろう。本文の中の幅の狭い画面への対応は、本文を書く側が持つ。
- タイトルはページの名前にする。説明はタイトルに足さず、`why` に書く。

## 限界

- 入口の発火は、この description との一致に頼っている。発火を確かめたのは Claude Code だけで、ほかのツールでは名前を指して読み込ませる。
- 保存先の書き込みを止める仕組みは無い。回答済みにしたあとの書き込みは、`answers` を正とすることで扱う。
- 2つの画面がほぼ同時に同じ項目を書いたときは、後から届いたほうが残る。
- `--body` の本文の安全さは、外部の読み込みが無いことまでしか確かめない。
- 図・長いページのタブ・読み比べ・「何もしなければ受け入れ」の印付けの部品は、まだ無い。
