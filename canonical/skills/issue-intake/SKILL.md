# issue-intake — issue 着手時の認識合わせ

issue に着手する瞬間に、「この issue で何を作るか」の認識合わせを1回だけ通す。issue は思いつきや問題が起きたときに書かれるので、書かれた時点では足りていないことが多い。足りないまま作ると、実装したあとで認識のずれが見つかり、後戻りになる。このスキルは、足りない部分を着手の前に見える形にし、owner が違和感を持つかどうかを1回で確かめる。

## いつ使うか

- 特定の issue を指して作業を始めるとき全般。統括（親）のセッションでも、単独のセッションでも使う。
- 特定の issue を子へ委譲するとき。委譲する側（親）が、子へ渡す前に通す。
- issue の指し方は問わない。番号・URL・タイトル・本文の貼り付けのどれでもよい。
- issue の無い作業（文章で始まる作業）では使わない。その作業で認識合わせをしたいなら、先に issue を起こしてから使う。issue を起こすかどうかは作業を始める人が決める。

## いつ使わないか（省く条件は2つだけ）

省くのは次の2つのときだけである。**これ以外の理由では省かない。** issue が小さい・自明に見える・既存のやり方を踏襲するだけに見える、は省く理由にならない。省くかどうかを AI の側で判断しない。

1. **owner が要らないと言ったとき。** 委譲なら、依頼の書面にそう書いてある（例:「認識合わせ: 省略（owner の指示）」）。
2. **確定版のコメントが既にあるとき。** 「1. 取り込みの最初の確認」の手順で確かめ、確定版を読んで前提にする。自分では認識合わせをやり直さない。

## 1. 取り込みの最初の確認

### 1-1. issue を特定する

`gh` が使えないときは「9. 手元に無いもの」に従う。

- 番号・URL は、そのまま使う。

  ```bash
  gh issue view <番号> --json number,title,body,labels,url
  ```

- タイトルは、タイトル全体をタイトルの中から検索する。一部の語だけで探すと、関係の近い issue が何件も返る。

  ```bash
  gh issue list --search '<タイトル全体> in:title' --state all --json number,title --limit 10
  ```

- 本文の貼り付けは、貼り付けた本文の中の特徴のある語句を1つ選び、本文の中から検索する。

  ```bash
  gh issue list --search '"<本文の語句>" in:body' --state all --json number,title --limit 10
  ```

- 検索の語に `'` が含まれるときは、シェルの引用が途中で閉じないように渡す（例: `'\''` で閉じ直す）。
- 特定できたとみなすのは、タイトルなら**タイトルが完全に一致する候補が1件**のとき、本文の貼り付けなら**候補の本文（`gh issue view` で読む）が貼り付けた本文と一致する候補が1件**のときである。このときは聞かずに特定したことにし、出力の1行目に「#<番号> と判断した」と書く。外れていれば、owner が1行で指せる。
- **一致する候補が1件にならないときは、止まって依頼した人に「どの issue か」を聞く。** 候補が無ければ「issue が見つからない。issue の無い作業として進めるか、issue を起こすか」を聞く。**issue を特定できないことを「issue の無い作業」に畳まない。** issue の無い作業だと決めるのは、依頼した人の明示だけである。
- 候補が複数あるときは、どの issue かだけを聞く。どの候補の本文で3つの出力を作るかを AI が選ぶと、特定できない issue を AI の判断で畳むことになるからである。認識合わせの1往復は、特定したあとに行う。
- 本文が貼り付けられていて、それに当たる issue が見つからないときは、貼り付けた本文から3つの出力を「issue が未特定の下書き」として作り、「issue の無い作業として進めるか、issue を起こすか」と一緒に出す。issue を起こすと決まったら、起こした issue の本文が提示と同じである限り、そのときの応答を確定として扱い、新しい issue に投稿する。

### 1-2. 既存の認識合わせのコメントを調べる

次のコマンドで、認識合わせの印（確定版か深掘り中か）で始まるコメントのうち、**最後の1件**の状態・投稿者の種類・見出しの数・URL を1行で得る。リポジトリの作業ディレクトリで打つ（`{owner}/{repo}` は `gh` がいまのリポジトリで埋める）。`gh` が使えないときは「9. 手元に無いもの」に従う。

```bash
gh api --paginate 'repos/{owner}/{repo}/issues/<番号>/comments?per_page=100' --jq '.[] | select(.body | test("^\\s*<!-- issue-intake:(confirmed|pending) v[0-9]+ -->")) | [(.body | capture("issue-intake:(?<s>confirmed|pending)").s), (if (.author_association | IN("OWNER","MEMBER","COLLABORATOR")) then "member" else "other" end), ([(.body / "\n")[] | select(startswith("### "))] | length | tostring), .html_url] | @tsv' | tail -n 1
```

- コメントはページを送って全件を読む。`gh issue view --json comments` は先頭の100件までしか返さないので使わない。100件を超える issue で、後ろにある深掘り中の版を見落とし、古い確定版を拾ってしまう。
- 印は本文の先頭で見る（前の空白は許す）。印を話題にして引用しただけのコメントは拾わない。
- 返った1行で、次のように動く。**止まる場面では、自分でやり直さずに依頼元（依頼元がいなければ依頼した人）へ知らせる。** 黙ってやり直すと、owner への2回目の提示になる。

| 返った値 | 意味 | 動き |
|---|---|---|
| 空 | 認識合わせのコメントが無い | 自分で認識合わせを通す（2 以降） |
| `confirmed`・`member`・見出し4以上 | 確定版がある | 読んで前提にし、自分では通さない |
| `pending` | 深掘りの途中である | 止まって知らせる。確定版が出るのを待つ |
| `other` | 候補はあるが、投稿者がリポジトリの所有者・メンバー・共同作業者ではない | 止まって「候補はあったが除外した」と知らせる |
| 見出しが4未満 | 印はあるが形が壊れている | 止まって知らせる |

- **依頼の書面に認識合わせのコメントの URL があるときは、上のコマンドが返した URL と文字列として一致するかを見る。** 一致すれば上の表どおりに動く。一致しなければ（別のリポジトリ・別の issue・古い版を指している）、止まって食い違いを知らせる。
- この判定は、owner が確定させたことを証明するものではない。取り違えと第三者のコメントを除くだけである。確定版を投稿するのはこのスキル自身で、投稿は owner の実際の応答の後に限る（5）。

### 1-3. 応答する人がいるかを決める

- この場に owner（または owner とやり取りできる依頼した人）がいるなら、5 で直接見せる。
- 委譲された子のように、この場に答える人がいないなら、5 で対話の問いかけをしない。3つの出力までを作り、依頼元へ渡して待つ（5 の最後）。

### 1-4. テンプレートと必要な欄を確かめる

- リポジトリの issue テンプレートを見る。

  ```bash
  ls .github/ISSUE_TEMPLATE/
  ```

- issue がどのテンプレートに当たるかを、ラベルと見出しで決める。当たったテンプレートの必須の欄が埋まっているかを見て、欠けは「issue に書いていないが要ること」に入れる。
- どれに当たるか決められなければ、それ自体を「issue に書いていないが要ること」に入れる。
- テンプレートが無ければ、目的と作業内容が書かれているかだけを見る。

## 2. 観点を先に固定する

issue 本文から出発して「書いてある／ない」を分けると、書かれていないものは見えない。そこで、**issue 本文を当てる前に観点の一覧を決め**、それを本文に当てて差分を出す。一覧は次の4つからなる。

1. **固定の問い3つ**（どのリポジトリでも同じ）
   - これが完成したあとも、人が手を動かして埋める残りはどこか。
   - いま人や前の世代が暗黙にやっていて、目的の文に名前が付いていないものは何か。
   - 達成したかどうかを何の数で見るか。
2. **当たったテンプレートの必須の欄**（テンプレートが無ければ「目的」と「作業内容」）。
3. **リポジトリの文脈の置き場で読んだもの。** 見つけ方は、owner の明示の指示を優先し、無ければ入口の文書（`CLAUDE.md` / `AGENTS.md`）の案内をたどる。案内が無ければ、出力に「このリポジトリでは文脈の置き場が分からなかった」と書く。リポジトリ特有のことは問いにせず、その置き場を読みに行く（このスキルに写すと二重に持つことになる）。
4. **owner 特有の観点の枠。** owner 特有の観点を持つ部品へ受け渡す枠である。受け渡し先を見つける方法が決まるまでは「未接続」と書き、推測で探さない。

文脈の置き場の案内や owner 特有の観点の受け渡し先が無いときの動きは、「9. 手元に無いもの」にまとめてある。

## 3. 3つの出力

**issue の要約は出さない。** owner が既に知っていることを読ませると、違和感の検査が薄まる。

- **この issue でやること**: 1〜3文で書く。外れていれば、読んだ人が1行で「そこは違う」と指せる形にする。数・前と後・変わるものの名前のどれかを必ず入れる。
  - 曖昧で当たっている文は、違和感を生まないまま通る。例えば「計画的な交代を1つのコマンドにする」は当たっていても何も指せない。「交代のとき人が手を動かすのは2回で、それを0回にする」なら、外れていればすぐ指せる。
- **issue に書いていないが要ること**: 1項目1行で書く。テンプレートの欄の欠けもここに入れる。
- **どの観点で見たか**: 2 の一覧を1行ずつ書く。固定の問いは問いの文を繰り返さず、短い名前と当てた結果だけを書く。

3つ合わせて20行以内を目安にする。owner が違和感の有無を数十秒で判定できる大きさである。超えるなら、それ自体が深掘りの材料になる。

出力の形は次のとおりである。

```text
（#<番号> と判断した: <特定の仕方>）  ← 検索で特定したときだけ
この issue でやること:
- …
issue に書いていないが要ること:
- …
- ［別モデル］…
どの観点で見たか:
- 完成後の人手の残り: …
- 暗黙の工程: …
- 達成を見る数: …
- テンプレート: <名前>（必須の欄の欠け: … ／ なし）
- 文脈の置き場: <読んだもの> ／ 分からなかった
- owner 特有の観点: 未接続
- 別モデル: <モデル>・<N> 件中 <M> 件を採った ／ 返答なし ／ できなかった（理由）
```

## 4. 別のモデルへ1回だけ問い合わせる

- **自分と違うモデルに、1回だけ**問い合わせる。自分と違う会社のモデルを選ぶのがよい。同じ会社のモデルは同じところを見落としやすい。
- 問い合わせには、issue 本文・3つの出力・観点の一覧を渡す。問いは次のとおりに固定する。

  > この一覧から漏れているものは何か。issue の目的を満たすのに要るのに、一覧のどこにも無いものを挙げよ。一覧にあるものの言い直しは挙げない。無ければ無いと書け。

- 返ってきたものは「［別モデル］」の印を付けて「issue に書いていないが要ること」に混ぜる。owner が別に読むものは増やさない。混ぜるのは3件までにし、残りは件数だけを「どの観点で見たか」に書く。
- **2周目はしない。** 「その観点でよいか」を同じ場で確かめ直すと終わりが無い。
- **待ち時間に上限を置く。** owner は提示を待っている。上限を超えたら、出力に「問い合わせたが返答が無かった」と書いて進む。
- **issue の内容を外へ送ることになる。** リポジトリの取り決めで外へ出せない内容なら、取り決めが許す別のモデル（社内の窓口や手元のモデルなど）に問い合わせる。許されるモデルが1つも無いときだけ問い合わせをせず、「どの観点で見たか」に「別モデル: できなかった（理由）」と書く。省くのは問い合わせだけで、3つの出力と owner の反応は必ず通る。
- 問い合わせる手段が無いときは「9. 手元に無いもの」に従う。
- 手段の例として、`so-compare` の1レーンを使う形を示す。プロンプトはファイルから渡し（issue 本文が長く、引数に直接書くと引用符で崩れる）、出力先はリポジトリの外の一時ディレクトリにする（リポジトリの中に置くと、追跡されうる）。

  ```bash
  SO_TIMEOUT=180 SO_CLAUDE_TIMEOUT=180 so-compare -f <プロンプトのファイル> -o <リポジトリの外の一時ディレクトリ> --codex-only
  ```

  | セッションのモデル | 使うレーン |
  |---|---|
  | Claude | `--codex-only` |
  | Codex | `--claude-only` |
  | Cursor | 実際に動いているモデルと違う会社のレーン（Claude が動いているなら `--codex-only`、それ以外なら `--claude-only`） |

  `so-compare` は空で返ったときに1回だけ延ばして再試行するので、上の上限では、最悪の待ちは codex でおよそ450秒、claude でおよそ360秒になる。

## 5. 反応を受け、深掘りの合図が出たかを決める

- **往復は1回だけにする。** 1往復とは、提示1回と、owner の**実際の応答**1回である。確認の段をこれ以上足さない。
- **応答が無いことを承認として扱わない。** 離席やセッションの終了で応答が無ければ、投稿せずに止まる。3つの出力の下書きはファイルに残し、置き場を出力に書く（置き場はリポジトリの取り決めに従う。取り決めが無ければ「9. 手元に無いもの」に従う）。
- 応答を受けたら、深掘りの合図が出たかを決める。合図は3つである。
  1. owner が違和感を指したとき。
  2. 「分からない」が残ったとき。
  3. 別のモデルが挙げた漏れを、owner が本物と認めたとき。
- owner が応答し、違和感も「分からない」も指さず、別のモデルの漏れも認めなければ、確定である。
- **応答する人がこの場にいないとき（1-3）は、3つの出力を依頼元へ渡して待つ。** 依頼元が owner に見せて応答を受け、6 のとおりに投稿し、コメントの URL を返してくる。受け取ったら 1-2 の手順で確かめて読み、前提にして作業を再開する。渡す手段の取り決めが無ければ「9. 手元に無いもの」に従う（最終の応答として3つの出力を返し、止まる）。

## 6. issue コメントに残す

- **合図が出なければ確定版を、出たら深掘り中の版を投稿する。**
  - 深掘り中の版を先に投稿するのは、深掘りが長引いたり担当が替わったりしても途中経過が会話にしか残らない状態を避け、issue を見る人に進行中であることを見せるためである。
  - 深掘り中の版に確定版の印を付けないのは、委譲された側の判定（1-2）に未確定の版を拾わせないためである。
- 投稿は、issue を見られる人なら誰でも見られる場所に置く。issue より見られる人が限られる場所だけに置かない。
- 確定版の形は次のとおりである。1行目は機械で探すための印で、HTML コメントなので表示されない。印の `v1` は書式の版で、後で見出しの文言を直しても古い確定版を読めるようにするためのものである。

  ```markdown
  <!-- issue-intake:confirmed v1 -->
  ## 着手時の認識合わせ（確定版）

  ### この issue でやること
  - …

  ### issue に書いていないが要ること
  - …

  ### どの観点で見たか
  - …

  ### 深掘り
  - なし ／ あり（出た合図: …・結果の置き場: …）
  ```

- 深掘り中の版は、1行目を `<!-- issue-intake:pending v1 -->`、見出しを「着手時の認識合わせ（深掘り中）」にし、見出しの4つは確定版と同じにする。「深掘り」の節に、owner が指した違和感と、「深掘りを終えたら確定版を別のコメントとして投稿する。担当はこの認識合わせを通した人」を書く。
- 別のモデルの指摘は、採ったものだけを差分に印付きで残し、採らなかったものは件数だけを「どの観点で見たか」に書く。
- 投稿は本文をファイルに書いてから行う。`gh` で投稿できないときは「9. 手元に無いもの」に従う。

  ```bash
  gh issue comment <番号> --body-file <ファイル>
  ```

- 投稿したら、コメントの URL を出力に書く。委譲するなら、その URL を依頼の書面に載せる。
- **最後の認識合わせのコメントが有効である。** 確定のあとで内容が変わったら、新しい確定版を別のコメントとして投稿する。**issue 本文を書き換えたときも同じである。** 確定版は本文の書き換えで機械的には無効にならないので、書き換えた人（owner か統括）がこのスキルを通し直し、新しい確定版を投稿する。依頼の書面に古い URL を載せていたら、書き換える（古い URL のままだと、委譲された側は 1-2 の照合で止まる）。

## 7. question-driven-design への受け渡しと、確定版への戻り

- 合図が出たら、`question-driven-design` に受け渡す。3つの出力・出た合図・owner の言葉をそのまま渡し、分かっていることを聞き直させない。
- **深掘りを終えたら、次の工程へ進む前に 6 へ戻り、確定版を投稿する。** 深掘り中の版が最後のコメントのまま残ると、委譲された側は止まり続ける。
- 合図が出なかったとき、または確定版を投稿したあとは、次の工程へ進む。**どの工程へ進むかはリポジトリのフローに従う。** このスキルは次の工程を名指ししない。

## 8. 後から見つかった抜けの足し方

認識合わせで拾えなかった要件が後から見つかったら、**見つけたその場で**、次の3つの行き先のどれに足すかを決めて記録する。「その観点でよいか」は1つの issue の中では決着しないので、issue をまたいで育てる。

1. **どのリポジトリでも同じ観点**: このスキルの固定の問いに足す。このスキルを直す issue を起こす（直すのはその issue の担当）。
2. **owner 特有の観点**: owner 特有の観点を持つ部品へ足す。受け渡し先が未接続のあいだは、その部品を作る場（issue など）に記録する。
3. **リポジトリ特有のもの**: そのリポジトリの文脈の置き場に書く。

## 9. 手元に無いものがあるとき

依存が欠けたときの動きを次に決めておく。欠けていることは出力に書く。

| 依存 | 無いときの動き |
|---|---|
| `gh`（issue を読む・投稿する） | 止まって、issue を読めないことを依頼した人に伝える。投稿できないときは、確定版の本文を出力し、貼ってもらう |
| 別のモデルへの問い合わせ手段 | 4 の「許されるモデルが無い」と同じ扱いで、出力に「できなかった（理由）」と書いて進む |
| 下書きの置き場の取り決め | リポジトリの外の一時ディレクトリに置き、パスを出力に書く |
| 依頼元へ返す手段の取り決め（委譲された側） | 最終の応答として3つの出力を返し、止まる |

## 限界

- **入口の発火は、このスキルの description との一致に頼っている。** 確実ではない。発火を実測する対象は Claude Code だけで、Codex と Cursor にも配られるが、発火は測っていない。
- 1-2 の判定は、owner が確定させたことを証明しない。取り違えと第三者のコメントを除くだけである。

## 補足: hub での具体例

ここから下は、このスキルを作ったリポジトリ（ai-development-hub）での具体例である。上の規則は、この節が無くても成り立つ。

- **フローの中の位置**: hub のフローでは、issue を起点にする作業はゲート0 でこのスキルを必ず通す（`document-format.md`「遷移規則」節の判定順0 と「ゲート配置」節の (0)）。統括は、作業に入る前と子へ渡す前に通す。issue の無い作業では、ゲート0 は今のまま必要なときだけである。
- **依頼の書面**: 統括が組む委譲の brief の可変節に「認識合わせ: [確定版コメントの URL ／ 省略（owner の指示）／ 対象外（issue の無い作業）]」の欄がある（`doc-flow-guardrail` の「② 委譲固定節テンプレ」）。子はこの欄を 1-2 の照合に使う。「対象外（issue の無い作業）」は、このスキルの適用範囲の外であることを示す値で、省く条件（「いつ使わないか」の2つ）を増やすものではない。
- **委譲された子から依頼元へ渡す手段**: 3つの出力を `.oe/question-<issue>-<n>.md` に書き、そのパスを `oe-send` で依頼元のペインへ1行で送って待つ。`oe-*` の呼び方は `doc-flow-guardrail` の「verb 解決規約」節に従う。
- **下書きの置き場**: `.oe/`（git の対象外の作業層）。
- **文脈の置き場**: hub の `CLAUDE.md` の案内に従う。蒸留の木（discussion / plan / episode / decision）は `docs/{name}/` と `projects/{name}/docs/` の下にある。
- **owner 特有の観点の受け渡し先**: owner の分身のレビュアー（issue #404）で検討中である。未接続のあいだに見つかった owner 特有の観点は #404 に記録する。
- **別のモデル**: 統括のセッションは Claude で動くので、`so-compare --codex-only` を使う。`so-compare` は `~/bin` に配られている。
- **後から見つかった抜け**: 見つけたその場で記録する。拾い損ねたものは、episode の closure（`episode-retrospective` の closure gate checklist）が受け皿になる。
