# judgment-board-flow — 判断ボードで owner への問いを受け付けて回収する

統括が子をいくつも並列に動かすと、owner への問いが子ごと・時刻ごとにばらばらに届く。会話に流すと、答えたものと答えていないものが混ざり、owner はどこで何に答えるかを探すことになる。このスキルは、統括ごとに1枚のページ（判断ボード）を使い続け、問いを決まった順で選り分けて載せ、答えを回収して、答えを使う先が受け取るまでを確かめる手順を決める。owner がいつ戻ってきても、判断ボードの1枚を見れば、いま答えるものと決まったものが分かる状態を保つためである。

## 言葉

- **owner**: 作業の方向を決める人。統括の会話に戻ってきて答える。
- **統括**: 子に作業を任せ、owner に向く問いを集めるセッション。owner が答えるページを出すのは統括だけである。
- **子**: 統括から委譲された作業のセッション。owner が答えるページを出さない。
- **判断ボード**: html-one-pager の種別 `board` のページで、統括ごとに1枚を使い続ける。
- **開いた問い**: 判断ボードの「いま決めること」にある、まだ回収していない問いのカード。
- **案内**: 判断ボードを出し直したあとに、会話に書く1行（6節）。
- **待つ期間**: 開いた問いがあるときの、案内を送ってから、owner の答えを回収するまでのあいだ。開いた問いが0件のあいだは、待つ期間ではない。
- **回収**: owner の答えを読み取り、正本に写し、答えたカードを表へ移して出し直すこと（7節）。
- **台帳**: 出来事を1行ずつ足していく記録（9節）。
- **問いのファイル**: 問いを html-one-pager のページのデータで書いたファイル（3節）。

## いつ使うか

統括の側:

- 子から問いのファイル・報告（`NEEDS_CONTEXT`・`BLOCKED` を含む）・ゲートの停止（plan を書いて止まったなど）が届いたとき。
- SO が終わり、指摘の採否を owner に聞きたいものがあるとき。
- 統括自身が、owner に判断・確認・依頼（値を貼る・画面を開くなど）を求めたいとき。会話で聞いてよいかも、ここで決める（「使わないとき・境目」）。
- 会話で聞いた問いに owner が答える前に、別の入力（子の報告・CI などの知らせ・owner の別の話題）が届いたとき。
- owner が判断ボードに答えた・会話で「全部推奨」と言った・番号を挙げて答えたとき。
- 回収した答えを子・承認の記録・認識合わせの確定版へ渡すとき。
- 統括を交代して、判断ボードと台帳を引き継ぐとき。

子の側:

- 委譲された子が、統括や owner に判断を求める問いを書くとき（3節）。

## 使わないとき・境目

- **会話で聞いてよい問い**は、次の (a) か (b) に当たるものだけである。どちらにも当たらない問いは、会話で聞かずに2.1 の判断の順に当てる。当たるかは統括のその場の見立てでなく、下の見える条件で決める。
  - (a) 統括の下に生きた子が1体もいない（`oe-tree` が成功し、自分の下の子が無いか、すべて `gone` である）。`oe-tree` が失敗したときや、状態が分からない子（`?` など）がいるときは (a) に当たらない。
  - (b) owner が自分の言葉で始めた問答の中の、その問答の対象についての問いである。問答は次の2つだけである。
    - 認識合わせの深掘り: owner の応答で深掘りの合図が出て、`issue-intake` のとおり深掘り中の版を issue に投稿してから、確定版を投稿するまで。
    - 設計の相談: owner が会話で、自分の言葉で設計を一緒に考えることを求めてから、その結果を plan などの文書に書くまで。
    - 始めるときに、会話に1行「ここから <何> を会話で進める（owner の『<owner の言葉>』による）」と書く。終わったら（結果を行き先に書いたか、owner が終えると言ったら）1行「<何> の問答を終えた」と書く。始まりの1行の無い問答は (b) に当たらない。
    - 作業を進めるための確認や許可（子を起こしてよいか・どちらの作業を先に進めるか・マージしてよいか）は、問答の途中でも (b) に当たらない。
- **会話で答えを待つ問いは、同時に1つまでにする。** 2つ目は、1つ目の答えを受けてから聞くか、判断ボードに載せる。
- **会話で聞いた問いを判断ボードへ移す条件**: 聞いたあと、次に届いた入力が「owner の発言で、その問いに答えるか、その問いについて尋ねるもの」でなければ、その場で判断ボードへ移す（移し方は2.6）。
  - 子の報告・CI などの知らせ・owner の別の話題（「その前にこれを整理したい」を含む）は、どれも移すきっかけになる。owner が黙って知らせだけが届くときも、最初の1件で移す。時間では移さない。
  - owner が問いについて尋ね、統括が答えたあとも、答えが来るまで、届く入力ごとにこの条件を当て続ける。
  - (b) の問答の中でも当てる（`question-driven-design` の「質問は一度に一つずつ」より先に当てる）。移すのは待っている1問だけで、問答は終わらない。owner が次に会話で発言したら、問答の次の問いをまた会話で聞いてよい。
  - 子を起こしたこと自体では移さない。子の最初の出力が届いた時点で、この条件で移る。
- 回収の途中の確かめ（7節の段3 の1行）は、すでに判断ボードにある問いについての1行なので、この入口の条件と2.6 には当てず、7節の段3 のとおりに扱う。
- **owner の答えとして受け取らない入力**: 末尾に ` [oe:<26文字>]` の印がある1行（`oe-send` が送った1行）、子の報告や問いのファイルのパス（`.oe/report-<issue>.md`・`.oe/question-<issue>-<n>.json` など）を知らせる1行、ツールの知らせ（バックグラウンドの作業の完了・監視の知らせ・hook の出力）。迷ったら答えとして受け取らず、移す。owner の答えを読み違えて移しても、owner は判断ボードで答えられる。
- 判断ボードは、owner が会話に居ないあいだに集まる問い（子の問い・ゲートの停止・SO の採否・統括があとで聞きたいこと）と、会話から移した問いを受ける場所である。会話の問答で決まったことは、その問答の行き先（認識合わせの確定版・plan など）に残す。
- **マージの依頼**は判断ボードで追わない（5節）。マージのほかの依頼（画面を開く・値を貼るなど）は、判断ボードの「owner への依頼」の表に出す。
- **ページの形・部品・検査**は html-one-pager が決める。このスキルは、いつ・どのページに・何を載せ、答えをどう回収して渡すかを決める。

## 位置づけ

このスキルは、統括と子の委譲の仕組み（orchestration-engine）の部品である。次のものを前提にする。

- 子へ1行を送る `oe-send` と、送った1行の受領印を確かめる `oe-confirm`。どちらも PATH に無いことがあるので、呼び方は `doc-flow-guardrail` の「verb 解決規約」節で決める。
- 統括のワークスペースの根にある作業層 `.oe/`（git の対象外で、3日で消えない場所）。子の worktree の中ではなく、統括のワークスペースの根の `.oe/` を使う。
- ページの形を決める `html-one-pager`（同じフォルダの `build.py` で検証して作る）。

隣のスキルとの分担は次のとおりである。

| スキル | 受け持つこと | このスキルとの境目 |
|---|---|---|
| `html-one-pager` | ページの形・部品・札・検査・答えの保存の形・ページの扱いの一般の決まり | 判断ボードのデータを書くときと、検査を通すときに使う |
| `delegate-task` | 子へ送る操作（send）・子の状態の見方 | 送ったあとの受け取りの確かめは、このスキルの7節と8節が持つ |
| `issue-intake` | 認識合わせの3つの出力・確定版の投稿・深掘りへの受け渡し | 認識合わせの答えは8節で `issue-intake` の流れへ渡す |
| `doc-flow-guardrail` | 委譲固定節・ゲート3 の baseline 記録・交代の工程・verb 解決規約 | ゲート3 の承認は8節で承認の記録を書いてから送る |

## 1. 判断ボードの形

- **統括ごとに1枚を、URL を変えずに使い続ける。** 新しい URL で作り直すのは、10節の3つのときだけである。答えを待つページ（開いた問いのあるページ）は、統括ごとに同時に1枚までにする。判断ボードがその1枚である。例外は、量で分けた一覧のページだけである（10節）。
- **区画は上から次の順に置く。** html-one-pager の判断ボードは、判定カードの節を先に、表をあとに置く決まりなので、この順で検査を通る。
  1. 「いま決めること」: 開いた問いのカードの節。作業ごとに節を分け、答えが無いと先へ進めない作業（止まっている作業）の節を先に置く。節の題には、作業の issue と、止まっているかを書く（例: 「#900 の plan の承認（ゲート3・止まっている）」）。
  2. 「owner への依頼」: 依頼・知らせ・待っている問いの表（5節）。
  3. 「動いている作業」: 統括が動かしている作業の表。
  4. 「最近決まったこと」: 直前の回収で決まった問いの表。
- **データのファイルは1つだけにする。** 統括のワークスペースの根の `.oe/board.json` に置き、書くのは統括だけにする。scratchpad のような数日で消える場所に置かない。出し直すときは、いつもこのファイルの最新を直してから作る（別の作業が古いデータから同じ URL に出すと、あとの出し直しが前の追加を消すため）。このファイルは「最後に出したページ」と「すぐ次に出す直し」だけを持ち、待たせている問いは入れない（2節）。
- **「最近決まったこと」の表には、直前の回収で決まったものだけを出し、次の回収で入れ替える。** 表の題に、いつ・どの回収の分かを書く（例: 「最近決まったこと（2026-10-26・#900 のゲート3 の回収の分）」）。列は、番号（`Q<数字>`・番号の列）・決まったこと（題を言い切りの文にしたもの。「追加: 」は付けない）・答え（選んだ選択肢の名前と、補足の要点）にする。表の行はすべて同じ回収で決まったので、いつ決まったかは行ごとに書かず、表の題に書く（html-one-pager の「いつ決まったか」をこの形で満たす）。
- **回収したあとの正本は、表にあるあいだは表の行、表から消したあとは台帳の `collected`（訂正があれば `corrected`）である。** ページの保存先の答えは、古いタブから書き換えられるので正本にしない。
- **「動いている作業」の表の中身と更新の決まりは、別に決める。** それまでは統括が手で書く。ただし、待つ期間には、この表の変化（PR を作った・段が移った）だけでは出し直さない。
- **問いの番号（`Q<数字>`）とカードの key は使い直さない。** 同じ key のまま、問いや選択肢の意味を変えない。変えるときは、古いカードを取り下げて（10節）、新しい key と番号で足す。保存先の答えは key で残るので、key を使い直すと前の答えが別の問いに付く。
- **SO のまとめのページ**を作ることがあっても、そこには判定カードを置かない。採否を owner に聞くものは、判断ボードの問いにする（答える場所を2つにしないため）。

## 2. 問いが届いたとき

### 2.1 判断の順

統括自身の問いは、先に「使わないとき・境目」で会話で聞いてよいかを決め、会話で聞けない問いをこの順に当てる。会話から判断ボードへ移す問いは、この順に当てず、2.6 のとおりカードにしてすぐ載せる（会話で聞いた時点で、owner に答えてもらうと決めているため）。

owner に向く問いが1件届いたら、次の順に当てる。軽い扱い（統括が決める・カードにしない）に落としたくない形を先に除く順である。子の報告（`NEEDS_CONTEXT`・`BLOCKED`）の形で届いた問いも、SO の採否も、この順に当てる。

1. **承認済みの plan や委譲時の書面を変える問いか。** 委譲固定節の「承認のあとに plan が変わるとき」の「変更」の級（step を削る・要件を弱める・ゲートを飛ばす・終端を書き換える・新しい作業義務や設計判断や対応範囲を足す）に当たるなら、統括に任された範囲かどうかに関係なく、owner の再承認の問いにする。「記録」と「補正」の級は再承認に回さない。
2. **owner が前もって統括に任せた範囲で決められるか。** 決められるなら統括が決め、判断ボードに問いとして載せない。子へ答えを送り（8節）、「owner への依頼」の表に知らせの行（「統括が決めた: …」）を出す。台帳には `asked`（`route` は `self`）を書く。
3. **表示を見て判断してもらう問いか。** そうなら、推奨をサンプルに当てて先に直し、判断ボードには「この表示で進めてよいか」の問いとサンプルへのリンクを載せる。サンプルを開いてもらうだけの依頼は、ここではなく4に当たる。
4. **依頼か知らせか。** 答えを選ぶ問いでないなら、問いのカードにせず、「owner への依頼」の表に出す（5節）。台帳には `asked`（`route` は `request`）を書く。
5. **一覧から行を選ぶ問いか。** 選び方のカードと選ぶ表ごと、判断ボードの問いとして載せる。量が多い一覧（候補が数十件）だけは、別のページにしてよい（10節）。
6. **答えを待っている問いが判断ボードにあるか。** あれば、閾値に関係なく載せる対象にする。いつ載せるかは待つ期間の決まり（2.3）に従う。止まる問いならすぐに「追加: 」を付けて出し直し、急がない問いは `next_publish` で待たせて次の出し直しで載せる。
7. **答えが無いと子か統括が先へ進めない問い（止まる問い）か。** そうなら、1件でも載せる。
8. **残り**は、次に載せるまで待たせる（2.2）。

段1・3・5 で問いにすると決めたもの（再承認の問い・表示を見てもらう問い・一覧から選ぶ問い）も、いつ載せるかは段6〜8 と2.2〜2.4 で決める。段1〜5 は「どの形で扱うか」を決める段で、「いますぐ出し直す」を決める段ではない。段2・4 で表に出す行（知らせ・依頼）も、待つ期間なら次の出し直しで出す。ただし、答えが無いと子か統括が先へ進めない依頼（値の依頼など）は、止まる問いと同じにすぐ出し直して案内で知らせる（行なので「追加: 」は付けない）。

### 2.2 閾値と、待たせる問い

- owner への問いが2件たまるか、止まる問いが1件出たら、判断ボードに載せる。時間の上限は置かない。会話から移す問いは、閾値に関係なくすぐ載せる（2.6）。
- 待たせる問いは、判断ボードのデータに入れず、台帳に `asked`（`route` は `held`）として、問いのファイルのパスと一緒に書く。中身の正本は問いのファイルのままである。待たせる理由を `hold` に書き分ける。
  - `threshold`（閾値を待つ）: 届いたときに開いた問いが無く、閾値に届かなかった問い。
  - `next_publish`（次の出し直しで載せる）: 届いたときに開いた問いがあった（2.1 の段6）が、待つ期間なので出し直さなかった問い。
- 待っている問いがあることは、判断ボードの「owner への依頼」の表に「待っている問い（次に載せる）」の行として出す（答える場所ではない）。待つ期間でないとき（開いた問いが0件のとき）に `threshold` で待たせた問いは、その場で出し直して行を出す。待つ期間に `next_publish` で待たせた問いは、次の出し直しでカードとして載るので行にはしない（待つ期間は出し直さないので、そのあいだは判断ボードにも案内にも出ない。owner が答えて回収したあとの出し直しで、カードとして見える）。

### 2.3 待つ期間（開いた問いがあるときの、案内を送ってから答えを回収するまで）

- 進み具合だけの変化（PR を作った・段が移った・作業の表が変わった）では出し直さず、次の出し直しにまとめる。owner が読んでいる途中で版が変わらないようにするためである。
- 急がない問いが届いても出し直さない。`hold` を `next_publish` にして待たせる。
- 止まる問いが届いたときと、会話から問いを移すとき（2.6）だけ、その問いの題の頭に「追加: 」を付けて出し直し、案内を送る（2.5）。答えが無いと子か統括が先へ進めない依頼（値の依頼など）が届いたときも、同じく出し直して依頼の表に行を出し、案内を送る（行なので「追加: 」は付けない）。

### 2.4 出し直すときに載せる問い

出し直すとき（回収のあとか、止まる問いが来たときか、会話から問いを移すとき）は、台帳から待たせた問いを拾い、次のとおりに載せる。会話から移す問いは、閾値に関係なく載せる。

- `next_publish` の問いは、すべて載せる。回収で開いた問いが0件になっても載せる。
- 開いた問いがあれば（いま載せるものを含む）、`threshold` の問いも閾値に関係なく載せる。
- 開いた問いが無ければ、`threshold` の問いは、閾値に届いたとき（ほかの問いと合わせて2件か、止まる問いが来たとき）だけ、待っているものをすべて一緒に載せる。届かなければ「待っている問い」の行のままにする。

### 2.5 「追加」の印

- 待つ期間に足した問いには、題の頭に「追加: 」を付ける（例: 「追加: 再試行の上限を何回にするか」）。判断ボードの札は `Q<数字>` に限られるので、札には書かない。開いた問いが0件のときに載せた問いには、印を付けない。その出し直しの案内が、それらの問いの最初の案内になるからである（「最初に URL を伝えたあとに足した問い」を、開いた問いのある待つ期間に足した問いと読む）。
- 一括の答え（「全部推奨」など）は、案内の時点で印の無かった問いにだけ当てる。**当てる範囲の正本は、台帳の最後の `announced` の `bulk`（key の集合）である。** 題の「追加: 」は owner に見せる印で、統括は題の文字ではなく `bulk` で範囲を決める。出し直す前に、題に「追加: 」のある問いと、`bulk` に入れない問いが一致することを確かめる。
- 追加の問いは、ページで選ぶか、番号を挙げて答えてもらう（案内の1行にそう書く）。
- 印は、答えを回収したあと、残りの問いを案内する出し直しのときに外す。外してから出し直し、案内を送る。案内を送った時点で開いている問いは、確かめを待つ問い（7節の段3）を除いて、すべて印の無い問いになる。確かめを待つ問いは、owner が番号を挙げて答えるまで印を残す。

### 2.6 会話から判断ボードへ移すとき

会話で聞いた問いが、「使わないとき・境目」の移す条件に当たったら、次のとおりに移す。

- 問いを統括の問いのファイル（4節）に書き、カードにして判断ボードへ載せる。台帳には `asked`（`route` は `board`・`moved_from` は `conversation`・`stops` は実際に止まるかどうか）を書く。
- 閾値と待つ期間に関係なく、すぐ出し直して案内を送る（6節）。待つ期間なら題の頭に「追加: 」を付ける（2.5）。会話で見せた問いを、次の出し直しまでどこにも見えない状態にしないためである。
- 会話では問いを書き直さない。会話に書くのは、移したことを含む案内の1行だけである。
- 移したあとの割り込みでは、移した問いのために出し直さない（ふつうの待つ期間の決まりに戻る）。移した問いを、また会話へ戻さない。
- 移したあとに owner が会話でその問いを名指しして答えたら、7節の段3 の「会話で、その問いを名指しした答え」として回収する。

## 3. 子の問いの書き方（委譲された子が読む）

統括や owner に判断を求める問いは、次の形で書いて統括へ送る。owner が答えるページは統括が出すので、子はページを公開しない。

- **置き場**: 統括のワークスペースの根の作業層に `.oe/question-<issue>-<n>.json` で置く（`<n>` は 1 から振る）。worktree の中には置かない。
- **形**: html-one-pager のページのデータにする。種別は `approve`、状態は `awaiting` である。`why` に、なぜいま聞くかを1文で書く。`source` は html-one-pager の `build.py source --git <worktree>` の出力に、`issue` を足したものにする。
- **カード**: html-one-pager の「問いのカードの書き方」に従う（題は問いの形・1つ目の塊は「何を決めるか」・2つ目は「推奨の中身」・置くなら3つ目は「ほかの案」・選択肢の名前は中身の言葉）。
  - カードの key と、選ぶ表の key は `i<issue>_` で始める（例: `i900_lib`・`i900_shops`）。統括の判断ボードでほかの作業の問いと重ねないためである。
  - 統括と別のリポジトリで作業する子は、issue の番号が統括の側の子と重なりうるので、ファイルを `.oe/question-<repo>-<issue>-<n>.json`、key の前置きを `<repo>_i<issue>_` にする（`<repo>` はリポジトリの名前を英小文字・数字・`-` に直したもの。例: `.oe/question-shop-900-1.json`・`shop_i900_lib`）。
  - 札（`Q<数字>`）は書かない。番号は統括が判断ボードの続きで振る。
  - 全体の承認のカード（札 `承認`）は使わない。「この plan で実装に進むか」を問いのカードとして書く（判断ボードには `承認` の札が無いため）。
  - 一覧から選ぶ問いは、選び方のカードと選ぶ表ごと書いてよい。
- **認識合わせ**（`issue-intake` の 5 で、子が依頼元へ渡す3つの出力）も同じ形にする。題は「#N の認識合わせを、この内容で確定してよいか」、1つ目と2つ目の塊は「何を決めるか」「推奨の中身」で、そのあとに3つの出力をそれぞれ自由な題の塊（「この issue でやること」「issue に書いていないが要ること」「どの観点で見たか」）で置き、issue の URL を塊の中に書く。
- **ゲートで止まるとき**（plan の GATE 3 など）も、GATE 3 の問いをこの形で添える。承認の対象は plan なので、カードの文と plan が食い違ったら plan を正とする。
- **Markdown の問いのファイルは書かない。** 2つ書くと食い違う。
- **検証してから送る**: `build.py check` が誤り無しで終わることを確かめる。
- **送り方**: 問いのファイルのパスを、報告の宛先へ `oe-send` で1行送る。最後に「待つ」か「続ける」を書く。「待つ」は、答えが無いと先へ進めない問い（止まる問い）であることを表す。送ったあとは exit code を確かめる。
- **しないこと**: 対話の選択肢（質問のメニュー）を使わない（子のペインには答える人がいない）。owner が答えるページを公開しない。

最小の形は次のとおりである。

```json
{
  "format": 1,
  "title": "#900 の plan の承認（ゲート3）",
  "kind": "approve",
  "status": "awaiting",
  "why": "#900 の plan を書いて止まった。答えが無いと実装に進めない。",
  "source": {"repo": "shop", "repo_url": "https://github.com/example-org/shop", "issue": 900, "branch": "feature/#900_retry"},
  "sections": [
    {"type": "decisions", "title": "#900 の plan で決めること", "cards": [
      {"key": "i900_retry_limit", "title": "再試行の上限を何回にするか", "recommend": "three",
       "blocks": [
         {"title": "何を決めるか", "points": ["決済の再試行を何回まで続けるかを決める。"]},
         {"title": "推奨の中身", "points": ["3回までにし、それを超えたら通知する。"]},
         {"title": "ほかの案", "points": ["5回までにする。外部の会社への依頼が増える。"]}
       ],
       "options": [{"key": "three", "label": "3回までにする", "kind": "go"}, {"key": "five", "label": "5回までにする", "kind": "warn"}]},
      {"key": "i900_approve", "title": "この plan で実装に進むか", "recommend": "go",
       "blocks": [
         {"title": "何を決めるか", "points": ["上の答えを入れた plan で実装に進むかを決める。"]},
         {"title": "推奨の中身", "points": ["この plan で進む。"]}
       ],
       "options": [{"key": "go", "label": "この plan で進む", "kind": "go"}, {"key": "fix", "label": "直してから進む（補足に）", "kind": "fix"}]}
    ]}
  ]
}
```

## 4. 統括が判断ボードに載せるとき

- **統括自身の問いも問いのファイルに書く**（3節と同じ形）。ただし、「使わないとき・境目」の条件で会話で聞く問いはファイルを作らず、判断ボードへ移すとき（2.6）に作る。統括が書くファイルは、issue に関わるかどうかに関係なく `.oe/question-cockpit-<n>.json` にし、`<n>` は統括が振る（子が振る `.oe/question-<issue>-<n>.json` と名前がぶつからないようにするため）。カードと選ぶ表の key は、issue に関わる問いなら `i<issue>_`、issue の無い問いなら `cockpit_` で始める。待たせた問いの中身を、いつも問いのファイルから引けるようにするためである。子の問いに要る問い（ゲートで止まった子の問いに、全体の承認の問いが無いなど）を統括が足すときも、このファイルに書く。
- **子のカードを写すときは、次の4つを直してから載せる。**
  1. カードの中と、一緒に写す選ぶ表の欄（`ref` の列を含む）にある `#N`・`PR #N` のうち、判断ボードの送り元と違うリポジトリの番号を、すべて `owner/repo#N` の形に書き直す（判断ボードのカードと表は子の `source` を持たないので、`#N` は判断ボードの送り元のリポジトリを指してしまう）。子の `source` のリポジトリが判断ボードの送り元と違えば、子が `#N` で書いた番号は子のリポジトリのものとして直す。**子の `source` が判断ボードの送り元と同じでも、この直しは省かない。** 本文や表の欄に、別のリポジトリの issue や PR が `#N` で書かれていることがあるからである。直すものが無いように見えても、番号ごとに、どのリポジトリのものかを子の問いのファイルの文脈で確かめる。
  2. 選ぶ表の候補の番号を、判断ボードの中で重ならないように振り直す。振り直すときは、選ぶ表の番号の列・`select` の `recommend`・カードの文の中の `候補<数字>` をまとめて直す。
  3. 表の key が判断ボードのほかの表と重なるなら直し、`select` の `tables` も同じ名前に直す。
  4. 札（`Q<数字>`）を、判断ボードの続きの番号で振る。
- **統括の判断を足す。** 各カードに、自由な題の塊「統括の判断」を足す（「ほかの案」があればその後ろ、無ければ「推奨の中身」の後ろ）。中身は、統括が照合したもの（plan の該当の節・前提にした decision など）と、推奨に同意するかである。子の推奨と違う推奨にするときは、カードの推奨を統括の推奨に変え、「統括の判断」に子の推奨を書く。ゲートで止まった子の問いは、plan と照合してからカードを直す。
- **並べる**: 作業ごとの節に入れ、選ぶ表は選び方のカードのある節の直後に置く。止まっている作業の節を先にする。
- **検査を通す**: `build.py check` が誤り無しで終わることを確かめてから出し直す。
- **台帳に書く**: 届いた問いごとに `asked`、出し直したら `published`、案内を送ったら `announced` を書く（9節）。

## 5. 依頼と知らせ

- 操作の依頼（画面を開く・値を貼る・サンプルを見るなど）と知らせ（統括が決めたこと・承認のあとの補正を見せることなど）は、問いのカードにせず、「owner への依頼」の表に出す。表の列は、依頼の中身・issue・状態（頼んだ・受け取った・待っている問いなど）にする。「手番」という言葉は使わない。
- 値の依頼の値は、関係する問いの補足欄か会話で受け取る。値のために意味の無い選択肢を作らない。受け取った値は、求めた側へ渡す（8節）。
- **マージの依頼はページでは追わない。** 会話で頼み、owner が会話で「マージした」と言ったら、統括が origin で着地を確かめる。

## 6. owner への案内の1行

出し直したら、会話に案内を1行で書く。中身は次のとおりである。

- 判断ボードの URL と版の時刻。
- いま決めることの件数と番号の範囲。そのうち止まっている作業のものの件数、「追加」の件数、待っている問いの件数。
- 「再読み込みして、1つのタブで答えてほしい」（2つの画面で同じ問いに答えると、あとから届いたほうが残る）。
- 「答えたら、この会話に一言書いてほしい（例: 全部推奨・Q43 は別案）」。ページに保存しても統括には届かないので、回収のきっかけは会話の一言である。
- 「補足を書いたら『保存しました』が出てから閉じてほしい」（補足欄は少し遅れて保存される）。
- 追加の問いがあれば、「『追加:』の問いは全部推奨に入らないので、ページで選ぶか番号を挙げてほしい」。
- 会話で聞いた問いを移したときは、そのことと番号（例: 「会話で聞いた問いを Q46 として移した」）。問いの中身は書き直さない。
- 確かめを待つ問いがあれば、「Q71 は確かめを待っているので、会話で番号を挙げて答えてほしい（ページで選んでも回収しない）」。追加の問いの案内（ページで選ぶか番号を挙げる）とは分けて書く。
- 新しい URL で作り直したときは、引き継いだ件数（10節）。アカウントや組織の切り替えで作り直したときは、「前のページで答えていたら、どの問いに何と答えたかを一言」の頼みも添える（10節）。

例を示す。

```text
判断ボードを出し直した（2026-10-26 10:05 JST）: <URL>。いま決めることは5件（Q41〜Q45）で、#900 の止まっている問いが3件、追加が1件（Q45）、待っている問いが1件ある。再読み込みして1つのタブで答え、答えたらここに一言（例: 全部推奨・Q43 は別案）。Q45 は追加なので全部推奨に入らない。補足は「保存しました」が出てから閉じてほしい。
```

- 案内を送ったら、台帳に `announced` を書く。`bulk` は、直前の `published` の `open` から `added` を除いた key、`added` は直前の `published` の `added` と同じにする（`ledger.py` がこの一致を確かめる）。
- 問いと選択肢と推奨は、会話に繰り返さない。答える場所を判断ボードの1つに保つためである。
- 対話の選択肢の道具（質問のメニュー）を、owner への問いに使わない。答える場所が3つ目になる。

## 7. 答えを集めて渡す（回収の6段）

owner が答えたと言ったら（会話の一言・子のペインへの直接の答えを含む）、次の6段で回収する。各段のあとに台帳に書く。

1. **対象を決める。** owner の発話が、どのページ（判断ボードか、量で分けた一覧のページか）のどの問いへの答えかを決める。台帳に `answered` を書き、その `id` を、この回の回収の「回」として以降の出来事の `round` に使う。
   - 質問（「Q43 の意味は」）なら答え、回収しない。
   - すでに回収した問い（「最近決まったこと」の表に移した問いと、表から消えた問い）への発話は、訂正として扱い、保存先を読み直さない。`corrected` を書く。問いがまだ表にあれば、その行の答えを直す（表にあるあいだは表の行が正本なので、直さないと訂正と食い違う）。訂正の発話も owner の答えなので、この回の回収（段2〜6）と一緒に扱い、出し直しは段4 で1回にまとめる（開いた問いがあれば、段2 でその保存先は読む。訂正した問いの保存先は読まない）。表から消えていれば、台帳の `corrected` が正本である。渡した先へ訂正として送り（`sent` の `kind` は `correction`）、受け取りを確かめる。一覧から選ぶ問いの訂正（選ぶ行だけが変わり、選択肢は同じことがある）は、`corrected` の `rows` に訂正後の行の番号と中身を書く（選ぶ表はもうページに無いので、中身は問いのファイルの選ぶ表から写す）。
2. **読む。** 発話の中身に関係なく（「全部推奨」でも）、判断ボードの保存先を毎回読む（12節）。`read` を書く。量で分けた一覧のページの答えも回収する回は、そのページの保存先も読み、読んだページごとに `read`（`url` はそのページ）を書く。
3. **写す。** 開いた問いごとに、答えを次の順で決める。
   1. 会話で、その問いを名指しした答え（番号か、どの問いかが一通りに決まる言い方で指した答え）。ページの答えと食い違ったら会話を採り、食い違ったことを回収の結果の1行に書く。
   2. 子のペインへの owner の直接の答え（子の報告で知ったもの・`via` は `child_pane`）。ページの答えと食い違ったら、子のペインの答えを採り、食い違ったことを回収の結果の1行に書く。
   3. ページの答え（保存先の `choice`）。
   4. 一括の答え（「全部推奨」）。最後の `announced` の `bulk` にある問いで、ページの答えが無いものだけに推奨を当てる。
   - 会話の答えは、どの問いへのどの答えかが一通りに決まるものだけを受け付け、owner の言葉を補足と `words` に残す。一通りに決まらなければ、その問いは未回答のまま残し、統括が読み取った内容を1行で返して確かめる。
   - この段の確かめ（読み取った内容・推奨と食い違う一括の答え・選んだ行の上限）の1行のあとに、owner の答えでない入力が届いたら、会話で確かめを書き直さない。その問いは未回答のカードのまま判断ボードに残し、次の案内の1行で「Q<数字> は確かめが要るので未回答のまま」と書く。確かめが済むまで、外へ向けた操作をしない。
   - 確かめを待つ問いは、owner が会話で番号を挙げて答えるまで回収しない（ページの答えも一括の答えも当てない）。確かめの1行には「会話で番号を挙げて答えてほしい（ページで選び直しても回収しない）」と添える。次の出し直しでは、題の頭に「追加: 」を付けて載せ、一括の答えの範囲（`bulk`）から外す（2.5）。あわせて「owner への依頼」の表に「確かめを待つ: Q<数字>（読み取った内容）」の行を出す。この行が、確かめを待っていることの正本で、統括が止まったり交代したりしても判断ボードから引ける。番号を挙げた答えで回収したら、行を除く。
   - 推奨と食い違う一括の答え（推奨が分かれているのに「全部 A でいい」など）は、外へ向けた操作（子へ送る・issue に書くなど）の前に、1行で確かめる。音声の聞き取りで「推奨」が抜けることがあるためである。
   - 一覧から選ぶ問いは、選んだ行の数を `build.py check --answers` で確かめる（保存先の文書をすべて `answers` の形に写し、カードと選ぶ表を除く前のデータに当てる）。上限を超えていたら、どの行を残すかを owner に確かめる。
   - 答えの決まった問いごとに、`ledger.py collect` で `collected` を書く（9節）。
4. **表へ移して出し直す。** 答えの決まった問いを、すべて「最近決まったこと」の表へ移し、表の行を今回の回収の分に入れ替える。選び方のカードを移すときは、名指した選ぶ表もページから除き、表の行に選んだ行を番号と名前で書く。そのうえで、待たせた問いを2.4 のとおり載せ、「追加」の印を外し（2.5）、`build.py check` を通して同じ URL に出し直す。`published` を書く。回収の結果を1行で owner に返し、案内（6節）を送って `announced` を書く。
   - 回収の結果の1行の例: 「回収した（Q41〜Q44）: 推奨どおり2件、別の案1件（Q42・会話で名指し。ページの答えは推奨だったので会話を採った）、未回答1件（Q44・追加の問い）。#900 の子へ送る。」
5. **渡す。** 答えを、それを使う先へ渡す（8節）。値の依頼で受け取った値も、求めた側へ渡す。
6. **記録と、途中から続けるとき。** 統括が止まったり交代したりして途中から続けるときは、台帳の最後の出来事から続ける。ただし台帳には別の問いの出来事が挟まるので、「最後の出来事」は**問いごとに**見る。`ledger.py trace --key <key>` でその問いの最後の出来事を見て、その次の段から続け、台帳全体の最後の1行では決めない。記録が無いことを、実行していないことと決めつけない。
   - `collected` のあとに `published` が無いときは、判断ボードを読んで、版の時刻と、その問いがまだ開いているかを見る。
   - `collected` のあとに `sent` が無い問いは、前の統括が子へ送ったかどうかが分からない。出し直し（`published`）の記録が無く、まだ送っていないように見えても、子へ答えを送る前に、子にその問いの答えを受け取っているかを照会し、返事を受けてから送る（同じ答えを二度送らないため。返事が「受け取っていない」なら送る）。
   - `sent` のあとに `received` が無いときは、子の返事か受領印を確かめ、確かめられなければ照会する。
   - 判断ボードの「owner への依頼」の表に「確かめを待つ」の行がある問いは、段3 の確かめを待つ問いとして続ける（ページの答えも一括の答えも当てない）。

## 8. 渡す先ごとの確かめ

- **子の問い**: `oe-send` で子へ1行を送る。1行には issue 番号・step・問いの番号と key・答え（選んだ選択肢の名前と補足）を入れ、同じ答えを二度受け取っても子が見分けられるようにする。一覧から選ぶ問いでは、選択肢の名前（「選んだ候補を試す」など）だけでは何を選んだか分からないので、選んだ行の番号と名前も入れる（例: 「候補2（アウトレット）・候補3（本店）」）。送ったら `sent`（`kind` は `answer`・`ref` は送った1行の識別子）を書く。exit 0 は配送の成功を意味しないので、子の返事か `oe-confirm` の受領印で受け取りを確かめ、`received`（`sent` に送信の `id`）を書く。確かめられなければ、送り直す前に子に照会する。
- **ゲート3 の承認と、承認のあとの「変更」の再承認**: 子へ送る前に、承認の記録と baseline（初回なら、承認した plan の commit・委譲時の書面の digest とアルゴリズム・ゲート表の版の3つ。張り直しなら entry）を書く（`doc-flow-guardrail` の「gate 3 の baseline 記録」）。`recorded`（`kind` は `approval`）を書いてから、子へ送る。送ったら `sent`（`kind` は `answer`）を書き、子の問いと同じく受け取りを確かめて `received` を書く。カードへの答えだけでゲート3 を済ませない。
- **認識合わせ**: `issue-intake` の 5〜7 のとおり、合図が出たかを決める。合図が出なければ確定版を issue に投稿し、`recorded`（`kind` は `intake`）を書いて、子へ確定版のコメントの URL を送る。合図が出たら、深掘り中の版を投稿し、owner と深掘りを終えて確定版を投稿してから、確定版の URL を送る。子へ送るのは確定版の URL だけである（子は確定版を受け取るまで待つ）。送ったら `sent`（`kind` は `answer`・`ref` に送った1行の識別子）を書き、受け取りを確かめて `received` を書く。深掘りの途中は、子に「深掘り中で、確定版を待ってほしい」と知らせてよい。
- **統括自身の問い**: そのまま作業に戻る。
- **値の依頼**: 受け取った値を求めた側へ送り、`sent`（`kind` は `value`）を書く。子へ送ったときは、答えと同じく子の返事か受領印で受け取りを確かめ、`received` を書く。
- **owner が子のペインに直接答えたとき**: 子が owner から直接受け取ったものとして扱い、`received`（`how` は `direct`・`sent` は空）を書く。統括は、子の会話記録で見ただけの答えを自分への承認として扱わず、中継し直さない。ゲート3 なら、承認の記録にその経路を書く。

## 9. 台帳

- **置き場**: 統括のワークスペースの根の作業層 `.oe/board-ledger.jsonl`。git の対象外で、3日で消えない場所である。台帳は1つだけにする。
- **形**: 1行1出来事の JSON（JSON Lines）。どの行も `id`（道具が振る26文字の識別子）・`at`（時刻）・`type` を持つ。作業層なので、ペインの番号を書いてよい。
- **つなぎ方**: 出来事どうしは、問いの key と、次の2つの参照でつなぐ。1回の回収は、きっかけになった `answered` の `id` を、その回の `read`・`collected`・`corrected`（と任意で `sent`）が `round` に持つ。受け取りは、どの送信の受け取りかを `received` の `sent` に、`sent` の出来事の `id` で書く。

| `type` | いつ書くか | 必須の項目 |
|---|---|---|
| `asked`（問いが出た） | 問いが届いて、判断の順に当てたとき・会話から判断ボードへ移したとき（2.6） | `keys`・`from`（誰の問いか）・`file`（問いのファイル）・`stops`（止まる問いか）・`route`（`board`・`held`・`self`・`request`）。`route` が `held` なら `hold`（`next_publish`・`threshold`）。任意で `issue`・`step`・`gate`（判断の順の何段で決めたか・1〜8）・`moved_from`（会話から移した問いなら `conversation`。そのとき `route` は `board`） |
| `published`（版を出した） | 判断ボードを出し直したとき | `url`・`version`（ヘッダーの版の時刻）・`open`（開いた問いの key）・`added`（「追加」の印の key・`open` の中）・`held`（待たせたままの key）。任意で `counts`（節の数・表の行の数など。長さを後で見るため） |
| `announced`（版を伝えた） | 案内の1行を送ったとき | `url`・`bulk`（一括の答えを当ててよい key）・`added`（追加の key・`bulk` と重ねない） |
| `answered`（答えた） | owner が答えたと言ったとき | `where`（`page`・`conversation`・`child_pane`）・`words`（owner の言葉のまま。無ければ空）・`keys`（名指した key。無ければ空） |
| `read`（保存先を読んだ） | 回収の段2 | `round`・`url`・`count`（読んだ文書の数） |
| `collected`（回収した） | 回収の段3（`collect` で書く） | `round`・`key`・`no`・`title`・`recommend`（key・名前・推奨の中身）・`choice`（key・名前）・`note`・`via`（`page`・`conversation`・`bulk`・`child_pane`）。一覧から選ぶ問いでは `rows`（選んだ行の番号と中身。行を選ばなかったときは空の並び）。任意で `words` |
| `sent`（渡した） | 答え・訂正・値を、子か求めた側へ送ったとき（承認の記録や確定版を書いたことは `recorded`） | `keys`・`kind`（`answer`・`correction`・`value`）・`to`（渡した先）・`ref`（送った1行の識別子・コメントの URL・記録のパス）。任意で `issue`・`step`・`round` |
| `received`（受け取った） | 子の返事か受領印を確かめたとき | `keys`・`sent`（受け取った送信の `id`。`how` が `direct` なら空でよい）・`how`（`reply`・`receipt`・`direct`） |
| `recorded`（記録を書いた） | 承認の記録か認識合わせの確定版を書いたとき | `keys`・`kind`（`approval`・`intake`）・`ref`（記録のパスかコメントの URL） |
| `withdrawn`（取り下げた） | 問いが要らなくなったとき | `key`・`reason` |
| `corrected`（訂正した） | 回収した問いの答えを owner が変えたとき | `round`・`key`・`choice`（key・名前）・`words`。任意で `rows`（一覧から選ぶ問いの訂正後の行） |

道具 `ledger.py`（このフォルダ）で書き足す。どのコマンドも、誤りがあれば台帳に何も書かずに終了コード 1 で止まり、ファイルが読めないなど中身より前の失敗は終了コード 2 で止まる。`<このスキルのフォルダ>` は、このスキルを読み込んだときに示されるフォルダのパスに置き換える。

出来事を書き足す（`collected` のほか）。日本語を含む JSON は、シェルの引用で崩れないように、標準入力から渡す。

```bash
python3 '<このスキルのフォルダ>/ledger.py' add .oe/board-ledger.jsonl asked --data-file - <<'JSON'
{"keys": ["i900_retry_limit", "i900_approve"], "from": "子 #900", "file": ".oe/question-900-1.json", "stops": true, "route": "board", "issue": 900, "step": "P3", "gate": 7}
JSON
```

回収した答えを書く。判断ボードのデータからカードの番号・題・推奨の名前と「推奨の中身」・選んだ選択肢の名前を引くので、手で写さない。一覧から選ぶ問いでは `--rows` が要り（行を選ばなかったときは `--rows ''`）、選ぶ表から行の中身を引く。`--via bulk` は、最後の `announced` の `bulk` に無い問いと、推奨と違う選択肢を拒む。

```bash
python3 '<このスキルのフォルダ>/ledger.py' collect .oe/board-ledger.jsonl --board .oe/board.json --key i900_retry_limit --choice five --via conversation --round <answered の id> --note 'Q41 は別案（会話）' --words 'Q41 は5回で'
```

台帳全体を検証する。1つの問いの出来事を、台帳の順に並べる（読むだけで、判定も知らせもしない）。

```bash
python3 '<このスキルのフォルダ>/ledger.py' check .oe/board-ledger.jsonl
python3 '<このスキルのフォルダ>/ledger.py' trace .oe/board-ledger.jsonl --key i900_retry_limit
```

道具の検査は、どの作業ディレクトリからでも回せる。

```bash
python3 '<このスキルのフォルダ>/tests/test_ledger.py'
```

## 10. ページを分けるとき・作り直すとき・取り下げるとき・長くなったとき

- **答え方の形（問いのカードか、一覧から選ぶか）ではページを分けない。** 分けてよいのは、量が多い一覧（候補が数十件）だけである。そのページは html-one-pager の種別 `pick` で別に作り、判断ボードの「owner への依頼」の表に「別のページで選ぶ」の行とリンクを出す。このページは「答えを待つページは1枚まで」の例外として数える。問いの番号は判断ボードの続きで統括が振り（例: 「Q47: 候補の一覧から選ぶ（別のページ）」と依頼の表の行に書く）、回収は7節の6段で行う。段2 ではそのページの保存先を読み、段3 の `ledger.py collect` には `--board` にそのページのデータを、`--no` にその番号を渡す。段4 では、そのページを html-one-pager の「回答済みにして出し直す」で止め、判断ボードの「最近決まったこと」の表を、判断ボードの問いと同じく、この回の回収の分（そのページの問いを含む）に入れ替え、依頼の表の行を除く。段5・段6 は判断ボードの問いと同じである。作業のまとまりでページを分けるのは、下の「長くなったとき」で owner に問うてからにする。
- **新しい URL で作り直すのは、次の3つのときだけである。** 1つ目は、開いた問いが0枚のときに、owner が新しく作ってよいと言ったとき（間が空いたときなど）。長くなったことを理由に統括が自分で作り直すことはしない（同じ中身で作り直しても短くならない。長くなったときの扱いは下の「長くなったとき」）。2つ目は、判断ボードのデータを失ったとき（保存先を読んで答えを回収してから作り直す。保存先には key と選択肢しか無く、問いの文は戻らない）。3つ目は、owner がアカウントや組織を切り替えたために、統括のセッションから判断ボードを読めないか、読めても出し直せないとき（手順は下の「アカウントや組織を切り替えたとき」）。作り直すときは、次の4つを引き継ぐ。
  - 開いた問い（同じ key のまま移し、引き継いだことを「統括の判断」の塊に書く）。
  - 回収したが、まだ渡し終えていない答え（問いごとの出来事で `sent` か `received` の無いもの）。
  - 受け取っていない値の依頼。
  - 問いの番号の続き（次に使う `Q<数字>`。新しいページでも番号を使い直さない）。
  - 引き継いだ件数を案内の1行で伝え、`published` に新しい URL を書く。古い URL には「このページは閉じた。続きは新しいページ」とだけ書いた短いページを出す（3つ目のときは、出せるようになってから出す）。
- **最新の URL の正本は、台帳の最後の `published` の `url` である。** 古い URL に閉じたページを出したことは `published` に書かない（書くと、最後の `published` が古い URL になる）。引き継ぎ文書や会話に書いた URL と食い違ったら、台帳を採る。
- **作り直すときの公開のファイル名**: 前に公開したどのファイル名とも違う名前にする。名前には、そのとき使っているアカウントや組織を見分ける印を入れ、同じアカウントや組織で作り直すときは回の番号も足す（例: `.oe/page-board-personal.html` のあとに `.oe/page-board-team.html`、また個人で作り直すなら `.oe/page-board-personal-2.html`）。同じファイルのパスで出すと、道具が前の URL へ出しに行き、アカウントを切り替えたあとは拒まれるからである。
- **アカウントや組織を切り替えたとき（3つ目）**: 手順は2つ目の「データを失ったとき」に近いが、前のページの保存先を読めない点が違う。
  - 開いた問いは、手元のデータのファイル・台帳・問いのファイルから、同じ key と番号で移す（上の4つの引き継ぎ）。
  - 作り直したら、案内の1行に「前のページで答えていたら、どの問いに何と答えたかを、この会話に一言書いてほしい」と添える。前のページに答えが無いように見えても、保存先を読めないので無いとは言えない。毎回頼む。owner が答えていたと言ったら、その答えを7節の段3 の1（会話で、その問いを名指しした答え）として回収する。
  - 前のページは、そのときは閉じたページに出し直せない。下の「アカウントを戻したとき」で出し直す。
- **アカウントを戻して、前のページがまた読めるようになったとき**: 使い続けるのは、台帳の最後の `published` の URL である。前のページへは戻らない。前のページは、12節の「別の会話から出し直す」と同じく先に読んでから、「このページは閉じた。続きは新しいページ」とだけ書いたページに出し直す。戻したアカウントで、最後の `published` の URL を読めないか出し直せないなら、それは3つ目のきっかけに当たるので、上の手順でもう一度作り直す。
- **取り下げ**: 問いが要らなくなったら（子の作業が取り消された・統括が自分で決めた）、台帳に `withdrawn` を書き、次の出し直しでカードを「いま決めること」から除き、「owner への依頼」の表に知らせの行（「取り下げた: Q45 …（答えなくてよい）」）を出す。「最近決まったこと」の表には入れない（あの表は直前の回収で決まったものだけを出す）。正本は台帳の `withdrawn` で、番号と key は使い直さない。
- **長くなったとき**: 切り替える点（何件で分けるか）は、まだ決めていない。それまでは1枚のまま、作業ごとの節で止まっている作業を先に置き、答えた問いは回収して表へ移すまでのあいだ畳まれる表示で受ける。出し直すたびに `published` の `counts` に節の数と表の行の数を書き、長さを後で見られるようにする。owner が「長い」「探しにくい」と言ったら、統括が分け方を owner に問う（作業の表を読むだけの別のページにする・作業のまとまりで問いを別のページに分ける、など）。

## 11. 統括が交代するとき

- **前任**: 引き継ぎ文書の人が書く節に、判断ボードの URL・データのファイル（`.oe/board.json`）・台帳（`.oe/board-ledger.jsonl`）のパスを書く。
- **後継**: 引き継ぎ文書からこの3つを取り、**出し直す前に、同じページを読む**（12節。別の会話から同じページに出し直すときは、先に読まないと拒まれる）。読むページは台帳の最後の `published` の URL で、引き継ぎ文書の URL と違えば台帳を採る（引き継ぎ文書を書いたあとに作り直したことがある。10節）。読んだページの版の時刻とデータのファイルが合っているかを見てから、同じ URL に出し直す。アカウントや組織の切り替えで読めないか出し直せないなら、10節の3つ目のきっかけとして作り直す。回収の途中なら、7節の段6 のとおり問いごとに続ける。台帳に `sent` の無い答えは、前任が送ったかどうかが分からないので、子へ送る前に子に照会する。

## 12. ページの公開と保存先の読み取り（接続）

このスキルのほかの節は「公開する」「保存先を読む」とだけ書く。どちらも、ページを置く場所の道具に依る。Claude Code で claude.ai の artifact に置くときは、次のとおりにする。ほかの環境では、この節だけを置き換える。

- **公開する**: html-one-pager の「公開と回収」節のとおり、Artifact の道具で、同じファイルのパスか同じ URL へ公開する。新しい URL で作り直すときだけは、10節のファイル名の決まりで新しいファイル名にして公開する。答える部品のあるページは `capabilities: {db: {}}` を付ける。公開したら、保存先を1回読んで確かめる。
- **保存先を読む**: `ArtifactData` の `list` で、collection `decisions` を読む。文書の doc id はカードの key（一覧から選ぶ行は `<カードの key>--<番号の数字>`）である。
- **別の会話から出し直す**: 先に Artifact の道具の `read` で同じページを読む。
- **アカウントや組織を切り替えたあと**: `read` で読もうとしても読めない（権限が無い・見つからない）か、出し直しが拒まれる。読んでいないことを理由に拒まれたときは、拒否と一緒に今のページが渡されるので、それを読んだことにして続ける。それとは違い、ページそのものを読めないときが、10節の3つ目のきっかけである。

## 13. しないこと

- 会話に、問いと選択肢と推奨を並べない（答える場所が2つになる）。「使わないとき・境目」の条件で会話で聞く問いだけは除く。
- 会話から判断ボードへ移した問いを、会話で書き直さない。
- owner への問いに、対話の選択肢の道具（質問のメニュー）を使わない。
- 「全部推奨」と言われたからといって、保存先を読まずに推奨で埋めない（ページで選んだ別の答えを捨てる）。
- 表へ移した問いの保存先を読み直さない（古いタブから書かれうる）。訂正は会話で受け、7節の段1 で扱う。
- 子に owner が答えるページを出させない。
- 待つ期間に、進み具合だけの変化で出し直さない。
- `oe-send` の exit 0 を、受け取りの確かめとして扱わない。

## 14. 限界

- 入口の発火は、この description との一致に頼っている。発火を測ったのは Claude Code だけで、ほかのツールでは名前を指して読み込ませる。
- 守るかはモデルに頼る。出し忘れ・取りこぼし（問いが閾値を越えたのに載っていない・送ったのに受け取られていない）を機械で知らせる道具は、まだ無い。台帳はその道具が読める形にしてある。
- 会話で聞いてよいか・移すかの条件は見える形にしたが、当てるのは統括の手である。機械で知らせる道具は、まだ無い。
- owner の答えでない入力の見分けは、`oe-send` の印・報告のパス・ツールの知らせの形に頼る。印を外して送られた子の入力が問いの答えに見える文（「推奨で進めてよい」など）なら、見分けられず、答えとして受け取りうる。
- 回収のきっかけは owner の会話の一言である。ページで答えて何も言わなければ、統括は気づかない。
- owner がアカウントや組織を切り替えたことは、道具からは分からず、ページを読もうとして・出し直そうとして拒まれて初めて分かる。作り直したあと、前のページに owner が答えていても、owner が会話で言わなければ統括は気づかない（案内で毎回頼むことで受ける）。前のページを閉じたページに出し直すまでは、答えを待つページが2枚あるように見える。
- 2つの画面がほぼ同時に同じ問いに答えると、あとから届いたほうが保存先に残る（html-one-pager の「限界」）。案内で1つのタブを頼むことで受ける。
- 「追加: 」の印の見分けやすさと、1枚の長さで owner が迷わないかは、実物の判断ボードで確かめる。
- 問いを書くのは統括と子の手で、問いのファイルから判断ボードのデータを作る道具はまだ無い。

## 補足: hub での具体例

ここから下は、このスキルを作ったリポジトリ（ai-development-hub）での具体例である。上の規則は、この節が無くても成り立つ。

- **決めた場所**: この流れは #466 の decision（`projects/orchestration-engine/docs/decisions/2026-10-24-decision-466-page-lifecycle-in-flow.md`）で決まり、#538 の decision（`projects/orchestration-engine/docs/decisions/2026-10-25-decision-538-judgment-board-flow.md`）でこのスキルの形を決めた。
