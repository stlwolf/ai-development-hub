# runbook-authoring — 手順書の書き方と、手順書・スキル・スクリプトの役割の分け方

手順書（ランブック）は、人か AI が端末やコンソールで操作を実行するための文書である。作業を AI に任せきりにすると、AI や実行環境が使えないときに、人が手順書を読んでも何もできない状態になりやすい。このスキルは、人が手順書だけで実行できる粗さの手順書と、その中を包むスクリプトを作るための決まりを持つ。

## 前提

- そのリポジトリに手順書の決まり（書き方・節・用語・検査）があれば、そちらに従う。このスキルは、決まりが無い所と足りない所に使う。
- 検査のスクリプト `check_runbook.py` は、Python 3.9 以上の標準ライブラリだけで動く。見本のスクリプトは、bash（3.2 以上）と標準のコマンドだけで動く。
- このフォルダだけで動く。以下のコマンドの `<このスキルのフォルダ>` は、このスキルを読み込んだときに示されるフォルダのパスに置き換える。

## いつ使うか

- 手順書を書く・直す・見直すとき。デプロイ・設定の反映・1回だけの初期化・失敗したときの戻し方などが対象である。
- 手順書で続けて実行しているコマンドを、スクリプトにまとめるとき。
- AI に手順書に沿って作業させるスキルの文を書くとき。
- 人が手順書だけで実行できるかを見るとき。

使わないのは、操作の手順を持たない文書（仕組みの説明・設計の記録・作業の記録）である。

## 役割の分け方

| 層 | 読む・使う者 | 持つもの | 持たないもの |
|---|---|---|---|
| 手順書 | 人（AI も同じものを読む） | いつ使うか、前提、段ごとの1つのコマンドと期待する出力と外れたとき、止まったときに読む表、戻し方 | 操作そのものの散文の手順、背景の説明、issue の番号 |
| スクリプト（または、そのリポジトリの入口のコマンド） | 手順書から呼ばれる | 続けて実行するコマンド、繰り返し、出力の加工、待つこと、期待が1つに決まる確かめ、対話の確認、記録に貼る行 | 読んで決める判定 |
| スキル（AI の入口） | AI | 「この手順書を上から実行する」ことと、AI が実行するときの共通の決まり | 手順の中身の写し（写すと手順書とずれる） |
| 背景・仕組みの説明、判断の経緯 | 人 | なぜこの順か、なぜこの形か | 作業の手順 |

- 手順書に散文の操作手順が1つでも要ったら、そこはスクリプトかコマンドに寄せる対象である。
- 手順書の冒頭で背景の文書へリンクし、「作業のときはこの手順書だけを見て進める」と書く。
- 入口のコマンドは、スクリプトでも、Makefile の target やパッケージの script でもよい。下の決まりは入口の形を問わず当てる。
- 理由と経緯は設計の記録や issue に置き、手順書から1回リンクする。過去の事例へのリンクは「間違えやすい所」の節だけに置く。

### AI の入口のスキルに書く文

業務のリポジトリに、手順書ごとの AI の入口のスキルを置くときは、次の形で書く。手順の中身は写さない。

```markdown
---
name: <作業の名前>
description: <この作業を頼まれたときに使う、という1文>
---

`<手順書のパス>` を上から実行する。

- 手順書の「AI が実行するとき」の節にある非対話の形で実行する。
- 何かを変える段の前に、その節の比べ方で承認を取り、承認された行と実行する行を文字列で比べてから進める。承認された文字列に手を入れない。
- 止まったら「止まったときに読む表」を引く。決まった次の操作が無ければ、そこで止めて人に返す。
- 読んで決める判定（差分が意図どおりか、など）は、スクリプトが出した要点を読んで決め、決めた理由を記録に残す。決められなければ止めて人に返す。
```

## 読者を人と AI に分ける

手順書は1本にし、「手順」の本体を人向けの粗い段にする。AI 向けに別の細かい手順書を作らない。人が分かる手順なら AI も判断でき、AI はさらに実物のコードを読んで手順の妥当性を確かめられる。2本に分けると、同じ手順の正本が2つになり、ずれる。

- **段の数は多くても6つにする。** 上限の6は決まりで、検査が見る。4〜6 は目安で、少ない段で済む作業は少なくてよい。6を超えたら、スクリプトに包める所を探す。
- **1段に1つのコマンドを置く。** 多くは入口のスクリプトの1つの名前である。各段は、目的の1行・実行するコマンド・期待する出力・外れたら、を持つ。
- **細かい確かめはスクリプトの中に置く。** スクリプトは、1つの確かめごとに番号つきの1行（`OK C1 …`・`NG C1 …` の形）を出し、外れたらそこで止まる。
- **「止まったときに読む表」は、確かめの番号ごとに意味と次の操作を持つ。** 手で確かめ直すときのブロックはここに置く。
- **1ブロック＝1確かめにする。** どのブロックも、実行すると1つの結果が出る単位にする。`&&` でつないで、最後に1つの結果を確かめれば足りる単位までは1ブロックにしてよい。コマンドごとに出力を読むものは、ブロックを分けて、それぞれに期待する出力を書く。人向けの段のブロックは中で多くを確かめるスクリプトを呼ぶが、最後に出る判定の行は1つである。
- **期待する出力は、`text` のブロックか本文の1行で書く。** コマンドのブロック（`bash` など）と言語の指定を分ける。
- **変更の種類による分岐を手順書に並べない。** スクリプトが対象と変更の種類を聞くか引数で受け、要る確かめだけを実行する。どうしても手順が分かれるなら、節か手順書を分ける。
- **「手順」の節の先頭に、段の一覧を1行ずつ置く。** 作業の大枠を先に見せる。
- **何かを変える段には「（変える段）」と書き、最初の変える段の直前に「ここが引き返せる最後の所である」と書く。** 変える段が2つ以上あるなら、それぞれの直前に、そこで止めたときの反映先の状態を書く。
- **値が1つに決まるもの（環境の名前・地域など）は、変数にせず実際の値を書く。** 置き換える所は `<…>` で書き、例の値とどこで引くかを書く。
- **スクリプトがまだ無い所は、1ブロック＝1確かめで書く。** 包む対象として「間違えやすい所」に残す。

## 手順書の種類

手順書の置き場に置くものは、次の3つの種類のどれかである。「いつ使うか」の節に `種類:` の行で書く。

| 種類 | 決まり |
|---|---|
| `ずっと使う` | ふつうの手順書 |
| `一時的` | `消す条件:` の行で、いつ消すかを書く（例: アプリ側の CI ができたら消す） |
| `1回だけの初期化` | 構築の前に一覧にし、担当と順番を持つ。ずっと使う手順書と分ける。どこにも書かれていない初期化は、本番の作業を途中で止める |

作業の記録（特定の日の作業で何をしたか）は手順書ではない。日付を持つのは記録だけで、手順書の置き場に置かず、記録の置き場に置く。混ぜると、人が「今回使う手順」を見分けられなくなる。

## 節の型

手順書は、次の8つの節を、この順で `##` の見出しとして持つ。前の4つは作業のときに上から読む節、後ろの4つは要るときに引く節である。ほかの `##` の見出しを間に入れてもよいが、8つの順は変えない。「関連」の節を最後に置いてよい。

| # | 節 | 持つもの |
|---|---|---|
| 1 | `いつ使うか` | `種類:` の行、使うとき、使わないとき、かかる時間の目安 |
| 2 | `前提` | 前提の型の4つの行（下）と、前の日までに済ませること（任意） |
| 3 | `手順` | 段の一覧と、`###` の見出しの段（「読者を人と AI に分ける」） |
| 4 | `確かめ方` | 作業のあとに人が目で見て確かめること。最初に見るものを先に置き、問いの形で書いてよい |
| 5 | `止まったときに読む表` | スクリプトが止まった行（確かめの番号）ごとの意味と次の操作 |
| 6 | `失敗や中断のとき` | 止まり方、再開の条件、戻し方（段ごとの早見表）、あとかたづけ（誰が・どの道で消すか） |
| 7 | `AI が実行するとき` | 非対話の形と、承認と実行の比べ方（「AI が実行するとき」の節）。AI に実行させない手順書でも省かず、「AI には実行させない（理由）」の1行を書く |
| 8 | `間違えやすい所` | 実際の作業で詰まった所を積む。過去の事例へのリンクを置けるのはこの節だけである |

- 背景の文書へのリンクは、最初の節の前の1文（「作業のときはこの手順書だけを見て進める」）に置く。
- 作業のたびに詰まった所は、その場で「間違えやすい所」に足す。別紙や会話に散らさない。
- 手順の段は `###` の見出しにし、コマンドのブロックのある段には `期待する出力` と `外れたら` で始まる行を置く。

### 前提の型

「前提」の節には、次の4つの行を、要らないときも「要らない」と書いて必ず置く。書いていないのと要らないのを区別するためである。

| 行 | 書くこと |
|---|---|
| `依存:` | 入っている必要があるものと、その確かめ方。スクリプトは先頭で確かめ、無ければ何も変えずに止まる |
| `資格情報:` | 要るか、どれか、何分で切れるか、どこでログインするか（AI のセッションでなく自分の端末で、など）、作業の区切りでログアウトするか |
| `実行する場所:` | リポジトリのどこで実行するか。スクリプトは実行する場所に頼らない |
| `1回だけの初期化:` | 済んでいる必要があるものと、その手順書と、済んでいるかの確かめ方 |

### 一覧（README）

- 手順書の置き場に `README.md` を置き、手順書を1つずつリンクする。手順書ごとに、種類・いつ使うか・最後に実際の作業で通した記録へのリンクを持つ。記録へのリンクは、通すたびに直す。
- 用語は一覧の「用語」で1回だけ説明し、手順書の中で繰り返さない。
- やりたいことから手順書を引く表（迷ったときの見分け方）を置いてよい。
- 手順書は置き場に平らに並べ、下のフォルダに分けない。

## スクリプトに包む

### 包む合図と粒度

- 人が続けて実行するコマンドが2つ以上になったら包む。
- 包んだ結果、人が実行するコマンドは1段に1つ、手順書全体で多くても6つにする。
- 入口は1本にまとめ、その下に名前を並べる形にする。対象（環境・名前・必須の入力・影響範囲・戻し方）が複数あるなら、1か所の表に持ち、各名前がそこから引く。

### 名前と終了コード

- 変えない名前（確かめる・差分を出す・状態を表示する）と、変える名前（足す・反映する・外す・戻す）を分ける。変える名前は、何度実行しても同じ結果にする（あれば何もしない・無ければ何もしない）。途中で失敗して実行し直したとき、済んだものを飛ばせる。
- 変える名前は、反映先を目当ての状態に「合わせる」操作にし、要る操作だけを実行する。2つのものを入れ替える操作にすると、2回実行したときに元に戻ってしまう。戻す名前も、前の版に合わせる操作にする。
- 変える名前は、実行せずに実行する操作の行を出す形（`--dry-run`）を持つ。実際に実行するときも、同じ行を同じ文字で出してから実行する。
- 終了コードは、「何も変えていない失敗」と「変わったかもしれない失敗」を必ず別にする。見本は次の割り当てを使う。リポジトリに決まりがあればそちらに従う。

| 終了コード | 意味 | 何が変わったか |
|---|---|---|
| 0 | 期待どおりに終わった（変える名前なら、変えたか、もともと同じで何もしなかった） | 期待どおり |
| 1 | 止まった（期待が1つに決まる確かめが外れたか、確認で断った） | 何も変えていない |
| 2 | 呼び方の誤りか、前提が足りない（依存・資格情報・端末が無い） | 何も変えていない |
| 3 | 変える途中で失敗した | 変わったかもしれない。止まったときに読む表と「失敗や中断のとき」を読む |

### 確認と非対話

- 変える名前は、変える前に、その回の差分の要点（何が変わるか）と戻し方を出し、端末から `yes` を待つ。対象ごとに決まった文言だけを出さない。決まった確認は減らさない。
- 確認は端末（`/dev/tty`）から読む。値を標準入力で渡しながら、確認だけを人が入力できる。
- 非対話の形（`--yes`）を持ち、表示は対話のときと同じに出す。
- 確認を待つあいだに、変える元（設定ファイルなど）が変わったら、何も変えずに止まる。確認の前に出した版と、実際に変える中身を一致させるためである。変えたあとにも、入れた中身の版を確かめる。

| 確認の結果 | 動き | 終了コード |
|---|---|---|
| 端末から `yes` が入った、または `--yes` がある | 続けて変える | 変えた結果による（0 か 3） |
| 端末から `yes` 以外が入った | 何も変えずに止まる | 1 |
| 端末が無く、`--yes` も無い | 何も変えずに止まる | 2 |

### 出力

- 確かめは1つごとに番号つきの1行を出す。判定の語（「すべて満たした」など）は、全部の確かめが通ったときだけ出す。途中の失敗を最後の判定の語で隠さない。
- 作業の最後の段（反映のあとを確かめる段など）で、記録に貼る1行を出す。何を・どこに・どの版を（作った commit など）・いつ（UTC）を入れる。
- 待つ処理は上限の時間を持ち、待っているあいだは「何を待っているか」と残りの時間を出す。別の端末で操作が要るなら、その操作を出す。

### 秘密

- 秘密の値は、画面にも記録にも出さず、長さだけを出す。
- コマンドの引数に載せない。同じ機械のほかの利用者から、プロセスの一覧で見える。
- 一時のファイルに書くなら、終了のときに消す（`trap`）。
- エラーの本文に値を含めない。
- 伏せる処理が失敗したら、伏せる前のものを写さず、何も出さずに止める。

### 場所・時刻・文字

- 実行する場所に頼らない。スクリプトは自分の置き場所からリポジトリの位置を決める。
- 変える先のパスは絶対パスに限り、空や `/` を受け付けない。変える先に、予定と違う種類のもの（リンクのはずの所にフォルダなど）があれば、変える前に止まる。
- 時刻を次の段に渡すときは、時間帯を UTC に固定して出し、末尾が UTC であることを確かめる。手元の時間帯のまま渡すと、範囲がずれる。
- bash では `set -euo pipefail` を置き、1行に1つのコマンドを書く。
- bash で、変数の直後に ASCII 以外の文字（全角の括弧など）が来る位置は、必ず `${var}` で囲む。UTF-8 のロケールでは、`$c（` の `（` の先頭のバイトが変数名の一部として読まれ、`set -u` なら止まり、無ければ値が消える。書いたら、検査の R9 か次のコマンドで囲み忘れを探す（当たりが無ければ終了コード 1）。macOS 付属の grep は `-P` を受け付けないので、この形にしてある。

```bash
LC_ALL=C grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^[:space:] -~]' '<スクリプトのファイル>'
```

- 日本語の文を含むヒアドキュメントは、展開が要らなければ `<<'EOF'` で囲む。囲まないと、バッククォートがコマンドとして実行され、変数の直後の全角で上と同じことが起きる。

### 読んで決める判定

スクリプトが自分の判定で止まるのは、期待が1つに決まる確かめが外れたときだけにする。確認で断られたとき・前提が足りないとき・操作が失敗したときに止まるのは、これとは別である。差分が意図どおりか・影響が許せるかのように読んで決める判定は、スクリプトが要点を出して確認を待ち、人か AI が読んで決める。決定論的に決められるもの・期待する結果が分かっているものと、そうでないものの区別は、スクリプトの役割で定義できるので、すべての手順書でこの線にそろえる。

## 確かめの落とし穴

- **「申請した」と「通った」を分けて確かめる。** 申請の操作は成功の応答がすぐ返り、通ったかは別の確かめで見ることがある。
- **結果整合の一覧で確かめるときは、待つか、1件を直接引く別の取り方で見る。** 入れた直後の一覧は、古い結果を返すことがある。
- **「無い」を言うときは、同じ取り方で「在る」ものが見えることを先に確かめる（陽性の対照）。** 権限の不足や問い合わせの形で、在るものが無いように見えることがある。
- **判定を「出力に X が出る」だけで書かない。** 「出ないときの読み方」も書く。道具が一部の差分（ASCII 以外の文字を含むものなど）を省略して出すことがある。
- **途中の失敗を、最後の判定の語で隠さない。** 「出力」の節と同じである。

## AI が実行するとき

手順書の「AI が実行するとき」の節には、次を書く。

- 非対話の形。その手順書のスクリプトの形（`--yes` など）で書く。
- 承認と実行の比べ方。承認を取るときは `--dry-run` の「実行する操作」の行を見せる。実行する直前にもう一度 `--dry-run` を実行して、承認された行と文字列で比べ、同じなら非対話の形で実行する。実行したときに出る同じ行も比べる。比べる行は決まった前置き（見本では `実行する: `）で始まる行だけにし、その行には時刻や乱数のように実行のたびに変わる値を入れない。
- 承認された文字列に手を入れないこと。画面の量を減らすためのフィルタも足さない。出力が多いブロックは、手順書の側で初めからファイルに逃がす形にしておく。

## 用語

`glossary.md` を読む。語を1つの意味に固定する表・使わない語の表・和訳しない用語の表を持つ。そのリポジトリだけの言い換えと、AI の運用の言葉を、手順書に持ち込まない。

## 検査

### コマンド

手順書の置き場を検査する（一覧との一致 R10 も見る）。`--root` は、コマンドのブロックで呼ぶファイルを引くリポジトリの一番上で、省くと作業ディレクトリを使う。

```bash
python3 '<このスキルのフォルダ>/check_runbook.py' --root '<リポジトリの一番上>' '<手順書の置き場>'
```

手順書を1つずつ検査する（R10 は見ない）。

```bash
python3 '<このスキルのフォルダ>/check_runbook.py' --root '<リポジトリの一番上>' '<手順書のファイル>'
```

検査のスクリプトと見本の検査を回す（どの作業ディレクトリからでもよい）。

```bash
python3 '<このスキルのフォルダ>/tests/test_check_runbook.py'
```

- 誤りは1件1行で、`R5 docs/runbooks/x.md:23 呼んでいるファイルが無い: scripts/y.sh` の形で出る。
- 終了コードは、誤りが無ければ 0、誤りがあれば 1、ファイルが読めないなどで検査ができなければ 2 である。
- そのリポジトリに手順書の検査があれば、そちらを使う。このスクリプトは、検査を持たないリポジトリと、ほかの言語の検査へ写すときの元に使う。

### 機械が見る項目

| 番号 | 何を見るか |
|---|---|
| R1 | 8つの節が `##` の見出しとして、この順にある。ほかの `##` の見出しは無視し、8つの相対の順だけを見る。節が無いときは R1 だけを出し、その節の中を見る R2〜R4 は出さない |
| R2 | 「前提」に前提の型の4つの行がある |
| R3 | 「いつ使うか」に `種類:` の行があり、値が3つの種類のどれかで、`一時的` なら `消す条件:` の行がある |
| R4 | 「手順」の段（`###`）が1〜6で、各段のコマンドのブロック（`bash`・`sh`・`shell`・`zsh`）は1つまで、ブロックのある段は `期待する出力` と `外れたら` で始まる行を持つ |
| R5 | 参照が在る。Markdown の相対のリンク（インラインの形・`<…>` で囲んだ形・参照の形の定義）は手順書の置き場から引く。コマンドのブロックで呼ぶファイルは `--root` から引く。呼ぶファイルとみなすのは、`;`・`&&`・`\|` などで区切った各コマンドの最初の語か、`bash`・`sh`・`python3` などの次の語で、`/` を含む相対のパスである。前に付く `env`・`sudo` などと、その値を取るオプションは飛ばす。`bash -c '…'` の中も見る。リダイレクトの先は見ない |
| R6 | 本文（コードの外）に issue の番号（`#数字`・`/issues/数字`・`/pull/数字`）が無い。`#数字` は、リンクの先と URL を除いた本文で見る。例外は「間違えやすい所」の節の Markdown のリンクの中だけである |
| R7 | 本文に日付（`YYYY-MM-DD`・`YYYY/M/D`・`YYYY年M月`）が無い。リンクの先の URL やパスは見ない |
| R8 | 本文に警告の印が無い |
| R9 | コマンドのブロックと、R5 で見つけた bash のスクリプトに、展開される変数の名前の直後の ASCII 以外の文字が無い。単一引用の中・`\$`・注釈・区切りを引用したヒアドキュメントの中は、展開されないので見ない |
| R10 | 置き場の `README.md` がリンクする手順書の集まりと、置き場の `*.md`（README を除く）の集まりが同じである |

警告の印: ⚠ ❗ ❕ ‼ ⁉ ★ ☆ 🚨 ⛔ 🛑 🔥 ❌

大事なことは、印で目立たせず、先に書くか独立した文にする。印は付け足されるうちに意味が薄れる。

### 人が見る項目

- 段の数が4〜6の目安に収まり、1段に変える操作を詰めていないか。
- 変える段と、引き返せる最後の所が書けているか。
- 変更の種類による分岐を、手順書に並べていないか。
- 前提の4つの行の中身が正しいか（とくに1回だけの初期化）。
- 使わない語と、内輪の言い換えと、AI の運用の言葉が無いか。
- 「止まったときに読む表」の番号が、スクリプトの確かめの番号と合っているか。
- 確認の表示が、その回の差分の要点を出しているか。
- 手順書やスクリプトをスクリプトで書き換えたなら、差分の塊ごとに読んだか。置換の残りや消えた行が出ることがある。
- 別のブランチにしか無いファイルを指していないか。指すなら、マージの順を PR に書いたか。

## 見本

`examples/` は、架空のサービス `shop` のリポジトリの一番上とみなした見本である。外の資源には触れない。

```text
examples/
  docs/runbooks/README.md             手順書の一覧と用語
  docs/runbooks/shop-config-apply.md  人向けの段の手順書（ずっと使う・4段）
  docs/shop-config.md                 背景の文書
  scripts/shop-config.sh              入口のスクリプト
  config/shop.conf                    反映する設定
```

- 反映先は手元のフォルダで、環境変数 `SHOP_STATE_DIR` で決める。無ければ一時の場所（`${TMPDIR:-/tmp}/shop-example-state`）を使う。
- 手順書の書き方とスクリプトの決まりは、このスキルの節と同じ順で見られる。動かし方は、手順書の「手順」の節のとおりである。

## 限界

- 入口の発火は、この description との一致に頼っている。発火を確かめたのは Claude Code だけで、ほかのツールでは名前を指して読み込ませる。
- 検査は文書の形を見るだけで、手順書のコマンドを実行しない。前提の中身が正しいか・手順が実際に通るかは、そのリポジトリの検査と、人が手順書だけで通す演習で確かめる。
- 検査が見ないもの: 別のブランチにしか無いファイルへの参照、npm の script や make の target の実在、スクリプトの確かめの番号と「止まったときに読む表」の番号の一致、置き場の下のフォルダの手順書、コードの中の issue の番号。
- R5 が読むコマンドの形は、上の表に書いたものだけである。関数・別名・変数に入れたコマンドは見ない。R9 は、行をまたぐ引用とヒアドキュメントは追うが、シェルの文法をすべて読むわけではない。
- 使わない語は検査で見ない。普通の語（作業の流れ、など）に当たりやすく、文脈の判断が要るためである。
