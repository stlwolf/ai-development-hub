# unmet-gate-check — 完了前の未達ゲート照合（経緯を渡さない検出層）

委譲アークを完了扱いにする前に、**未達のゲートと step を列挙する**。判定材料を「確定済みの書面 + 観測可能な状態」に限り、**完了や終端について述べた散文を一切渡さない**。

## いつ使うか

- 委譲を完了扱いにする直前（子の完了報告を受け取ったあと・成果物を承認する前）
- 実行列が長く、途中で追加指示や方向転換が入ったアークの終わり
- 承認ゲートが多いアークの終わり（承認ごとの安全確認に注意が向き、フロー上の位置を見る視点が押し出されやすい）

## いつ使わないか

- **依頼側の出力が判定材料に入らない照合**。外部の真実に当てる検証（文書の逐語確認・設定の実読・URL の probe）は経緯を知っている方が効率的で、経緯を遮断する利得が無い。
- **要件の意図を満たすかの判定**（`adversarial-review` の Compliance Review）。下記「境界」を参照。
- plan を持たない小さな委譲（母集団が定義できない）。

## 何を解いているか

長い実行列の終わりには2種類の故障が起きる。

1. **終端の再定義** — 実行中に出た場当たりの1文が、書面（brief の固定節・plan の step）より後に来るため書面に勝つ。指示を受けた側は直近の指示に従っただけで、逸脱していない。
2. **母集団を歩き直す義務の不在** — 終了時にゲート表を1行ずつ当て直す主体が居ない。

本スキルは 2 を担う。**1 は予防側の規律（`delegate-task` の ACK 規律・`implementer-contract` の指示矛盾ガード）が担う。**

## 限界（先に書く・これは検出層であって強制層ではない）

**本スキルは起動されれば効くが、起動されることを保証しない。** 起動を依頼側が覚えている必要がある限り、依頼側の故障モードは検出側にも引き継がれる（起動の省略）。

これは既知の未解決点であり、本スキルの手順では閉じない。閉じるには、起動を依頼側の記憶に依存させない層（通過ごとの耐久 receipt・経路の強制・完了権限の分離・承認時の義務コンパイルなど）が要る。**したがって本スキルを入れたことを「完了前の確認が仕組みとして入った」と数えない。**

## 判定材料（ここが本スキルの実体）

### 渡すもの（clean）

| 入力 | 渡し方 | なぜ clean か |
|---|---|---|
| 承認済みの plan | **path で渡す。要約・言い換えを渡さない** | 承認時点で確定した書面である。要約は依頼側の出力なので、終端の書き換えが要約に乗って伝染する |
| **委譲時の書面**（brief、または貼られた固定節） | **path で渡す** | 母集団には固定節が課した義務が入る（下記）。**入手経路を渡さないと、その義務が黙って落ちる**。承認時点で確定しているので clean |
| ゲート表（規範側） | 参照で渡す（**版も一緒に**） | タスクに依らず確定している |
| 観測可能な状態 | 照会コマンドの結果 | commit / PR / branch / SO 出力 / 生成された文書 / テスト結果など、書面の外にある事実 |
| baseline の digest | 承認時に記録された値 | 母集団が承認後に改変されていないことの確認に使う（下記） |

### 渡さないもの（contaminated）

- 会話履歴
- 完了報告の散文（**報告した側が正直でも渡さない。** 誤った終端認識は、それを受けた側の報告に派生して乗る）
- 承認・受領・追加指示の散文（ACK / addendum）
- 依頼側が書いた plan の要約や言い換え
- 依頼側が絞った検査対象のリスト（母集団を縮める経路）
- **依頼側が散文で述べた「どこまで終わったか」「いまどの境界か」**（境界は書面から導出する。下記「境界の導出」）

### 遮断の判定規則（時刻では切らない）

**この遮断リストは既知の経路の列挙であって、網羅ではない。** リストに無い経路が出たら次の規則で判断し、リストへ追記する。列挙に無いことを clean の根拠にしない。

規則は**生成時刻ではなく出所の種類**で切る。承認より後に生まれた情報でも、次のものは clean である。

- **一次状態と機械的観測** — commit / PR / テスト結果 / SO の出力ディレクトリ / ファイルの存在。照会すれば誰でも同じ値を得る。
- 承認より後に生まれること自体は問題ではない（照合は必ず承認より後に走るので、時刻で切ると観測がすべて遮断されてしまう）。

遮断するのは次である。

- **主体による終端の解釈・要約・進捗の申告** — 「終わった」「残りはこれだけ」「いまここ」。同じ事実を見ても主体によって変わり、誤った終端認識がそのまま乗る。

判定に迷ったら「**照会で再現できる値か、それとも誰かの判断か**」を見る。再現できるなら clean、判断なら contaminated である。

### 渡し方そのものが汚染経路になる3つ（渡す文書を守っても壊れる）

| 経路 | 何が起きるか | 守り方 |
|---|---|---|
| 閉じた問いを渡す（「X と Y が済んだか確認せよ」） | 母集団が依頼側の選んだ部分集合に縮む | **問いは開いた形に固定する**（未達はどれか） |
| plan を要約で渡す | 要約に終端の書き換えが乗る | path で渡す |
| 起動プロンプトを散文で書く | プロンプトが追加指示と同じチャネルになる | **固定テンプレの slot を埋めるだけにする**（下記） |

## 母集団の導出（ゲート表の側から導く・成果物の側から集めない）

**成果物や報告の側から集めると、実行されずどこにも記録が無いゲートを構造的に落とす。** 記録が無いことが検出したい対象なので、母集団は最初に確定した集合の側から導く。

母集団 = plan の step 集合 ∪ ゲート表のうちこのアークに該当する行 ∪ 委譲時の書面（固定節）が課した義務

各要素に次を付ける。

- **`owner`**: 誰の義務か（依頼側 / 実行側 / 人間の承認者）
- **`due_transition`**: どの遷移までに履行されるべきか

### 境界の導出（依頼側の申告で受け取らない）

**「いまどの境界か」を依頼側から散文で受け取ってはいけない。** 受け取ると、終端を誤認している依頼側が境界を手前に書くことで、後段の義務がまとめて「まだ due でない」に落ちる。**検出層が本当の未達を機械的に正当化してしまう**（防ごうとしている故障そのものを、検出側が追認する形になる）。

境界は**書面から導出する**。

1. 委譲時の書面に記録された**終端 step**（そのアークがどこまでを引き受けたか）を読む。
2. plan の step 集合の中でその終端 step が占める位置が、判定の境界である。
3. 終端 step が書面から読めない場合は、**`invalid-baseline` を返して判定に入らない**（境界を推測で埋めない）。

### due の割り当て（規則で決める・その場で発明しない）

`due_transition` は次の対応で決める。アークの終端 step を基準に、それより後のものは due ではない。

| 母集団の要素 | `owner` | due の位置 |
|---|---|---|
| plan の各 step | 実行側 | その step 自身 |
| 設計着手前・設計判断の確定前のゲート | 実行側 | 設計を確定するまで |
| plan 確定前の設計SO | 実行側 | plan を確定するまで |
| plan → 実装の承認ゲート | 人間の承認者 | 実装に入るまで |
| 実装 → PR のゲート（実装SO・テスト・レビュー依頼） | 実行側 | PR を出すまで |
| PR → merge のゲート（closure・昇格候補の洗い出し） | 実行側 | マージされるまで |
| **merge 後のゲート**（issue の close 判断・掃除・昇格の実行） | **依頼側 / 人間の承認者** | **マージより後** |
| 委譲時の書面が課した義務（報告の形・記録の残し方など） | 実行側 | その義務が指定する位置 |

**merge 後のゲートは、実行側の完了境界では原則 due ではない**（`not-yet-due`）。ここを `unmet` にすると正常な委譲でも毎回未達が出る。逆に `not-applicable` に畳むと「該当しない」と誤って記録され、後で誰も見なくなる。

**owner や due が規則から一意に決まらない要素は、推測で埋めずに `unknown` で返す。** 恣意的に後ろの位置を割り当てると、本当の未達がそのまま落ちる（これは誤検出より危険である）。

## 判定は5値で返す（畳まない）

| 値 | 意味 |
|---|---|
| `fulfilled` | 履行を**観測できた**（証拠の場所を添える） |
| `unmet` | 観測できて、かつ履行されていない |
| `unknown` | **証拠が見つからない。** 履行されていないのか、観測手段が届かないのかが判別できない |
| `not-yet-due` | **該当するが、この境界より後に due な義務である**（due の位置を添える） |
| `not-applicable` | このアークには該当しない義務である（該当しない理由を添える） |

規則は3つある。

- **`unknown` を `fulfilled` に畳まない。** 証拠が見つからないことは、履行されたことではない。
- **`not-yet-due` を `not-applicable` に畳まない。** 前者は「該当するが、まだその時ではない」、後者は「そもそも該当しない」である。畳むと、後から誰も見なくなる（**事故の実例がここにある**——マージ後に due な昇格確認が、完了境界で「該当しない」と扱われれば、その後に確かめる主体が居なくなる）。
- **`not-applicable` を空欄と区別する。** 空欄は「見ていない」であり、`not-applicable` は「見て、該当しないと判定した」である。区別しないと、0 を不在と読む誤りが判定の側で再生産される。

**`not-yet-due` が付いた要素は、そのまま「誰が・どの遷移で確かめるか」の申し送りになる。** 落とすのではなく、次の担い手へ渡す形で残す。

テスト実行・人間の確認・外部サービス上の操作など、状態の照会だけでは履行を判定できない義務がある。それらは `unknown` で返し、**依頼側の検証に渡す**（本スキルが推測で埋めない）。

## 母集団が改変されていないことの確認（baseline）

承認後に plan の step が削られると、**縮小された母集団を忠実に照合して「未達なし」を返す**。これは判定の誤りではなく、判定の前提が壊れている状態である。

**baseline は plan だけでは足りない。** 母集団は3つの出所から導くので、そのすべてを束縛する。plan だけを守っても、委譲時の書面が課した義務やゲート表の版が入れ替われば同じ穴が開く。

承認時に記録するもの:

- 承認した **plan**
- **委譲時の書面**（brief、または貼られた固定節）
- 使用した**ゲート表の版**
- **digest のアルゴリズムと対象**（何をどう計算したか。再計算が一致しなければ意味がない）

照合の手順:

1. 上の各対象について digest を再計算し、記録された値と比べる。
2. **1つでも不一致なら、ゲート判定に入る前に `invalid-baseline` を返して止める。** 未達が無いという結論を出してはいけない（母集団が信頼できないので、結論の意味が定義されない）。
3. **承認の記録に存在しない digest を baseline として受け取らない。** 照合の直前に計算した値を「承認時の値」として渡されたら、それは baseline ではない（常に一致するので検査が空回りする）。記録が見つからなければ `invalid-baseline` である。

記録先は**承認そのものが残る場所**に固定する（承認の記録と baseline が離れると、後から対応が取れない）。記録する義務は承認ゲートの側が持つ。

### 意図的に方針を変えるとき

実行中に方針を変える場合、plan を更新するだけでは足りない。更新すれば記録された digest と一致しなくなり、更新しなければ照合側が変更を認識できない。したがって **plan の更新 → 再承認 → baseline の再記録** までを1単位にする。再承認を経ない変更は `invalid-baseline` として現れるのが正しい振る舞いである。

## 出力

- 母集団の**全要素**について、5値のいずれかと根拠（観測した場所 / due の位置 / 該当しない理由）を返す。
- `invalid-baseline` の場合は、それだけを返して判定に入らない。
- **助言・評価・修正案・優先順位づけを書かない。** 未達の解釈と是正の判断は依頼側に残る（本スキルの射程は照合であって判断ではない）。

## 射程（何をしないか）

**照合だけを担う。要件の意図を満たすかの含意判定はしない。** 含意判定は plan の文脈を必要とし、その文脈は本スキルが遮断している材料と重なる。遮断した材料を要する判定を本スキルに載せると、遮断の意味が消える。

含意判定を外へ出し切ろうとすると、「その判定を誰が検証するのか」が一段外へずれるだけで解消しない。したがって含意判定は依頼側に残す設計である。

## 起動テンプレ（散文を書かず slot を埋める）

```text
未達のゲートと step を照合してほしい。判定材料は以下だけである。会話履歴・完了報告・承認や追加指示の文面は渡さない（渡ってきても判定に使わない）。

- plan: <plan の path>
- 委譲時の書面（brief / 固定節）: <path>
- ゲート表: <参照（版も）>
- baseline の記録（承認時の digest とアルゴリズム）: <path または参照>
- 作業ディレクトリ: <path>
- issue: #<N>

手順:
1. baseline を照合する。plan・委譲時の書面・ゲート表の版のそれぞれについて digest を再計算し、記録された値と比べる。1つでも不一致なら、または記録が見つからなければ、invalid-baseline だけを返して終了する。
2. 判定の境界を導出する。委譲時の書面に記録された終端 step を読み、plan の step 集合の中でのその位置を境界とする。書面から読めなければ invalid-baseline を返して終了する。
3. 母集団を導出する（plan の step 集合 ∪ ゲート表の該当行 ∪ 委譲時の書面が課した義務）。各要素に owner と due_transition を規則から割り当てる。一意に決まらなければ unknown にする（推測で埋めない）。
4. 各要素について、状態を照会して fulfilled / unmet / unknown / not-yet-due / not-applicable のいずれかを判定する。
5. 母集団の全要素について、判定と根拠（観測した場所 / due の位置 / 該当しない理由）を返す。

制約: unknown を fulfilled に畳まないこと。not-yet-due を not-applicable に畳まないこと。not-applicable と空欄を区別すること。助言・修正案・優先順位づけを書かないこと。
```

**slot は上の一覧に限る。slot を足さないこと。** とくに「いまどの境界か」「どこまで終わったか」を slot として渡してはいけない（境界は手順2 で書面から導出する。依頼側の申告を入れると、終端の誤認がそのまま判定に乗る）。

**問いを絞る追記（「特に X を見て」）をしない**（母集団が縮む）。

## 適用範囲

- **人間の承認ゲートを越えた委譲**（実装アーク）に適用する。判定材料が複数の成果物に分散し、終端が複数の書面に跨るため、照合の利得がコストを上回る。
- **調査・plan 単位には適用しない。** 終端が委譲時の書面1箇所で足り、成果物も1本なので、独立した照合の利得が小さい。
- 予防側の規律（ACK 規律・指示矛盾ガード）は**すべての委譲**に適用する。こちらはコストがゼロである。

## 境界（重なりの回避）

- **`adversarial-review`（Compliance Review）**: 発火タイミングは同じ（完了報告のあと・承認の前）だが、扱いが2軸で逆である。あちらは**完了報告を必須入力として受け取り**、要件の**意図**を満たすかを判定する（実装者の報告を疑い、実体を読む）。本スキルは**完了報告を遮断し**、義務が**履行されたか**を判定する（依頼側の終端認識を疑う）。**両者は相補であり、統合すると盲検が壊れる**（あちらの必須入力が、こちらの遮断対象である）。
  - **順序の制約**: 同じコンテキストで両方を回す場合、**本スキルを先に回す**。Compliance Review が完了報告を読んだ後では、「判定に使わない」と後から指示しても遮断された状態には戻らない（読んだものは消えない）。順序を自由にしたい場合は、**本スキルを別コンテキストの照合役として回す**（そちらが本来の形である）。
- **`branch-finish`**: ブランチの処分（検証 → 4択 → 掃除）を扱う。ゲート母集団の照合はしない。
- **`episode-retrospective`**: closure の内容と昇格候補の洗い出しを扱う。
- **`delegate-task`**: 親子委譲の操作（送信・受領・宛先解決）と ACK 規律。**予防側**。
- **`implementer-contract`**: 実行側の返却契約と指示矛盾ガード。**予防側**。
- **`doc-flow-guardrail`**: フロー地図と routing。本スキルの発火位置はそちらの routing 表が持つ。
