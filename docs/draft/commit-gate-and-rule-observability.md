# コミットゲートとルール観測可能性

> AI駆動開発におけるコミットフローの自動化検討から派生した、ルール vs 機械的ゲートの設計原則。

## 発端

[Addy Osmani — AI coding workflow](https://addyosmani.com/blog/ai-coding-workflow/) の「頻繁にコミットし、セーブポイントとして使え」「説明できないコードはコミットするな」から、自分たちの運用にどう落とすかを検討した。

## コミット粒度の考え方

### ステップ設計がコミット粒度を決める

- 「いつコミットするか」のタイミングルールではなく、「1ステップが何を意味するか」の設計精度がコミット粒度を自然に決定する
- Plan/タスク分解時に、各ステップを「完了条件つきの意味ある単位」にする → コミットはステップ完了の外化

### マルチエージェント文脈での優先順位

- 1コミットの「正しさ」（ビルド通る・テスト緑）より、**意図と作業段階の分離**が巻き戻し・再開・レビューに効く
- ブランチ上のWIPコミットは未完成でもOK。ただし段階ラベルと意図がメッセージから読めること
- master直pushはご法度（別ポリシー）
- 「プロンプト1往復=1コミット」は境界が曖昧。ステップ単位の方が意味が明確

### 「説明できないコードはコミットするな」の再解釈

記事の厳密解釈（言語化できないならコミットするな）だと実験的WIPをコミットしにくい。「**後から同じ文脈に戻れる説明（段階・仮説・スコープ）が付いていないならコミットするな**」と読み替えれば、意図と分離優先の方針と両立する。

## ルール vs 機械的ゲートの仕分け原則

コミットフローの検討から導出された、より汎用的な設計原則。

### ルールの弱点: 観測不能 → フィードバックループが回らない

- ルールに従わなかった → 人間が気づかないと素通り
- なぜ従わなかったのか → エージェント側の判断が不透明
- 修正指示を出しても → 次回も同じルールを無視する可能性がある
- **結果: フィードバックループが構造的に回らない**

### ルールが向くもの

- LLMの確率的柔軟性が活きるケース — 文脈依存の判断、例外が自然に発生する
- 機械的に全分岐を列挙すると条件爆発するもの — コンテキストによって「従わない合理的理由」が存在する
- 成果物（コード等）のレビューで暗黙的にフィードバックが回るもの — コードレビュー自体が検証になる
- 意図的に選んだ非デファクト構造の事前教示 — リポジトリアーキテクチャ等、デファクトから外れた選択を教えておく必要があるが、いつかその構造を壊すタイミングも来る。機械的ゲートだとその例外対応が条件分岐の肥大化を招く

### 機械的ゲートが向くもの

- 実行/非実行が二値で判定でき、スキップ理由を構造化して残せるもの
- ルールだと遵守/非遵守が観測しにくく、フィードバックループが回らないもの
- フォーマット検証、ブランチ保護、コミット形式チェック等

### 同一関心事での層分け

両者は排他ではない。同一の関心事でも層を分けて適用できる:

- **コミット粒度の判断** → ステップ設計ルール（文脈依存、柔軟性が要る）
- **ステップ完了→コミット接続の担保** → 機械的ゲート（観測可能、スキップ理由を構造化）
- **コミットメッセージ形式** → 機械的ゲート（`commit-msg` hook）

## 第3の層: 偽陽性許容バンド（Stop Hook 差し戻し）

「ルール vs 機械的ゲート」の二分法に対し、[臭うコード検出器の記事](https://zenn.dev/manalink_dev/articles/coding-agent-with-syntax-tree-analyze) は中間層を示す。仕分け軸を「観測可能性」だけでなく「検出可能性 × 偽陽性率」の2次元に拡張する。

| 層 | 検出可能性 | 偽陽性率 | 経路 |
|----|-----------|---------|------|
| 機械的ゲート(CI) | 静的に明確検出可 | 低 | CI で落とす |
| Stop Hook 差し戻し | 静的検出可だが偽陽性多 | 中 | CI に混ぜず、エージェント自身に差し戻して自己修正させる |
| ルール(CLAUDE.md/Skill) | 静的検出不可 | — | 事前教示 |

中間層の本質は「ブロックするほどではないが、もう一度見たい」**中間確信度バンド**。これは深掘り（`persistent-exploration` / [#77](https://github.com/stlwolf/ai-development-hub/issues/77)）・セカンドオピニオン（[#76](https://github.com/stlwolf/ai-development-hub/issues/76)）が働く領域と同型。詳細は `docs/research/2026-06-03-code-smell-stop-hook-and-confidence-band.md`。

## コミットメッセージ本文の充実度: ルールが適する領域

### 背景調査

AI向けのコミットメッセージ構造化は2025-2026で議論が増えている:

- [Lore論文](https://arxiv.org/abs/2603.15566) (arXiv:2603.15566, 2026-03) — git trailersに判断文脈・却下案・検証メタデータを載せる「Decision Shadow」提案。インフラ不要、CLI でクエリ可能
- [Claude Code: Assisted-by trailer 議論](https://github.com/anthropics/claude-code/issues/36105)、[OpenCode: agent 用 trailer 議論](https://github.com/anomalyco/opencode/issues/11552) — コミットへのAI帰属メタデータの議論が進行中
- Conventional Commits は仕様上「human and machine readable」を謳い、エージェントが `type(scope):` をパースする事実上の共通基盤

### ルール vs ゲートの仕分け上の位置づけ

コミットメッセージ本文の「充実度」（段階・意図・コンテキストを書く）は、**ルールがちょうどいい塩梅の領域**:

- **形式**（Conventional Commits の `type(scope):` ヘッダ）は機械的に検証可能 → hook向き
- **本文の充実度**（何の段階か、なぜこの変更か、仮説は何か）はフォーマットを厳密に強制するほどではないが、ガイダンスがないと空になりがち → ルール向き
- 成果物（コミット履歴）がそのままレビュー対象になるため、暗黙的フィードバックが回る
- 文脈によって書くべき内容が変わる（調査段階 vs 実装段階 vs WIP）ため、機械的に全パターンを列挙すると条件爆発する

### 導入候補（低コスト）

既存の `conventional-commits` スキルを維持しつつ、本文のガイダンスをルールとして追加:

- 本文に「この変更は何の段階か」「意図/仮説」を含めること
- WIPでも段階ラベル（例: `wip(agent): apply planner diff — tests red expected`）で文脈復元可能にすること
- trailers（`Stage:` / `Context:` 等）は任意。まず本文の充実度から始める

## コミットゲートの実装方向性（未着手）

- ステップ完了時に未コミット変更があれば検知・促進するゲート
- コミットしなかった場合はスキップ理由を構造化して残す
- master上では発火しない（ブランチ上のみ）
- 完全自動コミットはしない（コミット実行は人間 or エージェントの明示的判断）
