# #284 episode の本文層と振り返り層の責務分離

## Context / なぜこの作業が始まったか

episode は phase の違う2つのものを1つの文書と1つのスキルで抱えている。作業中に随時追記する本文層と、PR レビュー後の closure でまとめる振り返り層である。`episode-retrospective` は冒頭で「本文の書き方は担当外・本文に構造を課さない」と宣言しているのに、Step 3「出力型 × 消費チャネル」は各行に「書く内容」列を持っていた。この宣言と実体の食い違いを解くのが本ユニットである。

## 作業ログ（随時追記）

### 2026-07-27 前段の経緯（plan-first・gate 1 と gate 2 を4周した）

本 episode の枠を作る前に、plan-first で4回の反証を通した。**この節は着手時点までの経緯を plan から書き起こしたもので、以降の節はリアルタイム追記である。**

着地までに設計が3回組み替わった。順に記録する。

- **gate 1（`predecision-exploration`）**: 統括の推奨案（案B = Step 3 を役割で割り「書く内容」列を本文層へ移す）を `oe-refute` 3レーンへ投げ、**3/3 が refuted**。3レーンとも独立に同じ代替形へ収束した（案G = Step 3 を移設せず宛先を明示し、本文層は型を持たない目的指示だけを持つ）。決め手は repo 自身の設計原則で、フリーフォーム本文には目的指示、構造化セクションには手段指示、と置き場が対応づけられており、「両方をフォーマット化すると書きアンカーが潰れる」と明言されていた。Step 3 の「書く内容」は手段指示なので、本文層へ移すのは原典が潰れると予告した方向だった。
- **gate 2 第1周**: 案G を投げて **2/3 refuted**（claude レーンは未返却）。核心は「新スキルの核が既存規範の再ポインタに縮退する」。案G が新スキルに持たせようとした4要素（失敗と撤回の経緯 / リアルタイム捕捉 / 前提の転回 / 棄却した選択肢）は、すべて spec の性質ガイド・ライフサイクル規範・方向転換の記録・既存スキル2本に着地済みだった。
- **測定（owner 裁定「先に測る」）**: 3周の設計論争が「原典の読み方はどちらが正しいか」に帰着していたので、実データで決着させた。結果は下記。
- **gate 2 第2周（絞った1周）**: 測定を受けて確定した案N の実装形（Step 4 の確認対象を episode 全体へ移す + 述語 P1〜P3）を投げ、**2/3 refuted**。核心は「**歯止めの向きが逆**」。述語は「closure の主張 → 本文」の参照整合性しか見ず、本文側の未参照事実（＝省略）を検出できなかった。本文に失敗 A と B があり closure が A だけを正しいアンカー付きで書けば全部 pass する。
- **着地 = 案N′**（反証レーン自身が出した代替）。座礁点（事実・失敗節）を移さず、その中身を pointer 許容にする。二重執筆は止まり、省略検出は落ちない。

### 2026-07-27 測定（R3 が求めた再判断・本ユニット最大の成果）

監査 R3 は「随時追記の選択ガードレールは何もしない（defer）。owner の B 検証 + 対照群データで再判断（owner 受諾済み）」と決めていた。その再判断の材料が揃っていたので測った。

**型判定の方法を途中で訂正した。** 当初は本文の自己申告ラベルで判定した（master が squash マージなのでコミット数は使えないと考えたため）。これは誤りで、**squash が潰すのは master の履歴だけで PR のコミット列は残る**。7本すべての PR を取得して数え直した。

3軸の結果:

- **二重執筆は出た（6/6）**。本文にある事実を closure で再度書いている。**単一コミットの2本でも起きている**ので、原因は書き手の作業スタイルではなく、本文と closure の両方に同じ内容を要求する合格条件の設計にある。
- **why の欠落は出なかった**（追記型 0/3・#263 を含めて 0/4）。10 時間 23 分・9 コミットという最強の個体でゼロだった。
- **肥大は測れていない**（heavy tier 偏りの交絡・対照群設計になっていない）。

**機構的発見**: 二重執筆は Step 4（closure の外部チェック）が構造的に要求していた。プロンプトが「実行ログにある失敗が**事実・失敗セクションから**選択的に省略されていないか」と問うため、合格条件が「closure 節に全件書かれていること」になっていた。pointer 方式を試みた2例は、2例とも外部チェックに「圧縮が lossy」と判定されて展開を要求されていた。

### 2026-07-27 実装（5ファイル）

- **`episode-retrospective`**: (1)「いつ使わないか」に**持つ範囲の明示**を足した — Step 3 の内容プロンプトは構造化 FB セクション向けの手段指示であって本文への指針ではない、と宛先を書いた。(2) **read/write 契約**の節を新設し、述語 P1〜P4・pointer 形式 `` `本文: <見出し>` ``・補完マーカー `` `本文なし: <理由>` `` を置いた。(3) Step 3 の見出しに宛先を明記し、本文にある事実には pointer を付ける（全文の再掲は不要・1行要約の併記は任意）とした。(4) Step 4 に「pointer は省略ではない」を足し、プロンプト例にも1句加えた。**確認対象の範囲（closure 節）は変えていない。**(5) Step 1 tier に「トリガの出来事はその場で記録・判定は closure」を足した。
- **`document-format.md`**: 性質ガイドが本文層・構造化 FB 節が振り返り層であると明示。FB の5項目は**形式の例示**で項目の正本は skill 側だと明記（必須記述の数え上げはそのまま残した）。ライフサイクル規範のリアルタイム追記の行に、closure から指せる形で書く旨を追記。
- **`doc-flow-guardrail`**: 委譲固定節の「episode 義務」行に**生産者側の1文**を追加。これが本ユニットで唯一の生産者側の着地点である。
- **`spec-card`** / **`CATALOG.md`**: episode 行の routing と説明を新しい実体に合わせた。

`reconstructed` は**流用しなかった**。あれはファイル単位の宣言なので、closure の項目ごとの補完には別マーカーを立てた（gate 2 で「語の意味の乗っ取り」と指摘された点への対応）。

**新スキルは作っていない。** brief が挙げた変更対象のうち、新スキルの新設・CATALOG への追加行と件数変更・個別スキル索引への追加は不要になった（理由は plan に表で残した）。

### 2026-07-27 gate 4 実装SO round 1 — refuted（自分の仕様矛盾を検出された）

`oe-review --lanes 2 --base master`（弱・codex + cursor）。**verdict = refuted**（codex が material 検出・cursor は survived・conservative 集約で全体 refuted）。reviewed_sha = `2e20ebb`。

codex の指摘は正しかった。**契約側は「本文にある事実を再執筆しない」と禁止しているのに、Step 3 は「各項目は再掲でも pointer でもよい」と許可していた。**同じ入力が準拠にも違反にもなりうる状態で、しかも述語 P1（各項目は pointer か補完マーカーを持つ）とも噛み合っていなかった。二重執筆を止めるのが目的なのに、その規則自体が二枚舌になっていた。

意図は「再掲の禁止」ではなく「**再掲を要求しない**」だったので、その線で統一した。本文にある事実には pointer を必須にし、全文の再掲は不要、1行要約の併記は任意、要約だけ置いて pointer を省くのは不可とした。

- cursor レーンは survived（Markdown のみで実行コードを含まず、bash 例も適切に quote されている、との判定）。
- **SO 反復の停止判断を先に宣言する**: round 2 を最後とし、そこで新たな material が出たら自分で直さず親へ上げる（レーンが毎周新しい nit を出す構造に引きずられないため）。

### 2026-07-27 gate 4 実装SO round 2 — refuted（宣言した停止規則を意図的に破った）

reviewed_sha = `c6038d7`。cursor は **survived**、codex が material 2件。**どちらも正しく、しかも2件目は本ユニットの目的そのものに関わる**ので、宣言した停止規則を破って直した。破った理由を先に書く。

- 停止規則は「レーンの際限ない深掘りに引きずられない」ためのものだった。今回出たのは新しい nit ではなく、**round 1 と同じクラス（自分の変更内部の仕様不整合）**であり、しかも「直さないと目的を達成しない」種類だった。既知の欠陥を残して規則を守るほうが有害だと判断した。**round 3 は回さない**（規則の趣旨はここで守る）。

指摘と対応:

1. **episode の実装記録が正本と矛盾**（`c6038d7` 時点）。skill 側は round 1 で「pointer 必須・全文再掲は不要」に直したのに、この episode の実装記録は「各項目は再掲でも pointer でもよい」という**修正前の文言のまま**だった。→ 記録を実体に合わせた。自分の変更を記録する文が古いまま残るのは、まさに本ユニットが直そうとしている「宣言と実体の食い違い」と同型だった。
2. **契約の適用範囲が狭すぎた（こちらが重い）**。`document-format.md` は closure の「各項目」を pointer 化すると書いたのに、P1 と Step 3 は **「事実・失敗」だけ**に pointer を要求していた。つまり「決定と根拠」「わかったこと」「残課題」は再掲しても契約違反にならず、**測定で観測した二重執筆を塞げていなかった**（#263 の重複は 決定と根拠 4/4、#262 も 決定と根拠 だった）。→ 契約を Step 3 の**全出力型**に広げた。
   - 原因は自分の混同である。**契約の適用範囲**（何を pointer にするか）と **Step 4 の確認範囲**（どこで省略を突合するか）を同じものだと思っていた。前者は全出力型、後者は事実・失敗節のまま、が正しい。skill にこの区別を明文で足した。

### 2026-07-27 実装中に気づいた自己適用の失敗（記録）

本 episode 自身が、いま書いている契約に違反していた。closure でこの節を書くときに気づいた。

- round 1 の指摘を上の節に**再掲**しており、pointer にしていない。契約どおりなら closure 側は `` `本文: <見出し>` `` で指すべきである。
- ただし本 episode では**実行ログの節そのものが closure の材料**なので、closure 節を書く時点で初めて pointer が使える。**契約は closure 側にしか効かない**（本文の追記に pointer 義務は無い）ことを、自分で書いていて取り違えた。
- 実害は無いが、「契約の適用先は closure 節だけ」と読み取りにくい書き方だった可能性がある。closure でこの点を確認する。
