# #288 昇格の判定を closure の必須項目に置く — 縮んだ範囲の実装（M 系単位）

**この記録はリアルタイム追記である。** 着手時に枠を作り、判断・撤回・棄却をその場で書いている。closure は M5（マージ前）。

## Context（なぜこの作業が始まったか）

4層ドキュメントのうち decision 層は、書き方の基準より前に「そもそも昇格を検討したか」を通す仕組みが無かった。着地した3つの arc（#289 / #295 / #299）で新規 decision が0件になり、しかも**個々の子の判断は理由つきで妥当だった** ── 破綻は集計の側に出ていた。

本単位はその設計を6サイクル（F 系 rev.1〜5 / H 系 / J 系 / L 系）かけて詰めた末に、**owner が gate 3 で承認した縮んだ範囲だけ**を実装する。**設計の大半は落ちた。** 落ちた理由と、落ちたものの行き先は M3 で PR 本文に書く。

**owner が最後に差し替えた起点**: 測定から基準を導くのをやめる。生成結果は確率的で母数も小さいので、そこから規範を導くと確率の結果を規範に焼く。decision 層に置くのは「人間も読む意味があるもの」で、中核の判定は「**解釈が複数ありうるものに一つの解を与えた記録で、覆すには同程度の議論を要する**」である。

## M2. canonical への変更

変更したのは `canonical/skills/episode-retrospective/SKILL.md` の1ファイルだけである（249 → 311 行）。

### 足したもの（2件）

1. **Step 2 の必須項目に「昇格の判定」を1項目。** 処分は3値で、**集計の「昇格なし」1行では閉じられない**と書いた。**「該当なし」は正当な結果**とし、件数を運用指標にしないことも項目に書いた。
   - **この時点の enum は `promoted` / `not-promoted` / `unknown` だった。M4 の実装SO で「実行を含意する」と崩れ、`required` / `not-required` / `unknown` へ変えた**（`本文: M4. gate 4 — 実装SO + PR + Copilot`）。
2. **必須項目の中身を2節に分けた** ── 「昇格の判定」（判定基準）と「置き場の判定」（層の選択 + 混在の消費者別分離）。

### 限定を項目自身の側に書いた（owner の指定）

「昇格の判定」節の**冒頭に、扱える範囲を先に書いた**。

> 扱えるのは、この episode 由来の判断で、かつマージ前に同じ PR へ載せられる昇格までである。（**この書き方は M4 で撤回した** ── 「同じ PR へ載せられる」が実行を含意していた）

**節の末尾ではなく冒頭に置いた。** 末尾だと、手順を読んで実行に入った後で範囲を知ることになる。設計SO で「置けるのは限定経路まで」と確定した以上、**読む順序として範囲が先に来るべきだと判断した。**

### 判定を2段にした理由

**対象外（機械だけが消費する契約）を先に外す。** 後に当てると通ってしまう ── enum の選択にも代替案の比較は成り立つので、中核の4問（Q1〜Q4）を機械契約が形式的に満たしうる。この順序は設計段階で「除外ゲートを先に当てる」として決めていたもので、実装でもそのまま残した。

### 既存節との衝突を1箇所直した

Step 3 の「蒸留シグナル」行は昇格候補の型を書く任意の欄で、**新しい必須項目と役割が重なって見える。** 行の末尾に「**判定と処分は Step 2 の必須項目が持つ**（本行は候補の型を書く欄で、処分の代わりにはならない）」を足して、どちらが義務かを一意にした。

### 既存の数え違いも直した

見出し行は「**4 項目 + 条件付き 2 項目**」だったが、条件付きの実体は**3**である（evidence anchor / SO 証跡リンク / 観測の書き戻し）。必須を5に増やすので、**同じ行の条件付きの数え違いも一緒に直した**（5 項目 + 条件付き 3 項目）。

**これは指定された成果物の外だが、同じ1行を書き換える作業なので分けなかった。** 分けると、直した行に既知の誤りを残したまま commit することになる。

### 判断: `document-format.md` は触っていない

置き場の判定は §13.3 の型選択の**運用形**として書き、節の冒頭に「正本は `document-format.md`「昇格義務」節の型選択である。本節はその運用形で、定義を上書きしない」と明記した。**spec 変更禁止の制約を守るためと、運用形が正本を上書きしたと誤読されないため。**

### この段で意図して**やらなかった**こと

owner の成果物リストに無いので、**過去の rev で設計した次のものは実装していない。** 落としたことを PR 本文に書く（黙って消さない）。

**Minimal Scope に従って、指定された範囲だけに留めた。**

## M3. PR 本文と plan

PR 本文を `.oe/pr-body-288.md` に書いた（作業層なので gitignored・PR 作成時に本文として使う）。含めたのは owner が指定した3件と、それ以外に2件である。

- **受け入れ条件の改訂案**（issue は編集していない。編集は owner の判断）。改訂が要るのは1件で、**被参照0の2件を「decision ではない」と判定させる条件は前提が実体と違っていた** ── rule にも hook にも当該記述が無いことを grep で確認済みで、承認された定義を当てると2件とも通る。
- **狭い形の surface 2件。** どちらも当初の断定が言い過ぎだったので狭めた。とくに2件目は「物理的に存在しない」と書いたのが誤りで、統括が `wt 0.33.0` で `--no-remove` と hooks の実在を確認している。**繰り返さないよう、PR 本文に「当初こう書いたのは誤り」まで含めて書いた。**
- **限界の明記**（存在／到達／実行の3水準・`wt merge` 直叩きで迂回できる・停止 arc に乗らない・判定はすべて意味判断・本単位自身にも掛からない）。
- 加えて **v0 が inert であることを事実として記載**した（起票は統括の判断なので、ここでは事実だけ）。
- 加えて **意図して実装しなかったものを表にした**（Step 5 の母集団拡張・`doc-flow-guardrail` の変更・SO プロンプトへの観点追加）。**黙って消さないため。**

## M4. gate 4 — 実装SO + PR + Copilot

### SO を起動した後に自分で3件直した（順序を正直に書く）

実装SO を3レーンで起動した**直後**に、自分で読み返して3件の欠陥を見つけた。**したがって SO のレーンは修正前の状態を読んでいる可能性がある**（レーンごとに読む時点が違う）。SO の指摘がこの3件と重なった場合は、独立した確認として扱う。

**1件目が最も重い ── 正本の読み替えをしていた。**

既出の扱いを「人間向けの why が、それを探す人が到達する committed の場所（skill / rule / knowledge item / decision）に在るなら既出。**episode は実行記録なので到達先に数えない**」と書いていた。**しかし `document-format.md`「昇格義務」節の判定基準は、既出の対象に episode を明示的に含めている。** 私の書き方は正本の定義を狭めるもので、**同じ節の冒頭に「定義を上書きしない」と書いておきながら上書きしていた。**

直した形は、**同じ節が持つ tie-breaker を使う**ものにした ── 「既出は正本の判定基準に従う。ただし人間向けの why の所在が episode だけの場合は、同節の**『疑わしきは残す』に倒す**。これは tie-breaker を使うのであって既出の定義を狭めるものではない」。**正本の中の別の条文で解く形に変えた。**

**2件目と3件目は限定の穴。**

- 必須チェックリストの項目自身には限定が無く、節への参照だけだった。**チェックリストだけ読んで節を読まない経路で範囲を越えられる。** 項目の末尾に限定を1行足した。
- 「置き場の判定」節にも限定が無かった。**層を選べることが実行主体になれることと混ざる。** 「層を選べることは、実行主体になれることを意味しない」を足した。

**限定は3箇所（チェックリスト項目 / 「昇格の判定」節の冒頭 / 「置き場の判定」節）に入った。**

### 実装SO の結果 — 3レーンが同じ中核を崩した

3レーンすべて実返却・空返しなし（cursor 190秒 / codex `gpt-5.6-sol` 300秒 / claude 562秒）。生出力は `tmp/so-288-m4/` だが揮発するので**要点を本文へ転記する**。

**最も重い1件 ── owner が本単位から外した「実行」を、私が enum の意味として再導入していた。**

処分値の `promoted` を「**昇格させる**」と定義し、限定に「マージ前に**同じ PR へ載せられる**昇格まで」と書いていた。**どちらも実行を含意する。** 正本は closure を「昇格候補の洗い出し」、実行を merge 後に置いており、**owner は実行主体を #305 へ切り出している。** 3レーンのうち2レーンが独立にこれを名指しした。

**直した形**: enum を **`required` / `not-required` / `unknown`** に変え、限定を「**扱えるのは判定までである。昇格の実行は本節の外にある**」に書き換えた。**negative knowledge だけは Step 5 が in-PR で実行するので例外として明記した**（正本がそう定めている）。

**claude が出したもう1件が構造的に重い。**

既出の扱いを「why が skill 本文 等に在れば既出」と書き、置き場の判定で「手順・語彙・禁止 → skill / rule / hook」と書いていた。**この2つを合わせると、canonical skill を編集する単位は構造的に `not-required` へ落ちる** ── why を skill に書くので既出になる。**#288 が問題にした「0件」を規範として固定してしまう形だった。本単位自身がまさにその型の単位である。**

**直した形**: 既出は**正本の判定基準に従うと書くだけにして本節での言い換えをやめた**（文書型で疑いを立てず、要旨が実在するかの充足度で見る）。skill / rule / hook は**昇格先の追加ではなく「併設する実装アーティファクト」**として別に書き、「**併設したことは、なぜそう決めたかの昇格判定を代替しない**」を足した。

**残り4件も反映した。**

| 指摘 | 直した内容 |
|---|---|
| Q1〜Q4 の合否演算が未記載（AND なら正本に無い新しい入場規則） | **「4問は合否ゲートではない。全件 AND とは書かない」**と明記した |
| `unknown` と「疑わしきは残す」が重なる（材料があって評価が割れる場合が両方に該当） | `unknown` を**一次材料が取得できなかった場合に限定**し、**評価が割れる場合は「疑わしきは残す」に倒す**と書き分けた。各判定に**参照した材料**を書かせる |
| Step 2 の判定レコードが read/write 契約の述語 P1（Step 3 の箇条書きを対象）から外れる | 判定は **Step 3 の該当箇条書きを pointer で指す**形にした。Step 3 の蒸留シグナル行に「**Step 2 で初めて見つけた negative knowledge は本行にも書く**」を足した（Step 5 の母集団が本行と「原則」行から取るため） |
| 行数が stale（249→302 と書いたが実体は 311） | PR 本文と本 episode の両方を直した |
| 効果の言い切り4件 | 「検討したかが通る位置に置く」→「判定欄を置く。通ることは保証しない」／「#291 / #305 が着地するまで inert」→「どちらも必要条件だが着地すれば到達と実行が成立するとは限らない」／「core は満たす」→「判定欄が存在するところまで」／「役割を一意にした」→「書き場所の契約は一意にしたが P1 の対象になるかは未確定」 |

**可搬性の観点は3レーンとも不成立**（hub 固有パスの焼き込みは無し）。

### この段の学び

**SO を起動した直後に自分で3件見つけ、SO はさらに深い層で同じ方向の欠陥を出した。** 自分で見つけた3件は「**限定が抜けている場所**」で、SO が出したのは「**限定した内容そのものが正本と衝突している**」だった。**記載場所を直すことと、記載内容が越境していないことは別の検査である。** 前者を直して安心していた。
