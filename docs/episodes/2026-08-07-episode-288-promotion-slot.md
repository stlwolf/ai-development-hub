# #288 昇格の判定に機械可読な置き場を与える — 印と欄の二重アンカー

**この記録はリアルタイム追記である。** 着手時に枠を作り、判断・撤回・棄却をその場で書いている。closure はマージ前。

**注入された negative knowledge item（分母の記録）**: `01KYJ76D7CS7EBY3WDYY1NS9Y2` / `01KYJ76D830XME16ZFXC2XRPZZ` / `01KYW0BPJNHP94TNX0VG4G11TX` / `01KYMRE1NC7XX6N66RQ0MGGHF1`

## Context（なぜこの作業が始まったか）

PR #306 が `episode-retrospective` の closure に「昇格の判定」を必須項目として置いた。判定値は `required` / `not-required` / `unknown` の3値で、1件ずつ書くことを求めている。**しかし成果物である episode の側に、その判定を置く決まった形が無かった。** 判定を書いたかどうかを後から構造的に取り出せない状態だった。

本単位はその置き場を作る。gate 3 で owner が範囲を決め、**「義務の移設ではなく多重アンカー」**という整理が入った — 作業中にその場で置く印を一次アンカーとし、closure の必須項目を最後のアンカーとして残す。

plan は3版を経ている（`.oe/plan-288b-promotion-slot.md`）。作業層の doc なので消えるが、判断の要点はこの episode に残す。

## M3. gate 3 — owner が「多重アンカー」で範囲を決めた

owner の整理（`.oe/addendum-288-marker.md`）:

- 昇格と closure はもともと一緒になるよう設定されたものではない。昇格は4層ドキュメントのフローの話。
- closure は episode の品質を高めるために採用したもので、役目は「AI が作業を終えたと思った後から、マージされて人間の承認が出るまでに起きたこと」を振り返ること。随時追記とは離れた立て付け。
- **それでも closure に昇格の判定が乗っているのはおかしくない。** 理想はゲートが1個の常に動くコンポーネントとして毎回判断してくれることだが、そうはならなさそうなので、**それで動かなかった場合に最後にもう一度確認するフロー**として立て付けられているから。
- アンカーは多い方がよい。**ただしマーカー式は難易度が高いので、マーカーだけに賭けない。**

これを受けて rev.3 の差分は1点に絞った — **その場で印を置く側を足す。**

## M4. 段A の実装 — 印の規約と判定の欄

### 印の接頭辞は実測で決めた

昇格の印: 判定値そのものではなく固定接頭辞を印に使う判断

最初は `昇格候補:` を考えたが、**`昇格候補` は42ファイルに出現し、`- ADR 昇格候補:` という既存の FB 項目とも衝突する**ので使えなかった。`昇格の印` はリポジトリ内0件で衝突が無い。

**この選択の根拠は M0 の測定である** — enum 値（`unknown` 等）の grep は3ヒット中2件が無関係な別 enum の偽陽性だった。固定接頭辞は語形が変われば外れるので、この誤りが起きにくい。実際、既存の `振り返り不要:` は変形の `振り返り不要の補足:` を正しく除外する（自分で確認した）。

### 印の規約を箇条書き1行でなく小節に展開した

昇格の印: 配布物のなかで新しい規約にどれだけの紙幅を与えるか

§12「ライフサイクル規範」は箇条書きの規範集で、既存項目はどれも1行である。印もそれに倣って1行で済ませる案を採らず、**箇条書きに1行足したうえで小節を立てた**。理由は、印には「候補であって判定ではない」「後追いで貼らない」「1行だけ書く」という**守られないと機能しない条件**が複数あり、1行に畳むと落ちるため。ただし**書き手が守る内容そのものは1行**（`昇格の印: <1行>`）に保った。

### 規約の形式例に実在の記録を引くのをやめた

昇格の印: 規約の形式例と実在の記録の関係

Episode テンプレートの `promotion` 例に、最初は #288 の実在の判断（`enum を実行含意から判定値へ変える`）を書いていた。**しかし実在の記録ではその判定は `required` で、私は例に `not-required` と書いていた。** 形式例が実在の記録と食い違う状態である。

読み手が「これは #288 の判定を記録したものだ」と誤読しうるので、**プレースホルダ形（`<この単位が下した判断の1行要約>`）に変えた。** これは #286 が既知の罠として記録している「規約自身が形式例を含むと素朴な検査が見本を本物と誤認する」と同じ族で、**誤認するのが機械ではなく人間である版**である。

### #306 の文言を守った確認

`episode-retrospective` への追加は checklist の外側に隣接する小節として置き、**既存の箇条書き行には一切触っていない**。確認は diff の削除行がゼロであること（`git diff -U0 | grep '^-'` が空）。同じ確認を `document-format.md` にも当て、どちらも純粋な追加のみであることを確かめた。

見出しレベルで1件直した。最初 `####` で足したが、Step 2 配下の既存小節は `###` なので、`##` から `####` への飛びになっていた。`###` に揃えた。

### self-application で自分の規約を破っていた（注入 item の予測が当たった）

**私が置いた印5件は、すべてバッククォートで囲まれていた。** つまり規約が定める裸行の形（`昇格の印: <1行>`）に**1件も合致しておらず**、規約どおりの grep では0件だった。**規約を書いた本人が、その規約を最初から守れていなかった。**

囲んだのには理由があった — この episode は印の規約そのものを論じているので、裸の `昇格の印:` 行が「規約の例示」と混ざるのを避けようとした。しかし**ここでの印は例示ではなく本物である**。混ざるのを避けるべきは `document-format.md` の側で、そちらには既に「本節の例示は検査対象から除く」と書いてある。

**直し方は2つあった** — (a) episode を規約どおりに直す (b) 規約を緩めて囲み形も許す。**(a) を採った。** 置き場の値打ちは裸行が grep できることに依存しているので、自分の書き損じに合わせて規約を緩めると、値打ちそのものが消える。

これは注入された item `01KYW0BPJNHP94TNX0VG4G11TX`（自分が名指しした失敗の型がある領域で書き手に回るとき、自分の成果物にその型が出ていないか明示的に当てよ）が**予測したとおりの形で実際に出た**。当てなければ、規約と第1号の実例が食い違ったまま配布されていた。

**そして印の難易度についての owner の見立ての裏付けにもなった** — 規約を書いた本人が同じセッション内で破るのだから、「随時マーカー式は難易度が高い」は正しい。closure の独立の問いを floor として残した設計判断は、この一件で支持される。

## M5. 段B — 配布側（委譲固定節）への反映

### 終端が広がった経緯

段A の実装後、**owner が私の surface した齟齬に回答してスコープを広げた**（`.oe/addendum-288-guardrail.md`）。私は「`doc-flow-guardrail` が印を知らないまま残る」を限界として上げ、スコープ外に置いていた。owner の判断は逆だった。

> **「配布側に入ってないとまた先進まん」**

理由は構造的である。**印の規約が配布物に入らなければ、固定節だけを読んで作業する委譲では印が発火しにくく、一次アンカーの被覆が落ちる。** 分母を作るのが印なので、委譲分の狙いが薄くなる。（子が正本を自分で開く経路や、親が個別に指示する経路は残るので、「発火しない」と言い切ることはできない。gate 4 の指摘で弱めた。）

**私の留保は過剰だった。** 「3ツールへ配る枠を触るのは慎重に」と考えたが、この repo はチーム運用ではなく owner 個人の実験的なドッグフーディングであり、**ここで作られるものそのものが知見であり実際の PoC** である。前提の見積もりを誤っていた。

終端の再定義に当たるので、**黙って吸収せず plan を rev.4 に更新してから着手した**（`implementer-contract` の指示矛盾ガードの順序）。

### 固定節に書く量の判断

昇格の印: 配布される固定節に、実行に必要な最小をどこまで含めるか

**二重定義を避けよと言われている一方で、固定節だけ読んで子が実際に印を置けなければ意味がない。** 線をこう引いた。

- **含めた**: 発火のトリガ（「思ったその場で」）・トークンの形（`昇格の印: <1行>`）・迷ったら置いてよいこと。**これが無いと子は正本を開かない限り行動できない。**
- **含めなかった**: 後追いで貼らない・1行だけ書く・乱発を咎めない・なぜ固定接頭辞なのか・分母との関係。**すべて正本（`document-format.md`「ライフサイクル規範」節）にあり、固定節はそこを指すだけにした。**

結果は**1行の追加のみ**（`git diff --numstat` で 1 insertion / 0 deletion）。

### 固定節の中の例示が本物と誤認されない理由

固定節は brief に貼られるので、`昇格の印: <1行>` という文字列が委譲文書へ複製される。**これが印として拾われないのは、正本が「行頭の裸行」を印の条件として定めているからである** — 固定節ではインラインコードで囲んであるので条件を外れる。M4 で自分が踏んだ「囲むと規約に合致しない」性質が、ここでは逆に**例示と本物を分ける弁別子として働く。**

**ただしこの整理は、正本に裸行の規則が書かれて初めて成立する。** 段B の commit 時点では規則が正本に無く、整理が先走っていた（gate 4 の指摘）。M6 で正本に足した。

なお brief は作業層（gitignored）で episode ではないので、そもそも検査の母集団に入らない。

cursor はさらに踏み込んで、**エコシステム全体がトークンをインラインコードで教えている**（固定節・skill・episode の説明文がすべて囲み形）ため、**形そのものが取り違えを増やす方向に働く**と指摘した。M4 がその一次証拠である。

### P0-2: 「導入日」が値として存在せず、self-complete でなかった（2レーン独立）

しかも正本は「言えること」として「不在を3通りに切り分けられる」と書いており、**成立しない主張を正本に書き込んでいた**（前版の gate 2 で同じ型を指摘されたばかりである）。

**直した**: `date` が `2026-08-07` より前、と具体日を節に書いた。あわせて**日単位の粗さ**（導入日当日の episode は対象外に落ちない）を限界として明記した。

### P1-3: checklist の「該当なし」と `promotion: []` の写像が無かった（cursor）

必須項目は「該当なし」は正当と書いているだけで、`[]` との対応が無い。**放置すると「全部 not-required だったから該当なし → `[]`」と読まれ、rev.1 で SO に潰された故障が再発する。** checklist 本文は触れないので、隣接節に写像を1行足した。

### P1-4: 印と `promotion` エントリの対応規則が無かった（codex）

「印を分母の候補として使う」としか書いておらず、**各印が実際に検討されたかを後から言えない**。`subject` の一意性規則も無かった。隣接節に「印1件につきエントリ1件（同じ判断の重複印はまとめてよい）」「closure 側と同じ1行要約を使う」を足し、正本側に `subject` の一意性を書いた。
