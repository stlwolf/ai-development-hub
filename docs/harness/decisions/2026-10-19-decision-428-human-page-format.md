# 人向けのページは持ち運べるスキル html-one-pager で作る

## コンテキスト

owner に判定や回答を求めるページ（claude.ai の artifact）は、統括が作るたびに形がばらばらで、2026-10-18 時点の39件で答え方が4通りあった。判定カードの描画・保存・代替表示の文言は、7ページでほぼ同じ文字列を写していた。2026-10-19、owner と統括は質問フェーズでページの形を11点決め（#428 のまとめのコメント）、そのうち「部品の正本はリポジトリのファイルに置く」「スキルの中に hub への参照を入れず、持ち運べる形にする」が、作り方の前提になった。

この decision は、その11点を実装するときに下した判断のうち、次の作り直しや別のスキルでも同じ分岐に立つものを残す。ページの形そのもの（ヘッダー・札の言葉・部品の一覧）は owner の決定で（ヘッダーは見本を見た owner の調整で、2行から項目名と値の表に変わった）、現行の契約は SKILL.md と用語集が正本である。

## 決定

1. **持ち運ぶスキルのスクリプトは、Python 3（3.9 以上）の標準ライブラリだけで書く。** hub のほかのスクリプトは Bash だが、このスキルは hub の外のリポジトリやほかのツールのセッションへ持ち出す前提なので、追加のインストールが要らないことを優先する。owner がゲート3 の Q2 で承認した（2026-10-19）。
2. **描くのはスクリプトで、ページの JS は答え・保存・回答待ちの件数だけを持つ。** データ（JSON）を検証してから静的な HTML を描き、誤りがあれば HTML を書かない。いまの判定ページは、ページに埋め込んだ配列から JS で描いていた。
3. **保存される形は、いまの判定ページと同じにし、書き方だけを変える。** collection `decisions` に、doc id をカードの key にした `{key, choice, note, at}` を置く。統括の回収の手順（`ArtifactData` の list）は変わらない。書き方は、文書全体の書き直しから、まだ保存できていない項目だけの `update`（文書がまだ無いときだけ4項目の `set`）に変える。
4. **回収したあとの正本は、ページに埋め込んだ `answers` である。** 回答済みのページは選択肢と補足欄を押せない状態にし、保存先を読まず書かない。owner がゲート3 の Q3 で承認した。

## 根拠

### 決定1（Python 3 の標準ライブラリ）

- 退けた案は3つある。Bash と jq は hub の慣習に合うが、jq は既定で入っていない環境があり、HTML のエスケープと規則ごとの誤りの文言を書きにくい。Node は標準だけで書けるが、macOS と Linux の既定には入っていないことが多い（推測）。スクリプトを使わずにモデルが型を写して書く形は、いまのやり方そのもので、検証も描画の共通化も無い（plan の「ゲート1」節）。
- 設計SO の選択肢拡張は、ブラウザで動く生成器（Python が要らない）を挙げた。ページを作るのはシェルを使えるセッションのモデルで、ブラウザの画面を操作する経路を持たないことが多いので退けた。
- 当時の前提は「持ち出す先に Python 3.9 以上がある」ことである。macOS 付属の Python は 3.9.6 で、検査はこれと 3.13 の両方で通している。

### 決定2（スクリプトが静的に描く）

- ヘッダーの2行や札の言葉が決まった形で出ることを、ブラウザなしの検査（標準の unittest）で文字として確かめられる。JS が動かない表示でも中身は読める。
- 退けた案は「JS がページの中のデータから描く」（いまの判定ページの形）で、ヘッダーや部品の検査にブラウザが要り、JS が失敗すると何も出ない。
- 設計SO の選択肢拡張は、意味づけした HTML と `data-*` 属性を正本にする案も挙げた。標準ライブラリの HTML の読み取りで構造を検証するのは、JSON の型を見るより規則も文言も書きにくく、モデルが HTML を書くと前のページを写すのと同じ揺れが入りやすい（推測）ので退けた。読み物の本文だけは `--body` で HTML の断片を差し込み、信頼したコードとして扱う。
- 当時の前提は「ページの JS の自動の検査は持たず、ブラウザでの確かめで補う」ことである。実装SO の Cursor のレーンは、これを残るリスクとして挙げた。

### 決定3（保存の形を同じにし、書き方を変える）

- 保存の形を変えると、統括の回収の手順と、いま公開されている判定ページの読み方が変わる。owner の決定8 は「保存の形は、いまの判定ページと同じにする」である。
- 書き方を変えた理由は、設計SO の指摘3 である。文書全体を手元の状態から書き直すと、別の画面が先に選んだものを古い状態で上書きしうる。Copilot は実装のレビューで、補足の書き込みの失敗のあとに選択肢を押すと、補足を書き直さずに「保存しました」と出す形も見つけた。いまの形は、まだ保存できていない項目をまとめて1回で書き、全部そろったときだけ「保存しました」と出す。
- 保存先（artifact の db）には取引も「無ければ作る」書き込みも無い。そのため、2つの画面がほぼ同時に同じ項目を書く場合と、まだ文書の無いカードの違う項目を初めて書く場合は、後から届いた書き込みが残る。ページの側では防げないので、SKILL.md の限界に書いた。

### 決定4（回収のあとは answers を正とする）

- 保存先の書き込みを止める仕組みは無いので、回収の前に開いていた画面からは、回収のあとも書けてしまう。回収した答えをページに埋め込み、回答済みのページは保存先を読まないことで、統括が回収したものだけが正であることを見た目でも示す。
- 退けた案は「回答済みのページでも入力を残す」で、選び直しても統括に届かないのに届いたように見える。

## 結果

- スキルは `canonical/skills/html-one-pager/` にあり、PR #468 で入る。名前は、ゲート3 で承認したときの `human-page` から、owner の決定で `html-one-pager` に変わった（2026-10-19・plan の H9）。マージのあとに sync で3つのツールへ配られる。
- 統括の判定ページをこのスキルで作るという hub の運用の案内は、owner の Q4 の判断どおり、マージのあとに統括が実物で試してから別に決める。
- 決定1 の前提（Python 3.9 以上がある）が崩れる持ち出し先が出たら、設計SO が挙げたブラウザで動く生成器をもう一度検討する。決定2 の前提（JS の自動の検査を持たない）は、部品が増えて JS の振る舞いが増えたら見直す。
- 追補（2026-10-23）: 決定4 は、長く更新し続ける「判断ボード」（当初の名前は「手番の1枚」）の種別について、`docs/harness/decisions/2026-10-23-decision-478-one-pager-kinds.md` の決定4 で広げた。手番の1枚では、回収した答えをカードから「決まったこと」の表へ移すときに表の行に書き、その行を正とする（ページ全体を回答済みにせず、`answers` を使わない）。保存の形と `page.js` は変えていない。
