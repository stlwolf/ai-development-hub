# oe の verb の allow は #385 の例外として配らない — 止まったときは親のペインで通し直し、照らす手段は #471 で試す

## コンテキスト

2026-10-05〜06、統括のセッションが子のセッションへ `oe-send` で owner の承認を中継したとき、auto モードの判定器が送信そのものを「Protected-Scope IaC Apply」として止めたことが2回あった。回避は、owner が子のペインに直接打つか、リポジトリごとの手元の設定に `oe-*` の allow を手で足すかの2つで、どちらも hub は配っていない。#407 は、`oe-*` の allow を hub の宣言で配るかを決める issue である。

#385（2026-10-19 マージ）は「allow は hub の正本に置かない」と決めていた。#385 の discussion は「同じ確認が何度も出ていると具体的に分かった候補が出たときに、その候補だけを見直す」とも書いており、`oe-*` はその最初の候補に当たる。そこで #407 では、「`oe-*` を #385 の決定の例外として配るか」を6つの論点について問うた。

材料を集めると、判断に効く事実が3つ出た。1つ目に、`oe-send` は宛先のペインが生きているかしか確かめないので、allow を付けると、この機種のすべてのリポジトリで、どのペインへの打ち込みも判定器を通さずに通る（discussion の 5.1 節）。2つ目に、中継の文は子のセッションで利用者の発話として届き、owner が直接打った文との出どころの区別が無い（5.2 節）。3つ目に、止まった2件はどちらも本体 2.1.289 だったが、同じ規則の拒否は後の版にもあり、版で仕様が変わったとは言えない（論点6）。

## 決定

owner は、統括が作った判定ページ（2026-10-20）で、discussion の 9節の前半10問をすべて推奨どおりとした。owner の言葉は「基本推奨でよくて、issue にするやつは一つでいいや、一旦。2つ来てたやつは一つにまとめる」である。後半の6問は「配る」を選んだときだけ答える問いで、答えていない。

1. **`oe-*` の allow は、#385 の例外として配らない（q01・論点1 の 1A を採らない）。** `canonical/claude/settings.harness.json` に `permissions` の項目は足さない。#385 の決定1 は、`oe-*` についてもそのまま成り立つ。
2. **止まったときの手当てを、暫定の手順として書く（q02・論点1 の 1B）。** 中継が判定器に止められたら、owner が子のペインではなく親のペインで、公式の手順のどちらかで通し直す。1つは、次の発話で中継する変更を具体的に名指し、判定器にもう一度判断させること。もう1つは、`/permissions` の「Recently denied」で `r` を押し、owner の手動の承認で通し直すことである。書く場所は、この decision の「手順を書く場所の提案」で提案し、統括が決める。
3. **判定器の例外の文と、宛先と中身を照らす hook は、1つの issue（#471）で試してから採るかを決める（q03・q04・論点1 の 1D と 1F'）。** owner の言葉の「2つ来てたやつは一つにまとめる」による。
4. **親が本番の操作を実行する案（1G）と、承認を会話の外に記録する案（1H）は、#262 に申し送る（q05・q06）。** 申し送りのコメントは、統括がゲート6 で #262 に書く。
5. **許可の境界を認める（q07・論点5 の 5B）。** 中継の文が子で owner の承認として扱われる可能性を排除できない。そのうえで、親の側の判定器が送信を見る機会を残す。
6. **判定器の仕様の調査の結果を、この decision と issue に残す（q08・論点6）。** 結果は「結果」の節に書く。
7. **hub の手元の層の `oe-delegate` の allow を消す（q09）。** 統括が 2026-10-20 に消した。消す前の写しと比べて、変わったのはこの1件だけで、allow は 125 件から 124 件になった。
8. **別のリポジトリの手元の層の `oe-*` の allow 2件（送信1件・登記1件）を消す（q10）。** 統括がそのリポジトリの統括に依頼し、消した報告を受けた（2026-10-20）。統括が、手元に `oe-*` の規則が0件になったことを確かめた。

決めていないことは次のとおりである。

- **配ることになったときの形。** 消す手段（論点2 の 2B）・規則の形（論点3 の 3A・3A'）・対象の verb と分け方（論点4 の 4B・4C）・読み取りの呼び方を配るか（1A'）は、配らないと決めたので判定していない。将来見直すときの材料は discussion の論点2〜4 にある。
- **#471 で何を採るか。** 例外の文と hook のどちらを採るか、両方とも採らないかは、#471 で決める。
- **調査の結果を issue に書く担当。** q08 は「issue に残す」と決めたが、誰が書くかは決めていない。

## 根拠

- **配らない理由（決定1）。** 柱は、`oe-send` の allow が、この機種のすべてのリポジトリで、生きているどのペインへの打ち込みも判定器を通さずに通すことである（discussion の 5.1 節・P1）。宛先がシェルなら任意のコマンドになり、宛先が自分のペインなら、判定器の「Tmux Self Drive」の検査を飛ばして自分宛ての利用者の発話を作れる。この代価は、規則の形や項目の分け方を工夫しても消えない。2つ目の理由は、owner の発話と中継の文を両方読める親の側の判定器が、送信を見る機会を失うことである。ただし、判定器が両方を読めることは照らす保証ではなく（4.4 節で、owner が名指していない具体的な中継が通った）、この理由は1つ目より弱い。#385 の4つの理由のうち、「全リポジトリに届く」は `oe-*` では意図に合うので弱まるが、「書き込みか任意の実行ができる」は `oe-send` に強く当てはまる（discussion の 2節）。
- **暫定の手当ての理由（決定2）。** どちらの手順も公式の文書に書かれた手当てで（P12・P16）、owner が子のペインへ直接打たずに済む。issue 本文の「同じ結果を後の turn で追わない」という拒否の文は、本体 2.1.281〜2.1.292 のもので、2.1.294 以降の拒否には付いていない（4.3 節）。owner は、名指す経路を最近実際に使ったと補足している。今回の中継の拒否で名指す経路が効くかは確かめていないので、暫定とする。
- **試してから決める理由（決定3）。** 判定器が中継を止める場面を、使い捨ての環境で3回試しても再現できなかった（4.4 節）。効くかを確かめる方法から決める必要がある。採る条件は、正当な中継が通ることに加えて、owner が承認していない中継・承認を書き換えた中継・別の宛先への中継を通さないことである（論点1）。宛先だけを見る hook（1F）は、中身の2つの条件を作りの上で満たせないので、中身も照らす形（1F'）だけを試す候補にした（ゲート2 の指摘2）。
- **#262 に申し送る理由（決定4）。** 1G と 1H は、承認の運び方と本番の操作の実行者を変える案で、#407 の問い（allow を配るか）の外にある。承認の出どころを機械が確かめられるのは 1H だけである。1G は、統括は作業に手を出さないという委譲の固定節の規律とぶつかる。
- **境界を認める理由（決定5）。** 中継の文は子で利用者の発話として届き（4.3 節・この委譲の子自身が観測した）、判定器は利用者の発話が操作を具体的に名指していれば soft_deny を外す（P4）。判定器は委譲した別の agent の出力を同意として扱わない（P6）が、tmux の経路で届いた文にはその区別の印が付かない。代わりにならないことを機械の側で保証する仕組みは、いま無い。
- **手元の規則を消す理由（決定7・8）。** hub の `oe-delegate` の allow は、`oe-delegate` が権限を切った子の起動の owner の門として当てにしている判定器を飛ばしていた（5.1 節）。別のリポジトリの送信の allow は、決定1 の柱と同じ代価を、そのリポジトリの中で持っていた。

## 手順を書く場所の提案（決定2）

書く場所は統括が決める。提案は次のとおりである。

| 案 | 場所 | 良いところ | 気になるところ |
|---|---|---|---|
| 推奨 | `canonical/skills/delegate-task/SKILL.md` の「send（既存ペインへの送信）」の中、「追加指示・承認の書き方（終点を書かない・#289）」の直後に、小節「中継が判定器に止められたとき（#407）」を置く | 読むのは中継を打つ統括で、承認を中継する書き方がすでにこの節にある。親子委譲の操作の手順はこのスキルが持つ（3軸分離の操作軸）。#262 の承認の手順も同じスキルにある。canonical のスキルなので、sync で3つのツールへ届き、hub 以外のリポジトリの統括も読める | スキルの文を変えるのは配布物の変更なので、PR と SO の対象になる |
| 併せて | `canonical/skills/orchestration-toolkit/SKILL.md` の「駆動層規律」に、規範を1行（「中継が止められたら迂回せず、owner に親のペインでの通し直しを頼む。子のペインへの直接の入力を既定にしない」）と、`delegate-task` への参照を置く | 規範は toolkit、手順は delegate-task という既存の分け方（#262 の承認の手順と同じ）に合う | 1行でも配布物の変更である |
| 採らない | 委譲の固定節（`doc-flow-guardrail` の②） | — | 固定節はすべての brief に貼られ、子が読む。手当てを使うのは親と owner なので、読み手が合わない |
| 採らない | hub の `CLAUDE.md` や `.claude/rules/` | — | hub の中でしか読まれない。中継は別のリポジトリの統括も打つ |

小節に書く中身は、次の4つを提案する。

1. 中継が判定器に止められたら、同じ中継を形を変えて撃ち直さない。文を隠す・別の道具で送るなどは、判定器の「Auto-Mode Bypass」が止める対象である。
2. owner に、親のペインで次のどちらかをしてもらうよう頼む。1つは、次の発話で中継する変更を具体的に名指すこと。もう1つは、`/permissions` の「Recently denied」で `r` を押し、手動で承認すること。
3. 2 で通らなかったら、それ以上は自分で手を打たず、状況を owner に報告して扱いを決めてもらう。子のペインへの直接の入力を、既定の手当てにしない。
4. 中継の文には owner の言葉をそのまま引く。中継の文は子で利用者の発話として届くので、owner が言っていない承認を書かない。

書き方は、hub に固有のパスを剥がしても指示が成り立つ形にする（canonical のスキルの規約）。

## 結果

- hub の宣言（`settings.harness.json`）は変わらない。`oe-*` の allow は hub が配らず、#385 の決定1 がそのまま `oe-*` にも成り立つ。
- hub の手元の層から `oe-delegate` の allow が消え（決定7）、別のリポジトリの2件も消えた（決定8）。この機種の手元の層に、engine の `bin/` の `oe-*` を指す allow は残っていない。
- 暫定の手順を書く場所を統括が決め、その場所に書く（決定2）。
- #471 で、判定器の例外の文と、宛先と中身を照らす hook を試す。試すときの前提として、discussion の次の事実を申し送る。
  - 判定器の例外の文は `autoMode.allow`（soft_deny の例外）で、環境の説明（`autoMode.environment`）とは別の配列である。どちらも `"$defaults"` を入れないと既定の一覧を丸ごと置き換える（P10）。
  - PreToolUse hook は会話記録のパス（`transcript_path`）を受け取るので、owner の発話と中継の文を照らせる。ただし記録は非同期に書かれ、遅れることがある（P15）。また、会話記録を読めることは、承認の出どころを証明できることではない。記録の文が owner の発話である証拠にはならない（discussion の 5.2 節）。
  - auto モードで hook の `"allow"` が判定器を飛ばすかは、文書に書かれていない（P13）。
  - 判定器が中継を止める場面は、使い捨ての環境で3回とも再現できなかった（4.4 節）。
- #262 に、1G と 1H を申し送る（決定4）。
- **判定器の仕様の調査の結果（決定6・q08）。** 調べた範囲（公式の文書・CHANGELOG・本体 2.1.302 と 2.1.304 の `claude auto-mode defaults`・この機種の会話記録）では、次のとおりである。
  - allow・ask・deny の規則に当たる操作は、判定器より先に決まる。#385 の C15 は 2.1.304 でも変わっていない（P1）。
  - 「Protected-Scope IaC Apply」は、保護された IaC の範囲に当たる資源への apply・destroy を止め、利用者が具体的な変更を名指せば外れる soft_deny である。範囲の既定は、IAM・RBAC・ネットワーク・quota・node-pool の資源と、名前かタグに prod・production を含むものである（P2・P3）。2.1.302 と 2.1.304 で既定の規則の全文は同じだった。2.1.289 とは比べていない。
  - 規則の定義が変わった証拠は無い。判定の実行の条件（判定器のモデル・長い会話の扱い・client 側か server 側か）は、2.1.281〜2.1.302 のあいだに変わっている。
  - 2.1.281〜2.1.292 の拒否の文は「別の道具・sub-agent・後の turn で同じ結果を追うな」を含み、2.1.293 で取り消された。撃ち直しが効かなかった理由の一つは、この文にあった可能性がある。
  - `oe-send` の中継の拒否は2件とも 2.1.289 だったが、同じ規則の拒否は 2.1.292 と 2.1.296 にもある。版が変わって止まるようになった、または止まらなくなった、とは言えない。
- 本 decision は、#407 の枝の PR に discussion・episode と一緒に入り、マージ前に着地する。
