# html-one-pager の本文・表・カードの形

## コンテキスト

`html-one-pager`（#428）をマージした直後、別のリポジトリの統括が読み物のページを作り、owner が2回「読みづらい」と指摘した。原因は、本文（`--body`）を素の HTML で書いてスキルの class を付けなかったこと、表をデータで書く部品が無かったこと、番号と issue の ID を1つの欄に混ぜてリンクにしなかったことである。hub の統括が作った判断のページでは、推奨が1つしかないカードでも根拠の定型文を書かされること、認識合わせの3つの塊をカードの平らな要点に流し込むことになることを、owner が指摘した。

この decision は、その直しで下した判断のうち、次に部品を足す人や、同じページを作る人が同じ分岐に立つものを残す。値や規則の一覧は SKILL.md が正本である。

## 決定

1. **本文の素の要素の見た目は、`.hp-main` の中の class を持たない要素だけに当てる。本文を包まず、詳細度は 0 にする。** 表のセルも、表とセルの両方が class を持たないときだけ当てる。class の付いた要素には、プロパティが重なるかどうかにかかわらず1つも効かない。
2. **表の識別子の列は、必ずリンクにする。リンクにできない値は検証で止める。外部の課題管理の ID は、送り元に登録した接頭辞の形（`<接頭辞>-<数字>`）だけを、文字列の中から自動で探す。** 識別子ごとに URL を書かせる形も、明示の印で参照する形もとらない。
3. **判定カードの根拠（`reason`）は任意にする。** 推奨に説明が要らないカードでは書かない。書いたのに空なら止める。owner がゲート3 の Q2 で承認した（2026-10-20）。
4. **塊のある中身は、カードの `blocks`（小見出しと要点の並び・データの文字列）に置く。外から来た文を `--body` に写さない決まりは変えない。** owner がゲート3 の Q1 で承認した（2026-10-20）。

## 根拠

### 決定1（class の無い要素だけに当てる）

- 退けた案は4つある。「class の一覧だけを置く」は、2回とも class の付け忘れが元だったので、一覧があっても忘れれば崩れる。「素の要素の見た目だけを当てる」は、部品と同じ見た目（幅の狭い画面で行を積む表・札の色）に寄せる手がかりが無い。「build.py が素の要素に class を自動で足す」は、信頼したコードとして扱う本文を書き換えることになる。「本文で表を書くことを止める」は、本文の自由を残す #428 の決定2 を狭める。
- 初稿は、本文を `div` で包み、`:where()` で詳細度を下げる形だった。設計SO が、詳細度を下げても class の側が決めていないプロパティには素の規則が効くこと、包むと書き手の `.hp-main > section` のような CSS が効かなくなることを指摘した。実装SO が、表は class を持たなくてもセルが class を持つ場合を指摘した。「詳細度で負ける」ことと「効かない」ことは別で、後者を保つには当てる対象そのものを class の無い要素に絞るしかない。
- 当時の前提は「部品が `.hp-main` の中に描く要素は、すべて class を持つ」ことである（見本の出力で確かめ、検査 `BodyLooks` が見張る）。部品を足すときにこの前提を崩すと、素の要素の規則が部品に効く。検査が赤になるので、そのときは部品の要素に class を付ける。

### 決定2（識別子は必ずリンク・接頭辞を登録して自動で探す）

- 実物で起きたのは「識別子がリンクにならない」ことである。識別子の列はリンクになることを部品の約束にし、できない値（番号と識別子を1つの欄に混ぜたものを含む）は E-L1 で止める。番号と識別子を別の列にする決まりは、こうして部品の側が半分を受け持つ。逆向き（文の欄に識別子を混ぜる）は、「#212 を見る」のような普通の文まで止めることになるので止めない。
- 外部の課題管理の ID で退けた案は3つある。識別子ごとに `{label, url}` を書かせる形は、29か所のリンクを手で書いた実物と同じ負担が残る。ID の形を正規表現でデータに持たせる形は、書き損じと重い正規表現の危険があり、書く側（モデル）の負担も増える。設計SO が挙げた「参照の台帳と明示の印」の形は、誤ってリンクになることを防げるが、入力が長くなり、実物ではまだ誤ったリンクは起きていない。
- 当時の前提は「登録した接頭辞で、誤ってリンクになる文字列は実物で出ていない」ことである。前後に語が続く ID・コードの中・URL の中は変換しない。この前提が崩れたら（登録した接頭辞で誤ったリンクが実物で出たら）、参照の台帳の形をもう一度検討する。

### 決定3（根拠は任意）

- #428 で owner が決めた判定カードの形は「推奨・理由・選択肢・補足欄」だった。認識合わせを確かめる判断のページでは、4枚のカードがどれも同じ定型文の根拠を持ち、読む側に意味が無かった。
- 退けた案は2つある。「推奨と根拠を1行にまとめる」は、定型文を書かされることを変えない。「節ごとに共通の根拠を1回だけ書く」は、実物には合うが、定型文そのものが要らないという指摘に答えない。
- 書いたのに空なら止める形は残した。空の定型文で検証を通す逃げ道を作らないためである。省いてよい条件（推奨に説明が要らない確認のカード）は SKILL.md に書いた。条件を検証では決めないので、根拠を省きすぎるページが出たら、条件の書き方を見直す。

### 決定4（塊はカードのデータに置く）

- issue と確定版は、最小の形として「SKILL.md に、中身は `--body` に書きカードは問いと選択肢だけにする、と書く」を示していた。これを退けたのは、SKILL.md 自身が「外から来た文を `--body` に写さず、データの文字列に入れる」と決めているからである。認識合わせの中身は issue の本文から作る文なので、最小の形はこの決まりに反する使い方を勧めることになり、本文の HTML を書く手間（気づき1〜3 の元）も戻ってくる。
- 設計SO が挙げた「中身の共通の木をデータで持ち、カードから参照する」形は、同じ中身を読み物とカードの両方に置く場面がまだ実物で出ていないので退けた。`blocks` は、その木の一部（見出しと要点）をカードの中に持つ形で、あとから木へ移す道を閉じない。

## 結果

- スキルは PR #475 で直る。hub の側の変更は `canonical/CATALOG.md` の html-one-pager の行に表の部品を足すことだけである（ゲート3 の Q4）。
- 保存の形 `{key, choice, note, at}`・`page.js`・完成した HTML の外部の読み込みの検査（E-B1）は変えていない。#428 の decision の決定1〜4 はそのまま効く。
- 「次の版の候補」（`links` に手元のパス・`build` が前の版を残す口・本文の `#N` の変換）は入れていない。それぞれの理由ともう一度考える条件は plan の DJ-8 にある。
- 読みやすさの最終の確かめ（別のリポジトリの統括が同じページを作り直して owner が読む）は、マージのあとに行う。
