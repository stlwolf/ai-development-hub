# 手順書は1本にし、本体を人向けの粗い段にする

## コンテキスト

owner は業務のサービスのインフラのリポジトリ2つで、デプロイなど更新の作業の手順書（ランブック）を作り、作業を AI にさせていた。既存を取り込んだ側では、AI 向けに書いた細かい手順書（1つのコードブロックで1つを確かめる形）を、人が手順書だけで実行しようとしたところ、前提を確かめる段の途中で止まった。止まった理由はコマンドの数ではなく、1つ1つが細かいことと、変更の種類で実行する・しないが分かれる所があったことである（#467 の材料2・業務のリポジトリの統括の要約で、元の記録はこの単位では確かめていない）。新しいサービスの側の形も、踏襲でたまたま決まっていただけだった。

#467 は、手順書の書き方と、手順書・AI のスキル・スクリプトの役割の分け方を、業務のリポジトリへ持ち出すスキル `runbook-authoring` にした。この decision は、そのとき下した判断のうち、業務のリポジトリで手順書を書き直すときや、別のスキルを作るときにも同じ分岐に立つものを残す。節の名前や終了コードの値そのものは SKILL.md が正本である。

## 決定

1. **手順書は1本にし、「手順」の本体を人向けの粗い段にする。** 段は多くても6つで、1段に1つのコマンド（多くは入口のスクリプトの1つの名前）を置く。細かい確かめはスクリプトの中に置き、確かめの番号つきの1行を出して、外れたら止まる。手で確かめ直すときの細かいブロックは「止まったときに読む表」に置く。AI も同じ手順書を、非対話の形で実行する。owner がゲート3 の Q2 で承認した（2026-10-21）。
2. **スクリプトが自分の判定で止まるのは、期待が1つに決まる確かめが外れたときだけにする。** 差分が意図どおりか・影響が許せるかのように読んで決める判定は、スクリプトが要点を出して確認を待ち、人か AI が読んで決める。業務の側の「デプロイを止めるかの判定はスクリプトで止めない」を一般化して、すべての手順書に当てる。owner がゲート3 の Q3 で承認した。
3. **手順書の検査は、検査の項目の一覧と、それを機械で見るスクリプトの両方で持つ。** 機械で見る項目には、形の決まり（節・issue の番号・日付・警告の印・参照の実在・一覧との一致・変数の直後の全角）に加えて、このスキルの中心の決まり（前提の型・手順書の種類・手順の段の数とブロックの形）を入れる。使わない語は機械で見ず、人が見る項目にする。owner がゲート3 の Q4 で承認した。

## 根拠

### 決定1（手順書は1本・本体は人向けの粗い段）

- 退けた案は5つある（plan の「ゲート1」節）。人向けと AI 向けの2本を持つ案は、同じ手順の正本が2つになりずれる。いまの細かい手順書の先頭に「この回はどのブロックを実行するか」の分岐の表を足す案（材料2 の最小の案）は、人が実行する単位が細かいままである。スクリプトそのものを手順書にする案は、スクリプトが動かないときに人が読むものが無く、issue の目的（最悪のときに人が手で操作できる）に反する。細かい手順書から粗い版を機械で作る案は、人が実行するコマンドの数を減らさない。実行できる Markdown の道具を使う案は、業務のリポジトリに道具を入れる前提になり、持ち運べる形でなくなる。
- 材料2 の1回の出来事だけに頼った判断ではない。人が自分のために書いて使えていた手順書（材料3）も、同じ分け方をしていた。owner が以前に書いた作業フローは「基本はスクリプトで作業できるので、確認系を手動で行う」と書いて番号の付いたスクリプトを順に実行し、開発環境の README は長いコマンドを入口のスクリプト1本とその下の名前で包んでいた。
- owner はゲート3 で、人が分かる手順なら AI も判断でき、AI はさらに実物のコードを見て手順の妥当性を確かめられる、と補足した。人向けに書いたもののほうが AI 向けのものより判断の軸が多いという話も添えたが、それは owner が以前に調べた話の伝聞で、この単位では確かめていない。
- 当時の前提は「入口のスクリプトを書いて包める」ことである。包むスクリプトを置けない作業（コンソールの画面だけでできる操作など）が多いリポジトリでは、段が粗くならない。そのときは、スクリプトがまだ無い所を1ブロック1確かめで書いて包む対象として残す、という SKILL.md の決まりで扱う。

### 決定2（スクリプトが止まるのは、期待が1つに決まる確かめだけ）

- 退けた案は2つある。持ち込まず各リポジトリに任せる案は、スクリプトに何を止めさせるかの線が無く、包む人ごとに揺れる。業務の側の形のまま（デプロイの判定に限る）にする案は、設定の反映や初期化でも同じ線が要る。
- この線は、決定1 の「機械で決まる所はスクリプト、人と AI は確かめと判断」と同じ線であり、手順書・スクリプト・スキルの役割の境目そのものになる。owner はゲート3 で、決定論的に判断できるもの・期待する結果が分かっているものとそうでないものの区別は、スクリプトの役割で定義できるので、一般の決まりにして全部に合わせるほうがよい、と補足した。
- 確認で断られたとき・前提が足りないとき・操作が失敗したときに止まるのは、この線とは別である。実装SO の指摘で、SKILL.md の文をそう書き分けた。
- 当時の前提は「読んで決める判定は、機械で決められない」ことである。差分の規則が十分に決まり、機械で判定してよいと業務の側が決めたら、その判定は「期待が1つに決まる確かめ」に移る。そのときはこの線を動かすのでなく、確かめの側に足す。

### 決定3（検査は一覧とスクリプトの両方・中心の決まりも機械で見る）

- 退けた案は3つある。一覧だけ（各リポジトリが自分の言語で作る）にすると、検査を持たないリポジトリでは何も止まらず、hub の受入（見本が通り、壊した見本が落ちる）も機械で見られない。スクリプトだけにすると、規則の意味を人が読めず、ほかの言語へ写すときの元が無い。手順書のブロックを実際に実行する検査は、外の資源に触れ、業務の側の CI や演習の仕事になる。
- 2つの業務のリポジトリはすでに自前の検査を持つ。スキルは「そのリポジトリに検査があればそちらを使い、無ければこのスクリプトを使う」と書く。一覧は、自前の検査に規則を足すときの元になる。
- 前提の型・種類・手順の段を機械で見るのは、人向けの段の上限と前提の4つがこのスキルの中心の決まりだからである。見出しとラベルを数えるだけなので、誤検出は少ない。使わない語（「打つ」など）を機械で見ないのは、「打ち合わせ」「作業の流れ」のような普通の語に当たりやすく、文脈の判断が要るためである。
- 当時の前提は「手順書は Markdown で、決まった見出しとラベルで書く」ことである。手順書の正本を構造化したデータ（YAML など）にして Markdown を作る形（設計SO の選択肢拡張）は、確かめの番号とスクリプトのずれが実物で繰り返し起き、人が見る項目では止まらなくなったら、もう一度検討する。

## 結果

- スキルは `canonical/skills/runbook-authoring/` にあり、PR #479 で入る。マージのあとに sync で3つのツールへ配られる。
- 業務のリポジトリで既存の手順書をこの形に書き直す作業と、人が手順書だけで通す演習は、業務の側で行う。演習で人が止まった所は、決定1 の前提（包めるか）と決定3 の人が見る項目を見直す材料になる。
