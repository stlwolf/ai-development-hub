# html-one-pager のページの種別と識別子

## コンテキスト

`html-one-pager` には、ページの目的（`purpose` の3つ）と部品の一覧しか無く、SKILL.md は「目的は部品の組み合わせを縛らない」と書いていた。どの中身をどの部品でどう並べるかが毎回ページを作る側の解釈になり、owner は 2026-10-20〜21 に当てはめのずれを4回指摘した（#478）。同じ時期に、候補の番号を `#3` と書いた箇所がすべてリポジトリの issue へのリンクになった（#477）。深掘りで owner は、番号は何を指すかでリンク先を決め、ページの中の項目の接頭辞は書き手の気分で決めずにフォーマットとしてそろえる、と決めた（「利便性が第一。アンカーは読みやすさのため」）。

この decision は、その直しで下した判断のうち、次に種別や部品を足す人、同じページを作る人が同じ分岐に立つものを残す。値や規則の一覧は SKILL.md と用語集が正本である。

## 決定

1. **ページの種別（`kind`）はデータに必須の1つの値として書き、種別ごとに要る部品・置いてよい補足・並び・本文の可否を閉じた許可の表で検証する。** 種別は既存の部品の組み合わせの名前で、描く部品は増やさない。前の版の `purpose` は `kind` に置き換え、書けば理由つきで止める。`kind` の無いデータは既定の種別に畳まずに止める。
2. **ページの中の識別子を定義できるのは、カードの札と表の番号の列（列の型 `no`）の2か所だけにする。接頭辞の語は種別ごとに決め、用語集の「識別子の接頭辞」の節に置き、検証と描画の両方が同じ語を読む。** 書かなければ種別の接頭辞と順から番号を振る。
3. **本文の番号と識別子は、指すものでリンク先を決める。** `#N` は issue、`PR #N` は PR（`/pull/N`）、`owner/repo#N` は送り元と同じホストのそのリポジトリの issue、ページで定義した識別子はそのカードや行へのページの中のアンカーにする。裸の数字とページで定義していない識別子はリンクにしない。
4. **判断ボード（長く更新し続けるページ・当初の名前は「手番の1枚」で、owner のレビューで改名した）は、既存の部品の組み合わせだけで種別にする。番号は必ず書かせ、決まったカードはその番号のまま「決まったこと」の表へ移し、移したカードの答えは表の行を正とする。** #428 の決定4（回収のあとは `answers` を正とし、回答済みはページ単位）を、判断ボードでは「移したカード単位」に広げる形で、保存の形と `page.js` は変えない。owner がゲート3 の Q2 で承認した（2026-10-23）。
5. **一覧から選ぶページは、表の行ごとに選ばせる。行の答えは判定カードと同じ形 `{key, choice, note, at}` の文書に、行ごとに1つずつ保存する。** 選び方のカードに選ぶ数（上限は必須・下限は任意）と推奨の行を書き、doc id は `<選び方のカードの key>--<番号の数字>`、`choice` は選んだら `pick`、外したら `null` とする。回答待ちの件数には行を数えない。owner がサンプルを見て決めた（H8・2026-10-23）。
6. **レビューのページは、依頼したレビューの情報（対象・種類・経由・観点・なぜ）を必須で持ち、指摘の一覧の前に見せる。** 経由は決まった値にせず自由な文で書く。owner がサンプルを見て決めた（H8・2026-10-23）。

## 根拠

### 決定1（必須の種別と閉じた許可の表）

- 退けた案は4つある。「部品から種別を推し量る」は、いまの解釈のぶれをスクリプトに移すだけで、認識合わせと承認は部品が同じ（判定カード）なので見分けられない。「種別ごとの雛形を写して書かせ、検証しない」は、写したあとに変えればいまと同じぶれが残る。「種別ごとのデータの形を持ち、スクリプトが部品に組み立てる」は最も強く縛れるが、同じ部品に2つの書き方ができ、既存のデータの形をすべて変える。「依頼の単位（カード）に契約を付けて合わせ、ページの種別を持たない」（設計SO の代替案）は、混在するページを分けずに保てるが、どの契約をどう並べるかの解釈が作る側に残る（plan の「ゲート1」節）。
- 余計な部品をどこまで止めるかは、閉じた表にしたうえで、置いてよい補足を実物・見本・いまの SKILL.md が要るとした分だけ許す形にした。止めすぎると、種別に収まらない中身を無理に当てはめる元になる。要る部品と並びの決まりは、実物で起きた当てはめのずれ（認識合わせを平らな要点に流し込む・一覧の番号を `#N` で書く・選ぶ場所が分からない）を止めるために置いた。
- `kind` を必須にしたのは、古いデータを既定の種別に畳めないためである（`purpose: decide` のデータが、認識合わせ・承認・一覧から選ぶ・束のどれかを決められない）。古いデータを直す手間は1行の追加と1行の削除で、統括が作った実物の7件では、元のデータは `kind` と `purpose` の2件だけで止まり、`kind` を足すと当てはめのずれのある5件が種別の規則で止まり、中身を直すと7件とも通った（episode の I1-8）。
- 当時の前提は「種別は7つまでで、足すときはコードと検査を一緒に直す」ことである。種別の規則をデータ（定義のファイル）で持つ案は、「承認のカードは最後に1枚」のような条件の書式を持つことになるので退けた。種別が増えて規則のコードが読みにくくなったら、もう一度考える。種別に収まらず分けたページが実物で繰り返し出たら、依頼の単位の契約の案をもう一度考える。

### 決定2（識別子は札と番号の列でだけ定義し、接頭辞は用語集が持つ）

- 要点や本文の行頭の `B2:` でも定義できる形は、要点の文の書き方を規則にすることになり、平らな要点に流し込むずれを勧めるので退けた。表の最初の列を番号の列とみなす形は、上位の候補を並べる表のように番号を持たない表を区別できない（実物の一覧から選ぶページにある）ので、列の型 `no` で示す形にした。
- 接頭辞の語を用語集の「札の言葉と固定の文」の表に足す初稿は、設計SO の指摘で退けた。その表の言葉は、答える部品のあるページの埋め込みデータに丸ごと入るので、既存のページの出力が変わり、JS が使わない語をページに持ち込む。別の節に置き、語は文字だけ（数字と記号を含めない）にした。記号を含めないので、ページの中の識別子は外部の課題管理の ID（必ず `-` を含む）・`#N`・`PR #N` と同じ文字列にならない。
- 書いたものと書かないものを混ぜると止める。振る番号が書いた番号と重なりうるためである。判断ボードだけは位置で振らない（決定4）。
- 当時の前提は「1ページの中の識別子は、ページの中で重ならなければ足りる」ことである。版をまたいで同じ番号を別の項目に使い直すことは止められない。ページの外（別のページや文書）からページの中の項目を指す形は、今回の目的（ページの中の読みやすさ）の外として探していない。

### 決定3（番号は指すものでリンク先を決める）

- ページの中のアンカーは、ページで定義した識別子の文字列と完全に一致するものだけにした。接頭辞の形に当たるものをすべてリンクにする形は、定義の無い番号が飛び先の無いリンクになる。明示の印（`[[Q2]]`）で書いた所だけリンクにする形は、誤ってリンクになることは防げるが、owner の「本文に B2 と書けば飛ぶ」と合わない。アンカーは JS を使わないふつうのリンクで、#428 の決定2（JS は答えだけを持つ）を保つ。
- `PR #N` のリンク先は、#469 の plan の DJ-5 で `/issues/N`（GitHub 以外の置き場でも通りやすいという推測）にしていたのを、owner の深掘りの決定で `/pull/N` に変えた。GitHub では `/issues/N` からも PR へ転送されるが、`/pull/N` は転送を待たずに開く。GitLab などでは PR のリンクが開けないことを、SKILL.md の限界に書いた。
- 番号を並べる書き方（`候補43・41・49`）は、番号が3つ以上並び、並んだ番号がすべてページで定義されているときだけ止める。続く数字もリンクにする形は、裸の数字をリンクにすることになり、`Q2・3件` の3も Q3 へのリンクにしてしまう。2つだけの形は普通の文と見分けられないので止めない（設計SO の指摘で初稿の条件を直した）。実物の確かめでは、この規則が、選び方のカードの根拠と塊に残っていた並べる書き方を2か所拾った。
- 当時の前提は「書き手は接頭辞と番号を続けて書く」ことである。実物には `候補 3` のように空白を入れた書き方があり、いまはアンカーにも止まりにもならない（episode の I1-8）。この形が繰り返し出たら、空白を許すか止めるかを決め直す。`#N` の境界（`feature/#212` の `#212` がリンクになる）は、既存の出力を変えないために今回は変えていない。

### 決定4（判断ボード）

- 別のリポジトリの統括が報告した5つのずれのうち4つ（決まったものと開いているものが混ざる・どこまでが今か分からない・問いを個別に答えられない・本文がカードの上に出る）は、既存の部品の組み合わせ（要る順の節・決まったカードを表へ移す・問いを1枚に1つ・本文を置かない）で直る。値の依頼は表の行で見せるところまでで、値は補足欄か会話で受け取る。値のためにカードを作らせない。
- 退けた案は2つある。カードに `due`・`for`・カード単位の決定（`decided`）を足して自動で移す形（Q2 の C）は、決定4 と `page.js` に触れる一方、カード単位の鍵が無いと表せないことが実物でまだ出ていない。要求・回答・回収の履歴を正本にしてページを作る形（設計SO の代替案）は、転記の漏れや番号のずれを減らせるが、正本を毎回書き直す完成形の JSON から履歴へ移すことになり、今回の範囲を大きく超える。
- 番号を必ず書かせるのは、位置で振ると、カードを表へ移すたびに残りの番号がずれ、本文の参照が別の問いを指すためである。
- 当時の前提は「決まったカードを表へ移すのはデータを書く側の手で、スクリプトは移したかを見ない」ことである。移し忘れや番号の使い直しが実物で繰り返し起きたら、#466（いつ作り・更新し・止めるか）と一緒に、C か履歴の案をもう一度考える。

### 決定5（一覧の行は行ごとに選ばせ、行ごとの文書で保存する）

- owner の指摘は、候補が10件を超えると、下まで読んで番号を覚え、上のカードへ戻って答える形になる、だった（サンプルのレビュー）。
- 保存の形を変えないことを先に決めた（#428 の決定3）。退けた案は2つある。選んだ行の並びを1つの文書の `choice` に入れる形（`"候補2,候補5"`）は、`choice` が選択肢の key か `null` という今の意味を変え、回収の手順も変わる。行の各々を判定カードにする形は、カードが行の数だけ並び、一覧の表で読める形が崩れる。行ごとの文書にすると、今の保存の仕組み（変えた項目だけを書く・文書が無いときだけ4つの項目を書く）と回収の手順（`decisions` を読んで `answers` へ写す）がそのまま使える。
- 「上位2つを選ぶ」のような選び方の指定は、選ぶ数の上限と推奨の行の2つで表す（選ぶ数の指定とも、推奨の行の指定とも読めたため、両方を持てる形にした）。
- 実物の確かめで、公開したサンプルの保存先に、行ごとの文書が4つの項目の形で入ることを確かめた（owner がサンプルを触った記録・episode の「H9 と、H8 の受入の確かめ」）。
- 別の画面と同時に選んで上限を超えたときは、ページは行を外さずに知らせ、回収した答えが上限を超えていたら検証で止める（実装SO の指摘・H10）。自動で外す案を退けたのは、どの行を外すかは答える人が決めることで、ページが古い順や新しい順で外すと答えを書き換えてしまうためである。
- 当時の前提は「1つのページで選ぶ一覧は1つ（選び方のカードは1枚）」ことである。1つのページで2つの一覧から別々に選ばせたい場面が出たら、選び方のカードと表の対応を持たせる形を考える。

### 決定6（レビューの依頼の情報）

- owner の指摘は、指摘の一覧の前に、どんなレビューを依頼したか（観点・なぜ取ったか・何を経由したか）があると、指摘を解釈する情報が足りる、だった（サンプルのレビュー）。統括から、1行を足すだけでなく、よい方向があれば調整したい、と補足があった。
- 退けた案は2つある。依頼の1行を自由な文1つで持つ形は、owner の挙げた3つ（観点・なぜ・経由）の抜けを検証で拾えない。指摘の一覧ごと（`lane` ごと）に依頼の情報を持つ形は、同じ依頼を2つのモデルに出した場合に同じ文を2回書くことになる。
- 経由を決まった値にしなかったのは、PR のレビュー・Copilot・セカンドオピニオン・人のレビューのように、道具や人が増えても書けるようにするためである（owner の「経由は汎用に」）。
- 当時の前提は「依頼の違う2つのレビューは、1ページに混ぜずにページを分ける」ことである。混ぜたい場面が実物で出たら、指摘の一覧ごとに `via` を上書きできる形を考える。

## 結果

- スキルは `canonical/skills/html-one-pager/` で直り、この単位の PR で入る。hub の側の変更は `canonical/CATALOG.md` の html-one-pager の行1つである。
- 保存の形 `{key, choice, note, at}`・`template.html`・完成した HTML の外部の読み込みの検査（E-B1）は変えていない。`page.js` は、一覧から選ぶ行の保存のために足した（決定5）。#428 の決定1〜3 はそのまま効き、決定4 には判断ボードの規則が加わる。
- 種別をいつ作り・更新し・止めるか（工程との対応）は #466 に残る。SO のまとめの中身の決まりは、SO のスキルの側に残る。
- 実物の確かめ（次の判定のページで、owner が当てはめのずれや番号のリンクの誤りを指摘するか）は、マージのあとに統括が行う。
