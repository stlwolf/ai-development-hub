# html-one-pager の問いのカードと答え方

## コンテキスト

2026-10-24、#466 の判定ページ（26問・承認）を見た owner が「何を聞いているのか分かりづらい。今までのは判断できていたが、これは判断できない」と指摘した。題が話題の名前で、推奨の選択肢が「推奨どおり」で、discussion の符号を縮めた言葉が並んでいた。統括が同じ URL に出し直した版2（題を問いの形・「何を決めるか」「推奨の中身」「ほかの案」の塊・ボタンを中身の言葉）で、owner は26問と判断ボードの9問に答えた。同じ日に owner は、問いが多いと縦に長いので答えたカードを畳めるとよいと述べた。さらに #466 の決定12 で「答え方の形（問いのカードか、一覧から選ぶか）でページを分けない」と決め、一覧から選ぶ問いを同じページに置く直し（#466 の discussion の 13.5 節の9項目）をこの issue に入れた。

この decision は、その直しで下した判断のうち、次に部品や書き方の決まりを足す人、同じページを作る人が同じ分岐に立つものを残す。値・規則・検査の一覧は SKILL.md と用語集が正本である。

## 決定

1. **問いのカードの書き方は、塊（`blocks`）の形のまま、塊の題の語を用語集に置き、題の形・選択肢の名前・塊の題の並びを検査で止める（E-Q1〜E-Q3）。** 問いのカードは、判定カードのうち認識合わせのカードと全体の承認のカードを除いたものである。題は括弧書きを除いて「か」「？」で終わり、1つ目の塊は「何を決めるか」、2つ目は「推奨の中身」、置くなら3つ目は「ほかの案」で、問いのカードには平らな要点を置かない。選択肢の名前は推奨の語で始めず、括弧書きだけにしない。どれも表記の規則で、中身が分かるかは見ない。owner がゲート3 の Q1 で承認した（2026-10-24）。
2. **答えたカードは、頭（札・題）を外に置き、中身をブラウザの開閉の要素（`details` と `summary`）で包んで畳む。開閉はブラウザが受け持ち、`page.js` が足すのは「保存先の答えを最初に読んだときに答えのあるカードを1回だけ畳む」ことと「畳んだときの答えの行の文字」だけにする。** 手元で選んだカード、中の要素にフォーカスがあるカード、選んだ行が選べる数を超えている選び方のカードは畳まない（操作中の要素と、外すよう知らせる文を隠さないため）。回答済みのページは答えのあるカードを畳んで描く。#428 の決定2（JS は答え・保存・回答待ちの件数だけを持つ）を、「答えに応じて答えたカードを畳む」まで広げる。owner がゲート3 の Q2 で承認した（2026-10-24）。
3. **一覧から選ぶ問いは、選び方に `tables`（表の `key` の並び）を書いて選ぶ表を名指し、承認・束・判断ボードのページにも、組をいくつでも置けるようにする。** 選ぶ表の番号は種別に関係なく `候補<数字>` で、承認・束・判断ボードでは必ず書く。承認と判断ボードでは選ぶ表を選び方のカードの節の直後にカードの順・`tables` の順で置き、束では group の中に置いて group の送り元でリンクにする。行の答えの key（`<カードの key>--<番号の数字>`）がほかのカードの key と重なれば止める。一覧から選ぶページの今の書き方（`tables` を書かない）は変えない。#478 の決定2（接頭辞は種別ごと）を「種別と、選ぶ表かどうかで決める」に広げ、決定5 の当時の前提（1ページに選ぶ組は1つ）を外す。
4. **判断ボードで選び方のカードを回収するときは、選んだ行の数を `check --answers` で確かめ、カードと一緒に選ぶ表もページから除く。** `check --answers` には保存先の文書をすべて `answers` の形に写して渡し、ページに無い key（前に表へ移したカードの答え）は数えるだけにする。カードと表を除く前のデータに当てる。owner がゲート3 の Q4 で承認した（2026-10-24）。回収の手順そのもの（いつ読み、どの順に移すか）は #538 に残す。
5. **開いた問いが0枚の判断ボードは、番号の列の無い表だけで置ける。** owner がゲート3 の Q3 で承認した（2026-10-24）。

## 根拠

### 決定1（書き方を塊のまま検査で止める）

- 退けた案は2つある（plan のゲート1 の木）。「SKILL.md の決まりと見本だけにする」は、統括が版2 の書き方を memory を頼りに手で守っている状態（#536 の確定版の「暗黙の工程」）を変えない。版2 の前の判定ページも、スキルの見本も、題が問いの形でなかった（episode の P1 で数えた）。「専用の欄（`ask`・`detail`・`alternatives`）を足し、スクリプトが塊に組み立てる」は書き間違いが起きないが、カードの中身の書き方が `points`・`blocks` に加えて3つ目になる。#478 の決定1 が退けた「同じ部品に2つの書き方ができる形」に当たる。
- 選択肢の名前の検査を「推奨の語を含む」でなく「推奨の語で始まる」にしたのは、設計SO が「非推奨 API を置き換える」のような中身のある名前を止めると指摘したためである。「実施する（推奨どおり）」は通るが、中身の語があり、owner が指摘した形（中身の無いボタン）ではない。
- 当時の前提は「owner が読めないと指摘したのは表記の形（話題の名前の題・中身の無いボタン・前提の無いカード）で、形を止めれば大半を防げる」ことである。題が問いの形でも何を決めるかが分からないページが実物で繰り返し出たら、中身の検査（たとえば「何を決めるか」の文の長さや、ほかの塊との重なり）を考える。

### 決定2（ブラウザの開閉で畳み、JS は答えに応じた1回だけ）

- 退けた案は3つある。「JS で開閉のボタンを描き、答えのあるカードにだけ出す」は答えの無いカードを畳めなくできるが、開閉の状態を JS が持つことになり、#428 の決定2 を必要以上に崩す。「押したときだけ畳む」は決定2 のままだが、判断ボードのように答えてから回収するまで残るページでは、読み込み直すたびにすべて開き直す（#466 の discussion の場面 i）。「頭を `summary` の中に置き、題を押すと開閉する」（初稿）は押す場所が大きいが、題の中の `#N` のリンクを押す操作と開閉の操作が混ざり、`summary` の中の見出しは読み上げで見出しとして扱われないことがある（設計SO の指摘）。
- 答えの無いカードも手で畳めることは受け入れた。畳むと「答え: 未回答」が出て、ヘッダーの回答待ちの件数も残る。
- 当時の前提は「開閉の状態を覚えておく必要は無く、答えから決まれば足りる」ことである。読む人が畳んだ状態を読み込み直しても保ちたいと言ったら、手元の保存（artifact では空になることがある）か保存先に開閉の状態を持つ形を考える。

### 決定3（表を名指して、どの判断のページにも組を置く）

- カードと表の結び付きを「選び方の側に表の key を書く」にしたのは、今の一覧から選ぶページが1枚の選び方のカードで複数の表を扱い、推奨の行もカードに書くためである。「表の側にカードの key を書く」は向きが逆で、「表の位置で名指す」は部品を足し除きするとずれる。
- 承認・束・判断ボードで番号を必ず書かせるのは、行の答えの doc id が番号の数字を含むためである。表を足したり除いたりして番号が振り直されると、保存された答えが別の行を指す（#478 の決定4 で判断ボードの番号を必ず書かせた理由と同じ形）。
- 束の選ぶ表を group の中に置いたのは、group の外に置くと、別のリポジトリの group の候補の `#N` がページの送り元のリポジトリを指し、カードと表のあいだにほかの group が挟まるためである。group の中の候補の番号もアンカーにしたのは、「ページで定義した識別子はアンカーにする」（#478 の決定3）に例外を作らないためである（設計SO の指摘）。
- 行の答えの key とカードの key の重なりを止めるのは、カードの key が `-` を含められ、選び方のカード `tools` の候補1 と別のカード `tools--1` が同じ保存先になるためである。一覧から選ぶページにはカードが1枚しかないので今まで起きず、ほかの問いと混ぜる今回の直しで初めて届く形だった（設計SO が見つけた。実装SO は同じ形を開閉の要素の id でも見つけた。knowledge item `01M5PTAXJ7H0WFZ5C83HXD4RZ4`）。
- 当時の前提は「1つの一覧から選ぶ問いには、1枚の選び方のカードと、その節の直後の表で足りる」ことである。1つの表の行を2つの問いで別々に選ばせたい場面が出たら、1つの表を名指せるのは1枚という決まりをもう一度考える。

### 決定4（回収の確かめと表の除き方）

- 退けた案は2つある。「SKILL.md に数えて確かめると書くだけ」は、#478 の決定5 で「回収した答えが上限を超えていたら止める」としたのと同じ確かめを、判断ボードだけ人の目に戻す。「判断ボードにも `answers` を書けるようにする」は #466 の決定3（表の行と台帳を正とする）と食い違う。
- ページに無い key を数えるだけにしたのは、同じ URL の保存先には、移したカードの答えが残り続けるためである（設計SO の指摘）。保存先から写したものなので、打ち間違いの key は入らない前提である。
- 選ぶ表を除くのは、移したカードの行の入力を止めるためである（13.5 の8）。除き忘れると、名指されていない `候補` の番号の列が検査で止まるので、手で直すあいだの除き忘れを拾える。
- 当時の前提は「回収はページのデータを手で直して行う」ことである。判断ボードのページそのものを台帳から作る形（#466 の「決めていないこと」で #540 に預けられている）になったら、表の除き忘れと番号の使い直しはその仕組みが受け持つので、この決まりを見直す。

### 決定5（空の判断ボード）

- 退けた案は「止めたまま、最初は見取り図（`map`）で作り、最初の判断で判断ボードに作り替える」である。同じ URL のページの種別が変わり、#466 の決定1 の「1枚を使い続ける」と合わない。

## 結果

- スキルは `canonical/skills/html-one-pager/` で直り、この単位の PR で入る。hub の側の変更は `canonical/CATALOG.md` の html-one-pager の行1つである。
- 保存の形 `{key, choice, note, at}`・行の doc id・`template.html`・E-B1 は変えていない。
- #428 の決定2 と、#478 の決定2・決定5 には、この decision を指す追補を書いた。#466 の decision の「決めていないこと」の空の判断ボードにも、決まったことの追補を書いた。
- 「答えを受け取る」節の直し（会話で名指しした答えを正とする・#466 の決定16）と、判断ボードでの受け付けと回収の手順は #538 に残る。
- 実物の確かめ（次の判定のページで、owner が「何を聞いているか分からない」と言うか・一覧から選ぶ問いのためにページを分けたか）は、マージのあとに統括が行う。
