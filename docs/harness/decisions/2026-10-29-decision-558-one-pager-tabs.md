# html-one-pager のタブ

## コンテキスト

`html-one-pager` には長いページを分ける部品が無く、2026-10-28 に統括が見取り図（13の節・約100KB）の `--body` に CSS だけのタブを手で書き、owner から余白の直しが2回来た（#539 のコメント）。着手時の認識合わせで、owner は9項目（置き場と種別・見出し・余白・段と上限・URL の `#`・隠れたタブへのリンク・未回答の件数・小さな JS と JS が動かない表示・見た目の確かめ）を推奨どおりに決めた。

この decision は、その9項目の上で下した判断のうち、次にタブや本文の部品を足す人、同じページを作る人が同じ分岐に立つものを残す。書き方と規則の一覧は SKILL.md が正本である。

## 決定

1. **タブの定義（`key`・`label`・`row`）は、データのページの `tabs` に1か所だけ置く。本文（`--body`）でタブを使うときも、本文にはタブの中身（`class="hp-tabpanel"` と `id="<key>"` を持つ `section` か `div`）だけを書く。** 本文のタブとデータの部品のタブは1つのページで混ぜられ、1つのタブの中身はどちらか片方にする。owner がゲート3 の Q53 で推奨どおりに決めた（2026-10-29）。
2. **タブの `key` は英小文字と数字だけにし、パネルの id と URL の `#` にそのまま使う。タブのあるページでは、本文の id を `hp-` で始めさせない。** 描く要素の id はどれも `hp-` で始まり `-` を含むので、`key` から作る id はそれらと重ならず、本文の id も描く id と重ならない。
3. **タブを置ける種別は見取り図・判断ボード・承認・束で、束のページはタブで分けるときに限り、束の部品をタブごとに1つまで置ける。** タブの単位は、どの種別でも部品（`sections` の要素）にそろえる。owner がゲート3 の Q54 で推奨どおりに決めた（2026-10-29）。
4. **タブの帯は、答える部品のあるページの上に貼り付く帯（全部推奨どおりの案内と保存の状態）と同じ箱に入れる。帯・パネル・件数の最初の値は `build.py` が静的に描き、切り替えは `page.js` と別の小さな JS（`tabs.js`）が受け持つ。`tabs.js` はタブを選ぶ処理を1つの入口にまとめ、押す・キー・開いたときの `#`・`hashchange`・ページの中のリンクのどれもそこを通す。** #428 の決定2（ページの JS は答え・保存・回答待ちの件数だけを持つ）を、タブの切り替えと、隠れたタブを指すリンクで切り替えることまで広げる。タブごとの未回答の件数は、回答待ちの件数を持つ `page.js` が書き換える。
5. **段がいくつあっても、読み上げの上ではタブの並びを1つにし、段の名前は各タブの説明として伝える。** 段は見た目と横送りの単位である。

## 根拠

### 決定1（定義はデータに1か所・本文はパネルだけ）

- 確定版は「本文に決まった class の組を書けばタブになる」で、本文だけで完結するとも読めた。退けた案は2つある。本文のパネルに名前と段を属性で書かせて `build.py` が帯を描く形は、10-28 の参考のページのように本文のタブとデータの表のタブを混ぜると定義が2か所になり、帯を本文のどこに入れるかで、信頼したコードである本文の HTML を `build.py` が書き換えることになる。帯もパネルも本文に手で書く形（参考のページの形）は、タブの名前を2か所に書き、見た目と振る舞いが書き手ごとに揺れる（plan のゲート1 の木）。
- 定義をデータに置くと、段の上限（1段6つ）をデータだけで検査でき、帯をデータから描ける。代わりに、本文だけの見取り図でもデータに `tabs` を書く手間が増える。
- 本文の読み取りは標準の `html.parser` で、ブラウザの読み取りの決まり（暗黙に閉じる要素・`textarea` の中は文字・`template` の中は文書の外）を持たない。パネルの要素を `section` と `div` に絞り、`/>` で閉じる空でない要素と同じ属性の2回を止め、`textarea`・`title`・`template` を区別して、パネルの内外の読み方がブラウザとずれる形を減らした（設計SO と実装SO の指摘）。それでもずれる形（表の中にパネルを書くなど）は残り、SKILL.md の限界に書いた。
- 当時の前提は「本文のタブを使うページの書き手は、データの JSON も書ける（統括のセッション）」ことである。本文だけを書く書き手が出て、`tabs` を書く手間が実物で繰り返し問題になったら、本文の属性から `tabs` を作る補助を考える（定義を2か所にしない形で）。

### 決定2（`key` の形と本文の id）

- knowledge item `01M5PTAXJ7H0WFZ5C83HXD4RZ4`（利用者の key をつないで識別子を作るときは、key に使えない文字で区切る）をそのまま当てた。カードの key と同じ形（`-` と `_` を許す）にすると、`key` が `hp-card-x` のタブのパネルが、カード `x` の id と重なる。タブの名前から自動で作る形は、日本語の名前から英字の名前を作る規則が要り、名前を直すと `#` が変わって共有したリンクが切れる。
- 本文の id の `hp-` の頭を止めるのは、描く id をすべて数え上げて本文の id と比べる形（設計SO の案）より決まりが短く、描く id の作り方を足しても検査を直さずに済むためである。タブの無いページには当てていない。当てると今まで通っていたページを止めうるためで、タブの無いページの本文の id の検査は、本文の検査を扱う単位で決める（episode の follow-up）。

### 決定3（種別と、束の部品の数）

- 束のページは束の部品が1つしか置けず、部品をタブに割り当てる形のままでは分けられなかった。退けた案は、group にタブを割り当てて1つの束の部品の中で分ける形である。タブの単位が種別で変わり（部品か group か）、束の題がタブの外に残る。
- レビューのページは確定版の列挙に無く、指摘の一覧が先頭に要るので置けない。認識合わせと一覧から選ぶページは確定版のとおり対象外である。
- 当時の前提は「タブの単位は部品で足り、1つの部品の中をさらに分ける必要は無い」ことである。1つの束の部品の中の group をタブで分けたい場面が実物で出たら、group にタブを付ける形をもう一度考える。

### 決定4（帯の置き場・静的に描く・別の小さな JS・1つの入口）

- 帯を答える部品の帯と別に貼り付けると、上の帯の高さが保存の状態の文で 84〜128px に変わるたびに、下の帯の位置を JS で合わせ直すことになり、JS が動かない表示では重なる。同じ箱に入れれば、重ならないことが CSS だけで決まる。
- 切り替えを `page.js` に入れると、答える部品の無い見取り図に保存のコードが入る（#428 の決定2・保存のコードの無いページの検査）。CSS の `:target` と `:has()` だけで出し分ける形は、`#` がカードを指すとパネルの `:target` が外れて全部出るうえ、矢印キーと読み上げの印が無い。
- 件数を `tabs.js` が DOM の `aria-pressed` を見て数える形は、`page.js` を変えずに済むが、答えの状態を2か所で持ち、`page.js` の描き方に `tabs.js` が頼るので退けた。
- 入口を1つにしたのは、入口ごとに分岐を書くと、同じ `#` をもう一度押す（`hashchange` が出ない）・`replaceState` が投げる、のような組み合わせで抜けるためである（設計SO の選択肢拡張と指摘1）。実装SO はさらに、別の画面で開くリンクを取り込む誤りと、タブ自身の `#` で移らない抜けを見つけた。
- `#` は `history.replaceState` で履歴を積まずに書き換える。参考のページの `location.hash` に書く形は、パネルの id が `key` なのでページが飛び、戻るボタンがタブを1つずつ戻る。
- ブラウザでの確かめで、表の行へ移った先が既存の CSS（`.hp:has(.hp-bar) .hp-table tr:target`）の詳細度に負けて帯に隠れていたのを見つけて直した。開いたときの `#` でブラウザがパネルに当てるフォーカスの枠は、`:target` の CSS で消すと、あとでキーボードで入ったときの枠まで消えたので、開いたときのフォーカスだけを JS が外す形にした（episode の I1-5・I2-1）。
- 当時の前提は「JS が持つ状態は選んだタブだけで、ほかはデータと DOM から決まる」ことである。タブの開閉の状態を読み込み直しても保ちたい・タブを入れ子にしたい、などで JS の状態が増えたら、#428 の決定2 の範囲をもう一度考える。

### 決定5（読み上げの上で1つのタブの並び）

- 初稿は、見た目の1段をそのまま1つのタブの並び（`role="tablist"`）にしていた。選ぶものも Tab キーで止まる所も全体で1つで、左右の矢印キーは段をまたぐのに、読み上げでは別の集まりに聞こえる（設計SO の指摘5。SO はこれを「隠れていた前提」と呼んだ）。owner が決めた段の見た目は、読み上げの作りまでは決めていない。
- 当時の前提は「段は少なく（実物は3段まで）、段の名前は短い」ことである。段が多く、段の名前が長くなって説明として読み上げると冗長になったら、段ごとの集まりを読み上げで伝える別の形を考える。

## 結果

- スキルは `canonical/skills/html-one-pager/` で直り、PR #559 で入る。hub の側の変更は `canonical/CATALOG.md` の html-one-pager の行1つである。
- 保存の形 `{key, choice, note, at}`・`template.html`・E-B1 は変えていない。タブを使わないページの HTML は、style と script を除いて変わらない（9つの見本で確かめた）。
- #428 の decision の決定2 と、#478 の decision の決定1 に、この decision を指す追補を書いた。
- artifact に公開した表示（iframe の中）で、外側の URL の `#` でタブが開くか、タブを選んだときに外側の URL の `#` が変わるかは、統括が公開するサンプルで確かめる。変わらなかったら、SKILL.md の限界の文を直す。
- 段の数には上限を置いていない。幅 400px・高さ 800px で貼り付く箱はいちばん高くても画面の 30.6% だった。段が多いページで帯が画面の多くを占めると実物で分かったら、段の数の上限か、幅の狭い画面で帯を詰める形を決める。
