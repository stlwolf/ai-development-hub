# html-one-pager の見取り図の状況 — 行に状態を書く1つの部品を先頭に置き、表の分け方・題・列・件数・完了の日数は型が決め、見た目と語は状況のあるページにだけ入れる

## コンテキスト

見取り図と判断ボードは、ページごと・リポジトリごとに区画の名前・列・状態の語・終わったものの扱いがばらばらで、読む負荷が上がっていた（#668）。10枚のページを比べ、hub の見取り図に状況を当てたサンプルを3回作り直して、owner が形を決めた（状況は独立したタブ・状態ごとに表を分ける・状態は指示待ち・実行中・トリガー待ち・完了の4つ・列は表ごと・誰も持っていない作業は入れない）。

この decision は、その形をスキルに入れるときに下した判断のうち、次に見取り図の部品を足す人と、状況の更新の仕組み（#668 に残した）や判断ボードの表をそろえる作業（#539）をする人が、同じ分岐に立つものを残す。状態と列と規則の一覧は SKILL.md が正本である。

## 決定

1. **状況は、行ごとに状態を書く1つの部品（`status`）にする。表の分け方・並び・題・列・件数は型が決め、書き手は書かない。** owner がゲート3 の Q132 で推奨どおりに決めた（2026-11-18）。
2. **状況の部品は見取り図の部品の先頭に1つだけ置き、いつも本文より上に描く。タブのあるページでは最初のタブにする。本文のタブをデータのタブより先に並べる決まり（#558）の例外は、状況の部品だけに置く。** owner がゲート3 の Q133 で推奨どおりに決めた。
3. **完了の行は、型が既定2日（ページを作った日とその前の日・JST）で絞って描く。日付の項目は `YYYY-MM-DD` にする。日数はデータで変えない。** owner がゲート3 の Q136 で推奨と違う案を選び、「いったん2日分ぐらいで十分」と補足した。
4. **状況の部品の CSS（`status.css`）と語（用語集の `state.`）は、状況の部品のあるページにだけ入れる。状況の部品の無いページの HTML は変えない。** 状況のあるページの見出しの見た目（ページのタイトルと節の題）も、同じ `status.css` に置く（owner がサンプルで決めた）。
5. **状況の部品を型で必須にしない。** 統括が使い続ける見取り図には置く、と SKILL.md に書く。owner がゲート3 の Q135 で推奨どおりに決めた。
6. **概要のタブは本文のまま、「前の版からの変化」→「まとまりのつながり」→「次に進める候補」の3つの見出しを先頭に置く決まりにし、`check` では見ない。** owner がゲート3 の Q134 で推奨どおりに決めた。

## 根拠

### 決定1（行に状態を書く1つの部品）

- 退けた案は2つある。いまの表の部品に状態の印を足して書き手が表を4つ書く形（サンプルの形）は、表の書き忘れ・並びの誤り・件数の数え違いを書き手に残し、色を本文に手で書く必要があった。1つの表に状態の列を置いて描くときに分ける形は、いまの表が全行で列を共有するので、列を状態ごとに変える決まり（owner の決まったこと）と合わない（plan の DJ-1）。
- 行が状態を持つ形は、#668 の「出来事で決まった行だけを書き換える」方向にも合う。状態が変わったら行の1か所を直すだけで、行を別の表へ移さない。
- 当時の前提は「状況はページを出し直すたびに描き直す」ことである。出し直さずに行を書き換える仕組みを入れるとき（#668 に残した）、行の形（状態と日付）はそのまま使える見込みだが、件数と完了の絞り込みを描く側に置いたことは見直しうる。

### 決定2（先頭に置き、並びの例外は状況だけ）

- 並びの決まりそのものを外す形（本文をパネルごとに切り分け、データのタブと `tabs` の順に差し込む）は、どのタブでも先頭に置ける一般の形だが、本文の読み取りを位置まで広げる必要がある。本文の読み取りは Python の版の違いで直近に2回直している（PR #662・PR #664）。先頭に置きたいのは状況だけなので、壊れる場所を増やさない側を選んだ（plan の DJ-7 とゲート1）。
- 本文のタブを状況より前に置きたい見取り図が出てきたら、そのときに並びの決まりを一般の形にするかを決める。

### 決定3（完了は型が2日で絞る）

- 推奨は「型は日数を決めず、目安を題の下に出す」だった。理由は、日付の形を決める必要があり、出来事で行を書き換える仕組みと一緒に決めたほうがよい、というものである。owner は型が落とす形を選んだ。
- 型が範囲を守るので、題で「直近2日」と言い切れる。範囲を検査しないのに言い切る形は、ゲート1 で退けた（古い行が残っていても「直近」と出る）。
- 絞り込みは下限と上限の両方で見る（ページを作った日より後の日付の行も入れない）。下限だけだった最初の実装は、実装SO が未来の日付で見つけた。
- 当時の前提は「2日で十分」（owner の補足）である。日数を変えるときは `build.py` の定数1か所を直す。

### 決定4（見た目と語は状況のあるページにだけ）

- いまの作りは、CSS の全文と用語集の辞書の全体を、どのページにも埋め込んでいる。そのため `page.css` や用語集に足すだけで、状況の無いページの HTML も変わる（設計SO の指摘）。状況の CSS を別のファイルにし、状況の語を答えのページの JS に渡すデータから外すと、見本11件の HTML は変更の前とバイト単位で同じだった。
- 状況のあるページの見出しの見た目を全ページに広げる案（`page.css` を直す）は、全ページの HTML と判断ボードや承認のページの見た目を変えるので、owner が状況のあるページだけで決めた。
- 同じ形は、部品を足すたびに当てはまる。ただし、検証の理由の文に許可の一覧を並べている所（E-S1 と見取り図の E-K2）は、部品を足すと状況の無いページでも文が変わる。この単位では受け入れた（plan の DJ-12）。

### 決定5（必須にしない）

- 見取り図で必須にすると、いまの見取り図のデータ（どれも状態は随時更新）が直さないと止まり、統括の復帰の全体像のような説明だけのページにも状況を求めることになる。
- ゲート1 で、見取り図に「使い続けるページ」という宣言を足し、宣言したページだけで必須にする案が出た。宣言の書き忘れは止まらない。状況の書き忘れが実際に起きたら、この案を足す（宣言の無いページは変わらない）。

### 決定6（概要は本文のまま見出しを決める）

- 概要の骨格を型が持ち、図だけを本文の名前の付いた断片で差し込む案（ゲート1 で出た）は、見出しの欠けと順を `check` で止められるが、本文の新しい書き方とその読み取りが要り、決定2 と同じ理由で壊れる場所が増える。
- 見出しは `check` で止まらないので、ずれうる（#618 の棚卸しで、文だけで守らせる決まりはばらつきやすいと分かっている）。ずれが実物で見えたら、骨格を型が持つ案に移る。

## 結果

- スキルは `canonical/skills/html-one-pager/` で直り、PR #669 で入る。hub の側の変更は `canonical/CATALOG.md` の html-one-pager の行1つである。
- 状況の部品の無いページは、HTML が変わらない（見本11件で確かめた）。`check` の理由の文は E-S1 と見取り図の E-K2 だけが変わる。
- #558 の decision と #478 の decision に、この decision を指す追補を書いた。
- 状況の更新の仕組み、判断ボードの表をこの形にそろえること（#539）、cockpit の表示（#546）は、この decision の範囲の外である。
