# #348 会話面の output style — 測って分かったことと、未確定の採否

## いまの判定

**未確定である。** 採用するとも、採用しないとも決まっていない。

2026-09-10 に一度「採用しない」と書いたが、取り下げた。以下はその経緯である。**判定を書き換えた理由が読めるように残す。**

## 判定が動いた経緯

読み評価の設問2は「人が会話で言わない言い回しがありましたか」で、答えは「あった」か「無かった」の2値だった。owner の答えは3組のうち2組で「あった」だった。凍結した規則は「2問目で『あった』が3つのうち2つ以上なら、採用を止めて style を書き直す」なので、**字面どおり発動し、いったん「採用しない」と判定した。**

その後、owner が自分の答えの意味を訂正した。**挙げた言い回しは「あえて挙げれば」の程度で、「この言い回しはやめてほしい」という致命的なものは6つの応答の中に無かった。** 設問2は強さを取っていないので、この2種が同じ「あった」に畳まれていた。

したがって、規則は満たされていなかった。「採用しない」は取り下げ、判定は未確定に戻る。

### 動いたのは規則ではなく入力である

**この区別を残す。** 規則を読み替えたのではない。規則はそのままで、入力の意味を入力した本人が訂正した。「あった」に当たると思っていた答えが、当たらなかった。

規則を字面どおり当てた判断そのものは正しかった。次に同じ場面に当たった者が、規則を守ったのに判定が変わった理由を読めるように、ここに書いておく。

### 設問2 の欠陥

**設問2 は強さを取っていなかった。** 「あえて挙げれば気になる」と「これはやめてほしい」が、同じ「あった」に畳まれる。2つの違う原因が同じ値になるので、答えを見ても区別がつかない。

これは `#303` で見つけた欠陥と同じ型である。次に読み評価を作るときは、設問2 に強さの段階を入れる。

## この先

owner の関心は、採否から style の定義そのものへ移った。定義の書き直しを相談の形の SO でイテレーションする方針になっている。以下の観察は、**判定と独立に成り立つ**ので、書き直しの材料としてそのまま使える。

## なぜ人の答えに拒否権を置いたか

計画の途中で、凍結した指標が owner の名指しした病理を1つも捕まえない事例が出た。owner が「理解しづらい」と言った 146 文字の応答に対して、4軸すべてが閾値を下回った。原因は語彙ではなく言い方だった。**指標が取り逃す型が実在する以上、人の判断に拒否権を持たせないと、取り逃したまま採用しうる。** そう考えて、読み評価に片側の拒否権を置いた。

その拒否権は一度発動し、その後に入力の訂正で取り下がった。**仕組みとしては働いた。** 決定論の指標だけで見れば条件(a)は字面どおり満たしていたので、指標だけで進めていたら止まらなかった。止める側が一度でも効いたことは、拒否権を置いた判断の裏づけになる。

ただし、止めた根拠が「強さを取らない2値」だったことが同時に分かった。次は設問の側を直す。

## 凍結した条件の状態（判定とは別に併記する）

| 条件 | 状態 |
|---|---|
| (a) 主指標のうち2軸以上でフラグ率が下がる | **満たす。ただし確信度は低い。** 強調記号が2組から1組へ、文の数が1組から0組へ下がった。英語語は2組で変わらない。発火した組は軸ごとに1から2組しかなく、「下がった」の中身は各軸1件の事象である |
| (b) 見張り指標が悪化していない | **未達。** 英語 + する で悪化した対が1組ある |
| (c) 正確さと安全が落ちていない | **悪化の証拠は出なかった、までである。** 「落ちていないことを確かめた」とは書けない。理由は下記 |

### 条件(c) を断定しない理由

owner が2箇所で同じ限界を申告した。**元の質問の全文が無いので、回答が十全か、正確かまでは判断できなかった。** 読み評価の頁が抜粋200字しか出していなかったためである。これは測定の不備であって、応答の質についての情報ではない。

したがって条件(c)は未評価に近い。次に測るときは、評価の頁に元の質問の全文を載せる。

## owner が挙げた具体の言い回し（書き直しの材料・原文のまま）

要約しない。次のアークはここを直接読む。

**強さについての但し書き。** owner は後に、これらは「あえて挙げれば」の程度で、「この言い回しはやめてほしい」という致命的なものは無かったと訂正した。**どこから出たかという事実は変わらないが、直す優先度は高くない。** 書き直しの材料として使うときは、この3件を潰すことを目的にしない。

1. **「別に」を独立した節にするのは口語的すぎて違和感がある。**
2. **記事名を「崩れの診断と修正 3 種」のような内部の言い方へ圧縮すると、意図が汲み取れない。**
3. **「同じ方向を選んでいません」「逆（という表現）」**

### 1 と 2 は style 自身の指示が作った

**これが今回いちばん重い発見である。** 強さは低かったが、出どころが style の中にあることは変わらない。書き方を指示する文書は、指示した形そのものが読み手の違和感になりうる。

1 について、style は「本題と関係ない気付き。書くなら末尾に『別に:』で1回だけ」と書いている。**指示した形がそのまま owner の違和感になった。** owner に読ませる形として「別に:」という節を立てるのは口語的すぎた。

2 について、style は「知らない言葉を使わない」「比喩と造語を使わない」と書いている。にもかかわらず、記事名を内部の言い方へ圧縮する応答が出た。**量を削る指示が、語を説明する指示を踏み越えた。** style の中で、削る側の条項と説明する側の条項が競合しており、削る側が勝っている。

書き直しでは、この2つを直す。「別に:」の形は捨てる。量を削る条項に、語の説明を削ってはいけないという上位の縛りを付ける。

## 伏せの開封と回答

### 規則の外の読み方を持ち込まなかったこと（当時の判断・そのまま残す）

組2 は「両方にあった」なので、その1件は style 固有ではない。style 側にだけ出たのは組3 の1件である。この読み方をすれば「style 固有の違和感は1組だけ」と言える。

**当時、判定は動かさなかった。** 凍結した規則は「あった」の組数しか見ていない。そこで規則の外の読み方を持ち込むと、この計画で2回続けた条件の読み替えと同じ型になる。規則は結果を見る前に凍結したので、字面で当てた。

**この判断は今も正しい。** 判定が後で動いたのは、規則の読み方ではなく入力の意味が訂正されたからである。

### 設問5 の答え

区分が足りなくて読みにくい場面は無かった。**見出しが減ることは owner にとって問題になっていない。** 測定では対の比較でも観測でも見出しが減っており、良い変化か悪い変化かを事前に決めていなかった。この留保はこれで解ける。

### 読みやすさの自己申告は判定に使わない

style ありが1組、なしが2組だった。ただし owner 自身が順序効果を申告している。常に A を先に読むので、B を読むときに A の解釈を使っている可能性がある。単独では判定に使わない。

## 測定設計の作り直しを先送りする理由

前段で、対の比較の作り直しに2案を出していた。選定と比較に別の生成を使う案と、転記を切り詰めて位置の違いを直す案である。

**いまは着手しない。** 採用が止まって style を書き直すことになったので、測り直す対象そのものが変わる。どちらの設計を使うかは、書き直した style を測る段で決める。

**これは owner が判断を保留したのではない。前提が変わったことによる先送りである。**

## 残っている決めごと（owner）

- 書き直しを次のアークとして起こすか、別の作業を先にするか。

## この計画で分かったこと（次のアークが読む）

- **合成した題では病理が再現しない。** 12 本の合成 run で、狙った病理はほとんど出なかった。実運用の記録では出る。測る場所を実運用へ移した。
- **母集団の定義で順位が丸ごと変わる。** 全セッションを母集団にすると、読者の違う面（agent 間・委譲子・計測装置）が混ざる。owner 宛に絞ると 682 応答が 158 応答になり、ある実例の順位が 75.8% から 57.0% へ動いた。
- **観測量の集合そのものが仮説である。** 既存ルールが列挙している記号をそのまま定義に使ったので、実際に効いていた記号が視界の外にあった。
- **指標は実データに当てるまで検証できない。** 指標スクリプトを8回直した。8回とも、個票を目で読んだときに見つかった。設計した時点では1つも見つかっていない。
- **子の圧縮した書き方が、中継を通って owner の面へ出る。** 内部語が発火した14件のうち12件は、owner の発話ではなく子からの中継に応答したものだった。style は書き方を変えるが、渡された素材は変えない。
- **転記の形式で測れる軸が変わる。** terminal の export は markdown を落とすので、構造の軸は測れない。JSON の転記からしか測れない。
- **run の成否はファイルの有無で見ない。** 使用量の上限で落ちた run は、58 文字の応答ファイルとして存在する。`is_error` と `rc` で見る。
