# #407 oe の verb の許可規則を hub の宣言で配るか（判定の材料）

## 0. この文書の位置と読み方

- この文書は、owner が #407 の6つの論点を判定するための材料である。判定はまだ置いていない。owner の判定は、このあと decision に記録する。
- #385（2026-10-19 マージ）は「allow は hub の正本に置かない」と決めた。この文書は「`oe-*` の allow を、その決定の例外として配るか」を問う。#385 の discussion も「既定では配らず、同じ確認が何度も出ていると具体的に分かった候補が出たときに、その候補だけを見直す」と書いており、`oe-*` はその最初の候補に当たる。
- 用語は #385 の discussion に合わせる。許可規則は Claude Code の `permissions.allow`・`ask`・`deny` を指す。判定器は auto モードの classifier を指す。手元の層は各リポジトリの `.claude/settings.local.json`、ユーザー層は `~/.claude/settings.json` である。
- 中継とは、統括のセッションが `oe-send` で子のセッションの入力欄に1行を打ち込み、Enter を送ることである。子から見ると、利用者が打った発話と同じ形で届く。
- 根拠の強さは各行に付けた。`[verified]` は出典を開いて確かめた主張、`[measured]` は手元で試すか数えて確かめた主張（条件は 4.2〜4.4 節）、`[unverified-summary]` は出典はあるが言い切れるかを確かめていない主張、`[speculation]` は出典の無い推測である。
- 公開の文書なので、別のリポジトリの名前と中身は書かない。数だけを書く。

## 1. 推奨の一覧（先に読む表）

| 論点 | 推奨 | 一言の理由 |
|---|---|---|
| 1. #385 の例外として配るか | 配らない。止まったときの公式の手当て（親のペインでの通し直し）を暫定の手順として書き、誤って止める例を減らす手段は、効くかを試してから別の issue で決める | `oe-send` の allow は、この機種のすべてのリポジトリで、生きているどのペインへの打ち込みも判定器を通さずに通す。自分のペインへの打ち込みを止める判定器の検査も飛ばす |

確定版の「望む結果」のうち「判定器に止められず」は、この推奨では今は満たさない。止まる回数を0にすることより、どのペインへも判定器を通さずに打ち込める状態を作らないことを優先しているからである。1A を選んでも、規則に当たらない呼び方（4.3 節の変数の形の一部と worktree の形）は判定器に回り続けるので、止まらなくなるのは規則に当たる送信に限られる。

## 2. #385 の決定の読み直し

#385 が allow を正本に置かないとした理由は、decision の「根拠」に4つある。`oe-*` にそれぞれが当てはまるかを見た（knowledge item `01KZK26GQZ39WCFV5MYKQMRHWE`）。

| #385 の理由 | `oe-*` に当てはまるか |
|---|---|
| ユーザー層の allow は、この機種のすべてのリポジトリで確認なしになる（C6） | 弱まる。`oe-*` は hub が配る道具で、統括と子はどのリポジトリでも使う。全リポジトリに届くことは意図に合う。ただし、使わないリポジトリでも、そこで働く agent が `oe-send` を打てば確認なしで通る |
| 共通の形の allow のほとんどは、書き込みか任意の実行ができる | `oe-send` と `oe-delegate` では強く当てはまる。`oe-send` は生きているどのペインにも1行と Enter を送れる。宛先がシェルなら、その行はコマンドとして動く（5.1 節）。`oe-delegate` は権限を切った子を起動できる。読み取りに限った呼び方（`oe-tree` の表示など）には当てはまらない。ただし読み取りの verb にも状態を書く引数がある（論点4） |
| `union-array` は足すだけで、配った項目を個別に消せない | そのまま当てはまる。#385 は、消す手段（2B）が無いまま allow を配ってはいけないと決めた（論点2） |
| 本体の `/doctor` も、提案する allow をユーザー層には書かない（C14） | そのまま当てはまる |

したがって、`oe-*` は1つ目の理由が弱まるぶん #385 の一般論より配る余地があるが、肝心の `oe-send` は2つ目の理由に強く当たる。

## 3. 比べる基準

#385 の K1〜K3 をそのまま使う。

- **K1 危ない形を見つけられる範囲。** 届く場所・見分ける精度・止める力の3つに分けて見る。
- **K2 許可が意図せず広がる危険。** その案を入れたことで、確認なしで動くものが、意図より多くの場所や形に広がるか。
- **K3 運用と保守の手間。** owner が手で動かす回数、一覧を最新に保つ手間、誤って止めた操作を通し直す手間、効くかを確かめる手間。

この issue では、K3 の「owner が手で動かす回数」に、owner が子のペインへ直接打つ回数を含める。issue の本文は「止まったら人が直接打つ」を既定の運用にしないと書いている。

### 4.2 規則の形を試したこと

使い捨てのリポジトリで、`claude -p --model haiku --setting-sources project --permission-mode dontAsk --tools Bash --settings '<その場の JSON>'` を回した（2026-10-20・本体 2.1.304）。dontAsk は確認の要るものを自動で拒否するモードなので、規則に当たったかを拒否されたかで見られる。打たれたコマンドは stream-json の記録で確かめた。verb は副作用の無い `oe-tree --help` にした。記録は master の作業層 `tmp/407-oe-allow-rules-distribution/407-perm-test/` にある。

| 試験 | 規則 | 打ったコマンドの形 | 結果 |
|---|---|---|---|
| Q0 | なし | master の絶対パス | 拒否（対照） |
| Q1 | master の絶対パス | master の絶対パス | 当たった |
| Q2 | master の絶対パス | `"$HOME/…/oe-tree"` | 当たった（規則の無い対照は拒否） |

この試験が示すのは、規則の文字列がどの呼び方に当たるかである。規則が当たるのはパスであって、そのパスのファイルの中身や、それが読み込む lib の中身ではない。master を更新すると中身は変わるが、規則はそのまま当たり続ける。

### 4.3 手元の会話記録で数えたこと

この機種の会話記録（`~/.claude/projects/` の jsonl）を読んだ。中身は書かず、数だけを書く。数え方は episode にある。2つの数は別々の観測で、片方をもう片方の母数には使えない。

- **拒否。** 10月4日〜20日の記録で、判定器が `oe-send` を含む呼び出しを止めたのは2件で、理由は2件とも「Protected-Scope IaC Apply」、本体は2件とも 2.1.289 だった [measured]。同じ理由の拒否は 2.1.292 と 2.1.296 にも1件ずつあるが、どちらも `oe-send` を含まない [measured]。
- **送信の総数。** 10月1日〜20日の記録で、Bash のコマンドの先頭に置かれた `oe-send` は 779 件あった。中継に限らず、brief の送付や報告を含むすべての用途である。呼び方の内訳は、master の絶対パス 219 件、変数 463 件、相対パス 92 件、素の名前 5 件である [measured]。別のリポジトリの手元の層には `oe-send` の allow があるので、そのリポジトリの絶対パスの送信は判定器に回っていない。したがって、判定器が見た中継の数は分からず、拒否の率は出せない。変数の 463 件のうち、Q3 の形（当たる）と Q5 の形（当たらない）の内訳も数えていない。

- **拒否の文。** 「この拒否は結果そのものを覆う。別の道具・sub-agent・後の turn で同じ結果を追うな」という文は、2.1.285・2.1.289・2.1.292 の拒否に付き、2.1.294 以降の拒否には付いていない [measured]。
- **中継の届き方。** この子のセッション自身が、統括の `oe-send` の文を、利用者の発話として受け取っている [measured]。

### 4.4 判定器が中継を止める場面の再現（再現できなかった）

使い捨てのリポジトリに、引数をファイルに書くだけの偽の `oe-send` を置き、`claude -p --model sonnet --permission-mode auto` で、本番の IaC の変更の実行を子へ中継させた（本体 2.1.304・3回）。owner が中継の文を指定した回、曖昧に「進めて」と言った回、CLAUDE.md に「この口座は本番」と書いて Claude に中継の文を組ませた回のどれも、判定器は止めなかった [measured]。3回目は、owner が具体的な変更を名指していないのに、Claude が具体的な変更を書いた中継の文を組み、それが通った。止まるかどうかは文脈に強く依るので、この試験からは、止める条件も、例外の文や hook で止まらなくなるかも言えない。

## 5. いまの状態と許可の境界

### 5.1 `oe-send` と `oe-delegate` が実行できること（コードで確かめた）

- `oe-send` は、宛先に生のペインの番号（`%N`）を渡すと、そのまま通す。宛先が生きているかだけを確かめ、そのペインで何が動いているか（Claude Code か、シェルか）と、自分のペインかどうかは見ない。1行の文字列を打ち込み、Enter を送る（`lib/delegate-registry.sh` の `oe_reg_resolve`、`lib/delegate-send.sh` の `oe_send_line`）[verified]。
- したがって `oe-send` の allow は、「この機種で生きているどの tmux のペインにも、判定器を通さずに1行と Enter を送れる」ことを意味する [verified]（コードと P1 から言える。実際に試してはいない）。宛先がシェルなら、その行はコマンドとして動く。宛先が自分のペインなら、自分宛ての利用者の発話を作れる。判定器の P7 はこれを止める規則だが、allow に当たった呼び出しには判定器が回らない。
- `oe-delegate` は、`--claude-arg` で子の Claude Code に任意の引数を渡せる。権限を切る引数（`--dangerously-skip-permissions` など）を付けると、`--approved-digest` を求める。ただし、その値は同じ agent が `--print-approval` で計算できる。engine のコメントは「実際の起動そのものは、これまでどおり owner の門（判定器）を通る」と書き、判定器を owner の門として当てにしている（`bin/oe-delegate` の冒頭）[verified]。allow の規則はこの門を飛ばす（P1・P8）。

### 5.2 中継の許可と、子の本番の操作への承認

- 中継の文は、子の入力欄に打ち込まれる。子のセッションから見ると、利用者の発話と同じ形で届き、owner が直接打った文との出どころの区別が無い（4.3 節の最後）[measured]。
- 子の判定器は、利用者の発話が操作を具体的に名指していれば soft_deny を外す（P4）。判定器は委譲した別の agent の出力を同意として扱わない（P6）が、tmux の経路で届いた文には、その区別の印が付かない。したがって、具体的な中継の文が、子で owner の承認として扱われる可能性を排除できない [speculation]。その結果として子の本番の操作が実際に許されるかは確かめていない。
- 送信の許可そのものが、子の操作への承認になるわけではない。承認として働きうるのは、中継の文の中身と、それを読む子の判定器を通した経路である。
- 親の側の判定器は、owner の発話と中継の文の両方を読める（P5）[verified]。ただし、読めることは照らす保証ではない。4.4 節では、owner が具体的な変更を名指していないのに、Claude が組んだ具体的な中継の文が通っている [measured]。親の側の判定器が残すのは、照らす機会であって、照らす仕組みではない。PreToolUse hook も会話記録を読めるので（P15）、owner の発話と中継の文を照らす hook を作ることはできる。ただし、記録が遅れて書かれることと、記録そのものが owner の発話である証拠にならないことは、別の問題として残る。
- 確定版は「中継の許可が、子の本番の操作そのものへの承認の代わりにならないことを確かめる」ことを求めた。確かめられたのは、代わりにならないことを機械の側で保証する仕組みが無い、というところまでである。いま代わりにならないことを支えているのは、統括が owner の言葉をそのまま中継するという運用の約束である。

### 論点2 配った項目を消す手段

### 論点3 規則の形

問い: 規則をどの形で書くか。engine の `bin/` のフルパスか、`~/bin` に配った名前か。worktree から呼んだ verb をどう扱うか。

前提: 4.2 節の試験から、master の絶対パスの規則は、絶対パス（Q1）・`$HOME` の形（Q2）・同じコマンドで代入した変数（Q3）に当たり、worktree のパス（Q4）とコマンド置換で引いた変数（Q5）には当たらない。`~/bin` の名前の規則は `~` と書いたときだけ当たる（Q6・Q7）。`oe-send` は `~/bin` に配られておらず、`sync-bin.sh` が配るのは `oe-tree` と `oe-hookfire` だけである [verified]。lib を `dirname "$0"` で解く verb を symlink 越しに呼ぶと lib を見つけられない（`doc-flow-guardrail` の「verb 解決規約」）[verified]。宣言の正本はリポジトリの中の静的な JSON で、apply は値をそのまま写す。hub の正本には、owner のホームの絶対パスを書いた箇所が無い [verified]。

| 案 | 中身 | K1 範囲 | K2 広がる危険 | K3 手間 |
|---|---|---|---|---|
| 3A | master の checkout の絶対パスで書く。パスは正本に書かず、apply と check が同じ手順で組み立てる（名前付きのハンドラ） | 当たるのは、絶対パス・`$HOME` の形・代入した変数の形。worktree とコマンド置換の形は判定器に回る | 3C より狭い。別のパスに置いた同じ名前のファイルには当たらない。一方、同じパスのファイルや、それが読む lib が変わっても、許可を確かめ直すことは求められない | 中から悪い。ハンドラを1つ足し、検査の述語も対で書く（#359 の DJ-4）。いまの apply と check はスクリプトの場所からリポジトリの根を決める（`apply-claude-settings.sh` と `check-claude-settings.sh` の `REPO_ROOT`）ので、worktree から sync すると worktree のパスになる。master の checkout の決め方、決められないときの扱い、checkout を動かしたときに前に配ったパスを消す方法（論点2）を、条件として先に決める必要がある |
| 3A' | 3A に加え、統括と子の呼び方を「同じコマンドで代入した変数」か絶対パスにそろえる（スキルの「verb 解決規約」を直す） | 当たる範囲が広がる | 3A と同じ | 中。スキルの文の直しが要る。直したあとも、古い書き方は残る |
| 3B | `~/bin` に配った名前で書く（`Bash(~/bin/oe-send *)`） | 当たるのは `~` と書いた形だけ。`oe-send` は `~/bin` に無く、symlink 越しでは動かない | 3A と同じ程度 | 悪い。engine の verb の lib の解き方を変える必要がある（この issue の範囲の外） |

理由: 3A が当てるのは hub の master のそのパスのファイルだけで、別のリポジトリに同じ名前のファイルを置かれても当たらない。worktree のパスは作業ごとに変わるので並べられず、先頭の `*` で広げる 3C は、どのリポジトリのファイルにも当たる形になる。worktree から呼んだ verb が判定器に回っても、止まるのではなく、いまと同じく判定器が判断するだけである。3A の手間のうち重いのは、パスの組み立てを apply と check で揃えることと、master の checkout の場所が変わったときの後始末で、どちらも配ると決めたときの実装の条件になる。

### 論点4 対象の verb と分け方

問い: どの verb を対象にするか。読み取りの verb と、送信や登記の verb を分けて書くか。

engine の `bin/` の verb を、コードの冒頭の説明と引数の扱いで分けた [verified]。

- 読み取り: `oe-tree`・`oe-confirm`・`oe-list`・`oe-status`・`oe-vitals` など。冒頭の説明は read-only と書くが、verb のすべての引数に副作用が無いわけではない。`oe-confirm` は `--set-start-after` や `--write-latest` などで engine の状態のファイルを書く（`bin/oe-confirm`）。`oe-tree --pick` は tmux の焦点と表示を変える（`bin/oe-tree` の冒頭）。読み取りに限るなら、引数の単位で書く必要がある。
- 登記と受領印: `oe-register`（登記の書き込み）・`oe-ack`（受領印）。書き込むのは engine の状態のファイルだけである。`oe-register link` は、生きている別のペインを自分の子として登記できる。
- 送信: `oe-send`・`oe-report`。どのペインへも打ち込める（5.1 節）。
- 起動: `oe-delegate`・`oe-kick`・`oe-handoff`。新しい Claude Code のセッションを起動する。`oe-delegate` と `oe-kick` は `--claude-arg` で任意の引数を渡せる。

| 案 | 中身 | K1 範囲 | K2 広がる危険 | K3 手間 |
|---|---|---|---|---|
| 4A | issue の例どおり、日常的に撃つ verb をまとめて1つの項目にする（起動の verb を含む） | — | 悪い。起動の verb の allow は、P8 の検査と、`oe-delegate` が owner の門として当てにしている判定器を飛ばす（5.1 節） | 良い |
| 4B | 読み取り（引数の単位で絞る）・登記と受領印・送信を別の項目に分け、起動の verb は入れない | — | 項目ごとに違う。読み取りの項目は良い。送信の項目は 1A と同じく悪い（分けても送信の危険そのものは狭まらない） | 中。項目が3つになり、読み取りは引数まで書く |
| 4C | 読み取りに限った呼び方だけにする（1A' と同じ） | — | 引数まで絞れば良い。verb の名前の前方一致なら中 | 良いが、得るものは判定器を待つ時間だけである |

推奨: **配るなら 4B。起動の verb（`oe-delegate`・`oe-kick`・`oe-handoff`）は、どの案でも入れない。**

理由: 起動の verb を外す理由は verb ごとに少し違う。`oe-delegate` と `oe-kick` は、`--claude-arg` で任意の引数を渡せるので、権限を切った子を起動できる。engine は、その起動の owner の門を判定器に任せている（5.1 節）。allow で判定器を飛ばすと、#262 の承認の手順が当てにしている門が消える。`oe-handoff` は、後継のセッションを起動し、前任を止める工程を持つ。項目を分けることの効き目は、送信の危険を狭めることではなく、送信だけを外す・読み取りだけを残す、といった判定をあとで項目ごとにできることにある（論点2 の 2B と組み合わせる）。

### 論点5 許可の境界

問い: `oe-send` や `oe-delegate` を allow にすると、何が実行できるようになるか。中継の許可が、子の本番の操作への承認の代わりにならないことを確かめる。

確かめたことは 5.1 節と 5.2 節に書いた。要点は3つである。

1. `oe-send` の allow は、この機種で生きているどのペインにも、判定器を通さずに1行と Enter を送れるようにする。宛先がシェルなら任意のコマンドになり、宛先が自分のペインなら自分宛ての利用者の発話を作れる。
2. 中継の文は、子のセッションでは利用者の発話として届き、owner が直接打った文との出どころの区別が無い。具体的な中継の文が子で承認として扱われる可能性を排除できない。
3. owner の発話と中継の文の両方を読めるのは、いまは親の側の判定器である（hook も会話記録を読めるが、そうする hook はまだ無い）。読めることは照らす保証ではない。代わりにならないことを機械の側で保証する仕組みは、いま無い。

| 案 | 中身 | K1 範囲 | K2 広がる危険 | K3 手間 |
|---|---|---|---|---|
| 5A | 境界を文書に書くだけにし、allow を配る（1A と組む） | 親の側の判定器は送信を見なくなる | 悪い | 良い |
| 5B | 親の側の判定器が送信を見る機会を残す（1B か 1D と組む） | 見る機会は残るが、照らす保証は無い | 1A より良い | 中 |
| 5C | 照らす役を hook に移す。宛先だけを見る形（1F）と、会話記録を読んで中身も照らす形（1F'）がある | 1F は宛先だけ。1F' は中身も照らすが、精度は未確認 | hook の `"allow"` が判定器を飛ばすなら、1F は中、1F' は良い見込み | 中から悪い |
| 5D | 承認の運び方そのものを変える（1G・1H。#262 の承認の手順を中継の段まで広げる） | 照らすのは owner 自身か、承認の記録 | 良い | 悪い寄り。#262 の範囲で、この issue では決めない |

推奨: **今は 5B。** 論点1 の推奨（1B・1D）と同じ向きである。5C の 1F' は、論点1 の別の issue で 1D と並べて試す。5D は #262 の論点として申し送る。

理由: 確定版が求めた「代わりにならないこと」を、機械の側で保証する仕組みは無い。いまそれを支えているのは、統括が owner の言葉をそのまま中継するという運用の約束である。5B は、その約束を判定器が見る機会を残すだけで、保証を足すものではない。1F' は会話記録で照らせるが、記録の文が owner の発話である証拠にはならない。承認の出どころを機械が確かめられるのは 5D の 1H だけである。

### 論点6 判定器の仕様の残りの調査

問い: #385 で済んだ「allow・ask・deny の規則は判定器より先に決まる」を引き、Protected-Scope の種類の定義と、2.1.286 から 2.1.304 までの変更を、公式の文書と CHANGELOG で確かめる。

確かめたことは次のとおりである。

- **評価の順は変わっていない。** 規則に当たる操作は判定器より先に決まる（P1）[verified]。
- **規則の定義。** 「Protected-Scope IaC Apply」「Production Deploy」「Production Reads」は、どれも「must name」の付いた soft_deny で、利用者が具体的な対象や変更を名指せば外れる（P2・P4）[verified]。範囲の既定は、IAM・RBAC・ネットワーク・quota・node-pool の資源と、名前かタグに prod・production を含むものである（P3）[verified]。本体 2.1.302 と 2.1.304 で既定の規則の全文は同じだった [measured]。2.1.289 の本体は手元に無く、比べていない。
- **CHANGELOG の 2.1.286〜2.1.304。** 中継・tmux・この規則を名指す項目は無い [verified]。規則の定義が変わった証拠は無いが、判定の実行の条件（判定器のモデル・長い会話の扱い・client 側か server 側か）は版の間で変わっている。関係しうる項目は次のとおりである。
  - 2.1.281 で、拒否の文が「拒否は、その結果そのものを覆う」と Claude に伝える形に変わり、2.1.293 でそれが取り消された [verified]。手元の会話記録でも、この文は 2.1.285・2.1.289・2.1.292 の拒否に付き、2.1.294 以降の拒否には付いていない（4.3 節）[measured]。issue 本文の「同じ結果を後の turn で追わないと明記する」はこの文のことである。撃ち直しが効かなかった理由の一つはこの文にあった可能性がある [speculation]。取り消しのあとの文で通し直せるかは確かめていない。
  - 2.1.288 で、client 側の判定器が、Sonnet 5.5・Opus 5.5 を名指す `ANTHROPIC_DEFAULT_SONNET_MODEL` を無視して Sonnet 5 を使うようになった [verified]。2.1.302 で、client 側の判定器のモデルを `CLAUDE_CODE_AUTO_MODE_MODEL` で選べるようになった [verified]。手元の環境にこの2つの変数は無い [measured]。当時あったかは分からない。
  - 2.1.288 で client 側の判定器が、2.1.302 で server 側の判定器が、会話が長すぎて判定できないときに会話を圧縮するようになった（それまでは確認を出すか、失敗していた）[verified]。止まった2件のセッションの会話の長さは確かめていない。
  - 2.1.281〜2.1.282 で、判定器を server 側で動かす形が、条件によって既定になった [verified]。server 側の判定器は、本体の版と関係なく変わりうる [speculation]。owner のセッションがどちらで動いていたかは確かめていない。
  - 2.1.301〜2.1.302 で、OpenTelemetry の記録に判定器の規則の名前が載るようになった [verified]。止まった規則を数える手段として使える。
- **観測の読み直し。** `oe-send` の中継の拒否は2件とも 2.1.289 だったが、同じ規則の拒否は 2.1.292 と 2.1.296 にもある（4.3 節）。版が上がって止まらなくなった、あるいは 2.1.289 で止まるようになった、とは言えない。判定器は文脈で判断するので、同じ文でも止まる場合と止まらない場合がある、と読むのが記録と合う [speculation]。

推奨: **この結果を decision の「結果」の節に記録し、issue にも残す。** 調べた範囲では規則の定義が変わった証拠は無いので、判定器の仕様を前提にした設計は変えない。止まった場面を数えたいなら、OpenTelemetry の規則の名前（2.1.301〜2.1.302）を使える。

## 9. owner に判定してもらうこと

推奨のとおりでよいか、別の案にするかを、次の問いごとに決めてほしい。前半の問いは案ごとに独立していて、どれか1つだけを採ることもできる。後半の問いは、前半で「配る」を選んだときだけ答えればよい。

前半（どの場合も答える）:

1. **allow を配るか**（論点1・1A）: `oe-*` の allow を #385 の例外として配らない、でよいか。
2. **今の手当て**（論点1・1B）: 止まったときに owner が親のペインで公式の手順で通し直すことを、暫定の手順として書くか。
3. **判定器の例外の文を試すか**（論点1・1D）: 効くかを試す別の issue を起こすか。
4. **中身を照らす hook を試すか**（論点1・1F'）: 効くかを試す別の issue を起こすか（3 と同じ issue にしてもよい）。

6. **承認を会話の外に記録する案**（論点1・1H）: #262 に申し送るか。
7. **境界の認め方**（論点5・5B）: 中継の文が子の承認として扱われる可能性を排除できないことを認め、親の側の判定器が送信を見る機会を残す、でよいか。
8. **調査の結果を残すか**（論点6）: 調べた範囲では規則の定義が変わった証拠は無い、という結果を decision と issue に残すか。
9. **hub の手元の層の `oe-delegate` の規則**（10節）: 消すか、残すか。
10. **別のリポジトリの手元の層の `oe-*` の規則2件**（10節）: 消すか、残すか。

後半（1 で「配る」を選んだときだけ答える）:

採否が決まったあとで、書く場所と担当を決める。2 の手順を書く場所（hub のスキルか、運用の文書か）と、8 の結果を issue へ書く人（統括か、この単位の子か）である。判定のあと、統括が実装の issue を起こし、その番号を decision に書く。

## 10. この単位の範囲の外で見つかったこと

- hub の手元の層にある `oe-delegate` の前方一致の allow は、`oe-delegate` が owner の門として当てにしている判定器を、hub の中で飛ばしている（5.1 節）。権限を切った子の起動にも当たる。消すかどうかは owner が手で決めることで、この issue の判定とは別である。（判定の前の記述。owner の判定で消すと決まり、統括が消した。decision の決定7）
- 別のリポジトリの手元の層にある、送信と登記の verb の allow 2件のうち、送信の1件は、そのリポジトリのセッションから、どのペインへの打ち込みも判定器を通さずに通している（5.1 節）。同じく owner が手で決める。（判定の前の記述。owner の判定で消すと決まり、そのリポジトリの統括が消した。decision の決定8）
- `doc-flow-guardrail` の「verb 解決規約」が書く呼び方（コマンド置換で引いた変数）は、どんな絶対パスの規則にも当たらない（Q5）。規則を配らないなら影響は無い。配るなら論点3 の 3A' で扱う。
- ユーザー層の `autoMode.environment` は、本体の `/auto-mode-setup` が書いたものと読め [speculation]、hub の宣言の外にある。この文の「Protected IaC scopes」は本体の既定と同じである（P3）。宣言で持つかは別の判断である。
