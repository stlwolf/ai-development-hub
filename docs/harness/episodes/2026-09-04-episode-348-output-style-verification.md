## 1. 期待値の宣言（Q-1 の計測器確認・**測る前に書いた**）

「output style が headless で system prompt に乗るか」を測る。乗ったかどうかは**応答の中身とは別の経路**でも見る（NK 01KYMRE1N7N0J8VP3CBZZEZ8Q3: 「効かない」と書く前に計測器を疑え）。

計測器の候補は3つ立てた。

- M1 `--settings '{"outputStyle":"<name>"}'` で headless に style を指定する。
- M2 応答内容チャネル: style に **canary 指示**（応答の冒頭に固有トークンを置け）を書き、応答にそれが出るかを見る。
- M3 system prompt チャネル: `--system-prompt-snapshot on` でセッションに system prompt を記録させ、記録された本文に style の文言が入っているかを grep する。M2 と独立。

期待値（この順で当たると予想する）:

- **E1**: M1 は効く。`--settings` は「追加で読む settings」なので `outputStyle` も反映される。**確度 中**（help に `outputStyle` の明示は無い）。
- **E2**: M2 の canary は headless の応答に出る。**確度 中〜高**。ただし headless は `-p` の一発応答なので、公式の「反映はセッション開始時」は満たしている（毎回が新セッション）。
- **E3**: M3 で system prompt が transcript に記録され、style 本文が grep で拾える。**確度 低〜中**（`--system-prompt-snapshot` の記録先が transcript JSONL かどうかは未確認）。
- **E4**: 組込み `Concise`（2.1.237 で追加）はファイル不要で名前だけで効く。**確度 中**。
- **E5**: 陰性対照（style 無し）では canary も style 文言も出ない。**確度 高**。

3値の判定規約: **乗る**（M2 と M3 の少なくとも一方が陽性で、陰性対照が陰性）/ **乗らない**（陰性対照と差が無い）/ **判別できない**（M2 が陽性だが M3 が取れず、応答差が style 由来かサンプリング由来か切れない）。

## 2. Q-1 の計測結果（2026-09-04 03:2x〜03:3x・headless・すべて `--model opus`）

判定: **乗る**（3値のうち）。応答内容チャネル（M2）と system prompt チャネル（M3・別経路）の両方が陽性で、陰性対照は陰性だった。

| # | 条件 | 観測 | 期待との一致 |
|---|---|---|---|
| P0 | style なし | 応答は `2` のみ。canary なし | E5 一致 |
| P1 | `--settings '{"outputStyle":"oe348-canary"}'`（project `.claude/output-styles/`） | 応答の1行目に `OE348-CANARY-ZQ7`、末尾に `CANARY-SECTION-MARKER-QX9` | E1・E2 一致 |
| P2 | 上と同条件で system prompt の H1 見出しを列挙させた | `# Output Style: oe348-canary` と style 本文の H1 が、`# Environment` と `# Context management` の**間**に挿入されている | E3 は**別の計測器で**達成 |
| P3 | `keep-coding-instructions: true` 版 | H1 集合は P2 と同一（style 節の名前だけが違う） | 予想外（下記） |
| P4 | 組込み `Concise`（ファイル不要） | `# Output Style: Concise` + `# Concise Style Active` が同じ位置に入る | E4 一致 |

**E3 の期待は外れ、代わりの計測器が当たった。** `--system-prompt-snapshot on` を付けても、transcript JSONL（`~/.claude/projects/<slug>/<session-id>.jsonl`）に system prompt 本文は記録されなかった（canary の grep は assistant 応答の1件だけ。session ID 名のディレクトリには `custom-title.json` しか無い）。help の「system-prompt recording is not yet enabled な環境では効果なし」に当たったと読む。代わりに **headless セッション自身に H1 見出しを列挙させる**方法（NK 01KYMRE1N7N0J8VP3CBZZEZ8Q3 の「節見出しを引用させる」）が、応答内容チャネルとは独立に「乗ったこと」と「乗った位置」を出した。

**予想外だったこと（P3）**: `keep-coding-instructions` の true / false で H1 の集合が変わらなかった。`# Delivering work` も `# Corrections` も両方に残っている。ただし H1 の粒度は粗く、**無題段落やツール定義の中の指示が落ちたかはこの計測では見えない**。「keep-coding-instructions は H1 節を落とさない」までしか言えない。plan の副作用節ではこの限界つきで扱い、段階2 の観測量に「無題段落の有無」を足す。

**副産物（#307 の独立追認）**: Opus 5 の H1 は `Harness / Session-specific guidance / Memory / Environment / Context management / Delivering work / Corrections` で、`Writing for the user` が無く `Corrections` が在る。#307 §11 の採取と一致した（採取者・方法とも別）。また rules と CLAUDE.md は system prompt ではなく **user ターン内の `<system-reminder>`** として届いていることも、4条件すべてで一貫して報告された。output style は system prompt 側、rules は user ターン側という**層の違い**が、干渉を考えるときの前提になる。

**測った鎖のリンク（NK 01KZVHE0KFDPXMY6EED80RN9ZR）**: 測ったのは「settings → headless セッション開始 → system prompt に節として乗る → canary 指示が応答に出る」まで。**測っていない**のは (a) 対話セッションでも同じか (b) レジスタ指示が応答の読みやすさを変えるか (c) owner が読みやすいと感じるか、の3リンク。(a) は plan の owner 手順に、(b)(c) は段階2 の実験に置く。

**計測器の後始末**: canary style は計測器であって成果物ではないので、worktree の `.claude/output-styles/` ごと削除した。`~/.claude/output-styles/` は P5 のために作って**元どおり削除**した（確認前の実体は「ディレクトリ不在」で、確認後も不在）。plan には style の中身を snippet として載せる。

## 3. Q-2 で設計を組むときに迷って決めたこと

**判別実験の第3の軸を足した（設計判断・その場で書く）。** brief の受け入れ基準は「lean 化で契約が消えた」説と「RLHF の長さバイアス」説をどう見分けるかを求めていた。最初に思いついたのはモデル比較（Opus 5 と Fable 5.1）だけだったが、これは**モデルそのものが違う**ので、差を「`Writing for the user` の有無」に帰属させられない。弱い判別である。

そこで棄却しかけた案を戻して考え直したところ、#307 が実測している `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0`（長版 system prompt に戻す）が、**同じモデルの中で「契約の有無」だけを動かせる唯一の手段**であることに気付いた。これを1条件だけ足すと、判別の主軸をモデル間比較から同一モデル内比較へ移せる。run は2つしか増えない。

- 採った: 長版条件を Opus 5 × style なしにだけ足す。判定はこちらを主にし、モデル比較は補助にする。
- 棄却した: モデル比較だけで判別する案。帰属が成り立たない。
- 残る限界: 長版は `Writing for the user` 以外の節も一緒に戻すので、契約だけを動かしてはいない。plan §6.3 に明記した。

昇格の印: 「同じ効果を2つの経路（system prompt 層 / モデル層）で作れるとき、同一モデル内で効果だけを動かせる経路があれば、それが帰属の主軸になる」

**プロンプト型を3から2に削った。** T3（調査報告の要約）は内容選択の軸が一番出やすいが、run 数が 1.5 倍になる。時間予算（Q-2 まで 60 分）と段階2 の実行コストを考え、follow-up に落とした。

**自作 style に `output-format-rule` §5〜§7 を入れなかった。** リンクの形や絶対パスの規則は PR 本文や issue にも効く規則で、会話面に閉じていない。入れると rules との重複が二重になり、どちらが効いたか切れなくなる。§8 §9 と結論先出しだけを素材にした。

## 5. gate 2 の結果（3レーンとも refuted）と、前倒しで潰した2件

- audit_id: `20260903183633B3FV6EBT1GAJ` / verdict: **refuted**（3/3 レーン）
- 弱 SO なので1周だけ回す。反映できるものは plan に入れ、残りは disclose する。

レーンの指摘のうち、**実行すれば即座に決着するもの2件をその場で確かめた**。どちらも私の前提が誤っていた。

**訂正1: 組込み `Concise` は「短さだけの指示」ではない。** 私は期待値に「`Concise` は短さの指示であってレジスタの指示ではないので、接着記号と体言止めは減らない、むしろ増える」と書いた。cursor レーンが「本文を読まずに宣言するのは status inflation だ」と指摘したので、`Concise` を有効にした headless セッションにその節の要旨を出させた。実際には次を持っていた。

- 「最初の一文で答えに答えよ」という**順序の指示がある**。
- 「見出し・表・箇条書きは本当に構造があるときだけ使え。既定は平文」という**文体の指示がある**。
- 「断定的に平明に書け。ヘッジを省け」も文体である。
- さらに「他の箇所の書式指針と衝突したら**この節を優先する**」と宣言している。

つまり `Concise` は自作 style の競合であり、しかも既存 rules を明示的に上書きしうる。期待値は撤回し、条件の位置づけも「長さ専用の対照」から「有力な競合候補」に変える。

### 7.9 結論の手前で気付いた見落とし — baseline は「指示なし」ではなかった

no-go を書きかけて止めた。**私の C0（style なし）は「レジスタの指示が無い状態」ではない。** `~/.claude/rules/` の14本が user ターンの system-reminder として入ったままで、その中に `output-format-rule` の §8（日本語の語彙）と §9（operator 向けの散文）がある。つまり C0 は「指示なし」ではなく「**rules 層で指示がある**」条件である。

baseline がきれいだったのは、病理が存在しないからではなく、**rules が効いているから**かもしれない。この2つを分けずに no-go を宣言すると、まったく違う結論に化ける。

- 「病理が無い」と読むなら → headless では測れない。対話へ切り替える。
- 「rules が効いている」と読むなら → **rules 層は headless では機能している**。owner が「§9 は効いていない」と観測しているのは長い対話セッションの話なので、問題は層ではなく**regime**（セッションが長くなること）にある。output style へ移しても、同じ regime で同じように効かなくなる可能性がある。

この2つは #348 の問いそのもの（会話面のレジスタを output style で制御できるか）に直結する。切り分けずに進めない。

**切り分けの方法**: `--setting-sources project,local` で user 層の rules を落とせる。実際に落ちることを先に確かめた（セッションに聞いたところ「渡されていない」と答え、残っているのは CLAUDE.md と MEMORY.md の索引だけだった。CLAUDE.md には行動規範の6項目の要約はあるが §8 §9 は無い）。この条件で同じ題を測れば、**指示がまったく無い floor** が出る。

- floor で病理が出て、rules ありで消えているなら → rules は headless で効いている。#348 の設計は「rules が効かない regime」を再現するところからやり直しになる。
- floor でも病理が出ないなら → 病理は本当にこの regime に無い。裁定5 のとおり対話へ切り替える。

これは SO の codex レーンが指摘した「配置対照が無いと帰属できない」と同じ問題だが、私は C3（同じ文面を user ターンへ）を足しただけで、**C0 自体が既に rules 条件であることに気付いていなかった**。指摘の半分しか受け取れていなかった。

昇格の印: 「baseline は『何もしていない条件』ではなく『既定で入っているものが全部入っている条件』である。既定に測りたい対象と同じ指示が含まれていないかを、baseline を置く前に数える」

### 7.10 R-0 の確定 — P0-3 は no-go。ただし病理は実セッションに実在する

**floor（rules を14本とも外した条件）でも病理は出なかった。** §7.9 で立てた分岐のうち「rules が効いているから baseline がきれい」は棄却され、「病理がこの regime に無い」が残った。

| 条件 | 本数 | 接着記号 | 体言止め | 第1文が結論でない |
|---|---|---|---|---|
| rules あり（既定） | 7 | 10 本中 1 個 | 0 | 2 / 7 |
| rules なし（floor） | 3 | 0 | 0（検出は誤検出2件） | 0 / 3 |

floor の方が英語語の密度と中黒の使用は増えたが（`output-format-rule` §8 が狙っている層）、§9 が名指ししている接着記号・体言止め・前置きは**どちらの条件でも出ない**。

**では病理はどこに在るのか。** このリポジトリの実セッション 56 本から、assistant の応答（400 文字以上）682 件を取り出して同じ指標を当てた。

| 体言止めが1個以上の応答 | **40.9%** | 0% |
| 体言止めの密度（1,000 文字あたり・平均） | 0.77（p90 = 2.23・最大 14.71） | 0 |
| 散文の割合（平均） | 0.67 | 0.22〜0.83 |

**病理は実在する。headless の一問一答に無いだけである。** これで「効かない」と「測れない」の取り違えを避けられた。

残る候補は、対話と `-p` の違いそのもの、応答の発話行為の種類（報告・計画・board 更新のような密度の高い形が実セッションには混じる）、permission mode などである。**本アークでは決めない。** 名前だけ挙げて開いたままにする。

昇格の印: 「合成した題で病理が出ないとき、実運用の記録に同じ指標を当てれば、病理が『無い』のか『その regime に無い』のかが分かる。実運用の記録は既にあるので、追加の生成コストは 0 である」

### 7.12 再設計に効く発見 — `--resume` に style が乗る

### 7.13 実例1（外部リポの export）が届いた — 病理の中身が想定と違った

owner が export を作業層に置いた（gitignored）。**別リポの識別子と業務の固有名詞は本文に書かない。** 置換表は作業層に残した。以下は種別と指標だけである。

| 文字数 | 3,423 | 中央値 1,197 / p90 2,225 |
| **見出しの数** | **0** | 中央値 3 / p90 6（見出し0の応答は全体の 11.7%） |
| 文の数 | 52 | — |

- `output-format-rule` §9 が名指ししている病理（記号圧縮・体言止め）は、**この不満の原因ではない**。私の自作 style の「日本語のレジスタ」節は、起きていない病理を狙っている。

昇格の印: 「不満の原因は、不満を言っている本人が挙げた語（読みづらい）ではなく、その応答を測って初めて分かる。既存ルールが名指ししている病理と、実際に起きている病理は別物でありうる」

### 7.14 fixture の漏れ — 実験の題を実験の作業ディレクトリに置いてはいけない

匿名化した実例1 の題（Q4）で headless を2本走らせたら、両方とも**題そのものを作業層のファイルとして見つけて**、それについて答えた。第1文は「この入力は作業層の `tmp/348-runs/prompts/Q4.txt` と1文字も違わない」と「この turn は、私が作った Q4 の fixture そのものでした」である。

原因は、実験の題を worktree の `tmp/348-runs/prompts/` に置き、その worktree を cwd にして headless を走らせたことである。Q4 は文脈から切り離された報告文なので、モデルはそれを理解しようとしてリポジトリを調べ、自分の題を見つけた。

**この2本は病理のプローブとしては無効である。** そして、これは Q4 だけの問題ではない。**plan v2 の段階2a の 45 run はすべて同じ露出を持っていた**（同じ worktree を cwd にして、同じ `tmp/348-runs/` に題も style も置く設計だった）。R-1 に進んでいたら、条件を測るつもりで「モデルが実験の存在に気付いているかどうか」を測っていた可能性がある。

- 直し方: 題を worktree の外（session の scratchpad）へ出し、cwd も実験の作業層を含まないディレクトリにする。流し直した。
- plan v3 に**実験の隔離**という節を足す。fixture・style ファイル・生の応答・指標スクリプトのいずれも、被験セッションの cwd から見えてはいけない。
- ただしこれには張力がある。owner の実 regime は「作業中のリポジトリを cwd にする」ことなので、cwd を空にすると regime が変わる。案A（実運用の観測）ならこの問題は起きない。実運用のセッションは実験の fixture を持たないからである。**これは案A を推す3つ目の理由になる。**

昇格の印: 「合成した実験を、その実験の成果物が置いてあるリポジトリの中で走らせない。被験者が実験計画書を読める配置になっていないかを、run を投じる前に確かめる」

### 7.15 実例3 が届き、私の診断を1つ取り下げた

統括が owner の貼った実例3（判断を求める応答・別リポの統括セッション・Opus 5）を作業層に置き、読み8点と plan v3 への含意を添えた。**別リポの識別子は本文に書かない。** 以下は指標と読みだけである。

**取り下げ: 「実例1 は見出し 0 で構造が無い」は転記の副産物だった。** 統括の読み8 が正しかった。検査すると、terminal の export は markdown 記法をほぼ落としている（2,133 行の export に `**` が2箇所・`#` 見出しが0箇所）。対照的に JSONL の転記は 88.3% に見出しが、96.5% に `**` が残っている。したがって **terminal の export からは構造の軸を測れない**。長さの数値は記法に影響されないので有効なまま残る。

**2つの実例を hub の 682 件の分布に置くと、同じ裾に入る。**

| **強調記号（⚠ 等）の数** | 0 / 0 | 7（**99.9%**） | 8（**100.0%**） |

### 7.16 転記の形式が測れる軸を決める（計測器の一般則）

3つの取得経路で、測れる軸が違うことが分かった。

| 経路 | 構造（見出し等） | 長さ | 記号・語彙 | 備考 |
|---|---|---|---|---|
| JSONL の転記 | **測れる** | 測れる | 測れる | markdown が生で残る |
| terminal の export | 測れない | 測れる | 測れる | markdown が落ちる・折り返しで単語が行をまたぐ |
| 会話への貼り付け | 落ちている可能性あり | 測れる | 測れる | 経由回数だけ劣化する |

指標を当てる前に、**その転記が何を保存しているか**を確かめる必要がある。私は実例1 でこれを飛ばして、転記の欠落を応答の性質として読んだ。

### 7.17 外部の先例を1件当てて、設計の穴が3つ見つかった

統括が owner 提供の2例を一次取得して作業層に置いた。1件は読者モデルで出力の形を変える skill（star 27,078・MIT・評価ハーネスつき）、もう1件は書き手側のペルソナ指定の伝聞である。統括は `[verified]` を付けていたが、設計に直接効く2点は自分で `gh api` を叩いて再確認した（`evidence-verification-rule` §3 の spot-check）。どちらも一致した。

**穴1: style の書き方に読者モデルという形があった。** 私の狙い7点は規則の列挙である。先例は「読者は〜である」という事実を先に置き、そこから規則を導いている。規則が理由に接続されるので、書かれていない場面でも同じ方向へ外挿できる。私の7点は先例の10規則と5点重なり、重ならないのは**用語の定義・強調記号の禁止・日本語のレジスタ**の3点だった。この3点が hub 固有の差分であることが、外から見て確認できた。

先例が持っていて私が持っていなかったものが2つある。**規則を破ってよい条件の明示**（「説明して」と言われたら長く書いてよい・破壊的操作は確認が優先・規則が答えを消すなら課題が勝つ・harness の system prompt が上位）と、**送る前の削除チェック**である。前者は style が正確さと安全を削るのを防ぐ安全弁で、私の案には無かった。

**穴2: 採用基準に正確さと安全の軸が無かった。** 先例の rubric は5次元の重み付きで、**正確さが 35% と最大の重み**である。読みやすさ側（簡潔 10% / 行動可能性 20%）より重い。実測も簡潔 +1.14 に対して正確さ +0.19・安全 +0.02 で、「読みやすくして正確さを落としていない」を示す形になっている。私の基準は「必須要素の欠落」しか持っておらず、owner の読み評価3問も読みやすさ側に寄っていた。

**穴3: ゲートの設計に既知の罠があり、私の基準は同じ形をしていた。** 先例の著者は、比較条件（スコアの改善）の隣に絶対条件（blocker ゼロ）を置いた結果、スコアが 4.045 → 4.473 に改善し blocker が 7 → 3 に減っても**リリースゲートが FAIL になる**と自分で記録している。私の採用基準も「主指標で改善」+「見張りが悪化しない」+「欠落が増えない」の AND で、見張りを絶対条件で書くと同じ罠にはまる。**相対条件（baseline より悪化していない）で書く**ように直した。

**あわせて自分の floor の記述を訂正した。** R-0 で「rules を14本とも外した floor」と書いたが、`--setting-sources project,local` が落とすのは user 層だけで、project の CLAUDE.md は残る。正確には「§8 §9 の無い条件」である。先例の runner は `--setting-sources ""` で全部落としており、README は理由を「切らないと baseline に自分の always-on が注入され、skill を skill と比べることになる」と書いている。**私が C0 で踏んだ罠と同族のものが、先例では既に文書化されていた。** 以後の合成 run では `""` を使い、`--model` も明示で固定する。

**届け方の対抗案も1つ増えた。** 先例は output style を使わず、skill 本体 + SessionStart hook（matcher `startup|resume|clear|compact`）で本文を丸ごと注入している。**compaction の後も再注入される**点と、ツール横断で同じ本文を配れる点が output style に無い。ただし #348 の問いは「output style で制御できるか」なので、届け方の選び直しは follow-up に置く。終端は変えない。

昇格の印: 「同じ問題を解いた外部の実装を1件当てると、自分の設計の穴が『規則の書き方の形』『採用基準の欠けた軸』『ゲートの罠』の3層で出た。しかも著者自身が失敗を文書に残しているので、踏む前に読める」

### 7.18 再 HG の裁定を受けて plan v3 を書いた — 母集団を絞ったら読みが1つ変わった

owner が4点すべて推奨案で裁定した（案A・観測量 v3・読者モデル形の style・自作を先に）。統括が母集団の絞りを条件として付けた。

**絞りの効果が大きかった。** 「owner が直接やり取りしたセッションの owner 宛の応答」に絞ると、**56 セッション 682 応答が 9 セッション 158 応答になった**。除外の内訳は委譲子セッション 23 本・agent 間のレーン 15 本・計測 probe 6 本である。**前回の分析は 77% が会話面でないものだった。**

**この絞りで読みが1つ変わった。** 実例1 と実例3 の順位を、正しい母集団で計算し直した。

| 指標 | 682 件のとき | 158 件（正しい母集団） |
|---|---|---|
| 強調記号（実例1 / 実例3） | 99.9% / 100.0% | **100.0% / 100.0%** |
| 文字数（実例1 / 実例3） | 96.3% / 75.8% | 93.0% / **57.0%** |

**文字数は主指標にできない。** 実例3 は正しい母集団ではほぼ中央値（1,648 対 中央値 1,511）である。前回「長さと構造の欠如が病理の実体」と書いたが、長さの側も母集団を正すと弱くなった。plan v3 では文字数を従に降格し、文の数を残した。

一方で**強調記号は絞っても 100% のまま**である。母集団 158 件のうち強調記号を1個でも含む応答は **0.6%（1件）** しかないのに、owner が「分かりづらい」と言った2件はどちらも 7〜8 個を持つ。**唯一、両方に一貫して効く signal である。**

昇格の印: 「順位や p90 は母集団の定義に丸ごと依存する。母集団を『全部のセッション』にすると、読者の違う面（agent 間・委譲子・計測装置）が混ざって、裾の判定が動く。分布を根拠にするなら、母集団の定義を先に書いて、除外規則を機械で回せる形にする」

**style を読者モデル形に書き直した。** 「読者は、あなたが今やった作業をその場で見ていない人である。口頭で報告を受けるのと同じ条件で読む。一度聞いて意味が取れなければ伝わっていない」を先に置き、そこから8点を導く形にした。規則の列挙から、理由に接続された形へ変えた。破ってよい条件（正確さと安全が上位・答えが消えるなら答えが勝つ）と、送る前の削除チェックも付けた。

### 7.19 gate 2 が再び3レーンとも refuted — 自分で名指しした罠を、別の場所で踏んでいた

新しい設計（観測）で gate 2 を通したところ、3レーンとも refuted だった。中心の指摘は**採用ゲートが算術的に成立しない**である。

痛いのは、私が**その罠を自分で名指ししていた**ことである。`i-have-adhd` の著者が「比較条件の隣に絶対条件を置くと、改善しても永遠に通らない」と記録しているのを読み、plan の §8 に「見張り指標は絶対条件ではなく相対条件で書く」と明記した。見張り指標では避けたが、**主指標で同じ形の床を作った**。教訓を1箇所に適用して、隣の箇所に適用しなかった。

昇格の印: 「ゲートの式を書いたら、母集団の実測値を代入して『通りうるか』を計算する。閾値の妥当性ではなく、**式が動く余地があるか**を先に見る。中央値が 0 の量に『中央値が下がる』を要求していないか」

**他に受け入れた指摘が5つある。**

**持ち越したもの**: セッション単位の無作為化（設定の切り替えが運用の負担で、切り替え忘れが交絡になる）、盲検の対比評価（R-3 の設計時に詰める）、時期交絡（無作為化しない以上は残る。開示で扱う）。

owner が「まずこれが理解しずらい文章」と返した応答（統括セッション・Fable 5.1・style なし・146 字）に、凍結した閾値を当てた。

### 7.24 その読みづらい文章は、私が書いた文章だった

実例4 の応答を読んで気付いた。**語彙も構成も、私が直前に親へ送った報告そのものである。**

私の `oe-send` はこう書いていた。「収集窓を閉じる合図を待つ」「keep-coding-instructions の観察2件（該当 skill を先に読むか・既定ブランチで先に branch を切るか）は引き続きお願いしたい」。統括が owner へ出した応答は、この3つの語（収集窓 / keep-coding-instructions の観察2件 / 合図）をそのまま使っている。

**agent 間のチャネルで使った圧縮したレジスタが、中継を通って owner の面へ出た。** output style はセッションごとの main conversation に効くので、統括のセッションが再起動すれば統括の応答には style が乗る。しかし**語彙と構成は私が供給している**。style は「どう書くか」を変えるが、「何を素材として渡されたか」は変えない。

plan の scope は「agent 間のチャネルは対象外」と書いた。機構としてはそのとおりだが、**素材の流れは面をまたぐ**。この経路は plan v3 に無い。

昇格の印: 「委譲の階層では、子が親へ送る報告のレジスタが、親から人間への応答のレジスタを汚染する。人間向けの面だけを直しても、素材が圧縮されたまま流れてくるなら戻る。子の報告にも人間可読性の規律を当てるか、親が翻訳する責務を明示するかの選択がある」

私の報告は agent 間のチャネルなので、`output-format-rule` §9 の適用外である（§9 は自分でそう書いている）。しかし**その除外が、この経路を作っている**。#263 の「読者軸」と #348 の「面の軸」が交差する場所で、どちらの issue も拾っていない。

### 7.25 凍結した指標をどう扱うか（判断が要る・子は決めない）

内部語のリストを実例4 の語で広げれば、この型は捕まる。ただし2つの問題がある。

- **凍結を破ることになる。** HG-2 は閾値（内部語の種類数 4 以上）を凍結した。リストを広げると、同じ閾値でも意味が変わる。

一方で、**いま広げるなら「後」の腕のデータは1件も見ていない**ので、前後比較の公平性は保たれる。両方の腕に同じリストを当てる限り、感度が上がるだけで、どちらかに有利にはならない。事前登録として成立する。

### 7.26 HG-3 — 物差しを語彙から「言い方」へ移した

owner の説明で、私の見立てが1つずれていたことが分かった。私は実例4 の原因を「未定義の内部語」と読み、リストを広げるかどうかを判断点に上げた。owner の説明は**「個別の用語より説明の仕方。人が会話で言わない言い回し（収集窓が開いている・崩れていたら）が問題」**だった。

つまり問題は語彙ではなく**言い方**である。「収集窓」という語を知らないことより、「収集窓が開いています」という言い方を人がしないことが引っかかっている。語を1つずつ定義しても直らない。

裁定は6件で、方向が一貫している。

- 判定に使う内部語リストは**凍結のまま動かさない**。実例4 の語で広げた拡張リストは**参考列**にする。指摘された文から語を拾って足すと、その文に合わせた物差しになるからである。私が「広げるか」を判断点に上げたのに対し、**広げないという答えが返ってきた**。
- 代わりに、判定の重みを**人の読み**へ移した。owner の読み評価に**片側の拒否権**を持たせる。「人が会話で言わない言い回しがあった」が半数以上なら、決定論指標が改善していても採用を保留する。
- 読み評価の Q2 を「知らない言葉があったか」から**「人が会話で言わない言い回しがあったか」**に書き換えた。
- style の「送る前に消すもの」に**「同僚に電話で言わない言い回し。言うかどうかを一文ずつ問い、言わないなら人が言う形に直す」**を足した。

**この4つは同じ1つのことを言っている。** 読みづらさは語の集合では定義できず、言い方の問題である。機械の指標は語しか数えられないので、言い方の判定は人に残す。指標は補助に降りる。

昇格の印: 「読みづらさを語彙の問題と読むと、リストを増やす方向に行く。owner は『説明の仕方』だと言った。語彙は数えられるが言い方は数えられないので、数えられる方に寄せた設計は、問題の一部しか掴めない。数えられないものを人に残す設計にする」

**実務の変更を2つ実施した。**

- style ファイルに1行足した。時刻は **2026-09-05T16:31:20Z**（JST 2026-09-06 01:31:20）。新しいセッションに `--settings` を渡さずに「送る前に消すもの」の項目を列挙させ、6項目目として乗っていることを確認した。
- この時刻を**第2の切る点**にした。有効化（12:05:39Z）から style 修正（16:31:20Z）までを「後 v1」、それ以後を「後 v2」とする。主たる比較は前 対 後 v2 である。後 v1 は 3 セッションしかないので参考にする。

**中継の経路も plan に書いた。** 実例4 の語彙は私の報告由来である。統括のセッションが style の下で再起動されれば統括の応答は「後」の腕に入るが、素材は子が供給し続ける。**これは style の効果を過小に見せる方向の交絡**なので、結果ノートに明記する。

### 7.27 設定の優先順位で、腕の帰属が壊れうることが分かった

別 issue（#359）の調査から、統括が公式 docs の記述を持ってきた。**`/config` の Output style 選択は project の `.claude/settings.local.json` に書かれ**、設定の優先順位は managed > コマンドライン > project local > project 共有 > user である。

### 7.39 送っていた題は発話の全文ではなく、先頭200字だった

統括が指摘し、自分でも確かめた。**15組のうち13組で、題として送った発話が切れていた。** 落ちた分は 18 字から 1,015 字で、中央値は 236 字である。

原因は `corpus.py` の1行である。母集団を作るとき、応答を生んだ発話を `last_user[:200]` で記録していた。**この切り詰めは「どの発話が応答を生んだか」を記録するためのもので、題として送る用途には向かない。** それをそのまま fork の題に使った。

| 影響 | 判断 |
|---|---|
| 腕の比較 | **成立する。** 両腕とも同じ200字を受け取っているので、切れ方は共通である |
| 読み評価の「欠け・不正確」 | **効く。** モデルは切れた質問に答えている。答えの過不足を、切れた質問に対して判定することになる |
| 読み評価の「意味が取れたか」「次に何をすればよいか」 | 効きうる |

**同じ切り詰めが、前の測定でも起きていた。** R-4b（対照の腕の破れで無効と判定済み）も同じ題を使っている。R-3 の読み評価で owner が「元の質問の全文が無いので、回答が十全か・正確かまでは判断できなかった」と2箇所で申告したのも、**この切り詰めが原因である可能性が高い**。そのときは「統括の頁の作りの不備で抜粋200字しか出さなかった」と整理したが、**頁の問題ではなく、送った質問そのものが200字だった。**

昇格の印: 「記録のために作った切り詰めを、別の用途（送る・見せる）に流用しない。記録は短くてよいが、送るものは全文でなければならない。同じ変数に両方の役目を持たせると、どちらかが壊れる」

**直した。** `corpus.py` は発話の全文を持ち、短い版が要るときは別の項目（`request_excerpt`）を使う形にした。題を書く側には、**書いた直後に元の発話と長さが一致するかを検査する処理**を足し、違えば止まるようにした。実データで確かめたところ、218 字から 1,215 字の題が切り詰めなしで書かれた。

**run はしていない。** 次の測定で使う準備までである。

### 9.3 昇格の判定の理由

内訳は `required` 10件・`not-required` 15件・`unknown` 2件である。

`required` のうち9件は、再発する失敗の型として knowledge item に収穫した。7件のファイルに収まっている。

**統括が挙げた収穫候補は4件だった。3件を足して7件にしている。** 足したのは「走っているハーネスを書き換えない」（run 4本を実際に失った）、「ゲートの式に実測値を代入する」（本アークで3つの形で外し、うち2つは別々の回に起きた）、「凍結した条件文を引用してから判定を書く」（2回続けて外し、どちらも外部の反証レーンが止めた）である。3件とも、どの成果物からも復元できず、既存の item にも同旨が無い。

`not-required` の理由は3つの型に分かれる。

- **既存の knowledge item に同旨が着地している。** 「契約は名前でなく機能で探す」「指標を本番前に1本測って疑う」は `01KYMRE1N7N0J8VP3CBZZEZ8Q3`（ヒット0件を対象の不在と読むな）と `01M07QDKE73BTK0Q3K90FE4G9T`（対照で走査の健全性を確かめる）が持つ。「実験の題を実験の作業ディレクトリに置かない」は `01KYSKQHDT86GZW87E8EDMSE46`（遮断すると決めた情報が下流の実装で漏れる）が持つ。「観測量の集合そのものが仮説である」は `01KZNWK084YF0RP48337VFYMQQ`（測りやすい述語へ組み直すと元の目標事例を外す）が持つ。「設計を書く前に過去の否定的な実例を当てる」は `01KYW0BPJNHP94TNX0VG4G11TX`（自分で名指しした失敗の型がある領域で書き手に回るとき）が持つ。
- **正本の側に実装として着地している。** 日本語の文末判定で飾りを剥がす手順は `metrics.py` が変化しなくなるまで繰り返す形で持つ。母集団の定義と除外規則は plan と `corpus.py` が機械で回せる形で持つ。条項どうしの競合の解き方は v4 の「この規則より優先されるもの」節が持つ。設定の層と優先順位は公式 docs に一次で書かれている。
- **失敗の型ではない。** 帰属の主軸の置き方、外部の先例を1件当てる効果、合成で出ない病理を実運用の記録に当てる手法、語彙でなく言い方で測る設計、フィルタが病理の在る文脈を除いていないかの確かめ方、判定が動いた原因を規則と入力に分けて書くこと。いずれも有効だった手法か設計判断で、plan と結果ノートに committed で残る。覆すには測り直しが要る（議論ではなく確認である）。

`unknown` は2件で、どちらも一次の材料が本アークに1例しか無い。

### 9.6 訂正 — 「sync が output-styles を配らない」は枝が古かったための見誤り（2026-09-10）

R-7 の報告と PR #382 の本文に「`sync.sh claude` は `canonical/output-styles/` を配らない」と書いた。**これは誤りである。** 統括が指摘し、自分でも `origin/master` の実体で確かめた。

`scripts/sync/sync-claude.sh` には output-styles を配る段が実在する（master の 246〜250 行・#359 の PR #374 で 2026-09-06 にマージ済み）。**私が読んだのは枝の中のスクリプトで、枝は分岐点から master に7コミット遅れており、その段が入る前の版だった。** 枝の中の file を読んで master の状態を語った、というのが原因である。

**同じ型の誤りが本アークで3回目である。** 1回目は対照の腕が live の設定を受け継いでいたこと、2回目は確認器が同じ受け継ぎを持っていたこと。いずれも「自分が見ている対象が、語ろうとしている対象と同じか」を確かめなかった。今回は「枝の file」と「master の file」の違いである。**枝の中の file を読んで、マージ後の挙動を語らない。** 語るなら `git show origin/master:<path>` で当たる。

訂正したうえで、確かめて分かった別のことがある。**`sync_md_files` は、配り先に実ファイル（symlink でないもの）が既にあるとその1件を飛ばす**（`Skipping (regular file exists)`）。live の `~/.claude/output-styles/readable-conversation.md` は統括が手で置いた実ファイルなので、マージ後に `sync.sh claude` を打っても、この1件だけは symlink に置き換わらない。

**これは仕組みの欠陥ではなく、手で編集した file を黙って壊さないための守りである。** 正本から配る形にしたいなら、live の実ファイルを退避してから sync を打つ。実ファイルのまま置くなら、正本と live が離れないかを別の手段で見る必要がある。どちらにするかは統括の判断に回した（9.4 に登録済み）。
