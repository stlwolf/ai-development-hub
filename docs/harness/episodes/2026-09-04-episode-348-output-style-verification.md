## 1. 期待値の宣言（Q-1 の計測器確認・**測る前に書いた**）

「output style が headless で system prompt に乗るか」を測る。乗ったかどうかは**応答の中身とは別の経路**でも見る（NK 01KYMRE1N7N0J8VP3CBZZEZ8Q3: 「効かない」と書く前に計測器を疑え）。

計測器の候補は3つ立てた。

- M1 `--settings '{"outputStyle":"<name>"}'` で headless に style を指定する。
- M2 応答内容チャネル: style に **canary 指示**（応答の冒頭に固有トークンを置け）を書き、応答にそれが出るかを見る。
- M3 system prompt チャネル: `--system-prompt-snapshot on` でセッションに system prompt を記録させ、記録された本文に style の文言が入っているかを grep する。M2 と独立。

期待値（この順で当たると予想する）:

- **E1**: M1 は効く。`--settings` は「追加で読む settings」なので `outputStyle` も反映される。**確度 中**（help に `outputStyle` の明示は無い）。
- **E2**: M2 の canary は headless の応答に出る。**確度 中〜高**。ただし headless は `-p` の一発応答なので、公式の「反映はセッション開始時」は満たしている（毎回が新セッション）。
- **E3**: M3 で system prompt が transcript に記録され、style 本文が grep で拾える。**確度 低〜中**（`--system-prompt-snapshot` の記録先が transcript JSONL かどうかは未確認）。
- **E4**: 組込み `Concise`（2.1.237 で追加）はファイル不要で名前だけで効く。**確度 中**。
- **E5**: 陰性対照（style 無し）では canary も style 文言も出ない。**確度 高**。

3値の判定規約: **乗る**（M2 と M3 の少なくとも一方が陽性で、陰性対照が陰性）/ **乗らない**（陰性対照と差が無い）/ **判別できない**（M2 が陽性だが M3 が取れず、応答差が style 由来かサンプリング由来か切れない）。

## 3. Q-2 で設計を組むときに迷って決めたこと

**判別実験の第3の軸を足した（設計判断・その場で書く）。** brief の受け入れ基準は「lean 化で契約が消えた」説と「RLHF の長さバイアス」説をどう見分けるかを求めていた。最初に思いついたのはモデル比較（Opus 5 と Fable 5.1）だけだったが、これは**モデルそのものが違う**ので、差を「`Writing for the user` の有無」に帰属させられない。弱い判別である。

そこで棄却しかけた案を戻して考え直したところ、#307 が実測している `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0`（長版 system prompt に戻す）が、**同じモデルの中で「契約の有無」だけを動かせる唯一の手段**であることに気付いた。これを1条件だけ足すと、判別の主軸をモデル間比較から同一モデル内比較へ移せる。run は2つしか増えない。

- 採った: 長版条件を Opus 5 × style なしにだけ足す。判定はこちらを主にし、モデル比較は補助にする。
- 棄却した: モデル比較だけで判別する案。帰属が成り立たない。
- 残る限界: 長版は `Writing for the user` 以外の節も一緒に戻すので、契約だけを動かしてはいない。plan §6.3 に明記した。

昇格の印: 「同じ効果を2つの経路（system prompt 層 / モデル層）で作れるとき、同一モデル内で効果だけを動かせる経路があれば、それが帰属の主軸になる」

**プロンプト型を3から2に削った。** T3（調査報告の要約）は内容選択の軸が一番出やすいが、run 数が 1.5 倍になる。時間予算（Q-2 まで 60 分）と段階2 の実行コストを考え、follow-up に落とした。

**自作 style に `output-format-rule` §5〜§7 を入れなかった。** リンクの形や絶対パスの規則は PR 本文や issue にも効く規則で、会話面に閉じていない。入れると rules との重複が二重になり、どちらが効いたか切れなくなる。§8 §9 と結論先出しだけを素材にした。

## 7. 段階2 開始（gate 3 の裁定を受領・2026-09-04 04:1x）

owner が plan v2 を承認し、判断点5つはすべて推奨案で確定した。裁定の正本は `.oe/ruling-348-hg.md`。終端は R-5（PR 作成・STOP）。

### 7.1 R-0（Phase 0）の期待値宣言 — **測る前に書いた**

**P0-4 経路の生存確認。** 極端な style（応答を200文字以内に収めよ）を1本作り、同じ問いを style あり / なしで走らせる。

- 期待: style ありは 200 文字前後まで縮み、style なしは大幅に超える。**確度 高**。
- 外れたときの読み: 縮まなければ、指示が乗っても生成を動かせていない。段階2a の「効かない」という結果はすべて経路の問題として読み直す必要がある。

**P0-3 病理の再現確認。** 裁定の実例2（統括の応答で owner が説明を求め直した3例）の**構造**を写した汎用の設計相談を1本作り、Opus 5 × style なし × headless で走らせる。実例の文面は再構成しない。写すのは「判断を求める・前提の説明が要る・選択肢がある」という構造である。

- 期待: 病理が出る。具体的には (a) 第1文が結論ではなく前置きか問題の言い換えになる (b) 接着記号（`→` `＝` など）が散文に混じる (c) 体言止めが散文に出る (d) 前提の説明を飛ばして選択肢に入る。**確度 中**。
- **確度を中に留める理由**: headless の一問一答には会話の履歴もツール実行も無い。実例の病理はツール実行を挟む報告ターンで出たものが含まれるので、fresh な一発では出ない可能性がある。出なければ P0-3 は no-go であり、裁定5に従って対話での収集に切り替える。
- 先行実測（`docs/research/2026-07-16-register-portability-eval.md` 段階1）が、原文で内容プローブが全て通ってしまい文体の寄与を測れなかったと記録している。今回は床側で同じ形を踏みうる。

**判定規約**: P0-3 は (a)〜(d) のうち**2つ以上**が出れば go とする。1つ以下なら、同じ題でもう2本足して確かめてから no-go を宣言する（1本で床を宣言しない）。

### 7.2 R-0 の結果（1）— P0-4 経路の生存確認は go

同じ設計相談の題を、style なしと極端 style（応答を200文字以内に収めよ）で1本ずつ走らせた。

| 条件 | 応答の文字数 |
|---|---|
| style なし | 4,363 |
| 極端 style | 80 |

期待どおりで、確度の宣言（高）とも一致した。**output style は system prompt に乗るだけでなく、生成そのものを動かす。** 段階2a で「効かない」という結果が出たとき、それを経路の問題として読み直す必要はない。

副次の観察として、極端 style の条件ではモデルがリポジトリの調査そのものを省いた。長さの制約が、書き方だけでなく**作業量**まで変えている。段階2a の自作 style は上限を課していないが、「案を並べない」「要らないものを出さない」という量の条項が同じ経路で作業量を削る可能性がある。必須要素の欠落数で見張る対象はここである。

### 7.3 R-0 の途中で指標側の欠陥を2つ見つけて直した

45 run を投じる前に baseline を1本測ったところ、私の指標スクリプトに欠陥があった。Phase 0 は病理の確認だけでなく**計測器の確認**にもなった。

- **欠陥1: 接着記号を散文からしか数えていなかった。** SO の指摘に従って箇条書きを体言止めの対象から外したところ、箇条書きの中の `→` まで一緒に落ちていた。体言止めを箇条書きから外すのは正しい（箇条書きが名詞で終わるのは正常だから）が、記号は箇条書きの中でも記号である。散文・箇条書き・表の3層で別々に数える形に直した。
- **欠陥2: 英語語のカウントが引用を拾っていた。** 本体 system prompt の文言を「」で引用した部分の英単語まで数えていて、11 語のうち 6 語が引用由来だった。`output-format-rule` §8 が問題にしているのは**自分の語彙**なので、「」『』で囲まれた範囲を外す形に直した。直した後は 5 語である。
- あわせて、第1文の型に **`narration`（自分の行動を過去形で報告する実況）** を足した。baseline の第1文が「調査しました。」で、既存の4値ではどれにも当たらず `unknown` に落ちていた。これは owner が問題にしている前置きそのものなので、型として立てた。

昇格の印: 「指標を作ったら、本番の前に1本だけ測って指標自身を疑う。除外規定は狙った対象だけを外しているとは限らない（体言止めのために箇条書きを外したら記号まで外れた）」

### 7.4 Q2 を作り直した（構成概念の誤り・run 1 の後に気付いた）

**気付いたこと**: 裁定の実例2（例A・例B・例C）は、どれも**統括が owner に判断を求めた**ときの応答である。例Aは判断対象の中身を書かずに名前だけ並べた、例Bは前提の説明を飛ばして選択肢に入った、例Cは確認したいことと推奨が1つの表に混ざった。つまり病理が出るのは**判断を求める行為**のときである。

ところが私が最初に作った Q2 は「方針を決めたい。判断できる形で出してほしい」という**問いに答えさせる**題だった。実際 run 1 の応答は結論を先に置き、根拠を file:line つきで示す、よくできた答えだった。**題が実例の構造を写していなかった。**

これは結果を見て基準を動かしたのではなく、**題が構成概念を取り違えていた**という欠陥である。裁定は「同じ構造（判断を求める・前提が要る・選択肢がある）の汎用の問いに作り直してよい」と明示的に許している。作り直した Q2 は例Bの構造をそのまま写す。

- 旧 Q2（`prompts/Q2old.txt`）: ルールの退役方針を答えさせる題。run 1 と run 2 の記録は残す（baseline のばらつきの材料になる）。
- 新 Q2（`prompts/Q2.txt`）: 環境変数の使い方について**選択肢を出して owner に選ばせる**題。「私はこの件の前提を細かく覚えていない」を入れて、前提の説明が要る状況を作る。

| 観測 | 値 | 病理か |

**ここで一つ、判定規約の外の観測を足した。** 散文の割合（`prose_ratio`）は、私が §7.1 で宣言した (a)〜(d) の4つに入っていない。run 1 を見てから足した指標である。足す根拠は結果ではなく**裁定の例C**（結果より前に存在する）だが、事後に足したことは事実なので、go / no-go の判定は **(a)〜(d) だけの版**と **(e) を入れた版の両方**を報告する。

**この時点での読み**: 記号圧縮と体言止めという、`output-format-rule` §9 が名指ししている病理は、fresh な headless の一問一答では**ほとんど出ていない**。出ているのは前置き（実況）と、散文が表と箇条書きへ逃げることである。これが2本目以降でも同じなら、自作 style の条項のうち「記号を文法の代わりにしない」「体言止めをしない」は**測っても動かない**ことになる。そのときは style の中身を、実際に出ている病理（前置き・表への逃げ）へ寄せ直す必要がある。

### 7.6 自分のミス — 実行中のスクリプトを書き換えて4本を落とした

R-0 の2本目以降が走っている最中に、並列実行時の競合を避けるため `run-one.sh` に引数を1つ足す修正を当てた。bash はスクリプトを逐次読みながら実行するので、実行中のインスタンスが書き換え後のオフセットを読みに行き、`予期しないファイル終了` で死んだ。**走っていた4本すべてが失敗した。**

- 失敗の見え方が紛らわしかった。`.err` は 0 バイトで、`.txt` が生まれないだけだった。ログの最後の行を見て初めて気付いた。
- 直し方は簡単で、スクリプト自体は `bash -n` を通る。壊れていたのは実行中のプロセスが見ていた中間状態だけである。流し直した。
- 教訓: **走っているスクリプトは書き換えない。** 直す必要があるなら、走り終わるのを待つか、新しいファイル名で置いて次から使う。

昇格の印: 「並列 run のハーネスを直すのは、run が全部終わってから。実行中の書き換えは、構文エラーにも見えない形で子プロセスだけを殺す」

### 7.7 指標の欠陥をあと3つ見つけて直した（合計5つ）

Phase 0 の1本ごとに指標を当て直したところ、体言止めの検出が**全部誤検出**だったことが分かった。順に書く。

- **欠陥3: 文末の括弧注記を剥がす順序が誤っていた。** 「〜します（`sync-claude.sh:132-134`）。」という形の文で、閉じ引用を落とす文字クラスにバッククォートを入れていたため、インラインコードの終端だけが先に消え、残った `4` が文末の文字として判定された。結果は体言止め。Q3 の baseline で3件すべてがこの型の誤検出だった。**文末の飾り（句点・括弧注記・インラインコード・閉じ引用）を、変化しなくなるまで繰り返し落とす**形に直した。
- **欠陥4: markdown の強調記号が残っていた。** 「〜**成立しません**。」で `**` が文末に残り、`*` はひらがなではないので体言止めと判定された。強調記号も剥がす対象に足した。
- **欠陥5: 太字だけの行を散文の文として数えていた。** 「**参照した記録**」のような行は見出しの代用であって文ではない。見出しの層へ移した。

直した後の baseline は、**4本すべてで体言止め 0**である。直す前は3本で「体言止めあり」と出ていた。

昇格の印: 「日本語の文末を機械判定するときは、句点の手前に付く飾り（括弧注記・インラインコード・強調記号・閉じ引用）を全部剥がしてから見る。剥がす順序に依存する実装は、順序を固定した時点で誤検出を生む。変化しなくなるまで繰り返す形にする」

**この経験の一般化**: 私は指標を5回直した。5回とも、実データを1本測って中身を目で見たときに見つかった。指標を設計した時点では1つも見つかっていない。**指標は設計では検証できず、実データに当てて個票を読むまで検証できない。**

### 7.8 R-0 の中間の読み — 病理が headless に出ていない

baseline 4本（旧 Q2 1本・判断要求型 Q2 2本・Q3 1本）を測った結果は次のとおり。

| run | 題 | 文字数 | 散文の割合 | 接着記号 | 体言止め | 第1文の型 |
|---|---|---|---|---|---|---|
| 1 | 旧 Q2（調査 + 方針） | 4,363 | 0.218 | 1 | 0 | 実況 |
| 2 | Q2v2（判断要求のみ） | 3,056 | 0.664 | 0 | 0 | 計画の宣言 |
| 3 | Q2v2（判断要求のみ） | 3,211 | 0.503 | 0 | 0 | 結論 |
| 4 | Q3（調査報告） | 3,323 | 0.380 | 0 | 0 | 結論 |

§7.1 で宣言した (a)〜(d) の判定に当てると、**(a) 第1文が結論でないが 4本中2本、(b) 接着記号・(c) 体言止め・(d) 前提を飛ばして選択肢に入る はいずれも出ていない**。宣言した基準（2つ以上で go）に届いていない。

**この結果の意味は「style が効かない」ではなく「病理がこの regime に無い」である。** fresh な headless の一問一答では、Opus 5 の baseline はもともとよく書けている。結論を先に置き、記号を接着剤に使わず、体言止めもしない。`output-format-rule` §9 が名指ししている病理が、そもそも起きていない。

宣言した規約に従い、no-go を宣言する前に同じ題でもう2本足す。ただし足す題は、**4本の中で唯一まとまった病理を出した run 1 の形**（調査をさせてから判断を求める）に寄せる。run 1 は第1文が実況で、散文の割合が 0.218 まで落ちていた。裁定の例A・例B・例Cはどれも「統括が作業をした後に owner へ判断を求めた」ときの応答なので、**作業を挟むことが病理の条件**である可能性が高い。この形で3本測って判定する。

### 7.9 結論の手前で気付いた見落とし — baseline は「指示なし」ではなかった

no-go を書きかけて止めた。**私の C0（style なし）は「レジスタの指示が無い状態」ではない。** `~/.claude/rules/` の14本が user ターンの system-reminder として入ったままで、その中に `output-format-rule` の §8（日本語の語彙）と §9（operator 向けの散文）がある。つまり C0 は「指示なし」ではなく「**rules 層で指示がある**」条件である。

baseline がきれいだったのは、病理が存在しないからではなく、**rules が効いているから**かもしれない。この2つを分けずに no-go を宣言すると、まったく違う結論に化ける。

- 「病理が無い」と読むなら → headless では測れない。対話へ切り替える。
- 「rules が効いている」と読むなら → **rules 層は headless では機能している**。owner が「§9 は効いていない」と観測しているのは長い対話セッションの話なので、問題は層ではなく**regime**（セッションが長くなること）にある。output style へ移しても、同じ regime で同じように効かなくなる可能性がある。

この2つは #348 の問いそのもの（会話面のレジスタを output style で制御できるか）に直結する。切り分けずに進めない。

**切り分けの方法**: `--setting-sources project,local` で user 層の rules を落とせる。実際に落ちることを先に確かめた（セッションに聞いたところ「渡されていない」と答え、残っているのは CLAUDE.md と MEMORY.md の索引だけだった。CLAUDE.md には行動規範の6項目の要約はあるが §8 §9 は無い）。この条件で同じ題を測れば、**指示がまったく無い floor** が出る。

- floor で病理が出て、rules ありで消えているなら → rules は headless で効いている。#348 の設計は「rules が効かない regime」を再現するところからやり直しになる。
- floor でも病理が出ないなら → 病理は本当にこの regime に無い。裁定5 のとおり対話へ切り替える。

これは SO の codex レーンが指摘した「配置対照が無いと帰属できない」と同じ問題だが、私は C3（同じ文面を user ターンへ）を足しただけで、**C0 自体が既に rules 条件であることに気付いていなかった**。指摘の半分しか受け取れていなかった。

昇格の印: 「baseline は『何もしていない条件』ではなく『既定で入っているものが全部入っている条件』である。既定に測りたい対象と同じ指示が含まれていないかを、baseline を置く前に数える」

### 7.10 R-0 の確定 — P0-3 は no-go。ただし病理は実セッションに実在する

**floor（rules を14本とも外した条件）でも病理は出なかった。** §7.9 で立てた分岐のうち「rules が効いているから baseline がきれい」は棄却され、「病理がこの regime に無い」が残った。

| 条件 | 本数 | 接着記号 | 体言止め | 第1文が結論でない |
|---|---|---|---|---|
| rules あり（既定） | 7 | 10 本中 1 個 | 0 | 2 / 7 |
| rules なし（floor） | 3 | 0 | 0（検出は誤検出2件） | 0 / 3 |

floor の方が英語語の密度と中黒の使用は増えたが（`output-format-rule` §8 が狙っている層）、§9 が名指ししている接着記号・体言止め・前置きは**どちらの条件でも出ない**。

**では病理はどこに在るのか。** このリポジトリの実セッション 56 本から、assistant の応答（400 文字以上）682 件を取り出して同じ指標を当てた。

| 指標 | 実セッション（682 件） | 私の headless 実験（10 本） |
|---|---|---|
| 接着記号が1個以上の応答 | **27.6%** | 10%（1本に1個） |
| 体言止めが1個以上の応答 | **40.9%** | 0% |
| 体言止めの密度（1,000 文字あたり・平均） | 0.77（p90 = 2.23・最大 14.71） | 0 |
| 散文の割合（平均） | 0.67 | 0.22〜0.83 |

**病理は実在する。headless の一問一答に無いだけである。** これで「効かない」と「測れない」の取り違えを避けられた。

### 7.11 regime 仮説（長いセッションで崩れる）は実データに否定された

「文脈が溜まると崩れる」という私の仮説を、応答がセッションの何番目かで層別して検定した。

| セッション内の位置 | 件数 | 接着記号率 | 体言止め率 | 文字数 |
|---|---|---|---|---|
| 1〜2 | 80 | 0.450 | 0.450 | 2,643 |
| 3〜5 | 66 | 0.288 | 0.303 | 1,774 |
| 6〜10 | 63 | 0.270 | 0.413 | 1,663 |
| 11〜20 | 84 | 0.262 | 0.393 | 1,496 |
| 21 以降 | 389 | 0.242 | 0.422 | 1,114 |

**病理は位置とともに増えていない。むしろ冒頭が最も高い。** 「長いセッションで崩れる」は支持されない。したがって headless で再現しない理由は文脈の長さではない。

残る候補は、対話と `-p` の違いそのもの、応答の発話行為の種類（報告・計画・board 更新のような密度の高い形が実セッションには混じる）、permission mode などである。**本アークでは決めない。** 名前だけ挙げて開いたままにする。

昇格の印: 「合成した題で病理が出ないとき、実運用の記録に同じ指標を当てれば、病理が『無い』のか『その regime に無い』のかが分かる。実運用の記録は既にあるので、追加の生成コストは 0 である」

### 7.12 再設計に効く発見 — `--resume` に style が乗る

`claude -p --resume <session-id> --settings '{"outputStyle":"..."}'` を試したところ、**再開したセッションでも style が system prompt に乗る**（節の名前を答えさせて確認した）。公式が「反映はセッション開始時」と書いているので乗らない可能性を見ていたが、乗った。文脈が溜まったセッションを headless で再現しながら style を A/B できる。

ただし §7.11 で位置と病理が相関しないと分かったので、この手段の価値は当初想定より下がった。再設計案では第2候補に置く。

### 7.13 実例1（外部リポの export）が届いた — 病理の中身が想定と違った

owner が export を作業層に置いた（gitignored）。**別リポの識別子と業務の固有名詞は本文に書かない。** 置換表は作業層に残した。以下は種別と指標だけである。

まず export の読み取りで1つ引っかかった。owner の不満を探す最初の検索が空振りした。**terminal の折り返しで単語が行をまたいでいた**（「分か」と「りづらかった」が別の行）ためである。発話を1つに結合してから検索し直したら見つかった。転記から病理を探すときは、折り返しを畳んでから探す必要がある。

**この export のセッションは Opus 5 だった**（起動バナーで確認）。基準線と同じモデルなので、実例1 の証拠は基準線の上に乗っている。起動時のヒント行に「Fable 5.1 writes better code」と出るが、それは CLI の宣伝であってセッションのモデルではない。

owner が「分かりづらかった」と言った応答を特定し（子の報告を受けて統括が owner へ説明を出した1件・3,423 文字）、同じ指標を当てた。

| 指標 | 実例1 の当該応答 | hub 実セッション 682 件 |
|---|---|---|
| 文字数 | 3,423 | 中央値 1,197 / p90 2,225 |
| **見出しの数** | **0** | 中央値 3 / p90 6（見出し0の応答は全体の 11.7%） |
| 文の数 | 52 | — |
| 散文の割合 | 0.906 | 中央値 0.69 |
| 接着記号 | **0** | 中央値 0 |
| 体言止め | 1（密度 0.32） | 中央値 0 / p90 2.23 |
| 英語 + する | **0** | 中央値 0（15.5% の応答に1個以上） |
| 英語語の密度 | 37.42 | 中央値 12.95 / p90 25.83 |

**病理の中身は、記号圧縮でも体言止めでも英語+する でもなかった。** 実体は次の2つである。

1. **長い**。中央値の 2.9 倍で、p90 も超えている。
2. **構造が無い**。3,423 文字・52 文を、見出し 0 で平坦な散文として出している。見出し0の応答は全体の 11.7% しかないので、下位 12% に入る。

英語語の密度は高いが、内訳を数えたら大半が作業対象の**名前**だった（`blue` `green` `alarm` `pause` `bake time` など、外部サービスと設定値の名前）。§8 は名前を英語のままでよいと認めているので、これは §8 の病理ではない。§8 が名指しする形（英語 + する / させる）を専用の検出器で数えたら **0 件**だった。

**帰結が3つある。**

- `output-format-rule` §9 が名指ししている病理（記号圧縮・体言止め）は、**この不満の原因ではない**。私の自作 style の「日本語のレジスタ」節は、起きていない病理を狙っている。
- style が狙うべきは**量**と、**長い応答に構造を付けること**である。#307 の intake ノートが外部の観測として記録していた「見出しも区分もないフラットな長文になる」と一致した。伝聞だったものが、自分の環境の実測で裏付いた。
- **組込み `Concise` はこの失敗を悪化させる可能性がある。** `Concise` は「見出し・表・箇条書きは本当に構造があるときだけ使え。既定は平文」と指示している。長さは縮むが、構造を付けない方向に押す。今回の病理が「長い上に構造が無い」なら、`Concise` は片方だけ直してもう片方を押し進める。これは plan v3 で検証すべき予測である。

昇格の印: 「不満の原因は、不満を言っている本人が挙げた語（読みづらい）ではなく、その応答を測って初めて分かる。既存ルールが名指ししている病理と、実際に起きている病理は別物でありうる」

### 7.14 fixture の漏れ — 実験の題を実験の作業ディレクトリに置いてはいけない

匿名化した実例1 の題（Q4）で headless を2本走らせたら、両方とも**題そのものを作業層のファイルとして見つけて**、それについて答えた。第1文は「この入力は作業層の `tmp/348-runs/prompts/Q4.txt` と1文字も違わない」と「この turn は、私が作った Q4 の fixture そのものでした」である。

原因は、実験の題を worktree の `tmp/348-runs/prompts/` に置き、その worktree を cwd にして headless を走らせたことである。Q4 は文脈から切り離された報告文なので、モデルはそれを理解しようとしてリポジトリを調べ、自分の題を見つけた。

**この2本は病理のプローブとしては無効である。** そして、これは Q4 だけの問題ではない。**plan v2 の段階2a の 45 run はすべて同じ露出を持っていた**（同じ worktree を cwd にして、同じ `tmp/348-runs/` に題も style も置く設計だった）。R-1 に進んでいたら、条件を測るつもりで「モデルが実験の存在に気付いているかどうか」を測っていた可能性がある。

- 直し方: 題を worktree の外（session の scratchpad）へ出し、cwd も実験の作業層を含まないディレクトリにする。流し直した。
- plan v3 に**実験の隔離**という節を足す。fixture・style ファイル・生の応答・指標スクリプトのいずれも、被験セッションの cwd から見えてはいけない。
- ただしこれには張力がある。owner の実 regime は「作業中のリポジトリを cwd にする」ことなので、cwd を空にすると regime が変わる。案A（実運用の観測）ならこの問題は起きない。実運用のセッションは実験の fixture を持たないからである。**これは案A を推す3つ目の理由になる。**

昇格の印: 「合成した実験を、その実験の成果物が置いてあるリポジトリの中で走らせない。被験者が実験計画書を読める配置になっていないかを、run を投じる前に確かめる」

### 7.16 転記の形式が測れる軸を決める（計測器の一般則）

### 7.19 gate 2 が再び3レーンとも refuted — 自分で名指しした罠を、別の場所で踏んでいた

### 7.26 HG-3 — 物差しを語彙から「言い方」へ移した

owner の説明で、私の見立てが1つずれていたことが分かった。私は実例4 の原因を「未定義の内部語」と読み、リストを広げるかどうかを判断点に上げた。owner の説明は**「個別の用語より説明の仕方。人が会話で言わない言い回し（収集窓が開いている・崩れていたら）が問題」**だった。

昇格の印: 「読みづらさを語彙の問題と読むと、リストを増やす方向に行く。owner は『説明の仕方』だと言った。語彙は数えられるが言い方は数えられないので、数えられる方に寄せた設計は、問題の一部しか掴めない。数えられないものを人に残す設計にする」

### 7.28 手順書が自分の閾値に引っかかった

### 7.29 R-4 — 「暫定採用」と書きかけて、gate 4 に止められた

**私は「暫定採用」と書いて gate 4 に出した。2レーンともに refuted で、指摘が正しかった。**

指摘の中心はこうである。採用条件 (a) は「**主指標**のうち2つ以上でフラグ率が下がる」で、主指標は凍結した4軸（強調記号 / 内部語 / 文の数 / 英語語）である。**文字数と接着記号は主指標ではない。** 私は主指標外の2つで (a) を満たしたと書いていた。

レーンの処方どおり、fork の 12 組を軸別に発火数で数え直した。

| 主指標 | なしの発火 | ありの発火 |
|---|---|---|
| 強調記号 | 0 | 0 |
| 内部語の種類数 | 0 | 0 |
| 文の数 | 0 | 0 |
| 英語語の密度 | 1 | 0 |

**4軸のうち3軸が検定不能だった。** baseline がどの軸でも閾値に届いていない。平均と差で見ていたので、この事実が表に出ていなかった。**平均が動いていることと、閾値を超える応答が減ることは別のことである。** 私の主表は前者しか示していなかった。

他に4点を受け入れた。

- 条件 (b)（見張り指標が悪化していない）は未達である。体言止めが 3件→4件、英語+する が 0件→1件。**p 値が大きいことは非劣性の証明ではない。** 私は「雑音」と書いたが、2つの証拠が逆を向く事実から言えるのは「不確定」までである。

昇格の判定: 「平均の差で改善を語ると、閾値を使うゲートの判定とずれる。ゲートが『閾値を超えた件数の率』で書かれているなら、証拠も同じ単位で出す。平均と符号検定は補助にしかならない」を昇格の候補にする。

昇格の印: 「自分が凍結した条件の文面を、判定を書く直前にもう一度読む。私は『主指標のうち2つ以上』の『主指標』が何を指すかを、自分で決めた3週間後に取り違えた」
