# #390 交代の前任側のフローをガードレールのスキルへ入れる

**この episode は着手時に枠を作り、作業しながら追記している。** 後追いで再構成した節にはその旨を冒頭に書く。

## この単位の入力

前の単位（PR #396）は交代の**後継側**だけをガードレールのスキルへ書いた。交代を始めるのは前任なので、**入口が無いまま出口だけが在る形**になっている。前任がやることは machine-local の board にしか無く、別のリポジトリの統括はそれを読んでいない。

狙いは「owner が出す指示は『交代して』の1つで、そこから先は前任と後継が自分で回る」という状態である。詳細は plan の「背景」に書いた。

## 作業の記録

### ブリーフの断定を一次情報で当て直した（2026-09-13）

ブリーフが挙げた前提を merged master（`f8a9759`）と実行で確かめた。**食い違いは無く、1件は範囲を狭める必要があった。** 内訳は plan の「ブリーフの断定を当て直した結果」に書いた。

狭めたのは「人が書く節が埋まっていないと `retire` が通らない」である。`retire` が機械で見るのは**自己申告の表の行だけ**で、「渡らないもの」と「確立した運用」は見ていない。**手順にそのまま写すと、機械が見ていないものを「見ている」と書くことになる。**

### verb の在り処を、配布済みの verb から引く形にした（2026-09-13）

`command -v` で実測したところ、PATH にあるのは `oe-tree` だけである。`oe-handoff` / `oe-register` / `oe-send` は無い。スキルの現行の記述は「無ければ engine の `bin/` のパスで呼ぶ（hub では ...）」で、**hub の外ではこの関係だけでは在り処に到達できない。**

`oe-tree` は配布対象で、その実体は engine の `bin/` に在る。**配布された verb の実体を足がかりにすると、他の verb は同じディレクトリの隣に在る。** 設計と検算は plan の DJ に書いた。

### 設計SO（ゲート2・弱・2レーン）で plan を書き直した（2026-09-14）

`so-compare` を既定の2レーン（codex と claude）で1回回した。**2レーンとも「要修正」で返り、指摘を実物で当て直した結果、反証できたのは1件だけだった。** 変更の内訳は plan の「設計SO で変えたこと」の表に書いた。証跡は `tmp/so-design-20260913-235456/`（揮発するので表のほうが正本）。

**いちばん重い指摘は、交代が board を要求することだった。** `oe-handoff take` と `retire` はどちらも board を必須にしている（`bin/oe-handoff:474-476`・`:706-707`）のに、**board の在り処を後継へ伝える経路が配布物のどこにも無い。** `canonical/` 配下に `OE_BOARD_FILE` は0件で、`prepare` の機械の節にも board のパスは入らず、`start` は素の tmux split なので前任の環境変数も渡らない。**board を知っているのは前任だけなので、渡す工程は前任側にしか置けない。** 初稿はこの工程を持っていなかった。

昇格の印: 前任側の工程を「前任が打つ verb」から逆算して書いたので、**後継が席を取るのに要るもののうち、verb の引数で渡るものしか拾えなかった。**

**2番目は、輪が前任の出口で切れていたことである。** ③ の手順5 は `take` と `retire --execute` が済んだ前提で書かれているのに、**その順序は board にしか無い。** 初稿は ④ の末尾を手順5 へ繋いだだけだったので、**hub の外の後継は「次に何を打つか」を知れない。** ④ の末尾に後継の順序を1行だけ置く形に直した（③ は書き換えない）。

**3番目は受入である。** 11項のうち2項が**編集前から通る**形だった。「unknown を0に畳まない」は ③ の手順5 に同趣旨の文が既にあり、「閾値 85」は `oe-vitals` を見れば成立する。**前の単位で採った negative knowledge（`01M2DEC1G68X8PH2QEW2H1DWZZ`）は「変更そのものを見る項を足せ」だったが、足した項の錨が新しい節の外に在れば同じ穴が開く。**

昇格の印: 受入が変更を見ているかは、項目を足したかではなく**錨がどこに在るか**で決まる。

**反証できた1件は `readlink -f` である。** engine は `oe-tree:61` に「macOS の `readlink` は `-f` 非対応」と書いているが、codex レーンが現行の macOS 15.7.7 で `-f` が動くことを実測した。**`-f` を使わない判断は変えていない**（リンクが1段の絶対パスなので要らず、engine 自身が避ける書き方を選んでいる）が、**理由づけを事実に合わせて書き直した。**
