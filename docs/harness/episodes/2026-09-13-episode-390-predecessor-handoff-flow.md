# #390 交代の前任側のフローをガードレールのスキルへ入れる

**この episode は着手時に枠を作り、作業しながら追記している。** 後追いで再構成した節にはその旨を冒頭に書く。

## この単位の入力

前の単位（PR #396）は交代の**後継側**だけをガードレールのスキルへ書いた。交代を始めるのは前任なので、**入口が無いまま出口だけが在る形**になっている。前任がやることは machine-local の board にしか無く、別のリポジトリの統括はそれを読んでいない。

狙いは「owner が出す指示は『交代して』の1つで、そこから先は前任と後継が自分で回る」という状態である。詳細は plan の「背景」に書いた。

## 作業の記録

### ブリーフの断定を一次情報で当て直した（2026-09-13）

ブリーフが挙げた前提を merged master（`f8a9759`）と実行で確かめた。**食い違いは無く、1件は範囲を狭める必要があった。** 内訳は plan の「ブリーフの断定を当て直した結果」に書いた。

狭めたのは「人が書く節が埋まっていないと `retire` が通らない」である。`retire` が機械で見るのは**自己申告の表の行だけ**で、「渡らないもの」と「確立した運用」は見ていない。**手順にそのまま写すと、機械が見ていないものを「見ている」と書くことになる。**

### verb の在り処を、配布済みの verb から引く形にした（2026-09-13）

`command -v` で実測したところ、PATH にあるのは `oe-tree` だけである。`oe-handoff` / `oe-register` / `oe-send` は無い。スキルの現行の記述は「無ければ engine の `bin/` のパスで呼ぶ（hub では ...）」で、**hub の外ではこの関係だけでは在り処に到達できない。**

`oe-tree` は配布対象で、その実体は engine の `bin/` に在る。**配布された verb の実体を足がかりにすると、他の verb は同じディレクトリの隣に在る。** 設計と検算は plan の DJ に書いた。

### 設計SO（ゲート2・弱・2レーン）で plan を書き直した（2026-09-14）

`so-compare` を既定の2レーン（codex と claude）で1回回した。**2レーンとも「要修正」で返り、指摘を実物で当て直した結果、反証できたのは1件だけだった。** 変更の内訳は plan の「設計SO で変えたこと」の表に書いた。証跡は `tmp/so-design-20260913-235456/`（揮発するので表のほうが正本）。

**いちばん重い指摘は、交代が board を要求することだった。** `oe-handoff take` と `retire` はどちらも board を必須にしている（`bin/oe-handoff:474-476`・`:706-707`）のに、**board の在り処を後継へ伝える経路が配布物のどこにも無い。** `canonical/` 配下に `OE_BOARD_FILE` は0件で、`prepare` の機械の節にも board のパスは入らず、`start` は素の tmux split なので前任の環境変数も渡らない。**board を知っているのは前任だけなので、渡す工程は前任側にしか置けない。** 初稿はこの工程を持っていなかった。

昇格の印: 前任側の工程を「前任が打つ verb」から逆算して書いたので、**後継が席を取るのに要るもののうち、verb の引数で渡るものしか拾えなかった。**

**2番目は、輪が前任の出口で切れていたことである。** ③ の手順5 は `take` と `retire --execute` が済んだ前提で書かれているのに、**その順序は board にしか無い。** 初稿は ④ の末尾を手順5 へ繋いだだけだったので、**hub の外の後継は「次に何を打つか」を知れない。** ④ の末尾に後継の順序を1行だけ置く形に直した（③ は書き換えない）。

**3番目は受入である。** 11項のうち2項が**編集前から通る**形だった。「unknown を0に畳まない」は ③ の手順5 に同趣旨の文が既にあり、「閾値 85」は `oe-vitals` を見れば成立する。**前の単位で採った negative knowledge（`01M2DEC1G68X8PH2QEW2H1DWZZ`）は「変更そのものを見る項を足せ」だったが、足した項の錨が新しい節の外に在れば同じ穴が開く。**

昇格の印: 受入が変更を見ているかは、項目を足したかではなく**錨がどこに在るか**で決まる。

**反証できた1件は `readlink -f` である。** engine は `oe-tree:61` に「macOS の `readlink` は `-f` 非対応」と書いているが、codex レーンが現行の macOS 15.7.7 で `-f` が動くことを実測した。**`-f` を使わない判断は変えていない**（リンクが1段の絶対パスなので要らず、engine 自身が避ける書き方を選んでいる）が、**理由づけを事実に合わせて書き直した。**

### ゲート3 を通過し、自走の範囲が変わった（2026-09-14）

owner が「推奨選択で進める。判断3は自走させる」で通した（`.oe/addendum-390-predecessor-hg-go.md`）。**5件のうち4件は推奨どおりで、1件（判断3）は子の推奨が取り下げられた。**

**取り下げられたのは「`start` は owner の指示で打つ」である。** 初稿は「`prepare` は文書しか作らないが `start` は画面を変える」という線で段階を分けた。**owner の理由は、この単位の狙いが「owner が出す指示は1つ」だという点である。** `start` の手前にもう一度指示を要求すると狙いが壊れる。**同型の段階分けは #390 の本体で一度取り下げられている**（「停止コマンドを押すのは人がよい」が owner の優先順位と逆だった）。

昇格の印: 安全側に段階を足す判断が、**owner の優先順位（自分が手作業をしない）と逆を向くことが2度続いた。** 危険の大きさではなく、**人の手数が増えるかどうか**で見る必要がある。

**owner は1つを委ねた。** 「自分の context が閾値に近い」で始める場合は owner の指示を経ていないので、その扱いを plan で決めよと言われた。**`start` の直前に画面へ1行書いてから打ち、返事は待たない**を採った。**発火条件を owner の指示だけに絞る案は採らなかった** — ブリーフが発火条件を2つ挙げているので、片方を落とすと上流の scope を狭めることになる。

**順序の指示も受けた。** plan を再コミットして SHA を報告したら**もう一度止まる**。統括が baseline を記録してから実装の許可が来る。**前回は承認の直後に scope が動いて baseline が壊れ、未達ゲートの独立照合が走らなかった**ためである。

### 実装と検算を通した（2026-09-14）

`canonical/skills/doc-flow-guardrail/SKILL.md` に5つの step を入れ、検算を3本通した（コミット `76fdb11`・45行追加6行削除）。

**検算 A（verb 解決規約）。** PATH に在るのは `oe-tree` だけである（`oe-handoff` / `oe-register` / `oe-send` は `NOT_IN_PATH`）。規約のコマンドを `$HOME`（repo の外）で実行すると `oe_bin` が engine の `bin/` に解決し、`"$oe_bin/oe-handoff" --help` が出た。**足がかりを実体コピーに差し替えると `[ -x ]` が落ちて手順3 へ倒れる**ことも実行して確かめた。`oe-handoff:25`・`oe-register:35` が `BIN_DIR="$(cd "$(dirname "$0")" && pwd)"` であること、`oe-tree:61-65` だけが自分で symlink を辿ることも読み直した。

**検算 B（工程と口の照合）。** `oe-handoff --help` の「`prepare` / `start` は前任のセッションで走らせる」と ④ の記述が一致する。`retire` が申告に対して止める条件を `:809-1019` で数えると8本（節が無い / 表が0件 / 語彙の外 / 機械の節の PR / 機械の節の未 push / 実行時の open PR / 実行時の worktree / 実行時の未 push）で、**④ が挙げた集合と1対1である。** board の要求（`:474-476`・`:501-504`・`:706-707`）と閾値の既定（`oe-vitals:93`・`:105` = 85）も一致した。

**自分で見つけた限界を1つ書いておく。** `retire` には上の8本のほかに「数えられなかった」で止まる枝が3本ある（open PR / worktree / 未 push）。**④ はこれを書いていない。** 書かなかったのは、前任の行動が変わらない（申告の書き方で防げない）ためだが、「止めるのは…である」という書き方は網羅に読める。**実装SO の判断を仰ぐ。**

**検算 C（静的受入13項）。** 13項すべて OK。**項目10（hub 固有の語を落としても規約が成立するか）は、最初に走らせたとき落ちた。** 規約の手順1 が「bin sync の配布対象だけが載る」と書いており、**`bin sync` が hub のスクリプト名なので、その行ごと落ちた**ためである。**手順1 の括弧を「配られている verb だけが PATH に載る」へ変えた**（付録 A の文面からの逸脱1件目・下記）。直したあとは、落ちるのは hub の例を含む手順3 の1行だけで、(a) 足がかりを取る段・(b) 実体のディレクトリを引くコマンド・(c) 実体のパスで呼ぶ理由の3つは残る。

昇格の印: **受入の項目が、承認済みの文面そのものを落とした。** 上流が固定した文面と、上流が固定した受入が食い違うことがある。

### 承認された plan からの逸脱（2件・報告する）

1. **付録 A の手順1 の括弧を変えた。** 「bin sync の配布対象だけが載る」→「配られている verb だけが PATH に載る」。**理由は受入10 がこの行を落とすため**で、意味は変えていない（配布対象の正本への routing は規約の末尾に残っている）。
2. **`orchestration-toolkit` への言及が 8件から7件になった。** plan の baseline 表は「編集後も減らさない」と書いている。**内訳は、verb の起動方法を指していた2件（cold-start の手順4 と手順5）が規約への参照に変わり、規約の末尾に1件増えたためである。** routing の経路は切れていない（手順4 / 手順5 → 「verb 解決規約」節 → `orchestration-toolkit`）。**受入11 の本文（「残っている（消していない）」）は満たすが、baseline 表の括弧の条件は満たさない。** 数を戻すかは owner の判断に委ねる。

### 実装SO（ゲート4・弱・2レーン）で、書いた断定の範囲が広すぎたことが出た（2026-09-14）

**2レーンとも「反対」で返った。** 指摘を実物で当て直した結果、**反証できたものは1件も無かった。** 証跡は `tmp/so-impl-20260914-004139/`（揮発するので下の表が正本）。

**いちばん重いのは、board の渡し口が工程として閉じていなかったことである。** ④ の step 4 は「board の場所を渡す」と書いていたが、**その時点で後継のペインはまだ無い。** `start` が送るのは文書のパス1行だけで（`bin/oe-handoff:434`）、機械の節に board は入らず、素の tmux split なので環境変数も渡らない。**渡す口は引き継ぎ文書しか無い。** 設計SO で「board を渡す工程が要る」ところまでは直したのに、**渡す先を書いていなかった。**

昇格の印: 「渡す」と書いて渡し先を書かないと、工程は**閉じたように見えて閉じない。** 設計SO の指摘を受けて足した工程が、実装SO でもう一段掘られた。

**2番目は、規約に載せた例が実際には分岐していなかったことである。** `[ -x "$oe_bin/oe-handoff" ] || echo "…（3 へ）"` と書いたが、**シェルはその次の行をそのまま実行する。** 「3 へ倒す」という説明と、貼って動くコードが食い違っていた。**自分の検算は、コマンドを手で分岐させて実行していたので、この食い違いを踏まなかった。**

昇格の印: **検算で「手で分けて実行した」ものを、配布物では1本のコードとして載せていた。** 検算の実行形と配布物の記載形がずれると、検算は通るのに読者は踏む。
