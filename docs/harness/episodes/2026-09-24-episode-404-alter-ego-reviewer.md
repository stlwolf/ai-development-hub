# #404 分身レビュアー v1 — 設計、測定、校正

> **reconstructed**。本文は作業の終端（2026-10-06）で会話記録から書き起こした。リアルタイムの追記ではない。時刻は会話記録の日付に拠る。別リポジトリの識別子（組織・リポジトリ・アカウント・サービス名・ファイルパス）は伏せてある。実物の記録は worktree の `tmp/404-alter-ego/`（gitignored）に残した。

## 0. なぜこの作業が始まったか（2026-09-15）

owner の出発点は「自分の分身になる、サービス開発のレビュアーが一本立つのが理想」だった。ハーネスの rules は大原則（Evidence First、Minimal Scope など）までで、その一段下にある設計原則、つまりインターフェースの引き方、レイヤーの切り方、パッケージの範囲、運用の単位は持っていない。owner が重視するそれらは、実装する agent に伝わっておらず、コード量が多いと owner 自身のレビューからも抜ける。

実例が二つ挙がった。一つはこのリポジトリの統括オーケストレーションで、安全側の機構を足したが要否を誰も問わなかった件（episode-390）。もう一つは別リポジトリの IaC で、stack の分割が単独でデプロイできる単位になっておらず、後からリファクタ issue になった件。

## 1. 質問駆動の設計（2026-09-15〜16）

`question-driven-design` で一問ずつ進めた。確定した順に書く。

- 軸は「SaaS のドメイン知識」ではない。owner の訂正は「SaaS 開発におけるドメイン知識、つまり運用者がいるシステムを作るときの現実的な観点とリスク管理。AI はデファクトスタンダードを知っているが、現場でどう着地するかが抜けている」。一人で触るシステムなら要らない制約が、運用者がいると要る、という区別。
- 効かせる位置はレビュー側。owner の言葉は「俺がレビューするのと一緒。PR のレビューと一緒」。出すものは二種類で、読んでも分からない箇所には説明を求め、明らかにおかしい箇所にはこうすべきと提示する。
- 理想は質問ではなく判断まで出すこと。質問と指摘の比率が、そのまま分身の確度の目盛りになる。
- 根拠のラベルを二種類に分ける。一般に認められた原則から言えること（一般）と、owner の判断を推測して言っていること（推測）。校正が要るのは推測側だけ。
- 器は skill と agent の両方。配布はどちらも 3 ツールに届くので差にならない（sync スクリプトで確認）。本質的な差は文脈の分離だけで、「量が多くて読めない」には agent が要る。ただし agent は人に聞き返せない。書き換えの頻度が高い中身は symlink で配られる skill に置き、agent は薄い器にする。
- v1 は一体で作る。見方ごとに分けるかは校正の結果で決める。

参考記事として、カナリーの「デザイナー人格の skill 化」（Cocoda、2026-09-15）が同じ構造だった。LLM の出力が平均に収束する問題に対し、リードデザイナーの思考を過去の実物への問いかけで引き出して skill にした事例。特に「本人に書き下ろさせるのではなく、過去の成果物を材料に聞き手が引き出す」という方法を採った。

## 2. 引き出し方と測り方（2026-09-16）

引き出し方は「本人に原則を語らせず、実物に反応させる」の一点。逆算（後のリファクタ issue を正解として、元 PR のどこを見れば気づけたかを聞く）、予測の答え合わせ（私が先に「owner ならここを指摘するはず」を出し、印を付けてもらう）、二択。

測り方は、別リポジトリのリファクタ issue 2 本を正解表にし、元 PR だけを分身に渡して、出力に正解表の中身が現れる割合を見る。人が「良さそう」と言う評価ではなく、後から実際に必要になったものをどれだけ先に言えたか。

同時に、別リポジトリには一般基準（Well-Architected）に照らす skill が既にあり、「組織固有の判断は依頼側が持つ」「受け入れの記録は持たない」と明示的に担当外にしていた。分身はその空けられた場所にちょうど収まる。境界は設計せずに済んだ。

## 3. 材料の準備と予測（2026-09-24）

- 元 PR を特定した。+7665 行、19 ファイル。IaC のソース 3 本と、kickoff・decision・deploy plan・episode の文書が同梱されていた。正解表の三軸（粒度、環境、アカウント）の種はすべてこの PR にあった。
- 正解表を 16 項目に整えた。うち 2 項目は負（挙げたら減点。cross-stack の export/import は実害なし、と、コードに account guard を足さず手順側で閉じる）。1 項目は元 PR の時点に無く予測不能。
- 予測の一覧を 14 項目作った。読んで分かったのは、この PR はほぼすべての選択に理由が書かれていたこと（判断番号、owner の承認日付、SO の和解まで）。「理由の無い箇所を挙げる」という前提の形だと 1 項目しか出ない。後から問題になったものの多くは、理由があったが有効期限があった型（「移行プログラムだから」「stg だから」）か、理由の形が安全側で反証されにくかった型。

## 4. 聞き取り（2026-09-28）

問いは二つで打ち切った（最初の項目は owner の第一声への反応で、問いではない）。二問で機構が二つ出て、残りはどちらかに帰着する見込みだったため。

- 「細かい」という第一声。私は「owner の粒度より下」と推定したが外れた。owner の訂正は、二重定義のような一般的なコーディング原則は「指摘としては絶対見る点」であり、見逃すのは優先度が低いからではなく、CDK を毎回書いていないので深く読めないから。読解の深さの問題。
- 「同居でマージを止めたか、通したか」。私の推測「stg だからと通した」は外れた。実際は「そもそも構成を見ていない。分かれているものだという前提があって、確かめていなかった」。判断ではなく盲点。
- 「stg 既定値の理由を読んで納得したか、目に入らなかったか」。どちらでもなく、「定数化は一般則で細かく見れば絶対見る。ただし埋まっていること自体が悪ではない。cert の ARN は決まった文字列に見えるので違和感なく見逃しうる。判別の基準は、それがどういう文脈で PR されているかまで見たときの違和感」。

ここから skill の二つの核が決まった。一つ、出力の冒頭に判断を一切入れない「構造の要約」を置く（盲点への対策）。二つ、コードの各判断と「PR 自身の文書や関連 issue が予告している変更」を機械的に突き合わせる（違和感の近似。理由の有効期限は多くの場合 PR の中に書いてある）。

owner の整理では、観点は二種類ある。issue や領域から導き出せる実務の原則（手順 1 と 4）と、成果物に対する自分の一般原則（手順 5）。前者が後者のどれを選ぶかを決める。私の「推測」ラベルはどちらでも決まらない残りで、校正の対象。

## 5. v1 と第 1 回測定（2026-09-28）

skill 171 行、agent 39 行。sync は worktree からだと `~/.claude` のリンクが worktree を向くので使わず、汎用 subagent に定義を注入して走らせた。遮断として、正解表の issue 番号以降と、元 PR のマージ日以降を読ませなかった。

結果。正解表 13 件（負と予測不能を除く）のうち、完全一致 6、部分 5、外れ 2。負の 2 件は、1 件は踏まず、1 件は半分踏んだ（直し方の案で guard を先に出した）。約 16 分、36 万 token、ツール呼び出し 52 回。差分全体、同梱文書 12 本、差分外 7 本、関連 issue と PR 20 本を読み、遮断を守ったと自己申告し、issue 本文に混ざった後日の編集を自分で除外していた。

外した 2 件のうち 1 件は原因が skill 本文にあった。私が書いた「見送りの例」がその見送りを指示していた（「単位ごと差し替える前提なら見送る」。後の正解は差し替えでなく注入で、前提自体が偽になった）。もう 1 件は移行プロジェクト名のタグで、agent は「置換を伴わないので安い」と見送った。元 PR の時点では他サービスがまだ無く、正解表の動機が未発生だったので、外れとは言い切れない。部分一致 5 件のうち env guard の件は、「既定値を無くせば guard が要らない」という項目どうしの接続を作らせていなかったことが原因で、半分踏んだ負の項目（guard を足す案を先に出した）と合わせて、v1.1 の修正の対象になった。

正解表の外にも発見があった。PR 本文の「無改修で載せ替え可能」が成り立たないこと、既定値が稼働中の値とすでに食い違っていて渡し忘れると黙って前の挙動に戻ること、手で足した許可ルールと権限付与がどこにも追跡されていないこと、PR 本文と実作業の食い違い 5 件。

## 6. 校正（2026-10-06）

owner への問いかけは、会話では答えづらかった（「反応がいるもの、もう少しわかりやすく」「当たりの定義を教えて」）。owner の指摘で、分身の報告は AI 向けの正本を一つ持ち、人間が反応する面は artifact にする、と分けた（#329 と同型）。校正シートを artifact にし、推測 2 件と新規発見 3 件に三択のボタン、補足欄、保存先を付けた。

結果。推測 2 件は両方当たり。新規発見 3 件は 2 件当たり、1 件「気にしない」。報告の冒頭に上位 3 件を置く案は不採用。補足欄から次が出た。

- 「アーキテクチャ設計判断の齟齬で、要件のすり合わせができていない」（#408 の動機）
- 「コードを見ても気づけていなかった。SO で発見できないのは別の問題。分身が発見できる理由は多様性レビューのヒントになる」
- 「気にしない」の項目は、内容ではなく出し方の問題。「この PR で構築するものとして情報が足りない」という枠なら指摘する。起きる確実さや頻度で変わる
- 「PR 本文のフォーマットは外側だけで、内容の精度を担保するハーネスが無い」（#409）
- 「件数より、解釈しやすく判断しやすい文章と形式を磨くほうがいい」

## 7. v1.1（2026-10-06）

外した 2 件と半分踏んだ 1 件の原因への修正、運用の原則の一群（単独で出せる単位、戻す経路、影響範囲が閉じる、再現性、記録の欠落）、運用上の項目を「リスク」でなく「記録の欠落」の枠で出し起きる確実さを添える、項目どうしの影響を一文で繋ぐ、guard を足す案より手順側を先に置く、人間向けの要約は作らない。171 行から 194 行。

第 2 回測定は同条件で走らせた。結果は closure に書く。

## 8. 第 2 回測定（2026-10-06）

同条件（同じ PR、同じ遮断、opus）で v1.1 を走らせた。約 19 分、37 万 token、ツール呼び出し 55 回。

結果。正解表 13 件のうち、完全一致 11、部分 2、外れ 0。第 1 回の 6 / 5 / 2 から、厳密な再現率は 46% から 85% に上がった。負の項目は、前回半分踏んだ「code guard を足せ」を踏まなくなった一方、前回踏まなかった「cross-stack の export は実害なし」に半分触れた。agent の主張は「revision ごとに変わる値（task-def の ARN）が export され、消費者が文書で予告されている」という将来向きのもので、正解表の判定（import されている値は運用上変えない）とは別の主張になっている。skill の欠陥か owner の判断の境目かは、次の校正で owner が決める。

v1.1 の修正はそれぞれ対応する項目を動かした。項目どうしの相互作用の規則で、env guard の件が「既定値を無くせば guard も要らない」と接続された。見送りの境目の規則で、タグの件が見送りから質問に移った。guard より手順側の規則で、入口の固定の直し方が手順側から出て、推測ラベルが付いた。運用の原則の一群で、「宣言の外で作られた構成要素」が 9 件列挙され、うち 5 件が「記録に無い」という欠落の枠と条件付きの確実さで出た。これは第 1 回の校正で owner が「それなら指摘する」と言った形である。

副作用として、予告との接続を強めた分だけ、正解表の負の項目に将来向きの主張で触れた。

出力の量は増えた。指摘 7 件、質問 11 件、推測 3 件（前回 5 / 8 / 2）。前提とのずれは 12 項目になった。owner は「件数より解釈しやすさを磨く」と言っているので、量の制御は skill 本文ではなく人間向けの表示層（#329）で行う。

## 途中で起きたこと

- 伏せ字の基準を一度広く取りすぎた。owner の明示は「public なリポジトリと、インターネットから直接見えるものには出さない。自分の Claude アカウントで見る artifact は構わない」。校正シートは伏せて作ったが不要だった。記憶を書き換えた。
- scratchpad に置いていた作業記録 4 本と diff の切り出し 2 本が、約 3 日のアクセス空白で消えた（`/private/tmp` の掃除）。作業記録 4 本は会話記録から復元し、gitignored な `tmp/404-alter-ego/` に置き直した。worktree 側の `tmp/` は worktree と一緒に消えるので、同じ内容を master 側のチェックアウトの `tmp/404-alter-ego/` にも置く。日をまたぐ記録の置き場を記憶に残した。
