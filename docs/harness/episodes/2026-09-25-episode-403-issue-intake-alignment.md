# #403 issue 起点の認識合わせスキル

## なぜこの作業が始まったか

#390 で、ゲートを全部通したのに、後継が子の登記をつけかえる工程が落ちた。ゲートが発火しなかったのではなく、発火したゲートの中身がその観点を持っていなかった。issue の目的節が足りていなかったことが原因で、直すのは issue を作る瞬間ではなく使う瞬間である、というのが #403 の立て方である。ゲート0（owner と統括の `question-driven-design`）は 2026-09-22〜25 に済んでおり、この委譲は plan を作って設計SO を通すところまでを受け持つ（終端は brief の T3）。

## Step 0: 着手と上流の断定の裏取り（2026-09-25）

- baseline は master `99d0ecd`。`origin/master` と一致することを確かめてから worktree を作った。
- brief と #403 本文が断定していることのうち、plan の前提になるものを一次情報で確かめた。結果は plan の「設計の前提」節に強さつきで写した。要点は次の3つである。
  - `question-driven-design` の「いつ使わないか」節の該当行は、いまも31行目にある。本文も issue の引用どおりである。
  - hub の `CLAUDE.md`・`AGENTS.md`・`README.md` のどれにも、蒸留の文書（`docs/harness/` や `projects/*/docs/` の discussion / plan / episode / decision）への案内は無い。蒸留の木は4つある（`docs/harness/`・`projects/orchestration-engine/docs/`・`projects/wezterm-ai-mode/docs/`・`projects/cursor-thread-tools/docs/`）。
  - hub には `.github/ISSUE_TEMPLATE/` が無い。`issue-conventions` は、テンプレートが無ければ「目的・作業内容を本文に記述する」としている。取り込みの最初の確認は、テンプレートが無い場合を正面から扱う必要がある。
- **issue 本文の「`issue-conventions` は観測できる動作が引き金なので確実に読み込まれる」は、過去の実測では裏付けが足りない。** `docs/issues/67/step9-verification-results.md` によれば、Claude Code では Phase 1 で `issue-conventions` も `question-driven-design` も読み込まれず（NO_LOAD）、description を直したあとで読み込まれた。同じ実測は、`conventional-commits` について「一般知識で正しく実行できるタスクでのスキルロード強制は構造的課題」と書いている。「issue に着手する」は、モデルがスキル無しでもこなせると思いやすい種類の作業である。

昇格の印: 「観測できる動作を引き金にすれば確実に読み込まれる」は description の一致に頼っており確実ではない。入口の発火は実測で確かめる項を受入に入れる

## Step 1: plan の骨組みを決める

### 子の省略判定のコマンドを、実物と合成データで検算した

確定版コメントの探し方（plan DJ-5）を、スキルに載せる形のまま走らせた。

```bash
gh issue view 390 --json comments --jq '[.comments[] | select(.body | startswith("<!-- issue-intake:confirmed -->"))] | last | .url // empty'
```

- 実物（#390・コメント1件・印なし）では空行が返り、exit 0 だった。
- 合成データ（先頭に印のあるコメント2件と、印を引用しただけのコメント1件）では、最後の確定版の URL だけが返った。引用だけのコメントは拾わなかった。
- `gh issue view --json` のコメントは `url`・`body`・`createdAt`・`includesCreatedEdit` などを持つ。issue 本文の最終編集時刻を返す欄は無い。このため「本文が確定版の後で書き換えられたら確定版を無効にする」判定は入れなかった（plan の「棄却した案」節）。

### 投稿の順序を brief の骨組みから1箇所変えた

brief の骨組みは「owner の反応 → 確定版を issue コメントへ → 深掘りの3つの合図 → QDD への受け渡し」の順だった。plan では深掘りの合図を確定版の投稿より前に置いた（plan DJ-3）。合図が出たときの版はまだ確定していない。それを確定版の印つきで先に投稿すると、子の省略判定がその未確定の版を拾ってしまう。セッションが途中で終わったときの消失は、提示の時点で下書きを作業用のファイルに書くことで別に防ぐ。この変更は owner の判断3として plan に載せた。

### 別モデルへの問い合わせは「省く」分岐に見えないように書いた

issue の内容を別の会社へ送ることになるので、リポジトリの取り決めで外へ出せないときは問い合わせを省く、という規則を置いた（plan DJ-6）。これは「AI の判断で認識合わせを省く分岐は作らない」（ゲート0 の結論1）とぶつかって見えるので、省くのは問い合わせだけで、3つの出力と owner の反応は必ず通る、と本文に明記した。

### 入口の発火は確実ではない前提で、hub 側に2つ目の錨を置いた

Step 0 で見たとおり、スキルの読み込みは description との一致に頼っている。そこで hub のフロー側に、発火しなくても抜けが見える場所を作った。brief テンプレートの可変節に「認識合わせ:」の欄を足す（plan DJ-9）。統括が brief を組むときに欄が空なら、認識合わせを通していないことが見える。機械で強制する層（hook など）は作らず、D1 で読み込まれない形が残ったときに surface する。

昇格の印: 「入口の発火が確率的なスキルには、委譲の書面側に空欄として見える2つ目の錨を置く」は、他の入口系スキルにも効く設計の形かもしれない

### 受入のコマンドを変更前のファイルで走らせた

negative knowledge `01M2DRCP3QSG4NQWHNY6DSD3NJ` に従い、文書の変更を見る受入の項を変更前のファイルで走らせた。plan に書いた変更前の値（QDD の該当行 1・ゲート配置の該当文 1・guardrail の該当文 1・「認識合わせ:」欄 0、件数は見出し・ディレクトリ・表の行がどれも 28）と一致した。回帰を見る diff（ゲート表の 1〜6 行・② の固定節21行）は空だった。

件数の受入は、最初「29 と一致」と決め打ちしていた。#404（分身のレビュアー）も skill を作り、同じ `CATALOG.md` の表に追記する見込みが高いので、どちらが先にマージされても通るように「見出し・ディレクトリの数・表の行数が一致する」形に直した。

### owner への問いを1件出した

「hub は事情が違う」の中身を確かめられなかったので、`.oe/question-403-1.md` に候補（A: 木が4つある / B: 仕様側から辿れれば足りる / C: `CLAUDE.md` の役ではない / D: その他）と推奨（A の読みで規則を書く）を書いて、統括へ送った（`oe-send` exit 0）。ゲート3までに答えがあれば足りるので、plan と設計SO は推奨案のまま進める。

## Step 2: 設計SO（ゲート2・弱・2レーン）

### スキルの読み込み経路を公式文書で確かめた（SO と並行）

plan の「検証していない前提」にあった「Claude Code が作業ディレクトリの `.claude/skills/` からスキルを読み込むか」を、公式文書で確かめた。調べ物は subagent に任せ、返ってきた要約の出典（https://code.claude.com/docs/en/skills.md）を自分で開いて突き合わせた。起動したディレクトリと親をリポジトリの根まで、それに `--add-dir` で渡したディレクトリの `.claude/skills/` から読み込み、スキルのディレクトリは symlink でよい。

これで dogfood の足場が変わった。最初の plan は、リポジトリの外に `git init` した一時ディレクトリで D1 を回す形だった。`--add-dir` で読ませれば、hub の実物の checkout の中で、リポジトリに何も書かずに回せる。統括のセッションも `/add-dir` で読み込めるので、D2 をパス指定ではなく本物の引き金（「#<番号> に着手する」）で試せる。

一方で、非対話の出力のどの記録で「読み込まれた」と判定するかは、公式文書に書かれていなかった（subagent の要約も「not documented」）。これは D0 で実物から決めることにした。

### 1本目（Codex）で plan を大きく直した

Codex は「高7件・中6件。現 plan のままのゲート2通過には反対」と返した（`gpt-5.6-sol`・318秒・初回で返答）。採否の一覧は plan の「設計SO（ゲート2）」節にある。ここには、判断が覆った筋だけを書く。

- **AI の判断で省く口が、省く条件の節の外に2つ残っていた。** 1つは「issue を特定できなければ issue の無い作業として扱う」で、もう1つは「owner が何も指さなければ確定」である。前者は識別の失敗を「issue が無い」に畳み、後者は無応答を承認に変える。どちらも「省く条件は2つだけ」と書いた節の外にあったので、自分では条件の一覧だけを見て「口は塞いだ」と判断していた。省く口は、省く条件として書かれた場所ではなく、分岐が起きるすべての場所で探す必要があった。
- **仕様の直し方が「ゲート配置」節だけでは足りなかった。** 「遷移規則」節の判定順は「設計判断が絡むか」から始まり、絡まないと判断した issue はそのまま plan へ進める。(0) を必須にしても、入口層の判定がそれより前に走るので飛ばせる。brief は「遷移規則」節を参照に挙げていたが、読んだうえで直す箇所に入れていなかった。
- **検査の範囲を「hub の中だけ」と書いたのは実態と違った。** `document-format.md` と `doc-flow-guardrail` は sync で配られ、ほかのリポジトリの作業からも参照される。negative knowledge `01KYJ76D7CS7EBY3WDYY1NS9Y2`（規範の範囲と検査の範囲を別々に書け）を当てたつもりで、検査の側の範囲を実態より狭く書いていた。
- **D1 の安全の境界を、禁止の一覧で作っていた。** `gh issue comment` と `so-compare` を外しても、`gh issue edit` や `gh api` や `curl` が残る。書き込める道具を最初から渡さない形（`--tools Read,Grep,Glob,Skill` と `--strict-mcp-config`）に変えた。
- **投稿の順序は、元の順序（投稿 → 合図）と自分の順序（合図 → 投稿）のどちらでもなく、第三の形に落ち着いた。** 未確定の版を確定版の印で出さないという自分の理由と、途中の版が失われず進行中であることが見えるという元の順序の利点を、「深掘り中」の印で両立させた。

昇格の印: 「省く口は、省く条件として書いた節ではなく、分岐が起きるすべての場所で探す」は、ゲートや省略条件を設計するときの一般の教訓かもしれない

採らなかったものもある。owner の確認を機械で証明する仕組み（GitHub Actions の bot・署名つきの受け渡し）と、作業を始める verb で入口を担保する案は、ゲート0 の結論（器はスキル1本・機械の検査で閉じようとしない）と、owner の手数を増やさないという優先順位に反するので退けた。Codex と Cursor での発火の実測も、統括のセッションが Claude Code で動いていることから範囲外にした。

### 直した受入と確定版の探し方を、変更前のファイルと合成データで走らせた

- 節の範囲で見る形に直した受入（A3-2・A3-3・A4-1・A4-2・A5-2・A5-3・A6-2）は、変更前のファイルでどれも 0 を返した。図と段落の旧い文（A4-4・A4-5）は 1 を返した。どれも変更後に反転する向きである。回帰を見る diff（A4-6・A5-5）は、比較の相手を枝の分かれ目に変えても空だった。
- 条件を足した確定版の探し方（先頭の印・4つの見出し・投稿者の種類）を、実物の #390 と合成データで走らせた。実物では空が返り exit 0 だった（`gh` の中の jq でも `IN` が通る）。合成データでは、陽性1件だけが返り、陰性4件（印が先頭に無い・見出しが欠ける・投稿者が第三者・印が無い）はどれも拾わなかった。「深掘り中」の印のコメントが後ろにあっても、その前の確定版が返った。

上の最後の1文は、そのときは陽性として記録した。2本目の SO で、これが欠陥そのものだと分かった（次の節）。

### 2本目（Claude）で、1本目の直しが入れた欠陥が見つかった

Claude（`claude-opus-5-5`・effort high・304秒・初回で返答）は、1本目を反映した版に対して「書き直しで新しく入った高の欠陥が4件ある」と返した。採否の一覧は plan の「設計SO（ゲート2）」節にある。判断が覆った筋を書く。

- **状態を1つ足したのに、その状態を読む側を直していなかった。** 1本目の指摘10を受けて「深掘り中」の版を投稿する形にしたが、子の判定のコマンドは確定版の印しか見ないままだった。確定版のあとに認識合わせをやり直して深掘りに入ると、子は古い確定版を拾って進む。前の節の最後の検算で「深掘り中の版が後ろにあっても前の確定版が返った」を陽性として記録していたのは、この欠陥をそのまま正しい振る舞いとして確かめていたことになる。検算は「コマンドが書いたとおりに動くか」を見ていて、「書いたとおりの動きが設計として正しいか」は見ていなかった。直し方は、両方の印を見て最後の1件の状態で動く形にし、止まる場面ではやり直さずに知らせる形である。
- **受け渡し先から戻る道を確かめていなかった。** 深掘りを `question-driven-design` に受け渡したあと、そのスキルの「質問フェーズの完了」節は「次のステップ（Plan mode または直接実装）に進む」で終わる。受け渡す側の骨組みには「深掘りを終えたら確定版を投稿する」と書いたつもりだったが、実行の制御は受け渡し先に移っており、受け渡し先はそれを知らない。受け渡し先の完了節に戻りを1行足すことにした。
- **スキルが「plan へ進む」と名指ししていた。** 仕様の判定順には「軽微修正は plan 必須則の唯一の例外」と「設計判断が絡むなら discussion から」があり、スキルが次の工程を名指しすると仕様と逆のことを言う場面ができる。スキル本体は「次の工程へ進む（どれかはリポジトリのフローに従う）」にとどめ、仕様の判定順0 に「通したあと1〜5は従来どおり」「確定版を読めば通したことになる」を書く形にした。ゲート表の 0 の行を書き直すときに、従来の「設計判断が多いときの QDD」という条件を消しかけていたのも、同じ指摘で直った。
- **発火の測定に、hub の本番の主な言い方が入っていなかった。** hub で認識合わせを通す主な場面は、owner が統括に「#N を子に渡して」と言うときである。D1 の陽性は「着手して」の言い方だけだった。

昇格の印: 「状態を1つ足したら、その状態を読むすべての側（判定・検算・受入）を同じ変更で直す」は、SO の指摘を反映するときの一般の教訓かもしれない
昇格の印: 「スキルからスキルへ受け渡すときは、受け渡し先の完了の節が呼び出し元へ戻るかを確かめる」は、スキルの設計の一般の教訓かもしれない

採らなかったもの・一部だけ採ったもの: 状態をラベルで持つ案と、着手の前に下ごしらえする案は退けた。`gh issue view` を捉える `PreToolUse` の hook は、発火が足りなかったときの候補として判断6に入れた。マージ後の会話記録で発火率を測る案は、D1 を置き換えずに follow-up（判断7）として置いた。「どの観点で見たか」を1行に畳む案は、どの問いを当てたかが見えなくなるので、問いの文を繰り返さない形にとどめた。

2本目の出力の備考によれば、claude レーンはハーネスの指示で要約を `~/.claude/plans/` に書いていた。読むだけの依頼のつもりだったので、plan の範囲外の節に surface した。

### 3本目は回さなかった

2本とも「ゲート2の通過に反対」と返し、指摘の数も多かった。3本目を回せば、2本目の反映で入った欠陥が見つかる見込みはある。それでも回さなかったのは、brief の SO モードが弱2レーンで、弱 SO は1周で終えてよいことと、2本目の反映の確かめを実装SO（ゲート4）の観点に含められることによる。回すかどうかは owner がゲート3で決められる、と plan に書いた。

### 2本目の反映後の検算

- 認識合わせのコメントの探し方を、状態・投稿者の種類・見出しの数・URL を1行で返す形に直し、実物（#390・#403。どちらも空）と合成データ8件で走らせた。8件はどれも plan に書いた値を返した（確定版のみ・確定版のあとに深掘り中・印の前に空白・第三者・見出しの欠け・引用だけ・版の無い印・印が無い）。`gh` の中の jq でも、実物の issue で `test`・`capture`・`IN` がエラーなく通った。
- 新しく足した受入（A1-2 の frontmatter の切り出し・A3-4・A3-5・A4-1〜A4-5 の新旧の対・A5-1・A5-4）を変更前のファイルで走らせ、どれも plan に書いた変更前の値になった。

## Step 3: ゲート3の裁定（2026-09-28・条件つき承認）

統括から、owner の答えを書いた裁定のファイルが届いた。ゲート3は条件つきの承認で、判断4（dogfood の実物の issue）と判断5（確定版の後の本文の書き換え）が残っている。実装は、判断5の答えを反映し、統括が baseline の digest を記録してから、別の指示で始める。plan の status は `draft` のままにした。裁定の一覧は plan の「ゲート3の裁定」節にある。ここには、plan の中身が動いた筋と owner の理由を書く。

- **マージ後の発火率の観測（判断7）は置かないことになった。** 2本目の SO の代替案H を受けて、推奨として置いていたものである。owner の理由は、数を取っても有意義なものになるか分からないこと、問題は「owner にどう見えているか」のほうであること、以前に似た観測をしたときも取れているのかいないのか分からなかったことである。SO の指摘（測りたい発火と測れる発火のずれ）は正しいが、そのずれを埋める手段として数の観測を足すことは、owner の見え方の問題を解かない。発火の確認は D1（マージ前）までにし、「工程の主体」節の観測の行を消した。
