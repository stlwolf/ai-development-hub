# #467 ランブックの書き方と、ランブック・スキル・スクリプトの役割の分け方をスキルにする

**この episode は着手時に枠を作り、作業しながら追記している。** 後追いで再構成した節があれば、その節の冒頭にその旨を書く。

## なぜこの作業が始まったか

2026-10-19、owner は業務のサービスのインフラのリポジトリ2つで、デプロイなど更新の作業のランブック（人が読む手順書）を作っていると話した。作業は AI のスキルにさせているが、人や AI の実行環境に結果が左右されるので、最悪のときに人が手で操作できるようにしたい。既存を取り込んだ側では、人が手順書だけで実行する演習を初めて試したところ、owner は前提を確かめる段の途中で止まり、実行者を AI に替えた（材料2・#467 のコメント）。新しいサービスの側の手順書の形も、既存を踏襲してたまたま決まっているだけで強制力が無い（#467 の本文・材料1）。

## この単位の入力

- brief: 統括（cockpit 19代目）が 2026-10-21 に発行した委譲の書面（作業層・消える）。plan-first で、最初の終端は P3（plan を報告して止まる）、委譲全体の終端は I3（PR を作って報告する）。マージ・worktree の掃除・issue の close はしない。baseline は master `f6c86fc`。
- 認識合わせ: 確定版 https://github.com/stlwolf/ai-development-hub/issues/467#issuecomment-6311133796 。深掘りで材料3（人が人のために書いて使えていた既存の手順書）が足され、owner が読者をエンジニアに絞って5組を選んだ。
- scope: 新しい canonical のスキル1本と `canonical/CATALOG.md` の1行。brief の (1)〜(11)（役割の分け方・読者の書き分け・節の型・前提の型・手順書の種類・スクリプトに包む粒度・確かめの落とし穴・AI が実行するときの1行・用語の決まり・検査の項目・架空のサービスの見本）を持つ。持ち運べる形にし、hub を参照しない。
- 材料: 材料1・2 は別のリポジトリの統括が書いた要約で、手元の作業層（git の管理外）にある。材料3 は5組の既存の手順書で、置き場の一覧が手元の作業層にある。公開の成果物には、会社名・サービス名・顧客名・ホスト名・秘密の値を写さない。手元のファイルの名前にも業務の名前が入っているので、この episode と plan ではファイルの名前を書かず「材料1 の手元のファイル」のように書く。
- SO: 設計 weak・実装 weak（どちらも `so-compare` の Codex 1レーン。返らなければ Cursor のレーンに1回だけ切り替えてよく、切り替えたら理由をここに書く）+ Copilot 1ラウンド。SO に渡すのは hub の plan とスキルの文面と見本だけで、材料は渡さない。
- 注入された negative knowledge: 4件（frontmatter の `knowledge_observations`）。closure で全件に観測を書き戻す。

### P2: plan の初稿と、そこで下した判断の理由（2026-10-21）

plan の初稿を書いた。判断の結論は plan の DJ-1〜DJ-11 にあり、ここには結論に至った理由のうち plan に書き切れないものを残す。

- **読者の書き分けを案A にした決め手は、材料2 の1回の出来事ではなく、材料3 の人が書いた形にもある。** 材料2 の「人が演習で止まった」は元の記録を確かめられない要約である（P1）。一方、材料3 の2組目（owner が以前に書いた作業フロー）は、冒頭に「基本はスクリプトで作業できるので、確認系を手動で行う」と書き、番号の付いたスクリプトを順に実行する形だった。1組目の README も、長いコマンドを入口のスクリプト1本とその下の名前で包んでいた。人が自分のために書いた手順書が、すでに「機械で決まる所はスクリプト、人は確かめと判断」の形をとっていたので、案A は材料2 の提案の写しでなく、人が書いて使えていた形の一般化として置ける。

昇格の印: 手順書の読者を人と AI に分け、1本の手順書の本体を人向けの粗い段（多くても6）にし、細かい確かめはスクリプトの中と「止まったときに読む表」に置く判断

- **読んで決める判定の決まり（Q3）は、材料2 の決まりを一般化して持ち込む案を推奨にした。** 材料2 の決まりは「デプロイを止めるかの判定」に限った文で、そのままでは設定の反映や初期化に当てられない。一方、「スクリプトが止まるのは期待が1つに決まる確かめが外れたときだけ」という線は、包む粒度の決まり（確かめは機械・判断は人）と同じ線で、役割の分け方の境目そのものになる。brief が「持ち込むかは plan で決める」としたので、Q3 として owner に渡す。

昇格の印: スクリプトが止まるのは期待が1つに決まる確かめが外れたときだけにし、読んで決める判定は要点を出して人か AI に返す、という線

- **節は8つにし、「記録する場所」を節にしなかった。** 材料2 は「記録する場所」を節として持つが、材料1 のスクリプトは最後に記録に貼る行を出す。行を出すのがスクリプトなら、貼る場所は手順の最後の段に1行書けば足り、節を増やさずに済む。人が上から読む節を4つに抑えたかった。
- **節の名前を「罠」でなく「間違えやすい所」にした。** 材料1 は「罠」、材料2 は「間違えやすい所」と呼ぶ。owner への説明で比喩を避ける方針と、DJ-8 の「人が読む普通の語」に合わせた。業務のリポジトリの呼び方が優先する、と書く。
- **検査に R2〜R4（前提の型・種類・手順の段）を足す案を推奨にした。** brief の (10) の4つだけでは、スキルの中心の決まり（人向けの段の上限・前提の4つ）が機械で守られない。どれも見出しとラベルを数えるだけなので、誤検出は少ない見込みである（推測）。足す範囲が brief の文より広がるので Q4 にした。
- **description の初稿で、自分の用語の決まりを破った。** 初稿に「手順書の続けて打つコマンド」と書いた。DJ-8 で使わない語にした「打つ」である。配る文面ほど、書き手（AI）がふだんの言い方で書いてしまう。そこで受入に A8（スキルのフォルダ全体に使わない語を当てる）を置いた。同じ形で、DJ-8 の文の初稿に「親・子・委譲」と例を挙げたが、A6 の grep（hub の運用の語）に当たるので、例を「AI どうしの役割の呼び名」に直した。

昇格の印: 配るスキルの文面は、そのスキル自身が決める用語の決まりを書き手が破りやすいので、スキルのフォルダ全体に自分の決まりを当てる受入を置く
