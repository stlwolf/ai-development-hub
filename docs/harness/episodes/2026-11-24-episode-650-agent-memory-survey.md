# #650 Claude Code と Codex の記憶の仕組みを調べ、ハーネスに入れられる調整と制御の候補を並べる

## なぜ始まったか

2026-11-15 に、engine が起こした Codex の子の中で Codex の記憶を整理する会話が裏で動き、頼んだ作業の内容が owner の Codex の記憶に入り、頼んでいない報告も親へ送ってきた。記憶に何が入り、人がどこまで制御できるかを、まとまった形で確かめたことが無かったので、Claude Code と Codex の両方を調べる issue が起こされた（#650）。

## 認識合わせ（2026-11-24）

- 最初の下書きは、issue 本文どおり「比べて、決めること4つを決める」形だった。owner は、主の調査と望む結果は「ハーネスとして記憶をどう扱うか」で、出発点は「ハーネスに記憶を調整するものか制御するものを入れるのか、入れられるのか」だと指した。engine で記憶をどう使うかは別の話とした。
- 深掘りで決まったことは4つある。
  - 対象は Claude Code と Codex の両方である（ハーネスには当然 Codex も含む）。
  - 層を2つに分ける。この issue はハーネスの層（エージェントごとの記憶の扱い）を扱う。engine の層は、利用者ごとにハーネスがある前提で、engine の動きを変な方向に走らせないためにだけ、エージェントに依らない形で記憶を制御する話で、別の issue にする。
  - この issue は、いまの状態を調べる調査の issue で、ハーネスに何を入れるかは決めない。ほかの要素と絡んで発展する余地を残す。
  - 進め方は、Claude Code の側が両方を先に調べて文書を埋め、そのあと Codex がその文書を確かめて埋める。issue 本文の「それぞれが相手を知らない前提で調べる」から変えた。
- 確定版: https://github.com/stlwolf/ai-development-hub/issues/650#issuecomment-7134862521

## 作業の記録

### 初稿を書く（2026-11-25）

- ブランチ名を `docs/#650_agent_memory_survey` に変え、plan と episode の枠を commit した。
- 公式の文書は、まず Web を読む子に頼んだ。返ってきた要約は、原文にある文を「無い」と言ったり、原文の文を要約の扱いにしたりしていた（環境変数 `CLAUDE_CODE_DISABLE_AUTO_MEMORY` の項を、最初の要約は「無い」とした）。頼み直すと子は訂正したが、どちらも子の申告である。そこで `curl` で公式の頁の Markdown（Claude Code は URL の末尾に `.md`）と HTML を取り、要の文を `grep` で原文から確かめてから `[verified]` を付けた。
- Codex の記憶の頁は `developers.openai.com` から `learn.chatgpt.com` へ移っていた（308 の転送）。
- 手元の試し（DJ-6）は、plan のとおり2回で済んだ。試しA（設定をそのまま）では記憶が書かれ、試しB（`autoMemoryEnabled: false`）では書かれなかったので、比べられる場合に当たった。試しAの会話の記録では、記憶は `Write` の道具で書かれていた。これは、hook で記憶の書き込みを見る候補の根拠になった。
- 試しを打ったのはこの会話の Bash からで、子のプロセスには `CLAUDE_CODE_CHILD_SESSION=1` が入っていた。入れ子の会話でも記憶は書かれた。
- 試しが作ったフォルダは、試しの前後の一覧の差で2つ（一時ディレクトリのパスから作られた名前で、末尾が `exp-exp-a` と `exp-exp-b`）と特定し、scratchpad の `650-claude-experiment/` へ移した。一覧は試しの前と同じに戻った。消すかどうかは owner が決める。
- 調べている途中で、Codex の記憶の置き場が `memories/` と `memories_v2/` の2つあること、どちらの git も commit が1件だけであること、`~/.codex/config.toml` の hub の印の範囲の中に Codex 自身が書いた表が入り込んでいることが分かった。どれも文書に書いた。

昇格の印: 公式の文書を Web を読む子に要約させると、原文にある文を「無い」と返すことがある。`[verified]` を付けるのは、原文を取って `grep` で当てたあとにする

### 効き目と止めたときの影響の観点を足す（2026-11-25・plan の H1）

- Codex に書面を渡す前に、owner が「記憶がどの程度効いているか、いま止めたらどういう影響が出るかの観点はあるか」と聞いた。6項目は仕組みを見るもので、この観点は無かった。owner は観点を足し、書面を直してから渡すと決めた（plan の「ゲート3 のあとの変更」節の H1・変更の級）。
- 数えてみると、索引は上限にほぼ届いている一方で、直近 30 日に `Read` で開かれた記憶のファイルは3件・4回だけで、書かれた回数（40 回）のほうがずっと多かった。効いているのは毎回読み込まれる索引の1行の要約だ、という見立てになった。どの記憶がどの判断に効いたかは記録に残らないので、見立てのままにした。
- 「決まりやスキルに入った」記憶の数は、語で拾うと 12 行になったが、「正本」を方針の言葉として使う行が混じっていた。1行ずつ読んで 7 行に絞った。語で拾う数は、そのままでは使えない。
- 例として記憶の中身（指摘の文）を調査メモに書きかけ、文書の決まり（中身を写さない）に当たるので外した。
- Codex への書面に、節 6.2 を埋める項目を足し、節の番号のずれを直した。
