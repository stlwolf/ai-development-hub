**「別のところが持つから消せる」は、消す先の配布物が届く全ての環境で確かめないと成立しない。** 1つの環境で確かめた重複を、確かめていない環境にも一般化するのが典型的な壊し方である。

#307 の rules 棚卸しで起きた。判定表は「本体が持つ」列を主モデルと副モデルの2列で持ち、モデルによって本体の節の集合が違うことまでは押さえていた。**しかし配布先は3ツールあり、Codex と Cursor の列は空のままだった。** その状態で「本体が持つから消せる」と判定し、10本の PR のうち5本で実装SO が独立に同じ穴を突いた。自己点検の規定、依頼範囲を守る規定、ツール固有の環境変数名。どれも「自分の環境には代替が在る」ことは正しく、「他の配布先にも在る」は確かめていなかった。

**モデルの軸を足しても、ツールの軸を空にしたままなら同じ誤りが再発する。** 実際そうなった。段階1 でモデルの軸が足りないと指摘され、それを2列にして判定表を作り直したのに、段階2 で同じ形の穴がツールの軸で開いた。軸を1本足すことは、母集団を数えたことにならない。

**母集団は節ではなく文の単位で数える。** 同じ arc で、ドリフトした1文が rule の複数の節に散っていて、判定表の行（節名）だけを見て消したために rule が自分と矛盾しかけた。判定の単位と、消す対象の単位がずれると、片方だけが消える。

次にどう行動を変えるか。(1) 「別の層が持つ」を根拠に消すときは、**消す先の配布物が届く環境を先に列挙し、環境ごとに代替の有無を書く。** 空欄が1つでも残っているなら、その環境向けには消さないか、消す判断を保留する。(2) 列挙は索引や記憶ではなく**配布の実体**（配布スクリプトが何をどこへ配るか）から数える。(3) 判定の単位を先に決める。節で判定するなら節の中の文がすべて同じ判定でよいかを確かめ、違うなら文の単位へ落とす。
