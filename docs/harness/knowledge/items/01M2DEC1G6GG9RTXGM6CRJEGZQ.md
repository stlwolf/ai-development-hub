**引用は「読んだ」ことの証拠にはなるが、「その内容に合わせて書いた」ことの証拠にはならない。** 2つは別の工程である。

#390 のガードレール改訂で、配布物へ「`oe-send` は生の `%N` を登記を通さず素通しするので、**死んだ pane でも**送信そのものは成功しうる」と書いた。誤りである。素通しするのは登記による解決だけで、生存確認はその下の transport が必ず行う。存在しない pane へ送ると `target pane not found` で exit 1 になる。

**根拠にしたのは `oe_reg_resolve` のコメント1箇所だけで、その下の層を読んでいない。** しかも同じ plan の2行前に、自分が実行した `oe-send --help` の出力から「宛先が無い（生存しない `%N`）→ 1」を引用してある。**引用した一次情報が、続けて書いた断定を直接否定していた。**

## なぜ非自明か

「裏を取らずに書いた」だけなら不注意で片づく。そうではない点が2つある。

**ひとつは、引用が確認の感覚を作ってしまうことである。** 一次情報を引いて書く工程を踏むと、その資料について「確かめた」状態が心理的に成立する。ところが確かめたのは引用した命題だけで、同じ資料が答えている別の命題は確かめていない。**引用の存在が、確認していない断定を守ってしまう。**

**もうひとつは、この配置がレビューをすり抜けやすいことである。** 引用と断定が同じ節に並ぶと、読み手は「根拠つきで書かれている」と読む。実際に食い違いを見つけたのは、`--help` ではなく `lib/` の transport 層まで降りた外部レビューだった。**同じ資料の中で完結する矛盾なのに、資料を1段深く読まないと見えない。**

## 行動をどう変えるか

**引用した一次情報が答えている命題を、断定の前に数え直す。** `--help` の exit code の表・スキーマ・型定義のように「性質の一覧」を持つ資料を引いたときは、これから書く断定がその一覧のどの行に当たるかを先に見る。当たる行があればそれに従い、無ければ**その資料は根拠にならない**ので別の層まで降りる。
