**入口のスキルの発火は、渡す側と受け取る側の両方の言い方、それに引き金が重なる隣のスキルの言い方で測る。重なるなら、description にどちらを先に通すかを書く。**

#403 の `issue-intake` は、issue に着手するときの認識合わせを必ず通すための入口のスキルである。最初の測定では、着手の4つの言い方（番号・URL・タイトル・本文の貼り付け）で発火した。ところが「#355 を子に委譲して」と頼むと `delegate-task` だけが読み込まれ、`issue-intake` を通さずに委譲の準備へ進んだ。description に「delegate-task などで委譲の操作をする前に通す」と順序を書くと、委譲の言い方でも先に読み込まれた。

さらに、brief を受け取った子の側でも測ると、子は brief の規約を持つ `doc-flow-guardrail` だけを読み込んだ。確定版の URL を直接読んで前提にしたので結果は正しく見えたが、スキルの照合（最後の版か・URL が一致するか）は通っていなかった。別の issue の URL を書いた brief では、食い違いに気づいても止まらずに進んだ。description に受け取る側の場面を足すと、3つの場合とも照合を通った。

## なぜ非自明か

**入口のスキルを書く人は、自分が想定した1つの言い方で発火を確かめると満足する。** 委譲のように場面に2つの側がある場合、もう片側は別のスキルの領分に見え、測る対象から抜ける。**素通りされても結果が正しく見えることがある**ので、結果だけを見る受入では気づけない。

## 行動をどう変えるか

**入口のスキルの発火を測る表に、渡す側・受け取る側・引き金が重なる隣のスキルの言い方を、行として必ず入れる。** 受入は「結果が正しい」ではなく「そのスキルが読み込まれた記録がある」で見る。重なる隣のスキルがあれば、description に順序（どちらを先に通すか）を書く。
