**式の正しさの検算と、式に入ってくるデータの範囲の検算は別物である。取得のコマンドが何件を渡すか（ページの大きさ・件数の上限）を、式とは別に確かめる。**

#403 の `issue-intake` は、issue のコメントから認識合わせの印で始まるものの最後の1件を探す。最初は `gh issue view --json comments --jq '…'` の形で書き、合成データで陽性と陰性を流して、式の論理を確かめた。実装SO が「`gh issue view` は `comments(first: 100)` しか取らない」と指摘し、`GH_DEBUG=api` で確かめると、そのとおりだった。100件を超える issue では、後ろにある深掘り中の版を見落とし、古い確定版を「最後の1件」として拾う。

`gh api --paginate` で全件を読む形に直し、1ページ1件にしてページ送りを起こした実物と、ページを分けた合成データで確かめた。

## なぜ非自明か

**合成データは式の入力を直接作るので、取得の段で起きる切り詰めを再現しない。** 件数も小さいので、上限に当たらない。検算は「通った」と記録され、欠陥は外部のレビューまで残る。

## 行動をどう変えるか

**「最後の1件」「全件のうち」を判定するコマンドを書いたら、取得の段の上限を1回確かめる。** 方法は、取得側の仕様を読むか、デバッグの出力（`GH_DEBUG=api` など）で実際の要求を見るか、ページの大きさを1にしてページ送りを起こし、最後のものが返るかを見るかである。
