**陽性対照で「性質 P を守る」と書く前に、P を壊す変化を2〜3通り書き出し、その対照がそれぞれを見つけるかを確かめる。見つけない変化が残るなら、主張を「この欠陥への感度」に限るか、別の対照を足す。**

#401 で、apply と check が判定を共有しない（独立している）という性質を守るつもりで、陽性対照 M1（replace が手元の値を残す欠陥を apply の写しに入れ、check が落とすことを見る）を置いた。plan の草稿には「check が apply から期待値を作る形に変われば、M1 の欠陥が check にも伝わって落ちる」と書いた。設計SO の反例は「check が空の settings に apply を当てて期待値を作る」形だった。M1 の欠陥は空の入力には正しい値を書くので、その形の check は従来どおり欠陥を見つけ、M1 は緑のままになる。独立性を壊す変化のうち、M1 が見つけるのは一部だけだった。直しとして、どんな入力にも誤った値を書く対照（M6）と、互いのファイル名や読み込みの行が無いことを見る構造の確かめを足した。

## なぜ非自明か

**対照そのものは正しく動く。** M1 は期待した fixture を期待した理由で落としており、「期待した理由でその色が出たか」（knowledge item `01M00KCCHNMFPHP5HAGX2DZ1MK`）を確かめても穴は見えない。穴は、対照が何を見つけるかではなく、守りたい性質を壊す変化のうち何を見つけないかにある。その母集団を書き出さない限り、数えられない。

## 行動をどう変えるか

**性質を名乗る対照には、壊し方の一覧を添える。** たとえば独立性なら「片方がもう片方を呼ぶ」「片方がもう片方の出力を期待値にする」「共有のファイルへ処理を出す」のように書き、対照ごとにどれを見つけるかを表にする。見つけない行が残れば、主張を弱めるか、その行を見つける対照を足す。
