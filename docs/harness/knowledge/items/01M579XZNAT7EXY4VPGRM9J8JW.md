**bash で、変数の直後に ASCII 以外の文字が来る位置は、必ず `${var}` で囲む。書いたら `grep -nP '\$[A-Za-z_][A-Za-z0-9_]*[^\x00-\x7F]' <ファイル>` で、囲み忘れが無いことを確かめる。**

#401 で、テストの文言に `"M5: sync は shebang の interpreter（主版 $eq_sync_want）で動く"` と書き、1回目の実行が「`eq_sync_want�`: 未割り当ての変数です」で止まった。2026-10-18 に macOS で確かめると、bash 5.2.37 と 3.2.57 のどちらでも、ロケールが `ja_JP.UTF-8` と `en_US.UTF-8` のときに `'[$v）]'` が `v` の後ろの1バイトを食って未割り当てになり、`C` のときは `[1）]` と正しく出た。`set -u` を外すと、`[` と `bc 89` と `]` だけが出る（`）` の先頭のバイト `ef` が消える）。

同じ罠は、2026-09-28 の #403 で heredoc の追記を化けさせている（そのときの記録は作業者の memory にあり、ロケールを C 相当と書いていたが、上の確かめでは C では起きない）。heredoc ではなくテストの中の文字列だったので、当てはまると思わずに書いた。

## なぜ非自明か

**行を読んでも誤りに見えない。** `$eq_sync_want）` は、人が読めば変数と括弧の区切りが明らかで、shellcheck も警告を出さなかった。起きるかどうかは実行時のロケールで決まり、書いた本人の端末で再現しないこともある。

## 行動をどう変えるか

**日本語の文の中で変数を展開するときは、位置を問わず `${var}` で囲む。** とくに直後に `）`・`」`・`、`・`。` などが来る位置で起きる。書き終えたら上の grep を当てる。`set -u` は止まる側に倒すので、残しておく。
