**`claude -p` をスクリプトやループの中から起動するときは、標準入力を `</dev/null` にする。** 依頼文は引数だけで渡す。

#467 で `runbook-authoring` の発火を測るとき、10個の依頼文をファイルに1行ずつ書き、`while IFS=$'\t' read -r id prompt; do claude -p "${prompt}" … ; done < prompts.tsv` の形で順に起動した。10回とも終了コード 0 で返ったが、1回目（D0）の返答が「一緒に送られた9行の依頼の一覧について、どう扱うかの指示はありませんでした」と書き、残りの9行を表にしていた。ループの中の `claude -p` が、ループの標準入力（まだ読んでいない依頼文の行）を読み、依頼文に足していた。陽性と陰性の回の返答にも同じ印があり、その回の結果はすべて捨てた。`claude -p … < /dev/null` にして測り直すと、どの返答にも混ざった行は出なかった。

## なぜ非自明か

**引数で依頼文を渡しているので、標準入力は使われないと考えやすい。** 実際には、`claude -p` は標準入力が端末でなければそれも読む。ループの中のコマンドがループの標準入力を食う形は、`ssh` などでも知られたシェルの罠だが、`claude -p` は食った行を依頼文に足して返答するので、エラーにも空の結果にもならない。返答は依頼に応じた自然な形で、終了コードも 0 なので、結果の表だけを見ても汚れたことは分からない。今回は、返答の本文が「一緒に送られた」行に触れたので気づけた。

## 行動をどう変えるか

**`claude -p` をスクリプト・ループ・背景の処理から起動するときは、`</dev/null` を付ける。** 発火を測る足場（`--add-dir` の一時ディレクトリなど）を作るときは、1回目の返答の本文に、渡していない依頼が混ざっていないかを読んで確かめる。
