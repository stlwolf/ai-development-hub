**利用者の key をつないで別の識別子を作るときは、key に使えない文字で区切るか、作ったすべての識別子とほかの key の重なりを検査する。** 「今は1種類しか作らない」「1ページに1つしか置かない」ことに頼った作り方は、2種類目を足したときや部品を混ぜたときに、黙って衝突する。

#536 で `html-one-pager` の一覧から選ぶ問いを、ほかの問いと同じページに置けるようにしたとき、同じ形の衝突を2回作った。1回目は保存先で、一覧の行の答えの doc id を `<カードの key>--<番号の数字>` にしていた（#478 で決めた形）。カードの key は `-` を含められるので、選び方のカード `tools` の候補1 と、別のカード `tools--1` が同じ文書に書く。一覧から選ぶページにはカードが1枚しかなかったので、今まで起こりようがなかった。設計のセカンドオピニオンが見つけた。2回目は画面の要素の id で、答えたカードを畳む表示に、開閉の要素 `hp-fold-<key>` と答えの行 `hp-fold-ans-<key>` を足した。key が `ans-x` のカードの開閉の要素と、key が `x` のカードの答えの行が同じ id になり、JS がその id に文字を書くと開閉の要素の中身（選択肢と補足欄）が消える。1回目の直しを入れたあとなのに同じ形を作り、実装のセカンドオピニオンが見つけた。どちらも、検査と見本は普通の key しか使っていないので通っていた。

## なぜ非自明か

**作り方を足す人は、新しい識別子が今ある識別子と衝突しないかを、今ある key の集まりで考える。** 見本の key（`retry_policy`・`pick_tools`）どうしは衝突しないので、作り方の衝突は見えない。衝突は「ある key の前置きや後置きが、別の key と同じ文字列になる」ときだけ起き、見本にはそういう組み合わせが無い。しかも、その識別子の作り方は前の単位で決めて検査も通っていたので、混ぜる直しのときに見直す対象から外れやすい。同じ単位の中で1回直したあとでも、別の種類の識別子では同じ形を作った。

## 行動をどう変えるか

- 識別子を key からつないで作るときは、区切りに key の形の検査が許さない文字を使う（例: key が `[a-z0-9_-]` なら `.`）。今ある作り方（`hp-opt-<key>.<選択肢>`）がそうなっていれば、それに合わせる。
- 区切りを変えられない（保存の形のように後から変えられない）ときは、作ったすべての識別子と、ほかの key の重なりを検査で止める。
- 検査には、片方の key がもう片方の前置き・後置きを含む組（`x` と `ans-x`、`tools` と `tools--1`）を、両方の順で入れる。
