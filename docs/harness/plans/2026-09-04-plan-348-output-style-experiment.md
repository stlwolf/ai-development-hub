# plan — #348 段階2 の実験設計（v2）

## 0. 基準線と対照

- **基準線 = owner の主モデル Opus 5 × Claude Code 2.1.258 × 会話面（main conversation）**。この面の応答が読みづらい、という owner の観測が出発点である。
- **対照 = Fable 5.1**。統括セッションのモデルであり、基準線ではない。v2 では判別の主軸から降ろし、補助観察に置く（理由は §6.4）。
- 本計画を書いた委譲子は Opus 5（`claude-opus-5[1m]`）で動いており、CLI は `2.1.259`。基準線の 2.1.258 との差は本件の機構に効かない（組込み `Concise` は 2.1.237 で入っている）。
- 対象ツールは Claude Code だけである。output style は Claude Code の機能なので、Cursor と Codex への配布は本件の範囲に入らない。
- 対象の面は**端末に描かれる main conversation の応答**である。artifact・brief・board・issue コメント・SO の出力は対象外。output style は subagent には効かないので、agent 間のチャネルは機構としても対象外になる。

## 1. 段階1で確かめた計測器（結論だけ再掲）

判定は3値のうち**乗る**。詳細は episode の「Q-1 の計測結果」節にある。

- `--settings '{"outputStyle":"<name>"}'` は headless で効く。project 置き場・user 置き場・組込み `Concise` の3経路とも解決した。
- 乗った位置は system prompt の中で、`# Environment` と `# Context management` の**間**に `# Output Style: <name>` として入る。
- rules と CLAUDE.md は system prompt ではなく user ターンの `<system-reminder>` として届く。output style と rules は**層が違う**。
- 確認できていないのは、対話セッションでも同じ位置に乗るかである。§7 の owner 手順で埋める。

## 2. gate 2 の指摘で前倒しした前提確認（実施済み・結果は前提が2つとも誤りだった）

設計SO の3レーンが「判別の土台が一次未確認だ」と揃って指摘したので、run を投じる前に2件を確かめた。どちらも私の前提が外れた。

### 2.1 組込み `Concise` は短さだけの指示ではない

`Concise` を有効にした headless セッションに、その節の要旨を出させた。実際には次を持っている。

- 「最初の一文で答えに答えよ」という**順序の指示**。
- 「見出し・表・箇条書きは本当に構造があるときだけ使え。既定は平文」という**文体の指示**。
- 「断定的に平明に書け。ヘッジの定型句を省け」という文体の指示。
- 「短さのために正確さを犠牲にしない。エラー・失敗したテスト出力・セキュリティ警告・破壊的操作の確認は削らない」という例外規定。
- **「他の箇所の書式指針と衝突した場合、この節を優先する」という宣言。**

帰結を3つ書く。

- v1 の期待値「`Concise` は接着記号と体言止めが減らない、むしろ増える」は**撤回する**。根拠が無かった。
- `Concise` は「長さ専用の対照」には使えない。長さと順序と文体を同時に動かしている。
- `Concise` は自作 style の**有力な競合**である。自作の差分価値は、`Concise` が触れていない層、すなわち `output-format-rule` §8 の日本語レジスタ（記号を文法の代わりにしない・体言止めをしない・修飾語を日本語で書く・英語 + する の形にしない）に絞られる。

### 2.2 長版 system prompt に書き方の契約は在る。ただし名前が違う

`CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0` で Opus 5 を起動し、H1 を列挙させた。18 行あり、**`# Tone and style`** と **`# Text output (does not apply to tool calls)`** が在った。`Writing for the user` という名前ではない。

- 判別条件の土台は**成立する**。長版に書き方の契約が実在する。
- 一緒に戻る節も列挙できたので、交絡が「無限定」から「列挙済み」になった。lean に無くて長版に在るのは `System` / `Doing tasks` / `Executing actions with care` / `Using your tools` / `Tone and style` / `Text output` / `auto memory`（小見出し6つ込み）である。`Delivering work` と `Corrections` は両方に在る。
- 教訓として episode に印を置いた。契約は**名前でなく機能で探す**。`Writing for the user` が無いことを「契約が無い」と読むと外す。

## 3. Phase 0（go / no-go ゲート・run 4本）

本 plan が承認されたら、段階2a の 45 run を投じる前にこれを済ませる。ここで no-go なら設計を組み直す。

- **P0-3 病理の再現確認（陽性対照）**: owner が実際に読みづらいと言ったターンを対話の履歴から1つ取り、同じ入力を headless に流す。前置き・実況・記号圧縮・体言止めが baseline に**出るか**を見る。
  - 出なければ、headless 固定を**捨てる**。全指標が床に張り付いて何も測れない状態になるので、対話セッションでの収集に切り替える。
  - これは投機ではなく既知の失敗型である。`docs/research/2026-07-16-register-portability-eval.md` の段階1が、内容プローブが原文で既に全て通ってしまい「文体の寄与を測れなかった」と記録している。同じ形の天井・床を今回も踏みうる。
- **P0-4 経路の生存確認（陽性対照）**: 確実に効くはずの極端な style（応答の上限を 200 文字にする、など）を1本作って走らせ、生成が実際に動くことを見る。効かないという結果が出たとき、モデルの問題か経路の問題かを切り分けるために要る。
- run は P0-3 が2本（baseline を2回）、P0-4 が2本（極端 style と対照）で計4本。

## 4. 段階2a（採用の可否だけを見る・Opus 5 に固定）

### 4.1 条件（5値）

すべて Opus 5 に固定する。`keep-coding-instructions: true` を自作系の style すべてに付けて統制する。

| # | 条件 | 何を切り分けるか |
|---|---|---|
| C0 | style なし | baseline |
| C1 | 自作 `readable-conversation`（§5 の案） | 採用候補そのもの |
| C2 | **既存ルール逐語コピー style**（`output-format-rule` §8 §9 をそのまま style ファイルに置く） | **層が効くのか、文言が効くのか**。逐語コピーで同じ改善が出るなら、必要なのは新しい文言ではなく置き場の変更だけになり、自作 style を書く作業が要らなくなる |
| C3 | 自作 style と同じ文面を、**style ではなく user ターンの先頭**に置く | **層効果と反復効果の切り分け**。system prompt 層だから効いたのか、同じ指示が2回来て強度が上がっただけなのか |
| C4 | 組込み `Concise` | §2.1 のとおり有力な競合。これが1位なら配布物が要らない |

C2 と C3 は gate 2 の3レーンが揃って「最も安く最も決定的なのに先送りされている」と指摘した条件である。v1 では follow-up に置いていたのを、コアへ引き上げた。

### 4.2 プロンプト（3題・owner の実履歴から採る）

v1 は自作の一問一答2題だったが、これでは owner の不満の対象と場面が違う。**実際に読みづらいと言われたターンを含む3題**にする。

- **Q1 事実回答**: 一意の短答がある問い。正解文字列で機械判定できるもの。
- **Q2 設計相談**: 短答が無く自由文が伸びるもの。順序の問題が一番出る。
- **Q3 ツール実行を挟む調査報告**: **実況と前置きが出る唯一の場面**。v1 はツールを使わない題しか置いておらず、自作 style の「実況を書かない」条項が原理的に測れなかった。

### 4.3 反復と実行の統制

- 各条件・各題を**3回**繰り返す。5 × 3 × 3 = **45 run**。並列4本で流せば10分前後で終わる。
- v1 の2反復は捨てる。2観測の差はばらつきの推定にならないという指摘（3レーンのうち2レーン）を受け入れた。モデル軸（Fable 5.1）を段階2a から落として、その予算を反復に回している。
- **条件の実行順を無作為化する**。固定順だと時刻・負荷・バックエンド更新が条件差に混ざる。
- 各 run で次を記録する: 実行時刻 / CLI 版 / 解決されたモデル ID / system prompt の H1 集合のハッシュ / 乱数シード。

### 4.4 観測量

v1 の指標は3レーンすべてから「互いに独立でない」「構成概念を捉えていない」と指摘された。次のように直す。

**正規化する（相関を切る）**

- 記号と体言止めは **1,000 文字あたりの数**で数える。生カウントだと総文字数が減れば自動的に減り、「2軸以上で改善」が実質1軸（長さ）になる。

**散文だけを対象にする**

- 体言止めの判定から、**箇条書き行・見出し行・引用行・表の行を除外する**。日本語の箇条書きが名詞で終わるのは正常であり、レジスタの悪さではない。除外しないと体言止め指標が箇条書きの量の従属変数になる。
- **表の行数も数える**。散文を表に置き換えただけで「文字数が減って記号も減った」ように見えるのを検出するため。

**3軸すべてに指標を割り当てる**

| 軸 | 指標 | 数え方 |
|---|---|---|
| 内容選択 | 必須要素の欠落数 | 各題に**事前定義した必須要素リスト**（3〜5項目）を置き、応答に含まれるかを数える。これが v1 の「T1 の正誤」の置き換えである |
| 内容選択 | 総文字数 | 単独では採用判断に使わない（両仮説が同じ向きを予測するので判別力が無い） |
| 内容選択 | 代替案の数 | 見出しと箇条書きの塊の数。Q2 では少ないほど良いとは限らないので、方向づけせず記録だけする |
| **順序** | **第1文の型**（結論 / 前置き / 問題の言い換え / 計画の宣言 の4値） | Q2 と Q3 に適用する。v1 は順序を Q1 でしか測っておらず、**問題が一番出る場所で測っていなかった**。判定は固定 rubric で機械的に試み、判定できないものだけ owner に回す |
| 順序 | 先頭短答率 | Q1 のみ。正解文字列が先頭 120 文字以内に出るか |
| 表面の癖 | 接着記号の密度 | `→` `＝` `・` `★` `〔` `〕` を 1,000 文字あたりで数える。**`・` は日本語の通常表記でも使うので偽陽性が出る**。`・` だけ別カウントにして、他の記号と混ぜない |
| 表面の癖 | 体言止めの密度 | 散文の文だけを対象に 1,000 文字あたりで数える |
| 表面の癖 | **英語の修飾語の数** | `output-format-rule` §8 が主な可読性の問題だと名指ししているのに、v1 に指標が無かった。日本語文中の ASCII 英単語を数え、作業対象の名前（`git`・`PR`・`hook`・`oe-*` など）の allowlist を引く |
| 表面の癖 | 見出し数・箇条書き行数 | 方向づけせず記録だけする。既存ルールは通常の見出しと箇条書きを許容しているので、増減だけでは良し悪しを言えない |

### 4.5 owner の読み評価（従属的に使う）

- 提示物: Q1〜Q3 それぞれについて、5条件の応答を**条件を伏せて**順序を無作為にして並べる。反復のうちどれを見せるかは乱数で決め、選択バイアスを入れない。
- 設問（固定）: 一読で判断できたか / 必要な情報が欠けていたか / 不要な部分があったか / 結論がどこにあったか。
- **この評価は拒否権を持たない**（§8 参照）。v1 は「決定的な判定には使わない」と書きながら採用基準の AND 条件に入れていて、内部で矛盾していた。

### 4.6 統制しきれない残差（明記する）

- `Concise` 側の `keep-coding-instructions` 相当の設定は分からない。C4 だけこの変数が揃わない。
- thinking の有無と予算は条件間で固定するが、`effortLevel` の効き方までは追えない。
- 条件を伏せても、長さと記号の癖から条件を推測できる。盲検は完全ではない。

## 5. 自作 style の案（v2・`Concise` との差分に絞る）

§2.1 で `Concise` が順序と文体を既に持つと分かったので、自作の意味は **`Concise` が触れていない日本語のレジスタ**に絞られる。したがって自作 style は「`Concise` 相当 + `output-format-rule` §8」という形にする。

```markdown
---
name: readable-conversation
description: 会話面の応答を、operator が一読で分かる日本語の散文にする
keep-coding-instructions: true
---

# 会話面の書き方

この指示は、端末に描かれる会話の応答にだけ適用する。

## 順序

- 結論を最初の1文に置く。前置き・実況・これから何をするかの予告は書かない。
- 導出・調べた過程・検討した代替案は、結論と根拠の後ろに置く。

## 量

- 依頼に答えるのに要らないものを出さない。案を並べず、推奨を1つ述べる。
- 同じことを言い換えて繰り返さない。
- ただし短さのために正確さを削らない。エラーの本文・失敗したテストの出力・破壊的操作の確認は削らない。

## 日本語のレジスタ

- 完全な文で書く。体言止めで文を終えない。
- 記号を文法の代わりに使わない。`→` `＝` `・` `★` `〔〕` を接続や述語の代用にしない。
- 括弧の入れ子で主節を埋めない。1つの文に1つの主題だけを置く。
- 説明や修飾の語は日本語で書く。作業対象の名前（`git`・`PR`・`hook` など）は英語のままでよい。
- 英語に「する」「させる」を付けた形にしない。

## 例外

- コード・コマンド・ファイルパス・表・箇条書きは、これまでどおり使ってよい。禁じているのは、記号が文法の代わりをすることだけである。
```

- **`Concise` が持つ「衝突したらこの節を優先する」宣言は、意図的に入れない。** 既存 rules を殺したくないからである。ただし「宣言が無いと効かない」可能性があるので、宣言を入れた版との比較は段階2b に置く。
- **入れなかったもの**: `output-format-rule` §5（関連リンク）・§6（URL の形）・§7（絶対パス）。会話面だけでなく PR 本文や issue にも効く規則なので、会話面に閉じた style には入れない。

## 6. 判別実験（段階2b・段階2a で効果が出たときだけ走らせる）

### 6.1 2つの仮説

- **H-lean（契約が消えた説）**: lean 既定化で本体から書き方の契約が落ちた。Opus 5 の lean には `Tone and style` も `Text output` も無く、長版には在る（§2.2 の実測）。
- **H-rlhf（長さバイアス説）**: 主因は preference-tuning の副作用で、重み側にある。

排他ではない。判別の目的は寄与の向きを見ることであって、どちらか一方を選ぶことではない。

### 6.2 条件

- **2×2**: 簡易版 / 長版 × style なし / 自作 style。v1 は長版 × style なししか置いておらず、交互作用が見えなかった。
- **契約節そのものの注入**: 長版の `Tone and style` に当たる指示だけを style として Opus 5 に注入する。同一モデル内・単一因子で契約の有無を動かせるので、**判別の主軸はこれにする**。長版条件は交絡が列挙済みとはいえ7節を一緒に動かすので、従にする。
- **長さを統制した比較**: 同程度の文字数に揃えたときに接着記号と体言止めに差が残るか。これが無いと「style の改善はすべて長さの減少で説明できる」という対抗仮説を切れない。

### 6.3 読み方

| 観測 | 読み |
|---|---|
| 契約節だけの注入で、自作 style と同程度に改善する | H-lean を支持する。必要なのは契約であって新しい文言ではない |
| 契約節だけでは改善せず、自作 style で改善する | 契約の文面では足りず、明示の指示が要る |
| 長さを揃えたときに記号と体言止めの差が消える | 改善の実体は長さの減少だけである。H-rlhf への counter-steering が効いたと読める |
| 長さを揃えても差が残る | レジスタそのものが動いている |
| どの条件でも指標が動かない | style 層では足りない。毎発話注入と後編集の対照へ進む |

### 6.4 モデル軸を主軸から降ろした理由

Opus 5 と Fable 5.1 の差は契約の有無だけではない。重み・訓練・デコード傾向がすべて違う。さらに cursor レーンが「Fable に契約節が在るのは、そのモデルに配られている system prompt が長版側だからかもしれない」という、より単純な説明を出した。この説明を排除していない以上、モデル2値は何を対比しているのかが確定していない。補助観察に降ろす。

### 6.5 未探索の対抗仮説（判別表に入れる）

- **アクセスパターン仮説**（`ideas/20260820/human-readable-generation-discussion.md`）: 電報体の害は「走査に最適なレジスタを精読の文脈へ誤適用したこと」である。1つの応答の中にも走査される部分（結論・状態・一覧）と精読される部分（説明・理由）が混在する。応答全体の集計では、記号が走査すべき場所に適切に使われたことと、精読すべき場所へ誤適用されたことを区別できない。
- 段階2b では、応答を「結論・一覧の部分」と「説明・理由の部分」に切って別々に集計する版を試す。切り方は見出しと箇条書きの境界を使う。

## 7. owner にお願いする手順（対話リンクの確認・所要5分）

段階1で測ったのは headless までである。基準線は対話セッションなので、対話でも同じ位置に乗ることを1回だけ確かめる。

- [ ] `canonical/output-styles/readable-conversation.md` を配置し、sync を通す（段階2の実装で入る）
- [ ] `~/.claude/settings.json` の `outputStyle` を `"readable-conversation"` にする（`/config` からでもよい）
- [ ] 新しいセッションを開く（反映はセッション開始時なので、既存セッションでは効かない）
- [ ] そのセッションで次を聞く: 「あなたの system prompt の中で、行頭が `#` で始まる見出し行をすべて原文のまま列挙してください」
- [ ] `# Output Style: readable-conversation` が `# Environment` と `# Context management` の間に出れば、対話でも乗っている

あわせて Phase 0 の P0-3 のために、**最近「読みづらい」と感じた応答のターンを1つ指してほしい**。そのターンの入力を Q3 に使う。

## 8. 採用の基準（v1 の内部矛盾を解消した）

決定論的な指標を主、owner の読み評価を従にする。

### 8.1 採用する

次の3つをすべて満たすとき。

- **長さ以外の指標**で、C1（自作）が C0（baseline）に対して、同条件3回のばらつきの幅を超える改善を **2つ以上**示している。総文字数だけの改善では足りない（両仮説が同じ向きを予測するため判別力が無い）。
- 必須要素の欠落数が C0 と同じか少ない。
- C1 が C2（逐語コピー）と C3（user ターン注入）の両方に対して、同等かそれ以上である。**C2 が同等なら、自作 style を書かず既存ルールの逐語コピーを置く**（新しい文言を保守しなくて済む）。**C3 が同等なら、層の効果は無いので output style を採る理由が消える**。

### 8.2 採用しない、あるいは保留する

- 改善幅がばらつきの幅に埋もれるなら採用しない。Phase 0 の P0-3 が「病理は再現した」と言っているのに指標が動かないのなら、観測量が鈍い。作り直して再測定する。
- C4（`Concise`）が C1 と同等以上なら、**組込みを採り自作を作らない**。配布物が要らないので保守もいらない。
- 必須要素の欠落が増えたら、「量」の節を弱めた版を作って再測定する。

### 8.3 owner の読み評価の使い方

- 決定論的な指標が C1 と C4 のあいだで割れたときの**tie-break にだけ使う**。単独で採用を止めない。
- v1 は「決定的な判定には使わない」と書きながら AND 条件に入れていた。この矛盾を解消した。

## 9. 採用したときの配置

- 正本は `canonical/output-styles/readable-conversation.md` に置く。`canonical/` 直下に新しい木を作るので、`canonical/CATALOG.md` にも1行足す。
- 配布は `scripts/sync/sync-claude.sh` に1経路足して `~/.claude/output-styles/` へ配る。**user 置き場を採る**理由は、会話面のレジスタを repo ごとに変える理由が無く、hub でだけ効く style では dogfooding にならないからである。
- 有効化（`~/.claude/settings.json` の `outputStyle`）は **sync では触らない**。設定値の書き換えは配備物の範囲を超えるので、owner の手に残す。README か CATALOG に1行の手順を書く。
- `scripts/sync/sync-cursor.sh` と `scripts/sync/sync-codex.sh` は触らない。
- 段階2 は docs の PR（結果ノート）と code の PR（style + sync 経路）に分ける。

## 10. 判断してほしい点

| # | 論点 | 推奨 | 理由 |
|---|---|---|---|
| 1 | 組込み `Concise` を先に単体で試すか、自作と同時に条件へ入れるか | **同時に入れる** | §2.1 で `Concise` が順序と文体を既に持つと分かった。単なる対照ではなく**有力な競合**なので、同じ土俵で比べないと「自作を作る必要があるか」に答えられない |
| 2 | 観測を headless で済ませるか、対話を1回入れるか | **決定論的な観測は headless、読み評価だけ対話で1回**。ただし Phase 0 の P0-3 で病理が headless に出なければ headless 固定を捨てる | headless は条件を固定できて反復が安い。ただし「測りたい病理がそこで起きるか」は先に確かめる必要がある |
| 3 | 採用時の置き場と sync 経路 | **user 置き場**。正本は `canonical/output-styles/`、配布は `sync-claude.sh`、有効化は owner の手 | §9 のとおり |
| 4 | UserPromptSubmit 注入との比較を本アークに入れるか | **段階2a には入れず、段階2b の条件付き分岐に置く**（v1 の「follow-up にする」から一段引き上げた） | 3レーンのうち cursor が「外部3例が独立にこの層へ移っている。style が効かなかったとき『レジスタは制御できない』のか『この層では届かない』のかを区別できない」と指摘した。ただし段階2a で効果が出れば不要なので、条件付きにする。#307 段階2 との重なりは、発火したときに統括が順番を裁定する |
| 5 | **（新）Phase 0 の P0-3 が no-go だったときどうするか** | **対話セッションでの収集に切り替える。段階2a を止めて設計を組み直す** | headless で病理が再現しないなら、そこで測っても「効かない」と「測れない」が区別できない。先行実測（`register-portability-eval.md` 段階1）が同型の失敗を記録している |

## 11. follow-up（本アークでは扱わない）

## 12. 段階2 の step 案

- **R-0** Phase 0（4 run）。病理の再現と経路の生存を確かめる。**no-go ならここで止めて設計を組み直す。**
