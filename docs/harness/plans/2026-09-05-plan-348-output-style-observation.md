# plan — #348 段階2（v3・実運用の前後比較）

## 0. 基準線と対照

- **基準線 = owner の主モデル Opus 5 × 会話面（main conversation）**。対象ツールは Claude Code だけである。
- 対象の面は**端末に描かれる owner 宛の応答**である。artifact・brief・board・issue コメント・SO の出力・委譲子への指示は対象外。output style は subagent に効かないので、agent 間のチャネルは機構としても対象外になる。
- v2 で対照に置いていた Fable 5.1 は、**判別の軸から降ろす**。R-0 の実測で、Fable 5.1 の体言止め率が Opus 5 より高く、v2 の期待（本体に書き方の契約があるので読みやすいはず）と逆を向いたためである。母集団には混じるので、モデル別の内訳は記録だけする。

## 1. v2 を破棄した理由（R-0 の結果・確定済み）

- **P0-4（経路の生存）= go**。極端な style で応答が 4,363 文字から 80 文字になった。output style は system prompt に乗るだけでなく生成を動かす。
- **P0-3（病理の再現）= no-go**。合成した題を fresh な headless で 12 本走らせたが、`output-format-rule` §9 が名指しする病理（接着記号・体言止め）はほとんど出なかった。user 層の rules を落とした条件でも出ない。
- **病理は実在する**。owner が「分かりづらい」と言った応答2件を実測すると、母集団の裾に入る。合成 run では再現しないだけである。この確認をせずに 45 run を投じていたら、全条件で 0 が並び「output style はレジスタに効かない」という誤った結論が出ていた。
- **合成 run には隔離の問題もあった**。題と style を被験セッションの cwd に置いていたため、モデルが題を作業層のファイルとして見つけて、それについて答えた run が出た。v2 の 45 run はすべて同じ露出を持っていた。

## 2. 案A の設計 — 実運用の前後比較

owner の環境で style を有効にし、普段どおり使う。有効化の前後の実セッションを同じ指標で比べる。**合成 run を投じない。**

### 2.1 なぜこの形か

- 「前」の腕は**すでに測り終わっている**（§4）。追加の生成コストは 0 である。
- regime が実運用そのものなので、R-0 で起きた「病理がこの regime に無い」という問題が原理的に起きない。
- 実運用のセッションは実験の fixture を持たないので、隔離の作り込みが要らない。
- n が数百になるので、v2 で悩んでいた反復数とばらつきの問題が消える。

弱みは**交絡**である。時期と作業内容が style の有無と一緒に動く。§2.4 と §2.5 で抑える。

### 2.2 母集団の絞り（前後の腕に同じ規則を当てる）

対象は **owner が直接やり取りしたセッションの、owner 宛 main conversation の応答**である。判定は JSONL の転記に対して機械的に行う（規則は `tmp/348-runs/corpus.py` に実装済み）。

除外は3種類ある。判定はセッションの**最初の実質的な user 発話**で行う。

| 除外 | 判定 | 理由 |
|---|---|---|
| 委譲子セッション | 最初の user 発話が `.oe/brief-` を含む | 読者が親であって owner ではない |
| agent 間のレーン | 最初の user 発話が「独立した反証エージェント」「adversarial verifier」「# 設計SO」「ゼロベース代替探索」「純粋セカンドオピニオン」「独立した読解と反論」のいずれかを含む | SO レーンは agent 間の面 |
| 計測 probe | 最初の user 発話が計測用の定型（`N+N の答えだけ`・`行頭が # で始まる見出し行`・`Concise Style Active` ほか）を含む | 実験装置であって会話ではない |

応答の側では、**subagent の応答（`isSidechain`）を除く**。400 文字未満は短答の層に分けて主指標の対象から外す。

**fork 由来のセッションを除く**（HG-2 裁定3）。R-1'' の対比は `--fork-session` で新しいセッション ID を作るので、その ID の一覧を作業層に残し、「後」の腕から ID で除外する。除外しないと、実験のために作った応答が観測の母集団に混じる。

**含めるもの**: 親から `oe-send` で届いた子の報告を受けて owner 宛に出した応答は**含める**。これは owner の端末に描かれる応答であり、実例1 がまさにこの形だった。

### 2.3 層別（記述のみ・ゲートには使わない）

**v3.0 の層別は取り下げた。** 応答の中身（「判断してほしい」等を含むか）で切っていたが、**それは介入後の変数**である。style は応答の中身を変えるので、層の割り当てそのものが style で動く。設計SO の3レーンが揃って指摘した。

介入前の変数（直前の owner 発話）で切り直したところ、**158 件のうち 131 件が「その他」に落ちた**。owner の発話から何ターンも離れた応答が多いためである。層が薄くなると疑似反復（下記）が悪化するので、**層別はゲートから外し、記述として報告するだけにする**。

- 判定は直前の owner 発話に対して行う（介入前）。A 判断要求 13 件 / B 調査報告 14 件 / D その他 131 件。
- 400 文字未満は短答として主指標の対象から外す（これは介入前後で同じ規則）。

### 2.3.1 集計の単位はセッションにする（疑似反復への対処）

158 応答は **9 セッション**から来ている。同じセッション内の応答は独立ではないので、応答を 158 個の独立な観測として扱うと有意性を過大に見積もる。設計SO の3レーンが揃って指摘した。

- **主の集計単位はセッション**にする。各セッションについてフラグ率（§3.1）を出し、セッション間で「前」と「後」を比べる。
- 応答単位の集計は補助として併記する。
- **検出力の限界を先に書く**: 「前」が 9 セッション、「後」も同程度なら、検出できるのは大きな差だけである。小さな差は「差が無い」ではなく「この n では判定できない」と書く。

### 2.4 交絡の記録

**有効化の日時（前後を切る点）**: 2026-09-05 21:05:39 JST = **2026-09-05T12:05:39Z**。この時刻より後に開始されたセッションの応答が「後」の腕である。転記の `timestamp` は UTC なので、UTC で切る。

**style を直した時刻（第2の切る点）**: 2026-09-05T16:31:20Z（= 2026-09-06 01:31:20 JST）。HG-3 裁定4 の1行を「送る前に消すもの」に足した。腕を3つに分ける。

| 腕 | 範囲（セッションの開始時刻） | 扱い |
|---|---|---|
| 前 | 2026-09-05T12:05:39Z より前 | 基準 |
| 後 v1 | 12:05:39Z 以後・16:31:20Z より前 | **参考**。この間に始まったセッションは 3 本しかない |
| 後 v2 | 16:31:20Z 以後 | **主たる比較の相手** |

主たる比較は **前 対 後 v2** である。

**中継の経路（交絡であり、機構の外にある）**: 実例4 で、統括が子（本委譲子）の報告に使われた圧縮した語（収集窓 / keep-coding-instructions の観察2件 / 合図）を、そのまま owner への応答に使った。owner はそれを「理解しづらい」と返した。output style はセッションごとの main conversation に効くので、統括のセッションが style の下で再起動されれば、統括の応答は「後」の腕に入る。しかし**語彙と構成の素材は子が供給している**。style は書き方を変えるが、渡された素材は変えない。したがって「後」の腕に、子の圧縮したレジスタ由来の読みづらさが残りうる。これは style の効果を**過小に**見せる方向の交絡である。結果ノートに明記する。

**セッションを腕に振り分けるときは、project local の `outputStyle` も確認する。** 設定の優先順位は managed > コマンドライン > project local（`.claude/settings.local.json`）> project 共有 > user である。有効化は user 層で行ったので、project local に `outputStyle` が書かれると user 層を上書きする。`/config` の Output style 選択は **project local に書き込む**ので、owner が `/config` から選び直すと、そのリポジトリだけ別の style（あるいは none）になりうる。**その状態で始まったセッションは「後」の腕ではない。** 集計の時点で、hub と対象リポジトリの `.claude/settings.local.json` を見て `outputStyle` の有無を記録する。

2026-09-06 時点の実測では、hub の `.claude/settings.local.json` に `outputStyle` のキーは無く、worktree 側には file 自体が無い。user 層の設定が効いている。

有効化は `~/.claude/settings.json` の `outputStyle` を `"readable-conversation"` にする形で行われた（統括が owner の依頼で実施・バックアップ `settings.json.bak.20260905-210539` 有り・他のキーは不変であることを差分で確認）。**子が独立に有効化を確認した**（新しいセッションに `--settings` を渡さず H1 を列挙させ、`# Output Style: readable-conversation` と style 本文の H1 が `# Environment` の後に乗っていることを確認）。

各応答に次を紐づけて記録する。

- 応答の日時 / セッション ID の先頭8桁 / 応答がセッションの何番目か
- 解決されたモデル ID / Claude Code の版
- style の有効・無効（有効化の日時で切る）
- 層（A / B / C）

### 2.5 収集期間

**owner 宛の応答が 100 件を超えるか、5 営業日が経つか、どちらか早い方**を提案する。「前」の腕が 158 件（§4）なので、同じ桁の n が揃う。期間中は子は待機し、**統括が「収集窓を閉じた」と送ったら R-2 へ進む**。

## 3. 観測量（v3）

R-0 と実例1・実例3 の実測で決めた。**v2 の観測量からは大きく変わっている。**

| 層 | 指標 | 根拠（owner 宛 158 件の中の順位） |
|---|---|---|
| **主1** | **強調記号の密度**（`⚠ ❗ ‼ ★ 🔴 🚨 ✅ ❌`。接着記号とは別に数える） | 実例1・実例3 とも**順位 100%**。母集団は中央値も p90 も 0 で、1個以上を含む応答は **0.6%** しかない。唯一、両方に一貫する signal |
| **主2** | **内部語の数と種類数**（環境固有の一覧・増やせる形で持つ） | 実例3 で種類数 98.7%。owner が「この語の意味が分からない」と名指しで書いたのと直接対応する（対象の語は外部ツールの出力用語で、作業層にのみ記録）。判断要求の層で効く |
| 従 | 文の数 | 実例1 96.8% / 実例3 81.0% |
| 従 | 英語語の密度 | 実例1 98.1% / 実例3 94.9%。ただし題材の領域で値が動く交絡がある |
| 従 | 使役（〜させます）の数 | 実例3 で 100%。判断要求の層に固有 |
| **降格** | 文字数 | 実例1 は 93.0% だが**実例3 は 57.0%（ほぼ中央値）**。単独では主指標にできない。文の数の方が効く |
| 見張り | 接着記号 `→＝★〔〕`・体言止め・英語 + する | 実例1・実例3 のどちらでも裾に入らない（0% / 63.9% / 0%）。**悪化しないことだけ**見る |
| 構造 | 見出し密度・構造行の数・散文の割合 | JSONL からのみ測れる（§6）。案A は JSONL を読むので測れる |
| 未実装 | 質問への直答が先頭に在るか / 比喩と造語 / 前提の再掲の有無 | 機械判定が立たない。owner の読み評価に回す（§9） |

**内部語の拡張リストは参考列に置く（HG-3 裁定1）。** 実例4 は凍結したリストで種類数 0 になり、フラグが1つも立たなかった。実例4 の語（収集窓 / keep-coding-instructions / 観察2件 / 合図 ほか）で広げた拡張リストなら種類数 6 になり、母集団の p90（3）を超える。ただし**判定に使うリストは凍結のまま動かさない**。指摘された文から語を拾って足すと、その文に合わせた物差しになるからである。拡張リストは前後の両方に同じものを当て、**採用ゲートには使わず別列として報告する**。拡張リストでの母集団の分布は、種類数の中央値 1.0・p90 3.0 だった。

**廃止**: 英語語の総数（生カウント）。名前と修飾語を分けられず題材で値が動く。§8 の観点は「英語 + する」で代表させる。

### 3.1 複合フラグ（採用ゲートの単位・閾値をここで凍結する）

**v3.0 の「主指標の中央値と p90 が下がる」というゲートは算術的に成立しなかった。** 主1（強調記号）は母集団の中央値も p90 も 0 なので、下がりようがない。設計SO の3レーンが揃って指摘した。`i-have-adhd` の blocker ゲートの罠を見張り指標では避けたのに、主指標で同じ形の床を作っていた。

床を持たない量に変える。**応答ごとに、事前に決めた閾値を1つでも超えたら「フラグ」を立て、フラグ率を比べる。**

| 軸 | 閾値 | 決め方 |
|---|---|---|
| 強調記号 | 1 個以上 | 母集団に 0.6% しか無いので、1個で異常 |
| 内部語の種類数 | 4 以上 | 母集団 p90 = 3 の外側 |
| 文の数 | 37 以上 | 母集団 p90 |
| 英語語の密度 | 26.52 以上 | 母集団 p90 |

**閾値は 2026-09-05 の HG-2 承認をもって凍結した。** 「後」の腕を見てから動かさない。動かすなら結果ノートに理由と、動かす前後の両方の値を書く。

**過適合の自認**: この軸と閾値は、owner が「分かりづらい」と言った2件と母集団の分布から選んだ。2件への過適合が残る。独立の検証は owner の読み評価（§9）に置く。これは設計SO の指摘（2例から選んだ代理指標への過適合）に対する完全な答えにはならない。

**観測量の集合そのものが仮説である。** v2 で「接着記号」を `→＝★〔〕` と定義した時点で `⚠` は視界の外にあり、実例を母集団の分布に置くまで気付かなかった。既存ルールが列挙している記号をそのまま観測量の定義に使うと、ルールの見落としを一緒に引き継ぐ。結果ノートにこの限界を書く。

## 5. 自作 style（読者モデル形・口頭の報告の規律）

裁定3 に従い、規則の列挙ではなく**読者モデルを先に置いてそこから導く**形にする。

```markdown
---
name: readable-conversation
description: 会話面の応答を、その場にいなかった人への口頭の報告として書く
keep-coding-instructions: true
---

# 読者

読者は、あなたが今やった作業をその場で見ていない人である。
口頭で報告を受けるのと同じ条件で読む。一度聞いて意味が取れなければ、それは伝わっていない。
読み返す前提を置かない。前後を行き来しないと分からない書き方をしない。

この読者から、次のことが導かれる。

## 導かれること

- **答えを最初に言う。** 質問されたなら、その質問への答えが最初の1文である。前置き・実況・これから何をするかの予告は書かない。
- **判断を求めるときは、前提を1〜2文で先に置く。** 読者はその場にいなかったので、何の話かを覚えていない。前提なしの選択肢は選べない。
- **知らない言葉を使わない。** 初めて出す言葉は、その場で1文で説明する。説明できないなら使わない。
- **自分の帳簿を読まない。** 自分の文書がどうなっているか、どの仕組みが動いたか、どの工程を通ったかは、読者の判断に要らない。
- **記号で強調しない。** `⚠` `❗` `★` などを使わない。大事なことは、先に言うか、独立した文にする。
- **比喩と造語を使わない。** その場で通じない言い方は、口頭では聞き返される。
- **長いときだけ区分する。** 短ければ区分は要らない。長いときは、読者の問い（答えは何か / なぜそう言えるか / 次に何が起きるか / 私が決めることは何か）で切る。書き手の物語（調べた順・気付いた順）で切らない。
- **完全な文で書く。** 体言止めで終えない。記号を接続や述語の代わりにしない。

## 破ってよい条件

- 「詳しく説明して」と言われたら、長く書いてよい。短さより要求が優先する。
- 破壊的な操作の確認、エラーの本文、失敗したテストの出力、セキュリティ上の警告は削らない。**正確さと安全がこの規則より上位である。**
- この規則に従うと答えそのものが消えるなら、答えを優先する。
- harness の system prompt と課題の指示は、この規則より上位である。

## 送る前に消すもの

- 前置きの文（「〜します」「まず〜」）と、締めの挨拶。
- 本題と関係ない気付き。書くなら末尾に「別に:」で1回だけ。
- 情報を足していないヘッジ。
- 比喩と慣用句。
- 強調記号。
- 同僚に電話で言わない言い回し。言うかどうかを一文ずつ問い、言わないなら人が言う形に直す。
```

**v2 の style から変えた点**: 「日本語のレジスタ（記号圧縮・体言止め）」を主目的から外した。実例1・実例3 のどちらでも裾に入っていないので、そこを直しても owner の不満は動かない。最後の1項として保持だけする。

**先例から採った点**: 読者モデル形・破ってよい条件・送る前の削除チェックの3つは `i-have-adhd`（star 27,078・MIT）から採った。同 skill の10規則と本 style は5点重なり、重ならない**用語の定義・強調記号の禁止・日本語**の3点が本環境固有の差分である。

## 6. 計測器の制約

転記の経路によって測れる軸が違う。指標を当てる前に、その転記が何を保存しているかを確かめる。

| 経路 | 構造（見出し等） | 長さ | 記号・語彙 |
|---|---|---|---|
| JSONL の転記 | **測れる** | 測れる | 測れる |
| terminal の export | **測れない**（markdown が落ちる・折り返しで単語が行をまたぐ） | 測れる | 測れる |

## 8. 採用の基準

主指標を先に見る。**owner の読み評価は採用に対する拒否権を持つ（HG-3 裁定2・v3.0 から変更した）。**

読み評価で「人が会話で言わない言い回しがあった」が評価対象の**半数以上**なら、決定論指標が改善していても**採用を保留し、style を直して再測する**。拒否権は片側だけである。読み評価が良かったことを理由に、決定論指標が動いていないのに採用することはしない。

変更の理由は実例4 である。凍結した指標は、owner が「理解しづらい」と名指しした 146 字の応答に対して、フラグを1つも立てなかった。**指標が取り逃す型が実在する以上、人の判断に拒否権を持たせないと、取り逃したまま採用しうる。**

### 8.1 採用する

- **セッション単位のフラグ率（§3.1）の中央値が、「前」の 20.0% より下がっている。** あわせて応答単位のフラグ率（前 = 25.9%）も下がっている。
- **セッション間のばらつきを超えている**。「前」の 9 セッションの範囲は 0〜50% と広いので、中央値の差がこの幅に埋もれるなら「この n では判定できない」と書く。
- **見張り指標が「前」より悪化していない**（接着記号・体言止め・英語 + する）。**絶対条件（ゼロ）では書かない。** 比較条件の隣に絶対条件を置くと、改善しても永遠に通らないゲートになる（`i-have-adhd` の著者が自分の評価で記録した失敗）。
- **正確さと安全が落ちていない**。owner の読み評価の1問（§9）と、期間中に「答えが間違っていた」「必要な警告が消えた」という事象が起きていないことで見る。先例の rubric は正確さに 35% の重みを置き、読みやすさ側（簡潔 10% / 行動可能性 20%）より重くしている。

### 8.2 採用しない、あるいは保留する

- 改善が主指標1つに留まるなら保留し、収集期間を延ばす。
- 正確さか安全が落ちたら**採用しない**。style の「量」側の条項を弱めた版を作って測り直す。
- 交絡が説明として残るなら（期間中の作業内容が偏っていた等）、結果ノートにそう書いて保留する。

### 8.3 組込み `Concise` との切り分け

裁定4 に従い、**自作 style を先に入れる**。組込み `Concise` だけで足りるかは、効果が出た後の追加観察で切り分ける。

**予測**: `Concise` は「答えを最初に」と「前置きと実況を省く」を持つが、**強調記号の禁止・用語の定義・読者の問いでの区分は持たない**。さらに「見出し・表・箇条書きは本当に構造があるときだけ使え。既定は平文」は、本 style の「長いときは読者の問いで区分する」と逆を向く。自作の差分価値はここに出るはずである。
