# #359 Claude 設定のハーネス層

## 背景

owner の方針は「重要な設定は hub に正本を置き、sync で適用する。手元の状態を見に行かなくて済むようにし、変更は大元を書き換えて直す。個人と機種の好みは hub が触らない」である。

いま hub が正本を持っているのは `hooks` と `statusLine` の2キーだけで、それ以外は正本が無い。検査は `hooks` の一致しか見ていない。この plan は、正本を持つキーの集合を宣言できるようにし、その集合に対して適用と検査を効かせる。

調査の詳細と、途中で設計を直した経緯は episode に書いた。

## 設計の前提（調査で確定した事実）

- 設定の優先順位は5段で、hub が書いている `~/.claude/settings.json` は最下位である。`hooks` とリスト型のキーは段をまたいでマージされるが、スカラーのキーは上の段があれば負ける。
- 公式に文書化された top-level キーは 225 個ある。手元にあるのは12個。「個人層」をキーの列挙として定義することはできない。管理できるのは「hub が正本を持つ集合」1本で、残りはすべて残余として触らない。
- Claude Code 自身が user settings に書く操作が多数ある。`/model` は `model` を、`/effort` は `modelSettings` を、`/plugin` は `enabledPlugins` を、`/tui` は `tui` を、`/config` の各行はそれぞれのキーを書く。bypassPermissions の確認を一度承認すると `skipDangerousModePermissionPrompt` に true が書かれる。
- `/config` で output style を選ぶと、選択はプロジェクトの `.claude/settings.local.json` に書かれる。user settings に置いた `outputStyle` はそのプロジェクトでは負ける。
- 実効値を外から機械的に取る手段は公式に無い。`/status` は読み込んだファイルの一覧を出すだけで、どのキーがどのファイル由来かは出さない。
- 設定ファイル全体の symlink は、CLI の atomic write が symlink を通常ファイルに置き換える不具合が報告されている。
- 検査も配置も正本の側からだけ走査しているので、正本から消えたファイルの配布先は一度も訪れられない。

## 設計判断

ゲート1（ゼロベース反証）とゲート2（設計SO・3レーン）の両方で反証を受けており、以下は直した後の形である。何をどう直したかは episode に書いた。

### DJ-1 適用方式

hub に宣言ファイルを1つ置き、sync がそこに書かれた項目だけを `~/.claude/settings.json` へ適用する。宣言に無い項目は一切触らない。

代替案（全体 symlink / managed settings / 起動フラグ / 全体生成 / plugin として配る / プロジェクト設定へ置く）はすべて棄却した。理由は「棄却した案」節に書いた。

### DJ-2 宣言の項目は JSON Pointer で指す

宣言の単位を top-level のキーではなく、`/hooks`、`/statusLine`、`/permissions/allow`、`/env/FOO` のような JSON Pointer にする。

top-level に固定すると「そのキーを全部所有するか、全く触らないか」の二択しか書けない。`env` の中の1変数だけ、`permissions.allow` だけ、といった所有は確実に必要になる。宣言の形は契約なので、後から変えると全部の宣言を書き直すことになる。安いうちに決める。

### DJ-3 操作は4種類。例外は名前付きハンドラに逃がす

データ操作は次の4つだけにする。

| 操作 | 意味 |
|---|---|
| `replace` | そのパスの値を正本の値で置き換える（スカラーもオブジェクトも同じ） |
| `merge-object` | オブジェクトを深く重ねる。手元にしか無い下位キーは残す |
| `union-array` | 配列に項目が入っていることを保証する。重複を除き、他の項目は残す |
| `absent` | そのパスを手元から消す |

当初案の `set` は `replace` に畳んだ（JSON 操作として同じものだった）。`wrap` は操作の種類ではなく例外経路なので enum から外し、`handler: statusline-wrap` のような名前付きハンドラにする。

`union-array` を足したのは、`permissions.allow` のような配列を `replace` すると owner が足した項目が消え、`merge-object` では配列を表現できないためである。ただし `permissions` は今回の宣言には入れない。

### DJ-4 ハンドラは適用と比較を対で出す。比較を出せないものは宣言できない

`statusLine` の現行実装は3分岐ある。未設定なら正本を載せる。すでに拍動 producer が入っていれば command は保持して type と refreshInterval だけ更新する。owner 独自の statusLine があれば元のコマンドを退避して包み、padding などの既存フィールドは残す。

これを「包む」の一語で書くと、実装者が「毎回正本のコマンドに置き換える」と読み替えて二重に包むか、owner のコマンドを消す。だからハンドラは適用の関数と一致判定の述語を対で出す。`statusline-wrap` の一致判定は「拍動 producer の marker がコマンドに含まれているか」と「退避した元コマンドが失われていないか」の2つになる。

そして「比較の述語を出せない項目は宣言に書けない」を規則にする。いま `statusLine` が配られているのに検査されていないのは、一致の見方が決まっていないからである。規則にしないと、配るだけで見ない項目がまた増える。

### DJ-5 書き込みは1回にまとめ、置き換え直前に横取りを確かめる

現行は `hooks` と `statusLine` が別々に読み書きしている。宣言を素直に項目ごとのループで実装すると、項目の数だけ書き込みの窓が並ぶ。その途中で CLI が書き込むと、半分だけ適用された状態が残る。

- 宣言された項目を1回の jq で合成し、置き換えを1回にする。バックアップも1回で済む。
- 読んだ時点のファイルの digest を記録し、置き換える直前にもう一度確かめる。変わっていたら最新を読み直して宣言項目だけを当て直す。上限を決めてやり直し、それでも駄目なら非0で止めてバックアップを残す。
- バックアップは「最初に読んだ版」ではなく「実際に置き換える直前の版」を残す。

これは同時書き込みを防ぐものではない。CLI 側は同じロックを取らないので、ロックを足しても効かない。ここで守れるのは「配布が CLI の無関係な項目を消さない」ところまでである。この理由を設計文に書き残す。書かないと、後から「ロックを足せば直る」と誤解される。

### DJ-6 書けない相手の扱いを1箇所に集める

対象が symlink、通常ファイル以外、あるいは JSON として読めないときの態度を1箇所にまとめる。読めなければ何も書かない、空のファイルを作らない、終了コードで知らせる。

現行は項目ごとに態度が違う。`statusLine` は読めなければ黙って skip し、`hooks` は jq が失敗すると 1 を返す。一般化のときにここを揃える。

対象が symlink のときに置き換えを走らせると、rename が symlink を通常ファイルに変える。全体 symlink を棄却した理由と同じ現象を自分の配布スクリプトで起こすことになる。現行コードにはこの保護があるので、一般化で落とさない。

### DJ-7 検査は6つを報告する

当初は2つ（宣言との一致と、上位スコープの同名キー）にしていたが、それでは足りない。

1. **項目ごとの一致。** 判定は操作の種類ごとに変える。`replace` は正規化した JSON の一致、`merge-object` は正本側の葉が手元に含まれているか、`union-array` は正本側の項目が手元に含まれているか、`absent` はパスが無いこと、名前付きハンドラはそのハンドラが出す述語。
2. **一度も適用していない状態。** 現行は settings.json が存在するときだけ比較するので、ファイルごと無い機種では差分なしと表示される。項目ごとに「存在しない」を独立した状態として報告する。
3. **上位スコープに同名の項目があるか。** ただし文言を2つに分ける。`hooks` とリスト型は段をまたいでマージされるので、プロジェクト側にあるのは「hub のものが無効」ではなく「追加される」である。スカラーは上位が勝つので影になる。同じ文言だと owner が両者を区別できない。
4. **見ていないスコープの明示。** managed 設定と起動フラグと他のリポジトリの `.claude/` は読んでいない、と出力に列挙する。書かないと「一致」が「実際に効いている」と読まれる。
5. **適用できない状態。** 対象が symlink、通常ファイル以外、JSON として読めない、を報告する。
6. **宣言に書いた項目名が公式の一覧にあるか。** top-level のキーが 225 個ある以上、綴りを間違えても CLI は黙って無視する。一覧は古くなるので、失敗ではなく警告にとどめる。

読めるファイルの範囲で「どのファイルの値が勝つか」は計算できる。優先順位は文書化されていて、managed もプロジェクトの2ファイルも user のファイルも読める。ただし CLI から読んだ値ではないので、出力に「ファイルから計算した値であって、動いているセッションの値ではない」と添える。走っているセッションはディスクより古い像を持ちうるので、配布の後は既存セッションを再起動する、を運用の約束として書く。

### DJ-8 CLI と取り合う項目には印を付ける

`model` / `modelSettings` / `enabledPlugins` / `tui` / 危険モードの承認フラグは CLI が書き戻す。これらを宣言に入れると、検査が赤 → 配布 → CLI がまた書く、の往復になり、drift 報告の信用が落ちる。

宣言に「この項目は CLI が書く」という印を持たせ、報告の文言を分ける。owner が「これは取り合いになる項目だ」と学べる形にする。

### DJ-9 層の呼び方

issue の「2層に分類する」を「宣言された集合と、それ以外」に読み替える。公式のキーは 225 個あり、個人層を列挙で閉じることはできない。個人層は列挙する対象ではなく残余の呼び名になる。

## PR 分割

1 PR = 1論理変更。前の PR がマージされてから次に進む。順序は設計SOの指摘を受けて入れ替えた。掃除を最後に置くのは、その時点で走査器が知らない配布の種類が残っていると、正しい配備を孤児と誤認して消す危険があるためである。

### PR-1 宣言ファイルと検査（適用側には触らない）

- 成果物: `canonical/claude/settings.harness.json`（宣言。初期は現行の `/hooks` と `/statusLine` だけを、既存の正本ファイルを参照する形で書く）、`scripts/sync.sh` の `check_target claude` 分岐
- この PR の本当の仕事は「宣言が現実を正しく記述できている」ことの証明である。次の PR が必要とする等価性の土台がここで手に入る
- 受け入れ基準
  - 現行の手元の状態に対して、宣言との一致が緑になる（`statusLine` が包まれた状態でも緑になること。ここを JSON の値一致で書くと恒常的に赤になる）
  - 不一致があれば項目ごとに期待と実際を列挙し exit 1（既存の契約に揃える。`check_target` が 1 を返し `main` が exit 1）
  - DJ-7 の6項目すべてが出力に出る
  - `sync-claude.sh` を実行しても出力が変わらない
- 陽性対照
  - 一時 HOME の複製で、宣言の1項目だけをわざと違う値にし、その項目だけが列挙されることを見る
  - 値が `false` の項目と `null` の項目を含む複製で、どちらも見落とされないことを見る（jq の `paths(scalars)` は値が `false` と `null` のパスを静かに落とすので、実装がこれを使っていないことをここで担保する）
  - `statusLine` が包まれた状態と包まれていない状態の両方で緑になることを見る
  - プロジェクト側に `hooks` を置いた場合と `model` を置いた場合で、警告の文言が違うことを見る
  - 変更前後で `sync-claude.sh` の出力を diff し、既定の書き込み側が変わっていないことを見る
- ロールバック: revert する。手元のファイルは書き換えていない

### PR-2 孤児 symlink の検出（読み取りのみ）

PR-1 と同じ読み取り専用の枠なので、同じ PR にまとめてもよい。分けるなら順序はここ。

- 走査の根は sync が書き込む配布先ディレクトリの allowlist にする（`rules` / `skills` / `agents` / `commands` / `hooks` / `orchestration-spec` と、後で `output-styles`）。`~/bin` は別ターゲットなので別の一覧にする
- ファイルの symlink とディレクトリの symlink の両方を見る（`skills` はディレクトリ単位のリンクなので、ファイルだけ見ると孤児ディレクトリが残る）
- 分類を3つに分ける
  - `orphan-canonical`: リンク先が今の正本ディレクトリ配下を指しているのに、正本にその file が無い。これだけが後の掃除の対象
  - `dangling-outside`: リンク先が解決できないが、正本配下でもない。報告のみ。別の仕組みが張ったリンクを消さないため
  - `alive-outside`: リンク先は生きているが正本の外（別チェックアウトや別 worktree を指す）。触らないが、配備が古い場所に固定されている状態なので独立した分類として報告する
- 判定はリンクの生のターゲット文字列と `realpath` の両方で行う。リンク先が解決できないときは `realpath` が失敗するので、生の文字列で正本配下かを判断する
- 通常ファイルは対象にしない。正本から消えた後に残る通常ファイルは別の負債として「報告しない」と明記する。ここに足すと個人のファイルを消しにかかる
- 受け入れ基準: 孤児があれば分類つきで列挙して exit 1、無ければ既存の出力を変えない
- 陽性対照
  - 一時 HOME に、正本に無い名前で正本配下を指すリンクを1本作り、`orphan-canonical` として拾うことを見る
  - ディレクトリのリンクでも同じく拾うことを見る
  - `/tmp` を指す壊れたリンクを1本作り、`dangling-outside` として報告はするが掃除の対象に入らないことを見る
  - 同じ場所に通常ファイルを1つ置き、拾わないことを見る
- ロールバック: revert する（何も消さないので手元の復元は不要）

### PR-3 適用を宣言駆動に置き換える

現行の `hooks` 置換と `statusLine` の3分岐が、宣言から同じ結果を出すことを先に示す。DJ-5 の1回書き込みと横取り確認、DJ-6 の書けない相手の扱いをここで入れる。

- 受け入れ基準
  - 宣言が現行の2項目だけのとき、変更前と変更後で書き込み結果が一致する。目視ではなく fixture で示す
  - 宣言に無い項目は一切変更されない
  - 置き換えは1回。バックアップは置き換え直前の版
  - 対象が symlink のとき、置き換えを走らせない
- fixture は現行コードが分岐を持っている場所をそのまま並べる。settings.json が無い / `hooks` だけある / owner 独自の statusLine がある / すでに包まれている / JSON が壊れている / symlink である、の6つ
- 陽性対照
  - 一時 HOME で、個人層の項目（`theme` など）を含む複製に対して走らせ、その項目が変わっていないことを見る
  - 既存の `projects/orchestration-engine/tests/test_sync_claude_statusline.sh` が緑のままであること
  - 新規テストを同じ隔離方式（scratch HOME）で追加する
  - 書き込みの途中で settings.json が外から変わった状況を作り、やり直しが走ることを見る
- ロールバック: revert し、`~/.claude/settings.json.bak.*` の最新から復元する

### PR-4 output-styles の配布経路

`canonical/output-styles/` を作り、`~/.claude/output-styles/` へ symlink で配る経路を足す。`outputStyle` の項目自体は宣言に入れない（#348 の採用判定を待つ）。

- 前提: `canonical/output-styles/` はまだ存在しない。`~/.claude/output-styles/readable-conversation.md` は手で置かれた通常ファイルで symlink ではない
- 受け入れ基準
  - canonical に置いた output style が配布先に現れる
  - 既にある通常ファイルを上書きしない（他の sync 関数と同じ姿勢）
  - PR-2 の走査根の allowlist に加わり、孤児検出が効く
- ロールバック: revert し、配布した symlink を手で外す

### PR-5 孤児 symlink の掃除（明示フラグのときだけ）

`sync.sh` に `--prune` を足す。付けたときだけ PR-2 が `orphan-canonical` に分類したものを削除する。

- 受け入れ基準
  - フラグ無しでは何も削除しない
  - フラグ有りでも `orphan-canonical` だけを削除し、削除したものを1行ずつ出力する
  - 通常ファイルは削除しない
  - 正本の根が存在しない、列挙が0件、前回より大きく減った、のいずれかなら中断する。worktree から sync した後にその worktree を消す事故は既に起きており、正本の根が消えた状態で掃除を走らせると配備物の全部が孤児に見える
  - 削除の直前に検出をやり直す（検出と削除の間に owner がリンクを張り直した場合に備える）
- 着手条件: PR-2 を入れた後、報告だけの状態で実機を1周し、結果が空であることを確認してから実装に入る
- 陽性対照: PR-2 と同じ一時 HOME で、フラグの有無で削除の有無が切り替わること、正本の根を空にすると中断すること
- ロールバック: 削除するのは symlink だけなので、sync を再実行すれば正本から張り直される

## 棄却した案

| 案 | 棄却理由 |
|---|---|
| 設定ファイル全体を symlink にする | CLI の atomic write が symlink を通常ファイルに置き換える不具合が報告されている（Claude Code issue #40857） |
| managed 設定に置く | CLI が書かないので drift は構造的に起きないが、システムディレクトリへの書き込みに管理者権限が要り、owner が一時的にも上書きできなくなる |
| 起動フラグでプロファイルを渡す | CLI が書き戻さず、プロジェクトローカルより上に乗る利点があるが、起動のたびにフラグが要り、渡し忘れた起動では設定が丸ごと無効になる。IDE 拡張やデスクトップアプリが起こすセッションには渡せない |
| 設定ファイル全体を hub が生成して読み取り専用にする | 「個人の好みは触らない」と両立しない。未宣言の項目を保持するなら深マージと同じものになる |
| 公式の plugin として配る | plugin の設定ファイルで適用できるのは `agent` と `subagentStatusLine` の2キーだけで、本件の設定キー配布はできない |
| プロジェクトの `.claude/settings.json` を配布先にする | user 層より優先順位が上で、CLI が書き戻す頻度も低いので部分適用としては成り立つ。ただしリポジトリごと、worktree ごとにファイルが増える。並列 worktree 運用と相性が悪い |

## 範囲外（follow-up として起票する）

- Cursor の `~/.cursor/cli-config.json` と Codex の `~/.codex/config.toml` は、CLI 自身が書く設定ファイルという同じ問題を抱えている。Codex 側には「無ければ入れる」形の冪等 apply があるが、値が違っても直さない。同型の drift 検査は入っていない
- hub を公式の plugin として配る案。plugin は hooks / agents / skills / commands / output-styles を同梱できるので、配布先へ symlink を張る方式そのものが不要になり、孤児 symlink の問題が根から消える
- 配布時に「何をどこへどの方式で置いたか」の目録を残し、目録と実物を突き合わせる形。今回は symlink だけが対象なので不要だが、コピー方式の配布が増えると symlink 判定では孤児を見つけられなくなる。PR-2 の実装を目録に寄せた形にしておくと後で作り直さずに済む
- `~/.claude.json` の `mcpServers` は対象ファイルが違うので今回の宣言の対象外とする

## 検証していない前提

- 設定ファイル全体を symlink にしたときの CLI の挙動は、`~/.claude/settings.json` そのものでは確かめていない。報告されている不具合はプロジェクトの `.claude/settings.local.json` についてのものである。書き込み経路が同じなら同じ結果になるが直接の証拠ではない。全体 symlink を採らないので、この前提に依存する判断は無い
- hooks が走行中のセッションに反映されるかどうかは確かめていない。設計SOのレーンから「起動時に取り込まれ、途中の書き換えは反映されない」という指摘があったが、その場では公式で確認していないと但し書きが付いていた。PR-1 の出力に「これはファイルの状態であって動いているセッションの状態ではない」と書くので、この前提に依存する判断は無い。実装前に一次確認する
- `skipWorkflowUsageWarning` は公式に文書化されていない。どの操作が書くか分かっていないので宣言に入れない
- macOS の既定のファイルシステムは大文字小文字を区別しないので、`Foo.md` から `foo.md` への改名が「正本に無い」と判定されうる。PR-5 の掃除で効くので、そこで確かめる
