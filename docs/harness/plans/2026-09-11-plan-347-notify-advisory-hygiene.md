# #347 notify.sh の advisory 衛生3件

## 背景

`canonical/hooks/scripts/notify.sh` は advisory なフックで、「非ゼロ終了を出さない・stdout に何も出さない・末尾は無条件 `exit 0`」を契約にしている。その契約を破る箇所が3つ残っていた。#343 の実装子が範囲外として surface し、gate 4 の codex レーンが別 issue にすべきと言ったことから #347 が起票された。

3件とも着手時点の master（`04722ba`）で再現した。再現の手順と出力は episode に書いた。

**この plan は設計SO（ゲート2）で3つの設計判断を覆している。** 覆した経緯は「設計SO で変えたこと」節に書く。

## 設計の前提（実測で確定した事実）

- `HOME` 未設定で `rc=1` になる。落ちる場所はデバッグ判定の行（`notify-hook-debug` で検索すると当たる）で、`set -u` の下で素の `$HOME` を展開している。
- **この欠陥は `NOTIFY_DEBUG` が立っていないときだけ出る。** `[[ A || B ]]` の `||` は短絡するので、`NOTIFY_DEBUG` が非空なら `$HOME` は評価されない。対照を組むときにここを踏むと、修正前でも `rc=0` が出てしまう。
- **`HOME=/` は空文字と同じ場所を見に行く。** 実測すると `HOME=/` で `[[ -f //.notify-hook-debug ]]`、`HOME=//` で `[[ -f ///.notify-hook-debug ]]` が評価される。macOS はこれを `/` 直下として解決する。
- 制御端末を持たない起動で `/dev/tty: Device not configured` が stderr に出る。`-w /dev/tty` の guard は通過する。macOS では制御端末が無くてもデバイスノードへの `access` は成功し、`open` だけが失敗するためで、guard では防げない。
- リダイレクトは左から右へ処理されるので、`2>/dev/null` を先に置けば後続のリダイレクト失敗の診断も消える。終了コードは変わらない（実測で確認済み）。
- **同じ形は `notify.sh` の中に3箇所ある。** 配信の2箇所（tmux のペイン TTY 側と `/dev/tty` 側）に加えて、デバッグログの追記（`>> /tmp/notify-hook.log 2>/dev/null || true`）が同じ順序で書かれている。`|| true` が握り潰すのは終了コードだけで、診断は握り潰さない。
- `canonical/hooks/scripts/` の8本のうち、`set -u` の下で素の `$HOME` を展開しているのは `notify.sh` の1箇所だけである。他の5箇所はすべて `${HOME:-}` で受けている。
- **`notify.sh` を呼ぶツールは2つで、入力の形も2つである。** hook スクリプトは3ツールの `hooks/` へ symlink で配られるが、README のカバレッジ表によれば Cursor は通知に `notify.sh` を使わない。実在するのは Claude Code の「引数 + stdin の JSON」と Codex の「第1引数が JSON 文字列」である。
- hook スクリプトの symlink のリンク先は master の作業ツリーのパスなので、**この worktree での編集は、マージされるまで稼働中のフックに影響しない**。
- **同じディレクトリの他フックは `jq -cn` を使っている**（`session-name.sh` に3箇所・`oe-prompt-receipt.sh` に1箇所）。短オプションの連結なので、`notify.sh` のコメントが述べている規則をそのまま当てると 1.5 以降を要求する。
- `canonical/hooks/` にテストの置き場は無い（`projects/orchestration-engine/tests/` にはある）。
- 手元の `jq` は 1.8.0、`shellcheck` は 0.10.0。修正前の `notify.sh` は shellcheck clean である。

## 設計判断

### DJ-1 デバッグ判定は「環境変数」と「マーカーファイル」を別の文に分ける

issue が示した2文に分ける形を骨格として採る。1つの `[[ ]]` に括弧で入れ子にしても同値だが、読みにくくなるだけで得るものが無い。

### DJ-2 `HOME` の可否は「絶対パスであり `/` と `//` でない」で見る

**設計SO で覆した。** 当初は「読むだけだから非空で足りる」としていたが、両レーンが同じ反例を出した。`${HOME:-}` を退けた理由は「空文字のとき `/` 直下を見に行くから」である。その理由は `HOME=/` にそのまま当てはまる。`-n "/"` は真なので guard を通り、`//.notify-hook-debug` すなわち `/` 直下を見に行く。**空文字を退けた理由で `HOME=/` を退けていなかった。**

engine が #341 で `/` と `//` を名指しで落としたのは「書き込むから」ではなく「`/` を家として扱わない」からで、読むだけの用途にも同じ理由で効く。相対パスの `HOME` についても見積もりが軽かった。作業ディレクトリの下のマーカーファイルでデバッグが立つと、repo 名とブランチ名が `/tmp/notify-hook.log` という固定パスへ追記され続ける。ブランチ名に内部の識別子が乗る運用では露出面になる。

採る形は次のとおりで、engine の `_oe_home_usable` と同じ述語である。`notify.sh` は単体で3ツールへ配られるので engine の lib を source できない。`oe-hookfire` が `~/bin` へ単体配布されるために同じ述語をインラインで持っているのと同じ事情である。

```bash
# HOME の可否は非空では足りない。HOME=/ と HOME=// は「/」直下のマーカーを拾い、
# 相対 HOME は作業ディレクトリ配下を拾う。engine 側の _oe_home_usable（#341 DJ-2）と
# 同じ述語を、単体配布のためインラインで持つ。
_notify_home_usable() { case "${HOME:-}" in /|//) return 1;; /*) return 0;; *) return 1;; esac; }

if [[ -n "${NOTIFY_DEBUG:-}" ]] || { _notify_home_usable && [[ -f "${HOME}/.notify-hook-debug" ]]; }; then
```

**この述語が落とすのは2つの綴りだけで、「`/` を指すパスの集合」ではない。** 実装SO の両レーンが独立に同じ穴を挙げた。`///` ・ `/.` ・ `/..` ・ `/./` ・ `/tmp/..` はいずれも `/*` に一致するので通り、評価先は `/.notify-hook-debug` へ畳まれる。`HOME` が `/` へのシンボリックリンクの場合も同じである。つまり達成できているのは「`/` と `//` という綴りを退ける」までで、「`/` を家として扱わない」ではない。

それでも engine と同じ述語のままにする。ずらすと同じ名前の判定が2つの意味を持つからで、穴は engine 側と共有のものとして follow-up に出す。`notify.sh` の側は `-f` を1回するだけなので実害は小さく、engine の側は同じ判定の結果で `mkdir -p` まで進むぶん重い。

**防御としての効き目も、初稿が書いていたより弱い。** `HOME` を差し込める側は `NOTIFY_DEBUG` も差し込めるので、マーカーファイルを使わずに同じログを出せる。相対 `HOME` の話（作業ディレクトリを握る側がマーカーを置ける）は成立するが、`HOME=/` の話は「`/` に書ける者」を仮定しており、そこまで行けば他にいくらでも手がある。この修正の値打ちは、防御よりも「advisory が環境の事情で落ちない」ことと「engine と判定を揃える」ことにある。

**engine の形を丸ごと写すわけではない。** engine は `_oe_state_dir` で状態ディレクトリを組み立て、`mkdir -p` して `/` 直下を glob で走査する。`notify.sh` が要るのは可否の述語だけで、そこから先は持ち込まない。同じディレクトリの `session-name.sh` と `oe-prompt-receipt.sh` が採る「先頭で `home="${HOME:-}"` と受けて `[ -n "$home" ] || exit 0` と早期終了する」形も写さない。この2本は `HOME` 無しでは仕事が無いが、`notify.sh` にとって `HOME` はデバッグ用の飾りでしかなく、写すと `HOME` 未設定で通知そのものが出なくなる。

### DJ-3 リダイレクト失敗の診断は、ファイル内の3箇所とも直す

**設計SO で「2箇所」から「3箇所」へ訂正した。** 受け入れ条件が名指しするのは `/dev/tty` 側だが、同じ順序の形はデバッグログの追記にもある。`NOTIFY_DEBUG` が立っていて `/tmp/notify-hook.log` が開けないとき（別ユーザー所有・ディレクトリ・読み取り専用マウント）に、通知のたびに診断が stderr へ出る。`/tmp` は誰でも書けるので、他の uid で走ったプロセスが先に作る経路が現実にある。

3箇所とも `2>/dev/null` をリダイレクトの前へ移すだけで、終了コードも `&& delivered=1` の判定も変わらない。

### DJ-4 `jq` の下限は README の `notify.sh` 節に書く。「前提条件」節には値を書かない

**設計SO で置き場を変えた。** 当初は「前提条件」節に書くとしていたが、あの節は3ツール共通・全フック共通である。そこに「`jq` は 1.4 以上」と書くと、同じディレクトリの `session-name.sh` と `oe-prompt-receipt.sh` が `jq -cn`（短オプションの連結）を使っている事実と食い違う。フック群として実際に要る下限は少なくとも 1.5 であって、1.4 ではない。

1.4 という値が意味を持つのは `notify.sh` を改変する人だけで、その人に伝えたい中身は「下限は 1.4」ではなく「`-R -r` を `-Rr` に縮めるな。縮めると下限が 1.5 に上がる」である。読者が改変者に揃う `notify.sh` 節（「advisory 安全性」の下）へ書く。

「前提条件」節には値を書かず、「フックによっては `jq` の版に下限があり、各スクリプト側に書いてある」という誘導の1行だけ足す案も出した。**ゲート3で owner がこれを採らないと裁定した**（`.oe/addendum-347-gate3.md`）。採らない理由は、共通節に誘導を書くと同じディレクトリの他フックの下限まで語ることになり、#347 の範囲から出るためである。

コード中のコメントは消さない。あれは「なぜ `-R` と `-r` を分けて書くのか」というその場の書き方の理由で、読む人も目的も違う。

### DJ-5 回帰確認は臨時の足場で行い、テストの置き場は新設しない

`canonical/hooks/` にテストの置き場は無い。置き場を作るのは規約の決定であって、1ファイルの衛生修正の巻き添えで決める話ではない。足場は使い捨てにし、中身と出力は episode に残す。hooks にテストが無いこと自体は範囲外として surface する。

### DJ-6 陽性対照は、本番と同じ足場で、副作用を記録して取る

**設計SO で作り直した。** 当初は `bash -x` のトレースで「配信の分岐を通ったか」を見るとしていたが、両レーンが同じ穴を指摘した。対話端末から走らせると `/dev/tty` が開けてしまうので、**本番のフック文脈（制御端末なし）とは違う分岐を通る**。トレースを読む判定が目視依存でもある。

作り直した対照は次のとおりである。

- `PATH` の先頭に、受け取った引数をファイルへ追記するだけの偽の `terminal-notifier` を置く。
- `TMUX` と `TMUX_PANE` を外し、`os.setsid()` で制御端末を手放した足場から起動する（episode が `/dev/tty` の再現に使ったものと同じ足場）。
- 記録ファイルに title と body が現れれば、配信まで到達したことが副作用として確定する。
- `HOME` を設定した実行と記録内容を比べれば、「到達した」だけでなく「同じものが届いた」まで言える。
- フォールバックは `( ... ) &` で背景に投げられ、親は直後に `exit 0` するので、記録ファイルは短いポーリングで待つ。待たずに読むと、通ったのに通らなかったと読める。

`bash -x` のトレースは残すが、役目を1つに絞る。**「`/` 直下のマーカーを見に行かなかった」ことの確認**に使う。`-f` が評価されなかったことは副作用として観測できないので、ここだけはトレースに頼る。

### DJ-7 走査の健全性は、grep の外から対照を取る

「素の `$HOME` は1箇所だけ」は grep の結果であり、grep のパターンが見落とす形（間接参照やチルダ展開など）はそのまま盲点になる。対照は走査パターンの外から取る。`canonical/hooks/scripts/*.sh` の8本を実際に `env -u HOME` で起動し、終了コードと stderr を見る。振る舞いの側から見れば、書き方の形に依らず当たる。

## owner に預ける判断（ゲート3で裁定してほしい）

### 判断1: デバッグログの追記先に「通常ファイルでないなら触らない」ガードを足すか

`/tmp/notify-hook.log` が FIFO だったとき、`>>` は reader が現れるまで `open(2)` でブロックする。フックが止まればハーネスのタイムアウトまでセッションが待たされるので、advisory としては雑音より重い。README の「発火記録」節は、止める側の3本について同じ危険を明文で扱い、3つの追記先すべてに「存在するのに通常ファイルでないなら触らない」ガードを通したと書いている（実装は `block-destructive.sh` の `[ -e "$1" ] && [ ! -f "$1" ]`）。`notify.sh` の追記先にはそのガードが無い。

**推奨は「足す」。** DJ-3 で触るのと同じ文であり、repo に既に同じ形のガードがあり、README が危険を名指ししている。ただし #347 の受け入れ条件には無いので、勝手には広げない。足さないなら範囲外として surface する。

### 判断2: 「前提条件」節に誘導の1行を足すか

DJ-4 の後半である。値を書かない1行なので害は小さいと見ているが、issue の受け入れ条件が求めているのは「どこに書くかが決まっている」ことだけなので、`notify.sh` 節だけで足りるという裁定もありうる。

## 棄却した案（ゼロベース探索・ゲート1）

| 案 | 棄却の理由 |
|----|-----------|
| `${HOME:-}` だけで受ける | 空文字のとき `/` 直下を見に行く。受け入れ条件に真正面から抵触する |
| 非空（`-n`）で受ける | `HOME=/` と `HOME=//` が同じ `/` 直下を見に行く。設計SO の両レーンが同じ反例を出した（DJ-2） |
| 1つの `[[ ]]` に括弧で入れ子にする | 同値だが読みにくい。issue の形から離れる利点が無い |
| チルダ展開（`-f ~/.notify-hook-debug`）に置き換える | bash のチルダ展開は `HOME` が未設定ならパスワードデータベースの値を使うので `set -u` でも落ちない（実測で確認）。ただし「`HOME` が無いときは passwd の家を見る」という別の意味に変わる。フックの文脈で暗黙に他人の家を見に行く形は採らない |
| engine の lib を source して `_oe_home_usable` を使う | `notify.sh` は3ツールの `hooks/` へ単体で配られるので、engine の `lib/` を前提にできない。述語だけをインラインで持つ（`oe-hookfire` と同じ事情） |
| sibling の `home="${HOME:-}"` + 早期終了を写す | `HOME` 未設定で通知そのものが出なくなる。受け入れ条件と逆を向く |
| デバッグ用のマーカーファイルを廃止し `NOTIFY_DEBUG` だけにする | フックはツールが起動するので、利用者が環境変数を差し込む余地が無い。マーカーファイルはその代わりであり、役目がある |
| `-w /dev/tty` の guard を外し、リダイレクトの成否だけに任せる | guard は開けない相手への書き込みを1回減らしている。診断を消すのとは別の話で、まとめて外す理由が無い |
| `exec` で `/dev/tty` を1度だけ開き、失敗したらフォールバックへ落とす | `exec` のリダイレクト失敗は非対話シェルを終了させる。advisory の契約と相性が悪い |

## 範囲外（実装せず surface する）

- `notify.sh` の切り詰め（#343 で着地済み）
- `oe-*` 側の `HOME` 未設定（#341 で着地済み）
- fail-closed な妥当性契約（#344）
- **stdin が閉じられない場合に `input="$(cat 2>/dev/null || true)"` が戻らない。** `[[ -t 0 ]]` が弾けるのは端末だけで、開きっぱなしのパイプは弾けない。3つのハーネスが実際にそういう起動をするかは確かめていないので、これは推測である
- **`tr` や `basename` が `PATH` に無いと stderr に診断が出る。** 通常の macOS では起きない。ただし README の「外部呼び出しは全て `|| true`」は実装の厳密な説明になっていない
- `session-name.sh` と `oe-prompt-receipt.sh` にも「リダイレクトの後に `2>/dev/null`」の形がある。書き先は通常ファイルなので `/dev/tty` とは事情が違うが、同じ型ではある
- `canonical/hooks/` にテストの置き場が無い。回帰確認のたびに臨時の足場を組み直すことになる
- hook 側と engine 側で `HOME` の可否の基準が揃っていない。本 plan で `notify.sh` は engine 側に合わせるが、同じディレクトリの `cc-lint.sh` / `block-destructive.sh` / `block-force-push.sh` は非空止まりのままである

## 検証していない前提

- `jq` 1.4 で文字列スライスが動くこと、および `-Rr` と連結すると 1.5 が要ることは、#343 のゲート4が jq のソースまで当てて確定した内容をそのまま引く。本 plan では再検証しない（手元の `jq` は 1.8.0 で、1.4 と 1.5 を用意していない）。他フックの `jq -cn` が 1.5 を要求するという推論も、同じ規則を当てただけで実測していない。
- 通知が macOS の通知センターに実際に表示されるかどうかは人間の目が要る。Step 5 が機械的に確かめるのは「意図した宛先へ意図したバイト列と引数が渡るところ」までである。
