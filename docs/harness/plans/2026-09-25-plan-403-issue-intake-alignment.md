# #403 issue 起点の認識合わせスキル

## 背景

#390 では、ゲートを全部通したのに、後継が子の登記をつけかえる工程が落ちた。ゲートは発火していたが、発火したゲートの中身がその観点を持っていなかった。issue の目的節は誤っていたのではなく足りていなかった。

#403 はこれを、issue を作る瞬間ではなく使う瞬間で直す。issue に着手するたびに「この issue で何を作るか」の認識合わせを1回通し、その入口を人が言い出すことに頼らない形で作る。設計の大枠は issue 本文の「ゲート0 の結論」節で owner と統括が確定済みで、**この plan はそれを正本として扱い、覆さない**。この plan が決めるのは、その実装の形と、「残っていること」節の6項目への推奨案である。

**この plan は設計SO（ゲート2）の2本のレーンで、それぞれ大きく直した。** 何を採り何を退けたかは「設計SO（ゲート2）」節に書く。**ゲート3（2026-09-28）の判断は7つとも出そろった。** 裁定の内容は「ゲート3の裁定」節に書く。

## この plan の範囲

- 作るもの: 新しい canonical スキル1本（名前は DJ-1 の推奨で `issue-intake`、ゲート3で確定）。
- 直すもの: `question-driven-design` の「いつ使う／使わないか」節と「質問フェーズの完了」節、`document-format.md` の「遷移規則」節（判定順の先頭に1項）と「ゲート配置」節（図・説明・0 の行・表の下の段落）、`doc-flow-guardrail` のフロー地図の索引・routing 表の 0 の行・brief テンプレートの可変節、`canonical/CATALOG.md`。
- ゲート3で足すと決まったもの: `episode-retrospective` の closure への1行（推奨案5）、hub の `CLAUDE.md` と `AGENTS.md` への文脈の置き場の案内（推奨案2・暫定）。

## 設計判断

### DJ-1 スキルの名前は `issue-intake` にする（推奨・ゲート3で確定）

作る側の `issue-conventions` と `issue-` で並び、URL を起点に取り込む既存の `research-intake` と「起点-intake」の形で並ぶ。短く、description を読まなくても「issue を取り込むときのもの」と分かる。

退けた候補: `issue-alignment` は目的（認識合わせ）を表すが、`issue-conventions` と対になる「取る側」であることが名前から読めない。`issue-kickoff` は hub の文書型 `kickoff` と紛れる。

### DJ-2 description は「issue に着手する」を引き金に、`issue-conventions` と同じ粒度で書く

案文は次のとおりである。

> issue に着手するときの認識合わせを行う。特定の issue を指して作業を始めるとき、子へ委譲するとき（番号・URL・タイトル・本文の貼り付けのどれでも）、着手する issue を gh issue view で読むときに使用する。「この issue でやること」「issue に書いていないが要ること」「どの観点で見たか」の3つを出し、確定版を issue コメントに残す。深掘りの合図が出たら question-driven-design へ受け渡す。

`issue-conventions` の description は「何をするか。いつ使うか（動作とコマンド）。何を含むか。」の3部である。案文も同じ3部で書いた。「子へ委譲するとき」は、hub で認識合わせを通す主な場面が「#N を子に渡して」という依頼だからである（設計SO 2本目 指摘4）。

**先例の形を写す前提が、移植先にどこまであるか。** `issue-conventions` の引き金 `gh issue create` は、モデル自身が打つコマンドである。打つと決めた時点で、モデルは自分の次の動作と description を突き合わせられる。移植先ではこの前提が識別の形ごとに違う。

| 識別の形 | モデル自身の観測できる動作 | 先例の前提 |
|---|---|---|
| 番号・URL | `gh issue view` を打つ | ある |
| タイトル | `gh issue list --search` などで探す | 弱くある |
| 本文の貼り付け | 打つコマンドが無い | 無い |
| issue が無い（文章で始まる作業） | 無い | 無い |

本文の貼り付けは前提が無いが、ゲート0 の結論1は「識別の形は問わない」としている。そこで description に名指しで書き、発火するかを D1 で実測し、**4つの形と委譲の言い方のすべてで発火することを受入にする**（A8-1）。description の直しで届かなければ、止まって owner に諮る。発火を機械で担保する層は、ゲート3で別の issue にすると裁定された（判断6）。issue が無い作業はこのスキルの引き金に入れない（ゲート0 の結論9。推奨案1）。

**過剰に発火しないこと**も要件にする。「#<番号> の状態を教えて」のように issue に言及するだけの依頼で発火すると、毎回の手数が増える。案文が「着手する」「作業を始める」「委譲する」に限っているのはこのためで、D1 に陰性対照を入れて確かめる。

### DJ-3 本文の骨組みと、実行の順序

brief が挙げた要素（取り込みの最初の確認 → 固定の問い3つ → 3つの出力 → 別モデルへ1回 → owner の反応 → issue コメントへ → 深掘りの3つの合図 → `question-driven-design` への受け渡し）をすべて持つ。**節の並びは、上から順に読んで迷わず実行できる順にする**（設計SO 2本目 指摘11）。何を投稿するかは合図が出たかで決まるので、合図の判定を投稿の前に置く。応答する人がいるかは最初に決め、それで動き方を切り替える。

```markdown
---
name: issue-intake
description: （DJ-2 の案文）
---

# issue-intake — issue 着手時の認識合わせ

## いつ使うか
## いつ使わないか（省く条件は2つだけ・DJ-5）
## 1. 取り込みの最初の確認（issue の特定・既存の認識合わせのコメント・応答する人がいるか・テンプレートと必要な欄）
## 2. 観点を先に固定する（固定の問い3つ・テンプレートの欄・リポジトリの文脈の置き場・owner 特有の観点の枠）
## 3. 3つの出力（やること・書いていないが要ること・見た観点。issue の要約は出さない）
## 4. 別のモデルへ1回だけ問い合わせる
## 5. 反応を受け、深掘りの合図が出たかを決める（1往復だけ。応答する人がいなければ依頼元へ渡して待つ）
## 6. issue コメントに残す（合図なし＝確定版／合図あり＝深掘り中の版）
## 7. question-driven-design への受け渡しと、確定版への戻り
## 8. 後から見つかった抜けの足し方（3つの行き先）
## 9. 手元に無いものがあるとき（依存ごとの代わりの動き）
## 限界
## 補足: hub での具体例
```

各節の中身の要点は次のとおりである。

- **1. 取り込みの最初の確認**:
  - issue を特定する。番号・URL はそのまま使う。タイトルは検索する。本文の貼り付けは本文から探す。
  - 候補が1件で本文が一致すれば、聞かずに特定したことにし、出力の1行目に「#N と判断した」と書く。外れていれば owner が1行で指せる（設計SO 2本目 指摘10）。
  - **候補が複数あるか、本文が一致しないときは、止まって依頼した人に「どの issue か」を聞く。** 「issue の無い作業」には畳まない（設計SO 1本目 指摘2）。候補が無ければ「issue が見つからない。issue の無い作業として進めるか、issue を起こすか」を聞く。issue の無い作業だと決めるのは依頼した人の明示だけで、AI は決めない。聞くときは3つの出力も作って一緒に出し、往復を1回に収める。issue を起こすと決まったら、起こした issue の本文が提示と同じである限り、そのときの応答を確定として扱い、新しい issue に投稿する。
  - 既存の認識合わせのコメントを DJ-5 の手順で調べる。確定版があれば読んで前提にし、自分では認識合わせをやり直さない。
  - 応答する人がこの場にいるかを決める。委譲された子のように答える人がいない場面では、5 で owner に対話で問いかけず、依頼元へ渡して待つ（DJ-7）。
  - リポジトリの issue テンプレート（`.github/ISSUE_TEMPLATE/`）のどれに当たるかを、ラベルと見出しで決める。当たったテンプレートの必須の欄が埋まっているかを見て、欠けは差分に入れる。どれに当たるか決められなければ、それ自体を差分に入れる。テンプレートが無ければ、目的と作業内容が書かれているかだけを見る。
- **2. 観点を先に固定する**: issue 本文を当てる前に観点の一覧を決める（DJ-4）。
- **3. 3つの出力**:
  - 「この issue でやること」は1〜3文で書く。外れていれば読んだ人が1行で「そこは違う」と指せる形にする。数・前と後・変わるものの名前のどれかを必ず入れる。曖昧で当たっている文は違和感を生まないまま通るからである。対比の例は issue 本文の「計画的な交代を verb にする」と「交代のとき人が手を動かすのは2回で、それを0回にする」を一般化して載せる。
  - 「issue に書いていないが要ること」は1項目1行で書く。
  - 「どの観点で見たか」は観点の一覧を1行ずつ書く。固定の問いは問いの文を繰り返さず、短い名前と当てた結果だけを書く（例:「完成後の人手の残り: …」。設計SO 2本目 指摘15）。
  - 3つ合わせて20行以内を目安にする（受入の「数十秒で判定できる大きさ」の代わりに測れる量）。超えるなら、それ自体が深掘りの材料になる。
- **4. 別のモデルへ1回**: DJ-6。
- **5. 反応と合図**: 1往復だけにする。1往復とは、提示1回と、owner の**実際の応答**1回である。**応答が無いこと（離席・セッションの終了など）を承認として扱わない**（設計SO 1本目 指摘3）。応答が無ければ投稿せず、下書きを残して止まる。応答を受けたら、深掘りの合図が出たかを決める。合図は3つである。owner が違和感を指したとき、「分からない」が残ったとき、別のモデルが挙げた漏れを owner が本物と認めたとき。確認の段をこれ以上足さない（negative knowledge `01M2DRCP3WJA6XN77G9ZFA2Y9W`）。
- **6. issue コメントに残す**: 合図が出なければ確定版を、出たら深掘り中の版を投稿する。深掘り中の版を先に投稿するのは、深掘りが長引いたり担当が替わったりしても途中経過が会話にしか残らない状態を避け、issue を見る人に進行中であることを見せるためである（設計SO 1本目 指摘10）。確定版の印を付けないのは、子の省略判定に未確定の版を拾わせないためである。形は次のとおりで、1行目は機械で探すための印（HTML コメントなので表示されない）である。印には書式の版（`v1`）を入れ、後で見出しの文言を直しても古い確定版を読めるようにする（設計SO 2本目 指摘7）。issue を見られる人なら誰でも見られる場所に置くことが要件である。

  ```markdown
  <!-- issue-intake:confirmed v1 -->
  ## 着手時の認識合わせ（確定版）

  ### この issue でやること
  ### issue に書いていないが要ること
  ### どの観点で見たか
  ### 深掘り（なし ／ あり: 出た合図と結果の置き場）
  ```

  深掘り中の版は、1行目を `<!-- issue-intake:pending v1 -->`、見出しを「着手時の認識合わせ（深掘り中）」にし、「深掘りを終えたら確定版を別のコメントとして投稿する。担当はこの認識合わせを通した人」と1行書く。別のモデルの指摘は、採ったものだけを差分に印付きで残し、採らなかったものは件数だけを「どの観点で見たか」に書く。確定のあとで内容が変わったら、新しい確定版を別のコメントとして投稿する（最後の認識合わせのコメントが有効）。**issue 本文を書き換えたときも同じで、確定版は機械では無効にならないので、書き換えた人（owner か統括）がこのスキルを通し直す**（DJ-5・判断5）。
- **7. 受け渡しと戻り**: 合図が出たら、3つの出力・出た合図・owner の言葉をそのまま `question-driven-design` に渡し、分かっていることを聞き直させない。**深掘りを終えたら、次の工程へ進む前に6へ戻って確定版を投稿する**（設計SO 2本目 指摘2）。受け渡し先のスキルにも同じ戻りを書く（DJ-8 の4）。合図が出なかったとき、または確定版を投稿したあとは、次の工程へ進む。**どの工程へ進むかはリポジトリのフローに従い、このスキルは名指ししない**（設計SO 2本目 指摘3。hub のフローでは「遷移規則」節の判定順1〜5で決まる）。
- **8. 後から見つかった抜け**: 推奨案5。
- **9. 手元に無いもの**: DJ-10。
- **限界**: 入口の発火は description の一致に頼っており、実測は Claude Code だけで行った、と書く（設計SO 2本目の、1本目の判断への意見）。

### DJ-4 観点の一覧を先に固定し、それを issue に当てて差分を出す

issue 本文から出発して「書いてある／ない」を分ける形にすると、書かれていないものは見えない（negative knowledge `01KYJ76D830XME16ZFXC2XRPZZ`）。そこで、issue 本文を読む前に観点の一覧（母集団）を決め、それを本文に当てて差分を出す。一覧は次の4つからなる。

1. 固定の問い3つ（issue 本文のとおり。どのリポジトリでも同じ）
   - これが完成したあとも、人が手を動かして埋める残りはどこか。
   - いま人や前の世代が暗黙にやっていて、目的の文に名前が付いていないものは何か。
   - 達成したかどうかを何の数で見るか。
2. 当たったテンプレートの必須の欄（テンプレートが無ければ「目的」と「作業内容」）
3. リポジトリの文脈の置き場で読んだもの。見つけ方は owner の明示の指示を優先し、無ければ入口の文書（`CLAUDE.md` / `AGENTS.md`）の案内をたどる。案内が無ければ「このリポジトリでは文脈の置き場が分からなかった」と出力に書く。
4. owner 特有の観点の枠。**受け渡し先を見つける方法が決まるまでは「未接続」と書き、推測で探さない**（設計SO 1本目 指摘12・推奨案6）。未接続であることが一覧に見えるので、「あの観点が無い」に気づける。

「どの観点で見たか」はこの一覧を出す。一覧が短いので、owner は欠けに気づきやすい。

### DJ-5 省く条件は2つだけにし、既存の認識合わせのコメントは1本のコマンドで状態まで読む（子の判定の具体形）

AI の側で「この issue は省いてよい」と判断する分岐は作らない（ゲート0 の結論1）。省くのは次の2つのときだけである。

1. **owner が要らないと言ったとき。** 委譲なら brief の欄に「省略（owner の指示）」と書いてある。
2. **確定版のコメントが既にあるとき。** 親が通した認識合わせを、子が独立にやり直さないためである。確定版は読んで前提にする。

既存の認識合わせのコメントは、次のコマンドで調べる。印（確定版か深掘り中か）で始まるコメントのうち**最後の1件**について、状態・投稿者の種類・見出しの数・URL を1行で返す。印の前の空白は許す（手で貼った場合を落とさないため）。印を話題にして引用しただけのコメントは、印が先頭に無いので拾わない。

```bash
gh issue view <番号> --json comments --jq '[.comments[] | select(.body | test("^\\s*<!-- issue-intake:(confirmed|pending) v[0-9]+ -->"))] | last // empty | [(.body | capture("issue-intake:(?<s>confirmed|pending)").s), (if (.authorAssociation | IN("OWNER","MEMBER","COLLABORATOR")) then "member" else "other" end), ([(.body / "\n")[] | select(startswith("### "))] | length | tostring), .url] | @tsv'
```

返った1行で次のように動く。**止まる場面ではやり直さずに依頼元（依頼元がいなければ依頼した人）へ知らせる。** 黙ってやり直すと、owner への2回目の提示になるからである（設計SO 2本目 指摘1・7）。

| 返った値 | 意味 | 動き |
|---|---|---|
| 空 | 認識合わせのコメントが無い | 自分で認識合わせを通す（DJ-7） |
| `confirmed`・`member`・見出し4以上 | 確定版がある | 読んで前提にし、自分では通さない |
| `pending` | 深掘りの途中である | 止まって知らせる。確定版が出るのを待つ |
| `other` | 候補はあるが、投稿者がリポジトリの所有者・メンバー・共同作業者ではない | 止まって「候補はあったが除外した」と知らせる |
| 見出しが4未満 | 印はあるが形が壊れている | 止まって知らせる |

**brief に認識合わせのコメントの URL があるときは、上のコマンドが返した URL と文字列として一致するかを見る**（設計SO 2本目 指摘8）。一致すれば上の表どおりに動く。一致しなければ（別のリポジトリ・別の issue・古い版を指している）止まって食い違いを知らせる。これで brief の経路と issue を探す経路の判定が1本のコマンドにそろい、URL だけを取る別のコマンドは要らない。

**この判定は「owner が確定させたこと」を証明しない。** 印と見出しと投稿者の種類で取り違えと第三者を除くだけで、owner の確認を暗号的に確かめる仕組み（GitHub Actions の bot や署名つきの受け渡し）は入れない。ゲート0 の結論6が「機械の検査で閉じようとしない」としていることと、確定版を投稿するのはスキル自身で、投稿は owner の実際の応答の後に限る（DJ-3 の5）ことによる。

**issue 本文が確定版のあとで書き換えられても、確定版は機械では無効にならない。これは運用で扱う**（ゲート3の判断5で owner が受け入れた）。本文を書き換えたら、owner か統括がこのスキルを通し直し、新しい確定版を別のコメントとして投稿する。最後の認識合わせのコメントが有効なので、子の判定は新しい確定版を拾う（深掘りに入れば深掘り中の版が最後になり、子は止まる）。brief に古い確定版の URL が残っていれば、探し方が返す URL と一致しないので、子は止まって食い違いを知らせる。機械で無効にしないのは、`gh issue view --json` が本文の最終編集時刻を返さず、判定のために GraphQL の手順を足すことになるからである。スキル本体には、この運用を「6. issue コメントに残す」の節に書く。

### DJ-6 別のモデルへの問い合わせは、自分と違うモデル1本に1回だけ、上限を決めて出す

規範はゲート0 の結論4のとおり「別のモデル」である（設計SO 1本目 指摘8で、「別の会社」に強めていたのを戻した）。**推奨**は、自分と違う会社のモデルを選ぶことである。同じ会社のモデルは同じところを見落としやすいからである。

手段はコマンド名で書き、hub 固有のパスは使わない。推奨する手段は `so-compare` の1レーンで、セッションのモデルごとに次のように選ぶ。

| セッションのモデル | 使うレーン |
|---|---|
| Claude | `--codex-only` |
| Codex | `--claude-only` |
| Cursor | 実際に動いているモデルと違う会社のレーン（Claude が動いているなら `--codex-only`、それ以外なら `--claude-only`） |

プロンプトは `-f` でファイルから渡す（issue 本文が長く、引数に直接書くと引用符で崩れる）。出力先は `-o` でリポジトリの外の一時ディレクトリにする（既定の `tmp/so-*` は、`tmp/` を git の対象外にしていないリポジトリでは追跡されうる）。

**待ち時間と採る件数に上限を置く**（設計SO 2本目 指摘9）。owner は提示を待っているので、待ち時間の上限を環境変数で短く渡す（例: codex は `SO_TIMEOUT=180`、claude は `SO_CLAUDE_TIMEOUT=180`）。`so-compare` は空で返ったときに1回だけ延ばして再試行するので、最悪の待ちは codex でおよそ450秒、claude でおよそ360秒になる。これを超えて待たない。返ってきた漏れから差分に混ぜるのは3件までにし、残りは件数だけを「どの観点で見たか」に書く。

問い合わせには issue 本文・3つの出力・観点の一覧を渡し、問いは「この一覧から漏れているものは何か。issue の目的を満たすのに要るのに、一覧のどこにも無いものを挙げよ。一覧にあるものの言い直しは挙げない。無ければ無いと書け」に固定する。返ってきたものは「［別モデル］」の印を付けて差分に混ぜ、owner が別に読むものは増やさない。**2周目はしない。** 返答が無ければ、出力に「問い合わせたが返答が無かった」と書いて進む。

**issue の内容を外へ送ることになる。** リポジトリの取り決めで外へ出せない内容なら、取り決めが許す別のモデル（社内の窓口や手元のモデルなど）に問い合わせる。**許されるモデルが1つも無いときだけ**問い合わせをせず、「どの観点で見たか」に「別モデルへの問い合わせ: できなかった（理由）」と書く。これは owner の1往復の中で見えるので、黙って飛ばしたことにはならない。3つの出力と owner の反応は必ず通る。

### DJ-7 応答する人がその場にいないセッションでは、出力を依頼元へ渡して待つ

委譲された子のペインには答える人がいない。確定版のコメントが無いまま子に issue が渡ったときの流れを、主体ごとに閉じる（設計SO 1本目 指摘11）。

| 順 | 主体 | 操作 | 終わった証拠 |
|---|---|---|---|
| 1 | 子 | 3つの出力までを作り、依頼元へ渡して待つ（渡し方は環境の取り決めに従う。hub なら `.oe/question-<issue>-<n>.md` と `oe-send`） | 問いのファイルと送信の記録 |
| 2 | 依頼元（統括） | 3つの出力を owner に見せ、実際の応答を受ける | owner の応答 |
| 3 | 依頼元（統括） | 確定版（合図が出たなら深掘り中の版）を issue コメントに投稿する | コメントの URL |
| 4 | 依頼元（統括） | 子へコメントの URL を送り、作業の再開を伝える | 送信の記録 |
| 5 | 子 | URL を DJ-5 の手順で確かめて読み、前提にして再開する | 子の episode の記録 |

これは確認の段を足すものではない。hub のフローでは親が子へ渡す前に認識合わせを通すので（DJ-9）、この経路は親が通し忘れたときの受け皿である。

### DJ-8 `question-driven-design` は、issue の口を消し、受け渡しを守り、戻り道を足す

直し方は4つある。

1. 「いつ使わないか」の「Issue とコードベースの一次情報から主要な設計分岐を解ける」を「コードベースの一次情報から主要な設計分岐を解ける」に直す。コードベースを読めば答えが出る問いを聞かない、というコア指示と同じ趣旨の部分は残す。issue があることだけで質問を飛ばす口は消える。
2. 同じ節に「`issue-intake` から深掘りの合図で受け渡されたときは、この節の条件で省かない」を足す。これが無いと、合図で受け渡した先で「既存パターンの踏襲で済む」などの別の行を使って質問を省けてしまい、合図が空振りする。
3. 「いつ使うか」に、issue に着手するときは先に `issue-intake` を通す旨を1行足す。
4. 「質問フェーズの完了」節に「`issue-intake` から受け渡されたときは、次のステップへ進む前に `issue-intake` の確定版の投稿へ戻る」を足す（設計SO 2本目 指摘2）。これが無いと、深掘りを終えたモデルはそのまま plan へ進み、深掘り中の版が最後のコメントのまま残る。子はそれを見て止まり続ける。

「いつ使わないか」の他の2行は変えない（範囲を最小にする）。

### DJ-9 規範の範囲と検査の範囲を、3つの層に分けて書く

規範の範囲と、それを見るゲート表の範囲は違う（negative knowledge `01KYJ76D7CS7EBY3WDYY1NS9Y2`）。さらに、仕様とゲート表は hub の中だけで読まれるのではなく、sync で配られてほかのリポジトリの作業からも参照される（設計の前提）。そこで3つの層に分ける（設計SO 1本目 指摘9）。

- **スキル本体が持つ規範**: どのリポジトリでも、issue を指して着手するとき全般。統括でも単独のセッションでも。
- **フローの仕様とゲート表が持つ検査**: この仕様（`document-format.md` のフロー）を採用する作業の中。親が作業に入る前と、子へ渡す前。hub はその採用例の1つである。
- **hub 固有の例**: `.oe/` や `oe-send` などは、スキルでも仕様でも補足の側に置く。

スキル本体は仕様に頼らずに動く形で書き、仕様の側からスキルを指す。ゲート表に合わせてスキルの範囲を狭めない（例えば「統括が委譲する前」だけに書き換えない）。

**(0) は2つの部分からなるものとして書き直す**（設計SO 2本目 指摘3）。issue 起点の認識合わせ（必須）と、設計判断が多いときの `question-driven-design`（従来どおり必要時）である。書き直しで従来の条件を消さない。

直す箇所と、入れる文の案は次のとおりである（文面は実装時に詰めるが、受入はこの案の要素の有無を見る）。

- `document-format.md`「遷移規則」節: 判定順の先頭に次の項を足す。これが無いと、判定順1で「設計判断が絡まない」と判断した issue が (0) を通らずに plan へ進める（設計SO 1本目 指摘4）。
  - 案:「0. **issue を起点にする作業か** — そうなら、入口層を選ぶ前に (0) の認識合わせを通す（入口は `issue-intake`・「ゲート配置」節）。通したあと、1〜5 は従来どおり判定する。確定版のコメントがあれば、それを読むことで (0) を通したことになる（委譲された子も同じ）。」
- `document-format.md`「ゲート配置」節:
  - 冒頭の説明文の「設計着手前の soft gate (0)（必要時）」を「着手前のゲート (0)」に直す。
  - 図の左端を「[着手前]」にする（案: `[着手前] --(0)--> [設計判断] --(1)--> …`）。
  - 図の下の箇条を直す（案:「- (0) は着手前のゲート。issue を起点にする作業では必ず通し（入口は `issue-intake`）、設計判断が多いときの `question-driven-design` は必要時のみ挿入する」）。
  - 表の 0 の行を直す（案: 位置「着手前（issue 起点は必須・それ以外は必要時）」、ゲート「issue 起点: 認識合わせの3つの出力を owner とすり合わせ、確定版を issue コメントに残す。設計判断が多い / 前提未確定 / 着手可能性が不明なとき: 人間と scope・考慮漏れ・着手可能性をすり合わせる」、routing「`issue-intake`（合図で `question-driven-design`）/ `question-driven-design` + `implementation-gate-rule`」）。
  - 表の下の段落を直す（案:「(0) は2つの部分からなる。issue 起点の認識合わせ（必須）と、設計判断が多いときの人間とのすり合わせ（必要時・soft）である。§10 遷移規則の判定順0 が前者に、『設計判断が多い → discussion（QDD 併用）』が後者に対応する」）。
  - (1)〜(6) の行は変えない。
- `doc-flow-guardrail`:
  - 「① フロー全体地図」の索引表に「issue 着手（issue 起点の作業の入口）」の行を足す。
  - routing 表の 0 の行と、表の前の説明文（「gate (0) は必要時のみ挿入する soft gate」）を上と同じ内容に直す。
  - 「② 委譲固定節テンプレ」の**可変節**（タスク）に「認識合わせ: [確定版コメントの URL ／ 省略（owner の指示）]」の欄を足す。子の省略判定（DJ-5）の入口がここになる。固定節は変えない。
- `CATALOG.md`: Skills の表に1行足し、見出しの件数を直す。Workflow Chains の「Issue → Branch → Worktree → Finish」の行に `issue-intake` を `issue-conventions` の次に挟む。

### DJ-10 スキル本体に hub の仕様とパスを持ち込まず、依存ごとに代わりの動きを書く

操作は規則で書き、ツールはコマンド名で書く。hub の具体例（`.oe/` の置き場、`oe-send`、蒸留の木、`document-format.md`）は最後の「補足: hub での具体例」節に降格する。本体の規則は、補足節を消しても成り立つように書く。

パスを書かないだけでは足りない。hub に無いリポジトリで依存が欠けたときの動きを、本体の「9. 手元に無いもの」節に書き、使う箇所からそこを参照させる（設計SO 1本目 指摘12・2本目 指摘11）。

| 依存 | 無いときの動き |
|---|---|
| `gh`（issue を読む・投稿する） | 止まって、issue を読めないことを依頼した人に伝える。投稿できないときは確定版の本文を出力し、貼ってもらう |
| 別のモデルへの問い合わせ手段（`so-compare` など） | DJ-6 の「許されるモデルが無い」と同じ扱いで、出力に書いて進む |
| 下書きの置き場の取り決め | リポジトリの外の一時ディレクトリに置き、パスを出力に書く |
| 依頼元へ返す手段の取り決め（委譲された側） | 最終の応答として3つの出力を返し、止まる |
| owner 特有の観点の受け渡し先 | 「未接続」と書く（DJ-4 の4） |
| 文脈の置き場の案内 | 「分からなかった」と書く（DJ-4 の3） |

受入の Step 1 で、補足節より前に hub のパスが無いことを機械で確かめる。依存が欠けたときの動きは、Step 8 の D1 に hub の外のリポジトリの形を1つ入れて確かめる。

## ステップ

実装はゲート3の後に始める。各 step の受入のうち、文書の変更を見る項には「変更前のファイルでは落ちる」根拠を書く（negative knowledge `01M2DRCP3QSG4NQWHNY6DSD3NJ`）。変更前に落ちない項は「回帰がないこと」「整合を見ること」の項として区別する。回帰を見る項の比較の相手は、この枝の分かれ目（`git merge-base HEAD master`）にする。動いていく master と比べると、この枝と関係ない正当な変更で落ちる（設計SO 1本目 指摘13）。古い文が消えたことだけを見る項には、新しい文があることを見る項を対にする（設計SO 2本目 指摘12）。
