# #412 issue-intake の出力に「なぜやるか」の1文を足す

## 背景

`issue-intake` の3つの出力は、「この issue でやること」の最後に「望む結果」（終わったあとの状態＝後）を1文で書く。しかし、issue を作るきっかけになった出来事と、それがどこから来たか（前）は書いていない。2026-10-16、#412 自身の認識合わせで owner は、やることは分かったが「なぜやるのか、どこから来たのか」を思い出せず、issue を見に行った。owner の言葉は「行数とは関係なく、参照先の経緯は思い出せない。思い出せないことが違和感」である。

スキルは「issue の要約は出さない」と決め、その理由を「owner が既に知っていることを読ませると、違和感の検査が薄まる」に置いていた。owner が経緯を覚えているという前提が外れていた。前と後を並べると、やることがきっかけを解決するかを確かめやすくなる。

**この plan は、#412 の本文と確定版で決まった「やること」3点と「範囲」を正本として扱い、覆さない。** この plan が決めるのは、本文の「plan で決めること」3点への答え、スキルの直し方（文面）、受け入れ基準である。

**この plan は設計SO（ゲート2・Codex 1レーン）の指摘で直した。** 何を採り何を退けたかは「設計SO（ゲート2）」節に書く。

## この plan の範囲

- 直すもの: `canonical/skills/issue-intake/SKILL.md` の「3. 3つの出力」節（説明文・出力の形の例）と、「6. issue コメントに残す」節の確定版の形の例。確定版の形の例は「3. 3つの出力」節の外（6 の中）にあるが、issue の「範囲」が「出力の形の例と、確定版の形の例の両方に入れる」と書いているので対象に入る。

## 確定版と本文の「plan で決めること」3点への答え

### (1) 「なぜ」の1文を、20行の目安でどう数えるか

**20行の目安の数には入れる。やること本体の「1〜3文」の数には入れない。** 目安は「3つ合わせて（「なぜやるか」と「望む結果」の行を含めて）20行以内」と書き、特別な数え方を作らない。文数のほうは、スキルの親箇条に「やること本体を1〜3文で書く。最初に置く『なぜやるか』と最後に置く『望む結果』の各1文は、この文数に含めない」と明記する（設計SO の指摘2で足した）。判断は DJ-1。

### (2) 「owner が数十秒で判定できる大きさ」の言い方を外すか

**外す。** 20行の目安は残し、その理由を「超えるなら、それ自体が深掘りの材料になる」だけにする。判断は DJ-2。

### (3) 終わったかどうかの確かめ方

**2層にする。** この PR の受入は、変更そのものを見る静的な項目（下の「受入」節・grep で閉じる）で閉じる。owner の「望む結果」（issue を見に行かずに済む）は、マージ後に統括が次の intake で実物1回を確かめ、観測の結果ごとの扱い（達成・未達・効き目未確認）を決めたうえで #412 のコメントに記録する。この PR の中では確かめられない（応答する人がいない）。判断は DJ-4。

### 確定版の「望む結果」への答え

「owner が issue を見に行かなくても、出力だけで『なぜやるか』が分かる」は、確定版の「達成を見る数」（owner が出力を読んだあとに、経緯を思い出すために issue を見に行った回数。今回1回で、0回にしたい）で見る。数を取る場は上の (3) の実物の確かめである。この plan は、その数を取れる形（出力に「なぜ」の行が必ずある形）をスキルに置くところまでを受け持つ。

## 設計判断

### DJ-1 「なぜ」の1文は「この issue でやること」の最初の箇条に置き、20行の目安の数に入れ、やること本体の文数には入れない

- **置き場**: 「この issue でやること」の最初の行に `- なぜ: <1文>` を置く。見出しにはしない。
  - 前（なぜ）と後（望む結果）を同じ節に並べる。issue 本文が「前と後を並べると、やることがきっかけを解決するかを確かめやすくなる」と書いている。
  - 見出しの数を4つに保つ（1-2 が見出しの数を数える）。
  - #412 の確定版コメントと同じ形である。owner が受け入れた実例に合わせる。
- **20行の数え方**: 目安の数に入れる。目安は「超えたら深掘りの材料」という印であり、固定の行を除く特別な規則を足すと数える手順が増える。「望む結果」の行は今も数に入っている（除くとは書いていない）ので、同じ扱いにする。本体に使える行が2行減るが、目安であって上限ではない。
- **やること本体の「1〜3文」との関係**: 「なぜ」の1文と「望む結果」の1文は、やること本体の1〜3文の外である。**これをスキルの文面に明記する。** 「最初に」「最後に」という位置の指示だけでは、全体を3文に収めて本体を1文に圧縮する読みが残る（設計SO の指摘2）。親箇条を「やること本体を1〜3文で書く。最初に置く『なぜやるか』と最後に置く『望む結果』の各1文は、この文数に含めない」にする。
- **棄却した案**:
  - (a) 見出しの外（出力の1行目・「この issue でやること:」の前）に置く。3つの出力の外に4つ目の要素ができ、前と後が離れる。「（#N と判断した）」の行と混ざる。
  - (b) 目安の数から除く。規則が1つ増え、数えるときに行を選り分けることになる。
  - (c) 目安を21行に上げる。1行の違いに意味が無い。20は「数十秒」の根拠を外したあとは丸い目安でよい。

### DJ-2 「owner が違和感の有無を数十秒で判定できる大きさである」の文を外し、20行の目安は「超えたら深掘りの材料」の印として残す

- **外す理由**: owner の判断（時間がかかること自体は重要な要素ではない。#412「追わないこと」）と合わない。実物でも満たしていない（#403 D2）。残すと、書く側が圧縮に倒れ、足した「なぜ」の1文を削る方向に効く。brief の negative knowledge `01M486Z2ND07GQWV1GHS1SVB0J`（足した運用の効き目を打ち消す側を同じ変更で探せ）に当てて見つけた、節の中の打ち消す側である。
- **20行を残す理由**: 行数の目安そのものは #412 の範囲外である（「追わないこと」は行数から複雑さへの置き換えを追わないと言っており、目安を消すとは言っていない）。「超えたら深掘りの材料」という機能は、時間と無関係に残る。20行は深掘りの必要を証明する閾値ではなく、立ち止まる目安である（設計SO の指摘3）。「20行なら十分」とは読ませない。
- **棄却した案**: 20行の目安も外す。issue の範囲外で、長すぎることに気づく機械的な手がかりが無くなる（深掘り中の版で統括が挙げた懸念）。

### DJ-3 「issue の要約は出さない」は残し、理由は差し替えず、出さない範囲と「なぜ」の1文との区別を同じ段落に書く

- **理由は足さない**: 「owner が既に知っていることを読ませると」を外す（issue の指示）。最初の案は「要約は当たっていても指せる箇所が無く」に差し替えるものだったが、設計SO の指摘4で退けた。数・出来事・対象の名前を含む具体的な要約なら誤りを指せるので、この理由は一般化しすぎている。スキルの 136 行が問題にしているのは「曖昧で当たっている文」であって、要約一般ではない。根拠の無い理由を置き換えるより、出さない範囲を明確にするほうが安全である。
- **出さない範囲を書く**: 「issue 本文の目的や作業内容を並べ直した説明は付けない」。
- **区別を書く**: 「なぜやるか」の1文は、きっかけになった具体的な出来事とその出所だけを書くもので、この要約には当たらない。「要約は出さない」が「なぜ」の1文を書かせない方向に効きうる（brief の knowledge item の予測どおり、足した節の中にある止める規則）ので、その場で区別を書く。「なぜ」の1文も出来事を短くまとめる以上、普通の意味では要約になりうる（設計SO の指摘4）。だから「要約かどうか」ではなく「何を並べ直すか（本文の目的・作業内容）」と「何だけを書くか（出来事と出所）」で線を引く。
- **issue の指示より一歩多いこと**: issue は「理由を外す」とだけ言う。区別の1文を足すのは、足した規範（なぜの1文）と既存の規則（要約は出さない）の衝突を防ぐためで、設計SO もこの範囲の追記は合理的とした。owner がこれを望まなければ、区別の1文を外す（下の「リスク」）。
- **棄却した案**: (a) 理由を「指せる箇所が無い」に差し替える（上記）。(b) 理由も区別も書かず、規則だけ残す。足した「なぜ」の1文を「要約」として削る読みが残る。

### DJ-4 終わったかの確かめは2層にし、PR の受入は変更そのものを見る項目で閉じ、実物の確かめはマージ後の follow-up にして観測の結果ごとの扱いを決めておく

- 確定版の「望む結果」は上流が固定した受入の境界で、「どこまで確かめるか」を決めている（brief の negative knowledge `01M2DEC1G68X8PH2QEW2H1DWZZ`）。それだけを写すと、スキルを1行も変えなくても通る受入になる。だから、変更後の文面を固定文字列で見る項目を別に立てる（下の「受入」節）。これは境界を広げない（その場の grep で閉じる）。
- **実物の確かめ**: 次に intake を使うのは統括で、owner がいる場である。この委譲には応答する人がいない（スキルの 1-3）ので、PR の中ではできない。行き先はマージ後の統括で、次の intake で次の2つを #412 のコメントに記録する。
  - (a) 出力の「この issue でやること」の最初に「なぜ」の行が入っているか。
  - (b) owner が出力を読んだあとに、**経緯を思い出すために** issue を見に行ったか。別の目的で開いたものは数えない。出力だけで分かったか、記憶で答えたかも分けて書く。
- **観測の結果ごとの扱い**（設計SO の指摘5で足した。記録しただけで close に進まないため）:
  - 達成: (a) が入っていて、(b) で owner が出力だけで分かり、見に行かなかった。#412 を close してよい（判断は owner）。
  - 未達: (a) が入っていない、または owner が経緯を思い出すために見に行った。統括は未達として owner に返し、次の対応（スキルの 8 の行き先1で固定の問いに足す・説明文の例を足す・別の issue）を owner が決める。#412 は keep-open。
  - 効き目未確認: owner が記憶だけで答えられ、出力の「なぜ」が効いたか分からない。次の intake でもう1回だけ記録する。
- **棄却した案**: 子セッションで非対話に intake を走らせて測る（#403 の D1 の形）。「なぜ」の行が出るかは測れるが、owner が見に行かずに済むかは測れない。弱 SO の小さな変更に対して重い。

### DJ-5 印の書式の版（`v1`）と 1-2 の判定は変えず、規範の範囲とゲートの範囲が一致しないことと、規範の適用時点を明文で書く

- 1-2 は見出しの数だけを見る。箇条書きの追加は見出しの数を変えない。`v1` は「後で見出しの文言を直しても古い確定版を読めるようにする」ための版で、今回は見出しを直さないので上げない。
- brief の negative knowledge `01KYJ76D7CS7EBY3WDYY1NS9Y2`（規範の適用範囲と、検査するゲートの範囲は別々に決めよ）に従い、2つを分けて書く。
  - 規範「『なぜやるか』の1文を書く」が適用される範囲: **マージ後に新しく作る、または更新する出力**（提示（5）・深掘り中の版・確定版（6））のすべて。
  - 規範が適用されない範囲（設計SO の指摘6で足した）: 既存の確定版（#403〜#414 の分）への遡及の補記は求めない。「なぜ」の行が無いことだけを理由にした通し直しも求めない（通し直す条件はスキルの 6 の最後のとおり、本文の書き換えか内容の変化である）。
  - ゲート 1-2 が見る範囲: 見出しの数だけ。「なぜ」の行の有無は見ない。
  - 一致しない。「なぜ」の欠けを見つけるのは、owner の読み（違和感）と DJ-4 の実物の確かめである。
- **棄却した案**: 1-2 に `- なぜ:` の有無を足す。判定の手順は変えない（issue の「範囲」）。古い確定版が「なぜ」の行を持たないので、足すと古い確定版が壊れた形に読まれる。

## ゲート1（ゼロベース代替探索）

この plan の判断の多くは issue と確定版で方向が決まっているので、設計SO に回したのは DJ-1〜DJ-5 の形の判断である。ゼロベースでは、やり方そのものの代替を次のとおり挙げて退けた。

- **B: 出力の先頭に issue 本文の「目的」節をそのまま引用する。** 要約・引用を出す形で、「要約は出さない」と衝突し、owner が指せない文が増える。
- **C: 「望む結果」を「前→後」の1文に合成する（「Xだった場面が、Yになる」）。** 1文に2つ入り、前が外れたときに指しにくい。owner は前と後を並べて噛み合いを見たいと言った（issue の「きっかけ」節）。
- **D: スキルを変えず、統括が運用で書く。** #412 の確定版は統括がそうした。だが次の統括・子へは渡らない（スキルに無い運用は交代で落ちる）。
- **E: 「なぜ」を「issue に書いていないが要ること」の側に置く。** きっかけは issue 本文に書いてあることが多く、「書いていないこと」の節に置くと意味が合わない。

#!/usr/bin/env bash
# #412 の受入の検査。worktree の root で実行する。
#   引数なし: 作業ツリー（変更後）を検査する
#   引数あり: その commit を検査する（変更前は 00cf5a3）

set -u
F=canonical/skills/issue-intake/SKILL.md
BASE=00cf5a3
ref="${1:-}"

src_of() { if [ -n "$1" ]; then git show "$1:$F"; else cat "$F"; fi; }
count() { src_of "$ref" | grep -c -F -- "$1"; }
fail=0
chk() { # chk <id> <expected> <actual>
  if [ "$2" = "$3" ]; then echo "PASS $1 ($3)"; else echo "FAIL $1 (expected $2, got $3)"; fail=1; fi
}
# 出力の形の例（最初の ```text ブロック）と確定版の形の例（印から次の閉じまで）
text_blk() { src_of "$ref" | awk '/^```text$/{f=1; next} f&&/^```$/{exit} f'; }
conf_blk() { src_of "$ref" | awk '/<!-- issue-intake:confirmed v1 -->/{f=1} f&&/^  ```$/{exit} f'; }
# 「この issue でやること」の直後の行が「- なぜ:」で始まれば 1
first_is_naze() { awk 'hit{ sub(/^ +/, ""); print (index($0, "- なぜ:") == 1) ? 1 : 0; exit } /この issue でやること/{hit=1} END{ if (!hit) print 0 }'; }

# 変更を検出する項目（変更前は FAIL）
chk D1  1 "$(count '**issue の要約は出さない。** issue 本文の目的や作業内容を並べ直した説明は付けない。「なぜやるか」の1文（下記）は、きっかけになった具体的な出来事とその出所だけを書くもので、この要約には当たらない。')"

chk D4  1 "$(count '  - 最後に **望む結果**（後）を1文で書く。「なぜやるか」に書いた前の状態が、終わったときにどうなっているかである。やることの手段ではなく、解決されたあとの状態を書く。前と後を並べると、やることがきっかけを解決するかを確かめやすくなる。')"
chk D5  1 "$(count '3つ合わせて20行以内を目安にする（「なぜやるか」と「望む結果」の行も数に入れる）。超えるなら、それ自体が深掘りの材料になる。')"
chk D6  1 "$(text_blk | grep -c -F -- '- なぜ: <issue を作るきっかけになった出来事と、それがどこから来たか・1文>')"
chk D7  1 "$(text_blk | grep -c -F -- '- 望む結果: <前の状態が、終わったときにどうなっているか・1文>')"
chk D8  1 "$(conf_blk | grep -c -F -- '- なぜ: …')"
chk D9  1 "$(text_blk | first_is_naze)"
chk D10 1 "$(conf_blk | first_is_naze)"
chk D11 0 "$(count 'owner が既に知っていること')"
chk D12 0 "$(count '数十秒')"
chk D13 0 "$(count 'きっかけの場面（それが起きた場面）が、終わったときにどう変わっているか')"
# 番兵（変更前後とも PASS）
chk S1  4 "$(conf_blk | grep -c '^  ### ')"
chk S2  1 "$(count "gh api --paginate 'repos/<owner>/<repo>/issues/<番号>/comments?per_page=100' --jq")"
outside() { src_of "$1" | awk '/^## /{name=$0} !(name ~ /^## 3\. / || name ~ /^## 6\. /){print}'; }
if diff -q <(outside "$BASE") <(outside "$ref") >/dev/null; then echo "PASS S3"; else echo "FAIL S3 (差分が 3・6 節の外にある)"; fail=1; fi
exit $fail
```
