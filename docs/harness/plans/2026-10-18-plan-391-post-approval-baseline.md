# #391 承認のあとに plan が変わったときの扱いを規範に書く

## 背景

委譲の plan を owner が承認するとき（ゲート3）、統括は完了前の照合（`unmet-gate-check`）のために baseline を承認の記録に残す。対象は plan・委譲時の書面・ゲート表の版の3つで、いまは sha256 の digest で固定している。ところが承認のあとに plan を直すと digest が動く。#347（2026-09-11）では owner の裁定が「採らない理由を plan に1行残せ」という形をしていたため、裁定に従うこと自体が baseline を動かした。その後は、裁定より、実装SO・Copilot・完了前の照合の指摘で plan を直したときと、進捗の記録（済み印・実測値・status）で動くことのほうが多い。10-08 以降だけで取り直しが7回（#429 で4回・#412 で3回）、owner への再承認の依頼が3回（#412）あった。

逆向きの害も出ている。#390 では「digest が動いたら申告せよ」の規律を子が凍結の指示と読み、実装が2本進んでも plan の済み印と `status` を一度も動かさなかった。#411 では子が承認のあとに plan へ足しかけた節を baseline と食い違うので戻し、plan の表の誤りも直さずに残した。凍結を守る規律と、進んだことを書く規律が、同じ対象の上で衝突している。

**この plan は、#391 の本文と確定版で決まった「やること」と「範囲」を正本として扱い、覆さない。** この plan が決めるのは、推奨する案と棄却する案の理由、確定版の「issue に書いていないが要ること」7項目への答え、4つのスキルの直し方（文面）、受け入れ基準である。どの案にするかは、ゲート3 で owner が決める。

**この plan は設計SO（ゲート2・Codex 1レーン）の指摘で直した。** 何を採り何を退けたかは「設計SO（ゲート2）」節に書く。

## 承認のあとに plan が変わる形の分類（観測から）

## 推奨の案と、棄却した案

| 案 | 内容 | 採否 | 理由 |
|---|---|---|---|
| A | 今の形を明文化する（従ってよい・変化を申告・親が差分を実見して張り直す） | 一部を採る | 子の申告と統括の差分確認は残す。ただし A だけでは「digest を計算し直す」「何を見て張り直すかが統括の目」「owner に聞く線引きが無い」の3つが残り、確定版の望む結果（統括と owner の手間が減る）に届かない |
| B | baseline を承認時のコミット SHA で取り、照合は差分に対して行う | 採る（組み合わせの形で） | 統括が実際に行った判断は差分に対するもので、digest はその入口だった。commit で固定すれば plan の内容は git が持ち、digest を別に計算する必要が無くなる。B だけでは機械的な一致確認を失うので、下の組み合わせにする |
| B + digest | コミットで固定し、digest（git の blob の一致）は「記録された版から変わったか」の検知にだけ使う | **推奨** | 一致確認は残る（照合役は有効な版との一致と entry の形式だけを見る）。差分の判定は統括が照合の前に済ませ、受け付けた版を張り直しの entry に残す。digest の算術が消え、子が計算していない値を報告に書く穴（#390）も閉じる |
| C | 承認後の plan 編集を禁じ、裁定は committed な追補文書だけに置く | 棄却 | 進捗の記録（済み印・status）は plan の型が要求するので、禁じると #390 の凍結がそのまま規範になる。#347 では追補だけに置くと plan だけを読む人が裁定へ到達できなかった。読む場所が2つに割れる |
| D | 承認後に plan が変わったことを機械で親へ通知する | 棄却（この単位では） | 通知しても「どう扱うか」は決まらないので、規範が先に要る。仕掛けは #291（起動を保証する層）の領分で、この単位はスクリプトを触らない |
| E（ゲート1 で出した） | 承認した plan を不変にし、進捗と変更を別の committed 文書（plan の追補）に置く | 棄却 | C の committed 版。読む場所が2つに割れる点は同じ。plan の済み印の型と衝突する |
| F（ゲート1） | baseline の対象をステップ節だけに縮め、ほかの節は自由にする | 棄却 | 要件の弱体化は受入や DJ の節でも起きる（#412 D4 は受入の節）。ステップ節だけを守ると見えない |
| G（ゲート1） | 補正の受け付けを統括に任せるかどうかを、委譲ごとに owner が brief で選ぶ | 棄却（規範に欄は足さない） | 既定は統括で足りる。owner がある単位で全部を見たいなら、ゲート3 の裁定でそう言えば足りる。欄を足すと固定節が厚くなる |
| H（ゲート1） | 進捗の記録だけ digest の対象から外す（済み印と status を正規化して計算する） | 棄却 | 「完了」の注記や実測値の書き込みは正規化できない。正規化の規則が増えるほど、照合役が内容を判断する側に寄る |
| I（設計SO が出した） | owner が承認する正本を型付きの契約（義務 ID・要件・依存・ゲート・終端・範囲）にし、進捗は義務 ID に結んだ実績データに置き、plan は両者から生成する | 棄却（この単位では・将来案として残す） | 型・生成器・運用の変更が要り、4スキルの文面の改訂を越える。#291 の Alt-7（承認時の義務コンパイル）と同じ方向なので、統括が #291 にコメントするときに添える |

## 設計判断

### DJ-1 案B の組み合わせの形（コミットで固定し、一致は変化の検知にだけ使う）を採り、A の申告の規律と #390 の「禁止／必要」の分け方を組み込む

- 承認時の baseline は、plan については**承認時の commit** で固定する。plan の内容は git が commit ごとに持つので、sha256 を別に計算しない。「plan 全文（`status:` 行を除く）」と「ステップ節」の2つの digest を取る今の手間は無くなる。
- 一致確認は残す。完了前の照合は「plan のいまの内容が、承認の記録の**有効な版**と一致するか」を見る（git の blob の一致で足りる）。有効な版は、承認時の commit か、最後の張り直しの entry が指す commit である。
- 差分の判定は照合役ではなく統括が、照合の前に行う。受け付けたら承認の記録に entry を足す（変更前後の版・級・出どころ・確かめた項目それぞれの結果・受け付けた主体・級が変更なら owner の再承認の参照）。
- **棄却した読み**: 「digest をやめて差分だけを見る」（B 単独）。一致確認が無いと、申告の無い変更を照合役が見つけられない。
- **棄却した読み**: 「digest はそのまま、再承認だけ減らす」（A の強化）。digest の算術と、子が計算していない値を書く穴（#390 の knowledge `01M25B813S5ZD07QK92EF3D9PV`）が残る。

### DJ-2 承認のあとの変わり方を効果で3つの級に分け、級ごとに受け付ける主体を決める。まず「変更」に当たるかを見て、残りを「補正」とする

| 級 | 何が当たるか | 誰が受け付けるか |
|---|---|---|
| 記録 | 済み印・実施の結果・実測値・`status`・SO やレビューの結果の節。承認した内容そのものは変わらない | 子だけで進めてよい。申告も受け付けも要らない。報告に最新の commit を書く。統括は照合の前に差分を確かめ、記録だけならその版を張り直しの entry に足す |
| 補正 | 承認した内容の文面は変わるが、母集団（step 集合・要件・ゲート・終端）と owner が決めたことを変えず、新しい結果・対応範囲・作業義務も足さない直し。裁定や指摘を plan に書き込む・承認済みの結果を確かめる検査を強める・DJ の細部の訂正・衛生の置き換え・文言や構成の整理 | 子が申告して進めてよい。統括が次の報告で差分を項目で確かめて受け付け、張り直しの entry を足す。変更と判定したら子に止めさせて owner に戻す。owner の再承認は要らない（完了の報告で一覧を見せる） |
| 変更 | step を削る・要件や受入を弱める・ゲートを飛ばす・終端を書き換える・新しい作業義務や設計判断や対応範囲を足す（承認した文面の外の変更で振る舞いが変わるものを含む） | **実行する前に**統括へ照会し、owner の再承認を経る。plan の更新・再承認・張り直しの entry までを1単位にする |

- **判定の順序**: まず「変更」に当たるかを見て、当たらない残りを「補正」とする（設計SO の指摘1）。「受入を強める」は、承認済みの結果を確かめる検査の補強に限る。確かめる対象（対応環境・結果の種類）を増やす直しは、文面が「強める」でも変更である。
- **混合**: 1つの直しに級が混じるなら分けて見て、重い側で扱う（設計SO の指摘8）。
- **構成の整理**: step の分割や DJ の番号の整理は、新しい義務や判断を足さなければ補正である。ただし申告で、元の義務がどこへ移ったかを対応づける（設計SO の指摘2。一覧の項目1 に書く）。
- 級は**出どころで決めない**（確定版の項目1 の答え）。owner の裁定で直しても、裁定が「理由を1行残せ」なら補正であり、裁定が「人のゲートを外す」なら owner 自身が決めた変更である。SO や照合の指摘で直しても同じ。
- **迷ったら重い側に置く**（`document-format.md`「遷移規則」節の判定順3 と同じ向き）。補正か変更か迷うなら変更として owner に聞く。
- #390 の統括が分けた「禁止」（母集団を壊す変更）と「必要」（進捗の記録）は、それぞれ「変更」と「記録」に当たる。この分け方は作業層と #390 の episode にしか無かったので、ここで規範に入れる。
- 「記録」は変えるたびに受け付けを求めない。求めると #390 の凍結が戻る。統括の1回の差分確認（照合の前）で足りる。
- **補正は申告して進めてよい**（統括の受け付けを待たない）。#412 の子は D4 を直してから報告し、統括はその報告で受け付けた。待たせると往復が1回増え、確定版の望む結果（手間が減る）に逆行する。統括が変更と判定したときの戻り作業は、補正が定義上小さいので限られる（下の「リスク」）。
- **級の名前**: 記録・補正・変更の3語を使う。「変更」が総称と重い級の両方に使われる取り違え（設計SO の指摘10）を避けるため、総称は「plan が変わる」「変わり方」「変化」と言い、「変更」は級の名前にだけ使う。SO の提案（進捗記録・範囲内補正・再承認変更）は、繰り返し書く固定節では長い。
- **棄却した案**: 2つの級（禁止と必要）だけにする。#412 の再承認1・3 と #429 の張り直し1・2・4 のような「文面は変わるが母集団は変わらない」直しが、どちらにも入らず owner に戻る。実例の11件中8件がこの中間である。
- **棄却した案**: 級を節で決める（ステップ節が変われば変更、ほかの節なら補正）。受入の節で要件が弱まる（#412 D4 の逆）形を見逃す。効果で決める。

### DJ-3 owner の再承認は「変更」の級だけに求め、記録と補正は統括の受け付けで足りるとする

- 線引き（確定版の項目2 の答え）は DJ-2 の表の「変更」の列である。承認の対象、つまり owner が決めたこと・この単位がやること・照合の母集団のどれかが変わるときだけ owner に戻す。
- 「新しい作業義務や設計判断や対応範囲を足す」を変更に入れるのは、#412 再承認2（承認した5か所の外の既存の文を直す）と #429 再承認（新しい判断と step）が、実際に owner が決めるべきものだったからである。母集団を減らす側だけを変更にすると、増やす側が統括の判断で通る。
- 統括は補正を受け付けたら、完了の報告で owner に entry の一覧を見せる。owner がそこで異を唱えたら、その項目はその場で変更の級として扱い直す（取り消すか、再承認する）。統括の級の判定の誤りは、ここで owner が捕まえる。
- **棄却した案**: すべての plan の変化に owner の再承認を求める（今の読み）。#412 で3回のうち2回は聞かなくても同じ結果になる種類で、owner と統括の手間が増えるだけだった。
- **棄却した案**: 統括がすべてを受け付け、owner には何も戻さない。「変更」の級は owner が決めた内容を変えるので、統括が受け付けるとゲート3 が実質的に消える。

### DJ-4 baseline の記録の形。plan は承認時の commit、委譲時の書面は digest、ゲート表は版の commit。張り直しは entry で版を進める

- plan: 承認時の commit（枝に push 済みのもの）。張り直しの entry ごとに commit を進める。有効な版は最後の entry。
- 委譲時の書面（brief）: 作業層にあって commit できないので、全体の digest（アルゴリズムと一緒に）で固定する。承認のあとに変わることは稀だが、変われば plan と同じ級の規則で受け付けて entry を足す（#429 では統括が注記の HTML コメントだけを直し、注記を残した）。
- ゲート表の版: `doc-flow-guardrail` と `document-format.md` が入っている master の commit で固定する。照合ではその commit の対象パスから取り出した内容を使い、いまの作業ツリーの表を読まない（設計SO の指摘7。版を記録しても、照合に使う表をいまのファイルから読めば差し替わりを検出できない）。取り出せなければ `invalid-baseline`。
- 3つの対象の射程（確定版の項目5 の答え）: 級の規範が当たるのは plan と委譲時の書面である。ゲート表は版で固定し、級の対象にならない。
- 張り直しの entry が持つもの: 変更前と変更後の版（plan の commit か書面の digest）・級・出どころ（裁定・SO・Copilot・照合・進捗など）・確かめた項目それぞれの結果（DJ-6 の一覧）・受け付けた主体（統括か owner）。級が変更なら owner の再承認の参照も持つ。欠けた entry は照合で無効になる（DJ-5）。
- **棄却した案**: 承認の記録を committed にする。置き場の統一は範囲外で、いまの作業層の裁定の文書で動いている。
- **棄却した案**: plan の digest を残して commit と併記する。commit が分かれば blob は `git rev-parse <commit>:<path>` で引けるので、併記は手間を増やすだけである。

### DJ-5 `unmet-gate-check` の手順1 は「有効な版との一致」と「entry の形式」に置き換え、照合役は級を判定しない。規範の範囲と検査の範囲が一致しないことを明文にする

- 手順1（確定版の項目3 の答え）: 承認の記録から plan の有効な版を読み、いまの内容と一致するかを比べる。委譲時の書面は記録された digest を再計算して比べ、ゲート表は記録された commit の対象パスから内容を取り出して使う。1つでも一致しなければ `invalid-baseline`。
- **entry の形式検査**（設計SO の指摘3）: 有効な entry は、変更前後の版・級・出どころ・確かめた項目それぞれの結果・受け付けた主体をすべて持ち、級が変更なら再承認の参照を持つ。欠けた entry や参照が引けない entry が指す版は、記録に存在しないものとして `invalid-baseline` である。これで「照合の直前に版だけを指す entry を足して通す」形は形式として弾ける。
- **正直に書くこと**: 照合役は級や確かめた結果の妥当性を判断しない。したがって、誤った級で受け付けた変更や虚偽の結果は照合では捕まらない。受け皿は、統括の受け付けと、owner が完了の報告で entry の一覧を見ることである。最初の案の「再承認を経ない変更は `invalid-baseline` として現れる」は強すぎたので、「entry の無い変化は現れる。誤った級で受け付けた変化は現れない」に直した（設計SO の指摘3）。
- 照合役は級を判定しない。一致しない理由（申告の無い変更か、受け付けたのに entry を足していないか）を分けるのは統括の仕事である。したがって、規範が当たる範囲（3つの級すべて）と照合役が検査する範囲（有効な版との一致と entry の形式）は一致しない。これを本文に書く（knowledge `01KYJ76D7CS7EBY3WDYY1NS9Y2` の行動変更 (3)）。
- #291 への影響: Alt-7（承認時の義務コンパイル）の前提が「承認時に1回」から「張り直しごとに再コンパイル」に変わる。観測項目「digest 不一致の発生頻度」は「張り直しの回数と級の内訳」になる。設計SO の案I（型付きの契約から plan を生成する）は Alt-7 と同じ方向なので、同じコメントに添える。この単位は #291 を直さない。統括がゲート6 で #291 にコメントする（「マージ後に統括へ渡すこと」）。
- **棄却した案**: 照合役に「記録の級の差分なら通す」を判定させる。済み印の正規化は機械的だが、「完了」の注記や実測値の書き込みは内容の判断になる。照合役を判断の側に寄せない（本スキルの射程「照合であって判断ではない」）。

### DJ-6 差分を見る項目の一覧の正本は `implementer-contract` に置き、子が申告のときに自分で確かめ、統括が同じ一覧で確かめる

- 一覧（確定版の項目6 の答え）は8項目で、「直す箇所と直し方」の 7 にある。step 集合（分割や改名は元の義務の行き先を対応づける）・各 step の要件・ゲートの項目・終端 step・受入・設計判断の結論・範囲・追加（新しい結果・対応範囲・作業義務を要求する追加が無いこと）。最後の1項目は設計SO の指摘1 で足した。最初の7項目は削除と弱体化しか見ておらず、対応範囲の追加が「強める補正」として通った。
- 置き場を `implementer-contract` にするのは、子が申告のときに自分で当てる一覧と、統括が確かめる一覧を1つにするためである。2か所に書くと drift する（#289 の「同じ契約を3箇所に重複して書いていた」の教訓）。`doc-flow-guardrail` の注記と `unmet-gate-check` からは参照する。
- `unmet-gate-check` に置かないのは、照合役が級を判定しない（DJ-5）からである。一覧を照合役の文書に置くと、照合役が差分を判定する側に読まれる。
- 「承認済みの節を書き換えず、末尾の「ゲート3 のあとの変更」節に置く」は、一覧の項目ではなく推奨として書く。#412 以来の慣行で、diff を読みやすくするためのもので、守らなくても級は変わらない。
- **棄却した案**: 一覧を `doc-flow-guardrail` の注記に置く。枠は薄く保つ（DJ-11 二層）。注記はすでに長い。

### DJ-7 ゲート3 の性質は変えない。注記の末尾の文を、再承認の条件を限ることが性質の変更でないと読めるように書き直す。打ち消す側は3か所と、確かめた3か所

- ゲート3（plan → 実装の owner HG・§11 の行3）はそのままである。実装に入る前に owner が plan を承認する、は変わらない。
- 変えるのは、承認のあとに owner へ戻す条件である。今の文「plan の更新 → 再承認 → baseline の再記録を1単位にする」は、plan の内容が変わるたびに再承認が要ると読め、統括はそう運用した。新しい文は、再承認が要るのを「変更」の級に限る。承認の対象を変えないものに再承認を求めないのは、ゲート3 を弱めることではない。
- **打ち消す側を同じ変更で直す**（knowledge `01M486Z2ND07GQWV1GHS1SVB0J`）。「1単位にする」の文は3か所（`unmet-gate-check`・`implementer-contract`・`delegate-task`）にあり、どれか1つが残ると「変更の級だけ」を打ち消す。3か所すべてを直す。注記の「gate 3 そのものの性質（owner HG）は変わらない」は残し、括弧の中に「再承認の条件を変更の級に限るのは性質の変更ではない」を足す。
- **設計SO（指摘4）が `grep` で見つけた3か所**:
  - `unmet-gate-check` の「渡すもの（clean）」の表の plan と書面の行は、clean の理由を「承認時点で確定した書面」と書いている。新しい形では統括が受け付けた後続の版も入力になるので、初回の承認版しか許さない読みが残る。**直す**（「承認の記録の有効な版として確定した書面」に。直す箇所 1）。
  - `implementation-gate-rule` の「調査結果を報告したあとは、明示の承認なしに修正へ進まない」と「code change には規則と配布物の変更を含む」。この規則は**実装を始める承認**（ゲート3）の条件を決めている。補正は承認された実装の範囲の中の直しで、実装を始める承認をやり直すものではない。変更（新しい義務や範囲を足す）は再承認を要するので、この規則と同じ向きである。文面は変えず、`implementer-contract` の節に「補正は承認された実装の範囲の中の直しで、実装を始める承認をやり直すものではない」と1文を置いて関係を明らかにする（直す箇所 7）。

```python
def apply(src, dst, revert_k=None):
    src, dst = pathlib.Path(src), pathlib.Path(dst)
    files = {}
    for k, f, before, after in parse_edits():
        if f not in files:
            files[f] = (src / f).read_text(encoding="utf-8")
        if revert_k is not None and revert_k != k:
            continue
        old, new = (after, before) if revert_k == k else (before, after)
        n = files[f].count(old)
        if n != 1:
            sys.exit(f"edit {k} in {f}: expected 1 match, got {n}")
        files[f] = files[f].replace(old, new)
    for f, t in files.items():
        p = dst / f; p.parent.mkdir(parents=True, exist_ok=True); p.write_text(t, encoding="utf-8")

if __name__ == "__main__":
    cmd = sys.argv[1]
    if cmd == "check":
        sys.exit(0 if check(sys.argv[2], sys.argv[3] if len(sys.argv) > 3 else None) else 1)
    elif cmd == "apply":
        apply(sys.argv[2], sys.argv[3])
    elif cmd == "revert":
        apply(sys.argv[3], sys.argv[4], revert_k=int(sys.argv[2]))
    else:
        sys.exit("usage: see docstring")
```
