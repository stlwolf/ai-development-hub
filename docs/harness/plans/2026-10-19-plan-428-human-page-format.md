# #428 人向けの確認・回答用ページの形と部品を、持ち運べるスキルとして作る

## 背景

owner に判定や回答を求めるページ（claude.ai の artifact）は、作るたびに形がばらばらで、owner はその都度「こうしてほしい」と伝えてきた。調査メモ（2026-10-18）によれば、既存の39件で答え方が4通りあり、判定カードの描画・保存・代替表示の文言は7ページでほぼ同じ文字列を写していた。質問フェーズ（2026-10-19）で、owner と統括はページの形を11点決めた。この plan は、その11点を新しいスキルとして作る計画である。

## この plan の範囲

- やること: 新しいスキル `canonical/skills/human-page/`（名前は DJ-1・Q1）を作る。中身は、SKILL.md・ベースの HTML の型・部品の CSS と JS・データ（JSON）からページを作る小さなスクリプト・用語集・見本のデータ・スクリプトの検査である（DJ-2）。
- hub の側で変えるのは `canonical/CATALOG.md` の表に1行足すことだけである（DJ-13・Q4）。
- 直さないもの: いまの判定ページの保存の形（`db` の collection `decisions`・doc id はカードの key・項目は key・choice・note・at）と、統括の回収の手順（`ArtifactData` の list）。新しいページは同じ形で保存する（DJ-7）。sync のスクリプトも直さない。新しいスキルは、ディレクトリに `SKILL.md` があれば、いまの sync が3つのツールへそのまま配る（`sync-claude.sh` の 228 行目・`sync-codex.sh` の 274 行目・`sync-cursor.sh` の 191 行目）。
- 作らないもの（まとめの決定9 で、あとの版に回したもの）: 図・長いページのタブ・読み比べ・「何もしなければ受け入れ」の印付け。
- いつページを作り・更新し・止めるかは #466 に出した（まとめの決定7）。この plan は、そのとき使う部品（判断待ちの束）までを作る。
- **スキルは持ち運べる形にする。** スキルのフォルダに、hub の文書・リポジトリ名・issue 番号・`.oe/`・`oe-*`・hub の運用（統括・委譲・ゲート）への参照を入れない。どのリポジトリ、どのセッションでも、このフォルダだけで動く。ほかの hub のスキルにある「補足: hub での具体例」の節も置かない（owner・2026-10-19）。hub の運用でどう使うかは、この plan と episode に書く（「hub での使い方」節）。

## 上流の前提の確かめ（結果）

いまのコードと実物に当てて確かめた。経緯は episode の「P1」節にある。

| 前提 | 出所 | 結果 |

| `db` の doc id に使える文字 | 判定ページの互換 | `artifact-capabilities` の `db.d.ts` によれば、英字・数字・`_ - . ~ : @ +` で、1つの区切りは 200 バイトまでである。いまの key（`a_shape`・`q1_allow`）はこれに収まる |
| 新しいスキルは sync で配られる | 置き場 | 成り立つ。3つの sync とも、`canonical/skills/` の下で `SKILL.md` を持つディレクトリをまるごとリンクする。ただし、配られるのはマージのあとに sync を走らせたときで、それまでは手元のハーネスに無い |

## 設計判断

### DJ-1 スキルの名前は `human-page` にする

人に見せて読んでもらう・答えてもらうページの形と部品を持つスキル、という役目をそのまま名前にした。hub のスキルの名前は、役目を英語の kebab-case で書く（`issue-intake`・`spec-card`）。候補と退けた理由はゲート1 の木にある。owner の確認を Q1 に置く。

### DJ-2 フォルダの中身

```text
canonical/skills/human-page/
├── SKILL.md            いつ使うか・目的の選び方・データの書き方・作り方・公開と回収の仕方・限界
├── glossary.md         用語集。札の言葉（確かめた度合い・状態・重さ・採否・推奨）と、和訳しない用語
├── template.html       ベースの HTML の型。<title>・トークン・ヘッダーの枠と、差し込む位置の印だけを持つ
├── page.css            部品の CSS（トークン・明暗の2つの表示・狭い画面）
├── page.js             部品の JS（選んだものの保存・保存できないときの返答の文・回答待ちの件数）
├── build.py            データを検証し、通ったときだけ1枚の HTML を書く。source の補助コマンドも持つ
├── examples/
│   ├── decide.json     判断のページの見本（判定カード）
│   ├── bundle.json     判断待ちの束の見本（別の2つのリポジトリの作業の判断を1枚に並べる）
│   ├── review.json     セカンドオピニオンの結果を見るページの見本（指摘の一覧）
│   ├── grasp.json      読み物のページの見本（ヘッダーだけをそろえる）
│   └── grasp-body.html grasp.json と一緒に `--body` で渡す本文の断片の見本
└── tests/
    └── test_build.py   スクリプトの検査（標準の unittest）。見本が通ること、壊したデータがそれぞれ期待した規則と場所で落ちること
```

- 見本のデータは、架空のリポジトリ（`example-org/shop` と `example-org/billing`）と架空の issue で書く。hub の issue や文書を例に使わない。
- 検査はスキルのフォルダの中に置く。どのリポジトリに持っていっても `python3 tests/test_build.py` で回せるようにするためである。ただし「hub への参照が無いこと」の検査は、検査そのものが hub の名前を並べることになるので、フォルダの中に置かない（受入の A1 で1回だけ打つ）。
- フォルダの中のファイルは、フォルダの外を参照しない。`build.py` は自分の置き場所（`__file__`）から型・CSS・JS・用語集を読み、走らせたときの作業ディレクトリに頼らない。フォルダの外への相対パス・絶対パス・外向きの symlink を置かない。フォルダだけを別の場所へ写して動くことを受入の A1b で確かめる（設計SO 指摘8）。
- 前提は Python 3.9 以上だけである。tmux と git は無くても動く（tmux が無ければ送り元の tmux の項目を省く）。このことを SKILL.md の冒頭に書く。

### DJ-3 データの形（`format: 1`）

ページ1枚を JSON 1つで書く。書くのはセッションのモデルで、描くのはスクリプトである（調査メモの提案1・archify の作り）。未知の項目は誤りとして弾く（打ち間違いの項目名を黙って無視しないため）。

```json
{
  "format": 1,
  "title": "決済の再試行の方針を決める",
  "purpose": "decide",
  "status": "awaiting",
  "why": "決済が二重に走った障害（#212）の直し方が3通りあり、実装の前に1つに決めたい。",
  "source": {
    "repo": "shop",
    "repo_url": "https://github.com/example-org/shop",
    "issue": 212,
    "branch": "fix/#212_payment_retry"
  },
  "links": [
    {"label": "#212 の plan", "url": "https://github.com/example-org/shop/blob/fix/%23212_payment_retry/docs/plan.md"}
  ],
  "sections": [
    {
      "type": "decisions",
      "title": "再試行の方針",
      "cards": [
        {
          "key": "retry_policy",
          "tag": "DJ-1",
          "title": "再試行は冪等キーを付けて3回までにする",
          "recommend": "go",
          "reason": "冪等キーがあれば、二重の請求を決済の側で止められるため。",
          "points": [
            "いまは再試行の上限が無く、タイムアウトのたびに `charge` を呼び直している。",
            {"text": "決済の会社の API は冪等キーを24時間覚える。", "evidence": "verified"}
          ],
          "options": [
            {"key": "go", "label": "この形で進める", "kind": "go"},
            {"key": "fix", "label": "直してほしい（補足欄に）", "kind": "fix"}
          ]
        }
      ]
    }
  ]
}
```

項目の決まりは次のとおりである。

| 場所 | 項目 | 必須 | 決まり |
|---|---|---|---|
| ページ | `format` | 必須 | `1` |
| ページ | `title` | 必須 | 空でない。`<title>` と見出しに使う |
| ページ | `purpose` | 必須 | `decide`（判断）・`grasp`（把握・見取り図）・`review`（セカンドオピニオンの結果を見る）のどれか（まとめの決定6） |
| ページ | `status` | 必須 | `awaiting`（回答待ち）・`answered`（回答済み）・`live`（随時更新）のどれか（まとめの決定4） |
| ページ | `why` | 必須 | 「なぜこのページか」の1文。空でない（まとめの決定9） |
| ページ | `source` | 必須 | 送り元。下の表 |
| ページ | `links` | 任意 | 関連リンクの欄。`{label, url}` の並び。url は `https://` か `http://` で始まる |
| ページ | `sections` | 必須 | 部品の並び。1つ以上。`--body` を渡すときは空でもよい（DJ-8） |
| ページ | `answers` | 任意 | 回収した答え。`{key: {choice, note, at}}`。`status` が `answered` のときに書く（DJ-7） |
| source | `repo` | 必須 | リポジトリの名前（例 `shop`） |
| source | `repo_url` | 任意 | リポジトリの URL。あれば issue・ブランチ・本文の `#N` をリンクにする |
| source | `issue` | 任意 | issue の番号（整数）。無いページでは省く |
| source | `branch` | 任意 | ブランチの名前。無いページでは省く |
| source | `tmux` | 任意 | `{window, pane, name}`。ページの `source` で書かなければ、スクリプトが作ったセッションのペインから引く（DJ-6）。`bundle` の group の `source` では自動で引かず、書いたときだけ出す |
| decisions | `title`・`cards` | 必須 | カードは1枚以上 |
| カード | `key` | 必須 | 英小文字・数字・`_`・`-` で 64 文字まで。ページ全体で重ならない（`db` の doc id になる） |
| カード | `title`・`recommend`・`reason`・`options` | 必須 | `recommend` は `options` のどれかの key。`reason` は推奨の根拠で空でない。`options` は2つ以上で、key が重ならない |
| カード | `tag`・`points`・`evidence` | 任意 | `points` の各要素は文字列か `{text, evidence}` |
| 選択肢 | `key`・`label` | 必須 | `kind` は任意で、`go`・`fix`・`warn`・`no` のどれか（選んだときの色） |
| bundle | `title`・`groups` | 必須 | 各 group は `source`（必須）・`title`（必須）・`why`（任意）・`cards`（1枚以上） |
| findings | `title`・`items` | 必須 | `lane`（任意・どのモデルの指摘か）。各 item は `text`・`severity`（`high`・`mid`・`low`）・`adopted`（`adopted`・`partial`・`rejected`）・`reason`（空でない）が必須で、`evidence` は任意 |

- 札の値（`evidence` の `verified`・`sourced`・`guess` など）はデータでは英語の key で書き、ページには用語集の札の言葉で出す（DJ-10）。札の言葉を直すときは用語集だけを直せばよい。
- 本文の文字列はすべて平文として扱う。HTML として解釈しない。本文の中で効くのは3つだけで、`` `…` `` をコードの書式に、`https://…` をリンクに、`#N` を issue へのリンク（近い送り元に `repo_url` があるとき）にする（DJ-11）。どの文脈でどうエスケープするかは DJ-14 に書く。

型と境界の決まりは次のとおりである（設計SO 指摘10）。

- 「空でない文字列」は、前後の空白を除いたあとに1文字以上ある文字列をいう。空白だけの文字列は空として弾く。
- 整数の項目（`format`・`source.issue`・`source.tmux.window`・`source.tmux.pane`）に真偽値を受け付けない。Python では `True` が整数の `1` と等しく扱われるので、型を見るときに真偽値を先に除く。`issue` は 1 以上、`window` と `pane` は 0 以上である。
- 文字列の key（カード・選択肢）は、英小文字で始まり、英小文字・数字・`_`・`-` が続く 64 文字までにする。`db` の doc id が許す文字（英字・数字・`_ - . ~ : @ +`・200 バイトまで）より狭い独自の決まりで、いまの key（`a_shape`・`q1_allow`）を受け付ける範囲に取った。
- `answers` の各値は `{choice, note, at}` で、`choice` は文字列か `null`（未選択）、`note` は文字列（空でもよい）、`at` は文字列（ISO 8601）である。
- JSON の同じオブジェクトに同じ項目名が2回あると、Python の既定の読み込みは後ろの値だけを残し、前の値が黙って消える。読み込むときに重なりを見つけて弾く（終了コード 2）。

### DJ-4 スクリプトは Python 3 の標準ライブラリだけで書く

- どのリポジトリ・どのセッションでも動くことが要件なので、追加のインストールを要しない言語にする。Python 3 は macOS・Linux の開発環境のほとんどにあり、HTML のエスケープ（`html.escape`）と JSON の読み書きが標準にある。hub でも engine の計測のスクリプトで使っている。
- 書き方は Python 3.9 で動く範囲に限る（macOS 付属の `/usr/bin/python3` が 3.9.6 である）。`match` 文と型の `X | Y` を使わない。受入では 3.13 と 3.9 の両方で検査を回す（A2）。
- 退けた案（Bash と jq・Node・スクリプトを使わない形）はゲート1 の木にある。owner の確認を Q2 に置く。hub のほかのスクリプトは Bash だが、このスキルは hub の外へ持ち出す前提なので、hub の慣習より持ち運べることを優先した。

### DJ-5 出力は2つの形にする（artifact 用の断片と、手元で開く完全な文書）

- 既定の出力は artifact に公開する断片である。doctype・`<html>`・`<head>`・`<body>` を書かず、先頭に `<title>`・`<meta name="claude:viewport-fit-sides" content="cover">`・フォントの読み込み・`<style>` を置く（page contract のとおり）。`<title>` はファイルの先頭 8KB の中に入る。
- `--standalone` を付けると、同じ中身を doctype・文字コード（utf-8）・viewport の宣言で包んだ完全な文書を書く。手元のブラウザで開くときと、artifact の仕組みの無いツールで使うときはこちらにする。
- 2つの形の違いは包む部分だけで、中身（ヘッダー・部品・CSS・JS・データ）は同じ関数が作る。受入の A4 で、2つの出力の中身が一致することを確かめる。

### DJ-6 ヘッダー

タイトルの上に小さな文字で2行を置く（まとめの決定4）。

```text
shop ・ tmux 2.2「CC:shop」 ・ #212 ・ fix/#212_payment_retry
版 2026-10-19 18:05 JST（最終更新） ・ 回答待ち 3 件
決済の再試行の方針を決める                     ← タイトル（h1）
```

- 1行目は送り元である。項目の間は「 ・ 」でつなぎ、無い項目は省く。`repo_url` があれば、issue は issue のページへ、ブランチはそのブランチの木（`/tree/<ブランチ>`。`#` は `%23` にする）へのリンクにする。
- tmux の項目は「tmux <ウィンドウ>.<ペイン>「<ウィンドウ名>」」と書く。ページの `source.tmux` が無ければ、スクリプトが `TMUX_PANE` の指すペインから `tmux display-message` で引く。tmux の外か、引けなかったときは省き、そのことを標準エラーに1行で出す。省くのは正常な経路で、誤りにしない。セッションの番号は出さない（まとめの決定4）。テストと再現のために `--tmux off` で引かないようにできる。
- 自動で引くのはページ自身の送り元だけである。`bundle` の group の送り元は、その判断を出した作業のもので、束を作るセッションのペインではない。group の `source.tmux` は書いたときだけ出す（設計SO 指摘9）。判断を出す側のセッションは、`build.py source` で自分の送り元の JSON を出し、それを束を作る側へ渡す。
- 2行目は版と状態である。版は「版 YYYY-MM-DD HH:MM JST（最終更新）」で、スクリプトを走らせた時刻を JST（UTC+9）に直して書く。走らせたマシンの時間帯には頼らない（まとめの決定4 は JST と決めている・設計SO 指摘2）。時間帯の表の読み込みに頼らないよう、UTC+9 の固定の時差で直す。artifact のサービスの内部の版の番号は出さない（まとめの決定4）。テストと再現のために `--now 2026-10-19T09:05:00+00:00` のように時差つきの時刻を渡せ、別の時差で渡しても同じ瞬間が JST で出ることを検査で確かめる。
- 状態は用語集の札で出す。`awaiting` は「回答待ち N 件」で、N は答えの選ばれていないカードの数である。ページの JS が、保存した答えを読むたびに数え直す（読む前は、カードの枚数から `answers` にあるものを引いた数）。`answered` は「回答済み」、`live` は「随時更新」である。
- ページの「なぜ」（`why`）はタイトルのすぐ下に、関連リンク（`links`）はその下に置く。
- `bundle` の各 group の見出しにも、同じ形の送り元の1行を出す（どの作業からの判断かが分かるように）。
- `build.py source [--git <ディレクトリ>]` は、送り元の JSON を標準出力に出す補助のコマンドである。tmux の項目は自分のペインから引き、`--git` を渡したときは、そのディレクトリの git から `repo`（作業ツリーの最上位のディレクトリの名前）・`repo_url`（`origin` の URL を https の形に直したもの・直せなければ省く）・`branch`（いまのブランチ）を引く。セッションの作業ディレクトリと、作業している worktree が違うことがあるので、git は作業ディレクトリからでなく、渡したディレクトリから引く。`issue` は引かず、データに書く。

### DJ-7 答え方と保存

- 保存される形はいまの判定ページと同じにする。`db` の collection `decisions` に、doc id をカードの key にして `{key, choice, note, at}` を持つ文書を置く。`choice` は選んだ選択肢の key（まだ選んでいなければ `null`）、`note` は補足の文字列、`at` は最後に書いた時刻（ISO 8601）である。これで、統括の回収の手順（`ArtifactData` の list）を変えずに済む。
- 書き方は、いまの判定ページから1点だけ変える（設計SO 指摘3）。いまのページは、選ぶたび・補足を保存するたびに、手元の状態から文書全体を `set` で書き直す。この形だと、別の画面が先に選んだものを、手元の古い状態で上書きしうる。新しいページは、変えた項目（`choice` か `note`）と `at` だけを `update` で書き、その key の文書がまだ無くて断られたときだけ、4つの項目すべてを `set` で書く（`db.d.ts` によれば、`update` は文書があることを求め、無いと `invalid_argument` で断る）。どちらの道を通っても、保存される文書は4つの項目を持つ。
- 同じ key への書き込みは1つずつ順に行う（`db.d.ts` の「1つの文書に1度に1つの書き込み」）。補足は入力が止まって約1秒後に保存する。開いたあとは `onSnapshot` で読み、ほかの画面で選んだものも映す。ただし、入力欄に手元で打ちかけの文字があるあいだは、届いた値で入力欄を書き換えない。
- 残る競合は、2つの画面がほぼ同時に同じ項目を書いた場合で、書き込みは後から届いたほうが勝つ（`db.d.ts`。取引の仕組みは無い）。これはいまの判定ページから引き継ぐもので、この単位では直さない。
- 保存の状態を4つに分けて見せる（設計SO 指摘5）。「保存先に接続しています」（`use("db")` の答えを待っているあいだ）・「保存しました」・「保存できませんでした」（`set` か `update` が断られた・購読が切れた）・「この表示では保存できません」（`window.claude` が無い・`use("db")` が `null` か例外）である。
  - 接続を待っているあいだに押した選択と打った補足は、手元に持っておき、つながったら順に書く。つながらなかったら（10秒たって `null` になったときを含む）、手元に持っていたものを返答の文に入れる。
  - 書き込みが断られたときは、選択と補足を画面に残したまま、そのカードに「保存できませんでした」と出し、返答の文の欄も出す。保存できたように見えて保存されていない、という形を作らない。
- 保存できない表示（artifact の外・`db` を宣言していない公開・`use("db")` が `null`）では、選んだ内容から返答の文を組み立て、コピーのボタンと、選んでいつでも写せる読み取り専用の欄を出す（まとめの決定8・調査メモの提案2）。返答の文の形は次のとおりで、用語集に決める。

  ```text
  「決済の再試行の方針を決める」への答え（版 2026-10-19 18:05 JST）
  - retry_policy: この形で進める
    補足: 上限は5回にしたい
  - log_level: 未回答
  ```

- 答えの場所はページの1つだけにする（まとめの決定5・8）。ページの上に固定の文で「全部を推奨どおりにするなら、会話で『全部推奨どおり』と言えば足りる。ページで選んだものがあれば、その項目はページの答えを正とする」と出す。
- 推奨を先に出す（まとめの決定5）。カードの中で、推奨の選択肢と根拠をタイトルのすぐ下に「推奨: <選択肢の label>」と1行で出し、選択肢のボタンにも「推奨」の札を付ける。ボタンの並びはデータの順のままにする。
- 回収したあとは、`status` を `answered` にし、回収した答えを `answers` に写して1回だけ作り直して公開する（まとめの決定8）。`answered` のページは、選択肢と補足欄を押せない状態で出し、`answers` の答えを選ばれた形で見せる。`answers` に無いカードは「未回答」と出す。`db` は読まず、書かない（回収したものだけが正であることを見た目で示すため）。owner の確認を Q3 に置く。
- 回収のあとの正本は `answers` である（設計SO 指摘4）。`db` の書き込みを止める仕組みは無いので、回収の前に開いていた画面からは、回収のあとも `db` に書けてしまう。artifact は出し直すと開いている画面へ新しい版を届ける（`artifact-design` の「Open viewers」）ので、多くの場合は古い画面も回答済みの版に替わるが、それを保証とはしない。SKILL.md には、回収は1回だけ行い、回答済みにしたあとは `db` を読み直さない（読み直して食い違っても `answers` を正とする）と書く。
- 「全部推奨どおり」の一言で答えを受けたときは、回収する側が、ページで選ばれていない各カードの `choice` に推奨の key を入れて `answers` を作る。ページで選ばれたカードは、ページの答えを入れる（まとめの決定8）。
- `status` が `answered` なら `answers` を必須にし、`answers` の key はページのカードの key のどれかで、`choice` はそのカードの選択肢のどれか（または `null`）であることを検証する（E-P2・E-A1）。

### DJ-8 最初の版の部品

| 部品 | 置き場 | 中身 |
|---|---|---|
| ヘッダー | すべてのページ | DJ-6 |
| 「なぜこのページか」 | すべてのページ | `why` の1文 |
| 関連リンクの欄 | すべてのページ | `links`。無ければ欄ごと出さない |
| 確かめた度合いの札 | カード・カードの要点・指摘 | `evidence`。「確かめた」「出典あり・未確認」「推測」 |
| 判定カード（`decisions`） | 判断のため | タイトル・推奨と根拠・要点・選択肢・補足欄・保存の状態 |
| 判断待ちの束（`bundle`） | 判断のため | 複数の作業（別のリポジトリ・別の issue）の判定カードを、作業ごとの送り元の見出しの下に並べる。作業ごとに回答待ちの件数を出す |
| 指摘の一覧（`findings`） | セカンドオピニオンのため | 指摘・重さ・採ったか・理由の表。狭い画面では1件ずつの縦の並びにする。答える部品は持たない |

- 読み物のページ（`purpose` が `grasp` のページなど）は、ヘッダーだけをそろえ、中の作りはページごとの工夫を残す（まとめの決定1）。そのために `--body <HTMLの断片のファイル>` を受け付け、ヘッダー・なぜ・関連リンクの下、部品の上に、その断片をそのまま差し込む。断片の中ではテンプレートのトークン（色・文字）を使えるので、明暗の表示もそろう。
- **`--body` の断片は信頼したコードとして扱う**（設計SO 指摘7）。データの文字列と違ってエスケープしないので、断片の script・イベントの属性・CSS は、答えの処理やヘッダーを変えられる。断片はページを作るセッションが自分で書くものに限り、外の文書（issue の本文・レビューの出力など）を写すときはデータの文字列に入れて平文として出す、と SKILL.md に書く。スクリプトが保証するのは、断片を含めた完成した HTML に、許していない外部の読み込みが無いことまでである（DJ-14 の最後の確かめ）。断片の中の page contract（明暗・狭い画面）の適合は、断片を書く側の責任として SKILL.md に書く。
- **目的（`purpose`）は部品の組み合わせを縛らない**（設計SO 指摘1）。まとめの決定6 は、目的・中身の部品・答える部品の有無を独立の軸にしている。そこで目的は必須の項目として書かせる（issue 本文の「用途を先に決めてから中身を作る」）が、検証で部品を縛らない。目的ごとの勧める組み合わせは、SKILL.md の表に書く。

  | 目的 | 勧める部品 | 答える部品 |
  |---|---|---|
  | `decide`（判断） | 判定カード・判断待ちの束 | ふつうは持つ。判断の記録だけを見せるなら、`status` を `answered` にして持たせる |
  | `grasp`（把握・見取り図） | `--body` の本文 | ふつうは持たない。確かめてほしい点があれば判定カードを足してよい |
  | `review`（セカンドオピニオンの結果を見る） | 指摘の一覧 | ふつうは持たない。採否を owner に決めてほしい指摘があれば判定カードを足す |

  目的はページの外側の要素に `data-purpose` の属性として出し、あとの版で目的ごとに配置を変えるときの手がかりにする。最初の版では見た目を変えない。
- 状態（`status`）と部品の組み合わせは検証する（E-P2）。`awaiting` なのに答える部品が無い（回答待ちが0件のまま固定になる）、`answers` があるのに `answered` でない、`answered` なのに `answers` が無い、の3つを弾く。

### DJ-9 検証の規則

スクリプトは、データの誤りを全部集めてから出し、1つでもあれば HTML を書かずに終了コード 1 で終わる。ファイルが読めない・JSON として読めない・用語集が壊れているといった、データの中身より前の失敗は終了コード 2 にする。誤りは1件1行で、規則の番号・場所・理由を出す。

```text
E-C3 sections[0].cards[0].recommend: 推奨 "ok" が選択肢（go, fix）に無い
```

| 番号 | 何を弾くか |
|---|---|
| E-F1 | `format` が 1 でない |
| E-F2 | 知らない項目がある（打ち間違いを含む） |
| E-F3 | 必須の項目が無いか、型が違う（文字列であるべき所に数など） |
| E-H1 | `title`・`why` が空 |
| E-H2 | `source.repo` が空・`source.issue` が正の整数でない・`repo_url` や `links[].url` が http(s) で始まらない |
| E-H3 | `purpose`・`status` が決まった値でない |
| E-P2 | `status` と答える部品・`answers` の組み合わせが DJ-8 の決まりに合わない |
| E-C1 | カードの key が形に合わないか、ページの中で重なる（`bundle` の group をまたいでも重ならない） |
| E-C2 | 選択肢が2つ未満か、選択肢の key が形に合わないか重なる |
| E-C3 | 推奨が選択肢の中に無い |
| E-C4 | 推奨の根拠（`reason`）が空 |
| E-C5 | カードのタイトル・要点の文字列・選択肢の label が空 |
| E-T1 | 札の値（`evidence`・`severity`・`adopted`・選択肢の `kind`）が決まった値でない |
| E-S1 | 部品の `type` が知らないもの・部品の中身（カード・group・item）が0件・`sections` が空なのに `--body` も無い |
| E-S2 | 指摘の理由（`reason`）か本文（`text`）が空 |
| E-A1 | `answers` の key がカードに無いか、`choice` がそのカードの選択肢に無い（`null` は許す）か、`note`・`at` の型が違う |
| E-B1 | 完成した HTML に、許していない外部の読み込みがある（`--body` の断片から入ったものを含む・DJ-14） |

`format` の誤りを除くと、規則に当たっても検証は止めずに次へ進む。ただし、1つの誤りから同じ原因の誤りが重ねて出ないように、2つの決まりを置く（設計SO 指摘11）。

- 型が違う項目（オブジェクトであるべき所が文字列など）は、その項目の誤りを1件だけ出し、その下の項目は見ない。
- 部品の `type` が知らないものなら、E-S1 を1件だけ出し、その部品の中身は見ない。
- `format` が 1 でなければ、E-F1 を1件だけ出して止まる（形の版が違うデータを、いまの規則で見ても意味が無いため）。

検証が効いていることは、見本のデータを1か所だけ壊したデータで確かめる（注入された negative knowledge `01M00KCC…`）。

- 確かめるのは「落ちたこと」ではなく、「出た誤りが、期待した規則と場所の1件だけであること」である。見本のデータそのものは誤り0件で通ることも、同じ検査の中で確かめる。壊した1か所だけが落ちた理由であることを保証するためである。
- 1つの規則が複数の条件を持つときは、条件ごとに壊したデータを持つ（設計SO 指摘11）。たとえば E-H2 は、repo が空・repo が空白だけ・issue が 0・issue が真偽値・`repo_url` が `javascript:` で始まる・`links[].url` が相対パス、の6つを別々に持つ。E-C1 は、形に合わない key と、group をまたいで重なる key を別々に持つ。
- 独立した誤りを2つ入れたデータで、2件とも出ることも確かめる（全部集めてから出すことの確かめ）。
- 読み込みの段の失敗（JSON として読めない・同じ項目名が2回ある・用語集が壊れている）は、終了コード 2 と理由の文言を確かめる。

### DJ-10 用語集の初版（`glossary.md`）

用語集は2つの部分からなる。1つ目は札の言葉と、ページの固定の文である。`build.py` は描くたびにこの表を読み、データの key を札の言葉に直す。札の言葉の正本を用語集の1か所にするためである（まとめの決定11）。

- **受け付ける値の集まりは `build.py` が持ち、用語集が持つのは表に出す言葉だけである**（設計SO 指摘12）。用語集の言葉を直しても、データとして受け付ける値は変わらない。用語集を読んだとき、`build.py` が求める key がすべて1回ずつあることを確かめ、欠け・重なり・知らない key があれば終了コード 2 で止まる。
- 表は1行に1つの key を書く。言葉の中で数を差し込む位置は `{n}` で書き、`{n}` を持つべき行（回答待ち）に無いときも止まる。
- 選択肢の `kind`（`go`・`fix`・`warn`・`no`）は、選んだときの色を決める値で、言葉として出さないので用語集に載せない。受け付ける値は `build.py` が持つ（E-T1）。
- 用語集の言葉は、静的に描く文字（ヘッダーの札・カードの札）と、ページの JS が出す文字（回答待ちの件数・保存の状態・返答の文）の両方に使う。JS の分は、`build.py` がページに埋め込むデータに入れて渡す。用語集の1行を直すと3つとも変わることを検査で確かめる。

| 種類 | key | 札の言葉 |
|---|---|---|
| 確かめた度合い | `evidence.verified` | 確かめた |
| 確かめた度合い | `evidence.sourced` | 出典あり・未確認 |
| 確かめた度合い | `evidence.guess` | 推測 |
| 状態 | `status.awaiting` | 回答待ち {n} 件 |
| 状態 | `status.answered` | 回答済み |
| 状態 | `status.live` | 随時更新 |
| 重さ | `severity.high` | 高 |
| 重さ | `severity.mid` | 中 |
| 重さ | `severity.low` | 低 |
| 採否 | `adopted.adopted` | 採った |
| 採否 | `adopted.partial` | 一部採った |
| 採否 | `adopted.rejected` | 採らない |
| 推奨 | `recommend` | 推奨 |
| 固定の文 | `text.*` | 保存の状態の4つ・「全部推奨どおり」の文・返答の文の見出しと「未回答」・コピーのボタン（DJ-7） |

2つ目はページで使う用語である。定着した用語を独自に和訳しない（まとめの決定5）。初版には、ブランチ・コミット・プッシュ・マージ・PR・issue・レビュー・デプロイ・リリース・worktree を入れ、「枝」「打つ」のような言い換えをしないことを書く。この部分は人とモデルが読むためのもので、`build.py` は読まない。

### DJ-11 リンク

- 本文の `#N` は、その文字列にいちばん近い送り元の `repo_url` を使って `<repo_url>/issues/N` へのリンクにする（設計SO 指摘9）。`bundle` の group の中の文字列は group の送り元を、それ以外はページの送り元を使う。group の送り元に `repo_url` が無いときは、ページの送り元へは戻らず、リンクにしない（別のリポジトリの同じ番号へ誘導しないため）。GitHub は PR の番号でも issues の URL から PR へ移すので、PR と issue を分けない。`#N` の後ろに英数字か `_` が続くとき（`feature/#212_x` など）はリンクにしない。見本の `bundle.json` に2つの別のリポジトリを入れ、group ごとのリンクの先を検査で確かめる。
- 本文の `https://…` はそのままリンクにする。
- リンクはすべて新しいタブで開く（`target="_blank" rel="noopener"`）。owner は issue と PR を行き来しながら答えるので、ページを閉じずに済むようにする（issue 本文の方向性）。

### DJ-14 文脈ごとのエスケープと、完成した HTML の確かめ

データの文字列を「平文として扱う」を、文脈ごとに次のように決める（設計SO 指摘6）。

| 文脈 | 扱い |
|---|---|
| HTML の本文（タイトル・要点・補足など） | `html.escape` でエスケープしてから、コードの書式とリンクだけを足す。リンクにする部分も、エスケープした文字列の上で組み立てる |
| HTML の属性（`href`・`data-*`・`aria-label`） | `html.escape(…, quote=True)` でエスケープする。`href` に入れる URL は、検証で `https://` か `http://` で始まるものに限っている（E-H2）。ブランチの名前を URL に入れるときは、URL のエスケープ（`#` を `%23` など）をしてから属性のエスケープをする |
| ページに埋め込む JSON（JS が使うデータ） | `<script type="application/json">` の中に置き、`json.dumps` のあとで `<`・`>`・`&`・U+2028・U+2029 を `\u003c` などの形に置き換える。中に `</script>` があっても、要素を閉じない |
| JS が画面を書き換えるとき（保存の状態・返答の文・届いた補足） | `textContent` と `value` だけを使い、`innerHTML` を使わない |

- 検査では、タイトル・`why`・要点・補足・選択肢の label・用語集の言葉に、`</script><script>alert(1)</script>`・`"><img src=x onerror=alert(1)>`・`` `</code><b>` `` のような文字列を入れて作ったページを読み、要素として現れず、文字として出ることを確かめる（A7 で、ブラウザで開いて script が動かないことも見る）。
- 完成した HTML を書く直前に、外部の読み込みを1回だけ数える。`<script src>`・`<link href>`・`<img src>`・`<iframe>`・`<object>`・`<embed>`・CSS の `@import` と `url(` のうち、`https://fonts.googleapis.com/` と `https://fonts.gstatic.com/` 以外を指すものがあれば E-B1 で止める（`--body` の断片から入ったものを含む）。本文のリンク（`<a href>`）は読み込みではないので数えない。`data:` の URL は数えない。
- 実装の注意: 道具の呼び出し（Write・Edit・Bash）に書いた、バックスラッシュと u と16進の4桁が並ぶ表記は、ファイルに届く前にその文字に直される（この plan を書く途中で実際に起きた・episode の P2 の設計SO の節）。`build.py` と `page.js` の置き換えの表は、この並びを書かずに、`ord()` と書式（`'\\u%04x' % ord(c)` の形）で実行時に組み立てる。`</script>` を含むデータで要素が閉じないことを確かめる検査（A5 の (6)・A7 の (f)）が、化けたときの受け皿になる。
