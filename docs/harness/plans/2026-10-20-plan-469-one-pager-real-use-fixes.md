# #469 html-one-pager を実物の記録で直す（表の部品・本文の class・根拠の省略ほか）

## 背景

`html-one-pager` は #428（PR #468）で入った、人に見せて答えてもらうページを作るスキルである。マージの直後、別のリポジトリの統括が読み物のページを作り、owner は2回「読みづらい」と指摘した。1回目は表の線が無く番号の列が詰まっていたこと、2回目は番号と issue の ID が1つの欄で2行になり、ID がリンクでなかったことである。どちらも、本文を素の HTML で書いたことが元にある。スキルには本文で使う class の決まりも、表をデータで書く部品も無かった（#428 のコメント2件・気づき1〜9）。同じ日に hub の統括が判断のページを作ったところ、owner はさらに2点を指摘した。推奨が1つしかないカードでも根拠の定型文を書かされることと、認識合わせのような塊のある中身をカードの平らな要点に流し込むことになることである（#469 のコメント・気づき10・11）。

この plan は、それらの直しをスキルのフォルダの中で行う計画である。

- 変えないもの: E-B1（完成した HTML の外部の読み込みを止める検査）の判定と、その検査の項目。

## 設計判断

### DJ-1 本文の class の一覧を置き、素の要素にも最低限の見た目を当てる（気づき1・2）

二択でなく両方を行う。class を忘れた本文でも読める見た目になり、一覧があれば部品と同じ見た目に寄せられる。

- **素の要素の見た目は、class を持たない要素だけに当てる。** 規則は `.hp-main` の中で、`class` 属性の無い `section`・`h2`・`h3`・`p`・`ul`・`ol`・`table`・`pre` と、`class` 属性の無い `table` の中の `th`・`td` に限る（`:where(.hp-main section:not([class]))`・`:where(.hp-main table:not([class]) td)` の形）。class の付いた要素には、プロパティが重なるかどうかにかかわらず1つも効かない。本文の書き手の class（`.grasp-flow` など）も部品の class（`.hp-sec`）も、いまの見た目のまま残る（設計SO 指摘1）。セレクター全体を `:where()` で包んで詳細度を 0 にし、本文の書き手の CSS がいつも勝つようにもしておく（承認のあとの補正 H1）。
- **本文を包まない。** 初稿は本文を `<div class="hp-body">` で包む形だったが、包むと本文の書き手の CSS（`.hp-main > section` など）が効かなくなる（設計SO 指摘1）。範囲を `.hp-main` の中の class を持たない要素に限れば、包みが無くても部品には効かない。部品が描く要素は、指摘の一覧の表のセル（`th`・`td`）を除いてすべて class を持つ（見本の4つで確かめた・episode の P2）。セルは class を持つ表（`hp-table`）の中なので規則に当たらない。この前提が崩れないことを、見本の出力で確かめる検査を足す（部品が描く `.hp-main` の中の要素に、規則に当たるものが無いこと）。
- **当てるプロパティ**（部品と同じトークンを使う）:

  | 要素 | 当てるもの |
  |---|---|
  | `section` | 縦の並び・間隔 12px（`hp-sec` と同じ） |
  | `h2` | 15px・太字・余白0・薄い文字色（`hp-sec-title` と同じ） |
  | `h3` | 14px・太字・余白0 |
  | `p` | 余白0・行の幅 68ch |
  | `ul`・`ol` | 余白0・左の余白 1.4em |
  | `table` | 線を重ねる・幅 100%・13px・面の背景（`hp-table` と同じ） |
  | `th`・`td` | 線・余白・左寄せ・上寄せ（`hp-table` のセルと同じ）。`th` は 12px・薄い文字色 |
  | `pre` | 等幅・コードの背景・余白・横送り・角丸 |

- **幅の狭い画面では、素の表は表の中だけを横に送る。** 素の `td` には `data-label` が無いので、部品の表と同じ「行を積む」形にはできない。ページ全体が横に揺れないよう、素の `table` は幅の狭い画面で `display: block; overflow-x: auto` にする。行を積む形にしたいときは、表の部品（DJ-4）か `hp-table` と `data-label` を使う、と SKILL.md に書く。
- **試作で確かめたこと**: 初稿の形（包みあり・`:where(.hp-body)`）で、master の出力に案の CSS を手で足した試作のページを作って確かめた（episode の P2）。幅 400px で素の表は表の中だけが横に送られ、ページは揺れなかった。見本の本文の `.grasp-flow` の余白は変わらなかった。包みを外した形は、実装のあとに A10 で本物の出力で確かめ直す。
- **一覧**: SKILL.md の「書くときの注意」の近くに、本文で使える class を1つの表で置く。載せるのは `hp-sec`・`hp-sec-title`・`hp-table-wrap`・`hp-table`・`td` の `data-label` 属性・`hp-card`・`hp-lbl`・`hp-chip` と札の色の class（`hp-ev-*`・`hp-sev-*`・`hp-ad-*`）である。列は「class」「付ける要素」「見た目」の3つにする。
- **一覧と CSS がずれないことを検査で見る。** SKILL.md の一覧の表から class の名前を読み、すべてが `page.css` に定義されていることを確かめる検査を足す。一覧に載せた class は、このスキルが本文の書き手に約束する名前になる。名前を変えたら検査が赤になる。

### DJ-2 `check --body` の形を SKILL.md のコマンドの節に載せる（気づき4）

- 実装はすでにあるので、直すのは SKILL.md だけである。「コマンド」の節の検証の例のすぐ下に「読み物の本文と一緒に検証する」として `check '<データの JSON>' --body '<本文の HTML の断片>'` を載せる。「作り方の流れ」の4（検証する）にも、本文を差し込むページは `--body` を付けて検証すると書く。
- `check` は E-B1（外部の読み込み）を見ないことも書く。E-B1 は完成した HTML を見る規則なので `build` のときだけ働く。`check` を E-B1 まで見る形に変える案は、E-B1 の扱いを変えないという受入に合わせて採らない（ゲート1 の木）。

### DJ-3 答える部品の無いページには、保存のコードを入れない（気づき5）

- 答える部品（判定カード・判断待ちの束）が1つも無いページでは、`page.js` と、それが読む埋め込みのデータ（`<script type="application/json" id="hp-data">`）を出さない。`page.js` はカードが無いと先頭で止まるので、外しても振る舞いは変わらない。外すと、ページの中に `claude.use("db")` の文字列が無くなる。
- そのために `template.html` の2つの `<script>` の包みを、描画の側（`build.py`）に移す。型の差し込み口は、`{{data}}` と `{{js}}` の2つを `{{scripts}}` の1つにまとめる（承認のあとの補正 H2）。差し込み口がそれぞれ1つだけある決まりは変えない。答える部品のあるページ（見本では `decide` と `bundle`）の出力は、改行まで含めて変更の前と1文字も変わらないようにする。答える部品の無いページ（`review` と `grasp`）の出力は、2つの `<script>` が無くなることだけが変わる（A9 で比べる・設計SO 指摘2）。
- SKILL.md の「公開する」に、答える部品の無いページは保存のコードを持たないので `capabilities` を付けずに公開する、と書く。公開のときの注意が消えることは、I1-6 で1回公開して確かめてから書く（確かめられなければ書かない）。
- `page.js` そのものは変えない（保存の形と書き方を変えないため・A8）。

### DJ-4 表の部品 `table` を足す（気づき3・8・9）

列と行をデータで書く部品である。本文の HTML で表を書かずに済み、エスケープ・リンク・幅の狭い画面での形・検証が部品の側で決まる。

```json
{
  "type": "table",
  "title": "手番の一覧",
  "columns": [
    {"key": "no", "label": "番号"},
    {"key": "refs", "label": "issue / PR", "type": "ref"},
    {"key": "what", "label": "中身"},
    {"key": "result", "label": "結果"}
  ],
  "rows": [
    {"no": "A1", "refs": ["#212", "PR #215"], "what": {"text": "決済の再試行を直す", "evidence": "verified"}, "result": "マージ済み"},
    {"no": "A2", "refs": "OPS-41", "what": "障害の振り返りを書く", "result": ""}
  ]
}
```

- **列**: `columns` は1つ以上で、各列は `key`（カードの key と同じ形）・`label`（列の見出しで、幅の狭い画面では各欄の上に出る）・`type`（任意）を持つ。`type` は `text`（既定）と `ref` の2つである。
- **行**: `rows` は1つ以上で、各行は列の `key` をちょうどそろえたオブジェクトにする。知らない key は E-F2、足りない key は E-F3 で止まる。配列（列の順）で書く形は採らない（ゲート1 の木）。
- **`text` の欄**: 文字列か `{text, evidence}`。ほかのデータの文字列と同じく平文として扱い、`` `…` ``・`https://…`・`#N`・外部の課題管理の ID（下）だけがリンクやコードになる。空の文字列は空の欄として出す（「結果」がまだ無い行のため）。`{text, evidence}` の形は、カードの要点と同じく確かめた度合いの札を付ける。
- **`ref` の欄（識別子の列）**: 文字列か文字列の配列で、各文字列は識別子1つでなければならない。受け付ける形は `#N`（issue）・`PR #N`・外部の課題管理の ID の3つである。どれも必ずリンクになり、リンクにできないとき（形が違う・`#N` なのに送り元に `repo_url` が無い・ID の接頭辞が送り元に登録されていない）は E-L1 で止まる。表示は識別子ごとに折り返さない。空の配列は空の欄として出す。
- **誤りの規則の割り当て**（設計SO 指摘3）: 型が違う・必須の項目が無いは E-F3、知らない項目は E-F2、列の定義の誤り（`key` の形・同じ `key` の重なり・`label` が空・`type` が `text` と `ref` のどちらでもない）と `{text, evidence}` の `text` が空は新しい E-S3、確かめた度合いの値は E-T1、型の合った識別子をリンクにできないときは新しい E-L1 で止める。`columns` か `rows` が空の配列なら E-S1、`title` が空なら E-S1（ほかの部品と同じ）。
- **同じ原因の誤りを重ねない**: `columns` が読めない（配列でない・空・列の定義に1つでも誤りがある）ときは、行の key の照合（E-F2・E-F3）をしない。列が読めないまま照合すると、すべての行が同じ原因で止まるからである。行の値の型（E-F3）と識別子（E-L1）も、列の型が決まらないので見ない。
- **`#N` の桁**: いまの変換と同じく1〜7桁にする（`build.py` の `LINK_RE`）。
- **リンクの先**: `#N` と `PR #N` は、どちらも `<repo_url>/issues/N` にする。#428 の DJ-11 と同じで、GitHub は PR の番号でも issues の URL から PR へ移す。`PR #N` の表示の文字は「PR #N」のまま残す。
- **番号と識別子は別の列にする。** SKILL.md の書き方の決まりとして書く。`ref` の欄は識別子以外を受け付けないので、「A1 #212」のように1つの欄へ混ぜると止まる。逆向き（`text` の欄に番号と識別子を混ぜる）は検証では止めない（ゲート1 の木）。
- **見た目**: いまの指摘の一覧と同じ `hp-table-wrap`・`hp-table`・`td[data-label]` で描く。幅の狭い画面では行がカードの形に積まれ、各欄の上に列の見出しが出る（気づき9 の「狭い画面で2行になる」が起きない形）。
- **目的との組み合わせ**: 表は答える部品ではない。`purpose` を縛らないので、読み物にもレビューにも判断のページにも置ける。「目的と部品」の表の `grasp` と `review` の勧める部品に足す。

### DJ-5 外部の課題管理の ID をリンクにする（気づき8・9 の一部）

- 送り元（`source`）に任意の項目 `trackers` を足す。各要素は `{prefix, url}` で、`prefix` は ID の接頭辞（英大文字で始まり、英大文字と数字が続く10文字まで）、`url` は `{id}` をちょうど1つ含む `https://` か `http://` の URL である。ID の形は `<prefix>-<数字>` に固定する（例: `prefix` が `OPS` なら `OPS-41`）。`url` の `{id}` には ID の全体が入る。

  ```json
  "trackers": [{"prefix": "OPS", "url": "https://tracker.example.com/browse/{id}"}]
  ```

- 誤り（接頭辞の形・同じ接頭辞の重なり・`{id}` が無いか2つ以上・URL の形）は、送り元の誤りとして E-H2 で止める。
- **リンクにする場所は、表の `ref` の欄と、いま `#N` をリンクにしている表示の文である**（設計SO 指摘4）。いま `#N` を変換しているのは、`why`・部品の見出し・カードの見出し・推奨の行の選択肢の名前・`reason`・`points`・束の group の見出しと `why`・指摘の本文と理由である。これに、表の `text` の欄と `blocks` の見出しと要点を足す。ページのタイトル・選択肢のボタン・リンクの `label`・`tag`・`lane` はいまと同じく変換しない（エスケープだけ）。表だけでリンクになり、カードの要点ではならない、という食い違いを作らないためである。
- その文字列にいちばん近い送り元の `trackers` を使う。束の group の中では group の送り元を使い、group に無ければページの送り元へは戻らずリンクにしない（#428 の DJ-11 と同じ決まり）。
- **変換の順**: いまと同じく、先にコードの書式（`` `…` ``）を切り出し、その外だけを変換する。URL・`#N`・ID は1回の走査で左から見て、URL に当たった部分の中の `#N` や ID はリンクにしない。ID は前後に英数字・`_`・`-` が続くとき（`feature/OPS-41_x`・`XOPS-41` など）はリンクにしない。登録された接頭辞にだけ当たり、似た接頭辞（`OPSX-41`）や登録の無い接頭辞は文字のまま残す。
- 特定の製品の名前を前提にしない。スキルの中の見本と説明は「外部の課題管理」と書き、架空の URL（`tracker.example.com`）を使う。
- `--body` の本文の中は変換しない（DJ-8）。

### DJ-6 判定カードの根拠（`reason`）を任意にする（気づき10）

- `reason` を必須から任意に変える。書かないカードでは「根拠」の行を出さず、推奨の行だけを出す。書いたのに空（空白だけを含む）なら、いまと同じく E-C4 で止める。空の定型文を書いて通す形は残さない。

### DJ-7 カードに小見出し付きの要点の塊（`blocks`）を置けるようにする（気づき11）

- カードに任意の項目 `blocks` を足す。各要素は `{title, points}` で、`title` は塊の小見出し、`points` はいまの要点と同じ形（文字列か `{text, evidence}`）の1つ以上の並びである。いまの `points` は残し、両方あれば `points`（「要点」の見出しの下）を先に、`blocks` をその後に出す。
- 描くときは、塊ごとにカードの見出しより1段下の見出しを置き、その下に要点の箇条書きを置く。データの文字列なので平文として扱い、エスケープとリンクの変換が効く。

- `blocks` を足すのは、`--body` だけでは足りないからである。認識合わせの中身は issue の本文から作る文で、外から来た文を含みうる。SKILL.md の「書くときの注意」は、外から来た文を `--body` に写さずデータの文字列に入れると決めている。`--body` に書く形だけを勧めると、この決まりとぶつかり、本文の HTML を書く手間（気づき1〜3 の元）も戻ってくる。ゲート3 の Q1 で、SKILL.md に書くだけの最小の形とどちらにするかを owner に確かめる。
