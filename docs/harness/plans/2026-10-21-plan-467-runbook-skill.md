# #467 ランブックの書き方と、ランブック・スキル・スクリプトの役割の分け方をスキルにする

## 背景

owner は、業務のサービスのインフラのリポジトリ2つで、デプロイなど更新の作業のランブック（人が読む手順書）を作っている（2026-10-19）。作業は AI のスキルにさせているが、人や AI の実行環境に結果が左右されるので、最悪のときに人が手で操作できるようにしたい。既存を取り込んだ側では、人が手順書だけで実行する演習を初めて試したところ、owner は前提を確かめる段の途中で止まり、実行者を AI に替えた。止まった理由はコマンドの数ではなく、1つ1つが細かいことと、変更の種類によって実行する・しないが分かれる所があったことである（材料2）。新しいサービスの側の手順書の形も、既存を踏襲してたまたま決まっているだけで、強制力が無い（#467 の本文・材料1）。

この plan は、ランブックの書き方と、ランブック・スキル・スクリプトの役割の分け方を、持ち運べる canonical のスキル1本にする計画である。スキルは業務のリポジトリへ持ち出して使う前提で、`html-one-pager`（#428）と同じく hub を参照しない形にする。

この plan では、ランブックを「手順書」と書く。両方の材料の側がそう呼んでいて、語を1つに固定する決まり（DJ-8）に合わせるためである。

## この plan の範囲

- やること: brief の scope の (1)〜(11) を持つスキルを `canonical/skills/runbook-authoring/` に作り（名前は Q1）、`canonical/CATALOG.md` に1行足す。(1)〜(11) とファイルの対応は DJ-2 にある。
- 守ること: 持ち運べる形にする。スキルのフォルダの中に、hub の文書・リポジトリの名前・hub の運用への参照を入れず、ほかのスキルも参照しない。スクリプトは Python 3.9 以上の標準ライブラリか bash で書く（#428 の decision の決定1 と同じ考え）。業務のリポジトリに文書の決まりがあれば、そちらに従うと SKILL.md の冒頭に書く。
- 入れないもの: 材料の会社名・サービス名・顧客名・ホスト名・秘密の値。仕組みの側（実行の直前に扱う hook・委譲の起動の認可）。hub のほかのスキル・コード・設定の変更。
- 受入に入れないもの: 人が手順書だけで通せるかの演習。これは業務の側の仕事である。

## 材料と、上流の主張の確かめ（結果）

材料は3つある。材料1 と材料2 は、業務のリポジトリ2つのそれぞれの統括が書いた要約で、いまの手順書の決まり・人と AI が困った場面・スキルへの提案を持つ（一般化した版が #467 のコメント2件にある）。材料3 は、人が人のために書いて使えていた既存の手順書の5組で、owner が読者をエンジニアに絞って選んだ（確定版の「深掘り」）。どれも中身は業務のもので、手元の作業層にある。この plan には、一般化した形だけを書く。

上流（材料・確定版）が断定している主張のうち、この plan の設計を左右するものを確かめた（注入された negative knowledge `01KYMRE1…`・episode の P1）。

| 主張 | 出どころ | 確かめた結果 |
|---|---|---|
| 人が書いて使えていた手順書の形（材料3 の5組の「見るところ」） | 統括が選んだ5組の一覧（手元） | 5組を一次で読み、ほぼ当たった。当たらなかったのは2つである。「メンテナンスの切り替えの1枚がほかの手順から参照される」は、読んだ範囲の別の手順書では参照でなく同じ段を書き直していた。「作業フローのコマンドの詳細はリポジトリの README に分担」は、ページの中に README への言及を見つけられなかった。一覧に無い形で、スキルに効くものを3つ見つけた（下の箇条書き） |
| UTF-8 のロケールの bash で `$c（` が変数名として読まれる | 材料2 | 当たる。macOS の bash 3.2.57 と 5.2.37 で、ロケールが `ja_JP.UTF-8` のとき `set -u` で止まり、`C` のときは正しく出た。`${c}（` の形は `ja_JP.UTF-8` でも正しく出た（2026-10-21）。hub の knowledge item `01M579XZ…` と同じ結果である |
| 人の演習が前提の確かめの途中で止まった経緯と、owner の言葉 | 材料2 | 確かめていない。元の記録は業務のリポジトリにあり、この単位の範囲の外である。材料の要約として扱う。スキルの決まりは、この1回の出来事だけに頼らない形（人向けの段の上限・分岐を手順書に並べない）にし、材料3 の人が書いた形でも支える |
| 結果整合の一覧の API は入れた直後に古い結果を返す・差分の道具は日本語の説明を持つ資源の差分を省略する・申請の API は成功の応答がすぐ返り結果は別に見る | 材料1・2 | 確かめていない。特定の製品の振る舞いで、業務の環境が要る。スキルには製品を名指しせず「こういうことがある。だから確かめはこう書く」の形で入れる。決まり（待つか別の取り方で見る・出ないときの読み方も書く・申請と完了を分ける）は、振る舞いが製品で違っても成り立つ |

材料3 で見つけた、一覧に無い形の3つ:

- 開発環境の構築の README は、長いコマンドを入口のスクリプト1本とその下の名前（起動・初期化・消す など）で包み、ブロックの直前に目的を1行書き、データが消える操作にはそのことを横に書いていた。人が実行するコマンドを短くする「包む」形の、人が書いた前例である。
- owner が以前に書いた作業フローは、冒頭に「基本はスクリプトで作業できるので、確認系を手動で行う」と書き、番号の付いたスクリプトを順に実行し、戻すためのスクリプトを別に持っていた。DJ-4 の「機械で決まる所はスクリプト、人は確かめと判断」と同じ分け方である。
- あるリリースの手順書では、途中で失敗したスクリプトを直して実行し直したとき、すでに済んだものを飛ばす形にしてあった。当日の記録は、手順書の本体でなくページのコメントに分けていた。DJ-6 の「何度実行しても同じ結果」と、DJ-5 の「作業の記録を手順書と分ける」の、人が書いた前例である。

## 設計判断

### DJ-1 スキルの名前と入口（description）

- **名前は `runbook-authoring` を推奨する（Q1）。** 手順書を書くこと・直すこと・スクリプトに包むこと・検査することをまとめて指せる。比べた案は2つある。`runbook-conventions` は hub の `*-conventions`（書式の規約だけを持つスキル）に並ぶが、このスキルはスクリプトの設計と検査と見本も持つので名前が狭い。`runbook` は短いが、何をするスキルかが名前から読めない。#428 では承認のあとに owner が名前を変えたので、今回はゲート3 で先に決めてもらう。
- **description の案**（題材が欠けた依頼でも読み込まれるよう、注入された negative knowledge `01M5A1ZM…` に従う）:

  > ランブック（人か AI が端末やコンソールで実行する手順書。デプロイ・設定の反映・1回だけの初期化・失敗したときの戻し方など）を書く・直す・見直すとき、手順書で続けて実行しているコマンドをスクリプトにまとめるとき、AI に手順書に沿って作業させるスキルの文を書くとき、人が手順書だけで実行できるかを見るときに使う。どの作業の手順書か（題材）がまだ決まっていなくても、手順書を書く・直す依頼を受けたら、題材を聞き返したり探したりする前に読み込む（何を聞けばよいかは、このスキルの前提の型と節の型で決まるため）。手順書・スキル・スクリプトの役割の分け方、人向けの粗い段と AI 向けの1ブロック1確かめの書き分け、固定する節と前提の型、手順書の種類、スクリプトに包む粒度、確かめの落とし穴、用語の決まりと、このフォルダの check_runbook.py による検査を持つ。そのリポジトリに手順書の決まりがあれば、そちらを先に読み、足りないところにこのスキルを使う。

- description の中でも、DJ-8 の使わない語（「打つ」など）を使わない。受入の A8 で、スキルのフォルダ全体に当てて確かめる。
- 発火は、#428 と同じ方法で、題材のある言い方と題材の欠けた言い方の両方で測る（受入の A9・「発火の測り方」節）。

### DJ-2 フォルダの中身と、brief の (1)〜(11) の置き場

| ファイル | 持つもの | brief の項目 |

| `glossary.md` | 用語の決まり（使う語とその1つの意味・使わない語・和訳しない用語） | (9) |
| `check_runbook.py` | 手順書の検査のスクリプト（DJ-9） | (10) |
| `tests/test_check_runbook.py` | 検査のスクリプトの検査。見本が通ること、規則ごとに壊した見本が落ちること、SKILL.md の節の表とスクリプトの一覧が同じであること、見本のスクリプトの振る舞い | 受入 |
| `examples/` | 架空のサービスの見本（DJ-10）。手順書の一覧、人向けの段の手順書1本、それを包むスクリプト、反映する設定ファイル | (11) |

- `SKILL.md` は、`html-one-pager` と同じく300行前後を目安にする。決まりの理由は1文ずつ添え、材料の出来事はスキルに書かない（業務の中身になるため）。用語は `glossary.md` に、具体の形は `examples/` に逃がし、`SKILL.md` に同じことを書き写さない（設計SO 指摘11）。
- 型のファイル（節だけの空の手順書）は置かない。節の表（`SKILL.md`）と見本（`examples/`）で足り、3つ目の写しを置くとずれる元が増える。

### DJ-3 手順書・スクリプト・スキルの役割の分け方（(1)）

| 層 | 読む・使う者 | 持つもの | 持たないもの |
|---|---|---|---|
| 手順書 | 人（AI も同じものを読む） | いつ使うか、前提、段ごとの1つのコマンドと期待する出力と外れたとき、止まったときに読む表、戻し方 | 操作そのものの散文の手順（要ったらスクリプトかコマンドへ寄せる）、背景の説明、issue 番号 |
| スクリプト（または、そのリポジトリの入口のコマンド） | 手順書から呼ばれる | 続けて実行するコマンド、繰り返し、出力の加工、待つこと、期待が1つに決まる確かめ、対話の確認、記録に貼る行 | 読んで決める判定（DJ-6 の Q3） |
| スキル（AI の入口） | AI | 「この手順書を上から実行する」ことと、AI が実行するときの共通の決まり（非対話の形・承認の比べ方・止まったら止まって人に返す） | 手順の中身の写し（写すと手順書とずれる） |
| 背景・仕組みの説明、判断の経緯 | 人 | なぜこの順か、なぜこの形か | 作業の手順 |

- 手順書は冒頭で背景の文書へリンクし、「作業のときはこの手順書だけを見て進める」と書く（材料3 の5組目の形）。
- 入口のコマンドは、スクリプトでなくても、そのリポジトリの Makefile の target やパッケージの script でよい（材料2 は Makefile と scripts を併用していた）。DJ-6 の決まりは入口の形を問わず当てる。
- 業務のリポジトリの AI の入口のスキルに書く文の型を、`SKILL.md` にコードブロックで置く。スキルのファイルとして `examples/` に置くと、配った先でスキルとして読み込まれうるので置かない。

### DJ-4 読者を人と AI に分ける形（(2)・Q2）

材料2 で出たいちばん大きい論点である。いまの形（1ブロック＝1確かめ）は AI には足りるが、人には細かすぎて実行できなかった。

**推奨は案A（1本の手順書の中で層を分ける）である。**

- **案A**: 手順書は1本にする。「手順」の本体は人向けの粗い段にし、段の数は多くても6つにする。上限の6は決まりで、検査の R4 が見る。4〜6 は目安で、少ない段で済む作業（1回だけの初期化など）は少なくてよい。各段は、目的の1行・実行するコマンド1つ（多くは入口のスクリプトの1つの名前）・期待する出力・外れたら、を持つ。細かい確かめはスクリプトの中に置き、1つの確かめごとに番号つきの1行（`OK C1 …`・`NG C1 …` の形）を出し、外れたらそこで止まる。「止まったときに読む表」は、確かめの番号ごとに意味と次の操作を持ち、手で確かめ直すときのブロック（1ブロック＝1確かめ）をここに置く。AI も同じ手順を実行し（非対話の形）、確かめの行を読む。
- 比べた案: 案B（人向けと AI 向けの手順書を2本持つ）は、同じ手順の正本が2つになりずれる。案C（いまの細かい手順書の先頭に「この回はどのブロックを実行するか」の分岐の表を置く・材料2 の最小の案）は、人が実行する単位が細かいままである。案D（スクリプトそのものを手順書にし、説明も出す）は、スクリプトが動かないときに人が読むものが無く、issue の目的（最悪のときに人が手で操作できる）に反する。ほかの案はゲート1 の木にある。
- 案A で決める細部:
  - 変更の種類による分岐は手順書に並べない。スクリプトが対象と変更の種類を聞くか引数で受け、要る確かめだけを実行する。どうしても手順が分かれるなら、節か手順書を分ける（材料2 で人が止まった所）。
  - 「手順」の節の先頭に、段の一覧を1行ずつ置く（材料3 の「作業の大枠を先に出す」）。
  - 何かを変える段には「（変える段）」と書き、その直前を「引き返せる最後の所」と書く（材料3 の5組目のロールバックの早見表は、引き返しの最終点を段として持っていた）。
  - 1ブロック＝1確かめは、人向けの段にも止まったときに読む表にも当てる。どのブロックも、実行すると1つの結果が出る単位にする（`&&` でつないで最後に1つの結果を確かめれば足りる単位まで）。人向けの段のブロックは、中で多くを確かめるスクリプトを呼ぶが、最後に出る判定の行は1つである。
  - スクリプトがまだ無い所は、1ブロック＝1確かめで書き、包む対象として「間違えやすい所」か issue に残す。
  - 期待する出力は `text` のブロックか本文の1行で書く。コマンドのブロック（`bash` など）とは別の言語の指定にし、検査の R4 が数えるのはコマンドのブロックだけにする（設計SO 指摘6）。
  - 確かめの番号はスクリプトの出力と「止まったときに読む表」の両方に現れ、正本が2つになる。番号を機械で突き合わせる検査は持たず、人が見る項目と「限界」に書く（設計SO 指摘5・ゲート1 の木）。

昇格の印は episode の P2 に置く。

### DJ-5 固定する節・前提の型・手順書の種類（(3)(4)(5)）

**節は次の8つを、この順で `##` の見出しとして持つ。** 材料1 の7節と材料2 の8節を突き合わせ、確定版の［別モデル］の項目（失敗・中断のとき）と材料3 の形を足した。前の4つは作業のときに上から読む節、後ろの4つは要るときに引く節である（材料1 の「最短の手順を先頭に、止まったときに読む表をその後ろに」）。

| # | 節 | 持つもの | 突き合わせ |
|---|---|---|---|
| 1 | いつ使うか | 種類（下）、使うとき、使わないとき、かかる時間の目安、背景の文書へのリンク | 材料1「いつ使うか」・材料2「いつ使うか（位置づけ・使うとき・使わないとき・どの手順を通るか）」・材料3 の概要と想定の時間 |
| 2 | 前提 | 前提の型の4つ（下）と、前の日までに済ませること（任意） | 材料1「前提」・材料2「前提の確かめ方」・材料3 の事前準備 |
| 3 | 手順 | 段の一覧と各段（DJ-4） | 3つとも |
| 4 | 確かめ方 | 作業のあとに人が目で見て確かめること。最初に見るものを先に置き、問いの形で書いてよい | 材料1「確かめ方」・材料2「確認」・材料3 の確認を問いで書く形と、切り替え直後に見る4行 |
| 5 | 止まったときに読む表 | スクリプトが止まった行（確かめの番号）ごとの意味と次の操作 | 材料1 |
| 6 | 失敗や中断のとき | 止まり方、再開の条件、戻し方（段ごとの早見表）、あとかたづけ（誰が・どの道で消すか） | 確定版の［別モデル］・材料2「戻し方」・材料3 の逆操作とロールバックの早見表・材料1 の「あとかたづけ」 |
| 7 | AI が実行するとき | 非対話の形と、承認と実行の比べ方（DJ-7） | 材料2 |
| 8 | 間違えやすい所 | 実際の作業で詰まった所を積む。過去の事例へのリンクはこの節だけに置ける | 材料1「罠」・材料2「間違えやすい所」・材料3 の既知の問題と「詰まったところ」の別紙 |

- 任意の節は「関連」だけを最後に置ける。ほかの `##` の見出しも間に入れてよいが、8つの節の順は変えない。検査の R1 は、8つの節の相対の順だけを見て、ほかの `##` の見出しは無視する（設計SO 指摘1）。
- 「AI が実行するとき」は、AI に実行させない手順書でも省かず、「AI には実行させない（理由）」の1行を書く。書いていないのと、AI に実行させないのとを区別するためである（設計SO 指摘9）。
- 「用語」は手順書ごとに持たず、手順書の置き場の一覧（`README.md`）に1回だけ置く（材料1・2）。一覧は、手順書ごとの種類と「最後に実際の作業で通した記録」へのリンクも持つ（材料2）。
- 採らなかった節: 「記録する場所」（材料2）は、手順の最後の段に、スクリプトが出す記録の行を貼る場所を書く形に寄せる。「今後自動化したいこと」（材料3）は issue に置く。「仕組み」（材料3）は背景の文書に置く。
- 節の名前は「罠」でなく「間違えやすい所」にする。比喩を避け、普通の語にするためである（DJ-8）。業務のリポジトリがすでに「罠」と呼んでいれば、そちらの決まりが優先する。

**前提の型は4つで、どれも「要らない」も含めて必ず書く。** 書いていないのと要らないのを区別するためである。

| ラベル | 書くこと |
|---|---|
| 依存 | 入っている必要があるものと、その確かめ方。スクリプトは先頭で確かめ、無ければ何も変えずに止まる |
| 資格情報 | 要るか、どれか、何分で切れるか、どこでログインするか（AI のセッションでなく自分の端末で、など）、作業の区切りでログアウトするか |
| 実行する場所 | リポジトリのどこで実行するか。スクリプトは実行する場所に頼らない（DJ-6） |
| 1回だけの初期化 | 済んでいる必要があるものと、その手順書と、済んでいるかの確かめ方 |

**手順書の種類は、置き場に置くものとして3つと、置き場に置かないもの1つに分ける。**

| 種類 | 決まり |
|---|---|
| ずっと使う | ふつうの手順書 |
| 一時的 | 「消す条件」を書く（例: アプリ側の CI ができたら消す） |
| 1回だけの初期化 | 構築の前に一覧にし、担当と順番を持つ。ずっと使う手順書と分ける（材料1 で、どこにも書かれていない初期化で本番の反映が途中で止まった） |
| 作業の記録 | 手順書ではない。日付を持つのは記録だけで、手順書の置き場に置かず、記録の置き場に置く（材料2 では12本のうち5本が記録に近い日付つきのもので、人が「今回使う手順」を見分ける必要があった） |

「いつ使うか」の節に `種類:` の行で、置き場に置く3つのどれかを書く。

### DJ-6 スクリプトに包む粒度と書き方、読んで決める判定（(6)・Q3）

**包む合図と粒度:**

- 人が続けて実行するコマンドが2つ以上になったら包む（材料1）。手順書の段に、散文の操作手順が1つでも要ったら、そこも包む対象にする。
- 包んだ結果、人が実行するコマンドは1段に1つ、手順書全体で多くても6つにする（DJ-4）。
- 入口は1本にまとめ、その下に名前（変えない名前と変える名前）を並べる形を勧める（材料3 の1組目と材料2）。対象（環境・名前・必須の入力・影響範囲・戻し方）が複数あるなら、1か所の表に持ち、各名前がそこから引く（材料2）。

**名前と終了コード:**

- 変えない名前（確かめる・差分を出す・表示する）と、変える名前（足す・反映する・外す・戻す）を分ける。変える名前は、何度実行しても同じ結果にする（あれば何もしない・無ければ何もしない）。
- 変える名前は、実行せずに実行する操作の行を出す形（`--dry-run`）を持つ。実際に実行するときも、同じ行を同じ文字で出してから実行する（DJ-7 の承認の比べ方に使う）。
- 終了コードは、「何も変えていない失敗」と「変わったかもしれない失敗」を必ず別にする（材料2）。見本は次の割り当てを使い、リポジトリに決まりがあればそちらに従う。

| 終了コード | 意味 | 何が変わったか |
|---|---|---|
| 0 | 期待どおりに終わった（変える名前なら、変えたか、もともと同じで何もしなかった） | 期待どおり |
| 1 | 止まった（期待が1つに決まる確かめが外れたか、確認で断った） | 何も変えていない |
| 2 | 呼び方の誤りか、前提が足りない（依存・資格情報・端末が無い） | 何も変えていない |
| 3 | 変える途中で失敗した | 変わったかもしれない（止まったときに読む表と「失敗や中断のとき」を読む） |

**確かめと出力:**

- 確かめは1つごとに番号つきの1行を出す。判定の語（「すべて満たした」など）は、全部の確かめが通ったときだけ出す（材料2 で、途中の失敗が最後の `echo OK` に隠れた）。
- 変える名前は、実行の前に、その回の差分の要点（何が変わるか）と戻し方を出し、端末から `yes` を待つ。対象ごとの決まった文言だけを出さない（材料2）。決まった確認は減らさない（材料1）。
- 非対話の形（`--yes`）を持ち、表示は対話のときと同じに出す。端末が無く `--yes` も無ければ、何も変えずに終了コード 2 で止まる（材料1 は確認を端末から読む形にして、値をパイプで渡しながら確認だけを人が入力できた）。
- 確認を待つのは、何かを変える前だけである。確認の結果ごとの動きを次のとおりに決める（設計SO 指摘3）。

  | 確認の結果 | 動き | 終了コード |
  |---|---|---|
  | 端末から `yes` が入った、または `--yes` がある | 続けて変える | 変えた結果による（0 か 3） |
  | 端末から `yes` 以外が入った | 何も変えずに止まる | 1 |
  | 端末が無く、`--yes` も無い | 何も変えずに止まる | 2 |

  終了コード 1 の意味は「止まった（何も変えていない）」で、確かめが外れたときと、確認で断ったときの両方を含む。
- 最後に、記録に貼る1行を出す。何を・どの環境に・どの版を（作った commit など）・いつ（UTC）を入れる（材料1）。
- 待つ処理は上限の時間を持ち、待っているあいだは「何を待っているか」と残りの時間を出す。別の端末で操作が要るなら、その操作を出す（材料1）。

**秘密:**

- 秘密の値は画面にも記録にも出さず、長さだけを出す。コマンドの引数に載せない（同じ機械のほかの利用者からプロセスの一覧で見える）。一時のファイルに書くなら終了のときに消す。エラーの本文に値を含めない。伏せる処理が失敗したら、伏せる前のものを写さず、何も出さずに止める（材料2）。

**場所・時刻・文字:**

- 実行する場所に頼らない。スクリプトは自分の置き場所からリポジトリの位置を決める（材料1 で、別のフォルダで実行して必要なファイルが無く落ちた）。
- 時刻を次の段に渡すときは、時間帯を UTC に固定して出し、末尾が UTC であることを確かめる（材料2 で範囲が9時間ずれた）。
- bash で変数の直後に ASCII 以外の文字が来る位置は、必ず `${var}` で囲む。書いたら囲み忘れを探す（注入された negative knowledge `01M579XZ…`・材料2）。探し方は、検査のスクリプトの R9 か、`LC_ALL=C grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^[:space:] -~]' <ファイル>` にする。knowledge item が書く `grep -nP` は、macOS 付属の grep（BSD grep）が `-P` を受け付けず終了コード 2 になるので、持ち出す先では使えない（設計SO 指摘2・23 を 2026-10-21 に手元で確かめた）。日本語の文を含むヒアドキュメントは、展開が要らなければ `<<'EOF'` で囲む（材料1 で日本語とバッククォートを通して壊れた）。
- `set -euo pipefail` を置き、1行に1つのコマンドを書く。

**読んで決める判定（Q3）:** 材料2 の側は「デプロイを止めるかの判定は人か AI が要約を読んで決め、スクリプトでは止めない」と決めている。**推奨は、これを一般化して持ち込むことである。** 決まりの文は次のとおりにする。「スクリプトが止まるのは、期待が1つに決まる確かめが外れたときだけにする。差分が意図どおりか・影響が許せるかのように読んで決める判定は、スクリプトが要点を出して確認を待ち、人か AI が読んで決める」。理由は、包む粒度の決まり（確かめは機械、判断は人）と同じ線で、手順書・スクリプト・スキルの役割の分け方（DJ-3）の境目になるからである。比べた案は、持ち込まない（各リポジトリに任せる。スクリプトに何を止めさせるかの線が無く、包む人ごとに揺れる）と、材料2 の形のまま（デプロイの判定に限る。設定の反映や初期化でも同じ線が要る）である。

### DJ-7 確かめの落とし穴と、AI が実行するときの1行（(7)(8)）

**確かめの落とし穴**（`SKILL.md` に1項目ずつ、決まりと理由を書く。製品は名指ししない）:

- 「申請した」と「通った」を分けて確かめる。申請の操作は成功の応答がすぐ返り、通ったかは別の確かめで見ることがある（材料1）。
- 結果整合の一覧で確かめるときは、待つか、1件を直接引く別の取り方で見る（材料1）。
- 「無い」を言うときは、同じ取り方で「在る」ものが見えることを先に確かめる（陽性の対照）。権限の不足や問い合わせの形で、在るものが無いように見えることがある（材料2）。
- 判定を「出力に X が出る」だけで書かず、「出ないときの読み方」も書く。道具が一部の差分（ASCII 以外の文字を含むものなど）を省略して出すことがある（材料2）。
- 途中の失敗を最後の判定の語で隠さない（DJ-6 と同じ）。

**AI が実行するときの1行**（手順書の「AI が実行するとき」の節に書くこと）:

- 非対話の形（`--yes` など、その手順書のスクリプトの形）。
- 承認と実行の比べ方: 承認を取るときは `--dry-run` の「実行する操作」の行を見せ、実行するときに出る同じ行と文字列で比べてから進める（材料2 で効いた形）。比べる行は、決まった前置き（見本では `実行する: `）で始まる行だけにし、その行には時刻や乱数のように実行のたびに変わる値を入れない（設計SO 指摘10）。
- 承認された文字列に手を入れない。画面の量を減らすためのフィルタも足さない。出力が多いブロックは、手順書の側で初めからファイルに逃がす形にしておく（材料2）。
- 仕組みの側（実行の直前に扱う hook・委譲の起動の認可）は入れない（brief・確定版）。

### DJ-8 用語の決まり（(9)）

- `glossary.md` に3つの表を置く。(a) 使う語と、その1つの意味（実行する・反映する・確かめる・止まる・戻す・手順書 など）。(b) 使わない語と、代わりの語（打つ・撃つ・叩く・流す → 実行する・反映する。反映の意味の「出す」→ 反映する・リリースする）。(c) 和訳しない用語（ブランチ・コミット・デプロイ・リリースなど）。
- (c) は `html-one-pager` の用語集の「和訳しない用語」と同じ決まりで書くが、参照はしない（スキルどうしを参照しない・確定版）。同じ行を持つことになるので、片方を直したらもう片方を見る、と hub の側の episode に残す（スキルの中には書かない）。
- そのリポジトリだけの言い換え（内輪の呼び名）を説明なしに持ち込まない。AI の運用の言葉（AI どうしの役割の呼び名など）を手順書に持ち込まない（材料1）。そのリポジトリやチームがすでに使っている呼び方があれば、それに合わせる。スキルの文面でも、受入の A6 の grep に当たる hub の運用の語（例に挙げる形を含む）は使わない。
- 使わない語は、検査のスクリプトでは見ない（DJ-9）。「打ち合わせ」「作業の流れ」のような普通の語に当たりやすく、文脈の判断が要るので、人が見る項目にする。

### DJ-9 検査（(10)・Q4）

**検査の項目の一覧を `SKILL.md` に置き、機械で見られる項目は `check_runbook.py`（Python 3.9 以上の標準ライブラリ）にもする（推奨）。** 一覧は、ほかの言語の検査へ写すときの元になる。2つの業務のリポジトリはすでに自前の検査を持つので、スキルは「そのリポジトリに検査があればそちらを使い、無ければこのスクリプトを使う」と書く。

機械で見る項目（規則の番号は誤りの行の先頭に出る）:

| 番号 | 何を見るか | brief との対応 |
|---|---|---|
| R1 | 8つの節が `##` の見出しとして、この順にある。ほかの `##` の見出しは無視し、8つの相対の順だけを見る | 節の有無と順 |
| R2 | 「前提」に前提の型の4つのラベル（`依存:`・`資格情報:`・`実行する場所:`・`1回だけの初期化:`）がある | 足す（前提の型） |
| R3 | 「いつ使うか」に `種類:` の行があり、値が3つ（ずっと使う・一時的・1回だけの初期化）のどれかで、一時的なら `消す条件:` の行がある | 足す（種類） |
| R4 | 「手順」の段（`###`）が1〜6で、各段のコマンドのブロック（`bash`・`sh`・`shell`・`zsh`）は1つまで、ブロックのある段は `期待する出力` と `外れたら` の行を持つ | 足す（人向けの段） |
| R5 | 参照が在る。Markdown の相対のリンクは手順書の置き場から、コマンドのブロックで呼ぶファイル（行の最初の語か、`bash`・`sh`・`python3` などの次の語で、`/` を含む相対のパス）は `--root` から引く | 無いスクリプトやファイルの参照 |
| R6 | 本文（コードの外）に issue の番号（`#数字`・`/issues/数字`・`/pull/数字`）が無い。例外は「間違えやすい所」の節の Markdown のリンク（`[…](…)`）の中だけで、過去の事例へのリンクとして置ける。リンクでない `#数字` は、どの節でも誤りにする（材料1 の「罠の節だけ、リンクで残す」・設計SO 指摘8） | issue 番号の不在 |
| R7 | 本文に日付（`YYYY-MM-DD`・`YYYY/M/D`・`YYYY年M月`）が無い | 日付の不在 |
| R8 | 本文に警告の印が無い。印は ⚠・❗・❕・‼・⁉・★・☆・🚨・⛔・🛑・🔥・❌ の12個に固定し、`SKILL.md` の一覧とスクリプトの一覧が同じであることを検査で見る（設計SO 指摘7） | 警告の印の不在 |
| R9 | コマンドのブロックと、R5 で見つけた bash のスクリプトに、変数の名前の直後の ASCII 以外の文字が無い | 受入が求める（変数の直後の全角） |
| R10 | 置き場の `README.md`（一覧）がリンクする手順書の集まりと、置き場の `*.md`（README を除く）の集まりが同じ。置き場の下のフォルダは見ない（手順書は置き場に平らに並べる・設計SO 指摘12） | 一覧と実物の一致 |

- 出力は1件1行で、`R5 docs/runbooks/x.md:23 呼んでいるファイルが無い: scripts/y.sh` の形にする。終了コードは、誤りが無ければ 0、誤りがあれば 1、ファイルが読めないなどで検査ができなければ 2 にする（`html-one-pager` の `build.py` と同じ割り当て）。
- 呼び方は `python3 check_runbook.py [--root <リポジトリの一番上>] <手順書の置き場か手順書のファイル>...` にする。置き場を渡すと R10 も見る。`--root` を省くと作業ディレクトリを使う。
- R6〜R8 を本文に限るのは、期待する出力のブロックに時刻の例が入りうるからである。コードの中の issue 番号は見ないことを「限界」に書く。
- 見ない項目（「限界」に書く）: 別のブランチにしか無いファイルへの参照（参照先がこのブランチに在るかは R5 が見るので、マージの順は PR に書く決まりで扱う）、npm の script や make の target の実在（そのリポジトリの検査で数える）、前提の中身の正しさ、スクリプトの確かめの番号と「止まったときに読む表」の番号の一致、置き場の下のフォルダの手順書。
- 人が見る項目（一覧に置く）: 段の数が4〜6の目安に収まり、1段に変える操作を詰めていないか。変える段と引き返せる最後の所が書けているか。分岐を手順書に並べていないか。前提の4つの中身が正しいか。使わない語と内輪の言い換えが無いか。止まったときに読む表がスクリプトの確かめの番号と合っているか。
- R2〜R4 は brief の4つに足す項目である（Q4）。スキルの中心の決まり（人向けの段の上限・前提の型・種類）を機械で守るためである。

### DJ-10 架空のサービスの見本（(11)）

- 題材: 架空のサービス `shop` の設定ファイルを、反映先へ反映する手順書（ずっと使う）。反映先は手元のフォルダで、既定は一時の場所（`${TMPDIR:-/tmp}` の下）、環境変数 `SHOP_STATE_DIR` で変えられる。ネットワークに出ない。bash と標準のコマンドだけを使い、macOS の bash 3.2 でも動く。
- 置き方（`examples/` を架空のリポジトリの一番上とみなす）:

  ```text
  examples/
    docs/runbooks/README.md            手順書の一覧と用語
    docs/runbooks/shop-config-apply.md 人向けの段の手順書
    scripts/shop-config.sh             入口のスクリプト
    config/shop.conf                   反映する設定（キー=値）
  ```

- 人向けの段は4つにする。1 前提を確かめる（`check`）、2 差分を読む（`diff`）、3 反映する（`apply`・変える段・端末から `yes`）、4 反映のあとを確かめて記録を貼る（`verify`）。戻すのは `rollback` で、「失敗や中断のとき」に置く。`apply` と `rollback` は `--dry-run` と `--yes` を持つ。
- スクリプトが見せる決まり: 番号つきの確かめの行、何度実行しても同じ結果（同じ版なら何もしない）、DJ-6 の終了コードと確認の結果の表、端末からの `yes` と非対話の形、差分の要点を出してから確認する形、`--dry-run` と本番で同じ「実行する: 」の行、記録の行（UTC の時刻と版）、架空の資格情報 `SHOP_TOKEN` の長さだけを出す形、自分の置き場所から場所を決める形、`${var}` の形。
- 「確かめ方」の節は、問いの形の2〜3行にする（変わった行は差分を読む段で見た行と同じか、など）。
- 比べた案は、架空のクラウドへのデプロイを `--dry-run` だけで見せる案（実行しない形では、何度実行しても同じ結果・戻し方・記録の行を確かめられない）と、見本を2本（ずっと使う手順書と1回だけの初期化）にする案（brief の受入は1本で、種類の書き分けは表で足りる）である。
