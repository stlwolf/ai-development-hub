# #478・#477 html-one-pager に種別（kind）を定義し、番号と識別子のリンク先を決める

## 背景

`html-one-pager` は、人に見せて答えてもらうページを作るスキルである（#428・#469）。いまのスキルにあるのは、ページの目的（`purpose` の `decide`・`grasp`・`review`）と部品の一覧だけで、SKILL.md は「目的は部品の組み合わせを縛らない」と書いている。そのため、どの中身をどの部品でどう並べるかが毎回ページを作る側の解釈になり、owner は 2026-10-20〜21 に当てはめのずれを4回指摘した（認識合わせを平らな要点に流し込んだ・根拠が定型文になった・候補の番号が issue のリンクになった・選ぶ場所が分からない）。owner の言葉は「種別を定義していないので解釈がぶれる」である（#478）。

番号のリンクも同じ根を持つ。データの文字列の `#N` は、送り元に `repo_url` があれば必ず issue のリンクになるので、候補の番号を `#3` と書くと、すべてリポジトリの issue へ飛んだ（#477）。深掘りで、番号や識別子は「何を指すか」でリンク先を決めることになった。`#N` は issue、`PR #N` は PR、別のリポジトリは `owner/repo#N`、ページの中の項目はページで定義した接頭辞つきの識別子だけをページの中のアンカーにする。接頭辞は書き手の気分で決めず、種別ごとに決めて用語集に置く。owner の言葉は「利便性が第一。アンカーは読みやすさのため。接頭辞は各 AI が気分で決めているので、フォーマットとして統一できる」である。

## この plan の範囲

- やること: データに種別（`kind`）を足し、種別ごとに要る部品・置いてよい補足・並び・答える部品・札と番号の振り方を決めて、`check` で見る（DJ-1〜DJ-5）。ページの中の項目の識別子を定義し、本文の参照をページの中のアンカーにする（DJ-6・DJ-7）。`PR #N` と `owner/repo#N` のリンク先を直す（DJ-8）。種別ごとの見本を置き、SKILL.md の「目的と部品」の表を種別の表に置き換える（DJ-9）。
- 修正範囲: `canonical/skills/html-one-pager/` の中（`build.py`・`SKILL.md`・`glossary.md`・`page.css`・`examples/`・`tests/test_build.py`）と、`canonical/CATALOG.md` の html-one-pager の行1つである。`page.js` と `template.html` は変えない（DJ-6・DJ-7 はスクリプトが静的に描く範囲で収まり、「手番の1枚」を Q2 の B で入れても変えない）。
- 守ること（#428 の decision）: スクリプトは Python 3.9 以上の標準ライブラリだけで書く（決定1）。描くのはスクリプトで、ページの JS は答え・保存・回答待ちの件数だけを持つ（決定2）。保存の形 `{key, choice, note, at}` と書き方は変えない（決定3）。回収のあとは `answers` を正とし、回答済みはページ単位のまま（決定4）。Q2 で B を選んだときだけ、決定4 に「手番の1枚では、表へ移したカードの答えは表の行を正とする」という規則を1つ足す（DJ-5）。フォルダの中に hub の文書・リポジトリの名前・hub の運用への参照を入れない。
- 変えないもの: E-B1（完成した HTML の外部の読み込みを止める検査）の判定と、その検査の項目。表の識別子の列は必ずリンクにする決まり（#469 の決定2）。
- 入れないもの: SO のまとめの中身の決まり（何を採ったとみなすか・レーンの並べ方・要約の深さ）は SO のスキルの側に持たせる（owner 2026-10-21）。種別をいつ作り・更新し・止めるか（工程との対応）は #466 に送る。スキルは用途ごとに分けず1本のままにする（owner 2026-10-21）。
- 材料の扱い: 統括が作った実物のページのデータ7件（手元の作業層）は、手元で `check` に当てる確かめにだけ使う。どのファイルも、その一部の写しも、リポジトリの中（見本・検査・plan・episode）に入れない。SO の依頼文にも入れない。見本は架空のサービスで作る（統括の補足・2026-10-23）。この plan には形と件数だけを書く。

## 設計判断

### DJ-1 種別（`kind`）はページに1つ書き、部品の組み合わせの名前にする

- データのページの項目に `kind` を足す。値は次の表の key のどれか1つで、1ページに1つだけである（「1ページ＝1種別」）。2つの種別の中身があるなら、ページを分ける。
- 種別は、既存の部品（判定カード・判断待ちの束・指摘の一覧・表・本文）の組み合わせの名前であり、描く部品は増やさない。表の列の型を1つ足すこと（DJ-6 の番号の列）だけが部品の中の変更である。
- 種別の名前（日本語）は SKILL.md の表と `glossary.md` に置く。ページには出さない（ヘッダーの行を増やすと、すべてのページの出力が変わるため）。
- 選択肢にも `kind`（選んだときの色）がある。場所が違う（ページの項目と選択肢の項目）ので名前は重ねたまま残し、SKILL.md では「ページの種別（`kind`）」「選択肢の色（選択肢の `kind`）」と書き分ける。誤りの文言は場所（`kind` と `sections[0].cards[0].options[0].kind`）で区別がつく。

種別の表（SKILL.md の「目的と部品」の表を、この表に置き換える）:

| `kind` | 名前 | してもらうこと | 要る部品と並び | 置いてよい補足 | `--body` | 答える部品 | 札と番号 | 見本 |
|---|---|---|---|---|---|---|---|---|
| `confirm` | 認識合わせ | 中身を確かめ、「確定」か「違和感がある」かを答えてもらう | 判定カードの節1つ。カードは確かめる対象ごとに1枚で、どのカードも `blocks` を持つ | なし | 置かない | 持つ | 札は確かめる対象の issue（`#N`・`owner/repo#N`）か、書かない。番号は振らない | `confirm.json` |
| `approve` | 承認 | 問いに1つずつ答えてもらう。最後に全体を承認してもらうこともある | 判定カードの節1つ以上。全体の承認のカード（札は `承認`）を置くなら、ページの最後のカードにし、1枚だけにする | 表（判定カードのあと） | 置ける（カードの上に出る） | 持つ | 問いのカードの札は `Q<数字>`。書かなければ、問いの順に Q1・Q2… を振る | `decide.json`・`approve.json`（足す） |
| `pick` | 一覧から選ぶ | 一覧の中から選んでもらう | 判定カードの節1つ（カード1枚・選び方）を先頭に置き、そのあとに表を1つ以上。表の少なくとも1つが番号の列（DJ-6）を持つ | なし | 置かない | 持つ | 番号の列の値は `候補<数字>`。書かなければ、ページの中の行の順に 候補1・候補2… を振る。カードの札は自由（番号を振らない） | `pick.json`（足す） |
| `map` | 見取り図 | 読んで把握してもらう | 表1つ以上か、`--body` の本文 | なし | 置ける | 持たない | 番号の列の値は `項目<数字>`。書かなければ順に振る | `grasp.json`・`table.json` |
| `bundle` | 束 | いくつかの作業から届いた判断待ちに答えてもらう | 判断待ちの束の部品1つ | なし | 置ける | 持つ | 振らない（カードの札は、その作業の側の自由な札） | `bundle.json` |
| `review` | レビュー | 指摘と、それぞれを採ったかを見てもらう | 指摘の一覧1つ以上を先頭に置く | 表・判定カード（指摘の一覧のあと。採否を決めてほしい指摘があるとき） | 置ける | 判定カードを足したときだけ | 振らない（指摘には番号を付けない。カードの札は自由） | `review.json` |
| `board` | 手番の1枚 | 長く更新し続けるページで、いま決めることと決まったことを1枚で見てもらう | Q2 で決める。B のときは、判定カードの節0以上を先に、表0以上をあと（部品は合わせて1つ以上）。判定カードが0枚なら、番号の列を持つ表（決まったこと）を1つ以上 | なし | 置かない | 開いたカードがあれば持つ | B のときは、問いのカードの札と番号の列の値に `Q<数字>` を必ず書く（自動では振らない） | `board.json`（B のとき足す） |

- 種別の名前は、issue の候補の名前のまま使う。`map` の名前は「見取り図」で、いまの `grasp` の見本（`grasp.json`）と表だけの見本（`table.json`）がここに入る。
- `approve` の「全体の承認のカード」を必須にしないのは、問いだけを答えてもらうページ（いまの `decide.json`・実物の問いの束1件）があるためである。承認のカードを置くかどうかは中身で決まり、置くならページの最後に1枚という形だけを決める（plan の承認ではふつう置く、と SKILL.md に書く）。
- `confirm` は、塊の数や塊の見出しの文言を決めない（`issue-intake` の3つの塊はその使い方の1つで、このスキルはほかの確かめにも使う）。選択肢の key も決めない。

### DJ-2 `purpose` は `kind` に置き換える

`purpose` はデータから外し、種別から導く。データに `purpose` があれば、知らない項目（E-F2）として止め、理由の文に「`purpose` は `kind` に置き換えた。`kind` を書く」と出す。

| 種別 | 導く `purpose`（型の `data-purpose` の属性に出す値） |
|---|---|
| `confirm`・`approve`・`pick`・`bundle`・`board` | `decide` |
| `map` | `grasp` |
| `review` | `review` |

- 退けた案は2つある。「`purpose` を残し、`kind` と食い違えば止める」は、同じことを2か所に書かせ、食い違いの規則が1つ増える。「`purpose` を任意にし、書けば `kind` と照らす」は、古いデータを通す代わりに、書いても書かなくてもよい項目を残す。どちらの案でも、古いデータは `kind` を足さないと通らない（DJ-3）ので、`purpose` を残す利点は無い。
- 型の `data-purpose` の属性は、種別から導いた値で残す。どこからも参照されていない（`page.css` と `page.js` に `data-purpose` を読む規則もコードも無い）が、残せば既存の見本の出力が変わらない（A10）。

### DJ-3 `kind` の無いデータは止める（必須にする）

- `kind` は必須の項目にする。無ければ E-F3（必須の項目が無い）で止まる。値が表に無ければ E-H3（決まった値でない）で止まる。
- 退けた案は2つある。「既定の種別に畳む」は、`purpose: decide` のデータが `confirm`・`approve`・`pick`・`bundle` のどれかを決められない。「部品から種別を推し量る」は、いまの解釈のぶれをスクリプトに移すだけで、owner の指摘（種別が無いので解釈がぶれる）に答えない。
- 古いデータを直す手間は、`kind` を1行足して `purpose` を1行消すことである。種別の検証で止まるもの（下の表）は、そのぶん中身も直す。データはページを作るたびに書き直すもので、回答済みのページを作り直す場面でも同じ直しで足りる。

実物のページのデータ7件（手元の作業層・形と件数だけを書く）の当て方:

| 形 | 件数 | 新しい規則で止まる理由 | 通すための直し |
|---|---|---|---|
| 認識合わせ（塊あり） | 1 | `kind` が無い（E-F3）・`purpose` がある（E-F2） | `kind: confirm` を足し、`purpose` を消す |
| 認識合わせ（平らな要点） | 1 | 上の2つと、カードが `blocks` を持たない（E-K1・4枚） | 上に加えて、要点を塊に分ける（#469 で直した当てはめのずれそのもの） |
| 承認 | 3 | `kind`・`purpose`。うち2件は、札に括弧書き（`Q5（…）` の形）を足したカードがある（E-I1） | `kind: approve`。括弧書きは札から外し、カードの題か要点へ移す |
| 問いの束 | 1 | `kind`・`purpose`。札が `問い<数字>・論点<数字>` の形（E-I1・16枚） | `kind: approve`。札を外して Q1〜Q16 を自動で振るか、Q の番号を書く。論点の番号はカードの題か要点へ移す |
| 一覧から選ぶ | 1 | `kind`・`purpose`。番号の列を持つ表が無い（E-K1。番号は裸の数字の `text` の列に書いてある） | `kind: pick`。候補を並べた表の番号の列を、番号の列の型（DJ-6）にして `候補<数字>` を書く。上位の候補を並べた表は、ほかの表の候補を指すだけなので番号の列を持たず、`候補3・候補28` のように指す（DJ-7 で行へのアンカーになる） |

- 表の「止まる理由」のうち E-K1・E-I1 は、`kind` を足して `purpose` を消した段で初めて出る。元のデータでは種別も識別子も見ない（`kind` が無いので）ため、出るのは E-F3 と E-F2 だけである（DJ-10）。受入 A11 は、元のデータ・`kind` だけを直した写し・中身も直した写しの3段で確かめる（設計SO 指摘8）。写しは手元の作業層に置き、リポジトリに入れない。

### DJ-4 余計な部品は閉じた許可の表で止め、補足は実際に要る分だけ許す

種別ごとに、要る部品・置いてよい補足・`--body` の可否を DJ-1 の表で閉じて決め、表に無い部品は止める（閉じた許可の表）。置いてよい補足は、実物のデータ・いまの見本・いまの SKILL.md が勧めている使い方のどれかで要るとしたものだけを入れる。承認のページに表で補足する・レビューに採否の判定カードを足す、はいまの SKILL.md が勧めているので入れる。要る場面が実物で出たら、補足を1つ足すのは表の1行と検査の1つで済む。

要る部品と並びの決まりは、次の3つの当てはめのずれを拾うために置く。

1. 答える部品の無い種別（`map`）に、答える部品（判定カード・判断待ちの束）を置いた。保存のコードが入り、読むだけのページでなくなる。
2. 種別の定義が置き換えたものを、別の部品で書いた。`confirm` のカードに `blocks` が無い（認識合わせを平らな要点に流し込んだずれ）、`pick` に番号の列を持つ表が無い（候補の番号を `#N` や裸の数字で書いたずれ）がこれに当たる。
3. 並びが種別の読む順を壊す。`pick` で選び方のカードが表の上に無い、`approve` で承認のカードが最後に無い、`review` で指摘の一覧が部品の先頭に無い、がこれに当たる。

- **意図した制限を明示する。** `confirm` では、平らな要点だけのカードを止める（`blocks` を必ず持たせる）。平らな要点で足りる確かめは、認識合わせでなく承認の問いとして書く。いまの SKILL.md の「中身の置き場」（平らな箇条書きで足りるときは `points`）は、承認の問いのカードと `review`・`bundle` のカードに残り、`confirm` では `blocks` を使う、と書き直す。`confirm` に表の補足は置かない（実物にも見本にも要る場面が無い）。
- **「並び」は部品（`sections`）の順を指す。** `--body` の本文は、型の上でいつも部品の上に出る（`template.html`）。本文を置けるのは、部品の上に本文があっても読む順を壊さない種別（`approve` の前提の説明・`map`・`review` の前置き・`bundle` の前置き）だけにする。カードを先頭に置く種別（`pick`）、外から来た文を本文に写さない決まりの種別（`confirm`）、本文がカードの上に出たことがずれだった種別（`board`）では置かない。
- 誤りの規則は E-K1（要る部品が無い）・E-K2（置けない部品がある。`--body` を含む）・E-K3（並びが違う）の3つにする（DJ-10）。
- 退けた案は2つある。「補足を一切置かせない」は、承認のページに表で補足する・レビューに採否の判定カードを足す（いまの SKILL.md が勧めている使い方）を止め、種別に収まらない中身を無理に当てはめる元になる（brief の (6)）。「余計な部品は止めず、SKILL.md に書くだけ」は、実物で起きた当てはめのずれ（平らな要点・番号の列の無い一覧）を検証で拾えない。
- 限界: 1枚のカードに問いを5つまとめる（別のリポジトリの統括の実例）ような中身のずれは、部品の形からは見分けられない。SKILL.md に「問いは1枚に1つ」と書くだけにする。

### DJ-6 ページの中の項目の識別子を、カードの札と表の番号の列で定義する

- **識別子を定義できるのは2か所だけにする。** 種別が札の接頭辞を持つカードの札（`approve` と `board` の問いのカード）と、表の番号の列の値である。要点や本文に `B2` と書いても、識別子の定義にはならない。
- **表の番号の列を、列の型 `no` で示す。** `{"key": "no", "label": "番号", "type": "no"}` のように書く。値は文字列で、種別の行の接頭辞（`pick` は `候補`、`map` は `項目`、`board` は `Q`）のあとに1以上の数字を続ける。番号の列を置けるのは、行の接頭辞を持つ種別（`pick`・`map`・`board`）の表だけで、1つの表に1列までにする。
- **番号の振り方:** 書かなければスクリプトが振る（`approve` の問いのカードと、`pick`・`map` の番号の列）。振る番号は、ページの中の順（カードは問いのカードの順・行はページの中のすべての番号の列の行の順）で1から数える。1ページの中で、書いたものと書かないものを混ぜたら止める（E-I1。混ぜると、振った番号が書いた番号と重なりうる）。番号の列の値を書かないときは、その行のその key を省くか、空の文字列にする。`board` は必ず書く（DJ-5）。
- **接頭辞の形が合わなければ止める（E-I1）。** `approve` の問いのカードの札は `Q<数字>`、全体の承認のカードの札は `承認` だけを受け付ける。`confirm` の札は `#N` か `owner/repo#N` の形だけを受け付ける。札が自由な種別（`pick`・`bundle`・`review` のカード）は、いまと同じく空でない文字列なら通し、識別子にはしない。
- **識別子はページの中で重ねない（E-I2）。** カードの札と番号の列の値を合わせて見る。
- **接頭辞の語は `glossary.md` に置き、`build.py` が読む。** 用語集に新しい節「識別子の接頭辞」を足し、表に `prefix.question`（`Q`）・`prefix.candidate`（`候補`）・`prefix.item`（`項目`）・`tag.approval`（`承認`）の4行を置く。「札の言葉と固定の文」の表には入れない。その表の言葉は、答える部品のあるページの埋め込みデータ（`hp-data` の `labels`）に丸ごと入るので、4行を足すと既存のページの出力が変わり、JS が使わない語をページに持ち込むためである（設計SO 指摘3）。どの種別がどの接頭辞を使うか（振り方）は `build.py` と SKILL.md の種別の表が持ち、用語集は語だけを持つ。語を直せば、受け付ける札と番号の形も変わる（いまの用語集の「言葉を直しても受け付ける値は変わらない」の例外になる）ので、用語集にそう書く。
- **接頭辞の語の形:** 語は1文字以上で、すべての文字が文字（Python の `str.isalpha()` が真。英字・漢字・かなを含み、数字・空白・`-`・`#`・`・` などの記号を含まない）であること、4つが互いに重ならず、どれもほかの語の頭に当たらないことを、用語集を読むときに確かめる（壊れていれば終了コード 2）。記号を許さないので、ページの中の識別子（`Q2`）は、外部の課題管理の ID（`<接頭辞>-<数字>` で必ず `-` を含む）・`#N`・`PR #N` と同じ文字列になりえない（設計SO 指摘6）。
- **語は検証と描画の両方に同じものを渡す。** いまの `validate()` は用語集を受け取らず、`check` は読んだ用語集を捨てている。用語集から読んだ接頭辞の語を `validate(data, has_body, words)` と `render` の両方へ渡す形に変える（`words` を省いたら既定の用語集から読む）。接頭辞の語を変えた用語集で `check` と `build` が同じ判定をすることを検査で見る（A2）。
- **空の札と、番号の列の省略:** 札が空の文字列なら、いまと同じく E-C5 で止め、E-I1 を重ねない。札を省いた（`tag` の項目が無い）ときだけ、番号を振る対象にする。番号の列は、行の key を省いてよい唯一の列にする（ほかの列はいまどおり、足りない key を E-F3 で止める）。番号の列の値が空の文字列なら、省いたのと同じに扱う。
- 接頭辞の語の推奨（Q1 で owner が決める）: 問いは `Q`、候補は `候補`、見取り図の行は `項目`、承認のカードの札は `承認`。`Q` は承認のページ3件と別のリポジトリの統括の実例で使われてきた形で、札の幅が狭い。`候補` は一覧から選ぶ実物で使われ、owner も「`候補4` と書けば飛ぶ」と例に出した。`項目` は見取り図の行の中身を問わない語として選んだ（実物の見取り図は 手順・図・段 など中身ごとの語を使っていて、1つの語にそろった例が無い）。

### DJ-7 本文の中の識別子を、ページの中のアンカーにする

- **リンクにするのは、そのページで定義した識別子（DJ-6）の文字列と完全に一致するものだけにする。** 定義していない識別子（plan の `DJ-4` や、定義の無い `Q9`）と裸の数字は文字のまま出す。長い識別子を先に当てる。

- **照合の順:** コードの書式（`` `…` ``）を先に切り出し、その外を1回の走査で左から見る。同じ位置から始まる候補は、URL → `PR #N` → `owner/repo#N` → `#N` → 外部の課題管理の ID → ページの中の識別子の順に当てる。URL に当たった部分の中の文字は、ほかの形として見ない。`#N` と外部の課題管理の ID の境界は、いまのまま変えない（`feature/#212` の `#212` は、いまと同じく issue のリンクになる。変えると既存の見本と実物の出力が変わるため、今回は触らない）。

### DJ-8 `PR #N` は PR の URL に、`owner/repo#N` はそのリポジトリの issue にする

- **`PR #N`:** 表示の文の中の `PR #N`（`PR` と `#` のあいだに空白1つ）は、全体を1つのリンクにし、先を `<repo_url>/pull/N` にする。表の識別子の列の `PR #N` も同じ先にする。いまは `#N` の部分だけが `issues/N` のリンクになり、`PR ` は文字のまま残っている。前に英数字か `_` が続くもの（`XPR #3`）は `PR #N` として扱わず、いまと同じく `#3` の部分だけが issue のリンクになる。後ろの境界は `#N` と同じ（数字・英字・`_` が続かない）にする。
  - #469 の DJ-5 は、GitHub 以外の置き場でも通りやすいとして `/issues/N` を選び、`/pull/N` を「GitHub だけの形」として退けていた（推測で、確かめてはいない）。今回は owner が深掘りで `/pull/N` に決めた（#477 の確定版）。GitHub では、PR の番号を `/issues/N` で開くと転送されて開けるが、`/pull/N` は転送を待たずに PR を開く。GitLab などでは `/pull/N` が開けないので、SKILL.md の限界に書く。
- **`owner/repo#N`:** 表示の文と表の識別子の列で受け付け、先を「近い送り元の `repo_url` と同じホスト」の `/<owner>/<repo>/issues/N` にする。近い送り元に `repo_url` が無ければ、表示の文では文字のまま出し、表の識別子の列では E-L1 で止める（`#N` と同じ扱い）。別のリポジトリの PR も `owner/repo#N` と書く（GitHub が転送する）。
  - 形は、オーナーが英数字で始まり英数字と `-` が続く39文字まで、リポジトリが英数字・`.`・`_`・`-` の100文字まで、とする。前に英数字・`_`・`.`・`/`・`-` が続くもの（`docs/a/b#3` の中の `a/b#3`）はリンクにしない。`feature/#212_x` のようなブランチの名前は、`/` のあとがすぐ `#` なのでこの形に当たらない。
