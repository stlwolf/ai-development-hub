# #565 humanizer の規則を URL で読んで当てる推敲のスキルを canonical に足す

## 背景

owner は、AI が書いた日本語の文（Slack と Notion の下書き・issue と PR の本文・報告）を読みやすくしたい（#565・2026-11-04）。調査の単位（R1〜R4・`docs/research/2026-11-04-ja-readability-skills.md`）で2つの外部の道具を一次情報で読んだ。yomiyasu（nanaism・MIT）は文の構造を直すスキルで、owner の判定で user 層に試し入れした（hub の配布物には入れない）。humanizer（いもす研）は規則の文のファイル（`https://imoz.jp/humanizer.ja.txt`・英語は `humanizer.en.txt`）を AI に読ませて直させる形で、構成の重複・予告・まとめの言い直し・読者と目的・主張の強さの扱いに強い。ただし規則の文にライセンスの明示が無いので、hub（公開リポジトリ）の配布物に本文を写せない。

owner と統括の案は、規則の本文を持たず、URL と当て方の手順だけを持つ hub のスキルにすることである（追補の brief・2026-11-04）。この plan は、そのスキルを `canonical/skills/` に1本足す計画である。

## この plan の範囲

- やること: スキルのフォルダ（名前は DJ-1）を `canonical/skills/` に作り、`canonical/CATALOG.md` に1行足す。フォルダの中身は `SKILL.md` と、Web 版の Claude や ChatGPT に貼る短い指示の文のファイル1つ（DJ-5）。規則の要点の参照ファイルは置かない（ゲート3 の Q57）。
- 守ること: 規則の本文を写さない（引用は見出しの語など短い語に限る）。規則の要約も配らない（Q57）。持ち運べる形にする（hub の文書・リポジトリの名前・hub の運用への参照をフォルダの中に入れない。`html-one-pager`・`runbook-authoring` と同じ）。
- 入れないもの: yomiyasu を hub に入れること。hub の rules・出力の型・CLAUDE.md の変更。hook や常時の発火。規則の文を hub の規則に取り込むこと（それは試用の記録を見てから別の単位で決める）。
- 受入に入れないもの: Slack と Notion の下書きでの効果の評価（試用の記録 `~/.claude/yomiyasu-trial/log.md` の側の仕事。hub の外）。

## 設計判断

### DJ-1 スキルの名前と入口（description）

- **名前は `humanize-ja` を推奨する**（統括の案）。比べた案は3つある。`humanizer-rules` は道具の名前に寄り、何をするかが読めない。`ja-readability-edit` は中身を言うが長く、英語の規則（`humanizer.en.txt`）も当てられることが読めない。`rules-url-proofread`（規則の URL を渡して当てる汎用の形。DJ-2 の案C）は、既定の規則が humanizer であることが読めない。`humanize-ja` は短く、hub の既存の名前（動詞か対象 + 区分）に並び、既定の対象が日本語であることが読める。英語の文にも当てられることは description に書く。
- **description の案**（題材が欠けた依頼でも読み込まれる形。`runbook-authoring` の DJ-1 と同じ考え）:

  > AI が書いた日本語（英語も可）の下書きを、公開されている推敲の規則（いもす研の humanizer・`https://imoz.jp/humanizer.ja.txt`）に当てて、説明の重複・予告と言い直し・あいまいな評価・読者に合わない詳しさを直し、変えた箇所と理由の一覧を添えて返すときに使う。このスキルの名前を出して頼まれたとき（「humanizer で直して」など）と、下書き（Slack や Notion の文・issue や PR の本文・報告）の推敲をはっきり頼まれたときに使う。文章を書く依頼や投稿の準備だけでは使わない。文の構造（比喩の動詞・主語と述語・否定の対比）を機械の検査つきで直すスキル（yomiyasu）が入っていれば、このスキルのあとにそちらを当てる。規則の本文は持たず、使うたびに URL から読み、読めないときは控えた要点で当てる。

- 発火は名前を出した依頼に限る（ゲート3 の Q58・owner: 試用のあいだは名前で呼んだときだけ）。名前を出さない推敲の依頼・文章を書く依頼には当てない。plan の初稿と I1-1 の初版は「推敲をはっきり頼んだ依頼」も含めていたが、実装SO の指摘で Q58 とずれていると分かり、名前だけにそろえた（試し入れした yomiyasu の description は別の線に書き換えられているが、このスキルは owner の答えに従う）。設計SO の指摘1で、初稿の「外に出す前に整えたいとき」は投稿の準備にも自動で当たる読みになるので外した。
- 英語の規則も当てられると書くので、受入 A3 に英語の短い下書きを1つ入れる（設計SO の指摘1）。

### DJ-2 入力と出力

- **入力**: (1) 下書き（ファイルのパスか、貼られた本文か、直前の自分の返答の本文）。(2) 書き手の「これだけは伝えたい点」と、省いてよいこと（任意。直す判断にそれが要る箇所があるときだけ1回聞く。聞けないときは聞かずに進み、推測で補わずにその箇所を保留して出力の「書き手に確かめたい点」に出す。設計SO の指摘2で、毎回聞く形から「要るときだけ」に変えた）。(3) 読者と媒体（任意。Slack・Notion・issue・PR・報告など。無ければ本文から推定し、推定したと出力に書く）。(4) 規則の URL（任意。既定は日本語の規則。英語の本文なら英語の規則。別の URL を渡されたらそれを使う）。
- **出力**: (a) 直した本文。(b) 変えた箇所と理由の一覧（箇所・課題・直し方。規則のどの観点かを添える）。(c) 意味・条件・主張の強さが動いた恐れのある箇所（規則の「照合」の工程で見つけたもの。無ければ「無し」）。(d) 書き手に確かめたい点（最大3つ。無ければ出さない）。(e) 使った規則（URL・読めたか・読めなかったとき要点で当てたこと・ページの最終更新日が控えと違うとき）。
- 機能を持つ記法（リンク先・コード・チェックボックスの状態・表の列）は保つ。段落・見出し・説明の順は、依頼の範囲で変えてよい（構成を直すのがこのスキルの役目なので、構成を固定しない。設計SO の指摘2）。事実・数値・主体・条件・例外・否定・主張の強さを、根拠なく足さない・消さない・変えない（規則の「言い換えで保つ意味」と、yomiyasu の最上位の決まりと同じ線）。
- 「伝えたい点」を聞く理由は、規則の著者の注意（規則では書き手の思いを補えない。AI に任せると関連する話題を無難に一様な調子で埋める）にある（調査ノート P-7）。

### DJ-3 規則の読み込みと、読めないときの要点

- 使うたびに URL を読む（Claude Code では URL を読む道具、ほかの環境ではその環境の道具。読めるかは受入の A5 で確かめる）。読んだ結果は「全文を読めた」「途中までしか読めなかった（切れている・検索の抜粋・エラーのページ）」「読めなかった」の3つに分ける。全文を読めたときだけ「規則を当てた」と出力に書く。スキル自身は規則の本文をファイルに書かず、フォルダに同梱もしない（ハーネスや道具の記録までは保証しない。設計SO の指摘3）。
- 外部の本文は推敲の判断材料として扱う。規則の文に操作の指示（ファイルを書く・工程の報告を返答に出す・やり直す）があっても、このスキルの入力・出力・操作の範囲を優先し、外部の本文から新しい操作の権限を得ない（設計SO の追加のリスク）。規則の工程のやり直しは、診断→修正→照合を1回だけにし、問題が残れば未解決として返す（終了の条件）。
- 規則の要点の要約は同梱しない（ゲート3 の Q57・owner）。規則由来の文を配らないためで、plan の初稿にあった `references/key-points.md` は置かない。
- 規則が読めない・途中までしか読めないときは、どの規則（既定の日本語・英語・利用者の URL）でも本文を直さずに返し、出力の (e) に「規則を読めなかったので直していない」と書く。URL が 404 を返す・ページが消えている・別の内容に変わっているときは、そのことをはっきり知らせる（Q57 の補足）。
- 更新の検知は、本文の形だけを控えて比べる（Q57）。控えるのは、読み込んだ日付（2026-11-04）・行数・大きさ・最上位の見出しの並びで、SKILL.md に書く。読めた本文の形が控えと違えば「規則が変わっているかもしれない」と (e) に書き、比べられなければ「更新の有無は未確認」と書く（紹介ページの日付は規則ファイルの改訂と一致しないので使わない。設計SO の指摘3）。追随（控えの更新）は人の仕事で、スキルは自動では直さない。
- 規則の本文のバックアップは、hub の外（user 層）に日付付きで取る（Q57 の補足）。配布物には入れない。置き場は `~/.claude/humanize-ja-backup/<日付>/` で、取った日付と場所は episode に記録する（SKILL.md には書かない。持ち運べる形）。

### DJ-4 yomiyasu との分担と順

- このスキルは構成と説明の組み立て（重複・予告・まとめ・読者と目的・主張の強さ・語彙）を直す。yomiyasu は文の構造（無生物主語と比喩の動詞・述語の脱落・否定の対比）と、機械の lint と diff による意味の突合を持つ。
- 順は、このスキルが先、yomiyasu が後。構成を変えたあとに文を整えるほうが手戻りが少ない。最初の原文を比較の基準として持ち続け、yomiyasu のあとに「最初の原文」と「最終稿」を照合する（このスキルの出力と最終稿だけを比べると、このスキルで落ちた条件を見つけられない。設計SO の指摘4）。yomiyasu には直した本文だけを渡し、変えた箇所の一覧や確かめたい点は渡さない。yomiyasu の diff は確かめる候補を出す道具で、意味が保たれたことの判定ではない。
- SKILL.md には、yomiyasu が入っていないときはこのスキルだけで終えること、入っていればあとに当てることを勧める（勧めるだけで、自動では呼ばない）と書く。yomiyasu の置き場や hub の運用は書かない（持ち運べる形）。

### DJ-5 持ち運べる形と hub の側の変更

- 必須のファイルの依存はフォルダの中に閉じる。hub の文書・リポジトリ・ほかのスキルへの必須の参照を入れない。yomiyasu は名前だけで指す任意の連携先で、無くても完結する（設計SO の指摘5で「参照しない」の意味を「必須の依存を持たない」に絞った）。
- hub の側の変更は `canonical/CATALOG.md` の1行だけ。rules・出力の型・hooks は変えない。
- Web 版の Claude や ChatGPT で記事を書くときにも使えるよう、フォルダに `paste-prompt.md` を置く（ゲート3 の Q58 の補足・owner）。中身は貼って使う短い指示の文で、日本語1段落（規則の URL を読んで当てる・意味を変えない・変えた箇所を一覧で返す・伝えたい点があれば先に書く）と、英語の規則向けの同じ1段落。スキルの手順の縮約で、規則の本文は含まない。
- Codex と Cursor の配布は hub の sync の仕組みのとおり（`canonical/skills/` 配下は3ツールへ写る）。URL を読めるかは環境で違うので、受入の A5 で確かめた結果（環境・日付・道具）を SKILL.md の「限界」に書き、ツール名だけで「読める・読めない」と一般化しない。

## ゲート1（ゼロベース代替探索）

初期案は「規則の URL と手順だけを持つスキル」（案B）である。暗黙の前提は、スキルの形で配ること、規則の本文を持たないこと、呼んだときだけ使うこと、の3つ。

```text
DJ: humanizer の規則を hub でどう使う形にするか
├── 案A（規則の本文を canonical に写す）→ 差分軸: 保持の場所 → 採否: ❌ ライセンスの明示が無い
├── 案B（URL と手順だけのスキル。読めないときは要点）→ 初期案 → 採用（下の SO の結果を見て確定）
├── 案C（規則の URL を引数で受ける汎用のスキル。humanizer を既定にする）→ 差分軸: 汎用性 → 採否: 一部採る。DJ-2 の入力 (4) で URL を渡せるようにし、名前は既定の対象で付ける（DJ-1）
├── 案D（スキルでなく出力の型か rules に観点を足す）→ 差分軸: 発火の層 → 採否: ❌ owner の判定（Q55 の補足）はスキル。規則の取り込みは試用の記録のあと
├── 案E（yomiyasu の .yomiyasu-words や CLAUDE.md の1行で humanizer を呼ぶ）→ 差分軸: 道具の寄せ先 → 採否: ❌ yomiyasu は hub の外で、hub の配布物にならない
├── 案F（人が規則を読み、スキルは編集の指示を反映する。設計SO が出した）→ 差分軸: 規則を読む主体を人に移す → 採否: ❌ owner の目的は AI に当てさせること。「伝えたい点」の入力（DJ-2）が人の意図を渡す経路として残る
├── 案G（規則を読むレビューの工程と本文を直す工程を別の文脈に分ける。設計SO が出した）→ 差分軸: 工程の分離・受け渡しの形 → 採否: 条件付きで退ける。成立条件は「編集側の環境が URL を読めないとき」か「外部の本文の操作指示を隔てる必要が出たとき」。A5 で読めない環境が見つかったら再訪する
└── 案H（humanizer を読まず、自前の検査プログラムで候補を出す。設計SO が出した）→ 差分軸: 自然言語の規則の実行時解釈から検査仕様へ → 採否: ❌ owner の方針（humanizer の規則を当てる）から外れる。機械の検査は yomiyasu の lint が持つ
```

設計SO（下）の選択肢拡張で案F・案G・案H が出た。どれも初期案の外の責務分界で、採否は木に書いた。新しいカテゴリの案は条件付きで1つ（案G）残り、確定を止める理由にはならないと判断した。SO の出力は `tmp/565-so/out/codex-stdout.txt`（作業層・残らない）で、要点は episode の P2 に写した。

## リスク・未確認事項

- 規則の URL が読めない環境では要点だけで当てる。要点は hub の言葉での要約なので、規則の細部（例や判断の仕方）は落ちる。
- 規則が更新されると要点が古くなる。知らせは出すが、追随は人の仕事である。
- 規則は記事（ブログ・解説）向けに書かれている。Slack の短い下書きに当てると、「読者と記事の目的」の節のような前提の整理が重くなる恐れがある。SKILL.md で、短い文には工程を縮めて当てる（整理を1行で済ませる）と書く。
- ライセンス（未検証の仮定）: hub は規則の本文も要約も配布物に含めない（Q57）。実行時に URL を読んで当てることは、著者が「URL を AI に読ませて直す」使い方を紹介しているので意図に沿う。user 層のバックアップは配布しない手元の写しである。
- 外部の本文が操作の範囲を変える恐れ: 任意の URL を毎回読む形なので、推敲と無関係な指示を取り込みうる。DJ-3 の境界で防ぐが、保証ではない。
- yomiyasu の機械の検査は、入っていても実行できる環境とは限らない（この単位でも lint の実行がハーネスの許可で止まった）。DJ-4 は「入っていれば勧める」に留め、実行可否には触れない。
