# #668 見取り図の「状況」のタブと概要の構造を、html-one-pager に入れる

## 背景

- 見取り図と判断ボードの形がページごと・リポジトリごとにそろっておらず、読む負荷が上がっている（#668 の本文）。
- 10枚のページを比べ、hub の見取り図に「状況」を当てたサンプルを3回作り直して、owner が形を決めた（#668 のコメントの「決まったこと」）。
  1. 「状況」は見取り図の独立したタブにする。
  2. タブの中は状態ごとに表を分け、表の題に件数と状態ごとの色を出す。
  3. 状態は 指示待ち・実行中・トリガー待ち・完了 の4つ。
  4. 列は表ごとに変える（指示待ち: 何を待っているか・持っているセッション・いつから / 実行中: 持っているセッション・次に止まる所 / トリガー待ち: 何が起きたら動くか・止めた日 / 完了: 終わった日）。
  5. 誰も持っていない作業（起票のみ・未着手）は状況のタブに入れない。
  6. 概要のタブの構造も決める（中身の案は plan で出す）。
  7. この形を `html-one-pager` に入れ、データを書けば同じ形で描かれ、欠けを `check` が止める形にする。
- いまのサンプルは、本文の先頭の `style` で表の題に色を付け、状態ごとの表を `table` の部品で1つずつ書いている。件数は書き手が題に書いている。
- いまの型では、状況のタブを先頭に置けない。本文で書いたタブを、データで書いたタブより先に並べる決まり（`SKILL.md` の「タブで分ける」節・E-N3）があり、概要は本文で書かれているためである。

## この plan の範囲

入れるもの:

1. 見取り図（`map`）で、「状況」のタブをデータから描く部品。状態ごとに表を分け、題に件数と色を出す。決まった語でない状態や、状態ごとの列の欠けを `check` が止める。
2. 概要のタブの構造（案を2つ・推奨1つ）。
3. タブの並び（状況のタブを先頭に置けるようにする）。
4. `SKILL.md`・`glossary.md`・`examples/`・`tests/test_build.py` の整合と、`canonical/CATALOG.md` の html-one-pager の行。

入れないもの（#668 に残す・別の単位）:

- 状況のタブを出来事で書き換える仕組み（更新のタイミング・出し直さずに行を書き換える方法・通知）。
- 判断ボード（`board`）の「動いている作業」をこの形にそろえること（#539 と一緒に決める）。
- cockpit の表示（#546）。
- 統括の手順（`judgment-board-flow` など）の変更。

PR は1つにする。

## 設計判断

各判断は、案・推奨・捨てた案の弱い所の順に書く。owner に聞くものは「owner に聞くこと」節で問いにした。

### DJ-1 状況の部品の形

- **案A（推奨）: 新しい部品 `status` を1つ足す。** 行ごとに `state` を書き、`build.py` が状態ごとの4つの表に分けて描く。列は状態ごとに型が決める。
- 案B: いまの `table` に `state` の印を足す。書き手は状態ごとに表を4つ書き、`check` は印と列の組を見る。
- 案C: 1つの表に「状態」の列を置き、描くときに分ける。
- 推奨の理由: 案A は、表の数・並び・題・列を書き手が決めないので、ページごとにばらつく余地がいちばん少ない（#668 の「ばらつかせない」に合う）。状態を変えるときは行の `state` を1か所直すだけで、行を別の表へ移す手間が無い（#668 の「出来事で決まった行だけを書き換える」方向にも合う）。
- 捨てた案の弱い所: 案B は、表の書き忘れ・並びの誤り・題の件数の数え違いを書き手に残す。サンプルの形はこれで、`style` を本文に手で書く必要があった。案C は、`table` の行のオブジェクトに状態ごとに違う列を持たせられない（いまの表は列が全行で共通）ので、列を表ごとに変える決まり（決まったことの4）と合わない。

### DJ-2 行の項目

| 状態（`state`） | 表の題に出る語 | 行の項目（すべて必須） | 列の見出し |
|---|---|---|---|
| `waiting` | 指示待ち | `refs`・`what`・`need`・`who`・`since` | 作業・中身・何を待っているか・持っているセッション・いつから |
| `running` | 実行中 | `refs`・`what`・`who`・`stop` | 作業・中身・持っているセッション・次に止まる所 |
| `trigger` | トリガー待ち | `refs`・`what`・`wake`・`since` | 作業・中身・何が起きたら動くか・止めた日 |
| `done` | 完了 | `refs`・`what`・`ended` | 作業・中身・終わった日 |

- `refs` は表の `ref` の欄と同じ形（識別子1つの文字列か配列。`#N`・`PR #N`・`owner/repo#N`・外部の課題管理の ID）で、リンクにできないと E-L1 で止まる。issue の無い作業のために空の配列を許す。
- `refs` 以外は文字列か `{text, evidence}`（表の `text` の欄と同じ形）。**表と違い、空の文字列と空白だけの文字列は止める**（いまの表は空の欄を許すので、表の検査をそのまま使わない・設計SO の指摘4）。状態に無い項目（`running` の行の `since` など）と、知らない項目は止める。
- `who`（持っているセッション）は、統括か子のラベルで書く。ペインの番号（`%` と数字）を書くと止める（ページは長く残り、ペインの番号はすぐ別のペインを指すため）。
- 誰も持っていない作業を入れない決まり（決まったことの5）は、`check` では見ない。「起票のみ」と「未着手」を見分ける項目が行に無いためである。`SKILL.md` に書く。
- 捨てた案: 状態ごとに列を書き手が足せる形。ばらつきが戻る。

### DJ-3 状態の語と色の置き場

- **推奨: データには英語の key（`waiting`・`running`・`trigger`・`done`）を書き、表の題の語・説明・列の見出しは `glossary.md` の「札の言葉と固定の文」の表に置く。色は `page.css` に状態ごとのクラスで置く。** いまの札（確かめた度合い・採否）と同じ置き方である。
- 色は、サンプルで owner が見た組をそのまま使う（指示待ち: `--c-fix` の黄土色・実行中: `--c-go` の緑・トリガー待ち: `--c-plain` の青・完了: `--c-no` の灰色）。暗い表示の色も同じトークンで決まる。
- 捨てた案: 日本語の語をデータに直接書く形。言葉を直すたびにデータが止まる。色を書き手が選ぶ形。ページごとに色がばらつく。

### DJ-4 件数

- **推奨: `build.py` が行から数え、題に「指示待ち（2件）」の形で出す。** 書き手は件数を書かない。
- 捨てた案: 書き手が題に書く形（いまのサンプル）。行と件数が食い違いうる。

### DJ-5 0件の状態

- **推奨: 4つの状態の題をいつも出し、行が無い状態は題の下に「なし」の1行を出す。** 状態の並びと件数が、どのページでも同じ位置で読める。
- 捨てた案: 0件の表を出さない形。ページによって表の数が変わり、「指示待ちが0件」と「指示待ちを書き忘れた」が見分けられない。

### DJ-6 完了を何日ぶん残すか

- **推奨: 型は日数を決めない。** 部品に任意の `done_days`（1以上の整数）を置け、書けば完了の題の下に「残す目安: 4日」と出る。題は「完了（4件）」で、「直近4日」とは書かない（日付の範囲を `check` で見ないので、範囲を言い切ると、11-01 の行が残っていても「直近4日」と出てしまう・ゲート1 の指摘）。どの行を残すかは書き手が決める（日付は文字列で、年を持たない）。`done_days` は真偽値・0・小数を止める。
- 何日にするかは #668 の「まだ決めていないこと」に残す。決まったら `SKILL.md` の推奨の値として書き足す。
- 捨てた案: 型が日数を決め、`build.py` が古い行を落とす形。日付の形を決める必要があり、出来事で行を書き換える仕組み（範囲外）と一緒に決めるほうがよい。

### DJ-7 置き場とタブの並び

- **推奨: `status` の部品は見取り図に1つまでで、部品の先頭に置く。タブのあるページでは、最初のタブに `status` の部品だけを入れる。`build.py` は `status` を本文（`--body`）より上に描く。** 並びの検査（E-N3）は「状況のタブ → 本文のパネルのタブ → データの部品のタブ」の順で見る。`status` が無いページの並びの決まりは変えない。
  - タブの無い見取り図でも、状況は本文より上に出る。
- 捨てた案:
  - 本文をパネルごとに切り分け、データのタブと `tabs` の順に差し込む形（並びの決まりそのものを外す）。どのタブでも先頭に置ける一般の形だが、本文の読み取りを位置まで広げる必要がある。本文の読み取りは Python の版で違いが出て、直近にも2回直している（PR #662・PR #664）。状況だけを先頭に置ければ足りる。
  - 並びの決まりを変えず、状況を本文のタブ（概要）のあとに置く形。概要が先に来て、状況が先頭にならない。サンプルはこの形（概要 → 状況）だった。

### DJ-8 状況の部品を必須にするか

- **推奨: 型では必須にしない。** `SKILL.md` に「統括が使い続ける見取り図には状況のタブを置く」と書く。
- ほかの案（ゲート1 で出た）: 見取り図に用途の宣言（たとえば `profile: ongoing`）を足し、宣言したページだけで状況を必須にする形。いまのデータを壊さずに、使い続ける見取り図の書き忘れを止められる。ただし宣言の書き忘れは止まらない。この単位では入れず、状況の書き忘れが実際に起きたら足す（あとから足しても、宣言の無いページは変わらない）。
- 捨てた案: 見取り図（あるいは状態が `live` の見取り図）で必須にする形。いまの見取り図のデータ（hub の見取り図・統括の復帰の全体像・ほかのリポジトリの見取り図。どれも状態は `live`）が、直さないと `check` で止まる。説明だけのページ（統括の復帰の全体像のような題材の読み物）にも状況を求めることになる。

### DJ-9 概要の構造（案は2つ）

- **案1（推奨）: 概要は本文のまま、見出しの名前と順を決める。** 「前の版からの変化（期間）」→「まとまりのつながり」（図・任意）→「次に進める候補」の3つを、この順で先頭に置く。題材に固有の節（hub の「cloud に回せる小さな直し」など）は、3つのあとに足してよい。決まりは `SKILL.md` と見本に書き、`check` は見ない。
  - 良い点: 図（mermaid）と箇条書きの説明が書ける。いまの hub の見取り図の概要は、ほぼこの形で、直す量が少ない。
  - 弱い所: 本文なので、見出しの名前と順は `check` で止まらない（#618 の棚卸しで、文だけで守らせる決まりはばらつきやすいと分かっている）。
- 案2（ゲート1 で直した）: 概要の骨格を型が持つ。新しい部品 `overview` が3つの節の枠（題と順）を描き、「前の版からの変化」は期間と箇条（データ）、「次に進める候補」は表（データ）で書く。図だけは、本文の中の名前の付いた断片（たとえば `<template data-hp-slot="links">`）を、`build.py` が「まとまりのつながり」の枠に差し込む。
  - 良い点: 節の欠けと順を `check` が止め、図も書ける。
  - 弱い所: 本文の新しい書き方（名前の付いた断片）と、その読み取り・差し込みが要る。本文の読み取りは直近に2回直しており（PR #662・PR #664）、壊れる場所が増える。部品がもう1つ増える。
  - 捨てた形: 概要を全部データで書く形（最初の案2）。図が書けず、案2 の改めた形に負ける。
- 見た目に関わるので、2つの案をサンプルのデータに当てて統括に渡す（「owner に聞くこと」節）。

### DJ-10 判断ボードには置かない

- `status` の部品は見取り図だけに置ける。見取り図でない種別に置くと、いまの種別の検査（E-K2）で止める（E-U2 は出さない）。判断ボードの「動いている作業」をそろえるのは #539 と一緒に決める（範囲外）。

### DJ-11 検査の規則

| 番号 | 何を弾くか |
|---|---|
| E-U1 | 状況の部品の中身の誤り（`rows` が配列でない・行の `state` が4つの key のどれでもない・状態に要る項目が無いか空・状態に無い項目か知らない項目がある・`who` にペインの番号・`done_days` が1以上の整数でない） |
| E-U2 | 見取り図の中での状況の部品の置き場の誤り（1ページに2つ以上・部品の先頭でない・タブのあるページで最初のタブでないか、同じタブにほかの部品がある） |

- 同じ原因で規則を重ねない。見取り図でない種別に置いたら E-K2 だけ、本文に状況のタブと同じパネルがあったらいまの E-N3（本文とデータの両方があるタブ）だけ、`refs` のリンクにできない識別子はいまの E-L1 だけを出す。部品そのものが配列でない・`rows` が無いなどの形の誤りは、いまの共通の規則（E-F2・E-F3）に任せ、E-U1 は中身の決まり（状態・項目・空・ペインの番号・`done_days`）だけを持つ（設計SO の指摘2と4）。テストで、壊したデータごとに規則と場所の1件だけが出ることを固定する。
- 誤りは、いまの規則と同じく1件1行で、規則の番号・場所・理由を出す。

### DJ-12 いまのデータと見た目に触る所

- `status` の部品を持たないページは、`build` の HTML がバイト単位で変わらないようにする。そのために次の2つを守る（設計SO の指摘1。いまは CSS の全文と用語集の辞書の全体を、どのページにも埋め込んでいる）。
  - 状況の CSS は、`page.css` に足さず、新しいファイル `status.css` に置き、`status` の部品のあるページにだけ埋め込む（タブの JS をタブのあるページにだけ入れるのと同じ形）。
  - 状況の語（`state.*` と状況の固定の文）は、`build.py` が描くときだけ使い、ページの JS に渡す埋め込みのデータ（`hp-data.labels`）には入れない。
- 確かめ方は、見本のすべて（`examples/*.json`）を変更の前と後で、版の時刻・tmux（`--tmux off`）・本文を固定して `build` し、HTML がバイト単位で同じであることを見る。
- `check` の結果も、`status` を持たないページでは、終了コード・規則・場所・理由が変わらないようにする。例外が1つだけある。知らない部品の type を止める E-S1 の理由の文は、受け付ける type の一覧を並べるので、`status` が増える。これは受け入れる。いまのテストの壊したデータの検査がすべて通ることで確かめる（設計SO の指摘6）。
- 並びの検査（E-N3）は、`status` の部品があるページでだけ、状況のタブを先頭として扱う。

### DJ-13 見本と文書

- 見本 `examples/map-status.json` と `examples/map-status-body.html`（状況のタブ・概要の本文・題材の表のタブ1つ）を足す。概要は DJ-9 で決まった形にする。
- `status.css`（新しいファイル・DJ-12）と、`build.py` が状況のあるページにだけ埋め込む処理。
- `SKILL.md`: 「種別と部品」の表の見取り図の行・「データの書き方」の項目の表・「状況の部品の書き方」の節（新設）・「タブで分ける」の並びの決まり・「検証の規則」の表・見本の一覧・「限界」（誰も持っていない作業を入れない決まりは `check` で見ない、完了の日付の範囲は見ない）。
- `glossary.md`: 状態の語・説明・列の見出し・「なし」の文・完了の題の形。
- `canonical/CATALOG.md`: html-one-pager の行に、状況のタブを足す。

### DJ-14 部品の形と、build.py の手を入れる所

- 部品の項目: `type`（`status`・必須）・`rows`（配列・必須・空の配列を許す）・`done_days`（任意）・`tab`（タブのあるページでは必須）。`title` は持たない（題は用語集の「状況」で、ページごとに変えない）。
- `build.py` の手を入れる所（設計SO の指摘3）:
  - `SECTION_TYPES` と、種別ごとの許可の表（見取り図だけ）。
  - 検証の分岐（いまは最後の分岐が `findings` を受けるので、`status` の分岐を明示して足す）と、描画の分岐（同じ）。
  - 描画で `sec["title"]` を参照している所（タブの名前と同じ題を隠す処理）は、`status` では用語集の題を使う。
  - `GLOSSARY_KEYS` に状態の語・説明・列の見出し・「なし」・「残す目安: {n}日」を足し、差し込みの名前を決める。
  - 描く順: 状況のパネルを閉じてから本文、そのあとに残りの部品を描く。テンプレートの `{{body}}` と `{{sections}}` の順を入れ替えるだけでは足りないので、状況の部品を描いた HTML を本文の前に置く形にする。

## owner に聞くこと
