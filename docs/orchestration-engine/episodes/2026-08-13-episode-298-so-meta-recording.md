# episode — #298 SO の meta に使われた上限と CLI 版を記録する

> **`reconstructed`** — この episode は作業中のリアルタイム追記ではなく、**PR #328 を出した後に後追いで書き起こしたもの**である。リアルタイムのログと同じ証拠価値を持たない。時系列は会話ログ・コミット列・`tmp/so-*/` の meta から再構成した。**heavy tier の episode を作らずに PR を出したこと自体が本単位の不履行**であり、親の差し戻しで気づいた。

## Context — なぜこの作業が始まったか

so-compare の SO レーンは、既定240秒では codex がレビュー級のプロンプトで返らないことが繰り返し観測されていた。「片方の AI が返事を返さない」と長く誤診されていた原因が待ち時間の設定不足だったという経緯があり（claude 側は #296 で修正済み）、codex / cursor 側も実測に合わせて引き上げ、あわせて「実際に使われた上限」を meta に記録する、というのが #298 の当初の依頼である。

**結果として既定値は引き上げなかった。** 引き上げの根拠に使うはずだった測定が、根拠に使えないと2度判定されたためである。

## 実測 — 自分で測り直した

brief には統括の帳簿と、別リポジトリの伝聞が載っていた。negative knowledge `01KYMRE1NC7XX6N66RQ0MGGHF1`（上流の断定を写すな）が注入されていたので、数値はすべて自分で測り直した。

`tmp/so-*/` と `projects/*/tmp/so-*/` と `.attempt1` を全件走査し、レーン単位266件を得た。

| レーン | n（成功） | p50 | p95 | 最大 | 240秒超 |
|---|---|---|---|---|---|
| codex | 90 | 200 | 450 | 560 | 33/90 |
| cursor | 72 | 156 | 254 | 404 | 5/72 |
| claude | 48 | 374 | 888 | 1094 | 38/48 |

**測定中にいちばん効いた発見は、`timeout_empty` のレコードの `elapsed_seconds` が、そのとき効いていた上限そのものだということである。** 成功レコードからは上限が読めないが、失敗レコードからは読める。ここから過去に実際に使われた上限（codex なら 240 が5回 / 241 / 480 が2回）を回収できた。**上限が実行ごとに揃っていないことが、伝聞ではなく自分の測定で確認できた。**

伝聞の検証も1件やった。「プロンプト長は主変数にならない」という別リポジトリの伝聞を自分の母集団で当て直したところ、codex の成功64件でスピアマン順位相関は 0.687 で、バケット別の平均所要も単調に増えていた。ただし最長の535秒は中間バケットから出ており、裾は説明できない。**正しい言い方は「中心の傾向とは相関するが裾を縛らない」で、伝聞の書き方は言い過ぎだった。**

## gate 2 — 自分の測定が自分の結論を否定した

設計SO（弱2レーン・codex + cursor）は**2レーンとも refuted** で返った。指摘を全件自分で検算したところ、どれも正しかった。

**いちばん重いのは、自分が §1.3 で「この分布は右側が切られている」と書いた直後に、§1.7 でその分布を「真に必要だった時間」として既定値の根拠に使っていたことである。** 警告を書いた本人が、次の節でその警告を無視していた。

打ち切りを含めた粗い区間を計算し直すと、codex が480秒以内に終わる割合は 89.7%〜95.9% で、**自分の表が出していた 97.8% は最良側の境界すら上回っていた**。

もう1つ、`01KZ3MHMET3GTRXTQXZSZCSWJJ`（空返しの meta は原因を運ばない）に自分で抵触していた。「リトライが1回目の上限より短時間で返った → 1回目は止まっていた（上限では直らない）」と結論していたが、負荷変動・キャッシュ・経路差でも同じ観測になる。**brief で採用した item を、同じ plan の中で踏んだことになる。**

このほか、リトライが逐次実行であること（複数レーンの最悪壁時計は初版の表より長い）、`stderr_bytes` が0でないことを合格条件にしたのが誤りであること（成功かつ0バイトのレーンが実在する）を直した。

**そしてこの gate 2 自体が反証データになった。** codex レーンが531秒かかっており、自分が提案していた既定480秒なら、**その案を評価するための SO が、その案の下では失敗していた**。

## gate 3 の裁定

値の確定を owner へ上げ、案ア（480/360）〜案エ（据え置き）を提示した。**owner は案エを採った。** 理由は「打ち切られた測定を規範に焼き込むことになる」で、gate 2 の531秒が実例として挙げられた。

裁定を受けて **DJ-1（`SO_CODEX_TIMEOUT` / `SO_CURSOR_TIMEOUT` の導入）も落とした**。分ける値が無いのに変数だけ先に置くのは scope の拡大にあたる。

## 上限は試行の開始前に書くことにした

meta は従来、外部コマンドの終了後に一度だけ書いていた。**gate 2 の指摘で、この形では scope の中核（実効上限を残すこと）を満たせないと分かった** — リトライの途中で止められると「meta は1回目・stdout と stderr は2回目」という食い違いが残る。**実際その形の出力ディレクトリが5件残っている**ことを自分の走査でも確認していた（`.attempt1` はあるのに `retry=1` の追記が無い）。初版の設計（完了時に1行足すだけ）はこの欠陥を回避できていなかった。

試行の開始前に `attempt` と `timeout_limit_seconds` を置き、完了時は一時ファイルへ書いてから `mv` で差し替える形にした。

**ただしこの実装も1回目は不完全だった。詳細は次節の gate 4 にある。**

## gate 4 — 同じ欠陥を形を変えて残していた

実装SO の1周目は **codex が refuted / cursor が survived**。codex の指摘を全件再現したところ、すべて正しかった。

**いちばん重い指摘はこれである。** gate 2 は「`model_resolved` 用の文字集合（`^[A-Za-z0-9._:+-]+$`）が空白も括弧も通さないので、`codex-cli 0.147.0` と `2.1.229 (Claude Code)` が常に `unavailable` に落ちる」という欠陥を見つけた。**自分はこれを「空白と括弧も許す」と許可リストを広げることで直した。** ところがそれでは `codex@0.147.0` や `v1.2.3, build 4` や `v1.2.3 [arm64]` が依然として落ちる。

**指摘された個別の値は通るようになったが、欠陥の型は同じ場所にそのまま残っていた。**

**許可する文字を数え上げるという方針そのものが誤りだった。** meta が守りたい不変条件は「1行1組の `key=value` が壊れないこと」だけである。そこから導かれるのは拒否集合（制御文字・DEL・`=`）であって、許可集合ではない。許可集合は「実在する版文字列の集合」を予言する作業になり、予言は外れる。denylist に切り替えた。

### write-ahead の実装も、守ろうとした不変条件を守れていなかった

**gate 4 が「重い3点」として並べた先頭は、実は allowlist ではなくこちらである。**

前節のとおり write-ahead 形にしたのだが、**開始側の書き込みだけ `>` で直接 truncate していた**。完了側は一時ファイル + `mv` にしたのに、開始側は素の上書きのままだった。`echo` と `echo` の間で落ちれば `attempt` や上限を欠いた部分 meta が残る。**「どの時点で中断されても試行番号と上限は残る」という、この変更が掲げた不変条件そのものが崩れる。**

自分の検証ハーネスはこれを通していなかった。中断テストは**完全な `running` meta が書かれたことを確認してから** kill しており、書き込みの途中で落ちる経路を作っていなかった。**塞ぎたい穴の手前で待ってから殴っていた。** 開始側も `commit_meta` を経由させ、`mv` を境にして「旧 meta」か「完全な `running` meta」しか観測されない形にした。

### そのほか gate 4 で直したもの

- **NUL は bash の変数化の時点で黙って捨てられる**（`ver\0bad` が `verbad` になる）。変数化した後では検査できないので、出力を一時ファイルで受けてバイト列のまま検査するようにした。「制御文字を落とす」と書いたコメントが実装と食い違っていた。
- **空白だけの版を成功扱いしていた**。`-z` は空白のみを空と見なさないため。取得失敗として扱うようにした。
- **`--version` の呼び出しに上限が無かった**。レーン本体のタイムアウトの外側に、無限に待ちうる経路を新しく作っていた（gate 2 の指摘）。`timeout 5` を掛けた。
- **`running` で終わった meta が結果サマリで無表示だった**。集計では失敗側に数えられるので安全側だが、状態が読めない。「未確定(試行が完了していない)」を出すようにした。
- **SKILL.md の `running` の定義が強すぎた**。「中断された」と書いていたが、実行中に読めば当然この値になる。「未確定。終了後も残っていれば中断」に直した。

検証ハーネスは36項目から65項目へ増やした。

## gate 4 の2周目と、塞がなかった2件

2周目は **2レーンとも survived**。

cursor が残指摘を2件挙げた。`commit_meta` が生産側の失敗時も受け取ったバイトを `mv` する点と、`cli_version_for` の内部失敗がスクリプト終了になりうる点である。どちらも「現行の呼び出し形では実害に届く経路を示せなかった」とされている。

**塞がなかった。** gate 4 を通した後にコードを変えると、レビューを受けた版と出荷する版が食い違うためである。理由は PR 本文と plan §10 に残した。

## 承認された scope を使い切らなかった

gate 3 で「文書3つへの追随」を承認してもらったが、**実際に直したのは `SKILL.md` だけである**。同じ gate 3 で既定値の据え置きも決まったため、`document-format.md`（タイムアウト機構）と `scripts/README.md`（環境変数）には変わる記述が無くなった。両者は meta のフィールドに一言も触れていない（`grep` で0件）。

**承認された範囲を使い切らないという判断であり、承認の趣旨には反していない。** 段階2で追随対象に戻る。
