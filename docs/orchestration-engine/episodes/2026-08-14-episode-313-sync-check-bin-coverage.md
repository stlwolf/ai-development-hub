# episode — #313 `sync --check bin` の網羅性と `usage()` の BSD 互換

> この episode は着手時に枠を作り、作業中に随時追記している。締めで後追い再構成した節があれば、その節の冒頭に明示する。

## Context — なぜこの作業が始まったか

`./scripts/sync.sh --check bin` は配布対象8件のうち2件しか検査していない。残り6件が `~/bin` に張られていなくても `up to date` と表示される。実際 PR #312 の前は `oe-hookfire` が `~/bin` に無かったが、検査は緑だった。

配備が効いていないことが検査から見えない、という観測層の欠陥である。発見は PR #312 の surface で、そのとき「検査が何を見るべきか」は設計変更なのでついでに直さないと判断され、別起票として本 issue になった。

あわせて `scripts/sync.sh:46` の `usage()` が GNU 依存で、macOS の BSD `head` では `./scripts/sync.sh --help` が exit 1 になる。同じファイルを開くので同じ PR に載せる（owner 裁定・2026-08-14）。コミットは論理変更ごとに分ける。

## 着手時の再確認 — 親の実測は3点とも成立した

brief には統括の実測が載っていたが、鵜呑みにせず master `1838119` で自分で測り直した。

- `./scripts/sync.sh --help` は **rc=1**、`head: illegal line count -- -1` を出力する。
- `./scripts/sync/sync-bin.sh --help` は **rc=0**（`sed '$d'` へ置換済み）。issue 本文の「`sync-bin.sh:39`」は現在の master では成立しない。
- `./scripts/sync.sh --check bin` は **rc=0 で `bin: up to date`**。`~/bin` の8件はいま全て repo 実体への symlink として存在する。したがって陽性対照なしでは検査の緑に意味がない。
- `scripts/sync/sync-bin.sh --list` は8件（`so-compare` / `arena-compare` / `wez` / `wt-pane-issue` / `oe-tree` / `oe-hookfire` / `validate-knowledge` / `knowledge-list`）を印字する。

食い違いは無かったので、そのまま plan へ進んだ。

## 着手前の裏取り — 6件の欠落は意図的な保留ではなかった

negative knowledge `01KZK26GQZ39WCFV5MYKQMRHWE`（curated な集合の「欠落」を、一次記録で裏取りせずに受け取るな）を適用し、実装より先に committed 層を引いた。**結論は「保留ではなく drift」である。** 根拠は3つある。

1. **git の履歴。** `scripts/sync.sh` の `bin)` 検査を書いたのは `348d675`（#70・2026-04-14）の1回きりで、以後この節に触れたコミットは無い。その時点の `CMD_NAMES` は `("so-compare" "arena-compare")` の2件だけで、**書かれた当時は全件検査だった**。その後 `CMD_NAMES` は6回伸びたが（`a620383` wez / `8f0746c` wt-pane-issue / `f394738` oe-tree / `f7c57c6` validate-knowledge / `7f18012` knowledge-list / `d89da79` oe-hookfire）、どの回も検査側に触れていない。検査を意図的に狭めた commit は存在しない。
2. **反対向きの原則が committed で書かれている。** `projects/orchestration-engine/docs/episodes/2026-07-14-episode-248-doc-flow-guardrail.md:67` が「新 sync ターゲットを足したら `sync.sh --check` にも対応検証を足す（sync と check は対）」を pattern として、「sync だけ足して check を忘れると drift/欠落を検出できない」を anti-pattern として記録している。保留どころか、検査は追随すべきものとして明示されている。
3. **本件の routing 自体が「欠陥として起票する」だった。** `projects/orchestration-engine/docs/episodes/2026-08-09-episode-309-sync-hookfire-distribution.md:100` と `projects/orchestration-engine/docs/plans/2026-08-09-plan-309-exit-contract.md:303` が、この2件を統括が別に起票すると宣言している。それが本 issue である。

**保留のリスクは別の場所にあった。** 同じ episode 309 の :103 が警告しているのは「まだ配っていない `oe-*` verb を意図せず配布対象へ足すこと」であり、これは `CMD_NAMES` の中身＝配布スコープの話である。本 issue のスコープは「`CMD_NAMES` に既に載っている8件を検査が見るか」であって、`CMD_NAMES` 自体は増減させない。NK item が名指しした危険は、**触らないと決めた側**に落ちている。

## 設計 — 母集団を1か所にする案を仮採用した

探索木は plan の §3.2 にある。初期案は2つ（検査側にベタ書き / `sync-bin.sh` をそのまま `source`）しか無く、どちらも母集団の側から回っていないか副作用を持つ。ゼロベースで前提を1つずつ外して案C〜案G まで広げ、**配列の定義だけを副作用の無いファイルへ切り出して配布側と検査側の両方が `source` する案F**を仮採用した。

決め手は失敗の形である。案C（`sync-bin.sh` に組を印字する verb を足して子プロセスとして呼ぶ）は、子プロセスが失敗すると出力が空になり、ループが0回で回って**緑になる**。案F は定義ファイルが読めなければ `set -e` 下の `source` が落ちる。**計測器の故障が緑に見えるかどうか**が分かれ目で、negative knowledge `01KYMRE1N7N0J8VP3CBZZEZ8Q3` が言う「0件を不在と読む」故障を、検証手順ではなく設計の側で塞げる。

昇格の印: 「curated な集合の検査は、母集団を取り損ねたときに赤くなる側へ倒す」は #313 固有ではなく、検査を設計するとき一般に効く。

## 実測で自分の主張を1つ撤回した

plan の初版に「`set -e` 下でループの最終反復が `[[ ]] && cmd` の偽で終わると、ループ全体の終了ステータスが非ゼロになる」と書いた。`&&` 連結ではなく `if` で書く根拠として置いた主張である。

**実測したら誤りだった。** bash の `errexit` は `&&` / `||` リストの最終要素以外で失敗したコマンドを免除するので、左辺の `[[ ]]` が偽でもループは止まらない。再現コードと結果は plan §3.6 にある。

`if` を選ぶ結論自体は変わらないが、理由は別（source が repo に無い場合を飛ばさず警告するので else 節が要る）に置き換えた。**根拠が嘘のまま SO と gate 3 へ出るところだった。** 未検証の主張を plan に書いたのが原因で、書いた時点で「これは測っていない」と自覚していたのに測らずに進めた。

あわせて、`source` に関する仮定4件も実装前に scratch 環境で測った（plan §3.7）。ここで**定義ファイル単体では `shellcheck` が SC2034 で落ちる**ことが分かり、1行目に指示子を置く必要があると判明した。受け入れ基準に `shellcheck` が入っているので、これは机上のままなら実装時に詰まっていた。

## gate 2 — 2レーンが独立に同じ根拠を崩し、そのSOも1件は誤っていた

弱SO・2レーン（codex `gpt-5.6-sol` 381秒 / claude `claude-opus-5` 786秒）。両方とも実返却があったので partial ではない。6問中5問で「欠陥あり」が返り、指摘13件を plan へ反映した。詳細は plan の §9 にある。

**中心の指摘は1つに収束した。** 案F の安全性の根拠に置いた「`source` が落ちれば `set -e` で止まる」が、`check_target` の実際の呼び出し経路（`scripts/sync.sh:248` の `if ! check_target`）では成り立たない、という指摘である。両レーンが独立に同じ file:line を引いてきた。

**そのうえで、SO の測定のほうが本環境と食い違った。** codex は「bash 3.2 で実測した。`if ! f` の中では `source /nonexistent` の失敗後もコマンドが継続した」と書いていたが、自分で測ると `/bin/bash` 3.2.57 では**シェルが即死する**（`source` は POSIX の特殊組込みで、ファイルを開けない場合は `set -e` と無関係にシェルを終了させる）。`env bash` 5.2.37 では死なない。claude レーンは同じ主張を `unverified-summary` と明示し、測るためのコマンドを添えてきていた。

結論（明示ガードを書く）は変わらなかったが、**理由が「`set -e` が効かないから」から「止まる機構が `set -e` ではなく、しかも bash の版に依存するから」へ変わった。** `scripts/sync.sh` は `#!/bin/bash`＝3.2、`scripts/sync/sync-bin.sh` は `#!/usr/bin/env bash`＝5.2 で、**同じ定義ファイルが2つの bash で source される**という事実も、この測り直しで初めて出てきた。

昇格の印: SO の指摘は正しく、SO が添えた実測は誤っている、という組み合わせが実際に起きた。指摘の採否と、指摘に付いてきた測定値の採否は別に判断する必要がある。

**根拠を外した箇所がもう1つ見つかった。** 撤回1（自分で見つけた）で差し替えた「既存コードが `&&` を使っているのは case 節の途中で最後の文ではないため」も誤りで、`scripts/sync.sh:181` は `bin)` 分岐の最後の文だった。**同じ結論（`if` で書く）に対して根拠を2回書き替えたことになる。** 結論は最初から正しかったのに、それを支える理由を2回とも検証せずに書いた。

**自分の探索木にも漏れがあった。** episode 309:107 が「`sync-bin.sh --list` で列挙を導出可能にする案」を先行SOの第3案として記録し、行き先まで書いていた。plan の §2 は同じ episode の :100 と :103 を引きながら :107 を木へ運んでいない。**同じファイルの3行を引いて、2行だけ使っていた。**

**案F が計上していなかったコストも出た。** 正本を `sync-bin.sh` から新ファイルへ移すと、`scripts/README.md:39` の「対応は同スクリプトの `CMD_NAMES` / `CMD_SOURCES`」と `CLAUDE.md:22` の「正本は `CMD_NAMES`」が偽になる。しかもこの pointer は #309 で先行SOの指摘を受けて置かれたものだった。**前の単位が SO の指摘で足した pointer を、次の単位が SO の指摘で気づくまで壊しかけていた。**

## gate 3 — owner が案F でなく案N を採り、承認した作業の1つが消えた

owner の裁定は5件すべて出た。GNU 依存は2か所とも直す。**受け渡しは案N を採用し、案F は不採用**（新規ファイルを増やさない）。文書2本の追随は scope に入れる。案M は別起票で親が起票を持つ。案I は out。

親は A-2 へ直行させず、**まず plan を案N へ改訂せよ**と指示した。案N の採用が案F 前提で書いた範囲（DJ-1・ガード・受け渡し・変更対象ファイル・Step 構成）を実質的に変えるためである。この指示は正しかった。書き直してみると、**変わった節が13・変わらなかった節が7**で、plan の半分近くが案F に依存していた。

### 先例の引き写しが、今度は自分の設計で逆向きに働いた

案N は「`sync-codex.sh:270` に先例がある」ことを根拠の1つにしている。その先例は子を素で呼び、rc を捕まえていない。子が非ゼロなら `set -euo pipefail` で親が中断する、という設計である。

**同じ書き方を移すと壊れる。** 先例の `main` はトップレベルで呼ばれるので errexit が効くが、移植先の `check_target` は `if ! check_target` から呼ばれるので errexit が抑止される。実測したところ、**子が rc=1（差分あり）を返しても親は `up to date` と出した。**

negative knowledge `01KZVHE0KQ5VCX0SXH0F4SM14D`（先例の規律を移すときは前提も移るか確かめよ）が、**この単位で2回目の発火**である。1回目は plan §3.4 の `sed '$d'` で、そのときは前提が移ることを確かめて採用した。2回目のここでは前提が移らず、採用できなかった。

昇格の印: 同じ item が1つの単位で2回発火し、片方は「前提が移るので採用」、もう片方は「移らないので不採用」になった。item の価値は「引き写すな」ではなく「引き写す前に確かめよ」で、確かめた結果は両方向に出る。

### 壊れた子の rc は数値で意味を分けられなかった

親が rc をどう解釈するかを決めるため、子を壊して rc を測った。**同じ壊し方（実行可能ビットを落とす）でも、`bash -c` から呼ぶと 126、スクリプトファイルの中から呼ぶと 1 になった。** つまり「1 なら差分あり、それ以外は環境エラー」という契約は書けない。

対処は rc を細分するのをやめ、(a) 親は呼ぶ前に `[[ -x ]]` で弾く（`run_target` に同じ形の先例がある）、(b) 母集団の健全性は子の中で見る、の2つに分けた。**案F ではガードを親に置くしかなかったが、案N では母集団を持っているのが子なのでガードも子へ移る。**

### owner が承認した作業の前提が、別の裁定によって消えた

裁定3 は「`scripts/README.md:39` と `CLAUDE.md:22` の正本 pointer を張り替える」を承認したものだった。**ところが裁定2（案N 採用）によって正本が動かなくなり、張り替える対象そのものが無くなった。** 両方とも真のままである（一次確認した）。

代わりに別の追記（委譲関係の記述）が候補になるが、**承認されたのは張り替えであって追記ではない。** 勝手に読み替えず、選択肢3つを添えて owner へ戻した。

昇格の印: 同時に出された複数の裁定が、片方の採用によってもう片方の前提を壊すことがある。裁定を順に実行するだけだと、対象の消えた作業を「承認済み」として実行してしまう。

## A-2 実装 — 検証の probe を2回間違えた

owner が gate 3 を完了させ、文書追随は選択肢A（委譲関係を1行足す・正本の記述は書き換えない）に決まった。置き場は `scripts/README.md` を選んだ。同ファイルの `:41` が `sync-codex.sh` → `check-codex-guardrails.sh` の委譲関係をちょうど1文で書いており、粒度が一致するためである。`CLAUDE.md` はコマンドの早見表で粒度が粗い。

実装そのものは plan のとおりに進み、詰まる箇所は無かった。**手こずったのは検証の側である。**

### 受け入れ基準2の陽性対照を、最初は測れない形で書いていた

「9件目を足しても検査側を触らず追随する」を確かめるため、`sync-bin.sh` の複製を一時ディレクトリに置いて9件目を足す形で書いた。**2か所間違えた。**

1. 9件目の source を配列の**先頭**に挿入してしまい、名前と source の対応が1つずつずれた。
2. 複製を worktree の外へ置いたので、複製が自分の位置から解決する `REPO_ROOT` が一時ディレクトリになり、**8件すべての source パスが壊れた。**

結果は「rc=1（赤）」で、一見すると期待どおりに見える。**赤の理由が違った。** 出力を読むと `Source missing` が8件並んでおり、9件目の未配置ではなく複製の置き場所が原因だと分かった。

**これは陽性対照の裏返しの失敗である。** negative knowledge `01KYMRE1N7N0J8VP3CBZZEZ8Q3` は「緑を見たら計測器の故障を疑え」だが、ここで起きたのは**赤を見て検査が効いていると読みかけた**ことである。期待した色が出たときこそ、その色の理由を確かめる必要がある。

昇格の印: 陽性対照は「期待した色が出たか」ではなく「期待した理由でその色が出たか」まで見ないと成立しない。色だけの一致は偽陽性を通す。

直した形は、複製をやめて**実ファイルへ末尾追加し、測り終えたら戻す**ものである。あわせて `sync.sh` の md5 が前後で変わっていないことを assert に足した。「検査側を触っていない」を主張の形でなく観測の形にするためである。

### 検証は31 assert にまとめて全件 pass

実 `~/bin` には触れず `HOME` を差し替えて回した。(a) baseline から (l) 親子の rc 一致まで、plan の §5 Step 4 に書いた項目をすべて機械的な assert にした。目視で読む行は残していない。

コミットは3本に分け、**コミット1 が単独で成立することを stash で確かめた**。その時点では子の `--check` が欠落を検出する一方、`sync.sh --check bin` はまだ緑を返す。振る舞いの変化がコミット2 に載っていることが、この2つの観測で確定する。

## gate 4 — 文書がコミット1つ分だけ未来を語っていた

弱SO・2レーン（codex 189秒 / claude 511秒）。**両レーンが独立に、まったく同じ1件を突いた。**

## 追記（closure 後）— 蒸留木の置き場を owner 裁定で移した

**この節は closure より後に来た追加指示の記録である。** 上の closure は #313 の中核（`--check bin` の網羅性と `usage()` の BSD 互換）について書かれたもので、その判定は変わっていない。

### なぜ動かしたか

closure で収穫した knowledge item 3件を、私は `docs/knowledge/items/` へ置いた。「収穫元 episode と同じ蒸留木の `knowledge/items/`」という規則に素直に従い、自分の episode が `docs/episodes/` にあるので `docs/` を木のルートと読んだ結果である。

**owner の裁定は、そこは木のルートではない、というものだった。** `docs/knowledge/` は negative knowledge の仕組みができる前からある別種の知見ノートの置き場で、そこに store を生やすと性質の違う2つが同居する。さらに `docs/` 直下には `research/` や `issues/` や `draft/` も並んでおり、**`docs/` は蒸留木ではなく一般の文書置き場だった。**

昇格の印: 「収穫元と同じ木」という関係で置き場を解く規則は、**木のルートがどこかを取り違えると静かに外れる**。層のディレクトリが直下に並んでいることは、そこが木のルートである証拠にならない。
