### 判断の why — 陽性対照の probe に `--help` を使いかけて外した

最初に組んだ probe は `codex exec --help <不正バイト>` だった。**rc=0 が返った。** ここで「codex は不正 UTF-8 を受け付ける」と読むところだった。原因は `--help` が引数列の途中で短絡し、UTF-8 検証まで到達しないことである。不正な引数を positional の先頭に置き `--help` を後ろへ回したら `rc=2` と当該 stderr が出た。

**NK `01M00KCCHNMFPHP5HAGX2DZ1MK` の裏返しの形で踏みかけた。** item が警告しているのは「期待した色が出たが理由が別」だが、ここで起きたのは「期待した色が出ず、しかも出ない理由が足場（`--help` の短絡）の側」だった。色が出ないほうも同じ疑いを向ける必要がある。

さらに `rc=2` 自体は理由の証拠にならないことも測って確かめた。存在しないフラグを混ぜると、引数が妥当な UTF-8 でも不正な UTF-8 でも同じ `rc=2` が返る。**判定は rc ではなく stderr の文字列で行う。**

### 棄却した選択肢 — `cut -c` と `awk substr` は実測で落ちた

issue の候補 (a) が挙げる `cut -c` を実測した。**`cut` は行単位である。** 5行の fixture に `cut -c 1-5` を当てると各行の先頭5文字が返り、文書全体を N 文字に切る意味にならない。BSD awk の `substr` はさらに悪く、**バイト単位で切って不正 UTF-8 をそのまま作った**（`substr($0,1,5)` が `e381 82e3 81` を返した）。どちらも「切り詰めの idiom」として一見もっともらしいが、前提が違う。

これは NK `01KZVHE0KQ5VCX0SXH0F4SM14D` が言う「規律は写るが前提は写らない」の実例で、item の指示どおり**この環境の `cut` / `head` / `iconv` が何をするかを実測した**ことで着手前に落とせた。

### 実測で見つかった罠 — 候補 (b) の `iconv -c` は rc=1 を返す

`iconv -f UTF-8 -t UTF-8 -c` は出力としては正しく壊れたバイトを落とす（4000 → 3999 バイト）が、**この環境では終了コード 1 を返し stderr に `unexpected end of file; the last character is incomplete.` を書く。** 末尾の不完全な文字を「不正な文字」ではなく「EOF エラー」として扱うためである。

`so-compare.sh:5` は `set -euo pipefail` である。したがって `prev_content=$(head -c N "$f" | iconv -f UTF-8 -t UTF-8 -c)` と素直に書くと、**修正のつもりでスクリプト全体を落とす。** 候補 (b) を採るなら rc の握り潰しが必須で、「実装は最小」という issue の評価はこの環境では成り立たない。

昇格の印: 「配布物の切り詰めは文字境界で行う」は so-compare 固有ではなく、AI へ argv で渡す全経路に効く規範かもしれない。

### 撤回した判断 — 「(b) は `set -e` で落ちるから駄目」は一度言い過ぎた

上の節を書いた直後、対話シェル上の subshell で同じ形を試したら **`set -euo pipefail` を宣言しているのに落ちなかった**（`SUBSHELL reached len=1333`）。同じ文字列を `bash -c` に渡すと落ちる。食い違いをそのままにせず切り分けた。

原因は実行の形の違いである。`$( )` の中の subshell は `inherit_errexit` が無いと errexit を継がず、対話シェル配下の subshell ではさらに扱いが変わる。**so-compare.sh は先頭に `set -euo pipefail` を置いた素のスクリプトなので、そちらの形で測り直した。** 独立したスクリプトファイルとして走らせると `step2` に到達せず rc=1 で死ぬ。`bash -c` でも同じである。

したがって結論は変わらないが、**根拠は「対話シェルでの観測」ではなく「スクリプトとして走らせた観測」に置き換えた。** 最初の測り方のままなら逆の結論（落ちない）を書いていた。

### 先例が repo 内に2つあった — 前提はどちらも完全には移らない

候補を自分で考える前に repo を走査したら、同じ問題を既に解いている箇所が2つ見つかった。

**先例1 — `projects/orchestration-engine/scripts/knowledge-list.sh:180-184`。** bash の `${line:0:max}` で切っている。コメントに「UTF-8 ロケール前提で文字境界で切る（多バイト文字を割らない → jq の UTF-8 破損を避ける）」と理由まで書いてあり、`LC_ALL=C` では成立しないことも既知の限界として明記されている。実測すると書いてあるとおりだった（UTF-8 ロケールで 1333 文字 = 3999 バイト・妥当／`LC_ALL=C` では 1333 バイトで切れて不正）。**移らない前提は予算の単位である。** 先例は文字数の予算だが、`--prev` の `PREV_MAX_BYTES` はバイトの予算で、外部から環境変数で変えられる公開インタフェースになっている。

**先例2 — `canonical/hooks/scripts/session-name.sh:106`。** `head -c 80 | { iconv -f UTF-8 -t UTF-8 -c 2>/dev/null || cat; }` である。**候補 (b) そのもので、しかも上で見つけた rc=1 の罠を `|| cat` で既に回避している。** 実測でも 3999 バイト・妥当・rc=0 で通った。

だが `|| cat` の意味を読むと前提が移っていない。この fallback は「iconv が使えなければ無害化せず素通しする」という意味である。先例の消費者は pane のタイトルで、**化けた文字が出ても表示が崩れるだけ**だから素通しでよい。本件の消費者は codex の argv で、**素通しはレーン1本の即死に戻る。** 同じ idiom を写すと、無害化が静かに外れる経路を一緒に持ち込むことになる。

NK `01KZVHE0KQ5VCX0SXH0F4SM14D` が言う「規律は写るが前提は写らない」がそのまま2件出た。どちらも棄却ではなく、**前提の差分を埋めれば使える**という位置づけで gate 2 に載せる。

### 先例2 を verbatim で写すと欠陥がそのまま戻ることを実測した

上で「`|| cat` の fallback は前提が移っていない」と書いたのは読解だったので、測って確かめた。stdin を読まずに `exit 1` する iconv の stub を PATH の先頭に置いて、2つの書き方を比べた。

| 書き方 | iconv 正常時 | **iconv が読まずに失敗したとき** |
|---|---|---|
| `\| iconv … 2>/dev/null) \|\| true` | 妥当・3999 バイト | **空**（前回出力が黙って落ちる） |
| `\| { iconv … 2>/dev/null \|\| cat; }`（先例2） | 妥当・3999 バイト | **不正・4000 バイト（欠陥が戻る）** |

**先例2 をそのまま写すと、iconv が早期に失敗した場合に生バイトが素通しされ、いま直そうとしている当の故障が黙って復活する。** stub を外した対照では両方 3999 バイトで妥当なので、赤の理由は stub が効いていることであって足場の破壊ではない（NK `01M00KCC…` の教訓1）。

NK `01KZVHE0` の予測文（「先例では安全だった手順が新しい場所では故障を隠す」）がそのままの形で出た。**どちらも採らない。** 前提の差分を埋めた形（iconv の可用性を preflight で確かめ、無害化に失敗したら黙って進まない）を gate 2 に載せる。

### 文字予算に切り替えると入力が最大3倍に膨らむ

候補 (a) を bash の `${var:0:N}` で実装すると、予算の単位がバイトから文字に変わる。実測すると `PREV_MAX_BYTES=4000` のつもりが日本語で **6000 バイト**、実物のプロンプトで **7958 バイト**になった。`so-compare.sh` はプロンプト肥大を 50KB で警告する設計なので、この膨張は無視できない。**先例1（`knowledge-list.sh`）から移らない前提は「予算の単位」だった**、というのが数字で出た。

### 候補 (d) は本件を直さない — 実測で前提が崩れた

brief は「(d) を採ると本件と ARG_MAX の両方が根で消える可能性がある」と書き、issue も「(d) は他の defect も同時に消えうる」と書いていた。**費用と効果を gate 2 で測れという指示だったので、効果のほうを先に測った。**

`codex exec` は stdin からの入力に対応している（`--help` に「instructions are read from stdin」とある）。そこへ不正なバイトを含む短い指示を流した。

```
Failed to read prompt from stdin: input is not valid UTF-8 (invalid byte at offset 23).
Convert it to UTF-8 and retry (e.g., `iconv -f <ENC> -t UTF-8 prompt.txt`).
```

**rc=1 で落ちた。** codex は経路に関係なく UTF-8 を検証する。argv か stdin かは関係がない。

したがって **(d) は本件を直さない。** 消えるのは ARG_MAX の族だけである。しかも失敗の署名が変わる（argv 経路は `exit 2` + `invalid UTF-8 was detected in one or more arguments`、stdin 経路は `exit 1` + `input is not valid UTF-8`）ので、(d) を単独で採ると**現行の検出条件が外れたまま欠陥が残る**という悪い方向にも働く。

付け足すと、**codex 自身のエラーメッセージが `iconv` を推奨している。** 直し方の方向として外部からの裏づけになる。

昇格の印: 「渡し方を変えれば検証も緩む」という期待は、CLI が入力面すべてで検証する場合に成り立たない。委譲 brief に載る設計候補の前提として一般化できるかもしれない。

### iconv 案はロケールに依存しない — 指摘された穴5 が最初から立たない

### この環境の iconv の罠 — `/dev/null` に出すと妥当な入力でも rc=1

|---|---|---|
| `/dev/null` | **rc=1** | rc=1 |

NK `01KZVHE0KQ5VCX0SXH0F4SM14D` そのものである。**先例（この場合は他レーンの提案）の手順は写せるが、この環境の `iconv` が何をするかは写らない。** validator として使うなら出力先に注意が要る、という前提が抜けていた。(c) は実装可能だが、この罠を踏むと「常に fallback」という静かな故障になる。

### 差し戻された `/dev/null` の件 — 再現し、条件を特定した

gate 3 は「`iconv` を validator に使うと `/dev/null` では妥当な入力でも rc=1 になる」という自分の記述を差し戻した。**親の環境では同じ `/usr/bin/iconv` で4通りすべて rc=0 だった**という。

自分の環境では**再現した**。そこで条件を切り分けた。**内容と出力先の両方が効いていた。**

| 変えた軸 | 結果 |
|---|---|
| `あ`×1333（3999 B・妥当）→ `/dev/null` | **rc=1** `iconv(): Inappropriate ioctl for device` |
| ASCII 3999 B → `/dev/null` | rc=0 |
| ASCII 12288 B → `/dev/null` | rc=0 |
| `あ`×2（6 B）→ `/dev/null` | rc=0 |
| `あ`×1333 → **実ファイル** | rc=0 |
| `あ`×1333 → **パイプ**（`\| cat`） | rc=0 |
| `あ`×1333 → `/dev/zero` | **rc=1** |

二分探索で境界も出た。**`あ`×341（1023 B）は rc=0、`あ`×342（1026 B）は rc=1。**

まとめると発火条件は3つの積である。

1. stdout が**キャラクタデバイス**（`/dev/null` / `/dev/zero`。実ファイルやパイプでは起きない）
2. 入力に**マルチバイト文字が含まれる**（ASCII だけならサイズを問わず起きない）
3. そのマルチバイト内容が **1024 バイトを超える**

**親が再現しなかったのは、条件2または3を満たさない入力で測ったためだと考えられる**（短い入力や ASCII なら発火しない）。機序は「1KB のバッファを超えて2回目の write に入るとき出力 fd へ ioctl 相当を行い、キャラクタデバイスで ENOTTY になる」あたりだと推測するが、**機序は未確認**である。上の表と境界が検証済みの範囲である。

**自分の記述の食い違いも親の指摘どおりだった。** §4 では「環境の事実」として断定し、§9 では「壊れた計測器2件」の1つとして挙げていた。**両方とも正しいのだが、書き方が矛盾していた** — 事実としては iconv がそう振る舞い、その振る舞いのせいで自分の (c) prototype が全 fixture で fallback へ落ちた（`/dev/null` を使っていた）。**同じ1つの事実の裏表**なので、そう書き直した。

### P0 の足場で2回つまずいた（どちらも自分の scaffold 側）

**つまずき1 — `command -v` がシェルの alias を拾った。** `iconv` を見えなくするための最小 PATH を組むとき `command -v` で実体を引いたら、`cat -> "alias cat='bat'"` や `ls -> "alias ls='eza'"` という**壊れた symlink** ができた。`type -P` に替えて直した。

### 陰性対照が自分の sentinel で壊れていた

C3（陰性対照）は「上限を3の倍数にすれば文字の途中で切れないので、修正前でも妥当なはず」という設計だった。**修正前に走らせたら不正が出た。**

原因は自分が付けた sentinel である。fixture の先頭に `SENTINEL-F1CODEX `（17バイト）を置いたので、`head -c 3999` の切れ目は「`あ` の並びの 3982 バイト目」になり、3982 % 3 = 1 で文字の途中に落ちる。**「3の倍数なら安全」は sentinel を足す前の fixture にしか当てはまらない前提だった。**

手計算をやめ、各 fixture について「その N で切ると妥当か」を全部机上で列挙してから対照の N を選び直した。

| fixture | 切ると不正になる N | 切っても妥当な N |
|---|---|---|
| F1（`あ`） | 4000 / 3985 / 3987 / 3990 … | **3998** / 3986 / 3989 / 3992 … |
| F2（`𠮷`） | 3999 / 3990 / 3991 / 3992 … | 3989 / 3993 / 3997 / 4001 … |
| F3（混在） | **3993** / 3994 / 3996 / 3997 … | 4000 / 3986 / 3987 … |

**F3 も直した** — 既定の 4000 では偶然きれいな境界に当たっていて、陽性対照になっていなかった。**「fixture を作ったら陽性になっている」と思い込まないこと**が NK `01M00KCC…` の教訓そのもので、今回は3度目の適用である。
