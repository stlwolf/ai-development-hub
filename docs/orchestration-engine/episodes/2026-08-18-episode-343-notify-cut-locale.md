## 着手時の実測 — 親の実測4件はすべて再現した

計測器を先に検証した（既知の妥当 138 B → valid・既知の不正 80 B → INVALID）。そのうえで測った。

| 条件 | 結果 |
|---|---|
| `LC_ALL=C` を `cut` に | **不正・81 B**（78 バイト目が不正の先頭） |
| `LC_ALL=POSIX` を `cut` に | **不正・81 B** |
| `LC_ALL=ja_JP.UTF-8` | 妥当・138 B |
| `LC_ALL=C.UTF-8` | 妥当・138 B |
| `LC_ALL=en_US.UTF-8` | 妥当・138 B |
| 環境継承（このシェルは `LANG=ja_JP.UTF-8`） | 妥当・138 B |
| **`LC_ALL=C` を `printf` にだけ掛ける（親が踏んだ罠）** | **妥当・138 B＝再現しない** |
| `cut -b1-80`（ロケール問わず） | 不正・81 B |

**親の実測と食い違いは無い。** 罠のほうも再現した — 環境変数はパイプラインの最初のコマンドにしか掛からないので、`LC_ALL=C printf ... | cut` では `cut` のロケールが変わらない。`printf ... | LC_ALL=C cut` と書く必要がある。

`POSIX` も `C` と同じであること、`cut -b` はロケールに依らずバイトで切ることを追加で確かめた。**つまり `cut -c` は UTF-8 ロケールでは文字単位、`C` / `POSIX` では実質 `-b` に退化する。**

## 到達可能性を先に測った — 今日は発火していない

直す前に「この欠陥は実際に起きるのか」を確かめた。2つの軸がある。

**内容の軸: マルチバイトが入るのは既定である。** `msg` の元は `message` で、`:38` / `:47` を読むと `last-assistant-message`（Codex）または `.message` / `.last_assistant_message`（Claude）から取っている。**つまりアシスタント自身の発話で、この環境では日本語である。** 短い英語だけ、という想定は成り立たない。

**ロケールの軸: 今日は UTF-8 が渡っている。** フックを起動するプロセスの環境を覗くと `LANG=ja_JP.UTF-8` が入っている。`notify.sh` 自身はロケールを設定していない（`grep` で確認・設定行なし）。

**したがって現状は「潜在」であって「発火中」ではない。** #340 は実際にレーンが死んだ記録があったが、本件にそれは無い。直す価値は (1) `notify.sh` がロケールを自分で決めていないこと (2) 配布先が3ツールに広がっていること、に置かれる。**「今日壊れている」とは書かない。**

## 親の brief の前提が1つ崩れた — notify.sh も symlink で配られる

brief は「`notify.sh` は sync 経由で各ツールへ配られる。**#340 の symlink とは配布の仕組みが違う**ので反映のタイミングを確かめよ」と書いていた。確かめたら**仕組みは同じだった。**

`scripts/sync/sync-claude.sh:106` の `sync_hook_scripts()` は `:131` で `ln -sf "${file}" "${target_path}"` を実行する。**copy ではなく symlink である。** 実際の配布先も3ツールすべて symlink だった。

| 配布先 | 実体 |
|---|---|
| `~/.claude/hooks/notify.sh` | symlink → 主 checkout の `canonical/hooks/scripts/notify.sh` |
| `~/.cursor/hooks/notify.sh` | 同じ実体への symlink |

**反映は #340 と同じで、主 checkout の作業ツリーが更新された瞬間に効く。sync の再実行は要らない。** しかも指す先が1ファイルなので、**3ツールが同時に切り替わる**（#340 は1コマンドだった）。影響範囲は brief の想定より広い。

## #340 の前提が2つ移らない

**移らない1 — 依存が無いときに止めてはいけない。** `notify.sh:18` に「advisory 契約: 非ゼロ exit を出さない / stdout 無出力 / 末尾は無条件 exit 0」と明記され、`:26` は `command -v jq >/dev/null 2>&1 || exit 0` で**依存が無ければ黙って no-op** する。導入 commit（`fe1d61f`）も「advisory: set -e なし・非macOS/jq不在は no-op・常に exit 0」と書いている。

**#340 は `iconv` 不在を hard error にしたが、それをここへ写すと契約違反になる。** 通知が出ないだけの advisory な機能のために、フックが非ゼロで落ちてエージェント側に影響を出すのは筋が悪い。brief の懸念どおりである。

**移らない2 — `set -e` が無い。** `notify.sh:24` は `set -uo pipefail` で、`-e` が付いていない。#340 は `set -euo pipefail` だったので「rc を握り潰さないとスクリプトが死ぬ」という制約があったが、**ここにはその制約が無い。** `pipefail` は `$?` に出るだけで中断しない。

NK `01KZVHE0KQ5VCX0SXH0F4SM14D` の型がまた出た。**#340 で自分が書いたコードが今回の「先例」であり、その前提（消費者が CLI の argv・`set -e` あり・止めてよい）は3つとも移らない。**

## 80 の上限は OSC 777 の制約ではなく見た目の都合だった

brief の「そもそも80文字の上限が要るのか」を調べた。導入 commit `fe1d61f` の本文に「入力待ちは message を**80字** truncate」、README `:184` にも「入力待ちは ` — {message を80字 truncate}` を追加」とある。**意図は文字数**で、理由は通知本文の見た目である。

OSC 777 側の制約は README `:187` に「サウンド指定不可」だけが挙がっており、**長さの制約は書かれていない。** したがって上限そのものは残す（見た目の都合として妥当）が、**単位は文字であるべき**というのが元の意図である。`cut -c` を選んだこと自体は意図に合っていて、**壊れているのは「`C` ロケールで `-c` がバイトに退化する」ところだけである。**

## 候補を実測で横並びにした — #340 の形は本件では悪化させる

**最初に測った fixture（46文字）が短すぎて、切り詰めが一度も起きていなかった。** 「案 A は妥当」と読みかけたが、妥当だったのは切っていないからで、比べたかった挙動を一度も踏んでいない。NK `01M00KCCHNMFPHP5HAGX2DZ1MK` の「期待した理由でその色が出たか」がそのまま出た。100文字（300 B）の fixture に替えて測り直した。

上限 80、入力 100文字（300 B）。**期待は「80文字 = 240 B」である**（元の意図が文字数だったことは上で確認済み）。

| 案 | 結果 | 文字数 |
|---|---|---|
| master `cut -c1-80`（`LC_ALL=C`） | **不正・81 B** | — |
| master `cut -c1-80`（`LC_ALL=ja_JP.UTF-8`） | 妥当・241 B | 80 |
| A: `cut` に `C.UTF-8` を強制 | 妥当・241 B | **80（意図どおり）** |
| B: bash `${v:0:80}`（`LC_ALL=C`） | **不正・80 B** | — |
| B2: bash `${v:0:80}`（`C.UTF-8`） | 妥当・240 B | 80 |
| **C: `cut -c` の後に `iconv -c`（#340 の形）** | 妥当・79 B | **26** |

**C は #340 で採った形だが、本件では上限の意味を壊す。** バイトで切ってから不正バイトを落とすので、日本語の通知本文が **80文字のつもりで26文字**になる。妥当な UTF-8 にはなるが、**見えている成果物（通知の文面）が3分の1に縮む。** 受け入れ条件の「既存の通知経路が回帰していない」に正面から反する。

**「#340 と揃えるか」の答えは「揃えない」である。** 揃えるべきは実装の形ではなく、前提の確認の仕方だった。

## 案 A の致命的な穴 — 存在しないロケールは黙ってバイトに戻る

案 A（`cut` に UTF-8 ロケールを強制する）を採るつもりで、その失敗経路を列挙した。**列挙してよかった。**

```
LC_ALL=zz_ZZ.UTF-8 cut -c1-80  →  不正・81 B、stderr は空
```

**存在しないロケール名を渡すと、警告も出さずにバイト単位へ戻る。** つまり「`LC_ALL=C.UTF-8` を書いた」ことは「文字単位で切れている」ことを意味しない。`C.UTF-8` はこの macOS には在る（`locale -a` に UTF-8 ロケールが84件・`C.UTF-8` / `en_US.UTF-8` / `ja_JP.UTF-8` はいずれも在る）が、musl や古い BSD では在るとは限らない。

**案 A を採るなら「強制したロケールが実際に効いたか」を実測する probe が要る。** 3バイト文字1つを `cut -c1` に通して出力が何バイトになるかで判定できる。

| probe | `cut -c1` の出力 | 判定 |
|---|---|---|
| `LC_ALL=C` / `POSIX` / `zz_ZZ.UTF-8` | 2 B（`あ` の1バイト + 改行） | バイト単位 |
| `LC_ALL=C.UTF-8` / `ja_JP.UTF-8` | 4 B（`あ` 3バイト + 改行） | 文字単位 |

これは NK `01M07QDKEBVRB8K01TAHW513ND`（自分が #340 で収穫し、同じ単位で踏んだ item）の trigger そのものだった。**「ロケールを設定すれば直る」で止めず、設定が効かない変種を1つ挙げたら出てきた。**

昇格の印: 「環境変数で挙動を切り替える修正は、切り替わったことを実測するまで完了していない」は、#340 で収穫した2件とは別の型かもしれない。

## 案 E — jq でコードポイント単位に切る（ロケール依存が構造的に消える）

ロケールを制御する方向とは別に、**ロケールを見ない道具で切る**方向を探した。`notify.sh` は `jq` を**既存の hard 依存**として持っている（`:26` で不在なら `exit 0`・`message` 自体も `jq -r` で取り出している）。`jq` の文字列スライスは Unicode のコードポイント単位で、ロケールを参照しない。

```bash
printf '%s' "$message" | tr -d '\033\007' | tr '\n\r' '  ' | jq -Rr '.[0:80]'
```

**5環境すべてで同一の結果**（妥当・241 B・80文字）になった。

| 環境 | 結果 |
|---|---|
| `LC_ALL=C` | 妥当・241 B・80文字 |
| `LC_ALL=POSIX` | 妥当・241 B・80文字 |
| `LC_ALL=ja_JP.UTF-8` | 妥当・241 B・80文字 |
| `LC_ALL=C.UTF-8` | 妥当・241 B・80文字 |
| `env -i`（環境剥ぎ取り） | 妥当・241 B・80文字 |

**新しい依存は増えない。ロケール probe も fallback 連鎖も要らない。** 案 A が必要とした「効いたかを確かめる」工程が、構造的に不要になる。

### 案 E の失敗経路も列挙して当てた

| 入力 | 結果 |
|---|---|
| 空文字列 | 空（`msg=""` の経路が保たれる） |
| ASCII / 80字未満 | そのまま通る |
| 引用符・バックスラッシュ・`$var`・バックティック | そのまま通る（`-r` で生出力・エスケープが漏れない） |
| 絵文字・4バイト文字・結合文字 | そのまま通る |
| タブ・連続空白 | そのまま通る |
| 先頭が `-`（オプション誤認の懸念） | そのまま通る |

**順序に1つ制約がある。** `jq -R` は行単位で読むので、**改行を潰す `tr` より後に置かなければならない。** 先に置くと3行に割れることを実測で確かめた（`a\nb\nc` → 3行）。現行の `cut` の位置がまさにそこなので、置き換えは drop-in になる。

## 訂正 — 「tr はロケールに無関係」は言い過ぎだった

上で「`tr` の2段は両ロケールで同じ結果なので原因は `cut` に限られる」と書いたが、**それは入力が妥当な UTF-8 のときだけである。** 不正バイトを含む入力で測り直した。

| ロケール | `tr -d` の挙動 |
|---|---|
| `LC_ALL=C` | `\377` をそのまま通す（stderr 無し） |
| `LC_ALL=ja_JP.UTF-8` / `C.UTF-8` | **`tr: Illegal byte sequence`** を出し、不正バイト以降を落とす |

したがって不正入力に対しては `tr` もロケール依存である。**`message` は `jq -r` の出力なので原則として妥当な UTF-8 であり、この経路は本件のスコープ外**だが、「原因は `cut` だけ」と断定するのは誤りだったので訂正する。

なお皮肉な副作用として、**`LC_ALL=C` では master のパイプライン全体が不正バイトを素通しし、UTF-8 ロケールでは `tr` が落として妥当になる**（不正入力時）。ロケールの効き方が2箇所で逆向きに出る。

## gate 1 — 自分の見立てが2箇所で崩れた

codex 312秒 / 14,439 B、claude 512秒 / 15,790 B。**2レーンとも実返却あり。** 新カテゴリの案が12件出た（codex Z1-Z7・claude F/L/H/P/J）。

**崩れた1 — 到達可能性の見立てが誤りだった。** 自分は「`msg` の元はアシスタント自身の発話なので日本語が既定＝内容の軸では起きる」と書いた。**2レーンが独立に否定した。** コードを読み直すと、`msg` は `mode=wait` でしか計算されず（`:86`）、**Codex 経路は `:39` で `mode="done"` に固定される**ので `last-assistant-message` は構造上 `cut` に到達しない。到達するのは Claude の `Notification`（matcher `permission_prompt|idle_prompt`）→ `notify.sh wait` の1本だけで、そこに流れるのは **Claude Code 自身が生成する入力待ちの通知文**である。

発火には (1) 非 UTF-8 ロケール (2) `wait` 経路 (3) 通知文がマルチバイト の**積**が要る。**潜在性はむしろ強まった。** それでも直す理由は「ロケールを自分で決めていない」と「配布先が3ツール」の2点に絞った。

**崩れた2 — 「3バイト文字だけ再現する」を確かめたら半分だった。** claude レーンが「上限80は 1・2・4 で割り切れるが 3 では割り切れないので3バイト文字だけ」と指摘した。測ると、**純粋な `é`×100（2バイト）と `🎉`×100（4バイト）は修正前でも妥当**で、指摘どおりだった。**ただし先頭に `a` を1つ足すとどちらも不正になる。** 条件は「幅」ではなく「切断位置が文字の内側に落ちるか」で、**オフセット次第で全幅が再現する。**

これは対照の設計に直接効く。**2バイト文字を素朴に fixture に選ぶと、修正前でも緑になって「対照が成立していない」ことに気づけない。** §5.3 に「あえて緑になる対照（C5）」を1本置いた。

## gate 1 が見つけた自分の測定の誤り — また隣を測っていた

**codex レーンの指摘。** 自分が報告した「81 B / 241 B」は **`cut` の出力**であって `msg` に入る値ではない。`msg="$(...)"` のコマンド置換が末尾改行を落とすので、**実際の `msg` は 80 B / 240 B** である。

**#340 で踏んだ型と同じである。** あのときは argv の代わりに `prompt.txt` を測った。**今回は `msg` の代わりに `cut` の出力を測った。** 数値の結論は変わらないが、**測る対象を間違えていた**のは2回目である。

さらに両レーンが「パイプラインの断片ではなくスクリプト全体を実際の経路で走らせろ」と指摘した。初版の §5 はまさに断片を測る設計だったので作り直した（fake `tmux` で `pane_tty` を一時ファイルへ向け、Notification 形式の stdin JSON を渡し、worktree の絶対パスを直叩きし、sentinel が載っていることを先に確認する）。

昇格の印: 「隣の成果物を測って本体を測ったつもりになる」は2単位連続で踏んだので、独立した型として立つかもしれない（#340 では argv vs prompt.txt・#343 では msg vs cut の出力）。

## 採用案を決めた — (E) jq でコードポイント単位に切る

**#340 と実装を揃えない。** `iconv -c` の形はここでは上限の意味をバイトに変え、日本語の通知が **80文字→26文字**に縮む。揃えるべきは実装ではなく前提の確認の仕方だった。

採ったのは `cut -c1-80` → `jq -Rr '.[0:80]'` の1行置換である。決め手は4つで、いずれも実測に基づく。ロケール依存が構造的に消える（5環境で同一）・上限の意味（80文字）が保たれる・`jq` は既存の hard 依存なので advisory 契約に触らない・ロケール probe が要らない。

**(H)（`:47` の既存 `jq` に畳み込んで `tr|tr|cut` を消す）は技術的には上である。** 実測で E と同じ結果になり、プロセスが3つ減り、順序の制約も消える。採らなかったのは `:47` が `done` 経路も通る共有行だからで、**owner の判断に残した**（plan §6.2）。

## 案 E の想定外入力を先に当てた

gate 2 で「`-R` は行単位で読むので想定外に複数行になる入力があるのでは」と突かれる見込みがあったので、先に測った。**fixture が意図した文字を実際に含むことを検証してから測った**（前回この検証を省いて結果を読めなくした）。

| 入力 | `jq -Rr` の出力行数 |
|---|---|
| VT (U+000B) / FF (U+000C) / NEL (U+0085) | いずれも 1 |
| LS (U+2028) / PS (U+2029) | いずれも 1 |
| NUL (U+0000) | 1 |
| LF / CR（対照・`tr` が潰す） | いずれも 1 |

**改行系のどの文字でも複数行に割れなかった。** あわせて次も確かめた。

- `jq-1.8.0` で `.[0:1]` を4バイト文字に当てると4バイト全部が出る＝**コードポイント単位**である。
- 空文字列は現行と同じく空を返す（`msg=""` の経路が保たれる）。
- **`jq` が失敗しても advisory 契約は壊れない。** 不正な filter を渡すと rc=3 だが、`set -uo pipefail` の下で次の行に到達し、変数は空になる。

## gate 4 — 実装は崩せず、検証器の欠陥が3件出た

### jq の下限版が確定した — そして1文字で互換範囲が1版広がった

gate 2 で2レーンが 1.4 / 1.5 と食い違った件に、claude レーンが**ソースを引いて決着をつけた。両方が半分正しく、別のものを見ていた。**

- **文字列スライスは jq 1.4 から動く。** `jq-1.4` の `jv_aux.c:78-85` が文字列添字を `jv_string_slice()` へ振り分け、`jv.c:725-779` が `jvp_utf8_next()` で歩く（コードポイント単位）。codex の主張が正しい。
- **1.5 が要るのは `-Rr` という連結の書き方のほう。** `jq-1.4` の `main.c:40-45` は `strlen(text) == 2` で短オプションを判定するので、**3文字の `-Rr` は `-R` にも `-r` にも一致しない。** 連結が入るのは 1.5 の `main.c:83-99`。

**つまり自分のコメント「文字列スライスは jq 1.5 以降が要る」は、結論は合っていたが根拠が誤りだった。** そして根拠が誤っていたせいで、**`-R -r` と分けて書けば下限が 1.4 まで下がることに気づけなかった。** 1文字の空白で互換範囲が1版広がる。`-R -r` に変え、コメントも直した（この環境の jq-1.8.0 で両者の出力が同一であることは確認済み。古い jq は手元に無いので版判定はレーンが引いたソースに依存する）。

### 検証器が「常に緑」だった（両レーンが指摘）

**`assert.py` は JSON を印字するだけで、期待を満たさなくても exit 0 を返していた。** さらに `matches_expected` は `msg` 部が取れないケースでは**キーごと出力されない**ので、C14（fallback argv）を含む5件が**無条件に緑**だった。**gate 2 が「最も重い追加」と位置づけた対照が、機械判定の外に落ちていた。**

自分は JSON を目視して表を作っていたので**結論は正しかったが、保存した検証器が結論を支えていなかった。** 再実行しても一番大事な差分の回帰を検出できない状態だった。

直した内容は3つ。`assert.py` に oracle 種別（`osc-match` / `argv-match` / `osc-invalid` / `argv-invalid` / `no-msg`）を渡して**満たさなければ exit 1** にする。fallback の argv も oracle の対象にする。`set -uo pipefail` の `verify.sh` を作り、**1件でも落ちれば非ゼロで終わる**ようにした。

### 足場をさらに2回壊した（合計5回）

**つまずき4 — `has-fix` 検出器が自分の変更で壊れた。** 検出器は `grep -c "jq -Rr"` で書いてあった。**`-Rr` を `-R -r` に変えた瞬間に false を返すようになり、`after` の全ケースが `has_fix=0` と記録された。** 版指紋を足したのは「ラベルは版を保証しない」を直すためだったのに、**その指紋自体が変えうる表層の形に依存していた。** 安定なマーカー（コメント中の `#343`）を見る形に直した。
