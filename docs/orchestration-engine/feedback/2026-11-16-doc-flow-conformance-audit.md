# 蒸留の文書のフローが定義どおりに動いているかの調査（issue #652）

- 調べた日: 2026-11-15〜16
- この文書は、フローそのものの振り返りである。蒸留5層（discussion / kickoff / plan / episode / decision）の外に置く調査の記録で、決定は含まない。
- 比べる元: `docs/research/2026-06-10-episode-quality-audit.md`（52件の全数採点）
- 対象: hub の episode 138件（2026-06-11 以降）と、同じフローを使っているほかのリポジトリの episode 49件（同じ期間）。ほかのリポジトリについては、集計と型だけを書き、名前・番号・引用は書かない。

## 1. 要旨

1. **6月の弱点（放置と status の未確定）は、ほぼ消えた。** 閉じていない episode は187件中10件である。過去向きの4つの軸（WHY 復元・判断復元・証拠接続・蒸留度）は、どれも6月より高い。
2. **closure の点は、follow-up の行き先を「統括へ渡す」で済ませたものを数えるかどうかで変わる。** 数えなければ6月とほぼ同じ（hub 1.26、ほかのリポジトリ 1.04、6月は 1.12）、数えれば大きく改善（1.77、1.67）である。渡された先を抜き取りで追うと、84件のうち30件は痕跡が見つからなかった。
3. **owner のレビューは closure のあとに起き、結果は closure の本体に入らず継ぎ足されている。** 定義（closure → owner のレビューと merge）のとおりに動いた結果である。owner のレビューは、設計の縮小・昇格の判定の覆し・closure の欠けの発見といった中身のある結果を出している。
4. **Copilot の置き場所に定義の無理がある。** 定義は Copilot を「実装 → PR」のゲートに入れているが、Copilot は PR が無いとレビューできない。実際には PR のあとに走る。
5. **ゲート3（plan の承認）の記録は、ほとんど作業層にある。** 46本のうち、承認が issue のコメントに残っていたのは6本である。
6. **外からの指示は、ほぼすべての流れに記録がある。** 集まるのは、closure を書かせる・足させるところと、Copilot を依頼させる・返信させるところである。

## 2. 方法

### 2.1 採点

- 基準は6月の監査の「評価軸」の表（軸1〜5、各0〜2点）をそのまま使った。6月の採点の書面は残っていないので、軸5（closure）の判定の目安はこの調査で書き起こした。
- 軸5は2通りに付けた。**厳しい読み**は、follow-up の行き先を issue・文書・「追わない」の宣言だけに限る。**ゆるい読み**は、統括や owner への引き渡しも行き先に数える。
- 187件を17組に分け、subagent に採点させた。各点数に逐語の引用と行番号を必須にした。
- 検証は3つ行った。
  - **引用の機械照合**: 引用935か所のうち927か所が、実ファイルにそのまま在る [verified]（引用の先頭60字を、空白を無視して全文と照合）。
  - **独立採点**: 親が subagent の結果を見る前に9件を採点した。軸ごとの一致は 8・9・9・8・7 件（9件中）。軸5の食い違い2件は、どちらも subagent のほうが1点低い。
  - **較正**: 6月の監査で点数が分かっている10件を、今回の書面で採点させた。軸ごとの一致は 8・8・10・8・6 件。軸5は、6月に2点だった4件のうち3件が1点になった。今回の採点は6月より厳しめに出る。

### 2.2 ゲートごとの照らし合わせ

- 月で層に分けて、episode を46件抜き取った（hub 30、ほかのリポジトリ 16・乱数の種は固定）。1件を「issue から merge までの1本の流れ」として扱った。
- subagent が、episode・plan・issue のコメント・PR の commit とレビューの時刻を読み、ゲート0〜6 のそれぞれに「定義どおり・食い違い・理由を書いて省いた・当時は定義に無い・記録から判定できない」を付けた。
- 親が2本を GitHub の記録で確かめた [verified]。hub の1本は PR にレビューが1件も無いこと、ほかのリポジトリの1本は closure の commit の約4時間半あとに Copilot のレビューが付き、closure のあとに commit が2つ続くことで、どちらも subagent の記録と一致した。

### 4.1 定義と実際の食い違い

- **closure と Copilot の順番が、リポジトリで逆になっている。** closure と Copilot の両方の時刻が取れた流れで見ると、hub は26本のうち21本で closure が最後の Copilot のあと、ほかのリポジトリは13本のうち8本で closure が最初の Copilot より前だった。`document-format.md` の「ライフサイクル規範」節は closure を「PR レビュー後・マージ前」としているが、「ゲート配置」節の表は Copilot をゲート4（実装 → PR）に置いており、2つの節が同じ順番を指していない。
- **closure のあとに commit が足された流れは、hub で30本中14本、ほかのリポジトリで16本中11本ある。** 足された分は、closure を書き直さず、節を継ぎ足す形で記録されている。
- **Copilot が走っていない流れが、どちらにも3本ずつある。** 理由が書かれていないものを含む。Copilot は自動では走らず、依頼が要る。
- **ゲート3（plan の承認）の記録の置き場**: 46本のうち、issue のコメントが6本、作業層のファイルだけが23本、episode の中の言及だけが12本、見つからないものが3本だった（残り2本はその他）。この内訳は、subagent が書いた置き場の説明を語で分けたもので、目安である。
- **小さな直しでは、ゲート0〜3を brief の中で省いている。** owner の方針として brief に書かれているが、brief は作業層にあり、issue には残らない。
- **統括が owner の代わりにゲート3を通した流れがある。** owner の委任（推奨で進めてよい）のもとで行われている。定義は owner の承認としている。
- **ゲート6（merge 後の後始末）のうち、worktree の掃除と、作業層に残った昇格の拾い上げは、どの流れでも記録から判定できなかった。** 残る記録が無い。
- **1つの episode で複数の PR を進める流れ**では、途中の PR が、その PR を覆う closure の無いまま merge されている。

### 4.2 owner の考えとの関係

issue #652 の食い違い（owner の考えは「人のレビュー → closure → merge」、定義は「closure → owner のレビューと merge」）は、記録の上でも次の形で出ている。いずれも親が実ファイルで読んだ [verified]。ほかのリポジトリの分は引用を公開できないので、型だけを書く。hub の分も、同じ形にそろえて型だけを書く。

- closure のあとの PR のレビューで owner が設計の大幅な縮小を決め、結果が「追記」として足された（ほかのリポジトリ）。
- closure が「Decision への昇格は無し」と判定したあと、owner が覆して decision に昇格し、「後追いの訂正」として書かれた（hub）。
- owner が PR を見て「episode に closure が無い」と気づき、統括が closure を指示した。brief の終わりの定義に closure が入っていなかった（ほかのリポジトリ）。
- closure の外部チェックを辞退したあとに事実の誤りが残り、利用者の指摘で訂正した、と episode 自身が書いている（hub）。

### 4.3 「統括へ渡す」とされた follow-up の行方

抜き取った84件のうち、issue になったものが20件、文書に残ったものが27件、痕跡が見つからなかったものが30件、その他が7件だった [unverified-summary]。

## 5. 外から指示している場所

- 指示が記録に残っていた流れは、hub で30本中25本（36件・owner 16、統括 19、不明 1）、ほかのリポジトリで16本中16本（43件・owner 21、統括 22）だった。
- hub ではゲート5（closure を書かせる・足させる）に、ほかのリポジトリではゲート4（Copilot を依頼させる・未読のスレッドに返信させる）に集まる。
- 型は次の5つである。
  - closure を書いていない、または足りないことを、owner か統括が見つけて書かせる。
  - Copilot のレビューを依頼させる、返信させる。
  - 子が「完了」と報告したあと、統括が未達のゲートを見つけて差し戻す。
  - 昇格（decision など）を、merge のあとではなくその PR に入れさせる。
  - SO の周回を増やすか止めるかを、統括か owner が決める。
- owner と統括の会話、判断ボード、引き継ぎ文書は作業層にあり、この調査では読めていない。件数は下限である。

## 6. 食い違いが減ってきた理由

記録からは切り分けられない。分かるのは時期だけである。後追いで書いた episode は8月から減り、10月以降は0件になった。軸5のゆるい読みは7月に1.87まで上がり、9月に一度下がって、10月に1.97になった。スキルの変更日とモデルの切り替えの時期を並べる作業は、まだしていない。

## 7. 決めることのための材料（決定はしない）

- **closure をどこに置くか。** いまの記録では、closure のあとにレビューの結果が継ぎ足されている。owner の考えの順（レビュー → closure → merge）にすると、継ぎ足しは closure の本体に入る。一方で、レビューを待つあいだ closure が書かれないので、6月の監査が示した「先送りは埋まらない」の危険が戻る。
- **Copilot をどのゲートに置くか。** PR が要るので、「実装 → PR」のゲートには置けない。
- **「統括へ渡す」を行き先と認めるか。** 認めるなら、渡された側が issue か文書にしたことを追える記録が要る。
- **承認の記録をどこに残すか。** いまは作業層にあり、あとから確かめられない。
- **小さな直しでゲートを省くことを、定義に書くか。** いまは brief の中だけにある。

## 8. 限界

- 6月の採点の書面が無く、軸5の目安はこの調査で書き起こした。較正では今回のほうが厳しめに出た（10件だけの比較）。
- 独立採点は9件で、短い episode に偏っている。長い episode での一致は確かめていない。
- ゲートごとの照らし合わせは46本の抜き取りで、判定は subagent による。親が GitHub の記録で確かめたのは2本である。
- 作業層（`.oe/`・`tmp/`・判断ボード）は読めていない。承認と外からの指示は、episode が書き残した範囲でしか数えていない。
- GitHub の上では、エージェントの書き込みも owner のアカウントで出る。人のレビューかどうかは、文面と episode の記述から判断している。
- ほかのリポジトリについては、引用を載せていない。その部分の主張は、この文書だけでは確かめられない。
