# 蒸留の文書のフローと周りの決まりの棚卸し（issue #618 フェーズ1）

- 調べた日: 2026-11-16〜18
- この文書は調査の記録で、決定は含まない。蒸留5層（discussion / kickoff / plan / episode / decision）の外に置く。
- 先行の調査（[蒸留の文書のフローが定義どおりに動いているかの調査](2026-11-16-doc-flow-conformance-audit.md)・#652）は、文書に何が書かれたかを見た。この棚卸しは、決まりを**何で守らせているか**（機械・文・統括の手・owner の手）と、git に入っていない作業層の記録を見る。
- 対象: hub の正本の決まりと、hub の作業層。同じフローを使っているほかのリポジトリ1つの作業層も読んだ。ほかのリポジトリについては、集計と型だけを書き、名前・番号・引用・パスは書かない。

## 1. 要旨

1. **ゲート0〜6 のどれにも、機械で止める仕組みは無い。** 機械で止めているのは、破壊的な操作・コミットメッセージの形・送信の宛先・elevated の子の起動・統括の交代と復帰だけである。hub には CI も有効な git hook も無い。設計SO と実装SO の verb は判定を返すが、advisory で、先へ進むのを止めない。
2. **決まりは114行あり、そのうち50行は文だけで守らせている。** 統括の手が入る行は27、owner の手が入る行は20ある。定義の表に名前はあるのに、誰がいつどうするかの文がどこにも無い行が5つある（Copilot の依頼・owner のマージ・issue を閉じる判断・worktree の掃除・作業層に残った昇格の拾い上げ）。
3. **#652 が「記録から判定できない」とした3つは、作業層を読んで埋まった。** plan の承認は hub の42本のうち owner が37本で、統括が owner の委任のもとで代わりに通したものが4本ある。統括から子への closure・昇格・SO の周回の指示は 7〜9月に集まり、10月以降はほぼ0件になった。「統括へ渡す」とされた follow-up は、作業層まで追うと痕跡なしが42%から22%に下がった（ほかのリポジトリは31%）。
4. **3つに分けると、もう要らない候補が14行、文に頼っているが機械にできる見込みのものが24行、人の手でしか回っていないものが28行だった**（重なりを除いて53行・いまのまま56行）。
5. **後追いの episode が減った理由は切り分けられない。** 減った2つの時期は、どちらも決まりの変更とモデルの切り替えが同じ月に重なる。10月には、統括が brief の固定節をテンプレどおりに貼るようになったことも重なる。理由は分からないが、いまは起きない。
6. **定義の中と、定義と owner の考えのあいだに、食い違いが7つ残る**（7節）。

## 2. 方法

### 2.1 行の作り方（ステップ1）

- 行の出どころは、hub の正本の4つである: `canonical/orchestration-spec/document-format.md`（「遷移規則」「ゲート配置」「ライフサイクル規範」「昇格義務」節）、`canonical/rules/`、`canonical/skills/`（`doc-flow-guardrail`・`issue-intake`・`episode-retrospective`・`implementer-contract`・`unmet-gate-check`・`judgment-board-flow`・`delegate-task`・`predecision-exploration`・`branch-finish` ほか）と `canonical/commands/review/copilot-review-response.md`、`canonical/hooks/` と `projects/orchestration-engine/bin/`。
- 4つの subagent が、決まりを「1つの行動を求める決まり」1つにつき1件で抜き出した（合わせて191件と、機械の仕組み30件）。各件に逐語の引用とファイルの行を必須にした。
- 親が、フローの上で1つの行動として観測できるものを1行にまとめ直した。スキルの中の手順の細部は「〜の内部の手順」として1行にした。文体と用語の決まり、ゲートに結び付かない一般の規範は、それぞれ1行にまとめた。同じ決まりが2〜4か所で定義されているものは1行にし、定義の場所を全部並べた。
- 結果は114行になった。行の切り方は統括と owner が見て、そのまま進めることになった。

### 2.2 列の埋め方（ステップ2）

- 列は5つある: 決まりの中身と定義の場所 / 何で守らせているか / 実際に守られているか / その決まりが補っていた弱点はいまも起きるか / 意図した形か。
- 「守られているか」は、作業層の記録から埋めた。hub では、承認の記録42本、委譲の書面（brief）125本、統括から子への送信524件、owner が子のペインに直接打った入力222件、統括の引き継ぎ文書の「確立した運用」の節、判断ボードの台帳を読んだ。ほかのリポジトリでは、作業層の約400ファイル、作業層の外に置かれた指示の文書61本、判断ボードの台帳、episode 49本を読んだ。
- 「弱点はいまも起きるか」は、決まりを入れた commit（`git log -S`）から補っていた弱点を探し、そのあとに同じ弱点が起きた記録を episode・knowledge item・memory・#652 の数字から探した。判定は3つ: **起きる**（10〜11月の記録に出ている）・**起きていない**（決まりを入れたあとの直近の記録に出ていない。理由は切り分けていない）・**材料なし**（探した範囲に記録が無い。起きていない証拠ではない）。
- 統括の指示で、統括の交代と復帰の5行は表に残したが、列を埋めていない（#609 と重なり、機械で止める仕組みがあるため）。
- 送信の記録には宛先のリポジトリが無い。hub の送信は、受け取った側の入力の記録と時刻・先頭の文字で照合し、入力の作業場所で分けた（送信5,683件のうち hub 1,116・hub 以外4,514・不明53）。

### 2.3 確かめ

- subagent の判定には、逐語の引用とファイルの行を必須にした。
- 親が実ファイルか GitHub で照らしたのは32件で、32件とも一致した（ステップ1 で20件: 引用6・スキルの記述7・hook と verb の終了コード7。ステップ2 で12件: 承認の記録2・引き継ぎ文書の運用1・PR を通さない commit 2・モデルの切り替えの commit 3・ほかのリポジトリの主張3・follow-up の行方1）。

## 7. 定義の食い違い（決めることの材料・決定はしない）

1. **closure と Copilot の位置。** 「ゲート配置」節は Copilot をゲート4（実装 → PR）に置き、「ライフサイクル規範」節は closure を「PR レビュー後・マージ前」とする。Copilot は PR が無いとレビューできない。#652 の本文に書かれた owner の考えは「人のレビュー → closure → merge」で、いまの定義（closure → owner のレビューと merge）と逆である。
2. **小さな直しでゲートを省くこと。** 定義の例外は「軽微修正」だけで、`so.design` に「省いた」を表す値が無い。hub の brief では、plan を省くものが14本・設計SO を省くものが21本・認識合わせを省くものが11本あり、どれも owner の指示を理由に書いている。11月の小さな直しの5本は、固定節の plan-first を貼ったまま、plan なしと書いた本文と食い違っている。ほかのリポジトリでは「小さな直し」を理由に省く書き方は0本だった。
3. **統括が owner の代わりにゲート3 を通すこと。** 定義は owner の承認だが、owner の委任のもとで統括が代わりに通したものが hub で4件、ほかのリポジトリで1件ある。#661 の本文は、承認のときに owner が plan のどこまでを読んだかが記録に残らないこと、細部の確認が問いのカードに書かれた範囲でしかできていないことを挙げている。
4. **「統括へ渡す」を follow-up の行き先と認めるか（G5-05）と、作業層に残った昇格を拾う主体（P-06）。** どちらも未決である。P-06 は `document-format.md` 自身が「実行主体の置き場は未決」と書く。統括へ渡したものは、hub で2割強、ほかのリポジトリで3割が痕跡なしである。
5. **branch-finish の Option 1。** エージェントが `wt merge` を打つ前提で書かれており、owner がマージする（G5-08）と子はマージしない（G6-03）と食い違う。`wt merge` はマージと掃除を1回でするので、掃除の前に昇格を拾う時点も無い。
6. **master への直接の commit。** `workflow-awareness-rule` は issue の無い作業をデフォルトブランチに置いてよいとし、`branch-naming` は master への直接 push を禁じる。master には PR を通さない commit が 11-10 と 11-16 にある（owner の指示があったかは確かめていない）。
7. **一括の答えのときに保存先を読むか（Q-06）。** 統括の引き継ぎ文書の運用（owner が全部承認と言ったら保存先を読まなくてよい）と、#466 の decision（毎回保存された答えを読む）が食い違う、と子の報告が書いている。

## 8. 限界

- 行の切り方は親の判断である。スキルの中の手順の細部をまとめたので、まとめた行の中の一部だけが守られていない、という形は見えない。
- 「守られているか」の多く（72行で弱点の判定が材料なし）は、作業層まで読んでも記録が無い。材料なしは、起きていない証拠ではない。
- 再発は語で検索して探したので、言い換えて書かれた失敗は拾えていない。G5-01（随時追記）は `reconstructed` の宣言の数だけで見ており、実際に追記したかは測っていない。
- 送信の記録の本文は先頭の約60〜80文字しか残っていない。型の判定は語の当てはめで、#652 の5つの型は全件を読んだが、それ以外の型は抜き取りで読んだだけである。
- owner が統括に会話で出した指示は、会話の記録が9月より前の分は残っていないので読めていない。Codex の子への送信は照合できず、不明に入った。
- ほかのリポジトリについては、作業ごとのサブディレクトリの報告と実行の記録、1行の送信の記録、アプリ側の PR、外部のタスク管理を読んでいない。痕跡なしの件がそこで片づいている可能性は残る。この部分の主張は、この文書だけでは確かめられない。
- 月は、作業層のファイルの更新日時か、記録の時刻で分けた。あとから追記されたファイルは後ろの月に入る。
- 「機械にできる見込み」は、記録に残る物があるかを見ただけで、作れるかは確かめていない。
