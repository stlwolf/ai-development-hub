陽性対照は「**期待した色が出たか**」ではなく「**期待した理由でその色が出たか**」まで見ないと成立しない。色だけの一致は偽陽性を通す。

「0件・緑を不在と読むな」の裏返しである。緑を疑う規律は広く知られているが、**赤についても同じことが起きる**。しかも赤は「検査が効いた証拠」として歓迎される色なので、疑う動機が働かない。

#313 で実際に踏んだ。「配布対象を1件増やしたとき、検査側を触らなくても追随するか」を確かめるため、配布スクリプトの複製を一時ディレクトリに置いて9件目を足す形の対照を組んだ。**足場を2か所間違えていた。** 9件目の source を配列の先頭に挿してしまい名前と source の対応が1つずれ、さらに複製を作業ツリーの外へ置いたので、複製が自分の位置から解決するリポジトリルートが一時ディレクトリになり、8件すべての source パスが壊れた。

結果の rc は 1、つまり**期待どおりの赤**だった。「9件目が未配置なので赤い」と読むところだった。出力を読むと `Source missing` が8件並んでおり、赤の理由は9件目ではなく足場の破壊だと分かった。**確かめたかった経路（9件目の追随）は一度も踏まれていない。**

非自明なのは、**この失敗が「対照を通した」という強い証跡を残すこと**である。検証ログには「1件足すと赤くなることを確認」と書ける。後から読む人には正しく見える。緑の見逃しは「何も起きなかった」痕跡しか残さないが、偽の赤は積極的な証拠の形をとる。

次にどう行動を変えるか。(1) **対照で期待した色が出たら、出力に現れた理由が仕込んだ変更と対応しているかを1行確認する**（件数・名前・メッセージの種類のどれかで照合する）。rc だけを見て次へ進まない。(2) **対照の足場は、測りたい対象と同じ場所・同じ解決規則の下に置く**。複製を別の場所へ置くと、足場自身が持つパス解決や環境依存が新しい変数として入る。実物を一時的に変更して測り終えたら戻すほうが、変数が1つ減る。(3) 「触っていないこと」を主張に使うなら、**触っていないことも観測にする**（対象ファイルの hash を前後で比較する等）。主張と観測は別物である。
