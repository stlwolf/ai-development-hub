コミット単位の自己完結を確かめるとき、**コードの動作だけを見て文書の記述を見ないと、文書だけが1コミット先を語る状態が通る。** 「そのコミットの時点でコードが動くか」と「そのコミットの時点で同梱した記述が真か」は別の述語である。

#313 で起きた。「各コミットは単独でも動く状態にする」を自分で計画に書き、コミット1 を stash して単独検証まで実施した。検証は正しく通った ── 新しく足した verb は動き、呼び出し側はまだ旧来の振る舞いのままで、変化が次のコミットに載っていることを2つの観測で確定させた。

**それでも欠陥が残った。** 同じコミット1 に、`sync.sh --check bin` は `sync-bin.sh --check` へ委譲する、という文書の1行を同梱していた。委譲が入るのは次のコミットである。**コミット1 の時点でこの記述は偽だった。** 実装SO の2レーンが独立にこれを指摘した。

非自明なのは、**動作検証が原理的にこれを見つけられない**ことである。文書は実行されないので、どれだけ丁寧に checkout して動かしても差は出ない。しかも自分のコミットメッセージには「このコミットでは呼び出し側を触らないので振る舞いは変わらない」と正しく書いてあった。**メッセージと文書が同じコミットの中で食い違っていた**が、どちらも自分が書いたので違和感が出なかった。

分割の順序自体は正しかった点も押さえておく。提供側（verb）を先、消費側（委譲）を後に置くのは正しい。**壊れたのは順序ではなく、文書をどちらのコミットへ乗せるかの判断である。**

次にどう行動を変えるか。(1) **同梱した文書の各文に「このコミットの時点で真か」を当てる。** 未来形・断定形で他コミットの成果を語っている文を探す。(2) **機能を説明する文書は、その機能の消費側が入るコミットに乗せる。** 提供側のコミットには提供したもの（verb が増えたこと）だけを書く。(3) 分割の検証は動作だけでなく、`git show <sha>:<doc>` と `git show <sha>:<code>` を突き合わせる形にする。**片方だけを見ている限りこのクラスは出ない。**
