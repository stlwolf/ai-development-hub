**自分が列挙した失敗経路と、自分が書いた処方を1対1で突き合わせる。** 診断と処方を別の節に書くと、照合されないまま両方揃った形になる。

#340 で踏んだ。先例の `iconv` 呼び出しを検討する過程で、**自分で「iconv が在るのに失敗する」ケースを stub で作って赤を観測し、その経路を文書に書いた。** そのうえで処方として `command -v iconv` の preflight を置き、「これで握り潰しに隠れる失敗は残らない」と書いた。

**`command -v` が見るのは不在だけである。** 自分が見つけた「在って失敗する」経路には一切効かない。設計SO の2レーンが独立にここを最重要の指摘として返してきた。実測すると、その経路では前回出力が空になる一方で切り詰めの注記だけが付き、**中身が0バイトなのに「6000 バイトを 4000 バイトに切り詰めた」と書いたプロンプトが全レーンへ配られる**（rc は 0・警告なし）。直そうとした欠陥より静かな故障を作りかけていた。

非自明なのは、**この失敗が「診断も対策も書いてある」という完全な見た目を残すこと**である。文書には失敗経路の実測表があり、対策の節があり、両方が具体的である。**足りないのは両者の間の線だけ**で、線が無いことは節を順に読んでいるあいだは見えない。列挙が詳しいほど、処方が覆っている気配が強まるので気づきにくい。

次にどう行動を変えるか。(1) **処方を書き終えたら、自分が列挙した失敗経路の表に戻り、1行ずつ「この処方はこれを覆うか」を書く。** 覆わないものは覆わないと書く（対策を増やすか、範囲外と明示するかはそのあとの判断）。(2) 処方の効果を主張するときは**一般的な性質ではなく列挙した経路の名前で言う**（「握り潰しに隠れる失敗は残らない」ではなく「不在は覆う、在って失敗するは覆わない」）。(3) 自分で作った赤は**対策後にもう一度赤い入力として流す** — 見つけたときの再現手順が残っているので、対照として最も安い。
