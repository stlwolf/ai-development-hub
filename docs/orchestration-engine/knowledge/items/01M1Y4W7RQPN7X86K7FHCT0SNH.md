**打ち切られる側の出力を、集めてから渡すプロセス越しに受け取ってはいけない。** 打ち切りは「渡す」より前に来るので、観測は必ずゼロになる。

so-compare の claude レーンは `claude-safe` というラッパー経由だった。ラッパーは `nohup claude ... > 一時ファイル` で走らせ、`wait` が返った**後**に `cat` で自分の標準出力へ流し、`trap cleanup EXIT` で一時ファイルを消す。so-compare は `timeout` でこのラッパーを打ち切る。打ち切られるのは `wait` の最中なので、**`cat` の行に到達しない。** claude が上限の文言を出していようが途中まで答えていようが、記録は 0 バイトになる。しかも後片付けが走ると一時ファイルも消える。

非自明なのは、**この形が「原因不明」という結論を安定して生産する**ことである。ゼロバイトは「何も出なかった」と読めるので、観測の欠落ではなく被観測対象の性質として記録される。実際に、この症状を「モデルが無言で返した」と読んだうえで、外から極小の問い合わせを投げて生死を判定する仕組みを設計しかけた。**証拠は無かったのではなく、生成側で捨てられていた。**

もう一つ非自明なのは、**バイト数がゼロでなくても中身が無い場合がある**ことである。上の例では標準エラーが 120 バイトあったが、中身は bash の `Terminated: 15` という job 通知で、被観測対象由来の内容は1バイトも無かった。**証拠の形をしていて中身が無い。** 量だけを見ると「残っている」と読める。

次にどう行動を変えるか。(1) 打ち切りを掛ける対象の出力経路に間のプロセスが居るなら、**そのプロセスが「集めてから渡す」作りかを先に読む**。読む場所は、対象の起動行と、その出力を自分の標準出力へ渡している行の距離である。両者の間に待ち合わせがあれば、打ち切りはそこに刺さる。(2) **観測がゼロだったことを被観測対象の性質として記録しない**。記録するなら「経路のどこで消えたかを確かめていない」と併記する。(3) **バイト数がゼロでないことを証拠の存在と読まない**。中身を開いて、被観測対象由来の内容かを確かめる。
