## 1. 実測（自分で測った。母集団と手順を明記する）

### 1.1 測定手順

`ai-development-hub` の作業ツリー内に残っている so-compare の meta ファイルを全件走査した。走査対象は次の3か所である。

- `tmp/so-*/` （リポジトリ直下）
- `projects/*/tmp/so-*/` （`orchestration-engine` と `cursor-thread-tools`）
- 上記の `*-meta.txt.attempt1` （リトライ時に退避された1回目の記録）

`tool` が `codex` / `claude` / `cursor` のいずれかである行だけを採用し、**レーン単位のレコード266件**を得た。`tmp/arena-*/` の meta は形式が別なので除外している。

### 1.2 成功したレーンの所要時間

| レーン | n | p50 | p75 | p90 | p95 | 最大 |
|---|---|---|---|---|---|---|
| codex | 90 | 200 | 269 | 366 | 450 | 560 |
| cursor | 72 | 156 | 188 | 226 | 254 | 404 |
| claude | 48 | 374 | 638 | 780 | 888 | 1094 |

240秒を超えた割合は codex が 33/90（37%）、cursor が 5/72（7%）、claude が 38/48（79%）である。

### 1.3 この分布は右側が切られている（重要な限界）

**成功レコードの所要時間は、そのとき効いていた上限で頭を打たれた後の値である。** 上限を超えた実行は成功として残らず `timeout_empty` になるので、上の分布は真に必要な時間を**過小に**しか表していない。しかも過去の実行は上限が揃っていない。codex の 388〜560秒の成功は、既定240秒とリトライ360秒では走りきれないので、そのとき手動で上限が引き上げられていたことになる。

**これがそのまま scope 2（使われた上限を meta に記録する）の動機である。** 上限が記録されていないので、事後にこの分布を正しく補正できない。

### 1.4 上限が回収できる唯一の場所 — `timeout_empty` の `elapsed_seconds`

`timeout_empty` のレコードは、`elapsed_seconds` がそのとき効いていた上限そのものである。ここから過去に実際に使われた上限を回収できた。

| レーン | 観測された上限 |
|---|---|
| codex | 240 が5回、241 が1回、480 が2回 |
| cursor | 240、280 が2回、300、301 が2回 |
| claude | 240 が7回、360、420 が3回、480 が4回、720、958、1200 が2回 |

上限が実行ごとにばらばらであることが、伝聞ではなく自分の測定で確認できた。

### 1.5 リトライが1回目より速く返った例がある（原因は特定できない）

> **【gate 2 で棄却された節。修正済み】** 初版はこの観測から「1回目は止まっていた（上限を上げても直らない）」と結論していた。**設計SOの2レーンが揃ってこの推論を棄却した。** 棄却は妥当だったので、結論を観測の記述まで後退させた。詳細は §9 にある。

リトライが走ったケースを全件（18件）取り出し、**リトライが成功したときの所要時間を、直前に期限切れした上限と比べた**。

| レーン | 観測 | 件数 |
|---|---|---|
| codex | リトライのほうが、期限切れした上限より短時間で返った | 3 |
| codex | リトライは期限切れした上限より長くかかった | 1 |
| cursor | リトライのほうが短時間で返った | 2 |
| cursor | リトライも失敗 | 1 |
| claude | リトライは期限切れした上限より長くかかった | 4 |
| claude | リトライも失敗 | 4 |

codex の具体例を挙げる。`tmp/so-274-design` は480秒で1回目が空返しになり、リトライは410秒で成功した。`tmp/so-288-h3` は480秒で空返しの後、リトライが331秒で成功している。

**この観測から言えるのは「2回目が、1回目の上限より短い時間で終わった」までである。** 「1回目は上限をいくら伸ばしても終わらなかった」は導けない。別の説明が複数成り立つ。

- 実行ごとの負荷・キュー待ち・モデル側の混雑の変動（1回目は550秒かかる状態で上限480秒、2回目は410秒、というだけかもしれない）
- 2回目でプロンプトキャッシュや認証・作業ツリー走査が温まっていた
- リトライが別のバックエンドへ振られた
- 1回目は処理が進んでいたが、stdout が期限までに flush されなかった

**したがって「codex の失敗の3/4は上限では直らない」という初版の主張は取り下げる。** 分類名として妥当なのは「リトライで短縮した」までである。

なお、この誤りは brief で自分が採用した negative knowledge `01KZ3MHMET3GTRXTQXZSZCSWJJ`（空返しの meta は原因を運ばない・観測値から原因を断定するな）にそのまま抵触していた。**採用した item を、同じ plan の中で踏んだことになる。**

言えることは残る。**上限を上げても `timeout_empty` はゼロにはならない**（1200秒の claude で現に空返しがある。§5.1）。ただしその残る割合を、この観測から数値で見積もることはできない。

### 1.6 プロンプト長は主変数ではない、という上流の前提は言い過ぎだった

brief が別リポジトリの伝聞として載せていた「プロンプト長は主変数にならない」を自分の母集団で検定した。codex の成功64件について、プロンプトのバイト数と所要秒数の**スピアマン順位相関は 0.687** である。バケット別の平均所要は 3KB未満が156秒、3〜8KB が233秒、8〜20KB が332秒と単調に増える。

ただし**裾は説明できない**。最長の535秒は 3〜8KB のバケットから出ている。

正しい言い方は「プロンプト長は中心の傾向とは相関するが、裾を縛らない」である。**上限の決定にプロンプト長を使うことはできない**（裾が縛れないため）という結論自体は変わらないが、前提の書き方は不正確だったので記録しておく。

### 1.7 上限ごとの見込み（既定値を選ぶための試算）

1.2 の成功分布を「真に必要だった時間」とみなし、上限 L のときの挙動を試算した。1回目が L を超えたら `timeout_empty` になり、リトライ（L×1.5）で再実行される、というのが現行の機構である。

codex（n=90）:

| L | 1回目で通る | リトライが要る | リトライでも届かない | 平均待ち | p95 待ち |
|---|---|---|---|---|---|
| 240（現行） | 63.3% | 23/90 | **10/90** | 299秒 | 600秒 |
| 300 | 85.6% | 9/90 | 4/90 | 262秒 | 750秒 |
| 360 | 88.9% | 9/90 | 1/90 | 261秒 | 810秒 |
| 420 | 93.3% | 6/90 | 0/90 | 249秒 | 870秒 |
| **480** | **97.8%** | 2/90 | 0/90 | **232秒** | **450秒** |
| 600 | 100% | 0/90 | 0/90 | 221秒 | 450秒 |

cursor（n=72）:

| L | 1回目で通る | リトライが要る | リトライでも届かない | 平均待ち | p95 待ち |
|---|---|---|---|---|---|
| 240（現行） | 93.1% | 4/72 | 1/72 | 173秒 | 494秒 |
| 300 | 97.2% | 2/72 | 0/72 | 165秒 | 254秒 |
| **360** | **98.6%** | 1/72 | 0/72 | **162秒** | **254秒** |
| 420 | 100% | 0/72 | 0/72 | 157秒 | 254秒 |

> **【gate 2 で棄却された試算。下の但し書きを必ず併せて読むこと】** この表は**既定値を決める根拠には使えない**。設計SOの2レーンが揃って手続きの不当性を指摘し、棄却は妥当だった。表そのものは「桁感をつかむ材料」として残すが、**数値を根拠として引用しないこと**。

#### この試算が成立しない理由（gate 2 の指摘・自分で検算した）

この試算は、次をすべて同時に仮定している。いずれも確かめていない。

- タイムアウトで失われた観測が、成功した観測と同じ分布から来ている（**1.3 で自分が否定した仮定である**。警告を書いた直後に同じ分布を「真に必要だった時間」として使っており、手続きとして一貫していない）
- 同じ依頼の1回目とリトライの所要時間が同じである（1.5 で取り下げた仮定）
- 手動で上限を上げる判断が、課題の難しさと独立している（実際には難しい課題ほど上限を上げているはずで、右の裾が厚くなる方向に偏る）
- 上限がばらばらな実行を層別せずに混ぜてよい

**打ち切りを踏まえた粗い区間で見ると、表の楽観性がはっきりする。** 成功90件に `timeout_empty` 8件を足した98試行を母数に取り直すと、codex が480秒以内に終わる割合は次の区間にしかならない。

- 最悪側 **89.7%**（8件の timeout がすべて480秒超だったと置く）
- 最良側 **95.9%**（240/241秒で切られた6件がすべて480秒以内に終わったはずだと置く。480秒で切られた2件は480秒を超えたことが確定している）

**表が出している 97.8% は、この最良側の境界すら上回っている。** cursor も同様で、360秒の 98.6% に対して区間は 91.0%〜98.7% である。

「平均待ちが299秒から232秒に下がる」も同じ理由で数量として主張できない。回避できるリトライの利得だけを正確に数え、未知の長時間側とハングを楽観値で埋めているためである。**方向（1回目を通したほうが速い場合がある）は成り立ちうるが、67秒という数字は出せない。**

さらに、この平均は**レーン単体の所要時間の平均であって、SO の壁時計ではない**。実装は1回目を並列、リトライを逐次で回す（§6 で修正した）。「平均が下がる＝SO が速くなる」と読むのは対象の取り違えである。

引き上げの代償の見積もりも小さすぎた。初版は「ハング1件あたり240秒の悪化」と書いたが、**基準を240から480へ上げるとリトライ上限も360から720へ動くので、1件あたりの増分は約600秒である**。

#### それでも残る、確かなこと

打ち切りに影響されない事実がひとつある。**480秒で切られた codex が2件、240/241秒で切られた codex が6件、実際に存在する。** つまり現行の240秒が「1回目で通る」経路になっていないことは、区間の取り方によらず言える。**現行値が低すぎるという方向は確かである。到達点をこのデータで確定できない、というのが正確な状態である。**

### DJ-2 / DJ-3: 具体値 — **owner の判断を仰ぐ（gate 3）**

初版は codex=480 / cursor=360 で確定するつもりだった。**gate 2 の2レーンが揃って「このデータで既定値を確定することはできない」と判定した。** 検算した結果その指摘は正しかったので、**値の確定を owner へ上げる。**

確定を保留する理由を3つに整理する。

1. **1.7 の試算が根拠にならない**（上記のとおり）。到達点を分布から導けない。
2. **480 でも足りない実測が2件ある。** ひとつは既存の記録で、`SO_TIMEOUT=480` を明示して回した #319 の gate 4 が、それでも1回目に `timeout_empty` になっている（`projects/orchestration-engine/docs/episodes/2026-08-11-episode-319-adr-append-c1-c2.md:246`）。もうひとつは**この plan 自身の gate 2 である。§9 のとおり codex レーンは531秒かかった。** 480 を既定にしていたら、この SO は1回目に落ちていた。
3. **上限を上げるほど最悪の壁時計が伸びる**（§6 の修正表）。何を最適化するのかを先に決めないと、過小か過大かを一軸では判定できない。

#### owner に選んでもらう形

先に**目的関数**を決める必要がある。候補を並べる。

| 案 | codex / cursor | 弱2レーンの最悪壁時計 | 性格 |
|---|---|---|---|
| ア | 480 / 360 | 約1740秒（29分） | 初版案。観測の大半を覆うが #319 と本 plan の gate 2 が反例 |
| イ | 600 / 420 | 約2130秒（36分） | 観測した成功をすべて1回目で覆う。最悪待ちは最も長い |
| ウ | 480 / 360 ＋ SO 全体の壁時計上限 | 上限値そのもの | 最悪値を契約として固定する。**scope 拡大**（リトライ機構に触る） |
| エ | 据え置き（240 / 240） | 約960秒 | 既定は変えず、meta の記録（scope 2〜4）だけ先に入れて実測を貯める |

**案エは「何もしない」ではない。** 上限が meta に残るようになれば、次の単位は打ち切りを補正できる母集団を持てる。1.3 で述べたとおり、**現在この判断ができないのは、まさに上限が記録されていないからである。** 記録を先に入れて、値の決定を次の単位に送るのは筋が通っている。

**自分の推奨は案エである。** ただしこれは issue の受け入れ条件（「codex の既定が実測に基づいて引き上げられている」）を満たさないので、**issue の締め直しが要る。owner の判断を仰ぐ。**

#### 裁定: 案エを採用（2026-08-13・owner・gate 3）

**既定値は据え置く。240 / 240 のまま変えない。** 本単位で入れるのは記録の仕組みだけである。

owner が挙げた理由は、自分が §1.3 と §1.7 で書いたことより一段強い言い方になっている。**打ち切られた測定から既定値を導くと、その打ち切りを規範として焼き込んでしまう。** gate 2 の codex が531秒だった件は、その具体例として使われた。480秒案を採っていたら、**その案を評価するための SO 自体が、その案の下では失敗していた**ことになる。

したがって **DJ-1（レーンごとに上限を分ける）も採用しない。** 分けるのは値が違うときに意味があるので、据え置くなら不要である。

issue の受け入れ条件は統括が #298 のコメントで2段階に締め直し、issue は keep-open のままにする。**この単位は段階1（記録の仕組み）だけを閉じる。**

推奨する理由は、値を決めるのに必要なデータを今は持っておらず、しかも**そのデータを作る仕組み（scope 2〜4）が本単位の残り全部だから**である。案ア〜イを今入れると、根拠の弱い数字が「実測に基づく既定」という顔をして SKILL.md に載り、次の単位がそれを引用する。#319 が「スキルの推奨値400〜480では足りない」と書いたのと同じことが繰り返される。

**どの案を採っても、値は「実測に基づく運用ヒューリスティック」と label する**（`evidence-verification-rule` §3 の義務）。証拠に裏づけられたしきい値ではない。この但し書きはコードのコメントと SKILL.md の両方に書く。

### DJ-4: meta のスキーマ

```text
DJ-4: 使われた上限・CLI 版・stderr 量の記録形式
├── 案A（初期）: 既存の key=value 行に additive でフィールドを足す
│     → 採否: ✅ 採用。既存の読み手が grep '^key=' | cut -d= -f2 で
│              読んでいるので、行を足す限り壊れない
├── 案B（ゼロベース）: <tool>-meta.json を別に出す
│     → 差分軸: データ形式が変わる（構造化・入れ子が持てる）
│     → 採否: ❌ 二重管理になる。既存の読み手は全員 grep 方式で、
│              JSON を読む消費者が今いない
└── 案C（ゼロベース）: 試行ごとの上限を1行にまとめる（attempts=480,720）
      → 差分軸: 1レコードで履歴が読める
      → 採否: ❌ 1キー1値という既存の読み方を壊す。しかも試行ごとの
               meta は .attempt1 で既に分離保存されているので、
               各 meta が自分の上限だけを持てば履歴は復元できる
```

**採用するフィールド**（すべて既存の命名に揃える）:

| フィールド | 内容 | 既存の対応 |
|---|---|---|
| `timeout_limit_seconds` | **その試行で**実際に効いた上限 | `elapsed_seconds` に揃える |
| `cli_version` | そのレーンが呼ぶ CLI の版 | `model_resolved` に揃える |
| `cli_version_source` | 版の出所。取得できなければ `unavailable:<種別>` | `model_resolved_source` に揃える |
| `stderr_bytes` | そのレーンの stderr のバイト数（**進行の指標ではない**。Step 4） | `stdout_bytes` に揃える |
| `attempt` | 試行番号（1 = 初回、2 = リトライ） | gate 2 の指摘で追加 |
| `attempt_state` | `running` / `finished`。中断された meta を見分ける | gate 2 の指摘で追加 |

**これらは試行の開始前に書き、完了時に原子的に置き換える。** リトライ後に追記する形にはしない。理由は Step 2 で述べる。

## 3. 実装ステップ

各ステップは独立に検証できる粒度にしてある。

### Step 1: レーンごとのタイムアウト変数を導入する — **落とす（gate 3）**

**owner が案エ（既定は据え置き）を採ったので、この step は不要になった。**

`SO_CODEX_TIMEOUT` / `SO_CURSOR_TIMEOUT` を導入する意味は、codex と cursor で違う既定を持たせることにあった。両方とも240秒のまま変えないなら、変数を分ける必要がない。**使われない環境変数を先に置くのは scope の拡大である。**

`base_timeout_for()` も現行のまま触らない。将来また既定値を分ける判断が出たら、そのときの測定で決める。初版の設計（優先順位を「レーン個別 > `SO_TIMEOUT` > レーンごとの既定」とし、resolver で出所も返す形）は、そのとき読み直せるようにここに残す。

### Step 2: 使われた上限を meta に記録する（試行の開始前に書く）

初版は `run_*` の meta 出力ブロックに `timeout_limit_seconds=$tool_timeout` を1行足すだけの案だった。**gate 2 の2レーンが揃って、これでは scope 2 の目的を満たさないと指摘した。指摘は正しい。**

理由はこうである。`run_*` が meta を書くのは**外部コマンドが終わった後**である（`scripts/so-compare.sh:671` で実行し、`:688` 以降で meta を書く）。リトライは `.attempt1` へ退避してから同期で走る。**この間に親が止められると、次の状態で固まる。**

- `<tool>-meta.txt` は1回目の内容のまま
- `<tool>-stdout.txt` と `<tool>-stderr.txt` は2回目に上書き済み、または書きかけ
- `retry=1` も `retry_timeout` も存在しない

つまり **meta は1回目、本文は2回目という食い違いが残る。** §5.3 で自分が観測した5件はまさにこの形であり、初版の Step 2 はその欠陥を回避できていなかった。

**修正案: 試行を開始する前に、その試行の上限と状態を書く（write-ahead）。**

```bash
# 外部コマンドを起動する前
{
    echo "tool=$tool"
    echo "attempt=$attempt_no"
    echo "attempt_state=running"
    echo "timeout_limit_seconds=$tool_timeout"
} > "$OUT_DIR/${tool}-meta.txt"

# 外部コマンドの実行 …

# 完了後、確定内容を一時ファイルへ書いてから mv で置き換える（原子的に差し替える）
{ … 完全な meta … ; echo "attempt_state=finished"; } > "$OUT_DIR/${tool}-meta.txt.tmp"
mv "$OUT_DIR/${tool}-meta.txt.tmp" "$OUT_DIR/${tool}-meta.txt"
```

これで**どの時点で中断されても、その試行の番号・上限・開始済みかどうかが残る。** 読み手は `attempt_state` を見て、その meta が確定値か途中かを判別できる。

`attempt` フィールドを足すのも gate 2 の指摘による。**現行は最終 meta だけを見ても、それが1回目の成功なのかリトライの結果なのかを確定できない**（`retry=1` の追記が消えている場合があるため）。試行番号を試行自身に持たせれば、追記の有無に依存しなくなる。

既存の `retry=1` / `retry_timeout=` の追記はそのまま残す（後方互換）。ただし `timeout_limit_seconds`（その試行の上限）と `retry_timeout`（リトライ時に算出した上限）は意味が近く紛らわしいので、**SKILL.md に両者の違いを明記する**（これも gate 2 の指摘）。

### Step 3: CLI の版を meta に記録する

各レーンが実際に起動するコマンドから版を取る。実機で確認済みの取得方法と所要時間は次のとおりである。

| レーン | コマンド | 出力 | 所要 |
|---|---|---|---|
| codex | `codex --version` | `codex-cli 0.147.0` | 16ms |
| claude | `claude-safe --version` | `2.1.229 (Claude Code)` | 90ms |
| cursor | `agent --version` | `2026.08.11-e8db854` | 388ms |

3レーン合計でも0.5秒未満なので、数百秒の実行に対する負荷は無視できる。

取得値はそのまま書かない。meta は1行1組の `key=value` で読まれるので、`=` や改行や制御文字が混ざると行が壊れる。

> **【gate 2 が見つけた致命的な欠陥。修正済み】** 初版はここで「既存の `extract_claude_models()` と**同じ**健全性チェックを通す」と書いていた。**その通りに実装すると機能が丸ごと死ぬ。** 既存の許可集合は `^[A-Za-z0-9._:+-]+$` で、**空白も括弧も通さない**。実際の版文字列と突き合わせて自分で確かめた結果が次である。
>
> | 版文字列 | 既存の許可集合での判定 |
> |---|---|
> | `codex-cli 0.147.0` | **不合格**（空白） |
> | `2.1.229 (Claude Code)` | **不合格**（空白と括弧） |
> | `2026.08.11-e8db854` | 合格 |
>
> つまり codex と claude の `cli_version` は常に `unavailable:schema-unexpected` になり、cursor だけが記録される。**しかも4.3 の受け入れ確認は「フィールドが入っていること」しか見ていなかったので、この状態でも通ってしまう。**

**修正: 「同等の安全性」と「同じ文字集合」を分ける。** 版文字列には版用の規則を当てる。

- 拒否する: `=`、改行（CR / LF）、NUL、その他の制御文字
- 許可する: 空白、括弧、`.` `+` `-` `_` `:` `/` および英数字
- バイト長の上限を設ける（例: 200バイト）。超えたら `unavailable:schema-unexpected`
- 複数行が返った場合は1行目だけを採る

制御文字の混入は目視で気づけないので、実装時は生成物を `grep -nP '[\x00-\x08\x0b\x0c\x0e-\x1f]'` で確認する。

**`--version` の呼び出し自体にも短いタイムアウトを掛ける**（gate 2 の指摘）。掛けないと、レーン本体のタイムアウトの外側に、新しく無限に待ちうる経路を作ってしまう。実測は16〜388ミリ秒なので、5秒あれば十分すぎる。

```bash
version_raw="$(timeout 5 "$CMD" --version 2>/dev/null | head -1)" || version_raw=""
```

取得に失敗した場合は `unavailable:query-failed` とし、空欄にはしない。空欄にすると「記録漏れ」と「取得不能」が区別できなくなるためで、これは #295 が確立した方針である。

`cli_version_source` は `preflight-cli-flag`（本体の実行とは別に、事前に `--version` を叩いた値であることを示す）または `none` とする。**単なる `cli-flag` にしないのは、これが実行後の観測ではなく事前の別プロセスによる観測だからである。** codex の `model_resolved_source=config` が「観測値ではない」ことを明示しているのと同じ趣旨で、値の確からしさを名前に出す。

### Step 4: stderr のバイト数を meta に記録する

```bash
echo "stderr_bytes=$(wc -c < "$OUT_DIR/${tool}-stderr.txt" | tr -d ' ')"
```

claude レーンについては、処理の進行を表すのはプロセス本体の stderr なので `claude-stderr.txt` を対象にする（モデル抽出の診断を書く `claude-modelmeta-stderr.txt` は対象にしない）。

この値が #303 の材料になる理由は実測から言える。1回目が空返しになった codex の実行で、stderr は `tmp/so-274-design` が332KB、`tmp/so-288-h3` が831KB、`tmp/so-290-w4` が592KB まで育っていた。stdout が0バイトでも、stderr にはこれだけの出力が出ていた。

**ただし、この数字を「処理が進んでいた証拠」として使ってはいけない**（gate 2 の指摘。検算して同意した）。バイト数は**終了時点の総量**であって、時間の情報を持たない。開始直後に大量に出してその後停止した場合と、最後まで出し続けた場合を区別できない。**逆に0バイトも異常を意味しない。** 正常に成功したレーンで stderr が0バイトの実例がある（`tmp/so-161-review/claude-stderr.txt` と `tmp/so-188-design/cursor-stderr.txt` はどちらも0バイトで `timeout_status=success`）。

したがって `stderr_bytes` の位置づけは「#303 が切り分けるときの材料のひとつ」までである。**進行の指標として読ませない旨を SKILL.md に書く。** 進行を本当に見たいなら最終更新時刻や一定間隔の増分が要るが、それは #303 と watchdog の領分なので本単位では持たない。

### Step 5: 表示とエラーメッセージをレーンごとの値にする — **落とす（gate 3）**

Step 1 と同じ理由である。既定値を分けないので、現行の `codex/cursor=${SO_TIMEOUT}秒 claude=${SO_CLAUDE_TIMEOUT}秒` という表示は**そのままで正しい**。直す必要がない。

### Step 6: 文書を実装に追随させる

brief の scope 5 は `canonical/skills/so-compare/SKILL.md` だけを挙げているが、**同じ機構の説明が3つの文書にある**。

- `canonical/skills/so-compare/SKILL.md` — 冒頭の機構説明、環境変数表（51〜52行）、meta のフィールド一覧（117行）、「レーンごとの所要時間」節（226行以降）、未解決節（263〜271行）、注意点（343行）
- `canonical/orchestration-spec/document-format.md:280` — SO モード節の機構層の説明
- `scripts/README.md:87` — 環境変数の説明

**3つとも直す。** これは brief の文面を超える追加だが、勝手な拡張ではない。#296 の episode（`docs/orchestration-engine/episodes/2026-08-01-episode-295-so-model-record.md:202`）が、まさにこの2つの上流文書への追随を漏らして後から直したことを記録しており、同じ漏れを再生産しないための処置である。**この判断は owner の gate 3 で承認可否を確認したい。**

#### 実際に直したのは SKILL.md だけである（承認は得たが、他2文書は直す対象が無かった）

gate 3 で3文書への追随は承認された。しかし**同じ gate 3 で既定値の据え置き（案エ）も決まったため、残る2文書には直す箇所が無くなった。** 中身を確かめた結果は次のとおりである。

| 文書 | 何を書いているか | 本単位で変わるか |
|---|---|---|
| `canonical/skills/so-compare/SKILL.md` | meta のフィールド一覧と読み方 | **変わる。直した** |
| `canonical/orchestration-spec/document-format.md:280` | タイムアウト機構（既定値・リトライ幅）と弱 SO の consumer ルール | 変わらない。既定値もリトライ方針も据え置きのため |
| `scripts/README.md:87` | 環境変数の一覧と既定値 | 変わらない。環境変数を追加していないため |

**後者2つは meta のフィールドに一切言及していない**（`grep` で0件）。記述が古くなっていないので、触れば diff のノイズが増えるだけである。**承認された範囲を使い切らないという判断であり、承認の趣旨（実装と文書を食い違わせない）には反していない。**

既定値を動かす段階（issue の段階2）に入るときは、この2文書が追随対象に戻る。

SKILL.md の「未解決: codex / cursor 側の既定（240秒）も実は足りていない」節をどう書き換えるかは、**DJ-2 / DJ-3 で owner がどの案を選ぶかで変わる。**

- 案ア〜ウ（既定を上げる）を選んだ場合は、新しい既定とその根拠の弱さ（打ち切りのある標本から選んだ運用ヒューリスティックであること）を書く

**どちらの場合も「既定を上げれば返る」と読ませない。** 上限を上げても `timeout_empty` が残ることは確かで（§5.2）、#319 が `SO_TIMEOUT=480` でも1回目に落ちた記録と矛盾しない書き方にする。gate 2 も「480 で足りると読める文書は #319 を否定することになる」と指摘している。

### 4.3 実機での確認（issue の受け入れ条件）

issue は「3レーンを実機で走らせた証跡がある」を求めている。レビュー級のプロンプトで3レーンを1回走らせ、次を確認する。

- [ ] 3レーンの meta に新フィールドが入っている
- [ ] `timeout_limit_seconds` が、そのとき実際に効いた上限と一致する
- [ ] **`cli_version` が実際の版そのものと一致する**（`unavailable:*` に落ちていないことを値で確認する）
