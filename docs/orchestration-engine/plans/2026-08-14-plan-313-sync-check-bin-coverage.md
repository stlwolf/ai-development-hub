### 1.2 まだ誰も測っていなかったこと — 2つ目の GNU 依存も生きている

`scripts/sync.sh:46` には GNU 依存が**2か所**ある。

```bash
sed -n '/^# Usage:/,/^set -euo pipefail/p' "$0" | head -n -1 | sed 's/^# \?//'
#                                               ^^^^^^^^^^^   ^^^^^^^^^^^^^^^
#                                               (1) BSD head に -n -1 が無い
#                                               (2) BSD の BRE は \? を「省略可」と解釈しない
```

(2) を実測した。

```
$ printf '# hello\n#\n' | sed 's/^# \?//' | cat -A
#·hello␊
#␊
```

**行頭の `# ` が剥がれていない。** つまり (1) だけを直すと `--help` は rc=0 になるが、出力は全行が `# ` 付きのまま出る。受け入れ基準の文面（rc=0 かつ `head: illegal line count` を出さない）は満たすが、`--help` は読める形にならない。

先例（`scripts/sync/sync-bin.sh:46-52`）はこの2つを**両方**直しており、その理由をコメントに書き残している。§3.4（DJ-2）で扱う。

### 3.2.1 採用案 — 案N: `sync-bin.sh --check` を足し、`sync.sh` は子プロセスへ委譲する

- 差分軸: 共有するものを「母集団」から**「照合述語そのもの」**へ引き上げる。案D と違い `check_symlink` を共通 lib へ切り出さず、`sync-bin.sh` が自分の配布対象を自分で検査する。
- **repo に先例がある。** `scripts/sync/sync-codex.sh:270` が `scripts/check-codex-guardrails.sh` を子プロセスとして呼び、`scripts/README.md:41` がその関係を書いている。
- **初期案に無かった理由（隠れていた前提）**: §3.1 に前提を4つ挙げたが、「照合述語は `sync.sh` の `check_symlink` である」という5つ目の前提を挙げていなかった。それを §3.5 で固定した結果、この枝が見えなくなった。

- 案N が払うコスト: **照合述語が2か所になる。** `sync.sh` の `check_symlink` は cursor / claude / codex の3ターゲットで使い続け、bin は `sync-bin.sh` 側の実装を使う。同型のロジックが2本になるので、drift しうる。案F は「述語1本・母集団2か所」で、案N は「母集団1か所・述語2本」というトレードオフである。**issue が問題にしているのは母集団の drift なので、案N はその軸を潰す。**

#### 先例の規律をそのまま引き写すと逆向きに働く（実測）

negative knowledge `01KZVHE0KQ5VCX0SXH0F4SM14D`（先例の規律を移すときは前提も移るか確かめよ）が、ここで実際に発火した。

**先例は子を素で呼んでいる。** `sync-codex.sh:270` は `"${REPO_ROOT}/scripts/check-codex-guardrails.sh"` と書くだけで、rc を捕まえていない。子が非ゼロを返せば `set -euo pipefail` で `sync-codex.sh` が中断する、という設計である。

**その前提は移らない。** 先例の `main` は `sync-codex.sh` のトップレベルで `main "$@"` として呼ばれるので errexit が効く。移植先の `check_target` は `scripts/sync.sh:248` の `if ! check_target` から呼ばれるため **errexit が抑止される**。

同じ書き方を移した場合を実測した。

```bash
check_target() {
    local has_diffs=false
    "${D}/child.sh"          # 先例と同じ素の呼び方
    [[ "${has_diffs}" == true ]] && return 1
    echo "[INFO]  bin: up to date"; return 0
}
if ! check_target; then echo "RESULT=red"; else echo "RESULT=green"; fi
# 子が rc=1（差分あり）を返しても → "[INFO] bin: up to date" / RESULT=green
```

**子が差分を検出したのに親が緑になる。** 先例では安全だった書き方が、移植先では検査の失敗をまるごと飲み込む。**素の呼び方は採らない。**

#### 子の rc を「差分あり」と「実行できなかった」に分けきれない（実測）

rc を捕まえる形（`"${script}" --check || rc=$?`）にしたうえで、壊れた子の rc を測った。

| 壊し方 | `bash -c` から呼んだとき | スクリプトファイルの中から呼んだとき |
|---|---|---|
| 実行可能ビットを落とす | 126 | **1** |
| ファイルを消す | 127 | 1 |

**同じ壊し方でも呼び出し文脈で rc が変わる。** したがって **rc の数値だけで「差分あり(1)」と「子を実行できなかった」を区別する契約は書けない。** 幸い安全側の性質は保たれる（どちらも非ゼロ＝赤）が、診断が曖昧になる。

対処は2つ。

- **親は呼ぶ前に `[[ -x ]]` で弾く。** `scripts/sync.sh:200-203` の `run_target` が既に同じ形を持っているので、既存パターンに従う。これで 126 / 127 の経路が明示的なエラーになる。
- **母集団の健全性は子の中で見る**（§3.3）。親は「rc==0 なら緑、それ以外は赤」だけを守る。

#### gate 2 で出た他の案（いずれも不採用）

**案M — 強制力をテスト層に置く。** `tests/` に「`--check bin` が `CMD_NAMES` 全件を見る」を assert するテストを置く。Step 4 の陽性対照が使い捨てでなく恒久資産になる。**gate 3 の裁定で本単位には入れず別起票**（起票は親が持つ。本単位では実装しない）。

**案I — 検査の向きを双方向にする。** 「定義と現物の集合が一致しているか」と定義し直す。**gate 3 の裁定で out。** §8 の未探索へ移した。

**案Q（マニフェスト）・案H（callback 型 API）・案（repo 内 symlink の名前空間を正本にする）** も出たが、いずれも新しい壊れ方を持ち込み、本 issue の規模に対して過剰である。棄却する。

**案M — 強制力を実行時結合ではなくテスト層に置く。** 母集団の一元化をせず、`tests/` に「`--check bin` が `CMD_NAMES` 全件を見る」を assert するテストを置く。`projects/orchestration-engine/tests/` に30本超の `test_*.sh` という前例がある。**案F と排他ではない。** Step 4 の陽性対照が使い捨てでなく恒久資産になる点が大きい。hub に CI が無く実行が手動になるのが弱点。→ §7 で owner に上げる。

**案I — 検査の向きを双方向にする。** 「網羅性」を「母集団の全件を検査したか」ではなく「定義と現物の集合が一致しているか」と定義し直す。片方向だと `CMD_NAMES` から外された verb の残骸が `~/bin` に永久に残っても見えない。issue の「網羅性」の読みに入りうるので、in か out かを owner に確認する（§7）。

**案Q（マニフェスト）・案H（callback 型 API）・案（repo 内 symlink の名前空間を正本にする）** も出たが、いずれも新しい壊れ方（状態ファイルの陳腐化・変更量・二段 symlink の運用コスト）を持ち込み、本 issue の規模に対して過剰である。棄却する。

### 3.2.2 文書への影響 — 案N では owner が承認した追随が不要になる

**この節は gate 3 の裁定を受けて結論が反転した。owner の再確認を求める箇所である（§7-3）。**

案F を前提にしていたとき、正本が `sync-bin.sh` から新ファイルへ移るせいで次の2か所が偽になる、と書いていた。

- `scripts/README.md:39` — 「リンク名と実体の対応は**同スクリプトの** `CMD_NAMES` / `CMD_SOURCES`」
- `CLAUDE.md:22` — 「正本は `CMD_NAMES`」

owner はこの追随を scope に入れると裁定した（裁定3）。**ところが案N では正本が動かない。** `CMD_NAMES` / `CMD_SOURCES` は `sync-bin.sh` に残るので、**上の2か所はどちらも真のままである**（一次確認した）。裁定3 が守ろうとしていた対象が、案N の採用によって消えた。

なお `scripts/README.md:39` は配布対象8件を名前で列挙しているので、**母集団そのものが縮む故障に対する外部オラクル**としては引き続き使える（§3.3）。この用途は案の選択に依存しない。

### 3.3 DJ-1 の付随要件: 母集団を取り損ねたときに緑にしない（案N 版）

**この節は案N 採用にともなって全面的に書き直した。** 案F では「`source` が失敗したときに緑にならないか」を問題にしていたが、案N には `source` が無い。守るべき性質は同じ（計測器の故障を緑と読ませない）で、故障モードが入れ替わる。

#### 案N の故障モード

| # | 故障 | 案F にはあったか | 塞ぎ方 |
|---|---|---|---|
| N-1 | 親が子を素で呼び、子の非ゼロを飲み込む | 無い（案N 固有） | 素で呼ばない。rc を捕まえる（§3.2.1 で実測） |
| N-2 | 子が実行不能・不在で、rc が「差分あり」と紛れる | 無い（案N 固有） | 親が呼ぶ前に `[[ -x ]]` で弾く（`run_target` と同型） |
| N-3 | 子が母集団0件のまま rc=0 で返り、親が緑にする | 有る（形は違う） | **子の中で**件数と2配列の長さを見て `exit 2` |
| N-4 | 定義そのものから対象が消え、配布側も検査側もそろって縮む | 有る（同じ） | 設計では塞げない。外部オラクルとの突合（Step 4 (g)）と案M |
| N-5 | 2配列の**件数は合ったまま対応がずれる** | 有る（同じ） | **塞げない。** 下記 |

**N-5 は gate 4 で claude レーンが見つけた。** `CMD_NAMES` の途中に1件挿入し `CMD_SOURCES` の末尾に足すと、長さは一致するのでガードを通る。配置すると挿入位置より後の組が1つずれて張られ（`~/bin/oe-tree` が `oe-hookfire` の実体を指す等）、**検査は緑を返す**。配置と検査が同じ間違った対応表を読むためである。

外部オラクル（Step 4 (g)）でも捕まらない。`scripts/README.md:39` は8件の**名前**を並べているだけで、名前と実体の対応は「同スクリプトの `CMD_NAMES` / `CMD_SOURCES`」に委ねると書いているためである。**削除は捕まえるが、ずれは捕まえない。**

**実際に踏んだ。** Step 4 (f) の probe の初版で source を先頭に挿してこの状態を作っている（§10 の episode 参照）。そのときは別の理由（`REPO_ROOT` の解決先違い）で赤くなったので気づけたが、両方が正しく解決していれば緑で通っていた。

これは本単位の実装の欠陥ではなく、「`~/bin` が宣言された配布集合と一致しているか」という検査の契約の外側にある（対応表そのものの正しさは検査していない）。**恒久的に塞ぐのは [#333](https://github.com/stlwolf/ai-development-hub/issues/333) のテスト層の仕事である。**

**N-1 と N-2 は案N を採ったことで新しく生まれた故障である。** どちらも「親が子をどう呼ぶか」に属する。案F では `source` の失敗という1点だったものが、プロセス境界を挟んだことで2つに分かれた。

**N-3 の置き場が案F から動く。** 案F ではガードを親（`sync.sh`）に置くしかなかったが、案N では**母集団を持っているのは子である**。したがってガードも子に置く。親は母集団を知らないままでよい — それが案N の要点である。

#### 親の側（`scripts/sync.sh` の `bin)`）

```bash
bin)
    local script="${SYNC_DIR}/sync-bin.sh"
    if [[ ! -x "${script}" ]]; then
        error "  bin: 検査を委譲できません（実行可能ではありません）: ${script}"
        has_diffs=true
    else
        local rc=0
        "${script}" --check || rc=$?
        if [[ "${rc}" -ne 0 ]]; then
            has_diffs=true
        fi
    fi
    ;;
```

**`rc==0` のときだけ緑にする。** 1 か 2 かで扱いを変えない — §3.2.1 で測ったとおり、壊れた子の rc は呼び出し文脈で 1 にも 126 にもなり、数値で意味を分けられないためである。**子の側が人間向けの理由を印字する**ので、親が rc を細分する必要はない。

#### 子の側（`scripts/sync/sync-bin.sh --check`）

```bash
# 母集団の健全性を先に見る。0件や長さ不一致で「差分なし」を名乗らせない。
if [[ ${#CMD_NAMES[@]} -eq 0 || ${#CMD_NAMES[@]} -ne ${#CMD_SOURCES[@]} ]]; then
    error "配布対象の定義が空か、CMD_NAMES と CMD_SOURCES の長さが一致しません"
    exit 2
fi
```

`CMD_NAMES` は `sync-bin.sh` のトップレベルで必ず代入されるので、案F のときに要った「未定義配列に `${#...[@]}` を書くと `set -u` で死ぬ」への手当て（`declare -p` による存在確認）は**要らなくなる**。同じファイルの中に定義があるためである。**案F で見つけた穴のうち1つは、案N では構造的に消える。**

rc の契約は次のとおり。

| rc | 意味 |
|---|---|
| 0 | 配布対象の全件が期待どおり張られている |
| 1 | 差分があった（Missing / Mismatch / source 不在） |
| 2 | 呼び方の誤り、または母集団が健全でない（既存の引数エラーと同じ番号） |

2 を既存の引数エラーと同じ番号にするのは、`sync-bin.sh` が既に不正なオプションへ `exit 2` を返しているためである（`scripts/sync/sync-bin.sh:79,91`）。**「検査が成立しなかった」を「差分なし」と読ませないことが本質**で、番号を増やすことではない。

#### 引き続き効く原則と、案F の測定のうち生き残るもの

negative knowledge `01KYMRE1N7N0J8VP3CBZZEZ8Q3`（「0件・緑」を見たら対象が無いのか計測器が壊れているのかを区別せよ）を、検証手順だけでなく**設計にも**当てる、という原則は案が変わっても動かない。

gate 2 のために測った bash の意味論のうち、**案N でも生きるのは「版が2つある」という事実である。** `scripts/sync.sh`（親）は `#!/bin/bash`＝bash 3.2.57、`scripts/sync/sync-bin.sh`（子）は `#!/usr/bin/env bash`＝bash 5.2.37 で動く。**案N では両者がプロセスとして分かれるので、片方のコードが他方の bash で走ることは無くなる** — 案F にあった「同じ定義ファイルが2つの bash で source される」という制約は消える。子は 5.2、親は 3.2 で、それぞれ自分の版だけを考えればよい。

以下は案F を前提に測った表である。**採用案では使わないが、`source` を使う設計へ戻す判断が将来出たときのために残す。**

| 経路 | `/bin/bash` 3.2.57（`scripts/sync.sh` の shebang） | `env bash` 5.2.37（`sync-bin.sh` の shebang） |
|---|---|---|
| `if ! f` の中で通常のコマンドが失敗 | **errexit は抑止される**（後続が走る・rc=0） | 同じく抑止される |
| `source` 先が存在しない | **シェルが即死**（rc=1） | **死なない**・後続が走る（rc=0） |
| `source` 先が構文エラー | **シェルが即死**（rc=2） | **死なない**・配列が部分定義のまま後続が走る |
| `a=(); echo "${#a[@]}"` | 落ちない（0） | 落ちない |
| 未定義の配列に `${#a[@]}` | **`unbound variable` で即死** | 同じく即死 |

この表から案F 向けに引き出していた要件（`source` の rc を捕まえる・`declare -p` で配列の存在を確かめる・長さを照合する）のうち、**案N へ持ち越すのは長さの照合だけである。** 残り2つは `source` を使わなくなったので不要になった。

**残る穴（設計では塞げない・案が変わっても同じ）。** 定義そのものから6件消えれば、配布側も検査側もそろって2件になり緑が出る。母集団を1か所にした代償で、案F でも案N でも変わらない。外部オラクルとの突合が要り、`scripts/README.md:39` の8件の列挙がそれに使える（§5 Step 4 (g)）。**恒久的に塞ぐには案M（テスト層）が要る。gate 3 で別起票と裁定された。**

### 3.4 DJ-2: `usage()` の BSD 互換化をどこまでやるか

negative knowledge `01KZVHE0KQ5VCX0SXH0F4SM14D`（先例の規律を移すときは前提も移るか確かめよ）が効く。先例は `scripts/sync/sync-bin.sh:46-52` である。

**先例の前提が移植先にも在るかを確かめた。**

- `sed '$d'` が成り立つ前提は「`sed -n '/^# Usage:/,/^set -euo pipefail/p'` の出力の最終行が、落としたい `set -euo pipefail` の行である」こと。`scripts/sync.sh` では `# Usage:` が7行目、`set -euo pipefail` が27行目で、範囲内に他の一致は無い。**前提は移る。**
- 終了パターンが一致しなかった場合に範囲が EOF まで伸びる、という壊れ方は `head -n -1` と `sed '$d'` で同じである。**新しいリスクは増えない。**
- 先例のコメントが理由を書き残しているので、「理由を復元できないまま持ち込む」ケースには当たらない。

**そのうえで、先例は GNU 依存を2つ直している。** §1.1 のとおり `s/^# \?//` も BSD では効かない。**片方だけ移すと `--help` は rc=0 になるが全行が `# ` 付きで出る。**

```text
DJ-2: usage() の直し方
├── 案ア head -n -1 → sed '$d' だけ直す
│     採否: △ 受け入れ基準の文面は満たすが、--help の出力は読める形にならない。
│           同じ行の同じクラスの欠陥が残り、別起票が要る
└── 案イ 先例と同じく2つとも直す（sed '$d' + 2つの s コマンド）+ 理由のコメント
      採否: ⭕ 仮採用。同じ1行・同じ欠陥クラス・同じリポジトリ内の先例あり
```

**これは scope の拡大にあたるので owner の判断を仰ぐ**（§7 で明示）。実装側の推奨は案イである。

案イの出力は実行前に pipeline だけ再現して確かめた（`scripts/sync.sh` を変更せず、同じ sed 列を手で流した）。**行頭の `# ` が全行から剥がれ（`grep -c '^#'` が 0）、行内の `# 全ターゲット実行` のような注記は `^` 固定なので残る。** 期待どおりの出力になる。

**gate 2 が足した観点: 前提の確認を一時点の目視で終わらせないこと。** 範囲パターンが壊れたときの故障は3通りある。

- 開始パターンが消えると sed は**空出力・rc=0** になる（help が空でも緑）。
- 終了パターンが消えると usage 以降ファイル末尾まで出力し、`sed '$d'` は無関係な最終行だけを削る。
- 開始パターンが複数になると複数範囲を出力しうる。

**`rc=0` は正しさの証拠にならない。** `usage()` は最後に `exit 0` するので、パイプラインが空を返しても rc=0 になる。Step 3 の検証項目に、マーカーの件数と出力内容の照合を足す（§5 Step 3）。

### 3.5 DJ-3: 検査で何を見るか

issue のスコープ案が「リンク先が正しいかまで見るかを決める」と書いている。

**案N では述語が子へ移るので、この節は「`check_symlink` を再利用する」から「`check_symlink` と同じ判定を子で書く」に変わった。** 判定の中身は変えない。

- **今日の `check_symlink` と同じ3ケースを、子の側で実装する。** (a) 不在なら Missing、(b) symlink なら解決後パスの一致、(c) symlink でない実体ならファイル内容の diff。**新しい意味論を導入しない。** 現在 `so-compare` / `arena-compare` の2件に適用されている判定が、そのまま8件へ広がる形にする。
  - パス解決は `sync.sh` の `resolve_path` と同じ考え方（`realpath` → `python3` → 素通し）で書く。**同型のコードが2本になるのは案N のコストである**（§3.2.1）。
- **`[[ -f "${source}" ]] &&` のガードは持ち込まない。** 現行の `bin)` はこの形でガードしているが、これは「repo に source が無ければ検査を飛ばす」という意味であり、母集団を静かに縮める。source が repo に無いこと自体が defect なので、**警告を出して差分として数える**。
  - **非対称が生まれる点を明示しておく。** `scripts/sync/sync-bin.sh:113-116` は source 不在を error として印字したうえで `continue` し、`main` は 0 で終わる。`--check` は同じ状態で 1 を返す。**これは意図した非対称である**（配置は「できるところまでやる」、検査は「食い違いを見逃さない」）。配置側も失敗させるべきかは本 issue の外。
- **`&&` 連結ではなく `if` 文で書く。** 理由は §3.6 で2回差し替えた。最終的な理由は2つ。source 不在を「飛ばす」でなく「失敗として報告する」以上、条件分岐の意味自体が変わること。将来ループが関数末尾へ移っても壊れない形にしておくこと。

#### 意味論を変えなかったことで残る偽の緑（スコープ外・surface）

今日の `check_symlink` の (c) は、**`~/bin/<name>` が symlink ではない実体ファイルで、内容が repo 側と一致していれば緑にする**。ところが `sync-bin.sh:118-121` は実体ファイルを見つけると `Skipping (regular file exists)` として**配置をしない**。つまり sync が永久に管理しない状態が、検査では緑で通る。

これは #313 が問題にしている「配備漏れが緑で通る」と同じ型の欠陥だが、**原因も対象も別である**（本件は母集団の drift、こちらは判定の意味論）。案N で述語を書き直す機会に直したくなるが、**今日の振る舞いを変えることになるので本単位では直さない**（`behavioral-rule` §4 Minimal Scope）。統括へ surface する。

### 3.6 撤回した主張2つ — `set -e` とループ内の `&&`

**この節は、同じ1つの結論（`if` で書く）に対して根拠を2回書き替えた記録である。** 結論は動いていないが、根拠は2回とも事実と合っていなかった。

**撤回1（自分で実測して気づいた）。** 初版にはこう書いていた。

> `set -e` 下でループの最終反復が `[[ ]] && cmd` の偽で終わると、ループ全体の終了ステータスが非ゼロになる。

誤りである。bash の `errexit` は「`&&` / `||` リストの最終要素以外で失敗したコマンド」を免除するので、左辺の `[[ ]]` が偽でもループは止まらない（実測: `AFTER LOOP` / `AFTER g` が両方出て rc=0）。

**撤回2（gate 2 の claude レーンが指摘）。** 撤回1のときに差し替えた次の記述も誤りだった。

> 既存コードが `&&` を使っているのは case 節の途中で最後の文ではないため

`scripts/sync.sh:181` は `bin)` 分岐の**最後の文である**（一次確認した）。既存コードが無事なのは、`case` の後に :185 以降の文が続いてケースの終了ステータスが捨てられるからで、位置の問題ではない。

**さらに、そもそもこのコードパスでは errexit が抑止されている。** `check_target` は `scripts/sync.sh:248` の `if ! check_target "${target}"; then` から呼ばれる。実測のとおり `if !` の文脈では関数本体の errexit が抑止されるので、`&&` のままでも「`set -e` で落ちる」事象は起きない。

**根拠を2回外したのに結論が動かなかった、という形自体が記録に値する。** 「`if` のほうがよい」は最初から正しかったが、それを支える理由づけを2回とも検証せずに書いた。書いた時点で「測っていない」と自覚していた主張を、測らずに plan へ載せたのが原因である。

### 3.7 実装前に実測して確かめたこと（案F 前提・多くは案N では不要になった）

> **この表は案F（新ファイルを `source` する）を前提に測ったものである。** `shellcheck` の指示子に関する2行は、新規ファイルが無くなったので**採用案では不要**。生き残るのは「bash の版が2つある」という事実だけで、その扱いは §3.3 に書き直した。記録として残す。

plan の未検証の仮定のうち、机上で決めずに済むものを scratch 環境（repo 外）で先に測った。

| 仮定 | 実測結果 |

### Step 4 — 陽性対照（母集団側から全件を回す）

**実 `~/bin` は触らない。** `HOME` を一時ディレクトリへ差し替えた検証環境で行う。worktree から実 `~/bin` を検査すると、`~/bin` が master の作業ツリーを指しているため8件すべてが Mismatch になり、**赤くなった理由が「1件消したから」なのか「worktree だから」なのか区別できない**。

検証項目は次のとおり。**すべて目視でなく assert として書く**（rc を捕まえ、出力に現れる名前まで照合する）。gate 2 が「rc も名前も照合していない」「`set -e` を効かせたまま回すと最初の赤で止まり復元が走らない」と指摘した。

- **(a) baseline**: 8件そろっていれば rc=0。
- **(b) 1件ずつ落とす（本 step の核）**: 母集団の側から8件それぞれについて、rc=1 になること・**Missing 行に落とした名前が出ること**・復元後に rc=0 へ戻ることの3点を assert する。**名前まで照合しないと「1件消したら全件を赤にする」型の実装バグを通す。**
- **(c) リンク先違い**: `~/bin/<name>` を別の実体へ向け、`Mismatch: <name>` が出て rc=1 になること。
- **(d) 非 symlink の実体**（gate 2 の指摘・未踏の分岐）: 内容 diff 経路を踏む。`sync-bin.sh:118-121` が実体をスキップする以上、現実に起こる状態である。
- **(e) dangling symlink**（同・未踏の分岐）: 実体の消えたリンクが Missing として出ること。`[[ ! -e ]]` は dangling に対して真になるので、消えた worktree を指す孤児リンクをちょうど拾う。
- **(f) 受け入れ基準2の陽性対照**（gate 2 の指摘・初版に手順が無かった）: `CMD_NAMES` / `CMD_SOURCES` へ9件目のダミーを足し、**`sync.sh` を一切触らずに** `sync.sh --check bin` が赤くなること、配置を走らせると緑へ戻ることを確かめる。**案N ではこれが構造的に効く** — 母集団と検査が同じファイルに同居するので、`sync.sh` 側に追随の余地が無い。
- **(g) 母集団そのものが縮む故障の外部オラクル**（同）: `CMD_NAMES` の件数を `scripts/README.md:39` の列挙と突き合わせる。検査も対照も同じ正本から出ている以上、この行が無いと定義から6件消えた状態を2件で緑に回してしまう。
- **(h) 後片付け**: `$FIX` を消す。

#### 案N 固有の陽性対照（初版には無かった）

**プロセス境界が入った分、「委譲そのものが壊れる」経路を踏む必要がある。** §3.2.1 の実測が示したとおり、ここは黙って緑になりうる場所である。

- **(k) 子が rc=2 を返す**: `CMD_NAMES` を一時的に空にした状態で、`sync.sh --check bin` が緑にならないこと。**「母集団が空」が「差分なし」として通らないことの対照である。**
