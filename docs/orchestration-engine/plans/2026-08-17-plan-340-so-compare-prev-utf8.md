### 1.2 欠陥の再現（end-to-end）

`あ`（`E3 81 82`）を2000個並べた 6000 バイトのファイルを前回出力として置き、`--codex-only --prev` で回した。

```bash
python3 -c "import sys; sys.stdout.write('あ'*2000)" > "$PREV/codex-stdout.txt"
./scripts/so-compare.sh --codex-only --prev "$PREV" -o "$OUT" "テスト"
```

| 観測 | 値 |
|---|---|
| `so-compare.sh` の rc | 2（全プロバイダ失敗） |
| `prompt.txt` の UTF-8 妥当性 | **不正**（4093 バイト目 `0xE3` が invalid continuation byte） |
| `codex-stderr.txt` | `error: invalid UTF-8 was detected in one or more arguments` |
| `attempt_state` / `exit_code` | `finished` / `2` |
| `timeout_status` / `elapsed_seconds` | `error` / `0` |
| `stdout_bytes` | `0` |

**#270 の記録と完全に一致する。** `あ` は `E3 81 82` の3バイト文字で `4000 % 3 = 1` なので、`head -c 4000` は 1333 文字目まで（3999 バイト）を残したうえ、**1334 文字目の先頭1バイト（`E3`）だけ**を余分に残す。bash の `$(...)` はこの不正バイトをそのまま保持し、`prompt.txt` にも argv にも入る。

### 1.3 `exit 2` は原因の証拠にならない（陽性対照の足場を先に検証した）

NK `01M00KCCHNMFPHP5HAGX2DZ1MK` の適用として、対照の足場そのものを先に測った。**2つの落とし穴を実際に踏んだ。**

**落とし穴1 — `--help` は UTF-8 検証まで到達しない。** 最初に組んだ probe は `codex exec --help <不正バイト>` で、**rc=0 が返った。** ここで「codex は不正 UTF-8 を受け付ける」と読むところだった。`--help` が引数列の途中で短絡するためである。不正な引数を positional の先頭に置き `--help` を後ろへ回すと期待どおり落ちる。

**落とし穴2 — rc だけで判定すると偽陽性を通す。**

| probe | 引数 | rc | stderr |
|---|---|---|---|
| `codex exec <arg> --help` | 妥当な UTF-8 | 0 | （なし） |
| `codex exec <arg> --help` | **不正な UTF-8** | **2** | **`invalid UTF-8 was detected`** |
| `codex exec --nope-flag <arg>` | 妥当な UTF-8 | 2 | `unexpected argument` |
| `codex exec --nope-flag <arg>` | 不正な UTF-8 | 2 | `unexpected argument` |

**同じ `rc=2` が UTF-8 と無関係な理由でも返る。** したがって陽性対照の判定は rc ではなく **stderr の文字列**で行う（§5 の検証設計に反映した）。

この2行目の probe は**モデル呼び出しを伴わない**（引数解析の時点で落ちる）。対照を無償で何度でも回せる。

### 1.4 候補の実装手段をこの環境で実測した

NK `01KZVHE0KQ5VCX0SXH0F4SM14D` の適用として、「この環境の `cut` / `head` / `iconv` が何をするか」を先例の文面ではなく実測で確かめた。

| 手段 | 実測結果 | 使えるか |
|---|---|---|
| `cut -c 1-1333` | **行単位。** 5行の fixture では各行の先頭5文字が返る | **不可**（文書全体を切る意味にならない） |
| `awk substr($0,1,5)`（BSD awk 20200816） | **バイト単位。** `E3 81 82 E3 81` を返し不正 UTF-8 を作る。しかも行単位 | **不可** |
| `perl -CSD ... substr` | 1333 文字 = 3999 バイト・妥当・rc=0 | 可（新規依存） |
| bash `${var:0:1333}`（UTF-8 ロケール） | 1333 文字 = 3999 バイト・妥当 | 可（下記の前提つき） |
| bash `${var:0:1333}`（`LC_ALL=C`） | **1333 バイトで切れて不正 UTF-8** | ロケール依存 |
| `iconv -f UTF-8 -t UTF-8 -c` | 出力は正しい（4000 → 3999 バイト・妥当）が **rc=1**・stderr に `unexpected end of file; the last character is incomplete.` | 可（rc の手当てが要る） |

**`iconv` の rc=1 は `set -euo pipefail` の下で効く。** `so-compare.sh:5` は `set -euo pipefail` である。素のスクリプトとして次を実行すると、`step2` に到達せず rc=1 で死ぬ。

```bash
#!/usr/bin/env bash
set -euo pipefail
echo "step1"
prev=$(head -c 4000 "$f" | iconv -f UTF-8 -t UTF-8 -c 2>/dev/null)
echo "step2 reached"     # ← 到達しない
```

**この結論は一度言い過ぎて測り直している。** 対話シェル上の `( set -euo pipefail; ... )` では落ちなかった（`$( )` 内の subshell が `inherit_errexit` 無しでは errexit を継がないため）。so-compare.sh は先頭に `set -euo pipefail` を置いた素のスクリプトなので、そちらの形での観測を採った。

**`iconv -c` は妥当な入力に対して byte-identical な no-op である**（rc=0）。実測で確かめた。

| 入力 | サイズ | rc | 入出力の一致 |
|---|---|---|---|
| 実物のプロンプト（日本語・改行あり） | 8,356 B | 0 | `cmp` で同一 |
| 絵文字 / 4バイト文字 / 半角カナ混在 | 2,300 B | 0 | `cmp` で同一 |

4バイト文字（`𠮷` = `F0 A0 AE B7`）を 1 / 2 / 3 バイト目で切った場合も、`iconv -c` は部分列を落として妥当な出力（76 バイト）を返した。**2バイト・3バイト・4バイト文字のいずれの切断も同じ手当てで消える。**

### 1.7 `--prev` の byte 予算は意図的な設計ではない

`PREV_MAX_BYTES` を導入した commit は `49a1619`（`feat(verification): add consensus loop and iteration log to peer-ai-review`）で、`--prev` は peer-ai-review の合意ループを入れる作業の一部として「トランケート付きで自動追記」という粒度で足されている。**バイトを予算の単位に選んだ理由は記録されていない。** ただし `PREV_MAX_BYTES` は usage（`:34` / `:38`）に載った公開インタフェースなので、意味を黙って変えることはできない。

## 2. 何を直すのか（欠陥の構造）

不正な UTF-8 が `$PROMPT` に入る経路は3つある。

| # | 流入経路 | 実例の観測 | 現状の手当て |
|---|---|---|---|
| 1 | `--prev` の切り詰め（`:392`） | **あり**（#270） | なし |
| 2 | `-c` のコンテキストファイル添付（`:374`） | なし | なし（`cat` で全文・切り詰めない） |
| 3 | `-f` / stdin / argv のプロンプト本体（`:208` / `:297` / `:306`） | なし | なし |

経路2・3 は「入力そのものが不正な UTF-8 だった場合」にだけ起きる。**切り詰めが不正を作り出すのは経路1だけ**である。issue のスコープは経路1 に置かれている。

> **gate 2 で表現を訂正した。** 初版はここに「入力由来の不正は今回は触らない」と読める書き方をしていたが、**採用案の効果はそれより広い。** `head -c N` は N がファイルサイズより大きければ全文を返すので、**`iconv` は予算未満の前回出力に対しても必ず走る。** したがって「前回出力がもともと不正で、かつ予算未満」という入力に対して、今日は素通し（codex が死ぬ）だったものが、修正後は無害化される。
>
> **これは意図した副次効果として受け入れる**（消費者が codex の argv である以上、レーンが生き延びるほうがよい）。ただし黙って起きるのは避けるので、b7 は切り詰めが起きていないのに短くなった場合に警告を出す（§3）。**この経路の対照を C11 として足した**（§5.2）。
>
> 正確な言い方はこうである。**直すのは経路1が不正を作り出すことで、副次的に `--prev` の読み込み全体が無害化される。経路2・3 には触らない。**

## 3. 設計判断 DJ-1 — どこで、どう直すか

> **gate 2 で案が変わった。** 初版は下記の (b3)（`iconv` + `|| true` + `command -v` の preflight）で確定するつもりだった。**2レーンとも「そのまま確定するな」と返し、しかも代案が割れた。** 実測で両者の指摘を確かめたところ**どちらの指摘も正しかった**ので、両方を塞いだ形（b6）へ差し替えた。経緯は 3.5、owner に残る判断は 3.6。

> **gate 4 でもう一度変わった（b6 → b7）。** b6 は「無害化の失敗」を**出力が空かどうか**、「境界後退だけか」を**prefix かどうか**で判定していた。**2レーンが独立にどちらも双方向に誤ると指摘し、4件すべて再現した。** 経緯は 3.7。

**採る案: (b7) — 切り詰め直後に `iconv` を通し、成否を推測せず「実際に何バイト載ったか」を必ず伝える。**

```bash
# :392 付近
prev_raw=$(head -c "$PREV_MAX_BYTES" "$prev_file")
# iconv は末尾が不完全な文字のとき rc=1 を返すが、出力は正しく不正バイトを落としている。
# set -euo pipefail 下で落ちないよう rc を握り潰す（握り潰しが掛かるのは
# printf | iconv のパイプラインだけで、head は別行なので errexit に残る）。
prev_content=$(printf '%s' "$prev_raw" | iconv -f UTF-8 -t UTF-8 -c 2>/dev/null) || true
raw_bytes=$(printf '%s' "$prev_raw"      | wc -c | tr -d ' ')
prev_bytes=$(printf '%s' "$prev_content" | wc -c | tr -d ' ')
orig_size=$(wc -c < "$prev_file" | tr -d ' ')

if (( raw_bytes > 0 && prev_bytes == 0 )); then
    # 原因を断定しない（前回出力が UTF-8 でない / 上限が 1 文字の幅より小さい /
    # iconv の失敗 のいずれもありえ、出力からは区別できない）
    echo "Warning: 前回出力から妥当な UTF-8 が得られませんでした（…のいずれか）: $prev_file" >&2
elif (( orig_size <= PREV_MAX_BYTES && prev_bytes < raw_bytes )); then
    # 切り詰めが起きていないのに短くなった＝前回出力そのものが不正だった
    echo "Warning: 前回出力に不正な UTF-8 が含まれていたため $((raw_bytes - prev_bytes)) バイトを落としました: $prev_file" >&2
fi
if (( orig_size > PREV_MAX_BYTES )); then
    # 第 2 項は上限ではなく実際に載ったバイト数
    prev_content="${prev_content}"$'\n\n[... truncated: '"${orig_size}"' bytes -> '"${prev_bytes}"' bytes ...]'
fi
```

**b6 から落としたもの**: 空を根拠にした `exit 1`（正しい空を誤って止める）と prefix 判定（元から不正な末尾を見逃す）。**足したもの**: 実バイト数の記録と、空になったときの原因を断定しない警告。

`iconv` の存在確認は `--prev` の非空ファイルを処理する時点で行う（`exit 1`）。**予算未満の前回出力にも `iconv` は走るので、確認範囲も「非空の `--prev`」全体に掛かる** — §2 で受け入れた副次効果と整合する。初版のコメントは「実際に切り詰める対象が在ると分かった時点で」と書いていたが、**実際には切り詰めの有無を見ていない**（gate 4 の指摘）。コメントを実態に合わせた。

**`head` と `iconv` を2行に分けているのは意図的である。** 1本のパイプラインに書くと `|| true` が `head` の失敗まで握り潰す。分ければ `head` は errexit の対象のまま残り、握り潰しの対象が `iconv` の rc だけに狭まる。実測で確かめた。

| 書き方 | 正常系（`あ`×2000, N=4000） | 存在しないファイルを渡したとき |
|---|---|---|
| 1行（`head \| iconv … \|\| true`） | 妥当・3999 B | **rc=0**（`head` の失敗が消える） |
| **2行（採用）** | 妥当・3999 B | **rc=1**（`head` の失敗が残る） |

`printf` は shell builtin なので `exec` を経ず、argv 長の制限を受けない（guard-candidate `01KYA7C9MWDKQK79FGDWRC8W6H` の趣旨に沿う）。

### 3.0 切り詰め表示について（判断を変えた）

初版は `:394-395` の `[... truncated: X bytes -> N bytes ...]` のズレ（最大3バイト）を許容すると書いた。**gate 2 の claude レーンが、ズレの許容は (1) の guard を入れるかどうかに従属すると指摘した。** 実測で確かめた。

guard を入れないと、`iconv` が在って失敗したときに `prev_content` が空になる一方で `orig_size > PREV_MAX_BYTES` は成立するので、**中身が0バイトなのに `[... truncated: 6000 bytes -> 4000 bytes ...]` と書かれたプロンプトが3レーン全部へ配られる。** rc は 0、警告も出ない。

````text
### 前回の codex の回答
```

[... truncated: 6000 bytes -> 4000 bytes ...]
```
````

**「ずれる」ではなく「嘘をつく」である。**

> **gate 4 で解き方を変えた。** ここでは「guard で hard error にすれば嘘は消え、残るのは 1〜3 バイトのズレだけ」と書いていたが、**その guard 自体が誤判定する**ことが gate 4 で分かった（3.7）。**採ったのは注記の第2項を実バイト数にする案**で、これなら guard の有無に依らず嘘が構造的に作れない。ズレを許容するかどうかを判断する必要そのものが消えた。

### 3.5 gate 2 で何が起き、なぜ b6 になったか

**2レーンとも「DJ-1 を現状のまま確定するな」と返した。指摘の中身は次の点で一致していた。**

- `command -v iconv` の preflight は**不在しか見ない**。自分が §4.3 で作った赤は「在って失敗する」ケースだったので、**診断と処方が食い違っていた。** これは実測で確認した（上の「嘘をつく」プロンプト）。
- 5つの合格主張には**下限が無い**。「先頭だけ残す」実装が全部通る。
- **P4 の修正前 baseline が P1 で取られていない。**
- **新しく足す preflight 分岐を叩く対照が1つも無い。**

### 3.1 なぜこれか（4つの理由）

**理由1 — 根で直る。** 不正な UTF-8 を**作り出している**のは切り詰めだけである（§2）。ここを直せば作り出しは止まる。

**理由2 — ロケールに依存しない。** `iconv -f UTF-8 -t UTF-8 -c` はロケールを見ない。4環境（`ja_JP.UTF-8` / `C` / `C.UTF-8` / `env -i`）すべてで 3999 バイト・妥当を返す（4.2・episode の実測表）。文字予算に切り替える案（a1）は `LC_ALL=C` で不正を出し、UTF-8 ロケールでは予算を最大3倍超える。**採用案が持ち込むロケール依存はゼロである。**

**理由3 — 妥当な入力に対して byte-identical な no-op である。** 8,356 バイトの実物プロンプトと、絵文字・4バイト文字・半角カナを含む 2,300 バイトで `cmp` 一致・rc=0 を確認した（§1.4）。**`--prev` を使う既存経路の出力が1バイトも変わらない。** 配布物が全セッションへ即時反映される本件では、これが決め手になる。

**理由4 — 判定経路に触らない。** 変更は `--prev` の処理ブロック内に閉じる（切り詰め2行 + バイト数の記録 + 2種類の警告 + `iconv` の存在確認）。**レーンの起動経路（`:774` / `:851` / `:928`）にも `classify_result()` にも meta の書き出しにも触らない。** 初版の b3 に比べると行数は増えたが、増えた分はすべて「起きたことを伝えるための記録」であって、正常系の振る舞いは変えていない。**b6 が持っていた空ガードと prefix 判定は gate 4 で撤去した**（3.7）。

#### 3.2.1 `iconv` がキャラクタデバイスへ出力すると妥当な入力でも rc=1 になる（再現手順つき）

> **gate 3 で差し戻された項目である。** 初版は「stdout が `/dev/null` なら妥当な入力でも rc=1」と書いたが、**統括の環境では同じ `/usr/bin/iconv` で4通りすべて rc=0** だった。条件を切り分けたので手順を添える。

発火条件は**3つの積**である。ひとつでも欠けると起きない。

1. stdout が**キャラクタデバイス**である（`/dev/null` / `/dev/zero`）。実ファイルやパイプでは起きない。
2. 入力に**マルチバイト文字が含まれる**。ASCII だけならサイズを問わず起きない。
3. そのマルチバイト内容が **1024 バイトを超える**。

最小の再現手順。

```bash
# 発火する（あ×342 = 1026 バイト・すべて妥当な UTF-8）
python3 -c "import sys; sys.stdout.write('あ'*342)" > /tmp/mb.bin
iconv -f UTF-8 -t UTF-8 /tmp/mb.bin > /dev/null; echo "rc=$?"
#   => rc=1   iconv: iconv(): Inappropriate ioctl for device

# 発火しない（1バイト少ない・あ×341 = 1023 バイト）
python3 -c "import sys; sys.stdout.write('あ'*341)" > /tmp/mb2.bin
iconv -f UTF-8 -t UTF-8 /tmp/mb2.bin > /dev/null; echo "rc=$?"   # => rc=0

# 発火しない（同じ内容でも出力先が実ファイル or パイプ）
iconv -f UTF-8 -t UTF-8 /tmp/mb.bin > /tmp/out.bin; echo "rc=$?"          # => rc=0
iconv -f UTF-8 -t UTF-8 /tmp/mb.bin | cat > /dev/null; echo "rc=$?"       # => rc=0

# 発火しない（ASCII ならサイズを問わない）
python3 -c "import sys; sys.stdout.write('a'*12288)" > /tmp/as.bin
iconv -f UTF-8 -t UTF-8 /tmp/as.bin > /dev/null; echo "rc=$?"             # => rc=0
```

二分探索した境界は **`あ`×341（1023 B）で rc=0 / `あ`×342（1026 B）で rc=1** である。

**統括の環境で再現しなかったのは、条件2または3を満たさない入力で測ったためだと考えられる**（推測）。機序は「1KB のバッファを超えて2回目の write に入るとき出力 fd へ ioctl 相当を行い、キャラクタデバイスで ENOTTY になる」あたりだと思われるが、**機序は未確認**である。上の表と境界までが検証済みである。

**§9 で「壊れた計測器」の1つに挙げたのと同じ事実である。** 初版はここで環境の事実として断定し、§9 では自分の測り損ねとして挙げていて、書き方が矛盾していた（gate 3 の指摘どおり）。**同じ1つの事実の裏表である** — iconv が実際にそう振る舞い、その振る舞いのせいで `/dev/null` を使った自分の (c) prototype が全 fixture で fallback へ落ちた。

**採用案 b7 はこの事実に依存していない**（`-c` を付けてパイプで受けるので条件1を満たさない）。したがって実装には影響しない。

## 4. 探索木（gate 1・確定前の証跡）

### 4.1 候補 (d) は本件を直さない — 実測で落ちた

brief は「(d) を採ると本件と ARG_MAX の両方が根で消える可能性がある」とし、**費用と効果を gate 2 で測れ**と指示していた。効果のほうを先に測った。

`codex exec` は stdin からの入力に対応している（`--help` に「instructions are read from stdin. If stdin is piped and a prompt is also provided, stdin is appended as a `<stdin>` block」とある）。そこへ不正なバイトを含む短い指示を流した。

```
$ printf 'Reply with exactly: OK\n<不正バイト>' | codex exec --sandbox read-only
Failed to read prompt from stdin: input is not valid UTF-8 (invalid byte at offset 23).
Convert it to UTF-8 and retry (e.g., `iconv -f <ENC> -t UTF-8 prompt.txt`).
rc=1
```

**codex は経路に関係なく UTF-8 を検証する。** したがって次の2つが言える。

- **効果**: (d) は**本件を直さない**。消えるのは ARG_MAX の族だけである。しかも失敗の署名が変わる（argv 経路は `exit 2` + `invalid UTF-8 was detected in one or more arguments`、stdin 経路は `exit 1` + `input is not valid UTF-8`）ので、**(d) を単独で採ると現行の検出条件が外れたまま欠陥が残る**という悪い方向にも働く。
- **費用**: 起動箇所は3つ（`:774` codex / `:851` claude / `:928` cursor）で、行数だけなら各1行である。ただし `if timeout ... ; then` をパイプラインに変えると exit code の取り方が `pipefail` 経由になり、レーンごとに CLI の stdin 意味論を確かめ直す必要がある（codex は prompt 引数と併用すると `<stdin>` ブロックとして追記されるので併用不可、cursor は `nohup` 越し）。**3レーンすべての判定経路に触る。**

**費用が高く効果が本件に届かないので、(d) は本件の解として採らない。** ARG_MAX 側の関心（guard-candidate `01KYA7C9MWDKQK79FGDWRC8W6H`）は §7 に scope 外として残す。

**副産物として、codex 自身のエラーメッセージが `iconv` を推奨している。** 直し方の方向に外部からの裏づけがある。

|---|---|---|---|
| `master`（`head -c` のみ） | **不正**・4000 B | **不正**・3999 B | 妥当・4000 B |
| A: `iconv -c` + `\|\| true` | 妥当・3999 B | 妥当・3996 B | **妥当・4000 B（無変更）** |
| A': `iconv -c`（rc 未処理） | **rc=1 で死亡・出力 0 B** | **rc=1 で死亡・出力 0 B** | 妥当・4000 B |
| P: 先例2 の `{ iconv -c \|\| cat; }` | 妥当・3999 B | 妥当・3996 B | 妥当・4000 B |
| B: bash `${raw:0:N}`（文字予算） | 妥当だが **6000 B** | 妥当だが **6000 B** | 妥当だが **7958 B** |

読み取れることが3つある。

- **A' が実際に死ぬ。** rc を握り潰さない書き方は `set -euo pipefail` の下でスクリプトごと落ちる（§1.4）。
- **B は予算が壊れる。** 「4000」のつもりが日本語で 6000 バイト、実物のプロンプトで 7958 バイトになる。**先例1（`knowledge-list.sh`）から移らない前提は予算の単位だった**、というのが数字で出た。プロンプト肥大を 50KB で警告する設計（`:414`）と衝突する。
- **A と P は出力が同じに見える。** 差は iconv が失敗したときにだけ現れる（次項）。

### 4.3 先例2 を verbatim で写すと欠陥が黙って戻る

A と P の差を切り分けるため、stdin を読まずに `exit 1` する iconv の stub を PATH の先頭に置いて測った。

| 書き方 | iconv 正常時 | **iconv が読まずに失敗したとき** |
|---|---|---|
| A: `… \|\| true` | 妥当・3999 B | **空**（前回出力が黙って落ちる） |
| P: 先例2 の `… \|\| cat` | 妥当・3999 B | **不正・4000 B（欠陥が戻る）** |

stub を外した対照では両方 3999 バイトで妥当なので、**赤の理由は stub が効いていることであって足場の破壊ではない**（NK `01M00KCC…` の教訓1）。

`|| cat` の意味は「iconv が使えなければ無害化せず素通しする」である。**先例2 の消費者は pane のタイトルなので、化けても表示が崩れるだけ**で素通しでよい。本件の消費者は codex の argv で、**素通しはレーン1本の即死に戻る。** NK `01KZVHE0KQ5VCX0SXH0F4SM14D` の予測どおり、先例では安全な手順が移植先で故障を隠した。

**A も理想ではない** — iconv が失敗すると前回出力が黙って消える。前提の差分を埋めるなら、iconv の可用性を preflight（`:336-352` に既存の同型がある）で確かめ、無害化に失敗したときに黙って進まない形にする必要がある。

## 5. 検証設計（受け入れ条件の落とし込み）

**この節は採用案に依らない。** どの案を採っても同じ対照で判定できるように組んである。

### 5.1 判定に使う観測（rc を根拠にしない）

| 主張 | 観測する対象 | 合格条件 |
|---|---|---|
| **切り詰めが不正 UTF-8 を作らない** | **stub が記録した argv** を UTF-8 としてデコード | 成功する |
| 切り出した部分が予算を超えない | argv 中の前回出力部のバイト長 | `PREV_MAX_BYTES` 以下 |
| スクリプトが死んでいない | `so-compare.sh` 自身の rc と `codex-stderr.txt` の存在 | rc が想定どおりでファイルが在る |
| codex レーンが即死しない | `codex-stderr.txt` | `invalid UTF-8 was detected` を**含まない** |
| codex レーンが正常に返った | `codex-meta.txt` | `attempt_state=finished` かつ `exit_code=0` かつ `timeout_status=success` かつ `stdout_bytes>0` |

**主たる証拠は `prompt.txt` ではなく argv である。** 初版は `prompt.txt` を主証拠に置いていたが、これは `:410` が書く別の成果物で、codex が受け取る argv（`:774`）ではない。両者は同じ変数から作られるという実装上の偶然で一致しているだけなので、修正の置き場によっては偽陽性にも偽陰性にもなる（塞ぎ方は 5.2.1）。

`codex-meta.txt` は受け入れ条件1（レーンが正常に返る）を裏づけるもので、NK `01KYMRE1N7N0J8VP3CBZZEZ8Q3` に従い「緑」ではなく meta の値で確かめる。

### 5.2 陽性対照と陰性対照（NK `01M00KCC…` の適用）

fixture は3種類作る。**いずれも切断位置が文字の途中に来るように、文字幅と上限の剰余から逆算して作る。**

| fixture | 内容 | 切れ方（実測） |
|---|---|---|
| F1 | `あ` × 2000（3バイト文字・6000 B） | 既定 4000 で `4000 % 3 = 1` → 先頭1バイトだけ残る（不正） |
| F2 | `𠮷` × 1500（4バイト文字・6000 B） | **既定 4000 では `4000 % 4 = 0` でちょうど境界に当たり不正にならない。** `PREV_MAX_BYTES=3999` で3バイト分の部分列が残る（不正）。4001 / 4002 でも不正になることを確認済み |
| F3 | ASCII と日本語の混在（境界位置が自明でないもの） | **既定 4000 では偶然きれいな境界に当たり陽性にならない。** `PREV_MAX_BYTES=3993` で漢字の途中に落ちる（不正） |

**F2 は「既定値のままでは陽性にならない」ことを先に測って分かった。** 上限と文字幅の剰余が 0 になる組み合わせでは欠陥が現れない。fixture を作ってから「赤が出ないので直っている」と読む余地があるので、**各 fixture について修正前に赤が出ることを先に確かめてから修正へ進む。**

F4 として **2レーン分の fixture**（`codex-stdout.txt` と `claude-stdout.txt` の両方）も作る。`--prev` のループは `codex` → `claude` → `cursor` の順で回る（`:389`）ため、1本だけだと不正バイトが常に `$PROMPT` の終端側に来る「末尾」ケースしか踏まない。**不正バイトの直後に別の見出しが続く「中間」ケースを測るには2本要る。**

| # | 対照 | 版 | 期待 | 何を切り分けるか |
|---|---|---|---|---|
| C1 | F1 + 既定 4000 | **修正前** | argv 不正・stderr に `invalid UTF-8` | 欠陥が生きていること（陽性対照） |
| C2 | F1 + 既定 4000 | **修正後** | argv 妥当・切り出し部が予算以下 | 修正が効くこと |
| C3 | F1 + `PREV_MAX_BYTES=3998` | **修正前** | 妥当 | **赤の原因が「切断位置」であること**（上限や日本語一般ではない）。**3999 ではない** — fixture 先頭の sentinel 17 バイトのぶんずれるので、実測で切れ方を列挙してから選んだ |
| C4 | ASCII のみの前回出力 + 既定 4000 | 修正前 / 修正後 | 両者の argv が**バイト一致** | `--prev` の既存挙動を変えていないこと |
| C5 | `--prev` なし | 修正前 / 修正後 | 両者の argv が**バイト一致** | 受け入れ条件3（非 `--prev` 経路の無回帰） |
| C6 | F2 / F3 / F4 | 修正前 / 修正後 | 修正前は不正・修正後は妥当かつ予算以下 | 3バイト以外の幅と「中間」位置でも消えること |
| C7 | F1 を `LC_ALL=C` / `env -i` で | 修正前 / 修正後 | 修正後はロケールに依らず妥当 | 採用案がロケール依存を持ち込んでいないこと |
| C8 | F1 + **本物の codex**（stub なし） | **修正後** | meta が `exit_code=0` / `timeout_status=success` / `stdout_bytes>0` | 受け入れ条件1（レーンが正常に返る） |

- **C3 が偽陽性への効き所である。** C1 が赤いだけでは「日本語を渡すと赤い」までしか言えない。C3 が緑になって初めて「赤の理由は切断位置である」と言える。
- **C4 / C5 のバイト一致が回帰の主たる証拠である。** ここでも「動いたから良し」ではなく `cmp` の結果で判定する。
- 足場は**測りたい対象と同じ場所に置く**（NK `01M00KCC…` の教訓2）。fixture は worktree の `tmp/` に置き、`scripts/so-compare.sh` は動かさない。`-o` で出力先だけを分ける。
- **すべての対照で `./scripts/so-compare.sh` と明示的なパスで呼ぶ。** 素の名前 `so-compare` は主 checkout の版を指す（§1.5）ので、worktree の中に居ても「修正後」のつもりで master を測ってしまう。実行したパスを記録に残す。

### 5.2.1 判定の穴を3つ塞ぐ

gate 1 のレーンが陽性対照の設計に穴を指摘した。実測で確かめて反映した。

**穴1 — `prompt.txt` は argv ではない。** `prompt.txt`（`:410`）と codex が受け取る argv（`:774`）は別の成果物で、同じ変数から作られるという実装上の偶然で一致している。修正を書き出し側だけに入れれば偽陽性、レーン起動の直前に入れれば偽陰性になる。

**塞ぎ方（生産コードは1行も変えない）。** `CODEX_CMD="codex"` は PATH 解決なので、**argv を記録するだけの `codex` stub を PATH の先頭に置く**。実測で成立を確認した。

| 観測 | 値 |
|---|---|
| stub が捕まえた argv | 4145 B・不正（position 4093） |
| 同じ実行の `prompt.txt` | 4146 B・不正（position 4093） |
| 差 | 末尾の改行1バイトのみ（`echo` が足す分） |
| 足場の健全性 | meta に `cli_version=codex-cli 0.0.0-stub` が残り、stub が呼ばれたことを示す |

stub はモデルを呼ばないので、**C1〜C7 を無償で何度でも回せる**うえ、主張の対象が argv そのものになる。**C8 だけは本物の codex で回す**（stub では「レーンが正常に返る」を主張できない）。

**穴2 — 存在しないファイルへの `grep` は `!` を付けると必ず通る。** `! grep -q 'invalid UTF-8' "$OUT/codex-stderr.txt"` は、ファイルが無い場合も合格する。採用案が `set -euo pipefail` の下でスクリプトを殺せば（1.4）codex は一度も起動せず、**「修正がスクリプトを殺した」という最悪の結果が緑で通る**。判定には (1) `so-compare.sh` 自身の rc、(2) `codex-stderr.txt` の存在、(3) grep の結果 の3つを別々に主張する。

**穴3 — 「妥当だが予算超過」を捕まえられない。** C2/C6 に「妥当である」しか書かないと、文字数で切る案（`${var:0:N}`）が 4バイト文字で 1333 文字 = 5332 バイトを出しても緑になる。**すべての対照に「切り出した部分のバイト長 ≤ `PREV_MAX_BYTES`」を第2の主張として足す。**

**穴4（最重要・両レーンのうち codex だけが指摘）— 「内容を全部捨てる」修正も緑で通る。** 上の3つを塞いでも、**`--prev` の内容を丸ごと空にする実装は「argv は妥当」「予算内」「レーンは成功」をすべて満たす。** これは架空の懸念ではない — 有力案 A（`|| true`）は iconv が失敗したときに実際に空を返す（4.3 の実測）。

**塞ぎ方: sentinel。** fixture の前回出力に、**切り詰め後も必ず残る位置**（先頭付近）へ一意な識別子を埋め、**その識別子が実 argv に出現すること**を合格条件に足す。埋める位置は「予算の内側」でなければならないので、fixture の先頭から数十バイト以内に置く。

**穴5（gate 2・両レーン）— 合格主張に下限が無い。** sentinel は予算の内側（先頭から数十バイト以内）に置くので、**「先頭 100 バイトだけ残す」実装が4つの主張を全部満たす。** 穴4 が塞いだのは「全部捨てる」だけで、「ほとんど捨てる」は素通しする。

**塞ぎ方: 長さの下限を主張に足す。** 元 fixture が妥当な UTF-8 である限り、失われるのは末尾の不完全な1文字ぶん＝最大3バイトである。したがって

```
PREV_MAX_BYTES - 3 <= 切り出し部のバイト長 <= PREV_MAX_BYTES
```

を主張にできる。**この境界は案の選別にも効く** — `${var:0:N}` 案は上限側で落ち、行単位の (f) 案や「1行だけ残す」実装は下限側で落ちる。

**穴6（gate 2・claude）— F4 の sentinel が1個だと中間の欠落を検出できない。** F4 を置いた目的は「不正バイトの直後に別の見出しが続く中間ケース」なのに、sentinel が `codex-stdout.txt` の先頭にだけ在ると、**`claude` の節を丸ごと落とす実装が緑で通る。** `--prev` のループが回る `codex` / `claude` / `cursor` の各ファイルに**別々の sentinel** を埋め、argv に**全部**出現することを条件にする。

これで最低限の合格主張は6つになる。

1. 修正前の同一 fixture・同一の呼び出しで**赤**（欠陥が生きている）
2. 修正後の実 argv が**妥当な UTF-8**
3. 切り出した部分が**予算以下**
4. ~~切り出した部分が**予算 − 3 バイト以上**（下限）~~ → **gate 4 で撤回した。5.2.4 参照**
5. **各レーンファイルの sentinel が全部 実 argv に残っている**
6. レーンが**実際に成功して返る**（C8・本物の codex）

### 5.2.4 主張(4)「予算 − 3 バイト以上」は不変条件ではなかった（gate 4 で撤回）

gate 4 の claude レーンが指摘し、fixture を作って再現した。**コマンド置換は末尾の改行を「すべて」落とす。** 修正前は切断点に不完全な文字が残っていたおかげで手前の改行が末尾に来ず、削られなかった。修正後は `iconv` が不完全な文字を落とすので、**それまで隠れていた改行が末尾に露出して一緒に削られる。**

切断点(4000)の直前を `\n\n\n` にした fixture（F11）で測ると、**損失は 4 バイト**（不完全な文字1バイト + 改行3バイト）だった。**予算 − 3 を下回るので、正しい実装が主張(4)で落ちる。**

`あ`×2000 のような改行を含まない fixture では当たらない。**SO の実出力（段落間に空行が入る日本語）を fixture にすると当たる。** つまり主張(4)は「今の fixture では成り立つ」だけで、不変条件ではなかった。

**代わりに使う主張**: 切り詰め注記の第2項が**実際に載ったバイト数**を印字するようになったので（§3 の改訂）、その値をそのまま下限の観測に使う。固定の下限を置くのをやめた。

### 5.2.2 gate 2 で足した対照（新しい分岐を1つも未実行のまま PR にしない）

初版は P2 で preflight を1ブロック足すのに、完了判定が `shellcheck` の rc=0 だけだった。**新規に書いたコードが一度も実行されないまま PR になる。** しかもこの分岐を誤ると、マージと同時に全セッションの `--prev` が止まる。

| # | 対照 | 期待 | 何を切り分けるか |
|---|---|---|---|
| C9 | `iconv` を PATH から外して **`--prev` あり** | 想定のエラーで停止し、**レーンが1本も起動していない**（`OUT_DIR` に `*-stderr.txt` が無い） | 新しい失敗経路が意図どおり発火する |
| C10 | `iconv` を外して **`--prev` なし** | 正常に通る | 過剰な abort に対する回帰 |
| C11 | **予算未満で内部が不正**な前回出力 | argv 妥当・sentinel 残存・**警告が出る** | §2 の副次効果が意図どおり働き、黙っていないこと |
| C12 | `--prev` のディレクトリが存在しない / 空 / stdout が空 | 現行どおり**警告して続行**（abort しない） | preflight の遅延が効いていること |
| C13 | `iconv` が**在って `exit 1`** する stub 下 | **rc=0 で続行**し、注記が実バイト数（`6017 -> 0`）を書き、警告が出る | 3.0 の「嘘をつく」経路が塞がれたこと。**b7 では停止しない** — 空を失敗の根拠にしないため（3.7） |

gate 4 の後にさらに4本足した。

| # | 対照 | 期待 | 何を切り分けるか |
|---|---|---|---|
| C14 | 前回出力が**丸ごと非 UTF-8** | argv 妥当・警告が出る | `iconv` が正常に働いて全部落とす経路（C13 の stub 経路とは別） |
| C15 | 切断点の**直前が改行の連続** | argv 妥当・注記が実バイト数 | 損失が3バイトを超えること（5.2.4） |
| C16 | `PREV_MAX_BYTES=1`（1文字の幅より小さい） | **rc=0**・注記 `30 -> 0`・警告 | 正しい空で誤って停止しないこと |
| C17 | **部分出力して `exit 1`** する `iconv` stub | argv 妥当・注記が実バイト数（`6017 -> 3`） | 嘘の注記が出ないこと |

**C16 と C17 は gate 4 の HIGH 指摘に対応する。** b6 はこの2つで誤判定していた。

**C13 が最も重要である。** これは §4.3 で自分が見つけた赤に対応する対照で、初版の設計にはこれを塞ぐ処方が無かった。**b6 ではここを `exit 1` で塞ごうとして誤判定を招き、b7 で「止めずに真実を書く」へ変えた。**

### 5.2.3 stub の足場を固くする

gate 2 の claude レーンが1点指摘した。`cli_version_for()` は `timeout 5 "$cmd" --version` を呼ぶので、**stub の `--version` 分岐が argv 保存より前に return していないと、捕捉した argv が `--version` で上書きされる。** 現行の stub は先に return しているので問題は起きていないが、気づけるように足場の健全性チェックへ「捕捉した argv が 1000 バイト超であること」を入れる。

codex レーンは「4145 対 4146 の差は stub が改行を足している証拠だ」と読んだが、**これは逆である。** 実測すると `prompt.txt == argv + LF` がバイト単位で成立した。改行を足しているのは `:410` の `echo "$PROMPT"` のほうで、stub は `printf '%s'` なので足していない。ただし C4 / C5 のバイト一致主張のために、**stub には argc と NUL 区切りの全 argv も保存させる**（codex の提案のうちこの部分は採る）。

- **C3 が偽陽性への効き所である。** C1 が赤いだけでは「日本語を渡すと赤い」までしか言えない。C3 が緑になって初めて「赤の理由は切断位置である」と言える。
- **C4 / C5 のバイト一致が回帰の主たる証拠である。** ここでも「動いたから良し」ではなく `cmp` の結果で判定する。
- 足場は**測りたい対象と同じ場所に置く**（NK `01M00KCC…` の教訓2）。fixture は worktree の `tmp/` に置き、`scripts/so-compare.sh` は動かさない。`-o` で出力先だけを分ける。

### 5.3 モデル呼び出しのコスト

C1 はモデルを呼ばない（引数解析で落ちる）。C3 / C4 / C5 / C2 は codex レーンが実際に走る。**プロンプト本体を1行（例: `1+1 は?`）にして所要を短く抑える** — 検査しているのは `--prev` の切り詰めであって回答の質ではない。

### 5.4 静的検査

```bash
shellcheck scripts/so-compare.sh
```

master 時点で通ることを先に確認し、変更後も通ることを確認する（**変更前の状態を対照として取る** — 元から出ている指摘を自分の変更のせいだと誤読しないため）。

## 6. step 構成

S-2（owner の gate 3 通過後）で実行する。**各 step は独立に検証できる粒度で切ってある。**

| # | 内容 | 完了の判定 |
|---|---|---|
| P0 | 対照の足場を作る。fixture（**レーンファイルごとに別 sentinel**）と argv 記録 stub（argc + NUL 区切り argv も保存）、判定スクリプトを worktree の `tmp/` に置く。**fixture の SHA-256 を記録する。** 足場を組むときの注意3つ — (1) 実体の解決に `command -v` を使わない（シェルの alias 定義が返り壊れた symlink になる。`type -P` を使う）。(2) `iconv` を隠す最小 PATH は「必要なコマンドを列挙」ではなく**実 PATH の全実行ファイルを鏡像化して `iconv` だけ落とす**（列挙は必ず漏れる）。(3) SO の `-o` は実行ごとに新しくする（前の実行が生きていると同じディレクトリで競合し証跡が汚れる） | stub を通した実行で argv が記録され、meta に `cli_version=...stub` が残り、捕捉 argv が 1000 バイト超 |
| P1 | **修正前の観測を全部取る**（C1・C3・C6 修正前・**C4 / C5 の修正前 argv**・C11 修正前・C13 修正前） | F1/F2/F3/F4 で argv が不正、C3 は妥当、**C4 / C5 の baseline argv がファイルとして保存済み** |
| P2 | 修正を入れる（`:392` の切り詰め2行 + バイト数の記録 + 2種類の警告 + `iconv` の存在確認） | `shellcheck scripts/so-compare.sh` が rc=0 |
| P3 | **修正後の緑を全 fixture で取る**（C2・C6・C7・C11・**C15**） | 合格主張を全 fixture で満たす。fixture の SHA-256 が P0 と一致 |
| P4 | 回帰を取る（C4・C5） | P1 で保存した baseline argv と `cmp` 一致 |
| P5 | 新しい失敗経路の対照（C9・C10・C12・C13・**C14・C16・C17**） | 各期待どおり。とくに C9 でレーンが1本も起動していないこと、C16 で誤って停止しないこと、C17 で注記が実バイト数になること |
| P6 | **本物の codex で1回通す**（C8） | meta が `exit_code=0` / `timeout_status=success` / `stdout_bytes>0` |
| P7 | gate 4（実装SO 弱2レーン）。**素の名前 `so-compare` で呼び master の版を使う**（§1.5） | 2レーンのうち1レーン以上が実返却 |
| P8 | episode の closure（マージ前）+ NK 3件への観測書き戻し | slot の item id と観測を足した id が一致 |
| P9 | PR 作成 + Copilot レビュー依頼。**PR 本文にマージ後の smoke 手順と revert 手順、および挙動変更（`iconv` 不在時に `--prev` が止まる）を明記する** | PR URL が出る |

**P1 を P2 より前に置いているのは意図的である。** 修正を入れてから対照を組むと、赤が出ないことを「直った」と読む余地が残る。**先に全 fixture で赤を確認し、その赤の理由（stderr の文字列 / argv の不正位置）まで記録してから修正へ進む**（NK `01M00KCCHNMFPHP5HAGX2DZ1MK`）。

> **gate 2 で P1 の中身を増やした。** 初版の P1 は「C1・C6 の修正前・C3」だけで、**C4 / C5 の修正前 argv を取っていなかった。** C4 / C5 は plan 自身が「回帰の主たる証拠」と呼んでいるのに、その baseline が P2（修正投入）より後にしか取れない位置に置かれていた。2レーンが独立に指摘した。**回帰の主証拠が、手順上いちばん取りこぼしやすい場所に在った。**

### 6.2 マージ後の実物を走らせる step がこの plan には無い

**この plan のどの step も、マージ後に実際に配られる状態のスクリプトを実行しない。** P7（gate 4）は意図的に master の旧版を使うので、新コードのカバレッジはゼロである。子はマージしない（親 / owner の gate 6）ので、**PR 本文に引き継ぎとして書く。**

- マージ直後の smoke: 日本語の大きい前回出力を1つ置いて `so-compare --codex-only --prev` を1回。meta が `exit_code=0`。
- 1行の revert 手順。
- 挙動変更の明示: **`iconv` が使えない環境で `--prev` を使うと新たに停止する。**

### 6.1 実装SO（gate 4）で自分の変更版を使わないこと

`~/bin/so-compare` は主 checkout を指すので（§1.5）、**P6 で素の名前を使えば自動的に master の版が走る。** 変更中の版は P1〜P5 の中でだけ `./scripts/so-compare.sh` として走らせる。**計測器（SO）と被測定物（変更した script）を分ける。** 実行したパスと `git rev-parse HEAD` を episode に記録する。
