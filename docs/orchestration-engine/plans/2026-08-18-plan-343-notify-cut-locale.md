## 1. 着手時の実測（master `b0a647a`・自分で測った）

環境は macOS 15（Darwin 24.6.0）/ bash 5.2.37 / `LANG=ja_JP.UTF-8` / `LC_ALL` 未設定。

**計測器を先に検証した。** 既知の妥当な入力（138 B）→ valid、既知の不正な入力（80 B 切り）→ INVALID を確認してから測定に入った。妥当性の判定は `iconv ... >/dev/null` を使わず、**実ファイルかパイプで受けて python で decode する**形にした（#340 で特定した `iconv` の偽 rc=1 を避けるため。brief の「もう1つの罠」）。

### 1.1 統括の実測との突合 — 食い違いは無かった

| 統括が brief に書いた事実 | 自分の観測 | 一致 |
|---|---|---|
| 該当行は `notify.sh:86` の `cut -c1-80` | 同じ | ○ |
| 日本語46文字（138 B）で `LC_ALL=C` → 81 B・不正 | 同じ（78 バイト目が不正の先頭） | ○ |
| 同じ入力で `ja_JP.UTF-8` → 138 B・妥当 | 同じ | ○ |
| 同じ入力で `C.UTF-8` → 138 B・妥当 | 同じ | ○ |
| 罠: `LC_ALL=C printf ... \| cut` では再現しない | 同じ（妥当 138 B が返る） | ○ |

**4件すべて再現した。罠も再現した。** 環境変数はパイプラインの最初のコマンドにしか掛からないので、`cut` のロケールを変えるには `printf ... \| LC_ALL=C cut` と書く必要がある。

### 1.2 追加で測ったこと

- **`LC_ALL=POSIX` も `C` と同じ**（不正 81 B）。
- **`cut -b` はロケールに依らずバイト単位。** つまり `C` ロケールでの `cut -c` は実質 `-b` に退化している。
- **`LC_ALL=en_US.UTF-8` は妥当**（138 B）。UTF-8 ロケールであれば名前は問わない。

**文字幅で再現が変わる。** gate 1 の claude レーンが「上限80は 1・2・4 で割り切れるが 3 では割り切れないので、再現するのは3バイト文字だけ」と指摘した。**測ると半分正しかった。**

| 入力（`LC_ALL=C`・上限80） | 結果 |
|---|---|
| `é`×100（2バイト） | **妥当**（80/2 = 40 で境界に当たる） |
| `あ`×100（3バイト） | **不正** |
| `🎉`×100 / `𠮷`×100（4バイト） | **妥当**（80/4 = 20 で境界に当たる） |
| ASCII×100 | 妥当 |
| **`a` + `é`×100** | **不正**（1バイトずれて 79/2 が割り切れない） |
| **`a` / `aa` / `aaa` + `🎉`×100** | **いずれも不正** |

**「3バイト文字だけ」ではなく「切断位置が文字の内側に落ちるかどうか」である。** 先頭に1バイト足すだけで2バイト文字も4バイト文字も再現する。**fixture は「幅」で選ぶのではなく、切断位置を実測で確かめて作る。**

### 1.3 到達可能性 — gate 1 で自分の見立てが崩れた

> **訂正。** 初版は「`msg` の元はアシスタント自身の発話なので日本語が既定＝内容の軸は起きる」と書いた。**gate 1 の2レーンが独立に、これは成り立たないと指摘した。コードを読み直して確認した。**

`msg` が計算されるのは `mode=wait` のときだけで（`:86`）、`done` は `:90` で `msg=""` に固定される。そして **Codex 経路は `:39` で `mode="done"` に固定される**ので、`:38` で取り出した `last-assistant-message` は**構造上 `cut` に到達しない。**

配線を読むと到達経路は1本だけである。

| 配線 | 到達するか |
|---|---|
| `claude.hooks.json:49` `Stop` → `notify.sh done` | しない（`msg=""`） |
| `claude.hooks.json:58-62` `Notification`（matcher `permission_prompt\|idle_prompt`）→ `notify.sh wait` | **する** |
| Codex `notify`（config.toml）→ JSON 経路 | しない（`mode="done"` 固定） |

**したがって `cut` に流れるのは Claude Code 自身が生成する入力待ちの通知文であって、アシスタントの発話ではない。** `:47` の `.message // .last_assistant_message` は fallback 付きなので、`.message` が無いペイロードなら発話が流れうるが、Notification hook は `.message` を渡す。

**発火には3条件の積が要る。** (1) 非 UTF-8 ロケール (2) `wait` 経路 (3) 通知文がマルチバイト。**初版が「内容の軸は起きる」と書いたのは誤りで、潜在性はむしろ強まった。**

**それでも直す。** 理由は次の2点に絞る。

1. `notify.sh` がロケールを自分で決めていないので、**挙動が外から与えられる値に従属している。**
2. 配布先が3ツールに広がっており（1.4）、**将来の実行環境を1つに固定できない。**

**「今日壊れている」とは書かない。** どの経路で `C` / `POSIX` が渡るかの実例は、自分も両レーンも観測できていない（§7）。

## 2. 何を直すのか

不正な UTF-8 が `body` に入る経路は、`msg` の切り詰め1箇所である。`branch` と `loc` は切り詰めていない（`loc` は `tmux display-message` の出力）。

`:100-101` の `tr -d '\033\007;'` は制御文字と `;` を落とすが、**不正なバイト列は落とさない**（`tr` の削除集合に入っていない）。したがって `msg` が不正なら `body` も不正のまま OSC 777 へ出る。

> **訂正（実測）。** 当初「原因は `cut` に限られる」と書いたが、**入力が不正な UTF-8 のときは `tr` もロケール依存である**（`C` は不正バイトを素通し / UTF-8 ロケールは `Illegal byte sequence` で以降を落とす）。`message` は `jq -r` 由来なので原則として妥当であり本件のスコープ外だが、断定は誤りだったので直した。

## 3. 設計判断 DJ-1 — どう切るか

**採る案: (E) — `cut -c1-80` を `jq -Rr '.[0:80]'` に置き換える。**

```bash
# :86
msg="$(printf '%s' "$message" | tr -d '\033\007' | tr '\n\r' '  ' | jq -R -r '.[0:80]' 2>/dev/null || true)"
```

**`2>/dev/null || true` を付けるのは gate 2 の指摘による。** `notify.sh` の既存の `jq` 呼び出しは4件（`:37` / `:38` / `:46` / `:47`）**すべてがこの形で揃っている**ことを確認した。付けないと5件目だけが素になり、古い `jq` や想定外入力で stderr にノイズが出る（advisory hook は入力待ちのたびに走る）。

### 3.1 なぜこれか（4つの理由・すべて実測に基づく）

**理由1 — ロケール依存が構造的に消える。** `jq` の文字列スライスは Unicode のコードポイント単位でロケールを参照しない。5環境で同一の結果になった。

| 環境 | 結果 |
|---|---|
| `LC_ALL=C` / `POSIX` / `ja_JP.UTF-8` / `C.UTF-8` / `env -i` | **すべて妥当・80文字（240 B）** |

対して master は `LC_ALL=C` で不正 81 B である。

> **この表は「パイプライン断片」の観測である**（gate 2 の指摘で明示）。`notify.sh` 全体を `env -i` で走らせると別の理由で落ちる（§5.3 の C11）。断片の観測とスクリプト全体の観測を混ぜない。
>
> **測定に使った `jq` は `jq-1.8.0` である。** 初版はバージョンを記録していなかった。「将来の実行環境を1つに固定できない」ことを修正の根拠にしている（§1.3）以上、測定器のバージョンを書かないのは一貫しないという gate 2 の指摘は正しい。

**理由1の補強（gate 2 で分かった）。** `jq` は**入力に不正なバイトがあれば U+FFFD へ置換する**。`cut` は素通しする。実測すると `a<0xFF>b` に対し `jq -Rr` は `61 ef bf bd 62`、`cut` は `61 ff 62` を返した。**つまり (E) は「切断で不正を作らない」だけでなく「入力が不正でも出力は妥当になる」** ので、初版の主張より強い。

**理由2 — 上限の意味を変えない。** 元の意図は「80**文字**」（1.7）で、`jq` のスライスもコードポイント単位なので**意図がそのまま保たれる。** #340 で採った `iconv -c` の形はここでは**80文字が26文字に縮む**（下記 3.2）。

**理由3 — 新しい実行ファイル依存が増えない。** `jq` は `notify.sh` の**既存の hard 依存**である（`:26` で不在なら `exit 0`・`message` 自体も `:38` / `:47` の `jq -r` で取り出している）。`iconv` を足す案は「不在時にどうするか」の判断を新たに生むが、この案は生まない。

> **ただし「機能レベルの依存」は増える**（gate 2 の両レーンが指摘）。文字列スライス `.[0:N]` は `jq` の初期版には無い。古い `jq` では既存の `.message` 抽出は動く一方で `.[0:80]` だけが失敗し、**`msg` が空になって通知本文が黙って消える**（rc=0 と stdout 無出力は保たれるので advisory 契約は壊れないが、機能が壊れる）。
>
> **gate 4 で決着した。両レーンが半分ずつ正しく、別のものを見ていた。**
>
> - **文字列スライスは jq 1.4 から動く**（`jq-1.4` の `jv_aux.c:78-85` が文字列添字を `jv_string_slice()` へ振り分け、`jv.c:725-779` が `jvp_utf8_next()` で歩く）。codex の主張が正しい。
> - **1.5 が要るのは `-Rr` という連結の書き方のほう**（`jq-1.4` の `main.c:40-45` は `strlen(text) == 2` で短オプションを判定するので3文字の `-Rr` は一致しない。連結は 1.5 の `main.c:83-99` から）。
>
> **したがって `-R -r` と分けて書けば下限は 1.4 まで下がる。** 初版のコメント（「文字列スライスは 1.5 以降」）は**結論は合っていたが根拠が誤り**で、その誤りが1文字ぶんの互換範囲を隠していた。**採用形を `-R -r` に変え、コメントも直した。**
>
> **版判定はレーンが引いたソースに依存している。** 古い `jq` は手元に無く自分では実行検証できていない（この環境の jq-1.8.0 では `-Rr` と `-R -r` の出力が同一であることのみ確認済み）。
>
> したがって理由3の主張は「**実行ファイル依存は増えず、対応版では advisory 契約を保つ**」に弱める。

**理由4 — ロケール probe が要らない。** 案 A（ロケールを強制する）は、存在しないロケール名が**無警告でバイト単位に戻る**ため（§4.2）「強制が効いたか」を実測する probe が要る。**この案はその工程ごと不要になる。**

#### 3.2.1 「既存の流儀に揃えるべき」という反論への回答（gate 2）

同じ repo の `session-name.sh:106` が `head -c 80 | iconv -c` を採っているので「流儀に揃えろ」という反論が成り立つ、と gate 1 の claude レーンが挙げていた。**gate 2 で答えが出た。**

`session-name.sh:106` の実体はこうである。

```bash
desired="$(printf '%s' "$desired" | tr -d '\000-\037\177' | head -c 80 | { iconv -f UTF-8 -t UTF-8 -c 2>/dev/null || cat; })"
```

- **`-f UTF-8 -t UTF-8` を明示している**のでロケール非依存である。
- **単位がバイトなのは意図的である。** 守っているのは tmux の pane title で、入力は branch 由来の slug（構造上ほぼ ASCII）なので 80 バイトで足りる。

**つまり2箇所は要件が違うから単位が違うのであって、流儀は破られていない。** 共有されている不変条件は「**出力が妥当な UTF-8 である**」ことであり、`head -c | iconv -c` という**機構**ではない。**(E) は同じ不変条件を、この箇所の単位（文字）を保ったまま満たす。** 不変条件と機構を分ければ反論は溶ける。

### 3.3 (H) を採らない理由（gate 2 で「範囲」から「中身」へ差し替えた）

> **訂正。** 初版は「(H) は技術的には E より優れている（ロケール依存の表面がゼロ・プロセス3つ減）。採らないのは範囲の広さだけ」と書いた。**gate 2 の2レーンが独立に、この自己評価は持たないと指摘した。** 実測して確かめたので、**棄却理由を中身に差し替え、owner への open question を取り下げる。**

(H) は `:47` の既存 `jq` に sanitize と切り詰めを畳み込み、`tr | tr | cut` を消す案である。

**(a) 「ロケール依存の表面がゼロ」は差にならない。** (E) を採ったあと `:86` に残るのは `tr -d '\033\007'` と `tr '\n\r' '  '` の2段だけで、**削除対象はすべて ASCII の単一バイトである。UTF-8 は self-synchronizing なので ASCII バイトが多バイト列の内側に現れることはない。** 妥当な UTF-8 に対して、この2段はロケールに依らず同じ結果を出す。

**(b) 唯一の差（不正入力時の `tr` のロケール依存）は到達しない。** `message` の出所は `wait` 経路では `:47` の `jq -r` だけである。**`jq` は生の不正バイトを U+FFFD へ置換して出す**（実測: `61 ef bf bd 62`）。孤立サロゲートは parse error になり `|| true` で `message=""` になる。**つまり `:86` に入る `message` は常に妥当な UTF-8 であり**、(H) の「jq を先に置けば以降の `tr` が不正バイトを見ない」という利点はこの経路では発現しない。

**(c) (H) には実質的な劣化がある。** `:47` は「`message` を取り出す」場所であって「表示用に整える」場所ではない。畳み込むと `message` が抽出値ではなく**表示用の80文字値**に変わる。**`notify.sh` の既存 `jq` 4件はすべて素の抽出で揃っている**（`.cwd // ""` / `.message // ...`）ので、1つだけ整形を持つのは規約から外れる。さらに Codex 側の抽出は `:38` の別の `jq` なので、**同じ `message` に2つの異なる健全化規約が並ぶ。**

**(d) 現行との同値性が崩れる入力がある。** 非文字列の `.message` に対し、現行と (E) は `jq -r` が文字列化するが、(H) の `gsub` は**型エラーで空に縮退する**（実測）。

| `.message` | 現行 / (E) | (H) | (H) の rc |
|---|---|---|---|
| `42` | `42` | **空** | 5 |
| `true` | `true` | **空** | 5 |
| `["a"]` | `[ "a" ]` | **空** | 5 |
| `{"k":"v"}` | `{ "k": "v" }` | **空** | 5 |
| `null` | 空 | 空 | 0 |

**(e) codex が挙げた末尾 LF の反例は再現しなかった。** codex は「末尾 LF で現行/E は `a`、H は `a ` になる」と書いたが、**前段の `tr '\n\r' '  '` が LF を空白へ変えるので、3者すべて `a ` になる**（実測: `"a\n"` / `"a\n\n\n"` / `"a\nb"` のいずれも現行 = E = H）。**指摘の結論（H を強く推すな）は (c)(d) で支持されるが、この具体例は成り立たない。**

**残る差はプロセス3つだけで、advisory hook が入力待ちのたびに1回走るだけなので意味のある差ではない。**

**したがって (H) は「抽出点に表示の関心を混ぜるので採らない」で正面から棄却する。** §6.2 の open question は取り下げた — **存在しないトレードオフを owner に裁定させると、plan 自身の推奨が弱く見える。**

## 5. 検証設計

> **gate 2 で2度目の作り直しをした。** 2レーンが独立に「**旗艦の対照（C11）が空で緑になる**」と指摘し、実測で確認した。あわせて「80文字 240 B」という固定の合格条件が fixture 依存で sentinel 設計と衝突していることも両レーンが挙げた。**構造を変える。**

### 5.1 判定に使う観測 — 主 oracle をバイト完全一致にする

| 主張 | 観測する対象 | 合格条件 |
|---|---|---|
| **内容が正しく切れている（主 oracle）** | OSC 列から抜いた `msg` 部 | **fixture から計算した期待バイト列と `cmp` で一致** |
| 通知が出ている | OSC フレームの個数 | ちょうど1つ |
| advisory 契約 | rc / stdout / **stderr** | rc=0・stdout 無出力・**stderr が修正前より増えていない** |
| 既存経路が回帰していない | `done` 経路・ASCII の `wait` 経路・空 `message`・制御文字入り | 修正前後で**バイト一致** |

**初版の「妥当な UTF-8 かつ ちょうど80文字 240 B」を主 oracle から降ろした。** 理由が3つある（gate 2 の指摘）。

1. **240 B は日本語100文字 fixture 専用の数字である。** `a` + `é`×100 の fixture では正しい期待値は `1 + 79×2 = 159 B` になる。固定値を仕様として書くと、実行中に「これは別の数字だった」と手当てすることになり、**#340 で踏んだ「期待した理由でその色が出たか」の型に戻る。**
2. **sentinel が80文字の予算を食う。** 先頭に ASCII n 文字の sentinel を置けば出力は sentinel + fixture の先頭 (80−n) 文字であり、「ちょうど80文字 240 B」と両立しない。
3. **先頭固定の sentinel は狙った偽陽性を捕まえない。** 初版 §5.4 は「日本語を全部落とす実装も妥当を満たすので sentinel を別 assert にする」と書いたが、**sentinel は ASCII で先頭にあるので、マルチバイトを全部落とす実装でも残る。**

**期待値は fixture から機械的に計算する。**

```bash
expected="$(python3 -c 'import sys;s=open(sys.argv[1],encoding="utf-8").read();sys.stdout.write(s[:80])' "$FIXTURE")"
```

**バイト完全一致は「妥当な UTF-8」「ちょうど80コードポイント」「内容が落ちていない」「切り詰めが消えていない」を1つの assert に畳み込む。** 妥当性・文字数・バイト数・sentinel は補助の assert に降ろす。

**「80文字」は正確には 80 Unicode コードポイントである**（gate 2 の指摘）。書記素ではないので、結合文字や ZWJ 連結が境界に来れば視覚上の1文字は割れる。**ただし UTF-8 としては妥当なので本件の欠陥は再発しない。** UTF-8 ロケール下の現行 `cut -c` も同じ単位なので**回帰ではない。** 79/80/81 文字の境界で `cut` と `jq` の出力がバイト一致することを実測で確認した（237 / 240 / 240 B）。

**sentinel の役割を分ける。** 配送確認専用の fixture（sentinel 入り）と、切り詰め正確性の fixture（バイト一致で見る）を別にする。

### 5.2 足場 — スクリプト全体を実際の経路で走らせる

1. **stdin に Notification hook 形式の JSON を渡し、引数は `wait` にする。**
2. **`notify.sh` を worktree の絶対パスで直接叩く。** 配備 symlink は主 checkout を指すので、叩くと修正前を測る（§1.4）。実行したパスを記録に残す。
3. **`TMUX` に任意の非空値、`TMUX_PANE` に固定値を与える。** これを忘れると `:62` と `:112` のゲートで fake `tmux` が一度も呼ばれず、**足場が丸ごと迂回される**（gate 2 の指摘）。
4. **`tmux` を fake に差し替え、`pane_tty` を一時ファイルへ向ける。**
5. **`cwd` を固定値にする（または渡さない）。** `branch` / `loc` は `git -C "$cwd"` と `tmux display-message` に依存するので、**両版で同一でないと「バイト一致」が取れない。**
6. **既知の sentinel が出力に載っていることを先に確かめる。** 載っていなければ配送されていないので「不正バイトが無い」ではなく「何も観測していない」である。**環境を弄る対照（C11 / C12）では、その環境ごとに sentinel 確認をやり直す**（既定環境での1回では効かない）。
7. **ロケールはスクリプトの起動に掛ける。** パイプラインの前段に掛けても伝わらない（§1.1 の罠）。`locale charmap` を先に記録する。
8. **Q0 で fixture の SHA-256・バイト長・コードポイント数・正規化形（NFC / NFD）を記録する。** `é` は NFC なら 2 B、NFD なら 3 B で、**C5 の期待が反転する**（実測: NFC は妥当・NFD は不正）。macOS はパス名を NFD へ正規化するので、**fixture をファイル名や `ls` の出力から作らない。**

**C11 を作り直した。** 初版は `env -i` だったが、**2レーンが独立に「空で緑になる」と指摘した。実測で確認した。**

**したがってロケール変数だけを消す形にする。** `HOME` 未設定という軸は C11 から切り離し、**§7 に out-of-scope の観測として残す。**

**C14 を足した。** これが gate 2 の最も重い追加である。`notify.sh:120-131` の fallback は `terminal-notifier -title "$title" -message "${body:-notify}"` と `osascript - "$title" "${body:-notify}"` で、**どちらも `body` を argv で渡す。** これは **#340 で実際にコマンドが死んだ消費者型そのもの**である。初版 §7 は受け手を WezTerm 1つに絞って「表示が崩れる程度」と推測していたが、**絞り方が誤っていた。**

**C5 の位置づけを正した。** 初版は「対照が成立しないことを記録するための対照」と書いたが、**C5 は C6 と対になって「壊れるかどうかは文字幅ではなく切断位置で決まる」という機構主張の差分テストである。** C5 単独では意味を持たず、C6 があるから意味を持つ。

## 7. スコープ外・未検証の仮定

### 7.1 out-of-scope の観測（gate 2 で見つかった・本 PR では直さない）

- **`$HOME/.notify-hook-debug` の `$HOME` が素で展開されている**（修正後の `:109`。**行番号でなく検索できる形で書く** — コメントを足したので番号がずれた）。隣の `${NOTIFY_DEBUG:-}` は guard 付きなのに `$HOME` は素で、`set -u` により **`HOME` 未設定で rc=1 になり advisory 契約に反する**（実測）。**この repo は同族を直近で直している**（`d80c292`「HOME 未設定でも `oe-*` が引数解析へ到達する」#341）。
  - **直し方は `${HOME:-}` だけでは足りない**（gate 4 の codex 指摘）。`HOME` が空文字のとき `/.notify-hook-debug` を見に行くので、`[[ -n "${HOME:-}" && -f "$HOME/.notify-hook-debug" ]]` の形が正確である。
  - **2レーンとも「本 PR では直さず surface」に同意した。** ただし**メモに埋めず別 Issue にすべき**（codex）。
- **同じ袋の2件目（gate 4 の claude 指摘）**: 非 tmux のフック起動では毎回 `/dev/tty: Device not configured` が stderr に出る。`[[ -w /dev/tty ]]` は通るのに `open` が ENXIO で落ちるためで、`2>/dev/null` はリダイレクトより後に適用されるので効かない。**advisory 契約は非ゼロ exit と stdout しか禁じていないので違反ではないが、`$HOME` と同じ「advisory の衛生」の話である。**

### 7.2 未検証の仮定

- **`notify.sh` が非 UTF-8 ロケールで実行される具体的な経路。** 自分も gate 1 / gate 2 の各レーンも**実例を観測できていない。** ただし gate 2 で**候補は具体化した**（いずれも未検証）。
  - `LC_ALL=C claude` / `LANG=C claude` と明示して起動する。
  - Claude Code の `settings.json` の `env` に `LANG` / `LC_ALL` を設定する。

  - **Claude Code の Mac デスクトップアプリ**（Finder / launchd 起動なので `LANG` を持たず、`TMUX` も無い。しかも対話的なので `Notification` hook は発火する）。claude レーンが「一番鋭い候補」として挙げた。
