# 要求分析 × AI 協業パターン

カケハシ社の事例から、Claude Code に社内情報（コードベース・Slack・Confluence）を集約させて要求分析の叩き台を生成し、エンジニア2名で同期レビューするワークフローを分析した。

- **URL**: [kakehashi-dev.hatenablog.com/entry/2026/04/07/090000](https://kakehashi-dev.hatenablog.com/entry/2026/04/07/090000)

- **要約**: Claude Code に既存コードベース・Slack・Confluence を MCP/CLI で横断的に読み込ませ、RDRA（Relationship Driven Requirement Analysis）に基づく要求分析の叩き台（7成果物）を生成させた事例。エンジニア2名で同期レビュー・リアルタイム修正を行い、要求分析の立ち上げを約5時間+関係者すり合わせ1時間で完了。コードから機械的に読み取れる構造情報（データモデル・状態遷移・外部連携）は精度が高い一方、暗黙知や業務文脈に依存する成果物は人間の補完が不可欠。Claude Code の網羅的走査がスコープ外の観点（解約・契約変更フロー等）を引き出し、人間のバイアスを補完した点が特筆。

### パターン1: 多情報源統合インプット

「コードだけ読ませても、業務的な文脈が欠落した出力になる」というのが記事の核心的な主張。Claude Code に MCP/CLI 経由で読み込ませた情報源:

- **コードベース**: データ構造、状態遷移、外部連携の定義
- **Slack**: 仕様の意思決定経緯、業務上の制約に関する議論
- **Confluence**: 仕様書、運用手順書

コードは「何が実装されているか」を教えるが、「なぜそう実装したか」はSlackの議論に、「運用上の制約」はConfluenceに分散している。これらを横断的に統合して初めて、要求分析の叩き台として機能する精度が出る。

なぜ有効か: 情報の所在が分散しているのは組織の構造的問題であり、人間が手作業で集約するにはコストが高い。AI の「大量の非構造情報を横断的に読み込んで推論する」能力はこの問題に直接対応する。

### パターン2: 構造情報 vs 暗黙知の精度差

7成果物の精度を情報源の特性で分類した結果:

| 精度 | 成果物 | 情報源の特性 |
|------|--------|------------|
| **高（軽微な修正のみ）** | システムコンテキスト図、情報モデル、状態モデル | コードに明示的に記述された構造情報（外部連携定義、データ構造、状態遷移） |
| **中（部分的に修正）** | アクター一覧、要求一覧、ビジネスユースケース一覧、業務フロー図 | 業務的な意図・暗黙知に依存する情報 |

ideas/20260218 の推測比率モデルとの対応: コードに明示された情報 = 推測比率が低い（AI が正確に読み取れる）。暗黙知 = 推測比率が高い（AI が推測に頼る必要がある）。記事の精度マトリクスはこのモデルの実践的検証事例。

具体的な修正例（記事から）:

- **アクター一覧**: 開発・運用保守チーム自身がアクターに含まれていなかった。「当たり前すぎて書かない」暗黙の前提
- **要求一覧**: 業務的な条件・制約が欠落。「どんな条件で？誰が実行できて、誰はできない？失敗した場合は？」を人間が問い直す必要あり
- **業務フロー図**: 社内ドキュメントの情報が古く、実際の処理方式と異なっていた。ドキュメントの鮮度問題

### パターン3: AI ドラフト + 同期レビューの協業モデル

ワークフロー:

1. Claude Code に RDRA スキル + 多情報源を入力として7成果物のドラフトを生成させる
2. エンジニア2名で同期的に会話しながらレビュー
3. その場で Claude Code に修正指示を出し、リアルタイムで反映
4. 修正後の成果物を PRD にまとめて関係者と共有

役割分担: 既存システムに詳しいメンバーが業務知識を補完、統合先チームのメンバーが疑問点を質問・関係者にヒアリング。所要時間: 分析5時間 + 関係者すり合わせ1時間。

既存の `peer-ai-review` との比較: peer-ai-review は「修正案に対する複数 AI のレビュー」（実装段階）。記事のパターンは「要求分析の叩き台に対する人間レビュー」（設計段階）。AI の役割が「レビュアー」から「ドラフト作成者」に変わり、人間の役割が「修正実施者」から「品質チェッカー・暗黙知補完者」に変わっている。

### パターン4: RDRA スキル化（defer）

テックリードが RDRA ベースの要求分析用 Claude Code スキルを作成し、チームに提供した。このスキルが定義する成果物:

1. システムコンテキスト図
2. アクター一覧
3. 要求一覧
4. ビジネスユースケース一覧
5. 業務フロー図
6. 情報モデル
7. 状態モデル

「分析手法をスキルに固定し、成果物の構造をテンプレート化する」ことで、実行者が変わっても同じ構造の出力が得られる。これは本リポジトリの research-intake コマンドが「出力構造を固定して品質を担保する」のと同じ設計思想。

本リポジトリへの適用可能性: 新規スキルを設計する際に「手順」だけでなく「成果物テンプレート + 精度マトリクス（AI が得意な部分 / 人間が補完すべき部分の明示）」を含めることで、レビューの焦点を絞れる。

### パターン5: 網羅的走査によるバイアス補完

記事の最も印象的な発見: プロジェクトの主な関心は「契約中の顧客が使用するシステムの振る舞い」だったが、Claude Code は契約時・解約時・契約変更時のイベントまで含めた包括的な業務フローを提示した。

これは人間が持つ「スコープ絞り込みバイアス」を AI の全体走査が補完した事例。結果として「解約・契約変更時に既存フローが破綻しないか」「社内関係者の運用コスト増加」「顧客の自己完結操作範囲」という要求が追加された。

ideas/ の「コンテキスト限界の複雑性」テーマとの接続: AI のコンテキストが十分に広い場合、人間のスコープ制限を超えた網羅性を発揮できる。逆にコンテキストが不足すると推測比率が上がり精度が落ちる。情報源の統合（パターン1）がこの網羅性の前提条件。

### パターン6: 成果物ごとの精度マトリクス

AI が生成する成果物の品質をレビューする際の構造的な枠組み:

| 精度予測因子 | 高精度 | 低精度 |
|------------|--------|--------|
| 情報源 | コードに明示的に記述 | 暗黙知、口頭伝承 |
| 正解の定義 | 構造的に検証可能 | 業務的判断が必要 |
| ドキュメント鮮度 | コード = 常に最新 | 社内文書 = 古い可能性 |

このマトリクスを事前に持っておくことで、「AI ドラフトのどこを重点的にレビューすべきか」が構造的に決まる。全成果物を同じ強度でレビューする必要がなくなり、レビュー時間の配分を最適化できる。
