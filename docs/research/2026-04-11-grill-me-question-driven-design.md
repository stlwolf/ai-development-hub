# 質問駆動の要件定義: grill-me スキルの分析

## 記事情報

- **タイトル**: grill-me スキルがめちゃ良いので布教したい
- **URL**: [zenn.dev/ryonakae/articles/8783c6b3ead2cb](https://zenn.dev/ryonakae/articles/8783c6b3ead2cb)
- **著者/組織**: Ryo Nakae
- **公開日**: 2026-04-09
- **種別**: ブログ記事
- **要約**: Matt Pocock 作の Agent Skill「grill-me」の紹介。たった3行のスキルで、AIが実装前にユーザーに設計ツリーの枝分かれの先まで徹底的に質問し、決定事項間の依存関係を解決する。著者はこの導入後、Claude Code の Plan モード（opusplan）を使わなくなった。壁打ちセッション自体が実装計画になり、そのまま実装に移行できるシームレスさが利点。18〜24回の質問に答える認知負荷が高い点が欠点。

## grill-me スキル本体

[skills.sh/mattpocock/skills/grill-me](https://skills.sh/mattpocock/skills/grill-me) — 全文3行:

> この計画のあらゆる側面について、私たちが共通の認識に達するまで、徹底的に私に質問を投げかけてください。設計のツリーを枝分かれの先まで一つひとつたどり、決定事項間の依存関係を順番に解決していきましょう。各質問に対し、あなたの推奨する回答も併せて提示してください。
>
> 質問は一度に一つずつお願いします。
>
> もしコードベースを探索することで答えが得られる質問であれば、質問する代わりにコードベースを調査してください。

### パターン1: 質問駆動の要件定義

grill-me の核心は「設計のツリーを枝分かれの先まで一つひとつたどり、決定事項間の依存関係を順番に解決する」という指示。AIが18〜24回もの質問を通じて、ユーザー自身が意識していなかった設計判断を引き出す。

Plan モードとのアプローチの違い:

| 観点 | Plan モード | grill-me |
|------|-----------|----------|
| 主導権 | AI が計画を提案 → 人間がレビュー | AI が質問 → 人間が回答 → 合意形成 |
| 方向 | トップダウン（全体計画→詳細） | ボトムアップ（個別判断→全体像が自然に形成） |
| 修正コスト | 一部修正→計画全書き直しのループ | 質問の過程で漸進的に固まるため、大幅な手戻りが発生しにくい |
| 暗黙知の引き出し | 人間がレビュー時に気づく（受動的） | AI が質問で引き出す（能動的） |

なぜ有効か: 人間は「何が必要か」を網羅的に列挙するのが苦手だが、「この場合はどうする？」と聞かれれば判断できる。質問駆動は人間の判断能力を活かしつつ、AI の網羅性で漏れを防ぐ。

ideas/20260220/human-input-formatting.md との接続: 「AI側が質問フォーマットを提示し人間が回答する形が持続可能」という仮説の外部実装事例。grill-me は「質問+推奨回答の提示」で入力品質を構造化している。

### パターン2: 壁打ち = 計画の同一視

著者の報告: Plan モード使用時は「一部修正指示→実装計画全書き直し→修正指示→全書き直し」のループが発生していた。grill-me では壁打ちの過程で計画が漸進的に固まるため、完了後は「OK。これで実装して」で実装に移行できる。

壁打ちセッション履歴 = 実装計画という等式が成立する条件:
- 質問が設計判断の分岐点を網羅していること
- 各質問への回答が明確で、後から参照可能であること
- AI が回答を統合して一貫した実装方針を保持していること

著者は Opus 4.6 (1M context), medium effort で使用しており、数十回の壁打ちでもコンテキストウインドウに余裕があると報告。

### パターン3: 最小スキルの最大効果

多くのスキルが数十〜150行ある中で、grill-me は3行。含まれるのは:
1. 行動指示（共通認識に達するまで質問する）
2. 制約（一度に一つずつ）
3. 自律性（コードベースで分かるなら自分で調べる）

出力形式の定義もテンプレートもない。「何を出力するか」ではなく「どう振る舞うか」だけを定義している。これは research-intake のような「出力構造を固定して品質を担保する」アプローチとは対極にあり、タスクの性質（構造化された成果物 vs 対話的な合意形成）によって使い分けるべき。

### パターン4: コードベース探索による自己解決

「コードベースを探索することで答えが得られる質問であれば、質問する代わりにコードベースを調査してください」の1行が、不要な質問を減らす。

カケハシ記事（2026-04-10-requirements-analysis-ai-collaboration.md）のパターン2「構造情報 vs 暗黙知の精度差」との対応: コードから機械的に読み取れる情報は AI が自己解決し、暗黙知や業務判断のみを人間に質問する。質問の精度が上がることで認知負荷を適正化する。

## experiment: 導入検証の方針

### 検証対象

grill-me 相当のスキルを `canonical/skills/` に作成し、実案件で試行する。

### 検証観点

| 観点 | 測定方法 |
|------|---------|
| 合意形成の速度 | Plan mode のみ vs 質問フェーズ + Plan mode の所要時間比較 |
| 手戻り頻度 | 実装開始後の方針変更回数 |
| 認知負荷 | 質問回数と主観的な疲労感（記事では「とにかく疲れる」と報告） |
| Plan mode との棲み分け | どのタスク特性で質問フェーズが有効か／不要かの判断基準 |

### 想定する棲み分け（仮説）

| タスク特性 | 推奨フロー |
|-----------|-----------|
| 暗黙の設計判断が多い（新機能、アーキテクチャ変更） | 質問フェーズ → 必要なら Plan |
| 技術的に明確だが規模が大きい（リファクタ、マイグレーション） | 直接 Plan mode |
| 軽微な修正（1ファイル数行） | どちらも不要 |
