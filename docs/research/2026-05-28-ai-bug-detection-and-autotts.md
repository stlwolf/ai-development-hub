## 記事A: AI バグ探索 — 機能単位コンテキスト投入

### 記事情報

- **タイトル**: PRレビューツールが見逃すバグを、ClaudeにNext.js+Zustandのコードを渡して3つ発見した話
- **URL**: [zenn.dev/headwaters/articles/4bb85a2a1b93ea](https://zenn.dev/headwaters/articles/4bb85a2a1b93ea)
- **著者/組織**: ケン吉 / ヘッドウォータース
- **公開日**: 2026-05-26
- **種別**: ブログ記事
- **要約**: 機能単位（コンポーネント + Zustand store + FastAPIエンドポイント）でコードをClaudeに渡し、「潜在的なバグを発見し、ghコマンドでIssue化してください」というシンプルなプロンプトで、Jest/ESLint/TypeScript型チェックをすり抜けた3つの操作フロー起因バグを発見。PR差分レビューではなく機能コンテキストをまとめて渡すことで、モジュール間連携・状態管理のライフサイクルに起因する潜在バグを推論で検出できることを実証した。

|---|-----------|-------------|------|
| A1 | 機能単位コンテキスト投入 | PR差分ではなく機能単位（コンポーネント+store+API）でコードを束ねてAIに渡すことで、操作フロー文脈が保持され推論精度が上がる | 設計原則 |

### パターン詳細

#### A1: 機能単位コンテキスト投入

AIコードレビューツール（CodeRabbit, Cursor Bugbot, GitHub Copilot Code Review）はPR差分を対象とするため、「この機能がどう使われるか」という操作文脈を持てない。機能単位で関連ファイルをまとめて渡すことで、AIは以下の推論が可能になる:

- Zustand storeの初期化タイミングから「コンポーネントのアンマウント時にstoreがどうなるか」を推論
- フィルタリング条件パラメータから「複数条件が同時に渡ったときの状態変化」を推論
- バリデーションのトリガー箇所から「別経路で送信ボタンが押されたときの挙動」を推論

粒度の目安は「画面単位」「フォーム単位」。広すぎると推論が分散する。

#### A2: バグ発見→テスト生成の順序制御

AIにテストを書かせると、バグを含んだコードを「正」としてテストが生成される（同語反復の罠）。理想の順序は「バグ発見→修正→テスト生成」だが、既存テストがある状態での後付けバグ探索も有効であることが実証された。

#### A3: 数量非指定プロンプト

「3つ見つけてください」のように数を指定すると、実際のバグが1つでもAIが「3つ出さなければ」というプレッシャーで存在しないバグを作り出すリスクがある。「潜在的なバグを発見してください」と数を開放することで、本当に問題だと判断したものだけを報告する。

Issue #76（so-compare 選択肢拡張テンプレート）の「知らない選択肢を生成させる」プロンプト設計に直接接続する知見。

#### A5: テスト層の中間位置づけ

| テストの種類 | 何をするか | コスト | 位置づけ |
|---|---|---|---|
| 単体テスト（Jest/Vitest等） | 関数・コンポーネント単体を動かして検証 | 低 | すり抜けたバグを AI が補完 |
| AI静的推論レビュー | コードを静的に読んで操作シナリオを推論 | 低〜中 | 単体テストと統合テストの間を埋める |
| 統合テスト | 複数モジュールを組み合わせて動かして検証 | 中 | より確実な検証が必要な箇所に |
| E2Eテスト（Playwright等） | 実際にブラウザを動かしてユーザー操作を再現 | 高 | 最終的な品質担保 |

AI推論レビューは「どこを重点テストすべきか」の絞り込み手段として位置づけられる。

## 記事B: AutoTTS — AI によるアルゴリズム探索環境設計

### 記事情報

- **タイトル**: AIがAIアルゴリズムを自ら設計：Claude Codeが40ドルで発見した推論コスト7割削減の手法とは
- **URL**: [xenospectrum.com/autotts-ai-algorithm-discovery-tts-token-reduction/](https://xenospectrum.com/autotts-ai-algorithm-discovery-tts-token-reduction/)
- **著者/組織**: Y Kobayashi / XenoSpectrum（元論文: UMD・UVA・WUSTL・UNC・Google・Meta 13名共同）
- **公開日**: 2026-05-24（元論文: arXiv:2605.08083）
- **種別**: ブログ記事（論文紹介）
- **要約**: Claude Codeを探索エージェントとして使い、$39.90・160分でTest-Time Scalingの制御アルゴリズム（CMC: Confidence Momentum Controller）を自律発見。SC@64比でトークン使用量を約70%削減しながら精度を維持。核心はオフラインリプレイ環境（推論パスの事前保存による低コスト評価）で、FunSearch/AlphaEvolveと異なり個人研究者でも再現できるコスト構造を実現。「アルゴリズムを設計する」から「AIが探索できる環境を設計する」への研究プロセスの構造転換を示す。

### 本質的パターン

| # | パターン名 | 本質（1-2行） | 種別 |
|---|-----------|-------------|------|
| B1 | オフラインリプレイ評価 | 推論パスを事前保存し、候補アルゴリズムの評価時に本番モデルを再起動せず済ませることで評価コストを劇的に削減 | 実装パターン |
| B2 | 環境設計への責務シフト | 人間が「アルゴリズムを設計する」→「AIが探索できる環境（評価関数+探索空間+リプレイ環境）を設計する」。探索自体はAIに委ねる | 設計原則 |
| B3 | EMAトレンドベース停止 | 単一ステップの信頼度ではなくEMA（指数移動平均）による時系列トレンドで推論停止を判断。従来の設計思想にない発想 | 実装パターン |
| B4 | $40再現性のコスト構造 | 大規模計算資源を前提とせず、個人研究者・スタートアップでも再現できるコスト設計。探索と評価の分離が鍵 | 評価手法 |
| B5 | 幅×深さの2次元制御空間 | TTS制御を「並列ブランチ数（幅）」×「ブランチの伸長度（深さ）」に抽象化し、管理可能な探索空間を定義 | 設計原則 |

### パターン詳細

#### B1: オフラインリプレイ評価

AutoTTS の探索プロセスは3層構成:

1. **Claude Code**（探索者）: 制御アルゴリズムを Python コードとして直接生成。複数ラウンドで前回の弱点を特定し改良版を提案
2. **オフラインリプレイ環境**: 問題を解く LLM の推論パスをあらかじめ保存。評価時に推論 LLM を繰り返し起動不要
3. **評価関数**: 精度とトークン消費量のトレードオフでアルゴリズム候補をランク付け

FunSearch/AlphaEvolve は大規模計算資源と多数サンプリングを前提とするのに対し、AutoTTS はオフラインリプレイで評価部分を切り離すことで個別モデル呼び出し回数を抜本的に削減。これが $39.90 を実現した根本的な差異。

Issue #77（確定前ゼロベース探索）の「生成と反証を物理的に分離（別 invocation）」と同型の構造。

#### B2: 環境設計への責務シフト

研究者がやったことは:

- Claude Code の探索環境を整備
- 評価関数（精度とコストのトレードオフ）を定義
- オフラインリプレイ環境を構築

アルゴリズムの中身を考えることではなかった。Issue #77 の deterministic orchestrator パターン（探索は非決定的、評価は決定的）の論文レベル実証例。

#### B3: EMA トレンドベース停止

CMC（Confidence Momentum Controller）の4機構:

1. **EMA によるトレンドベース停止**: 信頼度が複数ラウンドにわたり安定して高い場合に推論を打ち切り。時系列トレンドで判断する点が従来と大きく異なる
2. **結合幅深度制御**: 幅（並列数）と深さ（反復数）の連動制御
3. **整列対応深度配分**: 問題の難度に応じた深さの動的配分
4. **保守的分岐破棄**: 見込みの薄いブランチの早期切り落とし

β≈0.5 で SC@64 比の精度を維持しながらトークン約70%削減。β=1.0 では 8 比較セルのうち 5 つで手作業ベースライン超え。

Issue #77 の収束条件（カウントベース）と Issue #78 の介入条件（N個蓄積）に対して、EMA トレンドベースという代替アプローチの選択肢を提供する。

#### B5: 幅×深さの2次元制御空間

TTS の制御軸を「幅（並列ブランチ数）」と「深さ（1ブランチの伸長度）」の2変数に抽象化。問題が簡単なら少ない幅・浅い深さで十分、難しければ広い幅・長い深さが必要。Issue #77/#35 の探索プロセス設計における共通設計言語として参照可能。

## 記事C: ドメイン特化 PR 自動レビュー基盤

### 記事情報

- **タイトル**: Claude Code Skills × Bedrockで実現するドメイン特化のPR自動レビュー
- **URL**: [techblog.zozo.com/entry/domain-specific-pr-review-with-claude-skills](https://techblog.zozo.com/entry/domain-specific-pr-review-with-claude-skills)
- **著者/組織**: 池上 寛登 / ZOZO（FBZブロック）
- **公開日**: 2026-05-29
- **種別**: ブログ記事
- **要約**: FBZ のドメイン知識（暗黙知）を NG/OK ペア形式のレイヤー別ガイドラインに形式知化し、Claude Code Skills + Amazon Bedrock で PR 自動レビュー基盤を構築。変更パスから参照すべきガイドラインを動的にロードし、2段レビュー（Reviewer Pass: 網羅的 → Validator Pass: 批判的再検証）+ Confidence スコアリングで誤検知を抑制。月次でガイドライン自動更新提案を起票する閉ループまで含む CI レベルの基盤。

### 本質的パターン

| # | パターン名 | 本質（1-2行） | 種別 |
|---|-----------|-------------|------|
| C1 | NG/OK ペアによる暗黙知の形式知化 | レビューコメントから繰り返し出現するアンチパターンを収集し、NG/OK ペアで構造化。LLM がルールの境界を判定しやすくなる | 設計原則 |
| C2 | 変更パス→ガイドライン動的ロード | 変更ファイルのパスから対応表で参照すべきガイドラインのみを選択的にロード。コンテキスト肥大化を防ぎ精度を保つ | 実装パターン |
| C3 | 2段レビュー（Reviewer + Validator） | 網羅的に拾うペルソナと批判的に再検証するペルソナを分離。役割分離により誤検知を抑制 | ワークフロー |
| C4 | Confidence スコアリング + Severity ラベル | 各指摘にチェック項目の採点合計で確信度を算出し、Severity（Important/Pre-existing/Nit）ごとに投稿閾値を設定 | 評価手法 |
| C5 | ガイドライン自動更新提案 | 直近のレビューコメントと既存ガイドラインを月次で照合し、追加・修正・削除を含む更新提案を自動起票。ルールの陳腐化を防ぐ閉ループ | ワークフロー |
| C6 | PRサイズ別モデル選択 | PR の差分行数×変更ファイル数で Haiku/Sonnet を動的切替。Opus はコスト対効果が合わず不採用 | 実装パターン |

### パターン詳細

#### C1: NG/OK ペアによる暗黙知の形式知化

PRレビューコメントから「同種の指摘が繰り返し発生」「既存ドキュメントでカバーされていない」「チーム全体で共有すべき設計判断」に該当する指摘をルール化。形式を統一することで LLM がルールの境界を判定しやすくなる。

Issue #62（Negative Knowledge）の蓄積フォーマット設計にそのまま使える具体形。また Issue #113（episode-retrospective）の「AI 駆動向け: Pattern / Anti-pattern」テンプレ候補の参考実装。KPT と比較して、NG/OK は対比構造が明確で LLM の自己回帰生成との相性が良い可能性がある。

#### C2: 変更パス→ガイドライン動的ロード

SKILL.md に対応表を記述し、変更ファイル一覧と照合して該当する章だけを動的にロード:

```yaml
'app/service/**': layer-rules/layer-responsibility.md
'app/dataaccess/**': layer-rules/data-integrity.md
'tests/**': layer-rules/test-and-coding.md
```

記事A の A1（機能単位コンテキスト投入）と同じ「適切なコンテキストだけを渡す」設計思想の CI 適用版。canonical アーキテクチャの CATALOG.md + skill-first-operations ルールと構造的に同型。

#### C3: 2段レビュー（Reviewer + Validator）

単一セッション内でペルソナを切り替える2段構成:

1. **Reviewer Pass**（網羅的に拾う）: 候補を出し切る
2. **Validator Pass**（批判的に再検証）: 根拠を再確認し、Confidence スコアを付与

adversarial-review スキルの Plan Review（網羅的チェック）+ Compliance Review（仕様照合）と同型構造。Issue #77（確定前ゼロベース探索）の「生成と反証の分離」の PR レビュー適用でもある。

#### C4: Confidence スコアリング + Severity ラベル

Validator Pass のチェック項目:

- 根拠コードを再読み込みしたか
- PR説明文を踏まえているか
- 影響範囲を確認したか

合計値が Severity 別の閾値を超えた場合のみ投稿。Important は厳しめ、Nit は緩めの閾値。

Issue #92（検証ゲート v2）の「検証 agent への完了報告内容の充実」が目指す方向の具体解。入力（完了報告）だけでなく出力（指摘の信頼度制御）にも構造を持たせることで検証ゲート全体の精度が上がる。

#### C5: ガイドライン自動更新提案

月次ワークフロー:

```
直近のレビューコメント × 既存ガイドライン → 差分抽出 → 更新提案を自動起票
```

メタガイドライン（追記場所・文体・重複チェック手順）を別ファイルで用意し、ガイドラインの一貫性を保つ。

Issue #62（Negative Knowledge）が Phase A（蓄積）→ Phase B（注入）で留まるのに対し、「蓄積 → 注入 → 既存ルールへの還元」までの閉ループ。Issue #113 がスコープ外にしている「振り返り内容を engine の学習ループへ自動投入する仕組み」の具体例でもある。

## 記事間の関連性

3記事は「**コンテキスト設計 > 実行そのもの**」というメタパターンを共有:

- 記事A: 「機能コンテキストを設計して渡す」ことで AI のバグ検出精度が上がる
- 記事B: 「探索環境を設計する」ことで AI のアルゴリズム発見が可能になる
- 記事C: 「ガイドラインを設計して動的にロードする」ことで AI のレビュー精度が上がる

人間の仕事が「成果物の直接生産」から「AI の探索環境の設計」にシフトするという方向性は共通。

さらに記事C は記事A/B に対して「閉ループ」を追加する:

- 記事A/B: コンテキスト設計 → AI 実行 → 結果
- 記事C: コンテキスト設計 → AI 実行 → 結果 → **結果からコンテキストを更新**（ガイドライン自動更新）
