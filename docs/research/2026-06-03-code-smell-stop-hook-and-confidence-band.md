# 臭うコード検出器（Stop Hook）と「臭う＝中間確信度バンド」アンカー

本記事は単独記事だが、`docs/research/2026-05-28-ai-bug-detection-and-autotts.md` の記事C（ドメイン特化 PR レビュー基盤）の**姉妹編**として読める。両者の核心は「人間レビューの前にAIに気づかせる仕組み」だが、本記事は **CI（ハード失敗）と CLAUDE.md（暗黙知）の間にある中間層を Stop Hook で実装する**点が独自。

そしてこの「臭う」という抽象概念は、フックの実装パターンを超えて、当環境の探索・セカンドオピニオン系の未解決課題（#77 / #78 / #35）に対する**欠けていたプリミティブ**になり得る——これが本ノートの主眼。

### パターン詳細

#### M1: 検出可能性×偽陽性率による3層仕分け

記事は規約遵守を機械化する際の優先順位を次の順で示す:

1. 静的に検出でき偽陽性が少ないもの → **CIで落とす**（例: Laravel標準Loggerではなく内製Logger Wrapperを使う）
2. 静的検出はできるが偽陽性が多いもの → **Stop Hook の"臭うコード"扱い**（例: UseCase層でDBアクセス用Modelを直接参照）
3. 静的に検出できないもの → **CLAUDE.md / Rules / Skill** で事前教示

ポイントは、従来「ルールに書く or CIで落とす」の二択だったものに、**偽陽性率という軸**で中間層を設けたこと。「CI に入れると偽陽性で混沌とするが、放置はしたくない」チェックの居場所を作った。

#### M2: Stop Hook 自己修正ループ

フロー:

1. "臭うコード"検出専用ルールのみを実行
2. Claude Code の Stop Hook で当該ファイルをチェック
3. 検出時に「絶対NGではないが、再検討してほしい」メッセージを返す
4. Claude Code 自身が応答して修正を試みる

Stop Hook を選んだ理由は明示的: **「CI内では偽陽性で混沌、Claude Code 内に閉ざしたい」**。git hook よりセッション単位で処理する Stop Hook が適切と判断。CI を汚さずにフィードバックを閉じた経路に隔離する「経路分離」の設計判断。

#### M3: `stop_hook_active` 無限ループガード

Stop Hook は応答を生成させるため、放置すると「フック→応答→またフック」の無限ループになる。`stop_hook_active`（既に応答中を示すフラグ）のときはスキップする定型ガードで防ぐ。Stop hook を実装する上での必須パターン。

#### M4: 構文木ベース規約検出

PHPStan のカスタムルール（Nodeベース）で AST を走査し規約違反を検出。記事中の検知事例:

- `useEffect` 内の `setState` 呼び出し（「9割くらい駄目」）
- Validation の最大値（`max:N` / `size:N`）漏れ
- テーブル外部キーの `ON DELETE CASCADE` 漏れ
- テスト内の `assertStatus(500)` を期待値にしている
- Interface 越境参照（レイヤー責務違反）

当リポジトリは Bash / Markdown 中心のためコードの直接流用はないが、「人が繰り返し指摘する観点を AST 検出に落とす」という原則の実例。

#### M6: レビュー実績→Skill自動生成サイクル

GitHub API で過去数年分のレビューコメントをダウンロード → AI 分析 → 頻出指摘を Skill 化 → Hook に配備。「実装→コミット→ルール化」の閉ループ。`2026-05-28` ノートの C5（ガイドライン自動更新、CI/Bedrock版）に対し、本記事は **Hook版**を提供する。

#### M7: 量産スタンス

偽陽性を許容する前提の検出器は「致命的な問題は起きづらい」ため、手軽に量産してよい、というスタンス。手元試験 → チーム共有の段階では `settings.local.json` での限定運用から始める。当リポジトリの Issue #24（フック拡充: 1フック=1サブIssue、独立追加可能）の方針と整合。

### 「臭う」の抽象概念としての本質（合成・解釈）

> 以下は記事本文の主張ではなく、「臭う＝中間確信度シグナル」という抽象を当環境の認知系資産に延伸した合成・解釈。

記事の M1 を**確信度の軸**で読み直すと、「臭う」は次の中間バンドを指す:

| 層 | 確信度 | 性質 | 対応する認知行動 |
|----|--------|------|----------------|
| CI落とし | 高・二値 | ハード失敗 | 機械的ゲート（フック） |
| **臭う（Stop Hook）** | **中・非二値** | **「ブロックするほどではないが、もう一度見たい」** | **深掘り / セカンドオピニオン / 再検証** |
| ルール（CLAUDE.md） | 検出不可 | 暗黙知 | 事前教示 |

中間層の「もう一度見たい」は、**「別視点を呼ぶ閾値に達したが、確定するには足りない」**状態。これがセカンドオピニオン・諦めない深掘りの発火条件と同型になる。この再フレームこそ、本ノートが既存マッピング（フック中心）に追加する核心的知見。

## なぜ認知系の接続の方が価値が高いか

- フック接続（M2→#24 H-7）は「既に計画済みのものの実装例」——新規性が低い。
- 認知接続（M1中間バンド→#77トリガー欠落）は「名前が無かった欠けたプリミティブに名前を与える」——#77 が「最大のギャップ」と呼んだ穴を `smell` という語で埋められる可能性。

「臭う」はフック実装の話と、探索/SO の発火プリミティブの話の二重性を持つ。後者の方が当環境の未解決課題（#77 / #78 / #35）に効く。
