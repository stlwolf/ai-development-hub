### A. Claude Codeのループが回らないのは、プロンプトではなく完了条件の問題だった

- **URL**: https://zenn.dev/gemcook/articles/467b1233efe811
- **著者/組織**: MJ / Gemcook
- **公開日**: 2026-07-10
- **種別**: ブログ記事（技術ノウハウ）
- **要約**: Claude Code の自律ループが空転する原因をプロンプト品質ではなく完了条件の分類不足に置く。完了条件を到達型（決定論・目標が事前に書ける）、収束型（決定論・探索的で終わりが事前に決まらない）、rubric+judge 型（非決定論）の 3 つに分け、型ごとに強制手段が決まると論じる。到達型は hook で検証スクリプトを機械実行、収束型は「or stop after 15 turns」のような上限句を必須にし「2 回連続で新規発見がゼロなら完了」を収束定義とする、rubric+judge 型は judge に経緯を渡さず成果物のみ渡す。失敗事例として、検証不能な空虚な完了条件（「タスクが正しく完了していること」「品質が十分であること」）と、検証失敗から修正試行を繰り返して同じ結果に戻る無限ループを挙げ、後者に対して git 状態と失敗出力がバイト単位で同一なら無進捗と判定してサーキットブレーカーを発動する対策を示す。委任判定は「完了条件が書けるか → どの型か → 上限句は必須か」の順で行う。

### C. Claude Codeを自分色に染める1つの習慣と1つの仕組み

- **URL**: https://blog.colopl.dev/entry/2026/06/25/110000
- **著者/組織**: 田中 / COLOPL
- **公開日**: 2026-06-25
- **種別**: ブログ記事（実践知見）
- **要約**: 習慣と仕組みの 2 本立て。習慣は、コミットや PR という作業の節目で「今回のやりとりを振り返って、今後に生かせることや改善すべきことはありますか」と問い、AI の出力だけでなく自分の指示の出し方も振り返り対象にすること。得られた学びは性質に応じて memory 機能か CLAUDE.md へ蓄積する。仕組みは、前日の使用履歴を毎朝自動で解析し、サブエージェントやスキルの新規作成・改善提案を生成して、優先度の高いものは PR を自動作成し Slack に通知するもの。LaunchAgent が起動し、Python スクリプトが履歴を整形し、Claude が 4 軸（同一セッション内のやり直し、実行後の手直し、繰り返し依頼、スタイルの再指定）でパターン判定する。集計とパターン判定で役割を分け、機械は決まった形への整形、AI はゆらぎのある判定を担う。詳細は 1 日分のみ読み、傾向は 7 日の軽いサマリで見る。発行済み提案の履歴ファイルで重複を抑止する。安全策として書き換え対象を `~/.claude/` 配下に限定し、1 実行あたり PR は最大 2 本。

### 束 1: ループの閉じ方（停止条件と停滞検知）

| # | パターン名 | 本質 | 種別 | 検証/根拠 |
|---|-----------|------|------|----------|
| P1-1 | 完了条件の 3 分類 | 完了条件を到達型・収束型・rubric+judge 型に分けると、型ごとに強制手段がほぼ自動的に決まる | ワークフロー | [unverified-summary] https://zenn.dev/gemcook/articles/467b1233efe811 |
| P1-2 | 無進捗のバイト同一判定 | git 状態と失敗出力がバイト単位で同一なら無進捗と判定し、2 回目でサーキットブレーカーを発動する。進捗のある失敗は粘らせ、何も変わらない再ブロックだけを打ち切る | 実装パターン | [unverified-summary] 同上 |
| P1-3 | 振動検知 | A→B→A の修正往復を振動として検出し、同じ層での修正を続けず再設計へエスカレーションする | 実装パターン | [unverified-summary] https://techblog.lycorp.co.jp/ja/techverse2026-219 |
| P1-4 | 収束型には上限句を必須にする | 探索型のループには「or stop after N turns」を必ず付ける。脱出口のないループは事故る | 設計原則 | [unverified-summary] https://zenn.dev/gemcook/articles/467b1233efe811 |
| P1-5 | 井戸の枯渇による完了定義 | 収束型の完了は「2 回連続で新規発見がゼロ」で定義する | 評価手法 | [unverified-summary] 同上 |
| P1-6 | judge には成果物のみ渡す | 非決定論的な完了判定では、書いた本人の採点は「できたように見える」しか出ないため、judge に経緯を渡さず成果物だけ渡す | 設計原則 | [unverified-summary] 同上 |
| P1-7 | 委任の前提条件としての完了条件 | 完了条件が書けないタスクは委任しない。書けるなら型を判定し、型から強制手段を導く | ワークフロー | [unverified-summary] 同上 |

**P1-1 の詳細。** 到達型は目標が事前に明示できる場合で、たとえば「`npm test` が exit 0、公開 API のシグネチャは不変」のように書け、hook で検証スクリプトを機械実行して強制できる。収束型は探索的で終わりが事前に決まらない場合で、上限句と枯渇条件の両方が要る。rubric+judge 型は成果物の良し悪しが機械判定できない場合で、独立した judge を立てる。3 分類の価値は分類そのものではなく、**分類が決まると強制手段が決まる**という写像にある。既存の #49 が「完了条件を書く」までを扱っているのに対し、この型と強制手段の対応表が欠けている。[speculation]

**P1-2 と P1-3 の関係が本ノートの中心。** どちらも「同じところを回っている」ことの機械判定だが、観測している対象が違う。P1-2 は差分の不在（前回と今回の状態がバイト単位で同一）を見る。P1-3 は状態遷移の履歴（A→B→A という往復パターン）を見る。前者は 1 ステップの反復を、後者は複数ステップの循環を捉えるので、検出できる停滞の形が異なる。`reframe-on-stall-rule` は停滞をカウントではなく観測可能な兆候で判断すると定めながら、その兆候を機械で取る手段を持っていない。[verified] `canonical/rules/reframe-on-stall-rule.md`（「Trigger: a stall, judged by observable signs (not a step count)」および Limits 節の「there is no firing guarantee」）

**P1-6 は当リポジトリの SO 設計と整合する。** 経緯を渡さない judge は、`adversarial-review` と `peer-ai-review` が別プロセスとして独立していることの理由付けになる。[speculation]

## 合流点

このノートで最大の収穫は、**停滞の機械判定に独立した 2 つの実装が同時に揃ったこと**（P1-2 と P1-3）。

背景として、当リポジトリの探索原則クラスタは soft 層まで着地して hard 層を defer している。`exhaustion-before-conclusion-rule` は決定的な hard gate を #77 / #78 の範囲で defer し、`reframe-on-stall-rule` を always-on の soft floor として置いた。[verified] `canonical/rules/exhaustion-before-conclusion-rule.md`（Application 節: deterministic hard gate is still deferred）。defer の理由の一部は、停滞を決定論的に検知する手段が決まっていなかったことにある。[speculation]

P1-2（差分の不在を見る）と P1-3（状態遷移の循環を見る）は、その手段の候補を 2 つ与える。しかも観測面が違うので、どちらが当リポジトリの実態に合うかを比較できる。フック実装としては、`hypothesis-gate.sh` が既に PostToolUse で advisory 通知を出す前例を持っているので、配線の型は再利用できる。[verified] `canonical/CATALOG.md`（Hooks 節: 仮説ゲートは `tmp/hypothesis-*.md` が N=3 で advisory 通知、Claude Code PostToolUse）

2 つ目の合流点は、**ループを閉じる話（束 1）とループを育てる話（束 2）が同じ観測面を要求している**こと。束 1 の停滞検知は「同じところを回っている」痕跡を数え、束 2 の改善提案生成は「やり直し・手直し・繰り返し依頼」の痕跡を数える。どちらも実行履歴に残る反復パターンの検出であり、収集する痕跡が重なる。停滞検知フックを作るなら、その観測データは改善提案の入力としても使える。[speculation]
