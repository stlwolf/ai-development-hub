### A. 個人のプロンプト術をやめて、チームで回るAI駆動開発ループを作った話

- **URL**: https://zenn.dev/explaza/articles/d0aeb08fcd1888
- **著者/組織**: ウンス / 株式会社エクスプラザ
- **公開日**: 2026-06-23
- **種別**: ブログ記事（実践事例）
- **要約**: 少人数チームが個人のプロンプト術から脱却するため、調査・質問・計画・実装・レビューを 1 つのループにまとめた `interview-dev-loop` という Agent Skill を導入した事例。skill は GitHub で公開管理し、特定ツールに依存しない形にして Codex と Claude Code の両方で使う。プロジェクト固有の指示は `AGENTS.md` に一元化する。質問の対象は Material Ambiguity（実装の方向、検証、ロールアウト、データ処理、権限、ユーザーに見える動作のいずれかが変わりうる不確実さ）に限定し、選択肢は実装方針が変わるものだけに絞って最大 3 つとする。失敗と修正として、毎回の挙動がぶれたので Material Ambiguity を定義した、答えが決まった質問が多発したので選択肢を絞った、調査の余計な文脈が実装に混入したので調査エージェントと実装エージェントを分離した、の 3 点を挙げる。人間が触るのは質問に答える・計画を承認する・動作確認する の 3 点に集約し、PR 後の指摘対応も別 skill で自動化する。効果として PR 初期レビュー指摘スコアが 1,000 変更行あたり 72.3% 減、P1 と P2 のコメントが 77.4% 減、同期間で変更行数は約 4.6 倍と報告している。

### B. 自社のレビュー履歴からAIコードレビュアーをつくる方法

- **URL**: https://zenn.dev/estie/articles/f0f114389662ba
- **著者/組織**: Nari / estie（取締役 CTO）
- **公開日**: 2026-07-21
- **種別**: ブログ記事（実装レポート）
- **要約**: 7 年分のレビュー履歴から自社向け AI コードレビュアーを構築した事例。収集・分析・蒸留・レビューの 4 ステップで進める。収集は GitHub の REST と GraphQL で PR・変更ファイル・レビューコメントを JSONL に落とし、レート制限対策として期間を半年ずつ区切って再開可能に設計する。ボットのコメント、自己レビュー、単なる LGTM は除外する。分析ではコメント長の中央値やカテゴリ別・レビュアー別の分布を数える。蒸留では規約ファイルを「カテゴリ / 指摘する条件 / 指摘の強さ / コメント例 / 根拠」の構成で作り、各項目に「この指摘は実績◯件」という分析結果を必ず添えて信頼性を与える。レビューは 6 つの担当（リポジトリ規約準拠、バグスキャン、git 履歴と依存関係、過去 PR 突合、コメント整合性、規約チェック）を並列に動かし、担当ごとにモデルを変え、最後に Judge を立てて行番号の正確性と blocker の過剰性を検証する。各指摘には 0 から 100 の信頼度スコアを付け、分類ごとに重みをかけて一定未満を捨てる。既存ツールとの比較実測では指摘件数・カバレッジ・誤検知率などで差が出て、一致率が低かったため相補的な運用を推奨している。前提条件として「レビューの中身が伴っている場合だけ効く。レビューが形骸化していたらデータを集めても意味のある規約は抽出できない」と明記している。

### C. AI Ready なはずだったアーキテクチャと、見えてきた課題・次に目指す状態

- **URL**: https://speakerdeck.com/wxyzzz/2026-07-15-ai-ready-nahasutatutaakitekutiyato-jian-etekitake-ti-ci-nimu-zhi-suzhuang-tai
- **著者/組織**: 和田悠佑 / IVRy（アナリティクスエンジニア / Engineering Manager）
- **公開日**: 2026-07-15（Findy Career Talk #7）
- **種別**: カンファレンス発表（スライド）
- **要約**: セマンティックレイヤーを通じて人と AI の両方がデータを使える 3 層構造の分析基盤を作ったが、運用して 3 つの課題が出た。1 つはデータ信頼性の低下で、Mart の横断利用や Raw Data からのアドホック構築により「人によって数字が違う」問題が再発した。2 つめは資産化プロセスの消失で、依頼なしに個人が解決するようになったため、良い形を作っていたデータエンジニアリングのプロセスが失われた。3 つめはコスト効率の疑問で、個人視点では加速していてもトークン代・処理実行代・組織全体の時間を考えると本当に効率的か不明確である。次に目指す状態は「AI で個人が早い」から「AI で組織が早い」へのシフトで、データ利用パターンの能動的な監視、自動知識抽出の活用、組織エコシステム全体を含む golden path の設計、人と対話する仕組みと学習しやすい仕組みの構築を挙げている。

### D. 「AIに生成させる」から「AIと一緒に考える」へ：要件定義・設計プロセスを見直した話

- **URL**: https://blog.howtelevision.co.jp/entry/2026/07/17/153409
- **著者/組織**: ハウテレビジョン（外資就活ネクスト開発チーム）
- **公開日**: 2026-07-17
- **種別**: ブログ記事（開発プロセス改善報告）
- **要約**: AI が要件から設計まで自動生成する運用をしていたが、実装者の理解不足とジュニア育成の阻害という問題に直面したため、AI の役割を生成者からコーチ兼レビュアーへ転換した。要件定義と設計をフェーズとして分離し、要件定義では開発者がユーザーストーリーと受け入れ条件を作り AI は与件の整理のみを担う。開発者が判断する前に AI がスコープ案やユーザーストーリー案を提示することを禁止し、開発者が案を作ってから AI が足りない観点をチェックリスト形式で返す（最大 2 周）。理解度の確認は要件書の内容をそのまま確認するのではなく「もし◯◯という状況だったらこの要件はどう振る舞うべきか」という設問に開発者が答える形で行う。設計フェーズのレビューは 2 段で、1 周目は良い点と考慮不足の問いのみで修正案を禁止し、2 周目でなお残る論点に限って推奨設計を提示して採否は開発者が言語化する。判断を含むセクション（ADR やアーキテクチャ）は開発者が書き、導出的なセクション（インフラ変更表や監視対象）は AI がドラフトして開発者が検証する。従来型の自動生成は影響範囲が小さいタスクに限る緊急モードとして残し、コーチモードをデフォルトにしてジュニアがなし崩し的に自動生成へ流れることを防ぐ。設計フェーズには緊急モードを置かない。

### E. AIエージェントに議論させよ：マルチエージェント連携による開発プロセスの再設計

- **URL**: https://techblog.lycorp.co.jp/ja/techverse2026-219

- **公開日**: 2026-06（Tech-Verse 2026 記事）
- **種別**: カンファレンス発表の記事化
- **要約**: 専門化した AI ロール同士の構造化された議論に開発プロセスを載せる設計。仕様・実装・デリバリの 3 フェーズで提案者と挑戦者が異なる専門的責務を持ち、オーケストレーターが決定する。討論の型はフェーズごとに変え、仕様はソクラテス式（質問のみで解決策を出さない）、実装は敵対的レビュー（具体的証拠を必須とする）、デリバリは陪審討論（オーケストレーターが最終判定）とする。すべてのタスクが同じ討論強度を必要としないため、リスクに応じて強度をルーティングする。各ターンは構造化 JSON で返し、status・summary・specialistInputs・決定根拠などのフィールドを持つ。人間の介入は開始時の意図定義と終了時の成果承認、および明示的なエスカレーション時のみ。自動化の境界として、ブランチと PR を必須にし、自己マージを禁止し、CI のバイパスを認めない。効果は定性的な記述のみで、単一パスのアシスタントワークフローより仕様が厳密になり問題を早期に表面化させると述べる。数値は記載されていない。振動検知とトランスクリプトの prior 圧縮は対の軸のノートで扱う。

### H. Hermes Agent と Slack で設計し、Linear のチケットから Draft PR まで作成するワークフローの素振りをした

- **URL**: https://azukiazusa.dev/blog/hermes-agent-slack-workflow
- **著者/組織**: azukiazusa
- **公開日**: 2026-07-25
- **種別**: ブログ記事（実装レポート）
- **要約**: 設計担当と実装担当をプロファイルとして分離し、要件から設計書、チケット、Draft PR までを回した実験レポート。設計担当は Slack を窓口にチケット管理と連携し、実装担当はターミナル実行権限を持つ。工程は 3 段（要件を問い詰める、仕様に落とす、チケットに割る）で、各段で変更内容を要約して明示的な承認を得る。工程の省略・順序変更・自動実行は禁止と明記する。エージェントごとに使えるツールを制限する。設計担当が作成・更新できるのは設計成果物 3 種（要件と用語と制約を書く文書、設計判断の記録、実装仕様書）だけに限る。チケットには依存関係と完了条件を設定し、順序が守られるようにする。実装担当は定期実行で動き、同時に着手するのは 1 件だけという制約を持つ。実装・テスト・lint・型チェックがすべて成功したときだけ Draft PR を作り、検証に失敗した状態では PR を作らない。リポジトリ固有の規約は `AGENTS.md` に集約し、ラベルやステータスの新規作成・削除・変更を禁止する。ローカル実行では意図しないファイル操作のリスクがあるためサンドボックス環境を推奨している。
