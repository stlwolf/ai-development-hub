# 強制力をどこに置くか

## 概要

Feedly の Read Later に 2026 年 8 月上旬に溜めた記事から、強制力の置き場という軸で束ねた 5 件の intake ノート。対の軸（統括セッションの設計）は `docs/research/2026-08-13-supervisor-design-intake.md` に分けた。

5 件は「守らせたいことを、どの層に置くか」という同じ問いに、別の段で答えている。ガイドライン、スキル、hook、専用ツール、実行基盤の分離、インフラの事前構築という 6 段の階段になり、当リポジトリは hook と専用ツールの段にいる。5 件のうち 1 件（agentlint）は階段とは直交していて、配備物そのものを静的に検査する話である。

各 claim には検証状態を付す（`evidence-verification-rule`）。`[unverified-summary]` は記事がそう述べていることの要約で、記事の URL を根拠とする。`[verified]` は当リポジトリの実体または API 応答を確認した事実。`[speculation]` は本ノートの推論。

### A. AIエージェントのハーネスを専用ツールへの置き換えで補完する

- **URL**: https://creators-note.chatwork.com/entry/2026/08/04/120000
- **著者/組織**: いまひろ / kubell（認証チーム）
- **公開日**: 2026-08-04
- **種別**: ブログ記事（実運用に基づく）
- **要約**: プロンプトやパーミッションではなく、ツールの実装レベルでエージェントが実行できる操作そのものを制限する戦略。汎用ツールや汎用 API は認証が通る範囲すべてを操作可能にしてしまうため、置き先やリソースを固定した薄いラッパーに置き換える。危険な引数の形を列挙して弾くブラックリスト方式ではなく、できることだけを実装するホワイトリスト方式にすることで、書き漏らしても「実装されていないので不可能」になる。実例として共有ドライブ用の CLI を挙げ、配置先をフォルダ ID で固定し、引数から URL やパスを一切組み立てず、削除機能を持たない設計を示す。副次効果としてコンテキストの節約と推論往復の削減にも触れる。重要な留保として、これは「セキュリティ境界」ではなく「安全装置（セーフティ）」であり、Bash がある限り迂回経路は原理的に残るため、信頼境界はサーバー側の権限設定やトークンスコープに置くべきと明記している。

### B. Golangでのhookを使う理由と実践例

- **URL**: https://tech.talentx.co.jp/entry/2026/08/04/114607
- **著者/組織**: 岸本 / TalentX（エンジニアリング部部長）
- **公開日**: 2026-08-04
- **種別**: ブログ記事（試行錯誤の記録）
- **要約**: Go のプロジェクトで Claude Code がコード生成コマンドを実行しない問題に対し、ガイドライン（CLAUDE.md）→ スキル → PostToolUse フックと段階的に強制力を上げた記録。各段で何が守られなかったかを書いている。ガイドラインはプロンプトの一部なのでモデルの重み付けに委ねられ、コンテキストが長いとき・指示項目が多いとき・タスクが複雑なときに落ちる。スキルは手順の文脈に位置づけると効くが、スキルの数だけ同じことを書く必要があり、別のスキルには効かず、呼び出し自体が Claude Code 次第になる。フックはエージェントの判断とは無関係に発火し、どの経路から作業されても効き、書く場所が 1 か所に集約される。実装上の工夫として、タイミングの決定（Pre から Post への移動）、宣言的マッチャの誤発火対策、ログによる観測性の確保を挙げる。

### C. Claude Code の .claude/ 設定を静的検証する Linter「agentlint」を作った話

- **URL**: https://tech-lab.sios.jp/archives/53730
- **著者/組織**: なーが / SIOS Tech Lab
- **公開日**: 2026-08-04
- **種別**: ブログ記事（自作 OSS の紹介）
- **要約**: `.claude/` 配下の設定ミスをコミット前に検出する Python 製の Linter。検査項目は 4 種で、frontmatter の検証（YAML 構文・必須キー・列挙値・型）、参照切れの検出（環境変数起点のパスと本文の相対パスの実在確認）、hooks 設定の検証（JSON 構文・イベント名・matcher の正規表現・command が参照するスクリプトの実在）、サブエージェント定義に再委譲禁止の記述があるかの確認。finding は AL1xx が frontmatter、AL2xx がファイルシステム、AL3xx が settings と hooks、AL4xx が運用ルールという体系。設計の最優先事項は誤検知をゼロにすることで、「error にするなら保守的に。迷ったら検出しない」という方針のもと、error は構文と構造のエラーおよびスクリプトの実在確認だけに限り、参照切れはすべて warning にしている。配布は pre-commit への統合と CI からの直接実行。

### D. GitHub Actions に AI を組み込んで定型作業を自動化した話

- **URL**: https://tech.revcomm.co.jp/ai-github-actions-automation
- **著者/組織**: 林 / RevComm
- **公開日**: 2026-08-04
- **種別**: ブログ記事（事例紹介・実運用）
- **要約**: 月に 300〜600 件の PR がマージされるリポジトリで、GitHub Actions 上で Claude を動かし定型作業を自動化した 4 事例。安全設計の柱は 3 つで、判定と実行の分離、人間の最終判断の維持、いつでも停止できること。AI には構造化された判定ファイルだけを出力させ（自然言語コメントは不可）、スキーマ検証を通してから後続のステップが承認を実行する。副作用のある処理は AI ではなくスクリプトが担う。セーフティは 3 層で、機械的判定（ファイルパスで判断し AI を使わない）、必ず人間レビューに回す領域のポリシー文書化、AI 分類器。除外条件は「変更の性質」ではなく「触れた領域」で判定する保守的な設計。キルスイッチはリポジトリ変数で承認ステップだけを条件付きにし、判定コメントの投稿は常時行う。運用は週次で数件を人間が事後レビューし、誤判定は反例として分類器のプロンプトの除外条件に追記する。記事は「作業の大半はプロンプトを書くことではなく、AI に何をさせないかを決めることだった」と要点をまとめている。

### E. 非エンジニアが安心してバイブコーディングして公開するには（Exoloop / VibeBox）

- **URL**: https://blog.g-gen.co.jp/entry/next-tokyo-26-vibe-coding-harness-and-vibe-box
- **著者/組織**: 高宮怜 / G-gen（登壇者は TieUps CTO 土井優紀）
- **公開日**: 2026-08-04
- **種別**: カンファレンスのセッションレポート
- **要約**: 非エンジニアが生成 AI でアプリを作り本番公開するときのセキュリティ課題に対する解。AI 駆動開発ハーネス「Exoloop」を Skills / Agents / Hooks / Rules の 4 要素で構成する。Skills が要件定義からデプロイまでの手順とセキュリティ設定の段階的適用、Agents が実装・テスト・レビューを分担して受入基準まで自律ループ、Hooks が機密検査（`gitleaks` による `.env` や API キーの誤コミット検出）と悪性スキルの遮断、Rules がプロジェクト固有のナレッジと規約。SDK「VibeBox」では管理者が Terraform でインフラを事前構築し、利用者は MCP 経由でのみ操作できる。危険なコマンドは自動ブロックされる。固定したのはインフラ構成・IAM・ネットワーク分離・シークレット管理で、開放したのはアプリコード・スキーマ定義・デプロイ判断。

## 取り込み方の判断軸（agentlint）

agentlint については、実際に走らせて実測を取ることは本 intake では行っていない。判断すべきなのは取り込み方であり、選択肢は 3 つある。それぞれの判断材料を残す。

### 選択肢 1: そのまま導入する

- pre-commit と CI に配線し、`.claude/` の検査を外部ツールに任せる
- 有利な点は、実装コストがゼロで、検査項目 4 種が今すぐ手に入ること
- 不利な点は 3 つある。対象がプロジェクトスコープの `.claude/` に限られ、`~/.claude/` は未サポートである。[unverified-summary] https://tech-lab.sios.jp/archives/53730 当環境は canonical を 3 ツール（`~/.cursor/`、`~/.claude/`、`~/.codex/`）へ配布する構成なので、検査の射程が構成と合わない可能性が高い。[verified]（`scripts/sync/` の構成）/ [speculation]（射程の不一致）
- 有効値リスト（`spec.py`）が手動メンテであること、matcher の検証が Python の正規表現による近似であることも記事が限界として挙げている。[unverified-summary] 同上

### 選択肢 2: パターンを回収して自前に作る

- 検査項目、finding のコード体系、誤検知ゼロ優先の方針だけを取り、当環境の構成に合わせた検査を作る
- 有利な点は、3 ツール配布と `~/.claude/` を含む射程で設計でき、既存の `sync --check` と統合できること。#313 が指摘している検査漏れは、そもそも当環境固有の配布構成に由来する
- ライセンスは MIT なのでコードの流用も可能である。[verified] GitHub API（`Shotaro-Yoshinaga-sti/agentlint`、SPDX が MIT）
- 不利な点は実装コストと、検査自体のメンテナンスが増えること

### 選択肢 3: 見送る

- 当面は既存の `sync --check` の穴（#313）だけを塞ぎ、静的検査の一般化はしない
- 有利な点は、対象が明確で作業が小さいこと
- 不利な点は、frontmatter の検証や参照切れの検出という別の型の漏れが残ること

### 判断に必要な材料

- 当環境の `.claude/` と `~/.claude/`、および `~/.cursor/` と `~/.codex/` に、現に何件の設定ファイルと参照が存在するか。射程の広さがそのまま選択肢 1 の適合度を決める
- #286（episode の機械検査）と #313（sync の検査漏れ）が別々に検査を持つのか、共通の検査基盤に寄せるのか。寄せるなら選択肢 2 が自然になる
- 外部ツールを配布物の検査に使うことが、canonical の自己完結性（フォーマットだけで指示が完結する方針）と両立するか
