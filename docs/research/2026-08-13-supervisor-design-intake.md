# 統括セッションの設計

## 概要

2026 年 8 月上旬の Read Later から、統括セッションの設計という軸で束ねた 2 件の intake ノート。対の軸（強制力をどこに置くか）は `docs/research/2026-08-13-enforcement-placement-intake.md` に分けた。同じ日に拾った 7 件のうち、この 2 件だけは強制力の階段に乗らない。扱っているのは「統括役に何を持たせ、何を持たせないか」であり、当環境の統括セッションの運用に直接当たる。

既存の判断を 2 か所で揺さぶる。1 つは最上位モデルを統括に置くという現行方針、もう 1 つは再委譲の扱いである。

各 claim の検証状態は対の軸のノートと同じ規約に従う。`[unverified-summary]` は記事がそう述べていることの要約で URL を根拠とする。`[verified]` は当リポジトリの実体または API 応答を確認した事実。`[speculation]` は本ノートの推論。

### A. 10枚以上のターミナル管理をやめて、AIキャラクターのマネージャーを雇った話

- **URL**: https://toranoana-lab.hatenablog.com/entry/2026/08/04/100000
- **著者/組織**: A.M / 虎の穴ラボ
- **公開日**: 2026-08-04
- **種別**: ブログ記事（実運用の記録）
- **要約**: 並列セッションが 10 枚を超えて管理が破綻したことに対し、音声で会話できる AI キャラクターを常駐のマネージャーとして立てた事例。マネージャーには実装や調査といった実作業を禁じ、仕事をタスク分解・割り振り・進捗管理・報告集約の 4 つに限定した。自分で能力を縛る設計に見えるが、実利が 3 つある。重いファイル読み込み中に返事ができない状態を避けられるので会話がいつでも成立する、調査で大量のトークンを消費して人格設定が薄れることがないのでコンテキストが汚れない、3 件同時に走っていても本人は暇なままなので並列に対応できる。状態はセッションの外に置き、日付・タスク名・状態・担当エージェント・成果物パスを 1 行として台帳に追記する。音声 UI 向けに、口頭の応答は 2〜3 文以内、文頭に感情タグを付ける、長い報告とコードと一覧はファイルへ書き出して口頭では要点と保存先だけ伝える、Markdown 記法は使わない、という設計を取っている。ガードレールは「下書きまでは自由、送信は承認制」。限界として、サブエージェントが `CLAUDE.md` を継承して無限委譲が起き、タスクが二重実行された事例、音声認識が技術用語と固有名詞でほぼ失敗してテキスト入力が主流になったこと、生産性が上がったかは測れていないことを挙げている。
- **参考実装**: `raku2wei/ai-companion-bridge`（MIT）

### B. オーケストレーターではなく調査役に Fable を活用した話

- **URL**: https://zenn.dev/genda_jp/articles/4c50c328c71cee
- **著者/組織**: okkun0524 / GENDA 開発部
- **公開日**: 2026-07-29
- **種別**: ブログ記事（構成変更の記録）
- **要約**: 自作のオーケストレーションツール baton で、最上位モデルを統括席から外して調査席へ移した記録。座席は 5 つで、要件をスコープに割る orchestrator、スコープを管理して worker に指示する scope orchestrator、新設した調査・推論専門の investigator、相談役の buddy、実装する worker。変更前は 2 つの統括席に最上位モデルを置いていたが、統括は読み書きを継続するため換算コストが目に見えて積み上がった。事前のセッションで要件分解を済ませる運用なので、実行中の統括に残る仕事は「もらった情報を適切な担当者に割り振る」ことが中心であり、最上位モデルの知能が常に必要ではないと判断した。統括を下位モデルへ落とし、最上位モデルは新設の investigator に置いた。あわせて scope orchestrator の境界に「調査や分析も自分でやらず investigator に委譲する（自分で調べに行くな）」というルールを追加し、遵守は進捗報告に委譲の発行数を含めさせて外部から確認する。委譲は probe というファイル形式で行い、spec に背景・番号付きの質問・調査範囲・入力パスを書き、findings に質問に対応した番号付きの結論・根拠の `file:line`・答えられなかったものを返す。probe は 2 種に分かれ、何がどこにあるかを探す discovery probe と、既知の入力に対して原因分析や設計選択肢の比較を行う reasoning probe があり、最上位モデルを投資するのは後者である。Claude の advisor tool と同じ概念だと整理している。限界として、統括が「自分で調べた方が早い」と判断して委譲をやめると、見た目の構成は変わらないまま難しい思考だけが安いモデルで静かに行われるリスクを挙げている。

### P3-1 は既存の判断に外部の裏付けを与える

当環境では統括はハンズオンの作業をしないという判断を既に取っている。[verified]（セッション memory `feedback_supervisor_no_hands_on_child_creates_worktree` に記録）A の記事はその理由を 3 つに分解している。会話の即応性、コンテキストの純度、並列対応。特に 2 つ目は当環境の文脈で言い換えると、統括が調査を自分でやるとコンテキストが汚れて統括としての判断精度が落ちる、という話になる。既存判断の理由づけとして使える。[speculation]

### P3-2 は board と handoff の設計に重なる

当環境は親しか書かない正本（board / handoff / 親の訂正）を持ち、そこに検証を乗せる課題が #290 として立っている。[verified] Issue #290 のタイトル。A の台帳は列が 5 つ（日付・タスク名・状態・担当・成果物パス）で、記録タイミングが 3 点（受付・委譲・完了と失敗）に固定されている。当環境の board が持つ列と記録タイミングを見直すときの比較対象になる。[speculation]

### P3-3 はチャネルごとに register を分けるという既存方針と一致する

`output-format-rule` は §9 で operator 向けの平易な散文を求め、agent 間のチャネルと board の電報体を明示的に対象外にしている。[verified] `canonical/rules/output-format-rule.md` §9。A は音声という別の制約から同じ結論に到達しており、「長い報告はファイルへ逃がし、口頭は要点と保存先だけ」という分け方は、当環境が chat と board で分けているのと同じ構造である。[speculation]

### P3-5 と対の軸の AL401 が問題と検査手段の対になっている

A が踏んだ再委譲ループは、サブエージェントが親の `CLAUDE.md` を継承したことによる。当環境の `subagent-strategy-rule` は委譲を積極的に使う方針で、子がさらに委譲することを明示的に禁じてはいない。[verified] `canonical/rules/subagent-strategy-rule.md`。対の軸のノートに記録した agentlint は、サブエージェント定義に再委譲禁止の記述があるかを AL401 として検査項目に持っている。[unverified-summary] https://tech-lab.sios.jp/archives/53730。実害の事例と、その静的検査手段が、別々の記事から同時に出てきたことになる。#293（親が子へ渡す書面を子の受領時に検査する）に対しては、検査対象の候補が 1 つ増える。[verified] Issue #293 のタイトル / [speculation]（対応づけ）

### P3-6 と P3-7 は現行方針と逆を向くが、論点が同じとは限らない

当環境は統括セッションを Fable 5 へ随時切り替える方針を取っている。[verified]（セッション memory `project_fable5_for_supervisor_sessions` に記録）B は逆に、統括から最上位モデルを外して調査席に置いた。

ただし理由の性質が違う。当環境の方針の理由はプランに組み込まれていて使用率が有利という枠の事情であり、B の理由は API 換算コストの積み上がりと役割適性の分離である。前者はコストが実質固定で、後者は変動する。したがって B の結論をそのまま当環境に適用できるとは限らない。[speculation]

一方で、役割適性の議論は枠の事情とは独立に成立する。B の主張は「事前に要件分解を済ませる運用なら、実行中の統括に残るのは割り振りであって最上位モデルの知能を常に要さない」であり、これはコストがゼロでも「最上位モデルを置く場所として統括が最適か」という問いになる。当環境の統括は決定・fact-check・人間ゲート・委譲に専念する設計なので、この問いは当てはまる。[speculation]

**あわせて記録すべき観察がある。** B はコスト半減を狙って統括に Opus 5 を試したが、判断ミスに加えて調査や把握の漏れが目についたため Fable の継続を選んだと書いている。これは体感であり計測ではないと著者自身が区別している。[unverified-summary] https://zenn.dev/genda_jp/articles/4c50c328c71cee。統括のモデルを下げる判断をするときの反証材料になる。

### P3-8 は返却契約の一形態である

probe の findings は、質問への番号付き対応、根拠の `file:line`、答えられなかったものの明示という 3 点を要求する。当環境の `implementer-contract` は status enum・報告フォーマット・self-review・スコープ外報告を要求しており、構造が近い。[verified] `canonical/CATALOG.md`（implementer-contract の説明）。特に「答えられなかったものを返す」は、当環境の失敗分類（#60）と接続しうる。[speculation]

**probe が 2 種に分かれている点が新しい。** discovery（何がどこにあるか）と reasoning（原因分析や選択肢の比較）を分け、最上位モデルを投資するのは後者だけとしている。当環境の委譲は brief と addendum で行われ、この 2 分類を持たない。[verified]（`doc-flow-guardrail` と `delegate-task` の構成）委譲の種類によってモデルを変える判断の入口になる。[speculation]

### P3-9 は #281 の測定軸の候補になる

統括が委譲をやめても構成は変わらないので、外形からは劣化が見えない。B の対策は、進捗報告に委譲の発行数を含めさせて外部から数えることである。#281 はオーケストレーションのフロー可視化と情報価値の測定を扱っている。[verified] Issue #281 のタイトル。「規律が守られているかを、成果物ではなく発行数のような副産物で数える」という形は、測定軸として使える。[speculation]
