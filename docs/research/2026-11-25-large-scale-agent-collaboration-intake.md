# 大規模なエージェント協業の型

## 概要

2026年11月に、自律エージェントの大きな協業の事例が2つ公開された。Amazon Web Services（AWS）は、クラウドの API のエミュレータを数百体のエージェントに作らせ続けており、人はコードを書かず、レビューもしていないと述べた。OpenAI は、性能の劣化を見つけて直す作業を、状態を持つ task とエージェントの組み合わせで回す仕組み（Performance Factory）を公開した。

この2つを読んだきっかけは、「大きな更新の作業（たとえば Web アプリのフレームワークのメジャー更新）を、人の作業を最小にして数か月かけて進められるか」という問いである。更新後のアプリを「更新前のアプリを再現するエミュレータ」と見なすと、AWS の事例と同じ構造になる。そう考えたうえで、作業の種類に依らない型を取り出した。

2つの事例は役割が違う。AWS の事例は「正解の基準をどう作るか」を示し、OpenAI の事例は「エージェントの工場をどう回すか」を示す。どちらも、統括が子を見る形を取っていない。作業の状態を外に置き、機械が配り、統括に当たる役は普段の流れに入らない。今の orchestration-engine は統括が子へ送って報告を読む形なので、この点が engine の方向性（#618）を決めるときの比較の軸になる。

このノートは、型と、hub の資産との対応と、定額のプランの上限の中で回すときの消費の実測を残す。新しい道具や試作は作らない。

### P1: 外の正解を先に作る

AWS の事例が成り立つ理由は、エージェントの数ではなく、実物の AWS という正解があることである。テストを作るチームは、作った場面を実物で確かめてから保存する。直すチームは、そのテストを書き換えられる立場にいない。合否は、エージェントの判断ではなく、実物との一致で決まる。

実物が外に無い作業では、正解を自分で作ることになる。大きな更新の作業なら、更新前の振る舞いを記録して正解にする。この手法には分野の名前があり、特性テスト（characterization test）またはゴールデンマスターテストと呼ぶ。今の振る舞いが意図どおりかどうかは問わない。意図と違う振る舞いも、そのまま正解として残す。直すのは別の作業にする。

正解を作るときに決めることは4つある。この4つは記事に無く、本ノートの推論である（`speculation`）。

- **入力の集め方。** 公開された仕様が無い対象では、入力を集め直す。元は3つある。あるもの（コードの入口の一覧）、呼ばれているもの（呼び出す側のコード）、実際に使われているもの（アクセスの記録）である。3つの食い違いは、それ自体が成果になる。
- **出力の取り方。** 入力はコードを読んで挙げ、出力は実行して記録する。エージェントがコードから推測した出力を正解の欄に書かせない。
- **網羅の測り方。** 分母（入口の数）が先に決まるので、何件を記録したかを数えられる。分岐に届いたかは、コードカバレッジで測る。止める条件は、始める前に決める。
- **毎回変わる値の扱い。** 時刻・乱数・発番される ID をどう揃えるかの規則を、正解の一部として最初に決める。決めないと、差が出るたびにエージェントが自分で判断することになる。

OpenAI の事例では、正解は「デプロイのあとに、本番の指標が元の水準に戻ったか」である。エージェントは回復を確かめてから task を閉じ、部分的にしか戻っていなければ残りを新しい task にし、戻っていなければ調査へ差し戻す。

正解を外に置いても、機械で比べられない性質は残る。AWS は、エミュレータを本番の用途とセキュリティのテストに使わないよう README に書いている（`verified`）。エミュレータが IAM のポリシーを評価しないこと、長時間の稼働と負荷の試験をしていないことは、二次の報道にだけあった（`unverified-summary`: https://www.helpnetsecurity.com/2026/11/12/aws-ai-agents-built-emulator/ ）。大きな更新の作業でも、性能・セキュリティの性質・同時に動いたときの振る舞いは、出力の一致では確かめられない。これらは最初から人の作業として計画に入れる（この段落の後半は、本ノートの推論である。`speculation`）。

### P2〜P4: 状態を外に持つ task・dispatch・出来事で起こす

OpenAI の仕組みは、4つの部品でできている。

- **task service。** workflow ごとに、設定のファイルと指示の Markdown を置く。設定には、task が取りうる状態、許される遷移、人が要る段を書く。指示は状態ごとに分ける。記事の例では、コードの変更の workflow が、設定のファイルと「実装中」「レビュー中」の2つの指示でできている。
- **dispatch loop。** 準備のできた task を定期的に探し、その状態の指示でエージェントを1回起こす。エージェントは進み具合を task に書き、段が終われば次の状態へ動かす。
- **クラウドでの実行。** エージェントは service identity で動く。権限を絞れて、どの操作がエージェントのものかを追える。
- **購読。** 人やデプロイを待つ task は、出来事を購読して止まる。出来事が届くと task が再び準備完了になり、dispatch loop が拾う。

この形で効いている点は3つある。

1. 状態と所見が task にあるので、エージェントの会話が短く済む。別のエージェントや人が、途中から引き継げる。
2. 送る側と受ける側のあいだで、メッセージを受け渡さない。届いたかどうかを確かめる処理が要らない。
3. 待つあいだにエージェントが動かないので、待ちで消費が出ない。

workflow は別の workflow の task を立てられる。記事は、劣化の候補を見つける workflow が、原因を追う workflow の task を立てる形を挙げている。

### P5: 役割を分け、反証役を当てる

AWS は、テストを作る・差を見つける・直すの3つを別のチームにし、取り込む前にレビュー役のエージェントを当てている。OpenAI は、診断を出したセッションとは別のセッションに、その診断を反証させている。反証役は、前提を確かめ直し、反対の場合を試す。たとえば、ある変更が原因なら、その変更に当たっていない要求は健全なままだったか、を見る。記事には、反証役が「原因とされた側はすでに回復しているのに、失敗が続いている」ことに気づいて調査を差し戻した例がある。

ここから取り出せる規則は、書く権限を役割で分けることである。直す役は正解を書き換えられない。確かめる役はコードを直せない。状態を変えられるのは機械の層だけにする。作った側が自分で採点する経路を残さない。

反証役を置いても、精度には限りがある。OpenAI は、原因の推定 100 件を人が採点した結果、正確だったのは 70% で、残り 30% は手直しが要るか因果を示し切れていなかったと書いている。修正は診断より難しく、必要以上に複雑な修正や、新しい問題を持ち込む修正があったとも書いている。構成の判断（たとえば、キャッシュを足すと速くなるが古いデータが出る）は人に回している。

人の関門の置き方は、2つの事例で違う。AWS は人のレビューを外した。OpenAI は、PR を人が見て、取り込むかを決めている。違いの理由は記事に書かれていないが、作るものの性質が違う。AWS のエミュレータは開発用の道具で、本番の用途に使わないよう明記されている。OpenAI の対象は本番のサービスである。本番のデータを扱う対象では、人の関門を残す側に倒すのが妥当だと読める（`speculation`）。

### P6: 人の注意を判断に使わせる

エージェントは、人が読める量より多くの調査をこなす。OpenAI の最初の版は、所見で埋まった画面を人に渡した。どれが大事かは、人が決めるしかなかった。今の版は、関連する障害をつなぎ、チームが気にする指標ごとにまとめ、影響の見積もりで並べる。task ごとの要約には、指標の推移や flame graph を付け、人が根拠をその場で確かめられるようにしている。

ここから先の、聞く条件と聞き方は、記事に無い。本ノートの推論である（`speculation`）。

人に聞く条件は、先に決めておく。決めずに回すと、エージェントは何でも聞くか、黙って決めるかのどちらかに寄る。大きな更新の作業なら、聞くのは次の4つに絞れる。

1. 公式の新しい方法に不都合がある場合。
2. 事実上の標準になりうる、別の手段がある場合。
3. 更新が強制する差を消せない場合。
4. 依存しているものに、更新後に対応した版が無い場合。

聞く前に、選択肢ごとの影響を測らせる。正解の記録があれば、エージェントに選択肢をそれぞれ試させて、差の件数を出せる。同じ選択は多くの箇所に出るので、原因ごとに1回だけ聞く（P9）。決めたことは規則として残し、同じことを二度聞かない。

### P7: エージェントの変更を過去の事例で試験する

指示やモデルを変えると、得意な事例と苦手な事例が入れ替わる。OpenAI は、過去の障害を試験の一式にして、変える前に流し直している。試験の条件は細かい。

- 毎回、新しいエージェントに、答えが分かる詳細を除いた元の信号だけを渡す。
- 保存したメモ、障害の報告書、前回の結果は見せない。
- 終わったあとに会話の記録を読み、答えが漏れていなかったかを確かめる。
- 時期が合っていても、原因を取り違えることがある。開始の時期・規模・影響を受けた要求・原因の順位づけを、別々に採点する。

人に渡す要約は、保存した task の写しで試験する。別の採点役が、その仕組みを知らない人が読んで分かるか、役に立つ図が残っているか、次の一手が根拠に支えられているかを見る。

### P8: 道具の故障を拾って自分で直す

エージェントが使う道具が壊れていても、最後の報告からは分かりにくい。OpenAI は、エージェントを毎日1回走らせ、最近の実行の記録から道具の失敗と権限のエラーを探している。同じエラーが何件もの調査を止めていれば、直す task を立てる。原因がはっきりしていればエージェントが修正を出し、人がレビューする。直したあとは、前に止まっていた段を越えられるかを試験で確かめる。

### P11・P12: 上限を天井にする・台数は期間を決める

2つの記事は、費用にも、使ったモデルにも触れていない。ここは手元の測定と推論である。

定額のプランには、短い時間の上限と週の上限がある。専用のプランを1つ用意し、その上限を天井にすれば、費用は固定になる。残る変数は、上限の中でどれだけ進むかと、何か月かかるかの2つである。上限の中の効率は、次の3つで上がる。

- 待ちで枠を空けない。判断を待つ作業があっても、判断に依らない作業が一覧に残っているようにする。
- 消費の出ない作業（テストの実行、記録の流し直し、差の比較）を、機械の層に寄せる。
- 会話を短く保つ。下の実測では、これがいちばん大きい。

1つのプランを全員で分け合うので、進み方は台数ではなく上限で決まる。数十体を並べても、上限に早く当たって全員が待つだけになりうる。

作業が互いに独立なら、総額は作業の総量で決まる。並べる台数で決まるのは期間である。台数を増やして高くなるのは、同じ箇所を同時に直して衝突する分と、取り込み直す分だけである。

## 追記（2026-11-27）: 3つ目の事例との対応

本ノートのあとに、Claude Code のチームが検証とコードレビューの進め方を書いた2本の記事を読んだ。主題は検証の層の運用で、`docs/research/2026-11-27-verification-layer-intake.md` にまとめた。ここには、本ノートの型と関連の強い点だけを書く。出どころは、どれも https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/ である（`verified`）。

- **P1（外の正解を先に作る）。** 記事は、新旧に同じ入力を流して比べる差分テストを「the old system is the oracle」と呼び、挙動を変えない大きな移行に特に有効だと書く。本ノートが推論として挙げた4つの決めごとのうち、2つに裏付けが付く。入力は、ランダムに作ったものか、本番のトラフィックの標本から取る。無関係な差を揃え、新しい環境では違ってよいと承認した変更の一覧を持つ。
- **並べられる台数は、検証で決まる。** 検証の仕組みが無いと、人が全部を確かめることになり、エージェントは1〜2体しか回せない。あれば、数十から数百体を並べられる、と記事は書く。本ノートの P12（台数は期間を決める）の手前にある前提である。
- **P5（役割を分け、反証役を当てる）。** レビューの基準は、base のブランチから読み、PR の変更からは読まない。変更が、自分を判定する検査を書き換えられないようにする。書く権限を役割で分ける、という本ノートの規則の具体例である。
- **止める条件。** 検査が3回直しても通らなければ、エージェントは止めて人を呼ぶ。
- **P7（エージェントの変更を過去の事例で試験する）。** 過去の障害と revert を題材に、レビュー役が実際に不具合を見つけるかを測る。問題なく動いている変更を対照に置き、調整に使う組と評価に使う組を分ける。
- **P8（道具の故障を拾って自分で直す）の隣。** 見逃しを規則にする条件（2件以上に出た型で、差分から見分けられるもの）と、増えた規則を定期的に片付けることが書かれている。

## 消費の実測（2026-11-13）

Claude Code の会話の記録 30 日分から、エージェント1体を1時間動かす消費を測った。

**測り方。** 会話の記録（JSON Lines）から、応答ごとの usage を読む。同じ応答が複数の行に出るので、応答の ID で重複を除く。「動いていた時間」は、セッションごとに、応答と応答の間が基準より短い区間を足したものとする。基準は 5 分と 15 分の2通りで測った。費用は、Claude の API の料金（2026-11 時点。Opus 5.5 は入力 4 ドル・出力 20 ドル・cache の読み込み 0.20 ドル、いずれも 100 万 token あたり）に換算した。1時間保持する cache の書き込みは、入力の2倍（Opus 5.5 は 100 万 token あたり 8 ドル）として計算した。倍率は料金表（https://platform.claude.com/docs/en/about-claude/pricing ）のとおりである。

**結果。**

| 項目 | 値 |
|---|---|
| セッション | 532 |
| 応答の回数 | 64,682 |
| 動いていた時間（延べ） | 346 時間（基準 5 分）〜545 時間（基準 15 分） |
| cache の読み込み | 243 億 6,110 万 token |
| cache の書き込み | 5 億 7,200 万 token |
| 出力 | 6,680 万 token |
| 1時間あたり（Opus 5.5 の料金に換算） | 約 19〜31 ドル |
| 1時間あたり（Sonnet 5.5 の料金に換算） | 約 10〜15 ドル |
| 費用の内訳 | cache の読み込み 46%・cache の書き込み 41%・出力 13% |

**読み取れること。**

- 費用の 8 割以上が、会話の読み直しと書き込みである。出力は 13% にすぎない。
- 1回の応答で、平均して約 38 万 token を読み直している（読み込みの合計を応答の回数で割った値）。統括のように長く続く会話が多いためである。
- この換算のまま 24 時間動かすと、10 体で月に約 14 万〜22 万ドル、100 体で月に約 140 万〜220 万ドルになる。従量の料金で今の使い方のまま台数を増やす道は、現実的でない。
- 逆に言えば、作業を「1体に1件」（P10）にして毎回新しい会話で始め、状態を外に置けば（P2）、読み直す量が大きく減る。下がり幅は測っていない。

**限界。** 測ったのは1人の利用者の、統括と子が混ざった記録である。定額のプランでの利用なので、換算した額は実際の請求ではない。記録の約 8 割は Opus 5.5 で、残りには単価の高いモデルが含まれるが、すべて Opus 5.5 の料金で計算した。

## engine への示唆

今の engine は、統括が子へ送り、子の報告を読んで判断する。数体なら成り立つが、数十体に増やすと、統括の文脈と注意が先に尽きる。送る形で起きている失敗（届いていないのに成功を返す、入力欄に別の文字が残る、止めの指示が受領の返事まで効かない）も、台数に比例して増える。

2つの事例は、この問題を、統括を強くする方向では解いていない。統括に当たる役を、普段の流れから外している。この形は、共有の作業板を独立した役がそれぞれ読み書きする設計に当たり、一般にはブラックボード型と呼ばれる。この呼び方と下の役の表は、2つの記事には無い。本ノートが2つの事例を整理し直したものである（`speculation`）。

| 役 | LLM か | 書いてよいもの | 書いてはいけないもの |
|---|---|---|---|
| 機械の層 | LLM ではない | 作業の状態、判定の結果 | コード、テスト |
| 作る役 | LLM | 担当する1件の成果物 | 正解、作業の状態 |
| 確かめる役 | LLM | 合否と理由 | 成果物 |
| 統括 | LLM（少数） | 計画の組み直し、人への問い | 普段の流れには入らない |
| 人 | — | 選択肢の判断 | — |

#618 のフェーズ3 で比べる案は、少なくとも3つある。

1. 今の形を続け、送り方と見張りを直す。
2. 今の engine に、状態の正本・期限つきの取得・file による完了の判定を足し、統括を例外だけに下げる。
3. 既にある道具（画面を持たない実行、ハーネスが持つ複数エージェントの仕組み、クラウドで動くエージェントの基盤）に乗り換える。

どの案でも、決まった動きをする部分（状態の正本と判定）は要る。そこを先に作れば、エージェントの側の回し方は、あとから差し替えられる。
