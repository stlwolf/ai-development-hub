# エージェントの検証の層の作り方と保ち方

## 概要

Claude Code のチームが、2026-10 と 2026-11 に、コードレビューと検証の進め方を2本の記事で公開した。コードの約 90% をエージェントが書いてレビューしている、と述べている。その規模で、検証の層をどう作り、どう信用できる状態に保つかが主題である。

2本の主張の芯は同じである。検証の仕組みが無いと、人が全部を確かめることになり、エージェントは1〜2体しか回せない。あれば、数十から数百体を並べられる。そのとき人の仕事は、差分を全部読むことから、「完了」の定義を決めて証拠を見ることへ移る。

`docs/research/2026-11-25-large-scale-agent-collaboration-intake.md`（以下、協業のノート）は、同じ問題を「正解の基準」と「工場の回し方」から見た。本ノートは、その間にある検証の層を扱う。取り出した型は3つの束に分かれる。

- **何で確かめるか。** 動かして確かめることと、投資する価値のある3種類のテスト。
- **検証の層をどう守るか。** 変更は自分の検査を書き換えられない。承認は1つの commit にだけ効く。新しい関門は観察だけのモードから始める。
- **検証の層をどう育てるか。** 検査する側を検査する。見逃しを規則にし、規則を片付ける。

当リポジトリには、対応する資産が多い。コミットのゲート、セカンドオピニオン、PR のレビューのスキルである。主張が逆を向く点も1つある。記事は、レビュー役を重ねるより1体を調整するほうがよいと書く。当リポジトリの強い SO は、複数のレーンが合意するまで回す。

### 何で確かめるか（P1〜P3）

記事 A は、テストより先に「変更を動かす」ことを置く。Web の変更ならブラウザを操作させ、モバイルならシミュレータを使わせ、バックエンドなら手元でサービスを動かさせる。動かし方（シミュレータの起動やアプリの起動）は、`verify` という名前の skill に書き、リポジトリの `.claude/skills/` の、関係するコードの近くに置く。エージェントは、commit の前にこの skill を使う。記事は、この skill を速く確実にすることに投資するよう勧めている。ほぼすべての変更を、この形で確かめているという。

テストの種類では、3つを挙げる。

- **E2E テスト。** 1つだけ選ぶならこれ、と書く。利用者の実際の流れ（カートに入れ、決済し、確認の画面へ進む）を記述する。機能の全体が動くか動かないかで決まるので、騙しにくい。完了の条件がはっきりしていて、何が壊れたかを具体的に示せる。単体のテストは速くて安定するが、通っても機能が壊れていることがある。
- **プロパティテスト。** 「壊れるはずがない」と思う性質を書き、ライブラリに数千の入力を作らせて反例を探す。例として、往復の符号化（符号化して復号すると元に戻る）、不変の条件（残高は負にならない）、冪等性（2回行っても1回と同じ）、等価性（最適化したコードが素朴で正しいコードと同じ結果を返す）を挙げる。入力が、元のコードを書いたエージェントと同じ偏りを持たない点が効く。仕様が本番の振る舞いからずれて、検証の拠り所にならなくなった書き直しで、特に役に立つと書いている。
- **差分テスト。** 見出しは「the old system is the oracle」である。挙動を変えない大きな移行に、特に有効だと書く。新旧に同じ入力を流し、結果が違えば、不具合か破壊的な変更である。決めごとは2つある。入力は、ランダムに作ったものか、本番のトラフィックの標本を使う。空白のような無関係な差を揃え、新しい環境では違ってよいと承認した変更の一覧を持つ。

どの種類でも避ける失敗が2つ挙がっている。テストが不安定だと、エージェントは壊れたコードを直さずに、テストを流し直すことを覚える。テストが遅いと、エージェントはまとめて流すようになり、どこで壊れたかを絞りにくくなる。

冒頭には、数字が1つある。構造を持つファイルを作らせる内部の試験で、別の採点役に基準に照らして確かめさせると、通常の指示の繰り返しに比べて、作業の成功率が最大で 10 ポイント上がった。上がり幅は、難しい問題ほど大きかった。試験の題材と基準の中身は書かれていない。

### 検証の層をどう守るか（P4・P7・P8）

**3回で人に渡す（P4）。** 誰もすべての変更は読めないので、失敗を、人が見るものを決める手がかりにする。検査が落ちたらエージェントが直し、3回直しても落ちるなら、止めて人を呼ぶ。記事 B には、この上限が無かったときの失敗がある。ある PR が、作者が止めるまでに、一晩で 50 回を超えるレビューの回を重ねた。直し方として、回の上限（3回を超えたら、作者にやり方の見直しを求める）、最初の数回のあとは差分だけを見直すこと、すでに出した指摘を繰り返さないことを挙げている。原因も調べている。レビュー役が繰り返し指摘していた箇所を git blame で見ると、約 59% は、最初のレビューの時点からあったコードだった。レビュー役は、新しい不具合を見つけていたのではなく、回ごとに古い不具合を少しずつ足していた。チームは、回を重ねるのを既定にしていた自分たちのやり方が、これを悪くしたと書いている。危険な変更には意味があるが、すべての PR に行うことではない。直す前後の数字も載っている。1回のレビューと修正で通る割合は 65% から 78% に上がり、5回以上かかる割合は 8.9% から 1.5% に下がった。

**変更は自分の検査を書き換えられない（P7）。** 記事 A は、「変更が、自分を判定する検査を変えられるなら、その検査は壊れている」と書く。レビューの基準（`REVIEW.md`）は、base か既定のブランチから読み、PR の変更からは読まない。レビューは commit に対して行う。レビューの最中に push があれば、その結果は使えない。古い commit に対する合格には、意味が無い。記事 B も、承認は1つの commit にだけ効くと書く。エージェントの push や手で解いたマージのように、仕組みが保証できない新しい commit が入ると、承認をやり直す。

安い検査を先に流すことも、同じ節にある。エージェントが手元で確かめる前に push すると、共有のレビューと CI の時間を使う。PR を開く前に、エージェントがテスト・ビルド・lint を流す。これは、エージェントが終わるときにテストを流す hook で強制できる、と書いている。

**観察だけのモードから始める（P8）。** commit ごとに、どう検証したかを刻む。「none」も刻むので、検証されなかった commit をあとから数えられる。そのうえで、セッションの中でコードレビューか検証を実行していなければ commit を止める関門を作った。モードは3つある。off、observe、enforce である。observe は、止めたはずのものを記録するだけで、誤って止める例を洗い、誰にも影響が出ないことを確かめるために使う。enforce は commit を止める。逃げ道が2つある。commit のメッセージに、検証しなかった理由を書ける。同じセッションで2回止めたら、3回目は通す。エージェントが詰まらないようにするためである。

### 検証の層をどう育てるか（P5・P6・P9・P10）

**差分で発火させる（P5）。** 信頼性のチェックリストは 39 項目ある。項目ごとに、差分から読める発火の条件、確かめる内容、元になった障害か PR を持つ。エージェントは差分を読み、条件に合う項目だけを確かめる。ふつうは 3〜10 項目である。過去の障害を、誰も覚えておかなくて済む。検査を書くのは、そのコードの持ち主である。持ち主が指摘するものを検査が指摘するようになるまで、調整する。検査が人を呼ぶときは、理由を言わせる。

**レビュー役を重ねない（P6）。** 記事 A は、レビュー役を足してレビューを良くしようとはしない、と書く。主のレビュー役の上に、高い2体目を足すのは、主を調整するより悪い手になることが多い。代わりに、そのコードで何を見るかを `REVIEW.md` に書く。回を重ねるときは、前の回と過去の失敗の文脈を引き継ぎ、全部を最初から見直さない。そのほうが安く、多く見つかる。

ただし、記事 B の AI のレビューは、中で複数のエージェントを使っている。複数のエージェントが並んで不具合を探し、別の組の検証役が指摘ごとに投票し、十分な数が同意した指摘だけを出す。記事 A の「重ねない」は、この仕組みの上に、さらに別のレビュー役を足さないという意味だと読める（`speculation`: 2本の記事を並べた、本ノートの読み）。

**検査する側を検査する（P9）。** チームは、レビュー役を定期的に見直す。見ている数字は3つある。マージされた変更のうち revert されたものの数、保守する人がマージの前に退けた変更の数、問題が出ていない変更のうち大きさを揃えた組、である。正式な評価もある。過去の障害と revert ごとに、レビューの時点の状態にリポジトリを戻し、不具合が何だったかを1文の答えとして用意する。その不具合を正しく述べた指摘だけに点を付ける。マージされて安定している変更を対照に置き、指摘しすぎを防ぐ。調整に使う組は、評価に使う固定の組から分ける。

再現率は、段ごとに分けて見る。最初に出た指摘、検証を通ったあと、最後のレビュー、の3つである。分けると、いったん見つけた不具合を、仕組みが途中で落としていないかが分かる。全部を1つの点数にまとめる評価では、これが見えない。

指摘の正しさのほかに、直すことの重さも見る。指摘には、Important、Nit、Pre-existing の札を付ける。Pre-existing は、その PR が持ち込んだのではない不具合を指し、作者の責任にしない。再現率を上げる調整は、次の改善が、不具合を捕まえることではなく評価への過剰な合わせ込みになるところで止める。

記事 B は、雑音の測り方も書いている。指摘ごとに、PR の作者がどう応じたか（直した、誤りだと言った、意図したものだ、どうでもよい）を見る。問題が無いと分かっている PR にもレビュー役を流し、害のある変更につながる指摘を数える。作者がエージェントのときは、雑音の費用が上がる。人は細かい指摘を数秒で流せるが、エージェントは直してしまい、commit とレビューの回がもう1つ増える。優先の順は、本物の不具合を捕まえることが先で、回を減らすことが次だと、書いて決めている。

レビュー役が何を読むかも書かれている。差分を、リポジトリの全体と、PR が述べている意図に照らして読む。`REVIEW.md` の良いものは短く、そのリポジトリで失敗がどう見えるかを言う。例として、文書なら「嘘を書いている」、設定なら「誤った先へ流す」を挙げている。

**見逃しを規則にし、規則を片付ける（P10）。** 見逃しを規則にする方法は2つある。

1. 人のレビューのコメントと PR の revert から、型を取り出す。2件以上の PR に出ていて、差分から見分けられるものだけを、規則の候補にする。3体のエージェントが反証を試み、人が PR でレビューして承認する。
2. 既知の障害に結び付いた PR に、3体の不具合探しを流し直す。2体以上が見つければ、検出できる不具合である。小さい差分で見逃したなら、`REVIEW.md` の規則にする価値のある穴である。

不安定なテストも同じ扱いにする。エージェントは、飛ばすことも、待ちを足すことも、通るまで流し直すこともできない。根本の原因が見つからなければ、テストを消して、理由を書き残す。

規則にも片付けが要る。テストの一式、検証の手順、Markdown の文書は、放っておくと増える一方なので、定期的に整理する。

冒頭には、検証の結果をエージェントに返す話もある。エージェントが、ログに利用者のデータが出ていないかを見るテストに何度も落ちるなら、hook か、より明示した規則を作る。

### 人の承認を、危険の度合いで決める（P11）

記事 B は、人の承認の数を、変更の危険の度合いで決める。度合いは、作者ではなく変更の中身から、分類器が判定する。低いものは、自動の検査が通れば人が要らない。中くらいのものは1人、高いものは2人が要る。必ず人が見る経路がある。持ち主が機微だと挙げた経路と、CI の workflow のファイルである。軽い経路を使えるのは、そのリポジトリの信頼する作者の一覧に載っている人だけで、ほかの人の変更には、もう1人の承認が要る。エージェントの承認は、人の承認には数えない。エージェントが書いた PR では、エージェントに指示した人が、必要なレビュアーの1人に数えられる。

人に残る仕事として、記事 B は次を挙げる。作るかどうかを決めること（方向・趣味・範囲）、危険なコードのレビュー、ほかが真似る構造のレビュー、証拠（テストの出力・実行したコマンド・画面の写し・レビュー役の指摘）を読むこと、結果に責任を持つこと、である。

足りないものも書いている。revert と障害の数が増えたときに、承認を自動で厳しくする仕組みは、まだ無い。人が見ないマージを増やす前に、それが欲しいという声がある。

## 主張が逆を向く点

記事 A は、レビュー役を重ねるより、1体を調整するほうがよいことが多いと書く。当リポジトリの強い SO（`peer-ai-review`）は、複数のレーンが合意するまで回す。どちらが正しいかを、このノートでは決めない。比べるときの論点を残す。ここは本ノートの推論である（`speculation`）。

- **対象が違う。** 記事の主張は、コードの不具合を探すレビューについてのものである。当リポジトリの SO は、設計の判断と plan の反証にも使う。不具合には、過去の障害という答えがあり、レビュー役を調整できる。設計の判断には、そういう答えが少ない。
- **調整できる前提があるか。** 記事のチームは、障害と revert の組を評価に使い、主のレビュー役を毎日測っている。当リポジトリには、SO のレーンの当たり外れを測る仕組みが無い。測れないものは調整できないので、重ねるほうに倒れている。
- **記事の仕組みも、中では複数である。** 記事 B の AI のレビューは、複数の不具合探しと、指摘ごとに投票する検証役でできている。記事が退けているのは、その上にさらに別のレビュー役を足すことである。
- **記事の比較には、別の系統のモデルが入っていない見込みである。** 記事を書いたのはモデルを作っている会社のチームで、記事に出てくるレビュー役はどれも自社のモデルである。ほかの会社のモデルをレビューに使った、という記述は無い。記事が比べているのは「同じ系統のレビュー役を、調整するか、もう1体重ねるか」だと読める。当リポジトリの SO は、別の会社のモデルをレーンに入れている。2体目が同じ偏りを持つ場合と、違う偏りを持つ場合では、重ねる効き目が違いうる。記事の結論を、そのまま当てはめることはできない。
- **数と調整は、別の軸である。** 「1体か2体か」と「調整するかしないか」は、分けて見る必要がある。記事が言っているのは、調整の余地が残っているうちは、重ねるより調整が先だということである。調整を尽くしたあとに重ねる効き目が残るのか、2体のときは調整の中身を変える必要があるのかは、記事からは分からない。

### 外の測定と、当リポジトリの記録

上の論点のうち2つには、外の測定がある。最初の版は、同じ日の調査メモ（`docs/research/investigations/2026-11-27-autonomous-loop-and-harness-evidence.md`）を通して数字を引き、原典を開いていなかった。2026-11-27 に原典を開いて照らしたところ、数字は合っていたが、読み方が強すぎる所が3つあった。この節は、照らした結果で書き直したものである。数字は、原典の本文に同じ値があることを確かめた（`verified`）。確かめられなかったものは、その場に書く。

- **別の系統の上位モデルを足すと、見つかる誤りが増える。ただし、効いたのがモデルの違いなのか、レビュー役を1つ足したことなのかは、分けられていない。** 同じモデルの新しいセッション（F1 は 28.6%）と、別の会社の上位モデル（32.3%）のあいだに、有意な差は出なかった。著者は、これは同等であることを示すものではない、と書いている。2つを組み合わせると、見つかる誤りの割合は、同じモデルを2回使った場合の 42.7% から 56.7% に上がった。一方、別の会社のモデルを2回使った場合と、混ぜた場合を比べると、有意な差は無かった（145 件中 76 件と 82 件、p=.184）。レビュー役は、それぞれ違う道具と指示のもとで動いていたので、モデルの違いだけを取り出した比較にはなっていない、とも著者は書いている。差が出たのは文書の題材で、コードの題材では、同じモデルの新しいセッションのほうが高かった（https://arxiv.org/html/2610.01471v2 ）。
- **別の会社のモデルを足した実務の報告は、著者が数字を取り下げている。** 最初の版が引いた「網羅率が 33.6% から 57.1% に上がった」は、著者が後の版で訂正した。調査役の報告では、訂正後の値は 47.2% から 72.3% で、著者は、これはレビュー役の数に対する曲線であって、会社の違いの効果ではない、と書いている。訂正版（https://zenodo.org/records/21328807 ）は、取りまとめた側では開けていない（`unverified-summary`）。
- **新しいセッションのレビューは、同じセッションでの見直しより高い。** 新しいセッションに成果物だけを渡す条件の F1 は 28.6% で、同じセッションでの自己レビュー（24.6%）と、同じセッションでの2回目の見直し（21.7%）を上回った。最初の版は「親の文脈を引き継ぐサブエージェントのレビューは高くなかった」と書いたが、その条件は、親の会話を引き継ぐものではない。生成のときの依頼文と成果物を、新しいセッションに渡す条件である（F1 は 23.8%）。作り手の依頼文を渡すと下がった、と読むほうが近い。使ったモデルは1つである（https://arxiv.org/html/2603.12123v1 ）。
- **LLM のレビュー役は、見逃しを補う検出器としては使えるが、合否を決める役には向かない。** LLM の検証役は、不合格の提出の 22〜49% を承認した（https://arxiv.org/html/2605.07073v1 。この数字は、取りまとめた側では照らしていない。`unverified-summary`）。
- **誤りは、会社が違っても重なる。** 350 を超えるモデルの調査では、両方のモデルが誤ったとき、約 60% で同じ誤答を選んだ。正確なモデルほど、誤りが相関した（https://arxiv.org/html/2506.07962v1 ）。9つのモデルを判定役に並べた研究では、全員が一致した項目でも 9.1% が誤りだった（https://arxiv.org/html/2605.29800v1 ）。

これらは、記事 A の主張と矛盾しない。ただし、最初の版が書いた「重ねる値打ちは、数ではなく、偏りの違いにある」という読みは、取り下げる。原典が示しているのは、独立したレビュー役を1つ足すと見つかるものが増える、という所までである。その1つが別の系統のモデルである必要があるかは、測られていない。誤りが会社をまたいで重なるという測定は、むしろ、系統を替えるだけでは見落としが減りにくいことを示している（`speculation`）。

当リポジトリの記録にも、同じ向きの事実がある。当リポジトリの PR の多くは、セカンドオピニオン（複数の系統のモデルのレーン）を通している。通さない PR もある。cloud のセッションが出した PR と、研究ノートだけの PR（この PR もそうである）が当たる。PR には、そのあとに、別のレビューの仕組み（GitHub の PR に付く自動のレビュー）が走る。2026-11-27 に PR のレビューコメントを全件取得して数えた結果は、次のとおりである。

| 項目 | 値 |
|---|---|
| 自動のレビューの指摘（スレッドの数） | 577 件 |
| 指摘が付いた PR | 147 本（マージ済みの PR は 270 本） |
| 採用して直した指摘 | 519 件（90%） |
| 採用しなかった指摘 | 34 件 |
| file の種類 | シェルスクリプト 197 件・文書 189 件・スキルと規則の文書 136 件・テスト 34 件 |

採否は、指摘への返信の書き出しで判定した。

セカンドオピニオンを通した PR への指摘かどうかを、PR の本文で分けた。本文に、セカンドオピニオンについての記述があるかどうかで見ている。

| PR の本文 | PR の数 | 指摘 | 採用して直した指摘 |
|---|---|---|---|
| セカンドオピニオンの記述がある | 121 本 | 452 件 | 422 件 |
| 記述が無い | 26 本 | 125 件 | 97 件 |

この分け方は、粗い目安である。本文に記述があっても、最後の差分にセカンドオピニオンを通したとは限らない。記述が無くても、通していることがある。実装の SO の記録と突き合わせれば、より確かに分けられるが、行っていない。

採用した指摘のうち 422 件は、セカンドオピニオンを通したと見られる PR に付いたものである。先のレーンを通ったあとに残っていた指摘として読めるのは、この分である。指摘の芯は、決まった型の誤りではなく、食い違いだった。文書とコード、計画と結果、説明と実装、テストの意図と実際の判定の食い違いである。記事 B が、良いレビューの基準の例に「文書なら、嘘を書いている」を挙げているのと合う。

この数字の読み方には、限りがある。

- **順番の影響を分けられない。** 自動のレビューは、いつも最後に走る。先のレーンが見つけたものは直っているので、数に出るのは「先のレーンが見逃したもの」だけである。逆向きの見逃しは、記録に現れない。記事 B の調べ（繰り返し指摘された箇所の約 59% は、最初のレビューの時点からあったコードだった）は、同じレビュー役でも、回を重ねれば別のものが出ることを示している。
- **原因を分けられない。** 見つけた理由は、モデルの違いか、レビュー専用の仕組み（差分の渡し方・周辺のコードの引き方）の違いか、分からない。記事 B は、レビュー役が差分を、リポジトリの全体と PR の意図に照らして読むと書いている。
- **折りたたまれた指摘は数えていない。** 数えたのは、行に付いた指摘だけである。

採用した指摘は、P9 の評価の題材になる。答えの分かっている見逃しだからである。題材にするときは、セカンドオピニオンを通した PR に絞る。その PR を直す前の commit に戻し、レーンに同じ差分を流せば、順番の影響を外して確かめられる。

確かめるなら、少なくとも3つを別々に動かす必要がある。レビュー役の数、モデルの系統（同じか別か）、調整の有無である。題材には、答えの分かっている過去の見逃しを使う（P9 の形）。どれか1つだけを動かさないと、何が効いたのかを切り分けられない。
