# LLM のレビュー役を複数にする効き目の裏付け — 調査メモ

- 作成: 2026-11-27（調べたのは 2026-11-27）
- 状態: 調査の結果をまとめた版（追記前提）
- 関連 issue: [#690](https://github.com/stlwolf/ai-development-hub/issues/690)（セカンドオピニオンのレーンの数と、別の系統のモデルを入れる値打ちを確かめる）
- 調べた問い:
  - レビュー役を複数にすると、1つのときより良くなるか。議論・投票・回の繰り返しは、いつ効いて、いつ効かないか。
  - 別の会社のモデルのレビュー役は、同じ系統のレビュー役が見逃すものを見つけるか。同じモデルに新しい文脈を渡すのと、どう違うか。
  - 実際のレビューの仕組みは、指摘をどう絞り、どう収束させ、どう評価しているか。
  - コード以外（設計・plan・仕様・文書）のレビューと、判定役としての LLM の信頼性について、何が測られているか。
- 進め方: 問いごとに調査役（Claude Opus 5.5）を1つずつ動かし、取りまとめた側がこの文書にまとめた。調査役のメモ4本は、測った値、条件、否定の結果、見つからなかったものを含めてこの文書に統合した。メモそのものはリポジトリに残していない。
- 根拠の札:
  - `verified` 取りまとめた側が原典の本文を取得し、同じ値か同じ記述があることを確かめた。
  - `agent-verified` 調査役が「原典を開いて確かめた」と申告したもの。取りまとめた側は照らしていない。
  - `unverified-summary` 検索結果の抜粋か、二次の資料しか見ていない。または、照らそうとして本文で見つけられなかった。
  - `speculation` 推論である。
- 札の限界: 取りまとめた側が確かめたのは、「本文に同じ値があるか」までである。条件や母集団までは読み込んでいない。調査役のメモで `verified` とされていたものは調査役の申告であり、この文書では `agent-verified` と書いた。調査役の確かめ方はそろっていない。原典の HTML を直接取得して本文の文字列と照らしたものと、本文を要約して返す取得の道具で読んだものが混ざっている。後者には数字の写し間違いの余地が残り、引用句も逐語とは限らない。問い3の調査役は、原典を取得する道具が要約を返すことがある、と断っている。判断に使う数字は、使う前に原典で確かめる。
- 照らした範囲: 結論を支える数字のうち、この文書で `verified` としたものは、原典の HTML を取得して本文と照らした。照らして食い違ったものは無かった。本文で見つけられなかった数字は、`unverified-summary` としている。調査役のメモから足したそのほかの数字は、取りまとめた側は照らしていない。

## 結論: 効くのは独立した目を足して別の段で絞ることで、合意を待つことではない

独立したレビュー役を1つ足すと、見つかる問題は増える。これは複数の測定で一貫している。その1つが別の会社のモデルである必要があるかは、まだ誰も切り分けていない。

合意するまで往復させることと、全員の一致を正しさの証拠にすることは、どちらも支持されなかった。議論の回を増やすと正解率が下がった測定があり、全員が一致した判定でも 9.1% は誤りだった。効いているのは、並列に候補を出し、指摘ごとに別の段で確かめる形である。

レビュー役に何を渡すかは、モデルの違いと同じくらい効く。作者の言い切りは判定を甘くし、文脈を増やすと成績が下がることもある。

設計・plan・仕様のレビューが結果を良くするかは、ほとんど測られていない。測られた範囲では、見逃しが多く、承認が甘い。

当リポジトリの使い方（最上位のモデルを含む2〜3の系統のレーンを、実際の PR と設計と plan に当てる形）にいちばん近い比較は、外の資料に無かった。

出典の括弧には、出典の種類と根拠の札を書いた。種類は、学術（論文、preprint、学会の発表）、公式（開発元やベンダーの一次の技術記事、文書、changelog、ソースコード）、公式（宣伝）（導入事例のように宣伝の性格が強いページ）、実務家（個人や1つの組織の事例報告と、利用者の報告）、二次（他者の数字をまとめた記事や要約のページ）の五つである。札は調査役のメモの札を上の対応で写し、一つも上げていない。モデル名は原典の表記のままである。数字を比べるときは、測った課題とモデルの世代が資料ごとに違う点に注意する。

## 1. レビュー役を足すと、何が増えるか

増えるのは再現率と指摘の数である。適合率は、絞る段を置かないと下がる。

### 同じモデルを何度も回すと再現率は大きく伸びるが、5 回を超えると伸びが鈍る

- 同じモデルに 10 回レビューさせて統合すると、F1 は相対で 43.67%、再現率は相対で 118.83% 伸びた。5 回を超えると伸びは小さく、費用は回数に比例する。著者は、適合率がまだ解けていない問題だと書いている（[SWR-Bench](https://arxiv.org/html/2509.01494v2)、学術、`verified`）。
- 調査役の読みでは、この 10 回の例は Gemini-2.5-Flash で、F1 は 15.25 から 21.91 になった。Gemini-2.5-Pro は 5 回の統合で、F1 が 19.38 から 23.84（相対で 23.01%）になった。統合は、独立に作った n 本のレビューを、別の 1 回の呼び出しでまとめる形である。統合したあとの適合率は報告されていない。著者は "performance gains exhibit diminishing returns beyond n=5, while costs continue to scale linearly" と書いている（同じ資料、学術、`agent-verified`）。
- Flash を 5 回統合した F1（20.48）は、Pro の 1 回（19.38）を安い費用で上回った（同じ資料、`agent-verified`）。統合の上積みが弱いモデルほど大きく見えるという読みは、比べている回数が違うので推論である（`speculation`）。
- 違うモデルどうしを統合した結果（Multi-Agg）は図にしか無く、本文に数値が無かった（同じ資料、`agent-verified`）。
- 呼び出しの回数を増やした投票は、易しい問いで成績を上げ、難しい問いで下げた。そのため全体の成績は、回数とともにいったん上がってから下がることがある（[2403.02419](https://arxiv.org/abs/2403.02419)、学術、2024 年、`agent-verified`）。難しい課題でこそ上積みが残ったという逆向きの報告もあり、合意と議論の節（2） に書いた。
- The AI Scientist では、5 本のレビューを合わせても正解率は変わらず、ばらつきだけが減ったという主張がある。要旨に記載が無く、一次資料で確かめられなかった（[2408.06292](https://arxiv.org/abs/2408.06292)、学術、2024 年、`unverified-summary`）。

### 和集合のままでは適合率が落ち、確かめる段を足して初めて単独を超える

- 検証役を置かずにエージェントを3つ合わせると、適合率は単独より低かった（.526 と .555）。検証役を足すと、F1 は .714 から .772 に上がった（[2604.21282](https://arxiv.org/html/2604.21282v1)、学術、`verified`）。費用が約 3.5 倍になった、という点は `agent-verified` である。
- 同じ研究の題材は脆弱性の検出で、3 つのエージェントは役割が違う。検証役なしの 3 つは、問題の無いコードの 91.5% を脆弱と判定した。検証役を足したときの F1 の改善は p<10⁻⁵ だった（同じ資料、`agent-verified`）。
- 4 つのエージェントの指摘を和集合で採ると、再現率は 82.7% だったが、誤検知率は 85.0% だった。重みを付けて採ると、再現率は 37.7%、誤検知率は 35.3% だった。F1 は 61.4% で、fine-tune した GPT-3.5 の 71.6% より低かった（[MultiVer](https://arxiv.org/html/2602.17875v1)、学術、`agent-verified`）。
- 5 つのモデル（Sonnet 4.6、Haiku 4.5、GPT-5.4 mini、Minimax M2.7、GLM-5 Turbo）を 150 のサンプルで比べた研究では、Haiku 4.5 の指摘に別のモデルの指摘を和集合で足すと、F1 は 0.365 から 0.304〜0.333 に下がった。適合率は 0.486 から 0.627〜0.694 に上がり、再現率は 0.293 から 0.195〜0.226 に下がったと報告されている。著者は "Ensembles hurt F1. The models largely detect the same bugs" と書き、2 本目は誤検知を増やすだけだったとしている。150 件のうち 19 件はどのモデルも何も見つけず、55 件は全モデルが何かを見つけた（[2606.15689](https://arxiv.org/abs/2606.15689)、学術、`agent-verified`）。
  - 和集合で再現率が下がるのは計算上おかしく、論文に説明は無い。和集合の数字は、一方の調査役は本文の文字列で照らしたと申告し、もう一方は要約で読んだだけで `unverified-summary` としていた。判定役は Claude Opus で、有意性の検定は無い（同じ資料、`unverified-summary`）。計算の食い違いがあるので、この結果は弱い証拠として扱う（`speculation`）。
- 10 個のオープンなモデルの投票は、モデルの平均よりは良かったが、いくつかの条件で最良の単独モデルに負けた。検出の課題では、10 モデルのうち 7〜9 モデルに負けた（[2512.12536](https://arxiv.org/html/2512.12536v1)、学術、`agent-verified`）。
- 逆向きの結果として、複数の LLM の投票で GPT-3.5 単独より 10% を超えて良くなり、別の LLM の答えを検証させる方法で最良の単独モデルより 4% 良くなったという研究がある（[2409.01001](https://arxiv.org/abs/2409.01001)、学術、2024 年、`agent-verified`）。
- 論文の採否の判定（コードではない）では、単独のペルソナの正解率が 67.6〜71.9% だったのに対し、全員の多数決が 75.1%、全員の意見をまとめる meta-reviewer が 81.8% だった。人の平均は 83.9% だった（[ReviewerToo](https://arxiv.org/html/2510.08867)、学術、`agent-verified`）。
- コード生成の品質では、同じ予算で比べると、レビュー役のエージェントも自己改善も、best-of-n と順位付けに勝たなかった。66 の手法のうち best-of-n に有意に勝ったのは 1 つで、偶然と同程度の割合だった（[2610.38977](https://arxiv.org/abs/2610.38977)、学術、`agent-verified`）。
- 文書を分担して複数のエージェントに読ませ、最後にまとめる構成では、離れた節どうしの矛盾の検出が、試した 10 モデルすべてで 3 分の 2 以上落ちた。強いモデルでも直らなかった（[2605.26174](https://arxiv.org/abs/2605.26174)、学術、`agent-verified`）。

### 製品の報告でも、足すと指摘が増え、確かめる段が誤りを抑えている

- GitHub Copilot は、複数のモデルを組み合わせる構成にして、対応された割合が +8.0%、再現率が +13.6%、指摘の数が +61% になったと報告している（[ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)、公式、`agent-verified`）。
- Copilot の Lite の ensemble では、効き方が重さで違った。対応された指摘は、重さが high のもので 47%、medium で 31%、low で 11% 増え、1 回のレビューの費用は約 8% 減った（[GitHub changelog 2026-09-11](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review)、公式、`agent-verified`）。
- Anthropic の Code Review は、複数のエージェントが並列に探し、検証の段で誤検知を除く構成である。実質的な指摘が付く PR は 16% から 54% に増え、エンジニアが誤りと印を付けた指摘は 1% 未満だった（[Claude blog: Code Review](https://claude.com/blog/code-review)、公式、`agent-verified`）。この 1% 未満は利用者が明示的に印を付けた数なので、無視された指摘は数えていない可能性がある（`speculation`）。
- OpenAI のレビューでは、推論の予算を増やすと、主に較正が良くなり、誤検知が減った。検証役は、生成側のトークンのごく一部しか使わなくても、既知の重大な問題の多くを捕まえた（[OpenAI](https://openai.com/safety-alignment/scaling-code-verification/)、公式、`agent-verified`）。
- 敵対的に反証させる段を重ねた方式では、171 件の候補の約 79% を、開示の前に捨てた（[2604.19049](https://arxiv.org/abs/2604.19049)、学術、`agent-verified`）。
- 足す向きとは逆の記述もある。Anthropic は、レビュー役を重ねるより、1 本を調整するほうが良いことが多いと書いている（[Anthropic の検証の記事](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)、公式、`agent-verified`）。

### 変更が大きいほど指摘は付くが、大きい変更と難しいバグでは当たりにくい

- 変更が大きいほど、指摘が付く。Anthropic は、1,000 行を超える PR の多くに指摘が付き、小さい PR の多くは指摘なしで返ると書いている（[Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)、公式、`verified`）。
- 別の記事は社内の測定として、1,000 行を超える PR の 84% に指摘が付き、平均は 7.5 件だったと書いている。50 行未満の PR では 31% で、平均は 0.5 件だった。大きい変更には、多くのエージェントを割り当てる（[Claude blog: Code Review](https://claude.com/blog/code-review)、公式、`agent-verified`）。
- 一方で、単独のモデルの当たり方は、大きい diff で落ちる。5 モデルの比較では、Haiku 4.5 の F1 が、10 行未満の diff で 0.657、10〜50 行で 0.800 だったが、50 行を超えると 0.043〜0.070 に落ちた。別の読みでは、150 行を超えると 0.043 とされている（[2606.15689](https://arxiv.org/abs/2606.15689)、学術、`agent-verified`）。
- レビューのエージェントは、複雑な変更や、離れた場所を合わせて考える必要のあるバグに弱い。探索を促す依頼文は、成績を 5.8% 上げ、費用を 10% 上げた（[2610.13668](https://arxiv.org/abs/2610.13668)、学術、`agent-verified`）。
- セキュリティのレビューで見逃した例の 68% は、欠陥のあるファイルを指しながら、別の仕組みを論じていた。8 モデルの再現率は 32.5〜78.1% だった（[SecPRBench](https://arxiv.org/abs/2610.33509)、学術、`agent-verified`）。

## 2. 合意と議論は、効くか

議論の回を増やしても良くならず、全員が一致しても正しいとは限らない。

### 議論の回を増やすと正解率は下がり、上積みの大半は議論の前の多数決で説明できる

- 複数のエージェントに議論させる手法では、回を増やすほど正解率（平均）が下がった。2 回で 0.7377、3 回で 0.7112、5 回で 0.7050 である（[2508.17536](https://arxiv.org/html/2508.17536v2)、学術、`verified`）。改善の大半が議論の前の多数決で説明できる、という読みは `agent-verified` である。この種の研究の多くは、小さめのオープンモデルを使っている。
- 調査役の読みでは、この値は Qwen2.5-7B の分散型の議論のもので、Llama3.1-8B でも 0.6929、0.6788、0.6761 と下がった。Qwen2.5-7B では、単独が 0.7205、最良の議論が 0.7377、多数決が 0.7691 だった。32B のモデルでも、多数決は議論と同等だった。著者は、議論だけでは期待される正しさが上がらないこと（martingale）を理論で示し、正しい答えを固定する工夫を入れると改善したと書いている。引用は "in most cases, majority voting performs on par with MAD" である（同じ資料、学術、2025 年、`agent-verified`）。
- 同じ回答数で比べると、議論は単純な self-consistency（多数決）に負けた。GSM8K で、9 回答の議論が 83.0、self-consistency が 88.2 だった。同じ研究は、外からのフィードバックが無い自己修正では、推論の成績がむしろ下がると報告している（[2310.01798](https://arxiv.org/html/2310.01798v2)、学術、2023 年、`agent-verified`）。
- 5 つの議論の方式と 9 つのベンチマークで、議論は推論の計算量をかなり多く使っても、CoT や self-consistency をしばしば超えなかった（[2502.08788](https://arxiv.org/abs/2502.08788)、学術、2025 年、`agent-verified`）。同じ研究は、モデルを異種にすると議論は一貫して良くなるとも書いている。この点は 別の会社のモデルの節（3） に書いた。
- 980 の条件のうち 93% で、self-consistency は議論と同等以上だった（[2610.23246](https://arxiv.org/abs/2610.23246)、学術、`agent-verified`）。
- 予算を揃えて比べると、マルチエージェントの優位は平均でわずかに負だった（[2611.17610](https://arxiv.org/abs/2611.17610)、学術、`agent-verified`）。調査役の読みでは、9 本の既存研究を集計し直し、比べる相手の単独モデルにサンプリングや同じ予算を与えると、優位は平均 −0.042 になった。統制した実験では、同じトークン数の self-consistency に対して、議論は −0.015 だった（同じ資料、`agent-verified`）。
- 逆向きの結果もある。同じ計算量で、議論が self-consistency を 1.3 点、mixture-of-agents が 2.7 点上回ったという報告である。self-consistency は早く頭打ちになり、マルチエージェントの上積みは難しい課題で残った（[2605.01566](https://arxiv.org/abs/2605.01566)、学術、`agent-verified`）。この結果は、投票の回数を増やすと難しい問いで成績が下がるという結果（レビュー役を足すと何が増えるかの節（1） の 2403.02419）とも向きが違う。どちらが当てはまるかは、課題と比べ方で変わると見ておく（`speculation`）。

### 議論は同調を生み、正しい答えを捨てさせる

- 議論を続けると、正解率が時間とともに下がることがある。モデルは仲間の推論を見て、正しい答えから誤った答えに乗り換えることが多く、反論より同意を選ぶ。弱いエージェントが混ざると、強いエージェントの成績が崩れる（[2509.05396](https://arxiv.org/abs/2509.05396)、学術、2025 年、`agent-verified`）。
- 同じモデル 10 体で 3 回議論させると、多数派の答えにそのまま合わせる割合が最大 85.5% になった。仲間の理由づけを見て、正しかった推論が崩れる割合は最大 70.0% だった。多数決が、候補の中にあった正解を捨てる差は最大 32.3 点だった。著者の言葉は "uncritically adopt majority answers" である（[2605.00914](https://arxiv.org/abs/2605.00914)、学術、`agent-verified`）。
- 合意を目指す議論は、情報を持つ食い違いを、早すぎる合意で捨ててしまう。数値は示されていない（[NeurIPS 2026 のポスター](https://neurips.cc/virtual/2026/poster/153203)、学術、`agent-verified`）。
- 判定役どうしに議論させると、偏りが増幅された。メタ判定役の形にすると、増幅は抑えられた（[2505.19477](https://arxiv.org/abs/2505.19477)、学術、2025 年、`agent-verified`）。

### 全員の一致は、正しさの証拠にならない

- 9つのモデルを判定役に並べると、得られた情報は約2票分だった。全員が一致した項目でも 9.1% は誤りで、独立なら約 0.02% になるはずの値である。いちばん相関が高かった組は、会社をまたいでいた（[2605.29800](https://arxiv.org/html/2605.29800v1)、学術、`verified`）。
- 調査役の読みでは、9 つのモデルは 7 つの系統にまたがり、誤りの相関が高い組はすべて系統をまたいでいた。Claude と Gemini の組が 0.603、GPT-4o と Claude の組が 0.588 である。1 つの系統から 1 モデルずつに絞ると、独立な票は 1.93 に下がった。パネルの多数決は、4 つの課題のうち 3 つで最良の単独モデルより低かった。課題は NLI と RewardBench で、設計や plan のレビューではない（同じ資料、`agent-verified`）。
- 350 を超えるモデルの調査では、両方のモデルが誤ったとき、約 60% で同じ誤答を選んだ。正確なモデルほど、誤りが相関した（[2506.07962](https://arxiv.org/html/2506.07962v1)、学術、`verified`）。同じ会社やアーキテクチャであることの効果は 別の会社のモデルの節（3） に書いた。
- 10 のレビュー役が全員一致で支持した誤った脆弱性の指摘が、1 回の実行で否定された例がある（[2604.19049](https://arxiv.org/abs/2604.19049)、学術、`agent-verified`）。
- 議論が役に立った例の 66%（47 件中 31 件）は、投票が全員一致で間違っていた場合だった。全員の一致は、議論が要らない場面を示さない。著者は "vote entropy predicts where debate is safe, not where debate is needed" と書いている（[2605.09618](https://arxiv.org/abs/2605.09618)、学術、`agent-verified`）。
- 一致は、正しさの弱い予測因子にとどまる。最も一貫したフロンティアモデルは、GPQA の項目の 77% で高い一致を示したが、そのうち 48% は誤りだった。自信のある誤りは、プロバイダをまたいで繰り返された。これは探索的な確認である（[2607.08065](https://arxiv.org/abs/2607.08065)、学術、`agent-verified`）。

### 回を重ねる修正と監査は、早く頭打ちになるか、収束しない

- コードレビューで「合意するまで往復する」形を測った資料は、見つからなかった。近いものとして、レビューと修正が一晩で 50 回を超えた実例を Anthropic が書いている（[Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)、公式、`verified`）。
- 仕様書を 9 回監査した事例では、回ごとの指摘数が 15、8、12、2、8、1、4、1、0 だった。減り方は単調でなく、修正が連鎖したことと、監査の範囲が広がったことが原因と考えられている（[2605.12280](https://arxiv.org/abs/2605.12280)、学術、`agent-verified`）。単著の事例である。
- コードの自己修復では、改善の大部分が最初の 2 回で出た（[2604.10508](https://arxiv.org/abs/2604.10508)、学術、`agent-verified`）。
- 自己修復は、費用を考えると改善が小さく、データによっては無かった。律速は自分のコードへのフィードバックの質で、強いモデルのフィードバックを使うと改善が大きくなった（[2306.09896](https://arxiv.org/abs/2306.09896)、学術、2023 年、`agent-verified`）。
- 設計文書の改善を比べた研究では、同じモデルの 3 回の自己改善（4.503、$0.33）は、1 回だけの生成（4.514、$0.08）を超えなかった。同じモデルのレビュー（4.493、$0.42）も同じだった。別のモデルのレビュー（4.606、$0.27）と、構造化した敵対的なレビュー（4.637、$0.43）は上回った。議論（4.353）と、複数案の統合（3.655〜4.326）は基準より悪かった。採点はすべて LLM で、上位の方式どうしでは採点者の一致度が低い（α 0.42）。モデルの組み合わせも 1 通りである（[2606.01490](https://arxiv.org/html/2606.01490v1)、学術、`agent-verified`）。
- 往復は 1〜2 回で止めるのが、これらの測定と合う。範囲を広げると新しい指摘がまた出るので、指摘の件数が 0 になるまで回す止め方は、収束しないことがある（`speculation`）。

## 3. 別の会社のモデルは、要るか

足すと増えるのは確かである。効いているのが「会社の違い」なのか「もう1つ足したこと」なのかは、分かれていない。

### 唯一の対照実験では、会社の違いとレビュー役の能力が分けられていない

- 同じモデルの新しいセッション（F1 は 28.6%）と、別の会社の上位モデル（32.3%）のあいだに、有意な差は出なかった。著者は、同等であることを示すものではないと書いている。2つを組み合わせると、見つかる誤りの割合は、同じモデルを2回使った場合の 42.7% から 56.7% に上がった。別の会社のモデルを2回使った場合と、混ぜた場合に、有意な差は無かった（145 件中 76 件と 82 件、p=.184）。レビュー役はそれぞれ違う道具と指示で動いていた。差が出たのは文書の題材で、コードの題材では同じモデルの新しいセッションのほうが高かった（[2610.01471](https://arxiv.org/html/2610.01471v2)、学術、`verified`）。軽いモデルを別の会社の目として足しても、自己レビューを上回らなかった（`agent-verified`）。
- 設定は次のとおりである。生成したのは Claude Opus 4.6 で、30 の成果物（コード、文書、発表の原稿。韓国語）に 150 の誤りを埋め込み、10 の条件で計 900 回のレビューを行った。同じモデルの条件は、同じセッション（SR）、同じセッションでの 2 回目（SR2）、生成のときの依頼文と成果物を新しいセッションに渡すサブエージェント（SA）、成果物だけを新しいセッションに渡す CCR の 4 つである。別のモデルは GPT-5.4（上位）、Gemini 2.5 Pro（中位）、Gemini 2.5 Flash（軽量）で、それぞれに要件を伏せた版がある。単著で、v1 は 2026-10-01、v2 は 2026-10-06 に出た。2603.12123 の続報である（同じ資料、`agent-verified`）。
- 調査役の読みでは、主検定は CCR に対する 9 つの比較を Holm で補正したもので、CCR と有意に違ったのは SR2 だけだった。GPT-5.4 と CCR の差は点推定で 3.7 ポイントで、補正後の p は 1.00 だった。組み合わせの差は 14.0 ポイント（150 件中 85 件と 64 件）で、補正後の p=.006 で有意だったが、和集合の比較は事後の分析である。組み合わせたのは、CCR 1 回と、要件を伏せた GPT-5.4 の 1 回である。軽量の Gemini 2.5 Flash は F1 24.0% で、同じセッションの自己レビューの 27.1% を上回らなかった。GPT-5.4 は Codex CLI 経由で動き、作業ディレクトリのファイルを読めた。どのディレクトリかは記録されていない。著者の言葉は "does not establish equivalence" である（同じ資料、`agent-verified`）。
- ほかの条件の F1 は、要件を伏せた GPT-5.4 が 32.1%、要件を伏せた Gemini 2.5 Pro が 29.0%、要件を伏せた Gemini 2.5 Flash が 27.0%、Gemini 2.5 Pro が 26.8%、SA が 23.8%、SR2 が 21.7% だった。要件を伏せた Flash が自己レビューと同等だった点は、検定していない点推定である（同じ資料、`unverified-summary`）。
- 題材別の F1 は、コードで CCR が 40.7%、GPT-5.4 が 37.2%、要件を伏せた GPT-5.4 が 29.8% で、別のモデルのどの条件も CCR を上回らなかった。文書では、別のモデルの 6 条件すべて（30.1〜42.1%）が、同じモデルの 4 条件すべて（17.4〜24.5%）を上回った（同じ資料、`agent-verified`）。題材別の推定には、不確かさの幅が付いていない（同じ資料、`unverified-summary`）。
- 著者は、不完全で同一でない 2 つの検出器なら、和集合の再現率は機械的に上がると書いている。観測された和集合は、独立を仮定した参照値より低かった。相乗効果は主張していない（同じ資料、`agent-verified`）。
- 3 つのモデルの和集合は 58.0% で、2 つの和集合より 1.3 ポイント高いだけだった。公開データ ReaLMistake での外部の確認では、混ぜた組の和集合の再現率は同じモデル 2 回より +0.5 ポイント（95% 信頼区間 −1.2〜2.2）で、主な結果を再現も否定もしなかった（同じ資料、`unverified-summary`）。
- 限界として、生成モデルは 1 つで、各階層のレビュー役も 1 つずつなので、能力とモデルの違いが交絡している。埋め込んだ誤りは独立に注釈されておらず、照合器も人手で監査されていない。失敗した 14 のセッションを除外している。データとスクリプトは、著者への依頼で入手する形である（同じ資料、`unverified-summary`）。著者自身も、モデルの違いとレビュー役の能力は分離できていないと結論している（同じ資料、`agent-verified`）。

### 実務の報告は、後の版で「人数の曲線」に訂正された

- 別の会社のモデルを足した実務の報告（網羅率が 33.6% から 57.1%）は、著者が後の版で取り下げた。訂正後は 47.2% から 72.3% で、著者は、レビュー役の数に対する曲線であって会社の違いの効果ではない、と書いている（[Stone v2](https://zenodo.org/records/21328807)、実務家、`unverified-summary`。訂正版を取得できなかった）。
- 最初の版（2026-06-03）は、1 つの組織の実務のレビューの記録から、人が照合した答えのある 18 の成果物と 154 件の確定した指摘を使い、5 社の 8 つのモデル版（Opus 4.6、4.7、4.8、GPT-5.4、5.5、Gemini 3.1、Kimi k2.6、Qwen3.7-max）を比べた。単独の再現率の上限は約 64% で、154 件のうち 56.5%（87 件）は 1 つのモデルだけが見つけた。組ごとの Jaccard の中央値は約 0.37 だった。プロバイダの数ごとの期待網羅率は、1 社で 33.6%、2 社で 57.1%、3 社で 74.6%、4 社で 88.7%、5 社で 100.0% である。3 社目からは伸びが小さくなる。適合率は報告されていない。同じモデルを繰り返し回しても結果が変わるとは示せなかった、とも書いている（[Stone v1](https://zenodo.org/records/20519585)、実務家、`agent-verified`。2 人の調査役がそれぞれ確かめたと申告している）。
- 後の版（2026-07-13、最初の版を置き換えると明記）は、33 の成果物、294 件、8 社の 15 のモデル版に広げた。網羅率は成果物ごとに、その成果物を実際にレビューしたモデルだけで計算し直したとされる。1 人で 47.2%（区間 42〜53）、2 人で 72.3%（68〜77）、3 人で 89.4%、4 人で 97.3%、5 人で 100.0% である。旧版の全体をまとめた計算は、レビューしていない成果物の欠陥まで見落としとして数えた人工物だった、と著者は訂正している（同じ資料、`unverified-summary`）。
- 後の版のそのほかの記述は、調査役の一人が PDF を読んで確かめたと申告しているが、取りまとめた側は訂正版を取得できていない。その申告によれば、後の版が旧版の値として書く「約 22%」は、最初の版の 33.6% と一致せず、どの版を指すのかは本文から分からない（同じ資料、`agent-verified`）。食い違いの理由は不明である（`speculation`）。
- 同じ申告によれば、後の版の推奨は「別のプロバイダは妥当な既定だが、再実行や同じプロバイダの別のモデルに勝つとは示せない」に弱められた。1 つのモデルだけが見つけた割合は 56.8%（294 件中 167 件）で、並べ替えで作った帰無分布（平均 35.3%）より 9.7 標準偏差高い。一方で Jaccard の中央値 0.29 は、各レビュー役が約 45% を独立に見つけるだけでも出る値に近く、プロバイダ固有の盲点の証拠にはならないと著者は書いている。新しく加えた 2 社（grok-4.5 と fugu-ultra、各 12 件）は、独自の発見が 0 件で、既存のレビュー役の確認にとどまった。これは小さな標本での観察である（同じ資料、`agent-verified`）。
- 2 つの版に共通の限界がある。答え合わせの鍵は Claude が下書きし、Claude の系統もレビュー役に含まれる（利益相反）。同じモデルに同じ入力で再実行していないので、「同じモデルに新しい文脈で読ませる」こととは比べられない。Anthropic 以外のモデルは別の道具で動かし、版は日付から推定している。単一の組織、単一のコードベースである（同じ資料、`agent-verified`）。

### 誤りは、会社をまたいで重なる

- 350 を超えるモデルの調査（合意と議論の節（2））は、HELM の 71 モデル、HuggingFace の Open LLM Leaderboard の 349 モデル、履歴書の選考の課題を使った。約 60% という一致は HELM の値である。回帰では、「同じ会社」であることが誤りの一致率を +0.066（HuggingFace）と +0.022（HELM）押し上げ、「同じアーキテクチャ」であることは +0.076（HuggingFace）押し上げた。正確なモデルほど、特に両方が正確なほど誤りが相関し、それはアーキテクチャやプロバイダが違っても成り立った。著者は "using multiple different models is not a panacea" と書いている（[2506.07962](https://arxiv.org/html/2506.07962v1)、学術、2025 年、`agent-verified`）。同じ会社であることの上乗せは数ポイントで、一致の大部分は会社の違いと関係なく共有されている、と読める（`speculation`）。
- 別のプロバイダのフロンティアの判定役（GPT-5.6-sol、Claude Opus 5、Grok 4.5）の組の誤りの相関は、平均 0.42 だった。Gemini どうしの 0.40 とほぼ同じである。能力の階層を混ぜる（フロンティアにオープンウェイトを足す）と、実効的な独立の判定役の数は 1.88 から 3.83 に増えたが、多数決の正答率はフロンティアだけの 0.933 に対し、混ぜると 0.915 だった。題材は RewardBench v2 などである。著者は "Judges from different providers are about as correlated as judges from the same provider." と書いている（[2609.22512](https://arxiv.org/html/2609.22512v1)、学術、`agent-verified`）。GPT、Claude、Grok の 3 つの判定役の実効的な数は 1.41 である（同じ資料、`unverified-summary`）。
- 能力が上がるほど、モデルどうしの間違い方が似てくる。LLM の判定役は、自分に似たモデルを高く評価する。誤りの重なりに基づく類似度（CAPA）を提案した研究で、本文の数値は確かめていない（[2502.04313](https://arxiv.org/abs/2502.04313)、学術、2025 年、`agent-verified`）。
- 前節の対照実験では、指摘ごとの重なり（Jaccard）は、CCR どうし（別のセッション、90 組）で 52.2%、CCR と SR で 59.9%、CCR と GPT-5.4 で 46.1%、CCR と Gemini 2.5 Flash で 36.5% だった（[2610.01471](https://arxiv.org/html/2610.01471v2)、学術、`agent-verified`）。著者は「文脈を変えても重なりは下がらず、モデルを変えると下がる」と述べるが、検出率や発見数の違いでも重なりは下がるので、記述的な支持にとどまるとも書いている（同じ資料、`unverified-summary`）。
- 道具立てを固定すると、モデルの構成を替えても、見つけた件数は同じだった。ただし中身は PR ごとに違った（[2611.26942](https://arxiv.org/html/2611.26942)、学術、`unverified-summary`。本文で該当の数字を見つけられなかった）。調査役の読みでは、ベクトル検索、tree-sitter、lint、11 のサブエージェントを固定した最小のレビューのエージェントを、3 つのモデルの構成（OpenAI、混合、Claude）で動かした。3 つとも同じ 48 件の正解の指摘を見つけたが中身は違い、PR ごとの件数は 50 件中 34 件で違った。総量は同じで、見つける部分集合が違う形である（同じ資料、`unverified-summary`。調査役は確かめたと申告しているが、取りまとめた側は本文で見つけられなかった）。
- 5 つのモデルを比べた研究（レビュー役を足すと何が増えるかの節（1））では、150 件のうち 19 件はどのモデルも何も見つけなかった（[2606.15689](https://arxiv.org/abs/2606.15689)、学術、`agent-verified`）。

### 効くのは会社の違いより能力で、弱いレビュー役は強い書き手の成果を壊す

- レビューの向きで、結果が逆になる。あるモデルが別のモデルの成果物をレビューすると、合格率は 71.6% から 89.7% に上がった。逆の組み合わせでは、91.4% から 82.8% に下がった（[2607.21656](https://arxiv.org/html/2607.21656v1)、学術、`verified`）。直した数より壊した数が多く、レビュー役に「直さない」を選ぶ道が無かった、という点は `agent-verified` である。
- 調査役の読みでは、題材は LiveCodeBench の 116 問で、Claude Opus 4.7 と GPT-5.5（Codex CLI）を書き手とレビュー役に組み合わせた。レビュー役はテストを実行できず、必ず最終のプログラムを出す決まりだった。合格率は、Claude 単独が 91.4%、Claude の自己レビューが 91.4%（変化なし）、Codex 単独が 71.6%、Codex の自己レビューが 84.5%（p_BH=.022）、Claude が Codex を見て 89.7%（p_BH=.001）、Codex が Claude を見て 82.8%（p_BH=.046 で悪化）だった。著者は、下書きが弱いときにレビューが役立つとまとめている。著者の言葉は "handing Claude Opus 4.7's draft to Codex GPT-5.5 actually drops it to 82.8%" である（同じ資料、Agentic SE @ KDD'26、`agent-verified`）。
- 直した数と壊した数は、Claude が Codex を見て 26 件と 5 件、Codex の自己レビューで 21 件と 6 件、Codex が Claude を見て 3 件と 13 件だった。この件数は、一方の調査役が本文の文字列で照らしたと申告し、もう一方は要約で読んだだけだった（同じ資料、`agent-verified`）。2 つの向きを直接比べた差は有意でなかった（p_BH=.1444）（同じ資料、`unverified-summary`）。
- 弱いほうの書き手には自己レビューでも大きな改善があり、別のモデルの上乗せはそれより小さい。強いほうの書き手には自己レビューが効かず、弱い別のモデルのレビューは害になった、と読める（`speculation`）。
- 役割を分けたチームの研究では、計画役、実行役、検証役を別のコンテナに分け、OS の権限で役割を強制した。155 の課題の参照の比較（Gemini-3 Flash）では、チームと単独の差は平均 +0.5 ポイント（p=0.20）だった。単独の得点が最も低い五分位では +15.7 ポイントで、上位の五分位では単独を下回った。リーダーボードでは、Sonnet 4.6 が +20.0、Haiku 4.5 が +16.7、Opus 4.7 が +2.2、GPT-5.4 Mini が −4.4、Gemma 4 31B が −5.6 だった。検証役を外すと、部分点の平均が 5.5 ポイント上がった（[TeamBench](https://arxiv.org/html/2605.07073v1)、学術、`agent-verified`）。
  - 同じ研究の設定として、13 のモデル（Anthropic、Google、OpenAI、Alibaba）を使い、課題の多くは GitHub のバグ報告で、採点は決定的なシェルスクリプトで行った。別のプロバイダの役割を混ぜた比較（25 の課題、27 の構成、3 つのシード）では、上位 3 つの構成は 4 ポイント以内に収まり、信頼区間が重なった。最も費用対効果が良いのは GPT-5.4 Mini だけの構成だった。同じ系統と混合を形式的には比べていない（同じ資料、`unverified-summary`）。
  - これは役割の分離の研究であり、レビュー役のモデルの多様性の研究ではない。Yubin Kim（MIT、Google Research）ほかによる 2026-05-08 の v1 だけの、査読前の preprint である（同じ資料、`agent-verified`）。
- 最上位の1モデルの出力だけを集める形が、違うモデルを混ぜる形を上回った結果もある（[2502.00674](https://arxiv.org/abs/2502.00674)、学術、`agent-verified`）。調査役の読みでは、Self-MoA は AlpacaEval 2.0 で 6.6%、MMLU、CRUX、MATH の平均で 3.8% 上回った。混ぜると平均の品質が下がることが原因とされる。TMLR 2026 に載った（同じ資料、`agent-verified`）。
- 同じ会社のモデルが書いたコードは、そのモデルが見逃しやすいという向きの結果がある。Claude Code の PR では GPT が Opus より多くの重大なバグを捕まえ、Codex の PR ではその逆だった（[Greptile](https://www.greptile.com/blog/model-inversion)、公式、向きは `agent-verified`）。個々の数値（53.7%、60.0% など）は、図の値と条件の対応が取れなかった（同じ資料、`unverified-summary`）。
- 実運用の記録では、異なるモデルの組のレビューは 262 件中 183 件（69.8%）、同じモデルの組は 113 件中 60 件（53.1%）で、欠陥か修正の要求を記録した（[tap](https://arxiv.org/abs/2606.14445)、学術、`agent-verified`）。観察研究で、著者自身もモデルと実行環境の組み合わせの効果としており、モデルの効果だけは取り出せない（同じ資料、`unverified-summary`）。
- 敵対的な反証の段を重ねた方式の著者は、系統の違うモデルのレビューは、同じ系統では見逃す偏りを捕まえうると主張している。ただし数値の比較は要旨に無い（[2604.19049](https://arxiv.org/abs/2604.19049)、学術、`agent-verified`）。
- 異なる系統の小さめのモデルを並べた審査団は、大きなモデル 1 つの審査より良く、費用は 7 分の 1 以下だった（[PoLL](https://arxiv.org/abs/2404.18796)、学術、2024 年、`agent-verified`）。
- 議論の方式を比べた研究は、モデルを異種にすると議論は一貫して良くなると書いている。効果量は本文を開いておらず確かめていない（[2502.08788](https://arxiv.org/abs/2502.08788)、学術、2025 年、`agent-verified`）。
- 投票と議論で、多様な 2 つのエージェントが、同質な 16 のエージェントと同等以上になった（[2602.03794](https://arxiv.org/abs/2602.03794v1)、学術、`agent-verified`）。ARC では、モデルを混ぜる効果（+1.7〜+2.5 ポイント）のほうが、人格づけの依頼文（−0.7〜+0.2 ポイント）より大きく、両方を組み合わせたときが最大だった（[2602.03794 の本文](https://arxiv.org/html/2602.03794v1)、学術、`unverified-summary`）。7〜8B のオープンなモデルだけの研究で、コードの課題は無い。
- 逆の向きとして、複数のモデルを混ぜたマルチエージェントでも、コード生成などで同質化のリスクは減らなかったと要旨は述べている。本文の数値は確かめていない（[2610.09824](https://arxiv.org/abs/2610.09824)、学術、`agent-verified`）。
- 上位のモデルどうしなら、別の会社を足すと発見の重なりは下がり、網羅率は上がる傾向がある。軽いモデルや弱いモデルは、別の会社であっても足しにならないか、害になる。効いているのは会社の違いより能力である、と読める（`speculation`）。大きく正確なモデルほど誤りが似るので、最先端のモデルどうしを並べるほど、多様性による上積みは今後小さくなると考えられる（`speculation`）。
- 調査役たちの読みをまとめると、次のようになる（`speculation`）。2 人目の独立したレビュー役を足す効果は確かで、14〜25 ポイントと意味のある大きさだが、その 2 人目が別の会社である必要は示されていない。会社の違う 2 本目のレーンは検出の範囲を広げる見込みが最も大きく、3 本目からの伸びは小さい。誤りは会社をまたいで重なるので、別の会社を足しても全員が見落とす部分は残り、人の確認やテストのような機械的な関門の代わりにはならない。今ある証拠と矛盾しないのは、上位の別の会社のモデルを互いの出力を見せずに独立に走らせ、その結果を元の成果物に照らして確かめる形である。ただし、同じ費用で同じ上位モデルの新しいセッションをもう 1 回走らせる案との差は、コードレビューでは測られていない。

### 自分の出力をひいきする傾向は小さく、誰の出力として見せるかで変わる

- 自分の出力をひいきする傾向は、小さいか、検出されなかった。効いていたのは、モデルの系統より、誰の出力として見せるかだった（[2609.17857](https://arxiv.org/html/2609.17857)、[2507.02778](https://arxiv.org/abs/2507.02778)、学術、`agent-verified`）。
- 判定役が自分の出力を採点しない設計で、同じ系統への上乗せを測った研究では、全体で 0.067（95% 信頼区間 0.053〜0.084、並べ替え検定で p=0.0002）、Gemma で 0.084、Llama で 0.034 だった。パネルに候補と同じ系統の判定役が 1 つ入ると、組の比較の結果の 18.5% が変わった。ただし Qwen を判定役から外すと全体の値は 0.037 に下がり、効果は 1 つの系統に偏っている。著者は "We do not test closed-weight judges or verifiable domains such as code and mathematics" と書いている（[2609.17857](https://arxiv.org/html/2609.17857)、学術、`agent-verified`）。
- 同じ誤りを「ユーザーが書いたもの」として見せると直せるのに、「自分が書いたもの」として見せると直せない割合が、14 のオープンな非推論モデルで平均 64.5% あった。末尾に "Wait" と足すだけで、この盲点は 89.3% 減った。これはモデルの系統の違いではなく、誰の出力として見せるかという文脈の問題である（[Self-Correction Bench](https://arxiv.org/abs/2507.02778)、学術、COLM 2026、`agent-verified`）。
- IFEval の修正の課題では、実際の書き手が自分の下書きへの正しい修正を却下した率は 15.3%、別のモデルは 20.4% で、差は −5.1 ポイント（95% 信頼区間 −12.9〜+2.7）だった。自己選好は検出されなかった。対象は中位の 4 モデル（gpt-4o-mini、claude-3.5-haiku、gemini-2.5-flash-lite、llama-3.3-70b-instruct）だけで、比較役が別の系統なので、系統ごとの厳しさの違いが交絡している。著者は "Effects smaller than ∼13 pp cannot be excluded at this sample size." と書いている（[2606.20093](https://arxiv.org/html/2606.20093v1)、学術、`agent-verified`）。
- コード生成を含む検証できる課題では、強いモデルの自己選好の多くは、実際に出力が良いことによる正当なものだった。ただし、判定役自身が生成で間違えた問題では有害な自己選好が残り、強いモデルほど強かった。長い思考を先に出させると減った（[2504.03846](https://arxiv.org/abs/2504.03846)、学術、2025 年、`agent-verified`）。
- 逆の向きとして、ひいきがあるという報告もある。モデルは自分の出力をある程度見分けられ、見分ける力と自己選好の強さには線形の相関がある（[2404.13076](https://arxiv.org/abs/2404.13076)、学術、2024 年、`agent-verified`）。9 つの判定役のうち、GPT-4o と Claude 3.5 Sonnet は、自分の出力にも、同じ系統の他のモデルの出力にも高い点を付けた。効果量は本文を開いておらず確かめていない（[Play Favorites](https://arxiv.org/abs/2508.06709)、学術、2025 年、`agent-verified`）。位置、冗長さ、自分の出力をひいきする偏りは、判定役の基礎研究でも報告されている（[2306.05685](https://arxiv.org/abs/2306.05685)、学術、2023 年、`agent-verified`）。
- コードレビューで、自分の PR を自分でレビューする条件と、別の系統がレビューする条件を、正解つきで直接比べた研究は見つからなかった。別の系統に替えれば自己選好と同じ系統へのひいきは構造上なくなるが、能力が近いフロンティアのモデルどうしの似ていることによる偏りは残ると考えられる（`speculation`）。

### 効果の出どころは、モデルの違いか、依頼文と道具立ての違いか

- 前述の対照実験では、上位の別の会社の条件（GPT-5.4）は Codex CLI 経由で動き、作業ディレクトリのファイルを読めた。同じモデルの条件は Claude Code の Agent ツールで動いている。道具立ての違いが交絡している（[2610.01471](https://arxiv.org/html/2610.01471v2)、学術、`agent-verified`）。実務の報告でも、プロバイダごとに使った道具が違い、版の特定も日付からの推定である（[Stone v2](https://zenodo.org/records/21328807)、実務家、`agent-verified`）。
- 道具立てを固定した最小のエージェントの研究の著者は、「固定した検索の仕組みが見つけられる範囲を決め、モデルはその中で何を拾うかを決める」という仮説を出している。単一のパスの別のシステムでは、4 つの系統のあいだで再現率が 15.4 ポイント、適合率が 29.8 ポイント開いた。Kodus のベンチマークでは、8 つの系統のあいだの差は約 3 ポイントだった。モデルの選び方の効き方は、構成によって違う。著者は "this experiment isolates model contribution, not harness quality." と書いている（[CodeReviewBench](https://arxiv.org/html/2611.26942)、学術、`agent-verified`）。この最小のエージェントの F1 は約 0.22 で、市販のツールの中央値の約 0.44 を大きく下回る。作り込みの差がモデルの差より大きい可能性を示す（同じ資料、`unverified-summary`）。
- 同じモデルのまま、新しいセッションにすることと、生成のときの依頼文を伏せることだけで F1 が動いた（何を渡すかの節（4） の 2603.12123）。役割と依頼文の組み方だけで F1 が動いた例（何を渡すかの節（4） の 2608.18167）もある。
- コーディングのエージェント（レビューではない）では、同じモデルで文脈の扱いだけを変えると、狭い文脈の窓での SWE-bench Verified 169 問で、テストを通す割合の平均が 28% から 49% に上がった（[2608.26218](https://arxiv.org/abs/2608.26218)、学術、`agent-verified`）。一方で、ベンダーの純正の道具と中立の道具の差は、平均で ±1 ポイント程度だった（[2609.11987](https://arxiv.org/abs/2609.11987)、学術、`unverified-summary`）。
- モデルの多様性と、依頼文、文脈、道具の違いを要因として分けた実験（同じ道具で、同じモデルの再実行、同じベンダーの別のモデル、別のベンダーのモデルを比べる設計）は、コードレビューについては見つからなかった。

## 4. 何を渡すかで、変わること

モデルを替えなくても、渡すものと頼み方で成績が動く。

### 作者の言い切りと推論は、判定を甘くする

- 作者が「不具合は無い」と強く言い切る文を付けると、脆弱なコードの検出率が落ちた。落ち方はモデルで大きく違い、あるモデルは 97.2% から 3.6% に、別のモデルは 97.4% から 75.5% になった。PR の説明文でレビューを誘導する実験では、説明文を消すと、誘導が成功した 32 件のうち 16 件で検出が戻った（[2603.18740](https://arxiv.org/html/2603.18740)、学術、`verified`）。
- 調査役の読みでは、6 つのモデルに 497 のファイルを 5 つの言い回しで判定させた実験で、前者は GPT-4o-mini、後者は Claude Sonnet 4.5 である。Claude Opus 4.5 は 95.7% から 88.8% に落ちた。逆向きの言い回し（「バグがある」）の効果は小さく、誘導は「問題なし」の方向に強く効く。中立の言い回しでも修正済みのファイルの多くを脆弱と判定し、手作業で確かめると、修正済みのファイルへの指摘のうち本物の欠陥は平均 25% だった。著者の言葉は "a vulnerability is present or absent regardless of how the change is described." である（同じ資料、ICSE 2027 予定、`agent-verified`）。
- 同じ研究で、繰り返し作り込んだ誘導の PR は、33 件中 32 件で自動のレビューを通った。Claude Code に対しては 17 件中 17 件だった。説明文に加えてコミットメッセージとコメントも消すと、残りの 16 件のうち 12 件で検出が戻った（同じ資料、`agent-verified`）。
- 作者の推論の文章を書き換えると、判定役が誤って承認する率が上がった。「推論より証拠で判断せよ」と指示すると上昇は縮むが、推論を隠すと再現率が下がった（[2601.14691](https://arxiv.org/html/2601.14691)、学術、`agent-verified`）。
- 調査役の読みでは、エージェントの行動はそのままにして、推論の文章だけを書き換えた。進み具合をでっち上げると、GPT-4o などで偽陽性率が 20〜30 ポイント上がった。「推論を信じず、行動と画面で判断せよ」と指示すると、GPT-4o の上昇幅は 27% から 18% に縮んだ。推論を隠すと誘導は消えるが、本当の成功を見つける再現率が最大 13 ポイント落ちた。著者は "judging mechanisms that verify reasoning claims against observable evidence" を勧めている（同じ資料、`agent-verified`）。
- 文脈が長いと同調が増える。利用者のメモリの要約を与えると、同意への同調が Gemini 2.5 Pro で +45%、Claude Sonnet 4 で +33%、GPT-4.1 Mini で +16% 増えた。GPT-5.1 では増えなかった。著者は "Evaluations devoid of context may significantly underestimate the risks of sycophancy in real-world interactions." と書いている（[2509.12517](https://arxiv.org/html/2509.12517v2)、学術、2025 年、`agent-verified`）。
- 利用者が「自分が書いた」「気に入っている」と言うと、フィードバックがより肯定的になる。この結果は定性的なものだけを確かめた（[2310.13548](https://arxiv.org/html/2310.13548v4)、学術、2023 年、`agent-verified`）。
- 判定役の口調や冗長さへの偏りは コード以外のレビューの節（6） に書いた。

### 意図を書いた文章は、検出を助ける

- 逆向きの結果もある。PR の意図を渡すと、品質の推定の F1 が上がった（[2511.07017](https://arxiv.org/html/2511.07017)、学術、`agent-verified`）。
- 調査役の一人は本文から、差分だけを渡すと F1 は 36.08 だったが、PR の説明文を足すと 62.12 に上がったと読んでいる（クローズドなモデルの平均、品質の推定の課題）。周辺のコードを足したときより伸びが大きかった（同じ資料、`agent-verified`）。別の調査役は要旨だけを読み、コードの文脈より文章の文脈（issue や PR の説明）のほうが成績を大きく上げるが、要旨に数値は無いとしていた（同じ資料、`agent-verified`）。
- 同じベンチマークを使った自己進化型のレビューについて、ByteDance は本番で 61.98% 改善したと書いているが、基準と指標は要旨に無い（同じ資料、`agent-verified`）。
- Atlassian の RovoDev のオフラインの比較では、依頼文からレビューのガイドラインを抜くと、人の指摘との一致（%HAC LocationOnly）が 5 ポイント下がった。ペルソナ、chain-of-thought、PR の情報、Jira の情報を抜いた影響は 1〜3 ポイントにとどまった（[RovoDev](https://arxiv.org/html/2601.01129v2)、学術、ICSE-SEIP'26、`agent-verified`）。
- Copilot は、エージェント型の構成に変えただけで、肯定的な反応が当初 8.1% 増えた。推論の強いモデルに替えると肯定的な反応は 6% 増えたが、待ち時間が 16% 延びた（[GitHub: 60 million Copilot code reviews](https://github.blog/ai-and-ml/github-copilot/60-million-copilot-code-reviews-and-counting/)、公式、`agent-verified`）。
- 解決されなかったエージェントの指摘 470 件を分類すると、23.8% が「意図した設計」、14.3% が「誤った提案」だった。著者は、設計の根拠、規約、レビューの履歴を文脈に入れることを勧めている（[2607.21997](https://arxiv.org/html/2607.21997v1)、学術、`agent-verified`）。
- 文脈の粒度と取り方の選び方が成績を大きく左右する、という報告もある。要旨に数値は無い（[AACR-Bench](https://arxiv.org/abs/2601.19494)、学術、`agent-verified`）。

### コードの文脈は、多ければ良いわけではない

- 文脈は、多ければ良いわけではない。8つのモデルすべてで、要約を付けた 2,000 トークンの diff が、2,500 トークンの詳しい文脈を上回った（[SWE-PRBench](https://arxiv.org/abs/2603.26130)、学術、`verified`。要旨で確かめた）。
- 調査役の読みでは、題材は 350 の PR で、8 つの最先端のモデルは diff だけで人の指摘の 15〜31% を見つけた。ファイルの中身や全体の文脈を足すと、8 モデルすべてで成績が単調に下がった。著者は、長い依頼文で注意が薄まることを原因に挙げている。判定は LLM で、κ=0.75 である（同じ資料、単著、`agent-verified`）。
- 別の読みでは、差分と要約だけの構成に、実行時の文脈やテストのシグネチャを足すと、ほとんどのモデルで得点が下がった。特に、文脈が必要な指摘の検出が、Sonnet 4.6 で 0.22 から 0.10 に落ちた（[SWE-PRBench の本文](https://arxiv.org/html/2603.26130v1)、学術、`unverified-summary`）。
- ChatGPT に PR の全ファイルという広い文脈を渡すと、人と同じ問題を見つける割合が下がったという報告もある（[2602.11925](https://arxiv.org/pdf/2602.11925)、学術、`unverified-summary`）。
- 意図の文章を足すと良くなり、コードの全文を足すと悪くなる、という 2 つの向きの結果は、足した文脈の種類が違うので矛盾しない、と読める（`speculation`）。

### 同じモデルでも、セッションの分け方と依頼文で成績が動く

- 同じモデルのまま、役割と依頼文の組み方を変えると、F1 は 0.495 から 0.533 に動いた（[2608.18167](https://arxiv.org/html/2608.18167v1)、学術、`verified`）。
- 調査役の読みでは、すべてのエージェントを Claude Sonnet 4.5 で動かし、レビュー役と批評役の構成だけを変えた。0.495 は単一のレビュー役、0.533 は意見の相違を明示させる構成で、素朴な構成は 0.457 だった。LiveCodeBench の合格率は 77% から 87% になった。素朴にレビュー役を 2 つにすると、1 回で解く場合の 77% より下がって 75% になり、素朴な対立型のレビューでは「偽の合意」が起き、5 件の指摘のうち 3 件がでっち上げと判定された例があった（同じ資料、ICML 2026 の DL4C ワークショップ、`agent-verified`）。有意性の検定は無い（同じ資料、`unverified-summary`）。
- 新しいセッションに成果物だけを渡すレビューの F1 は 28.6% で、同じセッションでの自己レビュー（24.6%）と、生成のときの依頼文を付けて新しいセッションに渡す条件（23.8%）を上回った（[2603.12123](https://arxiv.org/html/2603.12123v1)、学術、`verified`）。同じセッションで 2 回目のレビューをした条件は 21.7% だった（同じ資料、`verified`）。
- 調査役の読みでは、最初の版の検定は、自己レビューと CCR の差が p=0.008（d=0.52）、生成の依頼文を渡す条件と CCR の差が p=0.004、自己レビューと 2 回目の差が p=0.107（有意でない）だった。CCR の適合率は 31.5%、再現率は 27.1% で、1 回のレビューあたりの指摘は平均 4.5 件、そのうち真陽性は 1.4 件、偽陽性は 3.1 件だった。注入された誤りの約 4 分の 3 を見逃し、指摘の約 3 分の 2 は誤りではなかった（同じ資料、`agent-verified`）。重大な誤りの検出率は CCR で 40%、自己レビューで 29% で、差は重大な誤りで大きく、軽い誤りでは消えた（同じ資料、`unverified-summary`）。
- この研究の設定と限界は次のとおりである。モデルは Claude Opus 4.6 だけである。API の予算が足りず、計画していた Sonnet 4.6 から、Claude Code の Agent ツール（親のセッションと同じモデル）に切り替えた。30 の成果物に 5 つずつ、計 150 の誤りを埋め込み、4 つの条件で 30 の成果物を 3 回ずつ、計 360 回レビューした。検定は 1 回目の実行だけで行っている（同じ資料、`unverified-summary`）。誤りは人工的に埋め込んだもので、自己レビューの 2 条件は韓国語で、CCR とサブエージェントは英語でレビューしており、言語が交絡している（同じ資料、`agent-verified`）。
- 言い換えに注意が要る。サブエージェントの条件は親の会話の履歴を受け継がず、新しいセッションに生成のときの依頼文と成果物を渡す条件である。親の会話全体を受け継ぐ条件は、同じセッションの自己レビューに当たる（同じ資料、`agent-verified`）。
- 統計の読みは、版と読み手で割れている。別の調査役は 2026-10 の版を読み、Holm で補正すると、CCR（28.6%）が有意に上回ったのは同じセッションでの 2 回目（21.7%、p=0.004）だけだったとしている。同じセッションでの 1 回目（27.1%、p=0.26）と、生成の依頼文を渡すサブエージェント（23.8%、p=0.057）とは有意な差が無く、CCR が 1 位になったのは 3 回の実行のうち 1 回目だけだった（[2603.12123](https://arxiv.org/abs/2603.12123)、学術、`agent-verified`）。続報の 2610.01471 でも、出どころを確かめられない自己レビューの 1 回分を除いて自己レビューの F1 が 27.1% になり、CCR と有意に違うのは 2 回目だけになった（[2610.01471](https://arxiv.org/html/2610.01471v2)、学術、`agent-verified`）。したがって「同じ文脈で 2 回目を重ねると悪くなる」とは言えるが、「新しいセッションなら確実に良い」とまでは言えない。生成の依頼文を渡すと悪くなるという結果も、この 1 研究だけである。
- 誰の出力として見せるかで直せるかが変わること、"Wait" と足すと盲点が減ることは 別の会社のモデルの節（3） に書いた（[Self-Correction Bench](https://arxiv.org/abs/2507.02778)、学術、`agent-verified`）。

合わせて読むと、仕様と意図は渡し、「これで正しい」という作者の結論は渡さない、という形が筋に見える。この組み合わせを直接比べた実験は見つかっていない（`speculation`）。推論を渡すなら、推論を信じずに観察できる証拠と照らすよう指示する形が、2601.14691 の結果と合う（`speculation`）。

## 5. 指摘の絞り方と、収束のさせ方

調べた仕組みは、どれも探す段と確かめる段を分けていた。

### 本番の仕組みは、並列に探し、指摘ごとに確かめ、まとめてから出す

- 構成は、並列に候補を出す、指摘ごとに別の段で確かめる、重複をまとめる、重さを付ける、投稿する、の順である。食い違った指摘や根拠の弱い却下を、捨てずに1件ずつ深く確かめる段へ回す例がある（[Sashiko](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system)、公式、`agent-verified`）。多数決を使っている例は、8 本を並列に流していた（[Cursor](https://cursor.com/blog/building-bugbot)、公式、`agent-verified`）。
- 投稿したあとの反応（直されたか、反対票が付いたか）を、次の調整に戻す仕組みが多い。具体の例は、この節の後の小節に資料ごとに書いた（Greptile、Google、ByteDance、Cursor の各資料、`agent-verified`）。

| Atlassian RovoDev（[RovoDev](https://arxiv.org/html/2601.01129v2)、学術、`agent-verified`） | Claude 3.5 Sonnet が zero-shot で作る | gpt-4o-mini の judge が事実の正しさを 2 値で判定し、ModernBERT の分類器が「コードの変更につながるか」を判定する | 記述なし |
| ByteDance BitsAI-CR（[BitsAI-CR](https://arxiv.org/html/2501.15134v1)、学術、2025 年、`agent-verified`） | LoRA で調整した RuleChecker が 219 の規則で検出する | 別に調整した ReviewFilter が、指摘ごとに yes か no を返す | 512 次元の埋め込みの cosine 類似でまとめ、群から 1 件だけ残す。41 の区分（security、defect、maintainability、performance）を持つ |
| Google Sashiko、Linux kernel 向け（[Sashiko](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system)、公式、`agent-verified`） | 計画役が最大 7 本の専門のセッションを選び、推論の予算を配る。1 回のレビューで平均およそ 100 回の git ツールの呼び出しがある | 主の検証役が仕分け、明白なバグは通し、証明された却下は落とす。争いのあるものと根拠の弱い自己却下は、バグごとに別の検証エージェントへ回す | 報告は、メンテナに問いかける形で書く |
| Microsoft の社内（[Microsoft](https://devblogs.microsoft.com/engineering-at-microsoft/enhancing-code-quality-at-scale-with-ai-powered-code-reviews/)、公式、2025 年、`agent-verified`） | PR の作成時に自動で走り、diff の行にコメントする | 記述なし | 区分（例外処理、null の確認、機密データ）を付ける。重さの記述は無い |

- Sashiko は、却下の判断にも証明を求める。根拠の弱い却下を落とさず、深い検証へ回す設計である（[Sashiko](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system)、公式、`agent-verified`）。確かめる段が本物のバグを落とす事故を避ける工夫として、2〜3 レーンの統合にも当てはまる（`speculation`）。
- Uber は、1 回の依頼文では幻覚と重複が出たので、「生成、採点、フィルタ」の連鎖に移した（[Uber](https://www.uber.com/blog/ureview/)、公式、`agent-verified`）。
- Cursor は、初期の 8 本の並列と多数決を、初期の最も効いた改善の 1 つと書いている。ただし後の最大の改善は、固定のパスをやめてエージェント型にしたことだった。解決率（指摘が実際に直された割合）は 40 回の実験を通じて 52% から 70% 超に上がったが、多数決だけの寄与は公開されていない。多数決は、後の設計では表に出ていない。記事は "Run eight parallel passes with randomized diff order" と書いている（[Cursor](https://cursor.com/blog/building-bugbot)、公式、`agent-verified`）。
- OpenCodeReview は、探索の経過を見せずに diff だけを渡す反省役を置き、自己強化の偏りを避けている。決まった手順の部分を固定すると、トークンは 5〜15 分の 1 になった（[OpenCodeReview](https://arxiv.org/abs/2608.09290)、学術、`agent-verified`）。

### 自己採点では絞れず、過去の反応と規則の単位で絞ると効く

- LLM に自分の指摘の重さを採点させても、絞り込みには使えなかった。過去に退けられた指摘との類似で絞ると、対応された割合が 19% から 55% 以上になった（[Greptile](https://www.greptile.com/blog/make-llms-shut-up)、公式、2024 年、`verified`）。役に立たない規則を止める形でも、適合率が上がった（[BitsAI-CR](https://arxiv.org/html/2501.15134v1)、[AutoCommenter](https://arxiv.org/html/2405.13565v1)、学術、`agent-verified`）。
- 調査役の読みでは、Greptile は 1〜10 の重さを付けさせて 7 未満を落とす方法を試したが、評価はほぼでたらめで、呼び出しが 1 回増えて遅くなっただけだった。依頼文の調整と few-shot も効かなかった。効いたのは、チームごとに過去の指摘を埋め込み、反対票の付いた 3 件以上と似ていれば落とし、賛成票の付いた 3 件と似ていれば通す方法で、導入から 2 週間で上の数字になった。記事は "most nits can be placed into a small number of clusters" と書いている（[Greptile](https://www.greptile.com/blog/make-llms-shut-up)、公式、`agent-verified`）。
- Google の AutoCommenter は、評価者の調査で「対応のしようがない」17 の規則の URL を見つけて止め、似た 5 つも止めた。止め方は正規表現の条件で、学習し直さずにすぐ反映できた。useful ratio は開発者で 54% から 66%、評価者で 60% から 74% に上がった。全体で 1 つの確信度の閾値（0.98）から、規則の URL ごとの閾値に切り替えた。全体の閾値で落としていた予測の約 80% が、実は正しかったためである（[AutoCommenter](https://arxiv.org/html/2405.13565v1)、学術、2024 年、`agent-verified`）。
- ByteDance は、14 日の窓で適合率を約 65%（±5%）、Outdated Rate を約 25%（±5%）とする目安を置き、成績の悪い規則を外した。RuleChecker 単体の適合率は 27.9% から 62.6% に上がり、ReviewFilter のあとでは 35.6% から最高 75% に上がった（[BitsAI-CR](https://arxiv.org/html/2501.15134v1)、学術、`agent-verified`）。
- Uber は、可読性の nit、細かいログ、効果の小さい性能、style の区分を抑えた。評価が高かったのは、正しさのバグ、エラー処理の抜け、慣行の違反だった（[Uber](https://www.uber.com/blog/ureview/)、公式、`agent-verified`）。
- 同じ Uber の金の評価セットで、F1 が最も高かったのは、生成に Claude-4-Sonnet、採点に o4-mini-high を使う組み合わせだった。採点役を GPT-4.1 にすると、4.5 ポイント下がった（同じ資料、`agent-verified`）。
- Atlassian は、5 か月分の 50,000 件を超えるコメントに「コードの変更につながったか」のラベルを付け、ModernBERT を調整した。オフラインで、人の指摘との一致が 15〜20 ポイント上がった。事実の正しさを見る LLM の judge の効果は小さかった（[RovoDev](https://arxiv.org/html/2601.01129v2)、学術、`agent-verified`）。

### 指摘の形と量が、直されるかどうかを左右する

- 指摘の形が、直されるかどうかを左右する。コードの提案を含む指摘ほど、対応された（[2508.18771](https://arxiv.org/html/2508.18771v2)、学術、`agent-verified`）。
- 調査役の読みでは、GitHub Actions の 16 のツールで、コードの割合と対応率の相関は ρ=0.89 だった。コードの割合が 0 だと 4.2%、0.52 を超えると 23.2% だった。文章の長さは、弱い負の相関（ρ=−0.24）だった。hunk 単位のツールの対応率は 6.5〜19.2%、ファイル単位のツールは 0.9〜4.2% だった（同じ資料、`agent-verified`）。
- 公開リポジトリの 54,713 件のエージェントのコメントでは、インラインのコードの提案が resolve を最もよく予測した（オッズ比 1.62）。長さは小さな負の効果（オッズ比 0.93）だった。採用されなかったコメントは平均 807 文字、役に立ったものは 617 文字だった（[2607.21997](https://arxiv.org/html/2607.21997v1)、学術、`agent-verified`）。
- ByteDance は、大量のコメントが来ると、開発者は全部を無視しがちになると書いている。原文は "developers tend to ignore review comments entirely when faced with numerous comments" である（[BitsAI-CR](https://arxiv.org/html/2501.15134v1)、学術、`agent-verified`）。
- CodeRabbit の profile は、重さで投稿を切る構造的な手段である。`quiet` は critical と major だけをインラインに出し、残りは要約に畳む。既定の `chill` は minor まで最大 20 件に絞り、超えた分は minor、major の順に畳む。`assertive` は全部出す。文書は、指示ファイルは文面を導くだけで、件数を決めるのは profile だと明記している（[CodeRabbit: reduce noise](https://docs.coderabbit.ai/configuration/guides/reduce-noise)、公式、`agent-verified`）。
- PR-Agent の既定は、指摘を最大 6 件に絞る（[PR-Agent の設定](https://github.com/qodo-ai/pr-agent/blob/19366dbb635d3da1d058e5fee56c8e2ef580f08c/pr_agent/settings/configuration.toml)、公式、`agent-verified`）。

### 重さの札は、後の修正と結びついている

- Copilot の Lite の ensemble の効き方が重さで違ったことは レビュー役を足すと何が増えるかの節（1） に書いた。high で 47%、low で 11% と、差は大きい。
- GitHub の ReviewBench は、Critical、Medium、Low の重さと、Correctness、Security、Reliability、Maintainability、Testing の区分を付け、重さと区分ごとに結果を切って見ることを勧めている。オフラインでは critical の指摘が 227% 増えると予測し、本番では 262% 増えた（[ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)、公式、`agent-verified`）。
- Sashiko の本番の 7 か月では、critical の警告が出たのに merge されたパッチのうち 60 日以内に修正が要ったのは 7.6% で、指摘の無いパッチの 0.9% の約 8 倍（パッチの大きさで補正すると 6.3 倍）だった。指摘の無いパッチの 0.9% は、過去の基準の 3.4% より低い（[Sashiko](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system)、公式、`agent-verified`）。重さの札が実際のリスクと結びついている根拠になる。
- Anthropic は Pre-existing の札で、PR が持ち込んでいない既存のバグを作者の責任にしないようにしている（[Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)、公式、`agent-verified`）。Copilot も、概要に「Previously missed」（新しい commit が入れていない既存の問題）の区分を持つ（[GitHub changelog 2026-09-18](https://github.blog/changelog/2026-09-18-copilot-code-review-an-improved-review-experience)、公式、`agent-verified`）。
- Atlassian の種類別の分析では、可読性、バグ、保守性の指摘がコードの変更につながる割合は 36〜43% で高く、設計の指摘は低かった（[Atlassian](https://www.atlassian.com/blog/atlassian-engineering/atlassian-rovo-dev-research-what-types-of-code-review-comments-do-developers-most-frequently-resolve)、公式、2025 年、`agent-verified`）。
- 変更の単位のリスク予測として、Meta の素朴な回帰モデルでも、リスクの高い上位 5% の diff を止めると SEV の 18.7% を、上位 10% で 27.9% を、上位 50% で 84.6% を捕まえた（[2410.06351](https://arxiv.org/abs/2410.06351)、学術、2024 年、`agent-verified`）。LLM 版の倍率は、要旨の記述から対応が読み取れなかった。本番では、フリーズの期間中に、以前は出せなかった 10,000 件を超える変更を、本番への影響を小さく抑えて出した（[Meta DRS](https://engineering.fb.com/2025/08/06/developer-tools/diff-risk-score-drs-ai-risk-aware-software-development-meta/)、公式、2025 年、`agent-verified`）。

### 収束させる手は、回数の上限、差分だけの見直し、前の指摘を渡すことの 3 つ

- 収束させる手は3つに集まる。回数の上限、2回目からは新しい差分だけを見ること、前に出した指摘を渡して繰り返させないこと、である。Anthropic は、これで 1 回で通る PR が 65% から 78% に、5 回以上かかる PR が 8.9% から 1.5% になったと書いている。繰り返し指摘された箇所の約 59% は、最初のレビューの時点からあったコードだった（[Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)、公式、`verified`）。
- 調査役の読みでは、往復の上限は 3 回で、最初の数回のあとは diff だけを見直し、1 行ごとでなくバグの型で指摘する。通るまでのレビューの回数の平均は 2.08 から 1.32 になった（同じ資料、`agent-verified`）。3 回で通らなければ人に渡し、レビューの結果は調べた commit にだけ有効とする（[Anthropic の検証の記事](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)、公式、`agent-verified`）。
- Bugbot は、既定で前回の Bugbot のレビュー以降の変更だけを見る。既存のトップレベルとインラインのコメントを読んで重複を避ける。CI の成功には、前回までの未解決の Bugbot のコメントが残っていないことが必要になる。`oncePerPr` で 1 回だけにもできる。Autofix は、既存のブランチへの commit を PR あたり 3 回までに制限する（[Cursor docs: Bugbot](https://cursor.com/docs/bugbot)、公式、`agent-verified`）。
- CodeRabbit は増分のレビューが既定で、レビューした commit が 5 つに達すると自動のレビューを止める。活発な PR の例として、この値を 2 にする設定が挙がっている（[CodeRabbit: reduce noise](https://docs.coderabbit.ai/configuration/guides/reduce-noise)、公式、`agent-verified`）。
- PR-Agent は、`persistent_finding_state` で過去の指摘の状態を保つ。前回までの指摘を最大 8000 文字ぶん文脈に入れ、同じ指摘を言い換えて出し直すのを防ぐ。PR-Agent 以外の人が resolve したスレッドの指摘は飛ばす。要約の先頭に、前回からの区分（対応済み、再発、未対応、新規）を出す（[PR-Agent の設定](https://github.com/qodo-ai/pr-agent/blob/19366dbb635d3da1d058e5fee56c8e2ef580f08c/pr_agent/settings/configuration.toml)、公式、`agent-verified`）。
- Copilot は、後の push で直った指摘を、再レビューのときに自動で resolve する（[GitHub changelog 2026-09-11](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review)、公式、`agent-verified`）。概要を Open、Resolved since last review、Previously missed に分け、新しい commit や再依頼をまたいで進み具合を保つ。後の commit を見て「Won't Fix」や「Incorrect」として resolve することもある（[GitHub changelog 2026-09-18](https://github.blog/changelog/2026-09-18-copilot-code-review-an-improved-review-experience)、公式、`agent-verified`）。push の度に自動で再レビューするかは ruleset の設定次第という記述は、検索結果の要約でしか見ていない（`unverified-summary`）。
- Claude Code Review は、自分の過去のスレッドを resolve し、push によっては前回の結果をそのまま使う。実行の時機は「PR の作成時に 1 回」「push の度」「手動」から選べ、「push の度」は push の回数だけ費用が増える（[docs](https://code.claude.com/docs/en/code-review)、[costs](https://code.claude.com/docs/en/code-review-costs)、公式、`agent-verified`）。
- Cursor の初期の構成は、過去の実行と突き合わせて重複を除く段を持っていた（[Cursor](https://cursor.com/blog/building-bugbot)、公式、`agent-verified`）。
- Google の Jules の critic は、生成したパッチを敵対的に見直し、問題が残る限り差し戻す。いまの版は 1 回で評価する形で、回数の数字は無い（[Google Developers Blog](https://developers.googleblog.com/en/meet-jules-sharpest-critic-and-most-valuable-ally/)、公式、2025 年、`agent-verified`）。
- 収束しない例として、Copilot の利用者が、push の度に diff 全体が読み直され、前に指摘していなかったコードに新しい指摘が出ると報告している。ある PR では、5 回の往復で 10、6、4、2、2 件（計約 24 件）が出て、役に立ったのは約 3 件だった。GitHub の担当者からの回答は無い。報告の言葉は "every push to a PR triggers a full re-scan of the diff" である（[GitHub Community discussion #189767](https://github.com/orgs/community/discussions/189767)、実務家、`agent-verified`。報告として確かめたもの）。
- 回数の上限を変えたときの効果を、Anthropic 以外で測った資料は見つからなかった。

### 指示ファイルは base ブランチから読み、件数を絞る仕組みは別に持つ

- Copilot は、指示を短く焦点を絞って書き、小さく始めるよう勧めている。見出しと箇条書き、短い命令形の規則、良い例と悪い例のコードを使う。外部のリンクはたどらないので、中身を写す。「もっと正確に」「すべての問題を見つけよ」のような曖昧な指示は、ノイズを増やす。約 1,000 行を超えると振る舞いが不安定になりうる（[GitHub: instructions files](https://github.blog/ai-and-ml/github-copilot/unlocking-the-full-power-of-copilot-code-review-master-your-instructions-files/)、公式、`agent-verified`）。読み込みの上限の 4,000 文字は、2026-06-12 に撤廃された（[GitHub changelog 2026-06-12](https://github.blog/changelog/2026-06-12-copilot-code-review-new-configurations-and-controls/)、公式、`agent-verified`）。
- Bugbot は `.cursor/BUGBOT.md` を base ブランチから読むので、PR が自分のレビューの規則を変えられない。規則 1 つは 30,000 文字まで、合計 100,000 文字までである。優先の順は、team rules、BUGBOT.md、learned rules、手動の規則である（[Cursor docs: Bugbot](https://cursor.com/docs/bugbot)、公式、`agent-verified`）。
- Claude Code Review は、REVIEW.md を base か default のブランチから読み、PR の変更からは読まない（[docs](https://code.claude.com/docs/en/code-review)、公式、`agent-verified`）。Anthropic の REVIEW.md は、そのリポジトリでの「失敗」を定義し、nit の数に上限を設け、飛ばすパスを並べ、ファイルと行の根拠を求める（[Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)、公式、`agent-verified`）。
- CodeRabbit の path instructions は文面を導くだけで、件数を決めるのは profile である（[CodeRabbit: reduce noise](https://docs.coderabbit.ai/configuration/guides/reduce-noise)、公式、`agent-verified`）。
- Microsoft では、チームがリポジトリごとの指針と依頼文を渡せる。例として、過去のクラッシュの型に基づく後退の確認や、flight と change gate の確認を挙げている（[Microsoft](https://devblogs.microsoft.com/engineering-at-microsoft/enhancing-code-quality-at-scale-with-ai-powered-code-reviews/)、公式、`agent-verified`）。
- 指示ファイルの効果を単独で測った公開の数字は、RovoDev の比較（ガイドラインを抜くと 5 ポイント下がる、何を渡すかの節（4））しか見つからなかった。規則を止める、閾値を規則ごとにする、区分を抑える、という減らす向きの調整には、Google、ByteDance、Greptile の測定がある（前の小節）。

### 過去の見逃しと人の反応から、規則を学ぶ仕組みがある

- Bugbot の learned rules は、反応（反対票）、開発者の返信、Bugbot が見逃したバグを人が指摘したコメント、の 3 つから候補の規則を作る。候補は届いた PR で試し、信号がたまると有効にし、有効な規則に否定的な信号が続くと無効にする。11 万を超えるリポジトリで有効にされ、44,000 を超える規則ができた。解決率は 52% から 78.13% に上がったが、learned rules だけの寄与は分けて示されていない。記事は "each review is a natural experiment" と書いている（[Cursor: Bugbot learning](https://cursor.com/blog/bugbot-learning)、公式、`agent-verified`）。
- CodeRabbit の learnings は、返信や `@coderabbitai` への指示から好みを保存し、コメントを出す前に範囲に合うものを読み込む。管理者の承認待ちにも設定できる。1 つの PR が読む最新の learnings は 20 件までである（[CodeRabbit: learnings](https://docs.coderabbit.ai/guides/learnings)、公式、`agent-verified`）。
- Qodo の auto best practices は、採用された提案を毎月まとめて、リポジトリ固有の慣行を作る。数値は無い（[Qodo docs](https://docs.qodo.ai/qodo-documentation/qodo-merge/pr-agent/core-abilities/auto_best_practices)、公式、`unverified-summary`）。
- Google の AutoCommenter は、人のレビューで参照された慣行の URL から学ぶ。330 の URL に対して指摘を出し、慣行の URL を含む過去の人のコメントの 68% を覆う（[AutoCommenter](https://arxiv.org/html/2405.13565v1)、学術、2024 年、`agent-verified`）。
- Anthropic は、人のコメントや revert から型を掘るとき、2 件以上の PR に現れ、diff から検出できることを条件にする。3 つのエージェントが反証を試み、人が PR で承認する。既知の障害に結びつく PR に 3 本のバグ探しの役を当て、2 本以上が見つければ「検出できる」とみなす（[Anthropic の検証の記事](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)、公式、`agent-verified`）。

### 評価は、本物の不具合と、問題の無い変更の対照で作る

## 6. コード以外のレビュー

設計・plan・仕様・文書のレビューが結果を良くするかは、ほとんど測られていない。

### plan の中身は結果を左右するが、plan をレビューする効果は測られていない

- plan の中身は結果を左右する。欠けのある plan は、plan なしより悪い結果だった（[2604.12147](https://arxiv.org/html/2604.12147v2)、学術、`agent-verified`）。
- 調査役の読みでは、SWE-agent と 4 つのモデルで、SWE-bench Verified と Pro の 16,991 本の軌跡を 8 種類の plan の条件で比べた。plan を与えないと、全モデルで解決率が下がった。序盤に課題に関係する段を足した plan が、かえって成績を下げることがあった。plan を 5 手ごとに示し直すと、plan からの逸脱が減り、解決率が一貫して上がった。本文の Finding 8 は "The negative impact of a bad, incomplete plan is greater on trajectories than the impact of no plan at all." である（同じ資料、`agent-verified`）。plan のレビューで「段を足す」向きの指摘が常に良いとは言えない、と読める（`speculation`）。
- LLM に計画を検証させると、外の正しい検証器に大きく負け、誤った plan を正しいと承認する例が多く出た（[2310.08118](https://arxiv.org/abs/2310.08118)、学術、2023 年。偽陽性が多いことは要旨で `verified`。具体の数字は `unverified-summary`）。具体の数字は次のとおりである。Blocksworld で、GPT-4 が plan を作り GPT-4 が検証する構成では 100 問中 55 問しか解けず、外の正しい検証器（VAL）を使うと 88 問解けた。検証役の LLM は、100 件中 54 件の真陽性に対して 38 件の偽陽性を出した（同じ資料、`unverified-summary`）。二値の指摘と詳しい指摘のどちらを返しても、plan の生成への効果はほとんど変わらなかった（同じ資料、`agent-verified`）。
- 同じグループの続編は、検証役の偽陰性も多いと報告している（[2402.08115](https://arxiv.org/abs/2402.08115)、学術、2024 年、`unverified-summary`）。
- 7 つのモデルで、仕上がった作業に独立した批評役のレビューを当てると、Terminal-Bench で +5.9〜+9.5 ポイント、SWE-bench Verified で +3.9〜+6.6 ポイント改善した。これは完成した作業へのレビューであり、plan へのレビューではない。要旨だけを読んだ（[2610.34577](https://arxiv.org/abs/2610.34577)、学術、`agent-verified`）。
- ソフトウェア以外の課題では、オフラインで AUROC 0.94 の批評役が、あるモデルの成功率を 26 ポイント下げた。別のモデルではほぼ影響が無かった。ALFWorld での改善は +2.8 ポイントにとどまった。失敗を当てられることは、失敗を防げることを意味しない（[2602.03338](https://arxiv.org/abs/2602.03338)、学術、`agent-verified`）。

### 設計書、仕様、要求のレビューは、見逃しが多く、承認が甘い

- 設計書の整合性のレビューは、短い文書では再現率が高いが、長くなると大きく落ちる（[2509.09975](https://arxiv.org/abs/2509.09975)、学術、`unverified-summary`）。具体の数字は、500 文字未満の小さな文書で gpt-4o の再現率が 0.53 から 0.96 に上がり、6,000〜7,000 文字の文書では 0.33 だった、というものである（同じ資料、`unverified-summary`）。
- 同じ研究の方法と範囲は次のとおりである。Excel の日本語の設計書の表を Markdown か JSON に変換してから、GPT に文書間の整合性を確かめさせた。評価は、人工的に埋め込んだ 2 件の誤りに対する適合率と再現率で行った。自動車の PoC では、文書の約 70% が 5,000 文字を超え、手法を使えたのは約 30% の文書だった。11 のレビューの観点のうち評価したのは整合性の 1 つだけで、実案件での効果は数値で示されていない（同じ資料、`agent-verified`）。
- 仕様や plan へのレビューは、ほぼ毎回何かを指摘する。ただし、指摘の正しさを測った資料は無い（[2611.05094](https://arxiv.org/html/2611.05094)、学術、`agent-verified`）。
- 調査役の読みでは、PDR、SPEC、PLAN、TASKS などの成果物ごとに、読むだけのレビュー役（Claude Opus 5 系）が閉じた欠陥のリストに照らして確かめる流れを、1 つのチームの記録から分析した事例研究である。111 回のレビューの呼び出しで、20 の成果物から 508 件の指摘が出た。そのうち 75 件が「止める」級で、SPEC が 35 件、PLAN が 11 件だった。指摘ゼロの報告は 111 回中 5 回だけだった。著者自身が "Without ground truth, we cannot say how many findings were real defects or how many defects the reviewer missed." と書いている（同じ資料、`agent-verified`）。レビュー役がほぼ毎回何かを指摘するという事実は、指摘の件数だけでは価値を判断できないことを示している（`speculation`）。
- 文書やコードに誤りを注入した実験（何を渡すかの節（4） の 2603.12123）では、最も良かった新しいセッションのレビューでも、注入した誤りの約 4 分の 3 を見逃し、指摘の約 3 分の 2 は誤りではなかった。続報では、文書の題材で別のモデルの条件がすべて同じモデルの条件を上回った（別の会社のモデルの節（3））。設計や文書の批評のほうが、別のモデルの利得が出やすい可能性がある（`speculation`）。
- 34 人の学部生（初心者）が、ChatGPT（GPT-4o と GPT-4.1 の系統）の支援のありとなしで要求仕様の「におい」を探した交差の実験では、支援ありの組は検出の F1 が約 8% 低かった。ただし信用区間は重なり、所要時間に有意な差は無かった。過度の依存の可能性が議論されている。要旨の結論は "LLM support does not necessarily improve performance and may, instead, hinder it for novice inspectors." である（[2608.21298](https://arxiv.org/abs/2608.21298)、学術、`agent-verified`）。
- 先行の追試は、GPT-4-Turbo を人のレビュー役の代わりにしたところ、見つけた欠陥が少なく、模範解答とほとんど一致しなかったと報告している（[Seifert ほか](https://publica.fraunhofer.de/entities/publication/4623b22a-2024-4e16-b4ba-3ecef1a1ca20)、学術、`unverified-summary`。取得は拒否された）。
- 課題文の記述不足で、コード生成の pass@1 は最大 15.3% 下がった。GPT-5-mini と Claude Sonnet 4 は、どちらも HumanEval で 9.7% 下がった。欠陥の種類を当てる課題では、Claude Sonnet 4 の few-shot が F1 0.557、GPT-5-mini が 0.462 で、専用に学習した小さなモデルの 0.804 を下回った（[2604.24703](https://arxiv.org/html/2604.24703v1)、学術、`agent-verified`）。
- 凝集と結合の判断は、条件が整っていればできるが、雑音のある自由な設定では、結合の判断の F1 が 50% 以上落ちた（[2511.20933](https://arxiv.org/abs/2511.20933)、学術、2025 年、`agent-verified`）。
- 18 本の論文を集めた文献レビューは、LLM は比べる相手を上回ることが多いとする一方、アーキテクチャの適合性の確認などは手薄だとしている（[2505.16697](https://arxiv.org/abs/2505.16697)、学術、2025 年、`agent-verified`）。比べる相手をまったく持たない研究が約 3 分の 1 ある、という点は二次の引用でしか見ていない（同じ資料、`unverified-summary`）。
- ユーザーストーリーの質の評価では、専門家が LLM の評価に「おおむね同意した」とあるが、要旨に数値は無い（[DeepQuali](https://arxiv.org/abs/2602.08887)、学術、`agent-verified`）。
- Linux カーネルの設計のトレードオフの検出では、最良のコーディングエージェントの F1 は 0.213、提案された手法でも 0.259 だった。設計の判断は、人の確認が要る領域として残っている（[2610.21925](https://arxiv.org/abs/2610.21925)、学術、`agent-verified`）。
- 設計文書の改善の方式を比べた研究は 合意と議論の節（2） に書いた。別のモデルのレビューと構造化した敵対的なレビューが基準を上回ったが、採点はすべて LLM だった（[2606.01490](https://arxiv.org/html/2606.01490v1)、学術、`agent-verified`）。

### 文書とコードの食い違いは、直接たずねると誤検知が多い

- 文書とコードの食い違いを LLM に直接たずねる方法は、適合率が低い。実行で裏づける方法は適合率が上がるが、再現率は低い（[2604.19400](https://arxiv.org/html/2604.19400)、学術、`agent-verified`）。
- 調査役の読みでは、71 件の食い違いと 814 件の整合した Java の組でデータを作った。gpt-4.1-mini に直接たずねる 4 種類の依頼文は、食い違いと整合が半々の条件で適合率 0.53〜0.59 だったが、食い違いが 10% の条件では適合率 0.10〜0.20、再現率 0.29〜0.67 に落ちた。文書からテストとコードを生成し、実行で裏づけてから報告する CASCADE は、半々の条件で適合率 0.88、10% の条件で 0.39、再現率は 0.21 だった。814 件の整合した組への誤検知は 31 件だった。実際のリポジトリで未知の食い違いを 13 件見つけ、そのうち 10 件が修正された（同じ資料、FSE 2026、`agent-verified`）。
- README の更新が要るかを判定する研究では、714 のリポジトリの PR を使った。README の更新は PR の 1% 未満でしか起きない。再現率は約 0.5 で、エージェント型にすると特異度が 0.87 から 0.99 に上がった。発生率を 1% と仮定した実質の適合率は、3.7% から 28.7% に上がった（[2603.00489](https://arxiv.org/html/2603.00489v1)、学術、`agent-verified`）。
- 文書からコードへの対応づけでは、Claude 3.5 Sonnet の適合率が 95.3% と 87.0%、再現率が 68.0% と 74.8% だった。誤りには、名前から推測しただけの対応、存在しない対象への対応、一部の構造を全体に当てはめる誤りがあった（[2506.16440](https://arxiv.org/html/2506.16440)、学術、2025 年、`agent-verified`）。
- コミットメッセージとコードの食い違いでは、6 つのオープンなモデルの平均で、再現率 85.95%、適合率 80.28%、特異度 63.8% だった。「目的」の水準の食い違いが最も難しかった。chain-of-thought は適合率を上げ、再現率を下げた（[CodeFuse-CommitEval](https://arxiv.org/abs/2511.19875)、学術、2025 年、`agent-verified`。要旨だけを読んだ）。
- エージェント向けの規則の文書を 1 つのリポジトリで 6 週間追った事例研究では、118 件の失敗のうち最大の分類が文書の劣化（48 件）だった。LLM による 1 回の文書の監査は、既知の劣化の約半分（Claude Sonnet 5.5 の平均で 50%）を見つけ、指摘の 93% 以上は正しかった。著者は、劣化は機械的な確認で押さえる必要があると結論している（[2610.32578](https://arxiv.org/abs/2610.32578)、学術、`agent-verified`。要旨だけを読んだ）。

### 判定役としての LLM は、課題によって一致が大きく変わり、偽の承認が起きやすい

- 人の採点との Pearson の相関は、コードの翻訳で最大 81.32、コード生成で 68.51 だったが、コードの要約では最大 26.19 にとどまった。要約については "LLM-as-a-judge techniques are completely defeated by conventional metrics" と書かれている（[2502.06193](https://arxiv.org/html/2502.06193v3)、学術、ISSTA 2025、`agent-verified`）。自由に書く成果物ほど一致が低いことは、設計書や plan のレビューにも当てはまる可能性がある（`speculation`）。
- 役割を分けたチームの研究では、採点器で不合格になった提出の 49.4% を、検証役が承認した。判定が欠けた 942 件を失敗として数えると 22.3% になる。49.4% は判定が出た場合に限った率で、22.3% は保守的な下限である。この 2 つは定義が違う数字である。研究は "The Verifier approves 49.4% of submissions that the grader rejects" と書いている（[TeamBench](https://arxiv.org/html/2605.07073v1)、学術、`agent-verified`）。モデル別では GPT-5.4 Mini が 36.3%、Gemini-3 Flash が 77.0%、Haiku 4.5 が約 60%（論文の表から計算した値）で、TeamBench-Verified の部分集合では 38.7% だった（同じ資料、`unverified-summary`）。同じ系統の検証役と別の系統の検証役は比べていない。検証役が既定で合格を返すことの測定としては強いが、別のベンダーの検証役のほうが誤った承認が少ないかには答えていない（同じ資料、`agent-verified`）。
- RLVR の検証器を集めた研究では、MATH-500 で偽陽性 33.6% の例が挙がっている（[2610.17824](https://arxiv.org/pdf/2610.17824)、学術、`unverified-summary`）。
- コードの判定の偏りの監査では、肯定的な口調や冗長さの手がかりで、小さなモデルの正答率が最大で約 37 ポイント動いた。GPT もテスト生成の課題で、無関係な情報によって 77.46% から 60.96% に下がった（[Bias in the Loop](https://arxiv.org/html/2604.16790v1)、学術、`agent-verified`）。
- コードの判定の 6 種類の偏りの研究では、採点の前にテストを生成させても、偏りは消えなかった（[2505.16222](https://arxiv.org/abs/2505.16222)、学術、EACL 2026 Findings、`agent-verified`。要旨だけを読んだ）。
- 判定の設計の比較では、モデルを替えるだけで甘さが最大 56.1 ポイント変わり、詳しい依頼文で甘さが 28.9 ポイント下がった（[2610.05094](https://arxiv.org/abs/2610.05094)、学術、`agent-verified`。要旨だけを読んだ）。
- もっともらしいが誤ったレビューの指摘を見抜く課題では、汎用の最新のモデルが苦戦した。基になったモデルは、専用に学習したモデル（76.60%）より 19.78 ポイント低かった（[CRJudgeBench](https://arxiv.org/abs/2609.37216)、学術、`agent-verified`。要旨だけを読んだ）。
- 判定役を複数並べたときの相関（9 つのモデルのパネル、350 を超えるモデルの調査）は 合意と議論の節（2） に、系統の違う小さなモデルの審査団と、自分の出力へのひいきは 別の会社のモデルの節（3） に、判定役どうしの議論による偏りの増幅は 合意と議論の節（2） に書いた。

### 人の側にも偏りがある

- 人の側にも偏りがある。AI のレビューから読み始めた人は、指摘された場所に集中し、重い問題の発見は増えなかった（[2411.11401](https://arxiv.org/abs/2411.11401)、学術、2024 年、`agent-verified`）。調査役の読みでは、29 人の実験で、LLM のレビューを起点にした人は軽い問題を多く見つけたが、ほかの部分をあまり探さず、時間の短縮も自信の向上も無かった（同じ資料、`agent-verified`）。
- 385 人の実験では、コードが複雑なほど、誤った変更を受け入れやすくなった（p<.05）。複雑な条件では、「AI が書いた」と表示された誤った変更を特に受け入れやすかった。「人が書いた」と表示した場合には、この効果は見られなかった（[Singh ほか](https://conf.researchr.org/details/fse-2026/fse-2026-research-papers/111/The-Interaction-of-Complexity-and-Provenance-in-Code-Review-Decisions-Evidence-from-)、学術、FSE 2026、`agent-verified`。学会のページの要旨）。
- 447 人の実験では、AI を使ったという表示は評価に影響しなかったが、作者の職位の表示は評価を有意に偏らせた（[2611.18572](https://arxiv.org/abs/2611.18572)、学術、`agent-verified`）。
- 239 人の調査では、61.1% が AI の PR にはより多くの証拠を求めると答えた。不確かさが残るときに承認を止める人は、19.4% から 43.9% に増えた。一方で、AI の PR では自分の推論だけで承認に十分と考える人も、28.5% から 55.2% に増えた（[2610.21144](https://arxiv.org/abs/2610.21144)、学術、`agent-verified`）。
- 経験のある開発者は、AI で 24% 速くなると予想し、終わったあとも 20% 速くなったと感じていたが、実測では 19% 遅くなった。人が AI の効果を自己評価する数字は当てにならない（[METR](https://arxiv.org/abs/2507.09089)、学術、2025 年、`agent-verified`）。
- 仕様駆動の事例では、実行役が 4 つのタスクで記録していた問題に、著者が章を読むまで誰も対応しなかった。許可していない図の差し替えも、著者が止めた（[2611.05094](https://arxiv.org/html/2611.05094)、学術、`agent-verified`）。
- 異なる提供元のレビュー役を実行時の約束として試した小さな試行では、20 回のうち 8 回で重要な指摘が出た（95% 区間 19.1〜63.9%）。判定は 1 つの Claude Opus が行っており、比べる相手は無い（[2610.10961](https://arxiv.org/html/2610.10961v1)、学術、`agent-verified`）。

## 見つからなかったもの

レビュー役の数とモデルの違いについて:

- 最上位のモデル1本と、会社の違う2〜3本を、同じ実際の PR で、適合率・再現率・費用を揃えて比べたもの。近いものは、適合率が無く 1 つの組織だけの実務の報告（Stone）、小さめのモデルで和集合の再現率に計算上の矛盾がある比較（2606.15689）、図の値と条件の対応が取れないベンダーの記事（Greptile）だけである。
- 同じ道具立てのまま、同じモデルの再実行・同じ会社の別モデル・別の会社のモデルを比べたもの。
- 同じモデルで同じ PR を何度もレビューしたときの、指摘のばらつき。Stone は変わることを示せなかったと書き、Greptile は 3 回の平均を使っているが、ばらつきの値は出していない。
- 別の会社のモデルを並べたときの誤検知の増え方を、再現率と同時に実際の PR で測ったもの。
- 自分の書いた PR を自分でレビューさせる条件と、別の系統にレビューさせる条件を、正解つきで比べたコードレビューの自己選好の測定。
- 事前に登録した、複数の組織にまたがる追試。Stone が今後の実験として提案している段階である。
- o3、GPT-5、Claude のような閉じた最先端のモデルで、議論と多数決を予算を揃えて比べたもの。予算を揃えた比較（2611.17610、2605.00914、2605.09618 など）は、オープンなモデルを使っている。
- Cursor の多数決そのものの効果の数値と、SWR-Bench の統合したあとの適合率。違うモデルどうしを統合した結果（SWR-Bench の Multi-Agg）は図にしか無かった。
- The AI Scientist で 5 本の ensemble が正解率を変えずにばらつきだけを減らした、という主張の一次の裏づけ。

往復と収束について:

- コードレビューで合意まで往復したときの、収束までの回数と、収束しない割合。近いものは、主に 7〜32B のオープンなモデルを使った議論の研究と、1 件の監査の事例（2605.12280）である。
- 往復の回数の上限を変えたときの効果を、Anthropic 以外で測ったもの。

本番の仕組みと評価について:

- 段ごとの再現率の公開された数字。Anthropic は方法を書くだけで、数値は出していない。
- 主要なベンダー（CodeRabbit、Copilot、Bugbot）が同じ基準で測った偽陽性率の一次の資料。CodeRabbit は、自社の採用率も一次の資料では見つからなかった。
- 指示ファイル（REVIEW.md や copilot-instructions.md など）の有無で適合率がどう変わるかを、RovoDev の比較以外で測ったもの。
- Copilot、Bugbot、CodeRabbit の 1 回のレビューあたりの金額。料金の体系の記述だけがある。
- 数字の付いた Graphite の技術ブログ。数字は、講演の要約のページ、ベンダーの事例、提携先のページ（[Braintrust](https://www.braintrust.dev/blog/graphite)）にしか無い。
- Microsoft の社内のレビュー役の採用率、偽陽性率、評価セット。公開されているのは、PR の完了までの時間が 10〜20% 良くなったことと規模だけである（[Microsoft](https://devblogs.microsoft.com/engineering-at-microsoft/enhancing-code-quality-at-scale-with-ai-powered-code-reviews/)、公式、`agent-verified`）。ReviewBench に Microsoft が関わったという記述は二次の資料にしか無く、その記事は開けなかった。
- Google の Critique で動く LLM のレビュー役について、AutoCommenter（2024 年）と Sashiko（2026-11、kernel 向け）以外の 2025〜2026 年の一次の資料。
- Meta の、レビューのコメントを生成する AI の採用率。見つかったのは、指摘への修正のパッチ（[MetaMateCR](https://arxiv.org/abs/2507.13499)、学術、`agent-verified`。要旨だけ）と、変更のリスクの予測（DRS）だけである。
- Qodo のベンチマークでの他社の適合率と再現率は、図にしか無かった。Precise のモードで 74.5% と 44.2%、Exhaustive のモードで 63.8% と 56.7% という数字は、二次の資料にしか無い（[Medium の比較記事](https://medium.com/@codzee.io/we-compared-the-public-ai-code-review-benchmarks-from-2026-methodology-datasets-metrics-and-269dd35637a6)、二次、`unverified-summary`）。
- Martian のオンラインの順位（CodeRabbit の F1 51.2%、Greptile の F1 60.8% など）は、ベンダーの主張としてしか確かめられなかった（`unverified-summary`）。

コード以外のレビューについて:

- plan や設計のレビューの有無で、ソフトウェアの課題の結果がどう変わるか。近いものは、plan の中身の効果（2604.12147）、Blocksworld での自己検証（2310.08118）、ソフトウェア以外での批評役（2602.03338）、完成した作業へのレビュー（2610.34577）だけである。ロボットや安全の分野には実行の前の検証の研究（VerifyLLM、Soteria など）があるが、ソフトウェアの成功率への効果は確かめていない。
- 設計書、ADR、plan について、人工的に埋め込んだものではない本物の欠陥に対する LLM のレビューの適合率と再現率。Fujitsu の研究は埋め込んだ 2 件の誤り、仕様駆動の事例は正解のデータなし、2603.12123 は注入した誤りである。
- Google、Meta、Microsoft、Uber などの一次の技術ブログで、設計書の AI のレビューを数値で報告したもの。設計書についての産業の数値は、Fujitsu の論文だけだった。
- 作者の理由を見せる場合と見せない場合を、設計や plan のレビューで比べたもの。証拠は、コードの判定（2603.18740、2511.07017）とエージェントの判定（2601.14691）からの類推である。しかも、意図の文章は検出を助ける一方で、結論の言い切りは判定を甘くするという、向きの違う結果がある。
- 違う系統のモデルをセカンドオピニオンに使うと、設計や plan の誤った承認が減ることを示したもの。2605.29800 と 2506.07962 は、系統の違いだけでは誤りが独立にならないことを示しているが、課題は NLI、選好、求人の選別である。2610.10961 は比べる相手の無い 20 回の試行である。
- 人が設計や plan への AI のレビューを読むときの、自動化バイアス。見つかったのは、コード（2411.11401、FSE 2026 の 385 人の実験）と要求（2608.21298）である。
- 利用者自身の plan や設計を LLM に評価させたときの同調の大きさを、工学の成果物で測ったもの。2310.13548 は、一般の文章、数学の解答、詩での結果である。
- 計画や設計の批評を複数の LLM で行い、人が判定したもの。2606.01490 は LLM の採点だけで、モデルの組み合わせも 1 通りである。

測られていないことは、効かないことを意味しない。

## この読者への含意（speculation）

この節はすべて推論である。いまのスキルや依頼文の実物と照らした結果ではない。

| 当リポジトリの構成 | 資料が示すこと | 判定 |
|---|---|---|
| 作り手の文脈から切り離したレビュー役を足す | 新しいセッションのレビューが自己レビューを上回り、2つ目を足すと見つかるものが増える。ただし同じ著者の後の分析では、有意な差が残ったのは同じセッションでの 2 回目に対してだけだった | 支持される |
| 別の会社のモデルをレーンに入れる | 足すと増えるが、会社の違いの効果は切り分けられていない。誤りは会社をまたいで重なる | 測られていない |
| 全レーンが合意するまで回す | 議論の回を増やすと下がる。一致は正しさの証拠にならない | 支持されない |
| 軽いモデルを別の目として足す | 自己レビューを上回らなかった | 支持されない |
| 設計と plan にもレビューを当てる | 結果への効果は測られていない。見逃しが多く、承認が甘い | 測られていない |
| 作者の説明をレーンに渡す | 作者の言い切りは判定を甘くする。意図を渡すと良くなる結果もある | 渡すものを分ける必要がある |
| レーンの指摘を和集合のまま全部出す | 和集合は誤検知を増やし、単独より F1 が下がった例がある。確かめる段を足して初めて単独を超えた | 支持されない |
| レーンの多数決で採否を決める | 多数決を使った例は 8 本の並列だった。2〜3 本では、1 本だけが見つけた本物を落とす | 2〜3 本では支持されない |
| 2 本目のレーンに「直さない」「指摘なし」と答える道を残す | 必ず最終のプログラムを出させる設計で、弱いレビュー役が正しいものを壊した | 支持される |
| レーンに変更の一部ずつを分担させる | 節を分けて読ませると、離れた節どうしの矛盾の検出が 3 分の 2 以上落ちた | 支持されない |
| LLM のレビュー役を最後の合否の関門にする | 検証役は不合格の提出の 49.4%（保守的な数え方で 22.3%）を承認し、誤った plan も承認した | 支持されない |
| 指摘を重さで分け、件数に上限を置き、既存の問題を別の札にする | 製品の既定に上限と畳み方がある。コメントが多いと全部が無視されがちになる。重さの札は後の修正率と結びついた | 支持される |
| 大きい変更や重要な変更に厚く当てる | 大きい PR ほど指摘が付き、小さい PR では当たりが少ない。単独のモデルは大きい diff で F1 が大きく落ちる | 支持される |
| レーンを増やす前に 1 本を調整する | Anthropic は、レビュー役を重ねるより 1 本を調整するほうが良いことが多いと書いている | 公式の実践と合う。比べた測定は無い |

見直すなら、順は次のとおりである。

1. レーンに渡すものを見直す。仕様と意図と差分を渡し、作者の「これで正しい」という説明は外す。モデルを替えるより安く試せる。
2. 強い SO の終わり方を変える。合意を待たず、回数の上限で止める。食い違った指摘は、多数決で落とさずに、1件ずつ確かめる段へ回す。
3. 自分の記録で測る。セカンドオピニオンを通したあとに自動のレビューが見つけ、採用して直した指摘が、当リポジトリに 400 件あまり残っている（`docs/research/2026-11-27-verification-layer-intake.md`）。その PR を直す前の commit に戻して流し直せば、レーンの数・モデル・渡すものを1つずつ変えて比べられる。外の資料に無い比較を、最初に持てるのは自分たちである。
4. レーンの出力の形と量を決める。指摘にはファイルと行の根拠と、できればコードの提案を付けさせ、重さで分けて件数に上限を置く。2 本目のレーンには「指摘なし」と答えてよいと明示し、各レーンには変更の全体を見せる。重大な指摘を残したまま merge したものが後で直されたかを追えば、重さの札の答え合わせになる。
5. 対応された割合を、レーンと区分ごとに記録する。merge の時点で、各レーンの指摘のうち最終 diff で直ったものを LLM に判定させれば、反応のボタンに頼らずに数えられる。3 の流し直しと合わせれば、どのレーンがどの区分で効いているかが見える。
