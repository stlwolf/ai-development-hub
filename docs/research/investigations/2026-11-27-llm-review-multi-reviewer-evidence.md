# LLM のレビュー役を複数にする効き目の裏付け — 調査メモ

- 作成: 2026-11-27（調べたのは 2026-11-27）
- 状態: 調査の結果をまとめた版（追記前提）
- 関連 issue: [#690](https://github.com/stlwolf/ai-development-hub/issues/690)（セカンドオピニオンのレーンの数と、別の系統のモデルを入れる値打ちを確かめる）
- 調べた問い:
  - レビュー役を複数にすると、1つのときより良くなるか。議論・投票・回の繰り返しは、いつ効いて、いつ効かないか。
  - 別の会社のモデルのレビュー役は、同じ系統のレビュー役が見逃すものを見つけるか。同じモデルに新しい文脈を渡すのと、どう違うか。
  - 実際のレビューの仕組みは、指摘をどう絞り、どう収束させ、どう評価しているか。
  - コード以外（設計・plan・仕様・文書）のレビューと、判定役としての LLM の信頼性について、何が測られているか。
- 進め方: 問いごとに調査役（Claude Opus 5.5）を1つずつ動かし、取りまとめた側がこの文書にまとめた。調査役のメモ4本は、付録として `docs/research/investigations/2026-11-27-llm-review-evidence/` に置いた。
- 根拠の札:

  - `unverified-summary` 検索結果の抜粋か、二次の資料しか見ていない。または、照らそうとして本文で見つけられなかった。

## 結論: 効くのは独立した目を足して別の段で絞ることで、合意を待つことではない

独立したレビュー役を1つ足すと、見つかる問題は増える。これは複数の測定で一貫している。その1つが別の会社のモデルである必要があるかは、まだ誰も切り分けていない。

合意するまで往復させることと、全員の一致を正しさの証拠にすることは、どちらも支持されなかった。議論の回を増やすと正解率が下がった測定があり、全員が一致した判定でも 9.1% は誤りだった。効いているのは、並列に候補を出し、指摘ごとに別の段で確かめる形である。

レビュー役に何を渡すかは、モデルの違いと同じくらい効く。作者の言い切りは判定を甘くし、文脈を増やすと成績が下がることもある。

設計・plan・仕様のレビューが結果を良くするかは、ほとんど測られていない。測られた範囲では、見逃しが多く、承認が甘い。

当リポジトリの使い方（最上位のモデルを含む2〜3の系統のレーンを、実際の PR と設計と plan に当てる形）にいちばん近い比較は、外の資料に無かった。

## 1. レビュー役を足すと、何が増えるか

増えるのは再現率と指摘の数である。適合率は、絞る段を置かないと下がる。

- 同じモデルに 10 回レビューさせて統合すると、F1 は相対で 43.67%、再現率は相対で 118.83% 伸びた。5 回を超えると伸びは小さく、費用は回数に比例する。著者は、適合率がまだ解けていない問題だと書いている（[SWR-Bench](https://arxiv.org/html/2509.01494v2)、`verified`）。
- 検証役を置かずにエージェントを3つ合わせると、適合率は単独より低かった（.526 と .555）。検証役を足すと、F1 は .714 から .772 に上がった（[2604.21282](https://arxiv.org/html/2604.21282v1)、`verified`）。費用が約 3.5 倍になった、という点は `agent-verified` である。
- GitHub Copilot は、複数のモデルを組み合わせる構成にして、対応された割合が +8.0%、再現率が +13.6%、指摘の数が +61% になったと報告している（[ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)、`agent-verified`）。
- 変更が大きいほど、指摘が付く。Anthropic は、1,000 行を超える PR の多くに指摘が付き、小さい PR の多くは指摘なしで返ると書いている（[Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)、`verified`）。

## 2. 合意と議論は、効くか

議論の回を増やしても良くならず、全員が一致しても正しいとは限らない。

- 複数のエージェントに議論させる手法では、回を増やすほど正解率（平均）が下がった。2 回で 0.7377、3 回で 0.7112、5 回で 0.7050 である（[2508.17536](https://arxiv.org/html/2508.17536v2)、`verified`）。改善の大半が議論の前の多数決で説明できる、という読みは `agent-verified` である。この種の研究の多くは、小さめのオープンモデルを使っている。
- 9つのモデルを判定役に並べると、得られた情報は約2票分だった。全員が一致した項目でも 9.1% は誤りで、独立なら約 0.02% になるはずの値である。いちばん相関が高かった組は、会社をまたいでいた（[2605.29800](https://arxiv.org/html/2605.29800v1)、`verified`）。
- 350 を超えるモデルの調査では、両方のモデルが誤ったとき、約 60% で同じ誤答を選んだ。正確なモデルほど、誤りが相関した（[2506.07962](https://arxiv.org/html/2506.07962v1)、`verified`）。
- 10 のレビュー役が全員一致で支持した誤った脆弱性の指摘が、1 回の実行で否定された例がある（[2604.19049](https://arxiv.org/abs/2604.19049)、`agent-verified`）。
- 予算を揃えて比べると、マルチエージェントの優位は平均でわずかに負だった（[2611.17610](https://arxiv.org/abs/2611.17610)、`agent-verified`）。

コードレビューで「合意するまで往復する」形を測った資料は、見つからなかった。近いものとして、レビューと修正が一晩で 50 回を超えた実例を Anthropic が書いている（`verified`）。

## 3. 別の会社のモデルは、要るか

足すと増えるのは確かである。効いているのが「会社の違い」なのか「もう1つ足したこと」なのかは、分かれていない。

- 同じモデルの新しいセッション（F1 は 28.6%）と、別の会社の上位モデル（32.3%）のあいだに、有意な差は出なかった。著者は、同等であることを示すものではないと書いている。2つを組み合わせると、見つかる誤りの割合は、同じモデルを2回使った場合の 42.7% から 56.7% に上がった。別の会社のモデルを2回使った場合と、混ぜた場合に、有意な差は無かった（145 件中 76 件と 82 件、p=.184）。レビュー役はそれぞれ違う道具と指示で動いていた。差が出たのは文書の題材で、コードの題材では同じモデルの新しいセッションのほうが高かった（[2610.01471](https://arxiv.org/html/2610.01471v2)、`verified`）。軽いモデルを別の会社の目として足しても、自己レビューを上回らなかった（`agent-verified`）。
- 別の会社のモデルを足した実務の報告（網羅率が 33.6% から 57.1%）は、著者が後の版で取り下げた。訂正後は 47.2% から 72.3% で、著者は、レビュー役の数に対する曲線であって会社の違いの効果ではない、と書いている（[Stone v2](https://zenodo.org/records/21328807)、`unverified-summary`。訂正版を取得できなかった）。
- レビューの向きで、結果が逆になる。あるモデルが別のモデルの成果物をレビューすると、合格率は 71.6% から 89.7% に上がった。逆の組み合わせでは、91.4% から 82.8% に下がった（[2607.21656](https://arxiv.org/html/2607.21656v1)、`verified`）。直した数より壊した数が多く、レビュー役に「直さない」を選ぶ道が無かった、という点は `agent-verified` である。
- 道具立てを固定すると、モデルの構成を替えても、見つけた件数は同じだった。ただし中身は PR ごとに違った（[2611.26942](https://arxiv.org/html/2611.26942)、`unverified-summary`。本文で該当の数字を見つけられなかった）。
- 自分の出力をひいきする傾向は、小さいか、検出されなかった。効いていたのは、モデルの系統より、誰の出力として見せるかだった（[2609.17857](https://arxiv.org/html/2609.17857)、[2507.02778](https://arxiv.org/abs/2507.02778)、`agent-verified`）。
- 最上位の1モデルの出力だけを集める形が、違うモデルを混ぜる形を上回った結果もある（[2502.00674](https://arxiv.org/abs/2502.00674)、`agent-verified`）。

## 4. 何を渡すかで、変わること

モデルを替えなくても、渡すものと頼み方で成績が動く。

- 作者が「不具合は無い」と強く言い切る文を付けると、脆弱なコードの検出率が落ちた。落ち方はモデルで大きく違い、あるモデルは 97.2% から 3.6% に、別のモデルは 97.4% から 75.5% になった。PR の説明文でレビューを誘導する実験では、説明文を消すと、誘導が成功した 32 件のうち 16 件で検出が戻った（[2603.18740](https://arxiv.org/html/2603.18740)、`verified`）。
- 作者の推論の文章を書き換えると、判定役が誤って承認する率が上がった。「推論より証拠で判断せよ」と指示すると上昇は縮むが、推論を隠すと再現率が下がった（[2601.14691](https://arxiv.org/html/2601.14691)、`agent-verified`）。
- 逆向きの結果もある。PR の意図を渡すと、品質の推定の F1 が上がった（[2511.07017](https://arxiv.org/html/2511.07017)、`agent-verified`）。
- 文脈は、多ければ良いわけではない。8つのモデルすべてで、要約を付けた 2,000 トークンの diff が、2,500 トークンの詳しい文脈を上回った（[SWE-PRBench](https://arxiv.org/abs/2603.26130)、`verified`。要旨で確かめた）。
- 同じモデルのまま、役割と依頼文の組み方を変えると、F1 は 0.495 から 0.533 に動いた（[2608.18167](https://arxiv.org/html/2608.18167v1)、`verified`）。
- 新しいセッションに成果物だけを渡すレビューの F1 は 28.6% で、同じセッションでの自己レビュー（24.6%）と、生成のときの依頼文を付けて新しいセッションに渡す条件（23.8%）を上回った（[2603.12123](https://arxiv.org/html/2603.12123v1)、`verified`）。

合わせて読むと、仕様と意図は渡し、「これで正しい」という作者の結論は渡さない、という形が筋に見える。この組み合わせを直接比べた実験は見つかっていない（`speculation`）。

## 5. 指摘の絞り方と、収束のさせ方

調べた仕組みは、どれも探す段と確かめる段を分けていた。

- 構成は、並列に候補を出す、指摘ごとに別の段で確かめる、重複をまとめる、重さを付ける、投稿する、の順である。食い違った指摘や根拠の弱い却下を、捨てずに1件ずつ深く確かめる段へ回す例がある（[Sashiko](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system)、`agent-verified`）。多数決を使っている例は、8 本を並列に流していた（[Cursor](https://cursor.com/blog/building-bugbot)、`agent-verified`）。
- LLM に自分の指摘の重さを採点させても、絞り込みには使えなかった。過去に退けられた指摘との類似で絞ると、対応された割合が 19% から 55% 以上になった（[Greptile](https://www.greptile.com/blog/make-llms-shut-up)、`verified`）。役に立たない規則を止める形でも、適合率が上がった（[BitsAI-CR](https://arxiv.org/html/2501.15134v1)、[AutoCommenter](https://arxiv.org/html/2405.13565v1)、`agent-verified`）。
- 収束させる手は3つに集まる。回数の上限、2回目からは新しい差分だけを見ること、前に出した指摘を渡して繰り返させないこと、である。Anthropic は、これで 1 回で通る PR が 65% から 78% に、5 回以上かかる PR が 8.9% から 1.5% になったと書いている。繰り返し指摘された箇所の約 59% は、最初のレビューの時点からあったコードだった（`verified`）。
- 指摘の形が、直されるかどうかを左右する。コードの提案を含む指摘ほど、対応された（[2508.18771](https://arxiv.org/html/2508.18771v2)、`agent-verified`）。
- 対応された割合は、仕組みごとに定義が違うので、横に並べて比べられない。
- 評価は、revert や後から直されたバグを題材にし、大きさを揃えた問題の無い変更を対照に置く。人工的に埋めたバグは点数を大きく見せる。ある研究では、人工の題材で F1 が 0.847 だったモデルが、実際の PR では 0.066 だった（[2606.15689](https://arxiv.org/abs/2606.15689)、`agent-verified`）。

2〜3 レーンしか無い構成で多数決を取ると、1つのレーンだけが見つけた本物を落とす（`speculation`）。

## 6. コード以外のレビュー

設計・plan・仕様・文書のレビューが結果を良くするかは、ほとんど測られていない。

- plan の中身は結果を左右する。欠けのある plan は、plan なしより悪い結果だった（[2604.12147](https://arxiv.org/html/2604.12147v2)、`agent-verified`）。
- LLM に計画を検証させると、外の正しい検証器に大きく負け、誤った plan を正しいと承認する例が多く出た（[2310.08118](https://arxiv.org/abs/2310.08118)。偽陽性が多いことは要旨で `verified`。具体の数字は `unverified-summary`）。
- 文書とコードの食い違いを LLM に直接たずねる方法は、適合率が低い。実行で裏づける方法は適合率が上がるが、再現率は低い（[2604.19400](https://arxiv.org/html/2604.19400)、`agent-verified`）。
- 設計書の整合性のレビューは、短い文書では再現率が高いが、長くなると大きく落ちる（[2509.09975](https://arxiv.org/abs/2509.09975)、`unverified-summary`）。
- 仕様や plan へのレビューは、ほぼ毎回何かを指摘する。ただし、指摘の正しさを測った資料は無い（[2611.05094](https://arxiv.org/html/2611.05094)、`agent-verified`）。
- 人の側にも偏りがある。AI のレビューから読み始めた人は、指摘された場所に集中し、重い問題の発見は増えなかった（[2411.11401](https://arxiv.org/abs/2411.11401)、`agent-verified`）。

## 見つからなかったもの

- 最上位のモデル1本と、会社の違う2〜3本を、同じ実際の PR で、適合率・再現率・費用を揃えて比べたもの
- 同じ道具立てのまま、同じモデルの再実行・同じ会社の別モデル・別の会社のモデルを比べたもの
- コードレビューで合意まで往復したときの、収束までの回数と、収束しない割合
- plan や設計のレビューの有無で、ソフトウェアの課題の結果がどう変わるか
- 作者の理由を見せる場合と見せない場合を、設計や plan のレビューで比べたもの
- 人が設計や plan への AI のレビューを読むときの、自動化バイアス
- 段ごとの再現率の公開された数字

測られていないことは、効かないことを意味しない。

## この読者への含意（speculation）

この節はすべて推論である。いまのスキルや依頼文の実物と照らした結果ではない。

| 当リポジトリの構成 | 資料が示すこと | 判定 |
|---|---|---|
| 作り手の文脈から切り離したレビュー役を足す | 新しいセッションのレビューが自己レビューを上回り、2つ目を足すと見つかるものが増える | 支持される |
| 別の会社のモデルをレーンに入れる | 足すと増えるが、会社の違いの効果は切り分けられていない。誤りは会社をまたいで重なる | 測られていない |
| 全レーンが合意するまで回す | 議論の回を増やすと下がる。一致は正しさの証拠にならない | 支持されない |
| 軽いモデルを別の目として足す | 自己レビューを上回らなかった | 支持されない |
| 設計と plan にもレビューを当てる | 結果への効果は測られていない。見逃しが多く、承認が甘い | 測られていない |
| 作者の説明をレーンに渡す | 作者の言い切りは判定を甘くする。意図を渡すと良くなる結果もある | 渡すものを分ける必要がある |

見直すなら、順は次のとおりである。

1. レーンに渡すものを見直す。仕様と意図と差分を渡し、作者の「これで正しい」という説明は外す。モデルを替えるより安く試せる。
2. 強い SO の終わり方を変える。合意を待たず、回数の上限で止める。食い違った指摘は、多数決で落とさずに、1件ずつ確かめる段へ回す。
3. 自分の記録で測る。セカンドオピニオンを通したあとに自動のレビューが見つけ、採用して直した指摘が、当リポジトリに 400 件あまり残っている（`docs/research/2026-11-27-verification-layer-intake.md`）。その PR を直す前の commit に戻して流し直せば、レーンの数・モデル・渡すものを1つずつ変えて比べられる。外の資料に無い比較を、最初に持てるのは自分たちである。
