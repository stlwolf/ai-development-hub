- **一言で:** エージェント系コーディング向けの、ローカルファーストなワークフロー実行ツール（YAML で定義し Codex / Claude / Cursor 等のステップを繋ぐ）

### これは何か・何を解決するのか

[Rigg README](https://raw.githubusercontent.com/tryrigg/rigg/main/README.md) によれば、実装計画・レビューループ・修正検証・コードベースチェックなど、ターミナルやプロンプトでアドホックに行っていた多段作業を **`.rigg/*.yaml` として明示化**し、**Git 管理下で共有・標準化**するためのツール。対象ユーザーは「ローカル AI エージェントに仕事を移しているチーム」。

### 設計思想・アーキテクチャ

- **Local-first:** ワークフローをリポジトリ隣に置き、クラウド必須ではない運用を前提にしている（README の語彙）。
- **プロバイダ横断のステップ型:** `shell` に加え `codex` / `claude` / `opencode` / `cursor` などのタイプで「エージェント呼び出し」を同一ワークフロー内に並べられる（README 「Supported step types」）。
- **制御フロー:** `group`, `loop`, `branch`, `parallel` により複合フローを記述可能（同上）。
- **実行モードの二分:** TTY ありではインタラクティブ UI・バリア（承認）あり。`--headless` は CI/スクリプト向けで TTY 不要・バリア自動進行。README の「Notes」節に動作差が整理されている。
- **実行履歴:** ローカル DB が使えるとき `history` / `show` / `logs` で参照（README）。`packages/rigg/drizzle` および `drizzle.config.ts` の存在から永続化層が TypeScript パッケージ内にまとまっている（[directory listing](https://api.github.com/repos/tryrigg/rigg/contents/packages/rigg)）。

### 特徴的な点・注目ポイント

1. **「プロンプト習慣」をワークフロー資産化する** という打ち出しが明確（README 1–2 段落）。
2. **単一ツールロックインではなく**、複数 CLI（Codex / Claude / Cursor 等）を **同じ YAML 内でオーケストレーション**できる点がプロダクト差別化になりうる。
3. **`write_file` ステップ**があり、エージェント実行とファイル生成をパイプライン化できる（README 列挙。詳細は未読）。

### 使い方・典型的なワークフロー

README より（一次情報）:

```bash
rigg init
rigg list
rigg validate
rigg run <workflow_id> --input key=value
rigg run <workflow_id> --headless --output-format json
```

最小例（README の `smoke` ワークフロー）:

```yaml
id: smoke
inputs:
  name:
    type: string
steps:
  - id: greet
    type: shell
    with:
      command: echo "hello ${{ inputs.name }}"
      stdout:
        mode: text
```

要件: Bun 1.3.10、各 `type` に応じて `codex` / `claude` / `opencode` / `cursor` が PATH に必要（README Requirements）。

## 創作者コンテキスト（Zenn・二次ソース）

**出典:** [ハーネスエンジニアリングで人間のコードレビューをやめる（Akatsuki / Zenn, 2026-03-24 公開）](https://zenn.dev/theaktky/articles/1c6c3b9333117c)。記事本文は **製作者視点の解説記事**であり、リポ README や `review.yaml` と照合できる部分を一次に寄せ、それ以外は二次として扱う。

記事がこのリポジトリの調査と接続する要点:

- **動機:** 「ターミナルを行き来して CLI 出力をコピペしていた」手動フローを、**同じ手順を残す**ために Rigg に落とした、という因果（記事内「ワークフローとして定義する」節）。README の「private prompt habits」から **Git 管理のワークフロー**への転換と同型。
- **ハーネス四役（記事での整理）:** Constrain / Inform / Verify / Correct。OpenAI・Mitchell Hashimoto 等の公開議論との接続を記事が橋渡ししている（詳細は [Hub 側の整理](../../../projects/orchestration-research/synthesis/harness-engineering-mapping.md) と [ハーネス記事インデックス](../harness-engineering/README.md)）。
- **実レビューループ（記事）:** Codex review → Composer 2 による **トリアージ（severity・オシレーション検出・スコープ）** → Codex 修正 → Composer 2 バリデーション → コミット、を最大 6 周。終了条件に **構造化 findings の件数** を使う、という語り。
- **Rigg 実体への引用:** 記事は実運用ワークフローを [`.rigg/review.yaml`](https://github.com/tryrigg/rigg/blob/main/.rigg/review.yaml) にリンクしている。本調査では同ファイルを raw で取得し、**記事の5ステップ語りと機械可読定義の対応**を下表に整理した。

### 記事のステップと `review.yaml` の対応（検証）

| 記事での呼び名 | `review.yaml` 上の実装（要約） |
|----------------|--------------------------------|
| Step 1 レビュー（Codex） | `steps.remediation.steps.review` — `type: codex`, `kind: review`, `model: gpt-5.4`, base `main` |
| Step 2 トリアージ（Composer 2 と記載） | 実際は **`type: shell`** 内で `claude -p … --model claude-opus-4-6` と **Bun で JSON 抽出**。記事の「Composer 2」と **実装の Claude headless が不一致**。記事は概念モデル、YAML は作者の現在の実行構成と解釈するのが安全 |
| Step 3 修正（Codex） | `steps.remediation.steps.fix` — `type: codex`, `kind: turn`, triage 済み findings + **directives（オシレーション解消の拘束）** |
| Step 4 バリデーション（Composer 2 と記載） | `steps.remediation.steps.validate` — **`cursor agent --print … --model composer-2`**（記事と一致） |
| Step 5 コミット | `steps.remediation.steps.commit` — 変更があれば `git commit` |
| ループ上限 | 親ステップ `type: loop`, `max: 6`, `until` に **findings 件数ベース**の式 |

**検証メモ:** `review.yaml` は Rigg 自リポジトリ用に **`private/typescript-implementation-guide.md`** 等のパスがハードコードされている。**そのまま ai-development-hub にコピーしても動かない**。流用するときは入力・ガイドライン参照を差し替える必要がある（後述）。

## エンジニアリング文脈での位置づけ

- **問題领域:** 「単発プロンプト」ではなく **フィードバックループ付きのマルチステップハーネス**。ハーネス記事群で言う *Verify / Correct* と *ループ* に直結。
- **Rigg の特徴（README＋`review.yaml` 合成）:** 複数ベンダ CLI を **宣言的 YAML** で束ね、`loop` / `if:` / ステップ間の **`${{ … }}` 式**でデータを渡す。headless・JSON stdout は CI 統合向け（README Notes）。
- **Zenn 記事が補うもの:** **なぜそのループ構成になったか**（過剰指摘・振り子・バンドエイド）という **運用ナラティブ**。README だけでは読み取れない「改善を Git diff で残す」動機。

### 流用・実験の現実的判断（検証結果ベース）

- **そのまま流用:** 不可。`review.yaml` は **Rigg モノレポ専用パス・コマンド**（`bun run check` 等）に依存。
- **パターン流用（有望）:**  
  - **構造化 findings → 終了条件** を peer-ai-review 系フローに取り込む設計メモ化  
  - **directive オブジェクト**（振り子止め）を `implementer-contract` やレビューログに **JSON 形で残す**案の示唆  
  - **validate ステップを別セッション／別モデルに固定**する分離（Hub では既に Codex/Claude の役割分担に近い）
- **Rigg 導入を Hub に「依存」として載せるか:** リポジトリ規約は **Bash＋Markdown 薄型**（[`AGENTS.md`](../../../AGENTS.md)）。Rigg（Bun バイナリ・`.rigg/`）を **任意プロジェクト配下**で使うのは整合するが、**canonical に必須ツールとして取り込む**かは別判断（メンテ・再現性・ライセンスの確認が先）。
