## rulesync 調査結果

### 基本情報

- **リポジトリ:** [dyoshikawa/rulesync](https://github.com/dyoshikawa/rulesync)
- **言語:** TypeScript (Node.js CLI)
- **最終更新:** 2026-04-04（v7.27.1）
- **規模:** 970 stars, 97 forks, 59 open issues, コントリビュータ上位5名（主開発者 dyoshikawa が大半）
- **ライセンス:** MIT
- **配布:** npm (`rulesync`), Homebrew (`brew install rulesync`), シングルバイナリ（実験的）
- **一言で:** 統一されたMarkdownルールファイルから、27種以上のAIコーディングツールのネイティブ設定ファイルを自動生成するCLI

### これは何か・何を解決するのか

AIコーディングアシスタントの設定ファイルは断片化している。Cursor は `.cursor/rules/*.mdc`、Claude Code は `CLAUDE.md`、GitHub Copilot は `.github/copilot-instructions.md`、Gemini CLI は `GEMINI.md` と、各ツールが独自形式を要求する。チームで複数ツールを使う場合、同じルールを複数箇所に重複記述・同期する必要があり、管理コストが高い。

rulesync は `.rulesync/` ディレクトリ以下にMarkdown形式でルール・MCP設定・コマンド・サブエージェント・スキル・フック・ignore・パーミッションを一元管理し、`rulesync generate` 一発で各ツールのネイティブ形式に変換・出力する。逆方向（既存の設定ファイルから `.rulesync/` へ取り込む）の `rulesync import` もサポートし、既存プロジェクトからの移行を容易にしている。

**ターゲットユーザー:** 複数のAIコーディングツールを使い分けるチーム・個人開発者。特にルールの一貫性と監査可能性を重視する組織。

### 設計思想・アーキテクチャ

**中核の抽象:** "feature x target" マトリクス。8種類の feature（rules, ignore, mcp, commands, subagents, skills, hooks, permissions）と 27種の target（claudecode, cursor, copilot 等）の組み合わせで生成を制御する。各組み合わせは `src/features/{feature}/` 配下に個別プロセッサとして実装されている。

**設計上の判断:**

1. **ノーロックイン:** 生成されたファイルはプレーンな設定ファイルであり、rulesync を削除しても動き続ける。これは README と why-rulesync ドキュメントで繰り返し強調されている。
2. **宣言的設定:** `rulesync.jsonc` で targets と features を宣言し、ワイルドカード `"*"` で全対象を指定可能。per-target で feature を絞ることもできる。
3. **Frontmatter 駆動のルーティング:** `.rulesync/rules/*.md` の YAML frontmatter（`root`, `targets`, `globs`, `description` + ツール固有パラメータ）でルールの配置先を制御。
4. **Simulated Features:** commands/subagents/skills をネイティブサポートしないツールに対して、ルールファイル内にシミュレーション命令を埋め込む仕組み。ツール間の機能格差を吸収する。
5. **外部スキル取得とロックファイル:** `sources` 宣言 + `rulesync install` で外部リポジトリからスキルを取得し、`rulesync.lock` で再現性を担保。npm/yarn のパッケージ管理と同じメンタルモデル。

**依存ライブラリ:** commander (CLI), zod (スキーマバリデーション), effect (関数型エフェクトシステム), js-yaml/jsonc-parser (設定パース), @octokit/rest (GitHub API), fastmcp + @modelcontextprotocol/sdk (MCP サーバー)

**ディレクトリ構造の意図:**

```
src/
  cli/commands/    # CLI サブコマンド（generate, import, init, fetch, install, mcp, gitignore, update）
  features/        # feature 別プロセッサ（rules, ignore, mcp, commands, subagents, skills, hooks, permissions）
  types/           # 型定義（ToolTarget, Feature, RulesyncFile 等）
  config/          # 設定スキーマ・パース
  mcp/             # MCP サーバー実装
  lib/             # 共通ライブラリ
  utils/           # ユーティリティ
```

### 特徴的な点・注目ポイント

**1. ツールサポートの網羅性**

27種のAIコーディングツールをサポートし、それぞれで rules/ignore/mcp/commands/subagents/skills/hooks/permissions の8種類の feature を（サポート範囲に応じて）生成できる。README の対応表は圧巻で、各ツールの project mode / global mode 対応まで明記されている。新ツールの追加ペースも速く、v7.x 系だけで Kiro, Google Antigravity, AugmentCode, deepagents-cli 等が追加されている。

**2. Simulated Features のアプローチ**

Commands やスキルをネイティブサポートしないツール（例: Copilot の commands, AGENTS.md の commands/subagents/skills）に対して、ルールファイル内に「このプロンプトパターンが来たらこう振る舞え」という命令を埋め込む。`s/your-command` という省略記法まで定義しており、ツール間の機能格差を吸収する独自の解法。

**3. Declarative Sources + Lockfile**

外部スキルを `rulesync.jsonc` の `sources` で宣言し、`rulesync install` で取得、`rulesync.lock` で SHA をピン止めする。npm のパッケージ管理と同じ UX で、CI での `--frozen` フラグも用意。スキルのエコシステム形成を見据えた設計。

**4. MCP Server 内蔵**

`rulesync mcp` で MCP サーバーが起動し、AI エージェントが `.rulesync/` 内のファイルを CRUD できる。ツール定義は「1つだけ」に抑えてトークン消費を最小化している点が実践的。

### 使い方・典型的なワークフロー

**新規プロジェクトでの導入:**

```bash
# 1. インストール
npm install -g rulesync

# 2. 初期化（.rulesync/ ディレクトリ + サンプル + rulesync.jsonc を生成）
rulesync init

# 3. 公式スキルの取得（推奨）
rulesync fetch dyoshikawa/rulesync --features skills

# 4. rulesync.jsonc の編集
# targets: 使用ツールを指定、features: 生成対象を指定
```

**rulesync.jsonc の例:**

```jsonc
{
  "$schema": "https://github.com/dyoshikawa/rulesync/releases/latest/download/config-schema.json",
  "targets": ["copilot", "claudecode", "cursor"],
  "features": ["rules", "ignore", "mcp", "commands", "subagents", "skills"],
  "baseDirs": ["."],
  "delete": true
}
```

**ルールファイルの例（`.rulesync/rules/overview.md`）:**

```markdown
---
root: true
targets: ["*"]
description: "Project overview and conventions"
globs: ["**/*"]
---

# Project Overview

TypeScript プロジェクト。ESLint + Prettier で統一。
コミットは Conventional Commits 形式。
```

**既存プロジェクトからの移行:**

```bash
# Claude Code の CLAUDE.md を取り込み
rulesync import --targets claudecode

# Cursor の .cursorrules を取り込み
rulesync import --targets cursor

# 取り込んだ内容を全ツールに生成
rulesync generate --targets "*" --features "*"
```

**CI での利用:**

```bash
# 生成結果が最新かチェック（差分があれば非ゼロ終了）
rulesync generate --check
```

rulesync の最大の差別化要因は **対応ツール数と feature カバレッジの広さ**。特に hooks, permissions, simulated features, MCP server は他ツールにない。一方で対応範囲が広い分、各ツールの仕様変更への追従コスト（メンテナンスバーデン）も大きく、Issue に見られるように細かい不整合が発生しやすい。

自分のリポジトリ（ai-development-hub）との比較: 我々は `scripts/sync.sh` でシェルスクリプトベースの同期を行っているが、rulesync は「ツールネイティブ形式への変換」まで担う点が異なる。我々のアプローチは「canonical/ のファイルをそのままコピー」で変換ロジックを持たないため、各ツールの形式差を手動で吸収している。rulesync は変換を自動化する代わりに Node.js 依存を導入する。

### 制約・注意点

1. **Node.js 依存:** CLI 実行に Node.js（npm/npx）が必要。シングルバイナリは実験的で、Bun ベースの62.8MBバイナリ（Deno 時代の565MBから縮小）
2. **高速な breaking changes リスク:** 10ヶ月で v7.27 に達する開発速度。設定スキーマや CLI インターフェースの変更頻度が高い可能性
3. **単一メンテナ:** コントリビュータ上位は dyoshikawa の複数アカウント + AI。バス因子は低い
4. **ツール側仕様変更への追従:** 27ツールの仕様変更を継続的に追いかける必要がある。Issue を見ると、Antigravity の .gitignore 競合、Copilot subagents の拡張子問題、Windsurf の frontmatter 問題など、各ツール固有の不整合が発生している
5. **Global Mode の制約:** 現状 rules と commands のみ、root ファイル1つ限定、commands は Claude Code のみ
6. **生成ファイルの .gitignore 管理:** 生成ファイルを `.gitignore` に入れるか入れないかはプロジェクト方針次第だが、`rulesync gitignore` コマンドで管理する設計のため、既存の .gitignore 運用との統合に注意が必要

### 深掘り候補（コードリーディング対象）

1. **`src/features/rules/` 配下の各ツールプロセッサ** — frontmatter パースから各ツール形式への変換ロジック。特に simulated features の埋め込み方法
2. **`src/features/hooks/` 配下** — hooks の統一フォーマットから各ツール固有形式への変換（特に Cursor の camelCase vs Claude Code の PascalCase 変換）
3. **`src/mcp/` 配下** — MCP サーバー実装。「1ツール定義」でトークン消費を抑える設計の詳細
4. **`src/cli/commands/install.ts`** — ロックファイル解決・integrity チェックのフロー
5. **`src/types/ai-file.ts`** — RulesyncFile の基底クラス。ファイル抽象の設計
6. **`src/config/config.ts`** — 設定マージ（CLI args, rulesync.jsonc, rulesync.local.jsonc）のプリオリティ
