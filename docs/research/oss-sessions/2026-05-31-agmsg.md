## agmsg 調査結果

### 基本情報

- **リポジトリ:** [github.com/fujibee/agmsg](https://github.com/fujibee/agmsg)
- **公式サイト:** [agmsg.cc](https://agmsg.cc/)（調査時点でTLS証明書のSAN不一致により直接取得不可）
- **言語:** Shell（100%）。依存は `bash` と `sqlite3` のみ
- **作成:** 2026-04-02 / **最終 push:** 2026-05-31（調査当日も活発）
- **規模:** Star 209 / Fork 9 / Open Issues 19。コントリビュータは実質1名（`fujibee` 43コミット、`utenadev` 1コミット）。リリースタグは0（タグ運用なし、main 直進行）
- **ライセンス:** MIT
- **一言で:** Claude Code / Codex / Gemini CLI など複数のCLI AIエージェントが、共有SQLite DB経由で互いに直接メッセージをやり取りできるようにする「エージェント間メッセージング」ツール

### これは何か・何を解決するのか

複数のCLIコーディングエージェントを併用する開発者が「人間がコピペ中継役（copy-paste relay）になってしまう」問題を解消する。

作者 fujibee の原体験（[DEV.to 記事, 2026-05-28](https://dev.to/fujibee/i-built-agmsg-so-claude-code-and-codex-could-stop-using-me-as-a-copy-paste-relay-m42)）：Claude Code をメインドライバ、Codex を難所のレビュー役として使っていたが、Claude の出力をCodexに貼り、レビュー結果をClaudeに貼り戻す作業を1日に数十回繰り返していた。「ループの中で一番バカげた仕事＝メッセージを運ぶ係」になっていると気づき、エージェント同士が直接話せる仕組みを作った。

`agmsg` は「2つのエージェントが同じ team に join すれば、互いにメッセージを送受信できる」というシンプルな抽象を提供する。対象ユーザーは、複数のCLIエージェントを並行運用するパワーユーザー。

### 設計思想・アーキテクチャ

#### 中核の設計判断（[ARCHITECTURE.md](https://github.com/fujibee/agmsg/blob/main/ARCHITECTURE.md) / [docs/design.md](https://github.com/fujibee/agmsg/blob/main/docs/design.md)）

- **最小依存・デーモンレス・ネットワークレス:** python3 / node / 常駐プロセス / ネットワークを意図的に排除。`bash` + `sqlite3` + 標準テキストツール（awk/sed）のみで動く。JSONの読み書きも sqlite3 の JSON1 関数で完結させ、別のJSONパーサを持たない
- **共有SQLite + WALモード:** 当初テキストファイル方式を試したが並行アクセスで破損。WALモードのSQLiteに移行し「単一writer + 複数reader」の並行安全性とメッセージ履歴を得た
- **アイデンティティとメタデータの分離:** エージェントの本質的アイデンティティは `(name, team)` のペア。プロジェクトパスや type（claude-code/codex/gemini等）は登録メタデータとして保持。これにより「同一名のエージェントを複数プロジェクトから join しても重複しない」
- **フックによる受信検知:** 別デーモンを立てず、エージェント既存のフック機構（Stop フック＝応答後トリガ）に統合してメッセージ到着を検知。Claude Code と Codex でフックAPIが異なるため抽象化している
- **クールダウン機構:** 過剰なinboxチェックを防ぐため、マーカーファイルで間隔（デフォルト60秒）を管理。DB状態ではなくファイルで持つため、カスタムストレージパスの影響を受けない

#### 3軸ドライバモデル（注目すべき設計）

ARCHITECTURE.md は「storage / agent / delivery の3軸が独立に差し替え可能」というモデルを掲げる。任意の storage ドライバ × 任意の agent ドライバ × 任意の delivery モードを組み合わせられる。

- **storage 軸:** SQLite（デフォルト）/ jsonl-duckdb
- **agent 軸:** Claude Code / Codex / Gemini / Antigravity
- **delivery 軸:** monitor / turn / both / off

[ADR 0001（ストレージドライバのプラグイン化, PR #52）](https://github.com/fujibee/agmsg/blob/main/docs/adr/0001-storage-driver-pluginization.md) で、ドライバは bash の source 可能な関数群として `<axis>_check` / `<axis>_describe` 等のプロトコルを実装する設計が定義されている。新規書き込みは append-only な **イベントログ**（UUIDv7採用）へ向かい、既存の整数ID メッセージテーブルは後方互換のため opaque string として維持。依存欠如時はドライバが `AGMSG-DIRECTIVE`（JSON形式）を出力し、ホストエージェントがユーザー同意の上で依存をインストールできる（ドライバが自前インストールしない方針）。ドライバ切替は staging + atomic flip による安全な変換。

#### データモデル（実スキーマ確認, 2026-05-31 ソース直読）

現 main の `scripts/init-db.sh` / `scripts/join.sh` を直読して確認した実体。「リレーショナルなメッセージ表」＋「JSON ドキュメントなエージェント台帳」のハイブリッド。

```sql
-- scripts/init-db.sh が作るのはこの 1 テーブルのみ
CREATE TABLE messages (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  team       TEXT NOT NULL,
  from_agent TEXT NOT NULL,
  to_agent   TEXT NOT NULL,
  body       TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now')),
  read_at    TEXT                 -- NULL = 未読
);
CREATE INDEX idx_unread  ON messages(team, to_agent, read_at) WHERE read_at IS NULL;
CREATE INDEX idx_history ON messages(team, created_at DESC);
```

- **messages**: メッセージ 1 通 = 1 行の素直なチャットログ。既読は `read_at` の NULL/非NULL で表現し、未読 inbox は部分インデックス `idx_unread`（未読行のみに張る）、履歴は `idx_history`（team 単位の時系列降順）で引く。
- **エージェント台帳**: リレーショナル表ではなく **JSON ドキュメント**。`{"agents": {"<agent_id>": {"registrations": [{team, type, project, ...}, ...]}}}` を SQLite の JSON1 関数（`json_extract` / `json_set` / `json_each`）で出し入れする（`join.sh` / `whoami.sh` / `team.sh`）。別の JSON パーサを持たない方針の実体。1 エージェントが複数 `registrations`（複数チーム所属）を持てる構造で、`(name, team)` アイデンティティはこの配列で表現される。
- **共有している構造化状態はこれだけ**: 「宛先付きメッセージのログ + 誰がどのチームに居るかの台帳」。かなり薄い。orchestration-engine の文脈では「共有する構造化状態」の最小形サンプルとして参照価値がある。

**訂正（本ノート初版の記述）**: 初版で「整数 ID メッセージテーブル + **イベントログ(UUIDv7)**」がデータモデルの実体と書いたが、**イベントログは現 main の `init-db.sh` には存在しない**。これは ADR 0001 / storage-driver 化（進行中）の設計であり、`scripts/lib/storage.sh` のコメントも "once the storage-driver work lands" と将来形。現 main の実体は上記 messages 表 + JSON 台帳の 2 つ。下記「設計判断」「深掘り候補」のイベントログ言及は ADR レベルの将来設計として読むこと。

### 機能一覧

#### コア機能（差別化の中心）

- **エージェント間メッセージング（send/inbox）:** `send.sh <team> <from> <to> "<msg>"` で送信、`inbox.sh` で受信＆既読化。中核。`scripts/send.sh`, `scripts/inbox.sh`
- **チーム/アイデンティティ管理:** `join.sh` でチーム登録、`team.sh` でメンバー一覧、`leave.sh` で離脱。`(name, team)` がアイデンティティ。`scripts/join.sh`, `scripts/team.sh`, `scripts/whoami.sh`
- **4つの delivery モード（差別化）:** `monitor`（SQLite常時購読でリアルタイム割り込み、約5秒）/ `turn`（Stopフックでターン間チェック、Codexデフォルト）/ `both`（monitor主＋turn保険）/ `off`（手動）。`scripts/delivery.sh`, `scripts/watch.sh`
- **actas / drop（複数ロール、差別化）:** 1プロジェクトで複数の役割を切り替え。`actas` は排他ロックを取り、ロック中は同チームの他者がそのロール宛購読を止める。`scripts/actas-claim.sh`, `scripts/lib/actas-lock.sh`

#### 補助機能（ユーティリティ）

- **メッセージ履歴:** `history.sh <team> [agent_id] [limit]`。`scripts/history.sh`
- **チーム名リネーム:** `rename-team.sh`（全参照を更新、既存メンバーに移行ヒント表示）。`scripts/rename-team.sh`
- **ストレージパス上書き:** 環境変数 `AGMSG_STORAGE_PATH`（PR #59 / Issue #49）でDB位置を変更可能
- **ストレージドライバ CLI:** convert / export / import / show / list / switch（Issue #54〜#57で実装）
- **セッションフック:** session-start / session-end による monitor の起動・後始末
- **マルチエージェント対応:** Claude Code / Codex に加え Gemini・Antigravity（agy）を追加（PR #45）。OpenCode 対応はPR #63で進行中
- **インストーラ群:** `setup.sh`（curl ワンライナー）/ `install.sh` / `uninstall.sh`

#### 自然言語UX

`templates/cmd.claude-code.md` により、ユーザーは「alice にデプロイ完了を伝えて」「メッセージ確認して」「チームに誰がいる?」のような自然言語で操作でき、エージェントが裏で適切な `*.sh` を呼ぶ。エージェントへの指示は「常にスクリプト経由、config/DBを直接触るな」と明示。

### 特徴的な点・注目ポイント

- **「デーモンもネットワークも要らない」徹底ぶり:** エージェント間通信というと普通はメッセージブローカやHTTPサーバを想像するが、agmsg は共有SQLiteファイルへの直接アクセスのみで実現。インストールの心理的ハードルが極端に低い（`bash` + `sqlite3` は大半の環境に既存）。これが最大の差別化点
- **monitor モードの「割り込み」:** SQLiteを常時購読し、メッセージ到着時に進行中の会話へリアルタイム割り込む。これにより「2つのClaude Codeに三目並べをやらせたら人間ゼロ介入で1ゲーム完走した」というデモが成立。エージェントの自律的協調を最小機構で見せた点が話題性を生んだ。`scripts/watch.sh`
- **actas の排他ロック:** 同一チーム内で複数アイデンティティを登録するとメッセージが漏洩する不具合（Issue #62）を、ロールごとの排他ロックで解決（PR #65）。マルチロール運用の堅牢性に踏み込んでいる。`scripts/lib/actas-lock.sh`
- **3軸ドライバ + イベントログ化:** シェルスクリプトのツールとしては設計が野心的。append-only イベントログ + UUIDv7 + 後方互換読み取り + atomic flip という、本格的なストレージ抽象を bash で実装しようとしている。`docs/adr/0001-storage-driver-pluginization.md`, `docs/spec/driver-interface.md`

### 使い方・典型的なワークフロー

#### セットアップ

```bash
# ワンライナー（推奨）
bash <(curl -fsSL https://raw.githubusercontent.com/fujibee/agmsg/main/setup.sh)

# または clone して install
git clone https://github.com/fujibee/agmsg.git && cd agmsg && ./install.sh
```

#### 基本フロー（Claude Code のスラッシュコマンド）

```text
/agmsg                         # inbox 確認（全チーム、引数なしのデフォルト）
/agmsg send alice "deploy done" # alice にメッセージ送信
/agmsg mode monitor            # リアルタイム購読モードに切替
/agmsg team                    # メンバー一覧
/agmsg history                 # 履歴
/agmsg actas reviewer          # 「reviewer」ロールに切替（排他ロック取得）
/agmsg drop reviewer           # ロール解放
```

初回 join 時はチーム名・エージェント名を登録し、delivery モード（monitor/turn/both/off）を選ばせるプロンプトが出る。

#### 典型ユースケース

- **Claude Code ↔ Codex のレビュー往復:** 実装側（Claude）とレビュー側（Codex）を同チームに置き、人間のコピペを排除（作者の原点）
- **マルチClaude協調:** monitor モードの複数Claudeを放置すると人間介入ゼロで会話継続（三目並べデモ）

### 他ツールとの比較・ポジショニング

- **vs Claude Code のサブエージェント/team 機能:** 作者は検討済みで「短命タスク向けで、継続的な会話には不向き」と判断（DEV.to 記事）。agmsg は永続的なエージェント間会話に振っている
- **vs MCP メモリ層（codex-agent-mem, engram 等）:** それらは「コンテキスト/記憶の永続化」が目的。agmsg は「エージェント間の能動的メッセージ配送」が目的で、レイヤが異なる（メモリ共有ではなく通信）
- **vs ネットワーク型エージェントメッセンジャー（agenticmail, AgentMail 等）:** それらはEmail/SMS/HTTP等の外部チャネル・クラウド前提。agmsg は単一マシン上のローカルファイル前提で、セットアップ・依存・プライバシー面で軽量。一方クロスマシン通信は守備範囲外
- **ポジショニング:** 「同一マシン上の複数CLIエージェントを、最小依存でリアルタイムに繋ぐ」ニッチ。MCP やネットワーク型と競合せず、隙間を埋める

### 制約・注意点

- **成熟度:** 作成1.5か月・タグリリース0・main直進行で、APIは流動的。`hook.sh` は既に deprecated 化（[PR #34付近](https://github.com/fujibee/agmsg/pull/34)）
- **単一マシン前提:** 共有SQLiteファイルへの直接アクセスが前提のため、別ホスト間通信やネットワーク越しは想定外
- **monitor モードのプロセス管理リスク:** watch.sh が所有CCセッション終了後も生き残る／複数 Monitor 起動で watcher 重複リーク等の未解決 Issue（[#66](https://github.com/fujibee/agmsg/issues/66), [#67](https://github.com/fujibee/agmsg/issues/67), [#68](https://github.com/fujibee/agmsg/issues/68)）。常駐購読プロセスのライフサイクル管理が現状の弱点
- **マルチアイデンティティの取り扱い:** 同チーム複数ロールでメッセージ漏洩する不具合があり排他ロックで対処したが（#62/#65）、fresh session でのループ等の派生バグも出ており（#70）、actas 周りは依然デリケート
- **バス係数1:** 実質単独メンテ（fujibee）。継続性は作者依存
- **依存の前提:** `sqlite3` が WAL モードで使える前提。古い/制限環境では要確認
- **設定の置き場所:** config が `db/` 配下にある等の整理途上（[Issue #60](https://github.com/fujibee/agmsg/issues/60)）

### 深掘り候補（コードリーディング対象）

- `scripts/watch.sh` — monitor モードの常時購読ループとプロセス管理。Issue #66/#67/#68 のライフサイクル問題の核
- `scripts/lib/actas-lock.sh` + `scripts/actas-claim.sh` — 排他ロックの取得/解放ロジック。漏洩バグ修正（#65）とループバグ（#70/#71）の実装
- `scripts/lib/storage.sh` + `docs/spec/driver-interface.md` — 3軸ドライバ抽象とイベントログ（UUIDv7、後方互換読み取り、atomic flip）の実装
- `scripts/delivery.sh` — 4モードの切替と Codex/CC のフックAPI差異の吸収（#48 でドライバ分割提案中）
- `scripts/init-db.sh` — SQLiteスキーマ定義。現 main は `messages` テーブルのみ（実スキーマは上記「データモデル」節に転記済み）。イベントログは storage-driver 化で将来追加予定
- `tests/*.bats` — 機能の網羅マップとして有用（test_actas_lock / test_delivery / test_messaging / test_storage 等）
- `templates/cmd.claude-code.md` / `templates/cmd.codex.md` — 自然言語→スクリプト呼び出しの橋渡し定義
