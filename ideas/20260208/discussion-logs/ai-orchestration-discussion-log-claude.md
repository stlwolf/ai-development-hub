## 議論の流れ

### 1. 起点：Agent Teamsリリースを受けて、次の検証ステップは何か

Agent Teams（v2.1.32, 2026-02-05リリース）が、claude-safeやCLI連携で手動構築してきた多くの部分を公式機能としてカバーした。チームメイト間の直接メッセージング、共有タスクリスト、ユーザーからの直接介入など。

ただし、Agent Teamsが解決するのは「セッション内の協調」であり、エピソード記憶やガイドAgentの構想が解決しようとしている「長期的な知識層」とはレイヤーが異なる。競合ではなく、組み合わせの余地がある。

---

### 2. 核心的な視座：ベンダーロックイン回避とCLI層の戦略的価値

**Eddyの主張**:
> 各ツールの進化が加速するほど、特定ツールがデファクトになるとは限らない。むしろ進化の速さ自体がデファクト化を防いでいる。だからこそ、各ツールの上に自分で薄いレイヤーを挟む戦法（CLI/ターミナル起点）は相変わらず有効。

**議論の結論**:
- Agent Teamsが出たからclaude-safeの役割が移る、という発想は「ベンダーの進化に追従する側」の発想であり、逆。
- CLI/ターミナルは**全てのツールが共通して持つインターフェース**。Agent Teamsが出ようがCodexが出ようが、どれもCLIから叩ける。
- 各ツールの公式オーケストレーション機能は「素材」として使いつつ、上位にCLI層で薄くラップする形が正しい方向。
- 常に確認すべき3点: ①非インタラクティブモードでJSON入出力できるか ②セッション情報を外部から参照・注入できるか ③プロセスとして独立して動かせるか。この3つが担保されていればどのツールでも組み込める。

**Eddyの補足**:
> ある特定の母艦となるツールを持ちつつ（今はCursor）、各ツールがCLIレイヤーでどれだけ意思疎通・連携・データのやり取りが可能かを担保しておくべき。Claude CodeがCLIに帰ってきている時点で、やはりそこを起点にするのが肝。あらゆるオーケストレーションツールはラッパーにすぎないので、このラッパーを独自で持つか依存するかの問題。

---

### 3. 2段階フロー：調査・議論 → 実装・検証

**Eddyの構想**:

複数のWeb版モデルをブレストに使い、Notionのようなクラウドドキュメントに集約して議論・設計 → その結論をCursorなどのIDEに持っていき、CLIやツールで実装・検証。この2段階の流れ。

**フロー図**:

```
【第1段階：設計・議論】
  複数Web版AI（Claude / Gemini / GPT）
    ↓ 各モデルの出力を突き合わせ
  クラウドドキュメント（Notion等）
    ↓ 意思決定・制約・経緯を記録
    ↓ ＝ エピソード記憶的データの手動蓄積

【ブリッジ：コンテキスト移送】
  ドキュメント → CLAUDE.md / .cursorrules / プロンプト
    ↓ 第1段階の結論を実装環境に注入

【第2段階：実装・検証】
  Cursor（母艦）
    ├→ Claude Code（CLI / claude-safe）
    ├→ Agent Teams（必要に応じて）
    └→ 他ツール（Codex等、利用可能なら）
    ↓ 実装結果・失敗パターン

【フィードバック】
  実装中の知見 → クラウドドキュメントに還流
```

**ボトルネック**: 第1段階と第2段階の「ブリッジ」部分。コンテキスト移送をどれだけ楽に、構造的にできるかがフロー全体の課題。

### 4. 具体的な検証候補と優先度

#### 候補A: セカンドオピニオンフロー（最小コンポーネント）

- 今コピペでやっているレビューや確認を、claude-safe経由で別モデルに投げる
- 「AIが自信なさそうに出してきたもの」に絞って多角検証
- 日常のフローをほぼ変えずに始められる
- 副産物として「どういう場面でセカンドオピニオンが有効か」のログが溜まる → エピソード記憶の最初のサンプル

#### 候補B: ツールの実地調査

- Codex、Cursor Agent CLI、MCP設定等のCLI互換性確認
- takt等の既存フレームワークを「参考資料」として軽く触る

#### 候補C: EC2→ECS移行を題材にした統合検証

- 議論の各段階で明確な意思決定ポイントがある
- AWSのホワイトペーパーという「正解の基準」が外部に存在する
- セカンドオピニオンの価値が出やすい
- 検証と本番の成果物が兼用できる

**A・B・Cは並列で進められる**（後述の学習フロー変化により）。

### 5. 学習フローの変化：「調べてから作る」→「作りながら調べる」

**Eddyの指摘**:
> AIのおかげで学習フロー自体が一変した。ドキュメントを読んで調べるより、AIに作らせて確認させて説明させる方が速い。手戻りコストがAIで劇的に下がったので、探索的アプローチのROIが高い。

**含意**:
- 「ステップ1で調査マトリクスを作ってから…」という逐次思考は旧来型
- 「Codexを入れて叩いてみる」「セカンドオピニオンを1回やってみる」「Cursorの設定を開いてみる」をそれぞれ独立した15〜30分の実験として並列で回す
- Cursorのスレッド複数、Claude Codeのセッション複数を同時に開いて、コード付きで検証を並走させることも技術的に可能
- **人間がガイドAgentとして複数の専門Agentに並列でタスクを振っている構図** = エピソード記憶ドキュメントの「モデレーターAI」を人間が手動で担当している状態

**結論**: 自動化を急がず、手動の並列パターンの中で「繰り返し出てくるパターン」を観察し、そこだけをボトムアップでコマンド化していくのが自然。

### 6. DRY原則：8ヶ月間変わっていない根本課題

8ヶ月前のNuxt3 CDKインフラリポジトリ（ChatGPT + Windsurf連携）の時点で「やりとり自体を保存して再利用する」「再現性を確保する」という方向性は明確だった。

**変わっていない課題 = DRY問題**:
- 新しいセッションを開くたびにドメイン情報を注入する
- 毎回同じルールを説明する
- 前のセッションで得た知見を手動で次に持っていく
- セカンドオピニオンを取るたびにコンテキストをコピペする

**CLAUDE.mdや.cursorrules は部分的な対策だが、静的スナップショット**。「前回のセッションでこういう議論をしてこう決めた」という動的な経緯は入らない。

**エピソード記憶のガイドAgent構想** = この DRY問題を解こうとしている。「毎回同じ説明をしなくても、過去の経緯を踏まえてやってくれる存在」。

---

### 7. 自前システムの最大の優位性：「何を残すか」の判断を人間が持てること

Agent Teams、CrewAI、LangGraph、Cursorのコンテキスト圧縮 → **全部ブラックボックス**。何が残って何が落ちたかをユーザーが制御できない。

自前で作る場合：
- 圧縮のタイミングと粒度を自分で決められる
- 「何が将来重要になるか」はドメイン知識と経験に基づく予測 → AIにはできない判断
- 人間が意図的に残したものは「次回注入すべきコンテキスト」として信頼できる → DRYの基盤になる

**設計原則**: AIに全部任せるのではなく、判断のポイントでは人間が介入する仕組みを持つ。ツールの進化とは独立して有効であり続ける。

---

### 8. ドキュメントの粒度問題とグラフ的関係性

**Eddyの問い**:
> ドメインドキュメントと会話ログを分けて保持するとして、小さく分けるとファイルは読みやすいが数が増えて把握しづらい。大きくまとめると全体像はスッキリするがファットになる。AIに対しても同じトレードオフがある。
> コンテキスト自体の関係性をグラフ的に持つことは有用か？PageRank的な発想で。

**議論**:
- **GraphRAG**（Microsoftが2024年に発表）がまさにこの方向。Knowledge Graphを構築してグラフ構造で検索する。
- ただし、フル実装は重い。
- **現実的な落とし所**: ドキュメントのメタデータに`related: [ADR-005, conversation/2026-02-08]`のようなリファレンスを入れるだけでも、AIは関係性を補完できる。コード内の`import`文と同じ役割。
- 限界: リファレンスがあってもファイルがコンテキストに入っていなければ辿れない。Claude Codeのようにファイルを能動的に読みに行ける環境でのみ有効。

### 9. ドキュメントのツリー階層構造 × 意図的圧縮

**Eddyの着想**:
> 内部コンテキスト圧縮のようなものを、ツリー構造のドキュメント階層で人間が意図的にやる。上位層は少量の圧縮コンテキスト、必要なら下層の詳細に辿れる。AIの自動圧縮と違い、何を残すかをレビューする余地がある。

**具体的な構造案**:

```
docs/
├── context.md                    # 最上位圧縮（プロジェクト全体を1ページで）
│
├── domains/                      # 意味記憶層（What：今どうなっているか）
│   ├── _index.md                 # 全ドメインの1行サマリー + リファレンス
│   ├── auth/
│   │   ├── overview.md           # 圧縮
│   │   ├── api-spec.md           # 詳細
│   │   └── constraints.md        # 制約
│   ├── infrastructure/
│   │   ├── overview.md
│   │   ├── ecs-config.md
│   │   └── networking.md
│   └── monitoring/
│       ├── overview.md
│       └── alerting-rules.md
│
├── decisions/                    # エピソード記憶層（Why/How：なぜそうなったか）
│   ├── _index.md                 # 全決定事項の1行サマリー + リファレンス
│   ├── ADR-001-ecs-over-ec2.md
│   ├── ADR-002-fargate-spot.md
│   └── ADR-003-jwt-auth.md
│
├── episodes/                     # 生ログ層（経緯の詳細）
│   ├── _index.md                 # 時系列サマリー
│   ├── 2026-02-08/
│   │   ├── ecs-migration-discussion.md
│   │   ├── security-review-result.md
│   │   └── _summary.md           # この日の結論サマリー（人間が圧縮）
│   └── 2026-02-10/
│       ├── networking-design.md
│       └── _summary.md
│
└── prompts/                      # 再利用可能なコンテキスト注入用
    ├── project-context.md
    ├── review-request.md
    └── handoff.md
```

**3つのポイント**:

1. **各層に圧縮層（`_index.md` / `overview.md`）がある**: AIに渡すときはまず圧縮層だけ。詳細が必要になったらリファレンスを辿る。
2. **意味記憶（domains）とエピソード記憶（decisions + episodes）が物理的に分離**: 「今の仕様」と「なぜそうなったか」で参照先が異なる。
3. **episodesの`_summary.md`が圧縮の実体**: 1日の作業終了時に結論を抽出。人間のレビュー余地がここに入る。

**下から上への昇格フロー**:

```
episodes/2026-02-08/_summary.md  （日次の結論）
    ↓ 確定した判断は昇格
decisions/ADR-004-bluegreen.md   （意思決定として定着）
    ↓ 現状仕様に反映
domains/infrastructure/overview.md（今の状態として更新）
    ↓ 全体サマリーに反映
context.md                        （最上位の圧縮を更新）
```

**人間の記憶プロセスとの対応**: エピソード記憶 → 時間とともに意味記憶に統合。最初は「2月8日にECSについて議論してFargateに決めた」、やがて「ECSはFargateで動いている」だけが残る。でも必要なら元のエピソードに辿れる。

**更新ポリシー**: 古い圧縮が残っていても、新しい圧縮が横に並んでいればAIはタイムスタンプで新しい方を優先できる。完璧な一貫性より「イミュータブルなログとしてappend + 圧縮層だけ定期更新」が現実的。

## キーインサイト（この議論から得られた重要な視点）

1. **CLIレイヤーの戦略的価値は各ツールの進化が加速するほど上がる**。デファクト化を防ぐ構造的な理由がある。

2. **Agent Teamsなどの公式機能は「素材」であり、依存先ではない**。自前のオーケストレーション層の中で使うもの。

3. **DRY問題がAI開発の根本課題**。毎回同じコンテキストを注入する繰り返しが解消されていない。8ヶ月間変わっていない。

4. **「何を残すか」の判断を人間が持てることが自前システムの最大の優位性**。ブラックボックスな自動圧縮より、意図的な圧縮 + レビュー余地。

5. **ドキュメントのツリー階層構造 + 意図的圧縮 + リファレンスによる関係性表現**が、GraphRAGの重い実装なしでも現実的に機能する可能性がある。

6. **学習フローが「調べてから作る」→「作りながら調べる」に変わった**。検証は小さく並列で回す方が速い。計画を立てすぎないこと自体が正しい戦略。

7. **人間が今やっている手動の並列オーケストレーション（複数スレッド + 複数セッション）が、構想しているシステムのプロトタイプそのもの**。自動化は繰り返しパターンの観察から自然に導出する。
