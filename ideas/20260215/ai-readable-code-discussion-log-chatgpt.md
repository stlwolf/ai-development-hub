# 「Readable Code → AI-Readable Code」議論ログ

- 日付: 2026-02-15
- 参加: Eddy × ChatGPT 5.2 (Web版)
- 性質: 偶然の着想から展開した探索的議論のまとめ
- 発端: Kindleを久々に開いたら「読みやすいコードのガイドライン」の序章で止まっていた

---

## 0. この議論の偶然性について

このスレッドは計画的な議論ではない。Kindleアプリを開いたら、たまたまReadable Code系の本の序章が表示されていた、という偶然から始まった。

最初の問い：**「AIにコードを書かせている今、この本を読む必要があるのか？」**

この素朴な違和感が、段階的に深化し、最終的に「可読性の対象が人間からAIに拡張される」「有機的なサービス理解がAI開発の真のゴール」という地点に到達した。各段階の転換は、前の段階への反論や違和感から自然に生まれている。

---

## 1. 議論の展開

### Phase 1: Readable Codeは今でも必要か

**Eddyの問い**: AIにコード書かせてる今、読みやすいコードのガイドラインを読む必要があるのか。

**議論の結論**: 不要ではないが、意味が変わった。

- AIは「動くコード」を出すが、「意図が伝わるコード」は雑になりがち
- 可読性の知識はAIへの指示品質を上げる武器になる
- レビュー/保守のコストはAI時代に増えがち（生成量が増えるため）

---

### Phase 2: そもそも「可読性のルール化」は今あまり聞かない

**Eddyの観察**: Readable Code的な話題を最近聞かない。Claude Codeとか含めて、みんなreadableなコードのレビューしてるのか。

**議論の結論**: 言葉が変わっただけで消えてはいない。

- 「可読性」→ code health / maintainability / lint+formatter+型 / AI instructions に語彙が移行
- 機械に任せられる形式的な可読性（フォーマット、lint、型）は自動化に吸収された
- 人間が見るべき設計寄りの可読性（命名、責務分割、エラー方針）は残っている
- ルールが「会話」から「仕組み（設定・指示・CI）」に移住した

---

### Phase 3: 結局、人が見る部分って設計と指示のうまさでは？

**Eddyの反論**: 設計と指示がきちっとできていれば、AIは人間より綺麗に境界分けしないか。

**議論の結論**: 概ね正しいが、限界がある。

- 良い指示があればAIは一貫して綺麗に作れる
- ただし「綺麗」と「正しい/保守しやすい」は別
- 指示が良いほど「それっぽい誤り」が増え、レビューが騙されやすくなる
- 可読性ルールは消えるのではなく、レビュー観点・検査項目として形を変えて残る

---

### Phase 4: 困っているのは可読性ではなく、巨大コードベース×AI×文脈維持

**Eddyの転換**: 自分の範囲では可読性で困っていない。意識が向いているのは以下。

- ゼロベースから巨大コードベースへの段階的実装
- どれだけAIのコードだけで作っていくか
- 初期段階からAIに対してルール・コンテキスト矯正をどう維持するか
- 文脈的解釈を破綻させないドキュメントをどう残すか

ここで議論の軸が「コードの可読性」から「AI運用のためのコンテキスト固定化」にシフトした。

---

### Phase 5: 人間がほぼ書かないなら、AIが理解しやすい構造が正義では？

**Eddyのアイデア跳躍**:

> 人間がほぼ書かない世界なら、最適化対象は「人間が読みやすいコード」ではなく「AIが状況把握しやすいアーキテクチャ」に変わるべきではないか。

- コード構造自体はそれほど重要ではない
- 重要なのは、人間が求めるドメインやコンテキストがどれだけ正確にコードに反映されていて、断続した状態や複数のAIでもそれを正確に対比のもとにコード理解を進められるか

**議論の結論**:

- 方向性は正しい。ただし「コード構造が重要じゃない」までは振れない
- AIが復元するための"足場"として構造は重要（機械可読な手がかり）
- AIが把握しやすい設計の3条件:
  1. Single Source of Truth（唯一の真実）が明確
  2. Locality（局所性）が高い
  3. Machine-verifiable（機械で検証可能）

---

### Phase 6: AI時代のReadable = AI-Readable Code

**Eddyの核心的着想**:

> 将来、人間はコードを直接読むのではなく、AI IDE/DeepWiki的な解析結果の説明を見て把握する比率が上がる。すると「人間に読みやすいコード」が正義とは限らず、「AIが正しく説明を返しやすい形にコードがある」方がAI時代のReadableとして正義になる可能性がある。

**この着想の構造**:

1. 読む主体が人間→AI（人間はAIの説明を読む）に寄る
2. AIの説明は正しいとは限らない（幻覚/誤推論）
3. 正しさの担保はテスト・契約・データフロー検証
4. 人間向け可読性 ≠ AI向け可読性の可能性がある

**AI-Readableの仮説的性質**:

- **同型性**: ドメイン概念 ↔ コード構造が対応
- **局所性**: 情報が散らからない
- **単調性**: 変更で解釈が反転しにくい
- **検証可能性**: 主張がテスト/契約で固定される

---

### Phase 7: DBスキーマ抽出の話（同僚の事例から）

**Eddyの補足**: 同じチームの別エンジニアが、DBのスキーマをマイグレーションファイルから全部抽出してAI用に作り、必ず見させるようにしている。

**Eddyの評価**: 重要だが全てではない。あくまで実装の正しさのためだけにAIが理解するための一部。

**議論から得た整理 — AIの正しさを導くアンカーは複数ある**:

1. Schema Anchor（DBスキーマ）— データの真実
2. Contract Anchor（API/GraphQL/OpenAPI）— 外部I/Fの真実
3. Invariant Anchor（不変条件 + テスト）— ドメインの真実
4. Flow Anchor（データフロー/依存境界）— 副作用の所在
5. Decision Anchor（ADR/意思決定ログ）— なぜそうなっているか

---

### Phase 8: 有機的理解 — AIが真にサービスを理解するとは

**Eddyの問い**:

> 巨大なドメインとコンテキストとコードベースの中で、それぞれが有機的にリレーションを持っている。それをどう小さいコンテキストに収めて、かつ本質的に正しいことを前提とさせるかは単純じゃない。

さらに:

> この有機的な理解さえできればAIが人間と同じように、コードの無機質な部分だけじゃなくサービスとして有機的なものを真の意味で一緒に開発できる可能性がある。それが本当のAIがすべて開発するというところのゴール。

**到達した認識**:

- 「有機的理解」= 仕様・コード・データ・ビジネス文脈・変更履歴・意思決定が相互に反応する全体性の理解
- AIが有機的に振る舞うには、データ構造やユースケースだけでなく、変化の履歴・意思決定の背景・失敗の痕跡・チームの価値観まで含めた推論が必要
- エンジニアは「書く人」から「価値の決定者」へシフトする可能性

## 2. この議論から生まれた重要な問い

1. **人間向け可読性とAI向け可読性はどこで衝突するか？**
2. **AIが誤説明しにくいコード構造とは何か？**
3. **「説明の正しさ」を担保する最小セット（契約/テスト/ログ/ADR）は？**
4. **複数AIの理解が収束する「アンカー」は何か？**
5. **AIが「有機的理解」に到達するために、人間が設計すべき構造とは何か？**

この議論は以下の既存構想と直接接続する。

- コンテキスト「純度」の問題 → AI-Readableの「局所性」と同じ問題意識

- 「人間向け」から「AI向け」へのインターフェース転換 → AI-Readable Codeの直接的な前身
- レビュー問題と中間言語の逆転 → 「人間はAIの説明を読む」構図と一致

### 生成AI開発の本質的課題（ideas/20260130/generative-ai-development-challenges.md）

- コンテキスト消失、ドメイン理解の欠如、成果物の劣化 → 有機的理解の欠如として再解釈可能
