## 0. 発端

Kindleを久々に開いたら「読みやすいコードのガイドライン」の序章で止まっていた。そこから「AIにコード書かせてる今、この本を読む必要があるのか」という素朴な問いが生まれ、ChatGPTとの議論を経て、以下の地点に到達した。

この議論は計画されたものではない。偶然の違和感が起点であり、段階的に深化した。各段階の転換は前の段階への反論や違和感から自然に生まれている。この偶然性自体が記録に値する。

## 1. 核心テーマ：可読性の対象が変わる

### 1-1. 従来のReadable Code

- 目的: 未来の人間（チームメイト、1ヶ月後の自分）がコードの意図を復元できること
- 手段: 命名規則、ガード節、責務分割、コメント方針
- 前提: 人間が書き、人間が読む

### 1-2. AI時代のReadable Code

- 目的: AIが正しくコードを理解し、正しい説明/変更/生成を行えること
- 手段: 契約（型/スキーマ）、テスト（不変条件）、構造的一貫性、用語の正規化
- 前提: AIが書き、AIが読み、人間はAIの出力（説明/変更案）を検証する

### 1-3. 目的関数の再定義

**これまで**: 人間が変更しやすいように設計する

**これから**: AIが文脈を正しく復元し、人間がその結果を検証しやすいように設計する

この再定義は、Readable Codeの否定ではなく、**読み手が変わったことに伴う目的関数の拡張**。

## 2. 議論で到達した合意点

### ChatGPTとClaudeで共通する認識

1. **設計と指示が良ければ、AIは人間より一貫した分割をする** — コードの可読性問題は、コードの問題から指示（設計）の問題に還元される
2. **可読性ルールは消えていない** — 言葉が変わっただけ（code health、maintainability、AI instructions）。会話から仕組み（設定・CI・lint）に移住した
3. **DBスキーマ等の単一アンカーでは不十分** — AIの正しさを導くアンカーは複数必要
4. **有機的理解がAI開発の真のゴール** — 断片的にコードを書くのではなく、サービスの全体像を理解した上で開発に参加できる状態

### Claudeが追加した視点

5. **AI-Readableは現時点では「良い設計」の別名に近い** — 局所性、境界の明確さ、命名の一貫性は、人間向けでもAI向けでも同じ。乖離が始まるのはAIが人間には読めない中間表現を直接扱うようになったとき
6. **「書くためのアンカー」と「読むためのアンカー」は重なるが同一ではない** — 読むためにはさらに「なぜそうなっているか」の履歴情報が必要
7. **有機的理解は現LLMアーキテクチャでは構造的に困難** — ステートレスなモデルに「蓄積」を前提とする理解は原理的に難しい。だからこそ外部の仕組み（エピソード記憶、ガイドAgent、昇格フロー）が必要

## 3. 新しい概念の整理

### 3-1. AI-Readable Code

AIが正しく説明・変更・生成できるコード構造。仮説的な性質:

| 性質 | 意味 | 対比: 人間向けReadable |
|------|------|----------------------|
| **同型性** | ドメイン概念 ↔ コード構造が対応 | 命名規則、ドメイン語彙 |
| **局所性** | 1機能の情報が散らからない | ファイル構成、モジュール分割 |
| **単調性** | 変更で解釈が反転しにくい | 後方互換、段階的変更 |
| **検証可能性** | 主張がテスト/契約で固定 | コメント、ドキュメント |

現時点ではこれらは「良い設計」と大きく重ならない。**衝突が顕在化する場面**:

- **人間には読みやすいがAIには曖昧**: 暗黙的な文脈依存のコード（慣習ベース）
- **AIには明確だが人間には冗長**: 全前提を明示的にアノテーションしたコード

### 3-2. AIの正しさを導くアンカー群

単一のSSOTではなく、複数のアンカーの組み合わせ:

1. **Schema Anchor** — データの真実（DBスキーマ、マイグレーション）
2. **Contract Anchor** — 外部I/Fの真実（API/GraphQL/OpenAPI）
3. **Invariant Anchor** — ドメインの真実（不変条件 + テスト）
4. **Flow Anchor** — 副作用の所在（データフロー、依存境界）
5. **Decision Anchor** — なぜそうなっているか（ADR、意思決定ログ）

同僚のDBスキーマ抽出は1を強化している。Eddyが追求しているのは1〜5の統合。

### 3-3. 有機的理解

コードの静的構造だけでなく、以下を統合的に扱える能力:

- コードの構造理解（静的）
- データフローの理解（動的）
- ビジネス文脈の理解（意味的）
- 変更履歴の理解（時間的）
- 意思決定の理由の理解（因果的）

これが達成されれば、AIは人間と同じようにサービスとして有機的なものを開発できる。現LLMアーキテクチャでは構造的に困難だが、外部システム（エピソード記憶、ガイドAgent）で補完する方向が現実的。

### 3-4. AI時代の複雑性の再分類

Fred Brooksの分類を拡張:

| 種類 | 従来 | AI時代 |
|------|------|--------|
| **本質的複雑性** | ドメインの複雑さ | 変わらない |
| **偶有的複雑性** | ツール/言語由来 | AIが吸収（減少） |
| **新しい複雑性** | — | AIのコンテキスト限界に起因する複雑性（増加） |

3番目が「単純じゃない」の正体。局所的に正しいが全体で破綻する、生成品質の揺れが境界を侵食する、前に決めたことをAIが忘れて矛盾する実装を生む。

## 4. 既存構想との統合

この議論は新規のアイデアではなく、1月21日以降の全構想に対する**新しい切り口**を提供している。

### 既存: AIが正しく書くために何が必要か

- コンテキスト維持（エピソード記憶、昇格フロー）
- ルール注入（CLAUDE.md、.cursorrules、AI instructions）
- オーケストレーション（CLI連携、セカンドオピニオン）

### 新規: AIが正しく読む（説明する）ために何が必要か

- AI-Readable Code（同型性、局所性、単調性、検証可能性）
- 複数アンカーによる正しさの担保
- AIの説明を人間が検証するフロー

### 統合: 書くことと読むことの両方を正しく行うための構造

= 有機的理解を可能にする設計

これが全構想を貫く最上位のビジョンとして機能する。

```
有機的理解を可能にする設計
├── AIが正しく書くための仕組み
│   ├── コンテキスト維持（エピソード記憶、昇格フロー）
│   ├── ルール注入（North Star、Lexicon、ADR）
│   └── オーケストレーション（CLI連携、セカンドオピニオン）
│
├── AIが正しく読むための仕組み
│   ├── AI-Readable Code（構造設計）
│   ├── 複数アンカー（Schema/Contract/Invariant/Flow/Decision）
│   └── 人間による検証フロー
│
└── 長期的な知識層
    ├── ガイドAgent（文脈と履歴を理解するモデレーター）
    ├── やりとりの資産化（会話ログ→エピソード→判断→文脈）
    └── 意図的圧縮（三層構造 + 昇格フロー）
```

1. **人間向け可読性とAI向け可読性はどこで衝突するか？** — 現時点ではほぼ重なるが、衝突する場面を具体的に特定したい

### 運用レベル

4. **複数AIの理解が収束する「アンカー」の実装形態は？** — ファイルベースか、テストベースか、型ベースか
5. **「有機的理解」の度合いをどう測定するか？** — AIに同じコードを説明させて、正確度を比較する等

7. **人間がコードを読まなくなる世界で、デバッグ/インシデント対応はどうなるか？**

## 6. 検証アクション（軽量・短期）

### Action 1: AI-Readable vs Human-Readable の衝突実験

**やること**: 既存コードの一部を「AI-Readable優先」で書き直し、AIの説明精度が変わるか比較する。

- 対象: 既存のCakePHPまたはNuxt3の1ユースケース
- 方法: 同じ機能を「人間向けに読みやすい版」と「AI向けに明示的な版」（全前提をアノテーション、暗黙の慣習を排除）で用意
- 測定: 複数のAI（Claude、ChatGPT、Gemini）にそれぞれ説明させ、正確度と収束度を比較
- 期待: 衝突ポイントの具体例が得られる

### Action 2: アンカーの最小セット検証

**やること**: 同僚のDBスキーマ抽出に、1〜2個のアンカーを追加して、AIの生成/説明精度の変化を観察する。

- 追加候補: 用語辞書（Lexicon）、主要ユースケースのゴールデンテスト
- 方法: スキーマのみ vs スキーマ+Lexicon vs スキーマ+Lexicon+テスト で同じタスクをAIに依頼
- 測定: 生成コードの正確性、説明の正確性、指示の繰り返し回数
- 期待: アンカーの追加によるROIの感触が得られる

### Action 3: AIの説明を検証するフローの試行

**やること**: AI（DeepWiki的なツール、またはClaude Code）にコードを説明させ、その説明の正確性を人間が評価するプロセスを1回やってみる。

- 対象: 自分が詳しいドメインの既存コード
- 方法: AIに説明させる → 人間が正確性を0-10で評価 → 誤りの種類を記録（事実誤認/省略/曖昧/正しいが浅い）
- 期待: 「AIの説明のどこが壊れやすいか」のパターンが見える → AI-Readable設計の方向性が具体化

### Action 4: 既存の日次要約・ブリッジ実験との統合

2月8日の棚卸し（Tier 1検証）で提案されていた「日次要約」「ブリッジ実験」を、AI-Readableの観点を含めて実施する。

- 日次要約を書く際に「AIが次回このコンテキストを復元するために何が必要か」の観点を追加
- ブリッジ（Web議論→IDE注入）の際に、注入した情報でAIの理解がどこまで回復するかを観察

## 8. この議論で繰り返し確認された原則

2月8日の議論から引き継がれる原則:

> **AIは高速に案を出す。人間は保存価値を判断する。システムはその判断履歴を再利用可能にする。**

今回追加された原則:

> **可読性は「読む主体」が変わると目的関数が変わる。AIが主要な読者になるなら、コードは「AIが正しく説明できる」ように設計されるべきだ。**

> **有機的理解 — コードの静的構造だけでなく、動的フロー・ビジネス文脈・変更履歴・意思決定理由を統合的に扱える能力 — がAI開発の真のゴールであり、全構想を貫くビジョンとして機能する。**
