# コンテキスト永続化の4層モデル

FWアップグレード（2リポジトリ）の実践から導出した、AI開発におけるコンテキスト保存の階層モデル。

## 4層の定義

```
層1: 即時参照（GitHub Issue 本文 / コメント）
  - エージェントが gh api で即取得
  - 「契約書」: what（本文）、how（コメント）、learned（FB）

層2: 構造化ナレッジ（独自ドキュメントシステム）
  - レトロスペクティブ、プランテンプレート、エピソード記録
  - 再利用頻度の高い知見。AI ツールのコンテキスト設定とは独立

層3: 生ログ（SO stdout、会話エクスポート）
  - 抽出パイプラインがないと死蔵する
  - 「なぜその判断に至ったか」はここにしかない
  - 抽出後は破棄可能

層4: コード + コミット履歴
  - 「何を変えたか」はここにある。「なぜ変えたか」はない
  - Refs # による Issue リンクが層1への参照として機能
```

## 運用規約（案）

### 最小メタデータスキーマ（層2以上）

```yaml
task_id:      # Issue 番号 or タスク識別子
decision:     # 意思決定の要約（1行）
evidence:     # 根拠（Issue URL, SO 出力パス等）
valid_until:  # 有効期限の目安
```

### 昇格ルール（層3 → 層2）

- 再利用見込みがあり、根拠が明確なもののみ
- 生ログ全文ではなく、抽出された知見のみ
- 人間 or 要約エージェントが昇格判断

### TTL（保持期間）

- 層3: 30〜90日で自動削除（抽出済みなら即時削除可）
- 層2: 半年ごとにレビュー、陳腐化したものはアーカイブ
- 層1: GitHub 上に永続

### 現時点の制約

- 層3 の抽出パイプラインは未実装
- 実働しているのは層1（Issue）+ 層2（レトロスペクティブ手動作成）+ 層4（コード）の3層
- 層3 の自動化は生ログ抽出パイプライン（ExportTranscript → 要約エージェント → 構造化）として将来構築

## 情報の関連構造

Issue の `Refs #` や PR リンクはグラフの辺として機能する。リポジトリを跨いだ関連やSO ログとの関連はレトロスペクティブが橋渡し。エージェントがこのグラフを自律的にトラバースできるかが次の課題。

## 残すべき情報の判断基準

| 基準 | 残す | 残さない |
|------|------|---------|
| 将来の同種タスクで直接参照されるか | FB、プランテンプレート | SO の同意部分 |
| 意思決定の根拠を復元できるか | SO 修正指摘、レトロスペクティブ | SO の prompt.txt |
| 構造化されており検索可能か | Issue 本文、エピソード doc | stderr ログ |
| 抽出パイプラインなしで読めるか | PR 本文、FB コメント | 会話生ログ全文 |
