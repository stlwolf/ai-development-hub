## 着想

ComposioHQ/agent-orchestrator を見たことがきっかけ。OSSで開発されているオーケストレーションツールが複数存在する中、コード解析が得意な自分の強みを活かして、これらのツールの設計パターン・概念・実装方式を体系的に調査し、自分がこれまで検証してきたアイデアと組み合わせて自前のオーケストレーションツールを構築する、というアプローチ。

## 核となる認識: 2つのレイヤーの非対称性

既存のOSSオーケストレーションツールと自分の検証知見は、カバーしているレイヤーが異なる。

```
┌─────────────────────────────────────────────────┐
│ セマンティック層（自分の検証知見が厚い）          │
│  - 認知協調（SO、ルーラーエージェント）           │
│  - 知識永続化（4層モデル、昇格フロー）           │
│  - ドキュメント設計（write:read比率、指示設計）   │
│  - エージェント定義（正準フォーマット）           │
├─────────────────────────────────────────────────┤
│ インフラ層（OSSが厚い）                          │
│  - ワークスペース隔離（worktree、Docker）         │
│  - プロセス管理（tmux、セッション制御）           │
│  - イベント駆動フィードバック（CI連携、reactions） │
│  - プラグインアーキテクチャ                      │
│  - 状態管理・チェックポイント                    │
└─────────────────────────────────────────────────┘
```

この非対称性を活かす: OSSからインフラ層の設計パターンを抽出し、自分のセマンティック層と合成する。

## OSSの分類と抽出対象

調査時に意識する分類軸:

| 分類 | 代表的なOSS | 抽出対象 |
|------|------------|---------|
| タスクディスパッチ型 | agent-orchestrator | プラグインスロット設計、reactionsパターン、worktree隔離 |
| ワークフロー/状態管理型 | LangGraph | グラフベース状態遷移、チェックポイント/リジューム |
| 役割ベース型 | CrewAI, AutoGen | role定義モデル、タスク依存関係、メッセージパッシング |
| 自律コーディング型 | SWE-agent, OpenHands | 観察→仮説→実行→検証ループ、サンドボックス |
| MCP統合型 | Mastra | MCP toolの動的バインド |

## 進め方: リサーチ→構築→ドッグフーディング

```
Phase 1: ランドスケープ調査
  OSSの設計文書・インターフェース定義・アーキテクチャを読む
  → projects/orchestration-research/landscape/ に統一フォーマットで記録
  → concepts/ に共通パターンを抽出

Phase 2: 統合設計
  抽出した要素と自分の独自レイヤーの合流点を設計
  → synthesis/ に設計ノート

Phase 3: プロトタイプ構築
  自前オーケストレーションツールを projects/ に昇格して構築
  既存の検証フロー（SO、ピアレビュー等）をこのツール上で実行

Phase 4: ドッグフーディング
  構築したツールを自分の検証作業に使い、ツール自体を改善
  cursor-thread-tools で4フェーズ回したのと同じパターン
```

## なぜこのアプローチが有効と考えるか

1. **「作りながら調べる」フローとの一致**: 棚卸しドキュメント（20260208）で確認済みの原則。リサーチ→設計→構築→検証のサイクルが自然に回る
2. **ドキュメントが外部記憶になる**: landscape/ の調査結果が、個別スレッドでの検証時にコンテキストとして参照可能。4層モデルの層2に直接入る
3. **ドッグフーディングで検証密度が上がる**: cursor-thread-tools の4フェーズ運用で CONVENTIONS.md が成熟したのと同じ構図

## OSSにはない自分の独自要素（比較軸）

各OSSの調査時に「これがあるか/ないか」を確認する軸:

- **セカンドオピニオン統合**: 実装エージェントとは別に反証担当を配置する機構
- **判断履歴ナビゲーション**: 過去の決定を自動参照するルーラーエージェント
- **コンテキスト永続化**: セッション跨ぎの知識保存（4層モデル）
- **昇格フロー**: 生ログ → 構造化ナレッジ → 意思決定記録の段階的圧縮
- **コンテキスト・エンベロープ**: original_intent を不変で運ぶJSON構造
- **正準エージェント定義**: ツール非依存の定義 → 各プラットフォーム向け変換

## 付属GUIビューワーの構想

自前オーケストレーションツールに「融和的GUI」を付属させる案。CLIをSSOTとし、別途「増え続けるMarkdown/設定/実行結果を編集・整理・観測・介入する専用UI」として機能させる。ChatGPT webでの議論から。

### GUIの方向性は2つ

**管理コンソール（観測・介入・整理）**:
- run/session の一覧と状態表示
- 人間レビュー待ち（承認/差し戻し）
- 生成物（Markdown/パッチ/設計メモ）の閲覧・編集
- 「この決定をSSOTに保存」操作

**エディタ（Markdown/設定の専用編集）**:
- `project.yaml` や `agents.yaml` のフォーム編集
- プロンプト/ルール/テンプレ/ワークフロー定義の編集
- 構造化メタデータ付きMarkdown管理

### Markdown増殖問題へのGUIの効かせ方

Markdown増殖の本質は3つ: (1) 検索しづらい (2) 依存関係が見えない (3) 更新が散る。Markdownを置き換えるのではなく「周辺に薄い構造を足す」のが有効。

- **frontmatter（YAML）で索引化**: type/tags/status/links を付与し、GUI側でフィルタ・参照グラフを提供
- **Runログと決定の分離**: 自動生成のRunログ（JSONL + 参照MD）と、人間レビュー済みのSSOT（ADR/Decision）を分ける。GUIは「Runから決定に昇格」を支援する
- **重複検知・関連候補提示**: 類似MD検出、参照が必要そうなADRの提示（RAGの活用場面）

### 設計原則

- **SSOTはCLI/ファイルに置く**: 設定はYAML/TOML/JSON、記録はMarkdown + frontmatter、実行ログはJSONL
- **GUIは読み取り中心→介入はコマンド経由**: GUIが直接ファイルを書き換えない。変更は `orchestrator apply` のようなコマンド経由で差分/検証/ロールバックが効く
- **CLIでも編集可能を維持**: GUIが唯一の編集手段にならないようにする

### 避けるべき落とし穴

- GUIが唯一の編集手段になる → CLI/差分/レビューの運用と衝突
- ノードエディタに寄せすぎる → 条件分岐・例外系が増えた瞬間にメンテ不能
- Markdownを完全に構造化DBに置換しようとする → 移行・運用コストが跳ねる

### MVP画面構成案

- **Dashboard**: run一覧 + 状態 + 詰まり（入力待ち/失敗）
- **Run detail**: イベントタイムライン + 生成物（MD/パッチ/リンク）
- **Docs**: frontmatter索引（type/tag/status）+ 全文検索
- **Decision editor**: Runから要点を取り込み → ADR/Decisionとして保存（差分プレビュー付き）

### 実装の現実解

CLIバックエンド + ローカルWeb UI（Tauri / pure web + local server）が最もバランスが良い。CLI SSOT、拡張性、再現性の文脈に合致。

## リスク・未知数

- 調査に時間がかかりすぎて構築に至らない可能性 → landscape/ を2-3個書いた段階で判断
- OSSの進化が速く、調査結果がすぐ陳腐化する → 概念レベルの抽出に集中し、実装詳細には深入りしない
- 自前構築の必要性自体が不明確 → 既存OSSのフォーク/拡張で済むかもしれない。それもPhase 2で判断
