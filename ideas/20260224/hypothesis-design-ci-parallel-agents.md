## 着想

「デザイナー不在で、エンジニア+AIだけでデザイン→実装のループを回せるか」という問い。AIの画面理解力は向上しているが、UI/UXはドメインが異なり、最近デザイン込みタスクを実行していないため未検証。ここをオーケストレーションツールでどうカバーするか。

---

## 核心: 汎用レビュアーではなくパイプライン型サブエージェント群

デザイン系ロールを「1つの汎用デザインレビュアー」として立てるのではなく、**検証観点ごとに特化したサブエージェント群 + 定量チェックパイプライン**として構成する。

### 実装系 vs デザイン系の根本的な差

| 観点 | 実装・テスト系 | デザイン系 |
|------|-------------|-----------|
| 正解の定義 | 明確（テスト通過、型一致） | 一部定量化可能、定性部分が大きい |
| コンテキスト | 構造的（コード、スキーマ） | 視覚的+構造的+暗黙知 |
| FBループ自動化 | CI/linter/型チェックで即判定 | 一部自動化可能、統合判断は困難 |

実装系はCI/テストという既存インフラがあるから「並列で投げて、通ったものを採用」ができる。デザインにはそれに相当するものを**自分で構築する必要がある**。

---

## 検証観点の分割例

| 観点 | 手段 | 判定 |
|------|------|------|
| アクセシビリティ（a11y） | axe-core等の自動チェック | 定量: Pass/Fail |
| デザイントークン準拠 | トークン定義との差分検出 | 定量: 違反数 |
| レスポンシブ崩れ | Playwright複数viewport | 定量: overflow検出 |
| ビジュアルリグレッション | Storybook/Chromatic相当 | 定量: diff% |
| セマンティクスHTML | DOM構造解析 | 定量: Pass/Fail |
| 文言・文体 | UXライティングルールとの照合 | 半定量 |
| 全体トーン・UX一貫性 | **人間ゲート** | 定性 |

---

## 人間ゲートの最小化構造

```
定量ゲート全Pass → 人間チェック不要
定量ゲートにFail → Failした箇所だけ人間が見る
```

steipeteが300k LOCのプロダクトで「コードをほとんど読まない、ストリームを眺めるだけ」と言っているのは、CI/lint/型チェック+gitのdiffレビューという自動ゲートが人間チェックを代替しているから。デザイン領域で同じ状態を目指すには、上記の定量ゲートを並列エージェントとして構築する。

人間に残るのは「全体としてこれでいいか」の**統合的サニティチェックのみ**。steipeteがストリームを「眺める」こと自体が、高速な定性フィルタとして機能しているのと同じレベル。

## 性能向上の3方向

### 1. コンテキストの質で差をつける

デザインシステムのトークン定義、コンポーネントカタログ、既存画面のDOM構造一覧、ブランドガイドラインをサブエージェントに渡す。「デザインシステムからの逸脱検知」というスコープに限定すれば実装系ロールに近い精度は出せる。

### 2. 検証手段の多段パイプライン

Playwrightでレンダリング結果をキャプチャ → 画像認識で既存画面との差分検出 → DOM構造の差分解析。単一の「デザインレビューして」というプロンプトよりはるかに精度が上がる。

### 3. スコープの限定

「デザイン全体のレビュー」は難しくても、検証観点ごとにサブエージェントを分ければ、それぞれは判定可能なスコープに収まる。

## AIが画面を認識する手段の選択肢

| 手段 | 特徴 |
|------|------|
| 画像認識（スクリーンショット/Figma） | 直感的だが定性的 |
| Canvas（Claude Code x Figma） | デザイン↔コード双方向変換 |
| Playwright等E2E/RPA | 画像なしでDOM構造ベース認識 |
| コード直読 | 構造理解は可能、視覚的整合性は見えない |
| Peekaboo（steipete） | スクリーンショット+AI画像認識+GUI操作のループ |

Playwright（DOM構造）+ Peekaboo的な視覚認識の組み合わせで多角的検証が可能。

---

## 緩和策

- Storybook + 0→1からAIと共同構築 → デザイントーンの文脈をエピソードとして蓄積
- デザインシステムのルールを明示的にコンテキストとして渡す（steipeteのAGENTS.MD `<frontend_aesthetics>` セクションと同じアプローチ）
- セカンドオピニオン/アリーナでデザイン判断もレビューゲートに通す

## AI議論の裏付け

### Claude側の分析

デザイン系ロールは「パイプライン型のサブエージェント群として設計した方が性能が出る可能性がある」。コンテキストの質/検証手段の組み合わせ/スコープの限定、の3方向で精度向上が可能。ただし「全体としてこのUXは良いか」という統合判断は親スレッドか人間のゲートに残す。

### ChatGPT側の分析

「観点を分割して、定量ゲートを増やす」戦略を支持。具体的な観点リスト（a11y/トークン準拠/レスポンシブ/画面差分/文言・文体/情報構造）を提示し、「人間が見るべき箇所がFailに寄る」構造が現実的とした。

### 双方の合意

定量的な観点を並列エージェントで網羅すれば、人間チェックの大半は排除可能。ただしデザイン領域のCI相当を自分で構築する初期投資が必要。

## 検証するなら

- デザイン込みの小規模タスク（ページ1枚+API数本レベル）で、観点分割パイプラインのプロトタイプを試す
- a11y自動チェック（axe-core）+ デザイントークン準拠チェックの2観点から始めて、Pass/Failの精度を測る
- Playwright + スクリーンショット比較で視覚的リグレッション検出の実用性を検証

## 優先度

中〜低。デザイン込みタスクの実需が出てから着手。オーケストレーションツールの設計上は「拡張ポイント」として場所を用意しておき、ツール側の成熟に合わせて実装を埋める。
