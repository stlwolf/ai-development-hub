## 議論の流れ

### 1. 着想: メタリポジトリ構想

Oh My Open Codeの階層的AGENTS.md生成機能をきっかけに、本筋リポジトリを汚さずAI専用のメタデータ階層を自動生成・同期するシステムを構想。

**Claude の分析:**
- 実装手段として **git orphan branch + worktree パターン** を提案
- orphan branch（本筋とコミット履歴を共有しない独立ブランチ）に本筋と同じディレクトリ階層で AGENTS.md や構造サマリを配置
- `git worktree add .meta meta/agents` でマウント、`.gitignore` に `.meta/` を追加すれば本筋はクリーンなまま
- 同期トリガーは git hooks（post-commit, post-merge, post-checkout）で自動化
- トークン制御: ルート `.meta/AGENTS.md` → 各サブディレクトリ、という段階的ローディング

### 2. 展開: 保存場所の問題

[Zenn記事: sui-memory](https://zenn.dev/noprogllama/articles/7c24b2c2410213) を起点に、コンテキストの保存場所を議論。

**保存すべきものの3層整理:**
- **静的構造メタ**（CLAUDE.md / AGENTS.md相当）→ テキストファイルで git 管理が最適。orphan branch に載せる
- **動的経験記憶**（sui-memory がやっているもの）→ ベクトル検索が必要なので DB 的保存が向いている
- **構造変遷メタ**（「なぜこうなったか」の履歴）→ git notes やコミットメタデータに紐づける

**落としどころ:**
> ソースデータ（テキストチャンク）は git に置いて、インデックス（ベクトルDB）はローカルで再構築する。npm install で node_modules が再現されるのと同じ発想。

**Eddy の指摘:**
> 保存形式より **アクセスの抽象化レイヤー** の設計が本質的な論点。MCP経由で統一的にアクセスできるようになれば、保存先が git だろうが DB だろうが関係ない。

### 3. 転換点: 全部取っておく必要があるのか

3つの圧縮戦略の比較:
- **時間減衰型**（sui-memory方式）: データ自体は消えない。本質的解決にならない
- **要約圧縮型**（claude-mem方式）: 文脈が消えるリスク。「文脈を失わない要約」はLLMでは保証できない
- **チェックポイント型**（Entire方式）: 状態スナップショットを保存。全会話を保持する必要がない

**Claude の提案（最初）:**
> 生のトランスクリプトは一定期間後に消してよい。そこから抽出された「設計判断の原則」を CLAUDE.md / AGENTS.md に昇格させて永続化する蒸留パイプライン。

**Eddy の反論:**
> エピソード記憶の方が残りやすい。印象的なエピソードほど記憶に残る。意味記憶は逆にエピソードから反復抽出された結果。**エピソードが残っていれば意味記憶は再抽出可能**。

**Claude の修正:**
> 蒸留の精度が低ければ元データを失った時点で回復不能。**印象的なエピソードを選択的に残し、原則はオンデマンドで再抽出する** 方が安全かもしれない。

### 4. 核心: 決定記録という最小解

**Eddy:**
> 今までの開発ではコードとコミットメッセージしか残らない。「AとBを検討してBにした」という事実すら記録されない。**ゼロが10になるだけで劇的に違う**。

**Claude:**
> 「BではなくAを採用した。理由：パフォーマンス要件を満たさないため」——この1行が残っているだけで、3ヶ月後に「なんでBじゃないの？」という議論を丸ごとスキップできる。

**最小フィールド（5つ）:**

| field | 意味 |
|---|---|
| `when` | タイムスタンプ |
| `what` | 決定事項（1〜2行） |
| `weight` | 重要度（high / medium / low） |
| `status` | decided / tentative / reverted |
| `scope` | カテゴリ / 影響範囲 |

> 全部足しても1レコード200文字以内。1000件の決定記録でも200KB。grep 可能なテキストファイルで足りるかもしれない。

### 5. 2層の分離

- **人間が書く層**: ADR、設計書、README。意図的に書かれ情報密度が高い。本筋リポジトリに置く
- **自動生成メタ層**: セッションごとの決定記録。5フィールドのレコードが orphan branch にリポジトリと同じ階層構造で積み上がる。人間は何も書かない

コミット前の検討過程（「AとBどっちにする？」のやり取り）は意識的に切り捨てる。

**Eddy:**
> 決定したと明確にわかるタイミングだけ残っていれば、それまでの過程は実は必要ない可能性がある。今まで把握してなかったものを把握しようとして、完璧に把握しようとしすぎている。

### 6. メタデータスキーマの精緻化

**Eddy:**
> 要約と列挙だけでは足りない。最低限、時系列・重要度・確定事項・カテゴリのような付加情報が必要。ただし必要な情報の種別は意外と多くない。

**Claude の分析:**
> 必要なフィールドは驚くほど少ない。このスキーマは ADR や RFC の「重い」フォーマットを極限まで削ぎ落とした結果とほぼ同じ構造。ADR が普及しなかったのはフォーマットが重すぎたから。これを LLM の自動抽出で生成すれば、人間は何もしなくていい。

### 7. 実装エージェントの形態

**パターン1: hook スクリプト + 軽量LLM呼び出し（推奨）**
- post-commit hook で diff → API 1回投げ → 5フィールドのレコード追記
- Claude Haiku 級の軽いモデルで十分、1コミットあたり数円以下
- 常駐プロセス不要、git の hook 機構に乗るだけ

**パターン2: 常駐バックグラウンドエージェント**
- ファイル変更 watch + セッション終了検知 + コミットイベント統合
- 「typo 修正だから記録不要」「直近3コミットは同じ判断の段階的実装だから1レコードにまとめる」等のフィルタリング
- 複雑さが跳ねるので、パターン1で不満が出てから

**重要な設計判断:** 作業エージェント（Claude Code / Cursor）と同じコンテキストを持つ必要はない。diff とコミットメッセージだけ見れば決定事項は抽出できる。完全に独立したプロセスとして動ける。

### 8. Ralph Loop との接続

**Eddy の問い:**
> Ralph（Geoffrey Huntley 提唱の「AIエージェントを無限ループで動かし続ける手法」）と概念的に交差する部分があるか。

**Claude:**
- Ralph Loop の核心は「毎回コンテキストをリセットし、外部メモリ（progress.txt等）から状態を復元してループを回す」パターン
- 決定記録は Ralph の progress.txt を構造化・自動化したもの
- Ralph Loop が「コンテキスト汚染を避けるために毎回リセットする」のは、「全部取っておく必要はない」と完全に一致
- progress.txt はエージェント自身の自己記述 → 決定記録は post-commit で第三者的に自動生成。信頼性が高い

### 9. 正規化とビューの分離（最終到達点）

**Eddy:**
> AI が読む場合の構造化と、実装として見るときの構造化データは、一対一である必要がない。

**Claude:**
> 「ledger に保存する形式」と「AI に渡す形式」と「人間が見る形式」を全部同じにしようとしてしまうが、実際にはそれぞれ最適な形が違う。DB の正規化とビューの関係そのもの。

> 今回の議論で「保存の正規形」「AI への投影」「人間への投影」を分けて考えられるようになったのは、この先何を作るにしてもベースになる見方。

## 議論の正規形としての結論

**Phase 1（MVP）:** flat ledger としての decision 記録。JSONL で7フィールド。post-commit フックで LLM に判定させ、決定のみ追記。tree 構造はまだ作らない。

**Phase 2:** ledger に対する path 別・domain 別のビュー生成。

**Phase 3:** ビューから AGENTS.md 的なディレクトリサマリを自動生成。

**正規形の結論:**
> SoT は ledger。tree は派生ビュー。ただし tree は「単なるビュー」以上に重要で、人間と AI の共同理解インターフェースとして機能する。repo 構造を基本座標系として採用しつつ、乖離した部分だけ論理メタで補正する。
