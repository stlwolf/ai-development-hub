# メタデータ層を使ったAI向けリポジトリ構造の自動同期 - ブレスト議論

## 全体所感

この構想のコアは、実は「AI向けメタリポジトリ」そのものではなくて、

- 開発の判断をどこに残すか
- その残し方をどこまで自動化するか
- 本筋のリポジトリを汚さずにどう共存させるか

の3点だと思う。

で、今の議論は最初「AIが読むための階層メタ層」から入っているけど、途中でかなり本質に近づいていて、最終的には

> AIの長期記憶問題というより、開発判断の外部化・再読可能化の仕組み

になっている。

これはかなり良い方向。

## 結論を先に言う

今の案は、最終的には次の3層に分けて考えるのがいちばん安定すると思う。

### 1. 明示ドキュメント層

人間が意図して書くもの。

- README
- ADR
- 設計書
- 方針メモ

これは本筋 repo に置いてよい。
人間が読むことも前提。

### 2. 自動生成の決定記録層

今回いちばん価値があるところ。

- いつ
- 何を
- どのスコープで
- どういう確定度で
- どれくらい重要か

を **小さい単位で自動追記** する。

これは本筋 repo と分離してもいいし、同 repo 内の別 branch / worktree / hidden dir でもよい。
ここが AI 向け・検索向けの一次入口になる。

### 3. 一時的な生ログ/作業記憶層

会話ログ、試行錯誤、セッションメモなど。

これは永続本体ではない。
保持期間を短くしてよいし、ローカルDBやキャッシュでもよい。
長期保存対象ではなく **蒸留元**。

---

## いちばん良い着眼点

> 「ゼロが10になるだけで劇的に違う」

これは本当にそう。

現場の開発って、実際には

- コード
- コミットメッセージ
- たまにPR本文
- たまに issue

しか残らない。

だから、

- A/B 検討した
- B を採用した
- 理由は X
- Y は却下した

が残るだけで、後からの認知負荷がかなり下がる。

この意味で、**全文保存RAGより、決定ログの方が費用対効果が高い** 可能性が高い。

---

## かなり同意している点

### 1. 「検討過程は全部いらないかもしれない」

これはかなり正しい。

もちろん理想を言えば検討過程も欲しい。
でも実務で後から必要になるのは、多くの場合こういう情報。

- 何が決まったか
- 何が却下されたか
- なぜそうなったか
- 今も有効か

つまり、全対話ではなく**判断の分岐点**が重要。

なので「会話ログ全部保存」よりも、

- `decision`
- `rejected alternatives`
- `rationale`
- `confidence / status`

の方が、あとで使える。

### 2. 人間の明示文書と自動生成メタを分ける

これはかなり重要。

ここを混ぜると破綻しやすい。

理由は単純で、自動生成物はどうしても

- ノイズが混じる
- 精度に揺らぎがある
- フォーマットが機械都合になる
- 大量に増える

から。

人間が読むための文書と混ぜると、すぐ「汚い」「信用しにくい」「直したい」が発生する。
なので **明示文書層と自動メタ層は分離** がよい。

### 3. 最初は hook ベースの非常駐でよい

これも同意。

常駐バックグラウンドエージェントは魅力的だけど、最初からやると複雑さが跳ねる。

最初はむしろ、

- post-commit
- post-merge
- PR作成時
- セッション終了時

のどれか1個だけで十分。

特に MVP なら **post-commit か PR 時** のどちらかでいいと思う。

---

## ただし、ここは少し危ないと思った点

### 1. コミット = 決定、は少し強く見すぎ

ここは慎重に見た方がいい。

コミットは「意味のある変化」の単位ではあるけど、必ずしも「決定」の単位ではない。

例えば:

- typo 修正
- formatter の適用
- rename only
- WIP commit
- fixup commit
- 実装途中の分割 commit

こういうのは判断そのものではない。

逆に本当の決定は、

- issue で決まる
- PR レビューで決まる
- 口頭/Slack/Notion で決まる
- 実装前に設計で決まる

ことも多い。

なので、
**コミットを真実の決定単位とみなすのではなく、「決定の痕跡候補」くらいに見る** のがいいと思う。

これはかなり大事。

### 2. 「5フィールドで足りる」は半分正しいが、理由が弱い

5フィールド案はMVPとしてはよい。
でも、後から本当に効くかを考えると、最低でももう少し欲しい。

最小でもこうする。

| field | 意味 |
|---|---|
| `when` | 時刻 |
| `scope` | 影響範囲 / path / domain |
| `kind` | architecture / implementation / convention / ops など |
| `status` | tentative / decided / reverted / superseded |
| `importance` | high / medium / low |
| `decision` | 決定内容 |
| `rationale` | 理由の短文 |
| `evidence` | commit hash / PR / issue / doc link |
| `alternatives` | 却下候補があれば短く |
| `actor` | 人間 / agent / mixed |

特に重要なのはこの3つ。

- `rationale`
- `evidence`
- `status`

理由がない決定は後で弱い。
証跡がない決定は辿れない。
status がないと古い判断が今も有効か分からない。

なので 5 フィールドは最小MVPとしては良いが、
**本命としては 8〜10 フィールドくらいがちょうどよい** 気がする。

### 3. 「階層 mirror repo」は、早い段階では少しやりすぎの可能性がある

ここはブレスト上の重要ポイント。

最初の着想としてはすごく良い。
でも MVP として本当に必要かは分けた方がいい。

なぜかというと、階層 mirror を作ると設計課題が増える。

- どの path に何をぶら下げるか
- 横断的判断はどこに置くか
- 複数ディレクトリに跨る判断は？
- repo 再編時にメタ階層も追従？
- renamed path の履歴は？
- package/module 単位とディレクトリ単位がズレたら？

つまり、**ファイルシステム階層 = 意味階層** とみなす前提が必要になる。
でも実際のシステムでは、意味境界は path と一致しないことが多い。

だから初期は、

- path 紐付けはメタデータの一属性として持つ
- 保存は1箇所の log/ledger でもよい
- 表示時に path ごとに絞り込む

方が柔らかい。

つまり、

> 保存構造を階層化する
> ではなく
> **検索・投影を階層化する**

方が先にくる気がする。

これはかなり強めの意見。

## どう切るか

### フェーズ1: Decision Ledger

まずはただの台帳。

例:

```json
{
  "id": "2026-03-29T15:12:34Z-001",
  "scope": ["src/auth", "infra/cognito"],
  "kind": "architecture",
  "status": "decided",
  "importance": "high",
  "decision": "社内向け認証は Google Workspace のドメイン制限付き Google Login を採用する",
  "rationale": "社内用途で UX と運用負荷のバランスがよく、独自ID管理を避けられるため",
  "evidence": {
    "commit": "abc123",
    "pr": "#42",
    "doc": "docs/auth/decision.md"
  },
  "alternatives": [
    "独自SSO実装",
    "Cognito Hosted UI"
  ]
}
```

これを JSONL か YAML frontmatter 付き Markdown で積む。

この段階では mirror tree はいらない。

### フェーズ2: Path / Domain 別ビュー

ledger を元に、

- `src/auth` に関係ある決定
- `frontend` に関係ある決定
- `ops` に関係ある決定

を抽出するビューを作る。

ここで初めて「階層っぽさ」が出る。

でも元データは一元管理のまま。

### フェーズ3: Directory summary / AGENTS.md 自動生成

ledger の内容を蒸留して、

- ルート概要
- ディレクトリ概要
- サブツリー概要
- 関連設計判断

を自動生成する。

この段階でようやく、最初に言っていた

- 階層的 AGENTS.md
- AI 向け summary tree
- 司書エージェント向け入口

が効いてくる。

つまり、

> 最初から mirror metadata tree を正とするのではなく、
> **decision ledger を正にして、tree は派生物として作る**

方がいいと思う。

## これが大きいと思う論点

### メタ層の「正」は何か

ここは決めた方がいい。

候補は3つある。

**A. tree が正**
各ディレクトリの AGENTS.md / summary が本体。
これは人間にも見やすいが、更新や整合性が難しい。

**B. ledger が正**
決定のレコード列が本体。
tree や summary は派生。
これが有力だと思う。

**C. transcript/event stream が正**
生ログやイベント列を本体にし、要約は派生。
将来性はあるが、最初は重い。

今の議論は A と B の間を揺れている感じがある。
**B を正にして A を派生にする** のがよいと思う。

### 「AI専用メタ層」に限定しすぎない方がいい

これは地味に重要。

この仕組み、最初は AI 向けに見えるけど、実際には

- 人間のオンボーディング
- レビュー前の把握
- 過去判断の再確認
- ADR 補助
- PR 要約
- issue 起票補助

にも効く。

なので、思想としては

> AI専用の裏レイヤー

より

> **人間とAIの両方が使える、軽量な判断インデックス**

として設計した方が長持ちすると思う。

---

## Ralph Loop との関係についての見方

交差はある。
ただ、本質的には別責務。

**Ralph 系**

- 実行ループ
- 状態復元
- 次の一手の継続

**今回のメタ層**

- 判断の永続化
- 検索可能化
- 後からの文脈復元

だから、Ralph にとっては今回の仕組みは

- progress の補助記憶
- restart 時の context source
- 決定の外部メモリ

にはなるけど、Ralphそのものではない。

むしろ

- Ralph は「進捗メモ」
- 今回は「判断メモ」

という違い。

**この分離は保った方がいい。**

## 実際に作るなら、最初のMVPはこれで十分

### MVP案

**入力**

- `git diff --cached` or commit diff
- commit message
- 可能なら branch 名
- 可能なら PR title / body

**処理**

LLM に対して:

- これは決定か？
- ただの実装/雑修正か？
- 決定なら decision/rationale/scope/status/importance を返せ

とさせる。

**出力**

- `meta/decisions.jsonl`

**例**

- low importance は保存しない
- status=tentative は PR 時だけ
- commit 時は decided/reverted のみ

これだけでかなり試せる。

### 逆に、最初はまだ入れない方がいいもの

- ベクトルDB
- 全会話ログ保存
- MCP ベースの複数記憶バックエンド
- 常駐 daemon
- 階層ごとの複雑な同期
- 自動で原則抽出して全部 AGENTS.md 更新
- 人間文書との双方向同期

このへんは魅力的だけど、MVP段階では重い。

## いちばん面白い問い

議論の中で、いちばん重要だと思ったのはこれ。

> **保存すべきなのは「情報」なのか、「判断」なのか、「再構築可能性」なのか**

ここはもっと詰める価値がある。

今の仮説はこう。

- **情報** は原則として外部ソースにある
- **判断** は失われやすい
- **再構築可能性** は判断 + 証跡 + 最低限の理由で担保できる

なので保存の優先順位は

1. 判断
2. 理由
3. 証跡
4. スコープ
5. 生の過程

になる気がする。

### 今の案を一文で言い直すなら

> **AIの長期記憶基盤を作るというより、Gitイベントを起点に、開発判断を軽量な構造化レコードとして自動蓄積し、それを元にAI向け・人間向けの文脈ビューを派生生成する仕組み**

この表現の方が、構想がかなりクリアになる。

# 正規形は ledger か tree か — 詳細

## ここでいう「正規形」は何か

要するに、

> **どの表現を一次ソースとして保存し、他をそこから生成するか**

という話。

候補は主に2つ。

- **ledger 正規形**: 判断をレコードとして時系列に積む
- **tree 正規形**: リポジトリ階層に対応したメタファイル群を本体にする

これは DB 設計でいう
「正規化された事実テーブルを持つか」
それとも
「参照しやすいビューをそのまま本体にするか」
に近い。

## まず直感的に言うと

### ledger 正規形

「何が起きたか」を中心に保存する。

例:

- 2026-03-29
- `src/auth`
- Google Login を採用
- 理由は運用負荷削減
- Cognito Hosted UI は見送り
- status = decided

こういうイベント/判断の記録が本体。

### tree 正規形

「この場所は今どういう意味を持つか」を中心に保存する。

例:

`meta/src/auth/AGENTS.md`

```markdown
# src/auth

## 役割
認証と認可を担当する

## 現在の方針
- 社内向け認証は Google Workspace ドメイン制限付きログインを採用
- 認証基盤は独自実装を避ける
- SSOの責務はアプリ側に持ち込みすぎない

## 注意点
- Cognito Hosted UI は現時点では不採用
```

こういう現在状態の説明が本体。

## 何が違うのか

本質的な違いはこれ。

- **ledger は「差分・出来事」のモデル**
  - 時系列に強い
  - 由来を追いやすい
  - 履歴管理に強い
  - いまの状態は再構成が必要

- **tree は「現時点スナップショット」のモデル**
  - 読みやすい
  - AI に食わせやすい
  - 現在状態の把握が速い
  - なぜそうなったかは弱い

つまり、

- ledger は append-only log 的
- tree は materialized view 的

---

## ledger 正規形を詳しく

### どういう保存になるか

1件1件の判断をレコードで持つ。

たとえば JSONL:

```json
{"id":"d-001","when":"2026-03-29T15:00:00Z","scope":["src/auth"],"kind":"architecture","status":"decided","importance":"high","decision":"社内向け認証に Google Workspace ドメイン制限付き Google Login を採用","rationale":"Google Workspace 前提で UX と運用負荷のバランスがよい","alternatives":["独自SSO実装","Cognito Hosted UI"],"evidence":{"commit":"abc123","pr":"42"}}
{"id":"d-002","when":"2026-03-30T10:00:00Z","scope":["src/auth"],"kind":"architecture","status":"reverted","importance":"medium","decision":"Cognito Hosted UI の再検討を開始","rationale":"将来的な IdP 拡張可能性を再評価するため","evidence":{"issue":"84"}}
```

この形式の良さは、事実の追加に向いていること。

### ledger 正規形の強み

**1. 履歴に強い**

「なぜ今こうなっているか」を追いやすい。

たとえば:

- 最初は A を採用
- 後で B に変更
- さらに A の一部だけ戻した

みたいな変遷がそのまま表せる。

tree だと最終状態は書けるが、
途中の分岐や反転が薄まりやすい。

**2. 衝突しにくい**

append-only に寄せれば、複数人・複数エージェントでも比較的安全。

- 1レコード追記
- 1ファイル1行追加
- path 別 shard も可能

tree 正規形だと同じ AGENTS.md を複数人が更新しやすく、競合が増える。

**3. 後からいろいろなビューを作れる**

ledger からなら:

- path 別 summary
- ドメイン別 summary
- high importance だけ
- reverted を除いた current decisions
- 直近30日だけ
- architecture だけ

みたいな投影ができる。

つまり柔軟性が高い。

**4. 「決定」と「説明」を分離しやすい**

記録そのものと、後から生成する説明文を分けられる。

これは大きい。
生成物の品質が悪くても、元レコードが壊れにくい。

### ledger 正規形の弱み

**1. そのままだと読みにくい**

人間にも AI にも、素の event log は読みにくい。

100件レコードがあると、
「今どうなってるの？」に即答しづらい。

**2. "現在状態"は計算結果になる**

現在有効な方針を得るには、

- status
- superseded 関係
- scope
- importance
- 新旧関係

を解釈しないといけない。

つまり、読み出し側が賢くなる必要がある。

**3. スキーマ設計をサボるとすぐ汚れる**

自由文だけ積むと検索性が死ぬ。

- scope の粒度
- status の意味
- reverted / superseded の違い
- rationale の長さ
- evidence の形式

をある程度決めないと、ただの散らかったログになる。

## tree 正規形を詳しく

### どういう保存になるか

repo と同じ構造、または近い構造でメタファイルを持つ。

例:

```
.meta/
  AGENTS.md
  src/
    AGENTS.md
    auth/
      AGENTS.md
    billing/
      AGENTS.md
  infra/
    AGENTS.md
```

各ファイルはその階層の意味・方針・注意点を書く。

### tree 正規形の強み

**1. AI にとって非常に使いやすい**

これはかなり大きい。

AI にとっては

- ルートを読む
- 該当ディレクトリを読む
- 必要なら子を読む

という段階的ロードがしやすい。

これは token 制御とも相性がよい。

**2. 人間にも読みやすい**

`src/auth/AGENTS.md` を開けば、その場所の意味が分かる。
オンボーディングにも強い。

**3. repo の mental model と一致しやすい**

開発者は path で考えることが多いので、

- このディレクトリは何か
- ここで何をしてよいか
- 何が禁止か

がすぐ分かる。

**4. 現在状態に強い**

ledger が「何が起きたか」なのに対し、tree は「いま何なのか」が得意。

### tree 正規形の弱み

**1. 履歴に弱い**

これが最大の弱点。

たとえば `src/auth/AGENTS.md` に

- Google Login 採用
- Cognito 見送り

と書いてあっても、

- いつ決まったか
- 何と比較したか
- 誰が決めたか
- 後で覆ったか

が落ちやすい。

もちろん md に全部書けばよいが、それをやると今度は tree が肥大化する。

**2. 競合しやすい**

複数人が同じ場所を更新するとマージ競合しやすい。

特に root の summary 系は衝突しやすい。

**3. repo の構造変更に弱い**

ディレクトリ rename, module 再編, 境界見直しが起きるとメタも大移動する。

しかも意味境界と path 境界がズレるとつらい。

例:

- `src/auth` と `src/user` に跨る判断
- フロントとバック両方に効く方針
- `infra` と `app` 横断の制約

こういうものは tree だけだと置き場に困る。

**4. 自動更新が難しい**

要約ファイルは常に「今の正しい説明」を保つ必要がある。

つまり差分追記ではなく、再要約・再編集が必要になる。
これは生成品質と整合性の問題を持ち込む。

---

## 一番重要な視点

### 「事実」と「ビュー」を分けるかどうか

ここが本質。

- **ledger 正規形**: 事実 = ledger、ビュー = tree/summary/AGENTS.md
- **tree 正規形**: 事実とビューが同じものになりやすい

この違いはかなり大きい。

ソフトウェア設計的には、多くの場合

> 事実は細かく正規化して持ち、見せ方は派生にする

方が拡張しやすい。

なので、設計原則としては ledger の方が強い。

## じゃあどっちがよいのか

### 結論

**正規形は ledger に寄せる方がよい。**
**tree は派生ビューとして作る方が安定する。**

理由は4つ。

**1. 失いたくないのは「決定の事実」だから**

- 何を決めたか
- 何を却下したか
- なぜか
- いつか
- 今も有効か

これがコア。
これは ledger の方が自然に表現できる。

**2. tree は読みやすいが、正としては壊れやすい**

tree は要約された現在像なので、便利だが脆い。

- 生成ミス
- 更新漏れ
- path 再編
- 文書の陳腐化

が起きやすい。

**3. tree は後から何通りでも作れる**

ledger があれば、

- AGENTS.md
- docs-list
- path summary
- current constraints
- onboarding guide

は派生生成できる。

逆に tree しかないと、
履歴や判断の細粒度を復元しづらい。

**4. append-only の方が automation と相性がよい**

hook やエージェントで自動追記するなら ledger の方が楽。

### ただし、ledger 一択でもない

ここは大事。

利用時のUXは tree の方が圧倒的によい。
だから実運用では多くの場合、

- 保存の正規形は ledger
- 読み出しの主インターフェースは tree

になるのが自然。

### 推奨構成

**1. Source of Truth = ledger**

例:

- `meta/decisions.jsonl`
- `meta/decisions/*.json`
- `meta/events/*.yaml`

**2. Derived Views = tree**

例:

- `.meta/AGENTS.md`
- `.meta/src/auth/AGENTS.md`
- `.meta/infra/AGENTS.md`

**3. 必要なら index / search**

例:

- scope 別 index
- importance 別 index
- current-only summary
- reverted を除外した view

---

## 具体的にどう違うか、同じ事例で比べる

### 事例

「社内認証は Google Login を採用し、Cognito Hosted UI は見送った」

### ledger 正規形での表現

```json
{
  "id": "d-101",
  "when": "2026-03-29T15:00:00Z",
  "scope": ["src/auth", "infra/auth"],
  "kind": "architecture",
  "status": "decided",
  "importance": "high",
  "decision": "社内向け認証に Google Login を採用",
  "rationale": "Google Workspace 前提で UX と運用負荷のバランスがよい",
  "alternatives": ["Cognito Hosted UI"],
  "evidence": {
    "commit": "abc123",
    "notion": "auth-decision-note"
  }
}
```

### tree 派生ビューでの表現

`src/auth/AGENTS.md`

```markdown
# src/auth

## current decisions
- 社内向け認証は Google Login を採用
- Cognito Hosted UI は現時点では不採用

## rationale
- Google Workspace 前提の社内運用に適する
- 初期導入コストを抑えやすい
```

AI はこっちの方が読みやすい。
でも SoT は ledger にある。

---

## どんなとき tree 正規形が勝つか

例外もある。

### tree 正規形が向くケース

- repo 構造がかなり安定している
- 履歴より現在の説明が重要
- 単独開発で競合が少ない
- "読ませること" が最優先
- AGENTS.md を人間が積極的にメンテする文化がある

この場合は tree 正規形でも成立する。

ただしその場合でも、最低限

- 更新日時
- 元イベント参照
- deprecated / superseded の印

は欲しい。

---

## 逆に、この構想で ledger を推す理由

関心はかなり明確に

- 判断の蓄積
- 将来の再読
- AI 文脈復元
- 決定事項の自動同期
- Git と接続
- 後で必要な分だけ読む

にある。

これはかなり ledger 的問題設定。

tree 的問題設定はむしろ

- 各ディレクトリの役割説明
- AI にどこから読ませるか
- token をどう節約するか

の方。

だから順序としては、

1. ledger を作る
2. そこから tree を生成する
3. AI は tree を主に読む
4. 必要なら ledger に降りる

が自然。

---

## 設計判断として一番危ないのはこれ

### tree を正規形にしてしまうこと

一見きれいだが、すぐ以下に苦しむ。

- 更新漏れ
- summary の真偽
- 跨り判断の置き場
- path rename
- 履歴消失
- 競合

つまり、**説明文を source of truth にしてしまう問題**。

これは docs を SoT にしたときに起こる古典的な問題に近い。

### 定義

- **ledger 正規形**: 「意思決定の最小単位を、構造化イベントとして蓄積する」
- **tree 派生形**: 「ledger から現在有効な文脈だけを投影した、AI/人間向けの局所サマリ」

この役割分担が一番きれい。

---

## 最終的な推奨

### MVP

- 正規形: ledger
- 表示形: まずは簡単な summary だけ
- tree 生成: 後回しでもよい

### 実用段階

- 正規形: ledger
- 主要UX: tree
- つまり内部は ledger、外側は tree

### 一言でまとめると

- ledger 正規形は「失いたくない事実」に強い
- tree 正規形は「今すぐ読ませたい説明」に強い
- 構想の土台にすべきなのは前者
- AI に食わせる主インターフェースは後者

なので、

> **SoT は ledger、tree は materialized context view**

がよい。

# 仮想的な意味論層としてのメタ情報

## メタ情報は実装に従属しなくていい

メタ情報は実装そのものではない。
実装に寄り添って参照されることはあっても、実装構造に従属しなくていい。

したがって、メタの正体は「物理配置されたファイル群」ではなく、
**ある論理構造を持った仮想的な知識空間** と見た方が自然。

## 3層に分けて考える

### 1. 物理実装層

実際の repo / ディレクトリ / ファイル / commit / PR。

これは現実の変更対象。
AIも最終的にはここを読む。

### 2. 論理メタ層

「仮想的な状態」に近い。

本当はメタが持ちたいのは、物理 path そのものではなくて:

- この判断はどの関心に属するか
- どの責務に関係するか
- どの境界にまたがるか
- 今どの制約が有効か
- 何が superseded されたか

みたいな、**意味的なノードと関係**。

これは別に

- `src/auth`
- `backend/usecase`
- `infra/cdk`

みたいな path で最初から固定しなくていい。

### 3. 投影層

実際に使うときに、論理メタ層を実装都合に合わせて投影する。

たとえば:

- path 別に出す
- package 別に出す
- ドメイン別に出す
- AI kickoff 用に shallow summary にする
- 人間向けに ADR 候補にする

つまり、**利用時に実装へ合わせて展開する**。

この見方だと、tree は本体ではなく「投影の一種」になる。

## この整理はかなり強い

repo の構造って結局かなり偶然が混じる。

例えば:

- `src/auth` に認証責務がある
- でも一部は `middleware/` にもある
- infra は `cdk/` にある
- フロント側の login UI は `pages/login` にある

このとき、「認証」というメタ概念は実装上は分散している。
だからメタの本体まで path に縛ると、意味構造が壊れる。

その意味で、

> メタは仮想的・論理的であり、物理構造には投影されるだけ

という考え方はかなり正しい。

## 設計に落とすとどうなるか

### 発想の転換

今までは

- ledger 正規形
- tree 正規形

みたいに「保存形式」の話をしていたけど、ここから先はむしろ

- **logical canonical model**
- **physical projections**

で考えた方がいい。

### canonical model は何か

本体はたぶん「ノード + 関係 + イベント」。

**ノード**

- decision
- constraint
- concern
- component
- domain
- artifact
- session

**関係**

- affects
- relates_to
- supersedes
- derived_from
- scoped_to
- evidenced_by

**イベント**

- decided
- reverted
- introduced
- deprecated
- confirmed

つまり、正規形は ledger ですらなく、もっと抽象化すると
**意味グラフ + イベントログ** に近い。

### 例

「Google Login を採用した」という1件があるとする。

物理的には:

- `src/auth/login.ts`
- `infra/cognito-stack.ts`
- `docs/auth.md`

に関係しているかもしれない。

でも論理的には:

- concern: 社内認証
- decision: Google Workspace domain-based login を採用
- rejected alternative: Cognito Hosted UI
- rationale: UX / 運用負荷
- status: decided
- evidence: commit abc, PR 42, Notion note X

という1つの意味単位。

この意味単位を、使うときだけ:

- path `src/auth` に関係あり
- path `infra/` にも関係あり
- auth domain summary にも出す
- onboarding summary にも出す

と投影する。

こっちの方が自然。

## 更新版の立場

前は「SoT は ledger、tree は view」と言ったが、より正確にはこう。

> **SoT は logical metadata model**
> **ledger はその append-friendly な保存表現**
> **tree は repo-aligned な利用表現**

この三段がしっくりくる。

## ledger も実は中間形にすぎないかもしれない

ledger って保存上かなり便利だけど、メタの本質そのものではない可能性がある。

ledger は基本的に「時系列に並ぶ出来事」を強く表す。
でもメタの世界では、時系列だけでなく

- 横断関係
- 依存関係
- 同値性
- 上位概念 / 下位概念
- 関心のまとまり

も大事。

なので本当に厳密に言えば、

- ledger = 追記しやすい記録形式
- tree = 読みやすい表示形式
- **graph / logical model = 意味の本体**

という三分割の方が美しい。

## 重要な設計原則

### 1. path を主キーにしない

これはかなり大事。

path は anchor にはなるけど、identity にはしない方がいい。

なぜなら:

- rename される
- split/merge される
- 責務境界と一致しない
- 複数 path にまたがる

だから主キーはむしろ

- decision id
- concern id
- domain id
- component id

みたいな論理IDで持ち、path は relation にするのがよい。

### 2. 投影は何種類あってもよい

論理本体があるなら、投影先は複数持てる。

- repo tree view
- domain view
- time view
- AI kickoff compact view
- reverted を除いた current view
- importance high only view

### 3. 実装追従は projection 側でやる

repo の rename や再編が起きても、本体を壊さずに済む。

projection 側で

- 新 path に再マッピング
- summary 再生成
- obsolete path view の無効化

をやればいい。

## ソフトウェアアーキテクチャ的には何に近いか

かなり近いのは:

- イベントソーシング + read model
- knowledge graph + materialized views
- semantic layer + physical storage
- logical schema vs physical schema

つまり、

> 書き込みや真実は別の抽象層にある
> 読み取りは用途ごとに最適化された形に投影する

### 実装上の落としどころ

最初は ledger 風のレコードで保存する。ただし中身は論理メタとして設計する。

```json
{
  "id": "dec-001",
  "type": "decision",
  "timestamp": "2026-03-29T15:00:00Z",
  "decision": "社内認証に Google Login を採用",
  "status": "decided",
  "importance": "high",
  "concerns": ["internal-auth", "sso", "workspace-login"],
  "affects": [
    {"type": "path", "value": "src/auth"},
    {"type": "path", "value": "infra/auth"},
    {"type": "domain", "value": "authentication"}
  ],
  "alternatives": ["cognito-hosted-ui"],
  "rationale": "運用負荷とUXのバランス",
  "evidence": [
    {"type": "commit", "value": "abc123"},
    {"type": "pr", "value": "42"}
  ]
}
```

これなら保存形式は ledger っぽいけど、意味的にはすでに仮想層になっている。

# repo 構造は偶然ではなく、アーキテクチャの表明

## 理想的には

repo や directory の構造は理想的には

- ドメイン境界
- 責務境界
- チーム境界
- 依存方向

を表す。DDD でも Clean Architecture でも同じ。
**構造そのものが設計の表明** になっている。

## 3段階ある

### 1. 理想状態

repo 構造 = アーキテクチャ構造 = ドメイン境界

このときは tree ベースのメタがかなり強い。
tree projection はかなり高 fidelity。

### 2. 現実状態

開発途中・長期運用で少しずつ乖離する。

- 一時的な配置
- 便宜上の utils
- cross-cutting な実装
- 移行途中の構造
- 責務がまたがるコード
- 旧構造の名残

repo 構造は依然として強い手がかりではあるけど、完全には信用できない。

### 3. 崩壊状態

repo 構造がほとんどドメインを表していない。
tree を正とすると、メタも一緒に壊れる。

## 設計方針

### path は「第一級のシグナル」だが「絶対的な正規形ではない」

repo 構造を信じる設計は全然あり。
ただしそれは

- repo 構造を canonical model にする、ではなく
- **repo 構造を primary projection axis にする**

くらいがちょうどいい。

### デフォルトは tree-aligned

decision record に対して、まず自動で

- affected paths
- primary path
- nearest boundary
- module / package

を付与する。通常の投影はこの path 情報を使う。

### 例外だけ semantic relation を足す

- 認証方針だがフロントとバックとインフラにまたがる
- 課金判断だが `billing/` と `subscription/` の両方にまたがる
- 一時的に `legacy/` に置かれているが本来は `domain/user`

こういうものだけ、

- concern
- domain
- related boundaries
- true owner

みたいな補助メタを足す。

このやり方なら、repo 構造を最大限活かしつつ、破綻も防げる。

### 更新版の立場

- 論理 SoT は持つ
- ただしその論理SoTは **repo tree と高い相関を持つ前提** で設計する
- 通常利用では repo tree を主軸に展開する
- 乖離した部分だけ論理補正する

つまり、**tree-first but not tree-only**。

---

## メタ層は「乖離検知」の役割も持つ

もし理想として repo 構造がドメイン境界を表すなら、
メタシステムは単なる文脈供給ではなく、
**repo 構造と意味構造のズレを検知するセンサー** にもなれる。

例えば:

- ある decision が毎回3つ以上の unrelated path にまたがる
- `common/` や `utils/` に高重要度 decision が集中する
- 同じ concern が複数 directory に分散し続ける
- 本来同一 context であるはずのものが tree 上で離れている

こういうのは、設計劣化のシグナル。

つまりメタ層は「AI用メモ」だけじゃなく、
**アーキテクチャ健全性の観測層** にもなりうる。

# ミラーレポの北極星としての性格

## 3つを持つ

- **description**: これは何か
- **interpretation**: これはどういう意味か
- **orientation**: これはどこへ向かうべきか

この3つめ、orientation があるから北極星っぽい。

## ミラーは「説明層」だけではなく「規範層」でもある

もし mirror が単なる要約なら、「今こうなってます」で終わる。

でも本当はもっと強くて、

- この bounded context はここまでを担うべき
- この層からこの層への依存は避けるべき
- このディレクトリは本来この concern に属すべき
- この判断はこの system vision と整合しているべき

みたいな、**本質理解のための規範モデル** を持ちたい。

ここまで来ると、ミラーレポは単なる「AIが読みやすい補助情報」ではなく、
**プロジェクトの意味論的OS** みたいな位置づけになる。

## ミラーレポは「本体の影」ではなく「本体を照らす座標系」

本体 repo は変化し続ける。実装は汚れる。歴史的事情も混ざる。長期運用で乖離も起きる。

そのときに、mirror 側が

- 本来の責務境界
- 重要な判断
- 失ってはいけない制約
- 目指すべき構造
- いまの逸脱

を示せるなら、mirror は「従属物」ではなく **照準器** になる。

## 注意点

北極星層を入れると、mirror 側が間違う可能性も出る。

なので、北極星として使うなら mirror は

- immutable truth ではなく
- **revisable guidance**

として扱った方がいい。

つまり「真理」ではなく **現在時点での最良の意味モデル**。

## mirror に入る情報の内部階層

### A. 観測された事実

- この決定があった
- この path が変わった
- この制約が追加された

### B. 解釈された意味

- この変更は auth concern に属する
- これは domain boundary を跨いでいる
- これは実質的に architecture decision

### C. 規範・北極星

- auth はここまでを責務とするべき
- infra 依存は application に漏らすべきでない
- この context は将来的に独立可能であるべき

**この3つを混ぜると危ない。逆に分ければかなり強い。**

---

# 人間の理解の起点は物理層

## 人間はいきなり抽象モデルからは発生しない

多くの人にとって理解の入口はまず、

- repo
- directory
- file
- module

のような物理構造であり、そこから

- ここは auth の責務っぽい
- ここは domain の中心だ
- ここは infra だ

と意味が立ち上がる。

## mirror repo の価値

抽象モデルを tree に投影すること以上に、
**人間が最初に理解を開始する場所と同じ形をしていること** にある。

repo tree は単なる UI ではなく、**人間の理解の足場** である。

## 思考の順序

1. 物理層が先（repo / directory / file / module）
2. そこに意味を重ねる（責務、境界、判断、制約）
3. 必要に応じて抽象化する（横断 concern、北極星、ドリフト検知）

## mirror repo はやはり重要

最初の着想が repo という物理層から来ていたのは本質的で、
そこを外すとこの構想の強みが消える。

mirror repo が自然だったのは、ここが起点だから。

> mirror repo は、抽象モデルを tree に投影する話というより、
> **人間が最初に掴める物理構造を起点にして、その上に意味・判断・規範を積み上げる話**

---

# AI の有限コンテキストと中間層の必要性

## 物理層をそのまま全部は渡せない

- token budget がある
- ノイズが増える
- irrelevant context が精度を落とす
- 重要箇所だけを先に知りたい

物理層そのものを丸ごと渡す設計は現実的ではない。

## 中間層は「意味を保った圧縮」

単なる summary ではない。
本当に必要なのは、

- 何が重要か
- どこから読めばよいか
- 何を前提にしてよいか
- 何を壊してはいけないか
- 今回のタスクに関係ある境界はどこか

つまり **意味を保ったまま探索範囲を絞る圧縮**。

## メタ層の4つの役割

1. **物理層への接地**: repo / directory 起点で見られること
2. **コンテキストの圧縮**: AI に渡す情報を減らすこと
3. **タスクに応じた選別**: 今回のタスクに必要な範囲だけを surfacing すること
4. **設計意図や制約の保持**: 単なる縮約ではなく、失ってはいけない設計意図や制約を残すこと

## mirror repo はこれらを満たす

mirror repo は **意味論的圧縮のための物理 UI** として理解できる。

AI にとっては mirror は

- full context ではなく
- **context routing layer**

でもある。

# 中間地点を探る

## AI だけなら別のアーキテクチャでいい

もし AI だけで完結するなら、

- AI 用 IR
- AI 用 semantic graph
- AI 用専用言語
- AI 用最適化された knowledge storage

でよい。

## でも現実はそうならない

システムは必ず

- 人間が読む
- 人間がレビューする
- 人間が運用する
- 人間が責任を持つ
- 人間が引き継ぐ

だから必要なのは **人間とAIの共同理解に耐える中間的な構造**。

## mirror repo という形式の意味

- Git に乗る
- 差分を見られる
- 物理構造と対応する
- 人間が迷わず辿れる
- AI にも段階的に与えられる

つまり、**意味モデルと物理現実の妥協点**。

# ここまでの整理

議論の出発点は、本筋のリポジトリを汚さずに、AI が理解しやすいメタ的なミラー構造を別レイヤーとして持てないか という構想だった。最初は階層的 AGENTS.md やメタリポジトリのような形をイメージしていたが、話を進めるうちに、単なる補助ファイル群ではなく、**実装の背後にある意味・判断・方向性を外在化する基底モデル** を持ちたい、という発想が核だと見えてきた。

## 1. なぜミラーレポなのか

単に AI 向けの要約置き場が欲しいわけではない。
本質は、実装そのものではなく、その背後にある

- 何を担っているか
- なぜそうなっているか
- 何を守るべきか
- どこへ向かうべきか

といった **意味の骨格** を別レイヤーとして持つことにある。

そのため、ミラーされる対象はコードそのものではなく、

- 意思決定
- 責務
- 制約
- ドメイン境界
- 理想状態や北極星

のような、実装の理解に必要な基底モデルだと捉えた。

## 2. ただし起点は抽象モデルではなく repo の物理層

途中で明確になった大事な修正は、**人間の理解は抽象モデルから始まらない** という点。

多くの人にとって理解の入口はまず、

- repo
- directory
- file
- module

のような物理構造であり、そこから

- ここは auth の責務っぽい
- ここは domain の中心だ
- ここは infra だ

と意味が立ち上がる。

なので mirror repo の価値は、抽象モデルを tree に投影すること以上に、**人間が最初に理解を開始する場所と同じ形をしていること** にある。
repo tree は単なる UI ではなく、**人間の理解の足場** である、という整理に至った。

## 3. repo 構造は偶然ではなく、理想的にはアーキテクチャの表明

さらに、repo や directory の構造は単なる物理配置ではなく、理想的には

- ドメイン境界
- 責務境界
- 依存方向
- アーキテクチャの実装

を表すものである、という点も確認した。

もちろん現実には長期運用や歴史的事情で乖離するが、
それでも repo tree は **第一級のシグナル** であり、メタ層もまずはそれに沿って構成するのが自然だと整理した。

したがって立場としては、

- tree を絶対的真理とはしない
- しかし基本座標系としては強く採用する
- 乖離した箇所だけ論理メタで補正する

というバランスが良い、という結論になった。

## 4. AI には物理層を全部は渡せない

一方で、AI 側には明確な制約がある。
repo の全構造や全コード、全会話ログをそのまま入れることはできない。

理由は単にコンテキスト長の限界だけではなく、

- token budget がある
- ノイズが増える
- irrelevant context が精度を落とす
- 重要箇所だけを先に知りたい

という、有限コンテキストゆえの実務的な制約があるから。

そのため、物理層そのものを丸ごと渡す設計は現実的ではない。
ここで必要になるのが、物理層と AI の有限コンテキストの間にある **意味論的な圧縮層** だと整理した。

## 5. メタ層の本質は「意味を保った圧縮」

この中間層は単なる summary ではない。
本当に必要なのは、

- 何が重要か
- どこから読めばよいか
- 何を前提にしてよいか
- 何を壊してはいけないか
- 今回のタスクに関係ある境界はどこか

を与えることであり、これは単なる短い要約ではなく、
**意味を保ったまま探索範囲を絞る圧縮** だと整理した。

つまり mirror / メタ層の役割は少なくとも次の4つ。

1. 物理層への接地
2. コンテキストの圧縮
3. タスクに応じた選別
4. 設計意図や制約の保持

mirror repo は、これらを満たす **意味論的圧縮のための物理 UI** として理解できる、という見立てになった。

## 6. ledger と tree の議論

途中で、正規形をどう考えるかという話も出た。

- **ledger 正規形**: 判断やイベントを時系列レコードとして持つ
- **tree 正規形**: repo 階層に沿って現在状態の意味を持つ

という比較をした上で、当初は「SoT は ledger、tree は view」という整理を置いた。

ただその後、議論を進める中で、ここも少し修正された。
厳密には、

- 抽象的な意味や判断の記録は必要
- しかし人間の入口は repo tree である
- よって mirror は単なる派生ビュー以上に重要
- ただし完全に tree を真理にするのも危険

という位置づけになり、最終的には

> repo tree を主たる接地面として使いながら、必要に応じて論理メタで補正する

という立場に寄っていった。

## 7. mirror repo は AI 専用ではなく、人間とAIの共同理解層

最初は AI 向けの文脈圧縮から入ったが、最終的にはこれは AI 専用というより、
**人間と AI の双方にとっての理解基盤** だと整理された。

AI だけなら極論、

- AI 用アーキテクチャ
- AI 用専用言語
- AI 用の知識表現

でもよいかもしれない。
しかし実際の開発は必ず人間が関わり続けるので、
必要なのは **人間とAIが共同で扱える中間的な構造** になる。

mirror repo という形式が重要なのは、そこが

- Git に乗る
- 差分を見られる
- 物理構造と対応する
- 人間が迷わず辿れる
- AI にも段階的に与えられる

という、**意味モデルと物理現実の妥協点** だからだと整理した。

## 8. 北極星・規範層としての mirror

議論が進む中で、mirror repo は単なる事実や判断の記録ではなく、
**北極星や規範的座標系** の役割も持ちうる、という認識も強まった。

つまり、

- この bounded context は何を担うべきか
- どの依存は避けるべきか
- この構造はどこへ向かうべきか
- どこから逸脱しているか

のような、単なる説明以上の **方向付け** を持つ可能性がある。

ただしその場合、mirror は immutable truth ではなく、
**現時点の最良の意味モデル** として扱う必要がある、という注意点も確認した。

## 9. 結論として見えてきたもの

ここまでの議論をまとめると、mirror repo 構想は次のように位置づけられる。

> 人間が理解を開始する物理構造としての repo tree を起点にしつつ、そこに意味・判断・制約・方向性を重ね、AI の有限コンテキスト制約の中でも使えるように圧縮・選別された形で提示する、中間的な意味層

つまりこれは、

- 単なるドキュメント置き場ではない
- 単なる要約でもない
- 純粋な抽象モデルでもない
- 物理構造のコピーでもない

より正確には、

- repo tree という人間の理解の足場があり
- その上に意味論的圧縮層が重ねられ
- AI はそこから必要なものを選び
- 人間も同じ構造の上で理解できる

という構図になる。

## 10. 現時点での一番しっくりくる一文

> **mirror repo とは、実装をそのまま複製するための副次 repo ではなく、人間が理解の起点とする repo の物理構造に接地しながら、その背後にある意味・判断・制約・方向性を圧縮・選別して重ねることで、人間と AI の双方にとっての理解基盤および文脈ルーティング層として機能するもの**
