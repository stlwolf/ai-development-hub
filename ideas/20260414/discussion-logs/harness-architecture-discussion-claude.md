## 議論の流れ

### 1. 現在地の整理

canonical/ は4層分離（rules → skills → commands → agents）+ hooks の機械的ガードレールという構造が確立。ハーネス構成要素の約6割をカバー。

- 最大のギャップ: **制御ループの不在** — 検証の仕組みは存在するが自動ループしない状態
- 二層分離原則（hooks = 100%強制、rules/skills = 確率的）は明確に言語化済み

### 2. 論点1: CLIコマンドへのロジック内包

風呂場の着想から3つの論点が出てきた。1つ目は「スキルやhooksでも揺らぎ・コスト・重さの問題がある。CLIコマンド自体にロジックを内包する方向をもっと推し進めることで構造的に解決できるのでは」という仮説。

**3つの具体的利点:**

**① AIの判断負荷の削減:**
- スキルだと「この状況ではルールAを適用、別の状況ではルールBを適用」をLLMに判断させている
- コマンドにオプション内包すれば、AIは `--rule=A or --rule=B` を選ぶだけ
- 判断の粒度が「散文を解釈して適用する」から「引数を選ぶ」に落ちる

**② hooksの集約によるコスト削減:**
- pre-commit hookが3-4個積み重なると体感の遅延がかなり出る
- `workflow-pr` コマンド1本で一気通貫すれば、hookは「そのコマンドを通して実行されたか」の1点だけ検証すればよい

**③ プロジェクト固有のルール分岐の柔軟性:**
- スキルベースで一番つらいところ
- 「このプロジェクトでは規則Bは使わない」のようなコンテキスト依存判断は、散文だと「読んだけど無視した」「別の解釈をした」が起きる
- コマンドのオプションなら `--no-issue-prefix` のように明示的に制御できる

**Claudeの分析:**
- この方向性は以前の「定型フローをスクリプトに固める」議論の延長線上で、より一般化された形
- 「決定論的オーケストレーターが非決定論的ワーカーを制御する」アーキテクチャの自然な帰結

### 3. コマンド責務拡張の原則

**Eddyの言語化:**
> ある程度範囲が明確なものは、そもそもそのコマンドの責務を増やせばよい。コマンド前後で行う作業が機械的判断との分割で内包できるかが線引きの判断。

**Claudeの構造化:**
> コマンドの設計単位は「1つの機能」ではなく「1つのワークフロー区間で機械的判断が連続する範囲」

ブランチ作成フローの具体例:
- エージェントがissue番号を確認する（機械的）→ コマンドに吸収
- エージェントがスキルを読んで命名規則を解釈する（揺らぎあり）→ コマンドに吸収
- エージェントがブランチを切る（機械的）→ コマンドに吸収
- hookがブランチ名を検証する（機械的だが別プロセス）→ コマンド内部検証に吸収
- エージェントに残る判断: 「どのissueに取り組むか」「fixかfeatか」だけ

**副次的メリット:** エージェントのコンテキスト消費も減る。スキルを読ませる必要がなくなる部分のトークンを、本当に文脈判断が必要な作業に使える。

### 4. 論点2: 仮想環境による隔離と安全性

2つのサブ論点が絡み合った議論。

**A. hooks統合とコマンド内包:**
- コマンド自体を「仮想環境」と捉えれば、実行範囲内で安全性担保の検証をまとめて走らせられる
- hooksの「事後検証」→ コマンド内部の「実行中検証」へ
- コマンドが自分の出力を知っているから検証コストが安い（hookは毎回diffやファイル状態を外からパースし直す）

**B. オーケストレーション時の仮想環境隔離パターン:**

以前のMVPシミュレーション（1つのエピックで複数セッション管理）の体感から、「複数セッションが同じファイルを触るとマージ順の判断が難しい」問題への解決策:

1. 各セッションを隔離された仮想環境（worktree等）で並列実行
2. 各環境の結果を持ち寄り、差分を比較・議論
3. 指揮者がマージ順序・競合解決方針を決定
4. 仮想環境を全部破棄
5. 決定された順序に従って**直列で再実行**

ステップ4-5がポイント: 「並列の成果物をそのままマージする」のではなく「並列は探索・検証フェーズとして扱い、本番適用は直列でやり直す」。

**Claudeの整理:**
- 並列フェーズ = 非決定論的な探索（エージェントの仕事）
- 直列フェーズ = 決定論的な適用（スクリプト/オーケストレーターの仕事）
- 並列の成果物は「判断材料」であって「最終成果物」ではない
- git worktree が最も素直な仮想環境。各セッションに独立worktree → diffだけ抽出して比較 → worktree破棄 → mainから直列にpatch適用
- 検討事項: 再実行時に同じ結果が再現されるかの保証。探索結果の promotion 粒度設計の問題

### 5. 後片付けのコマンド化

**Eddyの着想:**
> それこそ後片付けの順番とか処理が同じなら、それこそコマンド化できる。後片付けを専門とするものを最終的に立ち上げて、そいつにすべてやらせる。

**Claudeの構造化:**
オーケストレーション全体のフローが3段階のコマンドに分解できる:

- **起動コマンド**: worktree作成、各セッションへのタスク配分、環境の初期化（機械的）
- **探索フェーズ**: 各仮想環境内でエージェントが実際のコード作業をやる（非決定論的 — ここだけエージェントの仕事）
- **収束コマンド**: diff抽出、worktree破棄、結果の構造化、マージ順序の提示、直列適用（機械的）

> 「強制できるもの」の範囲が hooks 単体から **コマンドライフサイクル全体** に拡張される形。

### 6. 論点3: セッション管理ツールの重要性

**Eddyの認識:**
- Claudeのエージェントチームもtmuxでセッション管理している
- 人間が視覚的に管理するのも含めて（最初は特に）、セッション情報のやりとりと環境分離が全体前提
- [Issue #20: wez CLI ツールキット](https://github.com/stlwolf/ai-development-hub/issues/20) の着手は早めに必要

**Claudeの分析:**
- `wez` が物理基盤になる: `wez pane split` で隔離環境、`wez pane capture` で成果抽出、`wez pane kill` で後片付け
- Phase 3 の `wez agent spawn` / `wez agent monitor` が「起動→探索→収束」の3段階をそのまま実装する場所
- セッション管理がないと上位の設計が全部「絵に描いた餅」になる
- Phase 1 のスコープが具体的でPoC検証済み

### 7. 議論の収束

**設計原則:**
> 機械的判断が連続する範囲をコマンドの責務にする。これがスキル/hooks の揺らぎ問題、hooks の重さ問題、オーケストレーションの安全性問題、全部に効く共通解。

**実装の積み上げ順序:**
1. `wez` CLI（物理基盤）
2. ワークフロー区間コマンド（ブランチ/PR等の定型フロー統合）
3. 起動/収束コマンド（並列探索の制御）

> 下から積まないと上が浮く。

## ChatGPTブレスト後のクロスレビュー

Claudeとの壁打ち内容をChatGPTに持ち込んだ後、ChatGPTの追加観点に対するClaudeの評価。

### 採用に値する観点

- **制御ループ = 閉ループ制御系 (5要素モデル)**: Controller位置づけの曖昧さの指摘が的確。以前の品質ゲート議論と接続
- **policyのcommand埋没リスク**: Claude側で明示的に出ていなかった重要な観点。Command / Policy / Context Resolver の3分割は実用的
- **仮想環境の3種分離（UI / execution / workspace）**: wezの責務を明確にする上で有用。wezに責務を積みすぎないガードレール
- **promotion artifactの粒度候補**: intent / evidence / diff / replay log の4点セット。以前のspeculation ratioやpromotion flow議論と直結
- **hooks削減の本質 = semantic observability**: 鋭い再フレーミング。本質的な価値は「文脈付き検証」ができること
- **セッション管理 = 認知補助**: orchestration cockpitとしての位置づけ

### 統合後のコア原則（5本柱）

1. **コア原則**: 非決定的な探索と、決定的な適用を分離する
2. **境界原則**: 機械的判断が連続する区間はcommandに吸収する
3. **安全原則**: 並列環境は探索のために使い、本番適用はpromotion/replayを通して行う
4. **観測原則**: 検証は外部hookの事後確認より、内部commandの文脈付き検証を優先する
5. **基盤原則**: セッション管理は単なる端末操作ではなく、人間の認知補助を含むorchestration substrateとみなす

### 次に詰めるべき4論点

1. **Controller contract** — ループ停止条件、失敗時再試行方針、partial successの扱い、並列探索の収束条件
2. **Promotion artifact** — diff / patch queue / intent+evidence / command replay logのどの粒度で昇格するか
3. **Isolation model** — UI隔離(pane) / execution隔離(process/env) / workspace隔離(worktree/container)の責務分担
4. **Policy extraction** — commandに埋めるもの vs 設定として切り出すもの vs project差分吸収の方法
