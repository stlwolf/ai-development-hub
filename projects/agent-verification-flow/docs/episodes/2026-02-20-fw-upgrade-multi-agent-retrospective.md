# FWアップグレード マルチエージェント開発レトロスペクティブ

## 概要

バックエンドFW 11→12 アップグレードを2リポジトリで実施し、AI エージェント主導の Plan→SO→Execute→FB サイクルを検証。

- **結果**: 両リポジトリとも ~1.5h で完了、テスト全通過、ステージング確認済み
- **SO の価値**: 事実確認（パッケージ互換性）と構造レビュー（漏れ検出）で高価値を発揮。ただし誤指摘（ハルシネーション）もあり、安全ネットであって絶対的な品質保証ではない
- **計画/実行分離**: GitHub Issue を「契約書」とした分離が機能した

**注意**: 本文書の知見は N=2 の観察に基づく仮説であり、再現実験で検証が必要。

---

## ワークフロー

```
[計画スレッド]
  調査 Issue 作成
  → 初期調査（依存パッケージ互換性）
  → SO で事実誤り検出
  → プラン作成 → SO R1: 構造的問題指摘 → プラン修正 → SO R2: 合意
  → 作業 Issue 作成（コマンドレベル詳細プラン転記）

[実行スレッド]
  Issue のプランに沿って実行
  → PR 作成 → SO PR レビュー
  → ステージングデプロイ + 動作確認
  → 実行フィードバックを Issue にコメント

[計画スレッドに戻る]
  FB 確認 → 次リポジトリのプラン（FB 反映済み → SO 1ラウンドで合意）
```

## SO の効果分析

### 高価値の場面

| 場面 | 影響度 |
|------|--------|
| パッケージ互換性の事実確認（バージョン誤判断を修正） | 高 — ブロッカー誤認を防止 |
| プランからの完全な欠落検出（テストツール更新、設定修正） | 高 — プランにない項目を発見 |
| 依存ライブラリの連鎖更新の事前察知 | 高 — dry-run 失敗の事前予測 |
| PR レビューでの後続タスク発見 | 中 — 運用品質向上 |

### 誤指摘事例

- 存在しないパッケージバージョンを推奨（**ハルシネーション**、Web検索の鮮度問題ではない）
- Codex / Claude 両方が同じ誤りを出した → 共通バイアスの限界
- 検出は `dry-run` の失敗による消極的なもの

### 収束パターン

| 対象 | SO ラウンド数 | 理由 |
|------|-------------|------|
| リポジトリ1 プラン | 2 | R1 で構造的問題を多数発見 |
| リポジトリ2 プラン | 1 | リポジトリ1 の FB が十分反映されていた |
| PR レビュー | 各1 | プランが十分検証されていた |

同種タスクの2回目は SO ラウンドが減る傾向（N=2、要再検証）。

## プラン精度の進化

### リポジトリ1（初回）

| プラン記述 | 実際 | 原因 |
|---|---|---|
| 特定バージョンに変更必須 | 自動解決で不要 | SO の誤指摘 |
| 静的解析ツール ^2.0 → 最新 | ^3.0（依存4連鎖） | 依存ツリー事前確認不足 |
| 見積もり 3-5.5h | ~1.5h | 過大見積もり |

### リポジトリ2（2回目、FB反映後）

| プラン記述 | 実際 | 原因 |
|---|---|---|
| 特定機能の互換性要確認 | SDK メソッドで影響なし | SO で修正済み |
| （なし） | ServiceProvider の dev 依存チェック漏れ | プラン欠落 |
| 見積もり 3.5-6h | ~1.5h | 過大見積もり（初回教訓の効果） |

見積もり乖離の要因は複合的: 破壊的変更が実質ゼロ、AI の作業速度の過小評価、SO がリスクを積み上げる傾向。

---

## コンテキスト消費とコスト効率

### スレッド分離の副次的メリット

各スレッドのコンテキスト使用量が抑えられた:
- 計画スレッド: 調査→SO→プラン。実行の詳細ログは含まない
- 実行スレッド: Issue を読んで実行→FB。計画の試行錯誤は含まない
- SO: 1ショットのプロンプト。会話履歴なし

### SO のコスト効率

SO は会話ではなく1ショット。コンテキスト圧縮を保ちつつ複数 AI の知見を活用するコスト効率の良いパターン。フルの会話セッションを複数 AI で並行するのと比較して桁違いに安い。

## 今後の検証課題

### 短期

- SO 誤指摘の検出メカニズムの標準化（レジストリ API での一次データ検証）
- 実行エージェントの逸脱プロトコル定義（プラン外判断のエスカレーション基準）
- コスト計測（SO 往復時間、人間オーケストレーション時間）

### 中期

- 破壊的変更を含むアップグレードでの同ワークフロー検証
- 新機能実装での計画/実行分離の再現性検証
- 生ログ抽出パイプライン（ExportTranscript → 意思決定抽出 → 構造化）
