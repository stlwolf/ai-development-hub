### フェーズ横断の因果関係: 変更の意図と結果

このスレッド（統合ハブ）での議論を通じて、各フェーズのフィードバックが次のフェーズのルール・フローに反映された。以下は主要な因果連鎖:

**1. 統合ハブ + フェーズ別子スレッドの分離構造**

- **原因**: キックオフ前の議論で「並列エージェントで分担できるか」「コンテキストを消費しないようにするか」というアイデアが出た
- **変更**: 「本スレッド = 統合ハブ（キックオフ起点 + 結論集約）」「子スレッド = フェーズ実装」の構造を採用。粒度はフェーズ単位（1a/1b の細分割はオーバーヘッドが大きいと判断）
- **結果**: 4フェーズを通じてハブスレッドのコンテキストは「キックオフ + 各フェーズの結論サマリ」に限定され、子スレッドの詳細がハブを圧迫しなかった。ハブでのフィードバック→CONVENTIONS.md 更新→次フェーズのキックオフという循環が成立

**2. INDEX.md 廃止 → CONVENTIONS.md への集約**

- **原因**: Phase 1 フィードバックで INDEX.md のドキュメント構造ツリーが実態とずれていた。「メンテが追いつかない」事実が判明
- **変更**: INDEX.md を廃止し、種別・命名規則・ドキュメントフローを CONVENTIONS.md に移管。正準ドキュメント（ツール非依存）→ 派生ビュー（Cursor rules 等）の構造を採用
- **結果**: CONVENTIONS.md がエージェント・人間共通の参照先として機能。Phase 3 以降「CONVENTIONS.md を参照でき教訓が活きている」というコンテキスト復元性能の評価

**3. ADR 昇格基準のフロー化**

- **原因**: Phase 2 フィードバックで「ADR 相当の判断がエピソードに埋もれた」。Phase 1 では ADR-001 が自然生成されたが、Phase 2 では protobuf アプローチ変更と better-sqlite3 バージョンアップが ADR 化されなかった
- **変更**: CONVENTIONS.md に4条件のフローベース昇格基準を追加。さらに Phase 3 フィードバックで「ADR 作成を Step の直後に独立 TODO として配置」ルールを追加
- **結果**: Phase 3 ではルールがあっても漏れた（ポストコンプリーションで発覚）。Phase 4 で **初めてフロー中に3件作成成功**。ルール制定→ルール不足判明→ルール強化→定着まで3フェーズかかった

**4. peer-ai-review gate の enforcement**

- **原因**: Phase 1 で gate が全て脱落。Phase 1 フィードバックでユーザールールに「gate は TODO に含めろ」を追加したが、Phase 2 でも効果なし
- **変更**: CONVENTIONS.md に gate 運用ルール（条件ベース記述、スキップ時の理由記載）を追加。さらに Phase 3 エピソードの提案で「gate のスキップ判断基準の明文化」を追加
- **結果**: Phase 3 で Gate 1 が実施（初）。Phase 4 で Gate 2回実施。**ルールだけでは効かず、CONVENTIONS.md への明文化 + エピソードでの遵守状況記録の二重構造で定着**

**5. スコープ変更（thread-done → 自動保存+CLI+カスタマイズ）**

- **原因**: Phase 2 完了後の機能要件整理で、機能の性質を A層（DB アクセス）/ B層（エクスポート・変換）/ C層（ワークフロー自動化）に分類。thread-done（C層）はコアに依存しない独立した関心と判明
- **変更**: ADR-004 でスコープ変更を記録。Phase 3 のキックオフを書き直し。VERIFICATION_MATRIX A-3 を差し替え
- **結果**: 外部ツール依存（git/gh）がなくなり、テスト容易性が向上。過去の Phase 1, 2 のコードへの影響はゼロ

**6. 3段階フロー（Agent→Plan→Agent）**

- **原因**: Phase 4 の最初の試行で、キックオフ MD だけ投げたところ peer-ai-review が実行されなかった。Plan mode の read-only 制約が `so-compare.sh` の実行を阻害。別スレッドの plan mode 調査で「プラン策定能力に差はない、実質的な価値はビルドボタンの利便性のみ」が判明
- **変更**: フェーズ実行フローを3段階に分離。Stage 1→2 に明示的な停止ポイントを設置（ユーザーが Plan mode に切り替える必要があるため）
- **結果**: Phase 4 で peer-ai-review がフロー中に自然実行。CP が `docs/plans/` に直接作成。キックオフ MD のみで初動が成功

**7. エピソードフィードバックセクションの構造化**

- **原因**: Phase 1, 2 のエピソードは自由形式で、フィードバック時に「プロセスとして何が機能した/しなかったか」を推測する必要があった。別スレッドでフィードバックフォーマットを議論
- **変更**: Phase 3 エピソードに構造化セクション（成果物一覧、想定外、規約遵守状況、コンテキスト復元性能、ナレッジ昇格、再利用可能知見、改善案）を導入
- **結果**: Phase 3, 4 のフィードバックが B 系列の検証データとして直接利用可能になった。「遵守できた/形骸化した」の二分構造が特に有効

### 改善アプローチの3層構造

本プロジェクトで見えた改善は、解決するレイヤーによって3つに分かれる。何かを改善しようとしたとき「どの層で対処するか」の判断基準になる:


| 層         | 何で解決するか                       | 具体例                                                 | 特徴                                                               |
| --------- | ----------------------------- | --------------------------------------------------- | ---------------------------------------------------------------- |
| **ツール層**  | リンター、スクリプト、自動化                | YAML フォーマット崩れ → カスタムリンター。Plan mode 制約 → 3段階フロー      | 一度作れば自動で効く。enforcement が確実                                       |
| **プロセス層** | CONVENTIONS.md のルール、フローへの組み込み | ADR 昇格基準 → Step 直後に TODO 配置。キックオフ突合 → エピソードの標準セクション | ルールとして書けるが、遵守は人間/エージェントの意識に依存。繰り返し改善して定着させる必要がある（ADR は3フェーズかかった） |
| **知見層**   | 分科会、アイデアメモ、別スレッドでの議論          | TDD 導入方針、ドメインテストの概念、レトロスペクティブ型ドキュメント                | まだ方向性が固まっていないもの。議論→アイデア→検証→プロセス層/ツール層に降りていく                      |


**従来の前提**: ツール層が最も確実だが作るコストがある → プロセス層で検証してからツール層に降ろすのが理想（例: ADR 昇格基準はプロセス層で3フェーズ検証 → 将来リンターで enforcement）。

**AI 時代の前提**: ツール層の「作るコスト」は圧倒的に低くなっている。本プロジェクト自体が Phase 1〜4 を1日で完走した実例。大規模タスクや数日かかるプロセスでも、並列で別の AI にツールを作らせる方が、プロセス層でルールを書いて定着を待つより早い場合がある。つまり **知見層で議論が出た時点で、検証用のツールを先に作り、それでプロセスを検証する** という逆順のアプローチも成立する。本プロジェクト（cursor-thread-tools）自体が「ドキュメントフローの検証のためにツールを作った」構造であり、この逆順パターンの実例でもある。

## 3. このプラグイン PJ の今後

### 機能拡張・改善候補


| 項目                    | 優先度     | 内容                                                                                            |
| --------------------- | ------- | --------------------------------------------------------------------------------------------- |
| CLI の独立化（Node.js 分離）  | 高       | 現状は `npm rebuild` が必要。ターミナルから手軽に呼べる形にしたい。スレッド内からコマンドやサブエージェント経由で「エクスポートして」「生ログから抽出して」と使えるのが理想 |
| テストコード（TDD）           | 次回機能追加時 | 独立タスクとしてはやらない。次の機能追加/修正時に TDD を採用し、protobuf decoder の unit test、CLI の integration test を入れていく |
| サブエージェントスレッドのフィルタ     | 中       | Phase 4 で `task-toolu_`* 形式の composerId を発見。`--filter` オプションで除外/抽出                            |
| 自動リンティング              | 中       | YAML frontmatter、ファイル命名規則の自動検証。ドキュメントフロー汎化にも貢献                                                |
| thread-done（Issue 投稿） | 低       | コマンドの組み合わせで当面は足りる。ツール化するなら独立 CLI として                                                          |
| リポジトリ分離               | 公開時     | 分離条件（安定動作 + 汎用 README + ドメイン固有情報なし）は達成済み。公開レベルになったら分離                                         |


### 運用への組み込み（段階的）

1. **まず使う**: スレッド完了時に手動で `cursor-thread-tools export` を実行。エクスポート結果をエピソード作成や生ログ抽出のインプットにする
2. **コマンド化**: Cursor コマンド（`thread-done.md` 等）やシェルスクリプトで、エクスポート→抽出→報告をラップ。スレッド内からワンアクションで呼べるようにする
3. **自動化検討**: 使ってみてどこを自動化すべきか見極める。キックオフ→実装→エクスポート→抽出の一連をどこまで人間の手間なしで回せるか

### 次の開発サイクルの進め方

- **同じリポジトリ、同じフローで継続**: 次の機能開発（CLI 独立化、サブエージェントフィルタ等）もこのリポジトリ内で、CONVENTIONS.md の3段階フローに従って実施する。`docs/plans/`, `episodes/`, `decisions/` にドキュメントが増えていく形
- **新しい統合ハブスレッドを立てる**: 現在の統合ハブスレッドはコンテキストが大きいため、次の開発サイクルでは新しいハブを立てて運用する。前サイクルのレトロスペクティブ（本ドキュメント）を初期コンテキストとして渡す
- **フローの定着確認**: Phase 1〜4 で確立したフローが「同じプロジェクトの次のサイクル」でも機能するかを検証する。惰性ではなく仕組みとして回るかの確認
- **リポジトリ分離との整合**: `extension/` のコードのみが分離対象。`docs/` は ai-development-hub に残るため、ドキュメントが増えても分離に影響しない。分離後のリポジトリでも同じ CONVENTIONS.md を適用

## Appendix: 分科会パターン — 並列スレッドによる有機的な知見生成

本プロジェクトの開発中、統合ハブスレッドと並行して複数の「分科会」的スレッドが自然発生した:


| 分科会スレッド         | タイミング        | 本プロジェクトへの影響                 |
| --------------- | ------------ | --------------------------- |
| フィードバックフォーマット議論 | Phase 2〜3 の間 | Phase 3 エピソードの構造化セクション導入    |
| plan mode 調査    | Phase 4 直前   | 3段階フロー（Agent→Plan→Agent）の確立 |
| TDD / ドメインテスト議論 | Phase 4 中    | テスト Step の実行環境明示、キックオフ突合の発想 |
| ドキュメントフォーマット議論  | Phase 2〜4 並行 | エピソードの自由形式と構造化の境界線          |


これらは**意図的に計画されたものではなく、作業中に思いついた疑問を別スレッドで気軽に聞いた結果**。実装の統合ハブが縦串（Phase 1→2→3→4 の直列進行）だったのに対し、分科会は横串として各フェーズに知見を注入した。

この「作業しながら横で議論し、結果をフローに戻す」パターンは:

- 人間の使い方としてのノウハウであり、ツールや仕組みで強制するものではない
- ただし「分科会の結論をどこに記録するか」は仕組み化できる（ideas/ にメモ → CONVENTIONS.md に反映 → 次フェーズのキックオフに含める）
- マルチエージェント構成で再現する場合、「調査エージェント」「レビューエージェント」が分科会の役割を担う可能性がある
