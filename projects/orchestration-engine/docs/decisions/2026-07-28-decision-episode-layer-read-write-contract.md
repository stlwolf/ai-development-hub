# episode の本文層と振り返り層を read/write 契約で分離する

## コンテキスト

本 decision は **後追いで書き起こしたものである**。判断そのものは 2026-07-27 に issue #284 と PR #285 で確定しており、本 doc の作成日は 2026-07-28 である。#284 の closure は「Decision / ADR 昇格は なし」と判定したが、owner との振り返りでその判定は不十分だと結論したため、確定済みの判断の正本を後から立てた。

情報源は #284 の成果物（episode・issue #284 のコメント群・PR #285・issue #217・PR に含まれる knowledge item 3件）に限った。復元できなかった箇所は埋めず、末尾の「復元できなかったこと」節に列挙する。棄却案の探索木だけは、成果物に無かったため owner 承認のうえリポジトリ外の raw log から復元した（同節に出所と強度を書く）。

### 何が問題だったか

4層ドキュメントのうち episode は、phase の違う2つのものを1つの文書と1つのスキルで抱えていた。作業中に随時追記する**本文層**と、PR レビュー後の closure でまとめる**振り返り層**である。

宣言としては分離していた。`episode-retrospective` は冒頭の「いつ使わないか」で「本文の書き方は担当外・本文に構造を課さない」と述べていた。しかし同スキルの Step 3「出力型 × 消費チャネル」は7行の表で各行に「書く内容」列を持っており、宣言と実体が食い違って見えた。

**当初の診断は誤りだった。** Step 3 の「書く内容」は本文への指針ではなく、**構造化フィードバックセクション（closure が書く層）に向けた手段指示**である。宛先が本文だったのではなく、宛先が明示されていなかった。したがって解は「表を本文側へ移す」でも「役割で割る」でもなく、**宛先の明示**だった。

### 実データで見えた本当の欠陥

設計論争が3周して「原典の読み方はどちらが正しいか」に帰着したため、実データで決着させた。ガードレール着地以降の episode 7本を、PR のコミット列と時刻幅で客観判定して検定した。

- **二重執筆は 6/6 で再現した。** 本文にある事実を closure で再度書いている。**単一コミットで書かれた2本でも起きている**ので、原因は書き手の作業スタイルではなく合格条件の設計にある。
- **why の欠落は出なかった**（追記型 0/3・#263 を含めて 0/4）。10時間23分・9コミットという最も追記型らしい個体でゼロだった。
- **肥大は測れていない**（heavy tier 偏りの交絡で対照群設計になっていない）。

そして**原因が特定された**。二重執筆は `episode-retrospective` の Step 4（closure の外部チェック）が構造的に要求していた。プロンプトが「実行ログにある失敗が**事実・失敗セクションから**選択的に省略されていないか」と問うため、合格条件が「closure 節に全件書かれていること」になっていた。pointer 方式は既に2例で試みられ、**2例とも外部チェックに「圧縮が lossy」と判定されて展開を要求されていた**。つまり契約だけを足しても Step 4 に潰される。

欠陥が出ていたのは**生産者側（書き手）ではなく消費者側（closure の合格条件）**だった。この一点が設計の向きを変えた。

## 検討した選択肢と、何で崩れたか

設計は4周した。案B（当初の推奨）→ gate 1 で 3/3 refuted → 案G → gate 2 で refuted → 案N → 絞った gate 2 で refuted → **案N′ で着地**。

棄却案の一覧を下表に置く。**復元の強度が2段に分かれるので列を分けた**。同格に扱ってはいけない。

### 案J の扱い（棄却ではなく部分採用）

closure の棄却案リストは案J を欠番にしていたが、**案J は棄却されていない**。定義と着地形を突き合わせると次のように分かれる。

- **採られた**: closure で事実を再執筆しない契約と、本文の durable anchor を closure が指す形。これは案N′ の中核そのものである。
- **採られなかった**: Step 3 の「書く内容」列を書き換える案（案N′ は Step 3 の表を動かしていない）。欠落補完に `reconstructed` を流用する案（案N′ は別マーカーを立て、`reconstructed` の流用は「語の意味の乗っ取り」として明示的に退けた）。

**この読みは本 decision の導出である**（#284 がそう述べた記録は無い）。ただし採否の実体は成果物だけで検算できる。

## 決定

1. **新スキルは作らない。** 当初 gate 0 で決めた「スキルを二つに割る」は、測定と反証を経て見直した。生産者側の欠陥（作業中に判断の why を捕まえられない）は実測でゼロだったため（追記型 0/3・#263 を含めて 0/4）、そこにスキルを立てる根拠が無かった。生産者側の着地点は委譲固定節への1文だけである。

2. **本文層と振り返り層を read/write 契約で分離する。** closure は本文と同じ内容を2度書かない。本文にある内容には pointer を付ければ足り、全文の再掲は要らない。1行の要約を添えるかは任意で、要約だけを置いて pointer を省くことはしない。本文に無い内容を closure で新規に書き起こすのは原則として避け、やむを得ず埋めた場合は必ず補完マーカーを付ける。マーカーの無い新規記述は契約違反とする。

3. **座礁点は動かさない。** Step 4 の確認対象は closure 節のままである。変えたのは「pointer は選択的省略ではない」という**合格の解釈だけ**。省略検出は事実・失敗セクションの列挙が担い続けるので落ちない。

4. **契約の適用範囲と、それを検査するゲートの範囲は別に決め、明文で書き分ける。** 契約は Step 3 の**全出力型**に及ぶ（二重執筆は「事実・失敗」だけでなく「決定と根拠」でも観測されたため）。一方 Step 4 が省略を突合する対象は**事実・失敗節のまま**で広げない。この非対称は読み手が自然に同一視するので、明文で書く。

5. **契約は将来のバリデータが検査できる述語の形で書くが、バリデータは実装しない**（soft のみの線）。述語は4本（closure の各項目が pointer か補完マーカーを持つ／pointer 先の見出しが同一ファイルに実在し一意である／episode が作業の期間にわたって複数の時点に分かれて更新されている／それを満たさない episode は冒頭に後追い宣言を持つ）。

6. **`reconstructed` を項目単位の補完マーカーに流用しない。** あれは「episode 全体が後追い再構成である」というファイル単位の宣言であり、意味が違う。項目単位には別マーカーを立てる。

## 根拠

### repo 自身の設計原則が、解の形を先に決めていた

設計原則の文書は、目的指示をフリーフォーム本文に、手段指示を構造化セクションに対応させている。同じ文書が「**両方をフォーマット化すると書きアンカーが潰れ、両方をフリーフォームにすると読みアンカーが潰れる**」と明記している。

Step 3 の「書く内容」（棄却した案と棄却理由を書け／トリガと機構と着地先を必須にせよ）は手段指示である。したがってこれを本文層へ移すのは、原典が「潰れる」と予告した方向だった。当初の推奨（案B）は**編集対象のスキル自身の決定根拠に反していた**。さらに同スキルの設計時の決定記録にも「内容セクションは必須テンプレにしない。根拠は監査 L2 / L3 と、手段指示は構造化セクション限定という設計原則」と残っていた。7型は当初から closure 側の出力契約として設計されていた。

この原典があるため、解は「移設」ではなく「宛先の明示」に決まった。

### 実測が、欠陥の所在を生産者側から消費者側へ動かした

前述の3軸の結果（二重執筆 6/6・why の欠落なし・肥大は測定不能）が決め手である。とくに次の2点が設計を動かした。

- **単一コミットで書かれた episode でも二重執筆が起きていた。** 書き手の作業スタイルが原因なら、一括執筆の個体には出ないはずである。出たので原因は合格条件の側にある。
- **pointer 方式は既に2例で試みられ、2例とも外部チェックに潰されていた。** 契約を足すだけでは足りず、Step 4 の合格解釈に手を入れる必要があると分かった。

あわせて、品質監査の R3 が「随時追記の選択ガードレールは何もしない（defer）。owner の検証と対照群データで再判断」と owner 受諾のうえ決めていた。その**再判断条件が満たされていた**ため、本ユニットで再判断を実施した。結論は「生産者側にスキルは要らない」であり、R3 の defer は結果として正しかった。

### 述語の向きを間違えた（案N が崩れた理由）

案N は Step 4 の確認対象を episode 全体へ移し、歯止めとして「closure の各主張が本文の解決可能なアンカーを持つ」という述語を置いた。gate 2 の2レーンが独立に同じ穴を指摘した。**向きが逆である。**

本文に失敗 A と失敗 B があり、closure が A だけを正しいアンカー付きで書いた場合、述語はすべて pass する。**B が省略されたことを検出できない。** closure に主張が1件も無ければ空集合に対して空虚に pass する。検査しているのは「書いたものが正しい先を指しているか」であって「書くべきものが書かれたか」ではない。

支えに使った3つの論拠も崩れた。「観点4つを保てば全文レビューにならない」は、一次文面が座礁点と skip 回避を一体で書いており観点数だけの話ではなかった。「読む範囲は実質変わらない」は、移すと探索空間がファイル全体になり pointer の解決と含意判定が乗るので成り立たなかった。「仕事は減る」は、二重執筆の停止が**書き手側**の利得である一方 Step 4 の設計理由は**外部チェック側**の摩擦であり、前者で後者を根拠づけていた。

したがって**座礁点を移さない**のが正しかった。省略検出は列挙が担い、契約は二重執筆の停止と導線の維持だけを担う。案N′ は反証レーン自身が出した代替で、これまでで最小の形である。

## 結果

### 何が変わったか

| 対象 | 変更 |
|------|------|
| `episode-retrospective` | read/write 契約（pointer 許容・補完マーカー）と述語4本を新設。Step 3 の宛先を構造化フィードバックセクションと明示。Step 4 に「pointer は省略ではない」を追加（**確認対象の範囲は不変**）。tier 判定のトリガに当たる出来事は作業中に記録する旨を1行追加 |
| `document-format.md` | 性質ガイドが本文層・構造化フィードバック節が振り返り層であると明示。同節の項目は形式の例示で正本はスキル側だと明記。ライフサイクル規範に pointer 前提を追記 |
| `doc-flow-guardrail` | 委譲固定節の「episode 義務」に生産者側の1文（追記は closure から指せる形で残す）。**本ユニットで唯一の生産者側の着地点** |
| `spec-card` | episode 行に作業中の追記の導線を1行 |
| カタログ | `episode-retrospective` の説明を実体に合わせて更新（**新スキル行は追加していない**） |

### plan と decision の層へ転用するときの形

**この節は本 decision が初めて明文化するものである。** #284 は転用形を宿題として立てたが（「作業中の層と事後の層という分け方を plan と decision にも同じ形で足せるようにする。ただし中身には触らない」）、成果物のどこにも答えを残していない。以下は #284 が決めた材料からの導出である。

転用の単位は「episode の本文と closure」という具体形ではなく、**型に依らない次の抽象**である。

> 一つの文書型が phase の違う2つの層を抱えるとき、(1) 作業中の層はフリーフォーム＋目的指示にする、(2) 事後の層は構造化＋手段指示にする、(3) 事後の層は作業中の層を再掲せず pointer で指す、(4) 手段指示の宛先を明文で書く。宛先が暗黙のままだと、同じ規定が層を越境していると読まれる。

(4) が #284 の実測から出た項目である。越境しているように見えた Step 3 は、実際には宛先が書かれていなかっただけだった。**宛先の不在は越境と区別できない**という点が、この抽象を単なる層分離論から一歩進めている。

plan と decision への当てはめは**観察であって決定ではない**。#284 が「今回は足さない」と限定した範囲を守り、実際の変更は行わない。

- plan には確定した計画（事後・構造化）と、作業中に判明した逸脱や discard の記録（作業中・フリーフォーム）が同居しうる。後者は spec の「方向転換の記録」節が既に受け皿を持っている。(3) に当たる規定は無い。
- decision には確定した判断が入り、探索と却下の詳細は discussion 側にある。spec の昇格義務の節が既に「重なる結論は pointer 化し、探索・却下側の詳細のみ残す」と書いており、**(3) と同じ形が episode より先に存在している**。

つまり (3) は decision 側で先例があり、(1) と (2) と (4) は plan / decision のどちらにも明文が無い。転用が成立しそうだという観察はここまでで、足すかどうかは別の単位が決める。

### 適用範囲（遡及しない）

追記判定の述語2本（作業の期間にわたって複数の時点に分かれて更新されている／それを満たさない episode は冒頭に後追い宣言を持つ）は、**#284 以降に作成される episode に適用し、既存の episode へ遡及適用しない。**

理由は2つある。第一に、既存 episode は述語が存在しない時期に書かれており、当時の散文規範には従っていた可能性がある。第二に、遡及して個別に直すとクラスの一部だけが是正され、残りが見えなくなる。既存分の扱いはクラス一括の掃除として別に判断する（#286）。

## 復元できなかったこと

後追いで書いた doc なので、自分の復元限界を宣言する。**成果物（episode・issue コメント・PR）だけでは decision を書き切れなかった。** これは本 doc を書く過程で得られた副次的な結果であり、read/write 契約が設計根拠を運べているかの試験結果でもある。

### 成果物から復元できなかったもの

- **棄却案10件の中身と棄却理由。** closure は記号を13個並べているだけで、内容が書かれているのは4案だけだった。上表は **owner 承認のうえリポジトリ外の raw log（Claude Code のセッション記録）から復元したもの**である。復元元は現存し再検証できるが、committed 層の外にあり将来失われうる。**本 doc からそのパスを durable な参照として指さない**（ローカル環境固有で他の読者からは解決できない）。
  - 復元の強度は2段に分かれる。**案A〜I は定義と棄却理由の両方**が当時の探索木の行として残っていた。**案J〜M は定義のみ**で、棄却理由は当時の記録に無い（上表の理由は後からの再構成である。例外は案L で、定義そのものが批評を含んでいる）。
  - 探索木は**1つのセッションに収まっていない**。案A〜I は実装側のセッション、案J〜M は統括側のセッションにあった。横断して集める必要があった。

### 測定値の食い違い（訂正済み）

「why の欠落」の値が成果物間で2通りあった。issue #284 のコメントと #217 のコメントは 0/6 と書き、episode と PR 本文は「追記型 0/3（#263 含め 0/4）」と書いていた。knowledge item が「訂正後は 0/6 が 追記型 0/3 になった」と明記しているので、**0/6 は型判定の方法を直す前の値**である。本 doc は訂正後の値を採る。訂正後に書かれた #217 のコメントが訂正前の値を運んでいた点は、本 doc の執筆中に指摘して修正された。

### 欠落が生まれた原因（記録）

**探索木が成果物に残らなかったのは、gate 6 の worktree 掃除が昇格義務を確かめずに実行されたためである。** 委譲固定節は「設計級の知見は closure と worktree 掃除の**前に** discussion / decision へ昇格する」と定めている。実際には子の closure は検証されたが、探索木が昇格されたかは確かめられないまま worktree が破棄された。同じ構造の欠陥（committed から作業層への参照が掃除で dead-end 化する）は過去にも扱われており、その**再発**である。

**ただし「不可逆」は言い過ぎだった。** 失われたのは committed 層への昇格経路であって、生データではない。raw log が残っていたので探索木は復元できた。

**この事実は昇格義務を不要にしない。** raw log はリポジトリの外にあり、gitignored 相当で、放置すれば消え、他の読者からは見えない。復元には owner の承認と、出所の切り分け（当時のセッションと後から書いたセッションの区別）と、持ち出してよい内容の線引きが必要だった。**昇格しておけば全部要らなかったコストである。** 昇格義務の価値は「唯一の記録だから」ではなく「参照可能な場所に置くから」である。

### 棄却案リスト自身の欠落（2件）

closure の棄却案リストは A / B / C / D / E / F / G / H / I / K / L / M / N で、**案J と案G′ が入っていない**。

- **案J** は棄却されていない。中核が採用案に採られている（前述）。
- **案G′** は案G に read/write 契約を足した中間案で、**反証を当てないまま案N / N′ に置き換わった**。リストからも漏れている。
