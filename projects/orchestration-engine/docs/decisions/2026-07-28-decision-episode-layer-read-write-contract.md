# episode の本文層と振り返り層を read/write 契約で分離する

## コンテキスト

本 decision は **後追いで書き起こしたものである**。記録している判断そのものは 2026-07-27 に issue #284 と PR #285 で確定済みで、#284 の closure は「Decision / ADR 昇格は なし」と判定したが、owner との振り返りでその判定は不十分だと結論したため後から正本を立てた。frontmatter の日付（2026-07-28）は本ユニットの着手日で、**実際の執筆は 2026-07-29 である**。

情報源は #284 の成果物（episode・issue #284 のコメント群・PR #285・issue #217・PR に含まれる knowledge item 3件）に限った。復元できなかった箇所は埋めず、末尾の「復元できなかったこと」節に列挙する。棄却案の探索木だけは成果物に無かったため、owner 承認のうえリポジトリ外の raw log から復元した（同節に出所と強度を書く）。

### 何が問題だったか

4層ドキュメントのうち episode は、phase の違う2つのものを1つの文書と1つのスキルで抱えていた。作業中に随時追記する**本文層**と、PR レビュー後の closure でまとめる**振り返り層**である。

宣言としては分離していた。`episode-retrospective` は冒頭の「いつ使わないか」で「本文の書き方は担当外・本文に構造を課さない」と述べていた。しかし同スキルの Step 3「出力型 × 消費チャネル」は7行の表で各行に「書く内容」列を持っており、宣言と実体が食い違って見えた。

**当初の診断は誤りだった。** Step 3 の「書く内容」は本文への指針ではなく、**構造化フィードバックセクション（closure が書く層）に向けた手段指示**である。宛先が本文だったのではなく、宛先が明示されていなかった。したがって解は「表を本文側へ移す」でも「役割で割る」でもなく、**宛先の明示**だった。この診断訂正は gate 1 の反証（3レーンが独立に同じ一次情報へ到達した）から出ている。

### 実データで見えた本当の欠陥

設計論争が3周して「原典の読み方はどちらが正しいか」に帰着したため、実データで決着させた。ガードレール着地以降の episode 7本を、PR のコミット列と時刻幅で客観判定して検定した。

- **二重執筆は 6/6 で再現した。** 本文にある内容を closure で再度書いている。**単一コミットで書かれた2本でも起きている**ので、原因は書き手の作業スタイルではなく合格条件の設計にある。
- **重複は「事実・失敗」型に限らなかった。** #263 は「決定と根拠」の4項目すべてが本文の再掲で、#262 の重複箇所も「決定と根拠」だった。この分布が後述の適用範囲を決めた。
- **why の欠落は観測されなかった**（追記型 0/3・#263 を含めて 0/4）。10時間23分・9コミットという最も追記型らしい個体でゼロだった。
- **肥大は測れていない**（heavy tier 偏りの交絡で対照群設計になっていない）。

そして**原因が特定された**。二重執筆は `episode-retrospective` の Step 4（closure の外部チェック）が構造的に要求していた。プロンプトが「実行ログにある失敗が**事実・失敗セクションから**選択的に省略されていないか」と問うため、合格条件が「closure 節に全件書かれていること」になっていた。pointer 方式は既に2例で試みられ、**2例とも外部チェックに「圧縮が lossy」と判定されて展開を要求されていた**。つまり契約だけを足しても Step 4 に潰される。

欠陥が観測されたのは**生産者側（書き手）ではなく消費者側（closure の合格条件）**だった。この一点が設計の向きを変えた。

## 検討した選択肢と、何で崩れたか

設計は4周した。案B（当初の推奨）→ gate 1 で 3/3 refuted → 案G → gate 2 で refuted → 案N → 絞った gate 2 で refuted → **案N′ で着地**。

棄却案の一覧を下表に置く。**復元の強度が2段に分かれるので列を分け、後から再構成した理由には理由本文の側にもその旨を書いた**。同格に扱ってはいけない。

| 案 | 内容 | 採否と理由 | 復元の強度 |
|----|------|-----------|-----------|
| A | Step 3 を丸ごと本文側へ移す | ❌ 外部参照2本が宛先を失う。設計原則 §5「両方をフォーマット化するな」と衝突 | 定義と理由の両方が当時の探索木に残存 |
| B | 役割で割り「書く内容」列を本文層へ移す（当初の推奨） | ❌ gate 1 で 3レーンとも refuted。案A と同じ衝突に加え、closure の内部契約が壊れる | 同上（成果物にも記録あり） |
| C | closure は1行申告のみにする | ❌ 1行申告は後続ユニットの領分で本ユニットのスコープ外 | 定義と理由の両方が残存 |
| D | Step 3 の行ごとに phase タグを付ける | ❌ 列を増やす方向で、監査 L2（足しすぎが蒸留を下げる）に不利。**ただしこれはトレードオフの指摘で、落とすに至った決定的理由は残っていない** | 定義と理由の両方が残存（理由は不完全） |

| H | 型 enum の正本を spec へ上げる | ❌ spec は大原則と routing のみを持つ二層構造に反し、spec 直書きを撤回した決定とも衝突。**ただし当時も「この線は絶対ではない」と留保が付いており、最終的に採否を分けた決め手は残っていない** | 定義と理由の両方が残存（理由は不完全） |

### 案J の扱い（採否は不明・定義の一部が採用案と一致する）

closure の棄却案リストは案J を欠番にしていた。**ただし「棄却されていない」と断定はできない。** 残っているのは案J の定義だけで、採否の記録も棄却理由も無いためである。案全体がいったん棄却され、後に一部の要素だけが別経路で再導入された可能性を排除できない。

言えるのは、案J の定義と着地形が次のように重なることまでである。

- **一致する部分**: closure で事実を再執筆しない契約と、本文の durable anchor を closure が指す形。これは案N′ の中核と同じである。
- **一致しない部分**: Step 3 の「書く内容」列を書き換える案（案N′ は Step 3 の表を動かしていない）。欠落補完に `reconstructed` を流用する案（案N′ は別マーカーを立て、`reconstructed` の流用は「語の意味の乗っ取り」として明示的に退けた）。

したがって正確な記述は「**採否は不明。構成要素の一部が N′ にも現れる**」である。この重なり自体は成果物だけで検算できる。

## 決定

1. **新スキルは作らない。** 当初 gate 0 で決めた「スキルを二つに割る」は、測定と反証を経て見直した。作業中に判断の why を捕まえられないという生産者側の欠陥は、実測で**観測されなかった**（追記型 0/3・#263 を含めて 0/4）。これは欠陥が存在しないことの証明ではなく、**観測範囲ではスキルを立てる根拠が得られなかった**ということである。生産者側の着地点は委譲固定節への1文だけとする。

2. **本文層と振り返り層を read/write 契約で分離する。** closure は本文にある内容を**再掲しなくてよい** — pointer を付ければ足りる。**これは再掲の禁止ではなく、再掲を要求しないという規定である**（意図の正本は #284 の実装記録にあり、述語も pointer と再掲の併存を違反にしていない）。1行の要約を添えるかは任意で、要約だけを置いて pointer を省くことはしない。本文に無い内容を closure で新規に書き起こすのは原則として避け、やむを得ず埋めた場合は必ず補完マーカーを付ける。マーカーの無い新規記述は契約違反とする。

3. **座礁点も、それを検査するゲートの範囲も動かさない。** この2つは別のものなので分けて書く。**座礁点＝事実・失敗セクション**（省略検出の母集団がここに列挙される）は据え置く。**Step 4 の確認対象の範囲＝closure 節**も従来どおりで広げない。変えたのは「pointer は選択的省略ではない」という**合格の解釈だけ**である。省略検出は事実・失敗セクションの列挙が担い続けるので落ちない。

4. **契約の適用範囲と、それを検査するゲートの範囲は別に決め、明文で書き分ける。** 契約は Step 3 の**全出力型**に及ぶ。一方 Step 4 が省略を突合する対象は**事実・失敗節のまま**で広げない。この非対称は読み手が自然に同一視するので明文で書く。
   - **時期の開示**: この非対称は案N′ 確定時点の判断ではない。N′ は pointer 許容を事実・失敗セクションの中身に置いており、**全出力型への拡大は実装中の gate 4 round 2 で「契約の適用範囲が狭すぎる」と外部レーンに指摘されて是正した結果**である。最終成果物としては正しいが、最初からそう決めていたわけではない。

5. **契約は将来のバリデータが検査できる述語の形で書くが、バリデータは実装しない**（soft のみの線）。述語は4本ある。
   - **P1 / P2 は pointer 契約の述語**（closure の各項目が pointer か補完マーカーを持つ／pointer 先の見出しが同一ファイルに実在し一意である）。契約に直接対応する。
   - **P3 / P4 は追記判定の述語**（episode が作業の期間にわたって複数の時点に分かれて更新されている／それを満たさない episode は冒頭に `reconstructed` を宣言している）。これは pointer 契約ではなく**ライフサイクル規範の側の軸**であり、P1 / P2 とは別物である。同じ節に置いたのは実装上の都合で、契約から導かれたものではない。
   - **P3 は入力を機械で取得できるが、判定規則が確定していない。** コミット数と時刻幅のどちらを閾値にするかは決めていない（5コミット・22分という中間の実例がある）。「機械検査できる述語」と書くときは、この未決を含んで読むこと。

6. **`reconstructed` を項目単位の補完マーカーに流用しない。** あれは「episode 全体が後追い再構成である」という**ファイル単位の宣言**で、項目単位の補完とはスコープが違う。流用すると、全項目に付ければ回避できる無制約の抜け道になる（gate 2 が「語の意味の乗っ取り」として指摘した）。項目単位には別マーカーを立てる。

## 根拠

### repo 自身の設計原則が、解の形を先に決めていた

設計原則の文書は、目的指示をフリーフォーム本文に、手段指示を構造化セクションに対応させている。同じ文書が「**両方をフォーマット化すると書きアンカーが潰れ、両方をフリーフォームにすると読みアンカーが潰れる**」と明記している。

Step 3 の「書く内容」（棄却した案と棄却理由を書け／トリガと機構と着地先を必須にせよ）は手段指示である。したがってこれを本文層へ移すのは、原典が「潰れる」と予告した方向だった。当初の推奨（案B）は**編集対象のスキル自身の決定根拠に反していた**。さらに同スキルの設計時の決定記録にも「内容セクションは必須テンプレにしない。根拠は監査 L2 / L3 と、手段指示は構造化セクション限定という設計原則」と残っていた。7型は当初から closure 側の出力契約として設計されていた。

この原典があるため、解は「移設」ではなく「宛先の明示」に決まった（決定2項・3項）。

### 実測が、欠陥の所在を生産者側から消費者側へ動かした

前述の測定結果が決め手である。とくに次の3点が設計を動かした。

- **単一コミットで書かれた episode でも二重執筆が起きていた。** 書き手の作業スタイルが原因なら一括執筆の個体には出ないはずである。出たので原因は合格条件の側にある（決定1項・2項）。
- **重複は「事実・失敗」型に限らなかった。** #263 は決定と根拠の4項目すべてが再掲、#262 の重複箇所も決定と根拠だった。**契約の適用範囲を全出力型にした根拠はこの分布である**（決定4項）。総数 6/6 だけでは範囲の決定を支えられない。範囲は「どこで欠陥が起きていたか」から決めるべきで、それを検査するゲートの都合から決めてはならない。
- **pointer 方式は既に2例で試みられ、2例とも外部チェックに潰されていた。** 契約を足すだけでは足りず、Step 4 の合格解釈に手を入れる必要があると分かった（決定3項）。

あわせて、品質監査の R3 が「随時追記の選択ガードレールは何もしない（defer）。owner の検証と対照群データで再判断」と owner 受諾のうえ決めていた。その**再判断条件が満たされていた**ため、本ユニットで再判断を実施した。結論は「生産者側にスキルを立てる根拠は観測されない」であり、R3 の defer は結果として正しかった。

### 述語の向きを間違えた（案N が崩れた理由）

案N は Step 4 の確認対象を episode 全体へ移し、歯止めとして「closure の各主張が本文の解決可能なアンカーを持つ」という述語を置いた。gate 2 の2レーンが独立に同じ穴を指摘した。**向きが逆である。**

本文に失敗 A と失敗 B があり、closure が A だけを正しいアンカー付きで書いた場合、述語はすべて pass する。**B が省略されたことを検出できない。** closure に主張が1件も無ければ空集合に対して空虚に pass する。検査しているのは「書いたものが正しい先を指しているか」であって「書くべきものが書かれたか」ではない。

支えに使った3つの論拠も崩れた。「観点4つを保てば全文レビューにならない」は、一次文面が座礁点と skip 回避を一体で書いており観点数だけの話ではなかった。「読む範囲は実質変わらない」は、移すと探索空間がファイル全体になり pointer の解決と含意判定が乗るので成り立たなかった。「仕事は減る」は、二重執筆の停止が**書き手側**の利得である一方 Step 4 の設計理由は**外部チェック側**の摩擦であり、前者で後者を根拠づけていた。

したがって**座礁点を移さない**のが正しかった（決定3項）。省略検出は列挙が担い、契約は二重執筆の停止と導線の維持だけを担う。案N′ は反証レーン自身が出した代替で、これまでで最小の形である。

### `reconstructed` を流用しない根拠（決定6項）

案N は欠落補完の印として `reconstructed` を流用しようとしたが、gate 2 が2点で退けた。第一に**意味の単位が違う** — `reconstructed` はファイル全体が後追い再構成であるという宣言で、項目単位の補完とはスコープが異なる。第二に**無制約の抜け道になる** — 全項目に付ければ補完の申告が形骸化し、契約が空になる。したがって項目単位には専用のマーカーを立てた。

### plan と decision へ転用するときの仮説（検証されていない）

**この節は本 decision が初めて書くもので、内容は検証されていない仮説である。** #284 は転用形を宿題として立てたが（「作業中の層と事後の層という分け方を plan と decision にも同じ形で足せるようにする。ただし中身には触らない」）、成果物のどこにも答えを残していない。以下は #284 が決めた材料からの導出で、**#284 が確かめたのは episode の本文と closure という1事例だけである**。規範として読まないこと。

転用の候補になりそうなのは、次の4項である。

1. 作業中の層はフリーフォーム＋目的指示にする。
2. 事後の層は構造化＋手段指示にする。
3. 事後の層は作業中の層を再掲せず pointer で指す。
4. 手段指示の宛先を明文で書く。

**各項の証拠強度は同じではない。** 一般化の可否を判断するときはここを見ること。

| 項 | 証拠 | plan / decision での検証 |
|----|------|------------------------|
| (1) | 設計原則は一般則として存在するが、phase 分離への適用事例は episode の1件のみ | 未検証・明文の先例なし |
| (2) | 同上 | 未検証・明文の先例なし |
| (3) | episode で実装され機能した（1事例） | 未検証。**下記のとおり decision 側の類似先例は同型ではない** |
| (4) | #284 の1事例のみ | 未検証・明文の先例なし |

(4) の出所を正確に書く。**これは実測から出た項目ではない。** 宛先明示という診断は gate 1 の反証（3レーンが独立に到達）と設計原則 §4 / §5、および `episode-retrospective` 設計時の決定記録から出ている。実測3軸は二重執筆・why の欠落・肥大であって、宛先の話ではない。#284 で観測されたのは「宛先が書かれていない手段指示が、越境していると誤診された」という1事例であり、**「宛先の不在は越境と区別できない」を一般命題として主張する根拠は無い**。

当てはめ先の見取りも、**同型性を示せていない**ことを明記する。

- plan には確定した計画と、作業中に判明した逸脱や discard の記録が同居し**うる**（これは推測である）。後者は spec の「方向転換の記録」節が受け皿を持つが、(3) に当たる規定は無い。確定した計画を「事後の層」と呼ぶ妥当性そのものも検証していない。
- decision について、spec の昇格義務の節に「重なる結論は pointer 化し、探索・却下側の詳細のみ残す」という規定がある。形は (3) に似ているが、**これは decision と discussion という別の文書型のあいだの pointer であって、「一つの文書型が2層を抱える」という前提とは違う。同型の先例ではない。**

したがって現状言えるのは「転用できるかもしれない」までである。**足すかどうかは別の単位が決め、その単位が改めて反証を通す。**

## 復元できなかったこと

後追いで書いた doc なので、自分の復元限界を宣言する。**成果物（episode・issue コメント・PR）だけでは decision を書き切れなかった。**

判断の骨格（何を決めたか・なぜそう決めたか・何が崩れたか）は成果物から復元できた。**復元できなかったのは主に探索の側**（棄却案の中身と落ち方）と、記録されなかった宿題への回答である。

### 決定の一部が実装中の是正であること

決定4項（契約の適用範囲を全出力型にする）は、案N′ 確定時点の設計判断ではなく**実装中の gate 4 round 2 で外部レーンに指摘されて是正した結果**である。決定節だけを読むと最初からそう決めたように見えるため、ここに開示する。決定として正しいことと、いつ確定したかは別である。

### 欠落が生まれた原因（記録）

**探索木が成果物に残らなかった直接の理由は、committed 層へ昇格されないまま worktree が破棄されたことである。** 委譲固定節は「設計級の知見は closure と worktree 掃除の**前に** discussion / decision へ昇格する」と定めている。実際には子の closure は検証されたが、探索木が昇格されたかは確かめられないまま gate 6 の掃除が実行された。同じ構造の欠陥（committed から作業層への参照が掃除で dead-end 化する）は過去にも扱われており、その**再発**である。

**ただし「不可逆」は言い過ぎだった。** 失われたのは committed 層への昇格経路であって、生データではない。raw log が残っていたので探索木は復元できた。

**この事実は昇格義務を不要にしない。** raw log はリポジトリの外にあり、gitignored 相当で、放置すれば消え、他の読者からは見えない。復元には owner の承認と、出所の切り分け（当時のセッションと後から書いたセッションの区別）と、持ち出してよい内容の線引きが必要だった。**昇格しておけば全部要らなかったコストである。** 昇格義務の価値は「唯一の記録だから」ではなく「参照可能な場所に置くから」である。

### 棄却案リスト自身の欠落（2件）

closure の棄却案リストは A / B / C / D / E / F / G / H / I / K / L / M / N で、**案J と案G′ が入っていない**。どちらも採否が不明なまま消えている。

**棄却案リストは採否の記録である。** 採用案に要素が流れ込んだ案と、反証を通っていない案を落とすと、後から探索の全体像が復元できなくなる。上表はこの2件を明示して補った。
