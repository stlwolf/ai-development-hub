# 常駐の見張りは session の外に置き、その沈黙は別の主体が検知する

> **後追いの昇格である。** 判断そのものは #336 のアークで gate 2 を通して確定し、PR #387 で実装・マージまで済んでいた。しかし closure 時に「判定までが closure・実行はゲート 6」と読み違えて昇格を先送りし、worktree が掃除された後に owner の指摘で書き起こした。**昇格は closure と掃除の前に行う**のが規約である（`document-format.md` §13.6）。この経緯自体は episode 側に記録がある。

## コンテキスト

委譲の親子で、送った指示・報告が相手の会話に着信しないことがある。送り手はそれを知る手立てを持たず、統括は届かないことを検知できずに子の画面を読みに行き、見張りの輪を手で組んでいた。pane を消すたびに張り直しが要った。

見張りを仕組みにするとき、**どこに置くか**が最初の分岐になる。素朴には統括セッションの中に常駐させたくなる。統括こそが結果を必要とする主体だからである。

しかし engine には同じ形で先に踏んだ単位がある。#301 は `oe-selfcheck` を定期実行へ配線する設計で、当初 statusLine を実行者にも描画器にも兼ねさせた。statusLine が止まれば表示は最後の文字列のまま凍り、経過時間は増えない。**凍った「42分前」と生きた「42分前」は読み手から区別できない。** 2 度目は定期実行の runner に鮮度判定を持たせた形で、同じ循環を作った。

## 決定

1. **常駐の見張りは session の外（launchd）に置く。** 統括セッションの中には置かない。
2. **その見張り自身の沈黙は、見張りとは別の主体が検知する。** 見張りは最終走査時刻を `latest.json` に書くだけで、その陳腐化を判定するのは別の verb（`oe-selfcheck` の `watchdog-freshness` 検査枝）である。
3. **検知できる故障の範囲を、共有している資源の数だけ狭めて書く。** 「別主体に分けたから検知できる」と一般化しない。
4. **「誰がいつその検査を実行し、誰が結果を読むか」＝出口は本決定では閉じない。** #301 の未決部分であり、閉じないまま自動化を名乗らない。

## 根拠

**(a) 停止を報告する主体が停止しうる当人だと、判定が循環する。** 「その報告が出ないことは何を意味するか」と問い、答えが「対象は健全」と「報告者が死んだ」の両方になるなら、報告者を分けていない。統括セッションの中に見張りを置くと、統括が死んだときに見張りも死ぬ。**#336 が守りたかったのはまさに「統括が死んで報告が虚空へ消える」経路**なので、そこに置いては目的を満たせない。

#301 の plan はこの循環を一次記録として持つ。「停止を判定する主体が停止する当人（同じ runner）なら、止まったときに誰も報告できない。初版の本文は『実行側が黙って止まればスナップショットが古くなって見える』と書きながら、その古さを見るのを同じ runner に置いていた」と、gate 2 の指摘を受けて改めた経緯が残っている。**同じ形を 2 つの単位が独立に踏んだので、領域固有の癖ではなく一般形として扱う。**

**(b) gate 2（設計SO・弱・2 レーン・1 本ずつ）が、当初案の沈黙検知を不成立にした。** 初版は `oe-selfcheck` に検査を足すだけで「別主体が拾う」と書いており、レビューは「誰がいつ実行し、その結果を誰が読むかが無い。#301 がまさに『出口のない検知』で park されたため、同じ穴を再生産している」と指摘した。**この指摘があって初めて、機構（別主体が読む）と出口（その主体が動く）を分けて書いた。** 本決定の 4 番目はその線引きである。

**(c) 同じレビューが、名前の衝突も検出した。** 当初は合成 verb を `oe-watch` と呼ぶ設計だったが、#301 が `oe-watch` を「既存 verb を `--json` で呼び `latest.json` を原子更新し、相互鮮度監視する汎用ランナー」として予約済みだった（`plan-301` の該当節）。**別契約に同じ名を与えると、統合する段になって設計が 2 つ重なる。** 名を使わず、検知は `oe-confirm` に持たせ、ランナー統合は #301 に委ねた。

**(d) 相互監視が保証するのは片系だけが止まる故障までである。** #301 の episode から収穫された negative knowledge（`01KZVHE0KJ12W3NG6A4R0WSWS4`）が、2 本を別の plist に分けても実体・状態の置き場・権限・配置場所を共有しているかぎり共通原因の故障では同時に止まる、と明記している。残るのは実体の消失・権限の変更・状態の破損・両方の登録解除・スケジューラ自体の停止である。**「スケジューラが止まったときだけ両方死ぬ」は誤りである。** 本決定の 3 番目（共有している資源の数だけ範囲を狭めて書く）はこの item をそのまま適用したものである。

### 棄却した置き場

- **統括セッション内の常駐（`Monitor` の輪を仕組み化する形）**: (a) で棄却。統括が死ぬと見張りも死ぬ。加えて pane を消すたびに張り直しが要るという運用の実測がある。
- **見張り自身に鮮度を判定させる**: (a) と同じ循環。#301 が 2 度踏んだ形である。
- **`oe-watch` という名の合成 verb を新設する**: (c) で棄却。#301 の予約と衝突する。

## 結果

- 送信の到達照合・子ペインの消滅・report 新規の検知は `oe-confirm`（read-only）が持ち、launchd から回す。plist テンプレートは `projects/orchestration-engine/launchd/` に在る。
- `oe-selfcheck` に `watchdog-freshness` が加わった。`latest.json` が無ければ `indeterminate`（**`ok` ではない**）、古ければ `broken`、新しければ `ok` の 3 値で返す。「記録が 0 件だから異常なし」と読ませないための 3 値である。
- **輪は閉じていない。** `oe-selfcheck` の定期実行は #301 が park 中で、人が打つまで動かない。本決定が担保するのは「別主体が検知**できる**」ことと、その陽性対照（片方の job を止めるともう片方が陳腐化を報告する）までである。**常時自動で拾うとは言わない。**
- 通知については別の制約が乗る。送出の成功を到達と読まない（#330 の型）、durable な signal（stdout と `latest.json`）を正本にする、送出成功で恒久抑止しない。**到達そのものの保証は #330 に残る。**

## 再判断の条件

- #301 が revive され、ランナーと出口が確定したとき。本決定の 4 番目（出口を閉じない）はそこで更新されるべきである。
- 共通原因故障が実際に起きたとき。(d) の範囲記述を、観測した故障の形に合わせて狭めるか広げる。
