# owner への問いは統括ごとに1枚の判断ボードで受けて回収する

## コンテキスト

2026-10-19、#428（人向けのページの形）の質問フェーズで、owner は次の流れを挙げた。子を2〜3つ並列に任せて答えを待つあいだ、owner は別の作業をして画面を見ない。戻ると、問いがいくつか重なって流れていて、答えたものと答えていないものが混ざる。#428 はページの形と部品だけを決め、いつ作り・更新し・止めるかを #466 に分けた。

材料を集めると、10-17〜10-23 に owner に判定を求めたページは15枚で、ゲートで子が止まったときのページはすでに毎回作られていた（discussion の 2.1 節）。答えた場所が分かる14枚のうち12枚で、会話が答えの経路に入っていた。ページの外では、単独の問い・マージの依頼・知らせが会話に流れていた（2.2 節）。

owner は判定を2回に分けて行った。1回目（26問・判定ページ）は、推奨どおりが21問、別の案が4問（Q1・Q3・Q18・Q20）、未回答が1問（Q7）だった。owner は Q3 の補足で、第一目的を次のように述べた。

> 本質的に求めたいのは、そのいっぱい複数あって並列で動いてるタスクに迷わない、対応することを迷わない認知負荷が減るっていうのが第一目的なんで、それを第一に、Q1もそうだけど、この上のQ1、Q2もそうだけど、そこを第一に考えたいね。

Q1 の補足では、毎回ページを作るとタブが重なって最新を探すことになること、2つの issue の答えの時期がずれると答えたページが別々になること、「判断付きの見取り図だったらどうするの」を挙げた。子はこれを受けて、場面ごとの流れ図で案を比べ直した（discussion の13節）。2回目（9問・Q27〜Q35）は、統括が試しに作った判断ボードの上で回収した。Q32 が「#536 に入れる」（推奨とは別の選択肢）、Q28 は Q27 で推奨を選んだので答えが要らず、ほかの7問は推奨どおりだった。

## 決定

各決定の末尾の括弧は、もとになった問いである。問いの文面は、owner が答えた判定ページのカードの題と推奨の中身による。owner の補足（原文）があるものは、要点を添えた。

1. **owner への問いを載せるページは、統括ごとに1枚の判断ボード（html-one-pager の種別 `board`）を使い続ける。中に「いま決めること」「owner への依頼」「動いている作業」「最近決まったこと」を置く。答えた問いは「最近決まったこと」の表へ移す。**（Q27。Q1 の補足を受けて詰め直したもの）URL は1つなので、owner は最新のページを探さなくてよい。
2. **使い続ける1枚は、owner に案内を送ってから答えが来るまでは、進み具合だけの変化（PR を作った・段が移った）では出し直さず、次の出し直しにまとめる。止まる問いが来たときだけ、「追加」の印を付けて出し直す。**（Q29）このあいだに急がない問いが届いても、それだけでは出し直さず、次の出し直し（owner の答えを回収したあとか、止まる問いが来たとき）を待つ。これはカードの「止まる問いが来たときだけ出し直す」から導いたもので、決定7 の段6・決定10 より、答えを待つあいだは決定2 を先に当てる。待つあいだ、その問いをページのデータに足しておくか別に持っておくかは、カードに無かったので決めていない（「決めていないこと」）。
3. **回収したあとの正本は、表にあるあいだは「最近決まったこと」の表の行、表から消したあとは台帳の「回収した」の行とする。ページに保存された答えは、古いタブから書き換えられるので正にしない。**（Q30）#478 の decision の決定4（判断ボードでは表の行を正とする）に、「表から消したあとは台帳を正とする」を足す。
4. **「最近決まったこと」の表には、直前の回収で決まったものだけを出し、次の回収で入れ替える。**（Q31）owner は Q1 の補足で「過去の判断は別に残さなくていい」と述べている。
5. **答えを待つページは、統括ごとに同時に1枚までにする。**（Q2）owner の補足は「1枚でいいけど、Q1 とも関係してくる」である。Q2 のカードの推奨にあった「別の作業の問いが来たら束に作り替える」は、決定1 で1枚の判断ボードになったので当たらない。
6. **最初に URL を伝えたあとに足した問いには「追加」の印を付け、「全部推奨」は印の無い問いにだけ当てる。追加の問いは、ページで選ぶか名指しで答えてもらう。**（Q4）1枚を使い続ける形で印をいつ外すかは、カードに無かったので決めていない（「決めていないこと」）。
7. **問いが届いたとき、ページに載せるかを8段の順で判断する。** 1 承認済みの plan や brief を変える問いなら、owner の再承認の問いにする。ここでの「変える」は、委譲固定節の「承認のあとに plan が変わるとき」の「変更」の級（step を削る・要件を弱める・ゲートを飛ばす・終端を書き換える・新しい作業義務や設計判断や対応範囲を足す）を指す。「記録」と「補正」は、いまの決まりのとおり再承認に回さない（discussion の 1-3。カードの文はその要約である）。2 owner が前もって統括に任せた範囲で決められるなら、統括が決めてページに載せない。3 表示を見て判断してもらう問いなら、サンプルを先に直して見せる。4 依頼や知らせなら、問いにせず依頼の表へ出す。5 一覧から行を選ぶ問いなら、決定12 のとおりにする。6 答えを待っている問いがページにあれば、そこに足す。7 答えが無いと先へ進めない問いなら、1件でも載せる。8 残りは、次に載せるまで待たせる。（Q5。カードの段4 の「見取り図の手番の表」、段5 の「別のページにする（Q3）」、段6・7 の「ページがあるか」「ページを開く」は、Q6 の用語と決定1・12 に合わせて言い換えた）
8. **マージなどの依頼と知らせは、問いのカードにせず「owner への依頼」の表に出す。値の依頼は、関係する問いの補足欄か会話で受け取る。「手番」という用語は使わない。**（Q6。owner の補足「手番の用語はやめて。依頼とかでもいいんでは」）ただし、マージの依頼は、あとから決めた決定9（Q35）のとおり表に出さない。表に出すのは、マージのほかの依頼（画面を開く・値を貼るなど）と知らせである。
9. **マージの依頼は、ページでは追わない。owner が会話で「マージした」と言うのを受けて、統括が origin で確かめる。**（Q35。origin で確かめることは、Q35 のカードの推奨の中身に書かれていた。前の Q7 は未回答で、補足に「直接、だいたい直接言ってんだけど…別にシート経由で追う必要はない気はする」とあった）
10. **owner への問いを2件たまるか、答えが無いと子か統括が先へ進めない問いが1件出たら、ページに載せる。待たせた問いは、次に載せるときに必ず載せる。待っていることは判断ボードに出す。時間の上限は置かない。**（Q8。カードの「ページを開く」「見取り図に出す」は、決定1 で1枚の判断ボードになったので、「ページに載せる」「判断ボードに出す」と言い換えた）
11. **owner が答えるページを出すのは統括だけにする。子の問いは統括が読み、統括が自分で決めるか owner に回すかを選り分ける。子は、ページのカードのデータ（JSON・送り元つき）を問いの正本として書き、Markdown は書かないか、カードのデータから作る。統括は、そのデータに自分の判断も足してページに載せる。**（Q9・Q10。Q10 の補足「その上で親の判断も入れるっていう感じだよね」）
12. **答え方の形（問いのカードか、一覧から選ぶか）ではページを分けない。分けるのは、作業のまとまりか量（たとえば候補が40件ある一覧）のときだけにする。一覧から行を選ぶ問いを同じページに置けるようにする html-one-pager の直しは、別の issue にせず #536 に入れる。直しが入るまでは、一覧から選ぶ問いだけ別のページにし、判断ボードの問いからリンクする。**（Q34・Q32・Q33。Q32 は #536 に入れる選択肢を選び、Q33 も推奨を選んだ。Q33 のカードは「Q32 で issue を起こすときに要る」と書いていたが、#536 に入れても直しが入るまでの期間は残るので、そのあいだに当てる。Q3 は1回目で別の案になり、2回目のこの3問で決まった。Q3 の補足「回答形式でページを分けるのを基本にはあんまりしない方がいい」）
13. **出来事を足していく専用の台帳を、作業層（git の外で、3日で消えない場所）に1つ置く。問いが出た・版を出した・版を伝えた・答えた・回収した・子へ送った・子が受け取った、を1行ずつ足す。引き継ぎ文書は台帳の場所を書く。**（Q11。補足「一旦別にして専用のを作っていく感じ」）
14. **答えを集めて渡すまでを6段の手順にする。** 1 owner の発話が、どのページのどの問いへの答えかを決める。2 答えを集める前の問いなら、owner が「全部推奨」と言っても、ページに保存された答えを読む。3 問いごとに答えを正本に写す。4 答えた問いを表へ移して出し直す。5 答えを、それを使う先（子・承認の記録・認識合わせの確定版）へ渡す。6 各段のあとに台帳に足す。表へ移した問いの保存された答えは読み直さない。（Q14。補足「基本見に行くでいいか」。段3・4・6 は、カードの推奨では「`answers` に写す」「回答済みで作り直して止める」「止めたページは読み直さない」だったが、決定1・3 で判断ボードを使い続けるので、正本は表の行と台帳、止める代わりに表へ移す形になる。この言い換えは決定1・3 から導いたもので、owner が Q14 で直接決めたことではない）
15. **会話の答えは、どの問いへのどの答えかが一通りに決まるものだけを受け付け、owner の言葉を補足に残す。一通りに決まらなければ未回答のままにし、統括が読み取った内容を1行で返して確かめる。推奨と食い違う一括の答えは、外向きの操作の前に1行で確かめる。**（Q15。補足「そっちの優先度は高い。ただ、意図は汲み取れない場合とかは、まあ聞いてくれれば」）
16. **ページの答えと会話の答えが食い違ったら、会話で名指しした答えを採り、食い違ったことを1行で返す。**（Q16）html-one-pager の「ページの答えを正とする」の文を直すことになる。
17. **答えを渡した先が受け取ったことまで、統括が確かめる。** 子へ送ったら、子の返事か受領印で確かめる。plan の承認（ゲート3）なら、承認の記録を書いてから子へ送る。認識合わせなら、確定版を issue に投稿してから、そのコメントの URL を子へ送る。途中で止まったら、台帳の最後の出来事から続ける。owner が子のペインに直接答えたときは、子が直接受け取ったものとして台帳に記録し、統括は自分が受け取った承認として中継し直さない。（Q17）
18. **判断ボードの申し送り2つ（#478 からの申し送り）は、決定1 で判断ボードを使うので、この流れの手順に入れる。** 回収のたびに、答えのある問いをすべて「最近決まったこと」の表へ移す。値の依頼は依頼の表に出し、補足欄か会話で受け取って、求めた側へ渡す。（Q18。1回目は「Q1 が決まってから」で別の案になり、Q27・Q30・Q31 の答えで discussion の 13.6 のとおりに決まった）
19. **未回答の問いは、同じ1枚に残るので、ふだんは次のページへ移さない。新しい URL で作り直すときだけ、同じ key のまま移し、引き継いだことを書き、引き継いだ件数を会話の1行で伝える。**（Q13。1回目は推奨どおりで、補足「Q1〜3 の決め方で変わる」。Q27 の答えで 13.6 のとおりに決まった）
20. **見取り図は統括ごとに1枚にし、統括が交代しても同じ URL を使う。作業の表は、issue・いまの段・子の状態・4層の文書・SO のまとめ・PR を持つ。更新は、統括に見える出来事（問い・答え・SO の終わり・段の移り・子の停止・交代・依頼）のたびに行う。終わった作業は「終わった」の表へ移す。**（Q19。表の中身と更新の決め方の細部は #539 で決める）決定1 で、見取り図は判断ボードの「動いている作業」として同じページに入る。カードの作業の表の「番号」の列は、`board` の番号の列が `Q<数字>` に限られるので置けず、issue の列で指す。種別は Q19 のカードが前提にした `map` でなく `board` になる。答えを待っているページへのリンク（Q12）は、同じページなので要らなくなり、別のページ（一覧から選ぶ問いのページ・SO のまとめ）へのリンクだけが残る。この段落は決定1 から導いたことで、owner が Q12・Q19 で直接決めたことではない。
21. **SO のまとめをいつ作るかは、この issue では決めない（保留）。**（Q20）owner の補足の要点は、SO の側が人向けの成果物まで持ち、それを上げて判断のページにつなぐ形もありうること、SO をオーケストレーションから独立させるか単独で育てるかの方針次第なので、こちらにきっかけを作るのはその方針が見えてからにすること、ただし engine の仕組みとしての可視化は必ず詰めること、である。
22. **#329 に「`so-compare` の出力も対象に入れるか」を申し送る。**（Q21）統括が #329 にコメントした（https://github.com/stlwolf/ai-development-hub/issues/329#issuecomment-6382425256 ）。
23. **実装は、統括が守る規則を先に作り、自動で動く道具をあとに足す。道具は、問いがたまったのにページに載っていないときに統括へ知らせる hook と、子の問いのデータからページのデータを作る verb である。**（Q22。カードの「答えを待っているページが無いとき」「束のページのデータ」は、決定1 に合わせて言い換えた）
24. **「いつページに載せるか」の規則は新しいスキルに置き、子から問いが届いた・SO が終わった・owner に判断を求める、といった場面で読み込まれるようにし、doc-flow-guardrail からも1行で指す。ページの扱いの一般の決まりは html-one-pager に置く。**（Q23）新しいスキルを engine の部品にするかハーネスに置くかは、owner が起こした #537（engine を独立したパッケージにしていく）を見越して、#538 で決める（Q23 の補足「依存関係をいつかは整理したいので…どこに置くかは決めたい」）。
25. **実装を4つの単位に分け、U1 → U2 → U4 の順で作る。** U1 は #538（判断ボードでの受け付けと回収の手順）、U2 は #539（作業の表と4層の文書の列）、U4 は #540（出し忘れと取りこぼしを知らせる道具）で、U3（SO のまとめ）は #329 の側に置く。U1・U2・U4 は同じ新しいスキルに足すので、同時には進めない。（Q24・Q25）
26. **owner が統括に前もって任せた判断の範囲を、1か所にまとめる issue を別に起こす。** #541 である。（Q26）

## 決めていないこと

- **SO のまとめをいつ作るか**（決定21）。SO をオーケストレーションから独立させるかの方針が見えてから決める。
- **新しいスキルを engine の部品にするか、ハーネスに置くか**（決定24）。#538 で、#537 を見越して決める。
- **ログをもっと厳密に分けていくこと**（Q11 の補足「ログのもうちょっと厳密に分けていくのが増えていくかもしれんけど、まあそれはちょっと別の話」）。この issue では扱わない。
- **Q28（判断のページだけを使い続けるなら、答えた問いをどう見せるか）**。Q27 で推奨の形を選んだので、答えていない。
- **答えを待つあいだに届いた急がない問いを、ページのデータに足しておくか別に持っておくか**（決定2）。#538 で決める。
- **使い続ける1枚で「追加」の印をいつ外すか**（決定6）。discussion の 13.4 は「回収のあとに残りの問いを列挙した案内を送ったときに外す」を提案しているが、カードには無かった。#538 で決める。
- **子が多くて1枚に収まらないときの扱い**。Q27 のカードの推奨の理由は「子が多いと1枚が長くなる（そのときは判断のページだけを使い続ける案のほうがよい）」と書いている。どこで切り替えるかは決めていない。#538 の実物で、1枚の長さと owner が迷ったかを見る。
- **html-one-pager に「更新を止めた」状態を足すか**。#539 で決める。
- **開いた問いが0枚の判断ボードに、番号の列の無い表だけを置けるようにするか**。#536 で一覧から選ぶ問いの直しとあわせて決める（統括の #536 へのコメント）。それまでの手当ての候補として、discussion の 13.5 は「表を空にしない」と「最初は見取り図（`map`）で作り、最初の判断で判断ボードに作り替える」を挙げているが、どちらを採るかは決めていない（#538 で決める）。
- **判断ボードのページそのものを台帳から作るか**。#540 で決める。
- **`so-compare` の出力を #329 の対象に入れるか**。#329 で決める。

## 根拠

- **1枚を使い続ける理由（決定1・2・5・20）。** owner が第一目的に挙げた「並列の作業で迷わない」で比べると、見るページが1枚に収まるのは判断つきの見取り図だけである（discussion の13節の場面 c）。毎回作る案（前の推奨）は、答えるのに開くのは1枚でも、残るページが回ごとに増え、どれが最新かを探すことになる（場面 a・b）。判断のページだけを使い続ける案とは、場面 a・b・d では同じで、違いは進み具合と判断のあいだを移らなくてよいことにある。その代わり、進み具合の変化でもページを出し直すので、答えている途中で版が変わる（場面 f）。決定2 はそれを受けるために置いた。子が多いと1枚が長くなる（場面 i）ことは、決めていないことに残した。
- **正本を表の行と台帳にする理由（決定3・4）。** #478 の決定4 は、判断ボードでは回収した答えを表の行に書き、その行を正とし、`answers` を使わないと決めている（#428 の decision の追補）。owner が過去の判断をページに残さなくてよいと述べたので、表の行は次の回収で入れ替える。そのあとの正本が要るので台帳にした。ページに保存された答えは、回収のあとも古いタブから書き換えられるので正にしない（html-one-pager の「回答済みにして出し直す」節の4）。
- **答え方の形で分けない理由（決定12）。** owner の補足は、答え方の形で分けるのを基本にしない、混ざってよいものと混ざってはいけないものは意味で分ける、量が多いなら分けてよい、である。いまのスキルでは、一覧から選ぶ問いは `pick` の種別にしか置けない（`build.py` が E-K2 で止める）。同じページに置くには、置ける種別・番号の列・表の結び付き・描画・回収の直しが要る（discussion の 13.5 の9項目）。owner は、これを別の issue にせず、問いのカードの書き方と答えたカードを畳む直しを持つ #536 に入れると決めた。同じファイルを直すので、1つの issue で進めると衝突が無い。
- **問いの受け付けと回収の手順の理由（決定6・7・10・14〜17）。** 1回目の推奨どおりで決まった。判断の順は、軽い扱い（統括が決める・カードにしない）に落としたくない形を先に除く順で、承認済みの対象を変える問いを先頭に置いたのは、ゲート2 の設計SO が「承認のあとに対応範囲を足す問いが、任せた範囲の例に似ているだけで統括の判断に落ちる」形を見つけたからである（discussion の 1-3）。回収のたびに保存された答えを読むのは、「全部推奨」と言われたときに読まない運用が、ページに保存した答えを捨てうるからである（2.5 節・6節）。
- **依頼と知らせをカードにせず、マージを追わない理由（決定8・9）。** 依頼と知らせは答えを選ぶ問いではない。マージは owner が会話で直接言い、統括は済まないと先へ進まないことが多い（Q7 の補足）。
- **規則を先にする理由（決定23・24）。** いまの手順では、ページの公開と保存された答えの読み取りは統括のセッションの中の道具で行っていて、engine の verb には無い。道具が受け持てるのは「知らせる」と「データを作る」までである（discussion の 2.5 節・論点8）。「いつ載せるか」の規則を html-one-pager に置かないのは、html-one-pager がページを作るときにだけ読み込まれ、作ると決める前の統括に届かないからである。

## 結果

- 実装は #538（U1）から始める。#538 は、判断ボードでの受け付けと回収の手順を新しいスキルに書き、同じ単位で、決定を打ち消しうる既存の規則を直す。打ち消しうる規則は discussion の6節にあり、主なものは次のとおりである。
  - 出力の型 `readable-conversation` の「判断を求めるときは選択肢と推奨を書く」。判断ボードがあるときの例外が要る。
  - html-one-pager の「答えの場所はページの1つだけ。会話で答えを1件ずつ受け取る形は使わない」と「ページの答えを正とする」。決定15・16 に合わせて直す。
  - `doc-flow-guardrail` の委譲固定節の問いの形（今は brief の可変節にしか無い）。決定11 に合わせて書く。
- 統括の引き継ぎ文書の「owner が全部承認と言ったら保存先を読まなくてよい」は、決定14 と食い違う。引き継ぎ文書は統括の作業層なので、統括が直す。
- #536 は、一覧から選ぶ問いの直しを入れて題を改めた（統括のコメント https://github.com/stlwolf/ai-development-hub/issues/536#issuecomment-6382424815 ）。#536 と #538 は html-one-pager を直す。
