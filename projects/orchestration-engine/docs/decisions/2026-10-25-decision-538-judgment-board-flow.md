# 判断ボードの流れは engine の部品のスキルに書き、待たせた問いは台帳で持ち、「追加」の印は回収のあとの案内で外し、台帳には書き足す道具を足す

## コンテキスト

#466 で owner は、owner への問いを統括ごとに1枚の判断ボードで受け付けて回収する流れを決めた（decision の決定1〜26）。#538 は、その流れを新しいスキルに書く単位（#466 の U1）である。#466 の decision の「決めていないこと」のうち4つ（スキルの置き場・答えを待つあいだの急がない問いの持ち方・「追加」の印をいつ外すか・子が多くて1枚に収まらないときの扱い）が、#538 に回っていた。台帳の形を文の決まりだけにするか、道具を足すかも、#538 の plan で決めることになっていた（#538 の確定版）。

子は plan に7つの問い（GATE 3）を書き、統括がそれを判断ボードの Q41〜Q47 として載せた。owner は 2026-10-25 に、7つともページで推奨を選び、会話でも「全部推奨で問題ない」と答えた。補足は無かった。統括は保存先を読み、会話の答えと一致することを確かめた。

## 決定

各決定の末尾の括弧は、もとになった問いである。問いの文面は、owner が答えた判断ボードのカードの題と推奨の中身による。

1. **判断ボードの流れを書くスキル `judgment-board-flow` は、orchestration-engine の部品として扱う。** 文書は engine の木に置き、スキルの位置づけに engine の部品であると書き、#537 でファイルを動かす段の対象に入れる。ファイルの置き場は、今の配り方のまま `canonical/skills/judgment-board-flow/` である（#537 が最後にファイルを動かす順で進めるため）。スキルの文は hub の中のパスに依らない形で書き、`oe-*` は `doc-flow-guardrail` の verb 解決規約で呼ぶ。hub の issue 番号と具体例は、スキルの末尾の補足の節に置く。（Q41）
2. **答えを待つあいだに届いた急がない問いは、判断ボードのデータに入れず、台帳に「待たせた問い」として、問いのファイルのパスと一緒に持つ。次に出し直すとき（回収のあとか、止まる問いが来たとき）に、閾値に関係なく必ず載せる。** 閾値に届かずに待たせる問いと同じ台帳で持ち、待たせる理由を `next_publish` と `threshold` に書き分ける。判断ボードのデータは、owner が見ているページと、すぐ次に出す直しだけを持つ。（Q42。#466 の決定2 の「決めていないこと」）
3. **「追加」の印は、題の頭の「追加: 」で付け、答えを回収したあと、残りの問いを案内する出し直しのときに外す。** 案内を送った時点で開いている問いは、すべて印の無い問いになる。一括の答えを当てる範囲の正本は、台帳の最後の案内の記録（`announced` の `bulk`）で、題の印は owner に見せる印である。（Q43。#466 の決定6 の「決めていないこと」）
4. **子が多くて判断ボードが長くなったときに別のページに分ける点は、いま決めない。** 「いま決めること」を作業ごとの節に分けて止まっている作業を先に置き、答えた問いは回収するまで畳まれる表示で受ける。出し直すたびに長さを台帳に残し、作業の表を足す #539 で、その記録と owner の声を見て決める。それより前に owner が長いと言ったら、統括が分け方を owner に問う。（Q44。#466 の「決めていないこと」）
5. **台帳は1行1出来事の JSON（JSON Lines）にし、スキルのフォルダに、検証して書き足す小さな道具 `ledger.py` を足す。** 道具が持つのは、出来事を検証して書き足す（`add`）・判断ボードのデータから問いの題と推奨の中身（一覧から選ぶ問いなら選んだ行の中身も）を引いて回収した出来事を書く（`collect`）・台帳全体を検証する（`check`）・1つの問いの出来事を順に並べる（`trace`）の4つだけである。台帳を読んで出し忘れや取りこぼしを知らせる道具は #540 に残す。（Q45。#538 の子からの申し送り「回収した出来事に問いの題と推奨の中身も残す」）
6. **出力の型 `readable-conversation` の「判断を求めるとき」の項目に、「選択肢と推奨を会話の外（ページなど）に置き、運用者にそこで答えてもらうときは、会話には、何を決めてほしいかと、答える場所と件数を書き、選択肢と推奨は会話に繰り返さない」の1文を足す。** スキルや「判断ボード」の名前は出さない。ルール（`output-format-rule.md` の §9）は変えない。（Q46）
7. **この plan（commit `158c434`）で実装に進む。** plan にある次のことも、この承認に含まれる。子の問いは Markdown をやめ、html-one-pager のページのデータ（`.oe/question-<issue>-<n>.json`・カードと選ぶ表の key は `i<issue>_` で始め・札は書かない）で書き、委譲固定節に入れる。html-one-pager の「答えを受け取る」節と、どのページにも出る「全部推奨どおり」の文を、#466 の決定6・15・16 に合わせて直す。owner が会話に居て始めた対話（認識合わせの深掘り・設計の相談）の中の問いは、今までどおり会話で聞き、判断ボードは owner が会話に居ないあいだに集まる問いを受ける。（Q47）

## 決めていないこと

- **html-one-pager の「作り方の流れ」の1 の「分けるのは、作業のまとまりが違うときか、量が多いとき」を、「答えを待つページは1枚まで」に揃えるか。** 実装の途中（I1-3）で子が食い違いに気づいて揃え、補正と申告したが、統括は「変更」と判定し、owner に再承認を聞いている（判断ボードの Q48・plan の「ゲート3 のあとの変更」の H1）。#466 の決定12（Q34）の文面の意味と、ほかのリポジトリの統括の使い方が変わるためである。答えが出たら、この節に追補する。
  - 追補（2026-10-26）: owner が Q48 で「揃える」を選んだ。html-one-pager の「作り方の流れ」の1 は「作業のまとまりが違う問いは1枚の中で分け、別のページにしてよいのは量が多いとき」になり、新しいスキルの1節と10節（plan の DJ-15）と同じ読みになる。owner の補足（URL は1枚のまま、タブでページの粒度を分ける手もある）は、長くなったときの分け方の案として #539 に申し送られた（統括）。
- **判断ボードが長くなったときに分ける点**（決定4）。#539 で決める。
- **台帳を読んで知らせる道具**（決定5）。#540 で決める。台帳と別の受け付けの列（キュー）を置く案と、問いごとの状態の移りを受け付ける道具の案は、ゲート1 で #540 の案として申し送った（plan の「ゲート1」節の代替案3・6）。
- **ページの中で表示を切り替える部品**（未回答だけ・止まっている作業だけ・作業ごと）。ゲート1 の代替案5 で、#539 の案として申し送った。

## 根拠

- **engine の部品にする理由（決定1）。** スキルの中身は、子への送信（`oe-send`）・受領印の確かめ（`oe-confirm`）・作業層の台帳・計画的な交代に依る。どれも統括と子の委譲の仕組みである。ハーネスに置いて engine に依る部分を補足に寄せると、流れの大事な部分が補足に移り、文書の木も #466 の decision（engine の木）と割れる。ファイルを今 engine の下に置かないのは、#537 が「境目を作り、配る手順を engine に持たせてから、最後にファイルを動かす」順で進めるからである。
- **待たせた問いを台帳で持つ理由（決定2）。** 待たせる仕組みが、閾値で待たせる問いと、答えを待つあいだに届いた問いで1つになる。判断ボードのデータが owner の見ているページと食い違わないので、owner が言う番号がいつもページの上にある。台帳には問いのファイルのパスを必ず書くので、待たせた問いの中身はいつも引ける（ゲート1 の指摘4）。待たせる理由を2つに分けたのは、回収で開いた問いが0件になったときに、答えを待つあいだに届いた問いが載らない読み違いを、ゲート1 の設計SO が見つけたからである（指摘1）。
- **回収のあとの案内で印を外す理由（決定3）。** 答えるまで印を残すと、次の回にも「全部推奨」が当たらず、番号を挙げて答え続けることになる。owner が何か答えたら外す形は、答えた時刻が追加した問いを読んだ証拠にならない。一括の答えの範囲の正本を案内の記録にしたのは、題の文字を運用の状態として読むと、題を直しただけで範囲が変わるからである（ゲート1 の代替案4）。
- **長くなったときの点を決めない理由（決定4）。** 決める根拠の記録が無い。#466 の1回目の判定ページは26件のカードを1枚で答えられている。1枚を長くする主な原因は #539 で足す作業の表である。
- **道具を足す理由（決定5）。** 日本語を含む JSON を手で書くと崩れやすく、hub ではすでに2回起きている。#540 までは検証が無い。問いの題と推奨の中身を手で写すと、#466 の子が困ったのと同じ取りこぼしが起きる。`ledger.py` は統括が手で呼ぶ道具で、自動では動かないので、#466 の決定23（規則を先に作り、自動で動く道具をあとに足す）に反しない。
- **出力の型に足す理由（決定6）。** 出力の型はいつも読まれるので、新しいスキルにだけ書くと、会話に選択肢と推奨を並べる側が勝ち、答える場所が2つになる（#466 の決定1・5）。§9 は運用者に見せる文の書き方の決まりで、判断の求め方を持たない。

## 結果

- `canonical/skills/judgment-board-flow/`（SKILL.md・`ledger.py`・検査）を足した。
- html-one-pager の SKILL.md（作り方の流れ・判断ボードの更新のしかた・答えを受け取る）と用語集の `text.all_recommended`、出力の型、doc-flow-guardrail（索引・委譲固定節・交代の工程の手順4）、issue-intake の hub の補足の1行を直した。
- #466 の decision の「決めていないこと」の4行と、決定12 の暫定に追補を書いた。
- 子の問いの形（ページのデータ）は、この単位の GATE 3 で最初に使われた。統括は子のカードのデータに札だけを足して判断ボードに載せた。
- 本 decision は、#538 の枝の PR に plan・episode と一緒に入り、マージ前に着地する。
