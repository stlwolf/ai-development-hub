# #289 発火位置の探索と、スコープ内に解が無いという構造的発見

## この doc の位置づけ

#289 の設計単位（plan 確定まで）で行った探索の**設計級部分のみ**を昇格したものである。実装そのものは PR #292 と canonical のスキル群が正本なので再蒸留しない（`document-format.md`「昇格義務」節の作業層 plan の扱い）。

残すのは3つである。**棄却した案とその理由**（当時の根拠）、**4パスの反証で崩れた主張と撤回の経緯**、そして**スコープ内に解が無いという構造的発見**。いずれも実装差分からは復元できない。

昇格元は作業層の `.oe/plan-289-blind-gate-check.md` と `.oe/tree-289-dj-exploration.md` で、どちらも gitignored のため worktree の掃除で消える。#284 の arc では同じ位置で昇格を飛ばして設計級を破棄し、復元のために別 PR 1本を要した。その再発防止としてここへ移す。

## 1. 問題の構造（2つの故障経路）

委譲アークには義務の集合（ゲート）があり、義務は2つの書面（委譲時の固定節と plan の step）に書かれている。それでもアークの終端で義務が未履行のまま誰も気づかない事故が2件起きた。経路は2つに分かれる。

- **(a) 終端の再定義** — 実行中に出た場当たりの1文が、確定済みの書面より後に届くため書面に勝つ。指示を受けた側は直近の指示に従っただけで、逸脱していない。
- **(b) 母集団を歩き直す義務の不在** — 終了時にゲート表を1行ずつ当て直す主体が居ない。

この2つは別の層を要求する。(a) は**その瞬間**の層（予防）、(b) は**終端**の層（検出）である。

## 2. 構造的発見（本 doc の中心）

> **#289 が指定したスコープ（skill と運用で効くところを見る・engine の大きな改造はしない）の内側には、非循環かつ事例1 を構造的に捕まえる発火位置が存在しない。**

候補空間は3つの軸（起動主体が依頼側か / 位置が事例1 の経路上にあるか / engine を触るか）で分類でき、**どの候補もこの3分類のどこかに落ちる**。

| 分類 | 該当する候補 | スコープ内で成立しない理由 |
|---|---|---|
| **(i) 依頼側が起動を覚えている必要がある** | 完了宣言の瞬間に照合役を起動 / routing 表の letter 行 / 毎 ACK での照合 / 人間への checklist | **依頼側の故障モードを継承する＝循環。** 依頼側が完了扱いを誤る故障では、同じ依頼側が照合役の起動も省略できる。routing 表への行追加は規範であって機構ではない（規範と機械強制の分離は `document-format.md`「ライフサイクル規範」節） |
| **(ii) 事例1 が到達しない位置にある** | PR → merge のゲート / merge 後のゲート / 不可逆操作の手前のラッチ | **発火しない。** 事例1 は commit も PR も無いまま報告で終わったので、merge も掃除も発生していない。加えて `wt merge` は merge と worktree 削除を1コールで束ねているため、その2つの「間」にラッチを置くこと自体ができない |
| **(iii) engine の改造を要する** | ゲート通過ごとの durable な receipt / 経路強制（prevention）/ 承認束縛の完了 capability / 承認時の義務コンパイル | **#289 がスコープ外に指定している。** 棄却ではなく判断待ちであり、#291 へ park した |

**この発見は #289 の問い自身への答えである。** issue は「まず skill と運用で効くところを見る」と書いた。見た結果、届くのは**規律層（予防）と検出層（起動されれば効く）**までで、タイトルが要求する「約束でなく仕組みで守る」には届かない。仕組みにするには (iii) へ入る判断が要る。

したがって v0 を「#289 完了」と数えないことが設計上の要求になる（issue は keep-open）。外部の反証2レーンが独立に「v0 で止めて完了と数えるのは有害（安心感だけ与えて発火主体が故障主体のまま残る）」と判定したことと一致する。

## 3. 設計判断（DJ）と棄却した案

棄却理由は当時の根拠で書いている（後から作っていない）。

### DJ-1 照合役の形 — 使い捨ての子

母集団を plan の step 集合から導けるので、アーク跨ぎの memory を必要としない。したがって使い捨てで足り、盲検の観点では使い捨ての方が強い（蓄積の持ち越しが無い）。

| 棄却した案 | 理由 |
|---|---|
| 常設の役割・コンポーネント | 依頼側とのやり取りをアーク跨ぎで蓄積する。その蓄積は本設計が禁じている汚染そのものであり、責務を分けたのに汚染経路を新設することになる（コストではなく原理の棄却） |
| 追記専用のゲート台帳 | 作業層は base/head を持たないので append-only を機械検査できない（同種の結論が別 episode で既に確定している）。行自体が自己申告なので虚偽記入には盲検子より弱い。母集団は plan から導けるので新しい成果物が不要 |
| 既存の SO レーンに相乗り | 事例1 は実装SO のゲートに到達していない。そのゲートに載せる検査は、**そのゲートが飛ばされる故障を自己参照的に検出できない** |
| 人間への checklist | それが現状であり、既に破れている（#289 の前提そのもの） |
| 実行側の自己再導出 | 実行側は指示を受けた当事者なので汚染側に居る。ただし予防側の別形（指示矛盾ガード）として残した |

### DJ-2 実体化の場所 — 新スキル + 薄い枠からの routing

| 棄却した案 | 理由 |
|---|---|
| 手順をガードレール枠に書く | 枠が自身を「中身の品質基準は個別スキルへ routing する・枠は薄く保つ」と宣言している。手順を枠に入れるのは枠の設計に反する |
| フロー定義の正本（ゲート配置節）を変える | routing 表が自身を「正本の 1:1 索引」と宣言している。委譲操作軸の行は skill 表側に置くのが確立した形である（既存の letter 行が前例） |
| always-on の rule 化 | rule は always-on だが**発火位置を持たない**。位置が要るのが本件の核心なので、rule 単独では (b) を塞げない |
| 一般の実装ゲート rule に digest 義務を置く | そのルールは委譲に限らず単独作業にも適用される。digest が意味を持つのは「その plan を後から盲検の照合役が読み直すアーク」だけなので、適用範囲が過剰に広がる |

### DJ-3 盲検の対象範囲 — provenance（出自）で定義する

汚染 = 承認以降の窓で**完了・終端について述べた言明**。clean = 承認時点で確定した書面 + 観測可能な状態。

| 棄却・修正した案 | 理由 |
|---|---|
| 「依頼側の出力そのもの」に限る | 字面では**派生汚染**が捕まらない。事例1 では実行側の報告は正直だったが、誤った終端認識が報告に乗っていた。汚染は推移的なので包含して1段強くした |
| 主体で定義する（依頼側が書いたものは全部汚染） | 承認以前の plan と委譲時の書面は clean である。主体で切ると clean な書面を捨て、**母集団そのものを失う** |
| 全部を盲検にする | 含意判定は盲検では担えない（plan の文脈を要する）。かつ検証を外へ出し切ろうとすると無限後退が起きる |
| 生成時刻で切る | 照合は必ず承認より後に走るので、時刻で切ると観測がすべて遮断される。**照会で再現できる値（clean）か、主体の判断（contaminated）か**で切る形に直した |

### DJ-4 入力と出力 — path で渡す / 5値で返す

渡す文書を守っても壊れる経路が4つある（閉じた問い・要約で渡す・起動プロンプトを散文で書く・**母集団そのものが承認後に改変される**）。最後の1つは反証で発見した。

| 棄却・修正した案 | 理由 |
|---|---|
| 出力を「未達の列挙のみ」にする | (i) 観測できて未達 (ii) 証拠が見つからない (iii) 該当しない が区別できず、証拠が無いことが履行と読まれる。母集団側に「該当なし」の明示を求めながら、出力側に同じ区別を持たせていなかった |
| 4値で足りるとする | 「該当するが、まだ due でない」の置き場が無い。後段の義務を「該当しない」に畳むと、その後に確かめる主体が居なくなる（事例2-b がまさにこれ）。第5の値を足した |
| 承認版を読むと書きつつ live path を渡す | 承認版を同定する手段が無いので**契約が物理的に供給不能**（承認後に step を削れば、照合は縮小された母集団を忠実に歩いて「未達なし」を返す）。承認時の digest 束縛で修復した |

### DJ-5 / DJ-6 予防側の2層

- **ACK 規律**: 終点を文で書かず step の位置を指す。「残りの義務を再掲する」案は棄却した（再掲しつつ別の終点を書く余地が残る）。
- **指示矛盾ガード**: 置き場は実行側の返却契約を**主**とし、依頼側が組み立てる書面を従にした。#289 の核心は「依頼側の1文が書面2つに勝った」ことなので、ガードを依頼側が組み立てる文書にだけ置くと**ガードの存在自体が依頼側の手に握られる**（貼り忘れ・削除の余地）。

弁別子は当初「step ID の位置指定は矛盾ではない」だけだったが、反証で自己矛盾が判明した（未達を残したまま「次へ進め」は、直後に定義する飛び越しそのもの）。**step ID が書かれていること自体は免責にならない**へ直し、基準の弱体化を第3の類型として足した。

### DJ-7 発火位置 — 構造的発見に到達（§2）

棄却の経過は §2 の表と §4 の撤回記録に分けて書いた。

## 4. 反証4パスで崩れた主張（撤回の経緯）

設計単位では反証を4パス通し、**8レーン判定すべてが `refuted`** だった。新カテゴリはパス2 と パス4 でどちらも0件になり、探索を打ち切った。

| パス | ゲート | 出た新カテゴリ | 主な撤回 |
|---|---|---|---|
| 1 | ゼロベース代替探索 | 3件（既存の活動ログの受領印イベント / read-only watchdog 同族 / 既存の検証ゲート） | 台帳が第3の形である / letter 行で発火する / 合成を「照合役の同一性」として主張していた |
| 2 | 同上 | 0件 | 「輪が閉じる」（受領印は完了遷移ではない）/ 配線欠如が不発原因という因果 |
| 3 | 設計SO | 7件（閉鎖動詞ラッチ / receipt / 経路強制 / 母集団凍結 / 完了権限の分離 / 完了 capability / 義務コンパイル） | v0 の主発火が棄却済みの循環を再導入していた（**自己矛盾**）/ 机上確認の「捕まる」が過大だった |
| 4 | ゼロベース代替探索（差し戻し後） | 0件 | ラッチと残渣スイープ（`wt merge` の一体化・事例1 が不可逆操作に到達しない） |

**最も重い撤回は パス3 のものである。** 探索木は letter 行を「循環する」として棄却したのに、v0 の発火位置を「依頼側が完了扱いにする瞬間」に置いていた。スキル手順に包んだだけで循環構造は同一であり、外部の2レーンが独立に指摘した。

実装単位でも同型の再発が1件あった。起動テンプレに「この境界」という slot を置いており、これは依頼側の終端認識を判定材料に戻す経路だった。終端を誤認した依頼側が境界を手前に書けば、後段の義務がまとめて「まだ due でない」に落ち、**検出層が取りこぼしを機械的に正当化する**。設計段階で塞いだ経路を実装で開け直していたことになる。

**この再発の形（自分が閉じた汚染経路を、別の層で slot や引数として開け直す）は、この arc で2回起きている。** 予防の教訓としては「汚染経路を閉じたら、下流の層で同じ情報を受け取る口が無いかを確かめる」に当たる。

## 5. 探索を尽くしたと言える根拠（自己申告で「十分」と言わないため）

- 新カテゴリが2パス連続で0件（パス2・パス4）。
- 各パスの反証は独立2レーン（他族）で、パス3 は3レーン起動。
- §2 の3分類が候補空間を網羅している（起動主体・位置・engine 改造の3軸で、どの案も分類先が一意に決まる）。

## 6. 未探索として残したもの（理由つき）

- **承認時の義務コンパイル / 経路強制 / 完了 capability / ゲート receipt** の実効性 — いずれも engine 改造なので机上のまま #291 へ渡した。**推奨は義務コンパイル**である（母集団の信頼性という上流前提を塞ぎ、かつ委譲時の書面のゲート順序誤りを承認時に弾ける。この事例は現在どの層でも捕まらない）。
- **並列委譲時の相互チェック** — 今回の事例2件はどちらも単一の実行側。並列が常態化した時点で開く。
- **承認版 plan の凍結手段** — 作業層は git 履歴を持たないため版固定の手段が無い。digest 束縛で「検出される穴」には変えたが、塞いだわけではない。
- **残渣を正常系と区別する述語** — 未完了アークの残渣（worktree の残存・PR の不在）は、作業中の正常な状態と機械的に区別できない。

## 7. 事例が捕まるかの机上確認（過大主張を撤回した後）

| 事例 | 結果 |
|---|---|
| 実装SO 以降が実行されず報告の完成が終点になった | **条件付き検出（照合役が起動された場合のみ）。構造的には捕まらない** |
| 委譲時の書面でゲートの順序を誤った | **捕まらない。** 母集団が誤った順序で seed されるので、母集団自体が汚染される。受け皿は承認時の義務コンパイル（#291）だけである |
| 昇格確認を飛ばして設計級を破棄した | **捕まる見込み。** ただし義務ごとの due の位置づけが必要で、掃除の順序制御は依頼側の規律に残る |
