## 5. 中心の観測 — 失敗の型は位置に付く

**観測の範囲を先に固定する**: 以下は**同一 arc（#290）・同一問題領域（正本層の検証設計）・観測者が同一系統（設計SO の codex/cursor レーン + 同一 owner）**という条件下の6例である。**一般法則としては書かない。** この arc で観測された型であり、範囲外への外挿は本 doc の主張に含まれない（当事者が自分の失敗から一般化する際に根拠の帰属を強めやすいこと自体、この arc の採用 negative knowledge が警告していた）。

観測: 「成立条件を落として効果を言い切る」型の過大主張が6回起き、次の3つの変化を**またいで**再生産された。

1. **書き手の個体が代わっても起きた** — 1〜5回目は plan 単位の子（opus）、6回目は別の子。
2. **モデルの系統が代わっても起きた** — opus → Fable 5。
3. **その型を明示的に知っている者でも起きた** — 6回目の書き手は、独立監査（A 系）でこの型を名指しし、5回の再生産を監査 doc に書いた当人である。監査者として型を検出できた者が、**書き手の位置に回った直後に同じ型を4件犯した**（「解消」「起きない」「規律にも依存しない」「脱落として現れることはない」— いずれも V4 の両レーンが検出。自己検出はここでもゼロ）。しかも4件のうち1件は、**同じ節の中で「言い切るな」という規律を自分で宣言した直後の行**で起きた。

この観測が #290 の問題設定を精密化する。「親の成果物に検証が乗らない」問題は、親の能力・注意・知識の問題として扱うと、6回目が反例になる（型を知り、検出実績まである者が犯した）。**この arc で観測された限りでは、故障は「書き手というポジション + 検証が構造的に届かない層」の組に付いており、個体を入れ替えても・モデル系統を替えても・型の知識があっても消えなかった。** ただしこの観測は、位置と他の共通要因（同一 arc・同一問題領域・同一レビュー系統）を因果的に分離したものではない — 位置を疑う根拠であって、位置の因果の証明ではない。対策の向きとしては「書き手に気をつけさせる」より「位置の外に検証を置く」を支持する — ただし、その「位置の外に置く」設計自体が5ラウンドで収束しなかった、というのが本 arc の結果である（§8）。

付記: 逆向きの観測も1件ある。書き手の位置で4件犯した同じ主体は、**読み手（監査・検証者）の位置では**上流の断定の誤り2件（統括の見立て・brief の強め替え）と未検討の候補1件を検出できている。同一主体が役割によって正反対の結果を出した — 位置仮説と整合する1観測だが、これ単独で位置の因果を確定するものではない。

## 6. 受け入れ条件2 の読みの分岐 — 結論を反転させたのは設計ではなく読みだった

### 6.1 分岐の構造

受け入れ条件2「各文書に確かめる主体が定義されている（**自己申告だけで閉じない**）」には2つの読みがあった。

- **強読み**: 検証の起動・母集団の供給・義務の履行まで含めて、機構が自己申告に依存しないこと。
- **弱読み**: 判定に自己申告以外の材料が入ること（起動保証は要求しない）。

rev.1〜rev.4 は強読みの下で「未達」と判定され、これは**強読みの下では正しかった**（設計SO 4ラウンドが支持）。owner が弱読みで確定（2026-07-31）した後の rev.5 は「満たす」側になり、V4 の両レーンも**この充足判定自体は崩さなかった**。つまり **rev.4 → rev.5 の判定反転の主因は設計の改善ではなく条件の読みの確定**である。この整理を落とすと「rev.4 の判定は誤りだった」という誤読が生まれる。

弱読みで「判定に入る自己申告以外の材料」として最終的に数えられたのは3点: (i) 突合候補の外部集合（issue の在庫・committed の変更履歴 — 書き手の申告から独立）(ii) イベントログの機械時刻（取れるとき・§7）(iii) 構造 validator の機械判定。probe 出力と検証主体の分離は、型選択・カタログ起草・固定節の貼付に書き手が関与しうるため**補助**に降格された（V4）。

### 6.2 #291 との境界（owner 決定の保全）

**機構による起動保証は #291 の領分であり、#290 の受け入れ条件ではない。** この境界は弱読みの確定と同時に owner が固定した。#290 を弱読みで閉じても「起動が保証された」ことにはならず、逆に #291 が起動保証を作っても「内容の正しさの判定」は含まれない（それは probe / 突合 / 読み手の側の仕事のまま）。

## 7. 第5境界候補の実測と部分撤回（#291 の設計材料）

突合型の検算には「交代の境界」（どの時点以後の外部変化と突合するか）が要る。書き手が書いた日付を境界に使うと窓が書き手の宣言に依存する。rev.4 は機械時刻の候補4件（tmux 2種・監視 sidecar の生成時刻・commit 時刻）を検討して全滅し「取得できる独立した境界は無い」と結論したが、独立監査が**候補集合の外**に第5候補を見つけた。

### 7.1 実測（2026-07-31・すべて実体を開いて確認）

- engine のイベントログ（`~/.claude/state/oe-events.jsonl`・append-only の jsonl）に、`oe-delegate` が spawn 手続きの末尾で emit する `child_spawned` イベントが `ts`（emit 時に `date -u` で機械生成）つきで残る。
- **委譲形 succession では、後任自身が oe-delegate の子として spawn されるため、後任自身の誕生が `to.pane = 後任` のレコードとして記録される**: 9代目の spawn は `2026-07-29T02:30:35+00:00`（from = 8代目 pane）、8代目の spawn は `2026-07-26T07:05:16+00:00`（from = 7代目 pane）— いずれも board の交代日と一致した。7代目は手動 seat（owner が pane を直接起動した世代）でレコード無し。**被覆は委譲形に限られる（実測 2/3 世代）。**
- `oe-register`（自己昇格の verb）はイベントを emit しない（ソース実読・emit 参照0件。対照として `oe-delegate` には emit 行が実在）。したがって**着任＝自己昇格の瞬間そのものは記録されず**、spawn の `ts` は着任の数分前に当たる（実測: 9代目は spawn の約8分後に registry へ root 書込）。
- emit は best-effort（jq 不在・抑止変数・dir 作成失敗で黙って skip）。ログに rotation は無い。

### 7.2 生き残った部分と撤回された部分

- **生き残り**: 後任自身の spawn ts は「**自分の誕生時刻の下限の足場**」として使える。ただし「`to.pane == 自ペイン` の最後のレコードを無条件に採る」は成立せず、stale 再利用で偽時刻を採りうる（下記の撤回 (2)・「分類が要らない」という当初の言い方はこの点で部分撤回済み）。レコードの**欠落**（手動形・emission 失敗）は `unknown` に倒して窓を狭めない、という規則は生き残った。
- **撤回（V4・両レーン）**: (1) 「そのレコードの `from.pane` が前任である」— `from.pane` は **spawn 親**であって前任と機構上同定できない（前任の在任中に別の coordinator が後任を spawn すれば、窓の下限が誤って後ろへずれ、前任の在任期間が突合の窓から**脱落する**）。(2) 「境界の故障は常に窓が広がる側」という全称 — pane ID が tmux server 再起動後に再利用され **stale なレコードが残っている**場合、規則は「レコードが無い」しか `unknown` に倒さないため、偽の誕生時刻を採って窓が**狭まる**。ログに server identity / sequence / digest が無いことが根にある。
- **#291 への含意**: 完了遷移の語彙を足すなら（Alt-2 系）、レコードに succession を表す type か role、および server identity を持たせると、この2つの穴が同時に閉じる位置にある — これは設計案であって決定ではない。

## 9. 反証を生き残った設計要素（規範ではない・将来単位の出発点）

5ラウンドの反証で「崩れなかった」または「条件つきで縮んで残った」もの。**いずれも採用されていない。** 将来 #290 を再開する単位が、ゼロからでなくここから出発できるように残す。

1. **突合型の候補生成（C1）**: 検算の母集団を state 文書の本文からでなく、**state 本文とは別に列挙できる集合**（issue の在庫・committed の変更履歴）から引く。出所ごとの混入度は残る — schema は書き手の外、issue と committed 履歴は「ほぼ外」（起票・記録するかどうかに書き手の影響が残る。「すべて書き手の外」という言い方は探索中に撤回済み）。「取得失敗は `unknown` で止め、候補ゼロと区別する」「全候補に処分を付け、`unknown` を `fulfilled` に畳まない」という契約ごと生き残った（4ラウンド目以降、両レーンとも崩していない）。効くのは「書かれるべきものが書かれていない」側だけで、「書かれたものが誤っている」側には効かない。
2. **検算手順の committed カタログ（Y1 の撤回後の形）**: 検算コマンドを書き手に発明させず、PR ゲートを通る committed 層の型カタログから引く。**成立条件**: 正しい型が選ばれる・型がカタログに在る・probe が主張の全域を覆う・再現入力が残る・カタログ自体が正しい。この条件群を落として「主故障モードに効く」と言い切った瞬間に過大主張になる（実際になった）。カタログの2層分離（canonical には型と要求を関係で書き、実コマンドは repo の committed 文書に置く）は可搬性と改変耐性の両立点として崩れていない。
3. **消費時検証（Y3）**: 主張の効力発生点を書き込みから消費へ移す — 検証者は書き手でない読み手（後任・委譲子）で、起動の**動機**は読み手自身の必要に由来する（誤りに依拠すれば自分が最初の被害者）。ground truth 4件と本 arc の F1（validator の exit code 誤り）は現にこの経路で捕まった。**残る限界**: 起動の**経路**（固定節の貼付・cold-start の読了）には書き手と読み手の規律が残り、確かめずに依拠する読み手の故障も残る。
4. **訂正の3要素**: 訂正の記録に「何が誤りだったか / 何で確かめたか / **誰が捕まえたか**」を持たせる。3つ目により、記録が正確で欠落なく付けられるという条件の下では、自己検出率という #289/#290 の中心メトリクスを記録から集計できる（記録自体は人手入力なので自己申告性は残る）。反証で崩れていないが、規範化されていないので現在は誰の義務でもない。
5. **state 文書の最小整備の形（DJ-7 案C）**: frontmatter に既存3キーのみ・現統括 marker は frontmatter に一意化・系譜の散文は残す。validator（exit 1 = blocking 配線可能）を通す形として両レーンが安全性を確認済み。**実施されていない**（規範を積まない判断に含まれ、現 board は validator を通らないまま）。

## 10. 盲検監査の設計と、遮断が破れた観測

本 arc は独立監査（A 系・Claude 系の別セッション）に「A1 で独立解を先に固定 → A2 で監査」という盲検2段を課した。設計意図は「先に『成立しない』という結論を読むと引かれる」の遮断である。

**観測**: 伏せると宣言された情報（gate 0 の決定③＝確かめる主体）が、**A1 の読了リスト自身の2経路**（board の in-flight 節・隣接 issue #293 の本文）から監査者に到達した。原因は構造的で、**gate 0 の決定を board / issue へ正本化する既存規範と、「その決定を伏せて board を読ませる」盲検設計が両立しない**。監査者は A1 冒頭で汚染を自己開示し、汚染された要素（確かめる主体の設計）と自前の導出（候補空間の分類・「成立しない」への反論）を区別して監査を成立させた。

- 適用形: **盲検委譲を組むときは、伏せる情報がその決定の正本化先（board・隣接 issue）に既に書かれていないかを、brief 発行前に機械的に確かめる。**
- この観測は negative knowledge item `01KYSKQHDT86GZW87E8EDMSE46`（遮断の決定と実装は別作業・下流の口）への観測として書き戻した（本 PR）。
- 手続き面で機能したもの: 独立解を監査より先に書面で固定する順序は、監査項目1（一致/相違の照合）を可能にした。反 anchoring 条項（「提案者であることを理由に擁護せず、自分の提案を自分で反証せよ」）は V4 で実際に機能し、SO 両レーンは自分たちが提案した方向（カタログ固定・cold-start 限定）を自分で反証した。
