## 3. engine の搬送路は14ある（設計上の事実）

「親が子へ渡す書面」が子に届く経路を、コードを読んで数え上げた。**`--brief` / `--kickoff` flag を通るのは4 verb だけで、残りは flag を通らない。**

### 3.1 flag を通る経路（検査を置ける位置がある）

`oe-send` / `oe-delegate` / `oe-select` / `oe-kick`（kickoff モード）の4つ。**4つとも `oe-send` に合流する。**

- `oe-select` は `exec "${BIN_DIR}/oe-send"` で素通しする（`projects/orchestration-engine/bin/oe-select:182,185`）。
- `oe-kick` は kickoff モードで `oe-delegate --kickoff` を組み立て（`bin/oe-kick:105`）、`oe-delegate` はキックを `oe-send --brief` に投げる（`bin/oe-delegate:377-380`）。

**成立条件**: 検査は `--brief` と `--kickoff` の**両方の分岐**に置く必要がある（`oe-select` / `oe-kick` が渡すのは非推奨 alias の `--kickoff`）。`bin/oe-send:42` は両者を同じ `case` 分岐で受ける。

**この合流は「flag を通る書面」についてのみ成立する。** 前単位の rev.1 は「4 verb が合流するので1箇所で覆える」と書いて崩れた — **flag の合流 ⊆ 書面の到達**という包含を落としていたためである（§5.1）。

**「覆える」とは書かない。** 合流点に検査を置けても、その4経路ですら**検査後の差し替え（TOCTOU）は残る** — `oe-send` は書面の内容を読まず存在検査だけを行い（`bin/oe-send:65`）、子はあとで自分で読む。**したがって flag 経路について言えるのは「検査を起動できる位置がある」までであって、「その経路の書面が検査を通ったものと同一である」ではない。**

### 3.3 `oe-kick` の issue モードは `--brief` を乗せない（とくに重い1件）


**含意（#291 への申し送り）**: 「親が子へ渡す書面」を検査対象にする設計は、**GitHub の issue 本文もその母集団に入る**ことを前提にしなければならない。ローカルのファイルだけを対象にすると、正式 verb の主要モードが射程から外れる。

### 3.4 経路14 と経路17 は、迂回のつもりで使う経路ではない

## 4. ULID は引用専用のトークンではない（測定範囲の異なる2つの実測）

前単位の設計は「ULID は knowledge item を指す引用専用のトークンだから、誤検知の構造的な余地が無い」という前提で述語を組んだ。**これは実測で崩れた。** 蒸留層の episode / discussion / decision / plan も frontmatter に同形式の `id` を持つ。

### 4.1 測定の方法を先に固定する

この節の数値は**当初、範囲も単位も揃っていない測り方**で出しており、実装SO の2レーンが独立に再計数して食い違いを指摘した。**指摘は正しかった。** 以下は方法を1つに固定して測り直した値である。

測定の述語（これを変えると数が変わる）:

```bash
# frontmatter の id 行。引用符の有無を問わない。作業ツリーの実体を見る（.git / tmp を除く）
grep -rlE '^id: *"?0[0-9A-HJKMNP-TV-Z]{25}"?' --include='*.md' <対象>
```

| 範囲 | ULID を持つ文書 | うち knowledge item | 非 item |
|---|---|---|---|
| A: `projects/orchestration-engine/docs/` + `canonical/` | 141 | 15 | 126 |
| B: repo 全体（作業ツリー・`.git` / `tmp` を除く） | 162 | 15 | 147 |

- 本 doc の discussion・episode・新規 item を作成した**後**の値である（`knowledge item` が 14 → 15 になっているのはそのため）。
- B と A の差21件は、orchestration-engine の蒸留木と `canonical/` の外にある別の蒸留木である: `docs/decisions` 2・`docs/episodes` 2・`docs/specs` 3・`docs/issues/38/plans` 3・`docs/research` 1・`projects/wezterm-ai-mode/` 10 [verified]。
- **独立の再計数は ±1 の幅で一致した**（実装SO の2レーンが 140 / 161 と 140 / 161 を報告し、本 doc は 141 / 162）。差は正規表現の細部（引用符の扱い・ULID の文字集合）に由来する。**この節の主張は総数の一致に依存しないので、幅があることを明記して先へ進む。**

### 4.2 当初の食い違いの原因（記録として残す）

- 委譲子の初回報告「132件中117件」は、**132 が `canonical/` を含む範囲の行数、117 が `canonical/` を含まない範囲のファイル数**で、範囲も単位も揃っていなかった。**これは1つの比率として並べてはいけない2つの数であり、単なる別測定ではなく不正な比較だった。**
- 統括の独立計数「145件中 knowledge item は14件」は repo 全体を引用符つき `id` で数えたもので、本 doc の作成物を含まない時点の値である。**方法を揃えた B の 162 とは、引用符なし `id`（14件）と本 doc の作成物3件の分だけ差が出る。**

### 4.3 結論（どの範囲・どの方法でも変わらない部分）

**knowledge item は15件で、ULID を持つ文書の圧倒的多数は knowledge item ではない**（15 対 126 ないし 15 対 147）。**したがって「ULID を見つけたら knowledge item に解決するはず」という述語は、文書 ULID の引用を誤検知する。** 前単位の corpus で12件すべてが解決したのは運用の偶然であって、構造の保証ではない。

**成立条件つきの言い換え**: ULID を検査対象にするなら、**先に型を判別する述語**（その ULID が knowledge item のものか文書のものか）が要る。**型判別を持たない存在検査も実装はできる — ただし意味のある判定にはならない**（文書 ULID の正当な引用を「解決しない」と報告するため）。

## 5. 述語の選定基準が崩れた経緯

### 5.1 何を基準にしたか

前単位は、誤検知を構造的に避けるために「**引用専用のトークン類だけを検査対象にする**」を選定基準にした。狙いは、パス（引用と「これから作る成果物」の指定が混在する）を避け、混在しないトークン類を選ぶことだった。

選んだのは3つである。

- P3: ULID が knowledge item に解決する
- P4: `gate N` とゲート名の対応が spec のゲート配置表と一致する
- P5: `「…」節` / `§N` が参照先 doc に実在する

### 5.2 3つのうち2つに実在の反例が出た

| 述語 | 反例 | 出典 |
|---|---|---|
| P3 | ULID は文書にも付く（§4）。加えて `disabled` / `superseded` / `retired` の item は履歴として残り、正当に引用される | `canonical/orchestration-spec/document-format.md:224-225` |
| P5 | 「これから書く節」への参照が実在する（「plan に『測定』節を足し」） | 作業層 `addendum-284-measure-first.md:42`（本 doc へ転記） |
| P4 | 反例なし | — |

**残ったのは P4 だけである。そして P4 は、#293 の一次データ（統括が実際に犯した誤り5件）のどれも捕まえない。** P4 が見るのは番号と名前の対応であって、順序ではない（§6）。

**教訓の形**: 「そのトークン類に『これから作る』側が存在しない」という直観は、**トークンの形が他の用途と共有されていないこと**まで確かめないと成立しない。ULID は形が共有されており、節タイトルは「これから作る」側が存在した。

### 5.3 検査を一部の経路にだけ置くと、無検査の経路へ流れる誘因ができる

反証で出た指摘で、owner の判断3（advisory lint を切り出さない）の根拠になった。

flag を通る4経路にだけ検査（とくに凍結のような間接参照の摩擦）を足すと、**摩擦の無い経路14・経路17 が相対的に楽になる。** 検査を足すこと自体が、検査されない経路の使用を促す方向に働きうる。

**成立条件**: この誘因が実際に効くかは未測定である。書き手が摩擦を避けて経路を変えるかどうかは観測されていない。**「期待値が負になりうる」までが言えることで、「負である」とは言えない。**

## 6. P8（ゲート順序）の5形式と、P5 の実測（#291 の設計材料）

#293 の動機となった誤りは「委譲 brief でゲート順序を逆に書いた」である。これを機械述語で捕まえられるかを5形式で実測した。

### 6.1 誤りの実体は作業層に残っていた

前単位は当初「誤っていた版は `.oe/` が gitignored なので復元できない」と書いた。**これは誤りだった。** gitignored は git 履歴が無いことを意味するだけで、ファイルが消えたことを意味しない。

誤りの実体（作業層 `brief-284-episode-layer-split.md:103` にあった記述を本 doc へ転記）:

> plan を書いて STOP → 親が fact-check → owner が gate 3 で承認 → 実装 → **gate 2 と gate 4 の SO** → PR → episode closure（gate 5）→ … → gate 6

ゲートの出現列は `3 → 2 → 4 → 5 → 6` である。**gate 2（設計SO）が gate 3（実装への承認）と実装の後に置かれている**のが誤りで、spec では gate 2 は plan 確定前である。訂正記録は作業層 `addendum-284-gate2-first.md:13` にあった。

### 6.2 5形式の実測

corpus は当時の作業層の書面33件（brief 26 + addendum 7）である。

| (a) | `gate N = <step ID>` の binding 同士の順序整合 | **母集団が空。** binding を2件以上持つ文書が33件中0件 |
| (b) | 文書中の全 `gate N` 出現列が非減少 | **30件中22件（73%）が違反。** 違反はすべて正しい書面である |
| (c) | ステップ節に絞って (b) を当てる | 正しい書面が非単調のまま。誤検知 |
| (e) | step 見出しごとの gate 出現を step 順に並べる | gate 言及が疎で、文脈参照が主。誤検知 |
| **(f)** | **矢印（`→`）を含む行に限り、その行内の gate 列が非減少** | **母集団8行・真陽性1・偽陽性1・正しく通過6** |

- 形式 (f) の真陽性は §6.1 の誤りそのものである。**この arc で唯一、述語が動機となった誤りを実際に捕まえた形式である。**
- 偽陽性は、**誤った順序を引用して訂正している行**だった（`addendum-284-gate2-first.md:13`）。訂正記録が誤りを再掲するので発火する。

**なぜ (b)(c)(e) が誤検知になるのか**: 書面はゲートを順路として並べるだけでなく、**文脈として前後参照する**。固定節が「マージ・掃除は親の gate 6」を早い位置に書き、ステップ節が「gate 2 は plan 確定前」と後で書く。どちらも正しい記述であって順序の誤りではない。**出現順は主張順を符号化しない。**

### 6.3 spec の矢印図には gate 2 が無い

前単位は「spec は順序を矢印図として機械可読に持つ」と書いたが、実物は次である（`canonical/orchestration-spec/document-format.md:573`）[verified]。

```text
[設計着手前] --(0)--> [設計判断] --(1)--> [plan 確定] --(3)--> [実装] --(4)--> [PR] --(5)--> [merge] --(6)--> [後始末]
```

**gate 2 が図に入っていない。** gate 2 は直後の散文（`:577`「(2) は plan 確定前（設計SO）」）でしか表現されない。**一次データの誤りはまさに gate 2 の位置なので、矢印図から機械的に取り出せる部分順序には肝心のゲートが載っていない。**

**#291 への含意**: 承認時に義務を機械可読な形で固定するなら、**ゲート順序の正解表は矢印図ではなく表の位置列か、そのために新設する構造から取る必要がある。** 現在の spec は、人間には順序が読めるが機械には完全な順序を渡していない。

### 6.4 P5 の実測（owner が #291 の設計材料として残すと指定した）

`「…」節` 形式の参照を corpus で測った [verified]。

- corpus 中の `「…」節` の出現は50件、ユニークな参照先は13件。
- **12件は repo 内の見出しに解決した。1件（`「再測定の設計改善（優先）」節`）は repo 内のどこにも見出しが無い。**
- 50件のうち39件は同じ行に `.md` のファイル名があり、**解決先の doc が決まる**。残りは解決先が書面から一意に決まらない。

**成立条件**: P5 が成立するのは「参照先 doc が特定できること」である。素の `§N` が誰の §N かは書面から一意に決まらない（前単位の plan は「§11 の表」と書いて spec の §11 を指したが、その plan 自身にも §11 があった）。

**#291 への含意**: 節参照の検査は、**解決先が明示された参照（同一行に doc 名がある形）に限れば「判定に入れる」ことができる。** 一次データのうち唯一「子が実際に裏取りで捕まえた誤り」（指示が指す節が昇格で別 doc へ移っていた）はこの類である。

**ただし「解決先が特定できる」は解決可能性の条件であって、誤検知が低いことの条件ではない。** §5.2 に記録したとおり、**解決先が決まっていても「これから書く節」への参照は正当であり、存在検査は偽陽性を出す。** 実効性を主張するには、その偽陽性の率を測る必要があり、本 arc は測っていない。

## 7. #289 の結論は覆らなかった

#289 は「委譲時の書面でゲートの順序を誤った場合、**受け皿は承認時の義務コンパイルだけである**」と結論した（`2026-07-29-discussion-289-completion-gate-firing-position.md:147`・推奨は同 `:137`）。

**#293 はこれを覆すつもりで受け渡し経路という位置を試したが、覆せなかった。** 理由は3つで、いずれも実測または一次コードに基づく。

1. **述語が一般的な受け皿にならない。** 順序を捕まえる形式は (f) だけである。**(f) は一次データ1 を真陽性として実際に捕まえた**（§6.2）ので「述語が成立しない」とは書かない — **成立したのは矢印行という限られた形の中でだけ**である。散文で書かれれば沈黙し、母集団8行で偽陽性が1件出ており、感度は未測定である。spec 側も完全な順序を機械に渡していない（§6.3）。
2. **起動が親の規律に条件付けられる。** 検査は `--brief` を使ったときだけ効くので、親が経路14 や経路17 を選べば起動しない（§3.4）。したがって #289 の分類 (i)（依頼側が起動を覚える必要がある＝循環）の残差を持つ。**完全な循環ではない**（flag を使えば機械発火し、別途の想起は不要）が、**flag を使うという選択自体が親の手に残る。**
   - **なお「書面を誤るような親ほど `--brief` も省きやすい」という相関は、本 arc では観測していない。** 前版はこれを理由の補強に使っていたが、未測定の利用者行動なので落とした（§5.3 で同種の誘因を「未測定」と限定しているのと揃える）。
3. **搬送の byte 同一性も、送信 verb の内側という位置では保証できない**（§7.2）。

### 7.2 凍結コピー（spool）が「spawn 後の `oe-send` の内側」では成立しない理由

途中の版は「受け渡し時に書面を凍結し、子には凍結コピーを読ませる」案を採り、「TOCTOU が閉じる」と書いた。**その位置では成立しない** [verified]。

**否定の範囲を限定する**: コードから言えるのは「**`oe-send` の内側（＝子の spawn より後）で凍結する形**は成立しない」までである。**送信側という位置一般の否定ではない。** 下記のとおり spawn 前や承認時に置けば同じ発想は成立しうる。

- 子は spawn の時点で `--add-dir` を固定される。`oe-delegate` は元 brief の親ディレクトリだけを `--add-dir` に渡して子を起動する（`bin/oe-delegate:200-202`・`:352`）。
- **キックの `oe-send` 呼び出しは spawn より後である**（`bin/oe-delegate:380`）。
- したがって `oe-send` の中で別ディレクトリへ凍結すると**子はそこを読めない**。同じディレクトリへ置けば親と子の双方から書き換え可能なので**凍結にならない**。

**この記録を残す理由**: 「凍結して渡せばよい」は直観的に出やすい案なので、**同じ位置に再提案されるのを防ぐ**。なお別の位置（spawn 前・承認時）に置けば同じ発想は成立しうる — 実際 envelope 系は生成時に検証しており（`lib/envelope.sh:60` が `scripts/validate-envelope.sh` を硬く呼ぶ）、これは #291 の材料になる。

**加えて未規定だった点**: 凍結すると元の書面と凍結コピーの2版が存在するが、**`unmet-gate-check`（#289 v0・マージ済み）はどちらを baseline に取るかが決まらない。** #289 v0 が塞いだ穴を開け直す経路であり、spool 型を将来検討する単位はここを先に決める必要がある。

## 8. SO の claude レーンはタイムアウトで落ちていた（横断的な事実・修正は別単位）

**この節は事実の保全だけを担う。** タイムアウトの修正は owner 判断で #295 の単位が扱う。

### 8.1 実測

#293 の gate 2 設計SO（`so-compare --with codex,claude,cursor`）で観測した値 [verified]（`tmp/so-293-gate2/claude-meta.txt` と `claude-meta.txt.attempt1` の内容を本 doc へ転記）。

| 試行 | タイムアウト設定 | 経過 | 結果 |
|---|---|---|---|
| 1回目 | 480 秒 | 480 秒 | `exit_code=124` / `timeout_status=timeout_empty` / **0 バイト** |
| リトライ | 720 秒（機構が 1.5 倍に延長） | **652 秒** | `exit_code=0` / `timeout_status=success` / **10,659 バイト・76行** |

**同じ arc の実装SO（本 doc の gate 4）で、3つ目の失敗の型を観測した** [verified]。`SO_TIMEOUT=900` で起動している。

| 試行 | タイムアウト設定 | 経過 | 結果 |
|---|---|---|---|
| 1回目 | 900 秒 | 958 秒 | `exit_code=124` / `timeout_status=timeout_empty` / **0 バイト** |
| リトライ | 1350 秒 | 795 秒 | `exit_code=1` / `timeout_status=error_partial` / **61 バイト** = `You've hit your session limit` |

### 8.2 何が言えるか

- **「この環境では claude レーンが返らない」という前提は誤りである。** claude レーンは返る実績がある（652 秒・10,659 バイト）。
- **ただし「タイムアウトを上げれば返る」も誤りである。** 900 秒で起動した実装SO では、1回目が 958 秒で `timeout_empty`、リトライがアカウントのセッション上限に当たって 61 バイトのエラー文字列を返した。**空返却の原因は少なくとも3種類ある**（時間不足 / 時間を上げても終わらない / 利用上限）。
- **したがって「N 秒での運用では構造的に空返却になる」とは書けない。** 言えるのは次までである。
  - **480 秒は少なくとも1回、時間不足が原因で空だった**（同じ内容が 652 秒では返った）。
  - **0 バイトのレーンを見たとき、原因を1つに決めつけてはいけない。** `timeout_status` と `exit_code` と stdout の中身を見れば、時間不足（`timeout_empty`）と利用上限（`error_partial` + メッセージ）は区別できる。**区別せずに「返らないレーン」と扱うと、対処（時間を延ばす / 時間をおいて再実行する）を取り違える。**

### 8.3 過去の SO 証跡の読み方への影響（ここが重い）

このクラスタの先行 arc は、claude レーンの空返却を「この環境の既知症状」として扱い、**必須レーンに数えないまま進めた**。#290 の discussion は明示的にそう記録している（「claude レーンは第1ラウンドで480秒タイムアウト・0バイト（この環境の既知症状）で、以後は必須レーンに数えていない」）。

**したがって #284 / #289 / #290 の設計SO は、事実上2レーンでの反証だった。** 3レーンで反証したつもりの記録は、レーン数の点で読み替える必要がある。

**この読み替えが実害を持つ根拠が、本 arc にある。** #293 の gate 2 では、遅れて返った claude レーンが**他の2レーンが触れなかった2件**を出した。

- ULID が引用専用トークンでないこと（§4）— これが選定基準を崩した（§5.2）。
- `oe-kick` の issue モードが `--brief` を乗せないこと（§3.3）。

**つまり3レーン目は「数の足し算」ではなく、判断の前提を崩す指摘を出した。** 空返却を許容して進んだ判断は、その時点では弱 SO の規約（partial は disclose して進んでよい）に沿っていたが、**落ちていたレーンが最も重い指摘を持っていた**という事例がここにある。

**成立条件・範囲の限定**: これは #293 の gate 2 で観測された1事例である。**過去の arc で落ちていた claude レーンが同様に重い指摘を持っていたかは検証していない**（生出力が残っていないラウンドがある）。「過去の判断が誤っていた」とは言えない。**言えるのは「2レーンだった」という事実と、「3レーン目が前提を崩しうる」という本 arc の1事例である。**

## 9. gate 0 に内部矛盾があった（「失敗の型は位置に付く」の追加事例）

統括は gate 0 で発火位置を「受け渡し経路（親が送る側）」と確定した。一方で #293 の受け入れ条件2 は「**子が受領時に**当てられる検査」のままだった。

**この2つは、受け入れ条件2 を強く読むと両立しない。** 送信側で起動する検査は、どれも「子が受領時に起動する」を満たさない。

- 委譲子はこれを「案の選択より前に決まっていなければならないブロッカー」と判定し、**確定を拒否して owner へ上げた。** owner の gate 3 はこの読みを強く確定し、判定は正しかった。
- **矛盾は探索の出発点に埋まっていたので、探索の中では解けなかった。** 2ラウンドの反証はどちらも「どの案が良いか」を評価しており、前提そのものの不整合は反証レーンも指摘していない（3レーン目が「案H を採用後の §9 まで保留した順序が誤り」と指摘したのが最も近い）。

**#290 の観測との関係**: #290 は「失敗の型は位置に付く」（書き手のポジション + 検証が構造的に届かない層の組）を同一 arc の6例で観測した。本件はその**追加事例**に当たる — **統括＝書き手の位置**で、自分が書いた2つの制約（発火位置と受け入れ条件）の整合が落ちた。

**範囲の限定**: これは1事例であり、#290 の観測範囲（同一 arc・同一問題領域・同一観測者系統）とも異なる。**一般法則としては書かない。** 位置を疑う根拠が1件増えた、というのが言えることである。

**前版はここを「三つとも承認時の義務コンパイルへ収束した」と書いたが、それは事実と合っていなかった。** 実装SO の2レーンが独立に指摘し、一次を読み直して確認した [verified]。

### 10.1 一致している部分（3つとも）

**「規範と規律の層では届かない」という否定側で一致している。** 3つとも、規範を積む方向・書き手に気をつけさせる方向では解けないと判定し、いずれも**規範を積まずに終わっている**（#289 は v0 を「完了と数えない」、#290 は「規範を積まない」、#293 は canonical を1行も変えない）。

### 10.2 一致していない部分

**肯定側の答えは3つで割れている。**

- #289 と #293 は**承認時の義務コンパイル**（engine 側・機械が正解を生成する方向）を指した。
- **#290 は義務コンパイルを指していない。** #290 が生き残らせたのは**消費時検証**（検証の主体を書き手から読み手へ移す方向）と**committed カタログ**である。方向が違う — 前者は「誰が起動するか」を engine に寄せ、後者は「誰が検証するか」を読み手に寄せる。

**したがって「三つが同じ場所へ収束した」とは書けない。** 2つが同じ方向を指し、1つは別の方向で止まった、が正確である。

### 10.3 この一致をどう読むか（成立条件つき）

- 否定側の一致は**同じ判定に3回到達したこと**を意味するが、**その判定が正しいことの証明ではない。** 3つの arc は同じ repo・同じ spec・同じ統括系統の下にあり、共通の盲点を共有しうる。#290 自身が「収束は確信を上げるが証明ではない・両方の passes が同じ盲点を持ちうる」と書いている。
- **義務コンパイルが実際に効くかは、どの arc も検証していない。** #289 は「机上のまま #291 へ渡した」と明記している。**未実証の推奨が2回参照されたことを、実証と読み替えてはいけない。**
