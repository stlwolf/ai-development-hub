# #284 の設計判断を decision へ後追い昇格

## Context / なぜこの作業が始まったか

#284 の closure は「Decision / ADR 昇格は なし」と1行で判定した。owner との振り返りでこの判定は不十分だったと結論したため、確定済みの設計判断を後追いで decision doc に書き起こす。判断そのものは #284 と PR #285 で既に確定しているので、本ユニットが作るのは正本の doc だけである。

本ユニットにはもう一つ目的がある。**episode と issue コメントだけで decision を書けるかどうかを試すこと**である。書けない箇所は埋めずに欠落として報告する、という条件で始まった。これは #284 で入れた read/write 契約が「設計根拠を運べているか」の試験に当たる。

なお本ユニットは 2026-07-28 に plan-first の計画を書き、owner の gate 3 承認を得て 2026-07-29 に執筆した。frontmatter の日付は着手日に合わせている。

## 作業ログ（随時追記）

### 2026-07-28 plan-first — 成果物だけを読み、復元できない箇所を先に洗い出した

情報源を #284 の成果物（episode / issue #284 の本文とコメント5本 / PR #285 の本文と diff と Copilot レビュー / issue #217 / PR に含まれる knowledge item 3件）に限って読み、decision に要る要素が揃うかを1件ずつ突き合わせた。

**先に欠落を洗い出してから執筆計画を立てた**のは、埋められない箇所を執筆中に発見すると、その場の推測で埋めてしまう誘惑が働くためである。計画段階で「これは書けない」と確定させておけば、執筆は残りに集中できる。

洗い出した欠落は6件で、うち2件が decision の中身に直接効いた。

- **G2**: DJ-8（plan と decision への転用形）への回答。issue 本文が要求しているのに、どの成果物にも答えが無い。
- **G3**: 確定版の受け入れ基準10項目。issue 本文は6項目で、その後2回書き換えられている。
- **G4**: SO の生出力（gate 1 / gate 2 / gate 4 / Step 4 のいずれも `tmp/` 配下で消えている）。
- **G5**: claude レーンが3回とも返らなかった原因。
- **G6**: 案N′ を出したレーンの特定。

あわせて、成果物どうしの食い違いを1件見つけた。「why の欠落」の測定値が、issue #284 のコメントと #217 のコメントでは 0/6、episode と PR 本文では「追記型 0/3（#263 含め 0/4）」になっていた。knowledge item `01KYJ76D6KY8RHD2EN3RQ654PK` が「訂正後は 0/6 が 追記型 0/3 になった」と明記しているので 0/6 は訂正前の値である。**訂正後に書かれた #217 のコメントが訂正前の値を運んでいた**ので、後続ユニットの前提を汚す欠陥として親へ上げた。子が他者の書いたコメントを書き換える筋合いではないと判断した。

親の fact-check は PASS で、G1 は親が独立に検証した。#217 のコメントは統括が自分で訂正コメントを投稿した。

### 2026-07-29 owner gate 3 通過 — 判断6点と、raw log からの探索木復元

plan の7章に挙げた判断6点はすべて裁定が出た。

- DJ-8 の答えは本 doc で導出してよい。「#284 が決めた形ではなく本 doc が初めて明文化する」と断り、plan と decision への当てはめは観察であって決定ではない、という書き分けを維持する条件つき。
- `date` は 2026-07-28（作成日）。判断の確定は 2026-07-27 と本文に書く。
- 同じ issue に2本目のブランチを切る点は brief の指定が優先。**規約（1ブランチ = 1 Issue）からの逸脱として本 episode に1行残す**（本節がそれである）。
- **gate 1 は通さない。** 理由は「省いた」ではなく「対象が無い」である。本ユニットは確定済みの判断を書き起こす作業で、新規の設計判断を確定しない。4.1 の転用形は観察として書き決定にしないので、ゼロベース代替探索の対象が存在しない。
- SO は gate 2 と gate 4 を1周に統合し、Step 4（closure 品質）は tier が heavy なら別に残す。

そして **G1 の情報源が見つかった**。worktree を消しても Claude Code のセッション記録は残っていた。統括のセッション文脈を情報源にする案は「再検証できない」ため取り下げられ、**再検証可能なファイル（raw log）から取る**方針で owner 承認が出た。

### 2026-07-29 raw log からの探索木復元 — 親の実測を自分で検算し、2点の訂正が出た

親の実測（案C / D / E / F / H / I はヒットする、案J / L / M はヒット0）を鵜呑みにせず自分で数え直した。**結果は概ね一致したが、2点で親の報告と違った。**

- **ファイル数が違った。** 親は「`*.jsonl` 5本」と報告したが、実際は **6本**（計 2.3MB・950行で、こちらは一致）。
- **案K / 案N も当該ディレクトリではヒット0だった。** 親は J / L / M の3件だけを0と報告していた。実際の内訳は 案A=17 / B=55 / C=22 / D=23 / E=19 / F=9 / G=195 / H=8 / I=8 / J=K=L=M=N=0 である。

**自分の検索が一度ゼロを誤報した。** hub 関連の全セッションディレクトリを横断して案J〜M を探した最初のループで、`grep -l` の出力を `sed` に通した際にパスを丸ごと削り落としてしまい、空文字列を「ヒット0」と読んだ。既知のヒットする記号（案G）を対照に置いて検索機構そのものを検算したところ、実際は案J〜M とも3ファイルでヒットしていた。**「ゼロが出た」ときに、対象が無いのか自分の計測が壊れているのかを先に切り分けなかった**のが誤りである。対照群を置いてから結論すべきだった。

横断検索で判明した構造は次のとおりである。**探索木は1つのセッションに収まっていない。**

- 案A〜I は **#284 の子（worktree 側）セッション**にあり、`差分軸: … → ❌ 理由` という探索木の行がそのまま残っていた。
- 案J〜M は **統括（本体リポ側）セッション**にあり、「反証レーンが出した未探索カテゴリ」という見出しの下に定義が列挙されていた。

### 2026-07-29 出所の切り分け — 3ファイルのうち2本は使ってはいけないものだった

案J〜M がヒットした3ファイルの中身を無検討に使いかけたが、mtime を見て止めた。**3本のうち2本は #284 当時のものではなかった。**

下表のファイル名は**ローカル環境固有の揮発的な識別子で、計測の証跡として載せている**（durable な参照ではない。mtime と行数だけでも同じ切り分けができる）。

| ファイル | mtime | 正体 | 採否 |
|----------|-------|------|------|
| `07e25700…` (2020行) | 2026-07-28 01:50 | #284 当時の統括セッション（開始 2026-07-27T16:47:42Z） | **これだけ使う** |
| `64723163…` (1693行) | 2026-07-29 00:34 | 本 addendum を起草した統括の現行セッション | 除外 |
| `5bf490ae…` (296行) | 2026-07-29 00:36 | **本ユニットを実行している自分のセッション** | 除外 |

自分のセッションの grep 出力が自分の検索対象に混じっていた。除外せずに集計すると、**自分が書いた文字列を「raw log に残っていた証拠」として数える**ことになる。取り下げられたはずの「統括のセッション文脈を情報源にする」案も、`64723163…` を混ぜた時点で復活してしまう。出所の切り分けをしないまま raw log を証拠に使うと、この2つの汚染が黙って入る。

**以降の抽出は `07e25700…`（#284 当時のセッション）だけに限定した。**

### 2026-07-29 復元の強度は案によって違う — A〜I と J〜M は同格に扱えない

`07e25700…` だけから抽出し直した結果、復元の強度が2段に分かれた。

- **案A〜I**: 定義と棄却理由の両方が探索木の行として残っていた。`案A 丸ごと本文側へ移す → 差分軸: 型名の単一化 → ❌ 外部参照2本が宛先を失う・§5 と衝突` のような形である。これは復元と呼べる。
- **案J〜M**: 定義は残っていたが、**棄却理由は残っていなかった**。あの4案は「反証レーンが出した未探索カテゴリ」として列挙された段階のもので、`❌ 理由` を付けた行が存在しない。addendum が表に書いた棄却理由（案K の「的が外れる」など）を raw log で探したが、**「的が外れ」は 0 ヒット**だった。つまりあれは統括が後から再構成した理由であって、当時の記録ではない。
  - 例外は **案L** で、定義そのものが「重心が『書き手の規律』ではなく『スキル間の I/F』に寄る」という批評を含んでいるため、棄却理由が定義に埋め込まれている形で残っている。

したがって decision doc では **A〜I を「復元した」、J〜M の棄却理由を「後から再構成した理由」と書き分ける**。同じ表に並べて同格に見せない。

### 2026-07-29 案J は棄却されていない — ただし「記載漏れ」も当時の記録ではない

addendum は「案J は棄却ではなく案N′ に吸収されており、closure の一覧が J を欠番にしているのは記載漏れである」と指示した。これを raw log で確かめたところ、**「記載漏れ」という判断自体は #284 当時の記録には無い**（0 ヒット）。統括の現行セッションでの再構成である。

ただし**吸収されたという実体は成果物から検算できる**。案J の定義は「Step 3 の型名は残すが『書く内容』を『本文で確認する証拠 / closure で行う disposition』へ変更し、closure で事実を再執筆しない契約にする。本文中の durable anchor を closure がリンク・要約し、欠落時だけ `reconstructed` として補完する」である。着地した案N′ と突き合わせると次になる。

- **採られた**: closure で事実を再執筆しない契約・本文の durable anchor を closure が指す形。これは案N′ の中核そのものである。
- **採られなかった**: Step 3 の「書く内容」列を書き換える案（N′ は Step 3 の表を動かしていない）。欠落補完に `reconstructed` を流用する案（N′ は別マーカー `本文なし: <理由>` を立て、`reconstructed` 流用は「語の意味の乗っ取り」として明示的に退けた）。

つまり **案J は中核が採用され、具体形2点が退けられた**。「棄却」でも「そのまま吸収」でもない。この読みは成果物だけで検算できるので、decision には自分の導出として書く。

**もう1件、addendum も親も気づいていない欠落を見つけた。** closure の棄却案リストは A / B / C / D / E / F / G / H / I / K / L / M / N であり、**案J だけでなく 案G′ も入っていない**。raw log には「案G′ ＝ 案G ＋ read/write 契約」という定義と、「案G′ には反証を当てていない（gate 2 は案G が対象だった）」という記述がある。つまり G′ は反証を通らずに N / N′ に置き換わった中間案で、リストからも漏れている。**欠番は1件ではなく2件**である。

### 2026-07-29 執筆と検証 — 自分の doc から1件の欠陥を検出した

decision doc を `projects/orchestration-engine/docs/decisions/2026-07-28-decision-episode-layer-read-write-contract.md` に書き、#284 の episode の「蒸留シグナル」項に後追いの訂正として昇格先への導線を1行足した。元の「Decision / ADR 昇格は なし」という判定文は消していない。判定が覆った経緯自体が記録なので、上書きせず追記の形にした。

plan の検証項目を全件実行し、**1件の欠陥を自分で検出して直した**。

- 決定の1項が「生産者側の欠陥は実測で 0/6 だった」と書いていた。**これは訂正前の値である。** 同じ doc の末尾で「0/6 は訂正前の値だ」と説明しているのに、本文では訂正前の値をそのまま主張していた。訂正後の値（追記型 0/3・#263 含め 0/4）へ直した。
- **食い違いを見つけた本人が、同じ食い違いを自分の doc に持ち込んだ**ことになる。plan の段階で「訂正後の値を使う」と検証項目に明記しておいたので機械的に拾えた。検証項目に落としていなければ通っていた。

他の項目は通った。ULID は両方26文字、`related[].ref` は in-repo 3件が実在・URL 4件（#284 closed / #217 open / #286 open / PR #285 merged）も実在、制御バイトなし、箇条書きは `-` のみ、命名規約に適合。**decision doc にローカル絶対パス・raw log のパス・作業層（`.oe/`）への参照は入っていない**ことを grep で確認した。client 識別子のスキャンでは hub 以外の org / リポジトリ参照はゼロだった。

#284 の episode に1行足したので、その episode 自身の pointer が壊れていないかも確認した。見出しの重複はなく、pointer 6件はすべて一意な見出しへ解決する（P2 を満たす）。

**この確認で成果物の食い違いをもう1件見つけた。** #284 の episode は自己適用の結果を「本文の**5節**を pointer で指して書いた」「実際に grep で照合して**5件**とも解決することを確認した」と書いているが、**実際に指されている見出しは6件ある**。統括の着地コメントは「実 pointer 6件すべて一意な見出しへ解決」と書いており、こちらが正しい。子の自己申告が1件少ない。

実害は無い（6件とも解決するので契約違反ではない）。しかし**自己申告した検証件数と実際の件数が合っていない**わけで、これは #284 が測定で見つけた欠陥（自己申告ラベルと実態が2本で食い違っていた）と同じクラスである。自己申告の数え上げは、それ自体が検算対象になる。本ユニットで見つけた成果物どうしの食い違いは、測定値（0/6 と 0/3）と合わせて2件になった。
