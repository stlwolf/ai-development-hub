### 食い違い1 — 「使用量上限だった」は出典に無い（候補B・item の記述を変えた）

brief は「原因は使用量上限だった」と断定している。**brief が挙げた3本の meta のどれにも、原因を名指しする情報は無い。** 失敗側は `exit_code=124`（`timeout` による kill）と `timeout_status=timeout_empty` だけで、stdout も stderr も 0 バイトである。

**この点で自分の探索が一度足りていない。** meta と `.oe/` と repo 内を検索した時点で「brief 自身の一文以外に記録は無い」と書いたが、**brief が `Refs #299 #303` と指定していた #303 を開いていなかった。** 開いたら、そこに根拠が記録されていた。

> 空だった時間帯は owner が使用量上限（5時間窓）のリセット待ちを実際に踏んだ時間帯と重なる。

つまり原因の帰属は無根拠ではなく、**owner の実体験という状況証拠**に基づく。#303 はさらに前日 2026-08-02 22:12 の 941 秒成功と、空だった時間帯（2026-08-03 04:07〜04:47）も記録している。**統括の要約が省いていたのは根拠の所在であって、根拠そのものではなかった。** 訂正して記録する。

**それでも item の作りは変えない。** meta から確実に言えるのは、同じ内容の依頼が後に **888 秒・exit 0** で完了したこと、888 秒は空返し2回が使った **1200 秒の budget の 74%** であることで、「この依頼は budget では終わらない」という読み方が成り立たないところまでである。

### 一般法則として書かないための処置

どちらの item も根拠は同一 arc（#299）の1事例である。以下を item 自身に書いた。

### わかったこと

- **収穫した item の「近さ」は `trigger` では測れない。** `trigger` は領域の語彙で書かれるので、同じ構造でも領域が違えば文字列は似ない。本文まで読まないと同型は見つからない（3レーンが指摘した近傍3件は、いずれも本文の中ほどに1文だけ入っていた）。
- **同じ構造が4つの arc に散らばっていて、どれも一般の形で着地していないことがある。** それ自体が「一般の item を立てる根拠」になる。逆に、既存 item に注記として入っていることを「着地済み」と読むと、領域の違う消費者には届かない。
- **notify すべき知識が store に在っても、注入されなければ効かない。** `01KYYHGNRJ…` は #299 の2日前に収穫され、#299 の失敗を予測していたが、brief の slot に載っていなかった。**store の充実と注入の網羅は別の指標である。**

### 原則（Pattern / Anti-pattern）

- **NG**: 外部レビューの指摘を1箇所の修正で閉じ、同じ型が他所に無いかを確かめない。**OK**: 閉じる前に「箇所か型か」を決め、型なら母集団を列挙して当てる。ただし**この処方の有効性はまだ観測されていない**（item A に明記した）。
- **NG**: 空返しの meta を原因の証拠に使う。**OK**: 値は「budget 到達で kill された」までと読み、原因を分けたいなら時間をおいて再実行する。
- **NG**: 1事例から立てた項の留保を、本文末尾や `exclusions` の末尾に置く。**OK**: 冒頭で格を宣言する。末尾の但し書きは、先に読まれた本文を打ち消さない。
- **NG**: 既存 item との重複を `trigger` の文字列一致で判定する。**OK**: 近傍候補は本文まで読む。**症状の語彙が違うだけの同型を落とす。**
