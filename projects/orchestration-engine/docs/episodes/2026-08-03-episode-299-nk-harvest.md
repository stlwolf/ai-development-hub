### 食い違い1 — 「使用量上限だった」は出典に無い（候補B・item の記述を変えた）

brief は「原因は使用量上限だった」と断定している。**しかし brief が挙げた3本の meta のどれにも、原因を名指しする情報は無い。** 失敗側は `exit_code=124`（`timeout` による kill）と `timeout_status=timeout_empty` だけで、stdout も stderr も 0 バイトである。`.oe/` 配下と repo 内も検索したが、使用量上限を示す記録は brief 自身の一文以外に見つからなかった。

**代わりに meta から確実に言えることがある。** 同じ内容の依頼が、後に **888 秒・exit 0** で完了した。888 秒は空返し2回が使った **1200 秒の budget の 74%** である。つまり「この依頼は budget では終わらない」という読み方は成り立たない。

そこで item B は原因の名前に依存しない形にした。**「meta の3フィールドは原因を運ばない。budget 内で完了する再実行が出るまで、時間切れと結論できない」**が確実に言える線である。使用量上限は統括の読みとして本文に置き、item の主張の根拠には使わない。

### 食い違い2 — 「同一プロンプト」は厳密には同一でない（候補B）

2本の `prompt.txt` を差分で比べたところ、**本文は完全に一致し、成功した再実行の側にだけ末尾3行（`ワークスペース: …` の2行と空行）が足されていた。** `-w` を付けたかどうかの違いである。依頼内容は同じなので候補B の筋は変わらないが、「同一プロンプト」と書くと厳密でないので、item では「同じ依頼（`-w` の有無だけが違う）」と書く。

### 食い違い3 — 「同じ型」の中身が候補A の記述とずれる（item の記述を変えた）

brief は screen-marker に残っていた型を「版依存の前提を自分で置く／対象の死後も緑になる」と2つ併記している。**しかし E6c を読むと、この2つは同じ箇所の性質ではない。**

- E5 で直した `hook-contract` の欠陥 = 生涯累計で1件でもあれば `ok`（対象の死後も緑）
- E6c で見つかった `screen-marker` の欠陥 = 版に固定された前提を自分で置き、しかも `ok` に構造的に到達できない

2つをまたぐ共通の型は、episode 自身の言葉では **「検査器が、自分の検出対象と同じ壊れ方をしている」** である。item A はこの言い方を採る。具体的な欠陥の形は箇所ごとに違い、**違うからこそ「直した箇所と同じ症状」を探すだけでは隣が見つからない**、という点が候補A の肝である。

### 判断1 — 候補A と `01KYW0BPJNHP94TNX0VG4G11TX` は分離する

### 判断2 — 候補B と `01KYYHGNRJ926N4CTTS4PE8GQH` は分離する（ただし軸を絞る）

ここが本単位でいちばん迷った。**brief は候補A についてしか近傍を名指ししていないが、候補B には brief が挙げていない最近傍があった。** 対照を17件すべてに当てて見つけた。しかも、この見落としの構造は候補A の教訓（指摘は1件ずつ来るが型は横に広がる）そのものである。

`01KYYHGNRJ…` は #293 から収穫された item で、行動変更の3つ目にこう書いてある。

> 未返却の原因を環境の恒常的性質と結論しない。**`timeout_status` と `exit_code` と stdout の中身を見て原因を分ける。**

候補B の「原因を確かめずに `timeout` と読むな」は、この処方とほぼ重なる。**単純に item 化すると重複である。**

分離を選んだ理由は、**#299 がこの処方の反例だから**である。#299 の空返しは `timeout_status=timeout_empty` / `exit_code=124` / stdout 0 バイト（stderr も 0 バイト）で、**3つとも本物の時間切れと同じ値だった。** 処方どおりに見ても原因は分かれない。`01KYYHGNRJ…` が挙げている使用量上限の例は `error_partial` と本文の文字列で分かれるケースで、#299 はその条件を満たしていない。

- 扱う軸を**診断だけ**に絞った。`01KYYHGNRJ…` の運用の軸（partial で閉じるなら差し戻す経路を用意する）には触れない。

- item 本文に `01KYYHGNRJ…` の反例であることを明示した。

**統合（既存 item の本文を書き換える）は採らなかった。** 反例を既存 item の中へ静かに畳むと、その item に既に付いている観測履歴と本文の対応が崩れる。supersede は段6（owner の別 PR）の領分で子の判断で動かすものではない。別 item にして相互参照を張るのが append-only の store に合う。

### 走査して見つけた、本単位のスコープ外の事実（surface のみ）

**`01KYYHGNRJ926N4CTTS4PE8GQH` は #299 の brief に注入されていなかった。** #299 の episode の Step 6 は注入された6件を列挙しているが、そこに含まれていない。この item の `observations` は現在も空である。

本単位では何もしない。理由は2つある。注入されていない item に観測を書き戻すと、台帳の「注入された分母」が壊れる。そして突合の仕組みを直すのは本単位のスコープ外である。**統括へ surface する。**

### 一般法則として書かないための処置

どちらの item も根拠は同一 arc（#299）の1事例である。以下を item 自身に書いた。

- 本文末尾に「観測範囲」の節を置き、何を観測して何を測っていないかを書いた（item A は反実仮想を検証していないこと、item B は「どれだけ時間をおけば返るか」を測っていないこと）。
- `exclusions` の最後に「位置の一般法則としての適用」を入れ、範囲外への外挿は根拠を持たないと明示した（既存 item `01KYW0BPJ…` / `01KYYHGNRJ…` と同じ書き方に合わせた）。
- `prediction` に観測の出どころ（#299 の1事例）を書き込み、予測が一般則でなく仮定であることを読み取れるようにした。
