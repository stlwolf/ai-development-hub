# #309 フックの発火記録を残す

## なぜこの作業が始まったか

止める側のフック3本（`block-destructive.sh` / `block-force-push.sh` / `cc-lint.sh`）は、発火したことを1行も記録しない。そのため「強制点が本当に発火したか」を当事者以外が確かめる手段が無い。#305 のアンカー設計が3ラウンド続けて反証された原因は、遡ると全部この1点に帰着した。閉ループ制御の5要素でいうと、フックは Actuator を担えているのに Sensor を担っていない。

本単位は plan-first である。計画を作って STOP し、plan doc のパスを親へ報告するまでが終端で、実装はそこから親が位置を指定する。

## この単位の設計上の中心 — 正面から衝突する2つの要求

1. 記録の失敗で操作をブロックしてはいけない。3本とも先頭に `set -euo pipefail` があり、Cursor は3本すべてに `failClosed: true` を付けている。記録の1行が失敗してスクリプトが非ゼロで落ちると、普通のシェルコマンドがブロックされうる。3本は3ツール全部に配られているので、影響範囲は日常の作業全体である。
2. しかし失敗を握り潰すと、欠測が見えなくなる。`|| true` や `2>/dev/null` で潰すと、「記録できなかった（環境エラー）」と「記録すべきイベントが無かった」が区別できない。それはこの issue が解こうとしている問題そのものの再生産である。

## Step 1 — 触る対象の実物を読んだ（一次確認）

読んだもの: `canonical/hooks/scripts/block-destructive.sh` / `block-force-push.sh` / `cc-lint.sh` の全文、`cursor.hooks.json` / `codex.hooks.json` / `claude.hooks.json`、`canonical/hooks/README.md`、`canonical/hooks/scripts/oe-prompt-receipt.sh` の全文。

確定した事実を、後段の設計が乗る土台として列挙する。

- **3本とも、終了経路は `allow()` と `deny()` の2つの関数に集約されている。** どちらも末尾で `exit` する。`block-destructive.sh` と `block-force-push.sh` は `main` の最後が `allow`、`cc-lint.sh` は `main` の最後が `deny` で、途中の分岐もすべてこの2関数のいずれかを呼んでから抜ける。つまり**記録を差し込む一点は `allow()` / `deny()` の中である**。判定ロジック本体には触らなくてよい。
- **ただし「すべての終了が allow/deny を通る」は `set -e` が発動しない限りの話である。** 3本とも `set -euo pipefail` なので、途中のコマンドが失敗すれば allow/deny を通らずに非ゼロで落ちる。この経路は既存の挙動であって本単位が作るものではないが、記録を足すときに**新しくこの経路を増やしてはいけない**という制約になる。
- **stdout は制御プロトコルの通信路である。** `allow()` は `CURSOR_PROJECT_DIR` か `CLAUDE_PROJECT_DIR` が立っているとき `{"permission":"allow"}` を stdout に出す。記録は絶対に stdout へ出せない。
- **Cursor の `failClosed: true` は3本すべてに付いている**（`cursor.hooks.json` の実物で確認）。README の「fail-open リスク」節にも「Cursor: `failClosed: true` を設定済み。フック失敗時もブロックする」と明記されている。Claude Code / Codex には fail-close 機構が無く、exit code 0/2 以外は non-blocking である。**つまり同じ1本のスクリプトが、ツールによって失敗時の意味が正反対になる。**
- **`oe-prompt-receipt.sh` が、ほぼ同じ問題を既に解いている。** 追記は best-effort で `exit 0` 固定、環境エラーは `oe-receipt-diag.jsonl` という**別の診断ファイル**と stderr に落とす。ヘッダコメントに「失敗を握り潰さない: 環境エラーとデータ不在を別に扱う」と明記されている。これは本単位が探している両立の実例である。ただし同スクリプトは `set -uo pipefail`（`-e` 無し）の advisory hook であり、fail-closed な3本とは前提が違う。

昇格の印: 記録の失敗を第2の経路（診断ファイル）へ逃がして判定経路に触れさせない型は、#309 固有ではなく fail-closed なフック一般に効く設計かもしれない

## Step 2 — 中心の仮定を実測して、半分が崩れた

gate 1 の探索へ入る前に、設計全体が乗っている bash の仮定を実機で測った。測ったのは「記録処理の失敗が、`set -euo pipefail` の呼び出し元を殺さないようにできるか」である。台本は `tmp/probe-errexit.sh` と `tmp/probe-errexit2.sh`。

当初の仮定は「記録関数をテスト文脈（`record || :`）で呼べば、`set -e` は関数本体の中では抑止されるので安全」だった。**この仮定は半分しか正しくなかった。**

- 抑止された（`record || :` で呼び出し元は生きる）: 関数内の `false`、深くネストした失敗、書けないパスへの追記、`command not found`、`pipefail` + 早期終了 consumer。
- **抑止されなかった: `set -u` 違反（未割り当て変数の参照）。呼び出し元ごと rc=1 で死ぬ。** これが致命的なのは、Cursor が `failClosed: true` を付けているため、**記録処理の中でうっかり `${TMUX_PANE}` のような変数を既定値なしで参照しただけで、普通のシェルコマンドがブロックされる**からである。しかも変数参照は記録処理でいちばん書きたくなる部分である。

さらに追試したところ、**サブシェルへ隔離する形（`( record ) || :`）は `set -u` 違反も `exit N` も封じ込める**ことが分かった。自分自身へのシグナル（`kill -TERM $$`）だけは貫通するが、これは記録経路の現実的な失敗ではない。

macOS の system bash 3.2.57 と Homebrew の bash 5.2.37 の両方で同じ結果になることも確かめた。フックが最小 PATH で起動されて `/bin/bash` に解決される場合を考えると、ここは確かめておく必要があった。

この実測の結果、DJ-1 の書き方は「テスト文脈で呼ぶ」から「**サブシェルへ隔離して呼ぶ**」へ変わった。規律（全変数に `:-` を付ける）でも回避できるが、規律は破られたことを検出できないのに対し、サブシェル隔離は破られても封じ込む。fail-closed な面を触っている以上、規律ではなく構造で止める側に倒す。

昇格の印: 「テスト文脈は set -e を抑止するが set -u は抑止しない」は bash 一般の非自明な落とし穴で、fail-closed なフックを触る作業すべてに効く negative knowledge の候補

## Step 3 — 記録量を推測でなく実測で見積もった

DJ-3（allow を毎回1行残すか）とローテーション方針は、記録量の桁が分からないと決められない。桁を推測で置くとローテーションの要否そのものが恣意的になるので、実測した。

Claude Code の transcript から Bash tool の呼び出しを日別に数えた（直近14日・transcript 200 件を上限にサンプリング）。

- 1日あたり約 200〜670 回。中央値はおおよそ 450 回。
- これは **下限**である。サンプリング上限で切っているうえ、Cursor と Codex の分を含んでいない。3本のフックは3ツール全部へ配られているので、実際の母数はこれより大きい。

フック3本がそれぞれ全 Bash 呼び出しで発火するので、毎イベント1行なら **1日あたり約1500行**になる。1行 180 バイト程度として **1日あたり約 270KB** である。

比較の基準として `~/.claude/state/oe-events.jsonl` を見ると、983 行 / 328KB を数か月かけて溜めた量である。owner はこの 317KB を「読み出しが互いのノイズを踏む」理由に挙げて別ファイル化を指示している。**毎イベント1行の allow 記録は、その台帳とほぼ同じ量を1日で作る。**

この数字は DJ-3 の判断を変える。allow を残す目的は owner が挙げたとおり陽性対照（一定期間0件＝フックが動いていない、と読めるようにする）であって、毎回の forensics ではない。**目的が生存確認なら、必要なのは毎回の1行ではなく「その日そのフックが動いた」という印1つで足りる。** 探索木 DJ-3 の案C2（deny は1行 JSONL・allow は日単位の集計）を本命へ上げる根拠がここで数値として立った。

## Step 4 — 陽性対照に使える具体的なコマンドを確定した

「記録0件」を「発火しなかった」と読むには、経路が生きていることを別に示す対照が要る（NK item 01KYMRE1N7N0J8VP3CBZZEZ8Q3）。対照は **発火するが、万一フックが死んでいて実行されても無害** でなければならない。ここが難しいのは、止める側のフックの対象がまさに破壊的コマンドだからである。`rm -rf /` を対照に使うわけにはいかない。

実スクリプトへ payload を通して確かめた（台本 `tmp/probe-hooks.sh`）。3本すべてに無害な対照が在る。

| フック | 対照コマンド | 結果 | フックが死んでいた場合 |
|---|---|---|---|
| `block-destructive.sh` | `echo "<SQL の DROP TABLE 文> sentinel309"` | deny (rc=2) | `echo` が文字列を表示するだけ |
| `block-force-push.sh` | `git push --force no-such-remote-309` | deny (rc=2) | 存在しない remote で git がエラー終了する |
| `cc-lint.sh` | `git commit -m "sentinel309 bad"` | deny (rc=2) | 使い捨て repo で実行すること（staged 変更があると本当にコミットしうる） |

`block-destructive.sh` が使えるのは、SQL の判定だけが行頭固定でなく**文字列の途中で一致する**ためである。`mkfs` は `^mkfs`、`dd` は `^dd` なので無害な対照を作れない。SQL 判定のこの性質が、たまたま安全な対照を1つ残していた。

この検査を組む過程で実地の証拠が1つ増えた。**最初に対照コマンドを普通に shell から流したら、生きている `block-destructive.sh` がその検査コマンド自体をブロックした。** 検査の payload を外側のコマンド行に置いた結果、フックが外側の行を読んで発火したためである。避けるには payload をファイルの中で組み立てる必要がある。これは実装フェーズのテスト設計に直接効くので記録しておく。

昇格の印: 止める側のフックを検査するとき、検査コマンド自身がフックに引っかかる。この「検査器が被検査対象に食われる」構造は他の強制機構の検査でも起きうる

## Step 5 — gate 1（ゼロベース探索 SO）と、その指摘の検算

探索木を `tmp/dj-309-exploration-tree.md` に外部化し、選択肢拡張テンプレを付けて3レーンへ投げた。プロンプトは `tmp/so-309-gate1-prompt.md`。

### レーンの実返却状況（正直に書く）

| レーン | モデル | 結果 |
|---|---|---|
| cursor（1回目・`auto`） | `Auto Balance` に解決 | `success_empty`。11秒で「Auto routed to Cursor Grok 4.5」の1行だけを返し、本文なし。実返却なしと扱う |
| cursor（2回目・明示指定） | `cursor-grok-4.5-high` | 実返却あり（13.7KB）。出力 `tmp/so-309-gate1-cursor/` |
| codex | `gpt-5.6-sol`（`model_resolved_source=config` なので観測値ではない） | `timeout_empty`（480秒）。最終回答を stdout へ出さないまま打ち切り |
| claude | `opus` / effort=high | 本節執筆時点で実行中 |

`auto` のまま投げた cursor レーンが空で返ったので、モデルを明示して投げ直した。so-compare スキルが警告しているとおり、`auto` は実行ごとに解決先が変わるので、レーンの多様性を主張するなら明示指定のほうが確実だった。

codex レーンは最終回答こそ出さなかったが、stderr に残った作業痕を見ると**私と同じ bash の実測を独自に行い、同じ結論に達していた**（`nounset_direct` で親が死に、`nounset_subshell` で親が生きる）。実返却としては数えないが、Step 2 の実測を独立に裏付ける材料にはなっている。

### cursor レーンの指摘3点を、鵜呑みにせず自分で検算した

台本は `tmp/probe-so-claims.sh` と `tmp/probe-bypass.sh`。

**指摘1（採用・設計が変わった）**: 「`( record ) || :` でもサブシェル内の `set -e` は効かない」。検算して**そのとおりだった**。`( echo STEP1; false; echo STEP2 ) || :` は STEP1 と STEP2 の両方を出す。`||` の左辺という文脈が、サブシェルの内側まで errexit を抑止する。

これは Step 2 で私が出した結論の穴だった。サブシェル隔離は「親を殺さない」ことは保証するが、「記録処理が途中で失敗したらそこで止まる」ことは保証しない。失敗したまま後続が走り、壊れた状態で記録を書きうる。

そこで**別プロセス（独立したスクリプト）ならどうか**を追加で測った。結果は `( bash recorder.sh ) || :` で STEP1 だけが出て STEP2 は出ない。**プロセス境界を越えると errexit の抑止文脈は伝播せず、レコーダーは自分の `set -e` を保てる。** つまり別プロセスのレコーダーは、親を殺さないことと、自分の中で失敗したら止まることを同時に満たす。同一シェル内の関数では両立しない。

この検算の結果、DJ-4 の本命が「各スクリプトに内蔵する関数」から「**独立したレコーダースクリプトを子プロセスとして起動する**」へ変わった。これが gate 1 で出てきた、初期案セットの外にある案である。

**指摘2（採用）**: 「サブシェルでも stdout は親へ貫通する」。検算して そのとおり。記録側が1行でも stdout へ出すと `{"permission":"allow"}` に混ざる。呼び出し側で `>/dev/null` を付ける二重の防御を入れる。

**指摘3（棄却・SO が誤り）**: 「`cc-lint.sh` は `&&` を含む非 commit コマンドで allow/deny に達する前に落ちる」。実スクリプトへ実際に通して検算したところ、`cd /tmp && ls` / `echo a && echo b` / `make build && make test` はすべて rc=0 の allow だった。**この指摘は成立しない。**

ただし指摘3が指していた「allow/deny を通らずに落ちる経路が在る」という論点自体は正しい。別の入口で実証できた。**`jq` が PATH に無いと3本とも rc=127 で落ち、allow/deny のどちらも通らない。** これは案B1（allow/deny の中に記録を置く）が原理的に記録できない経路である。Cursor では failClosed なのでコマンドはブロックされるが、記録は1行も残らない。

**指摘4（採用・DJ-7 が変わった）**: 「allow の定常流を陽性対照にするのは不十分」。理由は2つで、どちらも私が見落としていた。(a) allow が0件なのは「フックが死んでいる」だけでなく「エージェントが Bash を使っていない（idle）」でも起きる。(b) issue 本文が既に書いているとおり、Codex は trust されていない hook を警告ゼロで黙って skip する。どちらの場合も allow は0件になり、区別できない。

owner が gate 0 で確定した「止めたときも通したときも記録する」という制約は動かさない。動かすのは**その記録に何を言わせるか**である。allow の流量は受動的な傍証にとどめ、陽性対照の主柱は**意図的に撃つ既知のプローブ**（Step 4 で無害なものを3本分確定済み）に置く。プローブなら idle と死を区別できる。

昇格の印: 「errexit の抑止文脈はサブシェルには伝播するがプロセス境界は越えない」という性質は、fail-closed な機構に副作用のある処理を足す一般的な型として使える

## Step 6 — claude レーンが設計を作り替えた（gate 1 の本体）

claude レーン（`opus` / effort=high・725秒・32.9KB）が、cursor レーンとは別の3点で初期案を崩した。gate 1 を回した価値はここに出た。

### 指摘① 要求Aには鏡があり、そちらが危険である（採用・制約に追加）

owner が確定した制約は「記録の失敗で操作をブロックしない」だけを言っている。**鏡側、つまり「記録の失敗でブロックが解除されない」が書かれていない。**

`deny()` は `exit 2` に到達して初めてブロックになる。到達前に死ぬと exit code は 1 や 127 になり、Claude Code と Codex では 0/2 以外が non-blocking なので、**止めるべきコマンドが通る**。要求Aの違反（余計に止まる）は騒がしくてすぐ気づくが、鏡側の違反（止まらない）は静かで、しかも取り返しがつかない。

私は要求Aの側だけを見て設計していた。制約に1行足す。

### 指摘② 二層構造には中抜けがある（採用・設計が変わった）

案A3 の層1は「個別イベントの記録失敗」、層2は「フックが動いていない」を担う。この2つの間に第3の故障が挟まっている。**呼ばれたが、判定を出す前に死んだ場合**である。この経路では allow/deny を通らないので記録が増えない。しかし他のコマンドでは記録が増えるので層2の「一定期間0件」も鳴らない。沈黙のまま強制点が抜ける。

私は探索木で案B1 の弱点として「この経路は記録されないまま残る」と正直に書いていたのに、**それが陽性対照の穴でもあることを接続できていなかった**。そして解決を DJ-2 の中（ラッパーを入れるか）だけで探していた。

claude レーンの解は、ラッパーを持ち出さずに**入口にも記録を置く**ことだった。`inv − (allow + deny)` が「呼ばれたのに判定を出さずに死んだ回数」になる。1本のログの有無を眺めるのではなく、独立に取った2点の差が機械的に欠測を指す。Step 1 で実証した `jq` 不在の rc=127 経路も、これで初めて数として現れる。

複式記入という発想が初期選択肢に無かったのは、DJ-2 が「記録を差し込む位置」を `allow()` / `deny()` の**中**に限定した時点で、入口という地点が選択肢から消えていたからである。

### 指摘③ 記録の表現を1バイトまで落とす（採用・DJ-3 の対立が消えた）

私は DJ-3 を「毎回1行の JSONL か、日単位の集計か」で対立させていた。claude レーンは**1イベント1バイトの追記**を出した。ファイルサイズが件数、mtime が最終発火時刻になる。

実測で確かめた（`tmp/probe-a1.sh`）。並行60プロセス × 50回の追記で 3000/3000 バイト、ロストなし。所要は 0.102 ms で、子プロセス起動（8.6 ms）の約85分の1。100万コマンドで 1MB なので**ローテーションが不要**になる。

これで DJ-3 の対立そのものが消えた。日単位集計に必要だった `date` の exec も日境界という概念も要らない。私が Step 3 で量を実測して案C2 へ寄せた判断は方向としては正しかったが、**表現を落とすという軸を探索していなかった**。

なお私が Step 5 で採った「独立したレコーダースクリプトを子プロセスで起動する」案は、これで不要になった。プロセス境界は errexit の抑止文脈を遮断するという利点があったが、tally はサブシェル隔離だけで足り、fork のコスト（3本 × 全 Bash 呼び出しで1コマンドあたり約25 ms）を払う理由が無くなった。**gate 1 の中で自分の案が二度差し替わったことになる。**

私は共通ライブラリ案（D1）を「`source` の失敗が新しい fail-closed 経路になる」という理由で落としていた。claude レーンは「隔離サブシェルの中で source すればその失敗も封じ込まれるはずで、しかもあなたはそれを測っていない」と指摘した。

### 指摘⑤⑥ 検算して扱いを変えたもの

- **⑤「隔離サブシェルの中では最初の失敗で abort し、診断行に到達しない」→ 反証。** 実測では関数形・直書き形のどちらでも診断行に到達した。`||` の左辺という文脈が errexit を抑止するためである。ただし呼び出し文脈が変われば話が変わるので、`set +e +u` を中に明示するのは保険として残す。**確認済みの中断の修正ではなく防御である**と書き分ける。
- **⑥「陽性対照が配備物を通っていない」→ 採用。** 私の `tmp/probe-hooks.sh` は repo のコピーを直接叩いていた。実際に走るのは `~/.claude/hooks/` の symlink 経由である。repo コピーを叩く検査は dangling symlink・sync 漏れ・`settings.json` からの脱落という、いちばん怖い故障モードを検出できない。この repo は過去にまさにその形（worktree から sync してリンクが張り替わり、削除で dangling になってフックが無言で止まる）を踏んでいる。**対照は配備先のパスを叩く形に変える。**

### 両レーンが同じ誤りをした件

cursor と claude が**独立に**「`cc-lint.sh` は `&&` を含む非 commit コマンドで落ちる」と読んだ。2レーン一致は強い signal だったが、実スクリプトへ通すと rc=0 の allow だった。

## Step 7 — gate 2（設計SO）で、自分の測定の当て方が誤っていたと分かった

改訂設計を `tmp/design-309-revised.md` にまとめ、gate 2 として3レーンへ投げた（プロンプト `tmp/so-309-gate2-prompt.md`）。cursor レーン（`cursor-grok-4.5-high`）が最初に返した指摘が重かった。

### 指摘1（採用・私の測定誤り）: 「fork なし・0.102 ms」は測る対象を間違えていた

私は設計書に「tally は fork も exec も起きない。0.102 ms」と書いた。しかし**測ったのは素の `printf 'x' >> file` であって、設計書自身が書いた `hfr` の形ではない**。設計の `hfr` は `( set +e +u; mkdir -p ...; printf ... ) >/dev/null || :` であり、サブシェルは fork するし `mkdir` は外部コマンドの exec である。

測り直した（`tmp/probe-hfr-cost.sh`）。

| 形 | 実測 | 1 Bash コマンドあたりの追加（6回分） |
|---|---|---|
| 素の `printf` 追記（当初測った形） | 0.176 ms | 1.1 ms |
| **設計書が書いた形**（サブシェル + 毎回 `mkdir -p`） | **2.189 ms** | **13.1 ms** |
| サブシェルのみ（`mkdir` を外す） | 0.567 ms | 3.4 ms |
| 独立レコーダーを子プロセスで起動 | 7.450 ms | 44.7 ms |

設計書の主張は実測の12倍ずれていた。**自分に都合のよい数字を、別の構成から持ってきていた。** 指摘されるまで気づかなかった。

### そこから出た形（採用）

速い経路を builtin だけにして、失敗したときだけ隔離へ落とす。

```bash
printf 'x' >> "$T_INV" 2>/dev/null || { ( set +e +u; mkdir -p ...; printf ... ; 診断 ) >/dev/null 2>&1 || :; }
```

実測 0.186 ms で、素の追記とほぼ同じ。1 Bash コマンドあたり 1.1 ms（現行のフック3本ぶん約35 ms に対して +3%）。書けない状態でも呼び出し元が生き残ることも確認した。

この形は `set -u` の心配も要らない。参照する変数はスクリプト先頭で `${...:-}` 付きで代入済みのものだけで、hot path は単一の builtin だからである。**Step 5 で採った「独立レコーダーを子プロセスで起動する」案は、これで最終的に不要になった。** プロセス隔離が要るのは複数段の処理を保護したいときで、hot path が1操作しかないなら守るべき途中が存在しない。複雑な処理（`mkdir`・診断）は稀な fallback 側に寄せ、そちらは隔離する。

なお fast path の `2>/dev/null` は握り潰しではない。失敗は直後の `||` が捕まえて fallback へ渡し、fallback が診断を残す。抑えているのはシェルが出す重複のエラー文言だけである。

### 指摘2（採用）: 陽性対照が Claude の配備パスしか見ていない

設計書には「対照は `~/.claude/hooks/` 側を叩く」と書いた。しかし配備先は3系統ある（`~/.cursor/hooks/` / `~/.claude/hooks/` / `~/.codex/hooks/`）。Claude だけ叩いて緑にすると、**Cursor や Codex の側だけが脱落している状態を見逃す。** 受け入れ基準の「3ツールへの影響を確認した」に正面から関わるので、対照は3配備パスすべてに置く。

### 指摘3（採用）: 失敗とハングを混同していた

設計書に「隔離は exit code を変えないので鏡側も満たす」と書いたが、`( ... ) || :` が捨てるのは**終了した子の exit code** である。子が終わらなければ親も進まない。`deny()` の中で記録がハングすると `exit 2` に到達せず、Claude と Codex では non-blocking になって**止めるべきコマンドが通る**。要求Aの鏡が破れる。

これは正しい指摘である。緩和はするが消えない（記録経路をローカル FS の単一 builtin に限る・ネットワークやロックを持ち込まない）ので、**残る危険として正直に書く**。

### 指摘4（採用）: tally には時刻が無いので窓判定ができない

「直近の窓で判定する」と書いたが、tally が持つのは累計サイズと mtime ひとつだけで、イベントごとの時刻が無い。窓の中の増分を見るには**前回サイズのスナップショット（ウォーターマーク）が要る**。これが無いと、過去に1回起きた中抜けが累計差分を永久に汚し続ける。読み出し側にウォーターマークを持たせる。

### 指摘5（採用）: `inv − (allow + deny)` は純粋な指標ではない

この差には3つの異なる事象が混ざる。(a) 判定前に死んだ。(b) 判定は配送したが出口の tally 追記だけ失敗した。(c) 制御出力の後・tally の前で kill された。(b) は diag に痕が残るので、**差分と diag を併読して切り分ける**規約を読み出し側に置く。差分だけを見て「中抜け」と読まない。

### 指摘6（採用）: ツールごとの帰属ができていない

置き場をツール横断で共有すると、Cursor が死んでいても Claude が撃てば mtime が新しくなり、**偽の緑**になる。tally のパスにツール次元を足す（`tally/<tool>/<hook>.<slot>`）。ツールは `CURSOR_PROJECT_DIR` / `CLAUDE_PROJECT_DIR` の有無で判別し、どちらも無ければ `unknown` にする（Codex を名乗らせない。判別できないものを推測で埋めない）。

昇格の印: 「主張の根拠にした測定値が、主張している構成とは別の構成のものだった」という誤りの型は、性能を根拠に設計を選ぶ場面すべてで起きうる

## Step 8 — gate 2 の残り2レーンと、自分の論証の誤りが1件見つかった

### claude レーンが単独で出した、私の論証の誤り（採用）

ガードを書いたとき `[ -e X ] && [ ! -f X ] && return 0` と書いた。**このプラン自身が「`a && b` の形で書くな、条件が偽のとき `set -e` が発動する」と書いている、その規約を書いた直後に破った。** `if / then` へ直した。規約を知っていることと守れることは別だという実例なので、plan の該当項目に「執筆中に1度踏んだ」と書き添えた。

claude レーンは **「死を数えるのをやめて死を消す」**（3本に `trap` を張り、想定外の終了を必ず deny へ落とし、`jq` 依存を判定の手前から外す）を主柱に推した。採れば複式記入そのものが不要になり、本プランの複雑さの大半が消える。ただしこれは **Actuator の挙動を変える**変更で、今日は `jq` が無いと素通りしているものが止まるようになる。#309 は Sensor を足す issue なので、スコープ外として owner へ surface した。**プランの前提を置き換えうるので、実装着手前に判断してもらう項目の筆頭に置いた。**

## Step 9 — gate 3（owner 判断）で trap を採り、plan を改訂した

2026-08-09、owner が gate 3 で判断を下した。**私が「実装に入る前に決めてほしい」と surface した trap 案を採る。** 理由は「`jq` は実際に環境へ入っており、パッケージ化するなら必須にすればよい」で、私が引き換えとして挙げた「`jq` 不在で日常が止まる」はこの環境では成立しない、というものだった。

### 統括が足した論点 — trap は tally の置き換えではない

私が surface した書き方は「trap を採れば複式記入が不要になる」までで止まっていた。統括はそこに**私の書き落としを1つ足した**。

> trap は複式記入の置き換えであって、発火記録の置き換えではない。走らないフックに trap は張れない。

これは正しい。私は trap の効果を「死を数える必要がなくなる」と書きながら、**その死が「走った上での死」に限られること**を明示していなかった。本設計がいちばん恐れているのは Codex の silent skip のような「そもそも走らない」型で、そこには trap が届かない。もし統括がこれを足さなければ、「trap を入れたから tally は要らない」と読める余地が残っていた。**#309 の中心を落としかねない書き落としだった。**

改訂版では、2つの機構を「担当する故障」で対にして表に起こし、混同できない形にした。

### 実測してから書いた

trap は強制の挙動を変えるので、書く前に実機で確かめた（`tmp/probe-trap.sh` / `tmp/probe-trap2.sh`）。

- 正常系は壊れない（allow は rc=0・deny は rc=2）。**EXIT trap は正常終了でも発火する**ので、`0` と `2` を素通しする分岐を忘れると allow が deny に化ける。
- 内部エラー・`set -u` 違反・想定外の exit・**`jq` 不在**がすべて rc=2 へ収束する。今日 `jq` を外すと rc=127 で素通りするので、ここが本命だった。
- 収束時の stdout が**妥当な JSON** であることを確認した（`jq .` に通した）。**収束先の deny を `jq` で組んではいけない** — `jq` 不在こそ捕まえたい死因なので、収束先が `jq` を要求すると trap 自身が同じ死に方をする。素の `printf` で組んだ。
- `trap` は `HFR_*` の代入より**後**に張る必要がある。前に張ると、収束時に記録先の変数が未定義になって空パスへ飛ぶ（実測で確認）。
- 記録先も同時に壊れている最悪ケースでも再入せず rc=2 で終わる。

### 統括の見立てを1点訂正した

統括は「cc-lint の `inherit_errexit` の穴は、trap を採っても**ブロックすること自体は変わらない**」と見立て、違うと思えば指摘してよいと書いていた。**Cursor では正しいが、他2ツールでは正しくない。**

今日この穴が踏まれると、Cursor は `failClosed` でブロックするが、**Claude Code と Codex では rc=1 が non-blocking なので素通りする**。trap を入れると rc=2 になるので、3ツールすべてでブロックされるようになる。つまり trap は、この穴が踏まれたときの影響範囲を Cursor だけから3ツール全部へ**広げる**。trap の意図どおりの動作（内部エラーを黙って素通りさせない）ではあるが、別 issue の優先度を上げる材料なので plan に表で書いた。

### 副次的に良くなった点

複式記入を落としたことで、gate 2 が指摘していた弱点がまとめて消えた。累計差の解釈（残高であって死因の件数ではない）、ウォーターマーク、2回 snapshot の上下限、負値の扱い — これらは全部、差を数えるからこそ必要だったものである。**代わりに内部エラーが `deny.jsonl` に1件ずつ時刻つきで残るので、分解能はむしろ上がった。**

記録呼び出しも1起動あたり2回から1回に減ったので、ハングしうる面も減った。統括から「trap でハング面が増えていないか再評価せよ」と指示があり、**減っている**と答えられる形になった。

昇格の印: 「機構Aが機構Bを不要にする」と書くとき、A と B が同じ故障を担当しているかを確かめずに書くと、B が担当していた別の故障ごと落としかねない。今回は統括が拾ったが、書き手側の型として残す価値がある

### 修正方針は「握り潰さない」で縛られている

owner が名指しした negative knowledge item `01KYA7C9NN4VDM7H2NYXZB2PSX` は「失敗を `|| true` で握り潰して空出力を後段へ流すな」である。`grep` の非マッチ（1）と環境エラー（2以上）は、握り潰すと同じ見え方になる。

そこで採った形は次の3つである。

1. **非マッチは正常なデータ不在として扱い、環境エラーとは分ける。** `case` で 0 / 1 / それ以外を書き分け、環境エラーは呼び出し側へ返す。
2. **パイプラインをやめる。** `head` の早期終了は `pipefail` 下で SIGPIPE 由来の非0を生みうる（もう1つの item `01KYA7C9M4EN1EZM3HBEN5WDRP`）ので、非マッチと環境エラーの区別を壊す。`grep` を here-string で1回呼び、`head -1` と `sed` は bash のパラメータ展開に置き換えた。外部プロセスが2つ減るので、全 Bash 呼び出しで走るフックとしては速くもなる。
3. **正規表現は変えない。** マッチ意味論を触ると非回帰の証明が難しくなる。

呼び出し側で環境エラーを deny に倒すとき、**`deny` を `extract_commit_segment` の中で呼んではいけない**ことに気づいた。この関数はコマンド置換の中で走るので、そこで出した制御 JSON は本物の stdout に届かず置換の戻り値に化ける。呼び出し側で処理する形にした。

### 差分比較で非回帰を証明した

実スクリプトは触らず、`tmp/` に旧版と新版を並べて同じ入力を流した（`tmp/probe-310-fix.sh`）。

- **`inherit_errexit` off（今日の状態）で、16ケースすべて判定が一致した**（rc の差分 0 件）。`&&` の有無、commit の有無、CC 形式の可否、クォート内の `&&`、単一の `&`、`git -C . commit` などを含めた。
- **`inherit_errexit` on では、旧版が4ケースで rc=1 を返し、新版は 0 件だった**（`cd /tmp && ls` / `echo a && echo b` / `make build && make test` / `cd x && git -C . commit -m "bad"`）。受け入れ条件が「有効・無効の両方を測る」ことを求めているので、両方測った。
- `shellcheck` は新版で指摘なし。
