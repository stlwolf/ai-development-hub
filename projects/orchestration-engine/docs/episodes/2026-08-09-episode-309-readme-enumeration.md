# #309 残件 — README 3件の列挙を実体に合わせ、突合の口を1つ足す

`reconstructed`。本文は作業の終わりにまとめて書いた。リアルタイムの追記ログではないので、追記型の episode と同じ証拠価値は無い。時系列は会話・コミット・SO 出力から再構成したものである。

## なぜこの作業が始まったか

同じ #309 の先行単位が `oe-hookfire` を `~/bin` の配布対象に載せたとき、その作業の過程で文書側の列挙が実体から遅れていることに気づき、自分の scope 外として統括へ surface した。engine の README の構成ツリーに verb が7本足りない、`orchestration-toolkit` スキルが「全 11 verb」と書いている、といった指摘である。それが本単位の brief になって降りてきた。

owner の方針は先に出ている。**README は人間が全体を把握するための一覧なので、更新漏れは随時埋める。** 列挙をやめて「`--list` で見てください」に置き換えるのではなく、列挙は維持したまま埋める。

## brief の数が1件違っていた

brief は数を3つ渡してきた。構成ツリーが15本に対し実体22本、`bin/README.md` に節を持たない verb が7本、スキルの「全 11 verb」。同時に brief 自身が「**数は自分で測る。この brief に書いた数は前の単位の実測であって、あなたの成果物へ写す前に確かめること。違っていたら違うと報告する**」と書いていた。

測った結果、2つは合っていて1つは違った。

- 構成ツリー: 15本記載・実体22本。**合っていた**
- スキル: 「全 11 verb」・実体22本。**合っていた**
- `bin/README.md` の節: **22本すべて揃っており、欠けは1本も無かった**

食い違いの中身は取り違えである。brief は「節を持たない verb が7本ある」として `oe-ident` / `oe-jump` / `oe-register` / `oe-selfcheck` / `oe-undelivered` / `oe-view` / `oe-vitals` を名指ししていたが、この7本は**構成ツリーに欠けている7本と完全に同じ集合**だった。1つ目の文書で測った結果が、2つ目の文書の症状としてそのまま書き写されている。

実際に `bin/README.md` で欠けていたのは節ではなく**冒頭の索引**で、落ちていたのは別の5本（`oe-refute` / `oe-review` / `oe-register` / `oe-view` / `oe-tree`）だった。重なるのは `oe-register` と `oe-view` の2本だけである。

brief に従って節を7本新設していたら、既にある節と重複した節を作ることになった。**測ったから避けられたのではなく、brief がそう指示していたから測った。** ここは前任の規律が効いた場面として記録しておく。

## 何をどう埋めたか

数はすべて `ls` と `diff` で機械的に突き合わせた。目視で数えていない。

### 親 README の構成ツリー

`bin/` に7本を足して22本にした。位置は `bin/README.md` の節の並び順に合わせている。既存の15本が偶然その並びの部分列になっていたので、欠けを本来の位置へ差し込むだけで並びが揃った。

同じツリーの中で、他にも実体と合っていない箇所があった。`lib/` が14本記載で実体16本（`sanitize.sh` / `oe-viewer.sh` が未記載）、`schemas/` が「5 件」で実体6件（`oe-events` が未記載）、`scripts/` が3本記載で実体6本（`validate-board.sh` / `validate-knowledge.sh` / `knowledge-list.sh` が未記載）。これらも直した。

### bin/README.md の索引をどう埋めたか

節は揃っていたので触っていない。埋めたのは冒頭の索引である。

索引は3つの区分（本体エンジン / 親子委譲 CLI / 観測）を持っていたが、落ちていた5本のうち `oe-refute` と `oe-review` はどれにも収まらない。SO ゲートは engine 本体でも委譲でも観測でもないためである。`oe-view` も同じで、read-only 観測ではなくビューアペインを立てる側である。**区分を2つ新設した**（SO ゲート / doc 表示）。`oe-register` は親子委譲へ、`oe-tree` は観測へ入れた。

区分の切り方は `orchestration-toolkit` スキルの役割別リストに寄せている。新しい分類を発明せず、既にある同種の一覧と揃えたほうが、2つの文書を往復する読み手が迷わない。

### スキルの件数と役割別リスト

「全 11 verb」を22へ直した。ただし数だけ直すとリストとの不整合が残る。役割別リストは11本しか挙げていなかったので、**欠けていた11本も足した**。owner 方針の「列挙は維持して埋める」はここにも当たる。

配布 canonical なので、hub 固有の絶対パスを operational な位置に焼かないようにした。「実体は `projects/orchestration-engine/bin/`」を「実体は engine の `bin/`（hub では `projects/orchestration-engine/bin/`）」の形にし、hub のパスは括弧内の例へ降格している。同じファイルの別の節が既にこの書き方をしていたので、それに合わせた。詳細への routing 行も同じ形へ直した。

## 数だけを直すと同じ場所がまた古くなる

3つの文書はいずれも過去に一度は正しかったはずで、verb が増えるたびに置いていかれた。数を22に書き換えるだけでは、23本目が入った時点で同じ状態に戻る。

そこで**数え方の規則を数のすぐ隣に置いた**。`bin/README.md` の索引には「`bin/` 直下の実行可能エントリの全数。verb を足したらこの索引にも足す」、スキルには「この 22 は `bin/` 直下の実行可能エントリの実数なので、verb が増減したら下の役割別リストとこの数も直す」と書いた。

これで陳腐化が止まるとは言わない。**読んだ人が従うかどうかに条件付けられている**という点で、この文書群が既に抱えていた弱さと同じである。機械で止めるなら、`ls bin/` と各文書の列挙を突き合わせる検査を `tests/` に置くのが筋で、その材料は本単位で作った（下の `--list` と、実際に使った突合手順）。**本単位では踏み込まない。**

昇格の印: 列挙の陳腐化を人の規律でなく機械検査で止める案（`ls bin/` と3文書の列挙の突合を tests/ に置く）は、同じ形の陳腐化が繰り返し起きている以上、判断として記録する価値がある

## --list は置き換えではなく突合の口

brief の任意項目として `scripts/sync/sync-bin.sh` に `--list` を足した。`CMD_NAMES` を1行1件で印字して終了するだけで、配置は行わない。

**owner 方針との関係を取り違えないようにした。** 「列挙を `--list` に置き換えて消す」ことは禁じられており、これは守っている。文書側の列挙はすべて維持したままで、`--list` はそれが実体と合っているかを確かめるための出力に留めた。ヘッダの Description にもその線を書いてある（「ドキュメント側の列挙を置き換えるものではなく、突き合わせて確かめるための出力」）。

この案自体、先行単位の SO が出して統括へ surface されたものが戻ってきたものである。

## gate 4 で1件、実害のある指摘が出た

実装SO（弱SO・2レーン・`SO_TIMEOUT=600`）を**3周**回した。`oe-review` は reviewed diff の hash にバインドするので、指摘を直すたびに取り直している（古い版に対する SO が残ると、機械判定が stale な合格を出す）。設計SO は省いている。区分の新設や埋める位置の判断はあるが、いずれも既存の一覧に寄せる範囲で、棄却した設計案が立つ性質のものではなかったためである。**省いた事実をここに残す。**

1回目は codex が `refuted`、cursor が `survived` で、conservative 集約により全体 `refuted`（exit 3・advisory）。

| レーン | 所要 | 結果 |
|---|---|---|
| codex | 79秒 | refuted |
| cursor | 180秒 | survived |

codex の指摘は `--list` の引数検証だった。**`--lis` のような誤記がどの分岐にも当たらず、そのまま配置処理（`~/bin` の作成と symlink 更新）へ落ちる。** 実際に打って再現している。

これは私が持ち込んだ欠陥ではない。引数を無視して配置する挙動は元からで、`main "$@"` は引数を見ていなかった。**それでも直すべき指摘である。** `--list` を足したことで「読み取り専用のつもりで打つ」場面が新しく生まれ、そこでの誤記の落ち先が副作用を持つ処理になったからである。欠陥そのものは既存でも、実害を生む条件を作ったのは本変更である。

直す前に呼び出し側を確認した。`scripts/sync.sh` の `run_target` は `"${script}"` と引数なしで呼ぶので、厳格な引数検証を足しても既存の経路は壊れない。既知のもの以外を exit 2 で拒否し、引数が2つ以上ある場合も拒否するようにした。引数なしで配置する挙動は変えていない。

cursor レーンは3文書の verb 集合を独立に突き合わせて（Python での集合比較）欠落・余剰なしと判定し、schemas 6件と追加した lib / scripts の実体一致も確認している。**私の実測と独立な経路で同じ結論に到達している**ので、列挙の正しさについてはこの2つが根拠になる。

### 2周目 — スキルに書いた副作用の契約が実体と違っていた

修正後の diff に対して回し直した（`oe-review` は reviewed diff の hash にバインドするので、直した後の版で取り直さないと記録が古い版を指したままになる）。

| レーン | 所要 | 結果 |
|---|---|---|
| codex | 108秒 | refuted |
| cursor | 175秒 | survived |

codex が別の欠陥を挙げた。**私がスキルの watchdog の節に書いた「いずれも何も書き換えず」が実体と矛盾している。** `oe-undelivered` は `--set-start-after` で起点ファイルを作り、`--notify` の成功後に seen cache へ追記する。`oe-vitals` も通知成功時に seen cache へ書く。

一次確認を取った。`oe-undelivered:192,195,387,390` と `oe-vitals:335,336` に `mkdir -p` と追記があり、`oe-selfcheck` と `oe-hookfire` は書き込み箇所ゼロである。**指摘は正しい。**

私は4本を1つの節にまとめた時点で、`oe-selfcheck` / `oe-hookfire` が持つ「何も書き換えない」という性質を4本全体に広げてしまった。**まとめて書くと、一番強い性質が全体の契約として書かれる。** 元の `bin/README.md` は verb ごとに節が分かれていたので、この誤りは起きようがなかった。列挙を集約する編集そのものが持つ危険である。

engine の state を書き換えない点は4本とも正しいので、そこと自分用の記録を書く点を分けて書き直した。完全な read-only 環境では前2本が走らないことも明示している。

なお構成ツリー側に書いた `read-only` の表記は `bin/README.md` の各節の見出しをそのまま写したもので、新しい主張ではない。

### 3周目 — 直した文でも同じ型を踏んでいた

| レーン | 所要 | 結果 |
|---|---|---|
| codex | 142秒 | refuted |
| cursor | 222秒 | refuted |

この周から diff が 48281 バイトになり、`oe-review` の inline 上限（`OE_REVIEW_DIFF_MAX_BYTES` 既定 30000）を超えた。**レーンへの渡し方が inline から workspace フォールバックへ切り替わっている**（変更ファイル一覧と base ref を渡し、レーン自身に `git diff` を打たせる形）。1周目・2周目とは読ませ方が違うので、同じ条件の比較ではない。

**cursor が、2周目で直した文そのものの中に同じ誤りを見つけた。** 私は「`oe-undelivered` と `oe-vitals` は自分用の記録（seen cache・観測の起点）を書く」と書いたが、起点ファイルを持つのは `oe-undelivered` だけである。一次確認したところ `oe-vitals` には `start-after` の参照が1件も無い。**2本をまとめた時点で、片方だけが持つ性質を両方に広げた。**

つまり**収穫したばかりの knowledge item が予測している失敗を、その item を書いた同じ作業の中で犯した。** 4本を1本の文にまとめた誤りを直すとき、こんどは2本を1つの括弧にまとめて同じことをしている。集約の単位が4から2へ小さくなっただけで、構造は変わっていなかった。verb ごとに書き分ける形へ直した。

codex は別件で、`usage()` の `head -n -1` を material に格上げした。**既存不具合だが、`--list` の使い方を案内する経路がそれだという点が変わった。** 私が足した機能の説明が、対象環境では読めない場所にしか無い状態になる。1行で塞げるので直した——**先行単位が「本 PR では触らない」と routing していた項目を、本単位で解いたことになる。** 二重起票を避けるため報告で統括へ伝える。

直す過程で、同じ関数にもう1つ GNU 拡張があることが分かった。行頭の `# ` を落とす `s/^# \?//` の `\?` は BSD の基本正規表現では「省略可」と解釈されない。`--help` は exit 0 になっても `# ` が残ったままだったので、こちらも直した。**codex が指摘したのは exit 1 で落ちることまでで、出力が汚れる側は指摘に含まれていない。** 実際に打って初めて見えた。

cursor はもう1件、`sync-bin.sh ''`（空文字列）が空枝に入って配置が走ることを挙げた。軽微として非ブロッカー扱いだったが、引数を渡したのに配置が走るのは `--lis` を塞いだ理由と同じなので、引数の個数で判定する形に変えて塞いだ。

**cursor レーンはこの確認のために実際に `sync-bin.sh ''` を実行しており、`~/bin` の4本がまた worktree を指す状態になった。** 検出して復旧済みである。私が同じ事故を起こした直後に、レビュー側が同じ経路で同じ事故を起こしたことになる。**この罠は「気をつける」では止まらない**という証拠が2件になった。

## worktree から sync 経路を走らせてしまった

引数なしの挙動が壊れていないことを確かめるつもりで、worktree から `./scripts/sync/sync-bin.sh` を実行した。**brief が明示的に禁じていた操作である。**

`~/bin` の8本のうち4本（`so-compare` / `arena-compare` / `wez` / `wt-pane-issue`）が worktree を指すリンクに張り替わった。残る4本は出力を `head -2` で受けていたため SIGPIPE で途中終了して届いていない。worktree を削除した時点で、張り替わった4本は dangling になる。

メインの作業ツリーから `sync-bin.sh` を実行し直して復旧した。8本すべてがメインリポジトリを指すことを `readlink` で1本ずつ確認している。

**確認したかったのは「配置経路に入るか」だけで、実際に配置させる必要は無かった。** 分岐に入ったことを見るなら、引数検証の側（exit 2 で止まること）を確かめれば十分で、既存不具合の記録（`sync.sh --check bin` が8本中2本しか見ない）を思えば、`~/bin` を実際に触らせる確認は避けられた。

この罠は既知でもあった。worktree からの sync がリンクを張り替える件は memory に記録があり、brief にも1行で書いてある。**禁止事項として読んではいたが、目の前のコマンドがその禁止に当たると気づかなかった。** 禁じられていたのは `./scripts/sync.sh` で、私が打ったのは `./scripts/sync/sync-bin.sh` である。名前が違うので照合が外れた。

## 範囲をどこで切ったか

brief は「列挙以外の内容（説明の改善・構成の変更）に踏み込まない」と書いていた。判断が要ったのは2か所である。

**広げた側**: 構成ツリーの `lib` / `schemas` / `scripts`。brief は `bin/` しか挙げていない。同じツリーという1つの成果物の中で `bin/` だけ直して他を古いまま残すと、次に読む人は「このツリーは直近で更新された」と受け取ったうえで古い情報を読むことになる。列挙という同じ性質の欠けなので、内容の改善ではないと判断した。

**広げなかった側**: `usage()` の BSD 非互換。`head -n -1` は macOS の `head` が受け付けないので `--help` が exit 1 で落ちる。`--list` をヘッダに書き足したので、その説明が macOS では読めない状態になっている。それでも直していない。列挙とは別クラスの既存不具合で、先行単位が既に「本 PR では触らないが統括が隣接欠陥として記録する」と routing 済みだったためである。**新しい発見ではなく再発見**として扱う。

## 触らなかったもの

行き先を1件ずつ付ける。行き先の無い箇条書きは残さない。
