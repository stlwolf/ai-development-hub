# #239 — 子の状態を親が判定するレシピと、画面から承認を読まない規範

## なぜこの作業が始まったか

別リポジトリで並行して走っている統括が、実際の委譲をドッグフードしている最中に「親が子の状態をどう判定するか」の失敗を実測で拾った。その観測をこちら側と相互検証したうえで、下書きは向こうが書き、リポジトリへの適用はこちらが担う、という分担になった。一次証拠は向こうが持ち、編集権はこちらにある。

適用先は3つある。委譲の手順スキル（`delegate-task`）に判定レシピを足すこと、再発する失敗の型として negative knowledge item に収穫すること、そして「何をもって承認とするか」を常時ロードされる規範（`implementation-gate-rule`）に1行で置くことである。3つ目は下書きには無く、統括の判断で足した項目なので owner のゲートが残っている。

## 判別が本当に成立するか、こちらでも確かめた

下書きの中心的な主張は「補完のゴーストテキストは属性で機械判別できる」である。これは実測値の引き写しではなくこちらでも再現できるはずなので、書く前に自分の tmux で確かめた。

同じ tmux サーバ上で動いている委譲子のペイン `%309` を、属性なしと属性付きの両方で capture した。

```
# 属性なし（既定）
tmux capture-pane -p -t %309 -S -6 | grep '❯'
❯ そのままでいい。PR の URL を親へ報告して終端

# 属性付き（-e）— 制御バイトは cat -v で可視化
tmux capture-pane -p -e -t %309 -S -6 | grep '❯' | /bin/cat -v
^[[39m❯ ^[[2mそのままでいい。PR の URL を親へ報告して終端^[[0m
```

3つのことが同時に確かめられた。

1. **属性は本当に判別に使える。** 入力欄の `❯` は `ESC[39m`（既定色）で、その後ろの本文だけが `ESC[2m`（薄い表示）で始まり `ESC[0m` で閉じる。下書きの記述と一致した。
2. **属性なしの capture では区別が消える。** 同じ行が、装飾のない普通の文字列として出てくる。未送信の入力なのか補完の予測なのかを判定する材料が残らない。
3. **中身が、まさに親が送りそうな指示だった。** 「そのままでいい。PR の URL を親へ報告して終端」は、この委譲子が待っている次の一手そのものである。私は `%309` に何も送っていない。存在しない指示が、待っている指示の顔をして画面に出ていた。

3つ目は下書きが「補完は待っている承認の文面に似る方向へ偏る」と書いていた点の、こちらの環境での独立した再現になる。向こうの実測は「裁定が出ました。承認です」に相当する文面だったが、こちらで出たのは終端の指示だった。文面は違うが、**待っている文に寄る**という構造は同じである。

昇格の印: 画面に見えた承認を承認として扱わないことを、スキルではなく常時ロードの規範に置くかどうか

比較材料として、送信済みの履歴行は `ESC[37m`／`ESC[100m`（灰色背景）や `ESC[97m`（明るい白）で描かれており、薄い表示ではなかった。ただし**未送信の実入力が入った状態の入力欄**は、こちらでは撮れていない。自分のペインへ文字を打ち込む操作は分類器に止められたので、迂回はしていない。したがって「実入力は薄くない」は履歴行から見た傍証であって、直接の確認ではない。この穴があるからこそ、レシピ側は属性の判定を単独では使わせず、送信記録との突合と2本立てにする必要がある。
