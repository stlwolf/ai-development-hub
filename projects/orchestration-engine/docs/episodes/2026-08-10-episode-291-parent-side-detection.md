# #291 — 報告に依存しない親側の検知（設計単位）

## なぜこの作業が始まったか

委譲した子が作業を終えても親へ報告しないことがある。親はそれに気づけないまま、その子を「まだ動いている」と思って待ち続ける。この経路を塞ぐ層は #289 で探索されたが、#289 が指定したスコープ（skill と運用で効く範囲）の内側には**非循環な発火位置が無い**という構造的発見に到達して park された。

報告するかどうかを決めるのが子自身であるかぎり、判定は循環している。循環の外に居るのは親だけである。だから本単位は「報告に依存しない親側の検知」の1点だけを引き受ける。**報告を発火させる機構は扱わない**（それは #291 の残りである）。

先行する #291 の plan（Alt-7 承認時の義務コンパイル）は `halted-unconverged` で止まり、owner が要件表ごとの破棄を受け入れている。だから全部やり直さず、範囲を1点に絞った再開として始めた。

## この単位の終端

plan を作って STOP し、パスを親へ報告した時点で終わる。実装は owner の gate 3 を通ってから、親が位置を指定する。**この episode はその設計単位の記録である。**

### 数え方の比率をそのまま述語にすると誤検出する（brief の読みへの訂正）

比率だけでは足りないことが、時系列を並べた時点で分かった。`%293` の 5/3 は**報告を2回落としたのではない**。

```text
%293  I 14:20:07  R 14:59:16  I 18:16:46  R 18:22:31  I 18:23:38  I 18:28:16  I 18:28:50  R 19:07:40
%309  I 12:59:16  I 14:22:39  I 18:07:43  I 08:17:54(翌日)
%300  I 18:48:41  R 12:26:07  I 17:19:33  R 17:30:27  I 19:06:15  R 19:13:53  I 07:01:17  R 07:35:46
```

`%293` は5分の間に3件の指示を受け、その39分後に1件の報告を返している。**複数の指示を1件の報告にまとめた形**であって、報告の欠落ではない。いっぽう `%309` は4件の指示に対して1件も返していない。

つまり「受けた指示 > 送った報告」という述語は、**まとめて返した子**と**一度も返さない子**を同じ扱いにする。前者は正常な振る舞いなので、比率を検知の材料にすると誤検出になる。検知は「最後の指示以降に報告が1件も無い」側で組む必要がある。

brief の「ほぼ二値・最初の1回が予測子」という読みは、一度も返さない子（`%309`）と毎回返す子（`%300`）の対比としては測定と一致している。`%293` を「3回中2回落とした」と読む部分だけが測定と合わない。

### 対象の子は既にペインごと消えている

これが設計の形を変えた。目標事例の `%309`（exit-contract）と `%308`（readme-enum）は、**仕事そのものは完遂している**。

- `%309` の成果は PR #315（2026-08-10T09:02:48Z マージ）。最後に受けた指示は同日 08:17:54Z。
- `%308` の成果は PR #314（2026-08-09T17:32:49Z マージ）。

そのうえで報告を1件も送っていない。そして現在、`tmux list-panes -a` に `%288` `%289` `%293` `%300` `%304` `%308` `%309` `%314` はいずれも存在しない。

したがって、この型を検知しようとする時点で **`delegate-task` の判定レシピの信号 (a) プロセスの生死と (b) `%cpu` の絶対値は、そもそも引く対象が無い**。残るのは (c) 終端成果物と、活動ログである。停止の形は「アイドルで生きている」と「ペインごと消えた」の2つに分かれ、実測された事例は後者だった。

### `tmux display-message` は不在ペインでも成功する（新規に測った罠）

判定レシピの信号 (a) を素直に書こうとして踏んだ。

```text
pane=%288     rc=0 len=0
pane=%309     rc=0 len=0
pane=%99999   rc=0 len=0
pane=%318     rc=0 out=[89907]   ← 対照（実在）
```

`tmux display-message -p -t "%N" '#{pane_pid}'` は、**ペインが存在しなくても終了コード 0 と空文字を返す**。`=%288` と厳密指定しても同じだった。存在しない番号 `%99999` でも同じである。

そのため `rc` を存在判定に使うと、消えた子を「生きている」と読む。さらに空の pid をそのまま `ps -p` へ渡すと `ps` 側が不定の文字列を掴んでエラーを出すので、**エラーの出どころが tmux ではなく `ps` に見えて原因を取り違える**（最初にこれを踏んだ）。

engine の既存実装は既にこれを避けていて、`oe-undelivered:145` は `tmux list-panes -a -F '#{pane_id}'` で集合を取ってから所属を見る形になっている。検知を書くときはこちらへ揃える。

### `oe-undelivered` がこの型を見られないことの確認（陽性対照つき）

brief の主張を、0件を不在の証明に使わない形で確かめた。窓を60秒・起点を全期間にして実行したところ、**25行以上を出力した**（`exit=0`）。つまり投影は生きていて、出力が空だから何も出ないのではない。

そのうえで、出力に `%309` と `%308` は**1行も無い**。理由は母集団の定義である。`oe-undelivered` が数えるのは「送られた `message_sent`」なので、**一度も送っていない子は母集団に入らない**。窓を広げても起点を戻しても、この型は原理的に出てこない。

副産物として、報告の受領印がほぼ機能していないことも確認できた。通算で `child_spawned` 118件・`message_sent` 880件（親→子 474 / 子→親 382）に対し、**`report_received` は通算1件**である。`prompt_received` は101件。したがって「親が受領印を打っていないこと」を報告の不在の根拠に使ってはいけない。使えるのは子→親の `message_sent` の有無だけである。

### 活動ログの読み側で気をつける傷

- スキーマ違反のレコードが1件ある。`role` は `parent` / `child` / 空 の enum なのに、`2026-07-01T11:18:29Z` の1件は `role` に label（`#92 verify-commit-range-inputs`）が入っている。
- `role` が空文字の `message_sent` が23件ある。これはスキーマが「関係不明」として許している正当な値である。

どちらも `role` を単独の向き判定に使えないことを意味する。向きは `child_spawned` の親子対応から引くのが確実で、これも `oe-undelivered` が既に採っている複合解決と同じ方針になる。

### 報告経路そのものの欠落を疑って、外れた（追いかけた価値のある空振り）

brief は報告の呼び方を `oe-send "$PARENT_TMUX_PANE" '...'` と裸で書いている。これを素直に実行したら **exit 1** になった。`oe-send` は `~/bin` に配布されていない。

- 配布対象の正本 `scripts/sync/sync-bin.sh:57` の `CMD_NAMES` は8件で、`oe-*` は `oe-tree` と `oe-hookfire` の2本だけである。
- `orchestration-toolkit` はこれを不変条件として明記している。「`oe` / `oe-*` は原則 PATH 未登録」で、起動方法を決める前に `command -v` で確かめよと書いてある。
- `delegate-task` の例示は `"$BIN/oe-send"` の形で正しい。裸で書いているのは brief 側である。

そこで「未報告の原因は、報告しようとしたのにコマンドが無くて落ちたことではないか」を疑った。**これは外れた。** 順に確かめた。

1. `%308` の transcript には「`oe-send` / `oe-selfcheck` は PATH に無い」という記述が確かにある。しかしこれは `%308` の担当が配布 CLI の列挙だったからで、**報告を試みて失敗した記録ではない**。同じ transcript の Bash tool_use を全部見ると、`oe-send` を含むコマンドは **0件**である。試していない。
2. hub 系の transcript 20ディレクトリを横断して、tool_result に現れる失敗文字列（`oe-send: command not found` / `oe-send: No such file`）を数えたところ **2件**だった。しかもこのうち少なくとも1件は**本セッションで私自身が今日出したもの**である。
3. 陽性対照として同じ探し方で成功記録（`oe-send: sent to`）を数えると **486件**取れた。探し方が壊れていて0に見えているのではない。

したがって **PATH の欠落は brief の書き方に潜む本物の罠ではあるが、観測された未報告の原因ではない。** 子は「送ろうとして失敗した」のではなく「一度も送っていない」。

この空振りには意味がある。未報告が**配送の失敗ではなく試行の不在**だと確かめられたので、配送側の検出器（`oe-undelivered` の系列）をいくら強くしてもこの型には届かない。試行が無いことを見られるのは、試行を期待している側＝親だけである。#289 が構造として述べたことが、ここで測定として裏づけられた。

昇格の印: brief に書かれた報告コマンドが裸呼び出しで exit 1 になる。委譲の固定節の側で `$BIN/` 形に直す価値がある（本単位のスコープ外・親へ surface する）

### 自分の推論が2回崩れた

記録しておく価値があるのは、外から崩されたものより**手元に証拠があったのに推論しなかった**2件である。

1. **`pane-issue` の被覆。** 6件しか無いことを自分で印字していたのに、「119件の spawn に遡って効く」と書いた。6 対 119 が刈り取りを意味することを読まなかった。陽性対照が通ったのは目標事例が直近24時間内だったからで、**生存者バイアスだった。**
2. **PR オラクルの向き。** 「PR がマージ済み」を完遂の証拠として喜んだが、マージするのは owner である。**owner が既に関与した後でしか真にならない指標**を、owner に気づかせるための検知器の土台に置こうとしていた。

どちらも「測れた」ことに満足して「何を測ったのか」を問わなかった型である。

### 結論 — スコープの切り方そのものに問題があった

3ラウンドを経て残ったのは、実装可能な設計ではなく構造的発見だった。

> **本単位のスコープアウト（定期実行の配線＝#301）と、#291 が要求するもの（完了扱いの起動の保証）は分離できない。**

呼ばれない検知器は「親が起動を覚えている必要がある」分類に落ちる。#289 がその分類を**循環として8レーン全 refuted で棄却**している。したがって受け入れ条件「起動が親の記憶に依存しない形で保証されている」は実装した瞬間に未達が確定する。しかも同じ但し書き（「この台帳の値打ちは読み手が実際に走ることに条件付けられている」）を持つ verb が既に2本ある。

さらに、到達した述語は連言に「送信0」を含むため、**#291 の事例1（報告を送って終わった委譲）を構造的に排除する**。#291 が名指した事故とは別の事故を捕まえており、範囲の縮小ではなく別問題への乗り換えである。

**この2点は、範囲を1点に絞って再開したこと自体への反証である。** brief は「全部やり直さない・範囲を1点に絞る」と指示したが、絞った1点は単独では要求を満たせない位置にあった。

昇格の印: 「観測は生 fact まで・解釈はしない」（DJ-188-2 / DJ-206-2）を本単位が独立に再発見した。engine 横断の規範として昇格を検討する価値がある

昇格の印: 「呼ばれる保証の無い台帳を増やすと Sensor が埋まったと誤読される」型が3本目に達しようとしている。#301 の判断材料として蒸留する価値がある
