# #301 — oe-selfcheck を定期実行に配線する（設計単位）

## なぜこの作業が始まったか

`oe-selfcheck` は版に固定された前提が今も成り立つかを read-only で点検する verb である。#299 で新設された。ところが定期実行の配線が無く、人が思い出して打つまで動かない。

これは #289 が3度にわたって「循環する」と判定した形そのものである。起動が誰かの記憶に依存しているかぎり、検知器が沈黙していることを検知する手段が無い。#291 はこの構造的発見に到達して `halted-unconverged` で閉じた。同じ但し書きを持つ verb は既に `oe-hookfire` と `oe-prompt-receipt` の2本ある。

したがって本単位の値打ちは `oe-selfcheck` 単体ではなく、「呼ばれない検知器」という型を1つ終わらせることにある。

## 着手時に自分で測った事実

brief が渡してきた事実は統括の実測であり、写す前に確かめよという指示があった。確かめた結果、**1件が食い違っていた。**

### `oe-selfcheck` の判定は現在 `broken` 1件（brief は2件）

```
$ ./projects/orchestration-engine/bin/oe-selfcheck
CHECK                   VERDICT         DETAIL
screen-marker           broken          稼働中のペインが 2 枚あるのに目印 'esc to interrupt' を画面のどこにも観測できない（この版に目印が無い。対象 11 枚）
hook-contract           ok              直近の nonce 付き送信 20 件中 19 件に宛先ペインからの受領印がある
transcript-format       ok              新しい 5 本のうち 5 本から typed ターンを計 25 件取れる
pane-session-bridge     ok              129 件中 110 件が pane を持つ
retention-horizon       info            最も古い transcript の最終更新は 2026-06-30（受け手側の記録はこれより前へ遡れない。良し悪しは判定していない）
exit=1
```

brief は `screen-marker` と `hook-contract` の2件が `broken` だと書いていた。`hook-contract` は既に `ok` へ戻っている。受領印 hook が配備され、直近20件のうち19件に印が付いているためである。統括が測った時点では hook 配備前に停止した子の送信が母集団を占めていた。

この食い違いは設計に効く。**残った `broken` 1件は自然には消えない。** `screen-marker` はこの版の claude に目印が無いという事実を報告しており、本単位のスコープでは直せない。つまり配線した瞬間から、定期実行は毎回 `broken` を1件返し続ける。「たまに鳴る通知」ではなく「常時鳴り続ける通知」を設計することになる。

### `oe-hookfire` の exit code 衝突は解決済み（brief どおり）

```
$ oe-hookfire --help >/dev/null 2>&1; echo $?   # → 0
$ oe-hookfire --bogus >/dev/null 2>&1; echo $?  # → 2
$ oe-hookfire         >/dev/null 2>&1; echo $?  # → 1（broken の帯）
```

PR #315 の着地を確認した。残る論点は `indeterminate` を 2 のまま置くか 3 へ動かすかだけである。

### 配布の現状

`oe-selfcheck` は `sync-bin.sh` の `CMD_NAMES` に入っていない。`~/bin` に配置されておらず PATH から呼べない。配布されているのは `so-compare` / `arena-compare` / `wez` / `wt-pane-issue` / `oe-tree` / `oe-hookfire` / `validate-knowledge` / `knowledge-list` の8件である。

### launchd の前例（`com.stlwolf.oe-vitals`）

`~/Library/LaunchAgents/com.stlwolf.oe-vitals.plist` が15分間隔（`StartInterval` 900）で `oe-vitals` を走らせている。`RunAtLoad` は true、標準出力と標準エラーは `~/.claude/state/oe-vitals/cron.log` へ落ちる。

**この plist はリポジトリに入っていない。** `find . -name '*.plist'` は0件を返す。hub の絶対パスを焼いた状態で手で置かれている。#301 の受け入れ条件「配布される canonical に hub 固有のパスを焼いていない」はここに直接効く。

## gate 1 — ゼロベース代替探索（1巡目・3レーンすべて `refuted`）

`oe-refute --lanes 3 --rubric exploration`。audit_id `20260811020746FWT7NJSNWCHA`。出力先は `tmp/oe-refute-20260811020746FWT7NJSNWCHA/`（**永続しないので要点をここへ転記する**）。

反証にかけた初期案は「launchd で定期実行し、`(検査名, 判定)` を鍵にした seen cache で変化した検査だけ通知し、常時 `broken` の検査は静かなログへ落とす」だった。

### 3レーンが独立に同じ2点を突いた

**1. `(検査名, 判定)` を鍵にすると、この案が守ると宣言した失敗がそのまま起きる。**

`oe-selfcheck` の `broken` は検査名と4値では同定できない。`screen-marker` の `broken` には2枝あり（`oe-selfcheck:146` の「目印は画面に在るが走査窓に届かない」と `:150` の「この版に目印が無い」）、`hook-contract` の `broken` には3枝ある（`:172` 配線が無い / `:175` 実行可能でない / `:208` 発火していない）。いま出ているのは `:150` である。目印が戻って走査窓だけが届かない状態へ移れば、それは本単位のスコープで直せる別の壊れ方だが、鍵 `(screen-marker, broken)` は変化しないので黙ったままになる。

代わりに `detail` 全文を鍵にすることもできない。`detail` には実行ごとに動くペイン枚数が埋まっているので、毎回「変化した」と鳴る。

さらに cursor レーンが型そのものの誤りを指摘した。`oe-vitals` と `oe-undelivered` の seen cache は**離散イベント**用である。`broken` は**居座る状態**であり、イベント用の重複抑止を状態の沈黙へ移植したカテゴリの取り違えだった。

**2. 「静かなログ」は前例で既に死んでいる。**

落とし先として想定していたのは、自分で 2953 行・385KB・ローテーション無し・誰も読んでいないと実測した当の入れ物である。**毎回必ず鳴る唯一の信号**の置き場に、失敗が確認済みの容器を選んでいた。

### 3レーン共通で挙がった未設計の穴

- `wez notify` が cron / TTY 無しの文脈から owner へ届くかは、`oe-vitals:68` が自分で「段階0 から未検証」と書いている。**通知経路そのものが実測されていない。**
- スケジューラ自身が黙って止まったことを誰も検知しない（鮮度監視が無い）。
- `indeterminate` の扱いが案に無い。時刻駆動だと、稼働ペインが無い時刻の `screen-marker` は正常に `indeterminate` になる。
- `oe-selfcheck` は `CMD_NAMES` 未収録で PATH から呼べない。

### 1巡目を受けて測り直した事実

- **`oe-selfcheck` の実行時間は 4.5 秒**（`time` 実測）。`UserPromptSubmit` のような毎プロンプトのフックに載せるには重すぎる。
- **statusLine は既に全セッションで 10 秒ごとに走っている。** `~/.claude/settings.json` の `statusLine` は `statusline-oe-heartbeat.sh` を `refreshInterval: 10` で呼ぶ。この producer は `canonical/claude/statusline/` にあり **sync で配布される**。原子的な sidecar 書き込みという side-effect を best-effort で行い、失敗しても表示を壊さない作法が既にある。
- 現在配線されている hook イベントは `TaskCompleted` / `PreToolUse` / `PostToolUse` / `Stop` / `Notification` / `UserPromptSubmit` の6種で、`SessionStart` は使われていない。

この2点が組み合わさると、**時刻駆動より稼働中に走らせるほうが観測として良い**という筋が出る。`screen-marker` は陽性対照に稼働中のペインを要求するので、誰も作業していない時刻に launchd で走らせると正常に `indeterminate` へ落ちる。codex レーンが「イベント駆動で `indeterminate` が減る」と予測した点と一致する。

## gate 1 — 2巡目（3レーンすべて `refuted`・statusLine 案は棄却）

audit_id `2026081102162594X3WWYP7A22`。かけた案は「statusLine が経過時間を見て background で走らせ、同じ statusLine が結果を常時表示する」。

**claude レーンが決定的な指摘を出した。** この案の中心にある「statusLine は必ず走る」は、姉妹単位が一度掴んで手放した当の前提である。`2026-07-11-episode-239-pr-b-vitals-consumer.md:46` が **Anti** として登録している。

> Anti: observer の安全性主張を、上流の**未検証 premise**（refreshInterval-idle）に載せる。

前提を差し替えただけで、同じ Anti の再発だった。加えて statusLine 案は独立した3つの理由で失格になった。

- **実行者と描画器が同じ部品だと、実行者の死が見えない。** statusLine が止まれば表示は最後の文字列のまま凍り、経過時間は増えない。凍った `42m` と生きた `42m` は読み手から区別できない。
- **検査対象が実行者になる。** `oe-selfcheck` の `pane-session-bridge` は statusLine が書く sidecar を対象にしている（`oe-selfcheck:276-286`）。sidecar は掃除されないので、statusLine が数週間死んでいても件数は保たれ、この検査は死んだデータの上で `ok` を返す。
- **測定器が測定対象を動かす。** `screen-marker` の走査窓は画面下3行（`oe-selfcheck:124` の `tail -n 3`）であり、statusLine はまさにそこへ描画される。表示を1セグメント足すと走査窓の構成が変わり、`:146` の `broken`（目印が窓に届かない）へ倒れうる。

**自分の採用案に自分の基準を当てていなかった点も突かれた。** push を「鳴り続けると読まれなくなる」で落としながら、常時赤の1セグメントには同じ議論を当てていなかった。

## gate 1 — 3巡目（3レーンすべて `refuted`・ただし新カテゴリではなく前提の反証）

audit_id `20260811022619CQHBXKZ068BM`。かけた案は「実行者（launchd）と読み手（`SessionStart` hook）を物理的に分け、既知の `broken` はリポジトリ内の台帳で宣言する」。

3レーンが共通して突いたのは**同じ1点**である。人へ届く経路が2本（`SessionStart` の出力先・launchd からの `wez notify`）あり、**どちらも未実測のまま設計の土台に置かれていた。** 2巡目で叱られた Anti を、名前を変えて2箇所で繰り返していた。

このほかに挙がった指摘は次のとおり。

- `SessionStart` はリポジトリ自身の hook 仕様調査（`docs/research/2026-03-30-ai-tool-hooks-specification-survey.md:227`）が**モデルへの文脈注入**として分類している。人の面ではない公算が大きい。
- 読み手（hook）自身の無言死が未解決である。hook の配布は symlink（`scripts/sync/sync-claude.sh:131`）で、worktree から sync してその worktree を消すと黙って止まる。しかも hook の死を検出できるのは `oe-selfcheck` の `hook-contract` 検査であり、その結果を読むのが死んだ当の hook である。**循環を解いたのではなく一段上へ移していた。**
- `oe-vitals` の launchd への**相乗り**を、理由を書かずに捨てていた。しかもこの選択肢は実測すると生きている。
- `indeterminate` を 3 へ動かす案は exit 2 の実際の発生箇所と合っていない。`oe-selfcheck:78` は `jq` 不在で 2 を返しており、これは呼び方の誤りではなく**環境の失敗**である。帯を作り直すなら環境失敗の帯も決める必要がある。
- 台帳が分類の誤りを埋める足場になっていないか。いま唯一の `broken` である「この版に目印が無い」は、前提が崩れた（`broken`）というより**検査が成立する条件を版が満たしていない**（`indeterminate` 側）と読むほうが素直である。最初の登録者が誤分類かもしれない、という問いに答えていなかった。
- fresh な `indeterminate` が完全に沈黙する設計になっていた（codex）。`indeterminate` は「`ok` ではない」と verb 自身が書いているのに、信号から落ちていた。

## 反証が指した2つの実測を、自分で実行した

3巡とも `refuted` だが、3巡目の指摘は**新しいカテゴリではなく前提の反証**だった。3レーンとも「要るのは設計の作り直しではなく実測である」と書いている。そこで探索を止めて測った。

### `wez notify` は launchd 相当の環境から到達する（レーンの予測は外れた）

claude レーンは「機構の形からして否定側に傾いている」と書いた。根拠は hook 仕様調査の「CLI/フック文脈から通知が表示されないことを実機確認」と、`wez notify` の primary が TTY 直書きであることだった。**実際に測ると通った。**

launchd の plist が渡す環境（`PATH` と `HOME` のみ・`WEZTERM_UNIX_SOCKET` 無し・`TMUX_PANE` 無し）を再現し、`setsid` で制御端末を捨てたプロセスから測った。

```
WEZTERM_UNIX_SOCKET=[未設定] TMUX_PANE=[未設定]
[wez] Socket found: /Users/eddy/.local/share/wezterm/gui-sock-93106
[wez] Connected (1 panes)
pane_id=0 tty=/dev/ttys013
  キャラクタデバイス: あり
  書き込み可能: はい（OSC 直書きの主経路が通る）
```

`wez` はソケットの自動検出（`wez discover`）を持つので、環境変数が無くても mux へ到達できる。到達先の tty は同一ユーザーの書き込み可能なキャラクタデバイスであり、**制御端末の有無は OSC 直書きに関係しない。** レーンが引いた調査結果は `osascript` / `terminal-notifier` についてのものであり、`wez notify` の機構には当てはまらなかった。

途中で1つ罠を踏んだ。最初の測定では `WEZTERM_UNIX_SOCKET` を継承したままで、その値が**既に消えたソケット**を指していたため接続に失敗した。launchd はこの変数を渡さないので、継承させた測定のほうが実態から遠かった。

**副作用を避けるため通知そのものは撃っていない。** `lib/notify.sh:78-81` の fallback は `wezterm cli send-text` で対象ペインへ**打鍵**する。既定の対象は `.[0]`（固定のペイン）なので、そこが `claude` の入力欄なら文字列が着弾する。主経路が通ることまでを確認して止めた。

### `SessionStart` は測らずに依存を外した

こちらは測るのにフックの配線とセッション起動が要る。リポジトリ内の一次情報が「モデルへの文脈注入」と分類している以上、人へ届く保証の土台には置けない。**測ってから採るのではなく、依存そのものを外す**方へ倒した。

## gate 1 の停止判断

3巡すべて `refuted` である。押し通さない。ただし #291 が `halted-unconverged` で閉じた形とは違うと判断した。理由を書く。

- #291 は**ラウンドごとに新しいカテゴリが出続け**、収束の兆しが観測できなかった。
- 本単位は 1巡目で新カテゴリが大量に出たあと、2巡目・3巡目は**新カテゴリではなく前提の反証**に移った。3巡目の指摘は「相乗り」（1巡目で既出）と「2つの実測」であり、選択肢の空間は広がっていない。
- 3レーンとも「要るのは設計の作り直しではなく実測」と結論を揃えた。その実測を実行し、**1つは決着（`wez notify` は通る）、もう1つは依存を外して不要化**した。

**残した未探索**: codex が挙げた「消費者側の capability gate」（壊れた前提に依存する機能側を安全側へ倒す）は探索していない。本単位のスコープ（配線）を大きく超え、`oe-selfcheck` の消費者を洗い出す別単位になるためである。plan に申し送る。

## gate 3-0 の実測が返り、通知経路を差し替えた

owner の答えは**「見えない」**だった。統括が原因を特定している。`WEZTERM_UNIX_SOCKET` が死んだソケット（`gui-sock-25889`）を指し、実体は `gui-sock-93106` だった。長寿命セッションが起動時の値を持ち続けたためである。

**私の gate 1 の測定と矛盾しない。** launchd はこの変数を渡さないので `wez discover` が生きたソケットを見つける。壊れるのは変数を継承する側である。**私は測定中にこの罠を一度踏み、「継承させた測定のほうが実態から遠かった」と上に書いていた。** それを通知経路の設計へ結びつけていなかった。踏んだ記録は残したのに、設計は罠の上に立てたままだった。

### 統括の報告を写さず測り直したら、食い違った

統括は「`wez notify` は ERROR を出しながら exit 0 を返す」と報告した。**再現しなかった。** 名指しされた当の stale socket でも、存在しないパスでも、いずれも **exit 1** である。

```
$ WEZTERM_UNIX_SOCKET=/Users/eddy/.local/share/wezterm/gui-sock-25889 wez notify "検証" "..."
[wez] ERROR: notify: no WezTerm socket found
exit=1
```

**しかし懸念は実在し、報告された形より広かった。** コードで特定した。`notify.sh:71-76` の主経路は `[[ -c "$tty" ]] && [[ -w "$tty" ]]` を確かめてから OSC を書き、`printf` が成功すれば 0 を返す。**exit 0 は「tty へバイトを書けた」でしかない。** その先に WezTerm が居るか、ハンドラが発火したか、macOS が toast を出したかは見ていない。ソケットが見つかった後の全経路で、送信の成功と表示の成功が切り離されている。

これは gate 2 で codex レーンが既に言っていた。plan は受け入れ条件に1行入れただけで、**設計の側では exit 0 を状態遷移の根拠に使ったままだった。** 指摘を条件表に写して、設計に反映し忘れていた。

昇格の印: SO の指摘を受け入れ条件へ写しただけで反映したことにしない。同じ指摘が設計本体に残っていないかを、条件表とは別に見る。

### 直した2点

**通知の運び方を差し替えた。** `wez notify` は mux ソケットに依存し、その参照が静かに陳腐化する。対して owner の環境では他の toast が現在も飛んでおり、その経路である `canonical/hooks/scripts/notify.sh` は **OSC 777 を DCS passthrough でペイン TTY へ書く**（`:4-9` / `:113-116`）。**ソケットも `wezterm cli` も要らない。** 陳腐化する参照を持たないぶん故障面が1つ少ない。こちらを採る。

**状態遷移の根拠を送信結果から外した。** OSC 777 の経路でも「書けた」は「表示された」ではない。真の受領印は本単位のスコープ外なので、**手に入らない受領印を前提にしない**方へ倒した。状態を進める根拠は**記録の書き込み成功**（局所的に検証できる）に置き、送信の成否は条件にしない。同じ `open` は既定7日ごとに鳴らし直し、**鳴らしたつもりの回数を記録に残す**ので、経路が静かに死んでいても後から気づける。

初版は `oe-vitals:324-338` の「通知に成功したときだけ焼く」を引き写していたが、**あの規律は送信の成否が判ることを前提にしていた。** 判らない経路では同じ規律が逆に働き、書けただけで既読になって以後の通知が永久に止まる。#299 の「安全装置が置物」と同型である。

昇格の判定の候補: 先例の規律を移植するときは、その規律が成り立つ前提が移植先にも在るかを見る。`oe-vitals` の seen 規律は「送信の成否が判る」に依存していた。
