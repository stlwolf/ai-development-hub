# #319 U1 — 既存 ADR 2本へ C1/C2 を追記し、判定へ上げた先を書き戻す

## なぜこの作業が始まったか

`promotion` の判定欄が入って4日で `required` が24件溜まり、誰も上げていない状態になった（#319）。仕組み（実行主体）の決定は #305 → #301 → #291 の連鎖待ちで、その先頭が halted-unconverged で閉じたので、待つ先が無い。そこで仕組みを決めずに手で上げる暫定の作業が #319 として立ち、第1段の調査が24件を置き場別に8単位へ割った。**本単位はその U1** で、**新規ファイルを作らず既存 ADR 2本に各1節を足す**いちばん巻き戻しの小さい単位である。

対象は監査済み9件のうち2件で、どちらも「新規 decision ではなく既存 ADR の続き」と判定されている。C1 が承認の成立条件、C2 が画面ベース状態判定の許容範囲である。

## 上流の断定を自分で確かめ直した

brief は追記先2本と「判定は監査済み」を断定しているが、これは上流（`.oe/report-288-required-audit.md` と `.oe/report-319-stage1.md`）の産物である。注入された negative knowledge（`01KYMRE1NC7XX6N66RQ0MGGHF1`）がまさにこの位置を指しているので、**追記先が本当にその2本で正しいかを一次から確かめた。**

確かめたのは4点である。

1. **C1/C2 の judgment 実体**: `2026-08-10-episode-239-child-liveness-recipe.md` の `promotion` 欄の1件目（`:22-24`）と2件目（`:25-27`）が、報告書のいう C1/C2 と同じ subject であること。両者の `ref` が指す本文節（`本文: 規範に1行足す判断` = `:119`、`本文: 下書きの枠組みを1つ狭めた` = `:184`）を読み、棄却案が具体名で挙がっていることを確認した。
2. **C1 の追記先が正しいこと**: `2026-07-17-decision-spawn-permission-handshake.md:41`（§決定 2）が「認可の実体はハーネスの分類器であり、その解除は owner の直接アクションのみ」と決めている。C1 が足すのは**その owner の直接アクションを何をもって受け取ったとするか**で、同じ層の内側にあたる。
3. **C2 の追記先が正しいこと**: `2026-07-09-decision-238-239-succession-watchdog-lean-arch.md:106` が「お見合い pane-capture heuristic（段階2）」を明示的に先送りしている。C2 はまさにその heuristic に課す制約である。同 ADR `:102` が「低 context hang は beat も context% も動かない」という穴を書いており、段階2 で画面に手が伸びる理由もそこに在る。
4. **①既出でないこと**（`document-format.md:696` が grep での欠落確認を要求している）: C2 の軸（`1枚の画面` / `1枚のスナップショット`）は decision 層に1件もヒットしない。C1 の軸（`承認は経路` / `経路で判断`）も同じくゼロ。追記先 ADR 自身にも、承認の受け取り側を扱う記述は無い（`:42` は発火層の同定、`:64` は durable pre-auth で、どちらも別の論点）。

つまり上流の推奨と結論は一致したが、**一致は自分で確かめた結果である。** 数と判定を写していない。

昇格の印: 上流の断定を検算した結果が一致したとき、「一致した」だけを書くと検算したことが読み手に伝わらない。検算の述語（何を突合したか）を残すかどうかは、報告の形式の判断である

## 書き戻しの置き場が、素直な場所に無かった

受け入れ条件に「episode 側の判定に上げた先を書き戻す」が在る。素直に読めば `promotion` の該当エントリに行き先を足すことになるが、**そこには足せない。**

`document-format.md` の「昇格の判定」節が欄の形を機械契約として閉じている。

- `:510` — 「**本欄は機械契約の3つ組だけを持ち**、対応づけは `subject` で行う」。`landed:` のような4つ目のキーは足せない。
- `:495` — `ref` の形式は `本文: <見出し>` **または** `本文なし: <理由>` の2形だけで、配列が許されるのは根拠が複数箇所にあるときである。`ref` は「判定の**根拠の在り処**」なので、上げた先は意味的にも `ref` ではない。

**そこで欄を検査する機械の側も見た。** 注入された2件目の negative knowledge（`01KYJ76D7CS7EBY3WDYY1NS9Y2`）が「規範を触るとき、それを検査するゲートの範囲にも同時に触れるなら整合を確かめよ」と言っている位置である。`bin/` `lib/` `tests/` `scripts/` を `promotion` で走査したところ、**この欄を読む機械は1つも無い**（検査は #286 に未着地）。したがって欄を拡張しても機械は何も言わないが、**言わないことは許可ではない。** 規約の文が「3つ組だけ」と閉じているので、機械の不在を理由に足すのは規約に反する。

**採った形は2つである。**

- **frontmatter の `related[]` に既存型で2件足す。** §7 の昇格の参照（`:357`）が「provenance は本文の散文注記で残し、**`ref` には committed の昇格先を張る**」と定めており、`related` の `ref` に昇格先を置くのは規約が想定している向きそのものである（§13.4 の `:723` も昇格を「内容の移設 + 参照の張替」で1単位と定める）。**型は最初 `evidence_for` を選んだが、実装SO の指摘で `reference` へ直した** — 経緯は `本文: 実装 SO（ゲート4）が、自分の出典を全部壊していたことを見つけた`。
- **closure の蒸留シグナルに、実行の事実を足す。** 同節は「どちらも実行は本単位の外で、行き先は #239 の後続か owner が別途決める」と書いていて、この記述が本単位で偽になった。既存の文は消さず、**別単位からの後追いの書き戻しであることを明示して**足す。

**棄却した案**を残す。(a) `promotion` に4つ目のキーを足す — `:510` に反する。(b) `ref` に3つ目の形を足す — `:495` に反し、意味も根拠ではない。(c) `related` に `promoted_to` という新しい型を作る — §7 の `:355` は新型の追加を許しているが「既存の型で表現できるなら既存を使う」と条件を付けており、`evidence_for` で表現できる。加えて型を足すなら §7 の語彙表（＝規約本体）も直すことになり、#319 が scope 外に置いた規約の改訂に入る。

昇格の印: 上げた先を機械可読に持つ欄が `promotion` に無いので、書き戻しは `related` と closure の散文へ散る。欄に置き場や上げた先を持たせるかどうかは、#286 の機械検査と #305 の実行主体の設計に効く判断である

## 追記の中身をどう決めたか

**両節に同じ4つの見出しを立てた** — 決定 / 棄却した案 / 当時の前提（将来偽になりうるもの）/ 覆すコスト。decision 層の中核が「解釈が複数ありうるものに一つの解を与えた記録で、**覆すには同程度の議論を要する**」なので、覆す人が当時の前提と覆すコストを読めない節は中核を満たさない、という理由である。委譲の書面も同じことを要求していた。

**規範の文言は転記せず、正本への pointer だけにした。** `episode-retrospective/SKILL.md:156-162` が機械契約の複製を禁じ、「decision 側に書き写された enum の値そのものは正本への pointer に置き換える」と定めている。規範の1行は enum ではないが、**同じ理由がもっと強く当たる証拠がこの単位の材料の中にあった** — 元 episode 自身が、書き換わった規範の古い版を引用したまま closure に入り、外部チェックで拾われている（`:214`）。**転記した瞬間に版ずれの種を撒くので、追記側で同じ失敗を繰り返さない。** 代わりに「転記しない」理由をその場に1行書いて、後から誰かが親切心で全文を貼り直すのを防いだ。

昇格の印: 規範の本文を decision へ転記せず pointer に留める判断。`episode-retrospective` は enum の値について同じことを言っているが、規範の散文まで同じ扱いにするかは書いていない

**verification status のタグは watchdog ADR 側だけに付けた。** あちらは末尾に凡例の節を持っているので、その語彙（`[verified]` / `[unverified-summary]` / `[speculation]`）に合わせた。spawn 側は凡例を持たないので付けていない — **無い語彙を持ち込むと、その ADR の他の節が無タグであることが「未検証」を意味するかのように読める。** watchdog 側では別環境の実測に依存する1点（`%cpu` が画面の再描画コストの代理かもしれないという疑い）を `[unverified-summary]` のままにした。

**追記の位置は2本で違う。** spawn 側は末尾に置いた。watchdog 側は `verification status 凡例` の**直前**に入れた。凡例は文書全体にかかる末尾の節なので、その後ろに実体の節を置くと凡例の射程が読めなくなる。どちらも**既存の節は1行も書き換えていない**（`git diff` の削除行が両ファイル 0）。

**見出しに追記であることを書いた**（「#239 の判定から追記・2026-08-11」）。既存 ADR に後から足した節は、いつ・何を起点に足されたかが本文から読めないと、元の決定と同時に決まったものだと誤読される。先例は `2026-05-14-decision-issue-20-phase-convergence.md:68` の「（Step 4-1 フェーズ 5 で追記）」である。

**2節を互いに参照させた。** C1（承認の受領）と C2（稼働判定の許容範囲）はどちらも「画面から何を読んでよいか」に触れるので、片方だけを読んだ人が他方を緩めないように、**別の判断であることを両側に明示した。** 元の episode が同じ理由で `promotion` を2件に分けている（片方だけを挙げると、もう片方が判定されなかったように読める・`:286`）。

brief の slot に載っていた item は2件で、**どちらも適用機会が実際に在った**ので1レコードずつ書き戻した（`ref: "#319"` / `state: followed`）。期待集合を durable に残すため id をここに書く。

- `01KYMRE1NC7XX6N66RQ0MGGHF1` — 上流の断定を自分の成果物へ写すな。適用は `本文: 上流の断定を自分で確かめ直した`。
- `01KYJ76D7CS7EBY3WDYY1NS9Y2` — 規範を触るとき、それを検査するゲートの範囲にも同時に触れるなら整合を確かめよ。適用は `本文: 書き戻しの置き場が、素直な場所に無かった`。

`validate-knowledge` は2件とも OK。既存レコードは書き換えていない（両ファイル削除行 0）。

## 実装 SO（ゲート4）が、自分の出典を全部壊していたことを見つけた

弱 SO を2レーン（codex / claude）で回した。両レーンとも実返却あり。出力は `tmp/` 配下で git の外に出るので、判定も含めてここに転記する。

| レーン | 総合判定 | 分量 / 所要 | 答えたモデル |
|---|---|---|---|
| codex | **CRITICAL 3件 / WARNING 3件・現状はマージ不可** | 10.4KB / 273秒（**初回は 480秒で `timeout_empty`・×1.5 の再試行で返った**） | `gpt-5.6-sol`（設定からの値で、実行の観測値ではない） |
| claude | **重い欠陥3件 / 中3件 / 軽4件・マージ前に直すべき** | 27.1KB / 622秒 | **記録できていない**（`unavailable:schema-unexpected`） |

**`SO_TIMEOUT` の既定 240秒では足りないと分かっていたので 480秒にしたが、それでも codex は初回に返らなかった。** `so-compare` のスキルは「レビュー級の SO では 400〜480秒程度へ引き上げを検討」と書いているが、**本件はその上限で足りていない**（返ったのは再試行の 720秒枠で、実所要は 273秒）。レビュー級の実所要は初回枠を超えても再試行で収まる形になっており、初回枠を上げるほうが速いという同スキルの分析（claude レーンについての記述）は codex にも当たる。

### 両レーンが独立に当てた最も重い指摘 — 出典16件が自分の第2コミットで壊れていた

**これは本単位が作った欠陥である。** ADR 追記（第1コミット）を書いた時点の episode の行番号を引いたが、その直後の書き戻し（第2コミット）が **frontmatter に6行・closure に1行**を挿入したので、旧 N 行目は N が 14〜280 なら N+6、281 以降なら N+7 へ動いた。**引いた16件すべてがこの範囲にある。**

とくに悪い形になっていたのが、両 ADR が「該当の判定は同 `:16-18` / `:19-21`」と書いていた箇所である。**現在のその行は、自分が第2コミットで足した `related` エントリそのものを指していた** — C1/C2 の判定を指すはずの出典が、C1/C2 の書き戻しを指す循環になっていた。ずれの中には内容として逆を指すものもあった（`:59-60` は「既定は属性を落とす」の根拠に引いたが、動いた先は属性付き capture のコマンド例だった）。

**これは追記した本文の主題そのものを、自分が踏んだ形である。** C1 の節には「規範の文言を転記しない。転記は版ずれを生む」と書き、その根拠として元 episode が古い版を引用していた実例を挙げた。**その節が、同じ PR の中で同じ壊れ方をした。** 行番号は参照先が同一 PR 内で動くときに必ずこの型を踏む。

直したうえで、**行番号に節名を併記する形**にした（`同 :119-135`（節「規範に1行足す判断」））。行番号だけだと次に誰かが episode を触った時点で同じことが起きるが、節名が在れば辿り直せる。**最終状態で16件を再照合し、全件一致を確認した。**

昇格の印: 同一 PR の中で参照元と参照先の両方を触るとき、行番号で引いた出典は必ず壊れる。照合を「引いた時点」でなく「最後の編集の後」に置くかどうかは、出典の張り方の判断である
