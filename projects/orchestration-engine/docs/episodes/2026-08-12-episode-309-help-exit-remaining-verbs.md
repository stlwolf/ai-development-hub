`reconstructed` — 本 episode は closure 時に一括で書いた。作業中のリアルタイム追記ではない。

## なぜこの作業が始まったか

直前の単位（PR #321）で `oe-send` の帯を直し、**残りの取り残しは「直さずに一覧を報告」**という指定だったので報告に留めた。その報告を受けた owner が「あんまり細かく切らないで、ちゃちゃっと直せるところに行って、合わせて起票してしまえ」と判断したので、**一覧のうち機械的に直せる3本を消化した。**

`oe`（help 分岐が無く `--help` で 1 サイクル起動する）は別種で、何を表示すべきかの判断が要るので入れていない。`cc-lint` の素通りと `HOME` 未設定は #322 に切った。

## やったこと

`usage()` から `exit` を外して表示だけを担わせ、exit は呼び出し側が決める形にした。PR #315 と #321 と同じ形である。呼び出し点は3本あわせて **10か所**で、すべてに明示の `exit` を置いた。

| verb | 呼び出し点 | 備考 |
|---|---:|---|
| `oe-ack` | 4 | **2か所は `if` ブロックの最後の文が `usage` だった。** `exit` を書かなければ処理が先へ進む |
| `oe-delegate` | 3 | 先へ進むと spawn の副作用が出るので影響が最も大きい |
| `oe-report` | 3 | 1 は「親ペインが無い」を意味しており、そこに help が混ざっていた |

実測では13ケースすべてが変更前 1 で、変更後は help が 0、unknown option と必須引数の欠落が 2 になった。

## 契約の説明文はあえて足していない

`oe-send` では help 本文に exit 契約を書いた。**今回は書いていない。**

直前の単位で、その契約文を「送信した→0」と書いて **`--help`→0 を落とし**、実装より狭い契約になっているのを実装SO が検出した。本変更の目的そのものが契約から抜けていたという失敗である。3本それぞれの exit の意味を全経路洗い出したわけではないので、**同じことをもう一度やる余地がある。** 実装より狭い契約や誤った契約は、契約が無い状態より悪い（読み手が信じるため）。

したがって帯の移動だけを行い、契約文は書かなかった。書くなら各 verb の全経路を洗い出す別単位にする。

## テストが1件落ちた

`test_oe_ack.sh` の `--all` と target の同時指定が **exit 1 を期待していた**。これは旧契約（`usage()` 経由は 1）を固定していたテストなので、新しい帯に合わせて 2 へ直した。

**全38本を回して見つけた。** 直前の単位では関係しそうな5本だけを回していたので、同じやり方だとこれを見落としていた（`test_oe_ack.sh` は5本に入っていたので今回は拾えたが、範囲を絞る判断そのものが危うい）。**契約を変える変更では、影響範囲を推定せずに全部回すのが安い。**

あわせて3本に help と呼び方の誤りの検査を13件足し、`oe-delegate` では spawn に至らないことも確かめた。既存テストの期待値だけを書き換えて終わると、契約が固定されないままになる。

## 呼び出し側を確かめた

3本の exit を検査している呼び出し側は **repo 内に無い**（`bin/` / `lib/` / `scripts/` / `canonical/hooks/` を `rc=` と `$?` で走査し、当該 verb 自身とそのテストを除くとゼロ）。

**ここで自分の主張が1つ間違っていた。** 当初「`oe-ack` は本変更で exit 1 を返す経路が無くなる」と書いていたが、**誤りである。** `oe-ack:179` は `PANE="$(oe_reg_resolve "$TARGET")" || exit` で宛先を解決しており、`oe_reg_resolve` は解決できないラベルと曖昧なラベルに **1** を返す。それがそのまま伝播する。実測すると変更前も後も `oe-ack <解決できないラベル>` は 1 である（`oe_reg_resolve: no live target matches`）。

**間違えた原因は測り方である。** ファイル内の literal な `exit 1` を grep して「無い」と結論した。**source した関数の `return` が `|| exit` で伝播する経路は、その grep には映らない。** exit code を数える作業では、ファイル内の文字列ではなく実際の経路を見なければならない。

したがって `oe-ack` の 1 は `oe-send` と同じ意味（宛先が解決できない）で**変更前から在り、本変更でも保たれている**。帯としてはむしろ揃っている。

**`oe-kick` だけは `exec` で `oe-delegate` を呼ぶので exit がそのまま伝播する。** 確かめたところ `oe-kick` は**既に正しい帯に居た**（help→0・unknown option→2・値の欠落→2）。つまり変更前は、**同じ呼び出し経路の中で `oe-kick` が 2 を返し、その先の `oe-delegate` が同じ種類の誤りに 1 を返していた**。本変更でここが揃う。

## 触らなかった帯の重なり

`oe-delegate:162` と `oe-kick` の `exit 1` は「TMUX_PANE が無い（tmux 外で実行した）」で、`oe-delegate:362` の `exit 1` は「子ペインが起動中に死んだ」である。**前者は環境エラーなので、帯として整理するなら 2 が筋**だが、後者は実行時の失敗なので 1 のままでよい。**1 が2つの意味を兼ねている。**

今回は触らない。help と呼び方の誤りを 1 から外すことが本単位の範囲で、環境エラーを 1 から 2 へ動かすのは呼び出し側の前提を変える別の判断である（両者は独立に決められる）。#309 のコメントに残した。

## 実装SO（ゲート4）が、帯の隣にあった黙った切り詰めを見つけた

第1ラウンド（`audit_id: 20260811161749Z8W86BRCHSAG` / `reviewed_sha: 2512fc9` / codex は `gpt-5.6-sol` で137秒・cursor は `auto` で132秒、解決先は記録されず）は **codex が `refuted`・cursor が `survived`** で割れた。

**cursor（survived）**: `usage` の全10呼び出しに明示の `exit` があり fall-through も spawn 漏れも無い、既存の 1（`oe-report` の親未解決 / `oe-delegate` の環境と子の死 / `oe-ack` の resolve 失敗）も汚れていない、と確認した。**本変更の本体はこれで裏が取れた。**

**codex（refuted）**: 帯そのものではなく、**その隣にあった欠陥**を指した。3本は必須の位置引数を1つ目からしか読んでおらず、**2つ目以降を黙って捨てる**。3本とも `$@` も `$*` も使っていないので、余った語はどこにも現れない。

**いちばん危ないのは `oe-delegate` である。** クォートを忘れて `oe-delegate my task here` と打つと、task は `my` だけになり、**切り詰められた指示のまま子が spawn する。** 気づくのは子の様子を見てからになる。`oe-report` も同じ形で、切り詰めた message を親へ送る。

採って直した。PR #315 が `oe-hookfire` / `oe-selfcheck` に入れた `unexpected argument` の検査と同じ形で、呼び方の誤りなので 2 で弾く。**`oe-send` には入れていない** — あちらは ad-hoc テキストを位置引数で受けて `$*` で空白連結する仕様なので、複数の位置引数が正当である。**verb ごとに位置引数の意味が違うので一律には入れられない。**

壊れる呼び出しが無いことを確かめた。`canonical` のスキルと `bin/README.md` の実例はすべて位置引数を1つだけ渡しており、`oe-kick` は `oe-delegate` を `exec` するが `--` の後に1つだけ渡す。

**この指摘は帯の話ではない。** 本単位は「help と呼び方の誤りを 1 から外す」ためのもので、位置引数の検査はそこから出てこない。**同じ引数解析を読んでいたのに自分では見ていなかった** — 直す対象（`usage()` の `exit`）だけを見て、その周りを見ていない。

**第2ラウンド**（`audit_id: 202608111626346MNZFAE50VT7` / `reviewed_sha: e1e0e99` / codex は `gpt-5.6-sol` で125秒・cursor は `auto` で235秒）は **2レーンとも `survived`**。足した検査が正当な呼び出し（`--all` との併用 / `--brief` のみで task 無し / `--review` / `--` 以降のハイフン始まり）を誤って弾かないこと、`$#` を見る位置が引数解析ループの後で正しいこと、既存の 1 の意味が汚れていないことを、両レーンが実コードで追跡して確認した。

**第2ラウンドは、それとは別に自分の主張の誤りを1件訂正した。** 私が渡したコンテキストの「`oe-ack` は 1 を返す経路が無くなる」に対し、codex が「実際には解決失敗の 1 が既存どおり残る」と指摘した。**これは正しかった**（下記）。
