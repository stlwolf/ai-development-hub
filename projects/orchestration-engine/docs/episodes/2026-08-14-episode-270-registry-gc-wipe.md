# #270 registry GC が別 server pid の混入で全 entry を消す — 作業記録

## なぜこの作業が始まったか

cockpit の登記（`~/.claude/state/oe-delegate/`）の GC が、壊れた server pid で登記系コマンドが1回走ったのをきっかけに、生きている全 entry をまとめて消す。運用中に3回起きており、直近の1回は同じマシンで並行していた別ツリーの cockpit も巻き添えにした。登記ディレクトリが全 tmux ツリーで共有だからである。復旧は各 root からの再登記で済むので実害は小さいが、統括の観測基盤が突然落ちる体験を減らすための堅牢化として起票された。対策候補が3つあり、どれを採るか（あるいは何もしないか）が未決なので、選ぶこと自体が設計判断である。

## Step 1 — 一次読解（コードと issue コメント）

`oe_reg_gc`（`lib/delegate-registry.sh:167-186`）と、issue #270 の本文 + コメント3件を読んだ。issue 本文に書かれていない事実が2つ出た。

### 発生の型は2つある（issue 本文は1つしか書いていない）

削除条件は `[[ "$base" != "${pid}_"* ]]`（`:182`）で、`pid` は `_oe_reg_server_pid` が `$TMUX` の2番目のフィールドから取る。

- **型A: pid が別の値**。issue 本文が書いている型。detached な文脈で `$TMUX` が別 server の pid に解決される。
- **型B: pid が空**。コメント（2026-07-23 と 2026-08-11）が観測した型。`$TMUX` が失われると `_oe_reg_server_pid` は空文字を返し、prefix が `_` になる。正規の `25967__*` が全て不一致になって全滅する。残る stray は `__330.json` のように pid 部が無い名前になる。

**3回目（2026-08-11）で引き金が1本確定している。** 壊れた環境で `oe-delegate` を実行し、`__330.json` が書かれ、その `oe_reg_record` 末尾の GC（`:64`）が `25967_` で始まる正規 entry を全部消した。過去2回は引き金を切り分けられていなかった。

（**この節の当初の記述を後で訂正した。** issue コメントの文言をそのまま引いて「`TMUX` / `TMUX_PANE` が失われた状態で」と書いていたが、実コードと両立しない。下の「gate 1 の SO が見つけた自分の誤り」節を見よ。）

owner はこのコメントを自分で訂正しており、「他ツリーを巻き添えにする」は本文の「全 entry」に含まれる既知の帰結で新規性は無い、優先度を上げる材料にもならない、と書いている。**新しいのは引き金の経路が1本確定したことだけである。** ここは過大に読まない。

### 既存ガードが覆わない範囲

`:174-175` の空ペインガードは `tmux list-panes` の rc と出力の空を見ているが、`$TMUX` が無くてもデフォルトソケットのサーバへ繋がれば `list-panes -a` は成功して非空を返す。したがって型A / 型B のどちらもこのガードを素通りする。

### registry を読む消費者に「pid が空なら触らない」先例が既に2箇所ある

（当初この見出しを「同じ lib に」と書いていたが不正確なので直した。`event-bus.sh` は `lib/` だが `oe-ident` は `bin/` で、`delegate-registry.sh` 自身には先例が無い。正確には「registry を読む消費者群に2箇所」である。SO の codex レーンが同じ点を指摘した。）

`event-bus.sh:75` と `bin/oe-ident:67` は、`${pid}_*.json` を glob する前に `[[ -n "$pid" ]]` を必ず確かめている。pid が空のまま glob すると別物を掴むからである。**`oe_reg_gc` だけがこの作法を持っていない。** 対策の選択にあたって、これは「新しい発明を入れる」のではなく「既存の作法を GC にも揃える」形が1つあることを意味する。

昇格の印: registry を読む2箇所に pid の空を扱う作法が在るのに、最も破壊的な操作（削除）を持つ関数だけがそれを欠いていたという構造

## Step 2 — gate 1（ゼロベース代替探索）

### 自分で回した1巡目（SO を待つ前）

issue が挙げている3案 + 「何もしない」を出発点に、暗黙の前提を先に言語化してから案を足した。前提を書き出す段で、案が増えた。

暗黙の前提は6つあった。

- P1 登記ディレクトリは1つで、全 server が同じ平坦な名前空間を共有する。
- P2 single-server 前提なので「別 pid の entry はゴミ」と単純化して安全だった。
- P3 GC は書き込みのたびに暗黙に走る（**書き込みが破壊的掃除を引き起こす**）。
- P4 `$TMUX` は身元の情報源として無検証で信頼されている。
- P5 廃棄手段は削除のみで、隔離も soft-delete も無い。
- P6 既存ガードの合格条件は「環境が動いたか」であって「これから何件消すか」ではない。

P3 を書いた時点で、**`oe_reg_gc` の呼び出し元が `oe_reg_record` の末尾1箇所しかない**ことを grep で確かめた（`:64`）。これが探索の形を変えた。定期実行や独立 verb から呼ばれていれば「GC 自体を賢くする」以外に手が無いが、呼び出し元が書き込み経路1本なら、**書き込みを止めれば GC は起動しない。**

探索木（採否は gate 1 の SO を見てから確定する）。

```text
DJ-1 全消しをどう止めるか
├── A サニティガード（全件/一定割合を消すならスキップ）→ 差分軸: 結果を見る（P6 を崩す）
├── B 不正 pid の検知（空・pid=1・実サーバと不一致ならスキップ）→ 差分軸: 身元を検証する（P4 を崩す）
├── C pid スコープ見直し（別 pid は削除せず無視）→ 差分軸: 削除条件そのもの（P2 を崩す）
├── D 何もしない → 差分軸: 受容（復旧容易・実害なし・起票者本人が優先度は低いと明記）
├── E 書き込み側の不変条件（pid 不定なら record がエラー）→ 差分軸: 責務を write path へ（P3 の唯一の入口を断つ）
├── F server 別サブディレクトリ（`<pid>/` に分ける）→ 差分軸: データ配置で爆風を構造的に囲む（P1 を崩す）
├── G pid の導出元を変える（tmux 自身に訊く）→ 差分軸: 根本原因（P4）。ただしキー契約に触れる
├── H 非破壊 GC（`stale/` へ退避）→ 差分軸: 誤りの確率でなく誤りの代償を下げる（P5 を崩す）
├── I 書き込み経路から GC を外す（独立 verb / 定期）→ 差分軸: 実行経路（P3 を崩す）
└── J 年齢ベース GC（新しい entry は pid に関係なく残す）→ 差分軸: 判別子を時刻に替える
```

E・F・G・H・I・J は issue の3案の外にある。**前提を6つ書き出す作業が、そのまま案を6つ増やした**（案から案を連想したのではない）。

### この探索で出た、案の選択より上流の気づき

**削除条件（`:182`）は独立した2つの理由を `||` で混ぜている。** 「prefix が現 pid と違う（身元が不明 / 別サーバの持ち物）」と「生存ペイン一覧に無い（ペインが死んだ）」である。**後者は GC の本来の目的で、前者だけが事故を起こしている。** したがってガードは条件全体ではなく**身元の側の帯にだけ**当てるのが筋になる。

これは採用した negative knowledge の `01KYA7C9NN4VDM7H2NYXZB2PSX`（環境の失敗とデータの不備を別の帯に分けよ）が、GC の削除理由にそのまま当たった形である。既存ガード（`:174-175`）が `tmux list-panes` の失敗と空の結果を同じ経路で扱っているのと**同じ構造が、削除条件の側にもあった。**

昇格の印: ガードを「条件全体」ではなく「混ざっている2つの帯の一方」に当てるという判断の形

### A を採るなら踏む罠を先に書いておく

`01KZ21M0N0FZ4YMR2R6DPHTWQ4`（合格条件を累計で書くな・直近の窓で見よ）の一般形をここへ当てる。**「全件消すならスキップ」は、entry が1件しか無くその1件が正当に死んでいる場合に、正当な GC を永久に妨げる。** 割合で書くと「静かに何もしなくなるガード」になりうる。ガードの条件が壊れた状態でも通り続ける形になっていないか、という問いを、今回は「ガードが正しい仕事を止め続ける形になっていないか」の側から確かめる必要がある。

この罠は SO への質問4として明示的に投げた（追認を誘発しないよう、自分の傾きは伏せて出した）。

### 型B を隔離環境で再現した（推論でなく実測）

SO を待つ間に、機構を読解だけで確定させず隔離環境で再現した。`OE_DELEGATE_STATE_DIR` を `mktemp -d` に差し替え、実環境の共有 registry（`~/.claude/state/oe-delegate/`）には触れていない（スクリプト冒頭で `$HOME/.claude/*` を掴んでいたら中断する確認を入れた）。

正規 entry を2件（`25967__287.json` / `25967__327.json`）置き、`TMUX` を外した副シェルで `oe_reg_record "%330"` を1回だけ実行した。

```text
  _oe_reg_server_pid -> ''
  _oe_reg_key %330   -> '__330'
  --- record 直後（末尾の GC 実行後）---
__330.json
```

**2026-08-11 の観測（`__330.json` だけが残る）と完全に一致した。** issue のコメントが報告した形が、そのまま再現する。

あわせて、既存ガードが素通りする根拠も実測した。実 tmux に対し `env -u TMUX tmux list-panes -a` を走らせると **rc=0 で13行返る**。したがって `$TMUX` が無くても `:174-175` のガード（rc と空出力を見る）は通過する。**「list-panes が失敗するはずだから守られている」という読みは誤りである**ことを、推論ではなく実行で確かめた。

再現スクリプトは作業層に置いた（`tmp/` ではなくセッションのスクラッチ）。回帰テストの原型としてそのまま `tests/` の流儀（tmux 関数モック + `mktemp -d` 隔離）に載る形にしてある。

### 案K — 探索木の外で出た案（tmux を「キーの出所」ではなく「検査の物差し」に使う）

SO を待つ間に案G（pid の導出元を tmux 自身に訊く形へ変える）を検証しようとして、**G の弱点はキー契約に触れることだが、それは tmux を*キーの出所*として使う場合に限る**ことに気づいた。tmux に訊いた pid を**検査にだけ**使えば、キー生成（`wt-pane-issue.sh` / `session-name.sh` との契約）は一切動かさずに済む。

さらに、検査の物差しは**既存の `list-panes` 呼び出しの書式を伸ばすだけで取れる。**

```text
$ tmux list-panes -a -F '#{pane_id} #{pid}'
%331 25967
%321 25967
```

`$TMUX` を外して同じことをすると、`list-panes` は既定ソケットのサーバへ繋がって **pid=25967 を返す**一方、`_oe_reg_server_pid` は空を返す。**つまり食い違いが1回の呼び出しの中で検出できる。**

これが案Kである。**GC が正しく動くための不変条件は「prefix に使う `pid` が、`live_keys` を作ったサーバと同一であること」**で、案K はその不変条件を直接検査する。成立しなければ GC を丸ごとスキップする。

- 型B（pid が空）も型A（pid が別値）も**同じ1つの検査で覆う**。型ごとにガードを足さない。
- **物差しと母集団が同じ呼び出しから来る**ので、2回呼ぶ間に食い違う隙（provenance のずれ）が構造的に無い。
- 割合や件数のしきい値を持たないので、案A の「静かに正当な GC を止め続ける」罠に触れない。

昇格の印: 外部の権威を「値の出所」ではなく「整合の物差し」として使うと、既存契約に触れずに検証だけ足せるという形

案G を「キー契約に触れるから不可」で棄却しかけていた。**棄却理由が案の一部にしか当たっていなかった**わけで、これは初期セットの外に案が残っていた典型である。

### cursor レーンが持ってきた、自分に無かった事実（自分で突き合わせた）

cursor レーン（153秒・16KB）は案C（別 pid は削除せず無視）を第一候補に選び、**自分の案K と同じものを「新案L（命名身份と破壊権限の二重証人）」として独立に出した。** 収束は確信を上げるが証明ではない（同じ盲点を共有しうる）ので、レーンが挙げたコード根拠は自分で開いて確かめた。

**(1) 読み取り側は既に案C の意味論で動いている。** `bin/oe-tree:417-419` は別 pid の entry を `FOREIGN` として数え、`continue` で**残したまま飛ばす**。

```sh
if [[ "$_base" != "${SERVER_PID}_"* ]]; then
  FOREIGN=$((FOREIGN + 1))
  continue
fi
```

**同じ prefix 判定に対して、読み取り側は「他人の持ち物だから触らない」、GC だけが「ゴミだから消す」という意味論を持っている。** 案C は新しい方針の導入ではなく、**GC を読み取り側の既存の意味論へ揃える**変更である。これは自分の案K（整合の物差しを足す）より、`behavioral-rule` §6（既存パターンに従う）の観点で強い根拠である。自分はこの不整合に気づいていなかった。

**(2) 案E を採るなら、呼び出し側が失敗を握り潰している。** `bin/oe-delegate:373` は `oe_reg_record ... || true` である。

```sh
oe_reg_record "$CHILD_PANE" "$LABEL" "$WORKSPACE" "$PARENT_PANE" || true
```

したがって「pid が不定なら record がエラーを返す」だけでは、**登記されていないのに成功扱いで進む**。案E は verb 側のエラー伝播まで含めないと成立しない。**採用した negative knowledge `01KYA7C9NN4VDM7H2NYXZB2PSX`（失敗を握り潰して空を後段へ流すな）が、今度は自分の対策案の前提条件として当たった形である。**

**(3) 既存テストの契約が反転する。** `tests/test_delegate_registry.sh` の [6] は `stale foreign-pid removed` = `no`（削除されること）を期待している。案C を採ると**この期待は逆になる。** 受け入れ基準の「既存テストが回帰しない」と衝突するので、plan では「意図的な契約変更として期待値を更新する」ことを明示し、回帰と区別する必要がある。

### gate 1 の SO が見つけた自分の誤り（2件・どちらも訂正済み）

**(1) 「`TMUX` と `TMUX_PANE` が失われた」は実コードと両立しない。** codex と claude が**独立に**同じ指摘をした。自分で一次確認した。

- `bin/oe-delegate:164-169` は `TMUX_PANE` が空なら `exit 1` する。このガードは commit `5df5984`（2026-07-18）で入っており、**3回目の事故（2026-08-11）より前**である。
- `bin/oe-register:141-142` は `TMUX_PANE` が pane id の形であることと、**それが生存ペインであること**の両方を要求する。

昇格の印: `[[ ]]` のパターンで引用部分だけがリテラル化する規則が、そのまま「壊れた入力は守る側に倒れる」という安全性の根拠になっている構造

## Step 5 — 第2周を回そうとして `so-compare --prev` の defect を踏んだ（別件）

差し替えた案K には誰も反証していない（第1周が読んだのは案C の plan）ので、案K に絞った第2周を `--prev` 付きで回した。**codex レーンが 0 秒・0 バイトで即死した。**

```text

exit_code=2 / timeout_status=error / elapsed_seconds=0 / stdout_bytes=0
```

原因を特定した。`scripts/so-compare.sh:392` は前周の回答を `head -c "$PREV_MAX_BYTES"`（既定4000）で**バイト単位に切る**。日本語は3バイト文字なので、切れ目が文字の途中に落ちると不正な UTF-8 になる。実際に生成された `prompt.txt` を検査すると、**offset 10899 が lone `\xe5`（3バイト文字の先頭バイト単独）で終わっていた。** codex CLI は引数の不正 UTF-8 を拒否して即座に exit 2 する。

```text
不正位置 offset=10899 全体=19131 bytes
前後: b'arent_pane` \xe3\x81\x8c...\xe3\x80\x81\xe5\n\n[... '
```

**このリポジトリの SO 出力は日本語なので、`--prev` を使う反復 SO は codex レーンを構造的に失う。** しかも失い方が「タイムアウトで空」ではなく「即死」なので、`timeout_empty` のリトライ経路にも乗らない。

**本単位のスコープ外なので直さない**（`implementer-contract` に従い surface のみ）。起票の可否は統括 / owner に委ねる。

第2周は 2 レーン（cursor / claude）で続行した。弱 SO の終了条件は「実返却が1レーン以上あれば disclose して進む」なので、**"0 はなし" には抵触していない**が、**3レーンを取るつもりで2レーンになったことは記録する。**

昇格の印: バイト単位の切り出しが多バイト文字を壊し、下流の CLI が「引数の不正 UTF-8」で即死する経路（`timeout_empty` のリトライにも乗らない失敗の型）
