# #303 M-2 — 空で返ったレーンへ極小の1往復を投げて原因を切る（実行記録）

**なぜこの作業が始まったか**: #303 の主痛は、claude の「exit 124・経過が上限ちょうど・stdout も stderr も 0 バイト」という形が、**普通の時間切れと使用量上限で記録が完全に一致する**ことである（B-3）。M-1 の集計では、いまの版の区間で分類に値が付くのは故障8件中1件しかなかった。**残り7件はこの形で、meta からは分けられない。** 設計SO の claude と codex が独立に「空返しの直後に極小の1往復を投げて切る」案を出し、owner が「試す」と裁定した。

## 前提（着手時点で確定していること）

- **実験フラグの下に置き、既定は無効。** 本番の経路には入れない（plan v2 の M-2）。
- **期待値を測る前に宣言する。**
- P-1 の表の各型に対して1例ずつ陽性対照を取る。**取れない型は取れないと書く。**
- baseline は master `2299767`（so-compare に版記録と入力拒否が入った状態）。

## 随時追記

### 2026-09-07 置き場を so-compare の外にした

plan v2 は「実験フラグの下で（既定は無効）・本番の経路には入れない」と書いている。**so-compare の中にフラグを置く形も採れたが、外に独立した verb として置いた。**

理由は2つある。**独立した verb なら「呼ぶこと自体が opt-in」なので、既定で無効という条件が構造で満たされる。** そして #344 の単位で、配布物（`~/bin` の symlink で全セッションへ即時反映される `so-compare`）に検査を足すたびに正当な入力を落とす形を7回作った。**測定のための往復を、その critical path に置きたくない。**

**代わりに失うものがある。** 本走行の「直後」ではなく後から走らせるので、**時間窓がずれる。** 使用量上限は数時間続くので読めるが、負荷の波のような短い要因は本走行と同じ状態を見ていない。verb のヘッダと README に書いた。

### 2026-09-07 期待値を先に宣言した

verb のヘッダに書いてから測った。

| 本走行 | canary の期待 |
|---|---|
| 時間切れ | **成功する**（数秒で返る） |
| 使用量上限 | **上限の文言つきで非ゼロ**（数秒） |
| 認証切れ | **認証の文言つきで非ゼロ**（ほぼ0秒） |
| 環境エラー | **環境の文言つきで非ゼロ**（ほぼ0秒） |

### 2026-09-07 実測で偽陰性を作った（既定の上限が短すぎた）

最初、canary の既定の上限を 10 秒にしていた。**実機で当てたら canary 自身が時間切れになった。**

```text
canary_exit=124 canary_elapsed=10 canary_state=unknown
```

**これは「CLI は応答するのに応答しないと読む」偽陰性である。** cursor へ極小の1往復（`1+1`）を投げた所要を4回測ると **9 / 10 / 13 / 17 秒** で、10 秒は最小値の付近だった。**そこに上限を置くと半分くらい落ちる。**

直したのは2箇所である。

- **既定を 60 秒にした**（最大実測 17 秒に対して約 3.5 倍。本走行の上限 240〜1200 秒に比べれば十分小さい）。
- **canary 自身の時間切れを `unknown` に畳まないようにした。** `canary_timeout` という別の値にした。「証拠が無い」と「**極小のプロンプトにも応答しなかった**」は別の情報で、後者は「本走行が重かったのではなく CLI がいま応答していない」側に寄る。

昇格の印: 測定のための往復にも上限が要る。その上限は「測りたいものの所要」ではなく「その往復自身の所要」の実測から決める

### 2026-09-07 実機で取れた型・取れなかった型

**時間切れの型は3レーンとも実機で取れた。** 短い上限で本当に空返しを作ってから canary を投げている。

| レーン | 本走行 | canary |
|---|---|---|
| cursor | `timeout_empty` / exit 124 / 8秒 / stdout 0 / stderr 0 | **success** / exit 0 / 10秒 / 2バイト |
| codex | `timeout_empty` / exit 124 / 8秒 / stdout 0 / stderr 4051 | **success** / exit 0 / 7秒 / 2バイト |
| **claude** | `timeout_empty` / exit 124 / 5秒 / **stdout 0 / stderr 0** | **success** / exit 0 / 9秒 / 2バイト |

**claude の行が M-2 の核である。** これは #303 の主痛（B-3）とまったく同じ記録の形で、**meta からは使用量上限と区別できない。** その形に対して canary は **9 秒で答えを出した。**

**取れなかった型は取れなかったと書く。**

| 型 | 実機 | 理由 |
|---|---|---|
| 使用量上限 | **未取得** | 人為的に作れない。起きるまで待つしかない |
| 認証切れ | **未取得** | ログアウトは破壊的で、owner の環境を壊す |
| 環境エラー | **未取得** | 同上（信頼済みディレクトリの設定を壊すことになる） |
| cursor の上限 | **未取得** | 当リポに実例が無く、形そのものが未知 |

**この4つはスタブで分類器だけを確かめた。** テストではスタブが本物の文言を出し、期待どおりの値が付くことを固定している。**実機の CLI がその文言をその形で出すことは、使用量上限の1例（2026-09-05 の codex）以外は確かめていない。**

### 2026-09-07 M-3 へ渡せること・渡せないこと

**渡せる**: 「本走行が切られた」と「CLI がいま応答しない」は canary で分かれる。**主痛の形（B-3）に対して 7〜10 秒で答えが出る。**

**渡せない**: 「使用量上限」と「時間切れ」を実機で分けたことにはならない。**上限の側は実機で1例も取れていない。** 論理は「上限が効いていれば canary も上限の文言つきで落ちるはず」だが、これは**スタブでしか確かめていない**。
