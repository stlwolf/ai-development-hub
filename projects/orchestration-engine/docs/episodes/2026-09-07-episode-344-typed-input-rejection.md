# #344 / #303 I-3 — レーンへ渡す前に入力を型付きの理由で拒否する（実行記録）

**なぜこの作業が始まったか**: これまで不正な入力もそのままレーンへ渡し、CLI 側で落ちるのを待っていた。落ち方は CLI ごとに違い、**1レーンだけが静かに死ぬ**形になりうる。#340 では `--prev` の切り詰めが作った不正な UTF-8 で codex が exit 2 で即死し、3レーンで計画した検証が2レーンで進んだ。**「返らなかったレーンがあること」も「その原因」も消費者に届いていなかった。**

## 前提（着手時点で確定していること）

- plan v2 の I-3。**終了コードは `oe-refute` の `refuted`（3）と衝突しない値にする**（gate 2 の3レーンが揃って指摘し、`lib/so-verdict.sh` と `bin/oe-refute` を開いて確かめてある）。
- **検査は1箇所ではなく境界ごとに置く**（初版の「1箇所」は gate 2 で撤回済み）。
- 基準は「その入力の権威がどこにあるか」。利用者が明示的に指定したもの（`-c` / `-f` / `-w`）は拒否し、ツールが自分で作った参考情報（`--prev` の切り詰め）は修復してよい。

## 随時追記

### 2026-09-07 終了コードを 4 にした

**3 は使えない。** `so_verdict_exit()` が `refuted` に exit 3 を割り当てており、入力の拒否に 3 を使うと**入力の不備が「設計が反証された」として上位に届く**。

**あわせて既存の `exit 1` も 4 へ寄せた。** 1 は「部分成功（一部のプロバイダのみ応答）」の番号で、**「呼び方を間違えた」と「一部だけ返った」が同じ値だった**（plan v2 の §8 で指摘していた不整合）。移した先は14箇所ある。

型は2つの接頭辞に分けた。**利用者の入力の誤り**は `invalid:`、**環境に足りないもの**は `unavailable:` である。どちらも「レーンを1本も起動していない」点では同じなので終了コードは同じにし、どちらなのかは stderr の型で分ける。

### 2026-09-07 消費者の側も直した

`oe-refute` / `oe-review` は so-compare の終了コードを 2 のときしか見ておらず、それ以外は素通りしていた。**素通りすると、0 レーンの出力から VERDICT が取れないまま error として数えられ、保守側の集約が `refuted` を作る。** exit 4 を足すだけでは、入力の不備が「設計が反証された」に化ける経路が残る。

両 verb に `so_rc -eq 4` の分岐を足し、**判定を作らずに exit 2 で止める**ようにした。**スタブで実際に確かめてある**（`OE_REFUTE_SO_COMPARE` を `exit 4` するスクリプトに差し替え、`oe-refute` が 3 ではなく 2 で返ることを見た）。

### 2026-09-07 自分で偽陽性を作った（macOS の iconv）

最初、組み立て完了時点の検査を `printf '%s' "$PROMPT" | iconv` の形で書いた。**妥当な本文が不正と判定された。**

原因は macOS の `iconv` で、パイプから読ませると `iconv(): Inappropriate ioctl for device` で落ちることがある。ファイルを引数で渡すと同じ内容でも通る。

**検査対象を `prompt.txt` に変えた。** so-compare はもともと組み立て後の本文をこのファイルへ保存しているので、**保存してから見る**形にした。パイプを使わないので落ちないし、**実際にレーンへ渡る本文そのものを見る**ことになるので対象としても正確である。

昇格の印: 検査を足したら「不正を弾けるか」だけでなく「正当なものが通るか」を先に確かめる（自分の検査が偽陽性を出した）

### 2026-09-07 上限バイト数での拒否は入れなかった

plan v2 の型の表には `invalid:too-large` を挙げていたが、**入れていない。** 現状は 50KB 超で警告するだけで、**拒否の閾値を決める根拠がまだ無い**（plan 自身も「過去のプロンプト長の分布を見てから決める」としている）。**根拠のない閾値を配布物に焼くと、正当な大きい入力を落とす。** 理由をコードのコメントに残した。

### 2026-09-07 自分の観点を自分のコードへ当てて1件見つけた

3周目の指摘10（stdin の NUL）で「**自分で立てた観点を、自分のコード全体に一通り当ててから外へ出す**」と書いた。**それをその場で実行した。**

外部の値が変数へ入る経路と、算術で使う値を全部洗ったところ、**モデル名とエフォートと sandbox モードが素の値のまま meta へ書かれている**ことに気づいた。実機で確かめると、

```text
model_requested=a
b=c
```

**`SO_CURSOR_MODEL=$'a\nb=c'` を渡すと meta の行が割れ、偽のキー `b=c` が混入する。** 読む側は `key=value` の形しか見ないので、混入に気づけない。**meta は SO の証跡として committed 層から引かれるものなので、そこに偽のキーが入る形は残せない。**

拒否するのは**行を壊すバイトだけ**にした。同じファイルの `cli_version_for()` が同じ理由で採っている denylist の考え方で、許可リストを列挙すると実在する値を落とす（あの関数のコメントが「一度やっている」と書いている）。`=` は許す（読む側は `cut -d= -f2-` で取るため）。

**この1件は SO ではなく自分の掃除で見つけた。** 3周分の指摘を受けて、ようやく指摘される前に同じ種類のものを取れた。
