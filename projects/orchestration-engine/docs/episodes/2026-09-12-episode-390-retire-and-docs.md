# 統括の計画的な交代を verb にする — 残りの実装（retire と文書）

## なぜこの作業が始まったか

統括セッションは context を使い切るたびに交代するが、その工程は 14 代にわたって手作業だった。owner が「一つの指示で明確にフローが決まっていて、確実に引き継げる」形を求め（2026-09-11）、#390 で verb にする作業が始まった。`prepare`（状態を集めて引き継ぎ文書を書く）と `take`（後継が席を取る）と `start`（後継のペインを起こす）は着地または着地待ちで、**残っているのは `retire`（前任を閉じてよいかを判定して閉じる）と文書と受入である。**

この episode はその残りを記録する。**前の episode を引き継ぐのではなく、別の単位として立てた**理由は次のとおりである。

## この episode が別に立っている理由

当初は1本の episode で PR を4本またぐ予定だった。`document-format.md` は committed 層の plan を「実装の最初の PR と一緒に着地させる」と定めており、**1本の plan と episode を4つの PR にまたがらせた時点でその形が壊れていた**（着地した文書が後続の PR で変わり続ける）。owner の裁定（2026-09-12）で残りを1つの PR にまとめることになり、plan も episode もこの単位で立て直した。

- 前の episode は PR-1 と PR-2 の記録として `stable` で閉じてある。
- **設計の経緯（DJ-1 から DJ-12）・ゲート1 と2 の軌跡・棄却した案・実測値は、前の plan と前の episode が正本である。** ここには写さない。
- この episode に書くのは、`retire` と文書と受入の作業で新しく起きたことだけである。

### retire の実装（2026-09-12）

`oe-handoff retire` を入れた。**引数なしは下見で、何も停止しない。`--execute` だけが閉じる。**

**この段落は PR-3 を書いた時点（2026-09-12）の記録で、そのあと2回の owner 裁定で条件が変わった。** 当時こう書いていた。

> 停止の必須条件は3つで、plan の Step 3-2 のとおりである。前任の session_id が引き継ぎ記録に残っていること（`claude --resume` で開き直せる）、生きた委譲子が0体であること、申告の各項目に処分（`済んだ` / `引き継ぐ` / `取り消す`）が付いていること。

**3つのうち2つが、いまは止める条件ではない。**

- **生きた委譲子が0体** — 2026-09-13 の owner 裁定（1件目）で外した。**子が生きたままの交代が正常系であり、止めているほうが不具合である**という裁定である（`本文: DJ-11 が不具合と裁定された`）。実装では数えて一覧に出すだけで、**閉じない理由にはしない**。
- **session_id が引き継ぎ記録に残っている** — 同日の owner 裁定（2件目）で外した（`本文: 前提の誤りを根拠にした過剰な block が3回出た`）。**実際、この日の実交代で `retire` は session_id が `unknown` のまま閉じている**（`本文: 受入: 本物の交代が通った`）。

**いま止める条件を、実装（`bin/oe-handoff` の `retire`）と `bin/README.md` の `oe-handoff` の節から数え直した。** 4つの束になる。

1. **前任と自分が同じペインでないこと。**
2. **board の席が自分を指し、引き継ぎ記録の前任と board の註が一致すること。**
3. **自己申告の各項目に処分（`済んだ` / `引き継ぐ` / `取り消す`）が付いていること。** **「保留ゼロ」とだけ書いた申告は通さない**（表に項目が1つも無ければ落とす）。機械の節が挙げた PR と未 push も、**処分が付いた表の行**に出てこなければ落とす。
4. **閉じる直前の同一性の再検査。** tmux server の世代 → ペインの pid → その pid のコマンド名の順に突き合わせ、**どれか1つでも食い違えば閉じない**。記録が無い（古い形式の引き継ぎ文書）場合も閉じない。

**枝の数を実装から数えた**（2026-09-13 時点）。下見でも実行でも効く `note_fail` が **9本**、`--execute` の段階で同一性の突合により閉じるのを止める枝が **11本**、停止後に不在を確認できないことで止まる枝が **3本**である。

**止めないものは3つで、いずれも「引けなかったことは記録して進む」形である**（`note_fail` は0本）。生きた委譲子の有無 / 前任の session_id が引けるか / transcript が使えるか。**「引けた」と「引けなかった」は畳まない。**

**plan の Step 3-2 にも同じ古い記述が残っていたが、owner の承認を得て同じ PR で直した（2026-09-13）。** 1件目の裁定までは反映されていて、2件目が未反映だった。**`status: stable` とチェックはそのままで、行も消さず、本文だけを書き換えて前後を残した**（この plan の規約）。

**直すときに、Step 3-2 の射程を実装から確かめ直した。** この step が言う「停止の必須条件」は**下見でも `--execute` でも「閉じられない理由」になるもの**で、`note_fail` の9本が2つの束（前任の一意性4本・申告の処分5本）に収まる。**`bin/README.md` の「止めるもの」の4つの束はこの step より広く**、「前任と自分が同じペインでない」は入口の前提（`exit 2`）、「閉じる直前の再検査」は Step 3-4 の範囲である。**数は2つのまま変わらず、中身が `session_id` から前任の一意性へ入れ替わった。**

#### 前任を「どこから」読むかを2つに分け、食い違えば進まない

前任の pane は**引き継ぎ記録（引き継ぎ文書の機械の節）**から取る。あわせて board の註（「前任 `%N` は退任申告済み・停止待ち」）からも取り、**2つが食い違ったら進まない**ようにした。PR-2 で踏んだ「検査した相手と書き換える相手がずれる」と同じ型を、閉じる側でも作らないためである。閉じる操作は取り消しにくいので、こちらのほうが効く。

あわせて board の席が自分を指していることも見る。指していなければ「先に `take` を通す」と言って止まる。

#### 申告と機械の検査を突き合わせる

機械の検査をやり直して、**申告に出てこない open PR があれば食い違いとして列挙し、閉じない**。前任が「保留ゼロ」と書いたあとに PR が残っている、という形を拾う。

#### 段階1 で触れてよいのは前任のペインだけ

`--execute` は `tmux kill-pane` を前任のペインに対してだけ打つ。board・登記・イベントログ・worktree・PR には触れない。後始末（登記の掃除・worktree の掃除・issue の close）は人のゲートのまま残す。**テストが mtime で「触っていないこと」を見ている。**

停止の確認は `list-panes` の集合所属で行う（`display-message` は不在のペインでも rc=0 と空を返すため）。閉じたあとに `claude --resume <session_id>` の案内を出す。

#### テストが自分の fixture の誤りを暴いた

「申告の項目に処分が無ければ閉じない」というテストが、最初は**通ってしまった**（しかも前任のペインが閉じられた）。原因はコードではなく fixture で、`local disp="${3:-済んだ}"` と書いていた。**`${3:-...}` は空文字も既定値に置き換える**ので、`""` を渡しても「済んだ」が入り、**テストが主張どおりの条件を作れていなかった。** `${3-...}`（コロンなし）に直したら落ち、コードのほうは正しく止めていた。

**この単位で「テストが欠陥を固定する／テストが主張どおりの条件を作れていない」型は5回目である。** 今回は、テストが通ったことではなく**テストが通ってしまったこと**が手がかりになった（前任が閉じられてはいけない場面で閉じられた）。

昇格の印: テストが主張どおりの条件を作れているかを、シェルの既定値展開まで含めて確かめる

### board の `## succession 手順` の書き換え案（Step 4-3・実ファイルは触っていない）

**案である。適用は owner の承認を得てからで、この PR では board を1バイトも書き換えていない。** board は稼働中の実ファイルで、常駐の見張りが 15 分ごとに読んでいる。

いまの節はこうなっている（4行）。

```markdown
## succession 手順（後任がやること）
1. このボード + `MEMORY.md` を読む（durable 規律はメモリー側）。
2. open issues を `gh issue list` で確認し、次タスクを **owner と決める**（勝手に着手しない＝HG）。
3. 環境の鮮度を再確認（master HEAD・worktree・panes は上記時点のもの）。
4. owner が前任統括 pane を停止したら succession 完了（次回の前任 = 現統括 `%158`）。
```

**直したい点は3つある。**

1. **手作業で踏む工程が書かれていない。** 登記・board の張替・検算は、いまは立ち上げプロンプトに毎回手書きしている。verb になったので、板がそれを指せる。
2. **4行目が古い。** 「owner が前任統括 pane を停止したら完了」は owner 裁定2(a)（2026-09-12）で変わり、**打つのは後継**になった。しかも `%158` は何代も前の pane 番号がそのまま残っている。
3. **前任がやることが書かれていない。** この節は「後任がやること」だが、交代は前任の `prepare` と `start` から始まる。

#### 案（置き換える節の全文）

```markdown
## succession 手順（前任と後任がやること）

**owner が出す指示は1つ（「交代して」）。そこから先は前任と後任が自分で回す。**

前任（退く側）がやること:

1. `oe-handoff prepare` を走らせる。機械で取れる状態が引き継ぎ文書へ入る（引き継ぎ文書以外は書き換えない）。
2. 引き継ぎ文書の**人が書く節を埋める**。とくに「渡らないもの」と自己申告の残余は、ここでしか書けない。自己申告は**機械が挙げた項目それぞれに処分**（`済んだ` / `引き継ぐ` / `取り消す`）を書く。「保留ゼロ」とだけ書いた申告は `retire` が通さない。
3. **生きた委譲子が残っていたら、片づくまで交代できない**（子の報告先は前任のペインに焼き込まれていて張り替えられない）。`prepare` が件数を出す。
4. `oe-handoff start` を走らせる。後継のペインが起き、引き継ぎ文書のパスが送られる。

後任（着く側）がやること:

1. `doc-flow-guardrail` スキルを読む（cold-start）。
2. 引き継ぎ文書を全部読む。board はこの1行と in-flight 節だけ読む（全部読まない）。
3. `oe-handoff take` を走らせる。前提の検査 → 自己登記 → この行の張替 → 検算 → 交代イベント、の順に進む。**何度実行しても同じ結果になる。**
4. `oe-handoff retire` を走らせる（引数なしは下見）。前任の申告と機械の検査を突き合わせ、食い違いを列挙する。
5. 下見が通ったら `oe-handoff retire --execute` で前任を閉じる。**打つのは後任である**（owner 裁定 2026-09-12）。閉じるのは前任のペインだけで、**後始末（登記の掃除・worktree の掃除・issue の close）は人のゲート**のまま残る。
6. 次タスクは **owner と決める**（勝手に着手しない＝HG）。open issues は `gh issue list` で見る。

**確かめられないことが3つある**（`bin/README.md` の `oe-handoff` の節に詳しい）。`start` が送った kickoff が届いたかは受領印で見る（起動側では分からない）。`oe-vitals` の最終走査は確かめられない。pane がすぐ再利用された直後は、前任の session_id を取り違えうる。
```

### 実装SO（ゲート4）— 閉じる側の fail-open が4件（2026-09-12）

`oe-review --lanes 2` を回した。結果は `refuted`（2/2）で、**両レーンが同じ核心を指した**。「閉じてはいけない場面で閉じる経路が残っている」である。**閉じる操作は取り消しにくいので、この単位でいちばん重い指摘だった。**

- **board と自ペインが無いと、検査を飛ばしたまま閉じられた。** `board` を「あれば見る」にしていたので、渡さなければ前任の註との突合も席の確認も走らない。`TMUX_PANE` が空のときも `[ -n "$self" ] && ...` が偽になって **else の「席は自分を指している」へ落ちていた**。`take` は自ペインを必須にしているのに、**より危ない `retire` のほうが緩かった。** 両方を必須にした。
- **board の註や席が読めないことを成功扱いにしていた。** 註が読めなければ突合できないのだから、閉じない。
- **「機械の節が挙げた各項目に処分がある」ことを見ていなかった。** 表に1行あって語彙が正しければ通っていたので、**機械が挙げた PR を申告が無視しても閉じられた**。機械の節の PR 番号と未 push を申告に当てる形にした。再検査も open PR だけだったので、未 push と worktree まで広げた。
- **子の検査から `kill` までの窓が空いていた。** `--execute` の中で全体をやり直しても、子を数えたあとに前任が新しい子を起こせる。**閉じる直前にもう一度数える**ようにした。
- **停止後の `list-panes` が失敗したとき「不在」と同じ枝へ進んでいた。** 観測できなかったことを不在に畳み、**「不在を確認しました」と嘘を出していた。** 引けなければそう言って非0 で終わる。

#### 塞げていない窓は明記した

閉じる直前の数え直しから `kill` までのあいだに前任が委譲子を起こす窓は**残る**。閉じるには前任の側にもロックを持たせる必要があり、それはこの単位の外である。**できるのは窓を最小にすることまで**なので、出力にもそう書いた。

#### 自分の直しが正当な状態を止めていた

未 push の再検査を足したところ、**上流を持たない枝で交代が止まるようになった**。テストが落ちて気づいた。「数えられなかった」と「比べる相手が無い」を同じに扱っていたのが原因で、後者は正当な状態である。分けた。

**fail-closed を足す方向でも、足しすぎると正当な状態を止める。** この単位では fail-open ばかり直してきたので、逆側に振れた最初の例である。

昇格の印: fail-closed を足すとき、正当な「比べる相手が無い」を「分からない」に混ぜない

#### テストの作り方でも2つ踏んだ

呼び出し回数で stub の挙動を切り替える形にしたら、**実装の呼び方を変えた瞬間に壊れた**。目印ファイルで切り替える形に直した。もう1つは、前の case が前任を閉じたあとの生存状態を作り直していなかったこと（連鎖で7件落ちた）。

**踏めていない枝を1つ残した。** 「board の註は読めるが席は読めない」は、註の検査が先に走り、註に前任の `%N` が在れば席の解決も同じ行の `%N` を拾うので、fixture で作れない。**テストのために実装を歪めるより、踏めていないとコメントに書くほうを選んだ。**

### 次の単位の受入の境界（判断できるように書く）

**次の単位（ガードレールへの codify）の受入は、そこで使うコマンドとスクリプトが個々の責務を果たしていることまでとする。交代のフローが1回以上通ることを完了条件にしない。** ガードレールが指すコンポーネントは `#394`（この PR）で実装済みで、**実物で1回通っている**からである。

判定は次の3つで、**フローを流さずにその場で確かめられる**。

1. 手順が呼ぶコマンドが実在し、`--help` が名乗る責務が手順の記述と一致する。
2. 手順が書く引数と順序が、実際の口（`--help` と実装）と一致する。
3. 手順が書く検算が、そのコマンドの出力で実際に取れる。

**この境界を書いておくのは、次の単位が「交代をもう一度通す」まで膨らむのを防ぐためである。** 交代は実運用でしか起きず、待つと単位が閉じない。
