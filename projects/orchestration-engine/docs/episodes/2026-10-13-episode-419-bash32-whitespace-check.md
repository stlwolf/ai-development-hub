### 置き換え先を正規表現でなく glob にした（2026-10-13）

issue は置き換え先の例として「空白以外の文字を1つでも含むかを正規表現で見る形」（`[[ "$x" =~ [^[:space:]] ]]`）を挙げていた。候補として、これと bash の glob（`[[ "$x" == *[![:space:]]* ]]`）を比べた。

判定の意味を、空・半角空白・タブ・改行・CR・VT・FF・NBSP・全角空白（U+3000）・EN SPACE・LINE SEPARATOR・NEL・ゼロ幅空白・BOM・記号・不正な UTF-8 の 26 通りで、元の置換と突き合わせた（bash 3.2 と 5、`ja_JP.UTF-8`・`en_US.UTF-8`・`C` の組み合わせ）。

- **glob は 26 通りすべてで元の置換と同じ判定になった。** glob も元の置換も bash 自身のパターン照合なので、文字クラスの解釈が同じになる。（後注: この理由づけは不正なバイトを含む値では成り立たなかった。26 通りから一般化しすぎていた。反例は「実装SO（ゲート4・弱・Codex 1レーン）で、判定が分かれる反例と、検査の欠陥が出た（2026-10-13）」の節にある。）
- **正規表現は、不正な UTF-8 のバイトを含む文字列で判定が変わった。** UTF-8 のロケールでは、`a\xff` のように空白でない文字を含んでいても、不正なバイトが1つあると文字列全体が一致しなくなり、「空」と判定される。macOS の libc の正規表現が、不正なバイト列で照合そのものに失敗するためだと見ている（推測。返り値までは確かめていない）。`C` ロケールでは差は出なかった。

frontmatter に不正なバイトが1つ混じっただけで「empty frontmatter」と出るのは、判定の意味を変えないという issue の受け入れ基準に反する。そのため glob を採った。

速さは、判定1回だけを測って確かめた。glob は長さに比例して伸び、bash 3.2 でも 1,299,999 バイトで 0.031 秒、空白だけの 499,999 バイト（最後まで走査する最悪の形）で 0.080 秒だった。

棄却した選択肢: 正規表現（上の理由）。外部コマンド（`grep -q '[^[:space:]]'` など）はプロセスを起動する分だけ重く、grep もロケールと不正なバイトの扱いが bash と違いうるので、比べる前に外した。

### 変更前の master で、止まる場所が狙った行であることを確かめた（2026-10-13）

`/bin/bash`（3.2.57）で `test_validate_knowledge.sh` を上限 300 秒で回すと、開始 17 秒で [50] に入り、そのまま 300 秒で打ち切られた（exit 124）。bash 5.2.37 では 18 秒で最後まで通る（181 件・失敗 0）。

打ち切られたこと自体は、止まった理由の証拠にならない。そこで [50] と同じ fixture（108,119 バイト・frontmatter 中の空白は約 9,200 文字）を作り、変更前の `validate-knowledge.sh` を `PS4='+${LINENO}: ' /bin/bash -x` で 20 秒回した。最後に出た trace は 157 行（frontmatter を取り出す代入）で、158 行の `[[ -z "${fm//[[:space:]]/}" ]]` の展開が終わらないまま打ち切られた。止まっている bash を `sample` で見ると、スタックの先頭はほぼすべて `wcslen` で、ワイド文字列での照合をくり返していることと合う（bash 3.2 に記号情報が無いので、関数名までは追えていない）。

### test_knowledge_list.sh も変更前の master では bash 3.2 で止まった（2026-10-13）

issue は「`test_knowledge_list.sh` も止まる見込み（未確認）」と書いていた。変更前の master で `/bin/bash` に上限 300 秒を付けて回すと、開始 3 秒で [22]（約 1.5MB の値を持つ frontmatter）に入り、300 秒で打ち切られた（exit 124）。bash 5 では 8 秒で最後まで通る（124 件・失敗 0）。同じ fixture で変更前の `knowledge-list.sh` を `-x` で追うと、最後の trace は 234 行（frontmatter を取り出す代入）で、240 行の空白判定の展開が終わらなかった。

issue は遅くなる条件を「空白を多く含む長い文字列」と書いているが、[22] の frontmatter は空白が十数文字しかない。手元の測定では、空白を含まない文字列や先頭に空白が1つだけの文字列なら、bash 3.2 でも旧い書き方は速かった（8,001 バイトで 0.013 秒）。どういう形の入力で遅くなるかの詳細は追っていない。置き換え先の glob はどの形でも長さに比例したので、修正の中身には影響しない。

上限で打ち切ったあと、中で動いていた `knowledge-list.sh`（bash 3.2）が親を失ったまま走り続けていた。`timeout` は SIGTERM しか送らず、bash 3.2 は照合の最中にそれを受けても止まらなかった。`-x` で追ったときの `timeout 20` も、20 秒を過ぎて止まらなかった。どちらも自分が起動したプロセスなので SIGKILL で止めた。bash がシグナルを照合の後まで遅らせる作りだからだと見ているが、ソースまでは確かめていない（推測）。`test_validate_knowledge.sh` の打ち切りでは子は残らなかったので、いつも残るわけではない。

昇格の印: bash 3.2 の長い照合を `timeout` で打ち切るときは `-k` を付けないと子が残る（U4 の「時間の上限を付けて確かめる」に効く）

### 足した検査は、意味を保つための検査であって、変更前の master では落ちない（2026-10-13）

足した検査は `test_validate_knowledge.sh` の [51] と `test_knowledge_list.sh` の [33] である。空白は半角空白・タブ・全角空白を混ぜ、5か所それぞれで「空白だけなら空」「空白に囲まれた文字があれば空でない」を見る。frontmatter と本文には、不正な UTF-8 のバイトだけの値を「空でない」とする例を入れた。

この2つは、変更前の master のスクリプトに重ねても bash 5 で通る（194 件・130 件、失敗 0）。判定の意味を変えないための検査なので、それで正しい。negative knowledge `01M2DRCP3QSG4NQWHNY6DSD3NJ` に従い、受け入れの「変更前の master で落ちる」の錨には使わない。この単位の変更そのものに錨がある検査は、bash 3.2 で [50] が時間内に終わるかどうかである。

その代わり、検査が本当に効くことを、置き換え先を正規表現（`[[ ! "$x" =~ [^[:space:]] ]]`）に差し替えた写しで確かめた。5か所とも差し替わったことを grep で確かめたうえで回すと、`test_validate_knowledge.sh` は4件、`test_knowledge_list.sh` は2件落ち、落ちたのはすべて不正なバイトの例で、理由は「empty frontmatter block」「body prose is empty」「missing or empty frontmatter」が出たことだった。狙った理由で落ちている。trigger と source.ref の不正なバイトの例は、yq を通るので作っていない。

不正なバイトの例は、最初は「空の判定の文言が出ない」ことだけを見ていた。これだと出力が空でも通ってしまうので、変更後のスクリプトが実際に進む先（「malformed YAML frontmatter」）が出ることも確かめる形に締めた。

### 実装SO（ゲート4・弱・Codex 1レーン）で、判定が分かれる反例と、検査の欠陥が出た（2026-10-13）

依頼文は `tmp/419/so-impl-prompt.md`（作業層・gitignore）で、5つの仮定（判定の一致・線形時間・置き換えの漏れ・検査の効き・コメントの正しさ）の反証を求めた。Codex は 272 秒で返した（`timeout_status=success`・リトライなし・`model_resolved=gpt-6.1-sol` は設定からの値で観測値ではない）。

指摘と採否は次のとおり。

1. **判定が分かれる反例があった（仮定1は成り立たない・重大度 中）。** UTF-8 として不正な `0xA0` のバイトと全角空白だけの値（`\xa0\xe3\x80\x80`）を、旧い置換は「空」、glob は「空でない」とする。bash 3.2 と 5 の両方で再現した。範囲を確かめるため、0x80〜0xFF の単独バイト 128 通りを、空白なし・半角空白・タブ・全角空白・NBSP・EN SPACE・半角と全角の組の7通りと、前後2通りに組み合わせて比べた。**差が出たのは `0xA0` のバイトと ASCII 以外の空白が同居する場合だけ**だった（`C` ロケールでは差なし）。`0xA0` のバイトだけ、または ASCII の空白との組なら、どちらも「空」とする。glob は値に不正なバイトがあると、値全体をバイト単位で照合するので、全角空白のバイト列を空白と見なくなるのだと見ている（推測。bash のソースまでは当たっていない）。
   - **採否: 直し方は変えず、差を明記する。** この値は文字として読めないバイトを含み、受け入れ基準の「空白だけの値」にも「空白以外の文字を含む値」にも当たらない。正しい UTF-8 の値では、26 通りの突き合わせと Codex の 1,530 通りの比較で差は無かった。差を消すには、遅い置換に戻るか、不正なバイトを先に検出する手間を足すことになり、この issue の範囲に見合わない。挙動が変わるのは、本文がこの形のとき（これまでは WARN・exit 1、これからは WARN なし・exit 0）と、frontmatter と `knowledge-list.sh` で理由の文言が変わる（空の判定ではなく YAML の解析失敗になる）ときである。スクリプトのコメントと PR 本文に書く。
2. **足した検査がロケールに依存していた（仮定4は成り立たない・重大度 中）。** [51] と [33] は全角空白を空白として期待していたが、`LC_ALL=C` では旧い置換も glob も全角空白を空白と見ないので、意味を保った実装でも落ちる。直す前の検査を `C` で回すと、`test_validate_knowledge.sh` で6件、`test_knowledge_list.sh` で1件落ちた。
   - **採否: 採った。** 全角空白は、旧い置換の判定でそのロケールが空白に数えるときだけ fixture に混ぜる形にした。数えないロケールでは NOTE を1行出して、半角空白とタブだけで確かめる。
3. **trigger/prediction と source.ref を正規表現へ書き換えても、足した検査では捕まらない（重大度 低）。**
   - **採否: 直さず、理由をテストのコメントに書いた。** この2か所に来る値は yq と jq を通った正しい UTF-8 なので、正規表現と glob の判定が分かれる入力そのものを作れない。書き換えても挙動は変わらない。
4. **コメントの「終わらない」は、無限ループの証明ではない（仮定5への注記）。**
   - **採否: 採った。** 「実用的な時間に終わらない」に直した。
5. 線形時間（仮定2）は「判断できないが強く支持する」、置き換えの漏れ（仮定3）は「成り立つ」だった。

直したあと、2本のテストを bash 3.2.57 と bash 5.2.37、`ja_JP.UTF-8` と `C` の4通りで回し、すべて通った（194 件・130 件、失敗 0）。正規表現への差し替えは、直したあとの検査でも `ja_JP.UTF-8` で4件と2件落ちる（前と同じ不正なバイトの例）。

昇格の印: 不正なバイトを含む値では、bash の glob と置換が別の照合の仕方に切り替わり、空白判定が分かれる（glob への置き換えで「判定の意味を変えない」と言える範囲は正しい UTF-8 の値まで）
