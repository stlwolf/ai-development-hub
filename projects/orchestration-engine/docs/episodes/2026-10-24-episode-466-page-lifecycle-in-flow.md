- 実物の整理は、引き継ぎ文書の 10-17〜10-23 の経過の行から数えた。判定ページは15枚で、owner が会話だけで答えたのが9枚、ページと会話の両方が3枚、ページだけが1枚、子のペインに直接が1枚、記録に無いのが1枚だった。ページだけの1枚も、回収の合図は会話の一言だった。ページの外で会話に流れたのは、単独の問い5件・マージの依頼11件・表示の確かめの依頼2件・知らせ4件だった。記録は要約なので、どれも下限として discussion に書いた。
- **数えて分かったことで、論点の立て方が変わった。** issue 本文は「問いが2つたまったらページを作る」を出発点にしているが、ゲートで子が止まったときのページはすでに毎回作られていて、カードは3〜16枚あった。会話で流れて混ざっているのは、ゲートのページの外の単独の問い・マージの依頼・知らせである。そこで、owner に向くものを「答えを選ぶ問い」と「依頼・知らせ」に分け、後者は見取り図の手番の表に出してカードにしない、という当てる順序（discussion の 1-3）を置いた。
- **面の特定（knowledge `01M19CPRGAY3GJMM1DQPFKPFW0` を当てた）。** owner が戻ってくる場所は統括の会話で、ページは主に読む場所だと記録から決めた。答えの経路の大半が会話なので、html-one-pager の「会話で答えを1件ずつ受け取る形は使わない」をそのまま守ると、owner は「全部推奨」以外を言うたびにページへ戻ることになる。会話の答えを、カードごとに決められる範囲で受け付ける案を推奨にし、打ち消す規則として html-one-pager のその1文を6節に挙げた。
- **「いつ作るか」の規則は html-one-pager に置けない。** html-one-pager は「ページを作る依頼を受けたら」読み込まれるので、「いまページを作れ」を書いても、作ると決める前の統括には届かない。knowledge `01M486Z2ND07GQWV1GHS1SVB0J` の「受け渡し先の出口」と同じ形の穴だと判断し、規則の置き場を「一般の決まりは html-one-pager・流れとの対応は出来事の名前で発火する新しいスキル」に分けた（8-2a）。
- **道具だけでは完結しない。** ページの公開と保存先の読みはセッションの道具（Artifact・ArtifactData）で、bash の verb や hook からはできない。道具ができるのは「閾値を越えたのにページが無いと知らせる」と「束のデータを作る」までなので、8C（規則が先・道具があと）を推奨にした。
- **棄却した選択肢**: 判断ボード1枚を更新し続ける案（1B）は、owner の案「答えを消費したら更新しない」と合わず、移し忘れを `build.py` が見ないので採らなかった。URL が1つになる利点は、見取り図を入口にすることで取り込んだ。いつも `bundle` にする案（1C）は、`bundle` が `Q<数字>` を定義せず、owner が音声で問いの番号を言うことがあるので採らなかった。時間で区切る閾値（2C）と、止まる問いも2件目を待つ閾値（2D）は、子が止まったままになるので採らなかった。
- **範囲の外で見つけたこと**: html-one-pager に「更新を止めた」状態が無い（見取り図とレビューを止めても「随時更新」と出る）。引き継ぎ文書の「全部承認なら保存先を読まなくてよい」が html-one-pager の「ページの答えを正とする」と食い違う。#329 の背景が `oe-refute`・`oe-review` だけを挙げ、委譲で回している `so-compare` が入っていない。discussion の10節に置いた。

### ゲート2: 設計SO（弱・Codex 1レーン）の結果と採否（2026-10-24）

- レーン: Codex `gpt-6.1-sol`（設定から解決）・`codex-cli 0.163.0`・112 秒・初回で返答（`timeout_status=success`）。Cursor への切り替えはしていない。結論は「直してから出す」で、指摘は24件（高10・中14）。挙げられた行（`build.py` の `pick_rows` と `page_data`・`doc-flow-guardrail` の固定節と「gate 3 の baseline 記録」・`implementation-gate-rule` の承認の数え方・`issue-intake` の 5〜6）を一次情報で確かめ、24件とも採った。1件ごとの採否は discussion の8節の表にある。
- **撤回4（ゲート1 で直した案にも同じ穴）**: ゲート1 の指摘で「一括の答えは最後に伝えた版のカードに当てる」にしたが、伝えた時刻は owner が読んだ証拠にならない。版1 を読んでいるあいだに版2 を伝え、その直後に「全部推奨」と言われれば、読んでいない追加分に当たる。直しの案の中に、直した穴と同じ形の穴が残っていた。4案（版を伝える・追加の印・足さない・版を言ってもらう）を比べ、時刻を推し量らずにページの上で範囲が決まる「追加の印」を推奨にした。
- **撤回5（当てる順序の先頭）**: 当てる順序を「統括が決められるか」から始めていたので、承認のあとに対応範囲を足す問い（「同じ型の直しを別の対象にも当てる」）が、任せた範囲の例に似ているだけで統括の判断に落ちえた。knowledge `01M55M68F2Q128X7AZ1JN2X7WC` が予測する「足す方向が軽い側を素通りする」形そのもので、教訓を当てて順序を書いたのに、足す方向の具体の形を自分で作って当てていなかった。「承認済みの対象を変えるか」を先頭に足し、委譲固定節の「変更」の級に当たれば再承認の問いにする形にした。

- **撤回7（回収の出口）**: 回収の手順が「子へ送る」へ直行していて、ゲート3 の承認の記録と baseline、認識合わせの確定版の投稿へ渡る出口が無かった。knowledge `01M486Z2ND07GQWV1GHS1SVB0J` の「受け渡し先の出口」を、html-one-pager から子への出口にだけ当て、答えを使うほかの先（承認の記録・issue-intake）に当てていなかった。回収の段5 を「答えを使う先へ渡す」にして3つに分けた。

昇格の印: 分類や順序を直したら、直した案にも境目の具体の形を作って当て直す。ゲート1 で直した「版」の規則に、同じ形の穴が残っていた
