# #509 oe-view が前の viewer を閉じる前に、同じ WezTerm の中のペインかを確かめる

## なぜこの作業が始まったか

`oe-view` は md を開くたびに、記録したペイン番号のペインが「在るかどうか」だけを見て閉じてから、新しい viewer を開く。WezTerm を起動し直すとペイン番号は0から振り直されるので、記録の番号が作業中の別のペインに当たると、そのペインを閉じてしまう。2026-10-23 の engine の監査（#484 の候補 C-5・重大度 高）で報告され、2026-11-18 に owner が open issue の精査の結果からこの issue を選んだ。

## 着手から plan の承認まで

この節は、plan の承認のあとに、それまでの会話を振り返ってまとめて書いた（reconstructed）。次の「実装」の節からは、作業しながら書き足す。

- open issue を135件読んで「単独で着手できるもの」を分けたとき、#509 は、該当のファイル（`lib/oe-viewer.sh`）が監査のあと一度も変わっていない点と、重大度が高い点で、最初の候補になった。
- 認識合わせ（`issue-intake`）で、本文の行番号が報告の時点のものに古くなっていたことと、「WezTerm がペイン番号を起動ごとに振り直す」が報告でも統括でも推測のままだったことを拾った。Codex に1回だけ漏れを聞き、「手がかりが一致しても取り違えないか」の1件を採った。owner がそのまま確定した。
- 推測のままだった前提は、WezTerm のソースで確かめた。ペイン番号はプロセスの中の1つのカウンタで、0から増やすだけで使い回さない（`mux/src/pane.rs:24-28`）。このため「同じ GUI のプロセスに問い合わせて番号が在れば、それは自分の viewer」と言える。直し方は、番号そのものより「どの GUI のプロセスの番号か」を記録して照らす形に絞れた。
- 設計 SO（3レーン）は、初めの案の外に「ペインでなく viewer のプロセスを止める」「viewer を閉じずに中身を差し替える」という新しいカテゴリの案を出した。どちらも変更が大きいので、plan の探索の記録に残し、この issue では初めの案を固めた。
- 設計 SO の指摘をすべて手当てする形で plan を出したところ、owner が「その危険は現実的にありえないリスク判断に見える」「まあゼロではないレベル」と返した。挙げた危険は数ミリ秒や1秒の窓に複数のことが重なる組み合わせで、承認の問いにするものではなかった。同じ基準で見直し、プロセス名の確かめと、spawn の前後で開始時刻を取る確かめの2つも外した。どちらも同じくまず起きない組み合わせだけを防ぐものだった。owner はそのあと plan を承認した。

## 実装

### テストを先に足した

- mock の `wez` を `wez discover --quiet` と `wez pane --socket <S> <sub>` に対応させ、`ps` の mock を足した。既存の確かめのうち `'pane split'` のような文字列で探していたものは、`--socket` が間に入ると当たらなくなる。そのまま残すと「呼ばれない」を見る確かめが何もしないまま通るので、`--socket` の有無を問わずサブコマンドで探す `has_sub` に置き換えた。
- 変更の前のコードで走らせると、115項目のうち23項目が落ちた（結果は作業層の `tmp/509-test-before.txt`）。#509 の不具合そのものを再現したのは、古い形の記録（番号だけ）で、番号のペインが list にある場面である。変更の前のコードは、その番号のペインを閉じた。
- 別の GUI・開始時刻が違う・壊れた記録の場面は、変更の前のコードでも閉じなかった。変更の前のコードは新しい形の記録の1行目（`pane_id=7`）を数字と読めず、閉じる経路に入らないためである。不具合を再現しているのは古い形の場面で、新しい形の場面は「直したあとに閉じないこと」の確かめである。

### 直した

- `lib/oe-viewer.sh` に、接続先を1回だけ決める関数、GUI のプロセスの開始時刻を返す関数、閉じてよいかを決める関数を足し、`oe_viewer_resolve` をその順に組み直した。記録は `key=value` の3行にし、読むときは各行を最初の `=` で分ける。
- symlink をたどる処理は、`bin/oe-view` の `_oe_view_canonicalize` を使わず、`realpath` があれば使い、無ければたどらない形にした。`_oe_view_canonicalize` は bin の側にあり、lib から bin の関数を呼ぶと向きが逆になるためである。たどらなかった symlink は `gui-sock-<番号>` の名前にならないので、閉じない側に倒れる。
- 直したあと、`test_oe_view.sh` は bash 5 と bash 3.2 のどちらで起動しても115項目すべて通った。ただし、テストの PATH は `/usr/bin:/bin` だけなので、テストから起動する `oe-view` は、どちらの場合も `/bin/bash`（3.2）で動いている。bash 5 で lib を動かす確かめにはなっていない。
- `test_home_unset.sh` は1項目（`oe-register --help` が 1 を返す）が落ちた。master のままの本体のチェックアウトでも同じ項目が落ちたので、今回の変更とは関係ない。このセッションが tmux の外で動いていて `TMUX_PANE` が無いためで、#309 のコメントに同じ観察がある。

### ゲート4（実装の確かめ）の実装 SO

- commit `dedfb4e` を Codex（gpt-6.1-sol）と Cursor（composer-2.5・指定）の2レーンに1回渡した（出力は作業層の `tmp/509-impl-so/`）。2つとも `survived` で、must は0件だった。閉じる条件の5つと、すべての `wez pane` に `--socket` が付くことは、両方のレーンがコードの行で確かめた。
- should の2件を取り入れ、テストを足した。Codex は「viewer を開く前は開始時刻が取れ、開いたあとは取れない」場面が無いと指摘した。今までのテストは `ps` を前も後も失敗させていたので、開く前の値を使い回す誤った実装でも通ってしまう。`ps` の mock に「N 回目より後は失敗する」を足して場面を作り、空白だけを返す場面も足した。Cursor は、最初の1回の起動（記録が無い場面）でも `--socket` が付いているかを数えるよう勧めた。
- 足した確かめが空振りしないことは、わざと誤らせたコードで確かめた。記録を書く前に開始時刻を取り直す行を消して走らせると、足した場面の2項目が落ちた。コードを戻すと124項目すべて通った。

### 手元の WezTerm での確認（plan の手順8）

- このセッションは WezTerm の外で動いていて `WEZTERM_PANE` が無く、ここから打つと WezTerm の前面のペイン（tmux の画面）が分割される。plan を書いたときはこれを見込んでいなかったので、owner に確認の方法を聞いた。owner は手順を明示するよう求め、確認の手順をスクリプト（作業層の `tmp/509-real-check.sh`）にまとめて、owner が tmux の中のペインで実行した。
- 1回目は、最初の viewer から開けずに終わった。`wez discover` が失敗し、oe-view は rc 2 で止まっていた。tmux のグローバルな環境に、前の WezTerm の GUI のソケット（`gui-sock-510`）が `WEZTERM_UNIX_SOCKET` として残っていて、今の GUI（`gui-sock-7350`・2026-11-10 起動）とは違っていた。`wez` は `WEZTERM_UNIX_SOCKET` がソケットでないと自動検出に戻らずに失敗する。これは #431 の不具合そのもので、master の oe-view を同じ環境で打っても rc 2（`failed to spawn viewer pane`）で止まることを確かめた。#509 の変更とは関係ないが、tmux の中では oe-view が 11-10 から動いていなかったことになる。
- スクリプトにも誤りが2つあった。`pipefail` を付けていなかったので、viewer を開けなかったのに止まらずに進んだ。進んだ先で、空のペイン番号を記録に書き、記録が空の1行になった。空の記録は新しいコードでは「確かめられない」として扱われるので、害は無い。スクリプトは、開けなければ止まるように直し、`WEZTERM_UNIX_SOCKET` がソケットでなければ外して自動検出に任せるようにした。
- 直したスクリプトを owner がもう一度実行し、6つの場面がすべて OK になった（2026-11-19）。同じ GUI から開き直した場面（手順2・6）では前の viewer が閉じ、記録のソケットを別の GUI に装った場面・開始時刻を別の値に装った場面・記録を番号だけの古い形にした場面（手順3〜5）では前の viewer が残った。記録は `pane_id`・`socket`（`gui-sock-7350` の実体のパス）・`mux_started`（`Tue Nov 10 16:51:24 2026`）の3行になった。確認のあと `wez pane list` に残っていたのは、tmux を映している pane 0 だけだった。
- WezTerm を実際に起動し直す場面は試していない。手順3〜5は、起動し直したときと同じ「記録と今の GUI が合わない」状態を、記録を書き換えて作ったものである。
