自由文を許す文字列フィールドに deny-list（禁止パターンの列挙）で hygiene をかけると、**同じ family の迂回路が繰り返し出る**。#274 では `observations.ref` の揮発層参照を禁止する検査に対して、実装SO の3ラウンドのうち2ラウンドが独立に迂回路を実測した。1回目は判定順（URL と issue/PR 形式の免除を禁止検査より先に置いたため、末尾に `#274` を足すだけで `../../repo#274` や `/tmp/evidence.md#274` が通った）、3回目は正規化漏れ（生の文字列に先頭一致をかけていたため ` .oe/plan.md` や `./tmp/scratch.md` が通った）。

非自明なのは2点ある。第一に、**1つ直しても残りが見えない**こと。「免除の分岐を消す」修正で判定順の穴は閉じたが、正規化の穴はその修正では露出せず、別ラウンドの別レーンが指摘するまで残った。第二に、**下流が検証結果を信頼して判断に使う**と迂回の被害が拡大すること。#274 では検証を通った observation だけを集計と制御候補の判定に使う設計にしていたため、迂回した `harmful` レコードが「完全に valid な adverse 観測」として扱われ、誤った制御候補を立てていた。検証の穴が、そのまま判断の誤りに変換される。

次にどう行動を変えるか。(1) **判定前に正規化する**（前後の空白・区切り文字・`./` 等の冗長表記）。正規化は判定にだけ使い、記録する値は原文のままにする。(2) **免除の分岐を安易に足さない**。免除は禁止検査より後に置くか、そもそも不要か確かめる（`#274` のような形式は hygiene のどの条件にも触れないので、免除分岐そのものが迂回路だった）。(3) テストには**迂回クラスを列挙**する（前後の空白・冗長表記の `./`・別区切りの `\`・別形式の suffix・プラットフォーム固有の絶対パス表記〔ドライブレター・UNC〕・大文字小文字）。単発の負例1件では family が閉じない。実際 #274 では3ラウンド目の修正でも1クラス（ドライブレター絶対パス）が残り、closure の外部チェックで拾った。(4) 検証結果を判断に使う設計なら、**deny-list ではなく受け入れ形式の allow-list**（閉じた形の列挙）に倒せないか検討する。自由文を許す要求と両立しないなら、その緊張を明示して人間の判断に上げる。
