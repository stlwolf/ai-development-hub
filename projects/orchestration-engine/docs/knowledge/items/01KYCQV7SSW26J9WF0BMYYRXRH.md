`jq` の `strptime("%Y-%m-%d") | mktime` は日付の**カレンダー妥当性を保証しない**。実測（jq 1.7.1 / 1.8.0）では `2026-02-29` と `2026-04-31` がどちらも受理される。存在しない日は翌月へ正規化されるためで、拒否されるのは月が範囲外（`2026-13-01` 等）のときだけである。加えて jq の日付関数は C library 依存で、環境によって挙動が変わる余地がある。

非自明なのは、**テストが緑になる**点である。負例として月13（`2026-13-40` 等）だけを置くと strptime は失敗するので「カレンダー検査が効いている」ように見える。閏年や月末の実在チェックは通り抜けたまま残り、後から別の検証（人間のレビューや別ツール）で見つかる。#274 では設計SO のレーンが自分で jq を叩いて実測し、こちらの受け入れ基準（「date のカレンダー不正で exit 1」）が現行手法では満たせないことを示した。

次にどう行動を変えるか。日付の実在チェックは **純 jq で年・月・日を整数化し、閏年と月別最大日数を自分で見る**（`strptime` に頼らない）。テストの負例には月範囲外だけでなく**存在しない日**（`2026-02-29` / `2026-04-31`）と**閏年の正例**（`2024-02-29`）を必ず入れる。日付検査を書いたら「2月29日を平年と閏年の両方で試したか」を確認する。同じ穴が既存コードの別フィールドにも残っていないか（同一ファイルの片割れ）も併せて見る。
