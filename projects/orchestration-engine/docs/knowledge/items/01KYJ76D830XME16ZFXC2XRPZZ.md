完全性（漏れがないこと）を保証する述語は、**母集団の側から書かなければ成立しない**。書かれたものの側から書くと、参照整合性は検査できるが網羅性は検査できない。

#284 で「closure が本文の事実を省略していないか」を機械で担保しようとして、次の述語を置いた。「closure の各主張は本文の解決可能なアンカーを持つ」「アンカーが指す見出しが実在する」。これを歯止めと呼んで設計SO に出した。**2レーンが独立に同じ穴を指摘した。向きが逆である。**

具体的にはこうなる。本文に失敗 A と失敗 B があり、closure が A だけを正しいアンカー付きで書いた場合、述語はすべて pass する。**B が省略されたことを検出できない。** さらに closure に主張が1件も無ければ、述語は空集合に対して vacuous に pass する。検査しているのは「書いたものが正しい先を指しているか」であって、「書くべきものが書かれたか」ではない。

前例との類比も誤っていた。参照フィールドの解決可能性検査（`related[].ref` が存在するか等）を持ち出して「同じ種類の述語だ」と主張したが、**リンクの存在確認と命題の網羅性は検証クラスが違う**。機械的な形（文字列を解決する）が似ているだけで、保証している内容が別物である。

結果として、範囲を広げる設計判断（省略チェックの対象を広い範囲へ移す）をこの述語で支えようとしていたが、支えになっていなかった。最終的には**範囲を移すのをやめ**、省略検出は従来どおり母集団（実行ログ）と記録先を突合する人間 / SO のチェックに残し、述語の役割を「二重執筆を止めつつ所在を追えるようにする」ことだけに縮小して位置づけ直した。

次にどう行動を変えるか。(1) 完全性を主張する述語は、**母集団を先に定義してから書く**（何の集合に対する漏れを見るのか）。母集団を書けないなら、その述語は完全性を保証していない。(2) 「書いたもの → 参照先」の向きの述語を歯止めと呼ばない。**逆向き（母集団 → 記録）が要る**かを必ず確認する。(3) 既存の検査と類比するときは、**機械的な形ではなく保証している内容で比べる**。形が似ていることは同種であることの根拠にならない。(4) 述語で塞げない部分は、**誰が見るのかを明示して人間側に残す**（黙って落とすと、歯止めがあるつもりの空白になる）。
