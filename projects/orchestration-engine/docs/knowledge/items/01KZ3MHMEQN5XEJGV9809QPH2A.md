指摘は1件ずつ来るが、型は横に広がる。**外部レビューが名指しした1箇所を直した緑は、その型が消えた証拠ではない。**

**この item は格の違う2つを含む。先に格を書く。** 型が横に広がること（上の1文）は、この store の4つの arc で観測されている**事実**である。一方、それに対する処方のうち **「自分で走査すれば見つかる」は仮説** で、有効性は一度も観測されていない。以下、事実の側と仮説の側を分けて書く。

#299 の実装SO で、`oe-selfcheck` の `hook-contract` 検査が「生涯累計で1件でもあれば `ok`」になっている欠陥を2レーンが名指しした。子はその箇所を直近の窓で見る形へ直し、そのラウンドを閉じた。**しかし同じ検査器の隣にある `screen-marker` 検査には同じ型が残っていた。** 見つけたのは、遅れて返った3レーン目である。

**皮肉が二重にある。** `oe-selfcheck` は「版に固定された前提が壊れたことに気づくための検査器」であり、その検査器自身が版に固定された前提を置いていた。しかも `hook-contract` を直したとき、収穫元 episode には「marker が踏んだ罠を、marker を検知するための検査器で再生産していた」と自分で書いている。同じ言葉を書いた直後に、隣で同じことが起きていた。

**なぜ非自明か。** 2つの箇所の症状は同じではない。`hook-contract` は「累計で ok」、`screen-marker` は「版に固定された前提を自分で置き、しかも `ok` に構造的に到達できない」である。直した箇所と同じ症状を探すやり方では隣は見つからない。走査の対象は症状ではなく**型**で、この2件をまたぐ型は「検査器が、自分の検出対象と同じ壊れ方をしている」である。**指摘が1件だったことと、欠陥が1件だったことは別である。**

（「直した箇所が緑になると『終わった』という信号として働くから閉じてしまう」という機序を置きたくなるが、**これは推測である。** 出典が記録しているのは行動、すなわち隣を探しに行かなかったことだけで、なぜそうしたかは書かれていない。）

## 確立していることと、していないこと

この2つは証拠の強さが違うので分けて書く。

**確立していること（4つの arc で観測）。** 1箇所を直しても同種が他所に残る、という構造はこの store の既存 item が別々のドメインで3件記録している。

- `01KYA7C9MWDKQK79FGDWRC8W6H`: 同じ欠陥が値の流れる箇所ごとに再発し、3経路で順に露呈した。「1 箇所直しても別経路に同種が残りやすい」
- `01KYCQV7SSW26J9WF0BMYYRXRH`: 「同じ穴が既存コードの別フィールドにも残っていないか（同一ファイルの片割れ）も併せて見る」
- `01KYCQV7SD6BVBWVCRFYJH9TYG`（#274）: deny-list の迂回路を1つ直しても残りが見えず、「別ラウンドの別レーンが指摘するまで残った」

**4件とも、隣を見つけたのは自分ではなく後続の外部ラウンドである。** #299 もそうだった。

**確立していないこと。** 「自分で走査すれば見つかる」は本 item の処方だが、**その有効性は一度も観測されていない。** #299 で走査を入れていれば見つかったはずだ、という反実仮想も検証していない。

**それでも別 item として置く理由。** 上の3件はいずれも**ドメイン固有の trigger**（jq の日付検査 / argv へ値を渡す / deny-list 検証）の中に注記として埋まっている。別領域で外部指摘を受けた消費者は、どの trigger にも当たらない。**4つの arc で繰り返しているのに、一般の形ではどこにも着地していない**というのが、本 item を立てる根拠である。

## 行動をどう変えるか

証拠の強さに合わせて2段に分ける。

**観測が直接支持するもの。**

- **外部レビューを1ラウンドで閉じたことを、型が消えた証拠に使わない。** 4件とも隣を見つけたのは後続のラウンドである。遅延レーンや2ラウンド目が入る余地を残す（レーンを待つ側の規律は `01KYYHGNRJ926N4CTTS4PE8GQH`）。
- 指摘を受けたら、閉じる前に「これは箇所の指摘か、型の指摘か」を1行で決めて成果物に残す。判定そのものは安く、後から読み返せる。

**仮説として試すもの（効いたかを観測で測る）。**

- 型なら、走査の母集団（同じファイルの他の関数・同じ family の他の検査・同じ規約に従う他の呼び出し）を列挙して1件ずつ当てる。**走査は安いので試す価値はあるが、効くという証拠はまだ無い。**
- **型の言明を、症状の側の粒度で置かない。** #299 で走査が当たりえたのは「検査器が自分の検出対象と同じ壊れ方をしている」という粒度でだけである。「累計で ok」という症状の粒度に留めると、`screen-marker`（欠陥は累計ではない）には当たらない。**粒度を誤った走査は「走査済み」という記録だけを残し、確信を強めて終わる。** 母集団を列挙できない粒度に落ちたら、走査ではなく外部レビューをもう1ラウンド足す（`01KYJ76D830XME16ZFXC2XRPZZ`「母集団を書けないなら、その述語は完全性を保証していない」と同じ構造）。
- 走査した範囲と結果を成果物に残す。走査していないなら「していない」と書く。**この記録が、次の観測で「自己走査が隣を見つけたか」を判定する材料になる**（本 item の `observations` がその測定台帳である）。

## 近い item との軸の違い

- **同じ構造を記録している先行3件**（`01KYA7C9MWDKQK79FGDWRC8W6H` / `01KYCQV7SSW26J9WF0BMYYRXRH` / `01KYCQV7SD6BVBWVCRFYJH9TYG`）は上の「確立していること」に引いた。統合しないのは trigger が領域固有だからで、**先行事例として先にそちらを読んでよい。**
- `01KYW0BPJNHP94TNX0VG4G11TX`（自分が名指しした型を、書き手に回ったら免れると仮定するな）は**位置**の軸で、処方は「外部の目を必ず入れる」である。本 item は**外部の目が既に1発当たった後**の軸で、扱うのはその1件をどこまで広げるかである。前者を守って外部レビューを入れても、返ってきた指摘を箇所として処理すれば本 item の失敗は起きる。#299 はまさにその形（外部レビューは入れた・指摘は箇所として処理した）だった。
- `01KZ21M0N0FZ4YMR2R6DPHTWQ4`（検査の陽性判定を累計で持つな）は、本件で1件目に直した**具体的な欠陥**そのものを収穫した item である。本 item はその1件が型であることに気づかなかった側を扱う。
- `01KYSKQHDT86GZW87E8EDMSE46`（遮断の決定と実装は別で、下流の受け口を1つずつ閉じる必要がある）とは、「1点を処置したので全体が済んだと思う」という族が同じである。違いは起点で、あちらは**自分の決定**を下流の層へ展開する話（母集団は決定が触る層）、こちらは**外部からの指摘**を同種の他の箇所へ展開する話（母集団は同じ型を持ちうる箇所）である。
