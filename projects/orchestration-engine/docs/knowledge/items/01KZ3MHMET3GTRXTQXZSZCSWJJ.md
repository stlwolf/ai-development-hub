空返しのレーンについて、**meta の観測可能な値を原因の証拠に使ってはいけない。** 値は「budget の内側で終わらなかった」までしか言っておらず、なぜ終わらなかったかは運んでいない。

#299 の実装SO で、claude レーンが2回とも空で返った。meta は2回とも `exit_code=124`（`timeout` による kill）、`timeout_status=timeout_empty`、stdout 0 バイト、stderr も 0 バイトで、いずれも 1200 秒である。子はこれを時間切れと読み、他2レーンが返っていて「0レーン不可」の床を満たしていたので締めた。**後に同じ依頼（`-w` の有無だけが違う）を再実行したところ、888 秒・exit 0・27,523 バイトで完了した。** 888 秒は空返しが使った 1200 秒の 74% である。時間不足という読みは成り立っていなかった。

**実害が出た。** 遅れて返ったそのレーンは重い欠陥を3件出し、うち1件は「検査器が情報を持っていない」という設計級のものだった。

**なぜ非自明か。** meta は原因を報告する体裁を持っている。`timeout_status=timeout_empty` という名前は「時間切れで空だった」と読める。しかし実際に kill したのは budget を持つ側であり、この値は budget の内側で完了しなかったことしか意味しない。**同じ値の並びは、依頼が重い場合にも、供給側が一時的に止まっている場合にも出る。**

**既存 item との関係（本 item はその反例である）。** `01KYYHGNRJ926N4CTTS4PE8GQH` は「未返却の原因を環境の恒常的性質と結論しない。`timeout_status` と `exit_code` と stdout の中身を見て原因を分ける」と処方している。#299 では**その3つとも本物の時間切れと同じ値だった**ので、処方どおりに見ても原因は分かれない。分かれたのは、時間をおいた再実行が同じ budget の内側で完了したという事実だけである。既存 item の運用の軸（partial で判定を閉じるなら差し戻す経路を用意する）は本 item では扱わない。本 item が足すのは診断の軸だけである。

**安い対照が1つある。** 同一実行の他レーンは codex 450 秒 / cursor 113 秒でどちらも exit 0 だった。他レーンが成功していれば、失敗はレーン固有であって実行環境側ではないと言える。これは `01KYMRE1N7N0J8VP3CBZZEZ8Q3`（0件を不在と読む前に、既知の対照を同じ経路へ通す）をレーン単位に当てた形である。ただしこの対照で言えるのは「レーン固有」までで、原因の名前までは出ない。

**行動をどう変えるか。**

- 空返しの meta を原因の証拠に使わない。読み取れるのは「budget の内側で完了しなかった」だけだと扱う。
- 同じ budget のリトライが空でも「返らないレーン」と結論しない。#299 ではリトライも同じ 1200 秒で空だった。分けたいなら**時間をおいて再実行し、同じ budget の内側で完了するかを見る。**
- 同一実行の他レーンの結果を対照として先に見る。安く、レーン固有かどうかまでは分かる。
- 待たずに閉じると決めたなら、**原因は未確定であると書いて閉じる。** 時間切れと書かない。床（0レーン不可）を満たしていることは、原因を確かめた証拠ではない。

**原因の名前について。** 統括はこの空返しを使用量上限と読んだ。ただしその根拠は本 item の出典に含まれていない（3本の meta は原因を名指ししておらず、stderr も 0 バイトである）。**本 item の主張は原因の名前に依存しない。** 依存しているのは「同じ依頼が後に budget の内側で完了した」という観測だけである。

**観測範囲。** 根拠は #299 の1事例（claude レーン・空返し2回・後の成功1回）である。どれだけ時間をおけば返るか、どの供給側でこの症状が出るかは測っていない。
