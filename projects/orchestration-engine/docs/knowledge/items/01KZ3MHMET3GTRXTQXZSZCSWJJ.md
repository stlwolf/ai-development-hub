空返しのレーンについて、**meta の値から根本原因を確定してはいけない。** 値が確定するのは「budget に到達して kill された」ことまでで、なぜ完了しなかったかは運んでいない。

#299 の実装SO で、claude レーンが2回とも空で返った。meta は2回とも `exit_code=124`（`timeout` による kill）、`timeout_status=timeout_empty`、stdout 0 バイト、stderr も 0 バイトで、いずれも 1200 秒である。子はこれを時間切れと読み、他2レーンが返っていて「0レーン不可」の床を満たしていたので締めた。**後に同じ依頼を再実行したところ、888 秒・exit 0・27,523 バイトで完了した。** 888 秒は空返しが使った 1200 秒の 74% である。

**実害が出た。** 遅れて返ったそのレーンは重い欠陥を3件出し、うち1件は「検査器が情報を持っていない」という設計級のものだった。

**なぜ非自明か。** meta は原因を報告する体裁を持っている。`timeout_status=timeout_empty` という名前は「時間切れで空だった」と読める。しかし kill したのは budget を持つ側であり、この値は budget の内側で完了しなかったことしか意味しない。**「依頼が重くて終わらなかった」と「別の理由で進まなかった」は、この3つの値では同じに見える。**

## 主張の強さ（この線を越えない）

- **支持されること**: 同じ依頼が後の実行で budget の内側（74%）で完了した。したがって「この依頼は budget では終わらない」という読みは成り立たない。**値からは原因が決まらない。**
- **支持されないこと**: 最初の2回が何だったか。供給側の停止・負荷・確率的な処理時間差のいずれとも決まっていない。**本 item はどれかを主張しない。**
- **対照実験ではない**: 再実行は厳密には同一でなく、成功した側にだけ `-w` の3行（ワークスペース参照）が足されている。本文は一致するが、`-w` が到達時間に効かないことは測っていない。交絡が残る。

## 既存 item との合わせ方（矛盾ではなく順序）

`01KYYHGNRJ926N4CTTS4PE8GQH` は「未返却の原因を環境の恒常的性質と結論しない。`timeout_status` と `exit_code` と stdout の中身を見て原因を分ける」と処方している。#293 ではこれが働いた（`error_partial` と本文の文字列で原因が分かれた）。**#299 はその手が届かない場合である。** 3つとも本物の時間切れと同じ値だった。

**両方を読むときの順序はこうなる。**

1. まず値を見る（`01KYYHGNRJ…` の処方）。値が原因を名指ししていれば、そこで分かれる。
2. 名指ししていなければ、**値からは決まらない**と扱う（本 item）。そこから先は再実行で分ける。

既存 item の運用の軸（partial で判定を閉じるなら差し戻す経路を用意する・runner の完了を待つ）は本 item では扱わない。本 item が足すのは診断の軸だけである。

**この2件は片方だけ注入されると読み違えうる。** `01KYYHGNRJ…` だけを読んだ消費者は、値を見れば分かれると読む。両方を同じ slot に載せるか、`01KYYHGNRJ…` の診断節へ本 item への相互参照を1行入れるのが望ましい（後者は本 item を収穫した単位のスコープ外なので、統括へ申し送ってある）。

## 安い対照が1つある

同一実行の他レーンは codex 450 秒 / cursor 113 秒でどちらも exit 0 だった（**この2つの秒数は meta の実測値である。収穫元 episode の E5 表は cursor 136 秒 / codex 425 秒と書いており一致しない。** バイト数のほうは一致する。転記の経緯は下記の実行記録にある）。他レーンが成功していれば、失敗はレーン固有であって実行環境側ではないと言える。これは `01KYMRE1N7N0J8VP3CBZZEZ8Q3`（0件を不在と読む前に、既知の対照を同じ経路へ通す）をレーン単位に当てた形である。ただしこの対照で言えるのは「レーン固有」までで、原因の名前までは出ない。

## 行動をどう変えるか

- 空返しの meta から根本原因を確定しない。読み取れるのは「budget の内側で完了しなかった」だけだと扱う。
- 同じ budget のリトライが空でも「返らないレーン」と結論しない。#299 ではリトライも同じ 1200 秒で空だった。分けたいなら**時間をおいて再実行し、同じ budget の内側で完了するかを見る。**
- 同一実行の他レーンの結果を対照として先に見る。安く、レーン固有かどうかまでは分かる。
- 待たずに閉じると決めたなら、**原因は未確定であると書いて閉じる。** 時間切れと書かない。床（0レーン不可）を満たしていることは、原因を確かめた証拠ではない。

## 原因の名前について

統括はこの空返しを使用量上限と読んだ。**その根拠は meta には無い**（3本とも原因を名指ししておらず、stderr も 0 バイトである）。根拠は #303 に記録された状況証拠で、空だった時間帯が owner の使用量上限のリセット待ちと重なっていたこと、同じ実行の他レーンが成功していること、6時間後に同じ依頼が返ったことの3つである。**本 item の主張はこの名前に依存しない。** 依存しているのは「同じ依頼が後に budget の内側で完了した」という観測だけで、原因が何であれ行動は変わらない。

## `landing: guard-candidate` の理由

同じ故障（原因の違う空返しが `timeout_empty` という1つの値に畳まれている）を機械側で分ける単位として **#303 が起票済み**である。着地先が機構側に実在するので `nl` ではなく候補として記録する。ただし #303 自身が「stdout も stderr も 0 バイトだったので単純な文字列検出では取れない可能性が高い」と書いており、機構が落ちない可能性がある。**落ちるまでは本 item が床として効く。** 機構が落ちたら、本 item の観測を見て NL 側を退役させるか判断する（段6・owner の別 PR）。
