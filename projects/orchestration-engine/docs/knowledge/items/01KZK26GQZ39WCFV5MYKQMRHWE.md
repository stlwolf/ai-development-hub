curated な集合（配布対象・許可リスト・除外設定・登録先）の欠落を埋めよと指示されたとき、**その欠落は書き忘れではなく、どこかの gate で意図的に置かれた保留かもしれない。** 指示の側は「欠落」と呼ぶが、その呼び方は一次記録で裏を取ったものとは限らない。

brief が同時に「Y や Z は意図的に配っていない可能性があるので触るな」と警告している場合、この失敗は**起きやすくなる**。警告が名指ししていないことが、着手対象は例外だという証拠に見えてしまうためである。ただし警告が無い brief のほうが多く、そちらでも同じ失敗は成立する。**警告の有無は増幅要因であって発火条件ではない。**

#309 の残件で実際に起きた。brief は `oe-selfcheck` / `oe-undelivered` について「意図的に配っていない可能性がある」と警告しており、私はその指示を正しく守って触らなかった。ところが着手対象の `oe-hookfire` こそが、同じ issue の plan で「配布が要るかは後続 issue と一緒に決まるので、本単位では置くまでにする」と gate で確定させた保留の対象だった。先行 PR が配布対象に足さなかったのは書き忘れではなかった。

非自明なのは、**この誤りが実装ではなく根拠にしか現れない**ことである。足す変更そのものは正しく、`shellcheck` も配列の対応検査も通り、レビューの前半（コードの欠陥を見る観点）でも何も出ない。壊れるのは記録だけで、保留の巻き戻しが忘れ物の回収として残ると、後から読んだ人は決定が覆った経緯を追えない。今回それを検出したのは実装SO の1レーンであって、私自身ではなかった。committed 層の一次記録を読んでいたかどうかの差である。

次にどう行動を変えるか。(1) **着手前に、対象そのものの名前で committed 層を引く**（`grep -rn '<対象名>' <plan / decision の置き場>`）。brief の要約ではなく plan・decision・gate 記録の実物を読む。(2) **brief が「意図的かもしれない」と警告している対象の集合に、着手対象を必ず含めて考える。** 警告が名指ししていないことは、着手対象が例外である根拠にならない。(3) 一次記録に保留の記述が見つかったら、**変更を止めるのではなく根拠の書き方を変える**。保留を解くこと自体は依頼者の裁定でよく、記録すべきは「保留を、いつ・誰の判断で・何を待たずに解いたか」である。
