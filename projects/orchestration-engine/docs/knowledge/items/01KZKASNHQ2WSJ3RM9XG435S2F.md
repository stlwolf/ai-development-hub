個別の節に分かれていた対象を、概観や索引のために1つにまとめるとき、**共通の性質として書く一文は、群の中で最も強い主張に引きずられる。** 個別記述では対象ごとに書き分けられていた保証が、まとめた瞬間に群全体の契約になる。

危ないのは保証の語彙である。「いずれも read-only」「どれも副作用なし」「すべて冪等」「失敗しない」——これらは**強いほど書きやすく、短くまとまる。** 4つの対象のうち2つが厳密に read-only で2つが自分用の記録を書くとき、「いずれも何も書き換えない」は前2つの正確な記述であり、後2つについては嘘である。それでも1行に収めようとすると、この形で書いてしまう。

#309 の残件で実際に起きた。engine の watchdog 4本（`oe-undelivered` / `oe-vitals` / `oe-selfcheck` / `oe-hookfire`）をスキルの概観で1つの節にまとめ、末尾に「いずれも何も書き換えず」と添えた。実際には `oe-undelivered` は観測の起点ファイルを作り通知後に seen cache へ追記し、`oe-vitals` も seen cache へ書く。書き込みが本当に無いのは残り2本だけだった。元の `bin/README.md` は verb ごとに節が分かれており、各節は「engine state は mutate しない」「cache は verb 自身の bookkeeping」と正確に書き分けていた。**誤りは集約という編集操作そのものが持ち込んだ。**

非自明なのは、**この誤りがコードを一切変えずに入る**ことである。実装は無傷なので diff の review でも `shellcheck` でもテストでも何も出ない。壊れるのは文書が与える契約だけで、それを読んだ人が「read-only 権限の環境でも安全に走る」と判断した時点で初めて実害になる。検出したのは実装SO の1レーンが、まとめた記述と各スクリプトの書き込み箇所を突き合わせたからである。

次にどう行動を変えるか。(1) **保証の語彙を含む共通の一文を書いたら、群の全対象に対して個別に成り立つかを確かめる。** 確かめる先は元の個別記述ではなく実装である（個別記述も同じ誤りを持ちうる）。(2) **最も弱い対象に合わせて書く。** 全対象で成り立つ主張だけを共通部分に置き、成り立たない対象は例外として名指しする。名指しが長くなるなら、それは1つにまとめるべきでない群だという合図である。(3) **「いずれも」「すべて」「どれも」を書いた行は、まとめ作業の点検対象として扱う。** これらの語は集約したことの目印になる。
