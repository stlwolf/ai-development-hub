別のペインで動く委譲子の状態を親が判定する仕組みを書くとき、**手が届く指標のうち、直感的に選びたくなるものが3つとも外れる。**

1つ目は累積 CPU 時間である。「N分間変化しなければ止まっている」という形の判定は、書いた側の直感では素直だが**一度も発火しない**。アイドルのプロセスも CPU を少しずつ使い続けるので、変化量は常にゼロにならず、カウンタが毎回リセットされるからである。108分と15.5時間のアイドルを2件とも見逃し、`%cpu` の**絶対値**へ寄せたところ6分で発火した（別環境の実測。帯も時間も環境で動く）。ただし `%cpu` は直近の減衰平均なので、稼働中でも待ちの区間では一時的に低く出る（16.4% から 1.9% へ落ちた測定がある）。**1回のサンプルで決めてはいけないし、低い値が言えるのは「観測した窓で CPU をほとんど使っていない」までである。** 待ちに入っているのか、実作業が別のプロセス側で走っているのかは、この値からは区別できない。

2つ目は画面である。**待機中を示す表示は、止まった後も画面に残る**ので、1枚の画面に写っていることは稼働の証拠にならない。遡っても内容が増えないこともある（TUI が作業中の内容を scrollback に残さないため。「代替画面だから capture が返らない」という説明は、`capture-pane` の仕様に照らすと逆を向いている）。**禁じられるのは1枚の画面から状態を決めることであって、画面そのものではない。** 時間差で2回撮って差分を見る形は決定論的で有効である。

3つ目が最も危ない。**`capture-pane` は既定で属性を落とす。** 補完のゴーストテキストは薄い表示（検証した環境では `ESC[2m`）で描かれているので、属性を残して取れば判別の手がかりになるが、既定のまま読むと**普通の文字列として現れる**。手がかりであって契約ではない点は押さえておく。描画は TUI の実装に依存する。

ここで踏む害は3段ある。1段目は誤読で、補完の予測を実入力と誤認する。2段目は誤操作で、実在しない入力を消しに行き、子のバッファに本当に何かあれば壊す。3段目が**偽の承認の捏造**である。画面に出たゴーストを「owner の承認が出た」と読み、それを下流へ中継すると、人間のゲートが実質的に空になる。1段目と2段目は作業のやり直しで済むが、3段目は**承認なしで不可逆な操作を通す経路**になる。

3段目が構造的に避けにくいのは、**補完が「次に送られそうな文」を予測する**からである。予測は待っている文面に似る方向へ偏るので、**最も紛らわしい文が、最も危険なタイミングで出る。** 実測でも、ゲート待ちのペインに「裁定が出ました。承認です」に相当するゴーストが出ていた例と、終端の指示を待っている委譲子のペインに、まさにその終端指示の文面のゴーストが出ていた例の2件が別環境で観測されている。

次にどう行動を変えるか。(1) 稼働判定は **プロセスの生死・`%cpu` の絶対値・終端成果物の有無と更新時刻**の3点で組み、累積 CPU の変化量を使わない。機械が出すのは候補までで、確定は成果物と人に渡す。(2) **1枚の画面から状態を決めない**（時間差の差分は別で、こちらは使える）。(3) 入力欄については、属性と送信記録の両方を見てもなお十分条件にならないと見込む（送信記録を残さずに実入力を置く経路がある）。**入力欄の中身を根拠に消したり報告したりしない。** (4) **承認は経路で判断し、画面で判断しない。** 自分が受け取った経路（owner の発言・委譲元からの着信）だけを根拠にする。

手順の具体（どのコマンドで測るか、どの属性を見るか、どこに送信記録があるか）は、それを使う側のスキルに置く。ここに残すのは、**直感が外れる向き**と、**1枚の画面から状態を決めない**という線である。時間差で2回撮って差分を見る形は別物で、こちらは有効である。

隣の item との違い: `01KZ21M0N0FZ4YMR2R6DPHTWQ4`（検査の合格条件を累計の実績で書くな）と、1つ目の失敗は同じ構造を持つ。どちらも**累計に基づく述語は、対象の状態が変わっても遷移しない**という形である。あちらは検査の合格条件、こちらは稼働判定という違いだけである。
