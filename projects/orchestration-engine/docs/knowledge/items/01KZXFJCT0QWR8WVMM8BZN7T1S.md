**「検査が正当な値を弾く」という指摘を、許可集合へ文字を足して直してはいけない。** 指摘された値は通るようになるが、**欠陥の型は同じ場所に残る。**

#298 で二度続けて踏んだ。so-compare の meta に CLI の版を記録するとき、値の健全性検査に既存のモデル ID 用の集合（`^[A-Za-z0-9._:+-]+$`）を流用した。設計SO が「その集合は空白も括弧も通さないので `codex-cli 0.147.0` と `2.1.229 (Claude Code)` が常に `unavailable` へ落ちる。3レーン中2レーンで機能が死ぬ」と指摘した。正しかった。

**そこで空白と括弧を許可集合に足した。** 実在する3つの版文字列はすべて通るようになり、それを確かめるテストも書いた。

実装SO が同じ場所をもう一度指摘した。`codex@0.147.0` も `v1.2.3, build 4` も `v1.2.3 [arm64]` も、`key=value` の行を1バイトも壊さないのに落ちる。**1周目に見つかった欠陥は「この3つの値が落ちる」ことではなく「行を壊さない値が落ちる」ことだったのに、前者だけを直していた。**

## なぜ非自明か

**修正が指摘に対して妥当に見えることが罠である。** 指摘は具体値で来る（「`codex-cli 0.147.0` が落ちる」）。その具体値を通す最小の修正が許可集合への追加なので、指摘と修正が1対1で対応し、再現テストも緑になる。**指摘の粒度がそのまま修正の粒度になってしまう。**

さらに、許可集合を書く作業は**「実在する値の集合を予言する」作業**である。予言は外れる。外れたことは、その値が実際に現れるまで分からない。

## 何が正しかったか

**守りたい不変条件から拒否集合を導く。** ここで守りたいのは「meta の1行1組の `key=value` が壊れないこと」だけだった。そこから決まるのは拒否すべきバイト（制御文字・DEL・`=`）であって、許可すべき文字ではない。拒否集合は不変条件から**演繹できる**ので、予言にならない。

書き換えた結果、実在の3形はもちろん `codex@0.147.0` や `v1.2.3 [arm64]` も通り、行を壊す値だけが落ちるようになった。

## 行動をどう変えるか

- 「検査が正当な値を弾く」という指摘を受けたら、**まず検査が守っている不変条件を言語化する。** 言語化できないなら、その検査は目的を持たずに書かれている。
- 不変条件から拒否集合を導けるなら、**許可集合の列挙をやめて拒否集合に書き換える。** 許可集合へ文字を足す修正は、同じ指摘が別の値で再来する。
- 修正後のテストに、**指摘された値だけでなく「指摘されていないが通るべき値」を入れる。** 指摘の再現だけでは型が消えたことを確かめられない。

## 隣接する item との軸の違い

- `01KYCQV7SD6BVBWVCRFYJH9TYG` は**逆向き**である。あちらは「自由文を deny-list で検証し、その結果を下流の判断に使う」場面で、拒否集合の列挙が迂回されうると言う。**目的が違う** — あちらは危険な値を止めるゲート、こちらは正当な値を忠実に残す記録である。`exclusions` に書き分けた。
- `01KZ3MHMEQN5XEJGV9809QPH2A` は「指摘された箇所を直したら、**同じ型が別の箇所**に残っていないか見よ」と言う。本 item は**同じ箇所に残る**場合を扱う。捜索範囲の話ではなく、修正の形の話である。
