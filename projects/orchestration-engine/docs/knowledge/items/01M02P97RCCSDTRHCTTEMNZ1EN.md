「まだ観測されていない」を受容の理由にするなら、**観測範囲に自分たちの検証行為を入れて数え直す。**

#270 で踏んだ。GC が別サーバの entry を消す型（複数の tmux server が同時に生きている状態）を「一度も観測されていない」として受容し、follow-up へ出した。日常運用の3件はすべて単一サーバ上の別の型だったので、この文自体は正しい。

**ところが露出経路は日常運用ではなく engine のテストだった。** 共有ディレクトリ（`~/.claude/state/oe-delegate/`）はマシン上の全 tmux server から見えるので、検証のために `tmux -L <名前>` で一時サーバを立て、その中で登記系コマンドを1回でも走らせれば成立する。ソケットを数えると死んだ probe が15本あり、**そのうち2本は同じ単位の測定のために自分が前日立てたもの**だった。自分で plan に「サーバを立てた数十秒のあいだに記録が走っていれば本番の registry は消えていた」と書いておきながら、受容の理由づけではその経路を数えていない。

**非自明なのは、受容の文が半分だけ正しいために抵抗が働かないこと。** 「日常運用では観測されていない」は事実で、反証しようとしても本番のログからは反例が出てこない。抜けているのは観測の**範囲**であって、観測の**結果**ではない。

次にどう行動を変えるか。受容の理由に「観測されていない」と書いたら、**その資源に触れる主体を列挙する**（本番の利用者・並行して走る別の作業・CI・**自分たちの検証とデバッグの手つき**）。列挙して初めて「どの範囲で観測されていないのか」が言えるようになる。範囲を限定した形（「日常運用では観測されておらず、テストで踏む窓は別 issue で塞ぐ」）まで書けば受容は成立する。**限定を付けられないなら、それは受容の根拠として弱い。**
