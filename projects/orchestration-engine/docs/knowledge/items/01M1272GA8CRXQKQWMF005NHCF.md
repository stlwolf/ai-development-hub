**他の verb の idiom を借りるときは「その verb が何をしているか」ではなく「何をしていないか」を見る。**

#327 で踏んだ。ラベル解決のキーが `<server_pid>_<pane>` なので、`$TMUX` が空の環境でもキーを作れるようにしたかった。同じリポジトリの `oe-ident` が `TMUX="oe,${pid},0" _oe_reg_key "$pane"` という形でこれを解決していたので、そのまま借りた。

**結果、ラベルが空になった。** 借り先と違い、こちらのラベル解決は最終段で `tmux display-message -p -t <pane> '#{pane_title}'` を呼ぶ。`TMUX` を差し替えると、その tmux が実在しない socket 名（`oe`）を掴んで失敗する。

**`oe-ident` でこの idiom が成立するのは、あちらが tmux へ問い合わせないからである。** `oe-ident` は state ファイルだけを読み、引けなければ空を返して終わる（「無い物を捏造しない」）。だから `TMUX` を壊しても失うものが無い。私のコードは同じ前提の上に立っていなかった。

## なぜ非自明か

**借りた idiom は「動いている先例」なので、疑う対象になりにくい。** コメントに「`oe-ident:44` と同じ idiom」と書けること自体が正当化に見える。

そして**壊れ方が静かである**。例外も非ゼロ exit も出ず、ラベル列が空になるだけだった。テストは mock tmux が何でも答えるので緑のままで、実機で1行ずつ眺めて初めて気づいた。

## 次にどうするか

- idiom を借りるときは、**借り先がその変数・引数に依存する範囲**を読む。とくに環境変数を差し替える idiom は、差し替えた状態で走る**全ての外部呼び出し**を洗う。
- 影響範囲を絞れるなら絞る。今回は「キーの計算だけに効かせる」引数を共有関数へ足し、環境変数の差し替えをやめた。
- mock が寛容なテストでは検出できないので、**借りた直後に実機で1回出力を見る**。
