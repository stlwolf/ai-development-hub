**SO は「渡した量」ではなく「読ませる量」で落ちる。材料をレーンに読ませる形で回すなら、既定の上限を上げる。**

#327 で5回 SO を回した結果がこうなった。

| SO | プロンプト | codex | 結果 |
| --- | --- | --- | --- |
| 設計SO 3回 | 5.6KB / 20.4KB / 27.4KB | 168 / 160 / 237 秒 | すべて成功 |
| 実装SO（diff レビュー） | 6.1KB | 上限まで消費 | 空返し |
| closure チェック | **1.1KB** | 上限まで消費 | 空返し |

**27KB のプロンプトが通り、1.1KB が落ちている。** 量では説明できない。差は**プロンプトが自己完結しているか**である。成功した3回は claim doc の全文をインラインで渡していた。落ちた2回は、1342 行の diff と、226 行 + 339 行の doc をレーン自身に読ませる形だった。

`oe-review` は diff が 30,000 bytes を超えると inline せず「ワークスペースで `git diff` して読んでください」に degrade する。今回の diff は 104,286 bytes で、**うち 57% は同じブランチに積んだ plan と episode** だった。4層ドキュメントを同じブランチに積む運用では、diff は常にこの上限を超える。

## なぜ非自明か

**機構側にノブが既にある**（`SO_TIMEOUT` / `OE_REVIEW_DIFF_MAX_BYTES`）。落ちたときに「codex が不調」「プロンプトが複雑すぎた」と読んでしまい、既定値が仕事の形に合っていないという方向を疑わない。

実際に上限を 600 秒へ上げて回し直したところ、**codex は 308 秒で返り**、そのとき初めて指摘3件（うち高2件）が出た。既定の 240 秒では構造的に届かない仕事だった。**空返しは「意見が無い」ではなく「意見を取り損なった」である。**

## 次にどうするか

- SO を起動する前に「このレーンは材料を読みに行く必要があるか」を1度問う。読みに行くなら `SO_TIMEOUT` を上げる（実測では diff 1342 行で 308 秒）。
- inline できるなら inline する（`OE_REVIEW_DIFF_MAX_BYTES` を上げる / 材料を context ファイルに入れる）。
- 空返しが出たら、まず**プロンプトの量ではなく仕事の形**を見る。短くする方向は逆効果になりうる。
