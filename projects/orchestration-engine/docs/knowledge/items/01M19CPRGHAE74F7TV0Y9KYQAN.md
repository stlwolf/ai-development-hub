**非同期の到着を「来ない」と宣言するとき、前回1回の所要時間を閾値にしない。**

#327 で踏んだ。PR に Copilot のレビューを待っていた。前の PR では約4分で付いたので、12分待って付かないのを見て「Copilot レビューは未着」と報告し、**Copilot 無しで進める案を owner に出した**。

owner から URL を示された。**レビューはその直後に付いていた。**

## なぜ非自明か

**サンプルが1件しかないことに気づきにくい。** 「前回は4分、今回は12分待った、3倍だから来ない」という推論は形としてもっともらしいが、分布を1点から推定している。到着時刻のばらつきが大きい相手には当たらない。

もう1つ、**確認手段の側にも穴があった**。GraphQL 経由（`gh pr view --json reviews`）では author が `copilot-pull-request-reviewer`、REST 経由では `copilot-pull-request-reviewer[bot]` と表記が違う。片方だけで判定していたので、仮に到着していても取りこぼす形になっていた。

そして「来ない」の宣言は、そこで止まらない。**それを前提にした提案（ステップを省略して進める）を人に出してしまう**ので、誤りが人の判断に載る。

## 次にどうするか

- 非同期の到着について「来ない」と断定しない。**「まだ確認できていない」と書く**（状態の記述であって、相手の不在の主張ではない）。
- 待ちを打ち切るなら「来ない」ではなく **「ここまで待って打ち切る」** と書き、判断を人に返す。
- 確認手段が複数あるなら（REST と GraphQL のように表記が違うなら）、**両方で見てから**言う。
