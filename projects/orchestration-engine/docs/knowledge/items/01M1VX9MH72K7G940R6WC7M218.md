**走査で「そのファイルは空だった」と書く前に、そのファイルが存在するのかを確かめること。** 不在と空は同じ 0 バイトに見えるが、証拠としての意味が違う。**不在は「そのファイルを作らない版のコードが、このレコードを生成した」という情報を運んでいる。**

#303 で、過去の SO 出力 114 ディレクトリ・レーン記録 276 件を走査し、空返し 45 件の中身を開いた。claude のレーンに「使用量上限の文言が stdout に 61 バイトで入っている」記録が1件見つかり、そこから「claude の上限は stdout を見れば取れる」という観測点を設計に据えた。走査結果には「同じレコードの `claude-raw.json` も空」と記録されていた。

**しかしそのファイルは空ではなく、存在していなかった。** 走査スクリプトが不在のファイルを 0 バイトとして扱っていた。設計SO のレーンに指摘されてソースと `git log` を開いて確かめた結果、次が分かった。

- その記録は 2026-08-02 02:50 のもので、claude を JSON 形式で受ける変更（同日）より前だった。
- 現在の既定経路では、claude のプロセス標準出力は `claude-raw.json` に落ち、`claude-stdout.txt` は JSON の `.result` から取り出した本文だけになる。
- したがって**同じ故障が今起きても、文言は `claude-stdout.txt` には載らない。** 観測点の設計が丸ごと外れていた。

**なぜ非自明か。** 「中身を開く」ところまでは正しくやっていた。数値だけで判断せず実物を読む、という一段目の規律は働いている。**穴はその一段深いところにあって、開いたファイルが「読めた結果として空」なのか「開けなかった」のかを区別していなかった。** 数値の集計では両者が同じ値になるので、実物を開く習慣だけでは塞がらない。

**行動としては2つ。** 走査の集計に「不在」を空とは別のカテゴリとして持つこと。そして、集めた記録を設計の根拠にする前に、**生成側のコードがその期間に変わっていないかを `git log` で確かめること**。#303 の母集団は収集期間中に生成側が4回変わっており、そのうち1回は記録の意味そのものを変えていた。
