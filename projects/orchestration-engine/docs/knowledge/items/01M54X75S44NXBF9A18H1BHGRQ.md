awk・sed・tr のプログラムが正規表現（`sub`・`~`・`s///`・文字クラス）を使うと、UTF-8 ロケールでは入力を文字に変換してから当てる。入力に UTF-8 として不正なバイトがあると変換に失敗し、macOS の awk は「towc: multibyte conversion failure」、sed と tr は「illegal byte sequence」を出して失敗する。同じ入力を `LC_ALL=C` で与えると成功する。

非自明なのは、**この失敗は環境の失敗と終了コードで区別できない**点である。macOS の awk は、構文エラーや入力ファイルが開けないときと同じ 2 を返す。そのため「0 でなければ環境エラー」とする直し方は、データの不備を環境エラーに誤分類する。#442 で knowledge-list の excerpt の awk を exit 2 にそろえようとして見つけた。engine のほかのスクリプトでは、so-verdict の sed がこの失敗で判定を refuted から survived へ倒すことも分かった。

次にどう行動を変えるか:

- 正規表現を当てるコマンドの失敗を扱うときは、入力に不正なバイトを入れて、配備のロケール（UTF-8）と `C` の両方で通し、データで失敗する経路があるかを先に確かめる。
- 経路があるなら、終了コードだけで分けない。失敗したときだけ同じ入力を `LC_ALL=C` で再実行して分けるか、意味が変わらないと確かめたうえで最初から `LC_ALL=C` で走らせる。行頭の NBSP（U+00A0）のように、文字クラスの意味がロケールで変わる入力があるので、確かめずに切り替えない。
- 再実行で分ける形でも、「`C` で成功した」は原因の証明ではない（一時的な失敗や、`C` 以外でだけ失敗する環境も同じ扱いになる）。説明には「データの不備と見て」と書き、断定しない。
- 正規表現を使わないプログラム（比較・連結・出力だけ）は、データでは失敗しないことを確かめれば、終了コードだけで分けてよい。
