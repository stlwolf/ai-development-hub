**外へ出る道具を偽物に差し替えて確かめるときは、手順の引き方を最後までたどり、本物に届く経路が残っていないことを確かめる。PATH の先頭に偽物を置くだけでは足りない。**

#538 で、統括と子の手順（判断ボードの流れ）を、経緯を知らない新しいセッションに場面を当てて確かめた。子へ1行を送る `oe-send` は、別のペインへ文字を送る本物の操作なので、偽物に差し替える必要があった。最初の案は「引数を記録するだけの偽物の `oe-send` を PATH の先頭に置く」だった。

ゲート1 の設計SO が、この案では足りないと指摘した。手順が従う verb 解決規約は、`oe-send` を名前で呼ばず、PATH にある `oe-tree` の実体のディレクトリを引き、その隣の `oe-send` を呼ぶ。本物の `oe-tree` が `~/bin` にあると、偽物の `oe-send` を通らずに本物の `oe-send` が引かれ、本物の統括のペインへ確かめ用の文が届きうる。

直した足場は3重にした。偽の `bin/` に足がかりの `oe-tree` ごと置き、`~/bin` を PATH から外した。場面に出すペインの番号は、存在しない番号にした（本物の `oe-send` は存在しないペインへは送らない）。Bash の許可を、偽の `bin/` の中のコマンドと読むだけのコマンドに絞った。4回の確かめで、本物の `oe-*` は1回も呼ばれなかった（偽物は自分のパスを記録し、検査がそれを見た）。

## なぜ非自明か

差し替えは「同じ名前の偽物を先に見つかる場所に置く」で済むと考えやすい。間接の引き方は、手順の文（verb 解決規約）の中にあり、差し替える道具の名前の外にある。確かめる側は、偽物が呼ばれた記録が残ることで差し替えが効いたと思い込むが、記録が残るのは偽物が呼ばれた場合だけで、本物が呼ばれた場合は何も残らない。

## 次にどうするか

- 差し替える前に、手順がその道具をどう引くか（名前・PATH の別の道具・設定・環境変数）を最後までたどり、引き方の起点ごと偽物に替える。
- 偽物の側に「自分のパス」を記録させ、検査で「記録されたのは偽物だけ」と「本物の呼び出しが無い」の両方を見る。
- 本物が呼ばれても外へ出ない保険（存在しない宛先・許可の絞り込み）を重ねる。
