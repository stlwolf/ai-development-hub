SO の指摘は、手当てする前に「実際に起きる場面で、安全が変わるか」で振り分ける。指摘が成り立つのに、複数のことが数ミリ秒や1秒の窓に重なる必要があるなら、その経路は手当てせず、plan に「手当てしない経路」として理由と一緒に書く。owner への承認の問いにはしない。

#509 で、oe-view が前の viewer を閉じる条件を決めたときに起きた。設計 SO の3レーン（Codex・Cursor・Claude）が出した指摘を全部取り入れ、プロセス名の確かめと、viewer を開く前後で開始時刻を取る確かめを足した。そのうえで、残った経路（確かめてから閉じるまでの数ミリ秒に GUI が入れ替わる、同じ番号の GUI が同じ秒に起動している）を「受け入れる残りの危険」として、owner に承認を求めた。owner は「その危険は現実的にありえないリスク判断に見える」「まあゼロではないレベル」と返した。同じ基準で見直すと、足した2つの確かめも、同じくまず起きない組み合わせだけを防ぐものだった。2つを外し、残りの経路と一緒に「手当てしない経路」へ移してから、plan は承認された。

なぜ踏みやすいか。SO のレーン、とくに Codex は、反例が形式的に成り立てば must を付ける。「閉じてはいけないものを閉じない」のような絶対の言い方の条件を置くと、窓の競合も must になる。網羅を求める決まり（結論の前に探索を尽くす）に従っているつもりで、成立の頻度を見ずに全部を取り込んでしまう。網羅が求めているのは、検討から外さないことであって、全部を手当てすることではない。

振り分けの目安は次のとおりである。

- 実際に起きる場面（起動し直し・別のウィンドウ・OS の起動し直しのあとの同じ番号）を防ぐなら、手当てする。
- 成り立つのに、ミリ秒や秒の窓での複数の出来事の重なり、または人がわざと作った入力が要るなら、手当てせず、理由と一緒に記録する。
- 手当ての費用が1行で、被害がいちばん大きい場面を守るなら（例: 呼び出し元のペインは閉じない）、頻度が低くても入れてよい。
