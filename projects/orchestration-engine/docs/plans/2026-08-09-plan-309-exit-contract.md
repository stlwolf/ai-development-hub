## 1. 何が壊れているか

`oe-hookfire` と `oe-selfcheck` は3値の判定契約を宣言している。`ok` / `broken` / `indeterminate` / `info` の4語で、exit は「`broken`≥1 → 1 / `broken`=0 かつ `indeterminate`≥1 → 2 / 全部 `ok` → 0」である（`oe-hookfire:34,61` / `oe-selfcheck:24,50`）。

ところが**引数・使用法・前提のエラーが、この意味のある番号を再利用している。** 呼び出し側が exit code だけを見ると、「呼び方を間違えた」「前提コマンドが無い」が「broken を検出した」「indeterminate がある」として通る。**自動監視から見ると、壊れた呼び出しが正当な観測に化ける。**

### 統括の表を測り直した結果 — 3行とも一致した

| 入力 | 統括の報告 | 自分の実測 | 一致 |
|---|---|---|---|
| `oe-hookfire --bogus` | 1 | 1 | 一致 |
| `oe-hookfire --days xyz` | 2 | 2 | 一致 |
| `oe-selfcheck`（`jq` 不在） | 2 | 2 | 一致 |

**訂正すべき点は無い。** 統括の訂正（「意味的な exit 自体は壊れていない。壊れているのは引数・前提エラーとの衝突だけである」）も、コードを読んだ限り正しい。`oe-hookfire:292-294` と `oe-selfcheck:316-318` の集計そのものは宣言どおりに動いている。

### ただし表は衝突の全体ではなかった

自分で測ったところ、同型があと4件ある。

| 入力 | 実際の exit | その番号の契約上の意味 |
|---|---|---|
| `oe-hookfire --days`（値の欠落） | 1 | `broken≥1` |
| `oe-hookfire --help` / `-h` | 1 | `broken≥1` |
| `oe-selfcheck --bogus` | 1 | `broken≥1` |
| `oe-selfcheck --help` / `-h` | 1 | `broken≥1` |

**衝突は実測7件で、うち5件が exit 1（`broken` 帯）側である。** 統括は 2 側の衝突を重く見ていたが、**数の上では 1 側のほうが多い。** とりわけ `--help` が「壊れている」を名乗るのは筋が悪い。

## 2. 押さえておくべき非対称

- **`oe-hookfire` は `~/bin` へ配布済み。`oe-selfcheck` は配布対象ではない。** `scripts/sync/sync-bin.sh:45` の `CMD_NAMES` に入っているのは `oe-tree` と `oe-hookfire` の2本だけである。**repo 外の消費者を心配すべきなのは `oe-hookfire` だけで、`oe-selfcheck` の変更は repo 内に閉じている。**
- **`jq` の位置づけが2本で違う。** `oe-selfcheck:65` は `jq` を必須依存として hard guard を置き、不在なら即 `exit 2`。`oe-hookfire` は guard を持たず、`jq` を要る検査だけを `indeterminate` に落として続行する（`:203` / `:221`）。**「前提コマンド不在はすべて 2」と一律に書くと `oe-hookfire` については誤りになる。**
- **両 verb とも余分な位置引数を黙って無視する。** 引数解析が `while [[ "${1:-}" == -* ]]` なので、最初の非オプションでループを抜け、残りを検査しない（`oe-hookfire:71` / `oe-selfcheck:56`）。実測で裏づけた。`oe-hookfire --bogus` は stderr に `unknown option: --bogus` を出して usage で止まるが、**`oe-hookfire foo --bogus` は stdout に通常の判定表を出す**（`--bogus` が読まれていない）。`oe-hookfire foo --help` も help にならない。**これは統括の brief にも自分の初版探索木にも無かった経路で、設計SO の2レーンが独立に指摘した。**

## 3. gate 1 が崩した前提

`oe-refute --lanes 3 --rubric exploration` は **3/3 レーンが material に反証**した（`audit_id: 20260809130721H1PP65QAANJB`）。崩れたのは次である。すべて自分で測り直して確認した。

1. **初版の案は記述が実装と食い違っていた。** 「usage を repo 慣行の 2 に残す」と書いたが、**現状 usage は exit 1 である。** 「usage を 1→2 へ動かす」第2の変更が要り、それを書いていなかった。
2. **Nagios 規約の全面援用は成立しない。** 借りられるのは「実行不能を対象の判定と混同するな」という原理だけである。本 verb には Warning 帯が無いので、番号の対応が取れない。
3. **「同一 README の中で 2 の意味が二重化しているのは欠陥だ」は無条件には成り立たない。** exit code は実行ファイルごとの名前空間であり、README は索引であってグローバル規約の宣言ではない。
4. **初版の6案には符号化方式・責務分界・ライフサイクル段階・データフローの軸が丸ごと抜けていた。** bit field / preflight 分離 / observer 編入 / durable state / predicate 分解 が未探索だった。
5. **自分の証拠に帰属の誤りが3件あった。** `bin/README.md` の `:204` / `:417` / `:469` をそれぞれ `oe-review` / `oe-jump` / `oe-activity` と書いたが、正しくは `oe-jump` / `oe-tree` / `oe-undelivered` である。
6. **`--help` の集計方法が誤っていた。** 分岐の次の行を静的に読む方法で「12本対8本」と数えたが、**22本すべてを実際に走らせたところ `--help`→0 が15本、→1 が7本だった。** 静的な読みでは `usage()` の中身まで追えておらず、`oe-view` を 1 と誤判定していた。**以後この数字を使う。**

## 4. 設計

### 本単位で入れる番号（owner の裁定・確定）

| exit | 意味 | 呼び出し側が取るべき行動 |
|---:|---|---|
| 0 | `--help` / `-h`、または全判定が `ok`（`info` のみ含む） | 正常終了 |
| 1 | `broken` が1件以上（`indeterminate` 併存可） | 崩れた前提を直す。この観測に依存する判定を止める |
| 2 | **usage エラー・unknown option・余分な位置引数・`--days` の不正値・必須依存の不在**、および `broken`=0 で `indeterminate`≥1 | **この実行を観測として使わない。** 下記の但し書きを読むこと |

**`2` は2つの意味を兼ねている。これは承知のうえの妥協である。** 「呼び方を間違えた（人が直すまで永久に再発する）」と「検査が成立しなかった（次の窓で解消しうる）」が同じ番号に載る。**したがって `2` を見て自動で再試行してはいけない。** どちらなのかは stderr と `--json` にしか出ない。**この但し書きを契約の文言として両 verb と README に書く**（§8 step 4）。

分離（`indeterminate` を 3 へ）は #301 へ保留した。§0 と §13 を参照。

### 私が F1 を推した理由（記録として残す・棄却されたのではなく保留された）

**同じ `bin/` に、帯の切り方の先例がある。** `oe-refute` と `oe-review` は `--help`→0（`:77` / `:87`）、unknown option と余分な引数→2（`:79-80` / `:89-90`）、`jq` 不在→2（`:102` / `:101`）、そのうえで**意味のある判定**（`refuted`）に exit 3 を使っている。実測でも `oe-refute --bogus` は 2、`--help` は 0 である。

**ただし「番号のコピー」として読んではいけない。** 設計SO の claude レーンが指摘したとおり、**`oe-refute` には `exit 1` が1つも存在しない**（grep で確認）。この verb の構造は「判定の帯 {0, 3}」と「判定に到達しなかった帯 {2}」である。

借りるべきは番号ではなく**帯の切り方**である。それを対象2本へ写すとこうなる。

- 対象2本は判定を**3つ**持つ（`ok` / `broken` / `indeterminate`）。`oe-refute` は2つ（`survived` / `refuted`）しか持たない。
- したがって判定の帯には番号が3つ要る。`ok`=0 と `broken`=1 は既にあるので、**3つ目に空いている番号が 3 である。**
- 「判定に到達しなかった帯」は先例どおり 2 に置く。

**`indeterminate` を判定の帯に置くか、判定に到達しなかった帯に置くかが、この単位の唯一の分かれ目である。** F1 は判定の帯に置く。理由は次のとおり。

**`indeterminate` は「何も観測できなかった」ではない。** これは検査1件ごとに付く値で、1回の実行の中で `ok` の行と共存する。`oe-hookfire` が 5行 `ok` ＋ 1行 `indeterminate` を出したとき、**表は出ているし観測値もある。** 1行だけ結論が出なかっただけである。いっぽう `--days xyz` は表を1行も出さず、**そもそも実行されていない。** この2つを同じ番号に置くと、「部分的に観測できた」と「何も走らなかった」が区別できなくなる。

**それは #309 が直せと言った欠陥そのものである。** issue は「壊れた呼び出しが正当な観測に化ける」ことを問題にしていた。

**#299 の判断を覆さない。** #299 は「全検査が `indeterminate` でも exit 0 だった。機械監視から見て成功に見えるなら『indeterminate は ok ではない』は画面上の言葉でしかない」として exit 2 へ分けた（`docs/episodes/2026-08-03-episode-299-delivery-receipt.md:211`、原則化は同 `:359`、実装側の宣言は `oe-selfcheck:25-26`）。F1 はこれを保つ（3 は非0である）。むしろ 2 を usage へ明け渡すために判定を 3 へ動かすので、**`indeterminate` の非0性は強まりこそすれ弱まらない。**

### F1 に添えるもの（設計SO の claude レーンから採る）

**F1 を採るとしても、次の2つは案の採否と独立に正しいので併せて入れる。**

- **exit を advisory と宣言する。** `oe-refute:18` と `oe-review:25` は「**advisory・JSON が正本**」と明記している。**初版の探索木はこの2本を番号の先例として引きながら、同じ行にあるこの但し書きを読み落としていた。** 先例を借りるなら但し書きも借りるのが筋である。両 verb のヘッダと help 文に「exit は粗い信号で、`--json` が正本」と書く。これは「呼び出し側が exit だけを見る前提を、そもそも許すのか」への答えでもあり、**将来 #301 で番号を動かすことを契約違反にしない。**
- **契約テストで表を固定する。** 挙動変化の完全表を assertion として置く。番号がいずれ #301 で動きうる以上、**変更コストを下げておくこと自体が設計判断である。** 費用は小さい。

### 採らなかった案と、その理由

| 案 | 採否 | 理由 |
|---|---|---|
| F2: observer ファミリーへ編入（exit 常時 0・usage のみ 2） | **今は採らない** | `oe-undelivered`（`bin/README.md:469`）と `oe-vitals`（`:543`）の「常時 0」は、検出結果を notify と stdout に載せる前提の契約である。対象2本は通知しない診断器なので、exit から判定を外すと**代替チャネルが無い**。#299 が潰した「機械監視から見て成功」を判定帯全体へ広げることになる |
| F3: 番号を決めず #301 へ送る | **単独では採らない** | 開示だけでは、自己矛盾した契約が配布済みのまま固定される。開示は F1 の PR 本文に含めれば足りる |
| F5: adapter 分離（verb は判定を出したまま・#301 が薄い wrapper を書いて exit 0 にする） | **記録して残す** | #301 が「cron は exit を見ない」と決めた場合の正規の逃げ道。**本単位では実装しないが、#301 へ申し送る** |
| Z1: bit field（`broken` と `indeterminate` を直交ビットに） | 採らない | `fsck` に先例がある（16=usage error）。情報保存性は F1 より高いが repo 内に先例が無い。exit だけで併存まで完全に表すことが絶対要件になったときの選択肢として記録する |
| 二重モード・status artifact・harness 分離・predicate 分解 | 採らない | 消費者が1系統も居ない段階では過剰。#301 で必要と分かってから |

## 5. なぜ争点だけを切り離せるのか

**この単位は「#301 がどう決めても要る部分」と「#301 に依存する部分」に、きれいに割れる。** 裁定はその割れ目で切った。

- **#301 がどう決めても要る**: `--help`→1 と usage→1 の衝突。`--help` が「`broken` を1件以上検出した」と名乗るのは、消費者が exit を読もうが `--json` を読もうが偽である。**自己矛盾なので、外部の決定を待つ理由が無い。**
- **#301 に依存する**: 判定帯の分離（`indeterminate` 2→3）。**#301 が `--json` を読む設計になれば、この移動は使われない。** rev.1 の時点で私自身がそう書いていた。

**私は「依存する側も今やるほうが安い」と踏んで F1 を推し、owner は「依存する側は待つ」と判断した。** 分かれ目は費用の見積もりであって、事実認識の食い違いではない。

## 6. gate 2（設計SO）の結果

`so-compare -f .oe/so-prompt-B-gate2.md -w "$(pwd)" --cursor --claude-model opus --claude-effort high`。**3レーンとも返却した。** 所要は codex 388秒 / cursor 163秒 / claude 638秒。claude は `model_resolved=claude-opus-5`（`models_all=claude-haiku-4-5-20251001,claude-opus-5`・`model_resolved_source=cli-json`）、codex は `gpt-5.6-sol`（`model_resolved_source=config` なので観測値ではない）、cursor は `auto` で解決先を記録していない。

### 合意に至らなかった（owner に判断してほしい点）

**core の判断で2対1に割れた。`so-compare` の合意判定基準（問題認識・方針の方向性・重大な指摘の解消）を満たしていないので、これは3者合意ではない。**

| | codex | cursor | claude |
|---|---|---|---|
| 採るべき案 | **F1** | **F1** | **F4**（`indeterminate` を 2 のまま据え置き、usage も 2 へ） |

**claude の F4 とは何か。** 帯を「判定が出た帯 {0, 1}」と「判定が出なかった帯 {2}」の2つに切り、`--help`→0 と usage→2 だけを直して、**新しい番号 3 を導入しない**案である。「引数を間違えて判定に入れなかった」も「検査が成立せず判定を出せなかった」も、どちらも「この実行から観測値は得られていない」という同じ意味だから同じ 2 に置く、という読みに立つ。

**F4 の利点（正直に書く）**: 既存テストを1件も壊さない（`tests/test_hook_firing.sh:160-163` の `indeterminate`→2 がそのまま通る）。`jq` 不在のとき両 verb が同じ 2 に着地する（F1 だと `oe-selfcheck`→2 / `oe-hookfire`→3 に割れる）。#299 の判断にまったく触れない。

**それでも F1 を推す理由**: §4 に書いたとおり、`indeterminate` は `ok` の行と共存する**部分的な観測**である。F4 は 1 側の衝突5件を解くが、**2 側の衝突2件（`--days xyz` / `oe-selfcheck` の `jq` 不在）を解かない。** #309 が直せと言ったのはまさにそこである。

`jq` の非対称については、**F1 が新しい食い違いを作るのではなく、既にコードにある違いを正直に映すだけだ**と考える。`oe-selfcheck` は `jq` 不在で1行も検査せず終わる（判定が出ていない → 2）。`oe-hookfire` は2つの検査だけ落として残りは走る（部分的な観測 → 3）。**F4 はこの違いを隠す。**

**この判断は owner が覆してよい。** 分かれ目は「`indeterminate` を判定の帯に置くか、判定に到達しなかった帯に置くか」の1点である。

**決着を安く付ける手もある（claude レーンの提案）**: `cron` の1行を最小で書いてみて、その配線が `$?` を見るか `--json` を見るかを観測する。**`cron` の既定は非0終了でメールを飛ばすので、`indeterminate` が非0である限り、記録が溜まるまで毎日メールが来る。** それが望ましいか騒がしいかが F1 / F2 / F4 の選択を1回の観測で決める。

- どうしたか: 2レーン返却は弱 SO としては partial（disclose して進んでよい）だが、**統括の brief が「水準を下げずレーンを足して要求本数を確保する」と明示していたので、claude を単独で回し直した**（`SO_CLAUDE_TIMEOUT=1500`・バックグラウンド実行にして自分のタイムアウトに当たらないようにした）。結果 638秒で返り、3レーンを確保した。

- 転用可能な教訓: **長時間の SO はバックグラウンドで回す。** 実行系のタイムアウト上限は SO レーンの所要時間より短いことがあり、前景で待つと自分の上限が先に当たる。そして**返らなかったレーンを「この環境では返らない」と一般化しない。** 切ったのが自分か機構かを先に確かめる。

昇格の判定: **当初は「姉妹 verb の形へ揃えるだけなので昇格は要らない」と考えたが、gate 2 を経て判定し直した。** 分かれ目になった「`indeterminate` は判定なのか、判定に到達しなかったことなのか」は、番号の割り当てではなく**観測 verb の語彙の意味論**の問題であり、3レーンが割れた。同じ問いは検査 verb が増えるたびに再発する。**したがって `unknown` に留め、gate 3 で owner の判断が付いた時点で closure が確定させる。**

昇格の印: 観測 verb の `indeterminate` は判定なのか、判定に到達しなかったことなのか（同じ問いは検査 verb が増えるたびに再発する）
