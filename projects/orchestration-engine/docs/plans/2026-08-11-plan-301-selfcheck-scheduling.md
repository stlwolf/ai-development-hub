# #301 oe-selfcheck を定期実行に配線する — 実装プラン

## この plan は park されている（2026-08-13・実装へ進まない）

**gate 3 の裁定は park である。** 実装へ進まず、この plan と episode を committed の記録として残して単位を閉じた。**以下の設計内容は書き換えていない。** gate 1 と gate 2 を通過した検証の記録であり、再開時の出発点だからである。

### なぜ park か（owner の理由）

- **通知はクリックしてもペインへ飛べず、ターミナルに帰ってくるだけである。結局こちらからポーリングしに行く。** toast 自体は既に毎回来ており、1本増えても価値が変わらない。
- **本当に優先度が高いのは cockpit の可視化**（#281 / #169。何をやり取りし、何回やり取りし、今どういう状態かの把握）。ただし着手タイミングは owner が測っている段階で、いま繰り上げない。

つまり **`broken` の読み手（出口）が未確定である。** 出口の無い配線は「誰も読まない」問題を一段上で再生産する。**この plan 自身が DJ-2 でそれを急所として明記している。** 急所が未解決のまま実装へ進まない、という判断である。

### 再開条件

- **可視化（#281 / #169）が着地して出口ができたとき。** または owner が別の出口を決めたとき。
- 再開時は gate 3 の残り（下記「owner の gate 3 で判断してほしいこと」の 1〜4）から始められる。**gate 1 と gate 2 は通過済みで、設計は3版まで進んでいる**（初版・statusLine 版・独立2本版）。棄却した案とその理由は episode に集約してある。

### 再開時の出発点として保全してあるもの

- **F3 の材料**（#291 から引き渡された「呼ばれる保証の無い台帳を増やすと Sensor が埋まったと誤読される型が3本目に達しようとしている」・**decision 級の政策判断を含む**）は DJ-6 に保全されている。既存 ADR を確認して重複が無いことも記録済みなので、再開時に調べ直さなくてよい。
- 通知経路の実測結果（`wez notify` はソケット陳腐化で届かない・hook の OSC 777 経路はソケット非依存）と、**送信の成功を届いたと読まない**という設計上の帰結。
- #301 は **keep-open** である。配線の必要そのものは消えておらず、#305 と #291 の連鎖の栓であることも変わらない。

## この単位が引き受けるもの

`oe-selfcheck` は版に固定された前提が今も成り立つかを read-only で点検する verb だが、定期実行の配線が無く、人が思い出して打つまで動かない。それを配線する。

**値打ちは verb 単体ではない。** #291 が `halted-unconverged` で閉じたときの構造的発見は「呼ばれない検知器は『親が起動を覚えている必要がある』分類に落ち、#289 がそれを循環として8レーン全 refuted で棄却している」だった。同じ但し書きを持つ verb は `oe-hookfire` と `oe-prompt-receipt` で既に2本ある。**本単位は「呼ばれない検知器」という型を1つ終わらせる。**

あわせて #291 から F3 が引き渡された。「呼ばれる保証の無い台帳を増やすと Sensor が埋まったと誤読される型が3本目に達しようとしている」の置き場が #301 で、`291-detect:282` が **decision 級の政策判断を含む**と書いている。本プランはその政策も出す。

## 成立条件を5つに分ける

初版は成立条件を「起動が記憶に依存しない」と「人へ届く」の2つに割ったが、gate 2 の codex レーンが**2つとも現在の案では満たされていない**と判定した。粒度が粗すぎて、満たしていない箇所が条件の中に隠れていた。分け直す。

1. **自動で起動する。** 誰かが思い出して打つ必要がない。
2. **実行の失敗と鮮度を、停止しうる主体とは別の経路で観測する。** 止まる当人に自分の停止は報告できない。
3. **結果が永続する。** 次に読む者が過去を辿れる。
4. **名指しされた読み手へ届く。** 「置いてある」は「読まれる」ではない。
5. **届いたことが確かめられる。** 送信の成功は表示の成功ではない。

**条件5は本単位では完全には満たせない。** 到達の確認（ack）まで作ると範囲が跳ね上がる。**満たせないことを明示し、どこまで実測したかを書く**（後述の「未検証のまま残る鎖」）。条件を満たしたふりをしない。

## 設計判断

### DJ-1 実行経路 — 独立した2本の launchd job が互いの鮮度を見る

初版は稼働中の `oe-vitals` の plist へ相乗りする案だった。**gate 2 の codex レーンが論理矛盾を指摘したので改める。** 停止を判定する主体が停止する当人（同じ runner）なら、止まったときに誰も報告できない。初版の本文は「実行側が黙って止まればスナップショットが古くなって見える」と書きながら、その古さを見るのを同じ runner に置いていた。

改めた形は次のとおり。

- `oe-vitals` は**現在の plist のまま**触らない。15分間隔で稼働している実績を壊さない。
- `oe-watch`（新設・`oe-selfcheck` と `oe-hookfire` を呼ぶ）を**別の plist** で登録する。
- **2本が互いの心拍の鮮度を見る。** `oe-watch` は `oe-vitals` の最終実行時刻が古ければ報告し、`oe-vitals` は `oe-watch` の最終実行時刻が古ければ報告する。

初版が2本目を避けた理由は「2本目が生きているかを確かめる問題が増える」だったが、**相互監視がその問題そのものの答えである。** 片方が死ねばもう片方が言う。

**ただし相互監視が検出できるのは片系だけが止まる故障に限る。** 2本は runner の実体・状態の置き場・権限・repo の位置を共有するので、**共通原因の故障では同時に止まる。** 具体的には、実体の消失（worktree の削除を含む）、権限の変更、状態の置き場の破損、両方の plist の解除、launchd 自体の停止である。**これらが本単位の外側の境界であり、相互監視は塞がない。** 初版はここを「launchd が止まったときだけ」と書いていたが、信頼性の過大評価だった。

`oe-vitals` 側に鮮度チェックを足すのは既存 verb への追加変更になる。**範囲が増えるので owner の判断項目に上げる**（gate 3-4）。

**頻度**: `oe-watch` は15分間隔。`oe-hookfire` は 0.15 秒なので毎回。`oe-selfcheck` は 4.5 秒かかり検出対象（版の更新）が日単位で動くので、前回から60分経っていなければ飛ばす。

**配布**: plist のテンプレートとインストーラをリポジトリに置き、インストーラが実行時にパスを解決して生成する。配布物には hub 絶対パスを焼かず、生成物だけが持つ。**インストーラは worktree から実行されたことを検出して拒否する。** worktree のパスを焼くと、その worktree を消した瞬間に黙って止まる（`sync-claude.sh:131` の symlink で同型の罠が記録済み）。

**残る人の記憶**: インストーラを誰がいつ実行するか、plist が古くなったときに誰が更新するかは人に残る。**これは条件1の穴として開示する。** 塞ぐには配布の仕組み自体を変える必要があり、本単位の範囲を超える。

### DJ-2 誰が見るか — durable な記録を主経路にし、通知は best-effort に置く

**これが本単位の急所である。** 素朴に配線すると毎回鳴る。静かにするために検出を落とすと配線した意味が消える。

初版は `wez notify` を「人へ届く保証」の土台に置いた。**gate 2 は3レーンとも不成立と判定した。** 実測したのは OSC を書ける経路が在るところまでで、その先に鎖が残っていたためである。**「未検証の前提には載せていない」と書いた文そのものが、未検証の前提に載っていた。** 2巡目に登録された Anti の3度目である。

改めた形は `oe-vitals:56-68` と同型にする。

- **主経路は durable な記録**（`latest.json` と `history.jsonl`）。ここは失敗しない。
- **通知は best-effort**。届けば速く、届かなくても記録は残る。**通知の成功を成立条件の土台にしない。**

### 通知の運び方 — `wez notify` を使わず、hook の notify.sh と同じ経路にする

gate 3-0 の実測を受けて差し替える。`wez notify` は mux ソケットに依存し、**そのソケットの参照は長寿命セッションで静かに陳腐化する。** owner の環境で toast が見えなかった原因がこれである。

**対して、owner の環境では他の toast が現在も飛んでいる。** `canonical/hooks/scripts/notify.sh` はソケットを使わない。ヘッダ（`:4-9`）にこう書いてある。

> 配信は WezTerm の OSC 777 通知を主とする。tmux 内では DCS passthrough で包んでペイン TTY (`#{pane_tty}`) に直接書く（フックは controlling TTY を持たないため `/dev/tty` は使えない）。非 tmux は `/dev/tty`。どちらも不可なら terminal-notifier → osascript にフォールバック。

実装は `:113-116` で、`tmux display-message -p '#{pane_tty}'` で得たペイン TTY へ DCS で包んだ OSC 777 を書く。**mux ソケットも `wezterm cli` も要らない。** 陳腐化する参照を持たないぶん、故障面が1つ少ない。

**採る経路をこちらにする。** ただし `notify.sh` は hook として呼ばれる契約（第1引数が `done|wait`・stdin に JSON）を持つので、そのまま呼ばない。**同じ配信手順を共有できる形にするか、runner 側に同じ手順を持たせるかは実装時に決める**（配備先からリポジトリが見えない制約は #299 が既に踏んでいる。`notify.sh` は engine の lib を source しない作法で書かれている）。

### 送信の成功を「届いた」と読まない

`wez notify` の exit 0 が「tty へバイトを書けた」でしかないのと同じ問題は、OSC 777 の経路にもある。**書けたことは表示されたことではない。** 真の到達確認（ack）は本単位のスコープ外なので、**手に入らない受領印を前提にしない設計へ倒す。**

- **状態遷移を進める根拠は「記録の書き込みに成功したこと」に置く。** これは局所的に検証できる（ファイルが在り、内容が正しい）。
- **通知の送信結果は状態遷移の条件にしない。** 送れても送れなくても記録は進む。初版は「通知に成功したときだけ状態を進める」と書いたが、`oe-vitals:324-338` のその規律は「送信の成否が判る」ことを前提にしていた。**判らない経路では、同じ規律が逆に働く**（書けただけで既読になり、以後の通知が永久に止まる）。
- **同じ `open` が続くあいだは、既定で再通知しない。ただし無期限に黙らせない。** 一定期間（既定7日）ごとに1回だけ鳴らし直す。記録側には「鳴らそうとした回数」が残る。
  - **この記録は監査のためのものであって、到達不能の検出ではない。** 受領印を持たない以上、**正常に配送された場合と経路が静かに死んでいた場合の記録は同じになる。** 答えられるのは「何回鳴らそうとしたか」までである。
  - 到達不能に近づけるのは、**owner が「1通も見ていない」と言えるときに限る。** それは記録と人の記憶を突き合わせる操作であり、機械の判定ではない。**条件5（到達の確認）を満たさないことは変わらない。**

これが #299 の「安全装置が置物になっていた」と同型の形を避ける核である。**送信側の成功報告を信じない。**

**push するもの**（best-effort）:

- 台帳の外にある `broken`。
- **`check-unable` 系の `indeterminate`**（下記の分類）。
- 相方の job の鮮度が切れた（DJ-1 の相互監視）。

**`indeterminate` の分類を先に作る。** gate 2 の claude レーンが、`indeterminate` には意味が正反対の2種類あることを枝の行番号つきで示した。

| 種類 | 意味 | 該当する枝 | 扱い |
|---|---|---|---|
| `no-positive-control` | 検査は健全で、見るものが無いだけ | `oe-selfcheck:116` 生存ペインが無い / `:129` 入力欄を持つペインが無い / `:153` 稼働中が無い / `:205` 猶予を過ぎた送信が無い | **push しない。** 記録には残す |
| `check-unable` | 検査が実行できない | `oe-selfcheck:110` tmux が無い / `:115` list-panes 失敗 / `:178` 活動ログを読めない / `:247` transcript の置き場が無い / `:278` sidecar の置き場が無い / `oe-hookfire:176` tally を読めない | **1回目から push。** 待っても情報は増えない |

**初版の「N 回続けたら push」は捨てる。** `screen-marker` は誰も作業していない時間帯に必ず `no-positive-control` へ落ちるので、60分間隔で3回＝3時間の規則は**夜間に毎晩必ず発火する**。会議で3時間離席しても同じである。しかも同じ規則が、1回目で判明する `check-unable` の報告を3時間遅らせる。**両方向に間違っていた。**

**何が push から外れるかを先に書く。** 外れるのは (a) 台帳に宣言済みの `broken`、(b) `no-positive-control` の `indeterminate`、(c) `info` である。**この3つはいずれも `latest.json` に全量が残り、消えるのは push だけである。** `info` は `retention-horizon` の1本だけで、`oe-selfcheck:296` が「良し悪しの基準を持たない」と明記している。

**pull は「保存」であって「読まれる保証」ではない。** gate 2 の codex レーンの指摘を受けて、ここは正直に書く。`latest.json` を置くことは条件3（永続）を満たすが条件4（届く）は満たさない。**条件4を担うのは push だけである。** 読み手を名指しできる面（board への転記など）は本単位では作らない。

**`oe-vitals` の cron.log と同じ形にしない。** あちらは 2953 行・385KB・ローテーション無しで誰も読んでいない。`history.jsonl` は判定と `code` だけの圧縮形にし、保持日数で切る。

### DJ-3 台帳と重複抑止 — 状態遷移で持つ

`(検査名, 判定)` を鍵にした重複抑止は**成立しない**。`screen-marker` の `broken` には2枝、`hook-contract` には3枝あり、鍵が変わらないまま別の壊れ方へ移る。`detail` 全文を鍵にすると、埋め込まれたペイン枚数が動くので毎回鳴る。

そこで `oe-selfcheck` の JSON に**枝ごとの安定した `code`** を足す。**`broken` の枝だけでなく `indeterminate` の枝にも付ける**（DJ-2 の分類がそれを要求する）。台帳は `(検査名, code)` で既知の `broken` を理由つきで宣言する。

**重複抑止は `open` / `resolved` / `regressed` の状態遷移で持つ。** 初版は「通知に成功したときだけ seen へ焼く」しか決めておらず、**焼いたキーをいつ外すかが無かった。** `oe-vitals:326` の先例はキーが `kind|session_id` でセッションが使い捨てなので解除が要らなかったが、検査名は永続するので同じ形は使えない。永久に抑止すれば本当に死んだときも鳴らず、`ok` へ戻ったら解除すると `screen-marker` は昼夜で往復して毎晩鳴り直す。

**これは gate 1 の1巡目で codex が「incident / ack 状態機械」として挙げた案である。** 初版はこれを採らず、棄却理由も書いていなかった。3巡目に「相乗りを理由なく捨てていた」と叱られた形が別の選択肢で再発していた。**採る。**

**台帳の経年劣化に手当てを入れる。** 宣言した `code` が観測されなくなっても宣言は残り続ける。「宣言したが今回は観測されなかった」を `latest.json` に `info` として出す。費用はほぼゼロである。

**`code` の追加はスコープを超える。** 「既存の `oe-selfcheck` を配線するだけ」という指定と当たるので owner の判断項目に上げる（gate 3-1）。

**`code` は唯一の道ではない。** 初版はここを「`code` 無しでは台帳も分類も成立しない」と書いたが、gate 2 の3レーンがそろって**強すぎる**と判定した。**台帳で枝を黙らせる設計を採るなら `code` が要る**が、採らない倒し方が実在する。

- **push を捨てて記録だけにする**（台帳の需要そのものが消える）。
- **検査名の単位で常時 push し、クールダウンで頻度を抑える**（枝の取り違えは残るが `code` は要らない）。
- **`marker/absent` を `indeterminate` へ再分類する**（gate 3-2 の判断。常時 `broken` が消えるので台帳の需要が縮む）。
- **非 `ok` への遷移と低頻度の継続 reminder を push する**（同じ判定の内側の原因変化は、最大通知間隔で救う）。
- `detail` から変動する数値を剥がした fingerprint（脆いが、`code` 必須という主張の反例にはなる）。

**`code` を採る場合の宿題も1つ残っている**（codex レーン）。B1 は `oe-selfcheck` しか対象にしていないので、**`oe-hookfire` 側で `code` をどう供給するかが未定義**である。

### DJ-4 `indeterminate` の exit 帯 — この単位では動かさない

`oe-hookfire` と `oe-selfcheck` のヘッダが「分離は #301 で決める」と書き、#315 が「#301 が exit を読むか JSON を読むかを決めてから」と保留した。**決める。**

**答え: 配線側は `--json` を読む。exit は帯としては読まない。** したがって帯の細分は配線の要求ではない。そのうえで**この単位では動かさない**。理由は2つある。

1. **2 は「呼び方の誤り」だけではない。** `oe-selfcheck:78` は `jq` 不在で 2 を返す。これは呼び方の誤りではなく**環境の失敗**である（`oe-vitals:131` にも同型がある）。`indeterminate` を 3 へ動かすだけでは環境の失敗が「呼び方の誤り」の帯に残る。帯を作り直すなら3つ目の帯も決める必要があり、それは配線ではなく契約の再設計である。
2. 配布済みの verb 2本の exit 契約を変えることになり、本単位の可逆性が下がる。

**そのかわり runner 側の扱いを決める**（gate 2 の指摘）。

- verb が JSON を返さなかった / 壊れた JSON を返した → その verb の結果を `check-unable` 相当として記録し、push の対象にする。**黙って落とさない。**
- verb が起動できなかった（不在・実行不能）→ 同上。
- runner 自身の exit は常に 0（観測者。`oe-vitals:59` と同じ規律）。

**#309 の残件へ差し戻す。** 差し戻すときに、#315 が待っていた情報（消費者は JSON を読む）と、新たに判明した情報（帯を分けるなら環境失敗の帯も要る）を添える。**未決のまま置くのではなく、決めたうえで別の場所へ渡す。**

### DJ-5 `oe-hookfire` — 同じ配線に乗せる

0.15 秒と軽く、同じ3値契約を持つ。**同じ但し書きを持つ verb の型が2本同時に終わる。**

**ただし JSON スキーマが揃っていない。** 実測した。

```
$ oe-hookfire  --json | jq -r '.[0] | keys | join(", ")'   → detail, name, verdict
$ oe-selfcheck --json | jq -r '.[0] | keys | join(", ")'   → check, detail, verdict
```

検査名のキーが `name` と `check` で違う。**runner が正規化し、正規化のテストを持つ。**

`oe-prompt-receipt`（3本目）は hook であって verb ではなく、起動経路が別なので本単位では扱わない。

### DJ-6 政策（#291 の F3）— Sensor の成立条件を decision にする

**置き場を決める前に既存 ADR を自分で確認した。** #319 から届いた訂正が「`291-detect:280` の『既存の着地は code header と episode の散文だけ』は事実と食い違い、実際は ADR 2本に在る」というものだったので、同じ誤りを繰り返さないためである。

`projects/orchestration-engine/docs/decisions/` の14本を確認し、あわせて `Sensor` の語を engine の docs 配下と `canonical/` 全体で検索した結果、**閉ループ制御の Sensor 成立条件を扱った decision は無い。** `2026-07-09-decision-238-239-succession-watchdog-lean-arch.md` は watchdog の構造（declared 層と observed 層・read-only 観測）を決めているが、「呼ばれる保証」の政策は書いていない。

書く内容は次のとおり。初版は「起動の保証と読まれる保証の2つ」と書いたが、gate 2 が3レーンとも「強すぎる／運用不能」と判定したので、**満たせる形に落として、満たせない部分は開示の義務として書く。**

> **read-only の台帳・検知器は、次の5条件のうちどれを満たしどれを満たさないかを、新設時に名指しする。** 自動起動 / 停止の外部観測 / 結果の永続 / 名指しされた読み手への到達 / 到達の確認。
>
> **全条件を満たすことを要求しない**（到達の確認は多くの場合に費用が見合わない）。**要求するのは、満たしていない条件を verb が自分で名乗ることである。** 但し書きに「読み手が走ることに条件付けられている」とだけ書くのでは、どの条件が欠けているかが読めない。欠けた条件を名指ししないまま台帳が増えると、Sensor が埋まったと誤読される。

新規 decision として起こすが、**既存 ADR への追記のほうが正しいと owner が判断する余地は残す**（#319 が F1 について「新規ではなく追記が正しい」と裁定した前例がある）。

## gate 3-0 の実測結果 — `wez notify` の toast は見えなかった

owner に依頼した60秒の実測が返った。**答えは「見えない」だった。** 統括が原因を特定している。`WEZTERM_UNIX_SOCKET` が死んだソケット（`gui-sock-25889`）を指しており、実体は `gui-sock-93106` である。長寿命のセッションが起動時の値を持ち続けたためで、生きているソケットを明示指定すれば通る。

**私が gate 1 で「launchd 相当の環境から到達する」と測ったのと矛盾しない。** launchd はこの環境変数を渡さないので `wez discover` が生きたソケットを見つける。壊れるのは**変数を継承する長寿命セッション**の側である。私自身、gate 1 の測定中に一度この罠を踏み、「継承させた測定のほうが実態から遠かった」と episode に書いていた。**その観測を、通知経路の設計へ結びつけていなかった。**

### 失敗の見え方を自分で測り直した（統括の報告と食い違う）

統括は「`wez notify` は ERROR を出しながら exit 0 を返す」と報告した。**再現しなかった。**

```
$ WEZTERM_UNIX_SOCKET=/tmp/definitely-dead-sock-301 wez notify "検証" "..."
[wez] ERROR: notify: no WezTerm socket found
exit=1

$ WEZTERM_UNIX_SOCKET=/Users/eddy/.local/share/wezterm/gui-sock-25889 wez notify "検証" "..."
[wez] ERROR: notify: no WezTerm socket found
exit=1
```

統括が名指しした当の stale socket でも exit は 1 である。**ソケット不在は正しく非ゼロで返る。**

**しかし懸念そのものは実在する。しかも報告された形より広い。** コードを読んで特定した。`notify.sh:71-76` の主経路は次の条件で成功を名乗る。

```bash
if [[ -n "$tty_name" ]] && [[ -c "$tty_name" ]] && [[ -w "$tty_name" ]]; then
  if printf '\033]1337;SetUserVar=...' > "$tty_name" 2>/dev/null; then
    printf 'tty\n'; return 0
```

**`wez notify` の exit 0 は「tty へバイトを書けた」を意味するだけである。** その先に WezTerm が居るか、user-var ハンドラが発火したか、macOS が toast を出したかは一切見ていない。ソケットが見つかった後の全経路で、**送信の成功と表示の成功が切り離されている。**

これは gate 2 で codex レーンが既に指摘していた（「OSC write 成功は表示 receipt ではありません」）。plan は受け入れ条件に1行入れただけで、**設計の側では exit 0 を状態遷移の根拠に使ったままだった。**

### この件そのものが本 verb の検出対象である

`WEZTERM_UNIX_SOCKET` の陳腐化は「外部の版・環境に固定された前提が静かに壊れる」形そのもので、`oe-selfcheck` が存在する理由に一致する。**検査項目の追加は本単位のスコープ外**なので取らないが、**次の単位への候補として名指しする**（後述の申し送り）。

昇格の印: 自分の測定中に踏んだ罠を、設計判断の側へ結びつけ直す。踏んだ記録を残すだけでは、同じ罠が設計に残る。

**もう1つ賭けが残る。** 「台帳外だけに絞れば owner は読むようになる」は仮定である。#299 は shadow を既定にして同じ賭けを避けた。**PR-B は push を実行しない shadow で着地させ、昼夜を1日以上またいで観測してから live へ切り替える。** 夜間の `no-positive-control` が本当に push されないことは、この1日で必ず出る。
