# #303 / #344 段階1 — SO レーンの空返しを分類し、渡す前に入力を拒否する契約（設計プラン）

**段階1 は設計だけを作る。実装・マージ・issue close はしない。** 終端は本プランと gate 2 の結果を報告するところまでである。

## 1. 何を解こうとしているか

SO のレーンが返らないとき、`so-compare` は原因の違う複数の故障を同じ値に畳んでいる。畳まれている限り、待っても直らないものを待ち、恒久的な故障を「そのうち直る」と読む。実害はすでに出ている（#299 の実装SO が2レーンで締められ、あとから返った3レーン目が重い欠陥3件を出した）。

**本プランが増やすのは「なぜ返らなかったか」を機械が言える範囲であって、返らないこと自体は減らない。**

## 2. 実測（P-1・一次情報）

### 分けられないものは「分けられない」と書く

**B-3 を `usage_limit` と断定してはいけない。** #303 のときに原因が分かったのは「6時間後に同じプロンプトが返った」「owner が上限のリセット待ちを踏んだ時間帯と重なる」という**プロセスの外の情報**によってである。meta にあるどのキーからも導けない。

したがって本プランの分類は、**確定できるところまでしか言わない**設計にする。B-3 に付く値は `unknown`（原因不明の空返し）であって `usage_limit` ではない。

## 4. 撤回する判断と、残す判断

**撤回する。**

- **「claude は stdout を見る」**（指摘4）。いまの既定経路と噛み合わない。claude の観測点は、上限時に JSON の何がどこへ落ちるかを測ってから決める。
- **「入力の検査はプロンプト組み立て完了時点の1箇所に置く」**（指摘7・8）。取り逃す経路が具体的に列挙された。**境界ごとに置き、最後に共通の検査を足す**形へ変える。
- **「拒否したときは exit 3 を返す」**（指摘6）。`oe-refute` の `refuted` と同じ値になる。**別の値にするか、上位ツールに明示の分岐を先に入れる**。どちらにするかは実機で確かめてから決める。
- **「PR-1 → PR-2 の順で分類を先に入れる」**。消費者に届かない分類を先に入れても、判断は何も変わらない（指摘1・2・3）。順序を変える。

**残す。**

- **`timeout_status` を壊さず、原因を別のキーで持つ方向**。3レーンとも方向自体は妥当としている。
- **分からないものを断定しない原則**。B-3 を `usage_limit` と書かない。
- **経路によって拒否と修復を使い分ける方針**。ただし基準の言い方は直す（下記）。

## 5. 確定の前に測ること

**この3つを測らないと、分類の設計は決められない。** どれも実装ではなく測定である。

### 測定1: 分類に値が付く範囲は実際どれだけか

過去の 114 出力ディレクトリに分類を当て、**`unknown` でない値が付く件数を、so-compare の版で層別して**数える。版の境目は #296（2026-08-02）・#328（2026-08-14）・#345（2026-08-18）・#353（2026-08-28）である。

**判断の分かれ目**: 最新の版の区間で `unknown` でない件数がほぼゼロなら、**分類は診断表示としてしか正当化できない。** そのときは enum を6値も持たず、証拠の文字列を残すだけにする。

### 測定2: claude が上限に当たったとき、いまの経路で何がどこへ落ちるか

`claude -p --output-format json` が上限のときに何を返すかを1回測る。`.result` に文言が入るなら `claude-stdout.txt` に載り、入らなければ `claude-raw.json` にしか残らない。**観測点はこれで決まる。**

上限を人為的に作れないので、**次に上限に当たったときに記録する**（`claude-raw.json` を消さずに残す）。それまでこの設計は確定しない。

### 測定3: 空返しのあとに極小プロンプトを投げると、上限と時間切れは分かれるか

gate 2 の claude と codex が**独立に同じ案を出した**（追い打ち診断・canary）。cursor の代替Xも起動前ゲートという形で同じ的を射ている。

- やること: レーンが空で返った直後に、**数秒の上限で1往復する極小プロンプト**を同じ CLI へ投げ、終了コードと出力を記録する。
- 期待: 上限なら数秒で非ゼロ、時間切れなら成功する。
- **これが成り立てば、本プランの中核である「B-3 は分けられない」が崩れる。** #299 の 1200秒×2 も止められる。
- 反証のしかた: `SO_TIMEOUT=5` で人為的な時間切れを作り、同じ極小プロンプトが成功することを確かめる。上限に当たっている時間帯に投げて非ゼロになることを確かめる。

**3レーンのうち2レーンが独立に出した案なので、優先して測る。**

## 6. 入力の拒否（#344）— 境界ごとに置く

**「1箇所」を撤回し、境界ごとの検査＋最後の共通検査に変える。** 検査点は次の4つになる。

| 位置 | 何を見るか | 型付きの理由 |
|---|---|---|
| 引数解析の直後 | `-c` の各ファイル（実在・非空・UTF-8）／`-f` のファイル（実在）／`-w` のパス（実在） | `invalid:not-found` / `invalid:empty` / `invalid:not-utf8` |
| 引数解析の直後 | `-c` が問いを食っていないか（ハイフンなしの引数を全部取る癖） | `invalid:ambiguous-args` |
| 環境変数の入口 | `PREV_MAX_BYTES` などの数値（`SO_TIMEOUT` はすでにここに在る） | `invalid:not-a-number` |
| プロンプト組み立ての完了時点 | 最終的な本文が UTF-8 として妥当か・上限内か（**取り逃しの最後の網**） | `invalid:not-utf8` / `invalid:too-large` |

**経路名を型に載せる。** 組み立て後に見ても「どのファイルが不正だったか」は復元できないので、拒否の理由には経路（`-c` の何番目か等）を付ける。

**基準の言い方を直す。** 初版は「削ったら意味が変わるか」と書いたが、gate 2 が反例を出した（`--prev` の切り詰めも次の周の意味を変える／全損しても警告だけで続く）。**より安定した言い方は「その入力の権威がどこにあるか」である。**

- 利用者が明示的に指定したもの（`-c` / `-f` / `-w`）は**拒否する**。黙って削ると、削られた前提でレーンが答える。
- ツールが自分で作った参考情報（`--prev` の切り詰め）は**修復してよい**。ただし**全損したときは拒否に倒す**（現状は警告だけで続く。ここは変える）。

**`invalid:too-large` の上限値は決めない。** 現状 50KB 超で警告しているが、拒否の閾値を今決める根拠が無い。測定1と一緒に、過去のプロンプト長の分布を見てから決める。

## 8. PR 分割（測る → 繋ぐ → 拒否する）

**順序を変えた。** 初版は分類を先に入れる形だったが、消費者に届かない分類を先に入れても判断が変わらない。

### PR-1: 過去の出力に分類を当てる読み取り専用コマンド

- 変更: `so-compare` を**触らない**。出力ディレクトリを読んで分類を当てる独立コマンド（`oe-lane-explain` 仮称）を engine の `bin/` に置く。
- なぜ最初か: **配布物（`~/bin` の symlink で全セッションに即反映）を触らずに測定1ができる。** シグネチャを直しても誰の実行にも影響しない。gate 2 の claude 代替2 と cursor 代替Y が独立に出した形である。
- 受け入れ基準
