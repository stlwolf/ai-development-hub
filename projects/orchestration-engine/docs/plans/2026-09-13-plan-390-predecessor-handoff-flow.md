# #390 交代の前任側のフローをガードレールのスキルへ入れる

## 背景

前の単位（PR #396）は計画的な交代の**後継側**を `canonical/skills/doc-flow-guardrail/SKILL.md` へ書いた。cold-start の手順5（登記のつけかえと子への宛先の通知）がそれである。

**入っていないのは前任側である。** 交代を始めるのは前任なので、いまのスキルは出口だけがあって入口が無い。実測でも、スキル本文に `oe-handoff prepare` と `oe-handoff start` は**それぞれ0件**である（`grep -c`）。前任がやることは machine-local の board（`.oe/START-HERE-cockpit-succession.md` の「succession 手順」節）にしかなく、**この board は gitignored で hub にしかない。** 別のリポジトリで立ち上がった統括は読んでいない。

狙いは board が冒頭に書いている状態である。「**owner が出す指示は1つ（「交代して」）。そこから先は前任と後任が自分で回す。**」いまは前任が最初の一歩を踏めないので、この状態が配布物の側で成立していない。

この単位は (1) 前任側の工程をスキルへ入れ、(2) そこで使う verb の在り処を hub 相対でない形にする。

## ブリーフの断定を当て直した結果

ブリーフが挙げた前提を merged master（`f8a9759`）と実行で確かめた。**食い違いは無い。1件は範囲を狭める必要があった。**

### 一致したもの

- **スキル本文に前任側の入口が無い。** `grep -c 'oe-handoff prepare'` と `grep -c 'oe-handoff start'` はどちらも0。`oe-handoff` が出るのは3行（122 / 130 / 139 行目）で、いずれも後継側か、verb の一覧としての言及である。
- **前任の工程は board にしかない。** `.oe/START-HERE-cockpit-succession.md:182-185` に「前任（退く側）がやること」4項がある。**`canonical/` 配下で `oe-handoff` に触れているのは `doc-flow-guardrail/SKILL.md` だけ**で、他は0件（`grep -rn 'oe-handoff' canonical/`）。
- **PATH に在るのは `oe-tree` だけである。** `command -v` を5本（`oe-handoff` / `oe-register` / `oe-send` / `oe-tree` / `oe-delegate`）へ当てて確認した。配布対象の正本は `scripts/sync/sync-bin.sh:64` の8本で、`oe-handoff` / `oe-register` / `oe-send` は入っていない。
- **`prepare` と `start` は前任のセッションで走る。** `oe-handoff --help` の一覧と `bin/README.md:191-196` の表が一致する。`take` と `retire` は後継のセッションで走る。
- **人が書く節を埋めないと後継の `retire` が通らない。** 前の単位の engine 側 episode に実測がある（`projects/orchestration-engine/docs/episodes/2026-09-12-episode-390-retire-and-docs.md:354-355` — 申告が空の下見は exit 1、埋めたあとの下見は exit 0。落ちた理由は同 `:380-381`）。

### 狭めたもの（そのまま写すと事実より広くなる）

- **「人が書く節」全体を `retire` が見ているわけではない。** 機械が読むのは**自己申告の節だけ**で（`bin/oe-handoff:809` が節を切り出す）、そこから使うのは**表の行だけ**である（同 `:898`・`:913`）。「渡らないもの」「確立した運用」「owner が下した裁定」は**検査に使われない**。テンプレート自身が「`retire` が見るのは、この表の行だけである。散文に書いても処分にはならない」と書いている。
- **したがって手順には両方を書き分ける。** 表は機械が止める。残りの3節は機械が止めないが、**作り直せるのは機械の節だけなので、止まらないほうが失われる。**

## 設計の前提（実測で確定した事実）

### 前任にできることは3つだけ

issue #390 の「設計の骨」がそう定めている。**引き継ぎ文書を作る / 後継を起こす / 自己申告して閉じられる**、の3つで、席の紐付けと検算は後継の仕事である。理由は材料の在り処で、pane と session_id は後継のプロセスの中にしか無い。

### `prepare` が書くもの・書かないもの

- 集めるのは open PR / worktree / 未 push と枝 / 生きた委譲子 / 常駐の見張り / 前任の session_id・context%・拍動の古さ・**ペインの pid とそのコマンド名**である（`bin/oe-handoff:143` の `cmd_prepare`）。
- **書き換えるのは引き継ぎ文書だけ**で、その中でも**機械の節を毎回まるごと上書きし、人が書く節には触れない**（同 `:310-319` の awk 置換。目印は行全体一致・1組・順序まで書き換える前に検査する）。**厳密には置き場のディレクトリも作る**（同 `:271` の `mkdir -p`）ので、「文書しか触らない」ではなく「文書とその置き場しか作らない」が正しい。
- 既定の置き場は `<workspace>/.oe/handoff.md`（`--out` と `OE_HANDOFF_FILE` で変えられる）。**workspace の既定は git のトップレベル**なので、hub 以外のリポジトリでもそのリポジトリの `.oe/` に落ちる。**hub では `.gitignore` が `.oe/` を無視するが、他のリポジトリでそうとは限らない。** この文書は「会話にしか無かったもの」を書く場所である。
- 出力は「次にやること」を3項まで出す（人が書く節を埋める → `start` → 子が居れば引き渡し）。**この出力からスキルへの導線は無い**（`doc-flow-guardrail` の文字列は出力にもテンプレートにも0件）。

### 人が書く節は4つある

テンプレートの見出しは `## 前任の自己申告`（`:12`）・`## owner が下した裁定と、次のテーマ`（`:34`）・`## 確立した運用`（`:38`）・`## 渡らないもの`（`:44`）である。**機械が検査するのは1つ目の表だけ**だが、**残り3つも前任にしか書けない。**

### 申告に処分が要る項目の集合

`retire`（後継が走らせる）が止める条件は、**前任が何を書いたか**に依っている。前任側の手順はここから逆算する。

- **表に項目が1行も無ければ止まる**（`bin/oe-handoff:914-915`）。「保留ゼロ」とだけ書く形は通らない。
- **各行の処分は `済んだ` / `引き継ぐ` / `取り消す` のいずれか**でなければ止まる（同 `:904-906`・`:916-918`）。
- **照合に使うのは表の1列目（項目）と2列目（処分）だけ**である（同 `:898` の `item = c[1]; disp = c[2]`・`:913` の `DISPOSED`）。**3列目の補足は読まれない**ので、PR 番号を補足欄に書くと処分にならない。
- **機械の節が挙げた PR は、処分が付いた行に `#<番号>` の形で出てこなければ止まる**（同 `:941-947`）。番号だけの一致は種別をまたいで誤るので、`#` を要求する。
- **未 push が残っているのに処分の付いた行に出てこなければ止まる**（同 `:948-951`・再検査は `:1019`）。照合語は `未 push` か `unpushed` である。
- **main 以外の worktree も、処分の付いた行に出てこなければ止まる**（同 `:990-1006`）。**ただし出所が違う。** PR と未 push は**機械の節に書かれた値**とも突き合わせるが、**worktree は `git worktree list --porcelain` をその場で読み直した値**である（同 `:984`）。open PR と未 push もこれとは別に**実行時の値で再検査する**（同 `:958-971`・`:1015-1019`）。つまり `retire` は下見でも `--execute` でも**そのときの実状態を数え直す。**
- **open PR は作者で絞られない**（`lib/handoff-state.sh:344` の `gh pr list --state open`）。**他人の PR も機械の節に入り、処分を要求される。**
- **子の件数と session_id は止めない**（owner 裁定 2026-09-13・同 `:792`・`:796`）。**ただし数えられなかったときを0件に畳まない**（`prepare` も `retire` も「0 件ではありません」と書き分ける・同 `:231`・`:792`）。

### 交代は board を要求する（**設計SO で分かった・この単位の設計を変えた**）

- **`take` は board が読めて書けることを要求し、無ければ exit 2 で止まる**（`bin/oe-handoff:474-476`）。board から前任の宣言（`現統括:` の行）を読めなければ席を動かさない（同 `:501-504`）。
- **`retire` も board を要求し**（同 `:706-707`）、**board の註（「前任 `%N` は退任申告済み・停止待ち」）と引き継ぎ記録の前任が一致しなければ閉じない**（同 `:742-748`）。
- **board の在り処を後継へ伝える経路が、配布物にも文書にも無い。** `canonical/` 配下に `OE_BOARD_FILE` は**0件**。`prepare` の機械の節に board のパスは入らない。**`start` は素の `tmux split-window` で後継を起こすので、前任のシェルの環境変数は後継へ渡らない**（同 `:407`）。
- **したがって board の場所を知っているのは前任だけで、渡す工程は前任側にしか置けない。**

### `start` が起こすもの

- `oe-delegate` を使わず素の tmux split で `claude` を起こし、**登記の子にせず `PARENT_TMUX_PANE` も渡さない**（`bin/oe-handoff:387-410`・理由は「後継の自発的な報告の宛先が、これから閉じる前任のペインに焼き込まれる」）。
- **失敗の枝が2つあり、終了コードが違う。** ペインが一覧に現れなければ**送らずに exit 1**（同 `:427-431`）。ペインは現れたが送信に失敗したときは、手で貼る1行を出したうえで**exit 0 で終わる**（同 `:434-441`）。**終了コードだけでは「送れた」かが分からない。**
- 出力の最後は「次にやること: 後継のセッションで `oe-handoff take` を走らせる」である。**前任が打つ verb はここで終わる。**

### 交代の発火条件

- owner の「交代して」が正規の入口である（board の succession 手順の冒頭）。
- **常駐の見張りは context% で ping する。** `oe-vitals` は現統括の拍動を読み、`context_pct > T` で owner へ ping する。**T の既定は 85**（`bin/oe-vitals:93`・`:105`）。**ping の宛先は owner であって統括ではない**ので、これは「owner の指示が来る前触れ」である。

### verb の在り処

- **`oe-*` は原則 PATH 未登録**で、実測でも PATH に在るのは `oe-tree` だけである。
- **`oe-tree` は engine の `bin/` への symlink である**（`readlink "$(command -v oe-tree)"` → `.../projects/orchestration-engine/bin/oe-tree`）。**他の verb は同じディレクトリの隣に在る**（`ls` で `oe-handoff` / `oe-register` / `oe-send` を確認）。**リンクは絶対パスで1段だけ**である（`scripts/sync/sync-bin.sh:205` の `ln -sfn "${source_path}"`）。
- **多くの verb は実体のパスで呼ばないと壊れる。** `oe-handoff:25-31` と `oe-register:35-37` は `BIN_DIR="$(cd "$(dirname "$0")" && pwd)"` で `../lib/` を source し、**`dirname "$0"` は symlink を解決しない**。**25本中19本が同じ形**である。**配られている `oe-tree` は例外**で、自分で `readlink` のループを持つ（`oe-tree:61-65`）。
- **`readlink` に `-f` は付けない。** engine 自身が `oe-tree:61` に「macOS の `readlink` は `-f` 非対応のためループで解決」と書いている。**設計SO は現在の macOS 15.7.7 で `-f` が動くことを実測した**ので、**この註は現行 OS では古い。** それでも `-f` に依存しない形を採る。理由は (a) リンクが1段の絶対パスなので `-f` が要らないこと、(b) **engine 自身が `-f` を避ける書き方を選んでいること**である。
- **足がかりが symlink でなければ `readlink` は空を返す**ので、実体のディレクトリに目的の verb が在るかを確かめてから使う。実測では、実体コピーを足がかりにすると `[ -x "$oe_bin/oe-handoff" ]` が落ちて手順3 へ倒れる。
- 実測: `anchor="$(command -v oe-tree)"; oe_bin="$(dirname "$(readlink "$anchor" || printf '%s' "$anchor")")"` → `"$oe_bin/oe-handoff" --help` が通る。**cwd を `$HOME`（repo の外）にしても同じ**である。

### いま hub 相対になっている箇所の内訳

`grep -n 'projects/orchestration-engine' canonical/skills/doc-flow-guardrail/SKILL.md` は3行に当たる。**性質が2つに分かれる。**

- **72行目 = verb の在り処**（`projects/orchestration-engine/bin/oe-send %N '...'`）。**この単位で直す。**
- **140行目と167行目 = 文書への参照**（engine 側の discussion 2本）。**verb ではないので scope 2 の対象ではない。** ただし hub の外からは開けないので、**観測として範囲外に surface する。**
- **129行目と135行目には hub のパスが無い。** 代わりに「engine の `bin/` のパスで呼ぶ」という関係で書いてあるが、**hub の外ではその `bin/` が何処かを解けない。** 消しても消さなくても到達できないので、**リテラルの grep だけでは捕まらない側の穴である。**

## 棄却した案（ゼロベース探索・ゲート1）

### 前任側の工程をどこに書くか

- **③ cold-start 節の中に足す。** 後継側の手順5 と隣り合うので繋がりは見える。**棄却の理由は読み手が違うこと**である。③ は「memory の無い新 repo / 新統括セッション」の節で、前任は**走っている統括**である。cold-start していない読み手に cold-start の節を読ませる形になる。
- **② 委譲固定節テンプレに足す。** 固定節は統括が子へ貼る文である。前任は自分で踏むので読み手が違う。採らない。
- **routing 表に行を足す。** 表は蒸留フローのゲート 0-6 と委譲操作軸の索引で、`document-format.md`「ゲート配置」節と 1:1 に対応している。交代は蒸留フローのゲートではないので 1:1 が崩れる。採らない。
- **`oe-handoff prepare` の出力に足す（engine のコードを変える）。** 実行した人の目の前に出るので、いちばん踏まれやすい。**棄却の理由はブリーフが engine のコードを範囲外にしていること**だけである。効き目ではこちらが上なので、範囲外として surface する。
- **board に足す。** いまの在り処がそこで、**この単位はそこにしか無いことを問題にしている。** 採らない。
- **採る案 = 新しい節「④ 計画的な交代を始める（前任側の工程）」を ③ の直後に置く。** ③ の末尾にある「統括 succession は2つに分かれる」の段落から ④ を指し、④ の終わりから後継の工程（`take` → `retire` → ③ の手順5）を指して輪を閉じる。

### verb の在り処をどう書くか

- **`orchestration-toolkit` へ routing するだけにする（本文に規則を置かない）。** 3軸分離の宣言に照らすといちばん筋が良い（**設計SO の codex レーンもこれを推した**）。**棄却の理由は、routing 先も同じ穴を持っていること**である。`orchestration-toolkit:44` は「engine の `bin/` ディレクトリのパスで起動する（hub では ...）」と書いており、**hub の外では「engine の `bin/`」が何処かを解けない。** 他スキルの修正は範囲外なので、この単位で到達性を閉じるには本スキル側に規則が要る。**routing は残す**（配布対象の正本と詳細はあちらが持つ）。**移設は範囲外として surface する。**
- **環境変数（`OE_BIN` 等）で在り処を渡す。** engine に該当の変数は無い（`grep` で `OE_BIN` / `OE_HOME` / `OE_ENGINE` / `OE_ROOT` は0件）。**新設は engine の仕事**なので範囲外。
- **`oe-handoff` 等を bin sync の配布対象に足して PATH で解ける状態にする。** 根治に近いが `scripts/sync/sync-bin.sh` の変更であり、**symlink 経由では lib が解決できない**という別の問題を先に片付ける必要がある。範囲外として surface する。
- **このスキル自身の実体から辿る。** スキルは3ツールへ symlink で配られるので、`readlink` で実体（hub の `canonical/skills/...`）に出られ、そこから2つ上が repo root である。**棄却の理由は、そこから先に hub の内部構造（`projects/orchestration-engine/bin`）を知っている必要があること**で、**消したい知識をそのまま使う形**になる。足がかりの verb から引く案にはこの依存が無い（**実体の隣**しか使わない）。
- **引き継ぎ文書に verb の在り処を書く（`prepare` が書く）。** 後継も前任も必ず読む場所なので確実だが、engine のコードである。範囲外として surface する。
- **hub 相対のパスを書いたまま「hub 以外では読み替えよ」と註を付ける。** 読み替える先が分からないので手順にならない。採らない。
- **採る案 = 「PATH に在る `oe-*` を1本取り、その実体の隣から呼ぶ」規則を、独立した「verb 解決規約」節として置く。** 既存の「spec 解決規約」節（case-C）と同じ形である。**足がかりを固有名でなく関係で書く**ので、配布対象が増えても古くならない。

### 発火条件と `start` の扱い

- ~~**`prepare` で止めて、`start` は owner の指示で打つ。**~~ **子の初稿はこれを推したが、ゲート3 で取り下げられた**（2026-09-14）。理由は、`start` の手前にもう一度 owner を挟むと**この単位の狙い（owner が出す指示は1つ）が成立しない**ためである。**同型の段階分けは #390 の本体で一度取り下げられている**（「停止コマンドを押すのは人がよい」が owner の優先順位と逆だった）。**人のゲートは発火条件の側に既にある。**
- **閾値に達しても何もしない（owner の指示だけを入口にする）。** 見張りの ping は owner へ飛ぶので交代は始まる。**採らないのは、ブリーフが発火条件を2つ挙げているから**である（owner の指示 / 自分の context が閾値に近い）。片方を落とすと上流の scope を狭めることになる。
- **`start --dry-run` まで進める**（設計SO の claude レーンが挙げた中間案）。画面を変えずに「起こすもの・送るもの・登記しないこと」を出せる（`bin/oe-handoff:398-404`）。**採らないのは、下見が要る場面が思い当たらないため**である。`prepare` まで進めた時点で残りは1コマンドで、その内容は `--help` に書いてある。**手順には入れず、選択肢として存在することだけ知っていればよい。**
- **採る案 = 1回の指示で `prepare` から `start` まで通す**（ゲート3 の裁定）。**閾値で自分から始める場合だけ、`start` の直前に画面へ1行書いてから打つ**（下記 DJ-9・**owner が委ねた判断**）。

## 設計判断

### DJ-1 前任側の工程は独立した節「④」として、③ の直後に置く

読み手が違う（走っている統括であって cold-start する新セッションではない）。③ の末尾の段落が既に「計画的な交代は本スキルが持つ / 後継が踏む工程は手順5」と宣言しているので、**その段落へ「前任が踏む工程は ④」を1句足して入口にする。**

### DJ-2 ④ の末尾で、後継が踏む順序を1行だけ名指しする

**設計SO の両レーンが独立に指摘した。** ③ の手順5 は `take` と `retire --execute` が済んだ状態を前提に書かれているのに、**配布物のどこにも「`take` → `retire` 下見 → `retire --execute`」の順序が無い**（board にしかない）。前任側の工程だけを足すと、**輪は前任の出口で切れたままになる。**

**手順として後継側に書き足すのではなく、④ の末尾に「ここから先は後継が `take` → `retire`（下見）→ `retire --execute` → ③ の手順5 の順に進む」の1行を置く。** 前任が渡す相手の文脈であり、③ を書き換えないので scope も動かない。

### DJ-3 申告の書き方は、`retire` が機械で見るものと見ないものを分けて書く

見るもの（表の1列目と2列目・処分の語彙・PR の `#<番号>`・未 push・worktree）は**止まる条件として**書く。見ないもの（残り3つの人が書く節）は**作り直せないものとして**書く。**「人が書く節を埋めないと通らない」と一括りに書かない** — 事実より広く、かつ後継が最も必要とする節を機械が守っていると誤解させる。

### DJ-4 子の扱いは「抱えたまま渡す・件数の unknown を0に畳まない」の2点だけ書く

交代は子の数で止まらない（owner 裁定）。つけかえと宛先の通知は**後継の工程**なので ③ の手順5 を指すだけにして、前任側には重複して書かない。**unknown を0に畳まない**は engine が `prepare` の出力で明示的に書き分けている性質で、**畳むと後継が引き受ける相手を取りこぼす。**

### DJ-5 後継が席を取るのに要るもの（board と引き継ぎ文書の場所）を渡す工程を入れる

**設計SO の claude レーンが最重要として挙げた。** `take` と `retire` は board を要求するのに、**board の在り処を配布物のどこも伝えていない。** `start` が送るのは引き継ぎ文書のパス1行だけで、前任の環境変数は後継へ渡らない。**board を知っているのは前任だけなので、渡す工程は前任側にしか置けない。** 引き継ぎ文書を既定から動かした場合の `--handoff` も同じ形である。

### DJ-6 `start` のあとに状態を動かさないことを手順に入れる

`retire` は下見でも `--execute` でも**そのときの実状態**（open PR・未 push・worktree）を数え直して申告と突き合わせる。**申告を書いたあとに状態が動くと、後継の側で止まる。** 動かしたときの回復手順（`prepare` を打ち直す。人が書いた節は消えない）まで書く。

### DJ-7 verb の在り処は「PATH に在る `oe-*` の実体の隣」を first-class にする

`command -v` で1本を取り、その実体のディレクトリから目的の verb を**実体のパスで**呼ぶ。**手順1（PATH に在ればそのまま呼ぶ）と手順2（実体で呼べ）を分けない** — 分けると、将来 `oe-handoff` が PATH に symlink で置かれたときに手順1 が壊れた呼び方を指示する（**設計SO の codex レーンの指摘**）。**足がかりは固有名でなく関係で書く**ので、配布対象が変わっても古くならない。hub の例は最後の段にだけ additive に置く。

### DJ-8 規約は独立した節にして、既存の3箇所はそこを指す

同じ規則が本文の3箇所（72 / 129 / 135 行目）に散っていると、片方だけ古くなる（前の単位が `required` に判定した型）。**規約を1箇所に置き、3箇所は参照に変える。** ただし各箇所の固有の注意（`exit 127` の罠・送信後に exit code を見る・`orchestration-toolkit` への routing）は**消さずに残す。**

### DJ-9 発火条件は2つ。owner の指示で始まったなら `start` まで自走する（**ゲート3 で書き換えた**）

発火条件は owner の「交代して」と、自分の context% が閾値に近いことの2つである。**閾値の数（85）は `oe-vitals` の既定を引く**（`--threshold`）。ping の宛先が owner であることも書く（統括宛だと誤解すると、来ない通知を待つ）。

**owner の指示で始まったなら、同じ1回の指示の中で `prepare` から `start` まで通す。** 途中に owner を挟まない。**初稿は `prepare` で止める形を推したが、ゲート3 で取り下げられた**（2026-09-14）。狙いが「owner が出す指示は1つ」である以上、`start` の手前にもう一度指示を要求するとその狙いが壊れる。

**閾値で自分から始めた場合だけ、`start` の直前に自分の画面へ1行書く。** owner の指示を経ていないので、**新しいペインが黙って現れる形を作らない。** ただし**返事は待たない**（待つと、owner が手を動かさないという優先順位と衝突する）。**owner が委ねた判断はここで、採らなかったのは「発火条件を owner の指示だけに絞る」案**である（ブリーフが2つ挙げているので、片方を落とすと上流の scope を狭める）。

### DJ-10 「薄い枠」の宣言と衝突するので、位置づけ節に例外を書く（**ゲート3 で裁定済み**）

**設計SO の両レーンが指摘した。** `SKILL.md:18` は「本スキルが持つのは (a) 各段の大原則1行 と (b) routing 表 の2つのみ」、`:20` は「ツール軸（oe-*）＝ `orchestration-toolkit`」と宣言している。**④ も verb 解決規約もどちらの枠にも入らない。** 節を足すだけで宣言を直さないと、**スキル自身の記述が偽になる。**

**位置づけ節に「交代の工程と verb の到達性は例外として本スキルが持つ」を1文足す**（ゲート3 で認められた・Step 4）。

## 受け入れの境界（owner が明示した・そのまま書く）

**この単位の受入は、そこで使うコマンドとスクリプトが個々の責務を果たしていることまでで判定する。交代のフローが1回以上通ることを完了条件にしない。**

判定は次の3つで、**フローを流さずその場で確かめられる**。

1. 手順が呼ぶコマンドが実在し、`--help` が名乗る責務が手順の記述と一致する。
2. 手順が書く引数と順序が、実際の口（`--help` と実装）と一致する。
3. 手順が書く検算が、そのコマンドの出力で実際に取れる。

**「コマンドとスクリプト」が指すのは `oe-handoff` / `oe-tree` / `oe-register` / `oe-send` の4本である**（この単位はどれも変更しない）。**④ は `oe-vitals` の既定値も引くが、閾値は数の一致だけを見るので上の3項の検査対象には数えない。**

### 上の3項だけでは足りないので、変更そのものを見る項を足す

**前の単位で採った negative knowledge の1件目がこれである。** 上の3項は既存コマンドの性質だけを見るので、**`SKILL.md` を1文字も編集しなくても全部通る。** 境界（実運用の交代までは求めない）は動かさず、静的な受入を足す。**錨はすべて新しく書く節（④ と verb 解決規約）の中に置く** — 既存の本文で成立してしまう書き方にしない（**設計SO が2項でこれを検出した**）。

1. **前任側の工程が `SKILL.md` に実在する。** `oe-handoff prepare` と `oe-handoff start` が本文に出る。
2. **④ の工程が `prepare` → 人が書く節 → 子の扱い → 後継へ渡すもの → `start` の順で書かれている。**
3. **輪が閉じている。** ④ の末尾に後継の順序（`take` → `retire` 下見 → `retire --execute` → ③ の手順5）があり、③ の succession 段落から ④ への参照がある。
4. **④ が、人が書く節を4つとも挙げている**（自己申告と残余 / owner の裁定 / 確立した運用 / 渡らないもの）。
5. **④ が、機械が見るもの（表の1列目と2列目・処分の語彙・PR の `#<番号>`・未 push・worktree）と見ないもの（残り3節）を分けて書いている。**
6. **④ の本文に、子の件数の unknown を0に畳まない旨がある**（③ の手順5 にある同趣旨の文では代用しない）。
7. **④ に board の引き渡しがある**（`--board` か `OE_BOARD_FILE`）。
8. **④ の本文に閾値の数（85）が書かれており、`oe-vitals` の既定と一致する。**
9. **「verb 解決規約」節が在り、足がかりを固有名でなく関係で書いている。**
10. **hub 固有の語を落としても規約が成立する。** 判定は機械で行う。**`projects/orchestration-engine` / `canonical/` / `bin sync` / `hub` を含む行を落とした版**を作り、規約に (a) PATH から足がかりを取る段、(b) 実体のディレクトリを引くコマンド、(c) 実体のパスで呼ぶ理由、の3つが**すべて残っている**ことを見る。**これは存在の検査であって、読み手が完遂できることの証明ではない** — 完遂の側は設計SO の問い（hub 以外の統括が読んで実行できるか）で見る。
11. **3箇所（「報告2段構え」の項・cold-start の手順4・手順5 の routing）が規約を指す形に変わり、`exit 127` の注意と `orchestration-toolkit` への routing は残っている**（消していない）。
12. **位置づけ節に例外の1文がある**（④ と verb 解決規約を本スキルが持つ理由）。
13. **frontmatter の `description` に前任側の発火条件がある**（「交代」か「前任」の語で引ける）。
