# #390 交代の直後に踏む工程をガードレールのスキルへ書く

## 背景

2026-09-13 に統括の 14代目から 15代目への交代が実物で1回通った（PR #394・master `32b4e63`）。verb は4つとも通ったが、**後継が生きた委譲子の登記を自分の下へつけかえる工程を踏まなかった。** owner が画面を見て「動いていない」と指摘するまで、設計SO・実装SO・Copilot・テスト・`retire` の下見のいずれも反応しなかった。

原因は口が無いことではない。`oe-register link <%N>` の口は在り、`--help` にも `bin/README.md` にも載っている。無かったのは**交代の直後に踏む工程としての位置づけ**である。13代目は同じ状況で子3体を `oe-register link` で自分の下へ移していたので、差は手順ではなく人だった。

この単位は、その工程を `canonical/skills/doc-flow-guardrail/SKILL.md` に書く。あわせて、同じスキルが教えている報告の宛先が交代で古くなる件と、129行目の除外文が実物とずれた件を直す。

## ブリーフの断定を当て直した結果

統括のブリーフが挙げた前提を、merged master の一次情報で当て直した。**5件は一致し、3件は食い違った。**

### 一致したもの

- **`oe-register link <%N>` の口は在る。** `oe-register --help` の出力に `link <%N>   相手ペイン %N を自分の下に子として登記（parent_pane=$TMUX_PANE で record）` が在る（実行して確認）。`bin/README.md:166` と `canonical/skills/doc-flow-guardrail/SKILL.md:127` にも在る。
- **つけかえは1手で2つの症状を消す。** `lib/delegate-registry.sh:78` で `oe_reg_record` の最後の行が `oe_reg_gc` を呼び、`oe_reg_gc` は `tmux list-panes -a` に無い登記を消す（同 `:271-276`）。停止した前任の root 登記はこの掃除で消える。
- **`oe-report` の解決順は環境変数が先、無ければファイル。** `bin/oe-report:53-58` が `PARENT_TMUX_PANE` を先に読み、空のときだけ `/tmp/oe-parent-{pane}` を見る。**`oe-delegate` にこのファイルを書き出す箇所は0件**（`grep -c 'oe-parent' bin/oe-delegate` = 0）。`oe-delegate:201` は `PARENT_TMUX_PANE=... claude` の形で子の環境変数として渡すだけなので、起動後に書き換わらない。
- **129行目は実物どおり「復旧」と書いてある。** 全文は「統括 succession の**復旧**は本スキルの範囲外（engine track・#238/#239）」で、末尾に「自動化 verb `oe-reseat` は仮称・未実装」が在る。
- **復旧は #355 に残り、`oe-reseat` は未実装のままである。** #355 は OPEN（「統括セッションのクラッシュ後復帰を明示的な verb とフローで確立する」）。`bin/` に `oe-reseat` は0本。

### 食い違ったもの（食い違いのほうを採る）

- **ブリーフは「委譲固定節の `oe-send "$PARENT_TMUX_PANE"` の行」を1箇所として書いているが、実物は2箇所ある。** 71行目（報告2段構え）と 72行目（返信は `oe-send` で返す）の両方に在る。**直すのは2行である。**
- ~~negative knowledge item `01M1TK0A7AX20V0XKWYNAR5WM5` の置き場が違う~~ → **これは子の誤りだった（統括の指摘・ゲート3 で訂正）。** ブリーフの `item:` は `projects/orchestration-engine/docs/knowledge/items/` と書いており、実在もそちらである。`docs/harness/` なのは `source:`（収穫元 episode）のほうで、**item と source を取り違えて harness 側のパスを自分で組み立てていた。** closure の観測の書き戻し先は engine 木で正しい。
- **ブリーフは「あなたの `PARENT_TMUX_PANE` が何を指していても」と注意しているが、この子の環境変数は正しい宛先を指している。** 15代目に起こされたので焼き込まれた値がそのまま現統括である。ブリーフの指定（宛先を明示する）はそれでも守る。**ここで確かめられたのは「交代前に起きた子では古くなる」ことであって、「常に古い」ことではない。**

## 設計の前提（実測で確定した事実）

### 登記とつけかえ

- **`oe-register link` の guard は前任が生きているかどうかで分岐する**（`bin/oe-register:185-190`）。対象の子の現在の親が「非空・自分でない・**生存している**」の3つを満たすときだけ拒否し、`--force` を要求する。**親が gone（前任のペインが停止済み）なら orphan の引き取りとして素通りする。**
- **`--force` は corrupt entry の fail-closed も同時に上書きする**（`bin/oe-register:193`）。要らない場面で打つと、読めない登記を黙って上書きする経路が開く。
- **`oe-register root` は冪等で、`--label` と `-w` を省くと既存の値を保つ**（`bin/oe-register:158-162`）。**この再登記も `oe_reg_record` を通るので GC を呼ぶ。** つまり**子が0体でも、登記への書き込みの契機は作れる。**
- **`oe-handoff take` は自分を root として登記するが、既に root ならやり直さない**（`bin/oe-handoff:616-619`）。**交代の後継は cold-start の手順4（`oe-register root` での自己登記）を打つ必要がない。**

### 子の一覧をどこから取るか

- **`take` の一覧はその時点のスナップショットである**（`bin/oe-handoff:523-545`）。
- **`retire --execute` は閉じる直前にもう一度数え、各行を出す**（`bin/oe-handoff:1074-1086`）。コード中のコメントが「下見と実行のあいだに子が増えても閉じる。ただし増えたことは出す」と明記している。**つまり最新の一覧は `retire` の出力のほうである。**

### `retire` が閉じずに終わる分岐

- **閉じない理由が1件でもあれば exit 1**（`bin/oe-handoff:1035-1037`）、**申告と機械の検査が食い違っても exit 1**（同 `:1039-1043`）、**ペインの先頭プロセスが `claude` でなければ exit 1**（同 `:1184-1188`）。**どの場合も前任は生きたまま残るので、`--force` 無しの `link` は guard に拒否される。**

### 検算に使える出力

- **`oe-tree` の root は「parent 参照のうち entry が無い pane」と「parent が空の entry」の和である**（`bin/oe-tree:641-654`）。**前任の登記が GC で消えても、まだつけかえていない子が parent に前任を指しているかぎり、前任は entry の無い root として木に残る。** そのときのラベルは entry も `pane_title` も引けないので `?` になる（同 `:630-640`）。
- **したがって「`cockpit` の root が1本」は検算にならない。** 前任の登記が消えた時点でラベルが `cockpit` でなくなるので、子が1体も付いていなくても真になる。**見るべきは「前任の pane が木に現れないこと」と「引き受けた件数と自分の下に出る子の件数が一致すること」である。**
- この worktree から `oe-tree` を実行し、現統括の下に自分がぶら下がる形（`(you)` 付き）が出ることを確認した。

### 宛先と送信

- **`oe-send` の口は `oe-send [--brief <path>] [--] <target> [ad-hoc...]`**（`--help`）。exit は 0 送信 / 1 宛先無し / 2 呼び方と環境エラー / 4 未着の可能性。
- **target が空だと exit 2 で落ちる**（`bin/oe-send:60-61`）。**誰も設定しないシェル変数名へ差し替えると、空に展開されてここで落ちる。**
- **`oe-send` の宛先解決は `%N` を素通しするが、送信は生存確認を通る**（**ゲート4 で訂正。初稿はここを誤っていた**）。`oe_reg_resolve` が素通しするのは登記による解決だけで、`lib/delegate-send.sh:188-200` が `tmux list-panes -a` の集合所属を見て、無ければ exit 1 で落とす（`%99999` へ送って実測）。**残る危険は pane 番号の再利用と、exit 0 が配送の成功を意味しないことの2つである。**
- **子が自分の現在の親を機械で引く公開の口は無い。** `oe-ident` は role とラベルだけを出し親のペインは出さない。`oe-list` は PANE / SOURCE / LABEL の3列で親を持たない（`lib/delegate-registry.sh:219-228`）。`oe-tree` は木の形でしか出さず、機械可読の出力形式は無い（`--help` に JSON 出力の記載なし）。

### 3ツールへの配布

- **`canonical/skills/` は3ツールへディレクトリ単位の symlink で配られる。** `scripts/sync/sync-{claude,cursor,codex}.sh` がいずれも `sync_dirs "${CANONICAL_DIR}/skills" "${TARGET_BASE}/skills"` を呼ぶ。**ただし対象に通常ディレクトリが在るとそのスキルは警告だけで skip される**（`sync-claude.sh:93` / `sync-cursor.sh:96` / `sync-codex.sh:72`）ので、「3者が同じ1ファイルを見る」は**各対象が正しい symlink である場合に限る条件付きの主張**である。
- **engine の `bin/` は3ツールへ配られない。** `~/bin` へ配られる8本は `so-compare` / `arena-compare` / `wez` / `wt-pane-issue` / `oe-tree` / `oe-hookfire` / `validate-knowledge` / `knowledge-list` で（`scripts/sync/sync-bin.sh:64`）、**`oe-register` / `oe-send` / `oe-handoff` は入っていない。** 手順が使うもののうち名前で解決できるのは `oe-tree` だけである。
- **`oe-register` は自分の `dirname "$0"` から `../lib/` を source する**（`bin/oe-register:28-29`）。**単体の symlink を PATH に置くだけでは壊れる。**
- **この解決規約は既に `orchestration-toolkit` が持っている。** 「`oe` / `oe-*` は原則 PATH 未登録 → engine の `bin/` のパスで起動する。ただし bin sync の配布対象に入れた verb は例外。**配布対象であることと、その環境に配備済みであることは別である。起動方法を決める前に `command -v <verb>` で確かめること**」（`canonical/skills/orchestration-toolkit/SKILL.md:44`）。**`doc-flow-guardrail:71` も `oe-send` について同じことを書いている。** 一方 `doc-flow-guardrail:127` の `oe-register` は素の呼び方のままである。
- **`oe-register` は `TMUX_PANE` と tmux と jq を必須にし、無ければ落ちる**（`bin/oe-register:57-59`）。**黙っては壊れない。**

## 棄却した案（ゼロベース探索・ゲート1）

### つけかえの工程をどこに書くか

- **`oe-handoff` の `take` / `retire` の出力に足す（コードを変える）。** 実行する人の目の前に出るので、いちばん踏まれやすい。`take` は既に「子へ宛先を伝えていない」を `note_undone` で出しているので、同じ場所に1行増える形になる。**棄却の理由はブリーフが engine のコードを範囲外にしていることだけである。** 効き目ではこちらが上なので、範囲外として surface する。
- **引き継ぎ文書のテンプレートに足す。** 後継が確実に読むのは引き継ぎ文書であって、スキルではない。これも範囲外（`templates/` は engine）なので surface する。
- **`orchestration-toolkit`（ツール軸）または `delegate-task`（操作軸）に手順を書き、`doc-flow-guardrail` からは routing する。** **スキル自身の宣言に照らすといちばん筋が良い案である。** 本スキルは「3軸分離: 本スキル＝文書軸 / `orchestration-toolkit`＝ツール軸 / `delegate-task`＝操作軸」（`SKILL.md:20`）と「持つのは大原則1行と routing 表の2つのみ・枠を薄く安定に保つ」（同 `:18`）を自分で書いており、登記のつけかえは操作軸の手続きである。**それでも棄却するのは、owner が置き場を「board ではなくガードレールのスキルへ」と裁定しているからである**（episode の follow-up 表の1行目）。**代わりに、cold-start へ足す文は最小に保ち、verb の詳細と起動方法は `orchestration-toolkit` へ routing する。**
- **routing 表に行を足す。** 表はゲート 0-6 と委譲操作軸の索引で、`document-format.md` の「ゲート配置」節と 1:1 に対応している。**交代は蒸留フローのゲートではないので、行を足すと 1:1 が崩れる。** 採らない。
- **委譲固定節に足す。** 固定節は子へ貼る文である。つけかえを打つのは統括なので、読み手が違う。採らない。
- **採る案 = ③ cold-start 節に足す。** 127行目が既に `oe-register root` と `oe-register link %N` を扱っているので、同じ節に隣り合わせで置くのが既存の構造に沿う。

### つけかえをいつ打つか

- **`take` のあと、`retire` の前に `--force` 付きで打つ。** つけかえが最後の工程でなくなるので飛ばされにくく、後継が交代の途中で力尽きても子が宙に浮かない。**棄却の理由は2つある。** ひとつは `--force` が corrupt entry の fail-closed も上書きすること（`bin/oe-register:193`）。もうひとつは前任がまだ生きているので、**同じ書き込みが呼ぶ GC が前任の root 登記を掃かないこと**である。**安全に前倒しするには「現在の親が指定した前任と一致するときだけ移す」照合つきの口が要り、それは engine の範囲である**（範囲外として surface する）。
- **採る案 = `retire --execute` のあとに `--force` 無しで打つ。** **代償は飛ばされやすいことなので、不可逆操作の直後に隣接する工程として書き、検算まで手順に含める。**

### 報告の宛先をどう決めるか

- **子が登記から自分の親を引く。** いちばん筋が良いが、公開の口が無い。engine に verb を足す話になるので範囲外。surface する。
- **子が直近に指示を送ってきた相手へ返す。** 実運用ではこれで通っている（`bin/README.md` の `oe-handoff` 節）。ただし**機構が保証しているわけではない**とその README 自身が書いている。単独では採らない。
- **`$PARENT_TMUX_PANE` のままにして、後継が明示的に通知する運用で塞ぐ。** これは現状であり、実物の交代でも通知して初めて塞がった。**ただし固定節の文が「`$PARENT_TMUX_PANE` へ返す」と単独で書いてあるかぎり、通知を受け取っていない子は古い宛先へ送り続ける。**
- **採る案 = 「新しい明示が古い明示を上書きする」という順序で書き、可変節に宛先の欄を作る。** **出所の種類（brief か指示か）ではなく新しさで決める。** 交代の場面では brief（前任が書いた）と直近の指示（後継が送った）がまさに食い違うので、種類で並べると勝者が決まらない。

### 129行目をどう分けるか

- **行ごと消す。** 消すと復旧側の routing（discussion の §4-2 / §4-3 / §5(0) への参照）まで落ちる。episode の follow-up が明示的に禁じている。採らない。
- **「範囲外」を全部取り払う。** 復旧（#355）はいまも範囲外で、`oe-reseat` も未実装のままである。取り払うと嘘になる。採らない。
- **採る案 = 1つの除外文を2文に割る。** 「計画的な交代は本スキルが持つ」を先に置き、「復旧（#355）は範囲外」を後ろに残す。discussion への参照は復旧側に付けたまま動かさない。

## 設計判断

### DJ-1 つけかえは ③ cold-start 節の 127行目の直後に、独立した項として置く

127行目は cold-start の手順4で、登記の口を紹介している。その直後に手順5として「計画的な交代で後継として起きた場合」を足す。**口が在ることと工程として踏むことが別だったのがこの単位の発端なので、別の項に分ける。**

**あわせて 120行目の入口条件を直す。** 現在の入口条件が名乗る経路は「`oe-delegate` で子登記後に自己昇格した」と「spawn を経ず手動起動した」の2つで、**交代の後継はどちらでもない。** `oe-handoff start` は後継のペインを登記の子にせず `PARENT_TMUX_PANE` も渡さない（`bin/oe-handoff:57-58`・`:402`）。**入口条件に後継が入っていなければ、手順5 を足しても後継は「自分の節ではない」と判断して辿り着かない。** 今回の故障が「口は在ったのに読まれなかった」である以上、入口条件のほうが効く。

**これを scope 1（「交代の直後に踏む工程として位置づける」）の一部と解釈した。** 同じ節の中の話であり、位置づけが成立するための条件である。**解釈が違うなら外す**（ゲート3で裁定してほしい）。

**手順5 には「後継は手順4 を打たない」を1行入れる。** `take` が自己登記を済ませているので（`bin/oe-handoff:616-619`）、打てば余計な書き込みになる。

### DJ-2 順序は「`retire --execute` のあとに `--force` 無しで打つ」を正とし、一覧は `retire` の出力から取る

- **`--force` が要らない。** 前任が停止済みなら guard は orphan の引き取りとして素通りする。
- **同じ書き込みで前任の登記も片づく。** 前に打つと前任が生きているので GC が掃かない。
- **一覧は `retire --execute` の出力を正本にする。** `take` の一覧はスナップショットで、下見と実行のあいだに増えた子を取りこぼす。
- **`retire` が閉じずに終わったら、つけかえに進まない。** 前任が生きているので guard に拒否される。**閉じない理由を片づけるのが先である。**

### DJ-3 子が0体でも `oe-register root` をもう一度打つ

`oe-register root` は冪等で、再登記も `oe_reg_record` を通って GC を呼ぶ（`bin/oe-register:158-162` → `lib/delegate-registry.sh:78`）。**「子が0体だと書き込みの契機が無い」で止める必要はない。契機は作れる。** 手順5 に1行入れる。

### DJ-4 検算は「前任の pane が木に現れないこと」と「件数の一致」で見る

**root の本数では見ない。** 前任の登記が GC で消えても、まだつけかえていない子が parent に前任を指しているかぎり、前任は `?` という名前の entry 無し root として木に残る（`bin/oe-tree:641-654` と `:630-640`）。**「`cockpit` の root が1本」は、子が1体も付いていない状態でも真になる。**

### DJ-5 報告の宛先は「新しい明示が古い明示を上書きする」順序で書く

固定節に新しい項「報告の宛先」を 71行目の直前に置き、次の順序を書く。

1. 直近に受け取った「現統括はこの pane だ」という明示。
2. brief の「報告の宛先」。
3. `$PARENT_TMUX_PANE`。

**出所の種類ではなく新しさで並べる。** あわせて次の3つを書く。

- **候補が食い違うときは送らず、統括へ確認する。** brief は前任が書いたものなので、交代の場面では古くなる。
- **送っても返事が来ないときは宛先を疑う。** `oe-send` は生存しない `%N` を exit 1 で弾くので死んだ宛先へ黙って送ることはないが、**pane 番号が再利用されていれば別人へ届き、exit 0 も配送の成功を意味しない**（**ゲート4 で訂正**）。`oe-tree` で自分の親を見て、居なければ生きた統括へ照会する。
- **`oe-report` は `PARENT_TMUX_PANE` を先に読むので、交代のあとは使わない**（`bin/oe-report:53-58`）。

**環境変数は消さず、順序の3番目に既定値として残す**ので、交代が無い通常の委譲は今までどおり動く。

### DJ-6 差し替える文字列はシェル変数に見えない形にする

71行目と 72行目の `"$PARENT_TMUX_PANE"` を `"$REPORT_TARGET"` のような名前へ差し替えると、**誰も設定していないので空に展開され、`oe-send` が `target is required` で exit 2 になる**（`bin/oe-send:60-61`）。71行目はまさに exit code を確かめろと教えている文脈なので、127 と 2 が混ざると分かりにくい。**`<報告先>` のような、シェル変数に見えない差し込み記号を使う。**

### DJ-7 verb の起動方法は書かず、`orchestration-toolkit` へ routing する

手順5 が呼ぶ `oe-register` は3ツールのどこにも配られていない（`scripts/sync/sync-bin.sh:64`）ので、素の名前では hub の作業ディレクトリの外で解決できない。**ただし解決規約は `orchestration-toolkit:44` が既に持っており、そちらは同じ3ツールへ配られている。** 本スキルは薄い枠を宣言しているので、**規約を写さず1行で routing する。**

**127行目の素の `oe-register root` / `oe-register link %N` も同じ穴を持つ。** 初稿では範囲外として surface したが、**ゲート3 の判断3 で「直す」と裁定され、scope に入った。**

### DJ-8 可変の「タスク」節に「報告の宛先」の欄を足す

固定節が「brief が明示した宛先を優先する」と書いても、brief に書く場所が無ければ埋まらない。**欄の説明に「統括がそのとき自分のペインを引いて書く」と添える** — 前の brief から写すと欄だけが古くなるからである。**空欄なら子は `$PARENT_TMUX_PANE` に落ちる**ことも書く。

### DJ-9 規範の適用範囲と、ゲートの検査範囲は別に決める

この単位は規範（スキルの規定）を改訂するので、**それを検査するゲートの範囲にも触れうる。** 2つを同じ作業で決めると一方に引きずられるので、別々に判断した。

- **規範の適用範囲。** 手順5（つけかえ）が効くのは**計画的な交代で後継として起きた統括**だけである。通常の委譲・cold-start の他の経路・子には効かない。報告の宛先の規則（DJ-5）が効くのは**すべての委譲子**で、交代の有無に依らない（交代が無ければ順序の3番目に落ちるだけである）。
- **ゲートの検査範囲は変えない。** routing 表のゲート 0-6 と委譲操作軸の行 S / 行 C は、いずれも母集団を変える必要がない。
  - **交代は蒸留フローのゲートではない。** 表は `document-format.md`「ゲート配置」節と 1:1 の索引なので、行を足すと 1:1 が崩れる。
  - **ゲート3 の baseline は既に固定節を母集団に含んでいる**（「承認した plan / 委譲時の書面〔brief・固定節〕/ ゲート表の版」の3つ）。**固定節に項を1つ足しても、baseline が見る対象は変わらない。** 版が変わるだけである。

## 受け入れの境界（owner が明示した・そのまま書く）

**この単位の受入は、そこで使うコマンドとスクリプトが個々の責務を果たしていることまでで判定する。交代のフローが1回以上通ることを完了条件にしない。** ガードレールが指すコンポーネントは PR #394 で実装済みで、フローの受入は #390 の Step 4-5 / 4-6 で既に1回通っている（そちらが正本）。

判定は次の3つで、**フローを流さずにその場で確かめられる**。

1. 手順が呼ぶコマンドが実在し、`--help` が名乗る責務が手順の記述と一致する。
2. 手順が書く引数と順序が、**実際の口（`--help` と実装）**と一致する。
3. 手順が書く検算が、そのコマンドの出力で実際に取れる。

**読んだ人が「コマンドの責務までで OK としている」と判断できるように、ここに境界を書いた。** 交代をもう一度通すことは求めない。交代は実運用でしか起きないので、待つと単位が閉じない。

**「コマンドとスクリプト」が指すのは `oe-register` / `oe-tree` / `oe-send` / `oe-handoff` の4本である**（この単位はどれも変更しない）。

### 上の3項だけでは足りないので、静的な受入を足す

**設計SO の指摘である。** 上の3項は既存コマンドの存在・引数・出力だけを見るので、**`SKILL.md` を1文字も編集しなくても全部通る。** owner の境界は「どこまで確かめるか」（実運用の交代までは求めない）を決めたものであって、「編集の有無を見なくてよい」という意味ではない。**境界は動かさず、変更そのものを見る項を足す。**

- 検算が「前任の pane が木に現れないこと」と「引き受けた子が自分の下に出ること」で書かれており、root の本数では書かれていない（**ゲート4 で「件数の一致」から変えた** — 後継が自分の子を既に持つ場合に成り立たないため）。
- 入口条件（120行目）に交代の後継が入っている。

**この一覧は着手時点のもので、ゲート4（実装SO と Copilot）の反映で項目が増えた。** 件数をここに書かないのは、同じ数を2箇所に書くと片方が古くなるためである（前の単位が `required` に判定した型である）。**項目と結果の正本は episode の「実装とゲートを通した（2026-09-13）」節である。**
