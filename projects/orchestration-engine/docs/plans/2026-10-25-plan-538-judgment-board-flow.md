# #538 統括ごとに1枚の判断ボードで、owner への問いを受け付けて答えを回収する手順をスキルにする

## 背景

2026-10-24、#466 で owner は「並列で動く作業の判断に迷わないこと（認知負荷を減らすこと）」を第一の目的にして、owner への問いを載せるページの持ち方と手順を決めた（decision の決定1〜26）。統括ごとに1枚の判断ボード（html-one-pager の種別 `board`）を使い続け、問いが届いたら判断の順に当ててボードに載せ、owner の答えを回収して、答えを使う先まで届ける流れである。

いまは統括がその流れを、memory と手作りのスクリプト（master の `tmp/cockpit20-scratch/make_board.py`）で回している。答えの写しは `.oe/answers-*.json` に置かれ、決まった台帳は無い。#466 の子は、回収したあとの判断ボードのデータから2回目の問いのカードを読めず、統括のスクリプトから取り出した（#538 のコメント）。

この plan は #466 の U1 である。流れを新しいスキルに書き、決定を打ち消しうる既存の規則を同じ単位で直す。

## この plan の範囲

やること:

- 新しいスキル `judgment-board-flow` を作る（DJ-1〜DJ-15）。#466 の decision の決定のうち、判断のページと回収に関わるもの（決定1〜20・23〜24 の該当部分）を書く。対応は「#466 の決定との対応」節の表のとおり。
- #466 の decision の「決めていないこと」のうち、この単位に回った4つを決める（DJ-1・DJ-6・DJ-7・DJ-8）。
- 台帳の形を決め、小さな道具 `ledger.py` を足す（DJ-9・DJ-10）。
- 打ち消しうる既存の規則を、直すか直さない理由を書く（「打ち消す側」節の表）。直すのは html-one-pager の SKILL.md と用語集・出力の型・doc-flow-guardrail の SKILL.md・issue-intake の SKILL.md の hub の補足の1行である（DJ-16〜DJ-20）。
- CATALOG に行を足し、この単位の decision を書き、#466 の decision の「決めていないこと」に追補を足す（DJ-21）。

やらないこと:

- 作業の表と4層の文書の列（#539）。判断ボードの「動いている作業」の表の中身と更新の決まりは決めない。
- 出し忘れと取りこぼしを知らせる道具（#540）。台帳を読んで知らせる hook と、子の問いのデータからページのデータを作る verb は作らない。台帳の今の状態をまとめて出す道具も #540 に残す。
- SO のまとめ（#329・#466 の決定21 で保留）。SO のまとめをいつ作るかは決めない。
- 任せた範囲のまとめ（#541）。
- 統括の引き継ぎ文書（作業層）の直し。統括が直す。
- ルール（`canonical/rules/output-format-rule.md` の §9）の直し（DJ-17 に理由）。
- sync・マージ・worktree の掃除・issue の close。

## 設計判断

### DJ-1 新しいスキルを engine の部品にするか、ハーネスに置くか（決めていないこと1・GATE 3 の問い1）

- **推奨: engine の部品にする。ファイルは今の配り方のまま `canonical/skills/judgment-board-flow/` に置き、文書の木は engine の木にする。**
  - スキルの中身は、統括と子の流れ（子の問い・`oe-send` で答えを送る・`oe-confirm` で受け取りを確かめる・作業層 `.oe/` の台帳・計画的な交代）に依る。これは engine の仕組みである（#466 の discussion の 8-2a も「流れとの対応は engine の側の部品として新しいスキルに置く」を推奨し、owner は Q23 で承認した）。
  - ファイルを engine の下に置かないのは、#537 の進め方が「境目を作り、配る手順を engine に持たせてから、最後にファイルを動かす」だからである。今 engine の下に置くと、3つのツールの sync を同時に直すことになり、#537 が避けた形になる。
  - #537 に寄せるために、スキルの文は hub の中のパスに依らない形で書く。`oe-*` は `doc-flow-guardrail` の「verb 解決規約」で呼び、`$REPO/projects/orchestration-engine/bin` の形を書かない（#537 の段2 と同じ向き）。スキルの冒頭の位置づけに「orchestration-engine（統括と子の委譲の仕組み）の部品である」と書く。hub の issue 番号（#537 など）と hub の具体例は、本文でなく末尾の「補足: hub での具体例」の節に置く（issue-intake と同じ形。本文だけで規則が成り立つようにする）。#537 の「engine を名指すスキル」の一覧に足す申し送りは episode の follow-up に置く（#537 へのコメントは統括に委ねる）。
- ほかの案:
  - ハーネスのスキルにし、engine に依る部分を hub の補足の節に寄せる（issue-intake の形）。流れの大事な部分（子へ送って受け取りを確かめる・台帳・交代）が補足に移り、本文が抽象的になる。文書の木もハーネスへ移り、#466 の decision（engine の木）と割れる。
  - ファイルを `projects/orchestration-engine/skills/` に置き、sync を直す。今いちばん engine らしいが、sync の3本を直す範囲の広がりと、#537 の順を先取りする。

### DJ-2 スキルの名前と description

- 名前は `judgment-board-flow` にする（判断ボードの流れ）。ページの形の `html-one-pager` と、ページを使う流れを名前で分ける。
- description には、読み込まれてほしい場面を、渡す側と受け取る側の両方の言い方で並べる（注入された knowledge `01M486Z2N7…`）。
  - 統括の側: 子から問いや報告やゲートの停止が届いたとき、SO が終わって採否を owner に聞くものがあるとき、統括自身が owner に判断や確認を求めるとき、owner が答えた・「全部推奨」と言った・番号を挙げて答えたとき、owner へ依頼や知らせ（値を貼る・画面を開く）を出すとき、答えを子へ渡すとき、統括が交代して判断ボードを引き継ぐとき。
  - 子の側: 委譲された子が、統括や owner に判断を求める問いを書くとき。
- 隣のスキルとの順を description に書く。owner への問いをページに載せるときは html-one-pager より先に読み込む（いつ・どのページに・何を載せるかはこのスキルが決め、ページの形は html-one-pager が決める）。答えを子へ送るときは、`delegate-task` の send の前に読み込む（送ったあとの受け取りの確かめまでがこのスキルの手順である）。
- 発火は「確かめ方」節の表で測る。

### DJ-3 スキルの節の立て方

SKILL.md の節は次の順にする。統括が上から読んで一巡を回せる順で、子が読む節は1つにまとめる。

1. いつ使うか・位置づけ（隣のスキルとの分担。このスキルは engine の部品）
2. 判断ボードの形（統括ごとに1枚・4つの区画・データの置き場・同じ URL）
3. 問いが届いたとき（8段の判断の順・閾値・待たせる・答えを待つあいだ・「追加」の印）
4. 子の問いの書き方（子が読む節）
5. 依頼と知らせ・マージ
6. owner への案内の1行
7. 答えを集めて渡す（6段）
8. 渡す先ごとの確かめ（子・ゲート3 の承認・認識合わせ・統括自身の問い）
9. 台帳（出来事の種類と `ledger.py` の使い方）
10. ページを分けるとき・作り直すとき・取り下げるとき
11. 統括が交代するとき
12. ページの公開と保存先の読み取り（接続）
13. しないこと（会話に選択肢を並べる・対話の選択肢の道具を使う・保存先を読まずに推奨で埋める・子が owner のページを出す）
14. 限界

- 12 の「接続」の節に、ページを公開する操作と保存先を読む操作（Claude Code では Artifact と `ArtifactData`）だけを集める。ほかの節は「公開する」「保存先を読む」とだけ書き、道具の名前を書かない。問いの選り分け・回収・配送と受け取りの確かめ（流れの決まり）と、ページを置く場所への接続を分けておくためである（ゲート1 の代替案1 を一部採った。#537 で engine を独立させるとき、接続だけを差し替えられる）。

### DJ-4 子の問いのファイルの形（決定11）

- **子は、問いを html-one-pager のページのデータ（JSON）として `.oe/question-<issue>-<n>.json` に書く。** 種別は `approve`、状態は `awaiting`、`why` に「なぜいま聞くか」を書き、`source` は `build.py source --git <worktree>` の出力にする。カードは html-one-pager の問いのカードの書き方に従う。そうすると、子は `build.py check` で問いを検証でき、新しい形式を作らずに済む。
- カードの key と表の key（選ぶ表の `key`）は `i<issue>_` で始め（ページ全体で重ねないため・html-one-pager の「判断待ちの束」節と同じ考え）、札（`Q<数字>`）は書かない。表の key に前置きが無いと、2つの子が同じ見本から同じ表の key を作ったとき、判断ボードで E-S3 と E-C7 に止まる（ゲート2 の指摘3）。番号は統括が判断ボードの続きで振る。全体の承認のカード（札 `承認`）は使わず、「この plan で実装に進むか」を問いのカードとして書く（判断ボードには `承認` の札が無いため）。一覧から選ぶ問いは、選ぶ表ごと書いてよい（候補の番号は統括が判断ボードの中で重ならないように振り直す）。
- 認識合わせ（`issue-intake` の 5 で、子が依頼元へ渡す3つの出力）も同じ形にする。題は「#N の認識合わせを、この内容で確定してよいか」、1つ目と2つ目の塊は「何を決めるか」「推奨の中身」、そのあとに3つの出力をそれぞれ自由な題の塊（「この issue でやること」など）で置き、issue の URL を塊の中に書く。
- ゲートで止まるとき（plan の GATE 3 など）も、問いのカードのデータを添える。承認の対象は plan なので、カードの文と plan の GATE 3 節が食い違ったら plan を正とし、統括が照合してカードを直す。
- Markdown の問いのファイルは書かない（決定11 の「Markdown は書かないか、カードのデータから作る」の前者を採る。2つを書くと食い違うため）。
- 統括自身の問い（統括が owner に聞きたいこと）も、同じ形で問いのファイル（`.oe/question-<issue>-<n>.json`。issue の無い問いは `.oe/question-cockpit-<n>.json`）に書く。待たせた問いの中身を、いつも問いのファイルから引けるようにするためである（ゲート1 の指摘4）。
- 統括がカードを判断ボードへ写すときは、次の4つを直す（ゲート1 の指摘5・ゲート2 の指摘3）。子の `source` のリポジトリが判断ボードの送り元と違えば、カードの中の `#N`・`PR #N` を `owner/repo#N` の形に書き直す（html-one-pager の「番号と識別子の書き方」）。候補の番号を振り直すときは、選ぶ表の番号の列・`select` の `recommend`・カードの文の中の `候補<数字>` をまとめて直す。表の key が判断ボードのほかの表と重なるなら直し、`select` の `tables` も同じ名前に直す。札（`Q<数字>`）を判断ボードの続きで振る。選ぶ表は、選び方のカードのある節の直後に置く（html-one-pager の「並び」）。写したあとに `build.py check` を通す。
- 送るときは、パスを報告の宛先へ `oe-send` で1行送り、最後に「待つ」か「続ける」を書く。「待つ」は答えが無いと先へ進めない問い（止まる問い）を表す。今の委譲固定節の「途中経過を送るときは続けるか待つかを書く」を問いにも使う形で、新しい印を作らない。

### DJ-5 統括の判断を足して載せる（決定11 の後半）

- 統括は子の問いを8段の判断の順（DJ-6）に当て、owner に回すものだけを判断ボードに載せる。載せるときは、各カードに自由な題の塊「統括の判断」を足す（置けるのは「ほかの案」の後ろ。無ければ「推奨の中身」の後ろ）。中身は、統括が照合したもの（plan の該当の節・前提にした decision など）と、推奨に同意するかである。
- 統括が子の推奨と違う推奨にするときは、カードの推奨を統括の推奨に変え、「統括の判断」の塊に子の推奨を書く。
- 統括が自分で決めた問い（段2）は、子へ答えを送り、判断ボードの「owner への依頼」の表に知らせの行として出す（決定7 の段2 の「決めたことは知らせる」。#466 の discussion の 1-3 の2）。

### DJ-6 問いが届いたときの判断の順・閾値・待たせる問いの持ち方（決定2・7・10・決めていないこと2・GATE 3 の問い2）

- 8段の判断の順は、決定7 の文のとおりに書く。段5（一覧から選ぶ問い）は、#536 の直しが入ったので「判断ボードのカードとして選ぶ表ごと載せる。量が多い一覧（候補が数十件）だけ別のページにしてよい（DJ-15）」に書き換える。
- 閾値は決定10 のとおりにする（2件たまるか、止まる問いが1件出たら載せる・待たせた問いは次に載せるときに必ず載せる・時間の上限は置かない）。
- **待たせる問いは、ページのデータに入れずに台帳で持つ（推奨）。** 台帳に `asked`（行き先 `held`）として書き、問いのファイルのパスを必ず書く（中身の正本は問いのファイルのままである）。判断ボードのデータのファイルは「最後に出したページ」と「すぐ次に出す直し」だけを持つ。
  - 待たせる理由は2つあり、`asked` の `hold` に書き分ける（ゲート1 の指摘1）。
    - `next_publish`（次の出し直しで載せる）: 届いたときに開いた問いがあった（決定7 の段6 で「そこに足す」に当たる）が、答えを待つあいだなので出し直さなかった問い（決定2）。次の出し直し（回収のあとか、止まる問いが来たとき）で、閾値に関係なく必ず載せる。回収で開いた問いが0件になっても載せる。
    - `threshold`（閾値を待つ）: 届いたときに開いた問いが無く、閾値に届かなかった問い（決定10）。閾値に届いたとき（ほかの問いと合わせて2件か、止まる問いが来たとき）に、待っているものをすべて一緒に載せる。
  - 理由は3つある。待たせる仕組みが閾値と答えを待つあいだで1つになる。owner が見ているページとデータが食い違わないので、owner が言う番号がいつもページの上にある。#540 の道具が「`asked` で `held` のまま出ていない問い」を台帳だけで拾える。
  - ほかの案: ページのデータに足しておき、出し直さない。データと owner が見ているページが食い違い、番号を先に振ると owner の知らない番号ができる。進み具合の直しで出し直すと、待たせた問いが黙って載る。待たせた問いを、台帳とは別の受け付けの列（キュー）のファイルに置く（ゲート1 の代替案3）。待たせる状態の置き場が台帳と別にもう1つでき、決定13 の「専用の台帳を1つ」から外れる。台帳に問いのファイルのパスを必ず書く形で、中身を引けないという同じ穴を塞いだ。
- 出し直すときの決まり: `next_publish` の問いはすべて載せる。開いた問いがあれば、`threshold` の問いも閾値に関係なく載せる（決定7 の段6）。開いた問いが無ければ、`threshold` の問いは閾値に届いたときだけ載せ、届かない問いは「owner への依頼」の表に「待っている問い（次に載せる）」の行として出す（決定10 の「待っていることは判断ボードに出す」）。

### DJ-7 「追加」の印の付け方と外し方（決定6・決めていないこと3・GATE 3 の問い3）

- **付け方: 題の頭に「追加: 」と書く。** 判断ボードの札は `Q<数字>` に限られるので札には書けない。題の頭なら、畳んだカードにも出る。`build.py` を直さずに済む（題の終わりの形の検査 E-Q1 は頭を見ない）。見た目の確かめは、一巡の確かめで作るページで行い、owner には実物の判断ボードで見てもらう（統括の受入の外の確かめ）。
- **外し方（推奨）: 答えを回収したあと、残りの問いを案内する出し直しのときに外す。** 「待つ期間」を、案内を送ってから owner の答えを回収するまでとする。期間の途中に足した問い（止まる問いのときだけ足す・決定2）に印を付け、回収のあとの出し直しで印を外してから案内を送る。案内を送った時点で開いている問いは、すべて印の無い問いになる。#466 の discussion の 13.4 の提案のとおりである。
  - ほかの案: 答えるまで印を残す。次の期間にも「全部推奨」が当たらず、owner は番号を挙げて答え続けることになる。owner が何か答えたら外す。答えた時刻は読んだ証拠にならない（discussion の 1-3 の表）。
- 一括の答え（「全部推奨」など）は、案内の時点の印の無い問いにだけ当てる。**当てる範囲の正本は、台帳の最後の `announced` の `bulk`（key の集合）である。** 題の「追加: 」は owner に見せるための印で、統括は題の文字ではなく `bulk` で範囲を決める（ゲート1 の代替案4 を採った）。出し直す前に、題の印と `bulk` の外の key が一致することを確かめる。`ledger.py collect --via bulk` は、最後の `announced` の `bulk` に無い key を拒む。

### DJ-9 台帳の形と道具（決定13・#538 のコメント・GATE 3 の問い5）

- **推奨: 1行1出来事の JSON（JSON Lines）にし、検証して書き足す小さな道具 `ledger.py` をスキルのフォルダに置く。**
  - 置き場は、統括のワークスペースの根の作業層 `.oe/board-ledger.jsonl`（git の対象外・3日で消えない）。判断ボードのデータは `.oe/board.json` に置く（DJ-11）。
  - `ledger.py` は Python 3.9 以上の標準ライブラリだけで書く（#428 の decision の決定1 と同じ）。サブコマンドは4つにする。
    - `add <台帳> <種類> --data '<JSON>'`: 1件の出来事を、種類ごとの必須の項目と型で検証し、時刻を付けて書き足す。
    - `collect <台帳> --board <判断ボードのデータ> --key <カードの key> --choice <選択肢の key> [--note …] --via <page|conversation|bulk|child_pane> [--words …] [--rows 候補2,候補5]`: 判断ボードのデータからカードの番号・題・推奨の選択肢の名前・「推奨の中身」の塊・選んだ選択肢の名前を引いて、`collected` の出来事を書く。#538 のコメントの「問いの題と推奨の中身も残す」を、手で写さずに満たす。一覧から選ぶカード（`select` のあるカード）では `--rows` を必須にし、選んだ行ごとに番号と行の中身（選ぶ表の番号の列のほかの欄）を書く。表から消したあとも、台帳だけで何を選んだかが分かるようにするためである（ゲート1 の指摘2・html-one-pager の「選んだ行を番号と名前で書く」）。`--via bulk` は、最後の `announced` の `bulk` に無い key を拒む（DJ-7）。
    - `check <台帳>`: すべての行を検証する。
    - `trace <台帳> --key <カードの key>`: その key に触れた出来事を、時刻の順に並べて出す（読むだけ）。途中で止まったときに、問いごとにどの段まで済んだかを見るためである（ゲート1 の指摘3）。
  - 台帳を読んで「出し忘れ・取りこぼし」を知らせる道具と、今の状態をまとめて出す道具は作らない（#540）。`trace` は1つの key の出来事を並べるだけで、判定も知らせもしない。
  - 途中で止まったときに続ける位置は、台帳の最後の1行ではなく、**問いごとの最後の出来事**で決める（決定17。ゲート1 の指摘3）。台帳には別の問いの出来事が挟まるので、最後の1行は途中の問いの位置を表さない（DJ-13 の段6）。
- ほかの案（ゲート1 で足した）: 台帳を、出来事を書き足す道具ではなく、問いごとの状態の移り（受け付けた → 出した → 回収した → 送った → 受け取った）を受け付けて、前の段を満たさない記録を拒む道具にする（ゲート1 の代替案6）。途中で止まったときの続け方を道具が持てるが、今の状態をまとめる道具は #540 の範囲で、#538 で作ると境目を越える。#540 で決めるときの案の1つとして申し送り、#538 では、問い・案内・回収・配送を key でつなぐことと、各出来事の必須の項目を決めるところまでにする。
- ほかの案:
  - 形だけを文で決め、統括が手で JSON を書く。日本語を含む JSON をシェルで書くと崩れやすく（hub では制御バイトが化けた件と、`$var` の直後の全角が化けた件がある）、#540 までは検証が無い。問いの題と推奨の中身も手で写すことになる。
  - Markdown の表にする。#540 の道具が読めない（#466 の discussion の論点4 は「U4 の道具が読める決まった形」を求めている）。
- 決定23（規則を先に作り、自動で動く道具をあとに足す）との関係: `ledger.py` は統括が手で呼ぶ書き込みの道具で、自動で動かない。決定23 が名指した道具（知らせる hook と、ページのデータを作る verb）は #540 に残す。

### DJ-10 台帳の出来事の種類

### DJ-11 判断ボードの形（決定1・3・4・5・20）

- 統括ごとに1枚で、URL を変えずに使い続ける。データのファイルは `.oe/board.json` の1つだけにし、書くのは統括だけにする（#466 の discussion の 13.4「出し直しを1本にする」）。scratchpad に置かない。
- 区画は上から「いま決めること」（判定カードの節・作業ごと）→「owner への依頼」（表）→「動いている作業」（表）→「最近決まったこと」（表）の順にする。html-one-pager の判断ボードは判定カードの節を先、表をあとに置く決まりなので、この順で通る。
- 「最近決まったこと」の表には、直前の回収で決まったものだけを出す（決定4）。表の題に、いつ・どの回収の分かを書く。番号の列は `Q<数字>`・決まったこと・答え（選択肢の名前と、補足の要点）を持つ。
- 回収したあとの正本は、表にあるあいだは表の行、表から消したあとは台帳の `collected` である（決定3）。ページの保存先の答えは正にしない。
- 「動いている作業」の表の中身と更新の決まりは #539 で決める。それまでは統括が今のとおり手で書くが、答えを待つあいだは、この表の変化だけでは出し直さない（決定2）。
- 答えを待つページは、統括ごとに同時に1枚までにする（決定5）。判断ボードがその1枚である。例外は量で分けた一覧のページ（DJ-15）だけである。
- 統括が交代したら、後継は引き継ぎ文書から判断ボードの URL・データのファイル・台帳のパスを取り、**出し直す前に、同じ artifact を読む**（別の会話から同じ artifact に出し直すときは、先に読まないと拒まれる。#466 の discussion の 2.4 節。ゲート1 の指摘7）。読んだページの版の時刻とデータのファイルが合っているかを見てから、同じ URL に出し直す。回収の途中なら、DJ-13 の段6 のとおり問いごとに続ける。

### DJ-12 owner への案内の1行と、出力の型との関係

- 出し直したら、会話に案内を1行で書く。中身は、URL・版の時刻・いま決めることの件数と番号の範囲・そのうち止まっている作業のものの件数・「追加」の件数・待たせている問いの件数・「再読み込みして1つのタブで答える」・「答えたらこの会話に一言（例: 全部推奨・Q43 は別案）」・「補足を書いたら『保存しました』が出てから閉じる」である。
- 問いと選択肢と推奨は会話に書かない。出力の型の「判断を求めるとき」の1文には、会話の外の場所に選択肢と推奨を置いたときの例外を足す（DJ-17）。
- 対話の選択肢の道具（質問のメニュー）は owner への問いに使わない。答える場所が3つ目になるからである（決定1・5 から導いた。#466 の discussion の6節の行）。

### DJ-13 答えを集めて渡す6段（決定14〜18）

決定14 の6段を、判断ボードで使う形（決定1・3 から導いた言い換え）で書く。

1. **対象を決める。** owner の発話が、判断ボードのどの問いへの答えかを決める。質問（「Q43 の意味は」）なら答えて、回収しない。すでに回収した問い（表に移した問いと、表から消えた問い）への発話は訂正として扱い、保存先を読み直さない（決定14）。訂正は次のとおりにする（ゲート2 の指摘4）。`corrected` を書く。問いがまだ「最近決まったこと」の表にあれば、その行の答えを直して出し直す（表にあるあいだは表の行が正本なので、直さないと訂正と食い違う）。表から消えていれば、台帳の `corrected` が正本になる。渡した先へ訂正として送り（`sent` の `kind` は `correction`）、受け取りを確かめる（`received`）。
2. **読む。** 発話の中身（「全部推奨」でも）に関係なく、保存先を毎回読む（`ArtifactData` の `list`）。`read` を書く。
3. **写す。** 問いごとに答えを決める。決め方は、会話で名指しした答え → ページの答え → 一括の答え（`announced` の `bulk` の問いで、ページの答えが無いものだけ）の順である。会話で名指しした答えとページの答えが食い違ったら会話を採り、食い違ったことを回収の1行に書く（決定16）。会話の答えは、どの問いへのどの答えかが一通りに決まるものだけを受け付け、owner の言葉を補足と `words` に残す。決まらなければ未回答のままにし、読み取った内容を1行で返して確かめる。推奨と食い違う一括の答えは、外向きの操作の前に1行で確かめる（決定15）。一覧から選ぶ問いは `build.py check --answers` で選んだ行の数を確かめる（#536 の決定4）。答えの決まった問いごとに `ledger.py collect` を打つ。
4. **表へ移して出し直す。** 答えの決まった問いを、すべて「最近決まったこと」の表へ移す（決定18 の移し忘れ）。表の行は今回の回収の分に入れ替える（決定4）。選ぶ表もページから除く。待たせた問いを DJ-6 のとおり載せ、「追加」の印を外し（DJ-7）、`build.py check` を通して同じ URL に出し直す。`published` を書き、案内の1行を送って `announced` を書く。回収の結果は、案内の前に1行で owner に返す（推奨どおり何件・別の案は何番・未回答は何番・食い違ったものと採った側）。
5. **渡す。** 答えを使う先へ渡す（DJ-14）。値の依頼で受け取った値も、求めた側へ渡す（決定18）。
6. **記録する。** 各段のあとに台帳に書く。途中で止まったら、問いごとに最後の出来事を `ledger.py trace` で見て、その次の段から続ける（決定17）。台帳には別の問いの出来事が挟まるので、台帳の最後の1行では決めない。**記録が無いことを、実行していないことと決めつけない**（ゲート1 の代替案6 の考えを採った）。`collected` のあとの `published` が無いときは、判断ボードを読んで版の時刻と、その問いがまだ開いているかを見る。`sent` が無いときは、送ったかが分からないので、送り直す前に子に照会する。

### DJ-14 渡す先ごとの確かめ（決定17）

- 子の問い: `oe-send` で子へ送る。1行に issue 番号・step・問いの番号と key・答えを入れ、同じ答えを二度受け取っても見分けられるようにする。exit 0 は配送の成功を意味しないので、子の返事か `oe-confirm` の受領印で受け取りを確かめ、`received` を書く。確かめられなければ、送り直す前に子に照会する。
- ゲート3 の承認と、承認のあとの「変更」の再承認: 子へ送る前に、承認の記録と baseline（初回）か entry（張り直し）を書く（`doc-flow-guardrail` の「gate 3 の baseline 記録」）。`recorded`（`approval`）を書いてから送る。
- 認識合わせ: `issue-intake` の 5〜7 のとおり、合図が出たかを決める。合図が出なければ確定版を issue に投稿し、`recorded`（`intake`）を書いて、子へ確定版のコメントの URL を送る。合図が出たら、深掘り中の版を投稿し、owner と深掘りを終えて確定版を投稿してから、確定版の URL を送る。子へ送るのは確定版の URL だけで、深掘り中の版は送らない（子は確定版を受け取るまで待つ。`issue-intake` の 5 の「確定版を投稿してから URL を返してくる」・ゲート2 の指摘3）。深掘りの途中は、子に「深掘り中で、確定版を待ってほしい」と知らせてよい（答えではないので `sent` の `kind` にしない）。
- 統括自身の問い: そのまま作業に戻る。
- owner が子のペインに直接答えたとき: 子が直接受け取ったものとして `received`（`direct`）を書く。統括は自分が受け取った承認として中継し直さない（`implementation-gate-rule` の「見ただけのものは承認ではない」）。ゲート3 なら承認の記録にその経路を書く。

### DJ-15 依頼と知らせ・マージ・ページを分けるとき・作り直すとき・取り下げ（決定8・9・12・19・E7）

- 依頼（画面を開く・値を貼る）と知らせは、カードにせず「owner への依頼」の表に出す。「手番」の語は使わない。値の依頼の値は、関係する問いの補足欄か会話で受け取る（決定8）。
- マージの依頼はページでは追わない。owner が会話で「マージした」と言ったら、統括が origin で確かめる（決定9）。
- 答え方の形ではページを分けない。分けてよいのは量が多い一覧（候補が数十件）だけで、そのページは種別 `pick` で別に作り、判断ボードの「owner への依頼」の表に「別のページで選ぶ」の行とリンクを出す。このページは決定5 の1枚の例外として数え、回収は html-one-pager の「回答済みにして出し直す」で行う（決定12）。作業のまとまりでページを分けるのは、DJ-8 の owner への問いを経たときだけにする。
- 未回答の問いは同じ1枚に残す（決定19）。新しい URL で作り直すのは次の2つのときだけにする（discussion の 13.4・論点4。ゲート2 の指摘1）。1つ目は、開いた問いが0枚で、ページが長くなりすぎたとき（owner の「間が空いているなら新しく作ってよい」）。2つ目は、判断ボードのデータを失って作り直せないとき（保存先を読んで答えを回収してから作り直す）。
- 作り直すときは、次の4つを引き継ぐ。開いた問い（同じ key のまま移し、引き継いだことを「統括の判断」の塊に書く）、回収したがまだ渡し終えていない答え（台帳の問いごとの出来事で `sent` か `received` の無いもの）、受け取っていない値の依頼、問いの番号の続き（次に使う `Q<数字>`。番号は新しいページでも使い直さない）。引き継いだ件数を案内の1行で伝え、台帳の `published` に新しい URL を書く。古い URL には「このページは閉じた。続きは新しいページ」とだけ書いた短いページを出す。
- 問いが要らなくなったら、カードを「最近決まったこと」の表へ「取り下げた」として移し、`withdrawn` を書く。
