# #545 判断ボードの「会話で聞いてよい」例外を、見える条件で決める形にする

## 背景

`judgment-board-flow` は、owner への問いを統括ごとに1枚の判断ボードで受け付ける。「使わないとき・境目」の1つ目は例外で、owner がいまこの会話に居て一緒に考えている対話の中の問いは、判断ボードに載せず会話で1つずつ聞いてよい、としている。この例外に当たるかは、統括がその場で判断する。

2026-10-27、別のリポジトリの統括が、生きた子が3体いる状態で「子を起こしてよいか」をこの例外に当たると判断し、会話で聞いた。そのあと約30分で子の報告や CI の知らせが6件以上会話に割り込み、統括は返事のたびに同じ問いを書き直して5回繰り返した。owner は「流れると上を見る必要がある」「子の返しは制御できない」と指摘した（#545）。子がいると、会話が流れるかどうかを統括も owner も決められない。「一緒に考えている」という判断は、した時点では正しくても、あとで崩れる。統括は崩れたことに気づかないまま例外を使い続けた。

例外は #466 の decision には無い。#538 の plan の DJ-20 で、`question-driven-design`（推奨を添えて会話で1つずつ聞く）が判断ボードと答える場所を争うと設計SO が指摘したのを受けて入り、#538 の decision の決定7（Q47）の承認に含まれた。

## この plan の範囲

やること:

- 例外を使ってよい条件と、例外を使った問いを判断ボードへ移す条件を、外から見えるもの（`oe-tree` の子の数・会話に残す始まりの1行・issue の深掘り中の版・入力の出どころの印）で書く（DJ-1〜DJ-6）。
- 移したことを台帳に残すかを決め、残すなら `ledger.py` とテストを直す（DJ-7）。
- 決めた理由の置き場を決める（DJ-8）。
- スキルの直す節を決める（DJ-9）。
- 打ち消す側を探し、直すか直さない理由を書く（「打ち消す側」節の表）。

やらないこと:

- 判断ボードの作業の表と長くなったときの分け方（#539）、出し忘れを知らせる道具（#540）、任せた範囲のまとめ（#541）。
- 出力の型 `canonical/output-styles/readable-conversation.md` とルール `canonical/rules/output-format-rule.md` の直し（直す必要が無い理由は「打ち消す側」の R8・R9）。
- 統括の引き継ぎ文書（作業層）の直し。統括が直す。
- sync・マージ・worktree の掃除・issue の close。

## 設計判断

### DJ-1 案1と案2の採否と組み合わせ（GATE 3 の問い1）

両方を採り、役目を分ける。案1 を「会話で聞いてよいか」の入口の条件に、案2 を広げたものを「会話で聞いた問いを判断ボードへ移す」出口の条件にする。

- **入口**: 会話で聞いてよいのは、次の (a) か (b) に当たる問いだけである。どちらにも当たらなければ、判断ボードの流れ（2.1 の判断の順）に当てる。
  - (a) 統括の下に生きた子が1体もいない（`oe-tree` で、自分を root とする木に `alive` の子が無い）。
  - (b) owner が自分の言葉で始めた問答の中の問いである。当たるのは次の2つだけである。
    - 認識合わせの深掘り: owner の応答で深掘りの合図が出て、`issue-intake` の 6 のとおり深掘り中の版（`issue-intake:pending`）を issue に投稿したあと、確定版を投稿するまでの問答。
    - 設計の相談: owner が会話で、自分の言葉で設計を一緒に考えることを求めた（「相談したい」「一緒に考えたい」など）あとの問答。
    - 始めるときは、会話に1行「ここから <何> を会話で進める（owner の『<owner の言葉>』による）」と書き、終えるときに1行「<何> の問答を終えた」と書く。始まりの1行が無い問答は (b) に当たらない。
    - 問答の中の問いとは、その問答の対象（深掘りなら issue の認識、相談なら相談された設計）についての問いだけである。作業を進めるための確認や許可（「子を起こしてよいか」「マージしてよいか」「どちらを先に進めるか」）は、問答の途中でも (b) に当たらない（ゲート2 の指摘・中）。
    - 終わりは、問答の結果を行き先（深掘りなら確定版の投稿、相談なら plan などの文書）に書いたとき、または owner が終えると言ったときである。そのとき終わりの1行を書く。
- **出口**: 会話で聞いた問いのあと、次に届いた入力が「owner の発言で、その問いに答えるか、その問いについて尋ねるもの」でなければ、その場で判断ボードへ移す。子の報告・ツールの知らせ（CI の知らせを含む）・owner の別の話題（「その前にこれを整理したい」を含む）は、どれも移すきっかけになる。owner が問いについて尋ねて統括が答えたあとも、問いの答えが来るまでは、届く入力ごとにこの条件を当て続ける（ゲート2 の指摘・中）。
- **会話で答えを待つ問いは、同時に1つまでにする。** どの問いを移すかが一通りに決まるようにするためである。2つ目を聞きたくなったら、1つ目の答えを受けてから聞くか、判断ボードに載せる。

案1 だけにしない理由: 子のいる統括では、認識合わせの深掘りと設計の相談まで判断ボードの往復になる。#538 で設計SO が見つけた `question-driven-design`（会話で1つずつ聞く手順）との食い違いが戻ってくる。案2 だけにしない理由: 2026-10-27 の出来事は、子が3体いて割り込みが来ることが聞く前から見えていた。入口で止めれば、最初の1回も会話に書かずに済む。

出口は案2（owner の次の発言で見る）を「次に届いた入力」に広げたものである。案2 だけでは、owner が黙って知らせだけが続くとき、移るきっかけが来ない（確定版の［別モデル］の1つ目）。

入口の (b) を「どのスキルの手順を動かしているか」で決める初稿の形は、ゲート1 の指摘（高）で、統括の解釈に戻ると分かった（「子を起こしてよいか」も設計の相談に分類できる）。始まりを owner の言葉と、会話に残す1行と、issue の深掘り中の版で見える形にした。初稿にあった `issue-intake` の 5 の提示（深掘りの前の1往復）は (b) から外した。子が生きていれば判断ボードに載せ、`judgment-board-flow` の8節「認識合わせ」がすでに判断ボードの答えを確定版へ渡す流れを持つ。

### DJ-2 深掘りと設計の相談の途中で割り込みが来たとき（ゲート1 の指摘・GATE 3 の問い2）

(b) の問答にも出口を当てる（割り込みで、待っている1問を判断ボードへ移す）。問答そのものは終わらせない。owner が次に会話で発言したら、問答の次の問いをまた会話で聞いてよい（始まりの1行はそのまま有効で、終わりの1行を書くまで続く）。移した1問は、判断ボードで答えるか、会話で番号を挙げて答えてもらう。

- 理由: 「子の返しは制御できない」（owner）ので、割り込みを止めて問答を守る手段がスキルの文の中に無い。割り込みを受けても会話で待ち続けると、2026-10-27 と同じく問いが流れて書き直しが起きる。
- 退けた案（割り込みから問答を守る）: (b) の問答のあいだは、割り込みに1行の受け取りだけを返して中身を扱わず、問答を終えてから扱う。待つ1問は流れにくくなるが、止まる子の問いが問答のあいだ止まり続ける。owner が問答の途中で居なくなると、割り込みが積もっても移るきっかけが来ない。受け取りの1行と道具の表示でも、問いは少しずつ上へ流れる。
- 範囲の外として申し送る案（ゲート1 の代替案）: 問答だけを受け持つ別のセッションに分ける案と、子の報告や知らせを会話へ直接流さず受信箱に集めて統括が取りに行く案である。どちらも報告の届け方を変える engine の仕組みの話で、この issue の範囲（スキルの文）を越える。episode の follow-up として統括へ申し送る。

### DJ-3 owner の発言の見分け方（確定版の「要ること」1つ目）

出口は「次に届いた入力が、owner の発言でその問いに答えるか尋ねるものか」だけを見る。見分けが要るのは、届いた入力を owner の答えとして受け取ってよいかのときだけである。

- **owner の答えとして受け取らない入力**:
  - 末尾に ` [oe:<26文字>]` の印がある1行（`oe-send` が送った1行。子の報告・統括どうしの連絡）。
  - 子の報告や問いのファイルのパス（`.oe/report-<issue>.md`・`.oe/question-<issue>-<n>.json` など）を知らせる1行。印を外して送られた子の報告を拾うためである。
  - ツールの知らせ（バックグラウンドの作業の完了の知らせ・監視の知らせ・hook の出力）。CI の知らせはここに入る。
- **迷ったら答えとして受け取らず、移す。** 見分け違いの向きを、問いが判断ボードへ移る側に倒す。owner の答えを割り込みと読み違えても、問いが判断ボードへ移るだけで、owner はそこで答えられる。
- 印の無い子の入力を owner の発言と読み違えても、その入力がたまたま問いの答えに見えるもの（「推奨で進めてよい」など）でなければ、出口で移る（ゲート1 の指摘（高）を、出口の条件を1つにまとめることで受けた）。答えに見える印の無い子の入力は見分けられず、owner の答えとして受け取りうる。これはスキルの限界の節に書く（ゲート2 の指摘・中）。

### DJ-4 owner が黙って知らせだけが続くとき（確定版の［別モデル］1つ目）

別の条件は置かない。出口が最初の1件の知らせで発火する。時間で移す条件（N 分答えが無ければ移す）は置かない。owner が会話に居て考えている最中に移すことになり、居ないときは割り込みが来るまで問いが会話の最下部に残っていて流れていないからである。

### DJ-5 会話で聞いたあとに子を起こしたとき（確定版の［別モデル］2つ目）

子を起こしたこと自体では移さない。入口の条件は聞くときに当てる。子を起こすと、子の最初の出力（起動の確認・報告）が届いた時点で出口が発火して移る。起こすことを移すきっかけにすると、子を起こす手順（`delegate-task`）が読まれる時点にも規則を置く必要があり、発火する場所が増える（注入した knowledge item `01M5PKRS5MGHNHR2JS5C1TSPS9`）。出口だけで同じ結果になるので、場所を増やさない。入口（子の数で見る）と非対称になるのはこの理由による。

### DJ-6 移すときの手順

- 移す問いは、2.1 の判断の順に当て直さず、問いのカードにして判断ボードへ載せる。会話で聞いた時点で、統括は owner に答えてもらうと決めていたからである（段2 の「統括が決める」や段4 の「依頼の表」に回すと、owner に見せた問いが見えないところで決まるか、カードでなくなる）。問いのファイル（`.oe/question-cockpit-<n>.json`・4節の形）に書き、台帳に `asked` を書く（`route` は `board`・`stops` は実際に止まるかどうか）。初稿は、移す問いにも2.1 の順を当てる形と `route` を `board` に決める形が食い違っていた（ゲート2 の指摘・高）。
- **移した問いは、件数や止まるかに関係なく、すぐに判断ボードへ載せて出し直し、案内を送る。** 会話で聞いた時点で owner に見せた問いを、次の出し直しまで会話にも判断ボードにも見えない状態にしないためである。答えを待つ期間なら題に「追加: 」を付ける（2.3・2.5 のまま）。初稿は「止まる問いとして扱う」だったが、ゲート1 の指摘（中）で、止まるかどうかと混ぜない形にした。
- 会話では問いを書き直さない。案内の1行（6節）に「会話で聞いた問いを判断ボードへ移した（Q<数字>）」を足す。会話に書くのは、この案内の1行の1回だけである。
- 移したあとの割り込みでは、移した問いのために出し直さない（ふつうの待つ期間の決まりに戻る）。
- この「すぐ載せる」は、2.2 の閾値・2.3 の「止まる問いが届いたときだけ出し直す」・2.4 の出し直すときに載せる問いの例外である。3つの節それぞれに、移す問いの例外を書く（ゲート2 の指摘・高。2.1 の前置きだけでは、実際に動く節に逆の指示が残る）。
- 移したあとに owner が会話でその問いに答えたら、7節の「会話で、その問いを名指しした答え」として回収する（今のまま）。移した問いを、また会話へ戻すことはしない。

### DJ-6b 回収の途中の確かめが割り込まれたとき（ゲート2 の指摘・中）

7節の段3 の「読み取った内容を1行で返して確かめる」と「推奨と食い違う一括の答えを1行で確かめる」と「選んだ行の上限を超えたら確かめる」も、会話で答えを待つ問いである。ただし、確かめる問いのカードはもう判断ボードにある。確かめの1行のあとに、owner の答え以外の入力が届いたら、会話で確かめを書き直さず、その問いを未回答のカードとして判断ボードに残し、次の案内の1行で「Q<数字> は確かめが要るので未回答のまま」と書く。外へ向けた操作（子へ送る・issue に書く）は、確かめが済むまで行わない（今のまま）。

### DJ-7 台帳に残すか（確定版の「要ること」2つ目・GATE 3 の問い3）

会話で聞いたこと自体は台帳に書かない。移したときに書く `asked`（`route` は `board`）に、任意の項目 `moved_from`（値は `conversation` だけ）を足し、`ledger.py` が値と組み合わせを検証する（`moved_from` があるなら `route` は `board`）。

- 理由: `asked` の `file` は必須で、会話で聞く問いには問いのファイルが無い。会話で聞くたびに書く形（`route` に `conversation` を足す）にすると、`route` が `conversation` のときだけ `file` を任意にする例外が要り（`held` の問いには必須のまま検証できる）、深掘りの問いの1つずつに key を振って書く手間が増える。移したときだけ書く推奨の利点は、書く手間が移した回数分だけで済み、例外が流れた回数が台帳で数えられて #540 の道具が読めることである。代わりに、会話で待っている問いの再開や、会話で答えた問いの確かめは台帳からはできない（ゲート2 の指摘・中で、初稿の「`held` の検証が弱まる」という理由を直した）。
- ゲート1 の指摘（高）は、会話で待っている問いに識別も状態も無いと、どれを移すか・移したか・答えたかを確かめられない、だった。どれを移すかは、会話で待つ問いを同時に1つまでにして一通りに決めた（DJ-1）。答えたかどうかは、問答の行き先（確定版・plan）に残る今の決まりで受ける。会話で聞くたびに台帳に書く案は、GATE 3 の問い3 のほかの案として owner に見せる。
