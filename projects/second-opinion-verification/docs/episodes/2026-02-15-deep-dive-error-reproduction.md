# エラー再現経路の自律的特定 — 3エージェント深掘り検証

## 概要

PHP 8.1 の float→int deprecation を対象に、3エージェント（Cursor Agent / Claude Code / Codex CLI）がロール分担でエラー再現経路を特定し、Playwright MCP でステージング上のブラウザ操作を通じてエラー発火 → 修正後の非発火を確認した。

**核心の問い**: AIは、エラーが発火するUIフロー/APIフローを自律的に特定し、ステージングで再現できるか？

**結論: YES。** 計画策定（セカンドオピニオン4回）を含めて1セッションで完了。

---

## 検証結果サマリ

| 項目 | 結果 |
|------|------|
| 再現経路の特定 | 成功（フロントエンド → API → バックエンドの一気通貫） |
| ステージングでの発火確認（修正前） | 成功（Sentry に2件の新規イベント） |
| 修正後の非発火確認 | 成功（同一操作で新規イベント 0件） |
| 再現手順 | 3ステップ（ページアクセス → UI操作 → 自動発火） |
| 再現の再現性 | ページロード時に自動発火するため確実 |

### 深度レベル到達度

| Level | 定義 | 到達? |
|-------|------|:-----:|
| L1: コード表面 | エラー行と直接原因の特定 | 済 |
| L2: データ構造 | テーブル・カラムの特定 | 済 |
| L3: データ生成元 | フロントエンド→APIの経路特定 | 済 |
| L4: 再現条件 | 具体的手順でステージング発火確認 | 済 |
| L5: 根本原因+構造的修正 | スコープ外（意図的に除外） | - |

L5をスコープ外とした判断: 根本原因分析と再現経路特定を混ぜるとファクトがブレる。今回は「AIが自律的にエラー再現フローを辿れるか」に集中した。

## ロール設計（案B: 事実収集 → 仮説生成 → 仮説検証）

### 採用した設計

```
Cursor Agent: 事実収集者（Facts Collector）+ オーケストレーター
  - Sentry API でイベントデータ取得
  - Playwright MCP でステージング操作
  - 両エージェントの出力を統合

Claude Code (Opus 4.6): 仮説生成 + 一次検証者
  - facts.md から再現経路仮説を生成（4仮説）
  - 自ら一次検証し、矛盾を除去

Codex CLI (GPT-5.3): 二次検証 + 対立仮説探索者
  - 独立ミニ探索（アンカリング防止）
  - Claude Code の仮説をコードレベルで検証
  - 代替経路を独立に発見
```

### 設計の経緯

- 初期案（本リポジトリのキックオフ計画）: 同一プロンプト3並行
- セカンドオピニオン v1 で Claude Code / Codex CLI 双方が「役割分担型」を推奨
- v2 で具体的なロール設計を議論、v3/v4 で3者合意に到達
- 計4回のセカンドオピニオンで計画を固めてから実行

### ロール設計の評価

| エージェント | 役割 | 評価 |
|---|---|---|
| Claude Code | 仮説生成 | 4仮説を生成、H1が最終採用。フロントエンド→バックエンドの完全経路をレビュー段階で特定 |
| Codex CLI | 仮説検証 | H1をWEAKENED（データ出所の断定が根拠不足）、H4をREFUTED。代替トリガー経路を独立に発見 |
| Cursor Agent | 統括+実操作 | facts.md 作成、MCP Browser でステージング検証、最終再現手順の確定 |

各エージェントの特性を活かした分担:
- **Claude Code**: アーキテクチャ・設計レベルの構造的推論が強い → 仮説生成に適合
- **Codex CLI**: コード解析・実装レベルの裏取りが強い → 仮説検証に適合
- **Cursor Agent**: Sentry + MCP Browser + 対話 → 実データの事実確定 + オーケストレーション

## 実行タイムライン

### Phase 0: 環境準備

- Sentry API: 接続成功
- Playwright MCP: Cursor標準ブラウザツールとの競合を解決後、user-playwright で接続成功
- CLI ツール: so-compare.sh / claude-safe / codex exec 全て動作確認済み

### Phase 1: 事実収集（Cursor Agent）

- **Sentry データ**: request_params 全パラメータ取得 → 3つのコードパスが1つに絞れた（最大の成果）
- **バックエンド**: ルーティング → コントローラーメソッドの発火行を確認
- **フロントエンド**: ページコンポーネント → API呼び出し関数 → GET エンドポイント の経路を特定
- **facts.md**: 品質ゲート全5項目クリア（request_params, survey_type, フロントエンド判別, コードスニペット, 事実/解釈分離）

### Phase 2: 逐次ロール実行

#### Round 1: Claude Code 仮説生成（約186秒）

4仮説を生成:
- **H1 (HIGH)**: 基本経路（ページアクセス → UI操作 → API自動呼出）→ 最終採用
- **H2 (MEDIUM)**: 別のUI操作トリガー → H1のバリエーションとして統合
- **H3 (MEDIUM)**: 別のパラメータ変更トリガー → H1のバリエーションとして統合
- **H4 (LOW)**: 別ページからの経路 → 即座に自己棄却

#### Round 2: Codex CLI 仮説検証（約804秒）

- 独立探索でH1相当の経路を確認
- H1: WEAKENED（経路は正しいがデータ出所の断定が根拠不足）
- H4: REFUTED（コード上で排他確認）
- 代替経路: 別パラメータ変更でも同一APIが呼ばれることを発見

#### Round 3: Cursor Agent 統合

- H1が唯一の再現経路であり、H2/H3/代替は全て H1 の「トリガーバリエーション」
- 最終再現手順を3ステップに確定

### Phase 3: ステージング検証

#### 修正前

1. Playwright MCP でステージングにログイン
2. 対象ページにアクセス
3. 特定のUI操作を実行
4. **結果**: Sentry に2件の新規イベント発火

#### 修正後

1. fix ブランチを `gh release create` でステージングにデプロイ
2. 同一操作を実行
3. **結果**: Sentry に新規イベント 0件。ページ正常表示

## 発見と教訓

### 1. ロール分担はマルチエージェントの肝

- 同一プロンプト3並行では「同じ盲点を3回繰り返す」リスクがある
- 「何を渡さないか」が役割を定義する
- Claude Code / Codex CLI 自身がこの設計を推奨した点が興味深い

### 2. facts.md の品質がフロー全体を律速する

- Sentry の `request_params` が取得できた時点で、複数コードパスが1つに絞れた
- 品質ゲート（5項目チェックリスト）は有効に機能した
- 事実と解釈の物理的分離は、CLIエージェントへのアンカリング防止に効果的

### 3. セカンドオピニオンの反復が計画品質を上げた

- 4回のセカンドオピニオンで計画を磨いた（v1: 方向性、v2: ロール設計、v3: 合意、v4: Go/No-Go）
- 各AIが自身の能力を自己評価し、最適な役割分担を提案できた
- 「しつこいくらいに確認する仕組み」が計画の抜け漏れを防いだ

### 4. Playwright MCP でブラウザ自動化が実現可能

- ログイン → 画面遷移 → UI操作 → Sentry確認の一連のフローをAIが自律実行できた
- Cursor 標準ブラウザツール（cursor-ide-browser）との競合に注意が必要
- SPA 特有の問題（オーバーレイ等）は JavaScript 直接実行で回避可能

### 5. gh CLI でのリリース作成が実用的

- `gh release create` でブランチ指定デプロイが可能
- GUI 操作なしでステージングデプロイを完結できた

## 再利用可能なテンプレート

### facts.md テンプレート

事実/解釈を物理的に分離した構造化テンプレート。主要セクション:

1. 観測事実（Observations）— confirmed/inferred/unknown の confidence 付き
2. 解釈・仮説（Interpretations）— 事実セクションとは明確に分離
3. 再現に必要なデータ条件（Preconditions）
4. 未確定事項（Unknowns）
5. 否定済み経路（Excluded Paths）
6. 品質ゲートチェックリスト + 特定不能出口

### ロール別プロンプト設計

- **Claude Code 向け**: 思考順序指定 + ネガティブ制約 + 最低3仮説 + 棄却条件必須
- **Codex CLI 向け**: 独立ミニ探索 → 仮説検証 + 出力スキーマ固定 + inferred 明示ルール

### ステージング検証手順

1. Sentry ベースライン記録（操作前のイベント数）
2. Playwright MCP でブラウザ操作（再現手順実行）
3. Sentry で新規イベント有無を確認
4. 修正デプロイ後、同一操作で非発火確認
