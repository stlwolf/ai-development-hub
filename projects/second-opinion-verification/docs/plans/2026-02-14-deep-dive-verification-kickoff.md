# エラーユースケース深掘り検証 キックオフ

## 1. 検証の目的

### 直接の目的

特定のランタイムエラーの**発生フローを完全にトレースする**。対症療法的な修正は完了済みの前提で、「なぜその値がそこに存在するか」をコード・データ・ランタイムの各レイヤーから突き止める。

### 裏テーマ（再利用性）

> AIにアプリの一気通貫のデータフローを理解させるには、最小限どういうコンテキストをどういう形式で渡せばいいのか

今回の1件で具体的に炙り出し、次のエラー対応で同じ深度に到達するための「検証の型」を抽出する。

---

## 2. 深度レベル定義

3エージェントの分析結果を比較するための共通尺度。

### Level 1: コード表面

- エラーメッセージとスタックトレースの読み取りのみ
- **到達基準**: エラー行と直接原因を特定できている

### Level 2: データ構造

- DBスキーマやデータ格納構造を把握している
- **到達基準**: 問題の変数に入る値がどのテーブル・カラムから来るか特定できている

### Level 3: データ生成元

- 入力フォーム → APIリクエスト → バリデーション → DB保存 のパスを追跡
- **到達基準**: 問題の値がDBに入るまでの経路を特定できている

### Level 4: 再現条件

- 具体的なユースケース（操作手順 + データ条件）を提示
- ステージングで実際に再現可能な手順がある
- **到達基準**: 再現手順を実行してエラーが発火する（または修正後に発火しない）

### Level 5: 根本原因 + 構造的修正案

- 対症療法と根本修正の両方を示し、トレードオフを説明できている
- **到達基準**: 入力時のバリデーション追加等、根本的な修正を提案できている

### 評価ルール

- 各エージェントに Level を付与する（例: Codex=L3, Claude=L2, Cursor=L4）
- 「部分的に到達」もあり得る（例: L3-）
- 到達 Level だけでなく「なぜそこで止まったか」も記録する

---

## 3. ロール設計（案B: 逐次専門化）

初期案は「同一プロンプト3並行」だったが、セカンドオピニオンでClaude Code / Codex CLI 双方が「役割分担型」を推奨。以下に変更。

### 役割分担

| エージェント | 手段 | 役割 |
|---|---|---|
| **Cursor Agent** | MCP Browser + コード分析 + 統括 | 事実収集（Sentry API, ステージング操作）、全体統括 |
| **Claude Code** (claude-safe) | コードベース分析 | 仮説生成 + 一次検証（最低3仮説、棄却条件付き） |
| **Codex CLI** (codex exec) | コードベース分析 | 独立ミニ探索 → 仮説二次検証 + 対立仮説探索 |

各エージェントの特性:
- **Claude Code**: アーキテクチャ・設計レベルの構造的推論が強い → 仮説生成
- **Codex CLI**: コード解析・実装レベルの裏取りが強い → 仮説検証
- **Cursor Agent**: Sentry + MCP Browser + 対話 → 実データの事実確定 + オーケストレーション

## 4. 検証手順

### Phase 0: 環境準備

- Sentry API 接続確認 + ベースライン記録
- ステージング MCP Browser 接続確認
- so-compare.sh / claude-safe / codex exec 動作確認

### Phase 1: 事実収集（Cursor Agent）

```
1. Sentry API からイベント詳細を取得
   - 実際の変数値
   - request_params（最重要: コードパスを絞るキー）
   - スタックトレースのローカル変数
   - 発生パターン

2. コードの逆向きトレース
   - バックエンド: ルーティング → コントローラー → 発火行
   - フロントエンド: ページコンポーネント → API呼び出し関数

3. 収集した情報を facts.md にまとめる
```

**品質ゲート（Phase 2 に進む前に確認）:**

- request_params が取得できているか
- コードパスが絞れているか
- 発火元のフロントエンド判別ができているか
- 最低1つのコードスニペットが埋め込まれているか
- 事実と解釈が分離されているか

**「特定不能」出口**: 確定できない項目は候補を列挙した上で Phase 2 に進む。仮説生成時に候補ごとに分岐させる。

### Phase 2: 逐次ロール実行

#### Round 1: Claude Code 仮説生成

```bash
claude-safe -p "$(cat tmp/hypothesis-prompt.txt)" --output-format text \
  > tmp/round1-hypothesis.txt 2>&1
```

プロンプト設計原則:
- コードスニペットを直接埋め込む
- 思考順序を明示的に指定
- ネガティブ制約（スコープ外事項）を明記
- 最低3仮説 + 棄却条件を必須化

出力フォーマット（各仮説に必須）:
- 画面・URL、操作手順、APIコール、コードパス
- 証拠（確定/推定/未確認に分類）
- 棄却条件
- 検証依頼事項

#### Round 2: Codex CLI 仮説検証

```bash
codex exec -s read-only "$(cat tmp/validator-prompt.txt)" \
  > tmp/round2-validation.txt 2>&1
```

プロンプト設計原則:
- Round 2 冒頭に独立ミニ探索を含める（アンカリング防止）
- 出力スキーマを固定（verdict: CONFIRMED/WEAKENED/REFUTED）
- 「推測は inferred 明示、証拠なき断定禁止」
- 代替経路の独立探索を許可

#### Round 3: Cursor Agent 統合

- Round 1 + Round 2 の結果を突き合わせ
- Sentry 実データで裏取り
- MCP Browser でステージングの画面構成と照合
- 最終再現手順書を作成

### Phase 3: ステージング検証

#### Cursor Agent の MCP ブラウザ操作

```
1. ステージング環境にログイン（Playwright MCP）
2. エラー発生に関連する画面に遷移
3. コード分析で特定された操作を実行
4. Sentry API でエラー発火の有無を確認
```

到達レベルに応じた検証深度:
- L2以下: コード分析結果をもとにデータ構造を確認
- L3以上: 特定されたデータ生成経路をステージング + MCP Browser で確認
- L4: 再現手順をステージングで実行し、Sentry で発火を確認
- L4+修正済み: 修正コードで同手順を実行し、発火しないことを確認

### 複数ラウンドの想定

1回で Level 4-5 に到達する可能性は低い:
- **ラウンド1**: コードベース分析 + 初回ステージング操作 → Level 2-3 目標
- **ラウンド2**: 足りなかった情報を補って再分析 → Level 3-4 目標
- **ラウンド3+**: 必要に応じて

各ラウンドで「何の情報が足りなくて止まったか」を記録する。

## 5. 共通プロンプトテンプレート

`{{変数}}` を実データで埋めて使用する。

```markdown
# エラー発生フロー深掘り分析

## 対象エラー

- エラー: {{ERROR_MESSAGE}}
- 発生箇所: {{FILE_PATH}}::{{METHOD_NAME}}() Line {{LINE_NUMBER}}
- 修正: {{FIX_DESCRIPTION}}（対症療法として完了済み）
- 発生回数: {{COUNT}}回

## Sentry イベントデータ

{{SENTRY_EVENT_DATA}}

## 分析依頼

以下の問いに、コードとデータの両面から可能な限り深くトレースしてください。

1. **データの出所**: 問題の変数にこの値が入る経路は何か
2. **値が生じる原因**: なぜこの値は期待される型ではないのか
3. **再現条件**: 修正前の状態で、どういう操作手順でこのエラーを再現できるか
4. **業務影響**: 修正による型変換で、業務ロジック上の問題は生じないか
5. **根本修正案**: 対症療法ではない根本的な修正方法

## コンテキスト

### 対象コード

{{CODE_SNIPPET}}

### 関連テーブル・スキーマ

{{SCHEMA_INFO}}

### 補足情報

{{ADDITIONAL_CONTEXT}}
```

## 7. 成功基準

- [ ] エラーを発火させるUIフロー + 発火データ条件が特定できる

- [ ] 再現の再現性: 同じ手順で確実に発火する
- [ ] 最小再現手順: 余分なステップを削ぎ落とした最小の手順
- [ ] ロール設計が機能したか、改善すべき点が明確になる
